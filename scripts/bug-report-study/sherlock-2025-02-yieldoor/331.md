# Attacker will manipulate TWAP prices to steal funds from the protocol

## Summary
The inadequate price manipulation protection in the Leverager contract will cause significant financial losses for the lending pools as attackers will manipulate Uniswap V3 pool prices before opening leveraged positions with artificially inflated collateral values.

## Root Cause
In [Leverager.sol#L105-L129](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L105-L129) the `openLeveragedPosition` function uses TWAP prices from Uniswap V3 to value positions, but the check is insufficient to prevent manipulation:

```solidity
uint256 price = IVault(lp.vault).twapPrice();
require(IVault(lp.vault).checkPoolActivity(), "market too volatile");
```

The contract doesn't adequately protect against deliberate price manipulation, as it only verifies that market conditions aren't "too volatile" without comparing TWAP to external oracles or current spot prices.

## Internal Pre-conditions
1. The `leverageEnabled` parameter for the vault must be set to `true`
2. Users must be able to call `openLeveragedPosition` function in the Leverager contract
3. The protocol must rely on TWAP prices from Uniswap V3 for position valuation

## External Pre-conditions
1. A Uniswap V3 pool with sufficient manipulation potential must exist for the token pair
2. The attacker must have access to sufficient capital (potentially via flash loans) to influence TWAP
3. The pool must not have extremely high liquidity that would prevent TWAP manipulation

## Attack Path
1. Attacker prepares flash loans to acquire substantial liquidity
2. Attacker executes a series of trades in the Uniswap V3 pool to manipulate the TWAP price in their favor
3. Attacker calls `openLeveragedPosition` using the manipulated price, creating a position with artificially high collateral value
4. Attacker borrows the maximum amount allowed based on this inflated collateral
5. Attacker extracts value by never repaying the debt or immediately withdrawing portions of the position
6. When prices return to normal, the position becomes underwater but the attacker has already profited

## Impact
The lending pools suffer a direct loss of funds equivalent to the difference between the borrowed amount and the actual collateral value after price normalization. This could be a significant percentage of the total pool value if executed at scale. The attack could drain substantial liquidity from the protocol, leading to insolvency of specific lending pools.

## Mitigation
Implement cross-validation with external price oracles:

```solidity
function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {
    // ... existing code ...
    
    uint256 price = IVault(lp.vault).twapPrice();
    require(IVault(lp.vault).checkPoolActivity(), "market too volatile");
    
    // Add cross-validation with external price oracle
    if (IPriceFeed(pricefeed).hasPriceFeed(up.token0) && IPriceFeed(pricefeed).hasPriceFeed(up.token1)) {
        uint256 oracle0Price = IPriceFeed(pricefeed).getPrice(up.token0);
        uint256 oracle1Price = IPriceFeed(pricefeed).getPrice(up.token1);
        uint256 oracleImpliedPrice = oracle0Price * 10**ERC20(up.token1).decimals() / (oracle1Price * 10**ERC20(up.token0).decimals());
        
        // Ensure TWAP price is within acceptable deviation from oracle price (e.g., 5%)
        uint256 deviation = price > oracleImpliedPrice ? 
            (price - oracleImpliedPrice) * 1e18 / oracleImpliedPrice : 
            (oracleImpliedPrice - price) * 1e18 / oracleImpliedPrice;
        
        require(deviation <= 0.05e18, "TWAP price deviates too much from oracle");
    }
    
    // ... rest of the function ...
}
``` 
