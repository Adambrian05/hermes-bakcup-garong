# Incorrect Collateral USD Valuation in `Leverager._calculateTokenValues()` Can Lead to Improper Liquidations/Reverts or Overvaluation Due to Decimal Mismatch

### Summary

A miscalculation in `_calculateTokenValues()` will cause incorrect collateral valuation, i.e. `up.initCollateralUsd`, for leveraged users as the Leverager contract will miscalculate the USD value of user deposits due to incorrect decimal scaling when using TWAP price conversions.

### Root Cause

In Leverager.sol, the function `_calculateTokenValues()` incorrectly applies decimal scaling when converting token values using TWAP price.

The issue arises in the following lines:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L442-L448

```solidity
        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }
```
By referencing the `if` clause as an example, [`price`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L360) is already scaled using `PRECISION` (1e30), meaning that multiplying it by `amount0` and dividing by [`PRECISION`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L28-L29) should result in token1's unit, but with token0’s decimals. So, when when multiplying with `chPrice1` and dividing by `decimals1`, `usdValue` will only be 1e18 scaled if `decimals1 == decimals0`. Otherwise, if `decimals1 > decimals0`, `usdValue` will be assigned a value less than intended; and if `decimals1 < decimals0`, `usdValue` is going to be assigned a value more than intended. This leads to an incorrect USD valuation, either undervaluing or overvaluing the user's position.

### Internal Pre-conditions

1. A leveraged user calls `openLeveragedPosition()` to borrow against their collateral.

2. `isLiquidateable()` relies on `_calculateTokenValues()` at the end of the logic to determine if the position is above or below liquidation threshold.

3. Incorrect collateral USD valuation occurs due to improper decimal scaling in `_calculateTokenValues()`.

### External Pre-conditions

1. Chainlink price feed for one of the tokens may be missing, forcing the system to use TWAP conversion.

2. Despite a pass through check on [`Vault.checkPoolActivity()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L308-L342), `up.initCollateralUsd` returned as the USD price in 1e18 will be erroneous if `decimal1 != decimals0`.

### Attack Path

1. A leveraged user opens a position via [`openLeveragedPosition()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103-L166) where `token0` and `token1` entail different `decimals()`, e.g. 6-18 decimals that are supported. 

2. `_calculateTokenValues()` computes incorrect collateral USD valuation due to flawed decimal handling as afore explained.

3. If it creates a false positive, i.e. making `up.initCollateralUsd` inflated, 

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L129

```solidity
        up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price); // returns the USD price in 1e18
```
the user's position appears safer than it actually is, delaying liquidation (if not making it impossible) and increasing protocol bad debt inherently by the time [`owedAmount > totalDenom`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L411) is too late to be true.

4. Conversely, it prevents new positions from being created under the false negative condition, blocking some users unfairly due to the revert occurring at the following line:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L195

```solidity
        require(!isLiquidateable(_id), "position can't be liquidateable upon opening");
```
5. Alternatively, a valid position may be incorrectly marked as liquidateable, allowing liquidators to liquidate users who should not be liquidated and vice versa if the `require(!isLiquidateable(_id))` check in `openLeveragedPosition()` ever passed.

### Impact

- Leveraged users may lose positions unfairly due to underestimated collateral valuation or simply run into DoS when opening a leveraged position.

- The lucky users in the opposite scenario make liquidators fail to liquidate positions leading to higher protocol losses or suffer capital impairment as unhealthy positions remain open longer than they should. 

### Mitigation

Consider making the following fix:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L444-L448

```diff
        if (chPrice0 == 0) {
-            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
+            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals0;
        } else if (chPrice1 == 0) {
-            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
+            usdValue += amount1 * PRECISION / price * chPrice0 / decimals1;
        }
```
