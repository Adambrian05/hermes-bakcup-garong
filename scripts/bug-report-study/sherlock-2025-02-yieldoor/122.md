# Incorrect Price Scaling in Liquidation

**Summary and Impact**

The liquidation logic in the Leverager contract contains a critical flaw in how the borrowed value is calculated. Instead of properly converting the token amount to its USD value using the token’s decimal scaling factor (i.e. 10^(decimals)), the code mistakenly divides by the raw value returned by `ERC20(...).decimals()`. For example, if a token has 18 decimals, the function returns “18” rather than 10^18. This miscalculation can lead to a borrowed value that is orders of magnitude off from its intended amount. As a result, positions that are actually safe may be erroneously marked as undercollateralized, triggering liquidations even when the system’s invariants are intact. Given that liquidation triggers directly affect user funds and the overall stability of the protocol, this discrepancy represents a severe risk that could be exploited by a random user to game the system.

The protocol documentation and associated invariants clearly outline the requirement for precise price scaling to maintain collateral integrity. When the borrowed value is under-calculated, the liquidation checks fail to accurately assess a position’s health. This flaw undermines a core mechanism of the protocol and may result in unwarranted liquidations, loss of user funds, and a general erosion of trust in the system's financial soundness.

---

**Vulnerability Details**

At the heart of the issue is this code snippet in the `liquidatePosition` function of the Leverager contract:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L317-L318

The intended design is to scale the borrowed amount to its correct USD value by dividing by 10^(token decimals). However, since `ERC20(...).decimals()` returns the numeral “18” (for example), the computation mistakenly divides by 18 instead of 1e18. This miscalculation dramatically reduces the computed borrowed value. In a typical scenario where a position has a borrowed amount of 1e18 token-units and the price feed returns 1e18 (representing a $1 token), the correct calculation should yield:

  (1e18 × 1e18) / 1e18 = 1e18

Instead, the flawed logic computes:

  (1e18 × 1e18) / 18 ≈ 5.56e34 (when scaled, the value is drastically misrepresented)

A simulation test using Foundry confirms this miscalculation. The test creates a dummy position with typical parameters and compares the “vulnerable” borrowed value against the correctly scaled calculation using 10^(decimals). The difference is unmistakable and demonstrates that the liquidation conditions can be triggered erroneously. In practice, this means a position might be flagged as undercollateralized even if the deposited collateral is sufficient. As a consequence, a random user might trigger a liquidation to benefit from protocol fees or other incentives, while honest users could face unwarranted liquidations of their positions.

**Recommendations**

To remediate this vulnerability, the calculation in the liquidation routine must be updated to correctly incorporate the token’s decimal scaling factor. The fix is straightforward: replace the division by `ERC20(...).decimals()` with division by `10 ** ERC20(...).decimals()`.
