# Insufficient Observation Cardinality Check in checkPoolActivity Function

### Summary

The `checkPoolActivity()` function in Yieldoor's Strategy contract fails to verify that there are sufficient price observations (minimum cardinality of 2) before attempting to calculate price movements between consecutive observations. When interacting with new or illiquid Uniswap V3 pools with low observation cardinality, this can lead to incorrect market stability assessments, transaction failures, or denial of service for critical protocol functions.


### Root Cause

The function iterates through available Uniswap V3 pool price observations without first validating that the observation cardinality is sufficient to make meaningful calculations. While it does check for zero timestamps within the loop and reverts in those cases, it doesn't validate the minimum required cardinality before starting its calculations.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L310

### Internal Pre-conditions

- The Strategy contract must be deployed and linked to a Vault
- Functions that depend on `checkPoolActivity()` are called, such as `_priceWithinRange()`, `rebalance()`, or `compound()`
- No validation exists for minimum observation cardinality requirements



### External Pre-conditions

- A Uniswap V3 pool with observation cardinality less than 2 (typically new pools)
- The pool may be newly created or infrequently used, resulting in gaps in observations
- Users attempting to interact with protocol functions that trigger the pool activity check



### Attack Path

1. A user attempts to interact with a Yieldoor Vault that uses a newly created or low-cardinality Uniswap V3 pool
2. The operation triggers a call to `checkPoolActivity()` as part of validating pool stability
3. With insufficient observations (cardinality < 2), the function cannot properly calculate tick deltas between observations
4. The function might:
- Return an incorrect assessment of pool stability (false negative or false positive)
- Revert with "timestamp 0" if it encounters uninitialized observations
- Calculate incorrect tick deltas based on insufficient data
5. This leads to critical operations failing or executing when they shouldn't



### Impact

This vulnerability impacts protocol operations in several ways:
- Transactions may be incorrectly blocked when market conditions are stable
- Transactions might be incorrectly allowed during unstable conditions
- Users experience unexpected reverts when interacting with the protocol
- Newly created pools become effectively unusable with the protocol until they accumulate enough observations
- Rebalancing and compounding functions may fail when they should succeed


### PoC

No PoC

### Mitigation

Add an explicit check at the beginning of the `checkPoolActivity()` function to verify there are enough observations:
```solidity
function checkPoolActivity() public view returns (bool) {
    (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();

    // Add this check to prevent issues with insufficient observations
    if (observationCardinality < 2) {
        return false; // Not enough observations to determine stability
    }
    
    // Existing function logic...
}
```
Additionally, consider modifying the error handling for zero timestamps to return false rather than reverting, and implementing a mechanism to increase observation cardinality for pools used by the protocol.
