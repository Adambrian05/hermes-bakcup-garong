# Leverager.sol#isLiquidateable() - wrong check prevents undercollaterized positions from being liquidated

### Summary

The function `isLiquidateable()` incorrectly limits the liquidation threshold by forcing `base` to never exceed `initCollateralValue`. This can prevent necessary liquidations when `owedAmount` increases due to interest accrual or market volatility, potentially leading to bad debt accumulation for the protocol.

### Root Cause

In `Leverager.sol#isLiquidateable()`, the following code caps `base` at `initCollateralValue` even when the required collateral should be higher:

- [`Leverager.sol#isLiquidateable()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L209-L293) function:

```solidity
    /// @notice Checks whether a certain position is liquidateable
    /// @dev In order to be 100% accurate, expects Strategy.collectFees to have been called right before that
    /// @param _id The id of the position
    function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
        Position memory pos = positions[_id];
        VaultParams memory vp = vaultParams[pos.vault];

        uint256 vaultSupply = IVault(pos.vault).totalSupply();

        // Assuming a price of X, a LP position has its lowest value when the pool price is exactly X.
        // Any price movement, would actually overvalue the position.
        // For this reason, attackers cannot force a position to become liquidateable with a swap.
        (uint256 vaultBal0, uint256 vaultBal1) = IVault(pos.vault).balances();
        uint256 userBal0 = pos.shares * vaultBal0 / vaultSupply;
        uint256 userBal1 = pos.shares * vaultBal1 / vaultSupply;
        uint256 price = IVault(pos.vault).twapPrice();

        uint256 totalValueUSD = _calculateTokenValues(pos.token0, pos.token1, userBal0, userBal1, price);
        uint256 bPrice = IPriceFeed(pricefeed).getPrice(pos.denomination);
        uint256 totalDenom = totalValueUSD * (10 ** ERC20(pos.denomination).decimals()) / bPrice;

        uint256 bIndex = ILendingPool(lendingPool).getCurrentBorrowingIndex(pos.denomination);
        uint256 owedAmount = pos.borrowedAmount * bIndex / pos.borrowedIndex;

        /// here we make a calculation what would be the necessary collateral
        /// if we had the same borrowed amount, but at max leverage. Check docs for better explanation why.
        uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue; // @audit incorrect collateral comparison

        if (owedAmount > totalDenom || totalDenom - owedAmount < vp.minCollateralPct * base / 1e18) return true;
        else return false;
    }
```

- If `base` (calculated liquidation threshold) is higher than `initCollateralValue`, it is incorrectly reduced to `initCollateralValue`.
- This means even if a position becomes undercollateralized, it may not be flagged for liquidation.

If base is higher than initCollateralValue, it should be used for liquidation decisions.
Instead, the contract forces base = initCollateralValue, delaying liquidations even when the position is undercollateralized.

### Internal Pre-conditions

1. A user borrows at high leverage, setting `initCollateralValue` at an initial value.
2. Interest accrues over time, increasing `owedAmount`.
3. `base`, calculated based on `owedAmount`, should exceed `initCollateralValue`, but the code forces it back down.

### External Pre-conditions

1. Market conditions change, causing a significant price drop or increased borrowing costs.
2. The user’s collateral value decreases or their debt grows due to interest accumulation.

### Attack Path

**bug scenario path 1:**

1. A user opens a leveraged position at maximum allowed leverage.
2. They let interest accrue, increasing their `owedAmount`.
3. Instead of triggering liquidation, the protocol incorrectly limits `base` to `initCollateralValue`.
4. The position remains open longer than it should, leading to potential bad debt accumulation.

**bug scenario 2:**

1. A user borrows with 2x leverage, setting `initCollateralValue = $20,000`.
2. Due to interest accrual, `owedAmount` grows, increasing `base` to $25,000.
3. Instead of using the correct `base`, the protocol forces it back to `initCollateralValue ($20,000)`.
4. The position is NOT liquidated, even though it should be.

### Impact

- Bad debt accumulation: The protocol may fail to liquidate underwater positions, leading to losses for lenders and liquidity providers.
- Systemic risk: A large number of undercollateralized positions could cause cascading liquidations if not handled in time.
- Market manipulation risk: An attacker could intentionally take large leveraged positions, knowing they can delay liquidation.

### Mitigation


Calculates base dynamically as the minimum required collateral based on owedAmount and max leverage:

```solidity
    base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
```
and remove the following line

```solidity
base = base < pos.initCollateralValue ? base : pos.initCollateralValue;
```
