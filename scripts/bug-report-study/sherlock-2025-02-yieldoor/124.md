# Deposit Fee Truncation in Vault



## Summary 
In the Vault deposit function, shares are minted to users based on their deposited tokens and a deposit fee is subtracted. The fee calculation use integer division which truncate decimal values. For small share amounts, this truncation can result in no fee being charged or shares being reduced to zero.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L61-L62

## Vulnerability Details
The Vault contract apply a deposit fee by subtracting a percentage of the calculated shares. Due to integer division truncation, **small share amounts incur no fee** or result in zero shares leading to revenue loss or transaction reverts. This is critical for the protocol relying on fee income and users making small deposits.



1. **Fee Calculation in `deposit` Function**  
   ```solidity
   if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
   require(shares > 0, "shares cant be 0");
   ```
   The Subtractive fee calculation truncate small values to zero.  
   **Example**:  
     For `shares = 100`, `depositFee = 10` (0.1%):  
       `(100 * 10) / 10_000 = 1` -> `shares = 99` (okay, this is correct).  
     For `shares = 99`, `depositFee = 10`:  
       `(99 * 10) / 10_000 = 0` -> `shares = 99` (no fee to pay)

2. **Fee Cap**  
   ```solidity
   function setDepositFee(uint256 _fee) external onlyOwner {
       require(_fee <= 10, "fee is capped at 0.1%");
       depositFee = _fee;
   }
   ```
   Fees are then capped at **0.1%** (10 basis points)



## Proof of Concept

**Scenario 1: Truncation to Zero Fee**  
1. **Initial should be**:  
   `share = 99` (pre-fee), `depositFee = 10` (0.1%).  
2. **Calculation**:  
   ```solidity
   fee = (99 * 10) / 10_000 = 0.99 -> truncated to 0.  
   sharesAfterFee = 99 - 0 = 99.  
   ```  
3. **Result**:  
    User avoid paying the **0.1% fee.**
   -Over time then the small deposits bypass fees entirely.  

**Scenario 2: Shares Reduced to Zero**  
1. **Initial should be**:  
   `shares = 1` (pre-fee), `depositFee = 10` (0.1%).  
2. **Calculation**:  
   ```solidity
   fee = (1 * 10) / 10_000 = 0 -> sharesAfterFee = 1 - 0 = 1.  
   ```  
3. **Result**:  
   No fee charged and transaction succeed
   **Exploit**: Users can now split large deposits into tiny chunks to avoid fees.  

**Scenario 3: Edge Case with Maximum Fee**  
1. **Initial should be**:  
   `shares = 1`, `depositFee = 10_000` (100% fee but the  cap restrict this).  
2. **Calculation**:  
   ```solidity
   fee = (1 * 10_000) / 10_000 = 1 -> sharesAfterFee = 1 - 1 = 0.  
   ```  
3. **Result**:  
   Then the transaction will revert due to `require(shares > 0)` but the User lose gas.  



## Impact 
Small deposits bypass fees due to truncation.  
Dust deposits with 1 shares with high fees fail. 
Users exploit truncation to minimize fees.  


## Recommendation
 
Replace subtractive logic with multiplicative scaling to handle truncation fairly enough:
```solidity
if (depositFee > 0) {
    shares = (shares * (10_000 - depositFee)) / 10_000;
    require(shares > 0, "shares too small after fee");
}
```  

I will explain the recommendation based on calculations:
1. **Input**:  
   `shares = 100`, `depositFee = 10` (0.1%).  
2. **Calculation**:  
   ```solidity
   shares = (100 * 9990) / 10_000 = 99.9 -> truncated to 99.  
   ```  
   - Fee = 1 share which is  (100 - 99).  
3. **Edge Case**:  
   -'shares = 1`, `depositFee = 10`:  
     ```solidity
     shares = (1 * 9990) / 10_000 = 0.999 -> truncated to 0.  
     ```  
    Transaction reverts due to `require(shares > 0)`.  

**So the result shows that **  
Fees are rounded down ensuring protocol retain revenue.  
Revert transactions for negligible shares after fee.
