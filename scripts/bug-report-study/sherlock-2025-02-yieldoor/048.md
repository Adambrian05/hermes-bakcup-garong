# Untracked Fund Withdrawals in LendingPool via pullFunds Function

The LendingPool contract suffers from a severe vulnerability within its [pullFunds](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L209-L214) function, enabling the designated leverager to withdraw underlying assets from the `yToken` contract without updating critical reserve state variables like `underlyingBalance` or `totalBorrows`. When the leverager invokes `pullFunds(asset, amount)`, the `yToken` contract executes a transfer of `amount` of the underlying asset directly to the leverager, effectively reducing the `yToken` contract’s actual balance. However, the LendingPool’s reserve state, specifically `underlyingBalance`, is not adjusted to reflect this withdrawal. This creates a dangerous inconsistency where the reserve’s recorded liquidity—used by functions like `reserve.availableLiquidity()`—remains inflated compared to the actual funds available in the `yToken` contract. The `redeem` function, which allows users to exchange `yTokens` for underlying assets, relies on this overstated `underlyingBalance` to verify sufficient liquidity via a check such as `require(reserve.availableLiquidity() >= amount, "Insufficient liquidity")`. Since `pullFunds` does not decrement `underlyingBalance`, the check can pass even when the `yToken` contract lacks the funds to fulfill the redemption. The subsequent transfer operation, e.g., `underlyingAsset.transfer(msg.sender, amount)`, then fails due to insufficient balance, causing the transaction to revert. This issue arises because `pullFunds` and `pushFunds`—the latter intended to return funds—are separate, independent functions, with no mechanism enforcing that withdrawn funds are repaid in a timely manner. 
For example, consider a scenario where the `yToken` contract initially holds 1000 tokens, and `underlyingBalance` reflects this amount. The leverager calls `pullFunds(asset, 800)`, withdrawing 800 tokens, leaving the `yToken` contract with 200 tokens. The `underlyingBalance` remains at 1000, misleading the system. A user then attempts to redeem 500 `yTokens`, expecting 500 underlying tokens based on `reserve.availableLiquidity()` showing 1000. The check passes, but the transfer fails as only 200 tokens remain, halting the redemption.
## Impact
Users cannot redeem their `yTokens` due to insufficient underlying assets in the yToken contract, effectively locking their funds and disrupting the system’s core functionality.
## Mitigation
Merge `pullFunds` and `pushFunds` into a single atomic function that requires the leverager to repay withdrawn funds within the same transaction.
