# Mismatched Token Decimal Precision in Share Calculation Leads to Disproportionate Share Distribution and Potential Value Loss

## Summary
The Vault contract fails to normalize token decimals when calculating shares during deposits, leading to incorrect share distributions when tokens with different decimal precisions are used (e.g., USDC with 6 decimals and WETH with 18 decimals).

## Vulnerability Details
The vulnerability exists in the `_calcDeposit` function which handles share calculations for both initial and subsequent deposits. The function performs direct comparisons and calculations between token amounts without accounting for their decimal differences:

1. For [first deposits](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L133) (when `totalSupply == 0`):
```solidity
shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
```
This directly compares raw token amounts without normalization. For example, 1 WETH (1e18) vs 1 USDC (1e6) would incorrectly favor WETH due to its higher decimal precision.

2. For subsequent deposits:
```solidity
uint256 cross0 = depositAmount0 * bal1;
uint256 cross1 = depositAmount1 * bal0;
```
These cross-calculations also fail to account for decimal differences, leading to skewed ratios.

Visual representation of the issue:
```solidity
1 WETH (1e18) vs 1 USDC (1e6)
Raw comparison: 1,000,000,000,000,000,000 vs 1,000,000
Result: Heavily skewed towards WETH
```

## Proof of Concept
```solidity
function testDecimalMismatch() public {
    // Setup vault with USDC (6 decimals) and WETH (18 decimals)
    Vault vault = new Vault(USDC, WETH);
    
    // First deposit: 1 USDC and 1 WETH
    uint256 usdcAmount = 1e6;  // 1 USDC
    uint256 wethAmount = 1e18; // 1 WETH
    
    // This will mint shares based on WETH amount due to higher decimals
    // Even though both inputs represent "1" token
    vault.deposit(usdcAmount, wethAmount, 0, 0);
}
```

## Impact Details
The decimal precision mismatch leads to incorrect share distribution, where users depositing tokens with higher decimal precision receive disproportionately more shares than those depositing tokens with lower decimal precision. This creates an unfair advantage for certain token deposits and could lead to value extraction opportunities.

## Tools Used
Manual Review

## Recommendations
1. Add decimal tracking for both tokens:
```solidity
uint8 private immutable decimals0;
uint8 private immutable decimals1;
```

2. Normalize token amounts before calculations:
```solidity
function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
    internal
    view
    returns (uint256 shares, uint256 amount0, uint256 amount1)
{
    // For first deposit
    if (totalSupply == 0) {
        amount0 = depositAmount0;
        amount1 = depositAmount1;
        uint256 normalized0 = decimals0 < 18 ? amount0 * 10**(18 - decimals0) : amount0;
        uint256 normalized1 = decimals1 < 18 ? amount1 * 10**(18 - decimals1) : amount1;
        shares = (normalized0 > normalized1 ? normalized0 : normalized1) - (1000);
    }
    // For subsequent deposits
    else {
        // Normalize cross calculations
        if (decimals0 != decimals1) {
            if (decimals0 > decimals1) {
                cross1 = cross1 * 10**(decimals0 - decimals1);
            } else {
                cross0 = cross0 * 10**(decimals1 - decimals0);
            }
        }
        // ... rest of the calculation
    }
}
```
