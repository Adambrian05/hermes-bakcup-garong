# Incorrect tick range in vesting position fee collection leads to transaction revert

## Summary
The `Strategy#collectFees` function uses the main position's upper tick instead of the vesting position's upper tick when collecting fees, causing the transaction to revert and making fee collection impossible when there's an active vesting position.

## Relevant Context
The contract manages multiple Uniswap V3 positions including a vesting position. Fee collection is critical as it:
- Distributes protocol fees to the fee recipient
- Updates fee accounting for all positions
- Handles vesting position withdrawals

## Root Cause
In `Strategy#collectFees`, when collecting fees for an ongoing vesting position, the function incorrectly uses `mainPosition.tickUpper` instead of `vestPosition.tickUpper`:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L167

```solidity
if (ongoingVestingPosition) {
    collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
}
```

This causes the transaction to revert in `UniswapV3Pool#burn` for one of two reasons:
1. If `vestPosition.tickLower >= mainPosition.tickUpper`, the transaction reverts with 'TLU' (Tick Lower Upper) error
2. If the position with this incorrect tick range doesn't exist, the transaction reverts with 'NP' (No Position) error

## Attack Path
No malicious actor needed, the issue occurs naturally:

1. A vesting position is created with its own tick range
2. The main position's tick range is modified through a rebalance
3. When `collectFees` is called:
   - It attempts to collect fees using mismatched ticks
   - `UniswapV3Pool#burn` reverts
   - The entire fee collection transaction fails

## Impact Explanation
High. This bug:
- Makes fee collection impossible when there's an active vesting position
- Blocks protocol fee distribution
- Prevents vesting position withdrawals (which happen in `_withdrawPartOfVestingPosition` called by `collectFees`)

## Proof of Concept

The following test demonstrates how the fee collection reverts after a rebalance due to mismatched tick ranges:

```solidity
function testIncorrectVestingFeesCollection() public {
    bool FIRST_CASE = true;

    // Setup: Create initial vesting position
    uint256 vestingAmount0 = 0.5e8;    // 0.5 WBTC
    uint256 vestingAmount1 = 50_000e6; // 50,000 USDC
    uint256 vestingDuration = 7 days;

    // Fund owner address for vesting position
    vm.startPrank(owner);
    deal(address(wbtc), owner, vestingAmount0);
    deal(address(usdc), owner, vestingAmount1);
    
    // Approve tokens for vesting position
    wbtc.approve(vault, type(uint256).max);
    usdc.approve(vault, type(uint256).max);
    
    // Create vesting position
    IVault(vault).addVestingPosition(vestingAmount0, vestingAmount1, vestingDuration);
    vm.stopPrank();

    // Record initial tick range of vesting position
    IStrategy.VestingPosition memory vp = IStrategy(strategy).getVestingPosition();
    int24 vestingTickLower = vp.tickLower;
    int24 vestingTickUpper = vp.tickUpper;

    // Generate price movement to trigger rebalance
    if (FIRST_CASE) {
        swapWbtc(100e8);        // Large WBTC swap to move price up
    } else {
        swapUsdc(500_000e6);    // Large USDC swap to move price down
    }

    skip(360 + 1);  // Wait for rebalance interval

    swapWbtc(0.1e8);  // Small swap to update oracle price
    
    // Rebalance main position to a different range
    vm.startPrank(rebalancer);
    IStrategy(strategy).rebalance();
    vm.stopPrank();
    
    // Record new main position tick range
    IStrategy.Position memory mp = IStrategy(strategy).getMainPosition();
    int24 mainTickLower = mp.tickLower;
    int24 mainTickUpper = mp.tickUpper;
    
    // Verify main position range is different from vesting position
    assertTrue(mainTickUpper != vestingTickUpper, "Main position should have different range");
            
    // Attempt to collect fees - will revert
    if (FIRST_CASE) {
        vm.expectRevert(bytes("TLU")); // Tick Lower Upper error when vesting lower >= main upper
    } else {
        vm.expectRevert(bytes("NP"));  // No Position error when position doesn't exist
    }
    IStrategy(strategy).collectFees();
}
```

The test demonstrates two failure cases:
1. `FIRST_CASE = true`: Large upward price movement causes the main position to rebalance to a higher range. This makes `vestingTickLower >= mainTickUpper`, causing a 'TLU' revert in `UniswapV3Pool#checkTicks`.
2. `FIRST_CASE = false`: Large downward price movement causes the main position to rebalance to a lower range. The mismatched tick combination (`vestingTickLower, mainTickUpper`) doesn't correspond to any existing position, causing an 'NP' revert in `Position#update`.

Both cases show how the incorrect tick range usage in `collectFees` makes the function unusable when there's an active vesting position and the main position has been rebalanced.

## Recommendation
Use the vesting position's upper tick when collecting its fees:

```diff
if (ongoingVestingPosition) {
-   collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
+   collectPositionFees(vestPosition.tickLower, vestPosition.tickUpper);
}
```
