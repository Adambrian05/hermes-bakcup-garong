# Users are forced into lower leverage when borrowed token is one of the pool tokens

### Summary

Users are forced into lower leverage when borrowed token is one of the pool tokens, the maximum leverage will almost always be impossible to actually use when borrowed token is either token0 or token1.

### Root Cause

Users specify the position size they want to have and the part of it which they want to provide, this is essentially how their leverage is determined. For example, if a user provides `vault0In` and `vault100In` of 100 while `amount0In` and `amount1In` are 50, then we must borrow an equivalent of the borrowed token to the delta between the 2 values, that way we can repay the flashloan. The leverage of the position mentioned above would be `(200 + 100) / 200 = 1.5` (total position size is 200 and borrowed funds are 100, also ignore the fact that this should actually be a 2x leverage, this is a separate bug).

The issue is that if the borrowed token is either token0 or token1 and we do not provide liquidity in the perfect pool ratio, our leverage will be forcefully lowered due to these lines:
```solidity
        uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
        ILendingPool(lendingPool).repay(lp.denomination, denomBalance);
        up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
```

The `balanceOf()` call is problematic as it can include funds which are leftover from the liquidity provision, we are automatically repaying them.

### Internal Pre-conditions

1. Denom token is either token0 or token1, this is expected and handled by the code
2. The liquidity is not provided in the perfect ratio, this is also completely expected, it will pretty much always be the case as even if a user tries to actually provide the perfect liquidity, it won't be perfect anymore if someone swaps before him (either frontrun or in most cases, a simple race condition)

### External Pre-conditions

_No_

### Attack Path

1. The maximum leverage is 1.5, the user wants to create a position with the max leverage to get the most benefits out of the protocol. Also, borrowed token is token1.
2. To use the max leverage, he opens a position of 100 token0 and 100 token1 while providing 50 tokens of each, the calculation would be `(200 + 100) * 1e18 / 200 = 1.5e18` or 1.5 leverage (assuming everything is 1:1 which would make the liquidity provision perfect by default when providing equal amounts as in the example but this is just done for simplicity purposes, this does not matter for the issue)
3. Only 80 of the tokens are used up during the vault deposit, the variables for that are `a0` and `a1`
4. The user has provided a maximum borrow amount of 100 tokens, that is token1 and the balance of that token is now 120 (100 borrowed + 20 leftover from the deposit), the balance of token0 is 20 (20 leftover from the deposit)
5. We end up in the swap code and we must swap our token1 (borrowed token) to receive `80 - 50 = 30` token0
6. We conduct the swap and now our balances are 50 token0 and 90 token1 (increased token0 by 30 and decreased token1 by 30)
7. We repay the flashloaned deltas, now the balances are 0 token0 and 40 token1, we reach this code:
```solidity
uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
ILendingPool(lendingPool).repay(lp.denomination, denomBalance);
up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
```
8. The `denomBalance` will be 40 as that is token1, we repay it and our borrowed amount will be set to 60
9. Now, our total position size is 160 (80 token0 and 80 token1) while our borrowed funds are 60, the leverage is `(60 + 160) * 1e18 / 160 = 1.375e18` or 1.375 leverage
10. Our leverage was forcefully lowered from the 1.5 we wanted and essentially specified

### Impact

Leverage is forcefully lowered, users can not practically use the maximum leverage when borrowed token is either token0 or token1 as there will pretty much always be leftover tokens and the issue will occur as explained in the attack path.


Note that for someone it might seem logical that if a user provides a perfectly calculated borrow amount, then there wouldn't be any leftover tokens and the issue wouldn't occur. However, that is not the case, the result would be the exact same (lower initial borrow amount == lower borrow amount overall, same result).

### Mitigation

Remove this line:
```solidity
uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
```
Change it to this:
```solidity
uint256 denomBalance;
if (lp.denomination != up.token0 && lp.denomination != up.token1) {
      denomBalance = IERC20(lp.denomination).balanceOf(address(this);
} else if (lp.denomination == up.token0) {
      denomBalance =  IERC20(lp.denomination).balanceOf(address(this) - (lp.vault0In - a0);
} else if (lp.denomination == up.token1) {
      denomBalance =  IERC20(lp.denomination).balanceOf(address(this) - (lp.vault1In - a1);
}
```
Then, the leftover of the will be swept at the end of the function. With the example, we would now have `denomBalance = 40 - (100 - 80) = 20`, we will repay only 20 tokens and the other 20 will be swept, the borrowed amount would be `100 - 20 = 80`. The leverage would be `(160 + 80) * 1e18 / 160 = 1.5e18` (160 total position size of 80 token0 and token1 and 80 borrowed), this is 1.5 leverage as the user initially specified.
