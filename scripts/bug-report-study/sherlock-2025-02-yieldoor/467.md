# Integer Division Rounding in Deposit Fee Calculation Causes Loss of Protocol Revenue

## Summary
The Vault contract's deposit fee calculation uses integer division which can round down to zero for small deposits, especially with low decimal precision tokens. This causes the protocol to miss out on fee collection, resulting in revenue loss that compounds over time as more small deposits are made.

## Vulnerability Details
The Vault contract charges a deposit fee (up to 0.1%) when users deposit tokens. However, the fee calculation uses integer [division which can result in zero fees](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L61) being collected for small deposits:

```solidity
if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
```


For example, if a user deposits tokens resulting in 999 shares and the deposit fee is set to 10 (0.1%), the fee calculation would be:
- `shares * depositFee = 999 * 10 = 9,990`
- `9,990 / 10_000 = 0` (due to integer division)

This means no fee is collected even though the protocol intended to charge 0.1%.

This issue is more significant with tokens that have low decimal precision because each "unit" represents more economic value compared to tokens with higher precision. Since the shares inherit the decimal precision of the deposited tokens, low decimal tokens will result in fewer nominal shares for the same economic value.

> The shares inherits the decimal precisions of the first deposited tokens.
```js
shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
```

## Proof of Concept

## Impact Details
The protocol loses revenue from deposit fees on small deposits, particularly with low decimal tokens. This loss accumulates over time as more small deposits are made. Since the protocol supports tokens with 6-18 decimal places, this issue disproportionately affects pools with low decimal tokens, creating inconsistent fee collection across different pools.

## Tools Used
Manual

## Recommendations
Always normalize the shares decimal precision to 1e18 rather than inheriting the decimals of the tokens.
