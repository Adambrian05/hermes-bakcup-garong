# Secondary position ticks will not work as intended when ticks are negative

### Summary

Secondary ticks is not considering the negative modulo like main liquidity which will cause the secondary ticks to be miscalculated. 

### Root Cause

negative module is not considered
https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L373-L379

### Internal Pre-conditions

None needed

### External Pre-conditions

1. Current tick being negative and tick modulo is not "0" is enough

### Attack Path

None needed, it will naturally occur as long as tick is negative.

### Impact

Because of the miscalculated secondary ticks there will be idle tokens in the strategy. Since the idle tokens are meant to be put to the secondary position the functionality is broken. As long as the tick is negative and there is a modulo secondary tick position will never work as intended which will be creating great inefficiencies on the strategy. Hence, high. 

### PoC

Consider the current tick of the pool is "-7" with tick spacing being 10 and positionWidth is 100. 

Main ticks will be calculated according to this:
```solidity
function _setMainTicks(int24 tick) internal {
        int24 halfWidth = int24(positionWidth / 2);
        int24 modulo = tick % tickSpacing; // 
        if (modulo < 0) modulo += tickSpacing; // if tick is negative, modulo is also negative
        bool isLowerSided = modulo < (tickSpacing / 2); // 1 < 0

        int24 tickBorder = tick - modulo;
        if (!isLowerSided) tickBorder += tickSpacing;
        mainPosition.tickLower = tickBorder - halfWidth;
        mainPosition.tickUpper = tickBorder + halfWidth;

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

halfWidth = 50
modulo = -7
since modulo is < 0 modulo will be modulo + tickSpacing which will be: -7 + 10 = 3
isLowerSided = 3 < 5 = true
tickBorder = -7-3 = -10 (correct)
tickLower = -10 - 50 = -60
tickUpper = -10 + 50 = 40

This calculation is indeed correct for main position. Now, let's do the secondary position.

```solidity
function _setSecondaryPositionsTicks(int24 tick) internal {
        int24 modulo = tick % tickSpacing;
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;
            secondaryPosition.tickUpper = tick - modulo;
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing;
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }
```
 To better visualize, let's assume there are some token0 remaining after adding liquidity to main position. This means that the secondary ticks should be ahead of the current tick and its upper tick needs to be main liquidity upper. 

Let's do the calculations:
modulo = -7
bal0 = 1e8
bal1 = 0
bal0in1 = some value > 0
which means we will do the second statement, else.
tickLower = -7 -7 + 10 = -4 (WRONG!)
tickUpper = 40

Since the current tick is -7 and the secondary position lower limit -4 adding liquidity single sided with only token0 will be impossible hence, the token0 will be idle in the contract instead of being in the LP. 




### Mitigation

Do the same negative modulo calculation that is done in main tick position on secondary position as well.
