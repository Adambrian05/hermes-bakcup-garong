# Incorrect `initCollateralValue` update logic in `Leverager` contract.

### Summary

The `withdraw` function updates `initCollateralValue` by applying `pctWithdraw` directly, **without recalculating it based on the remaining position size**. 
This results in an incorrect `initCollateralValue`, which is later used in `isLiquidateable` to determine liquidation status.

### Root Cause

- [`initCollateralValue`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L288) is directly reduced by `pctWithdraw`.
- However, `borrowedAmount` is updated **separately**, using `totalOwedAmount` and `amountToRepay`.
And also `amountOut0` and `amountOut1`, which will be transferred to position owner, is calculated from current pool state
  ```solidity
  217  (uint256 amountOut0, uint256 amountOut1) =
            IVault(up.vault).withdraw(sharesToWithdraw, wp.minAmount0, wp.minAmount1);
       ...
  288  positions[wp.id].initCollateralValue -= up.initCollateralValue * wp.pctWithdraw / 1e18;
  299  positions[wp.id].borrowedAmount = totalOwedAmount - amountToRepay;
  ```
Recalculating `borrowedAmount` with the current state is equivalent to closing the old position and opening a new one.
This means that `initCollateralValue` should be calculated newly from current state with the recalculating logic of `borrowAmount`.

### Impact

The incorrect `initCollateralValue` will be used in  `isLiquidateable` function, and leads to fault check value.

### Mitigation

Instead of simply reducing `initCollateralValue` by `pctWithdraw`, recalculate it using the actual remaining position size with `_calculateTokenValues` function.
