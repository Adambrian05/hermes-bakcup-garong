# Vault::_calcDeposit() inflates the share value when vaults use tokens with higher decimals

### Summary

In `Vault::_calcDeposit()`, the shares calculation is done for the vault based on balances and amounts for both `token0` and `token1`.
In most scenarios, the else branch will execute. 
In this case, the `shares` calculation is based off crosses, which involves multiplying values that are in each tokens decimals.
The precision is not handled correctly which inflates the `shares` value when vaults use tokens with higher decimals.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L141-L149

### Root Cause

Inconsistent/improper decimal scaling for all conditional branches of `Vault::_calcDeposit()`

### Internal Pre-conditions

Vault is created where one token has 18 decimals and the other has 6 decimals

N/A

### Attack Path

N/A

### Impact

Broken core functionality - deposits for the affected vault are bricked after the first deposit, withdraws are bricked from the first deposit
Due to the precision loss on `withdraw()`, most user deposited funds would be permanently stuck.

    function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal

        returns (uint256 shares, uint256 amount0, uint256 amount1)

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired

            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1;

            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;

            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
            amount0 = (cross - 1) / bal1 + 1;
            amount1 = (cross - 1) / bal0 + 1;
            shares = cross * totalSupply / bal0 / bal1;
        }
    }

The output for the two stress tests on `Vault::deposit()` are shown above.
In `test_calculateDepositStress()`, a user deposits five times into a WBTC/USDC vault with the same amounts for each deposit - the shares minted and amounts used for both tokens are the same with each deposit.
In `test_calculateDepositStress1()`, a user deposits five times into a WETH/USDC vault with the same amounts for each deposit.
Notice how the shares that are minted to the user grow with each deposit.
After the first deposit, due to precision loss on the amount calculation, the system stops accepting USDC.
This will also result in users receiving nothing for USDC because the precision loss will occur on `withdraw()` as well.

The invariant that a deposit + withdraw will output the same amount of tokens +/- a few wei is broken. 
In `testDepositAndWithdraw()`, a user makes the first deposit then immediately withdraws.
On withdrawal, the user does not receive the same amount of tokens as they deposited due to precision loss.

### Mitigation

Shares are denominated in the token with the higher decimals (set on first deposit).
Refactor the else branch calculations to match those decimals.
Refactor `withdraw()` to ensure withdrawAmountX calculations > 0
