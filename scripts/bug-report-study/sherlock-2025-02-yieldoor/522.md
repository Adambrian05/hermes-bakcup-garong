# A vulnerability that can substantially manipulate the borrowedAmount in attacker's position, and even resulting DoS

### Summary

The missing checks of leverager balance in `Leverager.sol::openLeveragedPosition()` result in a vulnerability that can substantially manipulate the borrowedAmount in attacker's position while gain the same share from vault, and some attackers with enough assets can even cause DoS for other users.


### Root Cause

In `Leverager.sol:177`, the borrowed amount of a leveraged position is defined as:
```solidity
up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
```

Where **denomBalance** is defined as:
```solidity
uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
```

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103-L201

If anyone transfers the denomination token to Leverager and then calls `Leverager::openLeveragedPosition()`, this could lead to two results:

#### 1. Substantially manipulate the borrowed amount in attacker's position without any cost
An attacker can transfer **X** tokens to the Leverager, then call `openLeveragedPosition()`. Assuming the borrowed amount recorded in the same position would be **Y**, the attacker's borrowed amount would become **Y - X** (as long as **Y - X** is greater than the minimal borrow amount).

Since `_sweepTokens()` in `openLeveragedPosition()` returns all tokens in Leverager to the attacker, this vulnerability can be exploited to gain the same share from vault without any cost.

#### 2. Arithmetic underflow causing DoS for most users
If an attacker transfers a sufficient amount of tokens such that `lp.maxBorrowAmount < denomBalance` always holds, an arithmetic underflow will occur and result in Denial-of-Service (DoS).

Although `lp.maxBorrowAmount` is a configurable input, if `lp.maxBorrowAmount` exceeds the lending pool limit while `lp.maxBorrowAmount > denomBalance` still holds, the DoS scenario will persist.

Additionally, even when:
- `lp.maxBorrowAmount < lending pool's maximum`
- `lp.maxBorrowAmount > denomBalance`  

hold simultaneously, some users with limited assets are unable to open leveraged positions as their leverage ratio exceeds the threshold allowed by `_checkWithinLimits()`, while leverager were designed to help these users.

### Internal Pre-conditions

Basically no pre-condition for attacker to manipulate the borrowedAmount. 

If attacker aims to make DoS, then conditions mentioned above should be satisfied




### External Pre-conditions

Attacker has enough denomination tokens

### Attack Path

1.  Attacker transfers X tokens to the Leverager,
2.  Attacker calls `openLeveragedPosition()`.

The position.borrowedAmount is decreased by X while shares are the same.

### Impact

Anyone can manipulate borrowedAmount of their position to gain great amount of shares from vault. 
And some attackers with enough tokens can make most users unable to open a leveraged position.

### Mitigation

To avoid borrowedAmount manipulation, author should check the balance of leverager balance before calculating the borrowedAmount. 
To avoid DoS, author should add a token withdraw function to withdraw tokens from `leverager`.
