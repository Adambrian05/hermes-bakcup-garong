# Borrow Limit Accounting Vulnerability

### Summary

## Summary
The Yieldoor protocol contains a critical vulnerability in its borrow limit accounting mechanism. The protocol tracks borrowed USD amounts but does not properly account for price fluctuations of the borrowed assets. This creates a risk where the protocol could exceed its intended maximum borrow limits during significant price movements, potentially leading to over-leveraged vaults and protocol insolvency in extreme market conditions.

### Root Cause

The vulnerability exists in the Leverager contract's tracking and updating of borrowed USD amounts. The contract stores the initial borrowed USD value at position creation time ([L164-L166](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L164-L166)) but never updates these values to reflect price changes of the borrowed assets. When a partial withdrawal occurs, the accounting is updated proportionally, but still based on the initial values rather than current market values:

```solidity
// From Leverager.sol (lines 270-288)
// https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L270-L288
if (wp.pctWithdraw == 1e18) {
    vaultParams[up.vault].currBorrowedUSD -= up.initBorrowedUsd;
    delete positions[wp.id];
    _burn(wp.id);
} else {
    // Here, it doesn't matter that the initBorrowedUsd doesn't represent the real value. The scenarios are 2:
    // 1) Price has dropped. In this case, this would allow the user to actually have less than minBorrow opened,
    // but since borrowed asset's price has dropped, position is less likely to be liquidated
    // 2) Price has increased. In this case the user has to remain higher position value.
    
    // here the BorrowedUSD variables do not represent the current value of the borrowed asset, that's intentional.
    vaultParams[up.vault].currBorrowedUSD -= up.initBorrowedUsd * wp.pctWithdraw / 1e18;
    
    positions[wp.id].initBorrowedUsd -= up.initBorrowedUsd * wp.pctWithdraw / 1e18;
    positions[wp.id].initCollateralValue -= up.initCollateralValue * wp.pctWithdraw / 1e18;
    positions[wp.id].borrowedAmount = totalOwedAmount - amountToRepay;
    // ...
}
```

The code explicitly acknowledges that "`initBorrowedUsd` doesn't represent the real value" and indicates this is intentional. However, this design choice creates a serious vulnerability in borrow limit enforcement. The cumulative borrowed USD tracking (`vaultParams[up.vault].currBorrowedUSD`) is critical for enforcing vault-wide borrowing limits ([L455-L475](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L455-L475)), but it becomes disconnected from actual borrowed value during price fluctuations.

### Internal Pre-conditions

- Protocol must have active leveraged positions using various assets
- The vault parameters ([defined here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L35-L45)) must have a `maxCumulativeBorrowedUSD` limit set
- Price of borrowed assets has changed significantly since position creation


### External Pre-conditions

- Significant price increase in borrowed assets (e.g., ETH or other cryptocurrencies)
- Multiple users hold leveraged positions with the same borrowed asset

### Attack Path

This is not necessarily an explicit attack vector but a systemic risk that could lead to protocol insolvency:

1. Multiple users create leveraged positions borrowing the same asset (e.g., ETH) when its price is relatively low
   - Each position records `initBorrowedUsd` based on the ETH price at position creation time
   - The cumulative borrowed USD is updated with these initial values

2. The price of ETH increases significantly (e.g., doubles or triples)
   - The actual USD value of borrowed ETH is now much higher than `initBorrowedUsd` recorded
   - The protocol's `currBorrowedUSD` continues to reflect the initial values, not current values

3. New positions are created based on available borrow capacity:
   - The borrow limit check ([L470-L473](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L470-L473)) passes
   - However, the actual USD value of all borrowed assets far exceeds the intended limit
   
4. During market stress or liquidation events:
   - The protocol may not have sufficient reserves to handle liquidations
   - The risk parameters that were calibrated based on `maxCumulativeBorrowedUSD` are no longer effective
   - Protocol insolvency becomes possible if many positions need liquidation simultaneously

### Impact

- Vaults can exceed their intended maximum borrowing limits in USD terms
- Protocol's risk parameters become ineffective as actual borrowed value diverges from tracked value
- Increased risk of protocol insolvency during market stress events
- Potential for cascading liquidations that the protocol cannot handle effectively
- Loss of user funds and trust in the protocol if reserves are insufficient

### PoC

```solidity
// Demonstrating how vault borrow limits can be exceeded
function demonstrateBorrowLimitVulnerability() external {
    // Initial conditions
    address vault = 0x123; // Example vault address
    address borrowedToken = 0xETH; // Example borrowed token
    
    // Assume initial price of ETH is $2,000
    // And vault has maxCumulativeBorrowedUSD of $10,000,000
    
    // Step 1: Create 10 positions borrowing 100 ETH each when ETH is $2,000
    // Each position has initBorrowedUsd = 100 * $2,000 = $200,000
    // Total cumulative borrowed becomes $2,000,000
    for (uint i = 0; i < 10; i++) {
        createLeveragedPosition(vault, 100 ether);
        // After each creation, vaultParams[vault].currBorrowedUSD += 200,000
    }
    
    // Step 2: ETH price increases to $4,000
    // Actual borrowed value is now $4,000,000, but currBorrowedUSD still shows $2,000,000
    
    // Step 3: Create more positions borrowing 100 ETH each at new price
    // Each position has initBorrowedUsd = 100 * $4,000 = $400,000
    // Can create up to 20 more positions before hitting the $10M limit in tracked value
    for (uint i = 0; i < 20; i++) {
        createLeveragedPosition(vault, 100 ether);
        // After each creation, vaultParams[vault].currBorrowedUSD += 400,000
    }
    
    // Result: tracked currBorrowedUSD = $10M (at limit)
    // But actual borrowed value = $4M (original) + $8M (new) = $12M (exceeds limit by 20%)
    
    // This discrepancy grows larger with bigger price changes and over time
}
```


### Mitigation

1. Update borrow accounting to track current USD value rather than initial USD value:
```solidity
// When a position is modified or during regular update intervals:
function updateBorrowedUSDValue(uint256 positionId) internal {
    Position storage position = positions[positionId];
    uint256 currentPrice = IPriceFeed(pricefeed).getPrice(position.denomination);
    
    // Calculate current USD value
    uint256 currentBorrowedUSD = position.borrowedAmount * currentPrice / (10 ** ERC20(position.denomination).decimals());
    
    // Update global accounting
    vaultParams[position.vault].currBorrowedUSD = vaultParams[position.vault].currBorrowedUSD - position.initBorrowedUsd + currentBorrowedUSD;
    
    // Update position accounting
    position.initBorrowedUsd = currentBorrowedUSD;
}
```

2. Implement a vault-wide periodic rebalancing of borrow tracking:
```solidity
function rebalanceVaultBorrowTracking(address vault) external {
    uint256 totalActualBorrowed = 0;

```

3. Add a "safety margin" to the borrow limit calculations to account for potential price fluctuations:
```solidity
// When checking if a new position can be created
require(
    vaultParams[up.vault].currBorrowedUSD * SAFETY_MULTIPLIER <= vaultParams[up.vault].maxCumulativeBorrowedUSD,
    "vault exceeded borrow limit with safety margin"
);
```

The most effective solution would be to completely redesign the borrow tracking mechanism to regularly update based on current market prices rather than relying on initial borrowed values. This would ensure that risk parameters are enforced based on actual economic exposure rather than historical metrics.
