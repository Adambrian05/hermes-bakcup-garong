# Division Before Multiplication in _calculateTokenValues()

### Summary

The `_calculateTokenValues()` function in the `Leverager` contract contains a division before multiplication issue, leading to precision loss in USD value calculations. This can result in premature liquidations due to undervaluation of collateral and affect the opening of leveraged positions.

### Root Cause

The function performs division before multiplication if one of the token doesnt have a price feed, which can truncate significant digits in integer arithmetic, leading to an inaccurate USD value.

```solidity
    function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
        internal
        view
        returns (uint256 usdValue)
    {
        uint256 chPrice0;
        uint256 chPrice1;
        uint256 decimals0 = 10 ** ERC20(token0).decimals();
        uint256 decimals1 = 10 ** ERC20(token1).decimals();
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += amount0 * chPrice0 / decimals0;
        }
        if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
            chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
            usdValue += amount1 * chPrice1 / decimals1;
        }

        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
@>          usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
@>          usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }

        return usdValue;
    }
```

### Attack Path

Lets Assume

- 	`token0`: WBTC
- 	`token1`: USDC
- 	`amount0`: 99,999,998
- 	`amount1`: 99,999,999,999
- 	`price`: 887457459841049450118851858104201
- 	`PRECISION`: 1e30
- 	`chPrice1`: 1e18
- 	`decimals1`: 1e6

And also assume there is no price feed for WBTC token, so `chPrice0` become 0 and it will execute the following code.

**Current Calculation:**
```solidity
(amount0 * price / PRECISION) * chPrice1 / decimals1;
```
`88745744209000000000000`

**Actual Calculation:**
```solidity
(amount0 * price * chPrice1) / (PRECISION * decimals1);
```
`88745744209190025329786`

There is a difference of `190025329786` units

In this case, `usdValue` is calculated slightly lower than the actual token value. As a result, it does not accurately represent the USD value, which is used to determine the initial collateral value in `openLeveragedPosition()`.

```solidity
        up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price); // returns the USD price in 1e18
        uint256 bPrice = IPriceFeed(pricefeed).getPrice(lp.denomination);
        up.initCollateralValue = up.initCollateralUsd * (10 ** ERC20(lp.denomination).decimals()) / bPrice;
```

### Impact

1. **Inaccurate Collateral Valuation**: The initial collateral value in USD is underestimated.
2. **Leverage Ratio Miscalculation**: Users might unintentionally open positions with higher leverage than intended, increasing liquidation risk.
3. **Protocol Limits:** The protocol might incorrectly enforce borrowing limits based on underestimated collateral, affecting user experience and protocol efficiency.
