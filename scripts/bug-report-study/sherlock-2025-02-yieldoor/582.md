# Zero Token Deposit Exploit in openLeveragedPosition Function

### Summary

The openLeveragedPosition function in the ILeverager contract allows a user to open a leveraged position by depositing two tokens into a vault and borrowing a denominated token. However, the function does not enforce a minimum deposit requirement for amount0In and amount1In, allowing users to borrow funds with zero actual token deposits. This could lead to abuse scenarios where malicious users leverage borrowed funds without committing real collateral.

Affected Function
```solidity

function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {

```

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103C5-L189C29




### Root Cause

Root Cause:
the function does not enforce a minimum deposit requirement for amount0In and amount1In, allowing users to borrow funds with zero actual token deposits.

The following lines allow zero deposits:

```solidity
lp.amount0In = 0;
lp.amount1In = 0;
lp.vault0In = 0.5e8; //! 0.5 WBTC
lp.vault1In = 1000e6; //! 1000USDC



```

Since amount0In and amount1In are both set to 0, the function does not require the user to transfer any actual tokens before borrowing.

### Internal Pre-conditions

1. The function openLeveragedPosition does not validate lp.amount0In and lp.amount1In to ensure they are nonzero.
2. The lending pool allows borrowing even if no user funds have been deposited initially.
3. The vault accepts deposits and issues shares even if both input amounts (amount0In and amount1In) are zero.
4. There is no proper validation that ensures a borrower has "skin in the game" before leveraging.

### External Pre-conditions

1. The attacker must have access to call openLeveragedPosition, meaning they should be an externally owned account (EOA) or a contract.
2. The attacker must have enough gas to execute the transaction.
3. The lending pool should have available liquidity for the requested maxBorrowAmount.
4. The vault should allow deposits, even when no actual assets are provided by the user.

### Attack Path

1. Setup: The attacker prepares a LeverageParams struct where amount0In = 0 and amount1In = 0, but sets vault0In and vault1In to some values.
 
2. Borrow Funds Without Deposit: The function allows borrowing (lp.maxBorrowAmount) even though no initial funds are provided.
 
3. Use Borrowed Funds for Arbitrage or Rug Pull:
4. The attacker can swap the borrowed funds for other assets.
5. They may use this to drain liquidity from the lending pool.
 
6. Alternatively, they could create an underwater position by converting borrowed assets into worthless tokens and forcing governance to liquidate.
 
7. Repay a Minimal Amount (or Default):
8. The attacker may return only a small portion of borrowed funds, leaving the protocol with bad debt.
9. If they manage to manipulate prices (e.g., via a flash loan attack), the system may falsely believe they have repaid more than they actually did.

### Impact

- Arbitrary Borrowing Without Collateral
- Attackers could manipulate the lending pool by borrowing funds without any initial commitment. This creates an imbalance in the system, leading to systemic risk.

-  Potential Drain on Lending Pool
If an attacker executes multiple transactions exploiting this flaw, they could drain significant assets from the lending pool, preventing legitimate users from accessing funds.
 
- Creation of Unrecoverable Bad Debt
The attacker could take out a leveraged position and intentionally create an unprofitable trade.
 If liquidation cannot happen in time, governance might need to manually intervene and take a loss.
This could lead to a protocol bailout scenario, where stakers or users bear the cost.

### Mitigation

1. Enforce Minimum Initial Deposit
 Modify openLeveragedPosition to require amount0In and amount1In to be nonzero:

```solidity

require(lp.amount0In > 0 || lp.amount1In > 0, "Must deposit some initial funds");

```

2. Validate Borrowing Conditions

Ensure that borrowing cannot occur without a proportional initial deposit:

```solidity

require(lp.maxBorrowAmount <= (lp.amount0In + lp.amount1In) * leverageFactor, "Borrow amount too high");


```
