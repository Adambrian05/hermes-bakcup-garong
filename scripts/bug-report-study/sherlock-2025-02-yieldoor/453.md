# Incorrect Fee Collection Implementation Causes Protocol to Lose All Deposit Fee Revenue

## Summary
The Vault contract fails to properly collect deposit fees due to a fundamental design flaw. When users deposit assets, the contract reduces the number of shares minted to the user based on the fee percentage, but never mints these "fee shares" to a protocol-controlled address. As a result, when users withdraw their funds, they effectively receive their full deposit back, minus an insignificant amount (for first depositor), making the fee system completely ineffective.

## Vulnerability Details
The Vault contract implements a deposit fee mechanism in the[ `deposit()` function where the calculated shares for a user are reduced by a fee percentage before](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L61) minting:

```solidity
if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
```

However, this implementation has a critical flaw. The contract merely reduces the shares minted to the user but doesn't mint those reduced shares to any protocol-controlled address. In a vault system, the total value of underlying assets is represented by the total supply of shares. Since all shares are held by users (except for the 1000 initial shares in the BURN address), users collectively own 100% of the underlying assets.

When a user withdraws, the amount they receive is calculated as:
```solidity
withdrawAmount0 = totalBalance0 * shares / totalSupply;
withdrawAmount1 = totalBalance1 * shares / totalSupply;
```

Since the protocol never takes ownership of the fee shares, the total supply is lower than it should be, allowing users to withdraw a proportionally larger amount of assets than they should be entitled to.

## Proof of Concept
Consider this simple scenario:

1. Vault is initially empty (0 shares, 0 tokens)
2. `depositFee` is set to 10 (0.1%)
3. User deposits 10,000 of each token (token0 and token1)
4. Calculated shares = 10,000
5. After fee: shares = 10,000 - (10,000 * 10/10,000) = 9,990
6. User receives 9,990 shares
7. Total supply = 9,990 shares (all owned by the user)
8. When user withdraws all their 9,990 shares:
   - They receive: (9,990/9,990) * 10,000 = 10,000 tokens of each type
   - They get back 100% of their deposit despite supposedly paying a 0.1% fee

The user ends up getting their full deposit back because they own 100% of the total supply of shares, despite having paid a "fee" during deposit.

## Impact Details
The protocol fails to collect any revenue from deposit fees, undermining a key monetization mechanism. This result in significant lost revenue for the protocol, especially during periods of high deposit volume.

## Recommendations
To properly implement the deposit fee mechanism, the contract should mint the fee shares to a protocol-controlled address. This ensures that the protocol actually captures value from the fees charged.

```solidity
// Add a fee recipient address
address public feeRecipient;

// Initialize in constructor
constructor(address _token0, address _token1) ERC20("", "") Ownable(msg.sender) {
    if (_token0 > _token1) (_token0, _token1) = (_token1, _token0);

    token0 = _token0;
    token1 = _token1;
    feeRecipient = msg.sender; // Default fee recipient is owner
}

// Modify deposit function to mint fee shares
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... existing code ...

    if (depositFee > 0) {
        uint256 feeShares = (shares * depositFee) / 10_000;
        _mint(feeRecipient, feeShares); // Mint fee shares to fee recipient
        shares -= feeShares;
    }

    // ... existing code ...
    _mint(msg.sender, shares);

    // ... existing code ...
}

// Add ability to update fee recipient
function setFeeRecipient(address _newFeeRecipient) external onlyOwner {
    require(_newFeeRecipient != address(0), "Fee recipient cannot be zero address");
    feeRecipient = _newFeeRecipient;
}
```

This implementation ensures that when a fee is charged, the protocol actually receives shares representing that value, allowing it to properly capture revenue from deposit fees.
