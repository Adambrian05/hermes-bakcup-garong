# Missing Slippage Protection in `LendingPool.sol` Dynamic Redemption Process

### Summary

While `yTokens` are initially minted in a `1:1` ratio with the underlying asset at deposit, the redeem process relies on a dynamic exchange rate calculated by the `ReserveLogic` library. This dynamic rate, which reflects accrued interest, liquidity changes, and borrowings, can diverge from the initial `1:1` minting ratio. Without a mechanism for users to specify a minimum acceptable output (i.e., slippage protection), users risk receiving far fewer underlying tokens if market conditions or internal state changes affect the exchange rate. 

### Root Cause

The issue arises in the redeem process where the underlying token amount is computed dynamically in [LendingPool.sol:141](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L141)

```solidity
uint256 underlyingTokenAmount = reserve.yTokenToReserveExchangeRate() * yAssetAmount / PRECISION;
```

This function (defined in [ReserveLogic.sol:85](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol#L85)) calculates the exchange rate as:

```solidity
return totalLiquidity * PRECISION / totalYTokens;
```

Because the exchange rate can change due to interest accrual and liquidity fluctuations, and because the redeem function lacks a parameter for the caller to set a minimum acceptable amount of underlying tokens, users are exposed to slippage. The redeem process only checks that the pool has enough available liquidity in [LendingPool.sol:143](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L143):

```solidity
require(underlyingTokenAmount <= reserve.availableLiquidity(), "not enough available liquidity");
```

This check does not protect against unfavorable rate changes between deposit and redemption.


### Internal Pre-conditions

1. The redeem function calculates the underlying token amount using a dynamic exchange rate from `ReserveLogic`.
2. There is no provision for a user-specified minimum acceptable output (e.g., `minUnderlyingOut`).
3. The reserve’s state (total liquidity, total borrows, `yToken` supply) can change between deposit and redemption.

### External Pre-conditions

1. A sudden external market event causes the underlying asset's price to shift quickly.
2. External liquidity fluctuations occur that, combined with the dynamic rate calculation, lead to substantial changes in the redemption output.

### Attack Path

1.  A user deposits assets and receives `yTokens` minted at a `1:1` ratio.
2. Through either natural market movement or an attacker-induced event (e.g., flash loan or oracle manipulation), the reserve’s exchange rate shifts unfavorably.
3. The user initiates the redeem function with a specified amount of `yTokens`.
4. The function computes the underlying token amount based on the new, unfavorable exchange rate, without enforcing a minimum threshold.
5. The redemption completes, and the user receives significantly fewer underlying tokens than expected.

### Impact

Users may lose value due to receiving far fewer underlying tokens than anticipated.

### PoC

_No response_

### Mitigation

Add an additional parameter (e.g., `uint256 minUnderlyingOut`) to the redeem function, allowing users to specify the minimum acceptable amount of underlying tokens then insert a slippage check before processing the redemption
