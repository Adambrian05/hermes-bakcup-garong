# Premature liquidation due to uncollected Uniswap V3 fees not being accounted for in position valuation

## Description:
The Yieldoor protocol's liquidation mechanism in the `Leverager` contract does not account for uncollected Uniswap V3 trading fees when calculating the value of a user's position. This creates a situation where users can be liquidated prematurely, even though their actual position value (including uncollected fees) would be above the liquidation threshold.
The issue stems from how position values are calculated in the `Leverager::isLiquidateable()` function:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L385
```solidity
// Leverager.sol
function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
    Position memory pos = positions[_id];
    VaultParams memory vp = vaultParams[pos.vault];

    uint256 vaultSupply = IVault(pos.vault).totalSupply();

    (uint256 vaultBal0, uint256 vaultBal1) = IVault(pos.vault).balances();
    uint256 userBal0 = pos.shares * vaultBal0 / vaultSupply;
    uint256 userBal1 = pos.shares * vaultBal1 / vaultSupply;
    uint256 price = IVault(pos.vault).twapPrice();

    // Calculate total value and check if liquidatable
    // ...
}
```

This function relies on the `balances()` function from the `Vault` contract, which in turn calls the `balances()` function in the `Strategy` contract:

```solidity
// Strategy.sol
function balances() public view returns (uint256 amount0, uint256 amount1) {
    (uint160 sqrtPriceX96,,,,,,) = IUniswapV3Pool(pool).slot0();

    (uint256 idle0, uint256 idle1) = idleBalances();
    (uint256 m0, uint256 m1) = LiquidityAmounts.getAmountsForLiquidity(
        sqrtPriceX96,
        TickMath.getSqrtRatioAtTick(mainPosition.tickLower),
        TickMath.getSqrtRatioAtTick(mainPosition.tickUpper),
        mainPosition.liquidity
    );
    (uint256 s0, uint256 s1) = LiquidityAmounts.getAmountsForLiquidity(
        sqrtPriceX96,
        TickMath.getSqrtRatioAtTick(secondaryPosition.tickLower),
        TickMath.getSqrtRatioAtTick(secondaryPosition.tickUpper),
        secondaryPosition.liquidity
    );

    amount0 = idle0 + m0 + s0;
    amount1 = idle1 + m1 + s1;
}
}
```

The `Strategy::balances()` function calculates:
Idle balances (tokens in the contract) via `idleBalances()`
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L191
```solidity
// Strategy.sol
    function idleBalances() public view returns (uint256 amount0, uint256 amount1) {
        amount0 = IERC20(token0).balanceOf(address(this));
        amount1 = IERC20(token1).balanceOf(address(this));
    }
```
Tokens in the main Uniswap V3 position
Tokens in the secondary Uniswap V3 position

However, it does not account for uncollected Uniswap V3 trading fees that have accrued in the positions. These fees are only collected and added to the idle balances when the `Strategy::collectFees()` function is called:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L159

The `Strategy::collectFees()` function is only called only when calling other functions such as `Strategy::rebalance()`, `Strategy::compound()`, `Strategy::addVestingPosition`, `Vault::deposit()`, `Vault::withdraw()`

This means that between these calls, uncollected Uniswap V3 trading fees accumulate in the positions but are not reflected in the position valuation used for liquidation checks.

## Impact:
Users can be liquidated prematurely when their positions would actually be above the liquidation threshold if uncollected Uniswap V3 fees were accounted for

## Recommended Mitigation:
Modify the `Leverager::isLiquidateable()` function to collect fees before checking liquidation eligibility
