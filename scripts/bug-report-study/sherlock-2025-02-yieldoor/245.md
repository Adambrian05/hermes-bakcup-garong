# Uninitialized feeRecipient will divert protocol fees to the zero address, impacting protocol revenue

### Summary

The feeRecipient variable not being initialized in the Leverager contract will cause a complete loss of protocol fees for the protocol as fee transfers are directed to address(0) when fee collection functions (such as liquidatePosition) are executed.

### Root Cause

- In Leverager.sol, the [feeRecipient](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L47) variable is declared but never initialized or updated via a setter. This oversight causes its default value to be address(0), so any fee transfers using feeRecipient send tokens to the zero address.


### Internal Pre-conditions

1. Admin deploys the Leverager contract without setting feeRecipient, leaving it at address(0).  
2. No setter function is called (or available) to update feeRecipient to a valid, non-zero address.  
3. A fee collection event (e.g., liquidation via liquidatePosition) is triggered, invoking fee transfers.



### External Pre-conditions

1. The ERC20 token contracts used for fee transfers operate normally, allowing the fee transfer call to succeed.  
2. External protocols do not override or correct the feeRecipient value.


### Attack Path

1. The Leverager contract is deployed with feeRecipient uninitialized (defaulting to address(0)).  
2. An administrative action or event (such as a liquidation) triggers a fee collection process.  
3. The contract computes protocol fees and calls safeTransfer to feeRecipient.  
4. Since feeRecipient is address(0), the fees are sent to the zero address, effectively burning them.


### Impact

The protocol suffers an approximate loss of all protocol fee revenue because fees intended for accumulation are permanently sent to address(0), depriving the protocol of its fee-based income.


### PoC

```solidity
// Example PoC: Fee transfer to an uninitialized feeRecipient

// Assume feeRecipient remains uninitialized (i.e., address(0))
uint256 protocolFeePct = 500; // Example fee percentage (in basis points)
uint256 amount0 = 1000 * 1e18;  // Example token amount for fee calculation

// Calculation of fee amount
uint256 pf0 = protocolFeePct * amount0 / 1e18;

// Fee transfer executed during a fee collection event (e.g., liquidation)
IERC20(token0).safeTransfer(feeRecipient, pf0); // feeRecipient is address(0), fees are sent to zero address
```


### Mitigation

Implementing a setter function and initializing feeRecipient in the constructor with a valid non-zero address would mitigate this vulnerability.
