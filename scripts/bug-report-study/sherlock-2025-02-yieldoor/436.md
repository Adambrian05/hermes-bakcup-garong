# calculateBorrowingRate may not be continuous

### Summary

`InterestRateUtils::calculateBorrowingRate` is responsible for calculating the borrowing rate to be paid by borrowers during a certain interval, depending on the `utilization` of the `underlying token`. Typically, this follows **a stepwise, non-decreasing function** to ensure predictability for borrowers regarding the interest they must pay. However, in the current implementation, **there is a point where this continuity is broken**.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/InterestRateUtils.sol#L30-L31

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L241-L248

```solidity
if (utilizationRate <= config.utilizationA) {
            if (config.utilizationA == 0) {
                return config.borrowingRateA;
            }
            borrowingRate = utilizationRate * config.borrowingRateA / config.utilizationA;
        } else if (utilizationRate <= config.utilizationB) {
            if (config.utilizationB == config.utilizationA) {
                return config.borrowingRateB;
            }
            borrowingRate = (uint256(config.borrowingRateB) - config.borrowingRateA)
                * (utilizationRate - config.utilizationA) // (rateB - rateA) * (uR - uA) / (uB - uA) + bA
                / (config.utilizationB - config.utilizationA) + config.borrowingRateA;
        } else {
            if (config.utilizationB >= PRECISION) {
                return config.maxBorrowingRate;
            }
            borrowingRate = (uint256(config.maxBorrowingRate) - config.borrowingRateB)
                * (utilizationRate - config.utilizationB) / (PRECISION - config.utilizationB) + config.borrowingRateB;
        }
        return borrowingRate;
```

It can be noticed that there is a check for `config.utilizationB == config.utilizationA` (which can never be reached), **indicating the developers' intention to support this case** (second pre-condition).

Given that `utilizationRate > utilizationB` (third pre-condition), the code continues in the final `else block`, **where the minimum borrowingRate is borrowingRateB**. This results in a discontinuous function due to the first pre-condition.

### Internal Pre-conditions

`LendingPool::setBorrowingRateConfig` where:

* borrowingRateA != borrowingRateB
* utilizationA == utilizationB
* utilizationRate > utilizationB

### External Pre-conditions

*No Response*

### Attack Path

*No Response*

### Impact

* **Liquidity shocks**: If the borrowing rate increases drastically, borrowers may mass repay, causing liquidity fluctuations.

* **Misaligned incentives**: A sharp change in the slope could abruptly discourage borrowers or depositors, affecting the protocol's stability.

### PoC

_No response_

### Mitigation

Ensure that if compatibility with `utilizationA == utilizationB` is sought, `calculateBorrowingRate` remains continuous.
