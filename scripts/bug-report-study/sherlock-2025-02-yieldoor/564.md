# Infinite Loop in `_getTokenIn()` Causes Out-of-Gas Revert on Multi-Hop Swaps Blocking leveraged Positions from being opened

### Summary

The **`_getTokenIn()` function, responsible for extracting the input token from a swap path, contains a critical logic flaw**. When handling multi-hop swap paths (paths with more than one pool), the code **enters an infinite loop** because the `path` is never correctly advanced.

Since **the `skipToken()` result is discarded instead of being reassigned to `path`**, the `while` loop condition always evaluates to `true`, and the loop never exits. This causes **the transaction to revert due to an out-of-gas error**, effectively blocking all multi-hop swaps required for leveraged position creation.


### Root Cause


The following code causes the infinite loop within the [openLeveragedPosition](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L146):

```solidity
function _getTokenIn(bytes memory path) internal pure returns (address) {
    while (path.hasMultiplePools()) {
        path.skipToken(); // ❌ This does not modify `path`, so the loop never advances.
    }

    (, address tokenIn,) = path.decodeFirstPool();
    return tokenIn;
}
```

The `path.skipToken()` method **returns a new truncated path, but the code does not capture this return value**. As a result, `path` remains unchanged and always reports that it "has multiple pools," meaning the `while` loop runs forever, consuming all gas.


### Internal Pre-conditions

- A user attempts to open a **leveraged position**.
- The leveraged position requires a **multi-hop swap path**, such as:
  - DAI → USDC → WETH.

### External Pre-conditions


- The protocol integrates with UniswapV3 routers that support **multi-hop swaps**.
- The user provides a valid multi-hop `path` in the `ExactOutputParams`.


### Attack Path


1. A user calls `openLeveragedPosition()`, specifying a multi-hop swap path in `lp.swapParams1`.
2. The position logic calls `_getTokenIn()` to determine the input token for the final swap.
3. `_getTokenIn()` enters an **infinite loop** inside the `while (path.hasMultiplePools())` block.
4. The transaction **runs out of gas and reverts**, preventing position creation.


## Example Scenario

A user wants to open a leveraged position using the following swap path:

- DAI → USDC → WETH

When `openLeveragedPosition()` is called, it eventually calls:

```solidity
address tokenIn = _getTokenIn(swapParams.path);
```

However, because `_getTokenIn()` loops infinitely, the transaction fails with:

```bash
Transaction reverted: out of gas
```

This happens **regardless of liquidity, slippage, or token approvals**. All valid multi-hop paths will encounter this failure.

---

### Impact


- **Leveraged positions requiring multi-hop swaps are completely unusable.**
- **Users are forced to use direct pairs or face guaranteed transaction failure.**
- Protocol usability and asset composability is severely degraded.
- This is especially critical for exotic pairs or assets without direct pools.

### Expected Result

The position is opened after a multi-hop swap.

### Actual Result

The transaction reverts with:

```bash
    │   └─ ← [OutOfGas] EvmError: OutOfGas
    └─ ← [Revert] EvmError: Revert
```


### Mitigation



The `_getTokenIn()` function should **correctly advance the `path` variable** by updating it in each iteration:

```solidity
function _getTokenIn(bytes memory path) internal pure returns (address) {
    while (path.hasMultiplePools()) {
        path = path.skipToken();  // ✅ Correctly advance `path`.
    }

    (, address tokenIn,) = path.decodeFirstPool();
    return tokenIn;
}
```

This ensures the path is processed correctly, allowing multi-hop swaps to complete as intended.
