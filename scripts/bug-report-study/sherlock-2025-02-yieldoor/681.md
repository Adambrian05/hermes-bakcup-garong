# Incorrect decimal scaling in token value calculations

### Summary

`Leverager.sol#_calculateTokenValues()` function fails to properly account for decimal differences between tokens when one of the tokens has no price feed available. When tokens with different decimal places (such as WBTC with 8 decimals and USDC with 6 decimals) are involved, this causes substantial position misvaluations - either severely undervaluing or overvaluing positions depending on which token's price feed is missing. This could be exploited to borrow excessive amounts or trigger unfair liquidations.


### Root Cause

The vulnerability lies in the token conversion logic when fallback price calculations are used:

- [`Leverager.sol#_calculateTokenValues()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L424-L451) function:

```solidity
// In Leverager.sol
function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
    internal
    view
    returns (uint256 usdValue)
{
    // Earlier code omitted...

    // Bug occurs in these conversion paths
    if (chPrice0 == 0) {
        usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
    } else if (chPrice1 == 0) {
        usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
    }

    return usdValue;
}
```

The code converts from one token to another without considering the decimal difference between the tokens. For token pairs with different decimal places, this introduces an error factor equal to 10^(decimal_difference).

### Internal Pre-conditions

1. The function must process tokens with different decimal places
2. One of the tokens must have its price feed unavailable
3. The Leverager must use this function to calculate position values

### External Pre-conditions

1. Oracle network outages or delays
2. Chainlink maintenance periods
3. Extreme market volatility leading to price feed suspension
4. Network congestion affecting oracle updates


### Attack Path

**Scenario 1 - Higher decimal token (BTC) price feed missing:**

1. Attacker monitors oracle networks and identifies when BTC's price feed becomes unavailable
2. They quickly open a leveraged position with BTC and USDC
3. Due to the bug, their position is valued at approximately 50x its actual worth
4. They can borrow against this inflated valuation, extracting significantly more value than should be possible
5. When the price feed returns, they may be liquidated, but they've already extracted excess value

**Scenario 2 - Lower decimal token (USDC) price feed missing:**

1. When USDC's price feed goes offline, existing positions become undervalued by approximately 50%
2. Positions that should be healthy suddenly become liquidatable
3. Attackers can perform liquidations on these positions, acquiring assets at significant discounts

### Impact

Testing reveals dramatic valuation errors:

```solidity
Normal valuation:           2000000000000 ($20,000)
USDC feed missing:          1010000000000 ($10,100) - Undervalued by ~50%
BTC feed missing:           101000000000000 ($1,010,000) - Overvalued by ~50x
```

These valuation errors directly affect:

1. **Borrowing Limits**: Users can potentially borrow 50x more than intended when the higher decimal token's feed is missing
2. **Liquidation Thresholds**: Positions could be unfairly liquidated when the lower decimal token's feed is missing
3. **Protocol Solvency**: Excessive borrowing could result in bad debt, threatening the protocol's solvency
4. **User Trust**: Unexpected liquidations during oracle outages could severely damage protocol reputation

The severity of this issue is high, as it directly impacts core protocol functionality (position valuation) and affects financial safety mechanisms.

### Mitigation

The vulnerability can be fixed by properly accounting for token decimal differences during conversion:

```solidity
if (chPrice0 == 0) {
    // Token0 has no price feed - convert via token1 with decimal adjustment
    uint256 token0InToken1 = amount0 * price * decimals1 / (PRECISION * decimals0);
    usdValue += token0InToken1 * chPrice1 / decimals1;
} else if (chPrice1 == 0) {
    // Token1 has no price feed - convert via token0 with decimal adjustment
    uint256 token1InToken0 = amount1 * PRECISION * decimals0 / (price * decimals1);
    usdValue += token1InToken0 * chPrice0 / decimals0;
}
```

This fix appropriately scales the conversion by multiplying by the ratio of decimal bases between the tokens.
