# Wrong univ3 swap path check leads to OOG and DoS for Leverage positions where the swap path has more than one swap

### Summary

The protocol lets users leverage positions by depositing, for example WBTC and leverage his WETH/LINK position. This is achieved via the `Leverager::openLeveragedPosition` function. The user inputs all the data for the position, even an univ3 swap path which is used to
trigger a swap to acquire additional `token0` when the vault deposit exceeds the user’s input and the borrowed token differs from token0. This logic repeats for `token1` in the next if block, covering both vault tokens.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L143-L166
This is a key part of enabling leverage by converting borrowed funds into the vaults assets, ensuring the position matches the users specified `vault0In`/`vault1in` amount. 

The problem is that if the swap path is container more than one swap the transaction reverts with OOG and the functionality is completely denied.

The reason for this is because of a missing variable assignment in `_getTokenIn()` 
```Solidity
    function _getTokenIn(bytes memory path) internal pure returns (address) {
        while (path.hasMultiplePools()) {
            path.skipToken(); // <=
        }

        (, address tokenIn,) = path.decodeFirstPool();
        return tokenIn;
    }
```
What `hasMultiplePools` does is check if the value is longer than or eq to 66 bytes and if true `skipToken` is called which slices the a token and fee element from the bytes value. This is repeated until the value is less than 66 bytes.

However the value after the slice is never assigned to `path` hence `path` is never updated and the loop iterates until Out of Gas.

### Root Cause

Not updating the `path` variable when, when `skipToken` is called
```Solidity
    function _getTokenIn(bytes memory path) internal pure returns (address) {
        while (path.hasMultiplePools()) {
            path.skipToken(); // <=
        }

        (, address tokenIn,) = path.decodeFirstPool();
        return tokenIn;
    }
```

### Internal Pre-conditions

none

### External Pre-conditions

User wants to open a leveraged position and passes a uni swap path that consists of more than 2 pool/ tokes. 
For example:
WETH -> LINK -> USDC
WETH address // 20 bytes
Fee (0.3%): 0x000bb8 (3000 in hex) // 3 bytes
LINK address // 20 bytes
Fee (0.3%): 0x000bb8 (3000 in hex) // 3 bytes
USDC address // 20 bytes

43 bytes for one swap . Anything more than that and we get a OOG error



### Attack Path

none, bug 
The user just has to have a 3 token swap when opening a leverage position

### Impact

Opening a leveraged positions that have more than 2 uni v3 pools in their swap path are completely blocked and cannot be opened

### Mitigation

Add the following change to `Leverager::_getTokenIn`
```diff
    function _getTokenIn(bytes memory path) internal pure returns (address) {
        while (path.hasMultiplePools()) { // ok
-            path.skipToken();
+            path = path.SkipToken();
        }

        (, address tokenIn,) = path.decodeFirstPool();
        return tokenIn;
    }
```
