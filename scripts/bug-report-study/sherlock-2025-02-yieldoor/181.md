# Users can actually force a position to be liquidatable through a malicious swap

### Summary

Users can actually force a position to be liquidatable through a malicious swap

### Root Cause

The developer has the following assumption:
>// Assuming a price of X, a LP position has its lowest value when the pool price is exactly X.
// Any price movement, would actually overvalue the position.
// For this reason, attackers cannot force a position to become liquidateable with a swap.

This is actually incorrect. Usually the liquidatable check is done through a Chainlink price feed, the pool price is not even used. However, when there is only a price feed for 1 of the pool tokens, then we will use the pool price (TWAP). Then, an issue occurs, let's see the code:
```solidity
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += (amount0 * chPrice0) / decimals0;
        }
        ....
        } else if (chPrice1 == 0) {
            usdValue += (((amount1 * PRECISION) / price) * chPrice0) / decimals0;
        }
```
If we have a price feed for token0 and we don't have one for token1, we would end up in the above 2 checks. The `usdValue` from token0 would simply be based on the fetched CL price. Then, the USD value from token1 would be based on the same CL price, but it would also be based on the pool price. If the `price` (pool price) went up, then we would divide by a larger value, the `usdValue` would be less than supposed to, the CL price doesn't make up for that manipulation as it's stationary, it's an off-chain price and won't be moved. We are essentially mixing an incorrect price and a correct price for the token0 value while we are only using a correct value for the token0 value.

If we were to use only CL prices, then the issue wouldn't occur. If we were to only use pool prices, then the incorrectness in 1 direction would also apply to the incorrectness in the other direction, then what the developer mentioned in the comment would be correct. However, since we are doing a mix here, then it's not correct and the user can indeed become liquidatable through a swap.

Basically if we imagine that both tokens are computed using a pool price, swapping will increase the price of one and decrease the price of the other, however the total value will actually be bigger than the previous one, this is the idea the developer had. However, since we are using CL for one and the pool price for the other, then the attacker can simply decrease the price of one and the CL one will stay the same, this is lower than supposed to compared to the first case where a swap would have increased the total value.

### Internal Pre-conditions

1. A pair of tokens where only 1 has a price feed, this is completely expected and handled in the code.

### External Pre-conditions

_No_

### Attack Path

1. Attacker moves the pool price up or down based on which token is without a feed, that way the `usdValue` is lower than supposed to
2. Victims are closed to liquidation or already liquidatable based on factors such as how close he was to liquidation initially, how much the price is moved, how liquid is the pool, etc.

The POC shows below shows how if the price stays at the manipulated value for 12 seconds (1 block on Ethereum), on the Ethereum mainnet in an extremely liquid pool, the issue will occur. If we assume a less liquid (but still liquid) pool, let's say on a chain like Base which by default will have less liquidity, the attack will be much easier to pull off.

NOTE: I am aware that Ethereum is not in scope as a chain to deploy on, this is just a theoretical scenario as the POC is based on a mainnet fork. The same can occur on the listed chains in scope, the liquidity there will be lower which would make manipulations cheaper.

There are 2 options to keep the manipulated price for 1 block or 12 seconds:
- based on [this article](https://alvarorevuelta.com/posts/ethereum-mev-multiblock/), holding 10% of the validator power gives you an extremely high chance to propose a block twice in a row (25%). There are at least 2 companies around that mark which immediately makes it possible to simply manipulate the transaction ordering to allow it

- for regular users, they can simply block stuff. At current prices of ~2500\$ for an ETH, considering the block gas limit is 30M, the block length is 12 seconds and the current gas prices are 3 Gwei for priority, we can calculate a price to stuff a block of around ~200\$ (`30,000,000 gas × 3 gwei = 90,000,000 gwei = 0.09 ETH per block`). Obviously, simply using the priority fees likely won't stuff the whole block so even assuming a 10x of that, the costs would be ~2000\$ for the block stuffing. As liquidations can have extreme upside, especially considering they are slightly liquidatable (means profit will be pretty much the maximum possible for a liquidation as they are still very solvent), profits are likely. Also, one block stuff and one such price manipulation can net the attacker multiple liquidations, not just one, making it even more profitable. If this happens on a chain like Arbitrum where the sequencer handles transactions on a first come, first serve basis, then it becomes even easier there as the attacker can simply fill the block with his transactions and it will all be executed in that order.

### Impact

Attackers can actually make users liquidatable, this will be abused by attackers to liquidate users that are not supposed to be liquidatable. This also breaks a type of invariant and a very important assumption the developer had:
>// Assuming a price of X, a LP position has its lowest value when the pool price is exactly X.
// Any price movement, would actually overvalue the position.
// For this reason, attackers cannot force a position to become liquidateable with a swap.

### Mitigation

To properly match the developer's assumption, you must not mix the oracle prices. Either, use pool prices in both so the manipulation is in both sides (his assumption is indeed correct but when only using pool prices) or remove the functionality where only 1 token has a price feed.
