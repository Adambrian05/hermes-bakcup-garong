# Incomplete Reserve State Updates in Leverager’s pullFunds and pushFunds Enabling Over-redemption Risk

When users deposit funds into the LendingPool, the contract does the following:
> *Deposit Function*:
  - Transfers tokens from the user to the [yToken contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L115).
  - Mints corresponding [yTokens](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L123).
  - **[Updates the reserve’s accounting](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L129):**  
    ```solidity
    reserve.underlyingBalance += amount;
    ```
  This ensures that the pool’s record of liquidity matches the tokens held in the yToken contract.

> *Redeem Function:*
  - [Burns yTokens](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L146).
  - Transfers underlying tokens back to the user.
  - **Updates the reserve’s accounting:**  
    ```solidity
    reserve.underlyingBalance -= underlyingTokenAmount;
    ```
  
Thus, the reserve’s `underlyingBalance` is the single source of truth for the liquidity available in the pool.



## Issue

The functions [pullFunds](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L209-L214) and [pushFunds](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L217-L222) are designed for the leverager to temporarily move funds. Let’s look at their implementations:

#### **pullFunds Function:**
```solidity
function pullFunds(address asset, uint256 amount) external nonReentrant {
    require(msg.sender == leverager, "borrower not leverager");
    DataTypes.ReserveData memory reserve = getReserve(asset);
    IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
}
```

#### **pushFunds Function:**
```solidity
function pushFunds(address asset, uint256 amount) external nonReentrant {
    require(msg.sender == leverager, "borrower not leverager");
    DataTypes.ReserveData memory reserve = getReserve(asset);
    IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);
}
```

**Key Issues in These Functions:**

- **Use of Memory Instead of Storage:**  
  In both functions, the reserve data is obtained using:
  ```solidity
  DataTypes.ReserveData memory reserve = getReserve(asset);
  ```
  By assigning the return value to a memory variable, any changes to this variable (if attempted) would not persist to the contract’s storage. Although these functions do not try to update the `reserve` variable, the consequence is that the internal accounting (`underlyingBalance`) is not updated even though tokens are moved.

- **No State Update:**  
  - **For pullFunds:** The function transfers tokens out of the yToken contract using:
    ```solidity
    IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
    ```
    However, it does **not** subtract the withdrawn amount from `reserve.underlyingBalance`. As a result, the reserve continues to report a higher liquidity than it actually holds.
    
  - **For pushFunds:** Similarly, while tokens are transferred back into the yToken contract:
    ```solidity
    IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);
    ```
    no addition is made to `reserve.underlyingBalance` to reflect the returned funds.

---

## Root Cause
The critical mistake is that the leverager functions bypass the usual state updates that occur in deposit and redeem operations. They do not adjust the `underlyingBalance` within the `DataTypes.ReserveData` structure. Instead, they simply transfer tokens between contracts.  

## Impacts
  Suppose the leverager calls `pullFunds` to withdraw a certain amount of tokens. The tokens are transferred to the leverager, but the pool’s state still shows that these funds are available. Later, when someone (or the leverager) attempts a redemption based on the `underlyingBalance`, the calculation will use an inflated balance, allowing more tokens to be redeemed than actually exist in the yToken contract. This misalignment can result in a net loss of funds from the pool.
  The reserve's `underlyingBalance` is supposed to reflect the current liquidity. If tokens are moved out (or in) without updating this balance, all subsequent operations such as borrowing or redeeming—will rely on inaccurate liquidity data, leading to potential under-collateralization and fund extraction beyond what is truly available.

> **Note on Flashloan Behavior:**  
> Although the developer mentions that pullFunds and pushFunds function like flashloans—where any funds pulled are later pushed back—the temporary window during which the reserve’s underlying balance is not updated still presents a risk if any state-dependent operations occur within that timeframe.

## Mitigation
The contract should update the reserve’s state consistently in every function that alters the balance:
For `pullFunds`:  Update the function to subtract the withdrawn amount from `underlyingBalance`:
  ```solidity
  function pullFunds(address asset, uint256 amount) external nonReentrant {
      require(msg.sender == leverager, "borrower not leverager");
      DataTypes.ReserveData storage reserve = reserves[asset];
      IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
      reserve.underlyingBalance -= amount; // Adjust the internal accounting
  }
  ```
For `pushFunds`:  
  Similarly, add the returned amount to `underlyingBalance`:
  ```solidity
  function pushFunds(address asset, uint256 amount) external nonReentrant {
      require(msg.sender == leverager, "borrower not leverager");
      DataTypes.ReserveData storage reserve = reserves[asset];
      IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);
      reserve.underlyingBalance += amount; // Reflect the returned funds
  }
  ```
