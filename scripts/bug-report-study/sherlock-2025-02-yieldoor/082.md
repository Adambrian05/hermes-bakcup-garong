# The protocol will cause imbalanced token withdrawals for users due to proportional liquidity removal from inactive positions.

### Summary

The failure to dynamically adjust withdrawal proportions based on the actual token composition of each liquidity position will cause an imbalanced asset distribution for Vault depositors. 

This is because a depositor withdrawing partial shares will unintentionally trigger liquidity removal from both active (balanced) and inactive (out-of-range) positions, resulting in unexpected token ratios and potential financial losses.

### Root Cause

In the [withdrawPartial function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L134) of the [Strategy contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol), liquidity is removed proportionally from both the main position (which holds both tokens) and the secondary position (which, when out-of-range, holds only one token).

```solidity
/// @notice Withdraws a user's portion of the assets
    /// @dev Withdraws the portion evenly from the main position, secondary position and idle balances
    /// @dev Assumes collectFees has been called right before this call
    function withdrawPartial(uint256 shares, uint256 totalSupply)
        external
        onlyVault
        returns (uint256 amount0Out, uint256 amount1Out)
    {
        (uint256 bal0, uint256 bal1) = idleBalances(); // before withdrawing any liquidity, but after collecting fees.

        uint256 liqToRemove = mainPosition.liquidity * shares / totalSupply;
        (uint256 m0, uint256 m1) =
            _removeFromPosition(uint128(liqToRemove), mainPosition.tickLower, mainPosition.tickUpper);
        mainPosition.liquidity -= uint128(liqToRemove);

        liqToRemove = secondaryPosition.liquidity * shares / totalSupply;
        (uint256 s0, uint256 s1) =
            _removeFromPosition(uint128(liqToRemove), secondaryPosition.tickLower, secondaryPosition.tickUpper);
        secondaryPosition.liquidity -= uint128(liqToRemove);

        amount0Out = m0 + s0 + (bal0 * shares / totalSupply);
        amount1Out = m1 + s1 + (bal1 * shares / totalSupply);

        return (amount0Out, amount1Out);
    }
```

This design fails to account for the different token compositions between positions, leading to disproportionate withdrawals that skew the user’s received asset ratio.


### Internal Pre-conditions

1. The depositor holds shares in a Vault that has allocated liquidity across two positions: a main position (holding both tokens) and a secondary position that is out-of-range (holding only one token).
2. The `withdrawPartial` function calculates liquidity removal solely based on a fixed proportional share of total liquidity from each position, without considering the specific token composition of the secondary (out-of-range) position.

### External Pre-conditions

Not needed

### Attack Path

1. A Vault depositor establishes a leveraged position that includes:
- A main position with a balanced allocation of both tokens.
- A secondary position that is out-of-range, holding only one token `token0`.
2. The depositor initiates a partial withdrawal, say 10% of their shares.
3. The `withdrawPartial` function removes liquidity proportionally from both the main and secondary positions.
4. Because the secondary position holds only `token0`, the withdrawal returns an excess of `token0` and little to no `token1`, resulting in an imbalanced token distribution that deviates from the depositor’s original deposit ratio.

### Impact

Users suffer losses proportional to the imbalance in withdrawn tokens. If the secondary position contributes 60% of the withdrawn `token0`, the user loses `0.6 * withdrawalAmount * priceDifference`.

### PoC

Main position: `500 token0`, `500 token1` in-range
Secondary position: `1000 token0`, `0 token1` out-of-range
User withdraws 10% of shares, totalSupply = 1000 shares.
Expected (if and when balanced): `withdraw0 = 50`, `withdraw1 = 50`
Actual (due to secondary position): `withdraw0 = 150`, `withdraw1 = 50`

User receives 3x more `token0` than `token1`.


### Mitigation

Modify the `withdrawPartial` function to first assess the token composition of each liquidity position. Withdraw liquidity preferentially from in-range positions that hold both tokens, and adjust the removal from out-of-range positions accordingly.
