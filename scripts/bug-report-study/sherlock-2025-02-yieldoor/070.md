# Attacker will manipulate TWAP collateral valuation to trigger undercollateralized positions affecting leveraged users

### Summary

Reliance on TWAP prices which is susceptible to gradual manipulation within allowed deviation limits, will cause an overvaluation of collateral for leveraged positions as an attacker will execute incremental swaps to skew the TWAP, thereby opening over-leveraged positions and potentially triggering unjust liquidations for legitimate users.

### Root Cause

The choice to rely on TWAP prices for collateral valuation is a conceptual mistake as TWAP can be manipulated through incremental swaps.

In the [_calculateTokenValues function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L424) of the [Leverager contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol),  and [checkPoolActivity function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310) of the [Strategy contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol), the protocol uses TWAP prices with an allowed deviation of `maxObservationDeviation` that does not sufficiently prevent gradual price manipulation, leading to inaccurate collateral valuations.

```solidity
/// @notice Calculates the USD value of amount0 and amount1
    /// @dev Requires at least one of them to have set a trustworthy pricefeed.
    /// If one of them doesn't have a pricefeed, it uses the pool TWAP price to convert said token to the other one.
    /// @param token0 The address of the first token
    /// @param token1 The address of the second token
    /// @param amount0 The amount of token0
    /// @param amount1 The amount of token1
    /// @param price The TWAP token0/token1 price.
    /// @return usdValue The total token value, denominated in USD, scaled in 1e18.
    function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
        internal
        view
        returns (uint256 usdValue)
    {
        uint256 chPrice0;
        uint256 chPrice1;
        uint256 decimals0 = 10 ** ERC20(token0).decimals();
        uint256 decimals1 = 10 ** ERC20(token1).decimals();
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += amount0 * chPrice0 / decimals0;
        }
        if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
            chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
            usdValue += amount1 * chPrice1 / decimals1;
        }

        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }

        return usdValue;
    }
```

```solidity
/// @notice Checks the pool prices in consecutive observations, up to TWAP ago.
    /// @dev If there aren't enough observations to reach TWAP ago, returns false
    function checkPoolActivity() public view returns (bool) {
        (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();

        uint32 lookAgo = uint32(block.timestamp) - twap;

        (uint32 nextTimestamp, int56 nextCumulativeTick,,) = IUniswapV3Pool(pool).observations(currentIndex);

        int24 nextTick = tick;

        for (uint16 i = 1; i <= observationCardinality; i++) {
            uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
            (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
            if (timestamp == 0) {
                revert("timestamp 0");
            }

            tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));

            (nextTimestamp, nextCumulativeTick) = (timestamp, tickCumulative);
            int24 delta = nextTick - tick;

            if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
                return false;
            }

            if (timestamp < lookAgo) {
                return true;
            }
            nextTick = tick;
        }

        return false;
    }
```

### Internal Pre-conditions

1. The TWAP interval is set (e.g., 10 minutes) such that an attacker can execute multiple small swaps within this period without triggering an alert.
2. The `maxObservationDeviation` parameter is set to allow incremental price shifts that remain undetected by the pool activity check (e.g., ≤ 2% per observation).

### External Pre-conditions

1. The underlying liquidity pool must have sufficient liquidity to allow an attacker to perform incremental swaps that shift the TWAP gradually without incurring excessive slippage.
2. External market conditions must allow the attacker to manipulate the pool’s price within the permitted deviation range without attracting counter arbitrage bots or other market pressures.

### Attack Path

1. The attacker performs a series of small swaps on the underlying pool, each within the `maxObservationDeviation` threshold, gradually shifting the TWAP price to an overvalued level.
2. Leverager uses the manipulated TWAP price in the `_calculateTokenValues` function to compute an inflated collateral value.
3. Based on the overvalued collateral, the attacker opens a leveraged position exceeding safe limits, borrowing excess funds.
4. After the position is opened, a correction in the market or an additional deposit may cause the overvalued collateral to revert to true market levels, triggering a liquidation event that disproportionately harms legitimate users or the protocol.

### Impact

The attacker gains the ability to open over-leveraged positions and capture excess funds, thereby transferring value from honest users to the attacker. The protocol suffers bad debt proportional to the amount borrowed by the attacker.

### PoC

Step 1: Attacker performs a series of small swaps to adjust the pool price gradually, let's say 10 minutes.
Step 2: With the TWAP now artificially overvalued, the attacker opens a leveraged position with an excess borrowing enabled by inflated collateral
Step 3: Trigger a market correction to force liquidation, causing losses for other users.

### Mitigation

Combine TWAP with spot price verification during collateral valuation. Require that the TWAP price does not deviate (deviation threshold <1%) significantly from the current spot price beyond a tighter threshold before allowing leveraged positions. Reduce the TWAP interval to limit the window for gradual manipulation, thereby reducing the potential impact of incremental swaps. Also, lower the `maxObservationDeviation` parameter to ensure that even small manipulations are detected and prevent the overvaluation of collateral.
