# Incorrect token selection in Leverager.withdraw will miscalculate repayment amounts for leveraged positions

# Summary:
A bug in the withdrawal logic will cause incorrect repayment calculations for leveraged position holders as the contract mistakenly uses the wrong token balance when the borrowed asset equals the vault’s second token, leading to potential residual debt mismanagement.

# Root Cause:
In [Leverager.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol), within the `withdraw` function the repayment branch for when the borrowed token is `up.token1` contains a logic error.
Specifically, the code: https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L226C7-L235C10
```solidity
        // In case either of the tokens is denomination token, we directly take from it.
        if (borrowed == up.token0) {
            uint256 repayFromWithdraw = amountOut0 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
            amountOut0 -= repayFromWithdraw;
        } else if (borrowed == up.token1) {
            uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
            amountOut1 -= repayFromWithdraw;
        }
```
mistakenly uses `amountOut0` in the conditional expression instead of `amountOut1`.

# Internal Pre-conditions:
1. A leveraged position is opened where the borrowed token equals `up.token1`.
2. The withdrawal process is initiated with partial withdrawal parameters (i.e. `pctWithdraw` between 0 and 1e18) triggering repayment calculations.

# External Pre-conditions:
None specific; the vulnerability is purely internal to the contract logic.

# Attack Path:
1. A user with a leveraged position (with `up.token1` as the borrowed asset) initiates a withdrawal.
2. The faulty conditional subtracts an incorrect value (using `amountOut0` instead of `amountOut1`), leading to a miscalculation in the repayment amount.
3. This discrepancy can leave the position with an unintended residual debt or alter the collateral-to-debt ratio adversely.

# Impact:
Affected users may have their positions improperly adjusted during withdrawal, potentially exposing them to premature liquidation or causing financial loss due to residual debt mismanagement.

# PoC:
This PoC simulates the bug in the `withdraw` function for leveraged positions when the borrowed token equals token1. Instead of using the balance for token1, the code erroneously uses the token0 balance. In our example, if token1’s balance is less than the owed amount, the bug causes an over–repayment (or underflow) scenario.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

contract PoCWithdrawBug {
    // This function simulates the buggy branch in the withdraw function for positions
    // where the borrowed token is token1.
    // BUG: It mistakenly uses amountOut0 instead of amountOut1 when amountOut1 < owedAmount.
    function buggyWithdraw(
        uint256 amountOut0, // balance for token0 (erroneously used)
        uint256 amountOut1, // balance for token1 (should be used)
        uint256 owedAmount  // amount the position owes
    ) public pure returns (uint256 finalOwed, uint256 finalAmountOut1) {
        // Buggy logic: for token1, uses amountOut0 in the ternary check.
        uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
        // This subtraction may underflow or miscalculate the remaining owed amount.
        finalOwed = owedAmount - repayFromWithdraw;
        finalAmountOut1 = amountOut1 - repayFromWithdraw;
    }

    // Example:
    // Let amountOut0 = 100, amountOut1 = 50, and owedAmount = 80.
    // Expected: repay should be min(amountOut1, owedAmount) = 50, leaving owedAmount = 30.
    // Buggy: since 50 < 80 is true, repayFromWithdraw becomes 100, so owedAmount becomes 80 - 100 = underflow.
}
```
**PoC Explanation**
The PoC in `PoCWithdrawBug` simulates a logical error found in the withdraw function of the Leverager contract when handling positions in which the borrowed token is the second token (i.e., token1).

**The Bug:**
1. In the withdraw function, when the borrowed token is `token1`, the contract is intended to calculate the amount available for repayment by using the balance of `token1` (i.e. `amountOut1`).
2. However, due to a coding error, the condition uses `amountOut0` instead. The buggy line is: https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L228
```solidity
            uint256 repayFromWithdraw = amountOut0 < owedAmount ? amountOut0 : owedAmount;
```
It should use `amountOut1` to determine the repayment.

**How It Works:**
- For example, assume:
   - `amountOut0` = 100 (balance of token0)
   - `amountOut1` = 50 (balance of token1)
   - `owedAmount` = 80
- The correct behavior would be to take the minimum of `owedAmount` and `amountOut1`, i.e., 50, leaving a remainder of 30.
- Due to the bug, however, the contract uses `amountOut0` (100) instead. This miscalculation can lead to an underflow or improper adjustment of the position’s state, causing either an unintended debt reduction or making the position inconsistent.

**Attack Scenario:**
An attacker who controls or influences the token balances (for instance, by depositing tokens from a contract that behaves maliciously) could trigger this miscalculation. This could result in the attacker withdrawing more value than allowed or causing the position’s debt to be incorrectly managed, potentially leading to premature liquidation or allowing funds to be extracted improperly.

# Mitigation:
Correct the conditional to reference the correct token balance. For example, update the code to:
```solidity
if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```
Add unit tests to cover both scenarios where the borrowed token is token0 and token1.
