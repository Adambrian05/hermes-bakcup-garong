# When depositFee is larger than 0, deposit will be subject to inflation attack, thus stealing all the depositFee.

### Summary

The function deposit calculates the share based on the amount deposited by the user, and when depositFee is greater than 0, a portion of the share obtained by the user will be deducted. However, when depositFee is greater than 0, the function deposit will be subject to an inflation attack. Unlike in the past, this variant of the inflation attack does not steal all the user's deposited amount, but steals all depositFee.
Below is an example of an attacker performing a sandwich attack and an inflation attack to steal depositFee.
```solidity
Initially, totalSupply = 0 and depositFee = 0.1%.

First the attacker observes that the victim will execute deposit(1e18, 1e18).

(1) The attacker executes deposit(1e16, 1e16) by front-running, so attacker shares = (1e16 - 1000) * 0.999 = 9989999999999001, and BURN shares = 1000

(2) The attacker donates token0 and token1, making the amout of token0 and token1 in the pool be 10e18.

(3) victim will execute deposit(1e18, 1e18), so the victim  shares = 1e18 * (9989999999999001 + 1000) / 10e18 * 0.999 = 998001000000000.

(4) The attacker withdraws all shares, the amount of token0 and token1 = 11e18 * 9989999999999001 / (9989999999999001 + 1000 + 998001000000000) = 10.0009e18. 
```
So, the attacker extracted an additional 0.0009e18 (approximately 0.001e18, i.e., 0.1% depositFee) of token0 and token1. Note: A loss of 0.1% has reached a medium severity.

### Root Cause

The function deposit is vulnerable to inflation attacks, causing all deposit fees to be stolen. At the same time, no fees are required for withdrawals.

_No response_

### Mitigation

Implement a fee for the function withdraw, or set a time limit (cool-down period) for withdrawals. In this way, the depositFee will be equally shared by all users who has deposited.
