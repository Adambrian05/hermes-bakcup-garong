# Due to an incorrect leverage calculation, users are able to open positions with a leverage bigger than the max leverage allowed

### Summary

Due to an incorrect leverage calculation, users can bypass the maximum leverage restriction and open positions with much higher leverage than intended. This flaw allows traders to take excessive risk, increasing the protocol systemic risk.

### Root Cause

Function  [_checkWithinlimits] caluclates the position leverageusing the formulla
 `(initCollateralValue + borrowedAmount) / initCollateralValue`.

This formula is incorrect because `initCollateralValue` already includes the borrowed amount. 
- `initCollateralValue` : the total amount of assets deposited in the vault, which includes both the user’s contribution and the borrowed amount
- `borrowedAmount` : the amount borrowed

Since the borrowed value is counted twice in the numerator, the leverage is artificially low, making it impossible for the calculated value to exceed 2x, even if the actual leverage is much higher.

### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

This issue is easily exploitable whenever a user opens a leveraged position:
In [openLeveragedPosition()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L103-L201) the `initCollateralValue` is set to the value of the tokens deposited in `vault`, expressed in `denomination` (borrow) token . The deposit comprises amounts transferred from the user and amounts pulled from the `lendingPool`. As a result the `initCollateralValue` represents the position value (in borrowed tokens) at the time it was opened.

### Impact

User are able to open positions with a leverage much bigger than the maximum allowed, increasing the likelihood of liquidations and bad debt accumulation. 
In the provided test it is shown how an user can take a position with 10x leverage even if the maximum leverage 
 allowed is set to 2x. 

### PoC

Add the following test in `Leverager.t.sol` file. Execute it with 
`forge test --mt test_borrowOverMaxLeverage --fork-url https://eth-mainnet.g.alchemy.com/v2/UrUs2VjHvgMBc0valmD9JHOF1iElRR6s --fork-block-number 21756910 --match-contract Leverager -vvv`

**It is mandatory to fork block `21756910`**, otherwise the test will fail. 
Using a block with a different USDC/BTC ratio affects the WBTC-> USDC swap amounts. 
At block `21756910`, the BTC/USDC price was ~ 100k USD/BTC, which is the same price used in this test.

The test fails with the `[FAIL: next call did not revert as expected]` message. 
After the suggested fix is applied, the test passes - `openLeveragedPosition` reverts when leverage position exceeds the maximum configured leverage. 

### Mitigation

Consider calculating the `positionLeverage ` as the position size divided by the user’s own capital.
Subtracting `borrowedAmount` from `initCollateralValue` leaves only the user's actual contribution

```diff
    function _checkWithinlimits(Position memory up) internal {
        VaultParams memory vp = vaultParams[up.vault];
        (uint256 maxIndividualBorrow, uint256 maxLevTimes) =
            ILendingPool(lendingPool).getLeverageParams(up.denomination);

-        uint256 positionLeverage = (up.initCollateralValue + up.borrowedAmount) * 1e18 / up.initCollateralValue;
+        uint256 positionLeverage = up.initCollateralValue * 1e18 / (up.initCollateralValue - up.borrowedAmount);

        require(up.initBorrowedUsd >= minBorrow, "position must be at least minBorrow amount");
        require(positionLeverage <= vp.maxTimesLeverage && positionLeverage <= maxLevTimes, "too high x leverage");
        require(up.initBorrowedUsd <= vp.maxUsdLeverage, "too high borrow usd amount");
        require(up.borrowedAmount <= maxIndividualBorrow, "too high borrow for the vault");
        require(
            vaultParams[up.vault].currBorrowedUSD <= vaultParams[up.vault].maxCumulativeBorrowedUSD,
            "vault exceeded borrow limit"
        );
    }
```
