# Deposit Calculation Bypass: Missing Tokens Deduction in Single-Sided Liquidity

### Summary

The `Vault::deposit()` function deposits a user's funds into the strategy and mints corresponding shares. During the deposit process, the function calls `_calcDeposit()`, which calculates and returns the number of shares to be minted and the amounts of token0 and token1 that will be deposited.

However, suppose the vault or strategy currently holds liquidity in only one of the tokens. For example, if previous rebalancing or trading activity has converted or exhausted all of token0, then bal0 would be zero. In that case, the function cannot compute proportional shares based on both tokens and instead falls back to the branch [see here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L134C6-L139C51).

In this branch, the else if condition handles the deposit by returning only amount1 and the computed shares, while amount0 remains zero. Consequently, when the deposit() function proceeds to deduct funds from the user's wallet, it deducts 0 for token0. As a result, the user only pays for token1, effectively bypassing the requirement to deposit token0. Same for another one.

### Root Cause

The root cause is that the _calcDeposit() function does not properly handle the scenario where one token’s balance, bal0 or bal1, is zero.

### Internal Pre-conditions

bal0 or bal1 need to zero in `Vault::_calcDeposit()` and In `deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)`, amount0Min and amount1Min need to be 0

### Attack Path

1. The attacker first forces or waits for the vault or strategy to be in a state where it holds liquidity for only one token. For instance, through a series of rebalancing operations or strategic trades, the vault’s balance of token0 becomes 0, while token1 remains available.
2. the vault’s state now showing `bal0 == 0`, the attacker calls the `Vault::deposit()` function. and `deposit()` will call inner function `_calcDeposit()`. Since `bal0 is 0`, the function falls into the `else if` branch. Here, `amount0` is never computed, so the attacker is not required to deposit any token0.
3. Because the share calculation only considers `token1` in this branch, the attacker receives a number of vault shares as if they had deposited both tokens in the proper ratio. In reality, the vault’s state does not require any `token0`, so the attacker avoids depositing that token entirely.

### Impact

An attacker could exploit this scenario by depositing the desired amount while avoiding any token0 and token1 payment, thereby gaining an unfair advantage.

else if (bal0 == 0) {
