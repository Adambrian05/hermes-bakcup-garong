# Attacker will bypass token verification to compromise vault funds

### Summary

A missing check in the token verification logic within the openLeveragedPosition function will cause a complete bypass of critical security checks for vault deposits. This vulnerability allows an attacker to supply an arbitrary output token as the denomination even when the vault is designed to support only specific LP tokens. As a result, vault stakers risk a complete loss of funds if an attacker successfully exploits this flaw to open unauthorized leveraged positions.

### Root Cause

In Leverager.sol:openLeveragedPosition [code](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103) the function calculates delta0 and delta1 as the difference between the vault’s expected deposit amounts (vault0In and vault1In) and the user-provided amounts (amount0In and amount1In). If the attacker sets these user inputs equal to the vault inputs, both deltas become zero. This bypasses the calls to pullFunds() and pushFunds(), which normally contain critical verification logic—including checks that would ensure the denomination token (the token used for borrowing and swaps) aligns with the vault’s approved (collateral) tokens. As a consequence, the contract ends up using an arbitrary user‑supplied denomination token, even if it isn’t one of the vault’s approved tokens.

### Internal Pre-conditions

The attacker must set:
lp.amount0In to be exactly equal to lp.vault0In
lp.amount1In to be exactly equal to lp.vault1In
This causes delta0 = 0 and delta1 = 0, thereby bypassing both the pullFunds() and pushFunds() verification branches.

### External Pre-conditions

The owner of the vault must have enabled at least one more active asset in the LendigPool for this to work

### Attack Path

1. Setup:
The environment is initialized with sufficient liquidity for the vault’s approved tokens (e.g., WBTC and USDC).
The owner configures the lending pool to treat WETH as an active asset, even though it is not one of the vault’s collateral tokens.

2.Attack Execution:
The attacker constructs the LeverageParams with amount0In equal to vault0In and amount1In equal to vault1In, making both delta0 and delta1 zero.
The attacker sets the denomination token (lp.denomination) to the fake token (WETH).

3.Bypassing Verification:
Since both delta values are zero, the critical branches that call pullFunds() and pushFunds() are skipped.
The swap-based checks—which would normally enforce that the token used for swapping matches the denomination token and indirectly ensure that it’s one of the vault’s approved tokens—are never executed.

4.Position Opening:
The openLeveragedPosition call completes, borrowing funds using WETH as the denomination token and opening a leveraged position that should not have been allowed.

5.Exploitation:
The attacker now controls a leveraged position with an arbitrary denomination token (WETH), undermining the vault’s intended design where only the approved (collateral) tokens should be used.

### Impact

Vault stakers are exposed to the risk of a complete loss of funds as the attacker can create unauthorized leveraged positions using an arbitrary denomination token. This manipulation undermines the system's integrity by allowing positions to be opened with an asset that isn’t one of the vault’s approved (collateral) tokens, ultimately destabilizing the vault and eroding user trust.

### Mitigation

A potential mitigation would be to add an explicit check in openLeveragedPosition that verifies the supplied lp.denomination is among the vault’s approved (collateral) tokens (i.e., it must match either up.token0 or up.token1), regardless of whether delta0 and delta1 are zero. This additional check would ensure that the borrowed asset cannot be arbitrarily manipulated through bypassing the swap logic.
