# Lack of Pre-Withdrawal Health Check in withdraw Allows Users to Extract Value from Liquidatable Positions

### Summary

The withdraw function in the Leverager.sol contract allows users to withdraw a portion of their leveraged position while repaying a proportional amount of their debt. However, the function does not check if the position becomes liquidatable after withdrawal. This can lead to a critical issue where users can extract remaining collateral from an already liquidatable position, leaving the protocol exposed to bad debt.

### Root Cause
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L1C1-L580C2

This vulnerability occurs in the withdraw function of the Leverager.sol contract. The withdraw function allows users to partially or fully withdraw their leveraged position, repaying a proportional amount of their debt.
```solidity
function withdraw(WithdrawParams calldata wp) external nonReentrant {
    Position memory up = positions[wp.id];
    require(_isApprovedOrOwner(msg.sender, wp.id), "msg.sender not approved or owner");
    require(wp.pctWithdraw <= 1e18 && wp.pctWithdraw > 0.01e18, "invalid pctWithdraw");

    address borrowed = up.denomination;
    uint256 sharesToWithdraw = up.shares * wp.pctWithdraw / 1e18;

    (uint256 amountOut0, uint256 amountOut1) =
        IVault(up.vault).withdraw(sharesToWithdraw, wp.minAmount0, wp.minAmount1);

    uint256 bIndex = ILendingPool(lendingPool).getCurrentBorrowingIndex(borrowed);
    uint256 totalOwedAmount = up.borrowedAmount * bIndex / up.borrowedIndex;
    uint256 owedAmount = totalOwedAmount * wp.pctWithdraw / 1e18;

    uint256 amountToRepay = owedAmount;

    // Use withdrawn tokens matching denomination to repay
    if (borrowed == up.token0) {
        uint256 repayFromWithdraw = amountOut0 < owedAmount ? amountOut0 : owedAmount;
        owedAmount -= repayFromWithdraw;
        amountOut0 -= repayFromWithdraw;
    } else if (borrowed == up.token1) {
        uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
        owedAmount -= repayFromWithdraw;
        amountOut1 -= repayFromWithdraw;
    }

    // Perform swaps if requested
    if (wp.hasToSwap) {
        // ... swap logic ...
    }

    if (owedAmount > 0) IERC20(up.denomination).safeTransferFrom(msg.sender, address(this), owedAmount);

    ILendingPool(lendingPool).repay(borrowed, amountToRepay);

    if (amountOut0 > 0) IERC20(up.token0).safeTransfer(msg.sender, amountOut0);
    if (amountOut1 > 0) IERC20(up.token1).safeTransfer(msg.sender, amountOut1);

    if (wp.pctWithdraw == 1e18) {
        vaultParams[up.vault].currBorrowedUSD -= up.initBorrowedUsd;
        delete positions[wp.id];
        _burn(wp.id);
    } else {
        require(
            up.initBorrowedUsd * (1e18 - wp.pctWithdraw) / 1e18 > minBorrow,
            "remaining should be at least minBorrow"
        );
        vaultParams[up.vault].currBorrowedUSD -= up.initBorrowedUsd * wp.pctWithdraw / 1e18;
        positions[wp.id].initBorrowedUsd -= up.initBorrowedUsd * wp.pctWithdraw / 1e18;
        positions[wp.id].initCollateralValue -= up.initCollateralValue * wp.pctWithdraw / 1e18;
        positions[wp.id].borrowedAmount = totalOwedAmount - amountToRepay;
        positions[wp.id].borrowedIndex = bIndex;
        positions[wp.id].shares -= sharesToWithdraw;
    }
}
```
The function includes a comment explaining why it doesn’t check if the position is liquidatable post-withdrawal:
```solidity
/// @dev We do not check whether position is liquidateable as we remove collateral and repay debt
/// in the same ratio as the position currently is.
```
The rationale is that since the withdrawal removes collateral (shares) and repays debt proportionally (based on wp.pctWithdraw), the collateral-to-debt ratio remains unchanged, so the position’s health shouldn’t worsen. Specifically:
Shares withdrawn: `sharesToWithdraw = up.shares * wp.pctWithdraw / 1e18.`

Debt repaid: `owedAmount = totalOwedAmount * wp.pctWithdraw / 1e18.`

The function ensures the caller owns or is approved for the position (wp.id). Ensures wp.pctWithdraw is between 1% and 100% (0.01e18 < wp.pctWithdraw <= 1e18).

Burns wp.pctWithdraw percentage of the user’s vault shares, receiving amountOut0 of token0 and amountOut1 of token1. Computes the current debt (totalOwedAmount) using the borrowing index and determines the proportional debt to repay (owedAmount).
Uses withdrawn tokens matching the denomination token directly, swaps others if needed, or pulls remaining debt from the user.

Update Position:
If wp.pctWithdraw == 1e18 (full withdrawal), deletes the position and burns the NFT.

If partial withdrawal, updates the position’s state (shares, debt, collateral value) and ensures the remaining borrowed amount exceeds minBorrow.


The contract assumes that withdrawing collateral and debt proportionally maintains the position’s health (i.e., collateral-to-debt ratio). However, this assumption doesn’t hold in all cases, especially if the position is already close to or underwater (i.e., liquidatable). 

The comment suggests that since both collateral and debt are reduced by the same percentage (wp.pctWithdraw), the ratio stays constant, and thus there’s no need to check isLiquidateable. However:

Non-Linear Liquidation Conditions: The isLiquidateable function doesn’t just compare collateral to debt directly, it uses a more complex formula involving minCollateralPct and a base value derived from maxTimesLeverage. Reducing collateral and debt proportionally doesn’t guarantee the position remains non-liquidatable.

Pre-Existing Unhealthy Positions: If the position is already near or past the liquidation threshold (but hasn’t been liquidated yet), withdrawing even a small amount can push it further underwater or make it impossible to liquidate profitably.

Market Volatility: If market conditions change (e.g., token prices drop), the real-time collateral value may already be insufficient, and withdrawing worsens the situation.

The isLiquidateable Function
To understand why this matters, let’s look at isLiquidateable:
```solidity
function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
    Position memory pos = positions[_id];
    VaultParams memory vp = vaultParams[pos.vault];

    uint256 vaultSupply = IVault(pos.vault).totalSupply();
    (uint256 vaultBal0, uint256 vaultBal1) = IVault(pos.vault).balances();
    uint256 userBal0 = pos.shares * vaultBal0 / vaultSupply;
    uint256 userBal1 = pos.shares * vaultBal1 / vaultSupply;
    uint256 price = IVault(pos.vault).twapPrice();

    uint256 totalValueUSD = _calculateTokenValues(pos.token0, pos.token1, userBal0, userBal1, price);
    uint256 bPrice = IPriceFeed(pricefeed).getPrice(pos.denomination);
    uint256 totalDenom = totalValueUSD * (10 ** ERC20(pos.denomination).decimals()) / bPrice;

    uint256 bIndex = ILendingPool(lendingPool).getCurrentBorrowingIndex(pos.denomination);
    uint256 owedAmount = pos.borrowedAmount * bIndex / pos.borrowedIndex;

    uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
    base = base < pos.initCollateralValue ? base : pos.initCollateralValue;

    if (owedAmount > totalDenom || totalDenom - owedAmount < vp.minCollateralPct * base / 1e18) return true;
    else return false;
}
```
Collateral Value: totalDenom is the current value of the user’s vault shares in the denomination token, based on real-time prices (twapPrice, price feed).

Debt: owedAmount is the current debt, adjusted by the borrowing index.

Liquidation Condition: The position is liquidatable if either:
owedAmount > totalDenom (debt exceeds collateral value).

totalDenom - owedAmount < vp.minCollateralPct * base / 1e18 (the margin above debt is less than required by minCollateralPct).

The base value is a theoretical collateral requirement at max leverage, capped by initCollateralValue. This makes the liquidation condition non-linear—proportional changes in collateral and debt don’t necessarily maintain the same health status.

### Internal Pre-conditions

1. A position must exist with a collateral-to-debt ratio near or below the liquidation threshold (owedAmount > totalDenom or totalDenom - owedAmount < minCollateralPct * base / 1e18).
2. The user calls withdraw with wp.pctWithdraw < 1e18 (partial withdrawal).
3. The position hasn’t been liquidated yet (e.g., no liquidators have acted).

### External Pre-conditions

1. Market conditions must allow the position to be liquidatable (e.g., underlying token prices drop, reducing totalDenom).
2. Liquidators must not act immediately, allowing the user to withdraw before liquidation.

#### Attack Path

#### Initial Position

User opens a position with:

- **initCollateralValue** = 1000 DAI (initial collateral value).
- **borrowedAmount** = 800 DAI (borrowed DAI).
- **initBorrowedUsd** = 800 USD.

Vault parameters:

- **maxTimesLeverage** = 5e18 (5x leverage).
- **minCollateralPct** = 0.2e18 (20% minimum collateral buffer).

Assume borrowing index remains constant (**bIndex = borrowedIndex**), so **totalOwedAmount** = 800 DAI.

#### Market Conditions Change

The price of the vault’s underlying tokens drops, so the current value (**totalDenom**) of the position’s shares is now **820 DAI** (down from 1000 DAI). The debt remains **800 DAI**.

#### Check isLiquidateable

- **owedAmount** = 800 DAI, **totalDenom** = 820 DAI.
- **base** = owedAmount * 1e18 / (maxTimesLeverage - 1e18) = 800 * 1e18 / (5e18 - 1e18) = 200 DAI.
- Since **base < initCollateralValue**, we set **base = 200 DAI**.
- **minCollateralPct * base / 1e18** = 0.2e18 * 200 / 1e18 = 40 DAI.
- **totalDenom - owedAmount** = 820 - 800 = 20 DAI.
- Since **20 DAI < 40 DAI**, the position is **liquidatable**.

The position is already liquidatable but hasn’t been liquidated yet (e.g., no liquidators have acted, or market conditions just changed).

#### User Withdraws

User calls `withdraw` with **wp.pctWithdraw = 0.5e18 (50% withdrawal)**.

- **Shares withdrawn**: `up.shares * 0.5e18 / 1e18 = 50% of shares`.
- **Debt to repay**: `totalOwedAmount * 0.5e18 / 1e18 = 800 * 0.5 = 400 DAI`.

#### After Withdrawal

- **Remaining shares**: 50% of original.
- **Remaining debt**: 800 - 400 = 400 DAI.
- **New collateral value**: 50% of current value = 820 * 0.5 = 410 DAI.

#### Post-Withdrawal Health

#### Recalculate isLiquidateable

- **totalDenom** = 410 DAI, **owedAmount** = 400 DAI.
- **base** = `400 * 1e18 / (5e18 - 1e18) = 100 DAI`.
- **minCollateralPct * base / 1e18** = `0.2e18 * 100 / 1e18 = 20 DAI`.
- **totalDenom - owedAmount** = `410 - 400 = 10 DAI`.
- Since **10 DAI < 20 DAI**, the position is **still liquidatable**.

The position remains liquidatable, and the margin has worsened relative to the required buffer (**10/20 = 50% of required vs. 20/40 = 50% before**).

Although the ratio of collateral to debt (**410 / 400 = 1.025**) is the same as before (**820 / 800 = 1.025**), the absolute margin above debt (**10 DAI**) is smaller relative to the required buffer (**20 DAI**). Smaller positions are less attractive to liquidators, as the profit (or loss coverage) is thinner.

#### Protocol Risk

If the position was already liquidatable, allowing withdrawal without checking health lets users extract remaining value (e.g., **410 DAI** in tokens) while leaving the protocol with an underwater position that may not be economically viable to liquidate.

#### Potential Bad Debt

If liquidators don’t act (because liquidation isn’t profitable), the protocol accumulates **bad debt**, as the remaining collateral (**410 DAI**) won’t cover the debt (**400 DAI**) if prices drop further.


### Impact

1. Users can extract value from near-liquidatable positions, leaving the protocol with riskier debt.
2. Smaller positions post-withdrawal are less attractive to liquidators, delaying or preventing liquidation.
3. If the remaining position isn’t liquidated (e.g., too small to be profitable), the protocol may accrue bad debt if collateral value drops further (e.g., 410 DAI to 300 DAI vs. 400 DAI debt).

### PoC

_No response_

### Mitigation

1. A pre-withdrawal health check should be added to prevent withdrawals that would push a position into liquidation. The function should verify that the remaining collateral after withdrawal still meets the protocol’s minimum safety thresholds before allowing the transaction.
2. By implementing this fix, the protocol can prevent users from extracting value from liquidatable positions and reduce the risk of accumulating bad debt.
