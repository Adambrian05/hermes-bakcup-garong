# Liquidations will be significantly delayed due to incorrect maths

### Summary

Liquidations will be significantly delayed due to incorrect maths

### Root Cause

The root cause of the issue, simply put, is that (it seems) the calculations do not factor in the fact that the borrowed amount is actually a part of the total position's collateral. If a position size's collateral is 1e18 and the borrowed funds to create it are also 1e18, then the user actually provided nothing. Now, to the issue.

The code for determining whether someone is liquidatable:
```solidity
        uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;

        if (owedAmount > totalDenom || totalDenom - owedAmount < (vp.minCollateralPct * base) / 1e18) return true;
```
The `base` calculation aims to determine the necessary collateral to borrow `owedAmount` when using the maximum leverage, this is done so all users are liquidatable at the same level (considering the same borrow), otherwise it would be unfair to users.

The formula is related to this one when checking the limits:
```solidity
        uint256 positionLeverage = ((up.initCollateralValue + up.borrowedAmount) * 1e18) / up.initCollateralValue;
```
If we imagine that the maximum leverage is 2 or 2e18, the `base` value would be `2e18 * 1e18 / 1e18 = 2e18` (assuming debt is 1e18). When calculating `positionLeverage`, the calculation would be `(2e18 + 2e18) * 1e18 / 2e18 = 2e18`, they are essentially reversed, if we assume that the user opened his position at max leverage.

Since they are reversed, let's firstly prove `positionLeverage` is wrong, that way we can immediately know that `base` calculation is also wrong. The initial collateral value is made up of the borrowed amount as well as the provided by the user funds, thus in the `positionLeverage` formula, we are doing something like a double add. To reach a leverage of 2, something weird has to happen - the user must provide no funds and simply make his position from borrowing only. The calculation would be `(X + X) * 1e18 / X = 2X * 1e18 / X = 2e18`, this is 2x leverage and note that since we are double adding `X` in the parenthesis, this means that the position is made up only of borrowed funds. As a matter of fact, this will revert in the `isLiquidatable()` check as the user has provided no funds from his own pocket and he is immediately liquidatable.

To prove it further, let's imagine the maximum leverage of 5x (written in the README). For the leverage to be 5x, the calculation would be `(X + 4X) * 1e18 / X = 5X * 1e18 / X = 5e18`. This means, the borrowed funds of the position must be 4x bigger than the position. This is completely impossible as the position includes the borrowed funds, there is no way for the position to have more borrowed funds than the actual position size. Thus, we can see that the leverage is significantly undervalued, this is a bug on its own.

Now, back to the `base` calculation:
```solidity
uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
```
If we imagine a max leverage of 2 and owed amount of 2e18, the `base` would be 2e18 as well. This is essentially a reversed formula of the one we discussed above, as we mentioned earlier. For the user to have 2e18 borrowed funds at the max leverage of 2, he must have collateral of 2e18, this is obviously completely incorrect as that means his actual provided funds are 0 (`2e18 - 2e18 = 0`, the position includes the borrowed funds as mentioned earlier). In reality, the collateral needed at the max leverage of 2, should be 4e18. That way, the user provides `4e18 - 2e18 = 2e18` of his own funds to open a total position of 4e18 by borrowing 2e18. This means that the condition to liquidate (`totalDenom - owedAmount < (vp.minCollateralPct * base) / 1e18)`) is significantly in the favour of the user which could cause bad debt. Instead of being liquidatable at 10% of `4e18`, the user will be liquidatable at 10% of `2e18`, this is 50% lower than supposed to.

### Attack Path

No attack path necessary, explained in root cause.

### Impact

The less significant impact is that the leverage check will be useless, there is no way to reach the max 5x leverage.

The bigger impact is that liquidations don't work properly which can lead to bad debt. They are possible at a much later point than supposed to, the example given in the root cause showcases how the user is liquidatable at 5% of his collateral instead of the 10% that is mentioned everywhere (README, docs, codebase).

### Mitigation

In `_checkWithinLimits()`:
```diff
+ uint256 positionLeverage = up.initCollateralValue * 1e18 / (up.initCollateralValue - up.borrowedAmount)
- uint256 positionLeverage = ((up.initCollateralValue + up.borrowedAmount) * 1e18) / up.initCollateralValue;
```
In `isLiquidatable()`:
```diff
- uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
+ uint256 base = owedAmount * maxTimesLeverage / 1e18;
```
