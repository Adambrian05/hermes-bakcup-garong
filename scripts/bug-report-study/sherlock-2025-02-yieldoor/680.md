# Ineffective Fee Collection Mechanism

## Description

The Vault contract implements a deposit fee mechanism that reduces the number of shares minted to users during deposit operations. However, these reduced shares are not allocated to any beneficiary, resulting in fees being "charged" but not collected. This leads to a value leakage where users receive fewer shares than expected, but the protocol or its stakeholders do not benefit from the reduction.

## code snippet:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L61-L71

## Root Cause

The issue arises due to the implementation of the deposit function:
1. The contract calculates shares based on deposit amounts and existing balances.
2. A fee is applied by reducing the user's shares by a percentage (`depositFee`).
3. However, the deducted shares are not minted to a designated fee recipient.

As a result, the protocol does not collect revenue from deposit fees, despite users effectively paying them in the form of reduced shares. This creates an economic inefficiency where the protocol loses potential revenue.

## Impact

- Loss of protocol revenue that could be used for treasury, development, or token holder rewards.
- Potential economic imbalance, where early users subsidize later users.
- Lack of incentive alignment, as reduced shares are not allocated to stakeholders.
- Poor economic design, potentially leading to community distrust.

## Proof of Concept

The issue is present in the `deposit` function of the Vault contract. Here is the relevant code snippet:

```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... other code ...
    
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    // ... token transfers ...
    
    if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
    
    // ... validation checks ...
    
    if (totalSupply() == 0) _mint(BURN, 1000);
    _mint(msg.sender, shares);
    
    return (shares, depositAmount0, depositAmount1);
}
```

### Example Scenario
1. Assume `depositFee = 10` (0.1%).
2. A user deposits tokens worth 10,000 shares.
3. After the fee calculation: `shares = 10,000 - (10,000 * 10 / 10,000) = 9,990`.
4. The contract mints 9,990 shares to the user.
5. The 10 shares deducted are lost and never allocated to any recipient.

## Recommended Mitigation Steps

To properly implement fee collection, the deducted shares should be allocated to a designated fee recipient. Two possible approaches are:

### Option 1: Mint Fee Shares to a Designated Recipient

```solidity
// Add fee recipient address
address public feeRecipient;

// Function to set fee recipient
function setFeeRecipient(address _feeRecipient) external onlyOwner {
    require(_feeRecipient != address(0), "invalid fee recipient");
    feeRecipient = _feeRecipient;
}

// Modify deposit function
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... existing code ...
    
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    uint256 feeShares = 0;
    if (depositFee > 0) {
        feeShares = (shares * depositFee) / 10_000;
        shares -= feeShares;
    }
    
    if (totalSupply() == 0) _mint(BURN, 1000);
    _mint(msg.sender, shares);
    
    // Mint fee shares to recipient if applicable
    if (feeShares > 0 && feeRecipient != address(0)) {
        _mint(feeRecipient, feeShares);
    }
    
    return (shares, depositAmount0, depositAmount1);
}
```

### Option 2: Deduct Fee from Deposited Tokens Before Calculating Shares

```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    IStrategy(strategy).collectFees();

    (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();
    
    // Calculate initial deposit amounts
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    // Calculate fee amounts
    uint256 fee0 = 0;
    uint256 fee1 = 0;
    if (depositFee > 0) {
        fee0 = (depositAmount0 * depositFee) / 10_000;
        fee1 = (depositAmount1 * depositFee) / 10_000;
    }
    
    // Transfer main amounts to strategy
    IERC20(token0).safeTransferFrom(msg.sender, strategy, depositAmount0 - fee0);
    IERC20(token1).safeTransferFrom(msg.sender, strategy, depositAmount1 - fee1);
    
    // Transfer fees to fee recipient if applicable
    if (fee0 > 0) IERC20(token0).safeTransferFrom(msg.sender, feeRecipient, fee0);
    if (fee1 > 0) IERC20(token1).safeTransferFrom(msg.sender, feeRecipient, fee1);
    
    // Recalculate shares based on actual deposits (minus fees)
    (shares, , ) = _calcDeposit(totalBalance0, totalBalance1, depositAmount0 - fee0, depositAmount1 - fee1);
    
    // ... rest of existing code ...
}
```

## Conclusion

Implementing either of the recommended approaches ensures that the protocol effectively captures the value of deposit fees rather than losing them. The choice between options depends on the protocol's economic design and governance structure.
