# Issue with `modulo` calculation in `Strategy._setSecondaryPositionsTicks()` for negative `tick` values

### Summary

When `tick` is negative, the `modulo` calculation for the secondary position does not match that of the main position. This discrepancy leads to the secondary position being defined with incorrect lower and upper tick boundaries.

### Root Cause

In the `_setSecondaryPositionsTicks()` function, the value of `modulo` becomes negative if `tick` is less than zero. This results in potentially incorrect definitions for the lower and upper ticks of the secondary position.

If `modulo` is negative, the upper tick of the secondary position may exceed the current `tick` (as seen in the case where `bal0in1 < bal1`). This situation allows the secondary position to encompass the current tick, which is not the intended behavior.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L367
```solidity
    function _setSecondaryPositionsTicks(int24 tick) internal {
@>      int24 modulo = tick % tickSpacing;
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;
            secondaryPosition.tickUpper = tick - modulo;
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing;
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }
```

### Mitigation
