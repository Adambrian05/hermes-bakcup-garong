# Liquidation slippage parameters enable position owners to DoS liquidations

## Summary
The `Leverager#liquidatePosition` function uses `minAmount0` and `minAmount1` as slippage parameters when withdrawing assets from a vault. This allows position owners to front-run liquidation attempts by partially withdrawing from their position, causing the liquidation to fail due to insufficient assets.

## Relevant Context
The Yieldoor protocol allows users to create leveraged positions by borrowing assets and depositing them into vaults. When a position becomes undercollateralized, it can be liquidated by anyone. The liquidation process involves withdrawing the position's assets from the vault and using them to repay the borrowed amount.

## Root Cause
In the `liquidatePosition` function, the liquidator specifies `minAmount0` and `minAmount1` parameters to protect against slippage when withdrawing assets from the vault:

[`Leverager.sol#L312-L313`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L312-L313)

```solidity
(uint256 amount0, uint256 amount1) =
    IVault(up.vault).withdraw(up.shares, liqParams.minAmount0, liqParams.minAmount1);
```

However, these absolute value slippage parameters create a vulnerability. Since position owners can partially withdraw from their positions using the `withdraw` function, they can reduce the amount of assets in their position below the liquidator's specified minimum amounts, causing the liquidation transaction to revert.

The issue is compounded by the fact that the `withdraw` function doesn't check if a position is liquidatable, as noted in the function's documentation:

```solidity
/// @dev We do not check whether position is liquidateable as we remove collateral and repay debt
/// in the same ratio as the position currently is.
```

This means a position owner can withdraw a small percentage of their position (as low as 0.02e18 or 2%) repeatedly to stay just below the liquidator's expected minimum amounts while maintaining the same leverage ratio.

## Attack Path

1. A position becomes liquidatable due to price movements or accumulated interest
2. A liquidator attempts to liquidate the position by calling `liquidatePosition` with `minAmount0` and `minAmount1` set to reasonable slippage values (e.g., 0.5% below the expected amounts)
3. The position owner front-runs this transaction by calling `withdraw` with a small percentage (e.g., 2%)
4. When the liquidator's transaction executes, the `IVault(up.vault).withdraw` call reverts because the actual amounts are now below the specified minimums
5. The position owner can repeat this process whenever a liquidation is attempted, effectively preventing liquidation

## Impact Explanation
Medium. This vulnerability allows position owners to prevent liquidation of underwater positions, potentially leading to bad debt for the protocol. Liquidations are a critical mechanism for DeFi lending protocols to maintain solvency. The time-sensitive nature of liquidations makes this DoS attack particularly damaging, as delays can lead to further losses if asset prices continue to move unfavorably.

## Proof of Concept
Scenario:
1. Alice creates a leveraged position with 1 WETH and 1,000 USDC
2. Due to price movements, Alice's position becomes liquidatable
3. Bob attempts to liquidate Alice's position with parameters:
   - `minAmount0` = 0.995 WETH (0.5% slippage)
   - `minAmount1` = 995 USDC (0.5% slippage)
4. Alice sees Bob's pending transaction and front-runs it by calling `withdraw` with:
   - `pctWithdraw` = 0.02e18 (2%)
5. Alice's position now has 0.98 WETH and 980 USDC
6. Bob's liquidation transaction fails because the actual amounts (0.98 WETH and 980 USDC) are less than his specified minimums
7. Alice can repeat this process whenever a liquidation is attempted

## Recommendation
Replace the absolute value slippage parameters with a ratio-based approach that is resistant to partial withdrawals:

```solidity
// Setting both minAmount0 and minAmount1 to 0
(uint256 amount0, uint256 amount1) =
    IVault(up.vault).withdraw(up.shares, 0, 0);

uint256 ratio = amount0 * 1e18 / amount1;

require(liqParams.ratio - liqParams.tolerance <= ratio && liqParams.ratio + liqParams.tolerance >= ratio, "invalid ratio");
```

With this approach, liquidators would specify an expected ratio between the assets and a tolerance for deviation. This would be effective regardless of the absolute amounts in the position, making it resistant to partial withdrawals.
