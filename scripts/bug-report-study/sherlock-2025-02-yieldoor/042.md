# First vault depositor will bring DoS to the protocol and steal funds from forced depositing to Strategy

### Summary

First vault depositor can significantly skew token value ratio of Vault/Strategy, by depositing 0 `token0` and large amount of `token1`. Late depositors and leveragers cannot create positions due to underflow.
In order to bring back the system to be functional, the protocol team cannot help but deposit some amount of `token0` to Strategy contract. Ideally, `token0` and `token1` should have equal value in USD for maximum yield farming.
Then the attacker (first vault depositor) can withdraw from vault and steal part of forced deposited `token0`

### Root Cause

**First depositor can significanlty impact token balance ratio in Vault**

Let's take a look at [`Vault._calcDeposit`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L119-L151):

```solidity
    function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal
        view
        returns (uint256 shares, uint256 amount0, uint256 amount1)
    {
        uint256 totalSupply = totalSupply();

        // If total supply > 0, vault can't be empty
        assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired
            amount0 = depositAmount0;
            amount1 = depositAmount1;
            shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1;
        } else if (bal1 == 0) {
            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;
        } else {
            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
            amount0 = (cross - 1) / bal1 + 1;
            amount1 = (cross - 1) / bal0 + 1;
            shares = cross * totalSupply / bal0 / bal1;
        }
    }
```

Key takeaways are like the following:
- If `bal0 == 0`, then only `token1` can be deposited, and vice versa for `token0`
- `amount0` and `amount1` is set so that the ratio between `bal0` and `bal1` is maintained

Any deposit should follow the ratio set by the initial deposit. Moreover, if the first depositor deposits 0 `token0` and some amount of `token1`, subsequent depositors cannot deposit `token0`.

**In order for the protocol to function properly, `token0` and `token1` should have equal USD value**

Yieldoor yields from providing liquidity to Uniswap. To get maximized yield from Uniswap, you need to provide `token0` and `token1` so that their USD value ratio is nearly same as current exchange rate in Uniswap.

With that in mind, take a look at [`LiquidityAmounts.getLiquidityAmounts`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/LiquidityAmounts.sol#L58-L79) function:

Since final `liquidity` is take from min of `liquidity0` and `liquidity1`, if `amount0` is zero, final liquidity is always zero, and protocol cannot provide liquidity to Uniswap V3 Pool.


**When token value ratio is skewed, the only fix is to transfer tokens to Strategy to fix the ratio**

- Since `Vault.deposit` keeps the skewed value ratio, protocol team cannot fix the issue by depositing.
- Rebalancing and compounding do not work. They cannot fix skewed value ratio.

The only choice left for protocol team is to transferring `token0` to Strategy or create a vesting position to supply `token0`.

In either way, attacker benefits because they can withdraw corresponding amount of `token0` when they withdraw their share.

**Conclusion**

- Initial depositor (attacker) can significantly skew token value ratio of Vault.
- Subsequent depositors cannot but follow skewed token value ratio set by attacker
- Protocol works very inefficiently (or stops working in the worst case, see POC) due to skewed token value ratio
- In order to fix this, protocol team cannot but deposit some token to maintain token value ratio
- Attacker then can withdraw from Vault to steal foced deposited fund

### Attack Path

1. Attacker notices a new vault is being created.  
2. Attacker deposits 0 amount of `token0` and large amount of `token1` to Vault
3. The protocol suffers from skewed token vaule ratio
4. The protocol team deposits some `token0` to Strategy to mitigate the issue
5. Attacker withdraws from vault and steal `token0`

### Impact

- Protocol DoS due to underflow
- Extremely inefficient capital management due to skewed ratio
- Protocol fund loss to mitigate the issue

### PoC

**Scenario**

- Vault is created for `token0 = wbtc` and `token1 = usdc`
- Attacker (`user`) deposits 0 WBTC and 100k USDC
- Honest user (`depositor`) tries to create a leveraged position
  - `amount0In` = 0.5 WBTC
  - `amount1In` = 100k USDC
  - `vault0In` = 1 WBTC
  - `vault1In` = 100k USDC
  - `maxBorrowAmount` = 0.6 WBTC
  - `denomination` = WBTC
- Transaction reverts due to underflow (vault does not accept WBTC)
- In order to mitigate the issue, protocol team (`admin`) deposits 1 WBTC to `Strategy`
- `depositor` is able to create a leveraged position now
- Attacker (`user`) withdraws all shares from Vault and claims around 1 WBTC and 100k USDC

**Notes: Why underflow happens when opening a position**

Underflow happens on [calculating position's borrowed amount](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L171-L177):

```solidity
       uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
        ILendingPool(lendingPool).repay(lp.denomination, denomBalance);

        // if for some reason there have previously been a large amount of tokens "stuck", this could fail
        // this is ok as 1) its unlikely 2) anyone could sweep them 3) likely MEV bot would sweep them within seconds
        // Although opening positions is time-sensitive, please do not report this as a vulnerability, ty.
@>      up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
```

We have the following:

- `denomBalance = lp.maxBorrowAmount + lp.amount0In - a0`
- `a0` is always zero due to the token ratio skew attack, the vault deosn't accept `token0` deposit
- Thus, `denomBalance = lp.maxBorrowAmount + lp.amount0In > lp.maxBorrowAmount` and we have underflow error.

Notice that this underflow happens as long as `depositor` wants to use wbtc as denomiation. No matter how `depositor` tunes wbtc and usdc amounts and borrowed amounts, underflow will always happen. 


### Mitigation

The issue can be mitigated as the following:

- Create a VaultFactory or deploy script to create vault and do initial deposit in a single transaction
- Add a parameter for desired token balance ratio to Vault and rejects deposits that violates the ratio.
- Implement flexible token ratio in Vault. e.g. token ratio can be range instead of fixed one
