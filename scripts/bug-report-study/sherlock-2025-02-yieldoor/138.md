# The missing decimal normalization in `_calculateTokenValues` leads to inflated collateral valuations for tokens lacking a direct price feed, allowing borrowers to evade liquidation

### Summary

The Leverager contract's `_calculateTokenValues` function lacks proper handling of tokens with different decimal places, allowing someone to inflate their position’s USD value when a token without a direct price feed is converted through another token. In this scenario, the code uses the raw token amount and the pool price calculation without subtracting the missing decimal factor, effectively boosting the collateral’s perceived value.

### Root Cause

The issue comes from the fallback conversion path, [`Leverager:424`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L424) ,shown here in significantly simplified form:

```solidity
if (chPrice0 == 0) {
    // Convert token0->token1->USD using pool price
    usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
}
```

- `amount0`: Represents the raw balance of token0 (e.g., if token0 has 6 decimals, “1.0” token is 1,000,000 in raw integer form).  
-`price`: The pool’s TWAP price in 1e30 precision.  
- `chPrice1 / decimals1`: The conversion from token1’s quantity to USD.  

Because the code never divides by `token0`’s own decimal factor, an amount with fewer decimals is interpreted as though it matched `token1`’s (often 18 decimals). This decoupling can cause a token with only 6 decimals (like USDC) to be treated far more generously in valuation. For example, “1.0” USDC (raw integer 1,000,000) multiplied by a 1e30-scaled pool price can inflate the final USD value if token0’s decimals remain unaccounted for.

### Internal Pre-conditions

1. Protocol Governance fails to set a valid Chainlink price feed for the lower-decimal token (i.e., `chPrice0 == 0`).  
2. User chooses to deposit a token with fewer decimals as token0.  
3. The fallback pricing logic attempts to convert token0 → token1 → USD in `_calculateTokenValues()`, triggering the incorrect decimal handling.

### External Pre-conditions

There is sufficient market activity or liquidity to support the fallback TWAP pricing.

### Attack Path

1. A user deposits a token0 lacking a direct price feed (e.g., a 6-decimal stablecoin) as collateral.  
2. The protocol calls the fallback branch in `_calculateTokenValues()`, which fails to normalize token0’s decimal units.  
3. The user’s token0 amount is overvalued in USD terms, artificially inflating the collateral.  
4. The user borrows more than they should be permitted.

### Impact

This flawed calculation allows a position to seem overcollateralized, blocking legitimate liquidations. Attackers holding low-decimal tokens can accumulate artificially high “USD” balances, allowing them to borrow or remain safe from liquidation when they should be flagged as undercollateralized, ultimately leaving the protocol open to bad debt.

/**
 * @dev Test contract that exposes the internal _calculateTokenValues function
 * for testing purposes
 */
contract TestLeverager {
    address public immutable lendingPool;
    address public pricefeed;
    uint256 constant PRECISION = 1e30;
    
    constructor(address _lendingPool) {
        lendingPool = _lendingPool;
    }
    
    function setPriceFeed(address _priceFeed) external {
        pricefeed = _priceFeed;
    }
    
    /**
     * @notice Calculates the USD value of amount0 and amount1
     * @dev This is a copy of the vulnerable function from Leverager.sol
     */
    function calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
        public
        view
        returns (uint256 usdValue)
    {
        uint256 chPrice0;
        uint256 chPrice1;
        uint256 decimals0 = 10 ** ERC20(token0).decimals();
        uint256 decimals1 = 10 ** ERC20(token1).decimals();
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += amount0 * chPrice0 / decimals0;
        }
        if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
            chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
            usdValue += amount1 * chPrice1 / decimals1;
        }

        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }

        return usdValue;
    }
}

### Mitigation

The `_calculateTokenValues` function should be corrected to normalize `amount0` by its decimal places. A fixed version might look like:

```solidity
if (chPrice0 == 0) {
    uint256 token0Adjusted = amount0 * (10 ** decimals1) / (10 ** decimals0); // Normalize to token1 decimals
    usdValue += (token0Adjusted * price / PRECISION) * chPrice1 / decimals1;
}
```
- This ensures `token0`’s raw amount is properly scaled before conversion through the TWAP price.
- Similar logic should be applied to the `else if (chPrice1 == 0)` branch for consistency.
