# Faulty Remaining Debt Accounting for Position's `token0` Will Cause Direct Fund Loss for Liquidators When Liquidate Position

### Summary

Unaccounted swap outputs in debt calculation for position's `token0` will cause irreversible financial loss for liquidators, as the function `Leverager.liquidatePosition()` will force repayment of unmodified debt amounts after partial swap coverage. The missing reduction of `owedAmount` by swap from position's `token0` to borrowed denomination token during liquidation creates a discrepancy between actual debt coverage and required repayment, compelling liquidators to overpay borrowed tokens with no recovery mechanism.

### Root Cause

In function `Leverager.liquidatePosition()` ([`Leverager.sol#L355-L356`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L355-L356)), the liquidation debt calculation fails to account for swap outputs from position's `up.token0` to borrowed token, when determining remaining debt. The `owedAmount` variable is initialized as the full debt amount but not reduced by swap out amount for token conversions during liquidation. This is compounded by [`Leverager.sol#L355`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L355) executing swaps without tracking output amounts, and [`Leverager.sol#L369`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L369) enforcing liquidator to transfer the borrowed tokens with unmodified `owedAmount` as remaining debt.

The critical error manifests in four steps: 
1. Initial debt calculation using unadjusted `owedAmount`
2. Swap execution without output tracking to update `owedAmount`
3. Enforcing liquidator to transfer unmodified `owedAmount` as remaining debt
4. Final debt repayment using original `repayAmount`

This creates a discrepancy between the actual debt coverage achieved through swap and the protocol-enforced repayment amount, forcing liquidators to overpay unrecoverable funds.


### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

1. **Liquidator calls `Leverager.liquidatePosition()`** when a position becomes underwater, triggering vault shares withdrawal
2. **Swap parameters are executed** to convert withdrawn `up.token0` to borrowed denomination token, but swap outputs aren't tracked
3. **Debt calculation uses original owed amount** despite partial repayment through swap
4. **Liquidator is forced to transfer full owedAmount** of borrowed tokens regardless of swap coverage

### Impact

The liquidator suffers direct loss of funds equal to the swap output amounts, as they must repay the original debt value despite partial coverage through swap. This creates:

1. **Permanent loss of borrowed tokens** transferred via `safeTransferFrom` that exceed actual remaining debt
2. **Protocol liquidity risk** as liquidators are disincentivized from performing critical liquidations

This qualifies as **High Severity** due to irreversible financial loss in a core protocol mechanism with no recovery pathway, directly violating the "No forced loss of funds" principle.

### Mitigation

**Track swap outputs** during liquidation processing:

```diff

                abi.decode(liqParams.swapParams1, (IMainnetRouter.ExactInputParams));
            if (swapParams.amountIn > 0) {
                (address tokenIn,,) = swapParams.path.decodeFirstPool();

                IERC20(up.token0).forceApprove(swapRouter, swapParams.amountIn);
-               IMainnetRouter(swapRouter).exactInput(swapParams); // does not support sqrtPriceLimit
+               uint256 swapOut = IMainnetRouter(swapRouter).exactInput(swapParams); // does not support sqrtPriceLimit
+               owedAmount -= swapOut;
                amount0 -= swapParams.amountIn;
            }
```

This ensures debt repayment precisely matches the remaining obligation after swap conversions, eliminating forced overpayments while maintaining protocol safety.
