# Attacker Will Drain 99% of Future Deposits for LPs via First Deposit Manipulation

### Summary

The flawed initial share calculation in Vault.sol will cause near-total loss for subsequent liquidity providers (LPs) as an attacker will deposit dust amounts to mint 99%+ of vault shares.

### Root Cause

In Vault.sol, The deposit function's share calculation when the vault is empty could allow a first depositor to mint a large number of shares with a minimal deposit. The code subtracts 1000 wei, but if the initial deposit is just over that, the attacker could still gain a disproportionate share. For example, depositing 1001 wei of one token would result in 1 share (1001 - 1000), and subsequent depositors would have their shares calculated based on that initial tiny liquidity.

In Vault.sol#_calcDeposit() function:

The protocol subtracts a fixed value (1000 wei) from the larger deposit amount to calculate initial shares, enabling attackers to mint near-infinite shares with minimal deposits.

### Internal Pre-conditions

1. Vault totalSupply must be zero (first deposit)
2. No minimum deposit check exists for initial deposit
3. Token decimals allow fractional deposits (e.g., 18 decimals)
4. Attacker needs <$0.01 capital

### External Pre-conditions

1. No front-running protection exists
2. Protocol allows deposits of any size

### Attack Path

1. Attacker deposits 1 wei of token0 and 1001 wei of token1
2. Vault mints 1 share (1001 - 1000 = 1)
3. Legitimate user deposits 1000e18 tokens of both
4. Vault calculates: shares = (1000e18 * 1000e18 * 1) / (1 * 1001) ≈ 1e33 shares (0.0001% of total)  
5. Attacker owns 99.99% shares → withdraws 99.99% of future deposits

### Impact

1. Subsequent LPs lose 99%+ of deposited value
2. Attacker gains 99%+ of all future yields
