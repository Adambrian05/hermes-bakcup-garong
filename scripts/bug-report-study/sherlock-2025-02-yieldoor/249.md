# whitelisted asset  oversight will allow unauthorized assets to be deposited

### Summary

The missing asset whitelist check in the `LendingPool` contract will cause an unauthorized asset to be deposited for lenders as an attacker will supply unapproved tokens.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L70

### Root Cause

In `LendingPool.sol` the asset initialization and deposit functions do not verify if the asset has been whitelisted by the protocol’s governance. This is a mistake in the code because it allows any asset to be deposited even if it has not been approved, and without an associated `pricefeed`, borrowing and lending operations can be manipulated.

### Internal Pre-conditions

There are not special pre conditions or post conditions  for this vulnerability to come is play if protocol is deployed without mitigation then attack can be performed.

### External Pre-conditions

There are not special pre conditions or post conditions  for this vulnerability to come is play if protocol is deployed without mitigation then attack can be performed

### Attack Path

1. An attacker calls initReserve(asset) with an asset that is not whitelisted by governance.

2. The LendingPool initializes the reserve and deploys a new yToken for the asset, even though it is not approved.

3. The attacker deposits the unapproved asset via the deposit() function, receiving yTokens.

4. With no valid pricefeed in place, the attacker can manipulate borrowing operations (or force a failure in repayments), potentially draining funds or causing a denial of service for legitimate lenders.

### Impact


Lenders suffer an approximate loss of funds or exposure to manipulated asset valuations. In a worst-case scenario, the attacker gains the ability to borrow against an asset with no reliable price feed, which could lead to under-collateralization and losses for the protocol and its lenders.

1. The attacker supplies an asset that is not whitelisted by governance.
2. The asset does not have a valid pricefeed set up.
3. External market conditions allow the attacker to manipulate the value of the unapproved asset.
4. Users and other protocols interacting with the LendingPool assume that only governance-approved assets are used.

### Mitigation

 Introduce a whitelist mapping in the LendingPool contract that only allows assets approved by governance to be initialized. Before initializing a reserve in initReserve and before accepting a deposit in deposit, add a check:

```solidity

require(isWhitelisted[asset], "Asset not whitelisted");

```

This ensures that only assets vetted by governance with a proper pricefeed are accepted and this should specially be implemented in lendingpool's deposit function as if an asset is blocked from depositing into the pool then its not available for other operations.
