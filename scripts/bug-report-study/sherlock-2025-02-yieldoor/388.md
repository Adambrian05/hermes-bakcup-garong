# Rebalancer can manipulate tick ranges to cause instant fund release and owner fund loss


## Summary
The lack of tick range validation and fund refund mechanism in `addVestingPosition()` will cause a loss of funds for owners as rebalancers can manipulate the tick ranges to prevent proper vesting and cause immediate fund release.

## Root Cause
In [`Strategy.sol#L426-L456`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L426-L456), the `addVestingPosition()` function has two critical issues:

1. It uses the main position's tick range without validation
2. It doesn't refund unused tokens after liquidity provision

```solidity
    function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _vestDuration) external onlyVault {
        collectFees(); // we collect fees first, in case there hasn't been a call since previous vested position ended
        require(!ongoingVestingPosition, "there's a currently ongoing VestingPosition");

        _requirePriceWithinRange();
        VestingPosition memory vp;

        vp.tickLower = mainPosition.tickLower;
        vp.tickUpper = mainPosition.tickUpper;

        (uint160 sqrtPrice,,,,,,) = IUniswapV3Pool(pool).slot0();
        uint128 liquidity = LiquidityAmounts.getLiquidityForAmounts(
            sqrtPrice,
            TickMath.getSqrtRatioAtTick(vp.tickLower),
            TickMath.getSqrtRatioAtTick(vp.tickUpper),
            amount0,
            amount1
        );

        vp.initialLiquidity = liquidity;
        vp.remainingLiquidity = liquidity;

        IUniswapV3Pool(pool).mint(address(this), vp.tickLower, vp.tickUpper, liquidity, "");

        vp.startTs = block.timestamp;
        vp.lastUpdate = block.timestamp;
        ongoingVestingPosition = true;
        vp.endTs = block.timestamp + _vestDuration;

        vestPosition = vp;
    }
```

The function uses `mainPosition.tickLower` and `mainPosition.tickUpper` without any validation, which can be manipulated by the rebalancer. Additionally, any tokens not used for liquidity provision remain idle in the strategy contract instead of being returned to the owner.

## Internal pre-conditions
1. `rebalanceInterval` has elapsed since `lastRebalance`
2. No ongoing vesting position exists

## External pre-conditions
1. Pool price is stable for the TWAP duration
2. Current tick is significantly distant from the center of main position's tick range

## Attack Path
1. Rebalancer monitors for `addVestingPosition` transactions in the mempool
2. When detected, rebalancer frontruns with a rebalance operation that shifts the main position's tick range
3. Owner's `addVestingPosition` transaction executes with the new unexpected tick range
4. Less liquidity than intended is added to the vesting position
5. Excess funds remain idle in the strategy, effectively releasing them instantly instead of following the vesting schedule

## Impact
The owner suffers two types of losses:
1. Immediate loss of funds that remain idle in the strategy instead of being properly vested
2. Vulnerability to rebalancer manipulation that can force instant fund release instead of gradual vesting

## Mitigation
Two changes are required:
1. Allow owners to specify their own tick ranges for vesting positions
2. Add refund logic for unused tokens
