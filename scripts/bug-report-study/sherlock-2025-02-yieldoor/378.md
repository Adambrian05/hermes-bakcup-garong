# The `Leverager::_calculateTokenValues` function incorrectly calculates `usdValue` when one of the tokens doesn't have a price feed.

### Summary

An error exists in the `_calculateTokenValues` function within the Leverager contract. When one of the tokens in a pair lacks a price feed, the function incorrectly converts token values due to improper handling of token decimal differences. This can lead to significant undervaluation or overvaluation of positions, potentially allowing position manipulations, incorrect liquidations, or excess borrowing beyond intended risk parameters.


### Root Cause

The bug occurs in the `_calculateTokenValues` function's token conversion logic:

```solidity
if (chPrice0 == 0) {
    usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
} else if (chPrice1 == 0) {
    usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
}
```
https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L444

The conversion between tokens fails to account for the decimal differences between the tokens. For example, when converting from WBTC (8 decimals) to USDC (6 decimals), a 100x factor error is introduced. This error results in significant miscalculations when one token's price feed is unavailable.


### Internal Pre-conditions

1. The function must be calculating the value of a position that includes tokens with different decimal places (WBTC with 8 decimals and USDC with 6 decimals).
2. The protocol must be operating in a degraded state where one of the token's price feeds is unavailable.


### External Pre-conditions

1. The price feed for one of the tokens in a pair becomes unavailable, which could happen for several reasons:
   - Chainlink oracle maintenance or technical issues
   - Deliberate disabling of price feeds by protocol administrators
   - Network congestion affecting oracle updates


### Attack Path

1. An attacker monitors the price feeds used by the protocol.
2. When a price feed for a token becomes unavailable (particularly the token with higher decimals, like BTC):
   - The attacker can open positions that will be significantly overvalued
   - This allows them to borrow substantially more than would normally be permitted
3. When the price feed returns, the attacker's position is correctly valued, but they've already extracted excess value from the protocol.


### Impact

1. Positions could be liquidated prematurely when they should remain solvent
2. Users could borrow far more than intended risk parameters allow
3. The combination of incorrect liquidations and excess borrowing could lead to bad debt and protocol insolvency

### Mitigation

The fix requires properly accounting for token decimal differences during conversion:

```solidity
if (chPrice0 == 0) {
    // Token0 doesn't have price feed, convert via token1
    uint256 token0InToken1 = amount0 * price * decimals1 / (PRECISION * decimals0);
    usdValue += token0InToken1 * chPrice1 / decimals1;
} else if (chPrice1 == 0) {
    // Token1 doesn't have price feed, convert via token0
    uint256 token1InToken0 = amount1 * PRECISION * decimals0 / (price * decimals1);
    usdValue += token1InToken0 * chPrice0 / decimals0;
}
```

This corrected implementation properly scales the conversion by the ratio of decimal places between the tokens, ensuring accurate valuations regardless of which price feed is available.
