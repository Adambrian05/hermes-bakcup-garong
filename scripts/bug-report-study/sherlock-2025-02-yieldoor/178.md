# DoS the flow of checking pool activity

### Summary

The logic to check pool prices in consecutive observations can be OOG if the values of cardinality and twap are high.

### Root Cause

The [function `Strategy::checkPoolActivity()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310-L342) checks pool prices in consecutive observations to enforce the price is not deviated more than allowed, and up to `twap` ago. In worst case, the function will have to handle `observationCardinality` loops, with `observationCardinality` is the current maximum number of observations that are being stored in Univ3 pool. Indeed, this `observationCardinality` value can be increased up to maximum `65535`, which is executed by the logic from Univ3 Pool [function increaseObservationCardinalityNext()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L255-L267). 

So there exists a scenario that both `twap` and `observationCardinality` are high enough to cause out of gas error. For numerical example, `twap = 300` (5 mins, default value), with Arbitrum avg block time of 0.25s ([ref](https://dune.com/jacobdcastro/avg-block-times)), an attacker can increase pool's `observationCardinality` to `300 / 0.25 = 1200` to force the function `checkPoolActivity()` to loop over 1200 loops, which consumes more than 6M gas for the function `rebalance()`
```solidity
    function checkPoolActivity() public view returns (bool) {
@>        (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();

        uint32 lookAgo = uint32(block.timestamp) - twap;

        (uint32 nextTimestamp, int56 nextCumulativeTick,,) = IUniswapV3Pool(pool).observations(currentIndex);

        int24 nextTick = tick;

@>        for (uint16 i = 1; i <= observationCardinality; i++) { // <--- total loop = observationCardinality
            uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
            (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
            if (timestamp == 0) {
                revert("timestamp 0");
            }

            tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));

            (nextTimestamp, nextCumulativeTick) = (timestamp, tickCumulative);
            int24 delta = nextTick - tick;

            if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
                return false;
            }

            if (timestamp < lookAgo) {
                return true;
            }
            nextTick = tick;
        }

        return false;
    }
```

### Attack Path

1. An attacker calls Univ3's `increaseObservationCardinalityNext(<value>)`
2. At each block, the attacker add a very small liquidity in-range so that the observations are updated. Repeat until the pool's `observationCardinality` reaches `<value>`
3. Users can be unable to open leverage. OR positions will be unable to be rebalanced

### Impact

- The logic to check pool activity can be OOG
- The flow of rebalance, compound, open leverage can be DoS
