# Balance Manipulation will DoS the Whole Contract

### Summary

The vulnerability was found in the Leverager.sol [contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L21)

The developer has stated that this will not affect the system badly, but he has overlooked some really important details. 

The issue occurs in the openLeveragedPosition function, where the contract calculates how much was actually borrowed by using this logic: 

`=> uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));

ILendingPool(lendingPool).repay(lp.denomination, denomBalance);

=> up.borrowedAmount = lp.maxBorrowAmount - denomBalance;` // @audit this will always underflow

The mitigation that the developer has provided will not work:
// this is ok as 1) its unlikely 2) anyone could sweep them 3) likely MEV bot would sweep them within seconds

Let me explain why...

balanceOf address this can easily be manipulated, the _sweepTokens function WILL NOT work because:
1. It is called in the end of the openLeveragedPosition() function after the underflow vulnerability
2. It is an internal function that can be only called by openLeveragedPosition() and is not integrated into the ILeverager interface


The contract will ALWAYS fail if extra tokens are send to the contract, leading to DoS to the entire system without a way of sweeping the tokens out.

### Root Cause

How the function works:

1. The user is required to provide maxBorrowAmount, if a user or a bot for example tries to set maxBorrowAmount to zero to just try to sweep the tokens out of the contract this happens:
// line 171
denomBalance will be:
uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this)); 

We will try to calculate uint256 borrowedAmount with this denomBalance

// line 177
uint256 (up.borrowedAmount) = uint256 (lp.maxBorrowAmount = 0) - uint256 (denomBalance); 

The function will always revert because we expect borrowedAmount to be uint and the contract will most likely in some point of time have some leftover funds in it or an attacker will have already send funds to the contract.

2.How will an attack work:

The attacker will send the denomination token into the contract.

// line 103
A user will try to call openLeveragedPosition() 

Because we borrow the maxBorrowAmount from the LendingPool this automatically increases the balanceOf(address)this:

// line 135
 ILendingPool(lendingPool).borrow(lp.denomination, lp.maxBorrowAmount); // increased balance of the contract 

After that the contract hits this line and SET the denomBalance just before we repay

// line 171
  uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));

We repay in the next line:
ILendingPool(lendingPool).repay(lp.denomination, denomBalance);

After that the contract hits this line:

up.borrowedAmount = lp.maxBorrowAmount - denomBalance; 

Now the denomBalance is the maxBorrowAmount + balanceOf(address)this before the repay function was called
This causes an underflow

A user can set maxBorrowAmount to however high he wants and he will still not be able to bypass the underflow.




### Internal Pre-conditions

1. An attacker just needs to send some denomination tokens into the contract


### External Pre-conditions

1.none

### Attack Path

1.The attacker transfers an extra amount of the denomination token directly into the Leverager contract (using a simple ERC20 transfer).

### Impact

Legitimate users trying to open leveraged positions will face unexpected transaction reverts 

The contract's most important function will be DoS-ed

### Mitigation

Before you borrow denomBalance set it to the balanceOf(address)this

Also it will be a good practice to restrict or flag any tokens that do not originate from the expected flashloan or deposit process and get rid of balanceOf(address)this
