# pullFunds

https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L209
A close look reveals that the biggest logical gap is in the **`pullFunds`** (and, by extension, `pushFunds`) function. Unlike the `borrow` and `repay` paths, **`pullFunds`** and **`pushFunds`** do **not** update any of the reserve’s accounting variables (`underlyingBalance`, `totalBorrows`, etc.) or re‐compute interest rates. That means a leverager could call:

```solidity
pullFunds(asset, X);
```

…withdraw real tokens from the pool’s `yToken` contract, but the system’s internal accounting (such as `reserve.underlyingBalance`) never decreases. Likewise, `pushFunds` does not increase it. Because interest calculations, capacity checks, and “available liquidity” all rely on `underlyingBalance` (and related) staying in sync with actual token flows, letting someone pull tokens without state updates is an obvious loophole.

In contrast, look at how `borrow` is handled:

```solidity
function borrow(address asset, uint256 amount) external {
    ...
    // update states
    reserve.updateState();
    
    // check liquidity, update totalBorrows and underlyingBalance
    reserve.totalBorrows += amount;
    reserve.underlyingBalance -= amount;
    
    // move tokens out of yToken
    IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
    
    // update interest rates
    reserve.updateInterestRates();
}
```

Notice that **all** the relevant internal accounting and interest‐rate logic is triggered. By contrast, `pullFunds` simply does:

```solidity
function pullFunds(address asset, uint256 amount) external {
    require(msg.sender == leverager, "borrower not leverager");
    DataTypes.ReserveData memory reserve = getReserve(asset);

    // no state/accounting changes here!
    IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
}
```

Nothing is updated; the pool’s view of how many tokens remain in the system stays the same. In practice, this defeats the careful checks the contract enforces for normal `borrow`, `deposit`, and `redeem` operations.

### Why is that a problem?

- **Available Liquidity Mismatch**: Users who come to `redeem` may discover the tokens are gone if the leverager never “pushed” them back, yet the pool thinks they are still there (since `underlyingBalance` was never decremented).
- **Interest and Utilization Rate Mispricing**: Because the internal logic thinks there is more liquidity than actually remains, the utilization rate is understated and the borrowing rates are mispriced.

### What could be done?

If `pullFunds` / `pushFunds` is truly needed for a leverage workflow (e.g., temporarily taking tokens out to deploy somewhere and then returning them in the same transaction), the contract should:

1. **Update `reserve.underlyingBalance`** (and possibly `totalBorrows` if relevant) upon pull/push.  
2. **Recompute rates** or at least run `reserve.updateInterestRates()` so that depositors and borrowers see the correct borrowing costs and utilization.
