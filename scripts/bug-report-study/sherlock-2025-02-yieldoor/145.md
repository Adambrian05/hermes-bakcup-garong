# [H-2] - `Leverager::liquidatePosition` function incorrect decimals scaling leads to loss of funds for the protocol

### Summary

In the `liquidatePosition` [function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L299) of the `Leverager` contract, the borrowed USD value (`borrowedValue`) is calculated using the expression:

```javascript
uint256 borrowedValue = owedAmount * bPrice / ERC20(up.denomination).decimals();
```

The issue is that both `owedAmount` and `bPrice` are scaled to the appropriate number of decimals that the underlying asset has (i.e. 1e18 for `weth` for example), but we divide the result of the multiplication by the raw numeric value returned by the `decimals()` function. This leads to an incorrect scaling factor when computing the [borrowed USD value](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L318C9-L318C89).

We can look at the `openLeveragedPosition` function to see how different state variables are computed and we'll also look specifically at how `initBorrowedUsd` is computed:

```javascript
    function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {
//..
//..
//@audit all these variables will have 10 ** {decimals} scaling
        up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price); // returns the USD price in 1e18
        uint256 bPrice = IPriceFeed(pricefeed).getPrice(lp.denomination);
        up.initCollateralValue = (up.initCollateralUsd * (10 ** ERC20(lp.denomination).decimals())) / bPrice;
//..
//..
//@audit this variable is computed with 10 ** {decimals} scaling
        up.initBorrowedUsd = (up.borrowedAmount * bPrice) / (10 ** ERC20(lp.denomination).decimals());
//..
//..
    }
```

Now let's check the code inside the `liquidatePosition` function:

```javascript
    function liquidatePosition(LiquidateParams calldata liqParams) external collectFees(liqParams.id) nonReentrant {
//..
//@audit `owedAmount` is computed based on `borrowedAmount`. Let's assume 1e18 scaling for `borrowedAmount`
        uint256 owedAmount = (up.borrowedAmount * currBIndex) / up.borrowedIndex;
//..
//..
//@audit `bPrice` will also have 1e18 scaling in this case returned by the oracle
        uint256 bPrice = IPriceFeed(pricefeed).getPrice(up.denomination);
//@audit-issue `borrowedValue` will be inflated
//(owedAmount * bPrice) => some number with 1e36 precision, but we divide by 18 instead of 1e18
        uint256 borrowedValue = (owedAmount * bPrice) / ERC20(up.denomination).decimals();

//@audit-issue because `borrowedValue` is inflated this `if` block will not be true and the protocol will not get any fees
        if (totalValueUSD > borrowedValue) {
            // What % of the amountsOut are profit is calculated by `(totalValueUSD - borrowedUSD) / totalValueUSD`
            // Then, on top of that, we calculate the protocol fee and scale it in 1e18.

            uint256 protocolFeePct = (1e18 * liquidationFee * (totalValueUSD - borrowedValue)) / (totalValueUSD * 10_000);
            uint256 pf0 = (protocolFeePct * amount0) / 1e18;
            uint256 pf1 = (protocolFeePct * amount1) / 1e18;

            if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0);
            if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1);
            amount0 -= pf0;
            amount1 -= pf1;
        }
//..
//..
    }
```

The issue is that `borrowedValue` will have 1e18 more decimals than intended (or whatever decimals the underlying token uses) and the if statement `if (totalValueUSD > borrowedValue)` will be `false` although it should've been `true`. In these cases the protocol will not receive fees during liquidations, leading to a direct loss of funds for the protocol.


### Root Cause

Misinterpretation of the token decimals. The intent is to convert the borrowed amount of tokens into its USD equivalent by adjusting for the token’s decimal precision. However, the actual code implementation erroneously divides by the number of decimals (an integer like 8 or 18) rather than by 10 raised to the power of `decimals`, resulting in a borrowed value that is off by a factor of 10 ** decimals.

None

### External Pre-conditions

None

### Attack Path

This can occur during normal usage of the protocol.

### Impact

- Loss of funds for the protocol. When this bug occurs, the protocol will not receive fees, although it should have.

### Mitigation

```diff
-       uint256 borrowedValue = (owedAmount * bPrice) / ERC20(up.denomination).decimals();
+       uint256 borrowedValue = (owedAmount * bPrice) / 10 ** ERC20(up.denomination).decimals();
```
