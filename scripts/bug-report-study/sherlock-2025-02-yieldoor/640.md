# Opening Leveraged Position with Zero Deposit Amounts Allows Risk-Free Exploitation

### Summary

The missing check in openLeveragedPosition will cause financial loss and potential bad debt for the protocol as an attacker will open leveraged positions with zero deposits.



### Root Cause

In openLeveragedPosition function in the Leverager contract, there is a missing check on lp.amount0In and lp.amount1In, allowing users to specify zero amounts for both inputs while still borrowing funds and opening a position.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L103-L201



### Internal Pre-conditions

A numbered list of conditions to allow the attack path or vulnerability path to happen:

1. Governance needs to whitelist a vault to set vaultParams[lp.vault].leverageEnabled to be exactly true.

2. LendingPool needs to have available funds to allow ILendingPool(lendingPool).pullFunds to borrow at least delta0 or delta1 (calculated as lp.vault0In - lp.amount0In and lp.vault1In - lp.amount1In) when the user sets lp.amount0In and lp.amount1In to exactly 0.

3. The vault’s deposit function needs to return non-zero shares to allow the position to be opened successfully.



### External Pre-conditions

Similar to internal pre-conditions but describes changes in the external protocols:
1. The price feed (IPriceFeed) or TWAP (IVault(lp.vault).twapPrice()) needs to provide a stable price to pass the checkPoolActivity volatility check in openLeveragedPosition.

2. The external swap pool (used by IMainnetRouter.exactOutput) needs to have sufficient liquidity to execute swaps when converting borrowed funds to vault tokens.



### Attack Path

A numbered list of steps, talking through the attack path:
1. Attacker calls openLeveragedPosition with lp.amount0In and lp.amount1In set to 0, lp.vault0In and lp.vault1In set to non-zero values (e.g., 0.5 WBTC and 1000 USDC), and lp.maxBorrowAmount set to a high value (e.g., 20,000 USDC).

2. The contract borrows funds (delta0 and delta1) from the LendingPool to cover the vault deposit since the user provided no tokens.

3. The contract deposits the borrowed funds into the vault via IVault(lp.vault).deposit, receiving vault shares for the position.

4. The attacker performs swaps (if needed) using borrowed funds to meet vault deposit requirements, potentially manipulating prices to maximize profit.

5. If the position gains value (e.g., due to price movements or yield farming rewards), the attacker withdraws the profits without having risked any of their own funds.

6. If the position incurs a loss, the attacker abandons the position, leaving the protocol to cover the loss through liquidation or bad debt.



### Impact

In case it's an attack path: The protocol suffers an approximate loss proportional to the position’s loss value if the position becomes underwater. The attacker gains any profits accrued from the position without risking their own funds.

### Mitigation

Add a check in openLeveragedPosition to ensure that at least one of lp.amount0In or lp.amount1In is non-zero, enforcing that the user has some "skin in the game" and shares in both potential profits and losses. Example mitigation code:
solidity

require(lp.amount0In > 0 || lp.amount1In > 0, "must provide at least one token");

Alternatively, introduce a minimum collateral ratio or deposit amount relative to the borrowed funds:
solidity

uint256 totalInputUSD = _calculateTokenValues(up.token0, up.token1, lp.amount0In, lp.amount1In, price);
uint256 borrowedUSD = lp.maxBorrowAmount * bPrice / (10 ** ERC20(lp.denomination).decimals());
require(totalInputUSD >= borrowedUSD * minCollateralRatio / 1e18, "insufficient collateral");
