# Division by Zero in Interest Rate Calculation








#### **Summary**
A critical vulnerability exists where setting the `utilizationB` parameter to 100% (1e27 in precision) cause a **division-by-zero error** in the interest rate calculation. This stop all borrowing/lending operations for the affected asset in the `LendingPool`.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L241-L259



https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/InterestRateUtils.sol#L19-L44

## Description
The `InterestRateUtils` library computes borrowing rates using three utilization rate segments. If `utilizationB` (the upper bound of the second segment) is set to 100% (PRECISION = 1e27), the third segment calculation divide by `(PRECISION - utilizationB)`, resulting in **division by zero** when `utilizationB = PRECISION`.

**Affected Code Snippets**
1. **LendingPool Configuration**  
   `utilizationB` is converted from basis points (10,000 = 100%) to PRECISION (1e27):
   ```solidity
  
   function setBorrowingRateConfig(......) internal {
       reserve.borrowingRateConfig.utilizationB = PRECISION * utilizationB / 10_000; //audit:Converts 10,000 to 1e27
   }
   ```

2. **Interest Rate Calculation**  
   The third segment divide by `(PRECISION - utilizationB)` which become zero:
   ```solidity
   
   function calculateBorrowingRate(.......) {
       // ......
       borrowingRate = (config.maxBorrowingRate - config.borrowingRateB) 
           * (utilizationRate - config.utilizationB) 
           / (PRECISION - config.utilizationB) //audit: Division by zero if utilizationB = PRECISION
           + config.borrowingRateB;
   }
   ```



## Impact
- Borrowing, lending and withdrawals for the asset freeze.
- Users cannot interact with the affected pool leading to loss of funds or trust.



## Proof of Concept 
1. **Admin Misconfiguration**  
   An admin configures `utilizationB` to 100%:
   ```solidity
   lendingPool.setBorrowingRateConfig(
       asset,
       8000,  // utilizationA = 80%
       2000,  // borrowingRateA = 20%
       10000, // utilizationB = 100% (invalid)
       5000,  // borrowingRateB = 50%
       15000  // maxBorrowingRate = 150%
   );
   ```

2. **Utilization Reaches 100%**  
   Borrowers exhaust liquidity, triggering `utilizationRate = PRECISION`.

3. **Division by Zero**  
   The third segment calculation fail:
   ```solidity
   (15000e27 - 5000e27) * (1e27 - 1e27) / (1e27 - 1e27) resulting to  Division by zero.
   ```



## Recommendation
Add validation in the `setBorrowingRateConfig()`:
1. `utilizationA < utilizationB` to prevent invalid segments
2. `utilizationB < 100%` to avoid division by zero
```solidity

function setBorrowingRateConfig(
    address asset,
    uint16 utilizationA,
    uint16 borrowingRateA,
    uint16 utilizationB,
    uint16 borrowingRateB,
    uint16 maxBorrowingRate
) public onlyOwner notPaused {
    DataTypes.ReserveData storage reserve = reserves[asset];
    
    require(utilizationA < utilizationB, "utilizationA must be < utilizationB");
    require(utilizationB < 10_000, "utilizationB cannot be 100%");

    setBorrowingRateConfig(reserve, utilizationA, borrowingRateA, utilizationB, borrowingRateB, maxBorrowingRate);
}
```

The fix make sure that it :
Prevent Invalid Configurations to ensure `utilizationB` cannot reach 100%.
And also avoid Zero Division to guarantee `(PRECISION - utilizationB) > 0` in calculations.
