# First Depositor Loss Due to Underflow in Vault



## Summary 
The calculation of shares mint zero because of underflow if the initial deposit is small causing the user to lose fund as this prevent the Vault from initializing properly.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L129-L133

## Description
The Vault deposit function mint shares to users based on their deposited token amounts. For the first depositor, shares are calculated as (max(amount0, amount1) - 1000) where 1000 shares are burned to mitigate inflation attack but if the user deposits ≤1000 wei of either token, the subtraction underflows resulting in zero shares causing the user to lose their deposited tokens.

## Vulnerability Details

 

**Code Logic**  
The Vault deposit function calculate shares for the first depositor as follows:  
```solidity
if (totalSupply == 0) {
    shares = (amount0 > amount1 ? amount0 : amount1) - 1000; //audit@ it might underflow 
}
```  
After calculating shares, the code mint 1000 shares to the burn address:  
```solidity
if (totalSupply() == 0) _mint(BURN, 1000); // Burn 1000 shares
```  

Then this is where the vulnerability start: 
- Underflow Trigger:  
  ```solidity
  shares = (amount0 > amount1 ? amount0 : amount1) - 1000; // Subtracts 1000 from max(amount0, amount1)
  ```  
  If max(amount0, amount1) ≤ 1000, this operation underflow for example 1000 - 1000 = 0.
- Burn Minting:  
  ```solidity
  if (totalSupply() == 0) _mint(BURN, 1000); // Mint 1000 shares to burn address
  ```  
  This occur after calculating the user’s shares thereby locking the user out.  


 ## Proof of Concept
1. Deploy Vault: totalSupply = 0.
2. First Deposit:  
   ```solidity
   deposit(1000 wei token0, 500 wei token1);  
   ``` 
3. Share Calculation: 
   max(1000, 500) = 1000
   burn shares = 1000 - 1000 = 0 
4. Token Transfers:
   1000 wei token0 and 500 wei token1 are sent to the Strategy.  
5. Share Minting:  
   _mint(BURN, 1000) -> Burn address gets 1000 shares.  
   _mint(user, 0) -> User gets 0 shares.  
6. Then the outcome is :
   User’s balance: 0 shares  
   Burn address balance: 1000 shares.  
   User cannot withdraw tokens.

Now consider this scenario  of :
First Deposit: A user deposit 1000 wei of token0 and 
500 wei of token1.  
 Share Calculation: 
   max(1000, 500) = 1000  
   shares = 1000 - 1000 = 0
so the result is that:
  - The user receive 0 shares but the burn address receive 1000 shares.  
  - The user’s deposited tokens 1000 wei of token0 and 500 wei of token1 are sent to the Strategy contract.  
  - The user cannot redeem any tokens because of the 0 shares.  
  -

## **Impact**  
The user lose their deposited tokens but receive no shares.  
The Vault totalSupply becomes 1000 (burn shares) + 0 (user shares) = 1000 but the user cannot withdraw tokens. 

## Recommendation 
 Correct the deposit logic :
```solidity
if (totalSupply == 0) {
    _mint(BURN, 1000); // Mint burn shares first
    shares = amount0 + amount1; // User shares = sum of deposits
}
```  

Let me explain the fix code:  

The Deposit should be 1000 wei token0 + 500 wei token1 -> 1500 user shares.

So the Total Supply is 1000 (burn) + 1500 (user) = 2500.

Then the User owns 60% of the Vault and can withdraw fairly.
