# Inevitable loss of fees due to pool natural price movement since vault creation

### Summary

The [vault](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L11) takes user deposits and sends them to the strategy, where a main and a secondary positions are created. The purpose of the strategy is farming fees, which are only farmed when the liquidity is added to an active tick in the uniswap pool. Thus, the main position allocates liquidity symetrically to the left and right of the current uniswap tick, and whatever amount is left of one of the tokens, is deposited in the secondary position, which earns no fees but there is still a chance that may be crossed and earns some fees.

As such, the more liquidity the main position has, the more fees the pool captures. Consequently, it's vital that the strategy/vault is able to allocate most of its liquidity to the main position. However, currently there is no way to swap the amount of tokens or deposit at a different ratio to rebalance the pool in a way that most of the liquidity is allocated to the main position.

This means that, whenever the price of the pool moves since the pool was created, more and more liquidity will be idle in the secondary position instead of accruing fees in the main position. For example, if we created a USDC WBTC vault, and added liquidity at a price of 50k WBTC, we would have approximately 50000 USDC per WBTC. As the price of WBTC moves to, let's say 80k, we have to allocate 80000 USDC per WBTC, but the vault balances will always be extremely off and not according to this ratio, allocating most of the liquidity to the secondary position which does not accrue fees (it may accrue some, but much less).

### Root Cause

There is no way to change the balances ratio of the vault, so more and more liquidity will be allocated to the secondary position which does not earn fees.

### Internal Pre-conditions

None.

### External Pre-conditions

Uniswap pool price moves.

### Attack Path

1. Users deposit in the vault at a certain price.
2. Uniswap pool price changes.
3. Vault does not adapt and most liquidity goes to the secondary position which does not earn fees.

### Impact

Loss of fees.

### PoC

The main position initially allocates all wbtc and 98% of the USDC to the main position.
Due to a 2 million usdc swap, after rebalance, the position allocates only 53% of the USDC to the main position.
The price only moved `67913 - 67866 = 47` ticks or 0.47%.
Forked mainnet at block 21926419.

```solidity
    function test_POC_NoLongerCollectsFees() public {
        vm.startPrank(depositor);
        deal(address(wbtc), depositor, 1e8);
        deal(address(usdc), depositor, 100_000e6);

        wbtc.approve(vault, type(uint256).max);
        usdc.approve(vault, type(uint256).max);

        (, uint256 amount0In, uint256 amount1In) = IVault(vault).deposit(1e8, 100_000e6, 0, 0);
        assertEq(amount0In, wbtc.balanceOf(strategy));
        assertEq(amount1In, usdc.balanceOf(strategy));

        uint256 amountToSwap = 2_000_000e6;
        deal(address(usdc), depositor, amountToSwap);
        IMainnetRouter.ExactInputSingleParams memory swapParams;
        swapParams.tokenIn = address(usdc);
        swapParams.tokenOut = address(wbtc);
        swapParams.deadline = block.timestamp;
        swapParams.recipient = depositor;
        swapParams.fee = 3000;
        swapParams.amountIn = amountToSwap;
        usdc.approve(uniRouter, amountToSwap);
        IMainnetRouter(uniRouter).exactInputSingle(swapParams);

        vm.startPrank(rebalancer);
        skip(10 minutes);
        IStrategy(strategy).rebalance();

        require(wbtc.balanceOf(strategy) < 5 || usdc.balanceOf(strategy) < 5);
    }
```

### Mitigation

Add a way to deposit at a different ratio by a trusted party or swap one of the tokens to maximize farming.
