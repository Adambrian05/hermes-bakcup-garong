# Vesting Position Range Becomes Outdated After Rebalance, Leading to Inefficient Fee Generation and Suboptimal Capital Utilization

## Summary
When a vesting position is created, [it uses the same tick range as the main position.](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L433-L434) However, when the strategy is rebalanced,[ the main position's range is updated while the vesting position's range remains unchanged](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L201-L214). This causes the vesting position to become out of sync with the optimal range, potentially becoming out-of-range and stopping fee accrual. Since there's no functionality to update or remove vesting positions once created, this inefficiency persists until the end of the vesting period.

## Vulnerability Details
The Strategy contract allows the creation of vesting positions that are distributed to LPs over time as an incentive mechanism. When creating a vesting position, the contract sets its range to match the main position's current range:

```solidity
function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _vestDuration) external onlyVault {
    // ...
    vp.tickLower = mainPosition.tickLower;
    vp.tickUpper = mainPosition.tickUpper;
    // ...
}
```

The main position is designed to be rebalanced periodically to maintain optimal positioning as market conditions change:

```solidity
function rebalance() public onlyRebalancer {
    // ...
    _setMainTicks(tick);
    // ...
}
```

However, there is no corresponding mechanism to update the vesting position's range during rebalancing. This creates a divergence between the main position (which adapts to market conditions) and the vesting position (which remains static).

To visualize this issue:

```ascii
Initial state:
Main Position:      [-----Range-----]
Vesting Position:   [-----Range-----]  (same range)

After market moves and rebalance is called:
Main Position:            			[-----Range-----]  (updated)
Vesting Position:   [-----Range-----]  (unchanged, potentially out-of-range)
```

## Proof of Concept
1. A vesting position is created with `addVestingPosition()`, using the current main position's range.
2. Market conditions change, moving the price significantly.
3. The `rebalance()` function is called, updating the main position's range to adapt to the new price.
4. The vesting position's range remains unchanged, potentially becoming out-of-range.
5. If out-of-range, the vesting position stops accruing fees, reducing its value to LPs.
6. There is no function to update or remove the vesting position, so this inefficiency persists until the end of the vesting period.

## Impact Details
This issue reduces the effectiveness of the vesting incentive mechanism by potentially leaving vesting positions in suboptimal ranges where they generate fewer fees or no fees at all. The locked capital in these positions becomes inefficiently deployed, reducing overall protocol performance. Since vesting positions can have arbitrary durations, this inefficiency could persist for extended periods.

## Tools Used
Manual

## Recommendations
Implement one of the following solutions:

1. Update vesting position ranges during rebalancing:
```solidity
function rebalance() public onlyRebalancer {
    // ...
    _setMainTicks(tick);
    
    // Add this code to update vesting position if active
    if (ongoingVestingPosition) {
        // Save old position details
        int24 oldLower = vestPosition.tickLower;
        int24 oldUpper = vestPosition.tickUpper;
        
        // Remove liquidity from old position
        _removeFromPosition(vestPosition.remainingLiquidity, oldLower, oldUpper);
        
        // Update to new range
        vestPosition.tickLower = mainPosition.tickLower;
        vestPosition.tickUpper = mainPosition.tickUpper;
        
        // Add liquidity to new position
        (uint160 sqrtPrice,,,,,,) = IUniswapV3Pool(pool).slot0();
        IUniswapV3Pool(pool).mint(
            address(this), 
            vestPosition.tickLower, 
            vestPosition.tickUpper, 
            vestPosition.remainingLiquidity, 
            ""
        );
    }
    // ...
}
```

2. Alternatively, add a function to allow the owner to update or remove vesting positions when they become inefficient.
