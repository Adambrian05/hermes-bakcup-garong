# Users Not Allowed to Top Up Repayments and Could Only Resort to Forced Partial Repayment via `Vault.withdraw()` in `Leverager.withdraw()`

### Summary

The current implementation of `Leverager.withdraw()` forces a proportional repayment using the withdrawn tokens from the vault. This may lead to unnecessary liquidations still due to bad timing or prevent users from maintaining a healthy position. Instead of forcing partial repayment via vault share burning, users should be given the option to top up their denomination tokens to repay their debt and stabilize their position.

### Root Cause

Currently, `withdraw()` forces repayment by deducting from the withdrawn vault tokens and then decrement `up.initCollateralValue` proportionate to the amount of shares removed:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L288

```solidity
            positions[wp.id].initCollateralValue -= up.initCollateralValue * wp.pctWithdraw / 1e18;
```
The problem is the position could still be liquidateable after the above repayment if, for instance, `base` having been assigned by `pos.initCollateralValue` would still make `totalDenom - owedAmount < vp.minCollateralPct * base / 1e18` true:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L408-L411

```solidity
        uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;

        if (owedAmount > totalDenom || totalDenom - owedAmount < vp.minCollateralPct * base / 1e18) return true;
```
This does not allow users to control how they repay and may not always be beneficial depending on the market conditions.

The protocol should allow users to manually add denomination tokens to repay their debt instead of only using collateral withdrawn from the vault. This allows users to manage their position strategically whether to use the former or the latter method or the combination of both methods.

### Internal Pre-conditions

1. A user has an open leveraged position.

2. The user wants to make repayment via `Leverager.withdraw()`.

3. The protocol enforces a proportional debt repayment from withdrawn vault tokens.

### External Pre-conditions

1. Market conditions may make repayment from withdrawn vault collateral suboptimal.

2. The protocol determines liquidations based on debt ratios, which may not account for user-controlled repayments.

### Attack Path

1. A user attempts to withdraw collateral via `Leverager.withdraw()`, triggering a forced proportional repayment from the `Vault.withdraw()`.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L215-L218

```solidity
        uint256 sharesToWithdraw = up.shares * wp.pctWithdraw / 1e18;

        (uint256 amountOut0, uint256 amountOut1) =
            IVault(up.vault).withdraw(sharesToWithdraw, wp.minAmount0, wp.minAmount1);
```
2. The repayment uses withdrawn vault tokens, potentially at a bad market price (e.g. diminished `token0` or `token1` value and/or low yields rendered by the strategy to the vault), likely having the necessarily deficient denomination amount pulled from the user.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L263

```solidity
        if (owedAmount > 0) IERC20(up.denomination).safeTransferFrom(msg.sender, address(this), owedAmount);
```
3. The position remains liquidateable despite repayment, as the collateral value is recalculated dynamically via [`isLiquidateable()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L399-L411) using a current [`owedAmount`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L404) that's increasingly inflated due to accrued interest. 

4. The user is unable to manually repay additional debt, leading to an unavoidable liquidation.

### Impact

- Forced Liquidations: Users may lose their position due to bad timing in repayment.

- Lack of Flexibility: Users cannot manually top up debt repayments to restore position health.

- Suboptimal Debt Management: The system forces repayments that may not be beneficial in a volatile market.

### PoC

_No response_

### Mitigation

Replace the forced proportional repayment logic with an optional top-up mechanism, allowing users to contribute additional denomination tokens before finalizing the withdrawal. 

Additionally, the protocol should verify that the position is no longer liquidateable after repayment. Otherwise, it defeats the purpose of repayment wasting gas only to be liquidated by the bots still.
