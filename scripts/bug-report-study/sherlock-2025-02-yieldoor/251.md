# Misuse of Spot Price for Balance Calculation in Strategy Contract Allows Share Manipulation in Vault

### Summary

The `balance()` function of the Strategy calculates the available balance using the `slot0()` function, leading to price manipulation which will result in more shares minting / less shares burning inside the Vault contract.

### Root Cause

The Strategy contract calculates its available balance through the `balances()` function by summing the following amounts:

```Solidity
    function balances() public view returns (uint256 amount0, uint256 amount1) {
        (uint160 sqrtPriceX96,,,,,,) = IUniswapV3Pool(pool).slot0();

        (uint256 idle0, uint256 idle1) = idleBalances();
        (uint256 m0, uint256 m1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(mainPosition.tickLower),
            TickMath.getSqrtRatioAtTick(mainPosition.tickUpper),
            mainPosition.liquidity
        );
        (uint256 s0, uint256 s1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(secondaryPosition.tickLower),
            TickMath.getSqrtRatioAtTick(secondaryPosition.tickUpper),
            secondaryPosition.liquidity
        );

        amount0 = idle0 + m0 + s0;
        amount1 = idle1 + m1 + s1;
    }
```
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L502-L521

1. The liquidity value of the main position in the Uniswap V3 pool, calculated based on the spot price fetched from `slot0`.
2. The liquidity value of the secondary position in the Uniswap V3 pool, also calculated using the spot price from `slot0`.
3. The `balanceOf()` amounts of both underlying tokens held by the strategy contract itself.

The spot price is fetched directly from Uniswap V3's `slot0()` function without any time-weighted average price (TWAP) or oracle-based protection.

Both Vault deposit and withdrawal operations rely on the strategy's `totalBalance0` and `totalBalance1` values, which in turn are fetched via `balances()`. The Vault contract then uses the following formula to calculate the user’s share:

$$ shares = \frac{totalSupply \times amount}{ totalBalance} $$

Due to the direct use of spot price from Uniswap without any safety mechanisms, the available balance is vulnerable to price manipulation attacks.

Also, the deposit and withdrawal inside the vault can be called in the same tx or block as it is not protected to being included in the single block.

### Internal Pre-conditions

1. The main and secondary positions must be created and actively being used.

### External Pre-conditions

1. The price of the oracle should be manipulated (e.g. by a flash loan)
2. The deposit and withdraw should be called in the single tx to economically cost for the attacker 

### Attack Path

1. Attacker performs a flash loan swap to artificially increase the pool price.
2. He deposits a small amount of tokens into the vault.
3. Due to the manipulated price, the protocol will underestimate the strategy's balance, minting more shares than the actual deposit value.
4. The attacker then reverts the price manipulation and withdraws
5. This time, the protocol overestimates the balance, receiving more tokens than deposited.

### Impact

If an attacker manipulates the Uniswap V3 pool price via a flash loan or low liquidity swaps, the strategy will calculate an incorrect available balance. This will result in incorrect share minting during deposits, allowing attackers to mint more shares than intended and also incorrect share burning during withdrawals, which could allow attackers to drain more liquidity from the vault.

### Mitigation

Consider using another source for price fetching (an Oracle) or not letting the users deposit/withdraw at the same time (in a single block)
