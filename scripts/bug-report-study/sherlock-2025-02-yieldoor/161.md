# `openLeveragedPosition` fails when the swap `path` has multiple pools

### Summary

`Leverager.openLeveragedPosition(...)` reverts when the swap `path` includes multiple pools.

### Root Cause

The `_getTokenIn` helper function gets stuck in an endless loop because `path.skipToken()` returns updated bytes instead of modifying the current `path`:

```solidity
function _getTokenIn(bytes memory path) internal pure returns (address) {
    while (path.hasMultiplePools()) {
        path.skipToken();
    }

    (, address tokenIn,) = path.decodeFirstPool();
    return tokenIn;
}
```
> Source: [Leverager.sol#L566-L573](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L566-L573)

The Path.sol library itself is out of scope, but we can look under the hood to see how it's expected to work. The comment and code confirm that this returns a new value that `_getTokenIn` should be using:

```solidity
/// @notice Skips a token + fee element from the buffer and returns the remainder
/// @param path The swap path
/// @return The remaining token + fee elements in the path
function skipToken(bytes memory path) internal pure returns (bytes memory) {
    return path.slice(NEXT_OFFSET, path.length - NEXT_OFFSET);
}
```
> Source: [Path.sol#L55-L60](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/Path.sol#L55-L60)

### Internal Pre-conditions

1. A vault is available with leverage enabled.

### External Pre-conditions

n/a

### Attack Path

There is not a profitable attack here, just a loss of expected functionality.

1. A trader calls `Leverager.openLeveragedPosition(..)`. 
    - It includes `swapParams1` and/or `swapParams2` in order to swap the borrowed asset for one of the vault tokens.
    - The `swapParams.path` provided by the user makes multiple hops, in the PoC below we swap USDC for BTC and then BTC for WETH.

### Impact

The transaction to `openLeveragedPosition` reverts. Users are not able to use the optimal Uniswap path but instead the only option is to use a single pool with the required pair.

Some asset pairs may not have sufficient liquidity, potentially forcing users to accept larger slippage than should be necessary. And other pairs may not have an available pool / any liquidity.

Note: other similar functions are not impacted, `Leverager.withdraw(..)` and `Leverager.liquidatePosition(..)` both support paths with multiple pools correctly.

### Mitigation

Update the `_getTokenIn(..)` loop to use the `path` returned by `.skipToken()`:

```diff
diff --git a/yieldoor/src/Leverager.sol b/yieldoor/src/Leverager.sol
index b59c56c..b7cef4d 100644
--- a/yieldoor/src/Leverager.sol
+++ b/yieldoor/src/Leverager.sol
@@ -565,7 +565,7 @@ contract Leverager is ReentrancyGuard, Ownable, ERC721, ILeverager {
     /// @notice Gets the tokenIn in a exactOutput swap path
     function _getTokenIn(bytes memory path) internal pure returns (address) {
         while (path.hasMultiplePools()) {
-            path.skipToken();
+            path = path.skipToken();
         }
 
         (, address tokenIn,) = path.decodeFirstPool();
```
