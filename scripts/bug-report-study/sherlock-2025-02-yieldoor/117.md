# Invalid tick range in secondary position leads to rebalance failure

## Summary
The `Strategy#_addLiquidityToSecondaryPosition` function will revert when attempting to add liquidity to a position where the lower tick equals or exceeds the upper tick, which can occur during normal operation when rebalancing.

## Relevant Context
The strategy maintains two Uniswap V3 positions:
1. A main position centered around the current price
2. A secondary position that holds only one token type and is out-of-range

The ticks for these positions are set during rebalancing based on the current price and position width parameters.

[`_setMainTicks`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L232)

```solidity
    /// @notice Calculates and sets the ticks of the main position
    /// @dev Checks if the nearest initializable tick is lower or higher than the current tick
    function _setMainTicks(int24 tick) internal {
        int24 halfWidth = int24(positionWidth / 2);
        int24 modulo = tick % tickSpacing;
        if (modulo < 0) modulo += tickSpacing; // if tick is negative, modulo is also negative
        bool isLowerSided = modulo < (tickSpacing / 2);

        int24 tickBorder = tick - modulo;
        if (!isLowerSided) tickBorder += tickSpacing;
        mainPosition.tickLower = tickBorder - halfWidth;
        mainPosition.tickUpper = tickBorder + halfWidth;

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

[`_setSecondaryPositionsTicks`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L366)

```solidity
    /// @notice Sets the secondary position ticks.
    /// @dev This position should always be created consisting of just one of the tokens
    /// @dev Should initially be Out-Of-Range
    function _setSecondaryPositionsTicks(int24 tick) internal {
        int24 modulo = tick % tickSpacing;
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;
            secondaryPosition.tickUpper = tick - modulo;
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing;
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }
```

## Root Cause
In `Strategy#_setSecondaryPositionsTicks`, the secondary position's tick range is set based on the main position's ticks and the current price. However, when `positionWidth = 2 * tickSpacing`, certain price conditions can lead to `tickLower == tickUpper`:

- When `tick > 0` and either:
  - `tick % tickSpacing < tickSpacing/2` and `bal0in1 >= bal1`, or
  - `tick % tickSpacing >= tickSpacing/2` and `bal0in1 < bal1`

When this occurs, `_addLiquidityToSecondaryPosition` will attempt to create an invalid position. This leads to a division by zero in `LiquidityAmounts.getLiquidityForAmounts` because both `getLiquidityForAmount0` and `getLiquidityForAmount1` compute liquidity using formulas that divide by `(sqrtUpper - sqrtLower)`, which becomes zero when the ticks are equal.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L283

Having `positionWidth = 2 * tickSpacing` is a completely valid configuration that should work in these cases:

a) When `tick % tickSpacing < tickSpacing/2` and `bal0in1 < bal1`
```bash
Given:
- tickSpacing = 60
- positionWidth = 120 (2 * tickSpacing)
- Current tick = 180
- tick % tickSpacing = 0 (which is < tickSpacing/2 = 30)
- bal0in1 < bal1

1. _setMainTicks:
   - modulo = 180 % 60 = 0
   - isLowerSided = true (since 0 < 30)
   - tickBorder = 180 - 0 = 180
   - mainPosition.tickLower = 180 - 60 = 120
   - mainPosition.tickUpper = 180 + 60 = 240

2. In _setSecondaryPositionsTicks:
   - modulo = 180 % 60 = 0
   - bal0in1 < bal1 triggers the first branch
   - tickLower = mainPosition.tickLower = 120
   - tickUpper = tick - modulo = 180 - 0 = 180
3. Result: tickLower = 120, tickUpper = 180
```

b) When `tick % tickSpacing >= tickSpacing/2` and `bal0in1 >= bal1`
```bash
Given:
- tickSpacing = 60
- positionWidth = 120 (2 * tickSpacing)
- Current tick = 210
- tick % tickSpacing = 30 (which is >= tickSpacing/2 = 30)
- bal0in1 >= bal1

1. _setMainTicks:
   - modulo = 210 % 60 = 30
   - isLowerSided = false (since 30 >= 30)
   - tickBorder = (210 - 30) + 60 = 240
   - mainPosition.tickLower = 240 - 60 = 180
   - mainPosition.tickUpper = 240 + 60 = 300

2. In _setSecondaryPositionsTicks:
   - modulo = 210 % 60 = 30
   - bal0in1 >= bal1 triggers the second branch
   - tickLower = tick - modulo + tickSpacing = 210 - 30 + 60 = 240
   - tickUpper = mainPosition.tickUpper = 300
3. Result: tickLower = 240, tickUpper = 300
```

## Pre-conditions

Having `positionWidth = 2 * tickSpacing`.

## Attack Path
1. The `positionWidth` is set to `2 * tickSpacing` via `Strategy#changePositionWidth`
2. Market conditions cause the price to move such that `tick > 0`
3. The token balance ratio (`bal0in1/bal1`) aligns with one of the problematic tick modulo conditions
4. A rebalance is attempted:
   - `Strategy#rebalance` calls `_setSecondaryPositionsTicks`
   - Invalid tick range is set where `tickLower == tickUpper`
   - `_addLiquidityToSecondaryPosition` calls `getLiquidityForAmounts`
   - Division by zero occurs in liquidity calculations
   - Entire rebalance reverts

## Impact Explanation
High. This vulnerability prevents rebalancing under common and valid market conditions, leading to:
1. Direct loss of yield as positions cannot be rebalanced to optimal ranges
2. Increased risk exposure during market volatility when rebalancing is critical
3. Complete failure of the strategy's core functionality

## Recommendation
Add a validity check in `_addLiquidityToSecondaryPosition`:

```diff

    int24 tickLower = secondaryPosition.tickLower;
    int24 tickUpper = secondaryPosition.tickUpper;
```
