# Incorrect Token Usage in Withdrawal Debt Repayment Logic

## Summary and Impact

The `Leverager.withdraw()` function contains a critical bug in its debt repayment logic that allows users to significantly underpay their loans when the borrowed denomination is `token1`. This vulnerability occurs due to a coding error where the wrong token amount (`amountOut0` instead of `amountOut1`) is used in the repayment calculation logic.

This flaw directly violates a core invariant stated in the project documentation: "currBorrowedUSD for a vault should more or equal to the sum of all positions' initBorrowedUsd." When a user withdraws from a position where `token1` is the borrowed denomination, they can retain substantially more funds than they should, effectively "stealing" value from the protocol.

The real-world impact is severe: the protocol incurs bad debt as users can withdraw their full collateral while only repaying a fraction of what they actually owe. This creates a significant economic vulnerability that could drain liquidity pools and make the entire lending system insolvent if exploited across multiple positions.

Per the documentation, one of the key security invariants is that "If a user performs a deposit and then immediately withdraws the amount of shares they've just received, they should always get funds back in the same ratio as when they deposited them (excluding rounding down of a few wei)." This vulnerability fundamentally breaks this property for leveraged positions.

## Vulnerability Details

The bug is located in the `withdraw()` function of the `Leverager.sol` contract:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L227-L235

The bug is in the second branch where `borrowed == up.token1`. The ternary operation uses `amountOut0` instead of `amountOut1` in the comparison. This means that if `amountOut1 < owedAmount`, the function will use `amountOut0` (which could be much smaller) to calculate how much debt to repay, instead of the correct `amountOut1` value.

Let's examine how this bug affects the protocol:

1. When a user has a leveraged position with `token1` as the borrowed denomination:
   - Upon withdrawal, the protocol should use the withdrawn `token1` to repay the debt
   - The bug causes it to use `amountOut0` in the calculation instead
   - This typically results in a much smaller repayment than required

2. The repayment calculation has two scenarios:
   - If `amountOut1 < owedAmount`, the repayment should be the full `amountOut1` (all available `token1`)
   - Instead, it uses `amountOut0` (amount of `token0`), which in many pools could be significantly less
   - For example, in WBTC/USDC pools, the WBTC amount (token0) is typically much smaller than the USDC amount (token1) due to their relative values

3. After calculating `repayFromWithdraw` incorrectly, the function:
   - Subtracts this amount from `owedAmount` (reducing the recorded debt incorrectly)
   - Subtracts the same amount from `amountOut1` (reducing the user's withdrawn amount incorrectly)

The impact is magnified in pools with significant value differences between tokens (like WBTC/USDC) where `token0` balances are often tiny fractions of `token1` balances.

For a concrete example, consider a leveraged position with:
- 0.1 WBTC (token0) worth $5,000
- 5,000 USDC (token1) worth $5,000
- Borrowed 2,500 USDC (token1)

When withdrawing:
- The user should repay 2,500 USDC from their withdrawal
- Due to the bug, if WBTC is token0, the calculation uses 0.1 WBTC in the comparison
- The code might effectively only deduct ~0.1 WBTC worth of USDC (~$5,000) from the user's withdrawal
- The user receives nearly all their USDC, leaving significant bad debt in the protocol

This directly contradicts the security expectation mentioned in the documentation: "Proper decimals scaling. Due to different needs in different parts of the contract, Oracle (USD) pricing is in 1e18, Lending Pool Indexes are in 1e27 and Vault price is in 1e30." The bug causes incorrect token accounting that breaks these expectations.

## Recommendations

The fix is straightforward - correct the ternary expression to use `amountOut1` instead of `amountOut0` in the comparison:

```solidity
if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```
