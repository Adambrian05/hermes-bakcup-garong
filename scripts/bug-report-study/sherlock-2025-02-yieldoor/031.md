# Checking pool activity will incorrectly revert due to not rounding down the tick when necessary

### Summary

Checking pool activity will incorrectly revert due to not rounding down the tick when necessary

### Root Cause

Upon checking the pool activity, we have the following code:
```solidity
            tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));

            ...
            int24 delta = nextTick - tick;

            if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
                return false;
            }
```
The issue is that `tick` is not rounded down for negative tick cumulative. This will result in the `delta` to have an incorrect value, causing an incorrect result when checking the deviation.

### Internal Pre-conditions

1. Negative tick cumulative which results in truncation upon dividing by the timestamp delta.

### External Pre-conditions

_No external pre-conditions_

### Attack Path

No attack path necessary.

### Impact

Deviation check won't work properly, causing reverts when they shouldn't happen and vice versa.

### PoC

_No response_

### Mitigation

Add a check similar to the one in `twapTick()`:
```solidity
if (tickCumulativesDelta < 0 && (tickCumulativesDelta % int32(twap) != 0)) tick--;
```
