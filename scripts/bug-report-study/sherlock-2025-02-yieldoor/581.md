# Unfair yToken Allocation for First Depositor in LendingPool Contract

### Summary

The `LendingPool` contract, specifically in the `_deposit` function, unfairly reduces the `yTokenAmount` allocated to the first depositor by subtracting `MINIMUM_YTOKEN_AMOUNT` (1000 yTokens) after minting this amount to the `DEAD_ADDRESS`. This mechanism, intended to defend against liquidity pool inflation attacks, penalizes the first depositor by reducing their yToken entitlement, while their full underlying asset deposit contributes to the pool's liquidity. Subsequent depositors are unaffected, creating an inequitable distribution of rewards.

### Root Cause

The root cause lies in the `_deposit` function's logic for handling the first deposit:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L121


- After calculating `yTokenAmount = amount * exchangeRate / PRECISION`, the contract mints 1000 yTokens to the `DEAD_ADDRESS` to prevent inflation attacks.

- It then subtracts MINIMUM_YTOKEN_AMOUNT from `yTokenAmount`, reducing the `yTokens` minted to the first depositor (`onBehalfOf`), while the full amount of underlying tokens is still transferred to the pool.

This adjustment is not applied to subsequent deposits, making it exclusive to the first depositor.



### Internal Pre-conditions

1. The reserve for the asset must be newly initialized, with `IyToken(reserve.yTokenAddress).totalSupply() == 0`.

2. The `MINIMUM_YTOKEN_AMOUNT` constant is set to 1000.

3. The `deposit` function must be called with an `amount` that, when converted to `yTokens` via the exchange rate, exceeds `MINIMUM_YTOKEN_AMOUNT` (enforced by require(`yTokenAmount > MINIMUM_YTOKEN_AMOUNT)`).



### External Pre-conditions

1. The caller must have approved the LendingPool contract to transfer at least amount of the underlying asset via IERC20(asset).safeTransferFrom.

2. The contract must not be paused (notPaused modifier).

3. The reserve for the asset must be active and not frozen.



### Attack Path

This issue does not represent a traditional attack vector but rather an economic design flaw. However, an opportunistic user could exploit the knowledge of this penalty to avoid being the first depositor:

1. Monitor the blockchain for an uninitialized reserve (where `totalSupply() == 0` for the yToken).
2. Wait for another user to make the first deposit, incurring the `MINIMUM_YTOKEN_AMOUNT` penalty.
3. Deposit afterward to receive the full `yTokenAmount` without the deduction.
4. 
This behavior could delay pool adoption or discourage early participation.

### Impact

1. Economic Unfairness: The first depositor receives fewer `yTokens` (e.g., 1000 less) than their deposited underlying assets entitle them to, effectively losing value proportional to `MINIMUM_YTOKEN_AMOUNT * exchangeRate`.

2. Reduced Incentive for Early Adoption: Potential depositors may hesitate to initialize a reserve, knowing they will receive fewer `yTokens`, potentially slowing the growth of the lending pool.



### PoC

1. Deploy the `LendingPool` contract and initialize a reserve for an asset.

2. First depositor calls deposit(asset, 10000, firstDepositor):
- `exchangeRate = PRECISION` (1:1 for simplicity).

- `yTokenAmount = 10000 * PRECISION / PRECISION = 10000`.

- `totalSupply() == 0`, so 1000 yTokens are minted to `DEAD_ADDRESS`.

- `yTokenAmount -= 1000`, resulting in 9,000 yTokens minted to firstDepositor.

- Pool receives 10,000 underlying tokens, but `firstDepositor` gets only 9,000 `yTokens`.

3. Second depositor calls deposit(asset, 10000, secondDepositor):
- `yTokenAmount = 10000`, no deduction.

- Receives full 10,000 yTokens.

Result: First depositor loses 1000 yTokens’ worth of value; second depositor does not.



### Mitigation

Mint full yTokenAmount to first depositor
Modify `LendingPool.sol::_deposit` function to mint the full `yTokenAmount` to first depositer without subtractions:

```diff
    function _deposit(address asset, uint256 amount, address onBehalfOf) internal returns (uint256 yTokenAmount) {
        DataTypes.ReserveData storage reserve = getReserve(asset);
        require(!reserve.getFrozen(), "reserve frozen");
        // update states
        reserve.updateState();

        // validate
        reserve.checkCapacity(amount);

        uint256 exchangeRate = reserve.reserveToYTokenExchangeRate();

        IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);

        // Mint yTokens for the user
        yTokenAmount = amount * exchangeRate / (PRECISION);

        require(yTokenAmount > MINIMUM_YTOKEN_AMOUNT, "deposit is dust amount");
        if (IyToken(reserve.yTokenAddress).totalSupply() == 0) {
            // Burn the first 1000 yToken, to defend against lp inflation attacks
            IyToken(reserve.yTokenAddress).mint(DEAD_ADDRESS, MINIMUM_YTOKEN_AMOUNT);

            // @audit - first depositer will get unfair amount of tokens
--            yTokenAmount -= MINIMUM_YTOKEN_AMOUNT;
        }

        IyToken(reserve.yTokenAddress).mint(onBehalfOf, yTokenAmount);
        reserve.underlyingBalance += amount;
        // update the interest rate after the deposit
        reserve.updateInterestRates();
    }
```
