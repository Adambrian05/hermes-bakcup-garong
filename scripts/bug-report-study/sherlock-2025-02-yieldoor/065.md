# Unbounded loop in `checkPoolActivity()` can cause failures due to out-of-gas errors

### Summary

The unbounded loop in the `checkPoolActivity()` function will cause `Strategy` rebalancing failures and `Leverager` new positions to revert as high observation cardinality in popular Uniswap V3 pools will exceed block gas limits, preventing critical protocol operations.

### Root Cause

In `Strategy.sol`, the `checkPoolActivity()` function contains an unbounded loop that iterates through Uniswap V3 pool observations without any limit on the number of iterations:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L311-L342

The loop continues until it finds an observation with a timestamp older than the TWAP period or reaches the end of the observations array. For pools with high observation cardinality (which can be up to 65,535), this can lead to excessive gas consumption.

### Internal Pre-conditions

1. The TWAP period configured in the strategy needs to be sufficiently long to require checking multiple observations. While a 5-minute TWAP is less likely to cause problems than longer periods, it's still vulnerable to this issue, especially in pools with high observation cardinality and irregular activity patterns.

### External Pre-conditions

1. The Uniswap V3 pool's `observationCardinality` needs to be high (e.g., >300, which is common for popular pools like ETH/USDC)
2. The pool needs to have been active long enough to have filled many observation slots

### Attack Path

1. Rebalancer start a rebalance operation
2. The `checkPoolActivity()` function is called to verify pool activity
3. `checkPoolActivity()` iterates through hundreds or thousands of observations in the Uniswap V3 pool
4. The transaction reverts due to exceeding the block gas limit
5. Rebalancing fails preventing the strategy from adjusting positions to changing market conditions

In another case, an user using the `Leverager` contract can try to open a new position but will revert due to the same reason.

### Impact

The protocol suffers from critical functionality failure as rebalancing operations become impossible when integrated with popular, high-activity Uniswap V3 pools. This prevents the strategy from adapting to market changes, potentially leading to significant losses for users due to impermanent loss or missed yield opportunities.

### Mitigation

Implement a maximum iteration limit in the `checkPoolActivity()` function.
