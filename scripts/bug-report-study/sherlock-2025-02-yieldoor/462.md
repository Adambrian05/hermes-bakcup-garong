# Borrow Index Manipulation via Deposit/Withdrawal Allows Interest Rate Exploitation and Potential Token Theft

## Summary
The protocol's borrowing index, which determines interest payments, can be manipulated by depositing or withdrawing funds to artificially alter the utilization rate. This vulnerability allows attackers to either pay less interest on their own loans or force others to pay more. In extreme cases, attackers could potentially drain the protocol by manipulating the borrow index to near-zero values, effectively borrowing without repaying. The absence of deposit/withdrawal fees and time-weighted averaging makes this attack particularly feasible and profitable.

## Vulnerability Details
The vulnerability stems from how the protocol calculates and [updates the borrowing index based ](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L108)on the current utilization rate, which can be easily manipulated.

When `updateState()` is called, it triggers `_updateIndexes()` which updates the borrowing index:

```solidity
function _updateIndexes(DataTypes.ReserveData storage reserve) internal {
    uint256 newBorrowingIndex = reserve.borrowingIndex;
    uint256 newTotalBorrows = reserve.totalBorrows;

    if (reserve.totalBorrows > 0) {
        newBorrowingIndex = latestBorrowingIndex(reserve);
        newTotalBorrows = newBorrowingIndex * (reserve.totalBorrows) / (reserve.borrowingIndex);

        require(newBorrowingIndex <= type(uint128).max);

        reserve.borrowingIndex = newBorrowingIndex;
        reserve.totalBorrows = newTotalBorrows;
    }
    reserve.lastUpdateTimestamp = uint128(block.timestamp);
}
```

The `latestBorrowingIndex()` function uses `calculateCompoundedInterest()` with `reserve.currentBorrowingRate` as an input parameter. This rate is determined by the utilization rate:

```solidity
function updateInterestRates(DataTypes.ReserveData storage reserve) internal {
    reserve.currentBorrowingRate =
        InterestRateUtils.calculateBorrowingRate(reserve.borrowingRateConfig, utilizationRate(reserve));
}
```

The utilization rate is calculated as:
```solidity
function utilizationRate(DataTypes.ReserveData storage reserve) internal view returns (uint256 rate) {
    (uint256 total, uint256 borrows) = totalLiquidityAndBorrows(reserve);
    if (total > 0) {
        rate = borrows * (PRECISION) / (total);
    }
    return rate;
}
```

Where `total` is `reserve.underlyingBalance + borrows`. Since `reserve.underlyingBalance` changes with deposits and withdrawals, anyone can manipulate the utilization rate and consequently the borrowing rate and index.

The attack flow:
1. Manipulate utilization rate through deposits/withdrawals
2. This changes the borrowing rate
3. The borrowing rate affects the borrowing index
4. The borrowing index determines interest payments


## Proof of Concept
Attack Scenario 1 (Griefing):
1. Attacker monitors mempool for repayment transactions
2. When a victim is about to repay their loan in `Leverager::withdraw`
3. Attacker frontruns with a large withdrawal
4. This increases utilization rate → increases borrowing rate → increases borrow index
5. Victim pays more interest than they should

Attack Scenario 2 (Self-Profit):
1. Attacker takes a large flash loan
2. Deposits funds into the lending pool
3. This decreases utilization rate → decreases borrowing rate → decreases borrow index
4. Attacker repays their own loan with artificially reduced interest
5. Withdraws their deposit
6. Repays flash loan
7. Profits from the difference in interest

Attack Scenario 3 (Extreme Case):
1. Attacker manipulates borrow index to near-zero
2. Borrows assets
3. Manipulates index again when repaying
4. Pays virtually no interest
5. Effectively steals from the protocol

**Note**
An attacker can user thesame strategy to trigger liquidations of other users positions in the protocol. 
Notice the use of [`bIndex`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L404) in the `isLiquidatable` function
```solidity
uint256 owedAmount = pos.borrowedAmount * bIndex / pos.borrowedIndex;
```

## Impact Details
This vulnerability allows attackers to manipulate interest rates to their advantage, resulting in financial losses for other users or the protocol itself. In the worst case, attackers could potentially drain the protocol by borrowing without effectively paying interest. The lack of deposit/withdrawal fees and time-weighted averaging makes this attack particularly feasible and profitable.

## Tools Used
Manual

## Recommendations
1. Implement a time-weighted average (TWAP) for utilization rates to prevent rapid manipulation
2. Add deposit and withdrawal fees to discourage rapid liquidity changes
3. Implement rate smoothing mechanisms to prevent drastic changes in a single block
4. Consider adding a minimum time delay between rate updates
