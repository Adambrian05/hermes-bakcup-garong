# Leverager's deposit amount mismatch with Vault's rounded calculations

## Summary
In Vault.sol, `_calcDeposit()` f rounds up deposit amounts which can exceed Leverager's approved token amounts, causing transactions to fail
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L140-L149

## Root Cause: 
In `Vault.sol`, the `_calcDeposit()` performs upward rounding on amount0 and amount1, but Leverager.sol approves only the pre-rounded amounts (vault0In, vault1In) for transfer, leading to insufficient allowance.

## Internal Pre-conditions:
1. Vault's totalSupply must be > 0
2. Both bal0 and bal1 must be > 0 to trigger the rounding logic
3. The calculated cross value must not be perfectly divisible by bal0 or bal1

## External Pre-conditions:
1. User must call Leverager.openLeveragedPosition with vault0In and vault1In parameters
2. Flash loan must be needed to complete the position

## Attack Path:
1. User calls Leverager.openLeveragedPosition with vault0In=100 and vault1In=50
2. Leverager takes flash loan based on vault0In=100 and vault1In=50
3. Leverager calls Vault.deposit(100, 50)
4. Vault._calcDeposit rounds up amounts to 101 and 51
5. Vault transfers 101 token0 and 51 token1 to Strategy
6. Leverager calculates flash loan repayment based on original 100 and 50 values
7. Flash loan repayment fails due to insufficient funds (short by 1 token0 and 1 token1)

## Impact
The protocol becomes unusable for leveraged positions when Vault rounding is triggered, as flash loan repayments will fail. This effectively blocks users from opening leveraged positions in most real-world scenarios where perfect division is unlikely.

## Recomendation
1. Consider changing Vault's rounding mechanism to round down instead of up
2. Add explicit documentation about rounding behavior in Vault
3. Add validation checks in Leverager to ensure actual deposited amounts don't exceed expected amounts
