# Oracle manipulation risks

### Summary

The protocol relies on a combination of on-chain TWAP and an external price feed without sufficient cross-checks. This creates a risk where an attacker could manipulate price data to open unsafe positions or trigger wrongful liquidations.

### Root Cause

In `Strategy.sol` and `LendingPool.sol` (lines ~148–156 and ~490–498), Yieldoor uses a combination of on-chain TWAP (Time-Weighted Average Price) from the vault’s underlying AMM pool and an external price feed (`IPriceFeed`) for asset pricing. Key points in the code rely on these oracles:

-  When opening a leveraged position, the vault’s `twapPrice()` is fetched and `checkPoolActivity()` is called to ensure the pool’s price hasn’t moved too much recently. This is to avoid using a stale or manipulated TWAP in the position opening calculations. The external `pricefeed.getPrice(denomination)` is used to convert collateral values to the borrowed token value​.

- Liquidation checks use the vault TWAP price for current collateral value and the `pricefeed` for the borrowed token’s current price​. Notably, during liquidation `checkPoolActivity()` is not called (the code comment acknowledges this is to allow liquidations in volatile markets to prevent bad debt)​. Instead, it assumes TWAP is reasonably up-to-date and uses it directly.

The risk lies in manipulation of these price feeds. If an attacker can significantly manipulate the underlying DEX price (even if briefly) or feed falsified data into `pricefeed`, they could exploit the system. For example:

- Opening position exploit: Suppose the borrowed asset is a stablecoin and an attacker manages to momentarily lower its reported price (via the `pricefeed`) or raise the collateral token’s price on the DEX before the TWAP catches up. The attacker could open a position that appears safe under the manipulated prices but is actually under-collateralized. E.g., if the oracle says 1 USDC = $2 (instead of $1), the system thinks the debt is worth half its true value, allowing ~2× leverage than intended. Once real prices restore, the position could be immediately liquidateable (collateral insufficient), effectively creating a situation akin to borrowing more than allowed. The protocol’s `!isLiquidateable` check at position open​ is meant to catch obviously underwater positions, but if the same manipulated prices are used in that check, it might pass and create a vulnerable position. The attacker could then choose not to repay and let it fall to the protocol to cover the shortfall (if nobody liquidates, lenders face bad debt; if someone does liquidate, the liquidator might have to pay the difference in a truly underwater scenario).

- Forced liquidation exploit: During liquidation, because no anti-manipulation check is done, an attacker could pump or dump the pool price briefly and trigger `isLiquidateable`. For instance, pushing the price of the collateral token down sharply for a short period could make a healthy position appear under-collateralized (collateral value drops). A bot (controlled by the attacker or anyone fast enough) could then liquidate the position. Since the code will use the TWAP (which might lag slightly, but if the deviation is within tolerated range it may still register a big move) and the chainlink feed for debt, a savvy attacker could also manipulate the chainlink feed if it’s an insecure source (or if it relies on DEX pricing itself). The result: the position is liquidated and the attacker (as liquidator) could receive a profit if they timed it such that the collateral’s actual market value rebounds immediately. Even if not, the attacker could use this to grief a user by liquidating them without profit, forcing them to lose their position unjustly. The protocol does charge a liquidation fee on any profit, but as noted in Issue 1, that fee is currently not being collected due to the bug – meaning a malicious liquidator would currently keep 100% of any upside. This amplifies the incentive to attempt such an oracle manipulation attack.

### Internal Pre-conditions

1. The leveraged position uses TWAP and external price feeds for collateral and debt calculations.
2. The TWAP interval is short enough (e.g., 1 minute) to be manipulated.
3. There are no cross-checks between the TWAP and the external price feed.

### External Pre-conditions

1. An attacker can manipulate the underlying DEX pool’s price temporarily.
2. The external price feed is either manipulable or lags behind market changes.

### Attack Path

1. The attacker manipulates the DEX pool to artificially alter the TWAP value.
2. The attacker (or colluding bot) simultaneously influences the external price feed (or exploits its lag).
3. The attacker opens a leveraged position based on these skewed prices, causing it to be under-collateralized.
4. Once the manipulation ends, the position becomes liquidatable, and the attacker profits from the liquidation process.

### Impact

Oracle manipulation can lead to improper liquidations or creation of unsafe positions. The financial impact includes potential bad debt if positions are opened under false pretenses (the protocol/lenders eat the loss when it unwinds) or user losses if their positions are liquidated due to a momentary price manipulation. Since Yieldoor’s design leaves liquidation to external bots, it is critical that the criteria for liquidation are robust against price spoofing. The use of TWAP is a good practice to mitigate single-block swings, but TWAP can be fooled if the underlying pool has low liquidity or if an attacker can dominate the price for the window used. The separate `pricefeed` is presumably a Chainlink oracle – if so, it’s generally reliable, but if it were a custom or less secure feed, that’s another attack surface. In any case, reliance on an external price means trust in the source is vital.

### Mitigation

1. Use Multiple Oracles or Feeds: If possible, cross-verify price information. For instance, compare the vault’s TWAP price against an independent pricefeed for the same token pair. If they diverge by more than a certain threshold, consider halting new leveraged positions on that vault (or requiring a human review). Similarly, ensure the `pricefeed` for each token is coming from a reputable source (like Chainlink) and has adequate safeguards (e.g., sanity bounds, heartbeat intervals). If a pricefeed is updated by the owner (governance), it should only be set to well-known oracle addresses.

2. Tighten `checkPoolActivity` and TWAP Interval: The Strategy contract uses parameters like `tickTwapDeviation` and `maxObservationDeviation` to ensure the Uniswap V3 pool’s price observations are consistent​. Make sure the vault’s `checkPoolActivity()` uses these or similar logic to reject abnormally large price moves. If the TWAP interval is too long, attacks could still slip through by manipulating over a longer period; if too short, it might just follow instantaneous price. Find a balance (perhaps 5-15 minute TWAP) and enforce a maximum deviation from a trusted reference price. This could be as simple as: `require(pricefeedPrice * 1e18 / twapPrice < 1.1e18 && pricefeedPrice * 1e18 / twapPrice > 0.9e18, "TWAP dev too high");` to ensure TWAP is within 10% of Chainlink price for opening positions. During liquidation, such a check is intentionally off, but you might consider at least using the more conservative of two prices (e.g., for collateral, if spot price crash is what triggers liquidation, maybe use an averaged price that’s slightly higher to avoid liquidating on a freak dip – this is a complex area, though, and could also result in missing real needed liquidations).
