# Inconsistent Decimal Precision in Token Value Calculation When Using TWAP Prices Leads to Incorrect Position Valuations and Potential Improper Liquidations

## Summary
The `_calculateTokenValues` function in the Leverager contract fails to normalize decimal precision when calculating USD values for tokens with and without price feeds. When one token lacks a price feed, the function uses TWAP prices to derive its value, resulting in calculations with inconsistent decimal precision compared to tokens with direct price feeds. This inconsistency leads to incorrect position valuations, affecting leverage calculations, liquidation checks, and protocol fees.

## Vulnerability Details
The Leverager contract calculates the USD value of tokens in a position using different methods depending on whether a token has a price feed:

1. For tokens with price feeds,[ it uses the Chainlink price directly to calculate the USD value](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L433-L440):
```solidity
if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
    chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
    usdValue += amount0 * chPrice0 / decimals0;
}
if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
    chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
    usdValue += amount1 * chPrice1 / decimals1;
}
```

2. For tokens without price feeds, it uses TWAP prices to convert to the other token and then USD:
```solidity
if (chPrice0 == 0) {
    usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
} else if (chPrice1 == 0) {
    usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
}
```

The issue arises because these two calculation methods produce values with different decimal precisions:

- Direct price feed calculations inherit the decimal precision of Chainlink (typically 8 decimals)
- TWAP-based calculations result in a precision of:
  - For token0 without price feed: `(token0Decimal * TWAPPriceDecimal / PRECISION) * ChainlinkPriceDecimal / token1Decimal`
  - For token1 without price feed: `(token1Decimal * PRECISION / TWAPPriceDecimal) * ChainlinkPriceDecimal / token0Decimal`

When these values are added together, the function is adding numbers with inconsistent scales, resulting in mathematically incorrect totals.

This is particularly problematic for common trading pairs like WETH/USDC where token0 might have 18 decimals and token1 might have 6 decimals, creating a significant mismatch in the final calculation.

## Proof of Concept
Consider a position with:
- token0 = WETH (18 decimals) with price feed (8 decimals)
- token1 = USDC (6 decimals) without price feed
- amount0 = 1 WETH (1e18 wei)
- amount1 = 2000 USDC (2000e6 units)
- WETH price = $2,000 (2000e8 from Chainlink)
- TWAP price = 2000e30 (WETH/USDC price with PRECISION = 1e30)

Current calculation:
```solidity
// First, add USD value of token0 (which has a price feed)
usdValue = amount0 * chPrice0 / decimals0
usdValue = 1e18 * 2000e8 / 1e18
usdValue = 2000e8  // $2,000 with 8 decimals

// Then, add USD value of token1 (which doesn't have a price feed)
usdValue += amount1 * PRECISION / price * chPrice0 / decimals0
usdValue += 2000e6 * 1e30 / 2000e30 * 2000e8 / 1e18
usdValue += 2000e6 * 2000e8 / 1e18
usdValue += 2000e6 * 2000e8 / 1e18
usdValue += 4e14  // $0.0004 with 14 decimals

// Final result
usdValue = 2000e8 + 4e14 = 200,000,000,000 + 400,000 = 200,000,400,000
```

This is incorrect because we're adding values with different decimal precisions (8 decimals and 14 decimals).

Correct calculation (after normalizing to 8 decimals):
```solidity
// First part remains the same
usdValue = 2000e8  // $2,000 with 8 decimals

// For token1, normalize to 8 decimals
normalized_value = 2000e6 * 1e30 / 2000e30 * 2000e8 / 1e18 * 1e2
normalized_value = 4e16  // $2,000 with 8 decimals

// Final result
usdValue = 2000e8 + 2000e8 = 4000e8  // $4,000 with 8 decimals
```

## Impact Details
This inconsistency leads to significant undervaluation of tokens without price feeds when they have different decimal precisions than their paired tokens. This directly affects leverage calculations, liquidation thresholds, and protocol fees. Positions might be incorrectly liquidated or allowed to maintain unsafe leverage ratios, potentially causing financial losses to users and the protocol.

## Tools Used
Manual

## Recommendations
Normalize all calculated USD values to a consistent decimal precision before adding them together:

```solidity
// Define a standard precision for all USD values (e.g., 18 decimals)
uint8 constant USD_DECIMALS = 18;

// For tokens with price feeds
if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
    chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
    uint8 priceDecimals0 = IPriceFeed(pricefeed).decimals(token0);
    usdValue += amount0 * chPrice0 * (10 ** (USD_DECIMALS - priceDecimals0)) / decimals0;
}

// For tokens without price feeds
if (chPrice0 == 0) {
    // Calculate with consistent precision
    uint8 priceDecimals1 = IPriceFeed(pricefeed).decimals(token1);
    usdValue += amount0 * price * chPrice1 * (10 ** (USD_DECIMALS - priceDecimals1)) / PRECISION / decimals1;
}
```

This approach ensures all USD values are normalized to the same decimal precision before being added together, resulting in mathematically correct calculations.
