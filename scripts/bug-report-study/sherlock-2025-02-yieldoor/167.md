# Attacker will manipulate initial share price to steal funds from subsequent depositors

### Summary

The use of an imbalanced initial share calculation in the Vault will cause an unfair distribution of shares for subsequent depositors as an attacker will deposit an extremely skewed token ratio when the Vault is empty.

This manipulation sets an incorrect baseline share price, allowing the attacker to later withdraw a disproportionate share of assets after the Strategy rebalances to the correct token ratio.

### Root Cause

In the [_calcDeposit function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L119) of the [Vault contract](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol), when `totalSupply == 0`, the share calculation is performed as `shares = max(amount0, amount1) - 1000`.

```solidity
/// @notice Calculates the deposit amounts
    /// @param bal0 The current token0 balance of the strategy
    /// @param bal1 The current token1 balance of the strategy
    /// @param depositAmount0 The amount of token0 user wishes to deposit
    /// @param depositAmount1 The amount of token1 user wishes to deposit
    /// @return shares The amount of shares to be minted to the user
    /// @return amount0 The actual amount of token0 which the user will deposit
    /// @return amount1 The actual amount of token1 which the user will deposit
    function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal
        view
        returns (uint256 shares, uint256 amount0, uint256 amount1)
    {
        uint256 totalSupply = totalSupply();

        // If total supply > 0, vault can't be empty
        assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired
            amount0 = depositAmount0;
            amount1 = depositAmount1;
            shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1;
        } else if (bal1 == 0) {
            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;
        } else {
            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
            amount0 = (cross - 1) / bal1 + 1;
            amount1 = (cross - 1) / bal0 + 1;
            shares = cross * totalSupply / bal0 / bal1;
        }
    }
```

This method does not enforce a balanced (e.g., 50:50) deposit ratio for the initial liquidity, allowing an attacker to set an arbitrary and imbalanced baseline that skews subsequent share calculations.


### Internal Pre-conditions

1. The Vault must be empty `totalSupply == 0` at the time of the first deposit.
2. The attacker must be able to deposit tokens in an imbalanced manner. This means being able to deposit a minimal amount of one token, say 1 wei, and a large amount of the other.
3. The share calculation formula for the initial deposit uses `max(amount0, amount1) - 1000` without requiring or enforcing a balanced deposit ratio.

### External Pre-conditions

Not required.

### Attack Path

1. The attacker identifies a new Vault with no existing deposits `totalSupply == 0`.
2. The attacker deposits an extremely imbalanced ratio.
3. This means, for example, `1 wei` of `token0` and a large amount of token1 e.g., `1000 ETH` equivalent of `token1`, causing the Vault to calculate shares based solely on the large amount (minus 1000 shares burned).
4. The Strategy rebalances the pool to achieve a `50:50` token ratio by converting part of the excess `token1` to `token0`.
5. A legitimate user deposits balanced amounts into the Vault. However, the share calculation is skewed because it uses the manipulated baseline set by the attacker.
6. The attacker then withdraws their shares, receiving a disproportionately high share of the rebalanced, correctly valued pool, thereby extracting value at the expense of the legitimate depositor.

### Impact

The legitimate depositors suffer an approximate loss as they receive fewer shares relative to their actual deposit value, while the attacker gains by withdrawing an excessive amount of collateral.

### PoC

Step 1: Attacker deposits an imbalanced ratio in an empty Vault.
-- Depositing `1 wei` of `token0` and `1000 ETH` in wei of `token1`.
-- Shares minted = `max(1, 1000e18) - 1000` ≈ `1000e18 - 1000`.
Step 2: The Strategy rebalances to a 50:50 ratio.
Step 3: A legitimate user deposits a balanced amount.
Step 4: Attacker withdraws their shares.
-- Due to the skewed initial share price, the attacker extracts a disproportionate share of the balanced pool.

### Mitigation

Use the geometric mean (i.e., `sqrt(amount0 * amount1))` for initial share calculation instead of `max(amount0, amount1) - 1000` to ensure a fair baseline share price.

Or, require that the initial deposit meets a balanced ratio, such as within 1% of `50:50` to prevent imbalanced liquidity.
```solidity
if (totalSupply == 0) {
    require(
        amount0 * 1e18 / amount1 >= 0.99e18 && 
        amount0 * 1e18 / amount1 <= 1.01e18, 
        "Imbalanced deposit"
    );
    shares = sqrt(amount0 * amount1) - 1000;
}
```
