# Adding a vesting position will brick the Vault&Strategy once prices change

### Summary

When there is an active vesting position, calling `strategy.rebalance()` after any price change in Uniswap will cause all relevant Vault interactions to revert going forward. Funds become unrecoverable.

### Root Cause

Strategy.sol's `collectFees()` function attempts to collect fees by incorrectly using the `mainPosition.tickUpper` vs the expected `vestPosition.tickUpper`:

```solidity
function collectFees() public {
    ...
    if (ongoingVestingPosition) {
        collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
    }
   ...
}
```
> Source: [Strategy.sol#L167](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L167)

It is critical that the values for `tickLower/tickUpper` are the same that was used when the position was added to Uniswap. As we can see in the `collectPositionFees` helper, the tick range is how a position is identified in Uniswap:

```solidity
function collectPositionFees(int24 tickLower, int24 tickUpper) internal {
    IUniswapV3Pool(pool).burn(tickLower, tickUpper, 0);
    IUniswapV3Pool(pool).collect(address(this), tickLower, tickUpper, type(uint128).max, type(uint128).max);
}
```
> Source: [Strategy.sol#L185-L188](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L185-L188)

When `rebalance()` is called, the entire main and secondary positions are removed from Uniswap and then recreated using the latest tick:

```solidity
function rebalance() public onlyRebalancer {
    ...
    _removeLiquidity();
    (uint256 amount0, uint256 amount1) = idleBalances();
    (uint160 sqrtPriceX96, int24 tick,,,,,) = IUniswapV3Pool(pool).slot0();

    _setMainTicks(tick);
    (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);

    _setSecondaryPositionsTicks(tick);
    _addLiquidityToSecondaryPosition(sqrtPriceX96, amount0, amount1);
    ...
}

function _removeLiquidity() internal {
    _removeFromPosition(mainPosition.liquidity, mainPosition.tickLower, mainPosition.tickUpper);
    _removeFromPosition(secondaryPosition.liquidity, secondaryPosition.tickLower, secondaryPosition.tickUpper);

    mainPosition.liquidity = 0;
    secondaryPosition.liquidity = 0;
}
```
> Source: [Strategy.sol#L198-L215](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L198-L215) and [Strategy.sol#L385-L391](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L385-L391)

Notice how it recreates main and secondary positions, but it does not recreate the vesting position.

The vesting position does happen to start by using the same values as the current mainPosition:

```solidity
function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _vestDuration) external onlyVault {
    ...
    VestingPosition memory vp;
    vp.tickLower = mainPosition.tickLower;
    vp.tickUpper = mainPosition.tickUpper;
    ...
    vestPosition = vp;
}
```
> Source: [Strategy.sol#L426-L456](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L426-L456)

Since it starts with the same tick range, unit tests were passing. The PoC below shows how introducing a price change will brick the Vault since no position exists at `vestPosition.tickLower, mainPosition.tickUpper`.

### Internal Pre-conditions

1. The owner has called `vault.addVestingPosition(..)` and that position has not fully vested yet.
2. [external pre-condition below occurs]
3. The rebalancer has called `strategy.rebalance()`.

### External Pre-conditions

1. The price on Uniswap has changed, e.g. a non-trivially sized swap occurred after the vesting position has been added. This changes the current `tick` for the Uniswap pool.

### Attack Path

There is not a profitable attack here, the Vault will be bricked due to this issue during normal course of operations if vesting positions are used since some price movement is expected to occur in Uniswap pools.

### Impact

Withdrawing from the Vault will revert and funds are unrecoverable.

Once a `rebalance` has occurred with the new tick ranges, future attempts to `strategy.collectFees()` will revert. This blocks critical actions including `vault.withdraw(..)` since most functions will attempt to `collectFees()` first:

```solidity
function withdraw(uint256 shares, uint256 minAmount0, uint256 minAmount1)
    public
    returns (uint256 withdrawAmount0, uint256 withdrawAmount1)
{
    IStrategy(strategy).collectFees();
    ...
}
```
> Source: [Vault.sol#L84](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L84)

### Mitigation

Collect fees using the tick range stored in `vestPosition`:

```diff
diff --git a/yieldoor/src/Strategy.sol b/yieldoor/src/Strategy.sol
index 8b5f247..6203857 100644
--- a/yieldoor/src/Strategy.sol
+++ b/yieldoor/src/Strategy.sol
@@ -164,7 +164,7 @@ contract Strategy is Ownable, IStrategy {

         }
         if (ongoingVestingPosition) {
-            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
+            collectPositionFees(vestPosition.tickLower, vestPosition.tickUpper);
         }
 
         (uint256 afterBal0, uint256 afterBal1) = idleBalances();

```

Alternatively, the vesting position could be rebalanced like main position so they continue to use the same `tickUpper` value.
