# Rebalancing and compounding will fail on pools with negative tick

### Summary

Secondary position's `tickLower` and `tickUpper` can be equal on certain conditions.
This will make strategy's rebalancing and compounding revert with EvmError due to division by zero.
Also, depending on current tick of Uniswap Pool, new strategy may have secondary `tickLower` and `tickUpper` to equal values, which will lead to inefficient capital usage.

### Root Cause

**secondaryPosition can have equal `tickLower` and `tickUpper`**

In order to utilize the most out of the funds in Strategy, it creates two positions on Uniswap: main and secondary.

Main position's `tickLower` and `tickUpper` is calculated [as the following](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L232-L244):

```solidity
    function _setMainTicks(int24 tick) internal {
        int24 halfWidth = int24(positionWidth / 2);
        int24 modulo = tick % tickSpacing;
        if (modulo < 0) modulo += tickSpacing; // if tick is negative, modulo is also negative
        bool isLowerSided = modulo < (tickSpacing / 2);

        int24 tickBorder = tick - modulo;
        if (!isLowerSided) tickBorder += tickSpacing;
        mainPosition.tickLower = tickBorder - halfWidth;
        mainPosition.tickUpper = tickBorder + halfWidth;

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

main position's `tickLower` and `tickUpper` is set in order to meet the following invariants:

- `tickUpper - tickLower = tickSpacing * 4`
- `tick <= tickUpper - tickSpacing`
- `tick >= tickUpper + tickSpacing`

![Image](https://sherlock-files.ams3.digitaloceanspaces.com/gh-images/8b0fdd2c-9b6c-4ff7-b235-b5a8e39a0bf5)

Secondary position's `tickLower` and `tickUpper` is calculated [as the following](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L366-L382):

```solidity
    function _setSecondaryPositionsTicks(int24 tick) internal {
        int24 modulo = tick % tickSpacing;
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;
            secondaryPosition.tickUpper = tick - modulo;
        } else {
@>          secondaryPosition.tickLower = tick - modulo + tickSpacing;
@>          secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }
```

We can see that secondary position's `tickLower` and `tickUpper` can have the same value when the following condition is met:

- `bal0in1 >= bal1`
- `tick - modulo = mainPosition.tickUpper - tickSpacing`
  - This happens when tick `isLowerSided` in main position's tick interval

![Image](https://sherlock-files.ams3.digitaloceanspaces.com/gh-images/4bbd899a-f90a-4961-965b-a9f51f16ed1d)

For example:

- Current tick is -198036
- tick spacing is 60
- main position's main position's `tickLower` is -198180 and `tickUpper` is -197940, because:

```console
  modulo = tick % tickSpacing  + tickSpacing = 24
  isLowerSided = modulo < tickSpacing / 2 = true
  tickBorder = tick - modulo = -198036 - 24 = -198060
  tickLower = tickBorder - halfWidth = -198060 - 120 = -198180
  tickUpper = tickBorder + halfWidth = -198060 + 120 = -197940
```
- secondary position's `tickLower` becomes -197940 and `tickUpper` becomes -197940, because:

```console
  modulo = -198036 % 60 = -36
  secondaryPosition.tickLower = tick - modulo + tickSpacing = -198036 + 36 + 60 = -197940
  secondaryPosition.tickUpper = mainPosition.tickUpper = -197940
```
  **If `tickLower` and `tickUpper` are equal, `rebalance` and `compound` will revert**

If `tickLower` and `tickUpper` are equal, corresponding `sqrtRatioAX96` and `sqrtRatioBX96` will be equal as well.

This will cause division by error when calculating liquidity amount for rebalancing:

### Internal Pre-conditions

1. Strategy works on Uniswap Pool with negative tick (e.g. WETH-USDT pool)
2. Strategy's asset0 value is greater than or equal to asset1 value, for example:
  a. Strategy has 0.01 WETH and 0 USDT
  b. Strategy has 0 WETH and 0 USDT
3. Rebalancer executes `compound` or `rebalance`

### External Pre-conditions

1. Current tick is lower sided on main position, for example:
  a. `tickSpacing` = 60
  b. `tick` = -31

### Attack Path

This section describes front-running attack to DoS rebalancing:
1. Rebalancer submits transaction to execute `rebalance` or `compound`
2. Attacker notices this transaction from mempool and frontrun Uniswap transaction to set current tick to be lower sided
3. Later, rebalancer's `rebalance` or `compound` transaction is to be processed, but it will revert due to the above vulnerability

### Impact

- Rebalancing and compounding will frequently fail on Uniswap Pools with negative tick
  - It's very likely that `asset0` has gte value than `asset1` especially when both balances are 0
  - It's 50-50 chance that current tick is lower sided or not
- Attackers can front-run tick manipulation swap over rebalancer's rebalance/compound transaction to bring DoS to the protocol
- Also, new Strategy on negative tick pool can be initialized with `secondaryPosition.tickLower = secondaryPosition.tickUpper` depending on current tick
  - This will lead to extremely inefficient captial usage because it's providing liquidity on zero tick range.
