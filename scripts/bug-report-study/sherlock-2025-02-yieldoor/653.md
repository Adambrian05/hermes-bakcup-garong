# The different token decimals in pool isn't considered when setting secondry position ticks

### Summary

When setting secondry positon ticks, the token0 and token1 balance and amount is calculated with Uniswap V3 pool spot price. But the token0 and token1 decimals isn't considered. If the token0 and token1 decimals is different, the token amount will be wrong. 

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L366-L382
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L126-L129
The Uniswap V3 pool could have tokens with different decimals. So the price from `sqrtPriceX96` should be adjusted according to decimals. Refer to this [blog](https://blog.uniswap.org/uniswap-v3-math-primer).
The protocol used price from `sqrtPriceX96` directly.

### Internal Pre-conditions

1. The Uniswap V3 pool used in this protocol has different decimals for token0 and token1.

### External Pre-conditions

N/A

### Attack Path

1. The decimals of tokens in pool is different.
2. `_setSecondaryPositionsTicks` is called.

### Impact

The token amount calculated is wrong when token0 and token1 decimals are different. The secondary position ticks are inaccurate.

### PoC

_No response_

### Mitigation

```diff
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
+       uint256 decimal0 = IERC20(token0).decimals();
+       uint256 decimal1 = IERC20(token1).decimals();
+       uint256 decimalsScalingFactor = 10 ** (decimal0 - decimal1);
        uint256 _price = price();
-       uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting
+       uint256 bal0in1 = bal0 * _price * decimalsScalingFactor / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting
```
