# Incorrect Repayment Calculation in Withdraw Function for `Token1` Borrowed Positions in `Leverager.sol`

### Summary

When a user withdraws from a leveraged position where USDC (`token1`) is the borrowed asset, the contract is designed to repay a portion of the outstanding debt using the USDC collateral withdrawn from the vault. However, due to a coding error, the contract mistakenly uses the withdrawn value from `token0` (for example, WBTC) to determine the repayment instead of using the USDC value. Because these tokens have different decimal precisions and market values, this miscalculation causes the debt repayment to be under-calculated. In a correct scenario, if all the USDC collateral were used to repay debt, no USDC should be returned to the user; instead, because only a fraction is used for repayment, the user ends up receiving extra USDC collateral. 

### Root Cause

In the `withdraw` function, when the borrowed token is `token1`, the code is implemented as this in [Leverager.sol:231-235](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L231-L235):

```solidity
} else if (up.denomination == up.token1) {
    uint256 repayFromWithdraw = amount1 < owedAmount ? amountOut0 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```

This line is meant to compare the amount of `token1` withdrawn (`amountOut1`) with the outstanding debt (`owedAmount`). Instead, it mistakenly uses `amountOut0` (the withdrawn amount for `token0`). Since `token0` (e.g., WBTC) and `token1` (e.g., USDC) have different decimal places (WBTC has 8 decimals; USDC has 6 decimals), this error causes the repayment to be calculated incorrectly.

### Internal Pre-conditions

1. The borrowed (denomination) token is `token1` (USDC).
2. The vault’s withdrawal returns different amounts for `token0` and `token1` (`amountOut0` and `amountOut1`).
3. The outstanding debt for the withdrawn portion (`owedAmount`) is nonzero and greater than the withdrawn `token1` amount.

### External Pre-conditions

1. The vault manages two different tokens (e.g., WBTC and USDC) with different decimal precisions and market values.
2. Market conditions ensure that the vault’s withdrawal yields a realistic and distinct USDC amount (`amountOut1`) and a different value for `token0` (`amountOut0`).

### Attack Path

1. **Position Setup:**
    A user opens a leveraged position where USDC is the borrowed token. The vault holds collateral in both `token0` (e.g., WBTC) and `token1` (USDC).
2. **Withdrawal Request:**    
    The user initiates a partial withdrawal (e.g., 50% of the position). The vault returns:
    - `amountOut1` = 80 USDC (80e6 units) from token1.
    - `amountOut0` = 0.0007 WBTC, equivalent to roughly 35 USDC (`35e6` units) after conversion.
3. **Faulty Repayment Calculation:**
    The outstanding debt for the withdrawal portion is calculated as 100 USDC (100e6 units). The code then incorrectly computes:
    ```solidity
    uint256 repayFromWithdraw = (80e6 < 100e6) ? amountOut0 : owedAmount;
    // Evaluates to: repayFromWithdraw = 35e6
    ```
    Instead of using `80e6` (from `amountOut1`), only `35e6` USDC is applied to repay the debt.
4. **Residual Values:**
    - The remaining debt becomes: `100e6 - 35e6 = 65e6 USDC`.
    - The token1 collateral is reduced by `35e6`, leaving `80e6 - 35e6 = 45e6 USDC` to be returned to the user.
5. **User Benefit:**
    The user effectively receives `45e6` USDC of collateral that should have been used to repay the debt. They benefit by extracting 
    more collateral relative to the debt reduction, leaving the position undercollateralized.


### Impact

Because of this bug, when withdrawing from a leveraged position where USDC is the borrowed asset, the contract under-calculates the debt repayment. For example, instead of repaying 80 USDC (`80e6` units) and reducing the debt to 20 USDC (`20e6` units), it repays only 35 USDC (`35e6` units), leaving 65 USDC (`65e6` units) of outstanding debt. Additionally, this causes `80e6 - 35e6 = 45e6` USDC to be returned to the user as collateral—when under correct behavior, all of the USDC collateral should have been used for repayment (i.e., `amountOut1` would be 0). Over time or repeated withdrawals, this miscalculation allows the user to extract more collateral than intended, leading to undercollateralized positions and increasing the risk of severe losses and instability in the protocol.

### PoC

Imagine the following scenario:
- A leveraged position has an outstanding debt for the portion being withdrawn of 100 USDC (100e6 units).
- Upon withdrawal, the vault returns 80 USDC (amountOut1) and 0.0007 WBTC (amountOut0), where 0.0007 WBTC is worth about 35 USDC (35e6 units).

**Correct Behaviour:**
- The contract should set:
```solidity
repayFromWithdraw = (80e6 < 100e6) ? 80e6 : 100e6; // equals 80e6
```
- This would reduce the outstanding debt to `100e6 - 80e6 = 20e6 USDC`, and `amountOut1` would drop to zero.
- The user would not receive any extra USDC collateral since it was entirely used for repayment.

**Buggy Behavior:**
- The contract instead uses:
```solidity
repayFromWithdraw = (80e6 < 100e6) ? 35e6 : 100e6; // equals 35e6
```
- This reduces the debt to `100e6 - 35e6 = 65e6 USDC`.
- It also subtracts `35e6` from `amountOut1`, leaving `80e6 - 35e6 = 45e6 USDC` returned to the user.

Thus, due to the bug, the user ends up receiving 45 USDC (`45e6` units) of collateral that should have been applied to repay the debt. This misalignment benefits the user by reducing their effective repayment, thereby allowing them to withdraw more collateral than intended.

### Mitigation

Update the repayment logic for `token1` to correctly use `token1`’s collateral:

```diff
- uint256 repayFromWithdraw = amount1 < owedAmount ? amountOut0 : owedAmount;
+ uint256 repayFromWithdraw = amount1 < owedAmount ? amountOut1 : owedAmount;
```
