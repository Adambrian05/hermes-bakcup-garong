# LendingPool fails to initialize reserves for standard ERC20 tokens with bytes32 name() or symbol()

### Summary


Incorrect handling of non-standard ERC20 tokens' name() and symbol() method will cause an operational limitation for the protocol as admins will be unable to initialize reserves for tokens like MKR that implement symbol() to return bytes32 instead of string, contradicting the contest README's explicit claim that the "Protocol will work only with standard ERC20 tokens."


### Root Cause

In `LendingPool.sol:54` the contract directly calls `ERC20(asset).symbol()` and `ERC20(asset).name()` and assumes both return a string, which is incompatible with tokens like MKR that return bytes32. This contradicts the protocol's stated compatibility with "standard ERC20 tokens" as MKR is considered a standard ERC20 token despite its implementation difference.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L49-L54

### Internal Pre-conditions

1. Admin attempts to initialize a reserve for a token like MKR that implements `symbol()` to return bytes32 instead of string
2. The token in question is otherwise a standard ERC20 token that should be compatible based on the protocol's stated requirements


### External Pre-conditions

Not applicable 

### Attack Path

Not an attack vector, but the issue flow is explained below:

1. Admin calls `initReserve(tokenAddress)` where tokenAddress is an ERC20 token like MKR
2. The function calls `ERC20(tokenAddress).symbol()` expecting a string return type
3. The transaction reverts due to type mismatch when attempting to process either:
    - `string(abi.encodePacked(ERC20(asset).name(), "Yieldoor yAsset"))` or
    - `string(abi.encodePacked("y", ERC20(asset).symbol()))`
4. The reserve initialization fails, preventing the token from being supported by the protocol despite it being a standard ERC20 token

### Impact

The protocol suffers from reduced token compatibility, preventing the integration of valuable assets like MKR into the lending platform. This directly contradicts the protocol's stated compatibility with "standard ERC20 tokens" in the contest README.

Additional context:

- Both `name()` and `symbol()` functions encounter the same issue, making this a systematic problem with the protocol's handling of ERC20 metadata
- This issue demonstrates that the protocol doesn't actually work with all standard ERC20 tokens as claimed
- MKR (Market cap ~$1B) is a significant token in DeFi that would be expected to work with the protocol
- This limitation wasn't explicitly documented and contradicts the protocol's stated design goals
