# Strategy.collectFees() will not correctly claim the fees of VestingPosition

### Summary

Strategy.collectFees() does not correctly claim the fees of VestingPosition the fees accrued in UniswapV3 pool by VestingPosition.

### Root Cause

collectFees() function from Strategy contract expects to collect fees accrued so far in Uniswap by mainPosition, secondaryPosition and VestingPosition (this one only if is active). However, it fails to do it properly in the case of VestingPosition as upper tick it claims for is `mainPosition.tickUpper` instead of `vestPosition.tickUpper`.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L159-L181

As a consequence, if mainPosition's ticks change due to a rebalance (which is performed frequently), the accrued fees for VestingPosition will not be claimed between the correct ticks, which can potentially leave claimable fees stuck in UniswapV3 with no mechanism that allows to claim them. Taking into account that there are 1,774,545 possible ticks in a Uniswap pool, there can be drastic changes in pool's current tick over time, so a given tick could be inactive for months or even years in the pool, which turns it uncertain that a given tick that was active in the past will be active again soon.

Furthermore, the function will even revert if vestPosition.tickLower > mainPosition.tickUpper (as `collectPositionFees()` calls `burn()` function from UniswapV3Pool.sol, which checks that input tickLower is indeed lower than tickUpper), preventing the contract from claiming fees, which would disallow the Strategy contract from claiming any fee from Main, secondary or Vesting positions.

### Internal Pre-conditions

1. MainPosition has been initialized within ticks 200000 to 300000.

### Attack Path

1. New VestingPosition is set within the ticks of current mainPosition (200000 and 300000).
2. After several rebalances happen due to the nature of the contract, the new tickLower and tickUpper of mainPosition are now 50000 and 150000.
3. collectFees() function is called to get the accrued fees, fees for VestingPosition are claimed in the tick range of 200000 as tickLower and 150000 as tickUpper (value of mainPosition.tickUpper). collectFees() calls burn() function from Uniswap to update accrued fees with tickLower 200000 and tickUpper 150000, which reverts as the check `tickLower < tickUpper` fails. 

As a result, the contract cannot claim accrued fees from any of the positions.

### Impact

In the best case, fees accrued by VestingPosition cannot be fully claimed if vestPosition.tickLower < mainPosition.tickUpper, but mainPosition.tickUpper < vestPosition.tickUpper. In the worst case, if after the VestingPosition is set and mainPosition's ticks decrease so that vestPosition.tickLower > mainPosition.tickUpper, the contract will not be able to claim any fees accrued by Main, Secondary or Vesting positions because collectFees() will always revert. `deposit()` and `withdraw()` functions from Vault contract cannot be called as a result.

Take into account that it is not possible to remove manually the VestingPosition (after collecting fees it is checked whether the vesting ended) and that rebalance() and compound() do call collectFees() internally, therefore once mainPosition.tickUpper falls below vestPosition.tickLower, the contract will be totally locked without possible solution.

### Mitigation

Use the correct tickUpper for VestingPosition:
```solidity
function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0) collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(secondaryPosition.tickLower, secondaryPosition.tickUpper);
        }
        if (ongoingVestingPosition) {
-          collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
+         collectPositionFees(vestPosition.tickLower, vestPosition.tickUpper);
        }

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = (afterBal0 - preBal0) * protocolFee / 10_000;
        uint256 protocolFees1 = (afterBal1 - preBal1) * protocolFee / 10_000;

        if (protocolFees0 > 0) IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0) IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
            _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }
```
