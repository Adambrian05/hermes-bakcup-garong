# Unprotected External Position Width Change

### Summary

The missing access control in `changePositionWidth()` will cause a denial of service and potential value extraction for protocol users as any malicious actor will manipulate position width parameters and trigger forced `rebalances`

### Root Cause

In [Strategy.sol:395-399](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L395-L399) the `changePositionWidth()` function lacks access control modifiers, allowing any user to change position parameters and trigger rebalances.
```solidity
function changePositionWidth(uint24 _newWidth) external {
    require((_newWidth / 2) % uint24(tickSpacing) == 0, "half width should be divisible by tickSpacing");
    positionWidth = _newWidth;
    rebalance();
}
```

### Internal Pre-conditions

1. The contract has been deployed and is actively being used by the protocol
2. The `positionWidth` parameter is essential for determining liquidity position bounds
3. The `rebalance()` function has the `onlyRebalancer` modifier to restrict who can call it directly
4. The `lastRebalance` timestamp to be at least `rebalanceInterval` (360 seconds) earlier than the current timestamp

### External Pre-conditions

1. The Uniswap V3 pool needs to have price observations that meet the criteria in `checkPoolActivity()`
2. Pool price should be within acceptable deviation from TWAP as defined by `tickTwapDeviation`

### Attack Path



1. **Attacker observes when the `rebalance` interval (360 seconds) has passed since the last `rebalance`**
2. **Attacker calls `changePositionWidth()` with a valid width parameter (that passes the divisibility check)**
3. **The function updates the `positionWidth` state variable to the new value**
4. **The function directly calls `rebalance()`, which performs expensive operations:**
   - Collecting fees
   - Removing liquidity
   - Calculating new position ticks
   - Adding liquidity to new positions 
5. **The attacker repeats this attack whenever the rebalance interval passes**
6. **Alternatively, the attacker times this with pool price manipulation to extract value during rebalancing**

### Impact

**The protocol suffers increased gas costs and operational inefficiency due to unnecessary rebalances.** The protocol's liquidity is constantly being moved, potentially causing:

1. Increased gas fees paid by the protocol
2. Loss of optimal positioning as positions are continuously changed
3. Potential value extraction if combined with price manipulation strategies
4. Execution delay for legitimate rebalance operations

The attacker does not gain direct financial benefit (beyond potential MEV extraction) but forces the protocol to waste resources on unnecessary operations (griefing attack).

_No response_

### Mitigation

Add proper access control to the `changePositionWidth()` function:

```solidity
function changePositionWidth(uint24 _newWidth) external onlyOwner {
    require((_newWidth / 2) % uint24(tickSpacing) == 0, "half width should be divisible by tickSpacing");
    positionWidth = _newWidth;
    rebalance();
}
```

Or alternatively:

```solidity
function changePositionWidth(uint24 _newWidth) external onlyRebalancer {
    require((_newWidth / 2) % uint24(tickSpacing) == 0, "half width should be divisible by tickSpacing");
    positionWidth = _newWidth;
    rebalance();
}
```

This ensures that only authorized entities (either the owner or the designated rebalancer) can change position width and trigger rebalances.
