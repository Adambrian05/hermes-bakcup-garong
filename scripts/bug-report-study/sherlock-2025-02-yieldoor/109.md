# The pullFunds function and pushFunds function did not promptly update the reserve pool status.

### Summary

When a borrower invokes the `pullFunds` function, the reserve pool is not updated accordingly, which leads to errors in subsequent user fund withdrawals. Similarly, when a user calls the `pushFunds` function, the reserve pool is also not updated. As a result, errors may occur during repayment, such as incorrect calculation or updating of the available balance in the asset pool. This could potentially cause the amount of assets withdrawn to exceed the available liquidity.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L209-L222
Visibly, the function directly performs the transfer operation without conducting any checks.

### Attack Path

1. Alice calls the `pullFunds` function to withdraw the underlying asset, and the transaction enters the mempool.  
2. Bob observes this transaction and quickly initiates a front-running transaction, such as a repay or deposit operation, which alters the state of the reserve pool.  
3. However, Alice still operates based on the previous asset state, leading to significant discrepancies or errors.

### Impact

* **Failed Fund Withdrawal**: When the `pullFunds` function attempts to withdraw funds from the reserve pool, if the state of the reserve pool is not updated in a timely manner (e.g., the balance or liquidity of the underlying asset is not properly calculated), the withdrawal may fail, causing the caller to be unable to obtain the funds they are entitled to.

* **Over-Withdrawal of Funds**: If the state of the reserve pool is not updated, leveraged users may withdraw more assets than are actually available. For instance, if the liquidity of the underlying asset is not updated promptly, leveraged users might withdraw more funds than intended, leading to insufficient balances in the reserve pool.

* **State Inconsistency**: If multiple transactions are processed concurrently and the contract fails to correctly update the state of each reserve pool, it may result in a mismatch between the in-memory state of the contract and the actual asset balances. This can lead to inconsistent data and unpredictable behavior. For example, if one user has already withdrawn funds but the internal liquidity state of the contract is not updated, the next user may incorrectly assume there is sufficient liquidity when executing their transaction.

### Mitigation

Add operations to update the reserve pool for the `pullFunds` and `pushFunds` functions.
```solidity
function pullFunds(address asset, uint256 amount) external nonReentrant {
        require(msg.sender == leverager, "borrower not leverager");
        DataTypes.ReserveData memory reserve = getReserve(asset);

          reserve.updateState();

        IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
    }

    /// @notice Allows leverager to push back funds to yAsset
    function pushFunds(address asset, uint256 amount) external nonReentrant {
        require(msg.sender == leverager, "borrower not leverager");
        DataTypes.ReserveData memory reserve = getReserve(asset);

        reserve.updateState();

        IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);
    }
```
