# Incorrect validation of observation data in checkPoolActivity()

### Summary

Incorrect validation of pool observation data in 

> checkPoolActivity()

will cause an inaccurate price deviation check for Yieldoor’s pool activity monitoring.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310

In Strategy.sol:310, the check for valid Uniswap V3 observations relies only on timestamp == 0, ignoring the initialized return value that comes with checking pool observation, risking invalid tick calculations in pools with uninitialized slots.

```solidity
 for (uint16 i = 1; i <= observationCardinality; i++) {
            uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
            (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
            if (timestamp == 0) {
                revert("timestamp 0");
            }
```



### Internal Pre-conditions

1. checkPoolActivity() iterates over observations to check price stability.
2. Validation assumes timestamp != 0 means valid data.
3. Pool’s observationCardinality exceeds written observations

### External Pre-conditions

The pool being queried is either newly deployed, has low interaction volume or has recently increased observationCardinality, leaving some slots uninitialized, resulting in fewer observations than its observationCardinality (e.g., 2 observations written, cardinality = 100).



### Attack Path

1. System calls checkPoolActivity() on a pool with observationCardinality = 200, currentIndex = 49, but only 50 slots filled.
2. Function computes index = (200 + 49 - 150) % 200 = 99 (uninitialized).
3. Function fetches observations(99): timestamp = 1, tickCumulative = 12345, initialized = false.
4. Function passes timestamp != 0, uses bad tickCumulative, misjudges delta.

### Impact

The Yieldoor pool activity monitoring system suffers unreliable stability checks in edge cases, potentially misclassifying pool activity.

- False Positives: An invalid tickCumulative could make a volatile pool appear stable (small delta), risking user funds in the Strategy.

- False Negatives: Conversely, it could exaggerate delta beyond maxObservationDeviation, rejecting a stable pool and disrupting vault operations.

### PoC

_No response_

### Mitigation

Add initialized check

```solidity
(uint32 timestamp, int56 tickCumulative, , bool initialized) = IUniswapV3Pool(pool).observations(index);
if (!initialized || timestamp == 0) {
    revert("invalid observation");
}
```
