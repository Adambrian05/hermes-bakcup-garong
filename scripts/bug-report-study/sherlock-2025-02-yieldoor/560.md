# Deposit Fee Truncation Enables Fee Evasion for Share Values Between 1 and 9999

### Summary

The `Vault` contract includes a deposit fee mechanism within the deposit function, designed to deduct a fee from the calculated shares based on the `depositFee` value, which is expressed in basis points (bps) with a denominator of 10,000. The relevant code is:  

```solidity
if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
```

The `depositFee` is configurable via the `setDepositFee` function, with a cap of 10 bps (equivalent to 0.1%):  

Due to Solidity’s integer arithmetic, which truncates division results to the nearest integer below, the fee calculation `(shares * depositFee) / 10_000` evaluates to 0 when the result is less than 1. Specifically, when depositFee is set to its maximum of 10 (0.1%) and the pre-fee shares value falls between 1 and 999, the computed fee is less than 1 and truncates to 0. This allows users to manipulate their deposit amounts in the `_calcDeposit` function to target this share range, effectively bypassing the intended fee and receiving the full share allocation.

## Analysis
The fee subtracted from `shares` is:  

```solidity
fee = (shares * depositFee) / 10_000
```
- `depositFee`: A value in basis points, where 10,000 bps = 100%, 100 bps = 1%, and 10 bps = 0.1% (0.001 as a decimal).  

- `10_000`: The denominator, scaling the bps to a fractional value (e.g., 10 / 10,000 = 0.001).  

- `shares`: The number of shares calculated by _calcDeposit before the fee is applied.

With `depositFee = 10` (0.1%, the maximum allowed):  

```solidity
fee = (shares * 10) / 10_000 = shares / 1_000
```
Since Solidity performs integer division, the result is truncated. We want `fee = 0`, which occurs when: 

```solidity
shares / 1_000 < 1
```
This means `shares < 1_000`.
Case:
If  `shares = 999`:
```solidity
(999 * 10) / 10_000 = 9_990 / 10_000 = 0.999 → 0 (truncated)
```
Thus, for shares in the range `[1, 999]`, `(shares * 10) < 10_000`, and the fee truncates to 0. The subtraction becomes:  

```solidity
shares -= 0  // shares unchanged
```
The contract then enforces `require(shares > 0, "shares cant be 0")` after the fee adjustment. Since shares remains between 1 and 999, this check passes, and the user retains the full shares amount without any deduction.




### Root Cause

In `Vault.sol::deposit`, `if (depositFee > 0) shares -= (shares * depositFee) / 10_000` will always truncate the result of the calculation to `-0` for values between 1-999

### Impact

1. Fee Evasion: Users can craft deposit amounts (amount0, amount1) to ensure _calcDeposit yields shares between 1 and 999, avoiding the 0.1% fee entirely. This undermines the fee’s stated purpose—to deter griefing via spam deposits and withdrawals—as noted in the contract comments.  

2. Unfair Deposit Calculation: Users depositing larger amounts (e.g., shares = 1_000, fee = 1) pay the fee, while those exploiting this range do not, creating an inequitable system.  

3. Griefing Vulnerability: Attackers can repeatedly deposit small amounts targeting this range, incurring no cost, thus negating the fee’s protective intent and potentially disrupting vault liquidity over time.

### Mitigation

Minimum Fee Enforcement
- Ensure non-zero fee when a depositFee is enforced
```solidity
if (depositFee > 0) {
    uint fee = (shares * depositFee) / 10_000;
    if (fee == 0 && shares > 0) fee = 1;
    shares -= fee;
}
```
