# Leveraged Positions Can Be Opened with Zero Collateral

### Summary

A vulnerability in `Leverager.sol` allows a user to open a leveraged position without contributing any personal collateral. By setting the collateral contribution parameters (`amount0In` and `amount1In`) to zero while specifying nonzero desired vault deposits (`vault0In` and `vault1In`), the protocol flashloans the entire amount needed to open the position. This behavior violates the invariant that every leveraged position must be partially funded by the user's own capital, ensuring that users share in the risk. As a result, the user's own capital contribution is zero, which means that—even if the protocol enforces a maximum leverage limit—the effective leverage from the user’s perspective is not bounded by that limit. In simpler terms, the user circumvents the intended risk control because they are not held to the maximum leverage requirement that applies when personal funds are used.

### Root Cause

The bug originates from the lack of validation in the `openLeveragedPosition` function (and its `LeverageParams`) in [Leverage.sol:103-201](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103-L201) where the user’s collateral inputs—`amount0In` and `amount1In`—can be zero. 

### Internal Pre-conditions

1. The `openLeveragedPosition` function is invoked.
2. The `LeverageParams` struct provided to the function has:
      - `amount0In` == 0
      - `amount1In` == 0
      - Nonzero values for `vault0In` and `vault1In`
3. The vault and lending pool contracts are properly configured and operational.

### External Pre-conditions

1. The lending pool must have sufficient liquidity to flashloan the entire vault deposit amounts.
2. The underlying tokens (e.g. WBTC and USDC) behave normally and allow for transfers and approvals.
3. No external rate or oracle manipulations are required; standard market conditions apply.

### Attack Path

1. **Preparation:**
    A user prepares leverage parameters with:
         - `amount0In` = 0 and `amount1In` = 0
         - Nonzero `vault0In` and `vault1In` (e.g., 0.5 WBTC and 1000 USDC)
2. **Execution:**
    The user calls `openLeveragedPosition` with these parameters.
3. **Flashloan Activation:**
    Within the function, the protocol calculates:
    ```solidity
    delta0 = vault0In - amount0In; // equals full vault0In
    delta1 = vault1In - amount1In; // equals full vault1In
    ```
    These amounts are flashloaned from the lending pool.
4. **Position Creation:**
    The position is opened entirely with flashloaned funds, meaning the user’s own capital contribution is zero.

### Impact

Allowing leveraged positions to be opened without any user-contributed collateral means that positions can be entirely financed through flashloans. This exposes the protocol to increased risk because the entire position is funded by borrowed money and the intended maximum leverage cap is effectively rendered meaningless, leading to severely undercollateralized exposures. Furthermore, with no personal funds at stake, even small adverse price movements can trigger aggressive liquidations at unfavorable prices. This can result in a cascade of liquidations, increased slippage, and, under extreme conditions, indirect losses for the protocol despite the liquidation mechanism being designed to recover borrowed funds.

### PoC

Copy the test below and add it to the `Leverager.t.sol` test file:

```solidity
function test_borrowTokenWithZeroCollateral() public {
    // Start as the depositor
    vm.startPrank(depositor);
    
    // Prepare leverage parameters with zero personal collateral:
    ILeverager.LeverageParams memory lp;
    lp.amount0In = 0;         // User contributes 0 WBTC
    lp.amount1In = 0;         // User contributes 0 USDC
    lp.vault0In = 0.5e8;       // Desired vault deposit: 0.5 WBTC
    lp.vault1In = 1000e6;      // Desired vault deposit: 1000 USDC
    lp.vault = vault;
    lp.maxBorrowAmount = 20_000e6;
    lp.denomination = address(usdc);
    
    // Prepare swap parameters for potential swaps (not central to the bug)
    IMainnetRouter.ExactOutputParams memory ep;
    bytes memory _path = abi.encodePacked(address(wbtc), uint24(3000), address(usdc));
    ep.path = _path;
    ep.deadline = block.timestamp;
    ep.amountInMaximum = type(uint256).max;
    ep.recipient = leverager;
    lp.swapParams1 = abi.encode(ep);

    // Fund the depositor with minimal funds (just enough to satisfy approvals, but not used as collateral)
    deal(address(wbtc), depositor, 0.5e8);
    deal(address(usdc), depositor, 50_000e6);
    wbtc.approve(leverager, type(uint256).max);
    usdc.approve(leverager, type(uint256).max);

    // Execute leveraged position opening.
    // Since amount0In and amount1In are zero, the entire required deposit is flashloaned.
    ILeverager(leverager).openLeveragedPosition(lp);
    
    // At this point, the position is opened without any collateral from the depositor.
}
```

This test proves that a user can open a leveraged position without any personal capital by setting both `amount0In` and `amount1In` to zero. The vault receives nonzero deposit instructions (`vault0In` and `vault1In`), and the contract flashloans these amounts, violating the core invariant that the user must provide collateral. Furthermore, the calculated leverage (which is supposed to reflect user risk) is not properly bounded. The user, therefore, circumvents the maximum leverage restrictions that would normally apply if the user provided personal collateral.

### Mitigation

To fix this vulnerability, the contract should enforce a minimum personal collateral requirement by requiring that at least one of `lp.amount0In` or `lp.amount1In` is nonzero. For example:

```solidity
require(lp.amount0In > 0 || lp.amount1In > 0, "must supply collateral");
```
