# Malicious Users Can Exploit Fee Withdrawals to Freeze Protocol Functions

### Summary

In Strategy.sol#L159, the calculation of liquidityToRemove in _withdrawPartOfVestingPosition() does not check against remainingLiquidity, allowing an underflow revert when liquidityToRemove exceeds remainingLiquidity. This halts critical protocol functions dependent on collectFees().

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L159

### Root Cause

In [Strategy.sol#L465C9-L471C52](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L465C9-L471C52), when the protocol withdraws liquidity from an active vesting position, collectFees() is called and internally triggers _withdrawPartOfVestingPosition().

The following calculation does not cap liquidityToRemove, leading to an underflow when remainingLiquidity is insufficient:

```solidity
uint128 liquidityToRemove = lastValid == vp.endTs
    ? vp.remainingLiquidity
    : uint128(vp.initialLiquidity * (lastValid - vp.lastUpdate) / (vp.endTs - vp.startTs));

_removeFromPosition(liquidityToRemove, vp.tickLower, vp.tickUpper);

vp.remainingLiquidity -= liquidityToRemove;  // Underflow occurs here
vp.lastUpdate = lastValid;
```
Since collectFees() is public, it can be repeatedly called, draining liquidity before the vesting period ends, eventually triggering the underflow.

### Internal Pre-conditions

1. A vesting position is active (ongoingVestingPosition = true) with initialLiquidity set (e.g., 1000).

2. remainingLiquidity is gradually reduced through normal collectFees() operations or abuse.
 
3. A call to collectFees() occurs when remainingLiquidity is less than liquidityToRemove.
 
4. _withdrawPartOfVestingPosition() does not check for underflow before performing:

```solidity
remainingLiquidity -= liquidityToRemove;
```

### External Pre-conditions

- Any user can call the public collectFees(), triggering vested liquidity withdrawals.
- The Rebalancer and other protocol functions (e.g., rebalance, setProtocolFee, compound) also call collectFees(), expanding the attack surface.

### Attack Path

- Owner Action:
Calls addVestingPosition(amount0, amount1, 1 year), initializing:
initialLiquidity = 1000
remainingLiquidity = 1000

- Malicious User Exploit:
Calls collectFees() periodically (e.g., every 14 seconds) to bypass:
```solidity
if (vestPosition.lastUpdate == block.timestamp) return;
```
Gradually reduces remainingLiquidity with each call.

- Multiple calls from the malicious user, Rebalancer, or protocol functions (rebalance, setProtocolFee, compound) further reduce remainingLiquidity.
_withdrawPartOfVestingPosition() calculates a high liquidityToRemove:
```solidity
uint128(vp.initialLiquidity * (lastValid - vp.lastUpdate) / (vp.endTs - vp.startTs))
```
vp.initialLiquidity is immutable when a vesting positon is created.
(lastValid - vp.lastUpdate) grows over time.
remainingLiquidity -= liquidityToRemove underflows, causing a Solidity revert.

- All functions relying on collectFees() fail, including:
rebalance()
setProtocolFee()
compound()
The protocol remains unusable until endTs (1 year), when ongoingVestingPosition = false

### Impact

The entire Yieldoor protocol suffers an approximate loss of full functionality. Critical functions including rebalance, setProtocolFee, and compound become inoperable due to the revert in collectFees(), causing a Denial of Service (DoS) until the vesting period ends (endTs). This can be repeated with each new vesting position, halting the protocol.

### Mitigation

CHeck if liquidityToRemove does not exceed remainingLiquidity

```solidity
if (liquidityToRemove >= vp.remainingLiquidity) {
    liquidityToRemove = vp.remainingLiquidity;
}
```
