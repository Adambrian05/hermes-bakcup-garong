# `Leverager::_calculateTokenValues()` will return wrong prices for token pairs which: have different decimals and one of the tokens does not have a price feed.

## Summary

[The calculations](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L445) work fine if both tokens have the same decimals, but not if they don't:

```solidity
        // If chPrice0 is 0, it means token0 doesn't have a price feed.
        // Therefore, convert it to token1 and from there, convert it to USD.
        if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }
```

## Root Cause

Not adjusting for potential differences in decimals in the logic shown above.

## Internal Pre-conditions

- One token does not have a price feed. Expected to work fine as per docs.
- The two tokens used have different decimals.

## External Pre-conditions

It always happens given the internal pre-conditions.

## Attack Path

It is a logic error, so it always happens.

## Impact

Highly inflated or small prices for the tokens that abide by the internal pre-conditions. This leads to user positions' values being calculated higher or lower than they should be.

When over-calculating, if there are more positions and an overvalued one is fully withdrawn, it will take more funds than it deserves due to bad inflated accounting.

When under-calculating, this might lead to just a revert later in `isLiquidatable()` at the end of `openLeveragedPosition()`.

Calculating the actual value of collateral is crucial for all protocol operations; miscalculating it is a critical issue.

## PoC

Detailed flow of the execution, code [here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L424):

- Price feeds are trusted and always return 1e18 decimal precision values as mentioned [in docs](https://docs.google.com/document/d/1FUjXMXBRBRVgOYSMGORTFmS9fj_nh-ifQhoY0jjhwPY/edit?tab=t.0) and Discord.
- Let's take a pair where: `token0 == 18 decimals`, `token1 == 6 decimals`.
- The `PRECISION` constant is `1e30` in `Leverager`. See [here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L29).
- The `price` argument passed to `_calculateTokenValues()` comes from `IVault::twapPrice() -> Strategy::twapPrice()`, which is 30 decimals. See [here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L360). The sqrt price is scaled by `1e15`, which, when squared, gives `1e30`. All code calls to `_calculateTokenValues()` pass this price as an argument.

```solidity
 /// @notice Calculates the USD value of amount0 and amount1
    /// @dev Requires at least one of them to have a trustworthy price feed.
    /// If one of them doesn't have a price feed, it uses the pool TWAP price to convert said token to the other one.
    /// @param token0 The address of the first token
    /// @param token1 The address of the second token
    /// @param amount0 The amount of token0
    /// @param amount1 The amount of token1
    /// @param price The TWAP token0/token1 price.
    /// @return usdValue The total token value, denominated in USD, scaled to 1e18.
    function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
        internal
        view
        returns (uint256 usdValue)
    {
        uint256 chPrice0;
        uint256 chPrice1;
        uint256 decimals0 = 10 ** ERC20(token0).decimals();
        uint256 decimals1 = 10 ** ERC20(token1).decimals();
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += amount0 * chPrice0 / decimals0;
        }
        if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
            chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
            usdValue += amount1 * chPrice1 / decimals1;
        }

        // If chPrice0 is 0, it means token0 doesn't have a price feed.
        // Therefore, convert it to token1 and from there, convert it to USD.
        if (chPrice0 == 0) {
@>      // 👁️🟢 Let's analyze the decimals of this operation's output. When multiplying, decimals add; when dividing, decimals subtract.
@>      // token0Decimals * twapPrice30Decimals / 30DecimalsPrecision * 18DecimalsPrice / token1Decimals
@>      // 18 * 30 / 30 * 18 / 6
@>      // 18 + 30 - 30 + 18 - 6
@>      // 18 + 18 - 6
@>      // 36 - 6 = 30 decimals for `usdValue`
@>      // As per return comments, the system expects this value to have 18 decimals.
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
@>      // 👁️🟢 Let's analyze this one now:
@>      // 6 * 30 / 30 * 18 / 18
@>      // 6 + 30 - 30 + 18 - 18
@>      // 6 + 18 - 18
@>      // 6 decimals for `usdValue`
@>      // As per return comments, the system expects this value to have 18 decimals. But it has 6.
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }

        return usdValue;
    }
```

## Mitigation

Adjust for different token decimals in the `_calculateTokenValues()` function on the logic for no-feed tokens.

Like so:

```solidity
// Calculation when token0 has no feed:
// (amount0 * price / PRECISION) * chPrice1 / decimals1;
// (ends up with token0 decimals but it is a token1 amount! ) * chPrice1 / decimals1;
// There is where the error is, in that numerator calculation, a token1 amount with token 0 decimals.

// This first numerator calculation needs decimal adjustment, this one -> (amount0 * price / PRECISION)
// adjustment -> (token0 decimals - token1 decimals)
//  (amount0 * price / PRECISION / (scale-down factor if token0 decimals > token1 decimals))
//  (18 + 30 - 30 - (18-6)) = 18 - 12 = 6 decimals, just like token1.

// However, if token0 has fewer decimals than token1, the adjustment scale calculation differs:
// adjustment -> (token1 decimals - token0 decimals)
//  (amount0 * price / PRECISION * (scale-up factor if token1 decimals > token0 decimals))
//  (6 + 30 - 30 + (18-6)) = 6 + 12 = 18 decimals, just like token1 in this case.

// Apply similar adjustment logic in the token1 no-feed calculation part of the `if-else`.
// In this case the overall operation is: amount1 * PRECISION / price * chPrice0 / decimals0;
// The adjustment is needed after this => amount1 * PRECISION / price
// As this is a token0 amount in token1 decimals.
```
