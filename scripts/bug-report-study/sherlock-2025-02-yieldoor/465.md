# Inability to Withdraw Funds During Protocol Pause Restricts User Control Over Assets and Violates DeFi Safety Standards

## Summary
The LendingPool contract restricts users from [withdrawing their funds when the protocol is paused](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L85), violating a critical DeFi safety standard. While the contract allows repayments during paused state, it does not permit redemptions (withdrawals), effectively locking user funds in the protocol during emergency situations when users would most need access to their assets. This design flaw removes users' control over their risk exposure and contradicts established best practices for DeFi protocols.
[ref: Solodit ID: SOL-CR-2](https://solodit.cyfrin.io/checklist)

## Vulnerability Details
The LendingPool contract implements a pause mechanism through the `paused` state variable and the `notPaused` modifier. This modifier is applied to critical functions including `deposit()` and `redeem()`, but notably not to `repay()`.

The `notPaused` modifier prevents execution when the protocol is paused:

```solidity
/// @notice Checks whether the contract is paused or not.
modifier notPaused() {
    require(!paused, "contract paused");
    _;
}
```


The `redeem()` function, which allows users to withdraw their assets, is protected by this modifier:

```solidity
function redeem(address underlyingAsset, uint256 yAssetAmount, address to)
    public
    notPaused
    nonReentrant
    returns (uint256)
{
    // Function implementation
}
```


This means that when the protocol is paused (typically during emergencies or when security issues are detected), users cannot withdraw their funds. However, borrowers can still repay their loans since the `repay()` function does not include the `notPaused` modifier:

```solidity
function repay(address asset, uint256 amount) external nonReentrant returns (uint256) {
    // Function implementation
}
```


This asymmetric design creates a situation where funds can flow into the protocol during an emergency (via repayments) but cannot flow out (via withdrawals), effectively trapping user assets.

## Proof of Concept
Consider the following scenario:

1. A security vulnerability is discovered in the protocol.
2. The protocol owner calls `emergencyPauseAll()` to pause the protocol and prevent further exploitation.
3. Users, concerned about their funds, attempt to withdraw by calling `redeem()`.
4. All withdrawal attempts fail with the error message "contract paused".
5. Users are forced to keep their assets in the protocol despite the known security risk.

Meanwhile, borrowers can still repay their loans, which increases the pool of trapped assets.

## Impact Details
This vulnerability severely impacts user trust and violates a fundamental principle of DeFi: users should always maintain control over their assets, especially during emergencies. The inability to withdraw funds during a protocol pause could lead to significant financial losses if the pause precedes a more serious failure. Additionally, this design contradicts established industry standards and best practices for DeFi protocols.

1. Remove the `notPaused` modifier from the `redeem()` function to allow withdrawals even when the protocol is paused:

function redeem(address underlyingAsset, uint256 yAssetAmount, address to)
    public
    nonReentrant
    returns (uint256)

    // Function implementation
