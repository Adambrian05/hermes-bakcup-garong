# Secondary position is not compatible with position width <= 4 * tickSpacing

### Summary

Secondary position is not compatible with position width <= 4 * tickSpacing

### Root Cause

In [Strategy::_setSecondaryPositionsTicks()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L366) function 2 * tickSpace position width is not compatible due to mishandling of some scenarios. The default configuration is also covered by this issue because it uses 4 * tickSpacing. According to sponsor comment, it should support every position width which follows 2 * tickSpace condition.
[Sponsor comment](https://discord.com/channels/812037309376495636/1343598372187017309/1345491352799940609)

This function is always called just after main position adjustment. After this adjustment, one of those tokens balance may remain in the strategy contract and the secondary position is used for adding this liquidity to a range which doesn't cover current price in it.

This issue is occured because of incorrect implementation for else case in if check:

```solidity
        } else {
&>          secondaryPosition.tickLower = tick - modulo + tickSpacing; 
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }
```

For instance, in WETH/USDC pool if price is equal to 2,000 and if we have only USDC in the strategy, it will add this USDC liquidity to lower points such as [1990, 1980] range. 

This won't be possible if the tick is negative and currentTick is between upper tick and border point. ( For details attack path ). The main reason of this issue is directly setting one tick side to main position's upper/lower tick and mishandling the negative tick conditions.

### Internal Pre-conditions

1. Position width <= 4 * tickSpacing

> Note: This issue doesn't need to negative tick it can happen in positive tick conditions with 2 * tickSpacing position width

### External Pre-conditions

None

### Attack Path

Environment:
Tick spacing = 60
Current price tick = -110
Main position upper tick = 0
Main position lower tick = -240
Middle point of main position = -120
Pool WETH/USDT

1. Rebalance is called
2. Our previous position is out of range and higher than current price which means we have only WETH
3. Main position rebalanced but no liquidity is added
4. In second position adjustment bal0in1 > bal1
5. Modulo will be equal to -50 -> Solidity use following formula A%B = A - B * (A/B) 
6. tick - modulo + tickSpacing = -110 + 50 + 60 = 0 -> tick lower
7. But our upper tick is already 0 because it's directly set.

```solidity
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing; 
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }
```

The same scenario can be simulated with position width = 2 * tickSpace ( possible conf ) because this time lower tick will be higher than the upper tick and it won't work again.


### Impact

Rebalance and compound calls will revert because upper can't be lower than lower tick.  This situation may happen at the beginning of the pool creation because first user can deposit only WETH and if he only deposits WETH, the other users have to deposit WETH in order to join the strategy.

In addition, rebalance functionality is used for putting the liquidity to effective price ranges. The rebalance functionality remains affected until this condition is resolved. It will cause loss of yields in the end because previous position won't return any farming value until rebalance.

### Mitigation

Do not directly set the main position upper/lower points for both if cases. Instead be sure the price is out of range first and then adjust the other tick according to set tick.
