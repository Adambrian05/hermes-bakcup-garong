# Division error in liquidation function will miscalculate borrowed value for leveraged positions

# Summary:
An arithmetic error in the liquidation function will miscalculate the borrowed value for leveraged positions as the contract divides by the raw decimal count instead of the proper scaling factor, causing unintended liquidations.

# Root Cause:
In [Leverager.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol), within the `liquidatePosition` function the borrowed value is calculated as follows: https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L318
```solidity
        uint256 borrowedValue = owedAmount * bPrice / ERC20(up.denomination).decimals();
```
Here, `ERC20(up.denomination).decimals()` returns a value like 18 rather than the expected multiplier 10 ** 18. This results in an underestimation of the borrowed value used in liquidation threshold calculations.

# Internal Pre-conditions:
1. The liquidation function is triggered when a leveraged position is borderline liquidatable.
2. The borrowed asset’s price (`bPrice`) is fetched from the price feed and is scaled in 1e18.

# External Pre-conditions:
- The external price feed provides prices in a 1e18 scale, expecting the conversion factor to be 10 ** decimals.

# Attack Path:
1. Under volatile market conditions, a position nears the liquidation threshold.
2. The miscalculation in borrowed value (due to dividing by 18 instead of 10**18) causes the system to underestimate the actual borrowed USD value.
3. As a result, a position that should be safe becomes (or is deemed) under–collateralized and is liquidated prematurely.

# Impact:
Borrowers risk having their positions liquidated at an incorrect threshold, leading to unnecessary loss of collateral and financial harm.

# PoC:
This PoC demonstrates how dividing by the raw decimal value (e.g. 18) instead of the proper scaling factor (10**decimals) leads to a gross miscalculation of the borrowed value during liquidation. In the example, the correct borrowed value differs significantly from the buggy calculation.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

contract PoCDivisionError {
    // Correct calculation: borrowedValue = owedAmount * bPrice / (10 ** tokenDecimals)
    function correctBorrowedValue(
        uint256 owedAmount,
        uint256 bPrice,
        uint8 tokenDecimals
    ) public pure returns (uint256) {
        return owedAmount * bPrice / (10 ** tokenDecimals);
    }
    
    // Buggy calculation: borrowedValue = owedAmount * bPrice / tokenDecimals
    function buggyBorrowedValue(
        uint256 owedAmount,
        uint256 bPrice,
        uint8 tokenDecimals
    ) public pure returns (uint256) {
        return owedAmount * bPrice / tokenDecimals;
    }
    
    // Test function to compare both calculations.
    // For instance, if owedAmount = 1e18, bPrice = 1e18, tokenDecimals = 18:
    //   correctBorrowedValue = 1e18 * 1e18 / (10**18) = 1e18.
    //   buggyBorrowedValue = 1e18 * 1e18 / 18 ≈ 5.56e34, which is wildly incorrect.
    function testValues(uint256 owedAmount, uint256 bPrice) external pure returns (uint256 correct, uint256 buggy) {
        correct = correctBorrowedValue(owedAmount, bPrice, 18);
        buggy = buggyBorrowedValue(owedAmount, bPrice, 18);
    }
}
```
**PoC Explanation**
The PoC in `PoCDivisionError` demonstrates an arithmetic error in the liquidation calculation. The issue is that the borrowed value is computed by dividing by the raw value of the token’s decimals (e.g., 18) instead of the proper scaling factor (10 ** decimals).

**The Bug:**
- Correct Calculation:
```solidity
borrowedValue = owedAmount * bPrice / (10 ** tokenDecimals);
```
- Buggy Calculation:
```solidity
borrowedValue = owedAmount * bPrice / tokenDecimals;
```
- For a token with 18 decimals, instead of dividing by 1e18, the code incorrectly divides by 18.

**How It Works:**
- For instance, if `owedAmount` = 1e18 and `bPrice` = 1e18, then:
   - Correct Calculation:
1e18 * 1e18 / 1e18 = 1e18
   - Buggy Calculation:
1e18 * 1e18 / 18 ≈ 5.56e34, which is several orders of magnitude larger than intended.

**Attack Scenario:**
This massive miscalculation means that the liquidation threshold is based on an incorrect borrowed value. An attacker or even market fluctuations could trigger premature liquidations of positions that are actually sufficiently collateralized. In effect, the protocol might erroneously liquidate positions because the computed borrowed value is way off, leading to unnecessary loss of collateral for borrowers.

# Mitigation:
- Replace the division by `ERC20(up.denomination).decimals()` with a division by the proper scaling factor, for example:
```solidity
uint256 borrowedValue = owedAmount * bPrice / (10 ** ERC20(up.denomination).decimals());
```
- Ensure that all calculations converting token amounts to USD consistently use the full exponentiation of the token’s decimals.
- Add unit tests for the liquidation logic under various price scenarios to verify correct behavior.
