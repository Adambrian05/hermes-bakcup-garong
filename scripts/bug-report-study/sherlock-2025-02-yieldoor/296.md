# Stale borrowing index during rate config update leads to incorrect interest accrual

## Summary
The `LendingPool#setBorrowingRateConfig` function fails to update the borrowing index before changing rate parameters and doesn't update rates after, causing incorrect interest calculations until the next state-modifying operation.

## Relevant Context
The lending pool uses a borrowing index that accumulates interest over time. This index is used to calculate the total amount owed by borrowers. The borrowing rate configuration determines how interest accrues based on utilization levels.

This is the implementation of the functions `setBorrowingRateConfig` from Extra Finance:

[`LendingPool.sol#L796`](https://github.com/ExtraFi/extra-contracts/blob/a66e925d78ee5c990eb2bafa5009cebcbeafe42d/contracts/lendingpool/LendingPool.sol#L796)

[`LendingPool.sol#L527`](https://github.com/ExtraFi/extra-contracts/blob/a66e925d78ee5c990eb2bafa5009cebcbeafe42d/contracts/lendingpool/LendingPool.sol#L527)

## Root Cause
When updating borrowing rate parameters via `setBorrowingRateConfig`, the function doesn't:
1. Call `updateState()` to sync the borrowing index with current rates before the change
2. Call `updateInterestRates()` to apply the new rates after the change

[`LendingPool.sol#L348`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L348)

[`LendingPool.sol#L241`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L241)

This means:
- Interest accrued under old rates isn't properly accounted for before the change
- New rates don't take effect until the next state-modifying operation (deposit/withdraw/borrow/repay)
- The borrowing index remains stale during this period

## Attack Path

1. Reserve has active borrows with utilization rate of 80%
2. Current borrowing rate is 20% based on old rate config
3. Owner calls `setBorrowingRateConfig` to increase rates (e.g., new rate at 80% utilization = 30%)
4. Interest continues accruing at 20% instead of 30% until next state update
5. When next state update occurs, jump in rates creates discontinuity in interest calculations

## Impact Explanation
Medium. While funds aren't directly at risk, this leads to incorrect interest calculations that either:
- Disadvantage lenders if new rates are higher (lost interest)
- Disadvantage borrowers if new rates are lower (excess interest charged)

The impact is amplified with larger rate changes and longer periods between state updates.

## Proof of Concept
Scenario:
1. Reserve has 100 ETH borrowed, 125 ETH total (80% utilization)
2. Old config: 20% rate at 80% utilization
3. Owner updates to: 30% rate at 80% utilization
4. No transactions for 1 day
5. Interest accrues at 20% instead of 30% for 24 hours
6. Lost interest = 100 ETH * (30% - 20%) * (1/365) = 0.027 ETH

## Recommendation
Update `setBorrowingRateConfig` to properly handle state transitions:

```diff
function setBorrowingRateConfig(
    address asset,
    uint16 utilizationA,
    uint16 borrowingRateA,
    uint16 utilizationB,
    uint16 borrowingRateB,
    uint16 maxBorrowingRate
) public onlyOwner notPaused {
    DataTypes.ReserveData storage reserve = reserves[asset];
+   // Update state with old rates
+   reserve.updateState();
    // Set new rate config
    setBorrowingRateConfig(reserve, utilizationA, borrowingRateA, utilizationB, borrowingRateB, maxBorrowingRate);
+   // Update rates with new config
+   reserve.updateInterestRates();
}
```
