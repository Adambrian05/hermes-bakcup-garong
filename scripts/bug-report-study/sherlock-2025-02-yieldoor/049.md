# The consecutive-difference check in checkPoolActivity() allows attackers to manipulate pricing and force suboptimal rebalancing for depositors

### Summary

The `Strategy` contract’s price validation function, `checkPoolActivity()`, allows attackers to gradually manipulate Uniswap V3 pool prices without being detected. This happens because the function lacks a correct implementation and only verifies that each consecutive price change remains below a configured threshold (`maxObservationDeviation`) and exits early as soon as it encounters an older observation. This allows an attacker to spread multiple small price increments below maxObservationDeviation and bypass the pool-activity check, ultimately forcing rebalancing or compounding at manipulated prices.

### Root Cause

In [`Strategy.sol:310`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310) the `checkPoolActivity()` function only checks that **consecutive** observations differ by no more than `maxObservationDeviation` and returns early upon encountering an observation older than the TWAP interval. 

Because the function never evaluates the total accumulated movement across all observations, and only does it across consecutive ones only, attackers can accumulate a major price shift in increments, bypassing the intended manipulation protection.

### Internal Pre-conditions

The maxObservationDeviation parameter must be set to permit small but repeated price increments (e.g., 100 ticks each, like it appears in the strategy.sol constructor)

### External Pre-conditions

The attacker can execute multiple trades in the underlying Uniswap V3 pool, each shifting the price in small increments under maxObservationDeviation. 

### Attack Path

1. The attacker repeatedly trades in the Uniswap V3 pool to move its tick by small steps (e.g., 90–99 ticks) per observation.  
2. These trades are timed so that each difference **between consecutive observations** remains under maxObservationDeviation.  
3. Once an older observation is reached (timestamp < lookAgo), checkPoolActivity() exits early and returns true, concluding there is “no abnormal activity.”  
4. The attacker calls rebalance() or compound(), which rely on this passed check, causing strategy liquidity changes at artificially skewed prices. 

### Impact

- Depositors suffer losses from unfavorable asset swaps or liquidity positioning, as the strategy enters at manipulated price levels.  
- The attacker may extract a gain in the form of misaligned swaps, arbitrages, or artificially inflated protocol fee returns.

### Mitigation

1. Implement **Cumulative** Checks: Track the net price difference from the earliest relevant observation in the TWAP window to the most recent. Reject if cumulative movement exceeds a threshold.  
2. Remove Early Return: Continue verifying all observations across the TWAP window instead of returning true at the first observation older than lookAgo.
