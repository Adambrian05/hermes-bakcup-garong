# Creating vesting position might leave some unused balances, causing them to instantly be vested to the user

### Summary

When the owner wants to create a vesting position he calls `Vault::addVestingPosition`.

```solidity
    function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _duration) external onlyOwner {
        IERC20(token0).safeTransferFrom(msg.sender, strategy, amount0);
        IERC20(token1).safeTransferFrom(msg.sender, strategy, amount1);

        IStrategy(strategy).addVestingPosition(amount0, amount1, _duration); // all necessary checks are performed here.
    }
```

The function directly transfers the amount to the strategy and calls `Strategy::addVestingPosition`.


```solidity
   function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _vestDuration) external onlyVault {
        collectFees(); // we collect fees first, in case there hasn't been a call since previous vested position ended
        require(!ongoingVestingPosition, "there's a currently ongoing VestingPosition");

        _requirePriceWithinRange();
        VestingPosition memory vp;

        vp.tickLower = mainPosition.tickLower;
        vp.tickUpper = mainPosition.tickUpper;

        (uint160 sqrtPrice,,,,,,) = IUniswapV3Pool(pool).slot0();
        uint128 liquidity = LiquidityAmounts.getLiquidityForAmounts(
            sqrtPrice,
            TickMath.getSqrtRatioAtTick(vp.tickLower),
            TickMath.getSqrtRatioAtTick(vp.tickUpper),
            amount0,
            amount1
        );

        vp.initialLiquidity = liquidity;
        vp.remainingLiquidity = liquidity;

        IUniswapV3Pool(pool).mint(address(this), vp.tickLower, vp.tickUpper, liquidity, "");

        vp.startTs = block.timestamp;
        vp.lastUpdate = block.timestamp;
        ongoingVestingPosition = true;
        vp.endTs = block.timestamp + _vestDuration;

    
        vestPosition = vp;
    }
```

The function calculates the liquidity to be minted by the amounts and directly mints, without handling any excess funds that are not used.


In a situation, where the prices change while the owner's transaction is still pending it could leave excess amounts of `token1` or `token0` directly into idle balances, allowing those excess funds to instantly be redeemed by holders.

### Root Cause

When [minting liquidity](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L448) in `Strategy::addVestingPosition` excess amount is not returned causing it to instantly be redeemable by users.

### Internal Pre-conditions

None

### External Pre-conditions

1. Price slightly changes while the owner's tx is pending

### Attack Path

None

### Impact

The owner might suffer slight loss in assets.

### PoC

1. The price of ETH/USDC is 1/3000
2. The owner wants to add 5 ETH and 15,000 USDC
3. While the tx is pending the ratio drops to 1/2970
4. The owner add 5 ETH and 14 850 USDC leaving 150 USDC in idle balance ready to be claimed by anyone.

### Mitigation

Consider returning any excess amount to the owner disallowing it to instantly be claimed by other users.
