# Changing `maxLeverage`, might cause unfair liquidations

### Summary

To ensure whether a position is liquidatable or not `Leverager::isLiquidatable` is called.


```solidity
    function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
        Position memory pos = positions[_id];
        VaultParams memory vp = vaultParams[pos.vault];

        uint256 vaultSupply = IVault(pos.vault).totalSupply();

        (uint256 vaultBal0, uint256 vaultBal1) = IVault(pos.vault).balances();
        uint256 userBal0 = pos.shares * vaultBal0 / vaultSupply;
        uint256 userBal1 = pos.shares * vaultBal1 / vaultSupply;
        uint256 price = IVault(pos.vault).twapPrice();

        uint256 totalValueUSD = _calculateTokenValues(pos.token0, pos.token1, userBal0, userBal1, price);
        uint256 bPrice = IPriceFeed(pricefeed).getPrice(pos.denomination);
        uint256 totalDenom = totalValueUSD * (10 ** ERC20(pos.denomination).decimals()) / bPrice;

        uint256 bIndex = ILendingPool(lendingPool).getCurrentBorrowingIndex(pos.denomination);
        uint256 owedAmount = pos.borrowedAmount * bIndex / pos.borrowedIndex;

        uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;

        if (owedAmount > totalDenom || totalDenom - owedAmount < vp.minCollateralPct * base / 1e18) return true;
        else return false;
    }
```

To calculate the needed collateral, `base` is calculating `owedAmount / (maxLeverage - 1)`.

So if a user has borrowed 2 BTC at 5X leverage, `base` will be `(2e8 * 1e18) / 4e18 =  0.5e8`. and then `minCollateralPct` of `base` will be compared to `totalDenom - owedAmount` of the position.


However, in the situation where the maxLeverage gets changed the position could instantly, become liquidatable.

For the same 2 BTC at 5X leverage above, after time the maxLeverage gets changed to 2X.
`base` will be `(2e8 * 1e18) / 1e18 = 2e8`, in this case the collateral needed for that positition has increased 4X, which might cause the position to be liquidated despite being opened on the correct terms.


### Root Cause

In  [isLiquidatable](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L408) the calculations for base are using a maxLeverage that can be changed.

### Internal Pre-conditions

1. The owner has to lower/increase maxLeverage.

### External Pre-conditions

None

### Attack Path

None

### Impact

If `maxLeverage` gets lowered a lot of positions might get liquidated unfairly.

### PoC

1. User opens a position of $5000 with $1000 as collateral
2. His leverage is 5X
3. `base` is $4000 / 4 = 1000
4. The minimum collateral % is 10
5. `5000 - 4000 > 10% of 1000`, his position is save

His collateral has dropped to $4350

Owner changes maxLeverage to 2X.

-  `base` is $4000 / 1 = $4000
-  `4350 - 4000 < 10% of 4000`, his position can get liquidated now


### Mitigation

Consider saving `maxLeverage` into the position, to avoid unfair liquidations when it gets lowered.
