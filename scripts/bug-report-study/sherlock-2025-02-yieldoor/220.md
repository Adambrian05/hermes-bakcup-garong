# Inconsistent minimum borrow validation leads to reverting withdrawals

## Summary
The `Leverager#withdraw` function uses a different comparison operator (`>`) than `Leverager#_checkWithinlimits` (`>=`) when validating minimum borrow amounts, creating an inconsistency where positions that would be valid to create directly cannot be reached through partial withdrawals.

## Relevant Context
The protocol enforces a minimum borrow amount (`minBorrow`) to ensure positions maintain sufficient size. This is checked both when opening positions and during partial withdrawals.

## Root Cause
In `Leverager#_checkWithinlimits`, which is called when opening positions, the validation requires:

[`Leverager.sol#L466`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L466)

```solidity
require(up.initBorrowedUsd >= minBorrow, "position must be at least minBorrow amount");
```

However, in `Leverager#withdraw`, the check for remaining borrow amount uses:

[`Leverager.sol#L280`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L280)

```solidity
require(
    up.initBorrowedUsd * (1e18 - wp.pctWithdraw) / 1e18 > minBorrow,
    "remaining should be at least minBorrow"
);
```

This inconsistency in operators (`>=` vs `>`) creates a situation where positions cannot be partially withdrawn to an amount that would be valid to create directly. For example, if `minBorrow` is 100 USD, a user can create a position with exactly 100 USD debt, but another user cannot partially withdraw their larger position to reach 100 USD debt.

## Attack Path
1. Protocol has `minBorrow` set to some value X
2. User opens position with borrowed amount > X
3. User attempts to partially withdraw their position to exactly amount X
4. Transaction reverts due to `>` check in `withdraw`, despite X being a valid position size according to `_checkWithinlimits`
5. User is forced to either maintain a larger position than desired or fully withdraw

## Impact Explanation
Medium. Inconsistent in minimum borrow validation leads to reverting withdrawals.

## Proof of Concept
1. `minBorrow` is set to 100 USD
2. Alice opens position borrowing exactly 100 USD
   - Passes `_checkWithinlimits` check: `100 >= 100`
   - Position is valid
3. Bob opens position borrowing 200 USD
   - Passes `_checkWithinlimits` check: `200 >= 100`
   - Position is valid
4. Bob attempts to withdraw 50% of position
   - Remaining borrowed amount would be: `200 * 0.5 = 100`
   - Fails withdraw check: `100 > 100` is false
   - Transaction reverts despite resulting position meeting minimum borrow requirement

## Recommendation
Make the operators consistent by using `>=` in both locations:

[`Leverager.sol#L280`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L280)

```diff
- up.initBorrowedUsd * (1e18 - wp.pctWithdraw) / 1e18 > minBorrow
+ up.initBorrowedUsd * (1e18 - wp.pctWithdraw) / 1e18 >= minBorrow
```

This ensures positions valid at creation remain valid for partial withdrawals.
