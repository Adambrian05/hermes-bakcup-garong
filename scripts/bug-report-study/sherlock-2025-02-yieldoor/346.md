# Improper dp handling results in permanent DoS of Leverager::openLeveragedPosition

### Summary

`up.initCollateralValue` is not scaled correctly to 18 decimals, which results in an unintended DoS in `Leverager::openLeveragedPosition()` due to the `minBorrow` check.
The bug occurs because the system incorrectly assumes the values returned from `getPrice()` will be 1e18 scaled values.
The `getPrice()` method simply fetches the price, checks that it is > 0, and returns it.
Chainlink answer values depend on the type of feed. For USD based feeds, most answers are in 8 decimals.
This will brick the operation of `openLeveragedPosition()` on deployment.

### Root Cause

Improper decimal handling in https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L424-L451

The calculation for initCollateralValue is shown above in `openLeveragedPosition()` → `up.initCollateralUsd` * token dp / `bPrice`, where`up.initCollateralUsd` is the return value of `_calculateTokenValues()`.
In `_calculateTokenValues()`, if both feeds are whitelisted, the return value, `usdValue`, will be in the feeds decimals.
This will result in `up.initCollateralUsd` to be in the incorrect decimal scaling because both `_calculateTokenValues()` and `bPrice` are in the incorrect decimals..
This is a problem because it will cause a DoS later in `openLeveragedPosition()`

### Example
A user is borrowing WBTC, which has 8 decimals.
The decimals for `up.initCollateralUsd` would be: `1e8 (_calculateTokenValues) * 1e8 (token decimals) / 1e8 (bPrice) = 1e8`

### Mitigation

Rework the calculation in `Leverager::_calculateTokenValues()` - ensure that the values appended to usdValue in each conditional branch are in the same decimals.
Also, add the necessary scaling to `bPrice` in `Leverager::openLeveragedPosition()`
