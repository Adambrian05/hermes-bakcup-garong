# Contract will miscalculate repayment for lenders

### Summary

The root cause is the use of `amountOut0` instead of `amountOut1` in the repayment logic when `borrowed == up.token1`. This causes an incorrect partial repayment for positions that borrowed `token1`, leading to under-repayment or logical inconsistencies for the protocol, as the contract is repaying the debt with the wrong token amounts.

Root Cause: Misuse of `amountOut0` instead of `amountOut1` in the partial repayment calculation.
Impact: Leads to incorrect or incomplete debt repayment, causing potential financial loss or unexpected behavior.
Affected Party: Protocol / Liquidity providers (lenders) who might end up not being repaid correctly.
Actor / Attack Path: A position holder that borrows `token1` and performs a partial withdrawal can exploit or trigger this bug.

### Root Cause

In `Leverager.sol:231-235` (within the `withdraw()` function), when `borrowed == up.token1`, the partial debt repayment logic incorrectly references `amountOut0 `instead of `amountOut1`, as follows:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L231-L235

It should be referencing `amountOut1` in both the comparison and the ternary expression, not `amountOut0`. The correct logic would look like this:

```solidity
// Corrected snippet
} else if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```


### Internal Pre-conditions

1. A user opens (or holds) a leveraged position where the borrowed asset is `token1`.
2. The user has accumulated enough borrowed debt in `token1` that they wish to partially repay.
3. The user calls the `withdraw()` function with a partial withdrawal `(pctWithdraw < 1e18)` so that the code path for partial repayment executes.

### External Pre-conditions

(None strictly necessary beyond normal operations. The bug is purely an internal logic mistake. However, you might consider external conditions such as normal volatility or any required liquidity in the lending pool, but nothing special is required to trigger this bug.)

### Attack Path

1. User borrows `token1` by opening a leveraged position where denomination == `up.token1`.
2. User then calls withdraw() on that position with `pctWithdraw < 1e18` (a partial withdrawal).
3. During the partial repayment logic:
   -  The contract compares `amountOut1` with `owedAmount` but incorrectly decides to use `amountOut0` if `amountOut1 < owedAmount`.
   - Consequently, the repayment deducted from `amountOut1` is based on `amountOut0`’s value, causing an incorrect or incomplete repayment of the actual `token1` debt.

### Impact

The protocol (lenders) may end up not being repaid the correct amount of `token1`.
The user withdrawing may inadvertently (or maliciously) underpay their debt and walk away with extra token1, or the function could revert in scenarios where `amountOut0` is insufficient/unexpected.
This mismatch creates a financial risk for the protocol if positions remain under-collateralized or incorrectly reported.

    //       uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
    //       owedAmount -= repayFromWithdraw;

In this scenario, if `amountOut1 < owedAmount` but `amountOut0` is also small (or zero), the contract incorrectly deducts from `amountOut1` using the value from `amountOut0`, leading to an under-repayment. This mismatch can result in a net advantage for the borrower or cause other unexpected outcomes.

### Mitigation


**1. Correct the repayment logic for `token1`**  
In the `withdraw()` function, when `borrowed == up.token1`, **replace**:

```solidity
uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
owedAmount -= repayFromWithdraw;
amountOut1 -= repayFromWithdraw;
```

with:

```solidity
uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
owedAmount -= repayFromWithdraw;
amountOut1 -= repayFromWithdraw;
```

This way, if `amountOut1` is less than the owed amount, the contract will repay using all of `amountOut1`, rather than (incorrectly) using the value of `amountOut0`. If `amountOut1` is sufficient to cover the debt, it will properly deduct exactly the owed amount from `amountOut1`.

**2. Add targeted testing for partial repayments**  
To ensure no similar mistakes reoccur, introduce unit tests or integration tests specifically covering partial withdrawals (e.g. `pctWithdraw < 1e18`) in which the borrowed token is each of `token0` and `token1`. Verify that the post-repayment debt matches the expected owed amount in both scenarios.

**3. (Optional) Strengthen the repayment checks**  
As a defensive measure, you could also consider inserting a require statement (or a similar check) to ensure `repayFromWithdraw` always matches the correct asset’s quantity and does not exceed any available balance. For instance:

```solidity
require(
    repayFromWithdraw <= amountOut1,
    "Repayment exceeds amountOut1 balance"
);
```

This would provide an extra layer of certainty that incorrect variable references or arithmetic errors are caught early.

By making these changes and adding relevant test coverage, you ensure that the contract’s partial repayment logic will correctly handle both `token0` and `token1` as borrowed assets.
