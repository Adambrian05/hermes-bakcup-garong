# Zero-User Collateral Vulnerability in Leveraged Position Allowing Excessive Leverage

### Summary

A missing check for non-zero user collateral in the openLeveragedPosition function will cause excessive leverage and under-collateralized positions for the protocol. This vulnerability impacts all protocol participants as an attacker (or reckless user) will open positions entirely funded by flashloans, which in turn exposes the protocol to rapid liquidations and potential systemic instability.



### Root Cause

In [Leverager.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L103-L201) the openLeveragedPosition function does not enforce that lp.amount0In and lp.amount1In (the user-supplied collateral amounts) are greater than zero. This omission allows positions to be opened with zero personal collateral.

### Internal Pre-conditions

1. The vault parameters for leverage must be enabled (vaultParams[lp.vault].leverageEnabled == true).
2. The user provides leverage parameters where lp.amount0In and lp.amount1In are exactly zero.
3. The user specifies nonzero values for lp.vault0In and lp.vault1In, causing the contract to compute flashloan amounts (delta0 and delta1) equal to the entire vault deposit amounts.

### External Pre-conditions

1. The lending pool must have sufficient liquidity to cover the flashloan amounts requested.
2. The underlying oracle and TWAP mechanism must report a stable price such that IVault(lp.vault).twapPrice() returns an expected value and IVault(lp.vault).checkPoolActivity() returns true.
3. The swap router and price feed contracts are functioning as expected to facilitate any necessary token swaps.

### Attack Path

1. An attacker sets lp.amount0In = 0 and lp.amount1In = 0 while specifying nonzero values for lp.vault0In and lp.vault1In.
2. The attacker calls openLeveragedPosition with these parameters.
3. The function computes delta0 and delta1 as the full required deposit amounts.
4. The contract pulls the required funds via flashloans from the lending pool to fund the vault deposit.
5. The leveraged position is created entirely with borrowed funds, with no user-supplied collateral.
6. The position is recorded and subsequently, even a minor adverse price movement can trigger immediate liquidation due to the absence of any user-backed collateral.



### Impact

The protocol suffers a significant risk of under-collateralized leveraged positions, leading to rapid and widespread liquidations. In such a scenario, the protocol’s stability is jeopardized, and the risk of cascading failures increases, potentially resulting in substantial losses for the protocol and its participants.

### Mitigation

1. Enforce Minimum User Collateral:
Add a validation in openLeveragedPosition to require that at least one of lp.amount0In or lp.amount1In is greater than zero:

```solidity
require(lp.amount0In > 0 || lp.amount1In > 0, "User must supply collateral");
```

2. Implement Collateral Ratio Checks:
Verify that the ratio of user-supplied collateral to the total vault deposit meets a defined minimum threshold to prevent positions from being opened solely via flashloans.
3. Review Risk Parameters:
Reassess and adjust collateralization and liquidation thresholds to ensure positions opened with minimal or no collateral are either rejected or immediately flagged for liquidation.
