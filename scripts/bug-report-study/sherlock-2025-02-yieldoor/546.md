# Weak Swap Path Validation in Leverager.sol Allows Malicious Swaps Leading to Potential Fund Loss

### Summary

The Leverager.sol contract is vulnerable in its swap logic (openLeveragedPosition, withdraw, liquidatePosition) where it fails to fully validate the swapParams.path provided by users for IMainnetRouter.exactOutput and exactInput swaps. It only checks the first token in the path, allowing attackers to route swaps through malicious pools or contracts. This can lead to fund theft (via excessive approvals during swaps) or transaction failures (via manipulated rates).



### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/interfaces/IMainnetRouter.sol#L1C1-L63C2

In openLeveragedPosition, the contract performs exactOutput swaps using IMainnetRouter to convert borrowed denomination tokens (lp.denomination) into token0 or token1 to repay flashloans:
```solidity
if (a0 > lp.amount0In && up.token0 != lp.denomination) {
    swapParams = abi.decode(lp.swapParams1, (IMainnetRouter.ExactOutputParams));
    address tokenIn = _getTokenIn(swapParams.path);
    require(tokenIn == lp.denomination, "token should be denomination");
    IERC20(tokenIn).forceApprove(swapRouter, swapParams.amountInMaximum);
    swapParams.amountOut = a0 - lp.amount0In;
    IMainnetRouter(swapRouter).exactOutput(swapParams);
    IERC20(tokenIn).forceApprove(swapRouter, 0);
}
```
The _getTokenIn function validates that the first token in swapParams.path matches lp.denomination, but the rest of the path (intermediate tokens, pools, fees) is not checked. The IMainnetRouter.exactOutput function interprets path as a multi-hop route, executing swaps through each pool in sequence. Similar logic exists in withdraw and liquidatePosition for exactInput swaps, where only the input token is validated.
Since path is user-provided and defines the route (e.g., DAI -> FakeToken -> USDC), an attacker can include malicious pools in the path after the first token, bypassing the contract’s validation.



### Internal Pre-conditions

1. The vault must be enabled for leverage (vaultParams[lp.vault].leverageEnabled).

2. For openLeveragedPosition, the condition a0 > lp.amount0In && up.token0 != lp.denomination must trigger a swap.

3. The user must provide a swapParams.path where the first token matches the expected input (lp.denomination, token0, or token1), but intermediate tokens route through a malicious pool.

3. The swap must execute without reverting early (e.g., liquidity exists in the malicious pool).

### External Pre-conditions

1. The IMainnetRouter implementation must support multi-hop swaps via user-provided path without enforcing strict pool validation.

2. The attacker must deploy or control a malicious pool (e.g., DAI-FakeToken) that can execute harmful logic during the swap (e.g., drain approved funds, manipulate reserves).

### Attack Path

1. A user calls openLeveragedPosition with:
lp.amount0In = 0, lp.vault0In = 1000 USDC, lp.denomination = DAI, lp.maxBorrowAmount = 5000 DAI.

2. swapParams1 with amountInMaximum = 5000 DAI, path = DAI -> FakeToken -> USDC, where FakeToken is a token in a malicious pool controlled by the attacker.

3. The contract flashloans 1000 USDC (delta0 = 1000), deposits into the vault, and borrows 5000 DAI.

4. The contract approves the swapRouter to spend 5000 DAI and calls IMainnetRouter.exactOutput to get 1000 USDC:
First hop: DAI -> FakeToken in the malicious pool.

5. The malicious pool executes harmful logic (e.g., drains the approved 5000 DAI via router access, returns minimal FakeToken).

6. Second hop: FakeToken -> USDC in a legitimate pool, but yields less than 1000 USDC due to manipulation.

7. If the swap yields insufficient USDC, the subsequent pushFunds(up.token0, 1000) fails (assuming ILendingPool.pushFunds requires exact repayment). If funds are drained, the attacker profits 5000 DAI.

### Impact

1. Fund Loss: The attacker can steal up to swapParams.amountInMaximum (e.g., 5000 DAI) if the malicious pool exploits the approval during the swap.

2. Transaction Failure: Manipulated swap rates cause the transaction to fail, preventing position openings, withdrawals, or liquidations.

_No response_

### Mitigation

1. Validate Entire Path: Decode swapParams.path and ensure all intermediate tokens and pools are trusted (e.g., whitelist pools or tokens).

2. Use Trusted Paths: Remove user control over path and use a fixed, owner-configured path for swaps.
