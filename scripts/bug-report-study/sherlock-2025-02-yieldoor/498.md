# Users Can Create Risk-Free Leveraged Positions Leading to Potential Bad Debt for the Protocol

### Summary

In the Leverager.sol smart contract, a flaw lets users create leveraged positions, where they borrow money to amplify their investments without putting in any of their own funds. This happens because the contract doesn’t check if users contribute their own tokens before borrowing from the lending pool, allowing them to use only borrowed money to start a position. This could lead to losses for the protocol if these positions fail, as users have nothing to lose while the protocol might not recover the borrowed funds, leaving it stuck with debt.



### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103C2-L202C1

The root cause is that the openLeveragedPosition function in Leverager.sol, doesn’t require users to deposit their own tokens (token0 and token1) before pulling funds from the lending pool to create a position. Here’s how it works in the code:
```solidity
IERC20(up.token0).safeTransferFrom(msg.sender, address(this), lp.amount0In);
IERC20(up.token1).safeTransferFrom(msg.sender, address(this), lp.amount1In);
uint256 delta0 = lp.vault0In - lp.amount0In;
uint256 delta1 = lp.vault1In - lp.amount1In;
if (delta0 > 0) ILendingPool(lendingPool).pullFunds(up.token0, delta0);
```
lp.amount0In and lp.amount1In are what the user puts in—say, USDC or ETH—but there’s no rule saying these have to be more than zero. So, a user can set them to 0.

lp.vault0In and lp.vault1In are the total amounts needed to join the vault (like a trading pool). If the user puts in nothing (lp.amount0In = 0), then delta0 equals lp.vault0In, meaning the full amount comes from the lending pool via pullFunds.

This borrowed money gets deposited into the vault, giving the user shares that act as collateral, and then they borrow more money (called the denomination token) to leverage up—all without risking a penny of their own.



### Internal Pre-conditions

1. A user needs to call openLeveragedPosition and set lp.amount0In and lp.amount1In to exactly 0, meaning they contribute no tokens of their own.
2. The same user needs to set lp.vault0In and lp.vault1In to be at least 1 wei (a tiny amount) so the contract borrows something from the lending pool.
3. The lending pool must have enough available funds to let pullFunds borrow the full lp.vault0In and lp.vault1In amounts when the user’s input is zero.
4. The vault (a separate contract) needs to accept the borrowed funds and create shares worth at least 1 wei, forming the user’s position.

### External Pre-conditions

The lending pool’s pullFunds function must work without requiring users to put in their own money first—it just hands over the requested amount.

The vault must allow the deposit of these borrowed funds without failing, like if the vault’s trading pool has enough liquidity to handle it.


### Attack Path

A user calls openLeveragedPosition with no personal contribution—setting lp.amount0In = 0 and lp.amount1In = 0—and asks for lp.vault0In = 1000 USDC and lp.vault1In = 1000 ETH to be deposited into the vault, plus borrows 500 DAI as the denomination token.

The contract borrows 1000 USDC and 1000 ETH from the lending pool using pullFunds, since the user gave nothing, and the difference (delta0 and delta1) equals the full vault amounts.

These 1000 USDC and 1000 ETH are put into the vault, which gives the user shares—like a receipt showing they own part of the pool—without them spending their own money.

The contract then borrows 500 DAI from the lending pool, adding more debt to the user’s position, based on those vault shares.

At the end, it returns the 1000 USDC and 1000 ETH to the lending pool via pushFunds, leaving the user with vault shares and a 500 DAI debt—all funded by the protocol, not their wallet.

If the market drops and the vault shares aren’t worth 500 DAI anymore, liquidation happens, but if the shares can’t cover the debt, the protocol loses money while the user walks away unscathed.


### Impact

The protocol could lose up to the full borrowed amount—like 500 DAI per position in this example—if the market crashes and liquidation doesn’t recover enough. The user gains a free shot at profits if the position works out, or loses nothing if it fails, since they didn’t put in any money.

### Mitigation

1. Add a minimum collateral requirement to enforce user contribution:  
```solidity
require(lp.amount0In > 0 || lp.amount1In > 0, "Must provide collateral");
```
2. Limit the ratio of pulled funds to user-provided funds (e.g., delta0 <= lp.amount0In * 10) to ensure borrowed amounts don’t dominate the position.
