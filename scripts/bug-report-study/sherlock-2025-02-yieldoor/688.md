# Partial withdrawal logic bug (Potential underflow and stuck funds)

### Summary

During partial withdrawals, if a position’s borrowed asset is `token1`, the code mistakenly uses the wrong token’s amount (amountOut0) instead of amountOut1 to compute the repayable debt, causing incorrect state updates or transaction reverts.

### Root Cause

In `Leverager.sol` (lines ~279–287), the `Leverager.withdraw` function contains a logic error when the borrowed asset is the second token of the pair (`token1`). In the code that deducts the withdrawn collateral from the debt, it uses the wrong variable for the `token1` branch​. Specifically, it checks `if (borrowed == up.token1)` and then uses `amountOut0` in the ternary expression to calculate `repayFromWithdraw`​. This is almost certainly a copy-paste mistake and should use `amountOut1`. As written, if the position’s denomination (debt) is `token1`, the code will attempt to subtract liquidity using `amountOut0` (the other token’s amount). In scenarios where `amountOut1 < owedAmount`, this sets `repayFromWithdraw = amountOut0` (an unrelated value), leading to an incorrect reduction of `owedAmount` and `amountOut1`. In most cases this will cause an integer underflow on `owedAmount` or `amountOut1` (Solidity 0.8 will catch and revert the transaction).

### Internal Pre-conditions

1. A leveraged position is active where the borrowed asset is token1.
2. The user initiates a partial withdrawal.
3. The function logic for token1 is triggered.

### External Pre-conditions

1. The tokens follow standard ERC20 behavior without unexpected side effects.
2. The vault’s deposit/withdraw logic does not alter the expected token amounts.

### Attack Path

1. A user calls the partial withdrawal function on a position with token1 as the borrowed asset.
2. The contract computes the repayable amount using amountOut0 instead of amountOut1.
3. This miscalculation leads to underflow or incorrect debt reduction, causing the transaction to revert.

### Impact

Partial withdrawals can revert, trapping user funds. If a user’s leveraged position has its borrowed asset as `token1` (e.g., they borrowed the second token of the vault pair) and they attempt to withdraw a significant percentage of the position, the transaction will likely revert due to this bug. This means the user cannot partially deleverage or redeem their position in increments – they would be forced to either withdraw a smaller percentage or fully close the position. This is a denial-of-service for the normal user action of withdrawing some collateral. Inability to partially withdraw could also prevent users from rebalancing their own risk, potentially leading to liquidations that could have been avoided by withdrawing collateral. It does not directly allow an attacker to steal funds, but it severely impacts usability and fund access for affected positions (and could damage user trust or lead to unexpected liquidations).
