# Liquidation Will Fail Because `feeRecipient` is not Initialized in `Leverager.sol` but is Used for Fee Transfers

### Summary

The `feeRecipient` variable in `Leverager.sol` is never initialized (or set) to a valid non-zero address. During liquidation, if the liquidation conditions are met (i.e., the total USD value of collateral exceeds the borrowed value), the protocol attempts to calculate and transfer protocol fees to `feeRecipient`. Since `feeRecipient` remains the zero address, any attempt to transfer fees using SafeERC20’s `safeTransfer` call will revert the transaction. This failure in fee collection disrupts the liquidation process and could impede proper protocol operation.

### Root Cause

In the [liquidatePosition](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L320-L332) function, the fee logic is implemented as follows:

```solidity
if (totalValueUSD > borrowedValue) {
    uint256 protocolFeePct = 1e18 * liquidationFee * (totalValueUSD - borrowedValue) / (totalValueUSD * 10_000);
    uint256 pf0 = protocolFeePct * amount0 / 1e18;
    uint256 pf1 = protocolFeePct * amount1 / 1e18;

    // feeRecipient is used here for transferring fees.
    if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0);
    if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1);
    amount0 -= pf0;
    amount1 -= pf1;
}
```

However, the contract does not assign `feeRecipient` a nonzero address during deployment or via an initialization function. Thus, `feeRecipient` defaults to the zero address. When the fee logic is triggered, the call to `safeTransfer` fails because ERC20’s transfer function does not allow transfers to the zero address. This causes the liquidation transaction to revert.

### Internal Pre-conditions

1. A leveraged position exists that meets the liquidation condition (i.e., `totalValueUSD` > `borrowedValue`).
2. The liquidation function is invoked, triggering the fee calculation block.
3. The `feeRecipient` variable remains unset (i.e., equals `address(0)`).


### External Pre-conditions

1. The underlying tokens and external protocols (i.e the Uniswap V3 pool and price feed) operate normally.
2. No external oracle or market manipulation is necessary—the issue is solely due to the `feeRecipient` variable not being configured.

### Attack Path

1. A liquidation is triggered on a leveraged position where the collateral’s USD value exceeds the borrowed value (i.e., `totalValueUSD` > `borrowedValue`).
2. During liquidation, the fee calculation computes protocol fees based on the profit margin.
3. The contract attempts to transfer the calculated fees to `feeRecipient` `(address(0))`, and SafeERC20’s `safeTransfer` reverts the transaction because transfers to the zero address are not allowed.
4. The liquidation fails, disrupting normal operations.

### Impact

When liquidation conditions are met (`totalValueUSD` > `borrowedValue`), the protocol attempts to distribute fees to `feeRecipient`. Because `feeRecipient` is the zero address, the `safeTransfer` call fails, reverting the entire liquidation transaction. This not only prevents the liquidation from proceeding but also undermines the fee collection mechanism.

### PoC

Below is a test case demonstrating the issue (with comments for clarity):

```solidity
function test_liquidationFailsWhenFeeRecipientIsZero() public {
    // --- Precondition: Confirm feeRecipient is the zero address ---
    address fee = ILeverager(leverager).feeRecipient();
    assertEq(fee, address(0), "feeRecipient must be zero for this test");

    // --- Step 1. Open a Leveraged Position ---
    vm.startPrank(depositor);
    ILeverager.LeverageParams memory lp;
    // Provide realistic collateral inputs to ensure the position opens normally.
    lp.amount0In = 0.5e8;         // 0.5 WBTC provided by user
    lp.amount1In = 50_000e6;       // 50,000 USDC provided by user
    // Set vault deposit targets higher than collateral inputs to allow for profit margin.
    lp.vault0In = 1e8;           // 1 WBTC total deposit target
    lp.vault1In = 100_000e6;      // 100,000 USDC total deposit target
    lp.vault = vault;
    lp.maxBorrowAmount = 200e18;
    // Denomination token (e.g., WETH) for borrowing.
    lp.denomination = address(weth);

    // Prepare swap parameters (even if not used, required for function call).
    IMainnetRouter.ExactOutputParams memory ep;
    bytes memory _path = abi.encodePacked(address(wbtc), uint24(3000), address(weth));
    ep.path = _path;
    ep.deadline = block.timestamp;
    ep.amountInMaximum = type(uint256).max;
    ep.recipient = leverager;
    lp.swapParams1 = abi.encode(ep);
    
    _path = abi.encodePacked(address(usdc), uint24(3000), address(weth));
    ep.path = _path;
    lp.swapParams2 = abi.encode(ep);

    // Provide sufficient funds for the collateral portion.
    deal(address(wbtc), depositor, 0.5e8);
    deal(address(usdc), depositor, 50_000e6);
    wbtc.approve(leverager, type(uint256).max);
    usdc.approve(leverager, type(uint256).max);

    // Open the leveraged position.
    uint256 posId = ILeverager(leverager).openLeveragedPosition(lp);
    vm.stopPrank();

    // --- Step 2. Adjust the denomination token price so that totalValueUSD exceeds borrowedValue. ---
    MockOracle(wethOracle).setPrice(6000e18); // Set WETH price to $6,000
    assertTrue(ILeverager(leverager).isLiquidateable(posId));

    // --- Step 3. Attempt Liquidation ---
    vm.startPrank(liquidator);
    ILeverager.LiquidateParams memory liqParams;
    liqParams.id = posId;
    liqParams.hasToSwap = false;  // No swap actions needed for this test.
    
    // Approve the denomination token if necessary.
    weth.approve(leverager, type(uint256).max);
    
    // Expect the liquidation to revert because feeRecipient is zero.
    vm.expectRevert();
    ILeverager(leverager).liquidatePosition(liqParams);
    vm.stopPrank();
}
```

This test opens a leveraged position and then adjusts the oracle price so that liquidation conditions (`totalValueUSD` > `borrowedValue`) are met, triggering fee calculation. Since `feeRecipient` is the zero address, the `safeTransfer` call for fees fails, and the liquidation transaction reverts. This demonstrates the vulnerability.

### Mitigation

Set `feeRecipient` to a valid nonzero address during contract deployment or via a protected function.

```solidity
constructor(string memory name_, string memory symbol_, address _lendingPool, address _feeRecipient) Ownable(msg.sender) ERC721(name_, symbol_) {
      lendingPool = _lendingPool;
      feeRecipient = _feeRecipient;
}
```
