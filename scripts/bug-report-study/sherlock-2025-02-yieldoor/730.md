# Vault will reduce returns for users by omitting fees in deposit and withdraw

### Summary

The unverified collectFees call in deposit and withdraw will cause a loss of fee value for users as the Vault will miscalculate shares and withdrawals when collectFees fails, breaking the deposit-withdraw ratio invariant.

### Root Cause

In Vault.sol:52 and Vault.sol:84 the calls to IStrategy.collectFees() lack verification of success, causing balances() to exclude uncollected fees if it fails.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L52
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L84

### Internal Pre-conditions

User needs to call deposit to set totalSupply to be at least 100 (depositing 100 token0 and 100 token1).
Strategy needs to accrue fees to set mainPosition fees to be at least 10 token0 and 10 token1 via pool activity

### External Pre-conditions

No external preconditions required.

### Attack Path

User calls deposit, depositing 100 token0 and 100 token1, minting shares based on balances() assuming fees are collected.
Strategy accrues 10 token0 and 10 token1 in fees, increasing total value to 110/110.
User calls withdraw but collectFees fails (gas limit or silent revert in Strategy), leaving fees uncollected.
withdraw uses balances() without fees, calculating withdrawals as 100/100 instead of 110/110

### Impact

The users suffer an approximate loss of 10% of their entitled value per withdrawal (10/110 tokens per token type).

### PoC

// SPDX-License-Identifier: GPL-3.0-or-later
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import "../Vault.sol";
import "../Strategy.sol";

contract VaultFeeLagPoC is Test {
    Vault vault;
    Strategy strategy;
    address token0 = address(0x1);
    address token1 = address(0x2);
    address user = address(0x3);

    function setUp() public {
        vault = new Vault(token0, token1);
        strategy = new Strategy(address(0x4), address(vault), address(this), address(this)); // Mock pool, rebalancer, feeRecipient
        vault.setStrategy(address(strategy));
        vm.etch(token0, abi.encodePacked(type(IERC20).runtimeCode));
        vm.etch(token1, abi.encodePacked(type(IERC20).runtimeCode));
        deal(token0, user, 1000e18);
        deal(token1, user, 1000e18);
        vm.startPrank(user);
        IERC20(token0).approve(address(vault), type(uint256).max);
        IERC20(token1).approve(address(vault), type(uint256).max);
        vm.stopPrank();
    }

    function testFeeCollectionLag() public {
        vm.prank(user);
        (uint256 shares,,) = vault.deposit(100e18, 100e18, 0, 0);
        assertEq(shares > 0, true);

        // Step 2: Simulate fee accrual
            address(strategy),
            abi.encodeWithSelector(IStrategy.balances.selector),
            abi.encode(110e18, 110e18) // Fees accrued
        );
        vm.mockCall(
            address(strategy),
            abi.encodeWithSelector(IStrategy.collectFees.selector),
            abi.encode() // Fails silently
        );

        vm.prank(user);
        (uint256 amount0Out, uint256 amount1Out) = vault.withdraw(shares, 0, 0);

        assertEq(amount0Out, 100e18); // Expected 110e18
        assertEq(amount1Out, 100e18); // Expected 110e18
        // Ratio 1:1 deposited, expected 1:1 with fees, got 1:1 without
    }
}

### Mitigation

Verify collectFees success by caching balances() before and after the call in deposit and withdraw, reverting if no increase occurs (indicating fees weren’t collected)
