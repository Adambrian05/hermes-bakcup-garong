# Uninitialized Fee Recipient Causes Liquidation Failures

### Summary

The **uninitialized `feeRecipient` address** will cause **liquidation transactions to revert** for the protocol. This happens because liquidators attempting to collect fees will inadvertently trigger token transfers to the zero address (`address(0)`), which is forbidden in the ERC20 standard. The root cause is that the contract does not properly initialize or validate the `feeRecipient` state variable, leading to failed `safeTransfer` calls whenever protocol fees are applied.


### Root Cause
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L299C3-L381C1

In the `liquidatePosition` function, the protocol collects fees by transferring a portion of the liquidated funds to the `feeRecipient` address. This is done using the `safeTransfer` function from OpenZeppelin's ERC20 library:

```solidity
if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0);
if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1);
```

If the `feeRecipient` variable is not explicitly initialized, it defaults to `address(0)`. This leads to a problem when the contract attempts to execute `safeTransfer` because ERC20 tokens do not allow transfers to the zero address. Specifically, the `_transfer` function within the ERC20 implementation includes a check that will **revert** the transaction if `to` is `address(0)`, as shown below:

```solidity
// OpenZeppelin ERC20.sol
function _transfer(address from, address to, uint256 amount) internal {
    require(to != address(0), "ERC20: transfer to the zero address"); // Reverts here
    ...
}
```
The `feeRecipient` address should always be set before any liquidation can occur. However, because the contract does not enforce this requirement, it allows execution even when `feeRecipient` is unset. 

### Internal Pre-conditions

1. The `feeRecipient` state variable is uninitialized (defaults to `address(0)`).
2. A position becomes liquidatable (`isLiquidateable(liqParams.id)` returns `true`).
3. The liquidated position’s collateral value exceeds its debt (`totalValueUSD > borrowedValue`), triggering fee collection.

### External Pre-conditions

1. The protocol’s governance or admin fails to initialize `feeRecipient` during deployment.
2. A liquidator attempts to liquidate a profitable position (where fees apply).

### Attack Path

1. The protocol deploys the contract without explicitly setting `feeRecipient`.
2. A liquidator finds a profitable liquidation opportunity (`totalValueUSD > borrowedValue`).
3. They call `liquidatePosition` to liquidate the position and claim rewards.
4. The contract calculates protocol fees (`pf0` and `pf1`) and attempts to transfer them to `feeRecipient`.
5. Since `feeRecipient` is `address(0)`, `safeTransfer` fails, causing the entire transaction to **revert**.
6. The liquidation is blocked, allowing an undercollateralized position to remain active.

### Impact

- **Liquidators** cannot execute profitable liquidations, discouraging participation.
- **The protocol** accrues bad debt as undercollateralized positions remain unclosed, increasing insolvency risks.
- **Governance Failure**: The protocol depends on governance to initialize `feeRecipient`, but there is no safeguard enforcing this.

### Mitigation

1. **Initialize `feeRecipient` in the constructor**
   ```solidity
   constructor(address _feeRecipient) {
       require(_feeRecipient != address(0), "Invalid fee recipient");
       feeRecipient = _feeRecipient;
   }
   ```
2. **Validate `feeRecipient` before transfers**
   ```solidity
   if (pf0 > 0) {
       require(feeRecipient != address(0), "Fee recipient not set");
       IERC20(up.token0).safeTransfer(feeRecipient, pf0);
   }
   ```
3. **Restrict updates to `feeRecipient`**
   ```solidity
   function setFeeRecipient(address _feeRecipient) external onlyAdmin {
       require(_feeRecipient != address(0), "Invalid address");
       feeRecipient = _feeRecipient;
   }
   ```
