# Reversed Slippage Checks in Deposit Function Expose Users to Frontrunning Attacks

## Summary
The `deposit` function in the Vault contract [implements slippage protection incorrectly](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L64-L65). Instead of preventing users from depositing more tokens than intended, it requires that users deposit at least a minimum amount. This reversed logic fails to protect users from frontrunning attacks, which can result in users receiving fewer shares than expected for their deposited tokens.

## Vulnerability Details
Slippage protection in trading operations should protect users from market price movements between transaction submission and execution. In a deposit function, proper slippage protection should ensure users don't deposit more tokens than they're willing to for a given amount of shares.

The current implementation in the `deposit` function does the opposite:

```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... calculation of shares and deposit amounts ...
    
    require(depositAmount0 >= amount0Min, "slippage0");
    require(depositAmount1 >= amount1Min, "slippage1");
    
    // ... remaining function ...
}
```

The parameters `amount0Min` and `amount1Min` are being used incorrectly. The checks `depositAmount0 >= amount0Min` and `depositAmount1 >= amount1Min` ensure that users deposit *at least* the minimum amounts, when they should be ensuring users deposit *at most* the maximum amounts they're willing to spend.

## Proof of Concept
Consider this scenario:

1. User calculates they need to deposit 100 token0 and 200 token1 to receive X shares based on current pool state
2. User submits a transaction with:
```js
   deposit(100, 200, 100, 200)  // amount0, amount1, amount0Min, amount1Min
```
3. Before their transaction is mined, another large deposit changes the pool ratio
4. When the user's transaction executes:
   - The calculated `depositAmount0` is now 150 token0
   - The calculated `depositAmount1` is still 200 token1
   - The slippage checks pass because 150 >= 100 and 200 >= 200
   - User receives fewer shares than expected but still pays 150 token0 and 200 token1

The user has now spent 50 more token0 than intended for fewer shares than expected, but the transaction still succeeds because the slippage checks are reversed.

## Impact Details
This vulnerability causes users to spend more tokens than intended for fewer shares, effectively accrue a lost. This can happen due to frontrunning or normal operation where one trade occurs before the victims trade. In volatile market conditions, users could experience significant financial losses due to this incorrect slippage protection. The issue fundamentally undermines the purpose of having slippage protection in the contract.

## Tools Used
Manual

## Recommendations
Replace the current slippage checks with one of these two approaches:

1. Maximum input token amounts:
```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Max, uint256 amount1Max)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... calculation of shares and deposit amounts ...
    
    require(depositAmount0 <= amount0Max, "slippage0");
    require(depositAmount1 <= amount1Max, "slippage1");
    
    // ... remaining function ...
}
```

2. Minimum shares guarantee:
```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 minShares)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... calculation of shares and deposit amounts ...
    
    require(shares >= minShares, "insufficient shares");
    
    // ... remaining function ...
}
```

Either approach would properly protect users against unexpected price movements and frontrunning attacks.
