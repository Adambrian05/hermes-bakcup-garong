# Attacker will exploit stale oracle data to steal user funds

## Summary
The missing stale data check in the PriceFeed contract will cause significant financial losses for the protocol and its users as attackers will exploit outdated price data to create leveraged positions with incorrect values and prevent necessary liquidations.

## Root Cause
In [PriceFeed.sol#L123-L127](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/PriceFeed.sol#L123-L127) the critical check for stale oracle data is commented out:

```solidity
function _getChainlinkPrice(Data memory data) internal view returns (uint256) {
    (, int256 answer,, /* uint256 updatedAt */ ,) = AggregatorV3Interface(data.feed1).latestRoundData();
    require(answer > 0);
    // require(block.timestamp - updatedAt <= heartbeat);
    return uint256(answer);
}
```

The function retrieves the `updatedAt` timestamp from the Chainlink oracle but doesn't verify if the data is fresh, as evidenced by the commented-out code. This allows the protocol to use potentially stale or outdated price data for critical operations.

## Internal Pre-conditions
1. The `PriceFeed` contract must be used for price data across the protocol
2. The contract must use Chainlink price feeds as data sources
3. The stale data check must remain commented out or unimplemented

## External Pre-conditions
1. A Chainlink oracle for any supported asset must become stale (stop updating)
2. The actual market price of the asset must diverge significantly from the last reported oracle price

## Attack Path
1. Attacker monitors Chainlink price feeds for assets used in the Yieldoor protocol
2. Attacker identifies a situation where a price feed becomes stale (during network congestion or oracle downtime)
3. When a significant price movement occurs in the market but isn't reflected in the stale oracle:
   - If the actual price is lower than the stale price, attacker opens a leveraged position using the overvalued asset
   - If the actual price is higher than the stale price, attacker identifies positions that should be liquidated but won't be
4. For the first case, attacker borrows the maximum amount against collateral valued at outdated (higher) prices
5. For the second case, attacker identifies positions that would be healthy based on current market prices but appear liquidatable based on stale oracle data
6. Attacker liquidates these positions at a discount, profiting from the price discrepancy

## Impact
The protocol and its users suffer direct financial losses as positions are created with incorrect valuations or liquidated improperly. This can lead to:
1. Bad debt accumulation as underwater positions remain unliquidated
2. Excessive borrowing against overvalued collateral
3. Protocol insolvency if enough bad debt accumulates
4. Loss of user funds through improper liquidations

The severity of impact scales with the degree of price divergence and the amount of affected collateral.

## Mitigation
Implement proper stale data checking:

```solidity
function _getChainlinkPrice(Data memory data) internal view returns (uint256) {
    (uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = AggregatorV3Interface(data.feed1).latestRoundData();
    
    // Validate data freshness
    require(block.timestamp - updatedAt <= data.timeInterval, "Oracle data is stale");
    
    // Validate the answer is positive
    require(answer > 0, "Oracle returned negative or zero price");
    
    // Validate round completeness
    require(answeredInRound >= roundId, "Oracle round not complete");
    
    return uint256(answer);
}
```

Additionally, implement a multi-oracle solution and circuit breakers for suspicious price movements:
