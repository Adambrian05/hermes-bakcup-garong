# [M-03 | 0xKoiner]Swap Path Manipulation in Leverager Allows Malicious Users to Cause Fund Loss

### Summary

Insufficient validation of swap paths in the `openLeveragedPosition` function of `Leverager.sol` will cause reduced returns or fund loss for users as a malicious user will craft a `swapParams` path routing through low-liquidity pools to induce excessive slippage or drain borrowed funds.

refer: [`Leverager.sol::openLeveragedPosition`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103)

### Root Cause

In `Leverager.sol:165` and `Leverager.sol:178`, the `openLeveragedPosition` function decodes `swapParams1` and `swapParams2` and only checks that `tokenIn == lp.denomination` using `_getTokenIn`, which is a mistake as it fails to validate the full swap path, allowing malicious paths with intermediate low-liquidity pools or unexpected tokens.

- In `Leverager.sol:165`, the check `require(tokenIn == lp.denomination, "token should be denomination")` validates the input token but not the path `swapParams.path`, which could include low-liquidity pools.
- In `Leverager.sol:178`, the same limited check applies to `swapParams2`, leaving the path vulnerable to manipulation.

### Internal Pre-conditions

1. [Any user needs to call openLeveragedPosition] with a crafted `LeverageParams` where `swapParams1` or `swapParams2` includes a `path` routing through a low-liquidity Uniswap V3 pool between `lp.denomination` and the vault’s `token0` or `token1`.
2. [Owner needs to call initVault] to set up a vault with `leverageEnabled = true` and define `token0` (e.g., WBTC) and `token1` (e.g., USDC).
3. [LendingPool needs to have sufficient liquidity] of `lp.denomination` (e.g., WETH) to borrow `lp.maxBorrowAmount` for the swap.

### External Pre-conditions

1. A low-liquidity Uniswap V3 pool must exist on the Ethereum mainnet (or the test environment) between `lp.denomination` (e.g., WETH) and an intermediate token (e.g., a low-cap token), followed by a pool to `token0` (e.g., WBTC) or `token1` (e.g., USDC), allowing the malicious path to be executed via the `swapRouter` (Uniswap V3 Router).

### Attack Path

1. A malicious user constructs a `LeverageParams` struct with `lp.denomination = WETH`, `lp.maxBorrowAmount = 200e18`, and `lp.swapParams1.path` set to `WETH -> LOW_CAP_TOKEN -> WBTC`, where `LOW_CAP_TOKEN` is a low-liquidity token with a manipulated pool.
2. The user calls `openLeveragedPosition`, depositing minimal legitimate collateral (e.g., `lp.amount0In = 0.5e8 WBTC`, `lp.amount1In = 50_000e6 USDC`).
3. The function borrows 200 WETH from `LendingPool` (line 154) and approves the `swapRouter` for `swapParams.amountInMaximum` (line 168).
4. The `exactOutput` swap (line 171) routes 200 WETH through the low-liquidity `WETH -> LOW_CAP_TOKEN` pool, suffering extreme slippage (e.g., receiving only 0.01 LOW_CAP_TOKEN due to insufficient liquidity).
5. The swap continues to `LOW_CAP_TOKEN -> WBTC`, but the tiny amount of `LOW_CAP_TOKEN` yields negligible WBTC (e.g., 0.001e8), far less than the intended `a0 - lp.amount0In` (0.5e8).
6. The function completes, depositing reduced WBTC into the vault, leaving the user with a position worth less than the borrowed 200 WETH, effectively losing funds or passing the loss to the `LendingPool` upon liquidation.

### Impact

The users suffer an approximate loss of up to 200 WETH (or its USD equivalent, e.g., $500,000 at $2500/WETH) due to slippage and fund loss in the manipulated swap. The attacker gains by potentially sandwiching the swap externally to profit from the slippage, though direct in-contract gains are limited to under-collateralizing their position.

```solidity
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";
import {IMainnetRouter} from "../src/interfaces/IMainnetRouter.sol";

// Mock low-liquidity token for testing
contract MockLowCapToken is IERC20 {
    string public name = "LowCapToken";
    string public symbol = "LCT";
    uint8 public decimals = 18;
    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        emit Transfer(address(0), to, amount);
    }
    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }
    function transfer(address to, uint256 amount) external returns (bool) {
        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        emit Transfer(msg.sender, to, amount);
        return true;
    }
    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        allowance[from][msg.sender] -= amount;
        balanceOf[from] -= amount;
        balanceOf[to] += amount;
        emit Transfer(from, to, amount);
        return true;
    }
    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);
}

function testSwapPathManipulation() public {
    // Setup mock low-liquidity pool scenario
    MockLowCapToken lowCapToken = new MockLowCapToken();
    vm.startPrank(owner);
    lowCapToken.mint(address(this), 1e18); // Minimal liquidity for LCT

    // Assume a mock UniV3 pool: WETH -> LCT -> WBTC
    // In reality, this requires deploying mock pools, simplified here
    deal(address(weth), lender, 1000e18); // Ensure LendingPool has WETH
    vm.startPrank(lender);
    weth.approve(lendingPool, 1000e18);
    ILendingPool(lendingPool).deposit(address(weth), 1000e18, lender);

    // Malicious user crafts swap path
    vm.startPrank(depositor);
    deal(address(wbtc), depositor, 0.5e8);
    deal(address(usdc), depositor, 50_000e6);
    wbtc.approve(leverager, type(uint256).max);
    usdc.approve(leverager, type(uint256).max);

    ILeverager.LeverageParams memory lp;
    lp.amount0In = 0.5e8; // WBTC
    lp.amount1In = 50_000e6; // USDC
    lp.vault0In = 1e8; // Desired WBTC deposit
    lp.vault1In = 100_000e6; // Desired USDC deposit
    lp.vault = vault;
    lp.maxBorrowAmount = 200e18; // Borrow 200 WETH
    lp.denomination = address(weth);

    // Craft malicious path: WETH -> LCT -> WBTC
    bytes memory path = abi.encodePacked(
        address(weth), uint24(3000), address(lowCapToken), uint24(3000), address(wbtc)
    );
    IMainnetRouter.ExactOutputParams memory ep;
    ep.path = path;
    ep.deadline = block.timestamp;
    ep.amountInMaximum = 200e18;
    ep.recipient = leverager;
    ep.amountOut = 0.5e8; // Expect 0.5 WBTC
    lp.swapParams1 = abi.encode(ep);

    // Execute with mock swap behavior (simplified due to no real pool)
    vm.mockCall(
        uniRouter,
        abi.encodeWithSelector(IMainnetRouter.exactOutput.selector, ep),
        abi.encode(190e18) // Simulate high slippage: 190 WETH used, tiny WBTC out
    );
    lowCapToken.approve(uniRouter, type(uint256).max);
    deal(address(lowCapToken), leverager, 0.01e18); // Tiny LCT received
    deal(address(wbtc), leverager, 0.001e8); // Negligible WBTC received

    uint256 wethBefore = weth.balanceOf(lendingPool);
    ILeverager(leverager).openLeveragedPosition(lp);

    // Verify fund loss
    uint256 wethAfter = weth.balanceOf(lendingPool);
    assertApproxEqAbs(wethBefore - wethAfter, 200e18, 10e18); // ~200 WETH borrowed and lost
    assertLt(wbtc.balanceOf(strategy), 0.5e8); // Far less WBTC deposited than expected
}
```

### Mitigation

Validate the full swap path or restrict to trusted pools:
```solidity
// In Leverager.sol
function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {
    // Existing logic...
    if (a0 > lp.amount0In && up.token0 != lp.denomination) {
        IMainnetRouter.ExactOutputParams memory swapParams = abi.decode(lp.swapParams1, (IMainnetRouter.ExactOutputParams));
        address tokenIn = _getTokenIn(swapParams.path);
        require(tokenIn == lp.denomination, "token should be denomination");
        // Add full path validation
        (address tokenOut,,) = swapParams.path.decodeLastPool();
        require(tokenOut == up.token0, "path must end with token0");
        require(swapParams.path.countPools() == 1, "only single-hop swaps allowed"); // Restrict to direct swaps
        // Alternatively, check against trusted pools (requires storage of valid pool addresses)

        IERC20(tokenIn).forceApprove(swapRouter, swapParams.amountInMaximum);
        swapParams.amountOut = a0 - lp.amount0In;
        IMainnetRouter(swapRouter).exactOutput(swapParams);
        IERC20(tokenIn).forceApprove(swapRouter, 0);
    }
    // Similar validation for swapParams2...
}
```

### Validation Against Test Files

#### Analysis of Test Coverage
- **Relevant Test File**: `LeveragerTest.sol` is the primary file testing `openLeveragedPosition` and swap-related functionality.
- **Key Tests**:
  1. **`test_borrowToken1`**:
     - Opens a position borrowing 200,000 USDC, with `swapParams1.path = WBTC -> USDC`.
     - **Observation**: Uses a direct, high-liquidity path (WBTC -> USDC, fee 3000). No test of a manipulated path; succeeds as expected.
  2. **`test_borrowInThirdToken`**:
     - Borrows 200 WETH, with `swapParams1.path = WBTC -> WETH` and `swapParams2.path = USDC -> WETH`.
     - **Observation**: Direct paths to WETH, no intermediate low-liquidity tokens. Tests multi-swap but assumes well-funded pools.
  3. **`test_liquidationWithSwap`**:
     - Similar setup with swaps during liquidation, not opening, using direct paths.
     - **Observation**: Focuses on liquidation, not `openLeveragedPosition` swap vulnerabilities.
  4. **`test_cantOpenDueToPoolPriceOff`**:
     - Tests position opening with price manipulation, but swap paths are direct (WBTC -> WETH, USDC -> WETH).
     - **Observation**: Fails due to liquidation check, not swap path issues.
  5. **`test_LendingPool`** and Variants:
     - Opens positions with direct swaps (e.g., WBTC -> USDC), no malicious paths tested.
     - **Observation**: Assumes standard Uniswap V3 pools with ample liquidity.

- **Swap Path Handling in `Leverager.sol`**:
  - `_getTokenIn` extracts the first token from `path` (line 512), ensuring it’s `lp.denomination`.
  - No check on intermediate pools or `tokenOut`, allowing paths like `WETH -> LOW_CAP_TOKEN -> WBTC`.
  - `exactOutput` ensures the desired output (e.g., `a0 - lp.amount0In`), but slippage depends on pool liquidity, controlled by `path`.

- **Test Gaps**:
  - No test uses a multi-hop path with a low-liquidity intermediate pool.
  - No test verifies slippage or fund loss from a malicious `path`.
  - All swaps assume high-liquidity Uniswap V3 pools (fee 3000), masking the vulnerability.
