# New vaults vulnerable to rate manipulation through BURN address shares


## Summary
The vault's token rate preservation mechanism can be exploited during initial deposits. An attacker can establish a malicious token rate ratio by being the first depositor, then withdraw their funds while leaving the vault with non-zero total supply due to shares minted to the BURN address. This prevents subsequent depositors from using the vault as the token rate is permanently skewed.

## Root Cause
In [`Vault.sol#L48-L72`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48-L72), the `deposit()` function mints 1000 shares to a BURN address during the first deposit:

```solidity
    function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
        external
        returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
    {
        IStrategy(strategy).collectFees();

        (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();

->      (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);

        IERC20(token0).safeTransferFrom(msg.sender, strategy, depositAmount0);
        IERC20(token1).safeTransferFrom(msg.sender, strategy, depositAmount1); // after deposit, funds remain idle, until compound is called

        if (depositFee > 0) shares -= (shares * depositFee) / 10_000;

        require(shares > 0, "shares cant be 0");
        require(depositAmount0 >= amount0Min, "slippage0");
        require(depositAmount1 >= amount1Min, "slippage1");

->      if (totalSupply() == 0) _mint(BURN, 1000);
        _mint(msg.sender, shares);

        return (shares, depositAmount0, depositAmount1);
        // TODO - emit event
    }
```

The `_calcDeposit()` function enforces token ratios based on total supply:

```solidity
    function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal
        view
        returns (uint256 shares, uint256 amount0, uint256 amount1)
    {
        uint256 totalSupply = totalSupply();

        // If total supply > 0, vault can't be empty
->      assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired
            amount0 = depositAmount0;
            amount1 = depositAmount1;
->          shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1;
        } else if (bal1 == 0) {
            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;
        } else {
            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
->          amount0 = (cross - 1) / bal1 + 1;
->          amount1 = (cross - 1) / bal0 + 1;
->          shares = cross * totalSupply / bal0 / bal1;
        }
    }
```

Key vulnerabilities:
1. BURN address shares (1000) are never removed
2. Token ratio is enforced when `totalSupply > 0`
3. First deposit can set arbitrary token ratios
4. Subsequent deposits must match the initial ratio

## Internal pre-conditions
1. New vault has been deployed
2. No deposits have been made yet
3. BURN address is configured

## External pre-conditions
None - attack can be executed immediately after vault deployment

## Attack Path
1. Attacker identifies newly deployed vault
2. Makes first deposit with malicious token ratio:
   - Extreme ratio (e.g., 1:1000)
   - Very small amounts to minimize cost
3. Immediately withdraws all deposited funds
4. Result:
   - Vault's `totalSupply > 0` (1000 BURN shares)
   - Strategy holds negligible funds
   - Token ratio is permanently skewed
   - Future deposits must match malicious ratio

## Impact
1. Vault becomes unusable for legitimate depositors
2. Deployed vaults can be griefed at negligible cost
3. Protocol must redeploy new vaults
4. Loss of trust in protocol's vault deployment process

## Mitigation
Burn all share from BURN address when all positions aare withdrawed.
