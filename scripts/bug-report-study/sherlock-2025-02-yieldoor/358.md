# Economically Viable TWAP Manipulation Due To Short Time Window

## Summary
The TWAP period in `Strategy.sol` can be set too short (as low as 30 seconds), making price manipulation attacks economically viable despite existing safety checks.

Short TWAP period (1-10 minutes) will cause incorrect price calculations for protocol operations as an attacker will manipulate price during brief intervals

## Vulnerability Details
In Strategy.sol, the TWAP period can be set to a very short duration:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L547-L550
The minimum requirement of 30 seconds is insufficient because:
- Maintaining manipulated prices for such short periods is relatively cheap
- Even with price deviation checks (tickTwapDeviation and maxObservationDeviation), an attacker can 
  gradually influence the price
- The short TWAP window makes the protocol vulnerable to flash loan attacks
It is worth considering also from README.md:
> TWAP interval will be set individually for each pair. Assume values could range from 1-10 minutes. 

## Internal Pre-conditions:
1. TWAP period needs to be set between 1-10 minutes
2. Pool needs to have sufficient liquidity for price manipulation
3. `tickTwapDeviation` and `maxObservationDeviation` parameters need to be set to non-zero values

## External Pre-conditions:
1. Attacker needs to have enough capital to manipulate pool price
2. Pool price needs to be manipulatable within deviation limits

## Attack Path:
1. Attacker observes current TWAP period (e.g., 5 minutes)
2. Attacker gradually changes price to stay within `maxObservationDeviation` limits
3. Attacker maintains manipulated price for the short TWAP duration
4. Protocol calculates incorrect TWAP price that passes all safety checks
5. Steps 2-4 can be repeated each TWAP period

Let's break down why checks don't work for short TWAPs:

1- Basic checks in the contract:
```solidity
function _priceWithinRange() internal view returns (bool) {
    int24 _twapTick = twapTick();
    (, int24 currentTick,,,,,) = IUniswapV3Pool(pool).slot0();
    
    int24 minTick = _twapTick - tickTwapDeviation;
    int24 maxTick = _twapTick + tickTwapDeviation;
    if (currentTick < minTick || currentTick > maxTick) return false;
    return checkPoolActivity();
}
```

2. When the TWAP period is short (e.g., 30 seconds), the attacker can:
- Take a flash loan
- Manipulate the price within the allowed range (`tickTwapDeviation`)
- Maintain this price for only 30 seconds
- After that TWAP will already reflect the manipulated price

3. it is cost effective because:
- The cost of maintaining the manipulated price for 30 seconds is relatively low
- Checking `checkPoolActivity()` will not help if the price changes are gradual
- Once TWAP has reflected the manipulated price, it becomes the new "normal" value for checks

4. If TWAP's period were longer (e.g., 1 hour):
- The attacker would have had to maintain the manipulated price much longer
- The cost of the attack would increase significantly
- The risk of loss due to arbitrage would be higher

5. `checkPoolActivity()`:
- Only checks for sharp jumps
- Does not detect smooth manipulations
- Does not take into account the long-term trend


Thus, despite the presence of checks, the short TWAP period makes manipulation economically beneficial because the cost of short-term price changes within the allowed range is relatively low.


## Mitigation
Implement multiple TWAP periods of different durations (e.g., 1 hour, 4 hours, 24 hours) and compare them to detect manipulation. Increase the minimum TWAP period to at least 1 hour. Add additional checks comparing spot price with multiple TWAP windows.
