# Absence of Slippage Protection in LendingPool Redemptions Leads to Potential Value Loss for yToken Holders

## Summary
The LendingPool contract[ lacks a slippage protection mechanism for users redeeming their yTokens](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L83-L88), which exposes them to the risk of receiving fewer underlying tokens than expected when their transactions are processed. This can occur when other withdrawal or repay transactions are executed before theirs, changing the exchange rate between yTokens and underlying assets. Without the ability to specify a minimum acceptable amount of underlying tokens, users cannot protect themselves against this risk, potentially resulting in unexpected value loss during redemptions.

## Vulnerability Details
When users redeem their yTokens in the LendingPool, they receive underlying tokens based on the current exchange rate calculated by `yTokenToReserveExchangeRate()`. This exchange rate is determined by the ratio of total liquidity in the reserve to the total yToken supply.

The key issue is in the `_redeem` function:

```solidity
function _redeem(address underlying, uint256 yAssetAmount, address to) internal returns (uint256) {
    DataTypes.ReserveData storage reserve = getReserve(underlying);
    // update states
    reserve.updateState();

    // calculate underlying tokens using yTokens
    uint256 underlyingTokenAmount = reserve.yTokenToReserveExchangeRate() * yAssetAmount / PRECISION;

    require(underlyingTokenAmount <= reserve.availableLiquidity(), "not enough available liquidity");

    // burn yTokens and transfer the underlying tokens to receiver
    IyToken(reserve.yTokenAddress).burn(to, yAssetAmount, underlyingTokenAmount);

    // update the interest rate after the redeem
    reserve.underlyingBalance -= underlyingTokenAmount;
    reserve.updateInterestRates();

    return (underlyingTokenAmount);
}
```


The exchange rate calculation:

```solidity
function yTokenToReserveExchangeRate(DataTypes.ReserveData storage reserve) external view returns (uint256) {
    (uint256 totalLiquidity,) = totalLiquidityAndBorrows(reserve);
    uint256 totalYTokens = IERC20(reserve.yTokenAddress).totalSupply();

    if (totalYTokens == 0 || totalLiquidity == 0) {
        return PRECISION;
    }
    return totalLiquidity * (PRECISION) / (totalYTokens);
}
```


This exchange rate changes whenever:
1. New deposits increase both totalLiquidity and totalYTokens
2. Withdrawals decrease both totalLiquidity and totalYTokens
3. Borrows decrease totalLiquidity without affecting totalYTokens
4. Repayments increase totalLiquidity without affecting totalYTokens
5. Interest accrual increases totalLiquidity without affecting totalYTokens

If any of these actions occur between when a user submits their redemption transaction and when it's executed, the exchange rate will change, and the user will receive a different amount of underlying tokens than expected.

## Proof of Concept
Scenario 1: Front-running
1. Alice wants to redeem 1000 yUSDC from the LendingPool
2. Current exchange rate: 1.05 USDC per yUSDC
3. Alice expects to receive 1050 USDC
4. Bob sees Alice's transaction in the mempool
5. Bob front-runs with a large redemption of 10,000 yUSDC
6. Exchange rate changes to 1.03 USDC per yUSDC
7. Alice's transaction executes, but she only receives 1030 USDC
8. Alice loses 20 USDC of value with no way to prevent this

Scenario 2: Borrow front-running
1. Current pool: 100,000 USDC with 95,000 yUSDC (exchange rate: 1.05)
2. Alice submits a transaction to redeem 5,000 yUSDC, expecting 5,250 USDC
3. A borrower takes out a large loan of 20,000 USDC before Alice's transaction is processed
4. New exchange rate: 0.84 USDC per yUSDC (reduced liquidity)
5. Alice's transaction executes, but she only receives 4,200 USDC
6. Alice loses 1,050 USDC of value with no way to cancel the transaction

## Impact Details
This vulnerability exposes yToken holders to unexpected value loss when market conditions or transaction ordering causes the exchange rate to change unfavorably during redemptions. The impact is proportional to the size of preceding transactions relative to the pool size and can be significant during periods of high volatility or when large borrows/withdrawals occur. Users have no mechanism to protect themselves against this risk, which is a standard feature in most modern DeFi protocols.

## Recommendations
1. Add a `minUnderlyingAmount` parameter to the redeem function:
```solidity
function redeem(
    address underlyingAsset, 
    uint256 yAssetAmount, 
    address to,
    uint256 minUnderlyingAmount
) public notPaused nonReentrant returns (uint256 underlyingTokenAmount) {
    DataTypes.ReserveData storage reserve = getReserve(underlyingAsset);

    if (yAssetAmount == type(uint256).max) {
        yAssetAmount = IyToken(reserve.yTokenAddress).balanceOf(_msgSender());
    }
    // transfer yTokens to this contract
    IERC20(reserve.yTokenAddress).safeTransferFrom(msg.sender, address(this), yAssetAmount);

    // calculate underlying tokens using yTokens
    underlyingTokenAmount = _redeem(underlyingAsset, yAssetAmount, to);
    
    require(underlyingTokenAmount >= minUnderlyingAmount, "Slippage exceeded");
    return (underlyingTokenAmount);
}
```


2. Modify the internal `_redeem` function to maintain the same pattern:
```solidity
function _redeem(
    address underlying, 
    uint256 yAssetAmount, 
    address to
) internal returns (uint256 underlyingTokenAmount) {
    // ... existing code ...
    
    underlyingTokenAmount = reserve.yTokenToReserveExchangeRate() * yAssetAmount / PRECISION;
    
    // ... rest of existing code ...
}
```
