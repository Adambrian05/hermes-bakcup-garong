# Oracle Manipulation Risk in `Strategy::twapTick` Due to Single TWAP Window

### Summary

The [`Strategy::twapTick`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L345) function relies on a single Time-Weighted Average Price (TWAP) window from Uniswap V3 for price calculations. This single-window approach is vulnerable to price manipulation attacks, as recent price observations have an outsized influence on the TWAP. An attacker could manipulate the pool price before important operations like rebalancing or liquidation, potentially causing unfair liquidations or allowing underwater positions to remain open.


### Root Cause

The `twapTick` function retrieves the TWAP using a single time window:

```solidity
function twapTick() public view returns (int24) {
    uint32[] memory secondsAgos = new uint32[](2);
    secondsAgos[0] = twap;
    (int56[] memory tickCumulatives,) = IUniswapV3Pool(pool).observe(secondsAgos);
    int56 tickCumulativesDelta = tickCumulatives[1] - tickCumulatives[0];

    int24 tick = int24(tickCumulativesDelta / int32(twap));
    if (tickCumulativesDelta < 0 && (tickCumulativesDelta % int32(twap) != 0)) tick--;
    return tick;
}
```

The key issues are:

1. The function uses only a single TWAP window
2. With such a short window, an attacker can significantly influence the TWAP by executing large trades
3. There's no comparison with longer TWAP periods or other price sources to detect manipulation


### Internal Pre-conditions

1. The `twap` value must be set to a relatively short period
2. The underlying pool must have enough liquidity to be manipulated with reasonable capital
3. Functions like `isLiquidateable` in the Leverager contract must rely on this TWAP price


### External Pre-conditions

.

### Attack Path

1. An attacker identifies a position close to liquidation threshold
2. The attacker executes a series of trades to manipulate the pool price to either:
   - Force an unnecessary liquidation (by pushing the price in a direction that makes the position liquidatable)
   - Prevent a necessary liquidation (by pushing the price to keep an underwater position above the threshold)
3. The manipulated price affects the TWAP used by the `twapTick` function
4. This manipulated TWAP is then used by other protocol functions for critical decisions like liquidations
5. Once the attack is complete, the attacker can reverse their positions and potentially profit from the manipulation

### Impact

Price manipulation can lead to:
1. Unfair liquidations of otherwise healthy positions
2. Prevention of necessary liquidations for underwater positions
3. Manipulation of deposit/withdrawal amounts in the Vault
4. Incorrect rebalancing decisions in the Strategy

This can result in significant financial losses for users and potentially systemic risk to the protocol if large positions remain underwater without liquidation.

### Mitigation

1. Implement multiple TWAP windows and compare them:
   ```solidity
   function getValidatedTwapTick() public view returns (int24) {
       int24 shortTermTwap = getTwapTick(300);
       
       int24 longTermTwap = getTwapTick(3600);
       
       int24 maxDeviation = 100; 
       require(
           abs(shortTermTwap - longTermTwap) <= maxDeviation,
           "TWAP manipulation detected"
       );
       return longTermTwap;
   }
   ```

2. Implement a circuit breaker to detect unusual price activity:
   ```solidity
   uint256 lastObservedPrice;
   uint256 lastObservedTime;
   uint256 maxPriceChangeBpsPerHour = 1000; // 10% max change per hour
   
   function validateAndGetPrice() public returns (uint256) {
       uint256 currentPrice = twapPrice();
       uint256 timePassed = block.timestamp - lastObservedTime;
       
       if (lastObservedPrice > 0) {

           require(priceDiffBps <= maxAllowedChange, "Suspicious price movement detected");
       }
       
       lastObservedPrice = currentPrice;
       lastObservedTime = block.timestamp;

   }
   ```
