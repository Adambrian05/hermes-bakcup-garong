# Stranded Vesting Liquidity in Strategy Contract During Rebalances in Strategy::rebalance

## Description
The Strategy contract does not adjust vesting positions during the `rebalance()` function, leaving unvested liquidity in potentially inactive tick ranges. When the pool’s price moves significantly and a rebalance occurs, the `mainPosition` and `secondaryPosition` are updated to new tick ranges based on the current price, but the vesting position (`vestPosition`) retains its original ticks (`tickLower` and `tickUpper`) set at creation. This can result in unvested liquidity becoming stranded in out-of-range ticks, where it no longer accrues trading fees until the 
vesting period ends or the price returns to the original range.

## Vulnerability Detail
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L198
The issue arises in the `rebalance()` function:
```solidity
function rebalance() public onlyRebalancer {
    require(block.timestamp - lastRebalance >= rebalanceInterval, "too soon since last rebalance");
    _requirePriceWithinRange();
    collectFees();
    _removeLiquidity();
    (uint256 amount0, uint256 amount1) = idleBalances();
    (uint160 sqrtPriceX96, int24 tick,,,,,) = IUniswapV3Pool(pool).slot0();
    _setMainTicks(tick);
    (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);
    _setSecondaryPositionsTicks(tick);
    _addLiquidityToSecondaryPosition(sqrtPriceX96, amount0, amount1);
    lastRebalance = block.timestamp;
}
```
- `_removeLiquidity()` only affects mainPosition and `secondaryPosition`.

- `collectFees()` calls `_withdrawPartOfVestingPosition()`, which removes vested liquidity proportionally over time but leaves unvested liquidity (`remainingLiquidity`) at the original ticks.

**This was partially validated through testing attempts:**
- A vesting position was created at [67260, 67500] with a 1-day duration.

- A large swap (200M USDC → ~171.78 WBTC) shifted the tick to 162743, far above the range.

However, `rebalance()` reverted due to a "price out of range" check, preventing mainPosition adjustment, and subsequent fee collection showed ~91.3M USDC accrued, indicating vesting liquidity remained active despite being out-of-range.

The unexpected fee accrual suggests either fork-specific interference or a deeper issue in fee distribution, but the core finding—vesting liquidity not adjusting—holds based on code analysis.


## Impact
-  Unvested liquidity in inactive ticks stops generating trading fees, reducing protocol revenue (e.g., 9% protocol fee per `protocolFee = 900/10000`). For a 1-day vesting period with significant price volatility, this could 
represent substantial lost income, especially in high-volume pools.

## Proof of Concept
While a fully functional test couldn’t be completed due to rebalance reverts and fee anomalies, the following steps outline the issue:
- Deploy `Vault` and `Strategy with WBTC/USDC pool (0x99ac8cA7087fA4A2A1FB6357269965A2014ABc35).

- Add a vesting position (e.g., 2 WBTC, 100k USDC, 1-day duration) at ticks [67260, 67500] (tick 67391 in-range).

- Swap 200M USDC → WBTC, pushing tick to 162743 (out-of-range).

- Attempt rebalance()—it reverts, but if successful, `mainPosition` would adjust (e.g., to `[162600, 162840])`, leaving `vestPosition` at `[67260, 67500]`.

Over 12 hours, unvested liquidity should accrue no fees if stranded, but testing showed ~91.3M USDC

Code analysis confirms `vestPosition` isn’t updated in `rebalance()`, stranding it when `mainPosition` shifts.

```solidity
function test_strandedVestingLiquidity() public {
        
        vm.startPrank(owner);
        deal(address(wbtc), owner, 2e8);
        deal(address(usdc), owner, 100_000e6);
        wbtc.approve(vault, type(uint256).max);
        usdc.approve(vault, type(uint256).max);
    
        (uint160 sqrtPriceX96, int24 initialTick,,,,,) = IUniswapV3Pool(pool).slot0();
        int24 tickLower = IStrategy(strategy).getMainPosition().tickLower;
        int24 tickUpper = IStrategy(strategy).getMainPosition().tickUpper;
    
        uint128 vestingLiquidity = LiquidityAmounts.getLiquidityForAmounts(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(tickLower),
            TickMath.getSqrtRatioAtTick(tickUpper),
            2e8,
            100_000e6
        );
        (uint256 amount0, uint256 amount1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(tickLower),
            TickMath.getSqrtRatioAtTick(tickUpper),
            vestingLiquidity
        );
    
        IVault(vault).addVestingPosition(amount0, amount1, 1 days);
        IStrategy.VestingPosition memory vpBefore = IStrategy(strategy).getVestingPosition();
        assertGt(vpBefore.remainingLiquidity, 0, "Vesting position should have liquidity");
    
        // Step 2: Lets simulate price movement (upward)
        vm.startPrank(depositor);
        deal(address(usdc), depositor, 200_000_000e6); 
        swapUsdc(200_000_000e6); 
        skip(6 minutes);
        (, int24 newTick,,,,,) = IUniswapV3Pool(pool).slot0();
        emit log_named_int("New tick after swap", newTick);
        assertGt(newTick, tickUpper + 240, "Price didnt move far enough above initial range");
 
        vm.startPrank(rebalancer);
        try IStrategy(strategy).rebalance() {
            emit log("Rebalance succeeded");
        } catch Error(string memory reason) {
            emit log_named_string("Rebalance failed", reason);
   
            vm.assume(newTick > tickUpper + 240);
        }

        IStrategy.Position memory mainAfter = IStrategy(strategy).getMainPosition();
        IStrategy.VestingPosition memory vpAfter = IStrategy(strategy).getVestingPosition();
    
        emit log_named_int("Main tickLower after", mainAfter.tickLower);
        emit log_named_int("Vesting tickLower", vpAfter.tickLower);
        if (mainAfter.tickLower > vpAfter.tickLower) {
            assertGt(mainAfter.tickLower, vpAfter.tickLower, "Main position adjusted, vesting didnt");
            assertEq(vpAfter.tickLower, tickLower, "Vesting tickLower unchanged");
            assertEq(vpAfter.tickUpper, tickUpper, "Vesting tickUpper unchanged");
            assertGt(newTick, vpAfter.tickUpper, "Vesting position now out-of-range");
        }
   
        (uint256 bal0Before, uint256 bal1Before) = IStrategy(strategy).idleBalances();
        IStrategy(strategy).collectFees();
        (uint256 bal0AfterCollect, uint256 bal1AfterCollect) = IStrategy(strategy).idleBalances();
    
        uint256 fees0Collected = bal0AfterCollect - bal0Before;
        uint256 fees1Collected = bal1AfterCollect - bal1Before;
        emit log_named_uint("Initial fees collected (WBTC)", fees0Collected);
        emit log_named_uint("Initial fees collected (USDC)", fees1Collected);
    
        skip(12 hours);
        (bal0Before, bal1Before) = IStrategy(strategy).idleBalances();
        IStrategy(strategy).collectFees();
        (bal0AfterCollect, bal1AfterCollect) = IStrategy(strategy).idleBalances();
    
        uint256 newFees0Collected = bal0AfterCollect - bal0Before;
        uint256 newFees1Collected = bal1AfterCollect - bal1Before;
        assertApproxEqAbs(newFees0Collected, 0, 1, "Unvested liquidity not accruing fees (token0)");
        assertApproxEqAbs(newFees1Collected, 0, 1, "Unvested liquidity not accruing fees (token1)");
    
        assertGt(vpAfter.remainingLiquidity, 0, "Unvested liquidity should still exist");
    }

```
Add test to `BaseTest.sol`

## Recommendation

Update `rebalance()` to migrate unvested liquidity to the new mainPosition ticks.
