# Attacker Manipulates Share Distribution to steal funds from the protocol

### Summary

The balances() function’s reliance on the manipulable sqrtPriceX96 value leads to unfair share distribution, as an attacker can manipulate the price feed to skew balance calculations, resulting in losses for the protocol.
### Root Cause

The balances() function retrieves sqrtPriceX96 from IUniswapV3Pool(pool).slot0(). This price is vulnerable to manipulation via external trades or flash loans, causing incorrect balance calculations and enabling attackers to exploit the protocol, leading to fund losses.

### Internal Pre-conditions

None

### External Pre-conditions

The Uniswap V3 pool price (sqrtPriceX96) needs to shift within a single transaction or block, achievable via flash loans or large trades.

### Attack Path

**Normal scenario:**

1. User calls [deposit()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L48). 
2. Deposit invokes [balances()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L502) to calculate the strategy’s total balance across main and secondary positions.
3. Balances() call [getAmountsForLiquidity()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/libraries/LiquidityAmounts.sol#L119) to determine the balances of the main and secondary positions.
4. Deposit() uses [_calcDeposit()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L119) to compute the number of tokens to deposit based on these balances.

**Attack Scenario:**

1. Attacker executes a flash loan in the Uniswap V3 pool to manipulate sqrtPriceX96 to a value which favors token0 or token1.
2. Attacker calls deposit() on the strategy contract with a small amount0 and a large amount1.
3. Deposit makes a call to balances(). balances() calls getAmountsForLiquidity(). But, Instead of the execution of [this](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/libraries/LiquidityAmounts.sol#L131) condition, [this ](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/libraries/LiquidityAmounts.sol#L134) condition gets executed. 
4. Therefore amount0 is returned as 0. This can happen for both main and secondary position. 
5. This thus result in m0 and s0 = 0.
6. If for simplicity we assume there are no idlebalances, the return value of  amount0 in the balances() function would be 0.
7. This calculation later affects the _calcDeposit(). Here shares are calculated soleley based on amount1 as bal0 == 0 [here](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L134).
8. Now in this  0 amount1 tokens gets deposited to strategy.


**Attack example:**
Suppose exact totalBalance0 and totalBalance1 = 10,000 each.
 Attacker calls deposit with these args:

    function deposit(
        uint256 0, 
        uint256 1000, 
        uint256 amount0Min,
        uint256 amount1Min
    )

Manipulated balances() function returns: totalBalance0=0, totalBalance1 = 10,000
Now in _calcDeposit(). As bal0 =0, this condition gets triggered:

        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = (amount1 * totalSupply) / bal1;

assuming totalSupply of shares = bal1, the return values of _calcDeposit would be:
shares=1000, amount0 = 0, amount1 = 1000
Assming no fees attacker has got 1000 shares for 1000 amount of token1.

Now attacker calls withdraw():
Here amount for the attacker gets calculated based on the amount of shares it has: 

        withdrawAmount0 = (totalBalance0 * shares) / totalSupply; 
        withdrawAmount1 = (totalBalance1 * shares) / totalSupply;

withdrawAmount0 = 10,000* 1000/11,000 = 909, withdrawAmount1 = 11,000*1000/11,000 = 1000

Now user has 909 tokens0 and 1000 token1. 
Therefore the user was able to make a profit of 909 tokens0 by manipulating sqrtPriceX96.

### Impact

This results in two things:

1. Unbalanced Strategy Deposits: The attacker bypasses the intended balanced deposit mechanism, leaving the strategy with excess tokens of one type (e.g., token1). These excess tokens remain idle or, if deposited, incur losses for the protocol due to unfavorable pricing.
2. Profit for the Attacker: The attacker gains shares at a reduced cost and can later withdraw a disproportionate amount of both tokens, profiting from the manipulation.
