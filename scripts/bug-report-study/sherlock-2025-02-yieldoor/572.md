# Protocol Fee Loss Due to Frequent collectFees Calls

### Summary

The collectFees function allows anyone to call it, leading to frequent executions. Since it collects fees from the main, secondary, and vesting positions and then calculates protocol fees as a fraction of the fee increase, repeated calls result in minimal differences between preBal0 and afterBal0, causing protocol fees to round down to zero. This leads to the owner receiving no protocol fees.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L159-#L181

### Root Cause

Since collectFees() can be called by anyone and it doesn't provide any call Interval. If its frequently called It will lead to very small accumulated balance from collecting the fees which will result in protocolfees0 & protocolfees1  to round down to 0

```solidity
function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0) collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(secondaryPosition.tickLower, secondaryPosition.tickUpper);
        }
        if (ongoingVestingPosition) {
            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
        }
       

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = (afterBal0 - preBal0) * protocolFee / 10_000; 
        uint256 protocolFees1 = (afterBal1 - preBal1) * protocolFee / 10_000;

        if (protocolFees0 > 0) IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0) IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
            _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }
```

### Attack Path

User repeatedly calls collectFees

### Impact

Protocol Fee Loss: Repeated calls to collectFees result in small incremental balance changes, causing (afterBal0 - preBal0) * protocolFee / 10_000 to round down to zero, preventing protocol fee accumulation.
Economic Exploitability: Attackers can repeatedly call collectFees at short intervals, ensuring that protocol fees never accumulate enough to be claimed.
