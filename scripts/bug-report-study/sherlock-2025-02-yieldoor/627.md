# Ineffective Fee Collection Mechanism



## Description 

The Vault contract implements a deposit fee mechanism that reduces the number of shares minted to users during deposit operations without allocating these reduced shares to any beneficiary. This results in fees being "charged" but not collected, leading to value being lost rather than captured by the protocol or its stakeholders.

## Root cause 
The root cause of this issue is in the deposit function where the contract:
1. Calculates shares based on deposit amounts and existing balances
2. Applies a fee by reducing the user's shares by a percentage (depositFee)
3. Fails to mint these reduced shares to a designated fee recipient

As a result, the protocol is not actually collecting revenue from deposit fees, despite users paying them in the form of reduced representation of their deposits. This effectively creates a value leak where users receive fewer shares than they should based on their deposits, but no entity benefits from this reduction.

## Impact 
- Loss of protocol revenue that could be used for treasury, development, or token holder rewards
- Potential economic imbalance where early users are effectively subsidizing later users
- No actual incentive alignment since reduced shares are not being allocated to stakeholders
- Poor economic design that may lead to community distrust when discovered

## Proof of Concept

The issue exists in the deposit function of the Vault contract. Here is the relevant code section:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L61-L71

```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... other code ...
    
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    // ... token transfers ...
    
    if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
    
    // ... validation checks ...
    
    if (totalSupply() == 0) _mint(BURN, 1000);
    _mint(msg.sender, shares);
    
    return (shares, depositAmount0, depositAmount1);
}
```

To demonstrate the issue, let's walk through a scenario:

1. Assume depositFee = 10 (0.1%)
2. User deposits tokens worth 10,000 shares
3. After fee calculation: shares = 10,000 - (10,000 * 10 / 10,000) = 9,990
4. The contract mints 9,990 shares to the user
5. The 10 shares that were deducted are never minted to anyone



## Recommended mitigation steps

To properly implement fee collection, the contract should be modified to allocate the deducted shares to a designated fee recipient. Here are two recommended approaches:

### Option 1: Mint fee shares to a designated recipient

```solidity
// Add fee recipient address
address public feeRecipient;

// Add function to set fee recipient
function setFeeRecipient(address _feeRecipient) external onlyOwner {
    require(_feeRecipient != address(0), "invalid fee recipient");
    feeRecipient = _feeRecipient;
}

// Modify deposit function
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    // ... existing code ...
    
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    // ... existing code ...
    
    uint256 feeShares = 0;
    if (depositFee > 0) {
        feeShares = (shares * depositFee) / 10_000;
        shares -= feeShares;
    }
    
    // ... existing validation checks ...
    
    if (totalSupply() == 0) _mint(BURN, 1000);
    _mint(msg.sender, shares);
    
    // Mint fee shares to recipient if any
    if (feeShares > 0 && feeRecipient != address(0)) {
        _mint(feeRecipient, feeShares);
    }
    
    return (shares, depositAmount0, depositAmount1);
}
```

### Option 2: Take fee from tokens before calculating shares

An alternative approach would be to take the fee from the deposited tokens before calculating shares, which might be more transparent to users:

```solidity
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    IStrategy(strategy).collectFees();

    (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();
    
    // Calculate initial deposit amounts
    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    
    // Calculate fee amounts
    uint256 fee0 = 0;
    uint256 fee1 = 0;
    if (depositFee > 0) {
        fee0 = (depositAmount0 * depositFee) / 10_000;
        fee1 = (depositAmount1 * depositFee) / 10_000;
    }
    
    // Transfer main amounts to strategy
    IERC20(token0).safeTransferFrom(msg.sender, strategy, depositAmount0 - fee0);
    IERC20(token1).safeTransferFrom(msg.sender, strategy, depositAmount1 - fee1);
    
    // Transfer fees to fee recipient if any
    if (fee0 > 0) IERC20(token0).safeTransferFrom(msg.sender, feeRecipient, fee0);
    if (fee1 > 0) IERC20(token1).safeTransferFrom(msg.sender, feeRecipient, fee1);
    
    // Recalculate shares based on actual deposits (minus fees)
    (shares, , ) = _calcDeposit(totalBalance0, totalBalance1, depositAmount0 - fee0, depositAmount1 - fee1);
    
    // ... rest of existing code ...
}
```

Either approach properly captures the value of the fees for the protocol rather than simply reducing shares without allocating them to any beneficiary. The choice between options depends on the protocol's economics and governance preferences.
