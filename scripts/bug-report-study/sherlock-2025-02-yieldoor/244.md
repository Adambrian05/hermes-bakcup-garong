# Vault contract: Malicious user can potentially DOS Vault contract deposits or steal funds.

### Summary

- The Vault contract allows an initial deposit with zero values when the total supply is zero. This permits a malicious user to deposit tokens in only one currency while setting the other currency's value to zero. For example, depositing 1001 USDT and 0 WBTC blocking subsequent deposits.
-  There is a second alternative option open to the protocol that could lead to loss of funds by the protocol.

The protocol developer indicated that this issue should not arise since they plan to be the first depositor. However, without specific deployment procedures or scripts that I could check, there is therefore at least a theoretical risk as the code and documentation stands, that a malicious user could either be the first to deposit or front-run the initial deposit with a malicious transaction.

The reason I believe that it could be a medium is that should such a deposit occur, either the protocol would need to consider deploying a different vault contract(DOS) or, should they wish to deposit the missing currency type to the value of 50% of the malicious deposit, the malicious user could then withdraw and thus steal the donated funds. This seems the be in line with the Sherlock guidelines for a medium as set out in the Sherlock documentation.

### Root Cause

In [Vault::deposit](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48-L72) interacting with [Vault::_calcDeposit](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L119C14-L151) 

- The Vault contract allows an initial deposit with zero values as long as the total sum of the two input values is greater than or equal to the initial loss of 1000  shares, when the total supply is zero. There is a calculation in the _calcDeposit function, however when the totalSupply is zero, it merely accepts the values sent in and there is no `cross` check, as is in place for subsequent deposits. This permits a malicious actor to deposit tokens in only one currency while setting the other currency's value to zero. For example, depositing 1001 USDT and 0 WBTC would be accepted but would result in the `_calcDeposit` function reverting with the error `cross` when checking for the cross value of the missing currency, which then always reverts on the `cross > 0' check, for subsequent deposits.

No pre-conditions needed.

### External Pre-conditions

No pre-conditions needed.

### Attack Path

1. The Vault is deployed. The constructor sets all values so there is no need for any fursther interaction by the protocol.
2. The Malicious actor either intiates the frist depsot or front-runs the first deposit with the one of the deposit amounts set to zero.

### Impact

- This vulnerability could lead to a denial of service (DoS) for other users, forcing the protocol to abandon the deployed vault.
- Alternatively, if the protocol wishes to retain the vault address, they would need to donate tokens equivalent to at least 50% of the malicious user's original deposit in the missing currency. This scenario allows the malicious user to potentially withdraw the donated tokens along with their initial deposit, minus an initial loss of 1000 shares. The actor could also monitor for strategy updates to the contract and front-run those to ensure they got their initial funds back.

### Mitigation

To address the issue, the simplest approach, likely already implemented, is to deploy and deposit within a single transaction.

Alternatively, you may enhance the `_calcDeposit` function in the Vault contract by incorporating the following logic:

```diff
         uint256 totalSupply = totalSupply();
 
+        bool validDep0 = depositAmount0 >= depositAmount1/2 && depositAmount1 > 0;
+        bool validDep1 = depositAmount1 >= depositAmount0/2 && depositAmount0 > 0;
+        bool validDeposit = validDep0 || validDep1;
+
+        require(validDeposit,"Invalid deposit ratios");
+
         // If total supply > 0, vault can't be empty
         assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

```

This code ensures that the deposit ratios are valid by checking that each deposit amount is at least half of the other and that both amounts are greater than zero.
