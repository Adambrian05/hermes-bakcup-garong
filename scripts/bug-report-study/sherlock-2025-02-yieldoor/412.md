# Zero Position Vulnerability

### Summary

**Missing user collateral validation will cause a significant financial loss for the lending protocol as malicious users will open zero-collateral leveraged positions, borrow maximum funds, withdraw and abandon underwater positions.**

### Root Cause

### Root Cause  

The vulnerability arises due to **the lack of a minimum personal collateral requirement** in the `openLeveragedPosition` function.  

In **`Leverager.sol`**, the function allows users to initiate a leveraged position without verifying that they contribute any personal funds:  

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L119-L122

Here, `amount0In` and `amount1In` represent the user's contribution, but there is no `require` statement enforcing a nonzero value. An attacker can set `amount0In = 0` and `amount1In = 0`, relying entirely on flashloaned funds to deposit into the vault.  

Since the contract later uses the total deposited amount (which includes flashloaned funds) to determine the collateral value:  

```solidity
up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price);
```
  
The attacker **artificially inflates their collateral** without putting any personal stake at risk. This enables borrowing against non-existent personal funds, leading to potential protocol insolvency.

### Internal Pre-conditions

### Internal Pre-conditions  

1. **User needs to call** `openLeveragedPosition()` **to set** `amount0In` and `amount1In` **to be exactly** `0`.  
2. **User needs to set** `vault0In` and `vault1In` **to be greater than** `0` to trigger flashloan funding.  
3. **LendingPool needs to execute** `pullFunds()` **to move** `delta0` and `delta1` **from the pool to the vault** without verifying the user's personal contribution.  
4. **Vault needs to accept** deposits **funded entirely by flashloaned assets**, inflating the attacker's collateral.  
5. **Collateral calculation must use** `up.initCollateralUsd` **without differentiating between** user-provided and borrowed funds.  
6. **Leverage check must pass** despite the attacker not contributing any personal capital.

### External Pre-conditions

### External Pre-conditions  

1. **Flashloan provider needs to have sufficient liquidity** to fund the attacker's position.  
2. **Market conditions must allow** `up.initCollateralUsd` **to appear valid**, meaning the price oracle used for token valuation must not significantly change in a way that immediately triggers liquidation.  
3. **Gas fees must be low enough** for the attacker to execute the sequence of transactions cost-effectively.  
4. **No external monitoring system (e.g., governance or risk management bot)** should detect and prevent positions with zero personal collateral.  
5. **The lending protocol must not have active safeguards** against flashloan-based collateral inflation.

### Attack Path

### Attack Path  

1. **Attacker calls** `openLeveragedPosition()` **with** `amount0In = 0` and `amount1In = 0`, while setting `vault0In > 0` and `vault1In > 0`.  
2. **The contract calculates** `delta0 = vault0In - amount0In` and `delta1 = vault1In - amount1In`, which results in nonzero values.  
3. **The contract calls** `ILendingPool(lendingPool).pullFunds(up.token0, delta0)` and `ILendingPool(lendingPool).pullFunds(up.token1, delta1)`, pulling flashloaned funds.  
4. **The vault accepts** the flashloaned funds as collateral, **without checking** whether the attacker has contributed any of their own funds.  
5. **The contract sets** `up.initCollateralUsd` using `_calculateTokenValues()`, incorrectly treating the flashloaned funds as legitimate collateral.  
6. **Leverage checks pass**, since the contract only verifies total collateral, not the source of funds.  
7. **Attacker calls** `ILendingPool(lendingPool).borrow()` **to take out a loan**, despite not contributing any personal capital.  
8. **Attacker withdraws** the borrowed funds, leaving behind a position that is either highly leveraged or already underwater.  
9. **If the position becomes unprofitable**, the attacker **abandons the position**, leaving the protocol with bad debt.

### Impact

### Impact  

- **The protocol suffers an approximate loss of** the total borrowed amount, as the attacker can take out a loan without personal collateral and abandon the position.  
- **Lenders face significant risk**, as bad debt accumulates if multiple attackers exploit this issue.  
- **Governance is burdened** with handling liquidations of these zero-collateral positions, potentially at a loss.  
- **The attacker gains the full loaned amount** while risking only gas fees, making this a near-zero-cost attack.

### Mitigation

### Mitigation  

1. **Enforce a minimum personal contribution**:  
   ```solidity
   require(lp.amount0In > 0 || lp.amount1In > 0, "Must contribute personal collateral");
   ```  
   This ensures that users cannot open a leveraged position without providing some of their own funds.  

2. **Require a minimum contribution percentage**:  
   ```solidity
   require(
       (lp.amount0In * price / PRECISION + lp.amount1In) * 100 >= 
       (lp.vault0In * price / PRECISION + lp.vault1In) * MINIMUM_USER_CONTRIBUTION_PCT,
       "Must contribute minimum percentage"
   );
   ```  
   This prevents attackers from opening positions primarily funded by flashloans.  

3. **Adjust leverage calculations** to distinguish between user-provided funds and borrowed funds:  
   ```solidity
   uint256 userContributionValue = _calculateTokenValues(up.token0, up.token1, lp.amount0In, lp.amount1In, price);
   require(userContributionValue * MAX_LEVERAGE >= up.initBorrowedUsd, "Excessive borrowing vs contribution");
   ```  

4. **Implement withdrawal checks**: Ensure that withdrawals do not push the position into an immediate liquidatable state.  

5. **Monitor and limit flashloan usage**:  
   - Introduce rate limits or additional checks when flashloan-based collateral deposits occur.  
   - Require time-based confirmations before allowing borrowed funds to be withdrawn.  

6. **Improve risk monitoring**: Deploy automated risk monitoring to detect and flag suspicious zero-contribution leverage openings.
