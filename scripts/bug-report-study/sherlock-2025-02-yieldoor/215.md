# Malicious users will trap liquidator funds by blacklisting vault addresses

### Summary

**The lack of blacklist checking in the liquidation process will cause a complete loss of funds for liquidators as attackers will create positions with tokens that have blacklisting capabilities and then trigger blacklisting of the protocol's address, trapping liquidator funds during liquidation attempts. This prevents necessary liquidations, leading to bad debt accumulation and potential protocol insolvency.**


### Root Cause

In [Leverager.sol:299-384](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L299-L384) the liquidation process pulls funds from the liquidator before checking if transfers to the protocol will succeed. If the token used in the position has blacklisting capabilities (like USDC or USDT) and the protocol's address becomes blacklisted, the transfer to the vault will fail, but the liquidator's funds will already be in the protocol with no mechanism to recover them.


### Internal Pre-conditions

1. An attacker needs to open a leveraged position using a token with blacklisting capabilities
2. The position needs to become liquidatable (underwater)
3. The protocol's address (Leverager contract) needs to be blacklisted by the token issuer

### External Pre-conditions

1. The token used in the position needs to have blacklisting functionality (e.g., USDC, USDT)
2. The token issuer needs to blacklist the protocol's address (either through the attacker's request or coincidentally)

### Attack Path

1. **Attacker** opens a leveraged position using a token with blacklisting capabilities (e.g., USDC)
2. The position becomes underwater and eligible for liquidation
3. **Attacker** contacts the token issuer and reports the protocol address for suspicious activity, leading to blacklisting
   (alternatively, the attacker could be an entity with blacklisting authority, or the protocol could be blacklisted for unrelated reasons)
4. **Liquidator** calls `Leverager::liquidatePosition` to liquidate the underwater position
5. The protocol pulls funds from the liquidator via `safeTransferFrom`
6. When the protocol attempts to use these funds (transfer or repay), the transaction reverts due to the blacklisting
7. The liquidator's funds remain stuck in the protocol with no mechanism to recover them
8. The underwater position remains unliquidated, creating bad debt for the protocol

### Impact

The liquidator suffers a complete loss of the funds transferred to the protocol (equal to the debt amount of the position being liquidated). The protocol accumulates bad debt as underwater positions cannot be liquidated, potentially leading to insolvency if the value of these positions continues to decline. This vulnerability creates a systemic risk to the protocol's solvency and could lead to a cascade of failures if multiple positions become unliquidatable. Additionally, once this vulnerability becomes known, liquidators will be reluctant to participate, further destabilizing the protocol.


### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import {MockBlacklistToken} from "./mocks/MockBlacklistToken.sol";
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";

contract BlacklistTest is Test {
    MockBlacklistToken usdc;
    address user = address(0x1);
    address liquidator = address(0x3);
    address protocol = address(this); // Simulating the protocol address
    
    function setUp() public {
        // Deploy mock token with blacklist functionality
        usdc = new MockBlacklistToken("USD Coin", "USDC", 6);
        
        // Mint tokens to users
        usdc.mint(user, 1000e6);
        usdc.mint(liquidator, 1000e6);
    }
    
    function testLiquidationBlacklistVulnerability() public {
        // Initial state: liquidator has approved USDC to be spent by the protocol
        vm.startPrank(liquidator);
        usdc.approve(protocol, 1000e6);
        vm.stopPrank();
        
        // Record initial balances
        uint256 initialLiquidatorBalance = usdc.balanceOf(liquidator);
        uint256 initialProtocolBalance = usdc.balanceOf(protocol);
        
        console.log("Initial liquidator balance:", initialLiquidatorBalance);
        console.log("Initial protocol balance:", initialProtocolBalance);
        
        // Simulate liquidation process - Step 1: Protocol pulls funds from liquidator
        usdc.transferFrom(liquidator, protocol, 500e6);
        
        // Step 2: Protocol gets blacklisted (by token issuer)
        usdc.blacklist(protocol);
        assertTrue(usdc.blacklisted(protocol), "Protocol should be blacklisted");
        
        // Step 3: Protocol tries to use the funds (transfer, repay, etc.)
        vm.expectRevert("Blacklisted address");
        usdc.transfer(address(0x4), 500e6); // This will fail
        
        // The liquidator's funds are now stuck in the protocol
        uint256 afterFailLiquidatorBalance = usdc.balanceOf(liquidator);
        uint256 afterFailProtocolBalance = usdc.balanceOf(protocol);
        
        console.log("After failed liquidation:");
        console.log("Liquidator balance:", afterFailLiquidatorBalance);
        console.log("Protocol balance:", afterFailProtocolBalance);
        
        // Check that liquidator lost funds
        assertEq(afterFailLiquidatorBalance, initialLiquidatorBalance - 500e6, "Liquidator should have lost funds");
        
        // Check that protocol gained funds that are now stuck
        assertEq(afterFailProtocolBalance, initialProtocolBalance + 500e6, "Protocol should have gained funds");
        
        console.log("Liquidation failed due to blacklisted protocol");
        console.log("Liquidator funds stuck in protocol:", afterFailProtocolBalance - initialProtocolBalance);
        
        // The position remains unliquidated, creating bad debt for the protocol
        console.log("Position remains unliquidated, creating bad debt for the protocol");
    }
}
```

### Mitigation

1. **Pre-Liquidation Checks**: Add checks before pulling funds from the liquidator to verify that the protocol is not blacklisted by attempting a zero-value transfer.

2. **Pull-Based Liquidation Pattern**: Redesign the liquidation process to use a two-step approach where liquidation is first prepared and then executed, with funds only being pulled at the execution stage after all checks have passed.

3. **Try-Catch with Refund**: Implement a try-catch mechanism that refunds the liquidator if any part of the liquidation process fails.

4. **Emergency Circuit Breaker**: Implement a mechanism to handle blacklisted positions separately, potentially through governance intervention, to prevent bad debt accumulation.
