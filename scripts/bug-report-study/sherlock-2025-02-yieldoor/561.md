# _calcDeposit Disincentivizes Balanced Deposits in Vault Calculation

## Description
` _calcDeposit` function calculates the initial shares for a deposit when the total supply is zero using the maximum of the two token amounts (`max(depositAmount0, depositAmount1) - 1000`). This approach biases the share allocation towards the larger token amount (in wei ), resulting in fewer shares issued for balanced deposits (e.g., equal USD value of `token0` and `token1`) compared to unbalanced ones. This creates an unexpected and unfair outcome for users depositing tokens in proportions aligned with the pool’s price, disincentivizing balanced contributions due to the lack of price normalization.

## Vulnerability Detail:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L119
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48

- When `totalSupply == 0` (initial deposit), `shares = max(depositAmount0, depositAmount1) - 1000` uses raw token amounts (wei) without normalizing for price or pool ratio.

- The subtraction of 1000 accounts for an initial burn to the `BURN` address (`address(1337)`).

- For subsequent deposits, shares are proportional to existing liquidity, but the initial case sets a skewed baseline.

For example, in a WBTC/USDC pool (WBTC 8 decimals, USDC 6 decimals, 1 WBTC = 60,000 USDC):
Balanced deposit: 1 WBTC (1e8 wei) and 60,000 USDC (60_000e6 wei).
`max(1e8, 60_000e6) - 1000 = 60_000e6 - 1000 = 59_999e6`.

- A balanced deposit yields fewer shares than an unbalanced one (e.g., 1 WBTC alone = 1e8 - 1000 = 99_999_000), despite equivalent economic value (~$60k USD).

## Impact 
-  Users depositing balanced amounts (e.g., 1 WBTC and 60k USDC) receive fewer shares (59_999e6) than if they deposited only one token (e.g., 1 WBTC = 99_999_000), despite contributing equal value (~$60k USD). This penalizes balanced deposits, which is counterintuitive to Uniswap V3’s paired liquidity model.

- Users may exploit this by depositing single-token amounts initially (e.g., 1 WBTC for 99_999_000 shares), then rebalancing externally, reducing protocol adoption for balanced deposits


## Proof of Concept
Consider a WBTC/USDC vault (`token0 = WBTC, token1 = USDC, 1 WBTC = 60,000 USDC`):
- Balanced Deposit:
  - User deposits 1 WBTC (1e8 wei) and 60,000 USDC (60_000e6 wei).
   - `totalSupply = 0`, so:
    - `amount0 = 1e8, amount1 = 60_000e6`.
    - `shares = max(1e8, 60_000e6) - 1000 = 60_000e6 - 1000 = 59_999e6` (~59,999 with 6 decimals).
    - Value: ~$60,000 USD, `shares = 59,999,000,000`.
- Unbalanced Deposit:
 - User deposits 1 WBTC (1e8 wei) only.
   - `totalSupply = 0`, so:
   - `amount0 = 1e8, amount1 = 0`.
   - `shares = max(1e8, 0) - 1000 = 1e8 - 1000 = 99_999_000` (~99,999 with 6 decimals).
   - Value: ~$60,000 USD, `shares = 99,999,000`.
- Comparison:
  - Equal USD value (~$60k) yields 59,999e6 vs. 99,999,000 shares, a ~40% reduction for balanced deposits (59,999 / 99,999 ≈ 0.6).

## Recommendation
- Replace the `max(depositAmount0, depositAmount1) - 1000` calculation with the geometric mean (`sqrt(depositAmount0 * depositAmount1)`) for initial share allocation, normalizing for token value differences
