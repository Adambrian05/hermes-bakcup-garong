# Inconsistent Chainlink Price Feed Decimals in Token Value Calculation Leads to Incorrect Position Valuations

## Summary
The `_calculateTokenValues` function in the Leverager contract fails to normalize Chainlink price feed decimals when calculating USD values, resulting in incorrect position valuations. This affects leverage calculations, liquidation checks, and protocol fees, potentially leading to improper liquidations or unsafe leverage positions.

&nbsp;
## Vulnerability Details
The [`_calculateTokenValues`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L429-L440) function is documented in `openLeveragedPosition` to return "the USD price in 1e18" but fails to normalize different Chainlink price feeds to a consistent decimal precision. The vulnerability manifests in two distinct ways:

**Part 1: Different Price Feed Decimal Precisions**
When both tokens have price feeds but with different decimal precisions (e.g., 8 decimals for ETH/USD vs 6 decimals for USDC/USD), the function adds USD values with inconsistent scales:

```solidity
function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
    internal
    view
    returns (uint256 usdValue)
{
    uint256 chPrice0;
    uint256 chPrice1;
    uint256 decimals0 = 10 ** ERC20(token0).decimals();
    uint256 decimals1 = 10 ** ERC20(token1).decimals();
    if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
        chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
        usdValue += amount0 * chPrice0 / decimals0;  // Price with 8 decimals
    }
    if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
        chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
        usdValue += amount1 * chPrice1 / decimals1;  // Price with 6 decimals
    }
    // ...
    return usdValue;
}
```

**Part 2: Standard Price Feed Precision Doesn't Match Expected Output Precision**
Even when both tokens have price feeds with the same decimal precision (typically 8 decimals for Chainlink), the function still doesn't normalize the result to the expected 1e18 precision mentioned in the comment:

```solidity
up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price); // returns the USD price in 1e18
```

This means the function returns values with 8 decimal places when 18 decimal places are expected, causing significant undervaluation of positions.

Another instance of the issue is when `up.initCollateralValue` is calculated in `openLeveragedPosition`. The function uses an unnormalized price from `PriceFeed::getPrice`

&nbsp;
## Proof of Concept

**Part 1: Different Price Feed Decimal Precisions**
Consider a position with:
- token0 = ETH with price feed decimals = 8 (ETH/USD)
- token1 = USDC with price feed decimals = 6 (USDC/USD)
- amount0 = 1 ETH (1e18 wei)
- amount1 = 1000 USDC (1e9 units with 6 decimals)
- ETH price = $2,000 (2000 * 10^8 from Chainlink)
- USDC price = $1 (1 * 10^6 from Chainlink)

Current calculation:
```ascii
usdValue = (amount0 * chPrice0 / decimals0) + (amount1 * chPrice1 / decimals1)
usdValue = (1e18 * 2000e8 / 1e18) + (1000e6 * 1e6 / 1e6)
usdValue = 2000e8 + 1000e6
usdValue = 200,000,000,000 + 1,000,000,000
usdValue = 201,000,000,000
```

This is incorrect because ETH's contribution is calculated with 8 decimal places while USDC's is calculated with 6 decimal places.

**Part 2: Standard Price Feed Precision Doesn't Match Expected Output Precision**
Consider a position with:
- token0 = ETH with price feed decimals = 8 (ETH/USD)
- token1 = WBTC with price feed decimals = 8 (WBTC/USD)
- amount0 = 1 ETH (1e18 wei)
- amount1 = 0.05 WBTC (5e6 units with 8 decimals)
- ETH price = $2,000 (2000 * 10^8 from Chainlink)
- WBTC price = $40,000 (40000 * 10^8 from Chainlink)

Current calculation:
```ascii
usdValue = (amount0 * chPrice0 / decimals0) + (amount1 * chPrice1 / decimals1)
usdValue = (1e18 * 2000e8 / 1e18) + (5e6 * 40000e8 / 1e8)
usdValue = 2000e8 + 2000e8
usdValue = 4000e8
```

But the function is expected to return the USD value in 1e18 precision, which would be 4000e18.

&nbsp;
## Impact Details
This inconsistency leads to incorrect position valuations, with tokens using lower decimal precision price feeds being significantly undervalued compared to those with higher precision. This directly affects leverage calculations, liquidation thresholds, and protocol fees. Positions might be incorrectly liquidated or allowed to maintain unsafe leverage ratios, potentially causing financial losses to users and the protocol.

## Tools Used
Manual

&nbsp;
## Recommendations
Always normalize the price to ensure consistent 18-decimal precision.
