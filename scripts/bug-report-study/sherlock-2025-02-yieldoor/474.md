# Unprotected One-Sided Deposits Create Imbalanced Strategy Pools Leading to Protocol Dysfunction and Potential DoS

## Summary
The Vault contract allows first depositor to create imbalanced pools by depositing only one token type (token0 or token1), which leads to severe operational issues. The first depositor can make a one-sided deposit that forces the strategy into a sub-optimal state, preventing efficient positioning on Uniswap V3. This negatively impacts protocols performance, grief subsequent depositors, and can completely brick the deposit function for tokens that revert on zero-value transfers.

## Vulnerability Details
The vulnerability exists in the [`_calcDeposit` function which handles three deposit scenarios](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L129-L150): first deposit, deposit when one token is empty, and normal two-sided deposit. The issue occurs in two critical scenarios:

1. **Scenarios 1: First deposit vulnerability**: The vault doesn't require the first depositor to provide both tokens. When a first depositor adds only token0 or token1, they establish an imbalanced pool.

Perpetuation of imbalance: When one token balance is zero (bal0 or bal1), subsequent deposits enter the `else if` branches of the code:

```solidity
	else if (bal0 == 0) {
	    amount1 = depositAmount1;
	    shares = amount1 * totalSupply / bal1;
	}
	else if (bal1 == 0) {
	    amount0 = depositAmount0;
	    shares = amount0 * totalSupply / bal0;
	}
	// The function makes it worst by enforcing the deposit of the token that are already in the position instead of the receiving the one that is lacking.
```

In these branches, only one token amount is set while the other remains zero. This causes:
- A zero-value transfer for the unset token, which some ERC20 tokens revert on
- Continued imbalance in the pool composition. The function makes it worst by enforcing the deposit of the tokens that are already in the pool instead of the receiving the one that is lacking.
- Sub-optimal Uniswap V3 position management, which works best with balanced token pairs

2. **Scenarios 2: Recurring vulnerability during normal operation**: This imbalanced state can occur not just from the first deposit but during normal operations whenever market conditions or withdrawals lead to one token being fully depleted. For example, if the price of token0 drops significantly, the Uniswap V3 positions might end up holding only token1, depleting token0 entirely.


### Another attack vector a malicious first depositor can execute
First depositor Can manipulate token ratio for subsequent depositors by setting an extreme initial balance.
Implementation path:
1. The _calcDeposit function for first deposit accepts any ratio: 
```solidity
	 if (totalSupply == 0) {
		amount0 = depositAmount0;
		amount1 = depositAmount1;
		// ...
	}
```

2. Attacker identifies two tokens where normal market ratio is approximately 1:1
3. Makes first deposit with extreme ratio (e.g., 1000 of token0 : 1 of token1)
4. Receives shares based on the higher value: `shares = (amount0 > amount1 ? amount0 : amount1) - (1000)`
5. This establishes baseline where future depositors must:
   - Either match this skewed 1000:1 ratio (unlikely and inconvenient)
   - Or deposit balanced amounts but receive significantly fewer shares due to cross calculation
6. When subsequent users deposit balanced amounts, the cross calculation (min of cross0/cross1) forces them to effectively match the token1 side while "wasting" most of their token0


**Limited recovery options**
When the protocol enters such state, the recovery options are both unfriendly:
   - Protocol admins must donate tokens to rebalance the strategy, creating an unexpected cost burden.
   - Alternatively, if there's an active LP position, the protocol must wait for market prices to move favorably, which is entirely outside the protocol's control


## Proof of Concept
**Scenario 1: First Deposit Imbalance**
1. First user deposits 1000 token0 and 0 token1
2. `_calcDeposit` assigns `amount0 = 1000` and `amount1 = 0`
3. The vault now has token0 but no token1
4. Subsequent users trying to deposit both tokens will have:
   - `bal0 > 0` and `bal1 = 0`
   - The contract will try to process only token0, attempting a zero transfer of token1
   - For tokens that revert on zero transfers, the deposit function becomes unusable
5. This continues to persist the imbalance position
6. When the position gets some `token1`, say `amount0 = 999` and `amount1 = 1`
7. Now the user encouters a new problem: They have to match the position `token0` and `token1` in unorder to get a fair share amount
8. This effectively waste depositors token.

**Scenario 2: Operational Imbalance**
1. The vault has balanced positions in Uniswap V3
2. Token0 price drops significantly, causing the strategy's positions to convert entirely to token1
3. The strategy now has `bal0 = 0` and `bal1 > 0`
4. New deposits will attempt zero transfers of token0, potentially reverting
5. The deposit function is now broken until either:
   - An admin donates token0 to the strategy
   - The market price of token0 increases enough to naturally rebalance positions

## Impact Details
This vulnerability allows malicious users to permanently damage the protocol's functionality by creating imbalanced pools that cannot be efficiently corrected. The imbalance prevents optimal Uniswap V3 positioning, significantly reducing yield for all vault users, and accruing loses for subsequent depositors. Furthermore, for tokens that revert on zero transfers, the deposit function becomes completely unusable, effectively shutting down new deposits. Even during normal operations, market movements can trigger this vulnerability, requiring costly admin intervention or leaving the protocol at the mercy of market conditions.

## Recommendations
Modify the `_calcDeposit` function to enforce balanced deposits:

```solidity
	function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
	    view
	    returns (uint256 shares, uint256 amount0, uint256 amount1)
	{
	    uint256 totalSupply = totalSupply();
	
	    // If total supply > 0, vault can't be empty
	    assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);
	
	    if (totalSupply == 0) {
	        // For first deposit, just use the amounts desired
	        amount0 = depositAmount0;
	        amount1 = depositAmount1;
	        // Ensure first deposit must include both tokens
	        require(amount0 > 0 && amount1 > 0, "First deposit must include both tokens");
	        shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
	    } else if (bal0 == 0) {
	        amount0 = depositAmount0;
	        amount1 = depositAmount1;
	        // Require some token0 to fix the imbalance
	        require(amount0 > 0, "Must deposit token0 to rebalance the pool");
	        shares = amount1 * totalSupply / bal1;
	    } else if (bal1 == 0) {
	        amount0 = depositAmount0;
	        amount1 = depositAmount1;
	        // Require some token1 to fix the imbalance
	        require(amount1 > 0, "Must deposit token1 to rebalance the pool");
	        shares = amount0 * totalSupply / bal0;
	    } else {
	        // Original cross calculation remains unchanged
	    }
	}
```

This solution ensures:
1. The first deposit must include both tokens
2. Subsequent deposits that could help rebalance a skewed pool must include the missing token
3. Including a swapping functionality in the `rebalance` function that rebalances the ratio of `token0` and `token1` when the position is heavily skewed to one direction.
