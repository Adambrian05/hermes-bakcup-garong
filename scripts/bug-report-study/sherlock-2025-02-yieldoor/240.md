# [M-02 | 0xKoiner]No Collateral Ratio Enforcement in Vault Allows Malicious Users to Unbalance Liquidity

### Summary

The lack of collateral ratio enforcement in the `deposit` function of `Vault.sol` will cause liquidity imbalances for the vault as a malicious user will deposit skewed token amounts to disrupt the expected balance, affecting subsequent withdrawals.

refer: [`Vault.sol::deposit`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48)

### Root Cause

In `Vault.sol:73`, the `deposit` function does not enforce a minimum collateral ratio or validate `amount0` and `amount1` against the existing `totalBalance0` and `totalBalance1` retrieved from `IStrategy(strategy).balances()`, which is a mistake as it allows users to deposit arbitrary proportions of `token0` and `token1`, unbalancing the vault’s liquidity.

- In `Vault.sol:85`, the `deposit` function calls `_calcDeposit(totalBalance0, totalBalance1, amount0, amount1)` and uses the returned `depositAmount0` and `depositAmount1` without ensuring they align with the vault’s current asset ratio, allowing skewed deposits.

### Internal Pre-conditions

1. [Any user needs to call deposit] with `amount0` and `amount1` set to highly skewed values (e.g., a large `amount0` with a minimal `amount1` or vice versa) to deviate significantly from the vault’s existing `totalBalance0`/`totalBalance1` ratio.
2. [Owner needs to call setStrategy] to set `strategy` to a valid `Strategy` contract address, ensuring `IStrategy(strategy).balances()` returns meaningful `totalBalance0` and `totalBalance1`.

### External Pre-conditions

1. The Uniswap V3 pool (`IUniswapV3Pool`) used by `Strategy.sol` must be active and have sufficient liquidity to allow the `Strategy` to adjust positions after the skewed deposit, though this doesn’t prevent the initial imbalance.

### Attack Path

1. A malicious user observes the current `totalBalance0` and `totalBalance1` via `IVault(vault).balances()`, noting the existing ratio (e.g., 1 WBTC : 100,000 USDC).
2. The malicious user calls `deposit` with a skewed amount, such as `amount0 = 10e8` (10 WBTC) and `amount1 = 1e6` (1 USDC), which `_calcDeposit` accepts and adjusts to deposit as much as possible based on available liquidity.
3. The vault mints shares to the user, and the `Strategy` receives the skewed deposit (e.g., 10 WBTC and 1 USDC), significantly altering the `totalBalance0`/`totalBalance1` ratio.
4. The rebalancer calls `IStrategy.rebalance()` to adjust liquidity positions, but the vault remains unbalanced until then, allowing the attacker to exploit withdrawal mechanics.
5. A subsequent user calls `withdraw`, receiving tokens proportional to the now-skewed `totalBalance0`/`totalBalance1`, potentially draining one token type (e.g., USDC) while leaving excess of the other (e.g., WBTC).

### Impact

The vault suffers an approximate loss of balanced liquidity, as skewed deposits can lead to one token being disproportionately withdrawn, leaving the vault with an excess of the other token. The attacker gains by manipulating withdrawal amounts to extract more value than intended (e.g., draining USDC while dumping WBTC), though exact gains depend on market conditions and rebalancing frequency.

```solidity
// In a test file (e.g., extending BaseTest.sol)
function testSkewedDepositUnbalancesVault() public {
    // Initial state after setUp: 1 WBTC and 100,000 USDC in vault
    (uint256 initialBal0, uint256 initialBal1) = IVault(vault).balances();
    assertApproxEqAbs(initialBal0, 1e8, 1e6); // 1 WBTC
    assertApproxEqAbs(initialBal1, 100_000e6, 1e12); // 100,000 USDC

    // Malicious user deposits skewed amounts
    vm.startPrank(depositor);
    deal(address(wbtc), depositor, 10e8); // 10 WBTC
    deal(address(usdc), depositor, 1e6); // 1 USDC
    wbtc.approve(vault, 10e8);
    usdc.approve(vault, 1e6);
    IVault(vault).deposit(10e8, 1e6, 0, 0); // Skewed deposit

    // Check new balances
    (uint256 newBal0, uint256 newBal1) = IVault(vault).balances();
    assertGt(newBal0, initialBal0); // Increased WBTC significantly
    assertApproxEqAbs(newBal1, initialBal1 + 1e6, 1e4); // Minimal USDC increase

    // Normal user withdraws, potentially draining USDC
    vm.startPrank(user);
    uint256 shares = IERC20(vault).balanceOf(user);
    (uint256 out0, uint256 out1) = IVault(vault).withdraw(shares, 0, 0);
    assertGt(out1, out0 * 100_000); // Receives more USDC than WBTC ratio suggests, draining USDC
}
```

### Mitigation

Enforce a collateral ratio in deposit based on the Strategy’s expected proportions:

```solidity
// In Vault.sol
function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
    external
    returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
{
    IStrategy(strategy).collectFees();
    (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();

    // Enforce ratio (e.g., within 10% of current ratio if vault not empty)
    if (totalBalance0 > 0 && totalBalance1 > 0) {
        uint256 currentRatio = totalBalance0 * 1e18 / totalBalance1;
        uint256 depositRatio = amount0 * 1e18 / amount1;
        uint256 tolerance = 0.1e18; // 10% tolerance
        require(
            depositRatio >= currentRatio * (1e18 - tolerance) / 1e18 &&
            depositRatio <= currentRatio * (1e18 + tolerance) / 1e18,
            "deposit ratio out of bounds"
        );
    }

    (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);
    // Rest of the function...
}
```

### Validation Against Test Files

#### Analysis of Test Coverage
- **Relevant Test File**: `BaseTest.sol` is the primary file testing `Vault.sol` directly. `LeveragerTest.sol` interacts with `Vault` via `Leverager`, but deposit logic is mostly tested in `BaseTest.sol`.

- **Key Tests in `BaseTest.sol`**:
  1. **`testDeposit`**:
     - Deposits 2 WBTC and 100,000 USDC with min amounts (0.5 WBTC, 50,000 USDC).
     - Asserts deposited amounts match `Strategy` balances post-deposit.
     - **Observation**: Uses a balanced ratio (2:100,000 ≈ 1:50,000), not testing skewed deposits. No ratio enforcement is checked.
  2. **`test_fuzzDepositAndWithdraw`**:
     - Fuzzes `amount0` (1000 to 10e8) and `amount1` (1000 to 1_000_000e6), deposits, then withdraws.
     - Asserts withdrawn amounts approximate deposited amounts.
     - **Observation**: Fuzz range allows skewed deposits (e.g., 10e8 WBTC vs. 1000 USDC), but `_calcDeposit` adjusts amounts to fit liquidity. No explicit ratio check; tests focus on round-trip equality, not balance impact.
  3. **`test_canDepositAtAnyPrice`**:
     - Fuzzes deposits after swapping WBTC, testing deposit resilience to price changes.
     - **Observation**: Doesn’t test extreme ratio skews explicitly; focuses on price volatility, not deposit proportions.
  4. **`test_fuzzDepositWithdrawRemainRatio`**:
     - Deposits 1 WBTC and 100,000 USDC after swapping to skew pool price, checks deposit and withdrawal ratios against `Strategy` balances.
     - **Observation**: Verifies ratio preservation post-rebalance, but initial deposit (1:100,000) is balanced. Doesn’t test malicious skews pre-rebalance.
  5. **`setUp`**:
     - Initial deposit of 1 WBTC and 100,000 USDC, a balanced ratio.
     - **Observation**: Sets a baseline but doesn’t explore imbalance scenarios.

- **Key Logic in `Vault.sol`**:
  - `_calcDeposit` adjusts `amount0` and `amount1` to fit the vault’s liquidity:
    - If `totalSupply == 0`, uses raw `amount0` and `amount1`.
    - If one balance is 0, scales shares by the non-zero token.
    - Otherwise, calculates a `cross` to balance deposits against existing liquidity.
  - This adjustment mitigates some imbalance but doesn’t enforce a specific ratio, allowing skewed deposits to persist until `rebalance`.

- **Test Gaps**:
  - No test explicitly deposits a highly skewed ratio (e.g., 10 WBTC : 1 USDC) and checks subsequent withdrawal impact.
  - No test verifies vault balance post-deposit pre-rebalance, where the imbalance would be most exploitable.
  - `rebalance` by the `rebalancer` (tested in `test_fuzzRebalance`) eventually corrects imbalances, but the window between deposit and rebalance isn’t exploited or tested.
