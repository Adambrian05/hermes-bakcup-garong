# [M-01 | 0xKoiner] Lack of Input Validation in burn Function Locks Funds for LendingPool

### Summary

The absence of explicit balance checks in the `burn` function of `yToken.sol` will cause failed burns or locked funds for the `LendingPool` as the function assumes `msg.sender` (the `LendingPool`) has sufficient `yTokenAmount` and that `underlyingTokenAmount` is available to transfer without verifying these conditions.

refer: [`yToken.sol::burn`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/yToken.sol#L47)

### Root Cause

In `yToken.sol:47`, the `burn` function lacks explicit checks for the sender’s `yToken` balance and the contract’s underlying asset balance before calling `_burn` and `safeTransfer`, which is a mistake as it risks reverting or failing silently if these assumptions don’t hold.

Example:
- In `yToken.sol:47`, the `burn` function executes `_burn(msg.sender, yTokenAmount)` and `IERC20(underlyingAsset).safeTransfer(receiverOfUnderlying, underlyingTokenAmount)` without verifying `balanceOf(msg.sender) >= yTokenAmount` or `IERC20(underlyingAsset).balanceOf(address(this)) >= underlyingTokenAmount`.

### Internal Pre-conditions

1. [LendingPool needs to call burn] with `yTokenAmount` to be greater than its current `yToken` balance held in the `yToken` contract.
2. [LendingPool needs to call burn] with `underlyingTokenAmount` to be greater than the `yToken` contract’s balance of the underlying asset (`underlyingAsset`).

### External Pre-conditions

1. No external protocol changes are required for this vulnerability to manifest, as it depends solely on the `LendingPool`’s interaction with `yToken.sol`.

### Attack Path

1. This is a vulnerability path rather than an attack path, as it doesn’t require malicious intent but rather a misconfiguration or error by the `LendingPool`.
2. The `LendingPool` calls `burn` with a `yTokenAmount` exceeding its balance, causing `_burn` to revert due to insufficient tokens (handled by `ERC20.sol`’s internal check).
3. Alternatively, the `LendingPool` calls `burn` with an `underlyingTokenAmount` exceeding the `yToken` contract’s underlying asset balance, causing `safeTransfer` to revert.
4. The revert halts the `LendingPool`’s operation (e.g., during a redemption or liquidation), potentially locking funds or disrupting state updates.

### Impact

The `LendingPool` suffers an approximate loss of operational capability, as failed burns could prevent redemptions or repayments, locking funds in the `yToken` contract or disrupting downstream processes like `Leverager` withdrawals. No attacker gains directly; this is a denial-of-service or fund-locking issue.


### Mitigation

Add explicit balance checks in the **burn** function to prevent reverts and ensure safe execution:
```solidity
// In yToken.sol
function burn(address receiverOfUnderlying, uint256 yTokenAmount, uint256 underlyingTokenAmount)
    external
    onlyLendingPool
    nonReentrant
{
    require(balanceOf(msg.sender) >= yTokenAmount, "insufficient yToken balance");
    require(IERC20(underlyingAsset).balanceOf(address(this)) >= underlyingTokenAmount, "insufficient underlying balance");
    _burn(msg.sender, yTokenAmount);
    IERC20(underlyingAsset).safeTransfer(receiverOfUnderlying, underlyingTokenAmount);
}
```

### Validation Against Test Files

Let’s assess whether my finding holds based on the provided test files (`RequereOverflowTest.sol`, `BaseTest.sol`, `SetStrategyTest.sol`, `LeveragerTest.sol`, and `MockOracle.sol`). My concern was twofold:
1. **Insufficient `yToken` balance check**: The `burn` function relies on `ERC20._burn` to revert if `msg.sender` lacks sufficient `yTokenAmount`, but this isn’t explicitly checked beforehand.
2. **Insufficient underlying asset balance check**: No check ensures the `yToken` contract has enough `underlyingAsset` to transfer `underlyingTokenAmount`.

  - **`test_LendingPoolRepaymentFromBorrower`**:

- **Key Findings from Tests**:
  - **No Explicit `burn` Failure Testing**: None of the tests simulate:
    - `LendingPool` calling `burn` with `yTokenAmount` exceeding its balance.
    - `LendingPool` calling `burn` with `underlyingTokenAmount` exceeding the `yToken` contract’s underlying balance.
  - **Implicit Assumptions**: Tests use `deal` to ensure sufficient balances, masking the vulnerability. The `ERC20._burn` revert is relied upon for `yTokenAmount`, and `safeTransfer` is assumed to handle underlying balance issues, but no edge cases are validated.

#### Is My Finding Valid?
- **Yes, the finding is valid**: The lack of explicit checks in `yToken.burn` remains a vulnerability:
  - **For `yTokenAmount`**: While `ERC20._burn` checks the balance internally and reverts with "ERC20: burn amount exceeds balance", the absence of an explicit check in `burn` obscures this dependency, potentially leading to unexpected reverts in `LendingPool`. This could disrupt operations (e.g., `redeem`) without clear error messaging.
  - **For `underlyingTokenAmount`**: No test ensures the `yToken` contract has sufficient `underlyingAsset` before `safeTransfer`. If `LendingPool` calls `burn` with an `underlyingTokenAmount` exceeding available funds (e.g., due to prior borrows or miscalculation), it reverts with "ERC20: transfer amount exceeds balance", locking the operation.
- **Impact Confirmed**: Failed burns could halt `LendingPool`’s `redeem` or `Leverager`’s `withdraw`/`liquidatePosition`, disrupting users and potentially locking funds until manually resolved.
- **Test Gaps**: The tests don’t cover these failure modes, reinforcing the need for explicit checks to handle edge cases gracefully.
