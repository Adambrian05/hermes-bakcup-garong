# Bypassing deposit fees by exploiting an implementation bug, attacker can profit from it

### Summary

The documentation states that `deposit` and `withdraw` should be the only user-facing functions in`Vault`. However, this is not the case because `Vault` inherits from `ERC20`, making shares tradeable. This creates unintended consequences, such as bypassing the `depositFee`. Users who deposited before a deposit fee was introduced could raise some red flags making the admin add a `depositFee` ( according to the docs ). Once the fee is added, they can sell their shares for a price higher than what they originally bought them for, but lower than what a new user would get using the same amount of money via deposit (due to the fee), effectively profiting from the system’s design flaw. This contradicts the intended functionality and introduces potential economic exploitation risks.

### Root Cause

[`Vault.sol`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L11) inherits from `ERC20` without overriding the transfer functions, this violates the intended design ( as in the docs ) and lead to unintended consequnces.

### Internal Pre-conditions

A fee should be added.

### External Pre-conditions

N/A

### Attack Path

1. Attacker deposits and gets an amount of shares without a fee.
2. Attacker spams deposit/withdraw which raises red flags for the admin, making him add a deposit fee ( as in the docs ).
3. Attacker sells their fee-free shares to a user who would otherwise get less shares due to the fee.
4. The buyer withdraws, gaining more than what they should have.

### Impact

- A 0.01% loss to the protocol each time the attacker transfer their shares. ( technically the fee is capped at 0.1% according to Vault.sol:200, so the protocol may lose up to 0.1% in extreme cases.
- Approximately 0.005% gain to the attacker each time. ( or 0.05% in extreme cases ).

- Regardless bypassing fees, this also may allow tricking a user to sign a `approve()` transaction , then calling `transferFrom` and steal all the user shares.

### Mitigation

Override the functions `transfer` , `transferFrom` , and `approve` , and make sure the msg.sender is only the vault or the strategy.
