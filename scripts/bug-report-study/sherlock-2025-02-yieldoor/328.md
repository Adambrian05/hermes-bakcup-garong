# Incorrect Tick Upper Value in collectFees Function Prevents Vesting Position Fee Collection

## Summary
The `collectFees` function in the `Strategy` contract incorrectly uses `mainPosition.tickUpper` instead of `vestPosition.tickUpper` when collecting fees for the vesting position. This mismatch causes the contract to attempt collecting fees from a non-existent or incorrect position, resulting in lost fee revenue. The issue becomes particularly problematic after a rebalance operation changes the main position's ticks while the vesting position's ticks remain unchanged.

## Vulnerability Detail
In the Strategy contract, the `collectFees` function contains a critical bug on line 169:
The function incorrectly uses `mainPosition.tickUpper` instead of `vestPosition.tickUpper` when collecting fees for the vesting position.

When a vesting position is created in addVestingPosition(), it copies the current main position's ticks.  However, when the main position is rebalanced, its ticks change while the vesting position's ticks remain fixed. This creates a mismatch between the two positions.

In Uniswap V3, positions are uniquely identified by:
- The owner address (in this case, the Strategy contract)
- The lower tick
- The upper tick

When the contract tries to collect fees using `collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper)`, it's trying to collect from a position that doesn't match the one created with `vestPosition.tickLower` and `vestPosition.tickUpper` and so will revert.  

This has sever implications across the protocol, causing `Vault.withdraw`, `Vault.deposit` and `Leverager.liquidatePosition` functions to revert, due to their reliance on `collectFees()`.

## Impact
This bug has severe consequences for the protocol:
1. List itemFailed Fee Collection: After a `rebalance`, the `collectFees` function will attempt to collect fees from a position that doesn't exist (identified by `vestPosition.tickLower` and `mainPosition.tickUpper`), causing the transaction to revert.
2. Denial of Service: The `collectFees` function is called in multiple critical paths:
	- In the Leverager contract's collectFees modifier, which is required for liquidations
	- Before adding a new vesting position
	- When setting a new protocol fee.
	- When compounding
	- When rebalancing
	- During regular fee collection operations
	- During deposits that need to account for accrued fees
	- During withdrawals that need to account for accrued fees
3. Blocked Liquidations: The `liquidatePosition` function in the `Leverager` contract uses the `collectFees` modifier, which calls `IStrategy(strat).collectFees()`. When this fails, liquidations become impossible, potentially leading to bad debt in the protocol.
4. Blocked Deposits and Withdrawals: Functions that depend on fee collection will be blocked, preventing users from depositing or withdrawing funds.
5. Lost Fee Revenue: The protocol will fail to collect fees from the vesting position, resulting in lost revenue.

## Code Snippet
[### src/Strategy.sol#167](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L167)
```Solidity
function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0) collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(secondaryPosition.tickLower, secondaryPosition.tickUpper);
        }
        if (ongoingVestingPosition) {
            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper); // @audit-issue Should be vestingPosition.tickUpper
        }

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = (afterBal0 - preBal0) * protocolFee / 10_000;
        uint256 protocolFees1 = (afterBal1 - preBal1) * protocolFee / 10_000;

        if (protocolFees0 > 0) IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0) IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
            _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }
```

```Solidity
function collectPositionFees(int24 tickLower, int24 tickUpper) internal {
        IUniswapV3Pool(pool).burn(tickLower, tickUpper, 0); <-- will revert due to pool not exsiting
        IUniswapV3Pool(pool).collect(address(this), tickLower, tickUpper, type(uint128).max, type(uint128).max);
    }
```

## POC
Add the following test to the BaseTest.sol file which shows:
1. Create a vesting position with the current main position ticks
2. Generate fees through swaps
3. Trigger a rebalance to change the main position ticks
4. Verify that the main position ticks have changed but vesting position ticks remain the same
5. Attempt to collect fees, which fails with a revert

```Solidity
function test_vestingPositionFeeCollectionBug() public {
        // 1. Create a vesting position
        vm.startPrank(owner);
        
        deal(address(wbtc), owner, 2e8);
        deal(address(usdc), owner, 100_000e6);
        
        wbtc.approve(vault, type(uint256).max);
        usdc.approve(vault, type(uint256).max);
        
        (uint160 sqrtPriceX96,,,,,,) = IUniswapV3Pool(pool).slot0();
        
        int24 tickLower = IStrategy(strategy).getMainPosition().tickLower;
        int24 tickUpper = IStrategy(strategy).getMainPosition().tickUpper;
        
        uint128 liquidity = LiquidityAmounts.getLiquidityForAmounts(
            sqrtPriceX96, 
            TickMath.getSqrtRatioAtTick(tickLower), 
            TickMath.getSqrtRatioAtTick(tickUpper), 
            2e8, 
            100_000e6
        );
        
        (uint256 amount0, uint256 amount1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96, 
            TickMath.getSqrtRatioAtTick(tickLower), 
            TickMath.getSqrtRatioAtTick(tickUpper), 
            liquidity
        );
        
        // Add vesting position
        IVault(vault).addVestingPosition(amount0, amount1, 1 days);
        
        // 2. Generate some fees
        vm.stopPrank();
        vm.startPrank(depositor);
        
        // Perform some swaps to generate fees
        deal(address(wbtc), depositor, 5e8);
        swapWbtc(5e8);
           
        // 3. Trigger a rebalance to change mainPosition ticks
        vm.stopPrank();
        vm.startPrank(rebalancer);
        
        // Skip time to allow rebalance
        skip(361); // rebalanceInterval is 360
        
        // Store the original vesting position ticks for verification
        IStrategy.VestingPosition memory originalVP = IStrategy(strategy).getVestingPosition();
        
        // Rebalance to change the main position ticks
        IStrategy(strategy).rebalance();
        
        // 4. Verify the ticks have changed
        IStrategy.Position memory newMainPos = IStrategy(strategy).getMainPosition();
        IStrategy.VestingPosition memory vestPos = IStrategy(strategy).getVestingPosition();
        
        // Check that main position ticks have changed but vesting position ticks remain the same
        assertFalse(
            newMainPos.tickUpper == originalVP.tickUpper,
            "Main position tickUpper should have changed after rebalance"
        );
            
        // Call collectFees which has the bug
        vm.expectRevert(bytes("NP"));
        IStrategy(strategy).collectFees();
        
        console.log("Main position tickUpper:", newMainPos.tickUpper);
        console.log("Vesting position tickUpper:", vestPos.tickUpper);
        console.log("Bug: collectFees uses mainPosition.tickUpper instead of vestPosition.tickUpper");
    }
```

## Recommendation
The recommended fix is simply to use the correct tickUpper value
```Solidity
collectPositionFees(vestPosition.tickLower, vestPosition.tickUpper);
```
