# First user to deposit gets zero shares on exact deposit of 1000 in `Vault::deposit`

### Summary

If the first user tries to deposit either `token0` or `token1` to the `Vault` contract with an exactly amount of 1000, he will get zero shares, due to the incorrectly shares calculation. Before doing a safe transfer, deposit calls `_calcDeposit` function 

it will do some calculations based on the current total supply (0) 
if amount = 1000, shares = 0. because it does an 1000 - 1000 

```solidity
 shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
```

This can lead to serious the first user getting a revert because of the line: 

```solidity
 require(shares > 0, "shares cant be 0");
```


https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L129

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L67

### Root Cause

In `Vault::deposit` there is a edge case which is not prevented, in which first user tries to deposit with an amount of 1000 and he will get no shares at all, making the TX to revert 

### Internal Pre-conditions

Has to be first user and first deposit

### External Pre-conditions

First user deposits has to deposit exactly 1000 of any token 

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48

### Attack Path

Step 1: The attacker (or innocent user who could exploit it without knowing) tries to send a transaction to the deposit function with exactly 1000 units of `token0` and 0 units of `token1`. (Could be the inverse too)

Step 2: The `_calcDeposit` function calculates the shares for the attacker as 1000 - 1000 = 0.
