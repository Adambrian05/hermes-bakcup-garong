# Mistake in Debt Repayment Calculation Can Lead to Extra Costs or Liquidation

### Summary

A mistake in the `withdraw` function of the contract will cause an incorrect debt repayment calculation for users when the borrowed token is `token1`. The repayment logic incorrectly uses `amountOut0` instead of `amountOut1`, causing incorrect accounting. This miscalculation may leave the position under-collateralized or force the user to overpay, leading to financial discrepancies.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L203C1-L293C6

In the following block of the `withdraw` function, which handles repayment when the borrowed token is `token1`, the code mistakenly references `amountOut0` instead of `amountOut1`:

```solidity
} else if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```

Since `borrowed == up.token1`, the repayment should be calculated using `amountOut1`, but the ternary operation incorrectly references `amountOut0`, leading to an incorrect deduction.

if borrowed is `token1`, then we should use `amountOut1` to repay, not `amountOut0`. in the `else if (borrowed == up.token1)` block, the code uses `amountOut0` instead of `amountOut1`. 

This would lead to incorrect repayment calculations. For example, if the user has borrowed token1 (denomination is token1), when they withdraw, they get amountOut1. But the code here is checking if amountOut1 is less than owedAmount, and if so, takes amountOut0 (which is the other token) to repay.

### Internal Pre-conditions

1. A user must have an active leveraged position.
2. The borrowed asset must be `token1`.
3. The user must attempt to withdraw a portion of their position.
4. The contract must execute the `withdraw` function.

### External Pre-conditions

1. The lending pool must provide borrowing indices.
2. The vault must support withdrawals of `token0` and `token1`.
3. The user must have sufficient collateral and borrowed funds in their position.

### Attack Path

1. A user initiates a withdrawal from their leveraged position.
2. The contract calculates `owedAmount`, the portion of the borrowed amount that must be repaid.
3. The contract checks if `borrowed == up.token1`.
4. The contract incorrectly uses `amountOut0` instead of `amountOut1` when calculating `repayFromWithdraw`.
5. This miscalculation leads to an incorrect debt repayment:
   - If `amountOut0 < owedAmount`, the contract uses `amountOut0`, which is unrelated to `token1`.
   - The actual owed amount of `token1` remains unpaid or partially paid.
   - The remaining `owedAmount` calculation becomes incorrect.
6. The position may become under-collateralized or the user may overpay their debt, leading to financial loss or liquidation risks.

### Impact

1. Incorrect debt repayment can lead to unintended underpayment or overpayment.
2. If the debt is not fully repaid, the remaining debt calculations will be incorrect, increasing liquidation risks.
3. If the contract overcharges the user due to this miscalculation, they may lose excess funds unnecessarily.

### Mitigation

Modify the `else if (borrowed == up.token1)` block to correctly use `amountOut1`:

```solidity
} else if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```
This ensures that when `token1` is borrowed, the repayment correctly uses `amountOut1`, preventing debt miscalculations.
