# Incorrect Debt Accounting for `Token1` Denominated Position Causes Withdrawal Failures due to Underflow Error

### Summary

Incorrect accounting reference in `Leverager.withdraw()` will cause withdrawal failures for token1-denominated positions as users will trigger underflow errors during partial repayments. The flawed logic attempts to use token0 withdrawn amount for token1 debt settlement, creating arithmetic underflows when token1 withdrawal amounts are insufficient. This prevents users from accessing their collateralized assets and disrupts core protocol functionality.

### Root Cause

In function `Leverager.withdraw()` ([`Leverager.sol#L232`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L232)), the accounting logic incorrectly uses token0 withdrawn amount for token1 debt repayment. When handling token1-denominated positions, the code erroneously references `amountOut0` instead of `amountOut1` for partial repayment calculations. This mismatch creates an arithmetic underflow vulnerability when the token1 withdrawn amount is insufficient to deduct the token0 withdrawn amount. 

```solidity

    function withdraw(WithdrawParams calldata wp) external nonReentrant {
        // ...
        
        // In case either of the tokens is denomination token, we directly take from it.
        if (borrowed == up.token0) {
            uint256 repayFromWithdraw = amountOut0 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
            amountOut0 -= repayFromWithdraw;
        } else if (borrowed == up.token1) {
@>          uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
@>          amountOut1 -= repayFromWithdraw;
        }
        
        // ...

        if (owedAmount > 0) IERC20(up.denomination).safeTransferFrom(msg.sender, address(this), owedAmount);

        ILendingPool(lendingPool).repay(borrowed, amountToRepay);

        if (amountOut0 > 0) IERC20(up.token0).safeTransfer(msg.sender, amountOut0);
        if (amountOut1 > 0) IERC20(up.token1).safeTransfer(msg.sender, amountOut1);
        
        // ...    
    }

```

The flawed ternary operation `amountOut1 < owedAmount ? amountOut0 : owedAmount` attempts to use token0 withdrawn amount to repay token1 debt, violating asset consistency rules. This will cause invalid balance deductions when `amountOut1 < owedAmount` is true but `amountOut0 > amountOut1`, leading to failed withdrawals due to underflow errors.

### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

1. **User opens leveraged position** with token1 as denomination asset through `Leverager.openLeveragedPosition()`
2. **User calls `Leverager.withdraw()`** with parameters that trigger the condition `borrowed == up.token1 && amountOut1 < owedAmount`
3. **Faulty repayment logic executes** attempting to deduct `amountOut0` value from `amountOut1` balance
4. **Transaction reverts** due to underflow when subtracting larger repayment amount as token0 withdrawn amount from smaller token1 withdrawn amount

### Impact

The affected user suffers complete withdrawal failure and temporary fund lockup. While no direct financial loss occurs, users cannot access their collateralized assets until protocol fixes are implemented. This creates operational paralysis for token1-denominated positions meeting the repayment condition, undermining core protocol functionality and user trust.

### Mitigation

**Correct Asset Reference**: Modify the token1 repayment logic to use `amountOut1` instead of `amountOut0`:

```diff

-           uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
```
