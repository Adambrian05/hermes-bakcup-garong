# Improper calculation order in borrowed amount USD conversion enables bypassing leverage limits

### Summary

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L177-#L178

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L466-#L469

 A precision loss vulnerability in the leveraged position function calculation will cause financial risk for the protocol as attackers can bypass maximum leverage limits through carefully crafted transactions with small deposit amounts.

### Root Cause

In `openLeveragedPosition()`, the calculation order in converting borrowed token amounts to USD values leads to significant precision loss. 
```solidity 
up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
up.initBorrowedUsd = up.borrowedAmount * bPrice / (10 ** ERC20(lp.denomination).decimals());
```
And This allows an attacker  to bypass critical collateral and leverage checks, effectively enabling them to control a much larger position than intended. If market conditions are favorable, the attacker stands to gain significantly—despite having posted only a very small amount of collateral.

### Attack Path

 This Scenerio:
-The attacker deposits a very small amount   0.000001 WETH.
-  The  maximum borrow amount is set to 0.0001 WETH.
   => borrowedAmount= 0.0001 −0.000001 =0.000099 WETH

   Assuming the ETH price is $3,000 (represented as 3,000 with 18 decimals), the USD value is computed as:
     initBorrowedUsd  ≈0.297 USD
 
- Due to Solidity’s integer division, this calculation loses precision, so the protocol records the borrowed value as only $0.297

- With the recorded borrowed value at $0.297, the safety checks (which ensure positions aren’t over-leveraged) are misled into thinking the position is safe.

- The attacker now controls a position with 0.000099 WETH of borrowed funds, which could be used to perform trades far beyond what $0.297 collateral would normally allow.

If the market moves favorably—say ETH’s price increases—the attacker can close the position at a profit.

### Impact

An  attacker can exploit the precision loss to borrow more value than intended by the protocol’s safeguards.

### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.0;

import "forge-std/Test.sol";

contract PrecisionTest is Test {
    uint256 constant DECIMALS = 1e18;

    // Simulate the precision loss calculation
    function calculateInitBorrowedUsd(uint256 borrowedAmount, uint256 bPrice) public pure returns (uint256) {
        return (borrowedAmount * bPrice) / DECIMALS;
    }

    function testPrecisionLoss() public {
        // Set up the scenario:
        // borrowedAmount: 0.000099 ETH = 99,000,000,000,000 wei
        uint256 borrowedAmount = 99_000_000_000_000;
        // bPrice: $3000 scaled by 1e18 (3000 * 1e18)
        uint256 bPrice = 3000 * DECIMALS;

        uint256 initBorrowedUsd = calculateInitBorrowedUsd(borrowedAmount, bPrice);
        // Log the computed value; expected: 297000000000000000 (which represents 0.297 USD)
        emit log_uint(initBorrowedUsd);

        // You could assert that the value is as expected:
        assertEq(initBorrowedUsd, 297_000_000_000_000_000);
    }
}
```

### Mitigation

 Use a minimum borrowed amount check based on token amounts rather than USD values
```solidity  
require(up.borrowedAmount >= minBorrowTokenAmount, "position too small");
```
