# _calculateTokenVaules function will not calculate correctly amount when one of the tokens has no priceFeed

### Summary

A bug in _calculateTokenValues() misuses decimals, leading to incorrect usdValue calculations. This affects several functions, potentially causing wrongful liquidations, fee errors, and widespread issues in the Leverage contract.



### Root Cause

The calculations inside of the _calculateTokenValues() function will result in incorrect result, since the incorrect decimals are used for division in both calculations (if chPrice0 == 0, division should be done with decimals0, if chPrice1 == 0, division should be done with decimals1):
```solidity
if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }
```

This will result in completely wrong results being returned.

### Attack Path

1. A user wants to liquidate a certain position (it shouldn't be liquidatable at the moment), so they call the liquidatePosition() function.
2. The isLiquidatable() function is called, which takes the TWAP price from Vault and passes it as an argument to the _calculateTokenValues() function. Since the calculation for the usdValue is incorrect, the result that would be returned will be incorrect as well (if one of the tokens doesn't have a price feed).
3. This would lead to an incorrect check in the isLiquidatable() function, and the function would return true instead of false.
4. One more note: the _calculateTokenValues() function is also used in the liquidate function for calculating the fee, so that calculation will also be incorrect, potentially leading to the fee recipient getting an incorrect fee.



### Impact

Since the _calculateTokenValues() function is used in isLiquidatable, liquidatePosition, it will affect the calculations inside of these functions and potentially result in certain positions that should actually be non-liquidatable appearing as liquidatable. Since wrong calculations will be used, this could lead to users potentially losing money. The opposite could also happen, a position that should be liquidatable could appear as non-liquidatable. Additionally, in the liquidate function, this function is used to calculate the liquidation fee, which will, because of the usage of this function, be incorrect, leading to paying more or less depending on the result.
Furthermore, this function is also used in the openLeveragePosition function, where the value set is then used in withdraw, _checkWithinLimits, and isLiquidatable, also making it possible for these functions to fail in certain checks.

As seen, the impact of this vulnerability is very widespread and could affect a lot of functionalities of the Leverage contract.



### PoC

Let’s take an example of a WBTC/WETH pool (even though this will not happen to this pool since it is very likely that both of these tokens would have price feeds, so I’m just using this pool for easy explanation) on Arbitrum. The address of the pool is: 0x149e36E72726e0BceA5c59d40df2c43F60f5A22D. We will take an example using the calculations for when chPrice1 == 0. Also, we will assume that the price of WBTC is 90,000, and the price of WETH is 3,000 (so the TWAP price should be, if calculated correctly, 30 * 1e30).

1. Since this is the equation that is used : 

$$
\frac{\text{amount1} \times \text{PRECISION}}{\text{price}} \times \frac{\text{chPrice0}}{\text{decimals0}}
$$

we will try to calculate the usdValue for an amount1 of 15 * 1e18 (which is 15 ETH). The constant PRECISION is 1e30, price would be 30 * 1e30 (since we use the WBTC/WETH pool), chPrice0 would be 90000 * 1e18 (based on our assumption declared at the beginning that one WBTC is 90,000), and decimals0 would be 1e8.

2. Our calculation now looks like:

$$
\frac{(15 \times 10^{18}) \times (10^{30})}{30 \times 10^{30}} \times \frac{(90000 \times 10^{18})}{10^8}
$$

The first fraction would result in 0.5 * 1e18, and the second fraction would result in 90000 * 1e10.

3. Now our calculation is at this state:

$$
(0.5 \times 10^{18}) \times (90000 \times 10^{10})
$$

4. The result of this calculation is 45000 * 1e28.

5. This is an extremely large value since we know that the precision of 18 would be used for the price feed, so the expected return decimals for this function should also be 18.

Note: in solidity the order that I used to calculate will not be used (it will be calculated one by one from left to right, not simultaneously since I just did it like this to make things a bit faster, since the result in this example would be the same either way).





### Mitigation

Consider changing calculations to:
```solidity
if (chPrice0 == 0) {
            usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals0;
        } else if (chPrice1 == 0) {
            usdValue += amount1 * PRECISION / price * chPrice0 / decimals1;
        }


```
