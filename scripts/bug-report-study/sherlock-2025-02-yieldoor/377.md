# Missing Decimal Normalization in idleBalances() will cause incorrect share issuance for vault depositors

### Summary

The missing normalization of token balances in the **idleBalances()** function will cause an incorrect calculation of deposit shares for vault depositors, as an attacker (or even an honest user in a manipulated scenario) will exploit the differing decimal representations of tokens. In particular, if tokens with 6 decimals (e.g., USDC) and tokens with 8 or 18 decimals (e.g., WBTC or WETH) are deposited without conversion to a common scale, the share issuance will be significantly skewed. This vulnerability allows an attacker to deposit amounts that result in an over‑issuance or dilution of shares.

### Root Cause

In  `Strategy.sol:190`  The idleBalances() function returns raw token balances using IERC20(token).balanceOf(address(this)) without normalizing the amounts to a common 18‑decimal precision.
```solidity
function idleBalances() public view returns (uint256 amount0, uint256 amount1) {
    amount0 = IERC20(token0).balanceOf(address(this));
    amount1 = IERC20(token1).balanceOf(address(this));
}
```

_Example:_ In **idleBalances()**, token0 (e.g., WBTC with 8 decimals) and token1 (e.g., USDC with 6 decimals) are not scaled to 18 decimals. As a result, a deposit of 1 WBTC (1e8 units) and 1 USDC (1e6 units) should both represent an equivalent normalized value of 1e18; however, without normalization, the raw values differ by several orders of magnitude

### Internal Pre-conditions

1. A depositor (or attacker) deposits tokens with differing decimals into the vault (e.g., depositing 1e8 units of token0 with 8 decimals and 1e6 units of token1 with 6 decimals).
2. The Strategy contract’s **idleBalances()** function is used in share calculations without normalizing the token amounts to a common precision.

### External Pre-conditions

1. The underlying ERC-20 tokens must have non-standard decimal places (e.g., USDC with 6 decimals versus WBTC or WETH with 8 or 18 decimals).
2. Market conditions or deposit timings allow an attacker to manipulate the ratio of idle tokens, resulting in imbalanced normalized values.

### Attack Path

1. The attacker (or an unwitting depositor) makes a deposit into the vault using tokens with different decimals (e.g., USDC and WBTC).
2. The vault’s deposit function calls the Strategy’s idleBalances() to determine current liquidity, but the raw balances are used without normalization.
3. The share calculation in _calcDeposit() then uses these imbalanced idle balances, leading to an incorrect number of shares minted.
4. As a result, either existing depositors are diluted or the attacker can later withdraw more than their fair share.

### Impact

Vault depositors suffer an incorrect allocation of shares. In worst-case scenarios, this can lead to a significant loss of funds—either by diluting existing positions or by enabling an attacker to extract a disproportionate amount of assets relative to their deposit.

### Mitigation

- Normalize Balances: Update the idleBalances() function in Strategy.sol to convert raw token balances to a common 18‑decimal scale before they are used in any share or fee calculations. For example:
```solidity

function idleBalances() public view returns (uint256 normalizedAmount0, uint256 normalizedAmount1) {
    uint8 d0 = ERC20(token0).decimals();
    uint8 d1 = ERC20(token1).decimals();
    uint256 raw0 = IERC20(token0).balanceOf(address(this));
    uint256 raw1 = IERC20(token1).balanceOf(address(this));
    normalizedAmount0 = raw0 * (10 ** (18 - d0));
    normalizedAmount1 = raw1 * (10 ** (18 - d1));
}
```
- Review Deposit Calculations: Ensure that the Vault’s _calcDeposit function and any related calculations use the normalized values for fair share issuance.
