# Underflow Issue

### Summary
If either `token0` or `token1` is the same as the `denomination token`, the `denomBalance` can exceed the `maxBorrowAmount`.

### Root Cause
If either `token0` or `token1` is the same as the `denomination token`, the `denomBalance` can exceed the `maxBorrowAmount`.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L177
```solidity
        uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
        ILendingPool(lendingPool).repay(lp.denomination, denomBalance);

        // if for some reason there have previously been a large amount of tokens "stuck", this could fail
        // this is ok as 1) its unlikely 2) anyone could sweep them 3) likely MEV bot would sweep them within seconds
        // Although opening positions is time-sensitive, please do not report this as a vulnerability, ty.
177:    up.borrowedAmount = lp.maxBorrowAmount - denomBalance;
```

### PoC
Consider a user who wants to open a weth/usdc leveraged position with minimal usdc owed. 
Let's examine the following scenario:
token0 := weth, token1 := usdc, borrow token := usdc, wethPrice := 2500 usd, usdcPrice := 1 usd
vault0In := 40 weth, amount0In := 40 weth, vault1In = 10,000 usdc, amount1In = 9,980 usdc, maxBorrowAmount = 20 usd.

If the transaction is successful, the owed amount would be 20 usdc. 
However, due to fluctuations in the weth price on Uniswap, if more than 20 usdc remains, the calculation on line 177 may underflow.

Additionally, the remaining usdc belongs to the users, not to the free funds.

### Impact
Users are dosed.

### Mitigation

        uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));

        ILendingPool(lendingPool).repay(lp.denomination, denomBalance);
