# Uniswap V3 Tick Liquidity Limit Exploitation Enables Persistent Denial of Service Attack Against Strategy Rebalancing

## Summary
A malicious actor can prevent the Strategy contract from successfully rebalancing or compounding by exploiting Uniswap V3's tick liquidity limits. By front-running the strategy's transactions and filling the target tick ranges to their maximum capacity, an attacker can force the strategy's transactions to consistently fail. This prevents the strategy from generating revenue while leveraged positions continue to accrue interest, resulting in guaranteed losses for users.

## Vulnerability Details
The Strategy contract uses [deterministic logic to calculate which tick r](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L199-L214)anges to use when creating Uniswap V3 positions during rebalancing or compounding. These tick ranges are calculated based on the current tick and tickSpacing, making them predictable to external observers.

Uniswap V3 imposes a maximum liquidity limit per tick (`maxLiquidityPerTick`), which is calculated during pool initialization based on the pool's tickSpacing. When a transaction attempts to add liquidity that would exceed this limit, the transaction reverts with an "LO" (Liquidity Overflow) error.

The vulnerability arises from the combination of:
1. Predictable tick range selection in the Strategy contract
2. Fixed liquidity limits per tick in Uniswap V3
3. Lack of fallback mechanisms in the Strategy when position creation fails

An attacker can observe the strategy's rebalance or compound transactions in the mempool, calculate the exact tick ranges that will be targeted, and front-run with a transaction that fills those ticks to their maximum capacity. This forces the strategy's transaction to fail, preventing it from functioning properly.

Note that for L2s like Arbitrum where frontrunning is not possible, this attack can still be executed by simply following the price movement. The attacker doesn't need to wait for the strategy to be rebalanced before know which price range will be it's target, it can get predict that by calling Uniswap V3 `slot0` and using the returned values

## Proof of Concept
1. Monitor the mempool for the Strategy's `rebalance()` or `compound()` transactions Or track pools price.
2. Calculate the tick ranges that will be used by analyzing the current pool state and applying the same logic as in `_setMainTicks()` and `_setSecondaryPositionsTicks()`
3. Front-run with a transaction that adds liquidity to those tick ranges, bringing them close to or at the `maxLiquidityPerTick` limit
4. The Strategy's transaction will attempt to add liquidity to the same ticks and fail with the "LO" error
5. Repeat this process for each rebalance attempt, effectively preventing the strategy from ever successfully rebalancing

## Impact Details
This attack renders the Strategy contract non-functional by preventing it from rebalancing or compounding, which are essential for generating yield. Meanwhile, leveraged positions continue to accrue interest without offsetting revenue, resulting in guaranteed losses for users. The attack can be sustained indefinitely with minimal cost to the attacker, creating a persistent denial of service condition.

```solidity

        // Success - continue as normal
    } catch {
        // Fallback: adjust tick range and try again

        mainPosition.tickLower += fallbackOffset;
        mainPosition.tickUpper += fallbackOffset;

    }
}
```

3. Implement a circuit breaker that detects repeated failures and switches to a more conservative strategy:
```solidity
uint256 public consecutiveFailures;
uint256 public constant MAX_FAILURES = 3;

function rebalance() public onlyRebalancer {
    try {
        // Existing rebalance logic
        consecutiveFailures = 0;
    } catch {
        consecutiveFailures++;
        if (consecutiveFailures >= MAX_FAILURES) {
            // Switch to conservative mode with wider ranges or different strategy
			// E.g. 
			// - Create a position just outside initial bounds on both ends. Price is guaranteed to move either ways
			// - Increase the target range making it increasingly expensive for the attacker to successfully execute this attacker
        }
        revert("Rebalance failed");
    }
}
```
