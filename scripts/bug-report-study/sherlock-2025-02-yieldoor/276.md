# Incorrect collateral value calculation allows bypassing leverage limits

## Summary
The `Leverager#openLeveragedPosition` function incorrectly calculates the initial collateral value using both collateral and borrowed amounts, allowing users to bypass leverage limits and open positions with much higher leverage than intended.

## Relevant Context
The protocol implements leverage limits through two mechanisms:
1. `_checkWithinlimits` verifies the position leverage doesn't exceed maximum allowed leverage
2. `isLiquidateable` ensures the position maintains sufficient collateral relative to debt

The leverage is calculated as: `(collateral + debt) / collateral`

## Root Cause
In `Leverager#openLeveragedPosition`, the initial collateral value is calculated using the total amounts deposited into the vault (`a0` and `a1`), which include both user-provided collateral and borrowed funds:

[`Leverager.sol#L129`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L129)

```solidity
up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price);
```

This leads to incorrect leverage calculations in `_checkWithinlimits`:

```solidity
positionLeverage = (up.initCollateralValue + up.borrowedAmount) * 1e18 / up.initCollateralValue
```

Since `initCollateralValue` already includes the borrowed amount, the actual leverage becomes:
`(collateral + debt + debt) / (collateral + debt)`

This always evaluates to a number less than 2 regardless of the true leverage ratio `(collateral + debt) / collateral`.

## Attack Path

1. User identifies a vault with:
   - Maximum leverage of 5x
   - Minimum collateral percentage of 10%
   - Enabled for leveraged positions

2. User opens a position with:
   - 10 units of collateral
   - 400 units of borrowed funds
   - True leverage = 41x (410/10)

3. The position passes `_checkWithinlimits` because:
   - `initCollateralValue` = value of (10 + 400) = 410
   - `positionLeverage` = (410 + 400) / 410 ≈ 1.98 < 5

4. The position passes `isLiquidateable` check because:
   - `base` = 400 / (5-1) = 100 
   - Required collateral = 10% * 100 = 10
   - Actual collateral = 10 ≥ Required collateral

## Impact Explanation
High. This vulnerability allows users to bypass core protocol safety limits and open positions with extremely high leverage. This significantly increases the risk of bad debt for the protocol as these positions are much more susceptible to liquidation than intended.

## Proof of Concept
Consider a scenario where:
1. User deposits 10 USDC as collateral
2. User borrows 400 USDC (intended max should be 40 USDC for 5x leverage)
3. Total position value = 410 USDC
4. Calculated leverage = (410 + 400)/410 ≈ 1.98
5. True leverage = 410/10 = 41x

## Recommendation
Calculate initial collateral value using only user-provided amounts:

```diff
- up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, a0, a1, price);
+ up.initCollateralUsd = _calculateTokenValues(up.token0, up.token1, lp.amount0In, lp.amount1In, price);
```
