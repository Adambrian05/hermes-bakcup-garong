# Incorrect `bal0in1` Calculation in `_setSecondaryPositionsTicks`

## Summary
An incorrect calculation of `bal0in1` in the [_setSecondaryPositionsTicks](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L366) function will cause a suboptimal liquidity allocation for vault depositors as the system will misalign the Secondary Position ticks with the dominant token.

## Root Cause
In `Strategy.sol`, the calculation of `bal0in1` uses the formula `bal0in1 = bal0 * _price / PRECISION`, which is incorrect. The correct formula should be `bal0in1 = bal0 * PRECISION / _price` to accurately convert the balance of `token0` into the equivalent amount of `token1` for comparison with `bal1`. This error leads to an incorrect determination of the dominant token, resulting in misaligned tick boundaries for the Secondary Position.

## Internal Pre-conditions
1. Vault depositors need to deposit funds to set `bal0` (balance of `token0`) to be at least a non-zero value (e.g., 1000 USDC).
2. Vault depositors need to deposit funds to set `bal1` (balance of `token1`) to be at least a non-zero value (e.g., 0.5 WETH).
3. The system needs to call `rebalance` to trigger `_setSecondaryPositionsTicks` after a deposit or withdrawal that leaves residual `token0` or `token1` balances.

## External Pre-conditions
- None identified. The issue is internal to the Yieldoor protocol and does not depend on external protocol changes.

## Attack Path
1. A depositor calls `deposit` in `Vault.sol` to add 1000 USDC (`token0`) and 0.5 WETH (`token1`) to the vault.
2. The system calls `rebalance` in `Strategy.sol` to adjust the Main and Secondary Positions.
3. In `_setSecondaryPositionsTicks`, the incorrect `bal0in1` calculation (e.g., `1000 * (2000 * 1e30) / 1e30 = 2e6` instead of `1000 * 1e30 / (2000 * 1e30) = 0.5 WETH`) misidentifies the dominant token.
4. The Secondary Position ticks are set incorrectly (e.g., above the current price instead of below), reducing the efficiency of liquidity allocation and potential fee collection.

## Impact
The vault depositors suffer an approximate loss of potential yield (e.g., reduced fees from Uniswap V3 positions) due to suboptimal positioning of the Secondary Position. The exact loss depends on market conditions and trading volume but could range from 1-5% of potential earnings over time.

        // Trigger rebalance
        vm.prank(address(this));

        assertTrue(tickLower > currentTick, "Secondary Position incorrectly set above price");
    }

## Mitigation

Correct the `bal0in1` calculation in `_setSecondaryPositionsTicks` by updating the formula to:
```solidity
uint256 bal0in1 = bal0 * PRECISION / _price;
```
This ensures that `bal0in1` accurately represents the equivalent value of token0 in terms of token1, allowing the system to correctly identify the dominant token and set the Secondary Position ticks accordingly. After implementing this fix, thoroughly test the rebalancing logic with various deposit scenarios to confirm proper tick alignment and optimal liquidity allocation.
