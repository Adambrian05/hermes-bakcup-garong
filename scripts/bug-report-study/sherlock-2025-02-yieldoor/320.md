# The tick boundaries of a position can be manipulated due to a missing price check upon deployment

### Summary

The tick boundaries of a position can be manipulated due to a missing price check upon deployment

### Root Cause

Upon functions such as rebalancing, the developer has implemented a function to check the spot price is not manipulated by comparing it to the TWAP price:
```solidity
if (currentTick < minTick || currentTick > maxTick) return false;
```
This is important as the current tick is used to determine the tick boundaries of the position, otherwise the position can be created at tick boundaries such that the tick is outside them which would be problematic.

The issue is that upon deployment, we have the following code in the constructor:
```solidity
        (, int24 tick, , , , , ) = IUniswapV3Pool(pool).slot0();
        _setMainTicks(tick);
        _setSecondaryPositionsTicks(tick);
```
The code fails to call `_priceWithinRange()` to properly verify price is not manipulated.

### Internal Pre-conditions

_No_

### External Pre-conditions

1. Price is manipulated at time of deployment, this can either happen due to a malicious frontrun (on chains with public mempools) or the price just happens to be manipulated at that time

### Attack Path

1. Price is manipulated during deployment, either due to a frontrun or the price just happens to be manipulated at that time
2. The main and secondary position have incorrect tick boundaries

### Impact

Positions will have incorrect tick boundaries, based on manipulated tick.

### PoC

_No response_

### Mitigation

In the constructor:
```diff
        (, int24 tick, , , , , ) = IUniswapV3Pool(pool).slot0();
+       _requirePriceWithinRange();
        _setMainTicks(tick);
        _setSecondaryPositionsTicks(tick);
```
