# Invalid Zero Token Deposit Check Allows Users to Open Leveraged Positions and Profit Without Deposits in the `Leverager` contract


## **Summary**

The missing validation on `amount0In` and `amount1In` in [`ILeverager.openLeveragedPosition()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L103-L201) will cause an unintended profit for the depositor, as a user can borrow and withdraw funds without contributing any initial capital.


### **Root Cause**

In the [`Leverager`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol) contract, there is a missing validation check to ensure that users deposit a nonzero amount of tokens before opening a leveraged position. This allows users to initiate leveraged positions and profit without supplying any initial capital.

- The contract does not verify that `amount0In` and `amount1In` are greater than zero before proceeding with the leverage logic.
- The logic permits a user to specify zero deposits while still utilizing borrowed funds to generate profits.
- Without a proper check, the contract unintentionally allows users to create positions with no real exposure, leading to risk-free profit generation.

### **Internal Pre-conditions**

1. The contract must allow [`openLeveragedPosition()` ](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103-L201)to proceed even when `amount0In` and `amount1In` are both zero.
2. The system must allow leveraged borrowing based only on `vault0In` and `vault1In`, without requiring a user-supplied deposit.
3. There must be a price movement in favor of the user, allowing them to withdraw more than they initially committed, leading to risk-free profit.
4. The profit check does not account for the scenario where the user starts with a zero deposit but still gains from the trade.


## **Attack Path**

1. The **depositor** calls `openLeveragedPosition()` with zero initial tokens (`amount0In = 0, amount1In = 0`).
2. The **contract still executes the borrowing process**, allowing the depositor to take on debt.
3. The **depositor withdraws the entire position**, including borrowed funds.
4. The **final balance shows an increase in USDC**, causing `assertTrue(madeProfit)` to pass, even though no initial investment was made.


### **Impact**

This issue creates a major loophole that lets users take out leveraged positions without putting up any real deposit. In simple terms, it’s like getting a loan without any collateral and walking away with free money. Over time, this can:

- **Drain liquidity providers' funds**, since the borrowed assets aren’t backed by real deposits.
- **Make the protocol unstable**, as it allows users to profit unfairly without any risk.
- **Lead to major losses**, since users can keep repeating this exploit, slowly bleeding the system.
- **Break trust in the platform**, as honest users and lenders may start pulling out their funds to avoid being affected.

If left unchecked, this could turn into a ticking time bomb for the protocol, making it unsustainable in the long run.

wp.swapParams1 = "";

wp.swapParams2 = "";

  

ILeverager(leverager).withdraw(wp);

  
  

// Record final balances

uint256 finalWBTC = wbtc.balanceOf(depositor);

uint256 finalUSDC = usdc.balanceOf(depositor);

  

// Calculate profit or loss

bool madeProfit = finalUSDC > initialUSDC;

  
  

assertTrue(madeProfit, "Depositor did NOT make a profit!");

  

console.log("Initial USDC:", initialUSDC);

console.log("Final USDC:", finalUSDC);

console.log("Initial WBTC:", initialWBTC);

console.log("Final WBTC:", finalWBTC);

}

## **Mitigation**

1. **Require a minimum nonzero deposit (`amount0In` and `amount1In`) before allowing leveraged borrowing.**
2. **Validate that borrowing can only happen when sufficient collateral is provided.**
3. **Ensure that vault deposits (`vault0In` and `vault1In`) cannot be used to bypass collateral requirements.**
