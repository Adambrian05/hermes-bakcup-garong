# Flash Loan Attack Vector in Pool Activity Validation Enables Price Manipulation

## Details

## Affected Lines of code

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310-L342

The protocol's pool activity validation mechanism in `Strategy.sol (lines 308-342)` implements a discrete sampling approach to verify pool stability. This implementation checks price movements between consecutive Uniswap V3 observations using `maxObservationDeviation` as a threshold. The validation occurs in the `checkPoolActivity()` function which is called by critical protocol functions including `rebalance()`, `compound()`, and `addVestingPosition()`.

The current implementation examines price movements between observation points without considering the continuous nature of pool dynamics. This creates exploitable gaps between observation points where significant price manipulation can occur without detection. The validation relies heavily on the assumption that price stability between observation points indicates overall pool stability.


## Impact

First and foremost, the core risk measurement of leveraged positions becomes unreliable. As the protocol depends on the output of the discrete sampling from Uniswap V3 pool observations to determine if a market is stable enough for activities like opening positions or rebalancing, an attacker exploiting this weakness can effectively manipulate the observed price dynamics. As a result, positions may be opened or maintained under conditions that are far more volatile than they appear in the discrete data points. This misrepresentation directly leads to improper collateral valuation and erroneous leverage calculations.

When the maximum allowable deviation `(maxObservationDeviation)` is exploited with a flash loan attack—where rapid and precisely timed trades are executed between recorded observations—each individual tick change might still fall within acceptable bounds, while accumulating a significant drift in the underlying price. Consequently, the collateral and debt ratios calculated in contracts like `Leverager.sol` and `Vault.sol` become inaccurate. Users might unknowingly take on positions that are severely under-collateralized, exposing them to unanticipated liquidation events. Moreover, if liquidation triggers are based on these faulty stability checks, the protocol could either prematurely liquidate positions or delay necessary liquidation, resulting in systemic risk and financial losses to participants.

The uncertainty introduced by this vulnerability further undermines the reliability of protocol fees collected during rebalancing and compounding operations in Strategy.sol. These fees are computed based on the idle token balances after liquidity adjustments, which in turn depend on the assumed stability of the pool's pricing. If an attacker manipulates the pool's activities to appear stable when it is not, the protocol might end up misallocating fees—as well as incorrectly distributing yield—thus affecting both liquidity providers and borrowers. 

Furthermore, because the protocol design integrates these checks into every strategic action—ranging from opening leveraged positions to adjusting vesting schedules—this manipulative vector touches almost every component of the system. The risk is not isolated to a single transaction or contract: an attacker with sufficient resources could potentially orchestrate a broad market manipulation event that destabilizes several protocol functionalities simultaneously. In effect, the attacker’s ability to control the apparent health and stability of the underlying pool opens the door to both direct financial profit from arbitrage or liquidation advantages and indirect profit via strategic draining or misallocation of protocol resources.



## Illustration

The vulnerability manifests in Strategy.sol:

```solidity
function checkPoolActivity() public view returns (bool) {
    (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();
    uint32 lookAgo = uint32(block.timestamp) - twap;
    
    for (uint16 i = 1; i <= observationCardinality; i++) {
        // ... observation processing ...
        int24 delta = nextTick - tick;
        if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
            return false;
        }
    }
}
```

This creates exploitable conditions in `Leverager.sol` where position operations rely on this check:

```solidity
function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {
    require(IVault(lp.vault).checkPoolActivity(), "market too volatile");
    // ... position creation logic ...
}
```

## Recommendation

Implement continuous price monitoring:

```solidity
function checkPoolActivity() public view returns (bool) {
    // Add cumulative price impact checking
    uint256 cumulativeDeviation;
    uint256 lastValidPrice = getInitialPrice();
    
    for (uint16 i = 1; i <= observationCardinality; i++) {
        // Track cumulative price changes
        cumulativeDeviation += calculatePriceDeviation(lastValidPrice, currentPrice);
        require(cumulativeDeviation <= maxCumulativeDeviation, "Excessive price movement");
        
        // Add minimum observation requirements
        require(observationCount >= minRequiredObservations, "Insufficient observations");
        
        // Add volume-weighted price validation
        validateVolumeWeightedPrice(observations);
    }
}
```
