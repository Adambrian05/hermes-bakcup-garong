# Strategy::checkPoolActivity DOS

### Summary

`Strategy::checkPoolActivity` is responsible for verifying that, within a certain time frame, a pool does not experience volatility between observations, ensuring that user activity distributes volatility across adjacent observations.

The issue arises when an attacker can generate a **Denial of Service (DOS)** on the `Strategy::rebalance` and `Strategy::compound` functions.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L321-L324

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L201

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L408

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L331-L333

```solidity
uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
```

We can see that when `observationCardinality` increases, a new observation is added to the end of the pool's observation "array". This would cause the **volatility comparison between adjacent observations to eventually fail**, as the **new observation has default values like tickCumulative set to 0**. In many pools, this would be **considered excessive volatility**, causing `Strategy::_requirePriceWithinRange` **to revert.**

### Internal Pre-conditions

None

### External Pre-conditions

1. The time period being analyzed includes both the "latest" observations and the "firsts" observations within the observation "array" structure.

### Attack Path

1. When the external pre-condition is met, the attacker only needs to increase `observationCardinality` within the targeted pool.

### Impact

Reverting `_requirePriceWithinRange`, **causing a DOS on**:

* `Strategy::rebalance`

* `Strategy::compound`

### PoC

_No response_

### Mitigation

A potential solution could be to check the `initialized` property of the `observation`, and if it's false, skip it.
