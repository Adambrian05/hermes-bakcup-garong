# Single Failed Repayment Can Block All Future Repayments

### Summary

A failed token transfer in repay() after state updates will cause an inconsistent state for the lending protocol as the total borrows and underlying balance will be incorrect, potentially blocking all future repayments.



### Root Cause

Root Cause

In repay(), the function updates state variables (totalBorrows and underlyingBalance) before executing the actual token transfer. If the transfer fails or reverts, the contract will remain in an inconsistent state.

### Internal Pre-conditions

A user calls repay() and the function updates totalBorrows and underlyingBalance.

The token transfer (safeTransferFrom()) fails due to insufficient allowance, balance, or other external factors.

The protocol does not have a rollback mechanism to revert the state updates.

### External Pre-conditions

The user attempting repayment does not have sufficient token balance or allowance.

Network congestion or an external factor causes the transfer to fail.

The lending protocol does not use a reentrancy guard or atomic state updates to prevent partial execution.

### Attack Path

A user calls repay() to repay their debt.

The function updates reserve.totalBorrows -= amount and reserve.underlyingBalance += amount.

The token transfer fails due to insufficient balance or allowance.

The contract remains in an inconsistent state where:

totalBorrows is less than the actual borrowed amount.

underlyingBalance is more than the actual available balance.

Future repayments may fail due to incorrect balance calculations, preventing debt repayments.

### Impact

This vulnerability can cause a protocol-wide lock on repayments, preventing borrowers from settling their debts. This could lead to cascading failures, liquidity issues, and potential insolvency of the lending protocol.
