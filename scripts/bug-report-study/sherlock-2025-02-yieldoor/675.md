# Liquidation value miscalculation (Incorrect decimals scaling)

### Summary

When liquidating positions, the protocol computes the borrowed USD value by dividing by the token’s raw decimals (e.g., 18) instead of by 10^decimals. This arithmetic error inflates the debt calculation, preventing the proper collection of liquidation fees and potentially misclassifying positions.

### Root Cause

In `LendingPool.sol` (lines ~394–401), the `Leverager.liquidatePosition` logic, the calculation of the borrowed value in USD uses the token’s decimals incorrectly. The code divides by `ERC20(up.denomination).decimals()` (an integer like 18) instead of scaling by 10^decimals​. For example, if a token has 18 decimals, the code divides by 18 instead of 1e18, greatly inflating the computed `borrowedValue`. This is a clear arithmetic bug. As a result, the condition checking whether the collateral value exceeds the debt (`if (totalValueUSD > borrowedValue)`) will almost always evaluate to false (since `borrowedValue` is orders of magnitude larger than intended)​. The protocol thus assumes no profit even when there is one. It skips taking the intended liquidation fee and treats most liquidations as if they are fully underwater.

### Internal Pre-conditions

1. A leveraged position is opened with a standard 18-decimal ERC20 token.
2. The liquidation function is invoked using the erroneous calculation.
3. The position’s parameters are such that the liquidation check depends on the computed borrowed USD value.

### External Pre-conditions

1. The token used is a standard ERC20 with 18 decimals.
2. External price feeds provide correct values.

### Attack Path

1. An attacker (or misconfigured operator) opens a leveraged position.
2. The liquidation routine computes the borrowed value incorrectly due to wrong decimal scaling.
3. Liquidations are triggered without collecting the proper fee, allowing the attacker or liquidator to benefit fully from collateral recovery.

### Impact

Liquidators will receive excess profit and the protocol will collect no fees in many cases. Any time a position is liquidated with collateral greater than debt, the bug prevents the fee logic from executing. This means the `feeRecipient` isn’t paid its share, undermining the protocol’s revenue model. In edge cases, this miscalculation might also affect the distribution of collateral vs. debt repayment. (For instance, if `borrowedValue` is miscomputed as extremely high, the code might treat a profitable liquidation as a no-profit scenario; the liquidator still gets the leftover collateral, but the protocol fee is lost.) While this bug doesn’t allow theft of user funds directly, it breaks a core economic invariant (protocol fee on liquidation) and could erode confidence or leave value on the table.

### PoC

```
// Incorrect calculation:
uint256 borrowedValue = owedAmount * price / ERC20(token).decimals(); // e.g., divides by 18

// Correct approach:
uint256 borrowedValue = owedAmount * price / (10 ** ERC20(token).decimals());
```

### Mitigation

Update the liquidation code to scale by `10 ** ERC20(token).decimals()`. Add unit tests for tokens with various decimals to ensure accurate calculations.
