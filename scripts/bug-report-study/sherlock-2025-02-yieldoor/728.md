# Missing Slippage Protection in `LendingPool.redeem()` Allows MEV Front-Running Causing User Fund Loss

### Summary

The absence of a minimum output parameter in `LendingPool.redeem()` will cause financial losses for yToken redeemers as MEV bots will manipulate exchange rates through strategic front-running. The real-time calculation of redemption value based on mutable pool state (`ReserveLogic.yTokenToReserveExchangeRate()`) enables attackers to temporarily distort the yToken/reserve ratio during transaction execution windows, resulting in unfavorable conversion rates that directly reduce users' received underlying assets.

### Root Cause

In [`LendingPool.sol#L83-L101`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L83-L101),  the function `LendingPool.redeem()` lacks slippage protection when converting yTokens to underlying assets. The calculation of `underlyingTokenAmount` in `LendingPool._redeem()` uses a real-time exchange rate from `ReserveLogic.yTokenToReserveExchangeRate()` ([`ReserveLogic.sol#L93-L101`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol#L93-L101)) without allowing users to specify a minimum acceptable amount. This exchange rate is vulnerable to manipulation between transaction submission and execution due to:

1. Dependence on instantaneous reserve liquidity (`ReserveLogic.totalLiquidityAndBorrows()`)
2. Reliance on current yToken total supply
3. No protection against MEV sandwich attacks that could manipulate the yToken/reserve ratio

```solidity
contract LendingPool is ILendingPool, Ownable, ReentrancyGuard {
    function redeem(address underlyingAsset, uint256 yAssetAmount, address to)
        public
        notPaused
        nonReentrant
        returns (uint256)
    {
        // ...
        // transfer yTokens to this contract
        IERC20(reserve.yTokenAddress).safeTransferFrom(msg.sender, address(this), yAssetAmount);

        // calculate underlying tokens using yTokens
@>      uint256 underlyingTokenAmount = _redeem(underlyingAsset, yAssetAmount, to);

        return (underlyingTokenAmount);
    }
    
    function _redeem(address underlying, uint256 yAssetAmount, address to) internal returns (uint256) {
        // ...
        // calculate underlying tokens using yTokens
@>      uint256 underlyingTokenAmount = reserve.yTokenToReserveExchangeRate() * yAssetAmount / PRECISION;

        require(underlyingTokenAmount <= reserve.availableLiquidity(), "not enough available liquidity");

        // burn yTokens and transfer the underlying tokens to receiver
        IyToken(reserve.yTokenAddress).burn(to, yAssetAmount, underlyingTokenAmount);
        // ...
    }    
}
```

```solidity
library ReserveLogic {
    function yTokenToReserveExchangeRate(DataTypes.ReserveData storage reserve) external view returns (uint256) {
@>      (uint256 totalLiquidity,) = totalLiquidityAndBorrows(reserve);
@>      uint256 totalYTokens = IERC20(reserve.yTokenAddress).totalSupply();

        if (totalYTokens == 0 || totalLiquidity == 0) {
            return PRECISION;
        }
        return totalLiquidity * (PRECISION) / (totalYTokens);
    }
}
```

The absence of a minimum output parameter allows MEV bots to front-run redemption transactions by temporarily altering the pool's liquidity state through coordinated deposits/borrows, resulting in unfavorable exchange rates for users.

### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

1. **MEV bot monitors pending redeem transactions** in the mempool
2. **Attacker front-runs redemption** by either:
   - Depositing large amounts to temporarily inflate totalLiquidity
   - Borrowing significant amounts to reduce availableLiquidity
3. **Exchange rate calculation** in `LendingPool._redeem()` uses manipulated reserve/yToken ratio
4. **User's redemption executes** at unfavorable rate due to artificial liquidity changes
5. **Attacker reverses position** after transaction confirmation, profiting from rate differential

### Impact

The redeeming user suffers loss of expected value per transaction due to manipulated exchange rates. MEV bots gain this value difference through strategic front-running, while protocol users experience consistent value erosion during redemption operations. Over multiple transactions, this could compound to significant losses for frequent users.

### PoC

_No response_

### Mitigation

Add slippage protection to the redeem function by:

1. **Introducing a minimum output parameter** in the redeem interface:
```solidity
function redeem(
    address underlyingAsset,
    uint256 yAssetAmount,
    address to,
    uint256 minAmount
) external returns (uint256);
```

2. **Implementing validation check** in the redemption logic:
```solidity
require(
    underlyingTokenAmount >= minAmount,
    "Insufficient output amount"
);
```

3. **Updating dependent interfaces** (ILendingPool) to include the new parameter

This allows users to specify their minimum acceptable return based on current market conditions, preventing unexpected losses from price manipulation between transaction submission and execution.
