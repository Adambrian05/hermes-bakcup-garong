# Attacker can manipulate strategy token rates through unprotected withdrawals


## Summary
The `collectFees()` function in `Strategy.sol` lacks slippage protection when withdrawing liquidity from vesting positions. This vulnerability allows attackers to manipulate the token0/token1 rate through liquidations and sandwich attacks on protocol fee updates, potentially destabilizing the strategy's token ratios.

## Root Cause
In [`Strategy.sol#L159-L181`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L159-L181), the `collectFees()` function calls `_withdrawPartOfVestingPosition()` without slippage protection:

```solidity
    function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0) collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(secondaryPosition.tickLower, secondaryPosition.tickUpper);
        }
        if (ongoingVestingPosition) {
            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
        }

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = (afterBal0 - preBal0) * protocolFee / 10_000;
        uint256 protocolFees1 = (afterBal1 - preBal1) * protocolFee / 10_000;

        if (protocolFees0 > 0) IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0) IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
->          _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }
```

The `_withdrawPartOfVestingPosition()` function removes liquidity without any price checks:

```solidity
    function _withdrawPartOfVestingPosition() internal {
        if (vestPosition.lastUpdate == block.timestamp) return;
        VestingPosition memory vp = vestPosition;

        uint256 lastValid = block.timestamp < vp.endTs ? block.timestamp : vp.endTs;

        uint128 liquidityToRemove = lastValid == vp.endTs
            ? vp.remainingLiquidity
            : uint128(vp.initialLiquidity * (lastValid - vp.lastUpdate) / (vp.endTs - vp.startTs));

        _removeFromPosition(liquidityToRemove, vp.tickLower, vp.tickUpper);

        vp.remainingLiquidity -= liquidityToRemove;
        vp.lastUpdate = lastValid;

        vestPosition = vp;

        if (lastValid == vestPosition.endTs) ongoingVestingPosition = false;
    }
```

This vulnerability is compounded by two factors:

1. `Leverager.sol` calls `collectFees()` during liquidations:
```solidity
    modifier collectFees(uint256 _id) {
        Position memory up = positions[_id];
        address strat = IVault(up.vault).strategy();
->      IStrategy(strat).collectFees();
        _;
    }
```

2. `setProtocolFee()` calls `collectFees()` without protection:
```solidity
    function setProtocolFee(uint256 _protocolFee) external onlyOwner {
        require(_protocolFee <= 1500, "protocol fee can't be higher than 15%");
->      collectFees();
        protocolFee = _protocolFee;
    }
```

## Internal pre-conditions
1. Active vesting position exists with significant liquidity
2. Liquidatable leveraged position exists in the system
3. Protocol fee update is pending

## External pre-conditions
1. Time has elapsed since last fee collection
2. Pool has sufficient liquidity for price manipulation
3. Attacker has access to flash loan capital

## Attack Path
### Attack Vector 1: Liquidation Manipulation
1. Attacker identifies liquidatable position
2. Uses flash loan to manipulate Uniswap pool price
3. Triggers liquidation which calls `collectFees()`
4. Vesting position liquidity is withdrawn at manipulated price
5. Attacker repays flash loan and restores price
6. Strategy's token ratio is now skewed from normal rate

### Attack Vector 2: Protocol Fee Sandwich
1. Attacker monitors for `setProtocolFee` transactions
2. Front-runs with price manipulation
3. Owner's `setProtocolFee` executes, calling `collectFees()`
4. Vesting position liquidity is withdrawn at manipulated price
5. Attacker back-runs to restore price
6. Strategy's token ratio is permanently affected

## Impact
The vulnerability leads to:
1. Permanent deviation from intended strategy token ratios
2. Loss of value for strategy participants
3. Potential for repeated exploitation during each fee collection
4. Increased risk during high volatility periods

## Mitigation
1. Add slippage protection to `_withdrawPartOfVestingPosition()`
2. Implement price deviation checks before withdrawals
3. Add cool-down period for protocol fee updates
4. Consider using time-weighted average prices for withdrawals
