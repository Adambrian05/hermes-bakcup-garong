# Unrevoked Approvals When Changing Swap Router

### Summary

When changing the swap router via the setSwapRouter function, the contract does not revoke existing unlimited approvals given to the old swap router. This leaves an open window where a compromised or malicious old router could drain tokens from the contract.

-> https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L547

### Root Cause

The vulnerability stems from using forceApprove to grant unlimited approvals to the swap router without revoking the previous approvals when the router is changed. As a result, the old router continues to have spending rights indefinitely.

### Internal Pre-conditions

The contract must have previously set unlimited approvals to a swap router.
The old router retains those approvals after the new router is set.

### External Pre-conditions

An external attacker must compromise or exploit the old swap router.
The compromised router can interact with the contract to use the lingering allowances.

### Attack Path

-> The contract owner updates the swap router to a new address without revoking approvals from the old router.
-> An attacker compromises or gains control of the old swap router.
-> The attacker uses the lingering approvals to transfer tokens from the contract to their own address.

### Impact

-> Fund Theft: The attacker could drain tokens that were approved for swap operations.
-> Increased Attack Surface: Continued unlimited approval increases the risk of unforeseen vulnerabilities in the old router being exploited.

### PoC

_No response_

### Mitigation

Before updating the swap router address, revoke the existing approvals for the old router. For example:

```solidity 

IERC20(token0).forceApprove(oldRouter, 0);
IERC20(token1).forceApprove(oldRouter, 0);


```

Then, set the new swap router and grant approvals as necessary. This ensures that only the current, trusted swap router has spending rights.
