# Incorrect tick range for vesting position fee collection

### Summary

In the `collectFees()` function of the `Strategy.sol` contract, there is an issue where fees for vesting positions are collected using an incorrect tick range. The function uses `vestPosition.tickLower` but pairs it with `mainPosition.tickUpper` instead of `vestPosition.tickUpper`. This can lead to fees being collected wrongly from vesting positions.

### Root Cause

When a vesting position is created in `addVestingPosition()`, its tick range is copied from the main position at that time:

```solidity
    function addVestingPosition(uint256 amount0, uint256 amount1, uint256 _vestDuration) external onlyVault {
        collectFees(); // we collect fees first, in case there hasn't been a call since previous vested position ended
        require(!ongoingVestingPosition, "there's a currently ongoing VestingPosition");

        _requirePriceWithinRange();
        VestingPosition memory vp;

        vp.tickLower = mainPosition.tickLower;                            // here
        vp.tickUpper = mainPosition.tickUpper;                            // here

        (uint160 sqrtPrice,,,,,,) = IUniswapV3Pool(pool).slot0();
        uint128 liquidity = LiquidityAmounts.getLiquidityForAmounts(
            sqrtPrice,
            TickMath.getSqrtRatioAtTick(vp.tickLower),
            TickMath.getSqrtRatioAtTick(vp.tickUpper),
            amount0,
            amount1
        );

        vp.initialLiquidity = liquidity;
        vp.remainingLiquidity = liquidity;

        IUniswapV3Pool(pool).mint(address(this), vp.tickLower, vp.tickUpper, liquidity, "");

        vp.startTs = block.timestamp;
        vp.lastUpdate = block.timestamp;
        ongoingVestingPosition = true;
        vp.endTs = block.timestamp + _vestDuration;

        vestPosition = vp;
    }
```

However, during rebalancing, the main and secondary positions' ticks are updated while the vesting position's ticks remain fixed. The `rebalance()` function first removes liquidity via the `_removeLiquidity()` function, then takes `tick` from the Uniswap's `slot0`: `IUniswapV3Pool(pool).slot0();` and after recalculates the main position's ticks via the `_setMainTicks(tick);` function:

```solidity
    function rebalance() public onlyRebalancer {
        require(block.timestamp - lastRebalance >= rebalanceInterval, "too soon since last rebalance");

        _requirePriceWithinRange(); // we verify that the pool's price is currently not manipulated
        collectFees();

        _removeLiquidity();
        (uint256 amount0, uint256 amount1) = idleBalances();

        (uint160 sqrtPriceX96, int24 tick,,,,,) = IUniswapV3Pool(pool).slot0();

        _setMainTicks(tick);                                    // here
        (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);

        _setSecondaryPositionsTicks(tick);
        _addLiquidityToSecondaryPosition(sqrtPriceX96, amount0, amount1);
        lastRebalance = block.timestamp;
    }
```

Here is how thr `_setMainTicks()` works:

```solidity
    function _setMainTicks(int24 tick) internal {
        int24 halfWidth = int24(positionWidth / 2);
        int24 modulo = tick % tickSpacing;
        if (modulo < 0) modulo += tickSpacing; // if tick is negative, modulo is also negative
        bool isLowerSided = modulo < (tickSpacing / 2);

        int24 tickBorder = tick - modulo;
        if (!isLowerSided) tickBorder += tickSpacing;
        mainPosition.tickLower = tickBorder - halfWidth;              // here
        mainPosition.tickUpper = tickBorder + halfWidth;              // here

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

Since the main position is rebalanced and its ticks change over time, while the vesting position maintains its original tick range, using `mainPosition.tickUpper` for the vesting position's fee collection is incorrect and creates a position mismatch.

The `collectPositionFees()` functions calls Uniswap V3 pool's `burn()` with amount equal to 0 and then `collect()`:

```solidity
    function collectPositionFees(int24 tickLower, int24 tickUpper) internal {
        IUniswapV3Pool(pool).burn(tickLower, tickUpper, 0);
        IUniswapV3Pool(pool).collect(address(this), tickLower, tickUpper, type(uint128).max, type(uint128).max);
    }
```

And the [burn()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L517-L543) function of the `UniswapV3Pool.sol` is doing its calculations using the ticks via the [_modifyPosition()](https://github.com/Uniswap/v3-core/blob/d8b1c635c275d2a9450bd6a78f3fa2484fef73eb/contracts/UniswapV3Pool.sol#L306-L372) function:

```solidity
    function burn(
        int24 tickLower,
        int24 tickUpper,
        uint128 amount
    ) external override lock returns (uint256 amount0, uint256 amount1) {
        (Position.Info storage position, int256 amount0Int, int256 amount1Int) =
            _modifyPosition(                                               // here
                ModifyPositionParams({
                    owner: msg.sender,
                    tickLower: tickLower,
                    tickUpper: tickUpper,
                    liquidityDelta: -int256(amount).toInt128()
                })
            );

        amount0 = uint256(-amount0Int);
        amount1 = uint256(-amount1Int);

        if (amount0 > 0 || amount1 > 0) {
            (position.tokensOwed0, position.tokensOwed1) = (
                position.tokensOwed0 + uint128(amount0),
                position.tokensOwed1 + uint128(amount1)
            );
        }

        emit Burn(msg.sender, tickLower, tickUpper, amount, amount0, amount1);
    }
```

`_modifyPosition(ModifyPositionParams memory params)` is an internal function that handles the actual modification of a position's liquidity. It takes a `ModifyPositionParams` struct as input, which contains the `owner`, `tickLower`, `tickUpper`, and `liquidityDelta`.

So in the `collectFees()` function of the `Yieldoor` `Strategy` contract, the `tickUpper` for the vesting position is incorrect, this means the `burn()` function in the `UniswapV3Pool` contract will calculate the fees based on the incorrect `tickUpper`.

### Internal Pre-conditions

The main pool's token composition needs to be changed, it can be e.g. due to the swaps, and it needs to be rebalanced.

### External Pre-conditions

If even no one, the bot will rebalance, so the project just needs to live its own life.

### Attack Path

This is a wrong calculation, so there is no attack here.

### Impact

Fees might be collected from an unintended range, potentially leading to overestimation or underestimation of the vesting position's fees.
