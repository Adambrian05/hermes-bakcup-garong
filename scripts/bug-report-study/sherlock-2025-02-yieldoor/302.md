# Potential Price Feed Manipulation

### Summary

Currently The code only uses one data source i.e chainlink for Price update while ChainLink is secure. There are still risks associated with using one Data source since its just one it can be easily manipulated. Also the code doesn't consider timeouts or any other failure with chainlink. 

### Root Cause

   function getPrice(address asset) public view returns (uint256 price) {
        Data memory data = pricefeeds[asset];
        if (data.feedType == TypePriceFeed.CHAINLINK) return _getChainlinkPrice(data);
    }

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/PriceFeed.sol#L52-L63

### Internal Pre-conditions

oracle failures, timeouts or Oracle Manipulation

### External Pre-conditions

If the price feed used by yielddoor becomes manipulated, attackers could manipulate prices to cause incorrect borrow calculations, leading to liquidation or over-borrowing.

### Attack Path

1. Attacker detects that only one price Oracle is used to determine price without any fallback
2. Attacker triggers Oracle failure and causes pricefeed to use outdated price. 
3. Since Pricefeed doesn't have any fallback function attacker triggers liquidation or over-borrowing

### Impact

Atackers could manipulate prices to cause incorrect borrow calculations, leading to liquidation or over-borrowing.

### PoC

_No response_

### Mitigation

Implement a robust PriceFeed that uses Chainlink as primary oracle, and Tellor as fallback or any other decentralized price oracle. It should contain logic for
switching oracles based on oracle failures, timeouts, and conditions for returning to the primary Chainlink oracle. This ensures that the pricefeed is ready for any failure or manipulation whatever
