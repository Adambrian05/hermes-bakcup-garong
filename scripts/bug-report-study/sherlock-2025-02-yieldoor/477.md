# Incorrect Redemption Due to Stored Balance State

### Summary

**The LendingPool contract's reliance on an internally tracked balance variable rather than actual token balances will cause users to receive incorrect amounts during redemption, as attackers can manipulate the balance tracking mechanism without affecting actual token balances.**

### Root Cause

In `LendingPool.sol`, the [`_redeem`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L134C5-L154C6) function uses `reserve.underlyingBalance` to calculate redemption amounts instead of checking the actual balance of the yToken contract:

```solidity
    function _redeem(address underlying, uint256 yAssetAmount, address to) internal returns (uint256) {
        DataTypes.ReserveData storage reserve = getReserve(underlying);
        // update states
        reserve.updateState();

        // calculate underlying tokens using yTokens
        uint256 underlyingTokenAmount = reserve.yTokenToReserveExchangeRate() * yAssetAmount / PRECISION;

        require(underlyingTokenAmount <= reserve.availableLiquidity(), "not enough available liquidity");

        // burn yTokens and transfer the underlying tokens to receiver
        IyToken(reserve.yTokenAddress).burn(to, yAssetAmount, underlyingTokenAmount);

        // update the interest rate after the redeem

        reserve.underlyingBalance -= underlyingTokenAmount;
        reserve.updateInterestRates();

        return (underlyingTokenAmount);
    }

```

The issue is that `reserve.underlyingBalance` only gets updated through specific functions like deposit, withdraw, borrow, and repay. If tokens are transferred directly to the yToken contract through other means (direct transfers, etc.), there will be a discrepancy between `reserve.underlyingBalance` and the actual token balance.

### Internal Pre-conditions

1. The lending pool must have at least one initialized reserve with deposits
2. Tokens are transferred directly to the yToken contract, bypassing the LendingPool's accounting functions

### External Pre-conditions

.

### Attack Path

1. Attacker or any user sends tokens directly to the yToken contract (via direct transfer)
2. The actual token balance of the yToken contract increases, but `reserve.underlyingBalance` in the LendingPool remains unchanged
3. When a user redeems their yTokens, they receive an amount based on the outdated `reserve.underlyingBalance` value
4. The user receives less tokens than they should based on their share of the actual reserves

### Impact

Users redeeming their yTokens receive fewer tokens than they are entitled to based on their share of the actual reserves. This creates an unfair distribution of assets and effectively causes users to lose a portion of their funds. In the PoC, we demonstrated that a user(user1) loses approximately 33% of their entitled tokens.

### Mitigation

To fix this issue, the LendingPool should use the actual token balance in the yToken contract when calculating redemption amounts rather than relying on the internally tracked `reserve.underlyingBalance`.

Here's a suggested fix for the `_redeem` function:

```solidity
function _redeem(address underlying, uint256 yAssetAmount, address to) internal returns (uint256) {
    DataTypes.ReserveData storage reserve = getReserve(underlying);
    reserve.updateState();
    
    // Get total yToken supply and actual underlying balance
    uint256 totalYTokenSupply = IERC20(reserve.yTokenAddress).totalSupply();
    uint256 actualUnderlyingBalance = IERC20(underlying).balanceOf(reserve.yTokenAddress);
    
    // Calculate proportion of underlying tokens based on actual balance
    uint256 underlyingTokenAmount = yAssetAmount * actualUnderlyingBalance / totalYTokenSupply;
    
    require(underlyingTokenAmount <= actualUnderlyingBalance, "not enough available liquidity");
    
    // burn yTokens and transfer the underlying tokens to receiver
    IyToken(reserve.yTokenAddress).burn(to, yAssetAmount, underlyingTokenAmount);
    
    // update the interest rate after the redeem
    reserve.underlyingBalance = actualUnderlyingBalance - underlyingTokenAmount;
    reserve.updateInterestRates();
    
    return (underlyingTokenAmount);
}
```
