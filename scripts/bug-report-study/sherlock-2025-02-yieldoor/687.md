# Wrong Secondary Position boundaries definition due to wrong price calculation

### Summary

Price function doesn't count with tokens with different decimals to calculate the price.
[https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L360](url)


### Root Cause

price function is getting the sqrtPriceX96 and then do this math:

(sqrtPriceX96 *  1e15/ 2 ** 96) ** 2

Which is correct to get the price of tokens with same decimals number, however it doesn't count with token with different decimals.

### Internal Pre-conditions

n/a

### External Pre-conditions

token0 and token1 with different decimals

### Attack Path

n/a

### Impact

According to the PoC scenario, _price will be much higher than it should be, therefore bal0in1 will always be higher than bal1 and will always enter the else condition, meaning that secondary position always will be defined in the upper side of the main position regardless of the balances of token0 or token1.

This directly impacts one of the main purposes of this contract which is to avoid inactive balances by using secondary positions, but if the secondary position is defined incorrectly, we are basically going to have scenarios where the remaining token will be in less favorable secondary positions, until the point of becoming useless.

[https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L373-L379](url)

### PoC

If we say that token0 is USDC and token1 is WETH this should be the math:
price = WETH/ETH 
1 WETH represents 10^18 and WETH in the contract whereas USDC is 10^6. Therefore, USDC has 6 decimals and WETH has 18.

WETH*10^18 / USDC*10^6 = price
WETH/USDC * 10^18/10^6 = price
WETH/ETH = price / 10^18/10^6
WETH/ETH = price / 10^12

Therefore in this scenario price function is returning a much higher value than it should be, affecting the definition of the secondary position boundaries.

### Mitigation

Add decimals token to the price calculation as it is shown in the PoC section.
