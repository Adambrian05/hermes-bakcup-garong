# Improper Validation in setBorrowingRateConfig function Allows Invalid Interest Rate Curves

### Summary

The `setBorrowingRateConfig` function in `LendingPool` Contract lacks proper validation, allowing misconfigurations that break the borrowing rate model. Specifically:
`utilizationA` can be greater than or equal to `utilizationB`, breaking the expected interest rate curve.
`borrowingRateA` can be greater than `borrowingRateB`, leading to a decreasing rate instead of an increasing one.
`maxBorrowingRate` is not checked against `borrowingRateB`, potentially capping rates incorrectly.
This misconfiguration can cause unfair borrower incentives, protocol instability, and financial losses for lenders.

### Root Cause

The function `setBorrowingRateConfig` on https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L241C3-L259C6 allows setting an invalid borrowing curve due to missing validation checks.
The expected correct model should satisfy:
`utilizationA `< `utilizationB `(ensuring a logically increasing utilization curve).
`borrowingRateA `< `borrowingRateB `(ensuring increasing rates as utilization increases).
`borrowingRateB `< `maxBorrowingRate `(ensuring a valid upper bound).
Since the function does not enforce these conditions, the protocol can be configured with an invalid interest rate curve, leading to incorrect loan pricing and risk exposure.

### Internal Pre-conditions

These conditions must be true within the smart contract for the bug to occur:
1.The contract allows the admin to call `setBorrowingRateConfig`.
2.The function does not check for logical inconsistencies in the borrowing rate parameters.
3.The borrowing curve is expected to be non-decreasing but isn't enforced.

### External Pre-conditions

These conditions must be true externally for the bug to be exploitable:
1.A protocol admin (or governance-controlled entity) must call `setBorrowingRateConfig`.
2.The function is not restricted, allowing misconfiguration by accident or malicious intent.
3.The contract does not revert on invalid inputs, allowing an incorrect rate model to be set.

### Attack Path

A malicious or negligent admin could configure an illogical interest rate curve, leading to unfair rates:
1.Set an invalid interest rate configuration
`setBorrowingRateConfig(reserve, 9000, 30, 5000, 100, 200);`
-Issue 1: `utilizationA `(9000) > `utilizationB `(5000), which reverses the curve.
-Issue 2: `borrowingRateA `(30) < `borrowingRateB `(100), which incorrectly sets a decreasing rate.
-Issue 3: If `maxBorrowingRate `is set incorrectly, it can artificially cap borrowing rates.
2.Borrowers exploit the broken curve
-If borrowing rates decrease instead of increasing with utilization, borrowers could exploit cheaper loans at high utilization.
-If rates are misconfigured too high, borrowing could become impossible, freezing lending activity.
3.Protocol experiences financial losses
-Lenders lose yield due to incorrect rate calculations.
-Overly cheap borrowing rates could cause excessive debt accumulation, leading to bad debt risk.

### Impact

This vulnerability allows for mispricing of borrowing rates, potentially leading to:
-Unfair borrowing incentives (e.g., getting cheap loans at high utilization).
-Lenders losing yield due to underpriced loans.
-Protocol insolvency risks if excessive cheap borrowing leads to bad debt accumulation.
-Possible governance attack vector if malicious actors influence rate settings.

### Mitigation

Introduce validation checks in setBorrowingRateConfig to enforce a valid rate model:

```solidity
require(utilizationA < utilizationB, "utilizationA must be less than utilizationB");
require(utilizationA > 0 && utilizationB <= 10_000, "Utilization out of bounds");
require(borrowingRateA < borrowingRateB, "borrowingRateA must be less than borrowingRateB");
require(borrowingRateB < maxBorrowingRate, "borrowingRateB must be less than maxBorrowingRate");
require(maxBorrowingRate <= 10_000, "maxBorrowingRate out of bounds");
```
