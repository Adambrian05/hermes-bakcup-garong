# A malicious actor will exploit the miscalculation, impacting leveraged position holders

### Summary

The incorrect usage of the wrong variable in the repayment calculation will cause an erroneous repayment amount for leveraged position holders as a malicious actor will trigger a withdrawal transaction that exploits the bug to either over-repay or under-repay funds.

### Root Cause

- In **Leverager.sol** within the `withdraw` [function](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L232), the repay calculation for token1 withdrawals is implemented as:  
  ```solidity
  uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
  ```  
  instead of using `amountOut1`. This typographical mistake leads to the use of the wrong token balance, causing an incorrect repayment amount.


### Internal Pre-conditions

1. The withdraw function is invoked on a position where the borrowed token is `up.token1`.  
2. The function receives distinct values for `amountOut0` and `amountOut1`, such that `amountOut1` is non-zero and different from `amountOut0`.  
3. The repayment calculation branch for token1 withdrawals is executed, triggering the erroneous ternary operation.


### External Pre-conditions

1. No external protocol conditions or oracle manipulations are required; the vulnerability stems entirely from the internal logic of the contract.


### Attack Path

1. An attacker (or malicious user) initiates a withdrawal on a leveraged position where the borrowed token is `up.token1`.  
2. The contract executes the faulty repay calculation, using `amountOut0` instead of `amountOut1` in the conditional.  
3. Due to the miscalculation, the repayment amount is determined incorrectly, leading to either an over-repayment or under-repayment scenario.  
4. The attacker exploits this discrepancy to withdraw funds inappropriately, causing a potential loss of assets from the contract.


### Impact

Leveraged position holders suffer an approximate loss of funds as the miscalculation in the repay logic results in incorrect token transfers. This financial imbalance directly impacts users, as funds may be withdrawn in excess or insufficiently repaid, compromising the integrity of the protocol's accounting.


### PoC

```solidity
// PoC: Exploiting the faulty repay calculation

// Assume position with borrowed token equals up.token1, and the following balances:
// amountOut0 = 500, amountOut1 = 300, owedAmount = 400

// Incorrect calculation in the contract:
uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
// Expected correct calculation should be:
uint256 correctRepayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;

// In this scenario:
// Incorrectly computed: repayFromWithdraw = 500 (using amountOut0)
// Correctly computed: correctRepayFromWithdraw = 300 (using amountOut1)

// This discrepancy can be exploited to manipulate the repayment process,
// potentially leading to a loss of 200 units from the position holder.
```


### Mitigation

Implementing the recommended fix—using `amountOut1` consistently in the ternary operation—will ensure accurate repayment calculations and prevent potential fund loss.
