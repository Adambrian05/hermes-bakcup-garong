# Inconsistent tick rounding between TWAP calculations leads to incorrect price deviation checks

## Summary
The `Strategy#checkPoolActivity` function rounds tick calculations towards zero while `Strategy#twapTick` rounds away from zero for negative values, leading to inconsistent price deviation checks that could incorrectly allow or prevent rebalancing operations.

## Relevant Context
The contract implements price deviation checks to ensure rebalancing only occurs when prices are stable. This involves comparing:
1. TWAP vs spot price deviation (`_priceWithinRange`)
2. Consecutive observation tick deviations (`checkPoolActivity`) 

Both checks use tick calculations but implement different rounding behaviors.

## Root Cause
In `Strategy#checkPoolActivity`, tick calculations use integer division which rounds towards zero:

[`Strategy.sol#L326`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L326)

```solidity
tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));
```

However, `Strategy#twapTick` implements explicit rounding away from zero for negative values:

[`Strategy.sol#L351-L352`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L351-L352)

```solidity
tick = int24(tickCumulativesDelta / int32(twap));
if (tickCumulativesDelta < 0 && (tickCumulativesDelta % int32(twap) != 0)) tick--;
```

This inconsistency means the same underlying price movement could be rounded differently between the two functions.

## Attack Path

1. Price moves such that `tickCumulativesDelta` is negative and not perfectly divisible by the time interval
2. `twapTick` rounds down (away from zero) due to explicit check
3. `checkPoolActivity` rounds up (towards zero) due to integer division
4. The difference between these rounded values could be larger than intended, causing:
   - False positives: Rebalancing prevented when it should be allowed
   - False negatives: Rebalancing allowed when it should be prevented

## Impact Explanation
Medium. While this doesn't lead to direct fund loss, it could:
1. Prevent legitimate rebalancing operations, reducing strategy efficiency
2. Allow rebalancing during unstable price conditions, potentially leading to suboptimal position adjustments
3. Create inconsistent behavior that violates the intended price stability checks

## Proof of Concept

Consider the following scenario:
1. Time interval = 300 seconds
2. `tickCumulativesDelta` = -1501
3. In `twapTick`:
   - -1501/300 = -5.003333...
   - Rounds to -6 due to explicit negative rounding
4. In `checkPoolActivity`:
   - -1501/300 = -5.003333...
   - Rounds to -5 due to integer division
5. The 1 tick difference could incorrectly trigger or prevent deviation checks

## Recommendation
Standardize the rounding behavior across both functions. Since Uniswap V3's own TWAP calculations round negative values away from zero, that should be the standard:

[`Strategy.sol#L326`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L326)

```diff
- tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));
+ int56 tickDelta = nextCumulativeTick - tickCumulative;
+ int56 timeDelta = int56(uint56(nextTimestamp - timestamp));
+ tick = int24(tickDelta / timeDelta);
+ if (tickDelta < 0 && (tickDelta % timeDelta != 0)) tick--;
```
