# Incorrect slippage protection in `deposit`

### Summary

Users might suffer loses during deposits because:
1) Assets and shares calculations depend on `IStrategy(strategy).balances()`, which uses spot prices from `IUniswapV3Pool(pool).slot0()`;
2) Slippage protection is implemented incorrectly - users may be charged more than they expected, and there is no min amount check of shares received.

### Root Cause

[Link](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L48-L72)

Users has no control over `share` amount received, and `depositAmount` only checks for lower border, which is incorrect. Users should have the ability to specify max tokens amount they are willing to spend. Also some protocols interacting with `Vault.sol` might have unlimited allowance to the vault, and they might be unexpectedly overcharged and receive unexpectedly small `share` amount.
```solidity
 require(shares > 0, "shares cant be 0");
        require(depositAmount0 >= amount0Min, "slippage0");
        require(depositAmount1 >= amount1Min, "slippage1");
```
Also `IStrategy(strategy).balances()`, which is used to calculate deposit amounts, use spot prices from `IUniswapV3Pool(pool).slot0()`, which is can be easily manipulated. Combining these 2 factors, depositors are not protected from unexpected slippage.

For comparison:
1) `withdraw()` function burns exact amount of shares specified, and allows users to specify min amounts received;
2) All other actions in other contracts can be done when pool's price is within the range.

### Impact

Users might suffer loses during deposits because lack of slippage protection.

### Mitigation

1) Allow users to deposit only during calm periods by adding `_requirePriceWithinRange()` modifier;
2) Allow user to specify max deposit amount sent / min share amount received.
