# Missing Slippage Protection Allows MEV Bots to Steal Funds from Depositors Through Exchange Rate Manipulation

### Summary

The missing slippage protection in `LendingPool.deposit()` will cause a direct loss of funds for depositors as MEV bots will manipulate exchange rates through front-running/back-running attacks. The real-time exchange rate calculation based on mutable pool state allows attackers to artificially depress yToken minting rates during user deposits, especially when users deposit during volatile periods in low liquidity pool.

### Root Cause

In function `LendingPool.deposit()` ([`LendingPool.sol#L70-L77`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L70-L77)), the deposit mechanism lacks slippage protection parameters, creating vulnerability to MEV sandwich attacks. The root cause is:

1. The exchange rate calculation in function `ReserveLogic.reserveToYTokenExchangeRate()` ([`ReserveLogic.sol#L78-L86`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol#L78-L86)) uses real-time pool state (totalLiquidity and yToken supply)
2. The deposit function accepts deposits at whatever current exchange rate exists, with no minimum output guarantee

```solidity
contract LendingPool is ILendingPool, Ownable, ReentrancyGuard {
    function deposit(address asset, uint256 amount, address onBehalfOf)
        public
        notPaused
        nonReentrant
        returns (uint256 yTokenAmount)
    {
        yTokenAmount = _deposit(asset, amount, onBehalfOf);
    }
    
    function _deposit(address asset, uint256 amount, address onBehalfOf) internal returns (uint256 yTokenAmount) {
        // ...
@>      uint256 exchangeRate = reserve.reserveToYTokenExchangeRate();

        IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);

        // Mint yTokens for the user
        yTokenAmount = amount * exchangeRate / (PRECISION);
        // ...
    }
}
```

```solidity
library ReserveLogic {
    function reserveToYTokenExchangeRate(DataTypes.ReserveData storage reserve) internal view returns (uint256) {
@>      (uint256 totalLiquidity,) = totalLiquidityAndBorrows(reserve);
@>      uint256 totalYTokens = IERC20(reserve.yTokenAddress).totalSupply();

        if (totalYTokens == 0 || totalLiquidity == 0) {
            return PRECISION;
        }
        return totalYTokens * PRECISION / totalLiquidity;
    }
}
```

This allows attackers to manipulate the exchange rate through:
- Front-running deposits with large transactions to alter pool ratios
- Back-running withdrawals to profit from temporary rate changes

The core mistake is the protocol's design choice to omit slippage protection in deposit flows, despite handling user funds in volatile liquidity pool environments.

### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

1. **Attacker monitors mempool for deposit transactions** targeting low-liquidity reserves
2. **Attacker front-runs victim's deposit** with a large deposit transaction, increasing totalLiquidity before victim's transaction
3. **Victim's deposit executes** at manipulated exchange rate, receiving fewer yTokens than expected
4. **Attacker back-runs with withdrawal** to profit from temporary rate change
5. **Normal users receive fewer yTokens** than expected value in low liquidity conditions

### Impact

The protocol suffers loss of trust as depositors receive fewer yTokens than expected, especially when users deposit during volatile periods in low liquidity pool. All depositors are affected with no protection against MEV extraction.

### Mitigation

Add slippage protection to deposit flow through:

1. **Parameterized deposit function**:
```solidity:yieldoor/src/LendingPool.sol
function deposit(
    address asset, 
    uint256 amount, 
    address onBehalfOf,
    uint256 minYTokenAmount // New parameter
) public notPaused nonReentrant returns (uint256 yTokenAmount) {
    yTokenAmount = _deposit(asset, amount, onBehalfOf);
    require(yTokenAmount >= minYTokenAmount, "Insufficient yTokens received");
}
```

2. **Frontend integration**:
- Calculate expected yTokens using current reserves state
- Apply safety margin (0.1-0.5%) based on pool liquidity
- Pass calculated minimum to contract

3. **Interface update**:
```solidity:yieldoor/src/interfaces/ILendingPool.sol
function deposit(
    address asset, 
    uint256 amount, 
    address onBehalfOf,
    uint256 minYTokenAmount
) external returns (uint256 yTokenAmount);
```

This forces MEV bots to compete on price improvement rather than extraction, while maintaining protocol functionality for legitimate users.
