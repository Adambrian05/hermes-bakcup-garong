# Funds Lock Risk Due to State Update Before Transfer in Borrow Function

### Summary

The `borrow` function in the `LendingPool` contract has a design flaw in the order of state updates and external calls. The current implementation decreases `reserve.underlyingBalance` before attempting to transfer the assets. If the asset transfer fails (e.g., if the receiver is blacklisted), funds will remain in the contract while the state variable has already been updated, causing these funds to become inaccessible for future borrowing.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L170-L176

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol#L36-L38

### Root Cause

The root cause is that the `borrow` function violates the Checks-Effects-Interactions (CEI) pattern. The function updates state variables before successfully completing the external call:

```solidity:yieldoor/src/LendingPool.sol
// ... existing code ...
reserve.underlyingBalance -= amount;
// The receiver of the underlying tokens must be the farming contract (_msgSender())
IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
// ... existing code ...
```

### Internal Pre-conditions

None


### External Pre-conditions

- The transfer operation fails, for example:
  - The receiver is blacklisted by the token
  - The token implements some form of transfer restriction
  - The token contract is paused or malfunctioning

### Attack Path

1. User A borrows 1000 USDC
2. The `borrow` function executes, reducing `reserve.underlyingBalance` by 1000
3. When calling `transferUnderlyingTo`, the transfer fails due to blacklisting or other reasons
4. Although the contract actually still has 1000 USDC, `availableLiquidity()` returns 0
5. User B attempts to borrow, but fails with "not enough available liquidity" even though funds are present

### Impact

Fund lockup, Some borrowable assets may be locked in the contract, preventing other users from borrowing even though the actual token balance is sufficient. This can lead to a denial of service for borrowers.



### PoC

1. User A borrows 1000 USDC.
2. The `underlyingBalance` is decremented by 1000.
3. The `transferUnderlyingTo` fails due to User A being blacklisted or othor reason.
4. The contract's `underlyingBalance` is now 0, but the actual balance still has 1000 USDC.
5. User B attempts to borrow 500 USDC but is unable to due to the `underlyingBalance` being 0.



### Mitigation

Follow the Checks-Effects-Interactions pattern by executing the external call first and updating state after success:

```solidity:yieldoor/src/LendingPool.sol
// ... existing code ...
// Execute external call first
IyToken(reserve.yTokenAddress).transferUnderlyingTo(_msgSender(), amount);
// Update state after successful transfer
reserve.underlyingBalance -= amount;
reserve.totalBorrows += amount;
// ... existing code ...
```
