# Incorrect formula for converting tick value to the 1e30 price representation

### Summary

Incorrect price calculation in price() and twapPrice() functions leads to liquidation errors, incorrect fees, and misconfigured secondary positions, potentially causing unfair losses or gains for users and the protocol.

### Root Cause

In both price and twapPrice functions of the Strategy contract, incorrect calculation is used to convert the X96 format to the 1e30 precision because the calculation should also take into consideration the decimals of both token0 and token1:
```solidity
function price() public view returns (uint256 _price) {
        (uint160 sqrtPriceX96,,,,,,) = IUniswapV3Pool(pool).slot0();
        _price = FullMath.mulDiv(sqrtPriceX96, 1e15, 2 ** 96) ** 2;
}
```
```solidity 
function twapPrice() public view returns (uint256) {
        int24 tick = twapTick();
        uint160 sqrtPrice = TickMath.getSqrtRatioAtTick(tick);
        return (FullMath.mulDiv(sqrtPrice, 1e15, 2 ** 96) ** 2);
}
```
Specifically, the problem that I refer to is in this calculation:

```solidity
FullMath.mulDiv(sqrtPriceX96, 1e15, 2 ** 96) ** 2
```
which is used in both functions.

### Attack Path

- Attack Path 1:
1. The rebalancer calls the rebalance function.
2. Execution comes to _setSecondaryPositionsTicks().
3. The price inside the _setSecondaryPositionsTicks() function will be incorrectly calculated, leading to incorrectly setting the secondary positions' lower and upper ticks.
4. After that, in the rebalance function, the _addLiquidityToSecondaryPosition() function is invoked, where due to incorrect lower and upper ticks, the wrong liquidity could be added.

- Attack Path 2:
1. A user wants to liquidate a certain position (which shouldn't be liquidatable at the moment), so they call the liquidatePosition() function.
2. Inside the liquidate function, the isLiquidatable() function is called, which retrieves the twapPrice from Vault and passes it as an argument to _calculateTokenValues(). Since the twapPrice is incorrect, the result of _calculateTokenValues() will be incorrect as well (if one of the tokens doesn't have a price feed).
3. That would lead to an incorrect check inside isLiquidatable(), making the function return true instead of false.
4. Furthermore, twapPrice is also used in the liquidate function for calculating fees, so that calculation will also be incorrect, leading to the fee recipient receiving an incorrect fee.

### Impact

The more severe impacts are the ones that are connected to the usage of the twapPrice() function since the twapPrice() function is used in the Leverage contract (it is used through the Vault contract) and is used to get the variable called price, which is then passed as an argument to the _calculateTokenValues() function. If one of the tokens doesn't have a price feed, it will be used to calculate the token value. But since the price retrieved from twapPrice() is incorrect, the result of _calculateTokenValues() will be completely incorrect. If we check where the _calculateTokenValues() function is used in the contract, we can conclude that the impacts are that some positions could be liquidatable even when they, in reality, shouldn't be. This can also happen in reverse cases.

Also, since the product of that function is used for calculating fees, the fee would be incorrect. All of these issues would result just because of the incorrect twapPrice conversion and failing to truly represent it in 1e30 decimals. This could lead to users losing their funds if they get liquidated or not being liquidated even when they should be. Additionally, the feeRecipient could fail to get the proper fee, resulting in being overpaid or underpaid. (also, the result of the _calculateTokenValues() will be used in the openLeveragePosition function, which could cause some functions to fail.)

Since the price() function is used in the _setSecondaryPositionsTicks() function in the Strategy contract to determine which values would be set for the upper and lower tick of the secondary position, it could lead to incorrect setting of them. Also, the _setSecondaryPositionsTicks() function is used every time rebalancing occurs, so this problem could happen consistently.

Furthermore, since the lower and upper tick could be set incorrectly, and their values are used as arguments in _removeFromPosition throughout the contract, as well as in collectPositionFees and _addLiquidityToSecondaryPosition functions, it could lead to incorrect removal from position, incorrect collection of fees, and incorrect adding of liquidity to the secondary position. This could all lead to unfair loss/gain to the user but also affect the protocol since the collected fees would be incorrect (could lose/gain).

### PoC

Let's take, for example, the Uniswap pool used in the test files. The pool in question is the WBTC/USDC pool from the Ethereum mainnet (taking this one because is used in test, its just for proving the concept) with an address of 0x99ac8cA7087fA4A2A1FB6357269965A2014ABc35.

In this PoC, we will focus on this calculation:
```solidity
FullMath.mulDiv(sqrtPriceX96, 1e15, 2 ** 96) ** 2;
```
1. When we call slot0 from that pool, we get a sqrtPriceX96 value of 2294799014298756220246648854490.
2. Since the formula that calculates the price is FullMath.mulDiv(sqrtPriceX96, 1e15, 2 ** 96) ** 2, the calculated price will be 838938532147614095743970594561521.
3. The comment above the price function, /// @notice Returns the token0/token1 spot price in 1e30 precision, tells us that the price should have 1e30 precision. However, when we remove the 1e30 precision from the calculated price, we get 838, which is completely inaccurate and incorrect since the actual price of WBTC is around 83611.7.

### Mitigation

Consider including the number of decimals of tokens in your calculation to get the correct result.
