# Uninitialized Fee Recipient Leading to Permanent Loss of Protocol Fees


## Summary

The `Leverager` contract has a critical vulnerability where the `feeRecipient` address is never initialized or set, potentially leading to permanent loss of protocol fees if they are sent to the zero address.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L47

## Vulnerability Details
In the `Leverager` contract's liquidation function, protocol fees are transferred to a `feeRecipient` address:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L328-L329

```solidity
if (totalValueUSD > borrowedValue) {
    uint256 protocolFeePct = 1e18 * liquidationFee * (totalValueUSD - borrowedValue) / (totalValueUSD * 10_000);
    uint256 pf0 = protocolFeePct * amount0 / 1e18;
    uint256 pf1 = protocolFeePct * amount1 / 1e18;
    
    // feeRecipient is never initialized
    if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0);
    if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1);
}
```

The issue arises because:

1. The `feeRecipient` state variable is never initialized in the constructor
2. There is no function to set or update the `feeRecipient` address
3. By default, uninitialized address variables are set to `address(0)`

## Impact

### 1. Loss of Protocol Fees
- All protocol fees from liquidations will be sent to `address(0)`
- These tokens will be permanently lost and unrecoverable
- The protocol loses a critical revenue stream

### 2. Financial Impact
- If the protocol fee is set to 0.1% and a $1M position is liquidated with 10% profit:
  - Lost fees = $1,000 worth of tokens per liquidation
  - These losses accumulate with each liquidation
 
### 3. Protocol Sustainability
- Loss of protocol fees impacts:
  - Protocol revenue
  - Treasury growth
  - Long-term sustainability

## Root Cause
The root cause is the lack of proper initialization and management of the `feeRecipient` address in the contract's implementation.

## Recommended Mitigation

   - Add `feeRecipient` initialization in the constructor
   - Add a setter function with proper access control
   - Add zero-address checks

```diff
contract Leverager {
     // ...

    address public feeRecipient;

    // ...
    
-   constructor(string memory name_, string memory symbol_, address _lendingPool)
+  constructor(string memory name_, string memory symbol_, address _lendingPool, address _feeRecipient)
        Ownable(msg.sender)
        ERC721(name_, symbol_)
    {
+      require(_feeRecipient != address(0), "Invalid fee recipient");
        lendingPool = _lendingPool;
+     feeRecipient = _feeRecipient;
    }
    
+  function setFeeRecipient(address _newFeeRecipient) external onlyOwner {
+      require(_newFeeRecipient != address(0), "Invalid fee recipient");
+      feeRecipient = _newFeeRecipient;
+  }
}
```
