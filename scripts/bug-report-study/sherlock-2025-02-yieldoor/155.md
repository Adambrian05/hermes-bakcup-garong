# Liquidators have no control over the amount of protocol fee they have to pay

### Summary

`Leverager::liquidatePosition()` [gives](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L299) protocol fees according to:
`uint256 protocolFeePct = 1e18 * liquidationFee * (totalValueUSD - borrowedValue) / (totalValueUSD * 10_000);`
These prices are dependent on the price oracles, so the liquidator can be frontrunned by price updates and end up paying a much bigger fee to the protocol.

### Root Cause

In `Leverager:324`, there is no maximum fees paid by to the protocol check.

### Internal Pre-conditions

None.

### External Pre-conditions

Price update frontruns liquidator.

### Attack Path

1. Liquidator calls `Leverager::liquidatePosition()`, but gets frontrun by price updates and pays a much bigger fee to the protocol.

### Impact

Loss of funds for the liquidator.

### PoC

```solidity
uint256 totalValueUSD = _calculateTokenValues(up.token0, up.token1, amount0, amount1, price);

uint256 bPrice = IPriceFeed(pricefeed).getPrice(up.denomination);
uint256 borrowedValue = owedAmount * bPrice / ERC20(up.denomination).decimals();

if (totalValueUSD > borrowedValue) {
    // What % of the amountsOut are profit is calculated by `(totalValueUSD - borrowedUSD) / totalValueUSD`
    // Then, on top of that, we calculate the protocol fee and scale it in 1e18.

    uint256 protocolFeePct = 1e18 * liquidationFee * (totalValueUSD - borrowedValue) / (totalValueUSD 
        * 10_000);
```

### Mitigation

Add a parameter to check the max fee paid.
