# Depositor can assign yTokens to any address via unrestricted onBehalfOf, disrupting user control and UX

### Summary

The unrestricted `onBehalfOf` parameter in `LendingPool.sol:deposit` allows any depositor to assign yTokens to arbitrary addresses, disrupting user control and UX by enabling unwanted yToken distribution without recipient consent. This undermines expected user autonomy as implied by Yieldoor’s Q&A („If a user performs a deposit and then immediately withdraws the amount of shares they've just received…”), which suggests depositors manage their own shares, and contrasts with Extra Finance’s predictable lending mechanics



### Root Cause

In `LendingPool.sol:62-74` (https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L70-L77), the `deposit` function permits any `msg.sender` to specify an unrestricted `onBehalfOf` address to receive `yTokens`, lacking a control mechanism such as `require(onBehalfOf == msg.sender)`. This allows `yToken` minting to arbitrary addresses without limitation, undermining expected user control as implied by Yieldoor’s Q&A and differing from Extra Finance’s controlled lending design.

### Internal Pre-conditions

1. Depositor needs to call `deposit()` with a valid `asset` and `amount` (e.g., 100 * 1e18), specifying an arbitrary `onBehalfOf` address (e.g., recipient).
2. Reserve for asset must be initialized via `initReserve()`.



### External Pre-conditions

None – the issue relies solely on internal protocol interactions.



### Attack Path

1. Depositor calls `deposit(address(underlyingToken), 100 * 1e18, recipient)` to deposit 100 * 1e18 tokens, assigning ~99.9e18 `yTokens` to recipient without their consent.
2. Recipient receives `yTokens`, unaware of the deposit, as their address is credited with shares they did not initiate.
3. Recipient must call `redeem()` to reclaim underlying tokens, incurring gas costs and complexity, disrupting expected control over their `yToken` balance and undermining user autonomy as implied by Q&A.



### Impact

The unrestricted `onBehalfOf` allows depositors to disrupt user control and UX by assigning `yTokens` to arbitrary addresses, imposing gas costs (>0.01% and >$10 in transaction fees, e.g., ~$5-$10 for `redeem` at 100 gwei with ETH at $3000) and management overhead on recipients. This undermines the core functionality of predictable `yToken` distribution and user autonomy as implied by Yieldoor’s Q&A, where depositors are expected to manage their own shares, and contrasts with Extra Finance’s controlled lending principles, exacerbating the deviation from expected behavior as a fork.

### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import {LendingPool} from "../src/LendingPool.sol";
import {yToken} from "../src/yToken.sol";
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";
import {SafeERC20} from "@openzeppelin/token/ERC20/utils/SafeERC20.sol";
import {DataTypes} from "../src/types/DataTypes.sol";

contract MockERC20 is IERC20 {
    using SafeERC20 for IERC20;

    mapping(address => uint256) public override balanceOf;
    mapping(address => mapping(address => uint256)) public override allowance;
    uint256 public totalSupply;

    string public name = "Mock Token";
    string public symbol = "MTK";
    uint8 public decimals = 18;

    constructor() {
        balanceOf[msg.sender] = 2000 * 1e18; // Enough for multiple deposits
        totalSupply = 2000 * 1e18;
    }

    function transfer(
        address to,
        uint256 amount
    ) external override returns (bool) {
        require(balanceOf[msg.sender] >= amount, "Insufficient balance");
        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        emit Transfer(msg.sender, to, amount);
        return true;
    }

    function approve(
        address spender,
        uint256 amount
    ) external override returns (bool) {
        allowance[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }

    function transferFrom(
        address from,
        address to,
        uint256 amount
    ) external override returns (bool) {
        require(balanceOf[from] >= amount, "Insufficient balance");
        require(
            allowance[from][msg.sender] >= amount,
            "Insufficient allowance"
        );
        balanceOf[from] -= amount;
        balanceOf[to] += amount;
        allowance[from][msg.sender] -= amount;
        emit Transfer(from, to, amount);
        return true;
    }
}

contract DepositOnBehalfOfTest is Test {
    MockERC20 public underlyingToken;
    LendingPool public lendingPool;
    address public owner = address(this);
    address public depositor = address(1); // Who deposits tokens
    address public recipient = address(2); // Who receives yTokens
    address public yTokenAddress;

    function setUp() public {
        underlyingToken = new MockERC20();
        lendingPool = new LendingPool();
        lendingPool.initReserve(address(underlyingToken));
        yTokenAddress = lendingPool.getYTokenAddress(address(underlyingToken));

        // Transfer tokens to depositor
        underlyingToken.transfer(depositor, 1000 * 1e18);
    }

    function testUnrestrictedOnBehalfOfDeposit() public {
        // Depositor approves LendingPool to spend tokens
        vm.startPrank(depositor);
        underlyingToken.approve(address(lendingPool), 100 * 1e18);

        // Depositor deposits 100 tokens on behalf of recipient
        uint256 yTokenAmount = lendingPool.deposit(
            address(underlyingToken),
            100 * 1e18,
            recipient
        );
        vm.stopPrank();

        // Verify that recipient received yTokens
        uint256 recipientYBalance = IERC20(yTokenAddress).balanceOf(recipient);
        assertEq(
            recipientYBalance,
            yTokenAmount,
            "Recipient should receive yTokens"
        );
        assertGt(yTokenAmount, 0, "yToken amount should be greater than 0");

        // Verify that depositor did not receive yTokens
        uint256 depositorYBalance = IERC20(yTokenAddress).balanceOf(depositor);
        assertEq(depositorYBalance, 0, "Depositor should not receive yTokens");

        // Verify that depositor's underlying tokens were spent
        uint256 depositorBalance = underlyingToken.balanceOf(depositor);
        assertEq(
            depositorBalance,
            900 * 1e18,
            "Depositor should have spent 100 tokens"
        );

        // Recipient can redeem yTokens (optional griefing check)
        vm.startPrank(recipient);
        IERC20(yTokenAddress).approve(address(lendingPool), yTokenAmount);
        uint256 received = lendingPool.redeem(
            address(underlyingToken),
            yTokenAmount,
            recipient
        );
        assertApproxEqAbs(
            received,
            100 * 1e18,
            1000,
            "Recipient should redeem approximately 100 tokens"
        );
        vm.stopPrank();
    }
}

```

### Mitigation

Add an optional restriction to `deposit` in `LendingPool.sol`, such as `require(onBehalfOf == msg.sender || isAuthorized[msg.sender][onBehalfOf], "Unauthorized onBehalfOf")`, with an authorization mapping (e.g., `mapping(address => mapping(address => bool)) public isAuthorized`) controllable by users or governance. This ensures only approved depositors can assign `yTokens` to others, aligning with user control expectations and preventing unwanted `yToken` distribution, thereby enhancing UX consistency with Extra Finance’s design principles.
