# Protocol will witness DOS vulnerability due to incorrect use of wrong tickUpper in `collectFees()` and halt withdrawals and liquidations

### Summary

The protocol will revert due to incorrect wrong tickUpper passed to collectPositionFees() in [Line 167](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L167).

### Root Cause

When the collectFees function is called,and there is an ongoing vested position, the latest tickUpper of the mainPosition is used to collect the fees for the vesting position. Observe how the mainPosition is updated when a rebalance is triggered (check  rebalance() &  _setMainTicks()). 

Suppose a rebalance happens at this phase, the main and secondary positions are updated. 

<b>rebalance() happens every 6 minutes.</b>

The current implementation in the collectFees erroneously uses the mainPosition.tickUpper instead of vestPosition.tickLower and vestPosition.tickUpper when collecting fees for a vesting position.

```solidity
 if (ongoingVestingPosition) {
    //@audit-issue uses mainPosition.tickUpper instead of vestPosition.tickLower and vestPosition.tickUpper 
            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
        }
```

The function collect(recipient, tickLower, tickUpper, amount0Requested, amount1Requested) in the UNISWAP V3 Pool contract only works if a valid position exists at (tickLower, tickUpper).
If the tickUpper is incorrect and does not match the actual position stored in the pool, Uniswap cannot locate the position and the call will revert.

See collectPositionFees() where the uniswap pool contract collect() is called with the wrong tickUpper.

```solidity
    function collectPositionFees(int24 tickLower, int24 tickUpper) internal {
      // it will use the wrong tickUpper and revert
        IUniswapV3Pool(pool).collect(address(this), tickLower, tickUpper, type(uint128).max, type(uint128).max);
    }
``` 

### Internal Pre-conditions

1. Admin adds a new vesting position.
2. 6 minutes the bot rebalances.

### External Pre-conditions

1. Any function call that collect fees uses the latest mainPosition.tickUpper
2. Revert if vestPosition.tickUpper !=  mainPosition.tickUpper (UNISWAP collect fees fail to identify accurate vesting position ticks)

### Attack Path

- A vesting position is added to the strategy. 

  vestingPosition.tickLower == mainPosition.tickLower
  vestingPosition.tickUpper == mainPosition.tickUpper

- A rebalance happens at this phase.
  Fees collected (with accurate tickUpper from above).

  mainPosition.tickLower == newMainPosition.tickLower
  mainPosition.tickUpper == newMainPosition.tickUpper

- If liquidatePosition or withdraw is called next - or any function that collects fees - (it reverts causing a DOS)
  uses the latest mainPosition.tickUpper instead of vestingPosition.tickLower and vestingPosition.tickUpper

  vestingPosition.tickUpper != mainPosition.tickUpper

- collectFees cause function calls to fail

### Impact

- Critical calls to the protocol will revert due to incorrect use of wrong tickUpper in collectPositionFees() - withdraw(), deposit() on Vault contract and liquidatePosition() on Leverager contract.

- Users whose funds are in the protocol will not be able to withdraw their funds. 

- Liquidation is impossible afterwards.
