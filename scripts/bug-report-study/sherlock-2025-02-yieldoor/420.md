# Setting liquidation fee recipient is missing in `Leverager`

### Summary

When a position is in liquidation risk and the collateral value of the position is still greater than accrued borrowed value, the protocol takes liquidation fee.

However, since `feeRecipient` is initially set to the zero address and it's unchangeable, the liquidation will either revert due to an attempted transfer to the zero address or result in the loss of the liquidation fee.

### Root Cause

The `feeRecipient` is not set in the [constructor](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L60-L65) of `Leverager`, and there is no external function to set the fee recipient.

```solidity
    constructor(string memory name_, string memory symbol_, address _lendingPool)
        Ownable(msg.sender)
        ERC721(name_, symbol_)
    {
        lendingPool = _lendingPool;
    }
```

Therefore, the `feeRecipient` will always remain as zero address.

However, the protocol intends to take liquidation fee when the collateral is greater than accured borrowed amount in a liquidatable position.

```solidity
    function liquidatePosition(LiquidateParams calldata liqParams) external collectFees(liqParams.id) nonReentrant {
        ... ...
        if (totalValueUSD > borrowedValue) {
            // What % of the amountsOut are profit is calculated by `(totalValueUSD - borrowedUSD) / totalValueUSD`
            // Then, on top of that, we calculate the protocol fee and scale it in 1e18.

            uint256 protocolFeePct = 1e18 * liquidationFee * (totalValueUSD - borrowedValue) / (totalValueUSD * 10_000);
            uint256 pf0 = protocolFeePct * amount0 / 1e18;
            uint256 pf1 = protocolFeePct * amount1 / 1e18;

            if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0);
            if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1);
            amount0 -= pf0;
            amount1 -= pf1;
        }
        ... ...
    }
```

Therefore, the liquidation will be DoSed if the `token0` and `token1` don't support transfer to zero address. (Most ERC20 based tokens don't support that.)

For some tokens like `DAI`, the protocol will lose the liquidation fee due to transfer to zero address.

### Internal pre-conditions

- A position should be liquidatable and profitable while liquidation.

### External pre-conditions

*None*

### Attack Path

- Just runs liquidation for the positions that meet the internal pre-conditions

### Impact

Liquidations may fail or the protocol lose the funds.

### PoC

- If you check the `leverager` contract, you will easily notice that the function for setting a fee recipient is missing.
- For zero feeRecipient, we can check just running the following test case:
```solidity
    function test_H04_NoFeeRecipient() external {
        assertEq(ILeverager(leverager).feeRecipient(), address(0));
    }
```

### Mitigation

Add a new function to the `leverager`, which sets a fee recipient, and then update the `liquidatePosition()` function like below:

```diff
    function liquidatePosition(LiquidateParams calldata liqParams) external collectFees(liqParams.id) nonReentrant {
        ... ...
-       if (totalValueUSD > borrowedValue) {
+       if (totalValueUSD > borrowedValue && feeRecipient != address(0)) {
            ... ...
        }
        ... ...
    }
```
