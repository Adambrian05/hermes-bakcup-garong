# Incorrect `vestPosition` Handling in `collectFees()`

### Summary

The `collectFees(`) function is responsible for collecting outstanding position fees, including fees from the main position, secondary position, and any ongoing vesting position. However, there is an issue in the way `mainPosition` is handled when collecting fees for an ongoing vesting position. Instead of using `vestPosition.tickLower`, it incorrectly uses `mainPosition.tickUpper`, potentially leading to incorrect fee collection or lost fees.

### Root Cause



``` solidity
//  Strategy.sol

    function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0)
            collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(
                secondaryPosition.tickLower,
                secondaryPosition.tickUpper
            );
        }
        //@audit  it should be vestposition.tickUpper
        if (ongoingVestingPosition) {
>>            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper);
        }

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = ((afterBal0 - preBal0) * protocolFee) / 10_000;
        uint256 protocolFees1 = ((afterBal1 - preBal1) * protocolFee) / 10_000;

        if (protocolFees0 > 0)
            IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0)
            IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
            _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }

```

### Internal Pre-conditions


`{mainPosition.tickUpper}` must be different from vesting position's actual tickUpper, leading to incorrect fee collection.

### External Pre-conditions

{A third-party protocol or MEV bot} executes transactions that manipulate liquidity distributions, making the incorrect tick usage more damaging.

### Attack Path

{User} calls {collectFees()} when there is an ongoing vesting position.
{Contract} incorrectly calls {collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper)}.
{Liquidity provider} expects full fee collection, but due to the incorrect tick range, some fees are not collected.

### Impact

Some vested fees may remain uncollected or may be collected from an incorrect tick range.
Potential loss of accrued fees for users or the protocol.
