# Borrowing Order Bug Causes Open Position Failure for Users

### Summary

When calling the openLeveragedPosition function with token0 == denomination, only half of the available funds in the loan pool can be used to open a position. This is due to the fact that both the pullFunds and borrow functions can only utilize at most half of the pool’s funds. For instance, if the pool holds 100 tokens and the user provides an amount0In of 30 while attempting to open a vault position of 100, the process requires borrowing 70 tokens. However, during the pull operation, 70 tokens are extracted, leaving only 30 tokens available. Consequently, the maximum borrowable amount (maxBorrowAmount) is capped at below 30. After depositing, the remaining funds are insufficient to perform the push, which causes the transaction to revert. In addition, part of token0 is required to be swapped into token1 for repayment, further reducing the available token0 balance.

### Root Cause

In [Leverager.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L121-L169), the root cause lies in the design of the borrowing mechanism within the openLeveragedPosition function when token0 equals the denomination. The current sequence causes the pullFunds function to withdraw a significant portion of the pool’s funds before the borrow function is executed. As a result, even if the pool has sufficient overall funds, the maximum borrowable amount is limited due to the sequential withdrawal order.

### Internal Pre-conditions

none

### External Pre-conditions

1. The function openLeveragedPosition is called with token0/token1 equal to the denomination.
2. The provided amount0In is such that the vault position (e.g., 100 tokens) requires borrowing a significant amount (e.g., 70 tokens).

### Attack Path

1. A user calls the openLeveragedPosition function with parameters where token0 == denomination and a relatively low amount0In compared to the desired vault amount.
2. The pullFunds function is executed, withdrawing a large portion (e.g., 70 tokens) from the pool.
3. The borrow function then attempts to borrow the remaining required funds, but is limited by the fact that only half of the pool’s funds are available (e.g., only 30 tokens remain).
4. After depositing, the remaining funds are insufficient to perform the push, and additional token0 needed for conversion to token1 worsens the situation.
5. The transaction reverts, resulting in a failed position opening.

### Impact

In scenarios where users attempt to open a leveraged position with amounts approaching 50% of the pool’s capacity, the mis-sequenced borrowing leads to transaction reverts. Although the pool initially holds sufficient funds overall, the flawed borrowing order causes the system to restrict the maximum borrowable amount, ultimately resulting in failed transactions and potential financial losses (e.g., wasted gas fees) for users.

### PoC

_No response_

### Mitigation

Reorder the Borrowing Process:  redesign the mechanism to allow both functions to utilize a greater portion of the pool’s funds.
