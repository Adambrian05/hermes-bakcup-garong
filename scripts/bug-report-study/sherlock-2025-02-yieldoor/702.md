# Incorrect Tick Calculation in Secondary Position Due to Missing Modulo Normalization

### Summary

The lack of modulo normalization in `_setSecondaryPositionsTicks` will cause suboptimal liquidity placement for vault depositors as the rebalancer will miscalculate tick bounds for negative ticks. The secondary position is intended to be entirely out-of-range and hold only one asset (either `token0` or `token1`). Without proper normalization, the miscalculated bounds can make it partially in-range, reducing efficiency and misaligning with the strategy’s goals.

### Root Cause

In Strategy.sol: 
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L366-L382
 The `_setSecondaryPositionsTicks` function computes the modulo of the current tick without normalizing it for negative values, unlike the `_setMainTicks` function. This inconsistency leads to incorrect tick boundaries for the secondary position when the Uniswap pool's tick is negative. Additionally, a TODO comment suggests uncertainty about tick ordering, which may indicate further validation needs.

### Internal Pre-conditions

1. The rebalancer needs to call `rebalance()` to set the secondary position's tick bounds based on the current tick.
2. The strategy needs to have idle balances of `token0` and `token1` to determine the secondary position's range.
3. The Uniswap pool's current tick needs to be exactly a negative value (e.g., -15).

### External Pre-conditions

1. The Uniswap pool's price needs to shift such that the current tick becomes negative (e.g., when the price of token1 exceeds token0).

### Attack Path

1. The rebalancer calls `rebalance()` when the pool's current tick is negative (e.g., -15).
2. The `_setSecondaryPositionsTicks` function calculates `modulo = tick % tickSpacing`, resulting in a negative value (e.g., -15 % 10 = -5).
3. The function sets the secondary position's tick bounds using `tick - modulo` (e.g., -15 - (-5) = -10 for `tickUpper`), leading to unintended ranges.
4. Liquidity is added to the secondary position at suboptimal tick bounds, misaligning it with the strategy’s intended range.

### Impact

The vault depositors suffer an approximate loss of efficiency in liquidity placement, resulting in lower returns over time due to the secondary position being partially in-range or misaligned. This could reduce the strategy’s efficiency by up to 5–10% under volatile conditions, depending on tick movements.

### PoC

To demonstrate the issue, consider this scenario:

    Pool Tick: -15
    Tick Spacing: 10
    Main Position Ticks: tickLower = -20, tickUpper = 10 (normalized modulo)

Without normalization:

    modulo = -15 % 10 = -5
    If bal0in1 < bal1, tickUpper = -15 - (-5) = -10
    Secondary position range: -20 to -10

With normalization (expected):

    modulo = 5
    tickUpper = -15 - 5 = -20 (adjusted by Uniswap) The strategy likely intends a fully out-of-range configuration (e.g., -30 to -20 or -20 to -10), depending on asset balances.

### Mitigation

To resolve this issue, add modulo normalization to `_setSecondaryPositionsTicks`:

```solidity
function _setSecondaryPositionsTicks(int24 tick) internal {
    int24 modulo = tick % tickSpacing;
    if (modulo < 0) modulo += tickSpacing; // Normalize negative modulo
    // ... rest of the function
}
```
This ensures consistent tick calculations for both positive and negative ticks, aligning the secondary position’s behavior with the main position’s logic and preventing suboptimal liquidity placement.
