# Incorrect max leverage calculation in liquidation check delays necessary position liquidations

## Summary
The `Leverager#isLiquidateable` function uses an incorrect max leverage value when calculating the base collateral requirement, potentially allowing undercollateralized positions to avoid liquidation.

## Relevant Context
The protocol allows users to open leveraged positions with constraints on maximum leverage from two sources:
1. Vault-specific max leverage (`vp.maxTimesLeverage`)
2. Asset-specific max leverage (`maxLevTimes` from lending pool)

The effective maximum leverage for a position should be the minimum of these two values.

## Root Cause
In `Leverager#isLiquidateable`, the base collateral calculation uses only the vault's `maxTimesLeverage` parameter:

[`Leverager.sol#L408`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L408)

```solidity
uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
```

However, when opening positions in `_checkWithinlimits`, the protocol enforces that the actual leverage must not exceed either limit:

```solidity
require(positionLeverage <= vp.maxTimesLeverage && positionLeverage <= maxLevTimes, "too high x leverage");
```

This inconsistency means that when `vp.maxTimesLeverage > maxLevTimes`, the liquidation check uses a higher max leverage than what was actually allowed when opening the position, resulting in a lower base collateral requirement than intended.

## Attack Path
1. A vault is configured with `maxTimesLeverage = 5` while the lending pool sets `maxLevTimes = 3` for a particular asset
2. A user opens a position with leverage close to but under 3x (the effective limit)
3. The position's collateral value drops
4. `isLiquidateable` calculates a smaller base using 5x leverage instead of 3x
5. The position avoids liquidation despite being undercollateralized relative to its actual maximum allowed leverage

## Impact Explanation
Medium. This vulnerability can:
1. Allow positions to remain active despite being undercollateralized
2. Increase protocol's risk of bad debt

## Proof of Concept
Consider this scenario:
1. Vault sets `maxTimesLeverage = 5`
2. LendingPool sets `maxLevTimes = 3` for USDC
3. User opens a position with:
   - Initial collateral = 100 USDC
   - Borrowed amount = 200 USDC (3x leverage)
4. Position should require `200 * 1e18 / (3 - 1e18) = 100 USDC` base collateral
5. Instead, code calculates `200 * 1e18 / (5 - 1e18) = 50 USDC` base collateral
6. With `minCollateralPct = 0.5e18`, position avoids liquidation until collateral drops below 25 USDC instead of intended 50 USDC

## Recommendation
Modify the base calculation in `isLiquidateable` to use the minimum of both leverage limits:

```diff
function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
    Position memory pos = positions[_id];
    VaultParams memory vp = vaultParams[pos.vault];
+   (,uint256 maxLevTimes) = ILendingPool(lendingPool).getLeverageParams(pos.denomination);
+   uint256 effectiveMaxLeverage = vp.maxTimesLeverage < maxLevTimes ? 
+       vp.maxTimesLeverage : maxLevTimes;
-   uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
+   uint256 base = owedAmount * 1e18 / (effectiveMaxLeverage - 1e18);
    // ... rest of the function
}
```
