# Insufficient Minimum Borrow Enforcement During Price Fluctuations Leads to Economically Unviable Positions and Protocol Bad Debt Risk

## Summary
The Leverager contract fails to properly enforce[ minimum borrow requirements when asset prices change over time](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Leverager.sol#L279-L282). When users perform partial withdrawals during such conditions, they can create positions with real borrowed values below the `minBorrow` threshold while evading liquidation. These economically unviable "zombie positions" increase protocol overhead, reduce liquidator incentives, and potentially create bad debt if they eventually need liquidation when gas costs exceed position value.

## Vulnerability Details
The Leverager contract enforces a minimum borrow amount (`minBorrow`, set to 20e18 or $20) to ensure positions remain economically viable for management and liquidation. However, this enforcement has a critical flaw during partial withdrawals as market prices fluctuate.

The contract uses the initial USD value (`initBorrowedUsd`) rather than current market value when checking if a position meets minimum requirements after a partial withdrawal. The code comments justify this approach with the assumption that when prices drop, positions become less likely to be liquidated.

However, this assumption breaks down in common scenarios where both the borrowed asset and collateral asset change in value over time, with the collateral depreciating more than the borrowed asset. In such cases:

1. The position remains non-liquidatable based on absolute value comparisons
2. The real borrowed value falls below `minBorrow`
3. The contract fails to detect this issue because it only checks initial USD values

This creates positions that are:
- Too small to be economically viable to liquidate (gas costs exceed potential profits)
- Still at risk due to deteriorating collateral ratios
- Tracked and managed by the protocol despite being below minimum thresholds

## Proof of Concept
Consider this scenario:

**Initial Position Setup:**
- `minBorrow` = 20 USD (20e18)
- Borrowed Token: USDT
- Collateral Token: wBTC
- Initial USDT price: $1.00
- Initial wBTC price: $40,000
- Minimum collateral requirement: 50% of borrowed value

**User's Position:**
- User's collateral: 0.001 wBTC (= $40)
- Borrowed amount: 60 USDT (= $60)
- Total position value: $100
- `initBorrowedUsd`: 60e18 ($60)
- Leverage: 2.5x

**Position Health Check:**
- Equity: $40 (collateral value)
- Borrowed value: $60
- Required minimum collateral (50%): $30
- **Not liquidatable** since equity ($40) > required minimum ($30)

**Price Change (Phase 1):**
- USDT price drops to $0.90 (-10%)
- wBTC price drops to $32,000 (-20%)

**Updated Position Status:**
- User's collateral value: 0.001 wBTC = $32
- Borrowed value: 60 USDT = $54
- Equity: $32
- Required minimum collateral (50%): $27
- **Not liquidatable** since equity ($32) > required minimum ($27)

**User Partial Withdrawal (50%):**
- User withdraws 50% of position
- Repays 30 USDT
- Withdraws 0.0005 wBTC
- Remaining `initBorrowedUsd` = 30e18 ($30)

**Price Change (Phase 2):**
- USDT price falls further to $0.65 (-35% total)
- wBTC price falls further to $24,000 (-40% total)

**Final Position Status:**
- User's collateral value: 0.0005 wBTC = $12
- Borrowed value: 30 USDT = $19.50
- Actual borrowed value: $19.50 (below `minBorrow` of $20!)
- Equity: $12
- Required minimum collateral (50%): $9.75
- **Not liquidatable** since equity ($12) > required minimum ($9.75)

The position is now below the minimum borrow threshold in real terms ($19.50 < $20), yet the contract doesn't detect this issue because it only checks the initial USD values (30e18 > 20e18).

## Impact Details
This vulnerability creates economically unviable positions that burden the protocol with management overhead while providing insufficient liquidation incentives. As prices fluctuate over time, these positions could accumulate as "zombie debt" that liquidators won't touch due to gas costs exceeding potential profits. If many such positions form, they could collectively represent significant bad debt for the protocol.

## Tools Used
Manual

## Recommendations
1. **Use Current Market Values**: Modify the `withdraw()` function to check if the real current value of the remaining borrowed amount meets the `minBorrow` threshold:

```solidity
// Get current price of denomination token
uint256 currentDenomPrice = IPriceFeed(pricefeed).getPrice(up.denomination);
uint256 currentBorrowedValue = (totalOwedAmount - amountToRepay) * currentDenomPrice / (10 ** ERC20(up.denomination).decimals());

// Check against minBorrow using current values
require(currentBorrowedValue >= minBorrow, "remaining position below minimum borrow");
```


2. **Implement Forced Full Withdrawals**: If market conditions have caused a position's real value to fall near the `minBorrow` threshold, require users to fully withdraw rather than allowing partial withdrawals that would create sub-threshold positions.
