# Inconsistent Scaling Conversions will misvalue collateral for protocol users

# Summary:
Improper handling of fixed–point arithmetic across modules (using 1e18 for oracle prices, 1e27 for lending pool indexes, and 1e30 for vault prices) will cause inaccurate collateral valuation for protocol users as inconsistent conversion logic will let an attacker exploit rounding or scaling mismatches to bypass proper collateral requirements.

# Root Cause:

- In [ReserveLogic.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/libraries/ReserveLogic.sol) and [LendingPool.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol), the deposit and redeem functions use a constant `PRECISION = 1e27` for conversion, whereas in [Strategy.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol) and [Leverager.sol](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol) the contract uses a different `PRECISION = 1e30`.
- In Leverager’s `_calculateTokenValues` and liquidation logic, conversions sometimes divide by `ERC20(...).decimals()` (which returns a number like 18) instead of using the exponential factor (i.e. `10 ** decimals`). This mismatch can misprice collateral and borrowed values.

# Internal Pre-conditions:

1. The admin (or contract initializer) sets conversion factors in LendingPool and Leverager using different PRECISION constants.
2. Arithmetic operations in deposit, redeem, and liquidation functions operate on values with mismatched scales without centralized conversion functions.

# External Pre-conditions:

1. Chainlink price feeds (or fallback TWAP prices) return values scaled in 1e18.
2. Market conditions with low liquidity or high volatility amplify the effects of any rounding or conversion discrepancies.

# Attack Path:
1. An attacker deposits funds and opens a leveraged position while the system miscalculates collateral due to inconsistent scaling.
2. The attacker exploits these mismatches to open positions with a higher effective leverage than intended.
3. This misvaluation can lead to unintended liquidations or allow extraction of additional funds.

# Impact:
The protocol may incorrectly assess collateral, permitting over–leveraged or under–collateralized positions. This can lead to premature liquidations or allow an attacker to extract additional funds, thereby undermining the system’s financial integrity.

# PoC:
(A unit test demonstrating inconsistent conversion between LendingPool’s and Leverager’s arithmetic would illustrate how a small discrepancy can compound in a leveraged position.)

This PoC demonstrates how using different precision constants in the LendingPool (1e27) versus Leverager (1e30) leads to a miscalculation in collateral value. In this example, a deposit amount ends up “inflated” when the Leverager calculation is applied, enabling an attacker to benefit from an artificially high collateral valuation.
```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.13;

contract PoCScaling {
    // Simulated precision constants as used in different modules
    uint256 constant LENDINGPOOL_PRECISION = 1e27;
    uint256 constant LEVERAGER_PRECISION = 1e30;

    // Simulate LendingPool deposit calculation:
    // yTokenAmount = depositAmount * exchangeRate / LENDINGPOOL_PRECISION
    // Assume exchangeRate is set equal to LENDINGPOOL_PRECISION for simplicity.
    function deposit(uint256 depositAmount) public pure returns (uint256 yTokenAmount) {
        uint256 exchangeRate = LENDINGPOOL_PRECISION;
        yTokenAmount = depositAmount * exchangeRate / LENDINGPOOL_PRECISION;
        return yTokenAmount;
    }

    // Simulate Leverager collateral valuation which incorrectly applies a different precision.
    // For example, collateralValue = yTokenAmount * LEVERAGER_PRECISION / LENDINGPOOL_PRECISION.
    function collateralValue(uint256 yTokenAmount) public pure returns (uint256 value) {
        value = yTokenAmount * LEVERAGER_PRECISION / LENDINGPOOL_PRECISION;
        return value;
    }

    // Exploit demonstration:
    // If a user deposits 1e18 units, then:
    //   - LendingPool computes yToken = 1e18
    //   - Leverager incorrectly values collateral as 1e18 * 1e30/1e27 = 1e18 * 1000 = 1e21,
    // creating a discrepancy that can be exploited.
    function exploit(uint256 depositAmount) external pure returns (uint256 discrepancy) {
        uint256 yToken = deposit(depositAmount);
        uint256 val = collateralValue(yToken);
        // Ideally, collateral should equal depositAmount.
        discrepancy = val - depositAmount; // For depositAmount=1e18, discrepancy = 1e21 - 1e18 = 999e18.
    }
}
```
## PoC Explanation
The provided PoC (in the PoCScaling contract) illustrates a scenario where two modules—one in the LendingPool and another in the Leverager—use different precision constants for their arithmetic operations. Specifically:

LendingPool Precision: Uses a constant value of 1e27 to compute the exchange rate and mint yTokens.
Leverager Precision: Uses a constant value of 1e30 when computing collateral values.
**How It Works:**
1. When a user deposits funds, the LendingPool calculates the number of yTokens issued as:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L118
```ini
        yTokenAmount = amount * exchangeRate / (PRECISION);
```
2. For simplicity, if `exchangeRate` equals the precision (i.e. 1e27), then a deposit of `1e18` yields `1e18` yTokens.

However, when the Leverager later calculates the collateral value using these yTokens, it mistakenly applies a different conversion:
```ini
collateralValue = yTokenAmount * LEVERAGER_PRECISION / LENDINGPOOL_PRECISION
```
In our example, that computes as:

```ini
collateralValue = 1e18 * 1e30 / 1e27 = 1e18 * 1000 = 1e21
```
This inflates the collateral value by a factor of 1,000.

**Attack Scenario:**
An attacker could deposit a relatively small amount of funds but then open a leveraged position based on the inflated collateral value. This discrepancy might allow them to borrow more than what their real deposit should support, thereby bypassing the intended collateral requirements and ultimately leading to an undercollateralized position.

# Mitigation:
1. Standardize the conversion logic across all modules by using centralized helper functions that correctly convert between scales (e.g. using 10 ** ERC20(token).decimals() consistently).
2. Update both LendingPool and Leverager to use the same precision constant or explicitly convert between 1e27 and 1e30 where necessary.
