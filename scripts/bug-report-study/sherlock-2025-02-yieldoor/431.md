# Incorrect Token Transfer Method Causing Withdrawal Failures

### Summary

In the Vault’s withdrawal function, after calculating the proportional amounts that should be redeemed for the caller’s shares, the contract uses the ERC20 function `safeTransferFrom` to pull tokens from the Strategy contract and deliver them to the user. However, because the Vault never receives an explicit approval from the Strategy contract for the Vault to transfer its tokens, this approach will fail in practice. Instead, the `Vault` should directly transfer tokens held in the Strategy `(using safeTransfer)` rather than pulling them with safeTransferFrom. This issue can prevent users from successfully withdrawing their funds, leading to a critical loss of liquidity access.

### Root Cause

Transfer Method Mismatch:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L103
The Vault’s `withdraw()` function uses:
```solidity 
IERC20(token0).safeTransferFrom(strategy, msg.sender, withdrawAmount0);
IERC20(token1).safeTransferFrom(strategy, msg.sender, withdrawAmount1);
```
This implies that the Vault expects the Strategy contract to have approved the Vault as a spender of its token balances. However, no part of the protocol (or Strategy logic) sets such an approval. The tokens are held in the Strategy, but the Vault is not authorized to pull them. The correct approach would be to have the Strategy directly send the tokens out—i.e. by using `safeTransfer`.

### Internal Pre-conditions

The Vault deposits user funds into the Strategy via safeTransferFrom (from user to strategy).

The Strategy holds the tokens in its own balance (as verified by its idleBalances() and balances() functions).

The Vault has no mechanism in place to obtain an allowance from the Strategy contract for the tokens it holds.


### External Pre-conditions

Users expect to be able to redeem their Vault shares and receive the corresponding underlying tokens.

The ERC20 tokens used by the protocol do not allow implicit transfers without explicit allowance when using `safeTransferFrom.`


### Attack Path

1. User Deposit:

A user deposits tokens via the Vault. The tokens are transferred from the user into the Strategy contract successfully.

The Vault mints Vault shares accordingly.



2. User Withdrawal:

When the user calls `withdraw()`, the Vault calculates the amount of token0 and token1 to be redeemed.

The Vault then attempts to call:
```solidity 
IERC20(token0).safeTransferFrom(strategy, msg.sender, withdrawAmount0);
```



Because the Strategy has not granted the Vault an allowance, the ERC20 call fails.

The withdrawal transaction reverts, preventing the user from accessing their funds.

### Impact

User Funds Locked:
Users will be unable to withdraw their funds from the Vault, effectively locking liquidity in the Strategy contract.

Protocol Trust:
Repeated withdrawal failures can lead to severe loss of trust in the protocol’s functionality, even if funds remain safe in the Strategy.

Operational Risk:
Without successful withdrawals, the entire deposit–withdraw system fails to operate as intended, causing major disruptions in user experience.


### PoC

Assume Strategy holds 1,000 tokens of token0.

The user, holding 10% of Vault shares, should receive 100 token0 on withdrawal.

The Vault attempts to pull 100 token0 using safeTransferFrom(strategy, msg.sender, 100).

Since no approval exists (i.e. allowance(strategy, vault) == 0), the ERC20 call reverts with an allowance error.

### Mitigation

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L103
Replace `safeTransferFrom` with `safeTransfer`
In the `withdraw()` function of the Vault
