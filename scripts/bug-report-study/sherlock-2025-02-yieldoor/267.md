# Lack of Leverage Limit (Exceeds 5x) in LendingPool Contract

### Summary

The lack of a leverage limit in the `LendingPool` contract will cause users to set leverage above the expected 5x limit for borrowing, leading to potential over-borrowing and system insolvency.

### Root Cause

In `LendingPool.sol`, the `setLeverageParams()` (https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L369-L374) function allows the owner to set any value for `maxLeverage` without any upper bounds check. This allows an admin to set the leverage to an arbitrarily high value (e.g., 10x), violating the protocol's intended leverage cap of 5x.



### Internal Pre-conditions

1. The admin needs to call `setLeverageParams()` to set `maxLeverage` to be more than 5x (e.g., 10x).
2. The reserve needs to have sufficient liquidity to allow borrowing at the higher leverage.

### External Pre-conditions

1. The price of the underlying asset needs to be stable and not highly volatile to avoid additional risks when the leverage is set higher than expected.
2. The user needs to request a borrow that exceeds the safe 5x leverage ratio.

### Attack Path

1. The admin calls `setLeverageParams()` and sets the `maxLeverage` to 10x.
2. A user deposits funds and uses the new high leverage parameter to borrow an excessive amount.
3. If the market price shifts, the position may become underwater due to the excessive borrowing, leading to potential liquidation of other users or system collapse.

### Impact

The protocol could lose its solvency as users may borrow more than they can repay, resulting in liquidation risks and draining the liquidity pool. The protocol can suffer a significant financial loss, potentially leading to a breach of the platform’s liquidity.
- Users may lose more than 1% of their principal (more than $10) due to over-leveraging.
- The protocol could suffer the loss of over-leveraged funds, which exceeds its liquidity.


### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import "../src/LendingPool.sol";
import "../src/Leverager.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockERC20 is ERC20 {
    constructor(string memory name, string memory symbol) ERC20(name, symbol) {
        _mint(msg.sender, 10000 ether);
    }
}

contract LeverageLimitTest is Test {
    LendingPool pool;
    Leverager leverager;
    MockERC20 token;
    address owner = address(0x1);
    address user = address(0x2);

    function setUp() public {
        vm.startPrank(owner);
        pool = new LendingPool();
        token = new MockERC20("TestToken", "TTK");
        pool.initReserve(address(token));
        leverager = new Leverager("Leverager NFT", "LVR", address(pool));
        pool.setLeverager(address(leverager));
        vm.stopPrank();
    }

    function testLeverageExceedsLimit() public {
        vm.startPrank(owner);
        
        // Admin sets leverage above the 5x limit
        pool.setLeverageParams(address(token), 1000 ether, 10 ether);
        
        (uint256 maxBorrow, uint256 maxLeverage) = pool.getLeverageParams(address(token));
        assertEq(maxLeverage, 10 ether, "Leverage should not exceed 5x");
    }
}

```

### Mitigation

To mitigate this issue, a cap should be added in the `setLeverageParams()` function to prevent the leverage from being set above the desired limit (e.g., 5x). For example:

```solidity
require(_maxLeverage <= 5 ether, "max leverage cannot exceed 5x");
```
