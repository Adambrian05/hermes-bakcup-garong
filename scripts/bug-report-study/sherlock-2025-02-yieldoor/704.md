# Strategy.sol#collectFees() function - incorrect tick range used for vesting position

### Summary

Incorrectly using `mainPosition.tickUpper` instead of `vestPosition.tickUpper` in `collectPositionFees()` will cause incorrect fee distribution for vesting position liquidity providers, as the protocol may over-collect or under-collect fees if the tick range changes.

### Root Cause


In [`Strategy.sol#collectFees()`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L157C1-L182C1):

```solidity
    function collectFees() public {
        (uint256 preBal0, uint256 preBal1) = idleBalances();

        if (mainPosition.liquidity != 0) collectPositionFees(mainPosition.tickLower, mainPosition.tickUpper);
        if (secondaryPosition.liquidity != 0) {
            collectPositionFees(secondaryPosition.tickLower, secondaryPosition.tickUpper);
        }
        if (ongoingVestingPosition) {
            collectPositionFees(vestPosition.tickLower, mainPosition.tickUpper); // @audit different ticks
        }

        (uint256 afterBal0, uint256 afterBal1) = idleBalances();

        uint256 protocolFees0 = (afterBal0 - preBal0) * protocolFee / 10_000;
        uint256 protocolFees1 = (afterBal1 - preBal1) * protocolFee / 10_000;

        if (protocolFees0 > 0) IERC20(token0).safeTransfer(feeRecipient, protocolFees0);
        if (protocolFees1 > 0) IERC20(token1).safeTransfer(feeRecipient, protocolFees1);

        if (ongoingVestingPosition) {
            _withdrawPartOfVestingPosition(); // doing that now, otherwise we'd charge protocol fee for the vested position
        }
    }
```

- `mainPosition.tickUpper` is used instead of `vestPosition.tickUpper`.
- Vesting positions have their own tick range, so fees should be collected only within that range.
- If the main position’s tick range changes, fees may be over-collected or under-collected.

### Internal Pre-conditions

1. A vesting position is active (`ongoingVestingPosition == true`).
2. The main position's tick range changes (e.g., through rebalancing).
3. The protocol calls `collectFees()`.

### External Pre-conditions

1. Uniswap V3 pool fees accumulate within the tick range of the vesting position.
2. The main position’s tick range changes due to rebalancing or strategy updates.

### Attack Path

1. A vesting position is created with `tickLower` and `tickUpper`.
2. Fees accumulate within this tick range.
3. The main position’s tickUpper changes, expanding or contracting the tick range.
4. Protocol calls `collectFees()`, using `mainPosition.tickUpper` instead of `vestPosition.tickUpper`.
5. Fees are collected from the wrong tick range, leading to:
   - Over-collection: If `mainPosition.tickUpper` is higher than `vestPosition.tickUpper`, collecting fees that don’t belong to the vesting position.
   - Under-collection: If `mainPosition.tickUpper` is lower than `vestPosition.tickUpper`, missing some fees.

### Impact

Incorrect fee distribution among liquidity providers.  
Users may receive fewer rewards than expected.  
Vesting positions may become less profitable due to fee misallocation.
