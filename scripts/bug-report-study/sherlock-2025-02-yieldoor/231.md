# Incorrect Tick Calculation in `_setSecondaryPositionsTicks` Leading to Misaligned Liquidity Ranges

### Summary

The function `_setSecondaryPositionsTicks` is designed to set the tick range for secondary liquidity positions based on the current tick and remaining token balances. It aims to ensure that the secondary position is one-sided, requiring only one of the tokens. However, incorrect handling of the modulo operation for negative tick values leads to misaligned liquidity ranges, potentially requiring both tokens instead of a single asset.

### Root Cause

The issue arises from the modulo operation (`tick % tickSpacing`) when `tick` is negative.
1. **Incorrect Modulo Calculation for Negative Ticks:**
- In Solidity, `tick % tickSpacing` returns a negative value when `tick` is negative, which affects calculations.
- Instead of properly aligning to tick spacing, the function shifts the tick range incorrectly, moving `tickUpper` higher than intended or `tickLower` higher than expected.

2. **Misaligned Tick Assignment Causes Middle-Tick Issue:**
- When `bal0in1 < bal1`, `tickUpper` should align with the lower bound. The upper tick (`tickUpper`) is shifted higher which is the wrong direction, resulting in a tick range that requires both tokens instead of one-sided liquidity.
- When `bal0in1 >= bal1`, `tickLower` should align with the upper bound, but instead, the lower tick (`tickLower`) is moved higher than expected.

### Attack Path

**Given Parameters**
- **Position Width = 100**
- **Tick Spacing = 10**

## Case 1: tick = 24 (Positive Tick, Works Fine)
**Modulo Calculation:**
`24 % 10 = 4`

For `bal0in1 < bal1`:
- tickUpper = 24 - 4 = 20
- tickLower = mainPosition.tickLower = -30
- **Secondary Position:** [20, -30] ✅ (Correct)

For `bal0in1 >= bal1`:
- tickLower = 24 - 4 + 10 = 30
- tickUpper = mainPosition.tickUpper = 70
- **Secondary Position:** [70, 30] ✅ (Correct)

No issue here.

## Case 2: tick = -24 (Negative Tick, Issue Appears)
**Modulo Calculation (Incorrect Handling):**
`-24 % 10 = -4`

For `bal0in1 < bal1`:
- tickUpper = -24 - (-4) = -20
- tickLower = mainPosition.tickLower = -70
- **Secondary Position:** [-20, -70 ] ❌ (Incorrect, should have been [-30, -70])
- **issue:** The upper tick (`tickUpper`) is shifted higher which is the wrong direction, resulting in a tick range that requires both tokens instead of one-sided liquidity.
- 
For `bal0in1 >= bal1`:
- tickLower = -24 - (-4) + 10 = -10
- tickUpper = mainPosition.tickUpper = 30
- **Secondary Position:** [30, -10] ❌ (Incorrect, should have been [30, -20])
- **Issue:** The lower tick (`tickLower`) is moved higher than expected.

### Impact

Liquidity Mismatch: The secondary position may require both tokens instead of one, leading to unexpected liquidity provision requirements. when this happens No liquidity will be added to the secondary position
