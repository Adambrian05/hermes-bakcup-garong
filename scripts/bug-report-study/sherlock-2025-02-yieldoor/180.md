# A position's `initCollateralValue` is wrongly calculated, allowing users to open positions greater than the max leverage.

### Summary

A position's `initCollateralValue` is wrongly calculated, on it it is saved the total position value. This allows things like:

The [leverage calculation at](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L464) `Leverager::_checkWithinlimits()` is wrong because `initCollateralValue` accounts for both, user collateral and borrowed funds. This allows users to open positions greater than the max leverage.

```solidity
uint256 positionLeverage = (up.initCollateralValue + up.borrowedAmount) * 1e18 / up.initCollateralValue;
```

Numerical example:
- User collateral: 500
- Borrowed amount: 2000
- Total position value: 2500
- Max leverage: 2

- Position leverage as per calculation: (2500 + 2000) / 2500 = 1.8 leverage
- Actual leverage: (500 + 2000) / 500 = 5 leverage

Note that, as [per code docs](https://docs.google.com/document/d/1FUjXMXBRBRVgOYSMGORTFmS9fj_nh-ifQhoY0jjhwPY/edit?tab=t.0) at sections `Liquidations explained`, the code should calculate leverage like so: `totalPositionValue / userCollateral`.

### Root Cause

Using amount `a0` and `a1` to calculate `initCollateralValue` in `Leverager::openLeveragedPosition()`. These amounts included borrowed funds and not just collateral by the user. `initCollateralValue` is used accros the code in other key functions like: `Leverager::isLiquidatable()` and `Leverager::withdraw()`.

However, the logic of these functions is correct, the only issue is the wrong calculation of the value.

### Internal Pre-conditions

It always happens, it is a logic error.

### External Pre-conditions

It always happens, it is a logic error.

### Attack Path

It always happens, it is a logic error.

### Impact

- Leverage is always undercalculated, allowing users to bypass the leverage limit on `openLeveragedPosition()`. This is risky as there is a max leverage for system health reasons to prevent stuff like bad debt in certain asset combinations.

- We can also see in the PoC that a wrong value set on `initCollateralValue` won't make over-leveraged positions revert due to `isLiquidatable()` check. The check's logic seems correct, it is just that the value is wrong and leads to wrong results.

- `Leverager::withdraw()`: I could not see any issue with the withdraw logic as its value transfers and checks do not depend on `initCollateralValue`.

### Mitigation

Do not calculate `initCollateralValue` derived from the `a0` and `a1` amounts, as they also account for borrowed funds.

Use instead the actual amount the user provides which are the amounts transferred from the user on [these](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L116) `transferFrom()` in the `openLeveragedPosition()` function.
