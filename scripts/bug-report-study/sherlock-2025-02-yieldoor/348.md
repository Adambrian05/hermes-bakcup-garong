# Liquidation Logic Flaws in `Leverager.sol` will cause premature liquidations for borrowers

# Summary:
An inaccurate liquidation calculation based on a “max leverage” assumption will cause premature liquidations for borrowers as the protocol may erroneously deem a partially leveraged position (e.g. 1.25×) under–collateralized. In this scenario, an attacker or even normal market volatility (with TWAP lag) could trigger liquidation despite the borrower’s collateral ratio being safe under actual conditions.

# Root Cause:
The liquidation function in `Leverager.sol` calculates a required collateral “base” using the formula:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L408C8-L409C80

```solidity
        uint256 base = owedAmount * 1e18 / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;
```
This computation assumes that the borrowed amount was opened at the maximum allowed leverage. For a position that is not at maximum leverage (for example, 1.25× instead of 2×), this approach overestimates the required collateral drop needed to trigger liquidation. As a result, if the TWAP (time-weighted average price) lags or is manipulated slightly, the position might be marked liquidatable even when the borrower’s actual collateral ratio is safe.

# Internal Pre-conditions:
1. A leveraged position is opened at partial leverage (e.g. 1.25×) instead of the maximum allowed leverage.
2. The liquidation function uses the fixed max-leverage parameter (vp.maxTimesLeverage) rather than the position’s effective leverage.
3. The TWAP price used in the calculation is delayed relative to the current spot price, causing the computed collateral value to drop.

# External Pre-conditions:
1. Market volatility or price manipulation causes rapid changes in token prices or temporary discrepancies between spot and TWAP prices.
2. External price feeds (e.g. from Chainlink or the fallback UniV3 TWAP) experience a brief lag or deviation, resulting in an inaccurate collateral valuation.

# Attack Path:
1. A user opens a leveraged position with partial leverage (e.g. 1.25×) where the initial collateral is sufficient under normal conditions.
2. Due to market volatility or an attacker’s manipulation, the TWAP price temporarily lags behind the spot price.
3. The liquidation function calculates the required collateral using a “max leverage” assumption and determines that the current collateral value (derived from the lagged TWAP) falls below the threshold.
4. The protocol marks the position as liquidatable and triggers liquidation, causing the user to lose collateral unfairly.

# Impact:
Borrowers may face premature and unfair liquidations even if their positions are safe under current market conditions. This can lead to loss of funds for users and erode trust in the protocol, as positions that should remain healthy become subject to liquidation due to miscalculated collateral thresholds.

# Mitigation:
1. Adjust Liquidation Calculation: Modify the liquidation logic to compute the required collateral based on the actual effective leverage of the position rather than always using the max leverage assumption.
2. Dynamic Leverage Parameter: Incorporate the position’s actual leverage factor into the collateral threshold calculation.
3. Enhanced Price Checks: Use additional price observations or cross-reference multiple oracles to mitigate TWAP lag issues and reduce susceptibility to manipulation.
