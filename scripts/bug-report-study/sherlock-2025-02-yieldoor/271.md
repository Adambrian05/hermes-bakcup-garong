# Persistent DoS on openLeveragedPosition()

### Summary

`Leverager` doesn't differentiate between tokens that entered the contract using the intended functionality and external transfers. An attacker can externally transfer tokens to the leverager , which prevents users from opening positions.
***Please note*** that the developer's comment saying that it's not a vulnerability is incorrect since the assumptions he made on why this is fine are incorrect, and we'll explain why later.

### Root Cause

In [`Leverager.sol:177`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L177) , `up.borrowedAmount` is calculated by subtracting `denomBalance` from `lp.maxBorrowAmount`. `denomBalance` is the total balance of the leverager of the denomination token ( line 171 ).
This means an attacker can externally transfer tokens to the leverager, causing the subtraction `lp.maxBorrowAmount - denomBalance` to underflow, this makes this function always revert preventing users from opening positions.
### Why the developer' comment is incorrect
The developer said that this issue is fine since:
    - 1) **Anyone could sweep them:** This is incorrect, there is only one instrsuction in the codebase which sweeps tokens and it's in line `Leverager.sol:198` in the function `openLeveragedPosition()`. If the line 177 is gonna cause a revert, then we'll never reach that instruction anyway and no one will be able to sweep tokens.
    - 2) **MEV bots will sweep them within seconds:** MEV bots rely on the presence of an external or public function which allows sweeping tokens, there is no function in the entire codebase which does that except for `openLeveragedPosition()` , which is the vulnerable DoS'ed function. Also it's not recommended to rely on MEV bots for security.
    - 3) **It's unlikely** : It could be unlikely if the only way tokens got into the contract is by the intended functionality, but since external transfers also increase the balance, there is always a possibility that a malicious actor can transfer tokens directly to the contract causing a DoS. Yes he might gain nothing directly from the direct transfer, but he might be gaining from causing disruption to the protocol if he's benefiting a competing platform or has an interest in harming the system’s reputation. The loss of the attacker may be incomparable to the loss of the protocol.

### Attack Path

1. The attacker transfers an amount of tokens externally enough to cause the line `up.borrowedAmount = lp.maxBorrowAmount - denomBalance;` to revert.
2. The function will always revert and no one will be able to open a position or sweep tokens, which make the transferred tokens locked forever preventing the contract from functioning.

Please note that if a certain amount is transferred, all next calls will revert no matter how big `lp.maxBorrowAmount` is. This is because a big `lp.maxBorrowAmount` will also lead to adding to `denomBalance` via deposits , so it's a slippery slope and we can't assume that upping `lp.maxBorrowAmount` will prevent the underflow revert. ( demonstration in the PoC ).

### Impact

- Since opening leveraged positions within the leverager is a main functionality, causing a DoS on `openLeveragedPosition()` may cause the entire contract to break and render it useless.

### Mitigation

Add an external function which sweeps tokens, and don't make it only within the vulnerable function which is subject to the attack.
