# Attacker will prevent liquidations by manipulating denominated token price

## Summary
The missing price feed validation in the Leverager contract will cause accumulation of bad debt for the lending pools as attackers will manipulate or choose vulnerable price feed tokens to prevent timely liquidations of underwater positions.

## Root Cause
In [Leverager.sol#L369-L394](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L369-L394) the `isLiquidateable` function relies exclusively on the denominated token's price feed without validation:

```solidity
uint256 bPrice = IPriceFeed(pricefeed).getPrice(pos.denomination);
uint256 totalDenom = totalValueUSD * (10 ** ERC20(pos.denomination).decimals()) / bPrice;
```

The function doesn't validate the quality or freshness of the price feed data, and users can select which token to use as denomination when creating positions, enabling manipulation of the liquidation threshold.

## Internal Pre-conditions
1. A user must have an existing leveraged position in the protocol
2. The user must have chosen a manipulable token as the denomination for their position
3. The `pricefeed` contract must be used to determine asset prices for liquidation calculations

## External Pre-conditions
1. The price of the chosen denomination token must be manipulatable (e.g., through a low-liquidity market)
2. The collateral value of the position in USD must have decreased significantly
3. Without price manipulation, the position would be liquidatable under normal circumstances

## Attack Path
1. Attacker creates a leveraged position using a token with a manipulable price feed as denomination
2. Market conditions change, causing the position to become underwater in reality
3. Attacker manipulates the denomination token's price (e.g., by purchasing tokens to increase price) when the position should be liquidated
4. The artificially inflated price causes `isLiquidateable` to return false, preventing liquidation
5. Attacker continues to extract value through partial withdrawals while maintaining the manipulation
6. When the position eventually becomes too underwater to maintain, the protocol is left with bad debt

## Impact
The protocol suffers accumulation of bad debt as positions that should be liquidated remain open and become more underwater. This could lead to protocol insolvency if enough bad debt accumulates across multiple positions. Liquidators are unable to perform their function, and the integrity of the lending system is compromised.

## PoC
```solidity
function testDenominationPriceManipulation() public {
    // Setup
    address attacker = address(0x1);
    vm.startPrank(attacker);
    
    // Step 1: Create a leveraged position with manipulable denomination token
    address vulnerableDenom = setupVulnerableDenomination();
    LeverageParams memory params = createLeverageParamsWithDenom(vulnerableDenom);
    uint256 posId = leverager.openLeveragedPosition(params);
    
    // Step 2: Change market conditions to make position underwater
    simulateMarketDownturn(50); // 50% price decrease
    
    // Position should be liquidatable, but isn't yet verified
    bool shouldBeLiquidatable = true;
    
    // Step 3: Manipulate denomination price
    manipulateDenominationPrice(vulnerableDenom, 2); // Double the price
    
    // Step 4: Verify position isn't liquidatable despite being underwater
    bool isLiquidatable = leverager.isLiquidateable(posId);
    assertEq(isLiquidatable, false);
    assertEq(isLiquidatable, !shouldBeLiquidatable); // Contradiction
    
    // Step 5: Try to liquidate and verify it fails
    vm.expectRevert("isnt liquidateable");
    liquidatePosition(posId);
    
    vm.stopPrank();
}
```

## Mitigation
Implement multi-oracle price validation for critical operations:

```solidity
function isLiquidateable(uint256 _id) public view returns (bool liquidateable) {
    // ... existing code ...
    
    // Get price from primary oracle
    uint256 primaryPrice = IPriceFeed(pricefeed).getPrice(pos.denomination);
    
    // Get price from backup oracle (could be a different oracle provider)
    uint256 backupPrice = IBackupPriceFeed(backupPricefeed).getPrice(pos.denomination);
    
    // Use the lower of the two prices for safer liquidation calculation
    uint256 bPrice = primaryPrice < backupPrice ? primaryPrice : backupPrice;
    
    // ... rest of the function ...
}
```

Alternatively, restrict which tokens can be used as denominations:

mapping(address => bool) public approvedDenominations;
