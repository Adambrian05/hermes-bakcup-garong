# Flash Loan “Pull” Without Enforcement of Return

### Summary

The LendingPool’s flash loan mechanism allows the Leverager to pull funds without tracking the amount outstanding, relying solely on the Leverager’s correct invocation of pushFunds. This creates a risk if the Leverager fails to return the funds.

### Root Cause

In `LendingPool.sol` (lines ~235–243 for pullFunds and ~244–251 for pushFunds), no internal ledger tracks the outstanding “flash loan” amount. The functions assume that every pull will be immediately repaid, without verifying that the balance is restored by the end of the transaction. The Yieldoor design allows the `Leverager` to temporarily draw funds from the `LendingPool` via `pullFunds` and return them via `pushFunds` in the same transaction. This is effectively an internal flash loan mechanism used to supply liquidity to the vault optimistically, then borrow and swap to repay it – a clever design to achieve high leverage in one atomic transaction. However, the LendingPool contract itself does not enforce that `pullFunds` are returned or track them as an outstanding obligation. The function `LendingPool.pullFunds(asset, amount)` simply transfers underlying tokens from the yToken reserve to the caller (leverager)​, without marking down any balances or debts. It relies entirely on the Leverager contract to call the matching `pushFunds` for the same amount later in the transaction​. If for any reason the Leverager fails to do so (or does so incorrectly), the LendingPool would end the transaction with fewer assets than its accounting variables indicate.

It’s important to note that in the provided code, the Leverager does call `pushFunds` for the exact `delta0`/`delta1` it pulled​, and it repays any unused borrowed denom immediately​. So in normal operation, the invariant holds. The risk is more about trust and future changes: since `leverager` is a contract settable by the owner (only once)​, and `pullFunds`/`pushFunds` have no other safety checks, a malicious or buggy leverager could exploit this. For example, if an attacker somehow gained control of the Leverager contract (through an upgrade or exploit in the Strategy or Vault it interacts with) or if a new Leverager version is deployed incorrectly, it could call `pullFunds(asset, amount)` and never return the funds. Because `leverager` is hard-coded after initialization, this scenario is only possible if the Leverager itself has a flaw or is compromised, not by an arbitrary attacker calling (since the check `require(msg.sender == leverager)` protects it​). Nevertheless, it’s a privileged function without internal accounting to enforce correctness.

### Internal Pre-conditions

1. The Leverager calls `pullFunds` to extract a specified amount from the pool.
2. The LendingPool does not record this withdrawal as pending debt.
3. The subsequent operation is expected to call `pushFunds` to return the exact amount.

### External Pre-conditions

1. An attacker or bug in the Leverager contract prevents `pushFunds` from being called.
2. External interactions (e.g., rebalancer or liquidation bots) operate normally.

### Attack Path

1. An attacker-controlled Leverager calls `pullFunds` to drain a large portion of the pool’s liquidity.
2. The attacker deliberately does not call `pushFunds`, leaving the pool with a deficit.
3. Lenders attempting to withdraw funds later find the pool underfunded, leading to financial loss.

### Impact

In the worst-case misuse, LendingPool reserves can be drained by the Leverager contract. If the Leverager were malicious, it could withdraw the entirety of available liquidity from each reserve via pullFunds and never return it, resulting in an instant shortfall equal to all lender deposits. Lenders would not be able to withdraw, and the system would essentially collapse unless those funds were somehow recovered. Even without malicious intent, if a bug in Leverager’s openLeveragedPosition sequence caused the pushFunds calls to be skipped (e.g., due to a conditional revert or an edge-case path where delta0 or delta1 isn’t calculated correctly), the transaction might still succeed and leave the pool missing funds. (However, in practice, if pushFunds is not called, the likely outcome is the Leverager contract itself would end up with extra tokens at end of the transaction – depending on the code path, this might actually revert somewhere else or fail the final invariant check require(!isLiquidateable) if the flash loan wasn’t repaid, since the position’s collateral would be artificially higher. But we shouldn’t rely on indirect effects for safety.)It’s worth noting this is a systemic risk rather than an external exploit – it assumes the attacker can control or exploit the Leverager contract. That might be possible if, say, the rebalancer or strategy had a backdoor into leverager (none obvious in the given code) or if the owner sets an untrusted leverager address. The protocol explicitly marks the Leverager as trusted, but from a security standpoint this is a single point of failure. If compromised, users’ deposits are at risk.

### Mitigation

Add protective checks in LendingPool around the flash loan mechanism to enforce the “pull must equal push” invariant within a transaction. A straightforward approach is to maintain an accounting of how much was pulled and not yet returned for each asset:

- Add a mapping like `mapping(address => uint256)` pendingFlashDebt; in LendingPool’s reserve data.

- In pullFunds, before transferring, increment `pendingFlashDebt[asset] += amount` and maybe record the caller (though since only one caller is allowed, you know it’s leverager). Also consider checking `require(pendingFlashDebt[asset] == 0, "existing flash loan not returned")` to prevent recursive or multiple pulls in one tx (if that’s not intended).

- In pushFunds, decrement `pendingFlashDebt[asset] -= amount` before transferring the asset from leverager back into the reserve. If `pendingFlashDebt[asset]` would underflow (meaning pushing back more than pulled), revert as that indicates a mismatch.

- At the end of the Leverager’s `openLeveragedPosition` (or enforced by LendingPool), require that all pulled amounts for that tx are returned to zero. This could be done by an invariant check in LendingPool (though tricky without hooking into end-of-tx), or simply by structuring Leverager’s calls such that every pull has a corresponding push right after the dependent operation. The current code already does this (pull -> deposit to vault -> then push back immediately), which is good. The accounting would just formalize it and protect against future changes.
