# First depositor can cause a DoS on one of the tokens, preventing any future deposits of it.

### Summary

If the first user deposits 0 of token1 and an amount of token0, the condition `bal1 == 0` will always be true in future deposits and the `else if` block will always be entered since there is no instruction in the execution flow that sets the return amount of token1 , which prevents any future deposits.
The only way to remediate this after the attack is done is by externally transferring token1 to the strategy, and make sure `amount1 = (cross - 1) / bal0 + 1;` is greater than 1, but this will deposit in minimal amounts each time (impractical) and the damage will be done.

### Root Cause

In [`Vault.sol:137`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L137) , if the first depositor has deposited 0 of token1 and some amount of token0 , the condition `(bal1 == 0)` will always be true in each execution, this means the `else if (bal1 == 0)` block will be entered in each deposit. This is because there is no instruction that sets `amount1` in that `else if` block. Which leads to preventing future deposits.

This works for token0 too if the attacker deposited 0 of token0.
Please note that this doesn't have anything to do with rebalancing or compounding, i tried to execute them right before the deposit but i still wasn't able to deposit.

### Internal Pre-conditions

The attacker needs to be the first depositor.

### External Pre-conditions

N/A

### Attack Path

1. First user deposits 0 wbtc and 10000 usdc.
2. Second user tries to deposit 1000 wbtc and 1000 usdc but only the wbtc gets deposited and the usdc is returned.
3. This issue keeps going for every new deposit.

***Fix after the attack***
Let's assume the protocol maintainers noticed this issue after the attack and decided to transfer 1 usdc to the strategy to break the condition `bal1 == 0` .
This means in order to deposit only 2 usdc, ` (cross - 1) / bal0 ` , must result in at least 1 , which means users need to pass huge numbers as `depositAmount0` and `depositAmont1` only to deposit a small amount of token1, which leads to financial loss.
The protocol maintainers could also transfer externally a huge amount of token1 in order to increase bal1 , but that would result in financial loss. So fixing the vulnerability is the best solution.

### Impact

- DoS: The first depositor can permanently prevent deposits of one token type.
- Financial loss to users, since the only way to remediate this after the attack is to externally donate tokens, and even after doing so, users still need to deposit a huge amount of token0 alongside to deposit only a small amount of token1 ( so that the `cross` becomes big enough so that `amount0 = (cross - 1) / bal1` doesn't result in 0 ), which is impractical and not best for user experience.
