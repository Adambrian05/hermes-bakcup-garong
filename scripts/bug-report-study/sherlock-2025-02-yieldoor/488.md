# Strategy::_setSecondaryPositionsTicks is not one-side liquidity

### Summary

Reviewing the documentation, we find:

> In order to utilize the most out of the funds within it, 2 positions are made - 1 wider, which aims to be 50:50 (or as close as it can get, depending on the pool’s tick spacing). The other one should be filled with whichever token is left after filling the main position. In order to achieve this, the secondary position is always Out-Of-Range right after rebalancing.

However, in some cases, this is not true.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L373

```solidity
    function _setSecondaryPositionsTicks(int24 tick) internal {         // tickSpacing = 10, tick = -11
        int24 modulo = tick % tickSpacing;                              // modulo = -1
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;       // tickLower = -30
            secondaryPosition.tickUpper = tick - modulo;                // tickUpper = -10
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing;  // tickLower = 0
            secondaryPosition.tickUpper = mainPosition.tickUpper;       // tickUpper = 10
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }
```

When `bal0in1 < bal1`, **tickUpper is set to -10, while the pool tick is -11**. This makes it impossible to create a single-side liquidity position, **contradicting the intended behavior described in the documentation**. This alone is enough to prove that such a position cannot exist and **could likely cause the transaction to revert.**

To further verify, we can analyze where tickLower is set:

```solidity
    function _setMainTicks(int24 tick) internal {                 // tickSpacing = 10, tick = -11 
        int24 halfWidth = int24(positionWidth / 2);             // halfWidth = 20 
        int24 modulo = tick % tickSpacing;                          // modulo = -1 
        if (modulo < 0) modulo += tickSpacing;                  // modulo = 9
        // if tick is negative, modulo is also negative 
        bool isLowerSided = modulo < (tickSpacing / 2);    // isLowerSided = false 

        int24 tickBorder = tick - modulo;                   // tickBorder = -20 
        if (!isLowerSided) tickBorder += tickSpacing;     // tickBorder = -10 
        mainPosition.tickLower = tickBorder - halfWidth;   // tickLower = -30 
        mainPosition.tickUpper = tickBorder + halfWidth;  // tickUpper = 10 

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

As a result, in secondaryPosition:

```solidity
secondaryPosition.tickLower = mainPosition.tickLower;       // tickLower = -30
```

### Internal Pre-conditions

1. `bal0in1 < bal1`

### External Pre-conditions

Multiple situations may exist, this is one :

1. Pool tick: -11
2. Pool tick spacing: 10

### Attack Path

None

### Impact

* In certain cases, the secondary position cannot be single-side, leading to unexpected transaction reverts.

### PoC

_No response_

### Mitigation

Reduce the width of the secondary position further to ensure that the tick is always out of range.
