# Opening a position will incorrectly revert due to uncollected fees

### Summary

Opening a position will incorrectly revert due to uncollected fees

### Root Cause

One of the prerequisites for the `isLiquidatable()` call to accurately return whether a user is liquidatable is calling `collectFees()` on the strategy:
> /// @dev In order to be 100% accurate, expects Strategy.collectFees to have been called right before that

This is because when there are uncollected fees, the share value of the user is lower than supposed to, resulting in him having a lower value, thus closer to liquidation.

Upon opening a leverage position, this call collects the previously uncollected fees:
```solidity
(uint256 shares, uint256 a0, uint256 a1) = IVault(lp.vault).deposit(lp.vault0In, lp.vault1In, lp.min0in, lp.min1in);
```
Then, at the end of the function, we check whether he is liquidatable, fees are supposedly collected and everything is good:
```solidity
require(!isLiquidateable(_id), "position can't be liquidateable upon opening");
```

The issue is that to open a position, we are conducting swaps from the borrowed token to token0 and token1, that way we can repay the flashloan taken for the leveraged position:
```solidity
            if (a1 > lp.amount1In && up.token1 != lp.denomination) {
                swapParams = abi.decode(lp.swapParams2, (IMainnetRouter.ExactOutputParams));
                address tokenIn = _getTokenIn(swapParams.path);
                require(tokenIn == lp.denomination, "token should be denomination 2 ");
                IERC20(tokenIn).forceApprove(swapRouter, swapParams.amountInMaximum);

                swapParams.amountOut = a1 - lp.amount1In;
                IMainnetRouter(swapRouter).exactOutput(swapParams);
                IERC20(tokenIn).forceApprove(swapRouter, 0);
            }
```
As we are doing a swap, there are fees accruing in the corresponding pool. The pool we are swapping in is likely to be the one the user deposited in during the position open. For that to be the case, the following conditions must be true:
- the denomination token is either token0 or token1, this is completely expected and handled by the code (this is a requirement as we are swapping from denom token to token0 and token1, so if denom is let's say token0, we will swap token0 to token1 which is the pair we are depositing in)
- the fee specified by the depositor is the same as the pool we are depositing in, there are only 4 possible fee tiers, thus this is also very likely (especially considering that a logical user would aim to use the pool he deposited in for the swap, he would benefit from the fee accrual)

As the fees are not collected after the swap, the `isLiquidatable()` check can incorrectly revert despite the user not actually being liquidatable.

### Internal Pre-conditions

1. Denom token is either token0 or token1
2. Fee chosen by the user (in the path bytes) is the same as the fee in the underlying pool of the vault the user is depositing in

### External Pre-conditions

_No_

### Attack Path

No attack path necessary, explained in root cause.

### Impact

Users won't be able to open a position that they should actually be. The developer has himself confirmed that opening a position is time-sensitive:
> ... opening positions is time-sensitive ...

As it is time-sensitive and the function incorrectly reverts, this warrants a medium severity based on the rules.

### PoC

_No response_

### Mitigation

Collect fees again after the swaps when opening a position.
