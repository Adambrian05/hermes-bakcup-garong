# withdrawals from the vault rely on slot0 price which can be manipulated to withdraw more than they should and steal funds

### Summary

Anyone who has priorly deposited and has shares is able to withdraw his funds. In the `balances()` function in the `Strategy.sol` contract and the UniswapV3.slot0 is used to get the value of `sqrtPriceX96` that would then be passed as an argument to the `getAmountsForLiquidity(...)` function to get the amounts for liquidity for both the main and secondary positions. However, slot0 can be easily manipulated to inflate the returned amount from balances() and withdraw more than they should. The protocol is well aware of the dangers of slot0 since they used `_requirePriceWithinRange()` in all the critical functions like `compound()` and `rebalance()`, everywhere there was the call: `IUniswapV3Pool(pool).slot0();` except in a view functions `balances()` that would be called inside of a critical function in the `Vault` contract: `withdraw()`.
`Vault.sol`:
```solidity

        public
        returns (uint256 withdrawAmount0, uint256 withdrawAmount1)
    {
        IStrategy(strategy).collectFees();

>>>     (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();

        uint256 totalSupply = totalSupply();
        _burn(msg.sender, shares);

        withdrawAmount0 = totalBalance0 * shares / totalSupply;
        withdrawAmount1 = totalBalance1 * shares / totalSupply;

>>>     IERC20(token1).safeTransferFrom(strategy, msg.sender, withdrawAmount1);

        return (withdrawAmount0, withdrawAmount1);

        // TODO emit event
    }
```

The usage of `slot0` is extremely prone to manipulation. The slot0 in the pool stores many values, and is exposed as a single method to save gas when accessed externally.

### Root Cause

In `Strategy.sol:503, easily manipulated `slot0` is used to get `sqrtPriceX96` without checking it:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L503

### Internal Pre-conditions

1. Attacker called `deposit(...)` priorly

### External Pre-conditions

None

### Attack Path

1. Attacker manipulates slot0 in order to obtain a `sqrtPriceX96` that would increase `amount0` and `amount1` in `balances()`
2. Attacker calls `withdraw(...)` to withdraw more than he is allowed

### Impact

The `sqrtPriceX96` is pulled from `Uniswap.slot0`, which is the most recent data point and can be manipulated easily via MEV bots, which can cause the loss of funds when interacting with `withdraw()` function. This could lead to wrong calculations and loss of funds for the protocol.

### PoC

_No response_

### Mitigation

Make the following changes to the `balances()` function:
```diff
    function balances() public view returns (uint256 amount0, uint256 amount1) {
        (uint160 sqrtPriceX96,,,,,,) = IUniswapV3Pool(pool).slot0();
+       _requirePriceWithinRange();
        (uint256 idle0, uint256 idle1) = idleBalances();
        (uint256 m0, uint256 m1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(mainPosition.tickLower),
            TickMath.getSqrtRatioAtTick(mainPosition.tickUpper),
            mainPosition.liquidity
        );
        (uint256 s0, uint256 s1) = LiquidityAmounts.getAmountsForLiquidity(
            sqrtPriceX96,
            TickMath.getSqrtRatioAtTick(secondaryPosition.tickLower),
            TickMath.getSqrtRatioAtTick(secondaryPosition.tickUpper),
            secondaryPosition.liquidity
        );

        amount0 = idle0 + m0 + s0;
        amount1 = idle1 + m1 + s1;
    }
```
