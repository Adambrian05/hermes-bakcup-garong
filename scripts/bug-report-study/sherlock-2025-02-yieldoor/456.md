# Inefficient Rebalancing Mechanism Leads to Capital Inefficiency and Potential Liquidations

## Summary
The Strategy contract's rebalance() function fails to properly rebalance token ratios after significant price movements. When prices shift dramatically, the vault's position becomes heavily imbalanced toward one token. The current implementation[ simply repositions this imbalanced liquidity](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L201-L214) around the new price without correcting the token ratio imbalance. This results in suboptimal capital deployment, reduced fee generation, and potential liquidation risks for leveraged positions.

## Vulnerability Details
The Strategy contract manages liquidity positions in Uniswap V3 pools through a main position (intended to be balanced 50:50) and a secondary position (designed to be out-of-range and single-sided). When significant price movements occur, the token composition of these positions can become heavily skewed toward one token.

The current rebalance() function:
1. Removes all liquidity from existing positions
2. Calculates new position ranges based on the current price
3. Attempts to add liquidity back to these positions using the existing token balances

The key issue is that after a large price movement, the contract might have, for example, 90% token0 and 10% token1. When rebalancing:

```solidity
function rebalance() public onlyRebalancer {
    // ...
    _removeLiquidity();
    (uint256 amount0, uint256 amount1) = idleBalances();
    
    // No mechanism to balance token0/token1 ratio here
    
    _setMainTicks(tick);
    (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);
    // ...
}
```

Since the main position requires a balanced ratio of tokens, most of the liquidity ends up in the secondary position, which is less capital efficient. This problem is compounded by the Vault's deposit mechanism, which enforces users to maintain the existing token ratio, preventing natural rebalancing through deposits.

## Proof of Concept
Consider a scenario where ETH/USDC pool price moves significantly:

1. Initial state: 10 ETH and 20,000 USDC in balanced positions
2. Price drops 50%: After removing liquidity, we have ~15 ETH and ~10,000 USDC
3. During rebalance:
   - Main position (50:50) can only use 10,000 USDC worth of ETH (~10 ETH at new price)
   - Remaining 5 ETH goes to secondary position
   - Result: Only 67% of capital in the optimal main position

This creates a cycle where each significant price movement further reduces capital efficiency.

## Impact Details
This vulnerability leads to suboptimal capital deployment with most assets ending up in the less efficient secondary position. This reduces fee generation potential and overall vault performance. For leveraged positions in a Leverager contract, the imbalance could trigger liquidations during volatile market conditions, causing direct financial losses to users.

## Tools Used
Manual

## Recommendations
1. Implement a token rebalancing mechanism in the rebalance() function:
   ```solidity
   function rebalance() public onlyRebalancer {
       // ...existing code...
       _removeLiquidity();
       (uint256 amount0, uint256 amount1) = idleBalances();
       
       // Add token rebalancing logic
       // Consider swapping tokens to achieve better balance
       
       _setMainTicks(tick);
       // ...rest of function...
   }
   ```

2. Modify the Vault's deposit mechanism to allow and incentivize imbalanced deposits when they would help rebalance the overall position.
