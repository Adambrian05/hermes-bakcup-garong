# Flawed Share Calculation Based on Nominal Token Amounts Enables Economic Value Extraction Through Pool Manipulation

## Summary
The Vault contract's share calculation logic in the `_calcDeposit` function is inconsistent and vulnerable to manipulation as it calculates shares based on the nominal amounts of tokens rather than their economic value. This allows attackers to strategically manipulate the pool composition through a series of deposits and withdrawals, ultimately enabling them to receive more shares than they should for the economic value provided.

## Vulnerability Details
When a user deposits tokens into the vault, the [`_calcDeposit` function determines](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L128-L150) how many shares they receive based on the following logic:

```solidity
if (totalSupply == 0) {
    // For first deposit, just use the amounts desired
    amount0 = depositAmount0;
    amount1 = depositAmount1;
    shares = (amount0 > amount1 ? amount0 : amount1) - (1000);
} else if (bal0 == 0) {
    amount1 = depositAmount1;
    shares = amount1 * totalSupply / bal1;
} else if (bal1 == 0) {
    amount0 = depositAmount0;
    shares = amount0 * totalSupply / bal0;
} else {
    uint256 cross0 = depositAmount0 * bal1;
    uint256 cross1 = depositAmount1 * bal0;
    uint256 cross = cross0 > cross1 ? cross1 : cross0;
    require(cross > 0, "cross");

    // Round up amounts
    amount0 = (cross - 1) / bal1 + 1;
    amount1 = (cross - 1) / bal0 + 1;
    shares = cross * totalSupply / bal0 / bal1;
}
```

The key vulnerability is that the share calculation uses the raw token amounts (`bal0` and `bal1`) without accounting for their relative economic value. For example, 1 ETH and 2000 USDC may have the same economic value, but the share calculation treats them as different amounts.

Additionally, the deposit fee implementation is flawed as it simply reduces the shares allocated to the user without minting those shares to a fee recipient:

```solidity
if (depositFee > 0) shares -= (shares * depositFee) / 10_000;
```

This means the deposit fee only decreases the nominal value of shares received by depositors without actually collecting those shares as revenue for the protocol or any recipient. So there's effectively zero cost to this attack.

## Proof of Concept
An attacker could exploit this vulnerability through the following steps:

1. Observe a pool with balanced liquidity (e.g., 10 ETH and 20,000 USDC)
2. Execute a series of deposits and withdrawals to manipulate the pool composition:
   a. Deposit a significant amount of token0 (ETH)
   b. Immediately withdraw both token0 and token1 from the pool
   c. Repeat until the pool is heavily skewed toward token0 (ETH)
   
3.  Alternatively, the attacker can move the Uniswap pool price by trading heavily towards one direction.
	- As price moves in their direction, so does the token composition in the vault's LP direction.
	- This effectively skews the pool heavily towards their desired tokens

4. With the pool now containing only/majority token0, the attacker makes a final deposit heavily weighted toward token0.

5. The `_calcDeposit` function will calculate shares based on the formula `shares = amount0 * totalSupply / bal0`, where `bal0` is very small.

6. Due to the small denominator, the attacker receives disproportionately more shares than the economic value they've contributed.

7. The attacker can later withdraw their shares when the pool is balanced, extracting more value than they deserve.

### Note: 
The strategy positioning varies under normal market operations which can lead to inconsistent shares distribution at different times without a malicious user intentional unbalancing the strategies position. This means even if the balance of token0/token1 is not zero, the shares value or worth distributed at different times in protocol is inconsistent and favourable to earlier or later depositors depending on token0 and token1 composition


## Impact Details
This vulnerability allows malicious users to extract economic value from the vault by receiving more shares than justified by their economic contribution. This directly harms other vault depositors as it dilutes their ownership percentage and reduces their eventual withdrawable amounts. The issue is exacerbated by the lack of a proper deposit fee implementation, which removes a potential economic disincentive to such attacks.

## Tools Used
Manual

## Recommendations
1. **Value-Based Share Calculation**: Modify the share calculation to use the tokens' economic value rather than nominal amounts. Implement this by:
   - Using the TWAP price from the strategy to calculate the equivalent value of both tokens
   - Calculating shares based on the total economic value contributed relative to the pool's total economic value

2. **Proper Fee Implementation**: Implement a fee recipient address and ensure deposit fees are actually collected rather than burned:
```solidity
   if (depositFee > 0) {
       uint256 feeShares = (shares * depositFee) / 10_000;
       shares -= feeShares;
       if (feeShares > 0 && feeRecipient != address(0)) {
           _mint(feeRecipient, feeShares);
       }
   }
```
