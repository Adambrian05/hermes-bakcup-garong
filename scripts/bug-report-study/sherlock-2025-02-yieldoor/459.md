# Absence of Slippage Protection in LendingPool Deposits Leads to Potential Value Loss for Depositors

## Summary
The LendingPool contract [lacks a slippage protection mechanism for depositors](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/LendingPool.sol#L70-L77), which exposes them to the risk of receiving fewer yTokens than expected when their transactions are processed. This can occur when other deposit transactions are executed before theirs, changing the exchange rate between underlying assets and yTokens. Without the ability to specify a minimum acceptable amount of yTokens, users cannot protect themselves against this risk, potentially resulting in unexpected value loss.

## Vulnerability Details
When users deposit assets into the LendingPool, they receive yTokens based on the current exchange rate calculated by `reserveToYTokenExchangeRate()`. This exchange rate is determined by the ratio of total yToken supply to the total liquidity in the reserve.

The key issue is in the `_deposit` function:

```solidity
function _deposit(address asset, uint256 amount, address onBehalfOf) internal returns (uint256 yTokenAmount) {
    // ...
    uint256 exchangeRate = reserve.reserveToYTokenExchangeRate();
    
    IERC20(asset).safeTransferFrom(msg.sender, reserve.yTokenAddress, amount);

    // Mint yTokens for the user
    yTokenAmount = amount * exchangeRate / (PRECISION);
    // ...
}
```

The exchange rate calculation:

```solidity
function reserveToYTokenExchangeRate(DataTypes.ReserveData storage reserve) internal view returns (uint256) {
    (uint256 totalLiquidity,) = totalLiquidityAndBorrows(reserve);
    uint256 totalYTokens = IERC20(reserve.yTokenAddress).totalSupply();

    if (totalYTokens == 0 || totalLiquidity == 0) {
        return PRECISION;
    }
    return totalYTokens * PRECISION / totalLiquidity;
}
```

This exchange rate changes whenever:
1. New deposits increase both totalLiquidity and totalYTokens
2. Withdrawals decrease both totalLiquidity and totalYTokens
3. Borrows decrease totalLiquidity without affecting totalYTokens
4. Repayments increase totalLiquidity without affecting totalYTokens

If any of these actions occur between when a user submits their transaction and when it's executed, the exchange rate will change, and the user will receive a different amount of yTokens than expected.

## Proof of Concept
Scenario 1: Front-running
1. Alice wants to deposit 1000 USDC into the LendingPool
2. Current exchange rate: 0.95 yUSDC per USDC
3. Alice expects to receive 950 yUSDC
4. Bob sees Alice's transaction in the mempool
5. Bob front-runs with a large deposit of 10,000 USDC
6. Exchange rate changes to 0.94 yUSDC per USDC
7. Alice's transaction executes, but she only receives 940 yUSDC
8. Alice loses 10 yUSDC of value with no way to prevent this

Scenario 2: Normal operation during high activity
1. Current pool: 100,000 USDC with 95,000 yUSDC (exchange rate: 0.95)
2. Alice submits a transaction to deposit 5,000 USDC, expecting 4,750 yUSDC
3. Due to network congestion, several other deposits totaling 20,000 USDC are processed first
4. New exchange rate: 0.93 yUSDC per USDC
5. Alice's transaction executes, but she only receives 4,650 yUSDC
6. Alice loses 100 yUSDC of value with no way to cancel the transaction

## Impact Details
This vulnerability exposes depositors to unexpected value loss when market conditions or transaction ordering causes the exchange rate to change unfavorably. The impact is proportional to the size of preceding transactions relative to the pool size and can be significant during periods of high volatility or when large deposits/withdrawals occur. Users have no mechanism to protect themselves against this risk, which is a standard feature in most modern DeFi protocols.

## Recommendations
1. Add a `minYTokenAmount` parameter to the deposit function:
```solidity
function deposit(
    address asset, 
    uint256 amount, 
    address onBehalfOf, 
    uint256 minYTokenAmount
) public notPaused nonReentrant returns (uint256 yTokenAmount) {
    yTokenAmount = _deposit(asset, amount, onBehalfOf);
    require(yTokenAmount >= minYTokenAmount, "Slippage exceeded");
    return yTokenAmount;
}
```

2. Modify the internal `_deposit` function to check against the minimum amount:
```solidity
function _deposit(
    address asset, 
    uint256 amount, 
    address onBehalfOf, 
    uint256 minYTokenAmount
) internal returns (uint256 yTokenAmount) {
    // ... existing code ...
    yTokenAmount = amount * exchangeRate / (PRECISION);
    require(yTokenAmount >= minYTokenAmount, "Slippage exceeded");
    // ... rest of existing code ...
}
```
