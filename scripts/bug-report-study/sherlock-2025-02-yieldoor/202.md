# Lender will face significant disruption in fund withdrawal when pool utilization is high, violating protocol invariant and Extra Finance design principles

### Summary

The absence of a withdrawal buffer mechanism in `LendingPool.sol` will cause a significant disruption in fund withdrawal for lenders as the protocol blocks withdrawals when utilization exceeds available liquidity, violating the invariant from Yieldoor’s Q&A documentation that users should always receive funds back in the same ratio as deposited. This starkly contrasts with Extra Finance’s documentation (https://docs.extrafi.io/extra_finance/lending/introduction-to-lending), stating `if the utilization rate is very high, it may take some time to be able to withdraw the assets until farmers return them`, and the PFIR model ([Pseudo-Fixed-Interest-Rate Model Extra Finance](https://docs.extrafi.io/extra_finance/lending/pseudo-fixed-interest-rate-model)) noting `Once the utilization hits the threshold, the borrowing interest rate dramatically increases, encouraging borrowers to repay or attracting lenders to deposit funds. This design also creates a buffer for lenders to withdraw their deposits whenever they want`, both implying a robust delay mechanism rather than an outright block.

### Root Cause

In `LendingPool.sol` (https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/LendingPool.sol#L143)`, the strict liquidity check (`require(underlyingTokenAmount <= reserve.availableLiquidity(), "not enough available liquidity")`) abruptly blocks withdrawals when the pool’s available liquidity is insufficient, lacking any buffer or delay mechanism to queue withdrawals until liquidity is restored. This violates the invariant defined in Yieldoor’s Q&A and starkly deviates from Extra Finance’s design principles, where the documentation (https://docs.extrafi.io/extra_finance/lending/introduction-to-lending) states:  `if the utilization rate is very high, it may take some time to be able to withdraw the assets until farmers return them`, and further specifies in the PFIR model: `Once the utilization hits the threshold, the borrowing interest rate dramatically increases, encouraging borrowers to repay or attracting lenders to deposit funds. This design also creates a buffer for lenders to withdraw their deposits whenever they want` (PFIR model ([Pseudo-Fixed-Interest-Rate Model Extra Finance](https://docs.extrafi.io/extra_finance/lending/pseudo-fixed-interest-rate-model)), both highlighting a buffer mechanism that Yieldoor, as a fork, fails to implement.

### Internal Pre-conditions

1. Borrower needs to call `borrow()` to set `reserve.totalBorrows` to be at least 90% of the total deposited amount (e.g., `900 * 1e18 out of 1000 * 1e18`).
2. Lender needs to call `deposit()` to set `reserve.underlyingBalance` to an initial value (e.g., `1000 * 1e18`) before borrowing occurs.



### External Pre-conditions

None – the issue relies solely on internal protocol state and interactions.



### Attack Path

1. Lender calls `deposit(address(underlyingToken), 1000 * 1e18, lender)` to deposit 1000 * 1e18 tokens into the lending pool, receiving ~999e18 yTokens (after 1000 wei burn).
2. Borrower calls `borrow(address(underlyingToken), 900 * 1e18)` to borrow 90% of the pool’s liquidity, reducing `reserve.underlyingBalance` to 100 * 1e18.
3. Lender calls `redeem(address(underlyingToken), yTokenAmount, lender)` immediately after deposit to withdraw all yTokens (~999e18 underlying), expecting ~999e18 tokens back per the invariant from Yieldoor’s Q&A, but the transaction reverts with `not enough available liquidity` due to only 100 * 1e18 being available, undermining the expected functionality and contrasting with Extra Finance’s buffered withdrawal approach.



### Impact

The lender faces significant disruption in withdrawing their funds, violating the invariant from Yieldoor’s Q&A documentation that mandates users should always receive funds back in the same ratio as deposited (excluding minor rounding). This severely impacts the availability of funds for lenders when utilization is high (e.g., 90%), rendering immediate withdrawals impossible and stranding assets until liquidity returns, a critical deviation from user expectations. 

Extra Finance’s documentation outlines a contrasting approach: „if the utilization rate is very high, it may take some time to be able to withdraw the assets until farmers return them”, with adding: „Once the utilization hits the threshold, the borrowing interest rate dramatically increases, encouraging borrowers to repay or attracting lenders to deposit funds. This design also creates a buffer for lenders to withdraw their deposits whenever they want”, both underscoring a buffer mechanism that Yieldoor omits, exacerbating the invariant violation and disrupting core lending functionality as intended in the forked protocol.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.13;

import "forge-std/Test.sol";
import {LendingPool} from "../src/LendingPool.sol";
import {yToken} from "../src/yToken.sol";
import {IERC20} from "@openzeppelin/token/ERC20/IERC20.sol";
import {SafeERC20} from "@openzeppelin/token/ERC20/utils/SafeERC20.sol";
import {DataTypes} from "../src/types/DataTypes.sol";

contract MockERC20 is IERC20 {
    using SafeERC20 for IERC20;

    mapping(address => uint256) public override balanceOf;
    mapping(address => mapping(address => uint256)) public override allowance;
    uint256 public totalSupply;

    string public name = "Mock Token";
    string public symbol = "MTK";
    uint8 public decimals = 18;

    constructor() {
        balanceOf[msg.sender] = 2000 * 1e18; // Initial supply for both scenarios
        totalSupply = 2000 * 1e18;
    }

    function transfer(address to, uint256 amount) external override returns (bool) {
        require(balanceOf[msg.sender] >= amount, "Insufficient balance");
        balanceOf[msg.sender] -= amount;
        balanceOf[to] += amount;
        emit Transfer(msg.sender, to, amount);
        return true;
    }

    function approve(address spender, uint256 amount) external override returns (bool) {
        allowance[msg.sender][spender] = amount;
        emit Approval(msg.sender, spender, amount);
        return true;
    }

    function transferFrom(address from, address to, uint256 amount) external override returns (bool) {
        require(balanceOf[from] >= amount, "Insufficient balance");
        require(allowance[from][msg.sender] >= amount, "Insufficient allowance");
        balanceOf[from] -= amount;
        balanceOf[to] += amount;
        allowance[from][msg.sender] -= amount;
        emit Transfer(from, to, amount);
        return true;
    }
}

contract LendingPoolLowLiquidityTest is Test {
    MockERC20 public underlyingToken;
    LendingPool public lendingPool;
    address public owner = address(this);
    address public lender = address(1);
    address public borrower = address(2);
    address public yTokenAddress;

    function setUp() public {
        underlyingToken = new MockERC20();
        lendingPool = new LendingPool();
        lendingPool.initReserve(address(underlyingToken));
        lendingPool.setLeverager(borrower);
        yTokenAddress = lendingPool.getYTokenAddress(address(underlyingToken));
    }

    function testImmediateWithdrawWithHighUtilization() public {
        // Lender receives 1000 tokens from owner
        underlyingToken.transfer(lender, 1000 * 1e18);

        // Lender deposits 1000 tokens into the pool
        vm.startPrank(lender);
        underlyingToken.approve(address(lendingPool), 1000 * 1e18);
        lendingPool.deposit(address(underlyingToken), 1000 * 1e18, lender);

        // Lender approves yTokens for LendingPool
        IERC20(yTokenAddress).approve(address(lendingPool), type(uint256).max);
        vm.stopPrank();

        // Borrower borrows 900 tokens, setting utilization to 90%
        vm.startPrank(borrower);
        lendingPool.borrow(address(underlyingToken), 900 * 1e18);
        vm.stopPrank();

        // Immediate withdrawal attempt of all yTokens by lender
        // Expected to fail, violating invariant: "should always get funds back in the same ratio"
        vm.startPrank(lender);
        uint256 yTokenAmount = IERC20(yTokenAddress).balanceOf(lender);
        vm.expectRevert("not enough available liquidity");
        lendingPool.redeem(address(underlyingToken), yTokenAmount, lender);
        vm.stopPrank();

        // Verify utilization rate is approximately 90%
        DataTypes.ReserveData memory reserve = getReserve(address(underlyingToken));
        uint256 totalLiquidity = reserve.underlyingBalance + reserve.totalBorrows; // 1000e18
        uint256 utilizationRate = (reserve.totalBorrows * 1e27) / totalLiquidity; // ~0.9e27 (90%)
        assertApproxEqAbs(
            utilizationRate,
            0.9e27,
            1e24,
            "Utilization rate should be approximately 90%"
        );

        // Variant: No borrowing (0% utilization) to confirm invariant holds when liquidity is full
        LendingPool newPool = new LendingPool(); // New pool for isolation
        newPool.initReserve(address(underlyingToken));
        vm.startPrank(owner);
        underlyingToken.transfer(lender, 1000 * 1e18);
        vm.stopPrank();
        vm.startPrank(lender);
        underlyingToken.approve(address(newPool), 1000 * 1e18);
        newPool.deposit(address(underlyingToken), 1000 * 1e18, lender);
        address newYTokenAddress = newPool.getYTokenAddress(address(underlyingToken));
        IERC20(newYTokenAddress).approve(address(newPool), type(uint256).max);
        yTokenAmount = IERC20(newYTokenAddress).balanceOf(lender);
        uint256 received = newPool.redeem(address(underlyingToken), yTokenAmount, lender);
        assertApproxEqAbs(
            received,
            1000 * 1e18 - 1000,
            100,
            "Should receive deposited amount minus burn, per invariant"
        );
        vm.stopPrank();
    }

    function getReserve(address asset) private view returns (DataTypes.ReserveData memory) {
        (, bytes memory data) = address(lendingPool).staticcall(
            abi.encodeWithSignature("reserves(address)", asset)
        );
        return abi.decode(data, (DataTypes.ReserveData));
    }
}
```

### Mitigation

To comply with the invariant from Yieldoor’s Q&A and align with Extra Finance’s approach as described in both the lending introduction and PFIR model, implement a pending withdrawal mechanism in `LendingPool.sol`. When liquidity is insufficient (e.g., `underlyingTokenAmount > reserve.availableLiquidity()`), queue the withdrawal request in a mapping (e.g., `mapping(address => uint256) public pendingWithdrawals`), and process it when liquidity returns via repayments (`repay`) or new deposits (`deposit`). Update `redeem` to handle queued requests instead of reverting immediately, ensuring lenders can withdraw their deposits "whenever they want," as intended by Extra Finance’s PFIR design.
