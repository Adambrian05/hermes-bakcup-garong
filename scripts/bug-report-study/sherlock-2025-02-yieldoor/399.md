# Positions can be opened with unauthorized tokens leading to trapped funds


## Summary
The `enableTokenAsBorrowed()` function in `Leverager.sol` is intended to control which tokens can be borrowed from the LendingPool. However, the current implementation only sets token approvals without proper borrowing controls. This allows users to open leveraged positions with unauthorized tokens, but these positions cannot be withdrawn or liquidated, potentially leading to trapped funds.

## Root Cause
In [`Leverager.sol#L503-L508`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L503-L508), the `enableTokenAsBorrowed()` function only handles token approval:

```solidity
    /// @notice Allows users to borrow a certain token from the LendingPool.
    /// @param asset Asset to be enabled for borrows.
    /// @dev Needs to be called for a token in case no enabled vault has it one of its underlying tokens.
    function enableTokenAsBorrowed(address asset) external onlyOwner {
        IERC20(asset).forceApprove(lendingPool, type(uint256).max);
    }
```

The function's documentation indicates it should control borrowing permissions, but the implementation only sets approvals. Users can still borrow unauthorized tokens through `openLeveragedPosition()`:

```solidity
    function openLeveragedPosition(LeverageParams calldata lp) external nonReentrant returns (uint256 _id) {
        require(vaultParams[lp.vault].leverageEnabled, "leverage not enabled");
        ..............................................

        {
            // we first borrow the maximum amount the user is willing to borrow. Any unused within the swaps is later repaid.
->          ILendingPool(lendingPool).borrow(lp.denomination, lp.maxBorrowAmount);

            IMainnetRouter.ExactOutputParams memory swapParams;

            // Only important thing to verify here is that the tokenIn is NOT a vault share token.
            // Otherwise, attacker could utilize this to swap out all of the share tokens out of here.
            // We do not verify here that the output tokens is one of the lp tokens. If for some reason it isn't
            // The transaction will later revert within `pushFunds`
            if (a0 > lp.amount0In && up.token0 != lp.denomination) {
                swapParams = abi.decode(lp.swapParams1, (IMainnetRouter.ExactOutputParams));

                address tokenIn = _getTokenIn(swapParams.path);
                require(tokenIn == lp.denomination, "token should be denomination");

                IERC20(tokenIn).forceApprove(swapRouter, swapParams.amountInMaximum);

                swapParams.amountOut = a0 - lp.amount0In;
                IMainnetRouter(swapRouter).exactOutput(swapParams);
                IERC20(tokenIn).forceApprove(swapRouter, 0);
            }

            if (a1 > lp.amount1In && up.token1 != lp.denomination) {
                swapParams = abi.decode(lp.swapParams2, (IMainnetRouter.ExactOutputParams));
                address tokenIn = _getTokenIn(swapParams.path);
                require(tokenIn == lp.denomination, "token should be denomination 2 ");
                IERC20(tokenIn).forceApprove(swapRouter, swapParams.amountInMaximum);

                swapParams.amountOut = a1 - lp.amount1In;
                IMainnetRouter(swapRouter).exactOutput(swapParams);
                IERC20(tokenIn).forceApprove(swapRouter, 0);
            }
        }

        if (delta0 > 0) ILendingPool(lendingPool).pushFunds(up.token0, delta0);
        if (delta1 > 0) ILendingPool(lendingPool).pushFunds(up.token1, delta1);

->      uint256 denomBalance = IERC20(lp.denomination).balanceOf(address(this));
->      ILendingPool(lendingPool).repay(lp.denomination, denomBalance);

        ...........................................

        return _id;
    }
```

Critical issues:
1. No check if token is authorized for borrowing
2. `denomBalance` can be zero if user swaps all denomination tokens
3. `repay()` call succeeds with zero balance, allowing unauthorized position to be opened

## Internal pre-conditions
1. Owner has not enabled borrowing for specific token
2. Token has approval set for LendingPool

## External pre-conditions
None required - vulnerability can be exploited immediately

## Attack Path
1. User identifies unauthorized token with LendingPool approval
2. Opens leveraged position using this token as denomination
3. Swaps entire borrowed amount to other tokens
4. Position is created successfully because repay with zero balance doesn't revert
5. User cannot withdraw position
6. Position cannot be liquidated
7. Funds become trapped

## Impact
1. Users can lose funds by creating positions with unauthorized tokens
2. Positions become permanently locked
3. Protocol cannot liquidate bad positions
4. Increased risk of bad debt accumulation

## Mitigation
Add proper borrowing control flags:
1. Add mapping for authorized tokens
2. Implement permission check in borrow function
3. Ensure zero-amount repayments are handled correctly
