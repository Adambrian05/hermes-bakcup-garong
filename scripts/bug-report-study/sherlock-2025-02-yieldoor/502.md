# # Incorrect withdrawal amount reduction when the denomination token is `token1`

### Summary

When withdrawing a position via the `Leverager::withdraw()` function, if the borrowed token is `token0` or `token1`, the function reduces the amount to pay to the depositor.

However, when the borrowed token is `token1`, the withdraw amount is wrongly reduced.

### Root Cause

[Leverager.sol#L232](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L232)
```solidity
    function withdraw(WithdrawParams calldata wp) external nonReentrant {
        ... ...
        // In case either of the tokens is denomination token, we directly take from it.
        if (borrowed == up.token0) {
            uint256 repayFromWithdraw = amountOut0 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
            amountOut0 -= repayFromWithdraw;
        } else if (borrowed == up.token1) {
@>          uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
            owedAmount -= repayFromWithdraw;
            amountOut1 -= repayFromWithdraw;
        }
        ... ...

        if (amountOut0 > 0) IERC20(up.token0).safeTransfer(msg.sender, amountOut0);
        if (amountOut1 > 0) IERC20(up.token1).safeTransfer(msg.sender, amountOut1);
        ... ...
    }
```

As cana be seen from the marked line above, `repayFromWithdraw` is set as `amountOut0` instead of `amountOut1`.

### Internal pre-conditions

The denomination token should be `token1`.

### External pre-conditions

*None*

### Attack Path

Just withdrawing will reveal the vulnerability.

### Impact

This vulnerability can significantly reduce the `token1` amount to refund if `amountOut0` > `amountOut1`.

If the decimals of `token0` is greater than `token1`'s, the withdrawal will fail due to underflow error.
