# Inadequate handling of deflationary or Non-Standard tokens

**Description:** The `LendingPool.deposit` function assumes that transferring an `amount` of an ERC20 will result in that exact amount being received and credited​. It uses `IERC20.safeTransferFrom(msg.sender, reserve.yTokenAddress, amount)` and then unconditionally treats `amount` as deposited value, updating `reserve.underlyingBalance += amount` and minting the corresponding yTokens​. Many tokens (especially well-known ones) follow this behavior, but deflationary tokens or tokens with transfer fees break this assumption. For example, a token might burn 1% on every transfer – in that case, sending `amount=100` will result in only 99 tokens actually arriving. The Yieldoor code currently has no check for `actualReceived` vs. `amount`. It also doesn’t handle tokens that don’t return a boolean on transfer (e.g., USDT returns void) – though OpenZeppelin’s SafeERC20 handles no-return by assuming success, it cannot detect partial success like a fee-on-transfer scenario.


**Impact:** If a deflationary token is ever enabled as a reserve, deposits will mis-credit users with more value than actually received. The internal accounting (`underlyingBalance` and yToken supply) will think the pool has the full `amount`, while fewer tokens actually arrived in the yToken contract. This can lead to two bad outcomes:

- Pool Insolvency: A user could deposit a deflationary token and later withdraw the “full” credited amount, effectively pulling out tokens that were never actually deposited (the difference comes out of the pool’s reserves, hurting other lenders). For instance, deposit 100 (with 99 actually received), then borrow against or withdraw based on 100 credit – the missing 1 is a loss absorbed by the pool. Over multiple deposits, these losses accumulate and could be exploited to drain a portion of the pool’s funds.

- Stuck Funds / Inability to Withdraw: In some cases, the accounting mismatch may cause `redeem` operations to revert. Using the same example, if the pool thinks it has 100 but only 99 tokens exist, a full withdrawal of 100 would fail the underlying transfer (or hit a require like “not enough available liquidity” if properly checked). This traps liquidity and breaks the redeem function for that asset until governance intervenes.

Even with standard tokens like USDT (which doesn’t follow return conventions), the SafeERC20 library’s `safeTransferFrom` will succeed (since USDT doesn’t revert on success), but if any token returns `false` without reverting, the SafeERC20 wrapper would catch it and revert the deposit. The primary concern is the fee-on-transfer or rebasing tokens which can silently cause balance disparities. Without explicit safeguards, an attacker could repeatedly deposit and withdraw a deflationary token to systematically siphon the fee amount from the pool (each cycle taking a small percentage). This is an economic attack vector that can lead to loss of funds from the reserves.


**Recommendation:** If the protocol does not intend to support such tokens, explicitly forbid them. The owner, when calling `initReserve`, could be restricted to whitelist only known standard tokens (e.g., stablecoins, WETH, etc.). Document in the UI/frontend which tokens are supported, to prevent users from attempting to deposit problematic tokens. This is the simplest solution: treat it as a governance responsibility to not add deflationary tokens.
If support for any such token is needed, implement actual received amount checks in deposit and similar functions.

```solidity
uint256 balanceBefore = IERC20(asset).balanceOf(yTokenAddr);
IERC20(asset).safeTransferFrom(msg.sender, yTokenAddr, amount);
uint256 balanceAfter = IERC20(asset).balanceOf(yTokenAddr);
uint256 actualReceived = balanceAfter - balanceBefore;

```
Then use `actualReceived` for updating `underlyingBalance` and computing yToken to mint. If `actualReceived < amount`, one could either: mint fewer yTokens proportional to what actually came in, or revert the transaction if the difference is unacceptable (to prevent user confusion or gaming). Given Yieldoor’s model, minting based on actualReceived is more robust – this way, the user only gets credit for what was truly deposited. Similarly, on withdraw/redemption, use the actual current exchange rate which automatically handles any lost tokens (the yToken exchange rate would increase slightly if some tokens were burned on deposit, spreading that loss across all holders rather than letting a single user exploit it).
