# Attacker can DOS rebalancing and compounding operations by manipulating pool observations


## Summary
The `checkPoolActivity()` function's stability check uses observation indices instead of time-based intervals, allowing an attacker to deny rebalancing and compounding operations through rapid consecutive swaps that manipulate pool observations.

## Root Cause
In [`Strategy.sol#L310-L342`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310-L342), the `checkPoolActivity()` function validates pool stability by iterating through observation indices rather than time intervals:

```solidity
    function checkPoolActivity() public view returns (bool) {
        (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();

        uint32 lookAgo = uint32(block.timestamp) - twap;

        (uint32 nextTimestamp, int56 nextCumulativeTick,,) = IUniswapV3Pool(pool).observations(currentIndex);

        int24 nextTick = tick;

        for (uint16 i = 1; i <= observationCardinality; i++) {
            uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
            (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
            if (timestamp == 0) {
                revert("timestamp 0");
            }

            tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));

            (nextTimestamp, nextCumulativeTick) = (timestamp, tickCumulative);
            int24 delta = nextTick - tick;

            if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
                return false;
            }

            if (timestamp < lookAgo) {
                return true;
            }
            nextTick = tick;
        }

        return false;
    }
```

The function checks tick deviations between consecutive observations without considering the time intervals between them. This allows an attacker to create artificial volatility by executing large swaps in consecutive blocks, causing the function to return false and preventing rebalancing operations.

## Internal pre-conditions
1. `maxObservationDeviation` is set to a finite value
2. Pool has active positions that require rebalancing or compounding

## External pre-conditions
1. Pool has sufficient liquidity to allow significant swaps
2. Attacker has access to capital for executing large swaps

## Attack Path
1. Attacker monitors for pending rebalance or compound transactions
2. When detected, attacker executes two large swaps in consecutive blocks:
   - Block N: Large swap in one direction
   - Block N+1: Reverse swap in opposite direction
3. These swaps create tick deviations larger than `maxObservationDeviation`
4. `checkPoolActivity()` returns false when evaluating consecutive observations
5. Rebalancing and compounding operations are blocked for the duration of `twap`

## Impact
The vulnerability allows an attacker to:
1. Block protocol's critical rebalancing operations
2. Prevent compounding of earned fees
3. Force the protocol to operate with suboptimal position ranges
4. Potentially cause loss of yield for users

## Mitigation
Modify `checkPoolActivity()` to use time-based stability checks:
1. Sample pool state at fixed time intervals shorter than `twap`
2. Calculate average tick changes over these intervals
3. Only consider pool unstable if average deviation exceeds threshold over multiple intervals
