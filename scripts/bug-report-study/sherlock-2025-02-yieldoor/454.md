# Forced Balance Ratio in Deposit Function Prevents One-Sided Deposits and Custom Token Ratio Inputs

## Summary
The Vault [contract's `_calcDeposit` function forces depositors to provide tokens in the same ratio](https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Vault.sol#L128-L150) as the strategy's current balance. This design prevents users from making one-sided deposits (depositing only one token) or depositing tokens in their preferred ratio. The issue is particularly problematic for token pairs with significantly different values (like WBTC/USDC), making deposits unnecessarily restrictive and capital-inefficient. The issue is also concerning because as the vault's token0 and token1 composition in Uniswap V3 is adjusted with price change, it needs to encourage flexible deposits that allows it maintain an optimal LP position.

## Vulnerability Details
The vulnerability exists in the `_calcDeposit` function where the actual deposit amounts are calculated. When the strategy already has both tokens (the normal case after initial deposit), the function uses cross products to determine the deposit amounts:

```solidity
uint256 cross0 = depositAmount0 * bal1;
uint256 cross1 = depositAmount1 * bal0;
uint256 cross = cross0 > cross1 ? cross1 : cross0;
require(cross > 0, "cross");

// Round up amounts
amount0 = (cross - 1) / bal1 + 1;
amount1 = (cross - 1) / bal0 + 1;
```

This calculation effectively ignores the user's desired deposit ratio and instead forces deposits to match the strategy's existing token ratio. The issue occurs because:

1. The minimum cross product (`cross`) is used to calculate both token amounts
2. Both calculations use the same `cross` value but divide by different balance values
3. This maintains the existing token ratio regardless of what the user inputs for `depositAmount0` and `depositAmount1`

For example, if the strategy holds equal amounts of token0 and token1, the calculated `amount0` and `amount1` will always be equal, even if the user wanted to deposit more of one token than the other.

## Proof of Concept
Consider a scenario with a WBTC/USDC pool where:
- Strategy balance: 10 WBTC (`bal0`) and 200,000 USDC (`bal1`)
- User wants to deposit: 1 WBTC and 5,000 USDC

Here's what happens:
```solidity
cross0 = 1 WBTC * 200,000 USDC = 200,000
cross1 = 5,000 USDC * 10 WBTC = 50,000
cross = min(200,000, 50,000) = 50,000

amount0 = (50,000 - 1) / 200,000 + 1 = 0.25 WBTC (rounded up)
amount1 = (50,000 - 1) / 10 + 1 = 5,000 USDC
```

The user intended to deposit 1 WBTC and 5,000 USDC, but the contract will only accept 0.25 WBTC and 5,000 USDC. The user's desired deposit ratio is completely ignored, and their deposit is forced to match the strategy's existing ratio (1 WBTC : 20,000 USDC). 

If the user tries a one-sided deposit of just 1 WBTC:
```solidity
cross0 = 1 WBTC * 200,000 USDC = 200,000
cross1 = 0 USDC * 10 WBTC = 0
cross = min(200,000, 0) = 0

The require(cross > 0, "cross") will revert the transaction
```
This is dangerous because times where the vault position contains significantly token0 or token1 due to price movement, users will be unable to deposit more of the lacking tokens to help the protocol maintain an optimal LP position. 

## Impact Details
This restriction significantly limits the flexibility of the vault for users. It prevents one-sided deposits which are common in many DeFi protocols and particularly useful for rebalancing portfolios. The forced ratio also creates inefficient capital usage, as users must provide both tokens in specific proportions regardless of their holdings or market conditions.

## Tools Used
Manual

## Recommendations
Consider implementing these changes to improve the deposit functionality:

1. **Allow one-sided deposits**: Modify the deposit function to accept deposits of just one token by swapping a portion within the strategy.

2. **Accept any deposit ratio**: Change the calculation to respect the user's specified deposit ratio while still calculating fair shares based on the total value contributed:
```solidity
// Example approach
if (depositAmount0 > 0 && depositAmount1 > 0) {
    // Calculate shares based on the total value of both tokens
    shares = calculateSharesBasedOnTotalValue(depositAmount0, depositAmount1, bal0, bal1);
    amount0 = depositAmount0;
    amount1 = depositAmount1;
} else if (depositAmount0 > 0) {
    // One-sided deposit of token0
    amount0 = depositAmount0;
    amount1 = 0;
    shares = calculateSharesForOneSidedDeposit(amount0, 0, bal0, bal1);
} else if (depositAmount1 > 0) {
    // One-sided deposit of token1
    amount0 = 0;
    amount1 = depositAmount1;
    shares = calculateSharesForOneSidedDeposit(0, amount1, bal0, bal1);
}
```

3. **Include price awareness**: Incorporate token prices in share calculations to ensure fair distribution when token values differ significantly.
