# Incorrect Vesting Liquidity Calculation in Strategy


## **Summary**  
The Strategy contract miscalculate vested liquidity withdrawals by using the initial liquidity of a vesting position instead of the remaining liquidity after withdrawals. This problem allow user or the protocol to drain the position faster than intended violating the vesting schedule.


## Description
Vesting positions are designed to distribute liquidity over time  linearly over a 30-day period. When a user or the protocol withdraws a portion of the vested liquidity, the calculation should be based on the remaining unvested liquidity at the time of withdrawal. However, the current code use the initial liquidity of the position for all calculations ignoring withdrawals. This result in over-vesting and unfair distribution.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L459-L477

## Vulnerability Details 

**1. Vesting Position Initialization**  

When a vesting position is created through `addVestingPosition`, liquidity is minted and stored in the `vestPosition` struct:  
```solidity
vp.initialLiquidity = liquidity; //@audit: Initial liquidity (1000 units)
vp.remainingLiquidity = liquidity; //@audit: Initially should be equal to initialLiquidity
vp.startTs = block.timestamp;
vp.endTs = block.timestamp + _duration; //@audit: Vesting period (100 seconds)
```

**2. Faulty Withdrawal Calculation**  
The `_withdrawPartOfVestingPosition` function calculate withdrawals using `initialLiquidity` instead of `remainingLiquidity`:  
```solidity

uint128 liquidityToRemove = lastValid == vp.endTs
    ? vp.remainingLiquidity
    : uint128(vp.initialLiquidity * (lastValid - vp.lastUpdate) / (vp.endTs - vp.startTs));
```
- but the **problem** is after withdrawals, `remainingLiquidity` decrease but withdrawals still reference `initialLiquidity` leading to over-vesting.

## **Proof of Concept: Exploitation Scenario**

**Step 1: Create Vesting Position**  
nitial Liquidity: `initialLiquidity = 1000`  
Vesting Duration: `endTs - startTs = 100 seconds`  

**Step 2: First Withdrawal at 50 Seconds**  
Time Elapsed is `50 seconds`  
Expected Withdrawal is`500` (50% of `remainingLiquidity`).  
Actual Withdrawal (issue):  
  ```solidity
  liquidityToRemove = 1000 * 50 / 100 = 500 //@audit: Use initialLiquidity
  vp.remainingLiquidity = 1000 - 500 = 500
  ```  
  -**Result**: The withdrawal is okay but the code use `initialLiquidity` instead of `remainingLiquidity`.

**Step 3: Second Withdrawal at 75 Seconds**  
Time Elapsed since the Last Withdrawal is `25 seconds`  
Expected Withdrawal is `25% of 500 = 125`  
Actual Withdrawal (Flaw Code):  
  ```solidity
  liquidityToRemove = 1000 * 25 / 100 = 250 //@audit: Still use initialLiquidity
  vp.remainingLiquidity = 500 - 250 = 250
  ```  
 **Result**: User withdraw 250 instead of 125 stealing an extra 125 units.

**Step 4: Final State is as follows**  
Total Withdrawn: `500 + 250 = 750`  
Expected Total: `500 + 125 = 625`  
Outcome: 125 units (20%) is drained prematurely.


##  **Impact**  
Users/protocols receive more liquidity than entitled.  
when exploited, the vault’s liquidity reserves deplete faster than designed destabilizing the system.  


## Recommendation  
Change the  `_withdrawPartOfVestingPosition` to use `remainingLiquidity` for calculation:  
```solidity
uint128 liquidityToRemove = lastValid == vp.endTs
    ? vp.remainingLiquidity
    : uint128(vp.remainingLiquidity * (lastValid - vp.lastUpdate) / (vp.endTs - vp.startTs));
```

**Explanation**  
When the First Withdrawal 50 seconds is:
  ```solidity
  liquidityToRemove = 1000 * 50 / 100 = 500 (so the remainingLiquidity = 500)
  ```  
Then the Second Withdrawal at 75 seconds is:
  ```solidity
  liquidityToRemove = 500 * 25 / 100 = 125 (so the remainingLiquidity = 375)
  ```  
 Then the correct total withdrawal = 500 + 125 which is 625 aligning with the vesting schedule.
