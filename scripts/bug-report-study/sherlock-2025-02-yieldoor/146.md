# First depositor unfairly loses significant funds, which makes their funds stuck in the contract

### Summary

An unnecessary subtraction by 1000 in `Vault.sol` makes first depositer unfairly lose significant amount of funds.
This subtraction doesn't serve its intended purpose and can be removed ( more details in root cause ).

### Root Cause

In [`Vault.sol:67`](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L67), the vault prevents the first depositor from stealing funds by minting to the BURN address, this is a good practice.

In [Line 133](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L133) however, it incorrectly subtracts 1000 from the shares to be minted. It seems like the developer made the assumption that we are subtracting from the total supply , if that was the case , we would need to subtract 1000 to eliminate the funds that were minted to the BURN address, but in this case ( subtracting from the amounts desired ) no subtraction is necessary since we want to use the amounts desired directly and not make the first depositor unfairly loses 1000 tokens.

### Internal Pre-conditions

This happens only on the first deposit.

### External Pre-conditions

N/A

### Attack Path

1. First depositor deposits `deposit(1001, 1001, 0, 0);` for example.
2. Only 1 share is minted for him.
3. When he withdraws he will get 1 token0 and 1 token1 , which is significantly less that what he deposited.

### Impact

- Significant loss for first depositor ( 99.9% if he deposited 1001 tokens ).
- Forces the first depositor to deposit more than 1000 tokens since this line `shares = (amount0 > amount1 ? amount0 : amount1) - (1000);` would cause an underflow and revert.
***Note*** : If it's intended to force the first depositor to deposit more than 1000 tokens, then just use a require statement, which checks for that without making the user loses funds significantly.
- The users' funds will become stuck in the contract, inflating the balances and affecting how other users' shares are calculated, since all share are calculated by dividing by bal1 or bal0 ( line 149 and line 136 ).
