# Incorrect Decimal Usage in USD Value Calculation in `Leverager._calculateTokenValues()`

### Summary

Incorrect decimal usage in `_calculateTokenValues()` will cause an inaccurate USD value calculation for the protocol as the function will misrepresent asset values when converting tokens if one of the token doesnt have a chainlink price feed. `usdValue` is expected to have `18` decimals; however, due to this issue, it may be incorrectly overestimated or underestimated.

### Root Cause

The `_calculateTokenValues()` function is designed to compute the USD value of two tokens in a vault.

```solidity
    function _calculateTokenValues(address token0, address token1, uint256 amount0, uint256 amount1, uint256 price)
        internal
        view
        returns (uint256 usdValue)
    {
        uint256 chPrice0;
        uint256 chPrice1;
        uint256 decimals0 = 10 ** ERC20(token0).decimals();
        uint256 decimals1 = 10 ** ERC20(token1).decimals();
        if (IPriceFeed(pricefeed).hasPriceFeed(token0)) {
            chPrice0 = IPriceFeed(pricefeed).getPrice(token0);
            usdValue += amount0 * chPrice0 / decimals0;
        }
        if (IPriceFeed(pricefeed).hasPriceFeed(token1)) {
            chPrice1 = IPriceFeed(pricefeed).getPrice(token1);
            usdValue += amount1 * chPrice1 / decimals1;
        }

        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
@>          usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1; // @audit Use decimals0 instead of decimals1
        } else if (chPrice1 == 0) {
@>          usdValue += amount1 * PRECISION / price * chPrice0 / decimals0; // @audit Use decimals1 instead of decimals0
        }

        return usdValue;
    }
```

The protocol requires that at least one of these tokens has a trustworthy price feed, either from Chainlink or a highly liquid UniV3 pool. Price feeds are expected to return values in 18 decimals.

The following line of code handles scenarios where one of the tokens (token0 or token1) does not have a direct price feed.

```solidity
        // If chPrice0 is 0, it means token0 doesnt have a pricefeed.
        // Therefore, convert it token1 and from there, convert it to USD
        if (chPrice0 == 0) {
@>          usdValue += (amount0 * price / PRECISION) * chPrice1 / decimals1;
        } else if (chPrice1 == 0) {
@>          usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }
```

If `token0` lacks a price feed (`chPrice0 == 0`), the code converts `token0` to `token1` using the TWAP price (price) and then converts the result to USD using token1's price feed (`chPrice1`).

Similarly, if `token1` lacks a price feed (`chPrice1 == 0`), the code converts `token1` to `token0` using the inverse of the TWAP price and then converts the result to USD using token0's price feed (`chPrice0`).

The core issue lies in the incorrect handling of decimal normalization when calculating the USD value of tokens. Specifically, when token0 lacks a price feed, the function uses `decimals1` instead of `decimals0` to normalize `amount0`. 

This results in an inaccurate USD value calculation, as the conversion should be based on the decimal precision of `token0`, not `token1`. This miscalculation can lead to incorrect financial assessments and potential leveraging errors within the protocol.




### Internal Pre-conditions

1. At least one of the tokens does not have a Chainlink price feed.
2. The two tokens must have different decimal precisions.

### External Pre-conditions

1. Price feed must not be available for at least one of the tokens.

### Attack Path

Lets assume

- `token0`: USDC, which has 6 decimals and a price feed (`chPrice0`).
- `token1`: An 18-decimal token without a direct price feed (`chPrice1 == 0`).

The function attempts to convert `token1` to `token0` using the inverse of the TWAP price (price).

```solidity
        else if (chPrice1 == 0) {
@>          usdValue += amount1 * PRECISION / price * chPrice0 / decimals0;
        }
```

- `amount1 * PRECISION / price`: Converts `amount1` from `token1` to `token0` using the inverse TWAP price.
- `* chPrice0`: Converts the result to USD using `token0`’s price feed.
- `/ decimals0`: Incorrectly normalizes the result using `token0`’s 6-decimal factor.

**Calculation:**

1. `amount1` (token1) has 18 decimals.
2. `PRECISION = 10^30`.
3. `price` (inverse TWAP) has 30 decimals.
4. `chPrice0` (USDC price in USD) has 18 decimals.
5. `decimals0 = 10^6` (since USDC has 6 decimals).

Let’s break down the calculation step by step:
￼
`(10^18 * 10^30 / 10^30) * (10^18 / 10^6) = 10^30` 

The expected result should have 18 decimals (to maintain consistency with `usdValue`). However, due to incorrect division by `decimals0` (`10⁶` instead of `10¹⁸`), the final value increased to `10³⁰` decimals, making `usdValue` larger than expected.
￼


### Impact

The incorrect decimal handling in `_calculateTokenValues()` can lead to significant financial inaccuracies across the protocol, affecting `leverage`, `withdrawals`, and `liquidation` processes.

- [**openLeveragedPosition**](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103):
Miscalculating the initial collateral value in USD can lead to incorrect leverage ratios. This might allow users to open positions with higher/lower leverage than intended, increasing the risk of liquidation and potential losses for the protocol/user.

- [**withdraw**](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L209C14-L209C22):
Inaccurate USD value calculations during withdrawals can result in users withdrawing more or less collateral than they should. This can lead to imbalances in the vault.

- [**isLiquidateable**](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L385C14-L385C29):
Incorrect USD value assessments can cause the protocol to misjudge the liquidation status of positions. This might result in positions being liquidated prematurely or not being liquidated when they should be, leading to potential bad debt or unfair liquidations.
