# Incorrect Fee Collection Due to Restricted Tick Range

### Summary

The collectFees() function incorrectly calls collectPositionFees() using an unintended tick range:

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L167

Instead of using vestPosition.tickUpper, it mistakenly uses mainPosition.tickUpper. This restricts the fee collection range, potentially leading to undercollection of fees and lower-than-expected distributions to users or the protocol.

### Root Cause

The issue originates from an incorrect parameter in collectFees(). The function should collect fees within the full vesting position’s range (vestPosition.tickLower to vestPosition.tickUpper), but it mistakenly stops at mainPosition.tickUpper. If mainPosition.tickUpper is lower than vestPosition.tickUpper, this results in fewer collected fees than intended.

### Internal Pre-conditions

-The contract must have an active vesting position (ongoingVestingPosition == true).
-The rebalance() function must have been called, modifying mainPosition.tickUpper.
-The collectFees() function must be called.

### External Pre-conditions

-The protocol must have liquidity positions generating fees.
-An attacker or privileged user must be able to trigger collectFees().

### Attack Path

The attacker ensures there is a mismatch between vestPosition.tickUpper and mainPosition.tickUpper.
They trigger the collectFees() function.
The function collects fees only up to mainPosition.tickUpper, leaving some fees uncollected.
This may lead to fee inefficiency, affecting protocol or user rewards.

### Impact

Fee undercollection: Some earned fees remain unclaimed, leading to reduced protocol revenue or user earnings.
Financial inefficiency: Users and the protocol may not receive their full share of accumulated fees.

### PoC

_No response_

### Mitigation

Modify the collectFees() function to correctly collect fees only within the vesting position’s range:
collectPositionFees(vestPosition.tickLower, vestPosition.tickUpper);
