# Imbalanced Initial Deposit in Vault Causes Inability to Deposit Second Token

### Summary

The _calcDeposit function does not handle the case where token1 is not deposited initially, causing the vault to become permanently unable to accept deposits of token1 for all users, as any depositor can trigger this by depositing only token0 in the first deposit. The same issue can happen the other way around as well when token0 is not initially deposited.

### Root Cause

The _calcDeposit function assumes that if totalSupply > 0, at least one of bal0 or bal1 will be non-zero. However, if the first deposit only includes token0, bal1 will remain 0, and subsequent deposits will only be able to deposit token0. This is because the function falls into the else if (bal1 == 0) branch, which only allows deposits of token0.
https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L119-L151 

### Internal Pre-conditions

1. The vault has a total supply of 0 (i.e., no initial deposits).

2. The first deposit includes only token0 and no token1.

### External Pre-conditions

None

### Attack Path

1. A user deposits only token0 (e.g., 100 units) as the first deposit.

2. The vault mints shares based on token0 and sets bal0 to 100, while bal1 remains 0.

3. Subsequent users attempt to deposit token1, but the _calcDeposit function only allows deposits of token0 because bal1 == 0.

4. The vault becomes permanently unable to accept deposits of token1, leading to liquidity imbalance and reduced functionality.

### Impact

The vault becomes unable to accept deposits of token1 if the first deposit only includes token0. This limits the protocol's functionality and could lead to liquidity imbalances, affecting all users who wish to deposit token1.

_No response_

### Mitigation

Require Initial Deposit of Both Tokens: Modify the vault to require an initial deposit of both token0 and token1 to ensure both balances are non-zero from the start.
