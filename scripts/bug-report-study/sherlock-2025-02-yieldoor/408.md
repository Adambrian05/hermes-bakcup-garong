# Leverager.withdraw() will incorrectly use token0 for token1 debt repayment, causing user fund loss

### Summary

A critical logic error in the repayment calculation will cause a severe double-counting bug for users as the Leverager contract will incorrectly use token0 for token1 debt repayment while also reducing the token1 withdrawal amount, effectively taking both tokens from the user.



### Root Cause

In [Leverager.sol:231-235](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L231-L235) the repayment calculation for token1 borrowers incorrectly uses amountOut0 when amountOut1 < owedAmount:
```solidity
else if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut0 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```


### Internal Pre-conditions

1. User must have opened a leveraged position using token1 (USDC) as the borrowed denomination
2. User must attempt to withdraw an amount where the available token1 (amountOut1) is less than the owed amount
3. The position must have sufficient collateral value to allow withdrawal

### External Pre-conditions

None required

### Attack Path

1. User opens a leveraged position borrowing token1 (USDC)
2. Some interest accrues on the borrowed amount
3. User attempts to partially withdraw from their position
4. The withdrawal function calculates that the token1 (USDC) available from withdrawal is less than what is owed
5. Instead of using the available token1, it incorrectly uses the token0 (WBTC) amount for repayment
6. The contract still reduces the token1 amount as if it had been used for repayment
7. User receives significantly less tokens than expected, as both token0 and token1 are affected

### Impact

The user suffers a double loss during withdrawal:

1. Their token0 (WBTC) is effectively used for repayment without being converted to token1
2. Their token1 (USDC) is still reduced by the same amount
3. For a typical case with WBTC at $100,000/BTC, the loss could be substantial (e.g., a loss of 1 WBTC would equal $100,000)

### Mitigation

The bug can be fixed by correcting the repayment calculation to use the proper token for token1 borrowers:

```solidity
else if (borrowed == up.token1) {
    uint256 repayFromWithdraw = amountOut1 < owedAmount ? amountOut1 : owedAmount;
    owedAmount -= repayFromWithdraw;
    amountOut1 -= repayFromWithdraw;
}
```

This ensures that when token1 is borrowed, only token1 is used for repayment, preventing the incorrect use of token0 and double-counting.
