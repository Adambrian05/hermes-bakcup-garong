# Missing Price Validation After Liquidity Removal Enables Position Manipulation

### Summary

A missing price revalidation after liquidity removal in `rebalance` will cause a significant loss for the strategy as an attacker can manipulate the price after liquidity removal and force the strategy to rebalance at an unfavorable rate.



### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L198C4-L215C6

In strategy.sol:201, the `rebalance` function, the `_requirePriceWithinRange()` check is performed only once at the start of the function. After liquidity is removed via `_removeLiquidity()`, the pool’s liquidity depth is reduced, making it easier for an attacker to manipulate the price. The strategy then calculates new positions based on the manipulated price, leading to imbalanced liquidity and potential losses.

```solidity
function rebalance() public onlyRebalancer {
    require(block.timestamp - lastRebalance >= rebalanceInterval, "too soon since last rebalance");

    _requirePriceWithinRange(); // we verify that the pool's price is currently not manipulated
    collectFees();

    _removeLiquidity(); // Removes ALL liquidity without subsequent price validation
    (uint256 amount0, uint256 amount1) = idleBalances();

    (uint160 sqrtPriceX96, int24 tick,,,,,) = IUniswapV3Pool(pool).slot0(); // Gets potentially manipulated price
    // Uses potentially manipulated price for position calculations:
    _setMainTicks(tick);
    (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);

    _setSecondaryPositionsTicks(tick);
    _addLiquidityToSecondaryPosition(sqrtPriceX96, amount0, amount1);
    lastRebalance = block.timestamp;
}
```

### Internal Pre-conditions

1. Rebalancer needs to call `rebalance()` when the time since last rebalance is at least rebalanceInterval
2. Strategy must have significant liquidity deployed in its positions (main and secondary) to make removal impactful

### External Pre-conditions

1. Attacker needs to have sufficient capital to execute a price-moving trade after strategy's liquidity removal
2. Uniswap pool must have low enough remaining liquidity after strategy's contribution is removed to be manipulable

### Attack Path

1. Rebalancer calls rebalance() to optimize strategy positions
2. Function verifies price is within acceptable range via _requirePriceWithinRange()
3. Strategy removes all its liquidity from the pool via _removeLiquidity()
4. Attacker front-runs the remainder of the transaction with a large swap that significantly moves the price
5. Strategy reads the manipulated price via IUniswapV3Pool(pool).slot0()
6. Strategy calculates new position ticks based on manipulated price via _setMainTicks(tick)
7. Strategy adds liquidity to disadvantageous positions that benefit the attacker
8. Attacker executes a swap in the opposite direction, reverting the price manipulation after positions are set

### Impact

The protocol suffers an approximate loss proportional to the price manipulation. The attacker gains from the price manipulation, while the strategy’s liquidity is allocated at an unfavorable rate, reducing its overall value.


### PoC

_No response_

### Mitigation

Add a second price check after removing liquidity and before setting new ticks:
```solidity
function rebalance() public onlyRebalancer {
    require(block.timestamp - lastRebalance >= rebalanceInterval, "too soon since last rebalance");

    _requirePriceWithinRange(); // Initial price validation
    collectFees();

    _removeLiquidity();
    (uint256 amount0, uint256 amount1) = idleBalances();

    _requirePriceWithinRange(); // Add this second validation after liquidity removal
    
    (uint160 sqrtPriceX96, int24 tick,,,,,) = IUniswapV3Pool(pool).slot0();

    _setMainTicks(tick);
    (amount0, amount1) = _addLiquidityToMainPosition(sqrtPriceX96, amount0, amount1);

    _setSecondaryPositionsTicks(tick);
    _addLiquidityToSecondaryPosition(sqrtPriceX96, amount0, amount1);
    lastRebalance = block.timestamp;
}
```
