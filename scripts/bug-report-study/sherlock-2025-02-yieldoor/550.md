# Incorrect `modulo` Calculation in `Strategy._setSecondaryPositionsTicks` When `tick < 0`

### Summary

The calculation `modulo = tick % tickSpacing` yields a negative `modulo` when `tick < 0`. Consequently, the tick range for the secondary position may include the `tick`, violating the main invariants; specifically, `the secondary position is always Out-Of-Range`.

### Root Cause

The function [_setSecondaryPositionsTicks()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L367) computes `modulo` as `tick % tickSpacing`. This approach leads to a negative value when `tick < 0`, unlike the [_setMainTicks()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L235) function, where `modulo` is always positive for the main position. As a result, the tick range for the secondary position may encompass the `tick`, violating the main invariants; `the secondary position is always Out-Of-Range`.

As the current tick is included in the secondary position, adding liquidity to the secondary position requires both tokens. However, after liquidity is added to the main position, only one token will remain. Consequently, it becomes impossible to add liquidity to the secondary position.

Example Scenario

- `tickSpacing` = 60
- `tick` = -13

This results in:

- `mainPosition.tickLower` = -120
- `mainPosition.tickUpper` = 120

And for the secondary position:

- `secondaryPosition.tickLower` = -120
- `secondaryPosition.tickUpper` = 0

Thus, the secondary position's tick range of `[-120, 0]` includes `-13`, which is the `tick`.

```solidity
    function _setSecondaryPositionsTicks(int24 tick) internal {
@>      int24 modulo = tick % tickSpacing;
        uint256 bal0 = IERC20(token0).balanceOf(address(this));
        uint256 bal1 = IERC20(token1).balanceOf(address(this));
        uint256 _price = price();
        uint256 bal0in1 = bal0 * _price / PRECISION; // usually either of them should be 0, but might be non-zero due to rounding when minting

        if (bal0in1 < bal1) {
            secondaryPosition.tickLower = mainPosition.tickLower;
            secondaryPosition.tickUpper = tick - modulo;
        } else {
            secondaryPosition.tickLower = tick - modulo + tickSpacing;
            secondaryPosition.tickUpper = mainPosition.tickUpper; // TODO check if these need to be reversed.
        }

        emit NewSecondaryTicks(secondaryPosition.tickLower, secondaryPosition.tickUpper);
    }

------------------------------------------------------------

    function _setMainTicks(int24 tick) internal {
        int24 halfWidth = int24(positionWidth / 2);
        int24 modulo = tick % tickSpacing;
@>      if (modulo < 0) modulo += tickSpacing; // if tick is negative, modulo is also negative
        bool isLowerSided = modulo < (tickSpacing / 2);

        int24 tickBorder = tick - modulo;
        if (!isLowerSided) tickBorder += tickSpacing;
        mainPosition.tickLower = tickBorder - halfWidth;
        mainPosition.tickUpper = tickBorder + halfWidth;

        emit NewMainTicks(tickBorder - halfWidth, tickBorder + halfWidth);
    }
```

### Impact

This issue breaks the main invariants; `the secondary position is always Out-Of-Range`. Therefore, it is not possible to add any liquidity to the secondary position.

### Mitigation

Ensure that `modulo` is always positive, as implemented in `_setMainTicks()`.

