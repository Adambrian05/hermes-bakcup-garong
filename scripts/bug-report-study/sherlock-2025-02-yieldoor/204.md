# Users opening below the max leverage will be liquidated earlier than supposed to

### Summary

Users opening below the max liquidation will be liquidated earlier than supposed to

### Root Cause

The developer has implemented the following code for determining the liquidation levels:
```solidity
        uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;
```
We calculate the necessary collateral to open at max leverage, later we use it to calculate the liquidation levels. This is done as if a user were to open below the max leverage, it would be unfair to liquidate him based on his lower leverage. This is written in different places such as the code:
> /// here we make a calculation what would be the necessary collateral
/// if we had the same borrowed amount, but at max leverage. Check docs for better explanation why.

And the docs:
> However, in scenarios where the users are not using max leverage, this could cause unfair liquidations. ....

The issue is that these 2 lines actually allow for an issue:
```solidity
        uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;
```

2 positions can have the exact same current state (value and debt) but they will have different liquidation levels which is obviously unfair for the one with worse liquidation threshold.

### Attack Path

We will imagine a scenario in which 2 identical positions will have different liquidation thresholds, this should obviously not happen and it's an issue.

The max leverage is `1.5`. Alice creates a position with a size of 150 token0 and 150 token1, she borrows 100\$ to do so. The `initCollateralValue` of the position is 300\$ (using \$ for simplicity, in reality it's a token value), the leverage of the position is `(300 + 100) * 1e18 / 300 = ~1.33e18` or around 1.33 leverage.

Some time passes and Bob will now open a position. During that time, the price of token0 and token1 dropped, Alice's position is now worth 250\$ instead of the 300\$ it was initially, her debt also increased to 125\$ from the 100\$ it was initially (through interest). Bob opens a position with 150 token0 and 150 token1, this is now worth 250\$ as I mentioned above, he borrows 125\$ to open it, his leverage is `(250 + 125) * 1e18 / 250 = 1.5e18` or 1.5 leverage. Currently, the 2 positions are equal, they have 250\$ position value and 125\$ of it is debt.

Some time passes and the token value goes up, it increases back to 300\$, the debt of both positions go to 150\$. Let's check the state regarding liquidations. We have the following code:
```solidity
        uint256 base = (owedAmount * 1e18) / (vp.maxTimesLeverage - 1e18);
        base = base < pos.initCollateralValue ? base : pos.initCollateralValue;
```
For both positions, the initial `base` will be `150 * 1e18 / (1.5e18 - 1e18) = 300`. In the ternary operator line, the `base` value for Alice will stay at 300 as her `initCollateralValue` is also 300. However, for Bob's position, it will go to 250 as his `initCollateralValue` is 250. Then, this is the liquidation check:
```solidity
totalDenom - owedAmount < (vp.minCollateralPct * base) / 1e18)
```
They have the same `totalDenom` (300, that is the position size) and the same `owedAmount` (150). However, the `base` is different for both, they have different liquidation thresholds. This is obviously unfair for Alice, they have the same position.

### Impact

Positions with the same value and the same debt have different liquidation levels.
