# Double Withdrawal Vulnerability in yToken Contract

### Summary

This report details a critical vulnerability in the yToken smart contract that allows an attacker to withdraw more underlying tokens than they are entitled to, leading to insolvency. The root cause of this exploit is the improper handling of the transferUnderlyingTo() and burn() functions, which can be used in combination to withdraw funds twice.

### Root Cause

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/yToken.sol#L47-L68


1. transferUnderlyingTo() moves tokens without requiring the burning of yTokens, leaving an inconsistent state.

2. burn() does not verify if the tokens were already transferred out before executing the withdrawal.

3. The contract lacks proper accounting mechanisms to track transferred tokens.

### Internal Pre-conditions

1. [Attacker needs to deposit] underlying tokens to receive yTokens.
2. [Attacker needs to call] transferUnderlyingTo(target, amount) to move the underlying tokens to an external address without burning yTokens.
3. [Attacker needs to retain] the yTokens in their balance without any restriction.
4. [Attacker needs to call] burn(receiver, yTokenAmount, underlyingTokenAmount) to redeem the same amount of underlying tokens again.
5. [The contract fails to check] if the underlying tokens were already transferred before allowing the burn operation.

### External Pre-conditions

1. [The attacker must have access] to call both transferUnderlyingTo() and burn() functions.
2. [No external monitoring or pause mechanism] should be in place to detect abnormal withdrawals.
3. [No oracle or off-chain tracking] should verify the actual balance of underlying tokens in the protocol.
4. [Gas fees must be low enough] to allow rapid execution of the exploit without economic deterrence.
5. [No time delay or cooldown] should be enforced between token transfers and burn operations.

### Attack Path

Vulnerable Functions:

transferUnderlyingTo(address target, uint256 amount): Transfers underlying tokens to an external wallet without burning yTokens, leading to an imbalance.

burn(address receiver, uint256 yTokenAmount, uint256 underlyingTokenAmount): Burns yTokens and allows withdrawal of an equivalent amount of underlying tokens.

**Attack Steps:**

Initial Deposit:

The attacker deposits a certain amount of underlying tokens and receives yTokens in return.

Unauthorized Transfer:

The attacker calls transferUnderlyingTo(target, amount), moving underlying tokens to an external wallet.

However, they do not burn yTokens, meaning they still hold the right to redeem them.

Double Withdrawal:

The attacker then calls burn(receiver, yTokenAmount, underlyingTokenAmount), which burns yTokens and withdraws the same amount of underlying tokens again.

Since the contract still considers the attacker to have valid yTokens, it allows the withdrawal without detecting the prior transfer.

### Impact

1. The contract loses funds because it allows withdrawing the same underlying tokens twice.

2. This leads to insolvency, as the contract no longer has enough underlying tokens to cover all yToken holders.

3. Attacker profits by effectively withdrawing double their deposit.

### PoC

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.0;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";

interface IYToken {
    function transferUnderlyingTo(address target, uint256 amount) external;
    function burn(address receiver, uint256 yTokenAmount, uint256 underlyingTokenAmount) external;
}

contract DoubleWithdrawExploit {
    IYToken public yToken;
    IERC20 public underlyingToken;
    address public owner;

    constructor(address _yToken, address _underlyingToken) {
        yToken = IYToken(_yToken);
        underlyingToken = IERC20(_underlyingToken);
        owner = msg.sender;
    }

    function attack() external {
        require(msg.sender == owner, "Not authorized");
        
        uint256 balance = underlyingToken.balanceOf(address(this));
        require(balance > 0, "No tokens to exploit");
        
        // Step 1: Transfer underlying tokens to attacker wallet without burning yTokens
        yToken.transferUnderlyingTo(owner, balance);
        
        // Step 2: Burn yTokens to withdraw again
        yToken.burn(owner, balance, balance);
        
        // Step 3: Profit! The same tokens have been withdrawn twice
    }
}


### Mitigation

✅ Fix 1: Require Burning of yTokens Before Transfers

Modify transferUnderlyingTo() to require the user to burn their yTokens before moving underlying assets:

function transferUnderlyingTo(address target, uint256 amount) external onlyAuthorized {
    require(balanceOf(msg.sender) >= amount, "Insufficient yToken balance");
    _burn(msg.sender, amount);
    IERC20(underlyingToken).transfer(target, amount);
}

This ensures that any movement of underlying tokens is tied to an equivalent burn of yTokens.

✅ Fix 2: Track Transfers in underlyingBalance

Modify transferUnderlyingTo() to reduce underlyingBalance whenever tokens are moved:

function transferUnderlyingTo(address target, uint256 amount) external onlyAuthorized {
    require(underlyingBalance >= amount, "Insufficient balance");
    underlyingBalance -= amount;
    IERC20(underlyingToken).transfer(target, amount);
}

✅ Fix 3: Add Reentrancy Protection

Implement a reentrancy guard to prevent attackers from calling both functions within a single transaction:

modifier nonReentrant() {
    require(!entered, "Reentrancy detected");
    entered = true;
    _;
    entered = false;
}

Apply this modifier to both transferUnderlyingTo() and burn().


**Conclusion**
This vulnerability allows attackers to drain funds by transferring underlying tokens without burning yTokens, leading to a double withdrawal scenario. Fixing transferUnderlyingTo() or tightening withdrawal conditions will prevent insolvency and secure the contract against such exploits.
