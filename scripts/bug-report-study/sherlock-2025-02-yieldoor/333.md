# Attacker will force unfavorable rebalancing by manipulating pool observations

## Summary
The inadequate price validation in the Strategy contract's rebalancing mechanism will cause significant financial losses for liquidity providers as attackers will manipulate Uniswap V3 pool observations to bypass price validation checks and force unfavorable rebalancing operations.

## Root Cause
In [Strategy.sol#L150-L180](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L150-L180) the `checkPoolActivity` function only checks for price deviations between consecutive observations, rather than validating the cumulative price change across the entire TWAP period:

```solidity
for (uint16 i = 1; i <= observationCardinality; i++) {
    uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;

    (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
    if (timestamp == 0) {
        revert("timestamp 0");
    }

    tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));

    (nextTimestamp, nextCumulativeTick) = (timestamp, tickCumulative);
    int24 delta = nextTick - tick;

    if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
        return false;
    }
    // ... rest of function ...
}
```

This allows an attacker to execute a series of trades that each stay within the `maxObservationDeviation` threshold (set to 100 ticks in the constructor), but cumulatively result in a significant price manipulation.

## Internal Pre-conditions
1. The `rebalance` function must be callable (either by a rebalancer or after the rebalance interval has passed)
2. The `maxObservationDeviation` parameter must be set to a value that allows for consecutive manipulations
3. The protocol must use Uniswap V3 pool observations for price validation

## External Pre-conditions
1. The attacker must have sufficient capital to execute multiple trades affecting the Uniswap V3 pool price
2. The pool must allow for price movements within the `maxObservationDeviation` threshold multiple times
3. The current pool price must be such that manipulating it would result in an unfavorable rebalancing

## Attack Path
1. Attacker monitors the protocol to identify when a rebalance is likely to occur
2. Attacker executes a series of trades in the Uniswap V3 pool:
   - Trade 1: Move price by 99 ticks (below `maxObservationDeviation`)
   - Wait for this observation to be recorded
   - Trade 2: Move price by another 99 ticks
   - Repeat until desired price manipulation is achieved
3. When the rebalancer calls the `rebalance()` function:
   - `_requirePriceWithinRange()` is called
   - `checkPoolActivity()` returns true because each individual price movement is below the threshold
   - Rebalance proceeds with manipulated price
4. The strategy rebalances based on the manipulated price, potentially:
   - Setting incorrect ticks for the main and secondary positions
   - Removing liquidity at unfavorable prices
   - Adding liquidity at unfavorable prices
5. Attacker profits by trading against these suboptimal positions or by reversing their price manipulation after the rebalance

## Impact
The strategy and its liquidity providers suffer significant losses due to inefficient capital allocation and unfavorable liquidity positioning. This may result in diminished returns for users, potential impermanent loss, and decreased protocol TVL. In severe cases, this could lead to substantial financial losses if the manipulator can exploit the suboptimal positions through further trading.

## Mitigation
Implement cumulative price change validation to detect significant price movements across the entire observation period:

```solidity
function checkPoolActivity() public view returns (bool) {
    (, int24 tick, uint16 currentIndex, uint16 observationCardinality,,,) = IUniswapV3Pool(pool).slot0();

    uint32 lookAgo = uint32(block.timestamp) - twap;
    
    // Track the first tick to compare with the final tick
    int24 firstTick = 0;
    bool firstTickSet = false;

    (uint32 nextTimestamp, int56 nextCumulativeTick,,) = IUniswapV3Pool(pool).observations(currentIndex);
    int24 nextTick = tick;

    for (uint16 i = 1; i <= observationCardinality; i++) {
        // ... existing code ...
        
        tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));
        
        // Set first tick value for cumulative check
        if (!firstTickSet) {
            firstTick = tick;
            firstTickSet = true;
        }
        
        // ... existing code for checking consecutive observations ...
        
        // If we've reached the end of our lookback period
        if (timestamp < lookAgo) {
            // Add cumulative check - compare first and last tick in the period
            int24 totalDelta = nextTick - firstTick;
            if (totalDelta > maxTotalDeviation || totalDelta < -maxTotalDeviation) {
                return false;
            }
            return true;
        }
        
        // ... rest of existing code ...
    }
    
    return false;
}
```

Additionally, implement circuit breakers and use multiple time periods for TWAP calculations to further strengthen price validation.
