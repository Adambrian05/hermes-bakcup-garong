# Zero-Collateral Leverage Vulnerability in Leverage Protocol

### Summary

This report details a critical vulnerability in the openLeveragedPosition() function, which allows users to open leveraged positions without providing any initial collateral. If the trade moves against them, their position gets liquidated, allowing liquidators to earn fees while the protocol suffers a loss.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L103-L166

### Root Cause

1. The function does not enforce a minimum collateral requirement before allowing leverage.

2. maxBorrowAmount can be arbitrarily high, allowing attackers to take excessive leverage without risk.

3. There are no checks ensuring borrowed funds are backed by user deposits.

4. The protocol absorbs the loss when the position is liquidated.

### Attack Path

openLeveragedPosition(LeverageParams calldata lp): Enables users to deposit funds, take leverage, and borrow additional assets without requiring adequate initial collateral.

**Attack Steps:**

**Open Leverage Position Without Collateral:**

The attacker sets amount0In = 0 and amount1In = 0, meaning they contribute no initial collateral.

They set vault0In > 0 and vault1In > 0 to ensure the contract borrows the full required amount.

**Borrow Maximum Possible Funds:**

The attacker sets maxBorrowAmount to a high value, ensuring that they get the borrowed funds without actually providing collateral.

**Liquidation and Protocol Loss:**

If the trade moves against them, the position gets liquidated.

Liquidators earn fees while the protocol incurs a loss due to the borrowed amount exceeding the recovered collateral.

### Impact

1. Attackers can open zero-collateral leverage positions, leading to risk-free trades.

2. Liquidators profit from the liquidation process, while the protocol absorbs the losses.

3. Continuous exploitation of this vulnerability can lead to liquidity drain and protocol insolvency.

### Mitigation

✅ Fix 1: Require Minimum Collateral

Enforce a minimum initial deposit (amount0In and amount1In) to ensure users have actual collateral before borrowing.

require(lp.amount0In > MIN_COLLATERAL && lp.amount1In > MIN_COLLATERAL, "Insufficient collateral");

✅ Fix 2: Validate Borrower’s Contribution Against Total Deposit

Ensure that the user’s deposit is proportional to the leverage they are requesting:

require(lp.amount0In + lp.amount1In >= (lp.vault0In + lp.vault1In) / MAX_LEVERAGE, "Collateral too low for leverage");

✅ Fix 3: Cap Maximum Borrowing Based on Collateral

Introduce a check that prevents maxBorrowAmount from exceeding a safe leverage threshold based on initial collateral.

✅ Fix 4: Prevent Risk-Free Liquidations

Ensure that the initial collateral value is enough to prevent immediate liquidation:

require(up.initCollateralUsd >= up.initBorrowedUsd * MIN_COLLATERAL_RATIO / 100, "Leverage too high, position unbacked");
