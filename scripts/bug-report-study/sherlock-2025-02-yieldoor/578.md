# Denial of Service (DoS) in Deposit Function Due to Zero Liquidity

### Summary

A critical Denial of Service (DoS) vulnerability exists in the deposit function. If all users withdraw their liquidity, resulting in bal0 == 0 and bal1 == 0, any subsequent deposit attempts will fail due to an assertion failure in _calcDeposit(). This permanently locks the contract, preventing future deposits.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Vault.sol#L48-#L72

### Root Cause

When liquidity is entirely removed, both bal0 and bal1 are 0. This results in a division by zero scenario in _calcDeposit():

else if (bal0 == 0) {
    amount1 = depositAmount1;
    shares = amount1 * totalSupply / bal1;  // bal1 == 0 -> division by zero
}

Since totalSupply() would still be 1000 due to the _mint(BURN, 1000); logic, the calculation shares = amount1 * totalSupply / bal1.

This causes shares to become 0, leading to a revert in deposit():


```solidity
 function deposit(uint256 amount0, uint256 amount1, uint256 amount0Min, uint256 amount1Min)
        external
        returns (uint256 shares, uint256 depositAmount0, uint256 depositAmount1)
    {
        IStrategy(strategy).collectFees();

        (uint256 totalBalance0, uint256 totalBalance1) = IStrategy(strategy).balances();

        (shares, depositAmount0, depositAmount1) = _calcDeposit(totalBalance0, totalBalance1, amount0, amount1);

        IERC20(token0).safeTransferFrom(msg.sender, strategy, depositAmount0);
        IERC20(token1).safeTransferFrom(msg.sender, strategy, depositAmount1); // after deposit, funds remain idle, until compound is called

        if (depositFee > 0) shares -= (shares * depositFee) / 10_000;

        require(shares > 0, "shares cant be 0");
        require(depositAmount0 >= amount0Min, "slippage0");
        require(depositAmount1 >= amount1Min, "slippage1");

        if (totalSupply() == 0) _mint(BURN, 1000);
        _mint(msg.sender, shares);

        return (shares, depositAmount0, depositAmount1);
        // TODO - emit event
    }

function _calcDeposit(uint256 bal0, uint256 bal1, uint256 depositAmount0, uint256 depositAmount1)
        internal
        view
        returns (uint256 shares, uint256 amount0, uint256 amount1)
    {
        uint256 totalSupply = totalSupply();

        // If total supply > 0, vault can't be empty
        assert(totalSupply == 0 || bal0 > 0 || bal1 > 0);

        if (totalSupply == 0) {
            // For first deposit, just use the amounts desired
            amount0 = depositAmount0;
            amount1 = depositAmount1;
            shares = (amount0 > amount1 ? amount0 : amount1) - (1000); 
        } else if (bal0 == 0) {
            amount1 = depositAmount1;
            shares = amount1 * totalSupply / bal1; //pool balance
        } else if (bal1 == 0) {
            amount0 = depositAmount0;
            shares = amount0 * totalSupply / bal0;
        } else {
            uint256 cross0 = depositAmount0 * bal1;
            uint256 cross1 = depositAmount1 * bal0;
            uint256 cross = cross0 > cross1 ? cross1 : cross0;
            require(cross > 0, "cross");

            // Round up amounts
            amount0 = (cross - 1) / bal1 + 1;
            amount1 = (cross - 1) / bal0 + 1;
            shares = cross * totalSupply / bal0 / bal1;
        }
    }
```

### Attack Path

1. No deposits have been made yet.
2. 2 users call deposit where they provide liquidity for the Strategy and get their amount of shares + 1000 shares to  unusable address
3. Both users call withdraw with all their shares which makes strategy with 0 balance for both tokens (0 liquidity) however totalSupply is not 0 since contract minted to unusalbe address 1000 shares.
4. Now Leads to DOS since whoever deposits gets 0 shares minted

### Impact

Permanent Deposit Lock: Once all liquidity is withdrawn, new deposits will always revert with "shares cant be 0", effectively freezing the vault.
Funds Cannot Be Added: The protocol becomes non-functional since no new deposits can be made.
High Risk: If a protocol relies on continuous deposits, this can lead to financial losses and user dissatisfaction.
