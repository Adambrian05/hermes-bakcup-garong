# Overly Strict Pool Activity Check Preventing Rebalancing During Normal Volatility

The issue arises from the [_priceWithinRange](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L298-L306) function, which relies on [checkPoolActivity](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L310-L342) to ensure that price observations from the pool are consistent and not manipulated; however, the logic in `checkPoolActivity` can return false and even revert under natural market volatility or insufficient observation data, thereby blocking critical functions like `rebalance` and `compound`. 

Consider this snippet from `checkPoolActivity`:

```solidity
for (uint16 i = 1; i <= observationCardinality; i++) {
    uint256 index = (observationCardinality + currentIndex - i) % observationCardinality;
    (uint32 timestamp, int56 tickCumulative,,) = IUniswapV3Pool(pool).observations(index);
    if (timestamp == 0) {
        revert("timestamp 0");
    }
    tick = int24((nextCumulativeTick - tickCumulative) / int56(uint56(nextTimestamp - timestamp)));
    (nextTimestamp, nextCumulativeTick) = (timestamp, tickCumulative);
    int24 delta = nextTick - tick;
    if (delta > maxObservationDeviation || delta < -maxObservationDeviation) {
        return false;
    }
    if (timestamp < lookAgo) {
        return true;
    }
    nextTick = tick;
}
```

## Root Cause
  The function uses a hardcoded `maxObservationDeviation` ([default set to 100](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L109)) to determine if the change between consecutive ticks is acceptable. Natural market volatility could easily lead to differences that exceed this threshold, even without any malicious manipulation.
  The loop assumes that all observations have non-zero timestamps. In newer or less active pools, some observations might not be fully initialized (i.e., timestamp equals zero), triggering an immediate revert with `"timestamp 0"`. This behavior can inadvertently block rebalancing and compounding when the pool hasn't gathered sufficient observation data.

## Impact
  Since `_priceWithinRange` calls `checkPoolActivity`, a false return or revert from `checkPoolActivity` will cause functions like [rebalance()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L198-L215) and [compound()](https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Strategy.sol#L219-L228) to fail. This means that during periods of normal but higher-than-expected volatility, or when operating in a newly deployed pool with limited observation data, the strategy may be prevented from rebalancing its positions, potentially locking user funds and disrupting liquidity management. This overly strict check—meant to safeguard against price manipulation—can therefore become a bottleneck under ordinary market conditions, leading to a significant disruption of service.

## Mitigation
implement adaptive thresholds for maxObservationDeviation and fallback logic for uninitialized observations, allowing rebalancing to proceed during normal volatility while still guarding against potential manipulation.
