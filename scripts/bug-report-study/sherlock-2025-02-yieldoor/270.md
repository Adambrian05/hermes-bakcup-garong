# ### [H-1] Uninitialized feeRecipient in Leverager.sol Leads to Potential Fund Loss (Uninitialized State Variable + Loss of Protocol Fees)


## Description:
So, the `feeRecipient` variable in `Leverager.sol` (line 47: `address public feeRecipient;`) is declared as a public state variable but is never initialized in the constructor (line 67) or via any setter function. Slither flags this: `"Leverager.feeRecipient (src/Leverager.sol#47) is never initialized`. It is used in line 299-380: `Leverager.liquidatePosition(ILeverager.LiquidateParams)` (src/Leverager.sol#299-380)." 

In liquidatePosition (lines 329-330), the protocol fees (`pf0 and pf1`) collected during profitable liquidations are sent to `feeRecipient`. If this is uninitialized, it defaults to address(0), thereby causing these fees to be burned (sent to the null address) and lost forever. The security documents also states that `"Setting fee recipient to blacklisted address is not an issue`," which implies an expectation of initialization, yet no mechanism enforces this, making it a subtle oversight.

 This is rare because most contracts normally initialize key variables like fee recipients, and the lack of an immediate revert masks the issue, potentially escaping notice unless state variable initialization is thoroughly checked.

https://github.com/sherlock-audit/2025-02-yieldoor/blob/main/yieldoor/src/Leverager.sol#L47

## Impact:
The loss of protocol fees reduces the financial incentive for liquidators to execute liquidatePosition, as they rely on profitable liquidations for motivation. If liquidations stall due to diminished rewards, underwater positions may persist, accumulating bad debt in the LendingPool and destabilizing the system. This undermines the protocol’s economic model and could lead to significant operational risks over time.

## Proof of Concept:  
Deploy `Leverager.sol` without initializing feeRecipient in the constructor (current state: `constructor(string memory name_, string memory symbol_, address _lendingPool)`).

Set up a vault with WBTC/USDC, open a leveraged position, and simulate a price drop making it liquidateable (e.g., collateral value falls below minCollateralPct).

Call liquidatePosition with a profitable scenario (e.g., totalValueUSD > borrowedValue):
Code snippet: 

```solidity

if (pf0 > 0) IERC20(up.token0).safeTransfer(feeRecipient, pf0); // Line 329
if (pf1 > 0) IERC20(up.token1).safeTransfer(feeRecipient, pf1); // Line 330

```

feeRecipient is address(0) (default), so pf0 (e.g., 1 WBTC) and pf1 (e.g., 1000 USDC) are transferred to address(0).

Verify via blockchain explorer: Funds are burned (balance of address(0) increases), and no entity can recover them.

## Recommended Mitigation:

Modify the constructor to accept and set feeRecipient, ensuring it’s initialized at deployment:

```solidity

constructor(string memory name_, string memory symbol_, address _lendingPool, address _feeRecipient) 
    Ownable(msg.sender) 
    ERC721(name_, symbol_) 
{
    lendingPool = _lendingPool;
    feeRecipient = _feeRecipient; // Initialize here
}
```
