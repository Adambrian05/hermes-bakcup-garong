# TWAP Manipulation Due to Insufficient Observation History

### Summary

The Yieldoor protocol's Strategy contract fails to ensure that Uniswap V3 pools have sufficient observation history before using them for TWAP calculations. The protocol neither checks for adequate observation cardinality nor calls `increaseObservationCardinalityNext()` to ensure pools can store enough historical data. This makes the protocol vulnerable to TWAP manipulation, especially with newly created pools or pools with low cardinality, and can cause critical functions to fail when sufficient observation history is unavailable.


### Root Cause

Two key issues combine to create this vulnerability:

The `twapTick()` function directly calls Uniswap's `observe()` method without verifying if the pool has sufficient historical data:
https://github.com/sherlock-audit/2025-02-yieldoor/blob/b5a0f779dce4236b02665606adb610099451a51a/yieldoor/src/Strategy.sol#L345

The protocol never calls `increaseObservationCardinalityNext()` to ensure pools have adequate storage capacity for historical observations:

### Internal Pre-conditions

- The Strategy contract uses a Uniswap V3 pool for TWAP calculations
- The twapTick() and twapPrice() functions are called by critical operations
- No validation exists to check if the pool has sufficient observation history
- No mechanism exists to increase observation cardinality



### External Pre-conditions

- A Uniswap V3 pool with low observation cardinality (default is 1 for new pools)
- Insufficient historical data points to cover the TWAP period
- Infrequent transactions in the pool, creating gaps in observation history



### Attack Path

This vulnerability can be exploited in two ways:
Denial of Service Attack:

1. An attacker identifies a Yieldoor Vault using a Uniswap pool with insufficient observations
2. When users attempt to interact with the protocol (e.g., rebalance, compound, open positions)
3. The twapTick() function reverts because the pool lacks sufficient history
4. Critical protocol operations fail, causing denial of service

TWAP Manipulation Attack:

1. An attacker creates or identifies a pool with minimal observation cardinality (e.g., 1)
2. The attacker executes a trade to set the only observation to a manipulated price
3. If the protocol were to implement a fallback for insufficient observations, this manipulated observation would be used
4. The attacker exploits the manipulated price to their advantage (opening positions, avoiding liquidation)



### Impact

 - Critical functions like rebalance, compound, and leveraged position operations may fail
 - TWAP values can be manipulated more easily in pools with low cardinality
 - New pools become effectively unusable until they accumulate sufficient observations
 - Protocol security against price manipulation is compromised



### PoC

No PoC

### Mitigation

Add code to ensure sufficient observation cardinality for all pools:
```solidity
// Add to Strategy constructor
uint16 targetCardinality = uint16((twap / 15) + 2); // Assuming ~15 second blocks
IUniswapV3Pool(pool).increaseObservationCardinalityNext(targetCardinality);
```
