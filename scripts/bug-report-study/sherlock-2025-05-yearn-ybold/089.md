# [Medium] Strategy.sol::claim() allows any actor to trigger a zero-amount withdrawal from the Stability Pool, potentially griefing the strategy's operators or users

### Summary

The absence of access control on the `claim()` function and the unconditional call to `IStabilityPool.withdrawFromSP(0, true)` will cause an unnecessary external call and potentially incur gas costs for the strategy when an attacker calls `claim()`, even if there are no rewards to claim or auctions to process.

### Root Cause

In [Strategy.sol](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L185-L187), the claim() function is public and directly calls `sp.withdrawFromSP(0, true)` without any prior checks to determine if such a call is beneficial or necessary (e.g., checking for available auction proceeds or claimable rewards).

### Internal Pre-conditions

1. The `LiquityV2SPStrategy` contract is deployed and operational.
2. The `StabilityPool` address is correctly set in the `AddressesRegistry` used by the strategy.

### External Pre-conditions

1. The `IAuctionFactory` at the hardcoded address `0xCfA510188884F199fcC6e750764FAAbE6e56ec40` is operational (though for this specific grief, its state is less critical as `claim()` proceeds to `withdrawFromSP(0, true)` regardless of auction activity if `priceIsDown` is false).
2. The `IPriceFeed` returns `priceIsDown = false` when `fetchPrice()` is called. If `priceIsDown` were true, the `claim()` function would attempt to kick an auction, which might be a different flow.

### Attack Path

1. An arbitrary EOA (attacker) calls the public `claim()` function on the `LiquityV2SPStrategy` contract.
2. The `claim()` function retrieves the `priceFeed` and `stabilityPool` from the `addressesRegistry`.
3. It calls `priceFeed.fetchPrice()`. In our PoC, this returns (`1e18, false`), so `priceIsDown` is false.
4. Since `priceIsDown` is false, the strategy proceeds to call `stabilityPool.withdrawFromSP(0, true)`.
5. This external call is made, potentially incurring gas costs for the transaction, which might be borne by a keeper or the strategy itself if it's part of a larger automated process.

### Impact

The strategy (and by extension, its users or operators responsible for calling `claim`) suffers a minor gas cost for the unnecessary `withdrawFromSP(0, true)` call. While a single call might be negligible, repeated calls by a malicious actor could lead to a denial of service by draining gas from automated systems that call `claim`, or simply cause a nuisance and waste of resources. The attacker does not gain anything directly, making this a griefing attack. The exact gas cost would depend on the implementation of the `StabilityPool`'s `withdrawFromSP` function.

### PoC

The `ClaimGriefingTest` contract simulates the environment.

- It deploys mock contracts for `IAuctionFactory`, `IStabilityPool`, `IPriceFeed`, and `IAddressesRegistry`.
- The `MockStabilityPool` records calls to its `withdrawFromSP` function.
- The `MockPriceFeed` is set up to return `priceIsDown = false`.
- The `setUp()` function deploys the `LiquityV2SPStrategy` with these mocks.
- The `testAnyoneCanGriefClaim()` test case simulates an attacker calling `strategy.claim()`.
- Assertions verify that `MockStabilityPool.withdrawFromSP` was called with `_amount = 0` and `doClaim = true`.

### Mitigation

To mitigate this, the `claim()` function should have appropriate access control (e.g., `onlyRole(KEEPER_ROLE)` or `onlyOwner`) if it's intended to be called by specific actors.

Alternatively, or in addition, add checks within the `claim()` function to ensure `sp.withdrawFromSP(0, true)` is only called when it's logical to do so. For example, check if there are any actual rewards or auction proceeds to claim from the Stability Pool before making the call. If the intention of `withdrawFromSP(0, true)` is to trigger some other claiming logic within the Stability Pool even with a zero amount, this should be clearly documented, and the griefing potential acknowledged or addressed through other means (e.g., rate limiting, or ensuring the gas cost is truly negligible).

**Recommended code change (conceptual):**
```solidity

        _grantRole(KEEPER_ROLE, msg.sender); // Grant to deployer or a designated keeper

    function claim() external override onlyRole(KEEPER_ROLE) { // Added access control
        // ... existing logic ...

        // if (sp.getPendingRewards(address(this)) > 0 || /* other conditions */) {
        //    sp.withdrawFromSP(0, true);
        // }
        // If withdrawFromSP(0, true) is always necessary when priceIsNotDown,
```

If the `claim()` function is intended to be callable by anyone to process auctions (when `priceIsDown`), then the `withdrawFromSP(0, true)` part should be conditional on whether there's something to actually withdraw or if that call serves another critical purpose that justifies its unconditional execution.
