# Protocol users will receive inaccurate asset valuations due to unclaimed collateral gains being excluded from total assets calculations

### Summary

The omission of unclaimed collateral gains in `estimatedTotalAssets()` will cause an inaccurate asset valuation for protocol users, as the strategy underreports its true holdings. This breaks the core invariant that total assets must fully represent all claimable and held value, leading to potential misinformed decisions by users and integrators relying on this metric. The root cause is the failure to include `SP.getDepositorCollGain(address(this))` in the total assets calculation, which results in an underestimation of the strategy’s actual assets.


### Root Cause

In strategy.sol , the estimatedTotalAssets() function fails to include unclaimed collateral gains from SP.getDepositorCollGain(address(this)) in its calculation, causing an incomplete accounting of the strategy’s total assets. This coding omission breaks the invariant that all claimable and held assets must be reflected in total asset calculations.

### Internal Pre-conditions

1. The strategy must have accumulated unclaimed collateral gains via `SP.getDepositorCollGain(address(this))` that are non-zero.

2. The `estimatedTotalAssets()` function is called before these collateral gains have been claimed (e.g., before `claim()` is called).

3. The strategy’s asset balance (`asset.balanceOf(address(this))`) and compounded deposits (`SP.getCompoundedBoldDeposit(address(this))`) are non-zero to make the collateral omission material.

4. No internal process or external actor has triggered the `claim()` function recently to update the collateral balances.

These pre-conditions set the stage for the reported total assets to underrepresent the actual total assets held by the strategy.

### External Pre-conditions

None

### Attack Path

  
1. Strategy contract accumulates collateral gains in the Stability Pool that are unclaimed (i.e., `SP.getDepositorCollGain(address(this))` grows).  
2. External actor or governance queries `estimatedTotalAssets()`.  
3. The function returns a value that excludes unclaimed collateral gains, causing an underreporting of the strategy’s true asset holdings.  
4. Because the accounting is incomplete, downstream systems relying on this value (e.g., risk modules, withdraw limits, performance fees) operate on inaccurate data.  
5. Over time, repeated unclaimed gains compound this discrepancy, exacerbating the financial misrepresentation.  
6. Optionally, if the `claim()` function is never called, the discrepancy persists indefinitely, violating the invariant that *total assets equal all held plus claimable assets.*

### Impact

The strategy and its users suffer from financial misrepresentation because estimatedTotalAssets() underreports the true value by excluding unclaimed collateral gains. This can lead to:

Incorrect accounting and decision-making based on incomplete asset valuations.

Potentially impaired risk assessments and capital allocation by users or external protocols relying on this metric.

Reduced user trust due to discrepancies between reported and actual assets.

While no direct token loss occurs, this broken invariant of accurate total asset reporting means the strategy cannot reliably represent its true holdings, potentially causing economic inefficiencies and user confusion.

### Mitigation

- Update the `estimatedTotalAssets()` function to include unclaimed collateral gains by adding `SP.getDepositorCollGain(address(this))` to the total. This ensures the reported asset value fully reflects all holdings, both claimed and unclaimed.

- Alternatively, ensure that the `claim()` function is regularly called to convert collateral gains into claimable assets, reducing the discrepancy.

- Add clear documentation about what is included in `estimatedTotalAssets()` to set accurate expectations.

- Consider emitting events or metrics that track unclaimed collateral separately, so external parties can monitor discrepancies if immediate inclusion isn’t possible.
