# Claim condition fails to consider stashed collateral in stability pool

### Summary

The condition used to trigger the claim from the stability pool fails to consider potential stashed collateral balance in the pool.

### Root Cause

The stability pool implementation works by calculating the gains between snapshots. Every time the user interacts with the pool, the system checkpoints the state and, using the previous snapshot, calculates the gains based on the difference.

These gains can be withdrawn or not, depending on the value provided to the `_doClaim` parameter.

In the strategy implementation, deposits have this variable set to false, which means that collateral gains are always stashed.

However, the implementation only queries the pending collateral gains when checking if there is anything to claim, as can be seen in the `isCollateralGainToClaim()` function.

https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L98-L100

### Internal Pre-conditions

1. Strategy deploys funds, which checkpoint the stability pool and store gains in the stashed balance.
2. Later on, the strategy uses `SP.getDepositorCollGain(address(this))` which ignores any available stashed balances.

### Impact

The keeper will not execute the job, even if there are stashed collateral tokens to sell and compound in the vault. If deposits are frequent, this can lead to a cascading effect that never executes the job, as deposits will move gains to stash, causing gains to never be enough to trigger the condition.

### Mitigation

Consider stashed balance in the implementation of `isCollateralGainToClaim()`.

```solidity
SP.getDepositorCollGain(address(this)) + SP.stashedColl(address(this)) > dustThreshold;
```
