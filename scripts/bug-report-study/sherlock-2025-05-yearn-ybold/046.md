# Strategy's Immutable `ACCOUNTANT` Can Become Stale, Leading to Reward Misdirection if Vault's Accountant Changes

### Summary

The `LV2SPStakerStrategy` [contract ](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Staker.sol#L9)initializes an `immutable` state variable `ACCOUNTANT` in its constructor. This variable is set to the address returned by `IVault(_vault).accountant()` at the time of the strategy's deployment. The `ACCOUNTANT` variable is subsequently used in the `_harvestAndReport()` function to call `ACCOUNTANT.distribute(address(asset))`, which is responsible for distributing claimed rewards (e.g., yBOLD tokens).

Yearn vaults (represented by the `IVault` interface) allow their governance to update the vault's accountant address *after* the vault has been deployed. However, because the `ACCOUNTANT` variable in `LV2SPStakerStrategy` is `immutable`, it cannot be updated to reflect such changes.

If the vault associated with the strategy changes its accountant, the strategy will continue to hold a reference to the original (now potentially outdated) accountant. Consequently, when `_harvestAndReport()` is executed, the `distribute()` function will be called on this stale accountant address. This can lead to rewards being sent to the `feeRecipient` configured in the old accountant, rather than the `feeRecipient` of the vault's current, correct accountant.


### Root Cause

The root cause is the use of an `immutable` variable (`ACCOUNTANT`) to store an address that can change externally (the vault's accountant). The strategy does not have a mechanism to update its `ACCOUNTANT` reference if the corresponding vault's accountant is changed post-deployment.


### Internal Pre-conditions

*   An `LV2SPStakerStrategy` instance is deployed and associated with a Yearn vault.
*   The `ACCOUNTANT` variable in the strategy is initialized with the vault's accountant address at the time of strategy deployment.
*   The `_harvestAndReport()` function is called, triggering the `ACCOUNTANT.distribute()` call.


### External Pre-conditions

*   The Yearn vault (`IVault(_vault)`) that the `LV2SPStakerStrategy` is linked to updates its accountant address through its governance mechanism. This change occurs *after* the `LV2SPStakerStrategy` has been deployed.
*   The `feeRecipient` of the old accountant (referenced by the strategy) differs from the `feeRecipient` of the new, current accountant of the vault, or the old accountant is no longer the designated entity for handling distributions for that vault.


### Attack Path

This scenario is less of an "attack" by a malicious actor and more of an operational issue stemming from a state mismatch.
1.  A `LV2SPStakerStrategy` is deployed. During its construction, it sets its `immutable ACCOUNTANT` variable to `OldAccountantAddress`, which is the current accountant of `VaultX`. `OldAccountantAddress` is configured to send fees to `OldFeeRecipient`.
2.  Sometime later, `VaultX`'s governance decides to change its accountant. They set `VaultX`'s accountant to `NewAccountantAddress`. `NewAccountantAddress` is configured to send fees to `NewFeeRecipient`.
3.  A keeper or other authorized party calls the `_harvestAndReport()` function on the `LV2SPStakerStrategy`.
4.  Inside `_harvestAndReport()`, the strategy calls `ACCOUNTANT.distribute(address(asset))`.
5.  Since `ACCOUNTANT` in the strategy still points to `OldAccountantAddress`, the `distribute()` function of `OldAccountantAddress` is executed.
6.  `OldAccountantAddress` transfers the rewards (e.g., yBOLD tokens) to its configured `feeRecipient`, which is `OldFeeRecipient`.
7.  The rewards are thereby sent to `OldFeeRecipient` instead of `NewFeeRecipient`, which is the intended recipient according to `VaultX`'s current configuration.


### Impact

The primary impact is the **misdirection of rewards**. Instead of rewards being distributed via the vault's current accountant to the intended `feeRecipient`, they are sent via the stale accountant reference to an outdated `feeRecipient`. This can lead to:
*   **Loss of Funds for the Intended Recipient:** The entity designated by the vault's current accountant to receive fees/rewards will not receive them from this strategy.
*   **Operational Complexity:** Recovering misdirected funds, if possible, can be complex and may require off-chain coordination or further governance actions.
*   **Protocol Integrity Concerns:** Users and stakeholders might lose confidence if funds are not routed correctly according to the latest protocol configurations.
