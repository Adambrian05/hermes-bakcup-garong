# Strategy Factory offers no protection for deployment mapping

### Summary

Deployment asset and stability pool mappings can be overwritten by calling [StrategyFactory::newStrategy()](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/88a3b89c05fd6e59ec130c79659195cd05d872af/yv3-liquityv2-sp-strategy/src/StrategyFactory.sol#L38-L58) with the same parameters `addressRegistry` and `asset`.

### Root Cause

New strategies can be deployed using [StrategyFactory::newStrategy()](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/88a3b89c05fd6e59ec130c79659195cd05d872af/yv3-liquityv2-sp-strategy/src/StrategyFactory.sol#L38-L58):

```solidity
    function newStrategy(
        address _addressesRegistry,
        address _asset,
        string calldata _name
    ) external virtual onlyManagement returns (address) {
        // tokenized strategies available setters.
        IStrategyInterface _newStrategy = IStrategyInterface(address(new Strategy(_addressesRegistry, _asset, _name)));

        _newStrategy.setPerformanceFeeRecipient(performanceFeeRecipient);

        _newStrategy.setKeeper(keeper);

        _newStrategy.setPendingManagement(management);

        _newStrategy.setEmergencyAdmin(emergencyAdmin);

        emit NewStrategy(address(_newStrategy), _asset);

        deployments[_asset][_newStrategy.SP()] = address(_newStrategy); // @audit: can also be overwritten
        return address(_newStrategy);
    }
```

At the end of the function, the `deployments` mapping is updated with the asset, stability pool, and newly deployed address. No checks are in place to prevent subsequent calls from also overwriting this value - similar to this [issue](https://github.com/sherlock-audit/2025-05-yearn-ybold-th3outcast/issues/1).

### Internal Pre-conditions

1. An asset needs to have been deployed to a strategy.

### External Pre-conditions

None

### Attack Path

1. A legitimate user deploys a new strategy to an asset - USDT by calling `StrategyFactory::newStrategy(addressRegistry, USDT_address, "USDT-strategy")`.
2. Another user or malicious actor deploys that same asset - USDT using the same or different name parameter, but the same `addressRegistry` value, this ensures that it resolves to the same stability pool that is used in the second inner mapping.
3. `deployments[USDT_address][_newStrategy::SP()]` is now overwritten with the address of the new strategy.


### Impact

Frontends that perhaps rely on strategy discovery by parsing `emit NewStrategy(address(_newStrategy), _asset)` logs from the `StakerFactory` contract, or even verifying deployed strategies by calling [StrategyFactory::isDeployedStrategy()](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/88a3b89c05fd6e59ec130c79659195cd05d872af/yv3-liquityv2-sp-strategy/src/StrategyFactory.sol#L70-L76) could be misled into promoting these other strategies to users.

Strategy accumulated yields could also be potentially missed and assets deployed into malicious actor-controlled strategies. Similar to the same impacts in [issue](https://github.com/sherlock-audit/2025-05-yearn-ybold-th3outcast/issues/1).

### Mitigation

Revert if the given mapping already exists in `deployments`:

```solidity
    function newStrategy(
        address _addressesRegistry,
        address _asset,
        string calldata _name
    ) external virtual onlyManagement returns (address) {
        ...

        require(deployments[_asset][_newStrategy.SP()] == address(0), "mapping exists");  // @audit-fix
        deployments[_asset][_newStrategy.SP()] = address(_newStrategy);
        ...
    }
```
