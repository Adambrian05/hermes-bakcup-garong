# Strategy deployment mapping may be unreliable due to trust in external call (`SP()`)

https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/StrategyFactory.sol#L38


#### Summary

The deployment registry in the `StrategyFactory` contract uses the value returned from `_newStrategy.SP()` to record the deployment in the `deployments` mapping. Since `SP()` is a call to the just-deployed contract, this introduces a trust assumption and an opportunity for inconsistency or misdirection if the strategy's constructor does not initialize the `SP` value correctly or if it returns a malicious address.

#### Root Cause

In [`StrategyFactory.sol:38`](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/StrategyFactory.sol#L38
), the contract performs an external call to the freshly deployed strategy to retrieve the `SP` address:

```solidity
deployments[_asset][_newStrategy.SP()] = address(_newStrategy);
```

This introduces reliance on the behavior of the unverified strategy constructor logic.

#### Internal Pre-conditions

* Strategy constructor logic allows control or manipulation of `SP()` return value.
* Factory does not verify the correctness of the return value.

#### External Pre-conditions

* A malicious or erroneous strategy is deployed.
* `SP()` is overridden to return an incorrect or misleading value.

#### Attack Path

1. Attacker calls `newStrategy()` with crafted parameters or deploys a contract with tampered `SP()` return value.
2. `SP()` returns a fake or shared stability pool address (e.g., hardcoded or spoofed).
3. This value is used as a key in the deployment registry.
4. An incorrect mapping is formed in `deployments[_asset][_sp]`.
5. `isDeployedStrategy()` may later validate an illegitimate or duplicate deployment as legitimate.

#### Impact

* Strategy registry may be poisoned with incorrect or conflicting mappings.
* Legitimate strategies may be overridden or shadowed.
* Users and protocol components relying on `isDeployedStrategy()` may receive false positives.
* Attackers could trick integrations into interacting with malicious or duplicate contracts.

#### PoC

Assuming a malicious strategy with a hardcoded `SP()` value:

```solidity
function SP() external view override returns (address) {
    return address(0xDeadBeef...); // shared fake pool
}
```

Multiple deployments would all register under the same `_asset`/`SP()` key.

#### Mitigation

* Require `_stabilityPool` to be explicitly passed as a parameter to `newStrategy()`, and validate it against `SP()` return value from the deployed strategy:

  ```solidity
  require(_stabilityPool == _newStrategy.SP(), "SP mismatch");
  ```
* Alternatively, initialize `SP` inside the factory with verified values or trusted logic instead of querying from the contract post-deployment.
