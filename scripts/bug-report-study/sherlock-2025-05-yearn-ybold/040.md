# FeeManager can cause Denial of Service for yBOLD users by setting maxLoss too low

### Summary

The lack of a minimum check on `maxLoss` in `setMaxLoss` allows the FeeManager to set `maxLoss` to zero or an arbitrarily low value, which breaks yBOLD’s critical invariants. Specifically, yBOLD’s design expects that temporary losses—such as those arising from auctions or liquidations—are accepted within configured limits and are first covered by Accountant.sol before any fees are charged. However, if `maxLoss` is set to zero, the Accountant’s `report()` function will reject *any* reported loss, even small or temporary ones, since it requires `loss <= current_debt * maxLoss / MAX_BPS`. This effectively prevents the protocol from accepting normal, expected loss events and causes harvests and withdrawals to fail or revert, blocking users from accessing their funds. This directly violates the yBOLD protocol invariant that losses must be accepted and handled gracefully, ensuring no role can permanently block withdrawals or steal depositor funds. Thus, the absence of a minimum bound on `maxLoss` risks turning normal, expected loss reporting into a DoS vector that disrupts the entire protocol flow.


### Root Cause

In accountant.sol (function setMaxLoss), there is no minimum bound check on the _maxLoss parameter, allowing it to be set to zero or an arbitrarily low value. This omission means the protocol cannot enforce acceptance of temporary or small losses as intended. Consequently, the report() function’s invariant check, which requires loss <= current_debt * maxLoss / MAX_BPS, can become impossible to satisfy even for expected loss scenarios like auctions or liquidations. This breaks the fundamental yBOLD protocol invariant that losses must be accepted within configured limits before fees are taken, leading to potential denial-of-service conditions where legitimate strategy reports are rejected.https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L353-L363

### Internal Pre-conditions

1. FeeManager needs to call `setMaxLoss` to set `maxLoss` to exactly 0 or a very low value (e.g., close to 0 basis points).

2. The vault strategies must report any loss greater than zero (e.g., temporary losses during collateral auctions or liquidations).

3. The `report()` function in `accountant.sol` is called by the vault with a loss value exceeding the permitted threshold defined by the configured `maxLoss`.


### External Pre-conditions

1. Market conditions cause temporary losses during collateral auctions or liquidations that are reported by the vault’s strategy.

2. External liquidation or auction protocols trigger losses that are reflected in the vault’s asset value drop.

3. The vault reports these losses via the `report()` function while the `maxLoss` is configured too low or zero, causing rejection of legitimate losses.


### Attack Path

1. FeeManager calls `setMaxLoss()` to set `maxLoss` to 0 or a very low value.

2. A strategy experiences a temporary loss during collateral auction or liquidation, causing a loss greater than `current_debt * maxLoss / MAX_BPS`.

3. The vault calls `report()` on the Accountant contract to report the loss.

4. The `report()` function rejects the report because the loss exceeds the configured maxLoss limit.

5. As a result, the vault cannot report legitimate temporary losses, potentially blocking withdrawals or causing protocol disruptions.


### Impact

The vault and its depositors cannot report legitimate temporary losses incurred during collateral auctions or liquidations if `maxLoss` is set too low (e.g., 0). This results in:

* Vaults are being blocked from updating their state with valid losses.
* Potential denial of withdrawals or rebalancing actions, disrupting user experience and protocol operations.
* Violation of the yBOLD invariant that temporary losses within limits must be accepted before fees are applied.

While no direct financial theft occurs, this leads to operational disruption and loss of protocol functionality, negatively impacting all vault users.

### Mitigation

Enforce a sensible minimum bound on `maxLoss` (e.g., greater than zero) in the `setMaxLoss` function to ensure temporary losses can be reported and accepted as designed.

Additionally, implement validation logic or governance controls that prevent setting `maxLoss` to values that contradict the protocol’s operational assumptions, preserving the invariant that temporary losses during auctions are allowed within configured limits.

Finally, consider adding monitoring or alerts when `maxLoss` is set unusually low to catch potential misconfigurations early.
