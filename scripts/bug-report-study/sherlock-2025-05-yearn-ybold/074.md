# Silent Overwriting of deployments Mapping in StakerFactory.sol

### Summary

The StakerFactory contract overwrites the deployments mapping entry for a given asset each time a new strategy is deployed for that asset. This behavior can lead to unexpected overwriting of existing deployments, loss of tracking for previously deployed strategies, and potential security vulnerabilities if a malicious user can deploy strategies becuase theres no owner role in new strategy (stakerFactory.sol Not StrategyFactory.sol).

### Root Cause

The newStrategy function deploys a new strategy contract for a given _asset and stores the resulting strategy address in the deployments mapping:

deployments[_asset] = address(_newStrategy);
The mapping is defined as:

mapping(address => address) public deployments;
This design allows silent overwriting of an existing deployment for the same asset. Any prior strategy address for _asset is irreversibly replaced by the new one.

https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/StakerFactory.sol#L46

### Internal Pre-conditions

The management (or an external caller) needs to call newStrategy() with an asset address _asset.

The _asset must already have an existing strategy deployment (deployments[_asset] != address(0)).

### External Pre-conditions

The caller must have access to call newStrategy(). (If there is no restriction, any user can exploit this.) no restriction in stakerfactory.sol

The new Strategy contract must deploy successfully for the given _asset.

### Attack Path

The actor calls newStrategy(_asset, _name) on StakerFactory.

The function deploys a new Strategy contract.

The mapping deployments[_asset] is overwritten with the new strategy’s address.

The old strategy becomes untracked and possibly orphaned, potentially causing system inconsistencies or loss of control.

### Impact

The protocol suffers a loss of tracking and potential control over asset strategies. Existing strategies for an asset may become orphaned, potentially leading to mismanagement, broken integrations, or even security vulnerabilities if the old strategy retains control over funds.

### PoC

// Assume _asset already has a deployed strategy
factory.newStrategy(_asset, "New Malicious Strategy");
// Now deployments[_asset] points to the new strategy, replacing the original one.


Deploy a strategy for an asset A:


factory.newStrategy(A, "First Strategy");
Deploy another strategy for the same asset A:

factory.newStrategy(A, "Second Strategy");
The original deployment deployments[A] is replaced, and the first strategy becomes untracked.



### Mitigation

Add a deployment check in newStrategy():

require(deployments[_asset] == address(0), "Strategy already deployed for this asset");
Alternatively, if multiple strategies per asset are intended, refactor deployments to map to an array of strategies.
