# Setting `maxGain` to `0` will disable the profit health check, causing the gain verification to be completely skipped!

### Summary

If either a custom or the default maxGain is set to 0, the `else if (fee.maxGain > 0)` condition in the `report` function will evaluate to false, resulting in complete bypass of the profit verification check. Attackers could exploit this vulnerability to report arbitrarily high profits and circumvent risk controls.


### Root Cause

The `maxGain` parameter lacks conditional restrictions, allowing the feeManager to improperly set it to `0`. This causes the profit verification check to be completely bypassed in the report function when `if (gain > 0)` is evaluated.

### Internal Pre-conditions

1. The feeManager can set `maxGain = 0` in both the `setCustomConfig` and `updateDefaultConfig` functions.

### External Pre-conditions

2. When `maxGain = 0`, any value of `gain` will be automatically considered valid during the Vault's `report` call, since the `else if (fee.maxGain > 0)` condition evaluates to false.

### Attack Path

1. The feeManager can set `maxGain = 0` in both the `setCustomConfig` and `updateDefaultConfig` functions.

2. When `maxGain = 0`, any value of `gain` will be automatically considered valid during the Vault's `report` call, since the `else if (fee.maxGain > 0)` condition evaluates to false.

3. This results in complete bypass of the profit verification check. Attackers could exploit this vulnerability to report arbitrarily high profits and circumvent risk controls.


### Impact

Attackers can exploit this vulnerability to report arbitrarily inflated profits, enabling malicious strategies to artificially boost reported gains. This would cause the Accountant to levy unreasonable fees, ultimately depleting the strategy's funds.

### Mitigation

The `setCustomConfig` and `updateDefaultConfig` functions should prohibit setting `maxGain = 0`.
