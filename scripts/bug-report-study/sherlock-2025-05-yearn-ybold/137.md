# Unrestricted `newStrategy` Function Permits Unauthorized Strategy Instantiation and Registry Manipulation

### Summary

The `StakerFactory` contract's `newStrategy(address _asset, string calldata _name)` function is declared with `external` visibility and lacks any access control modifiers. This deficiency allows any arbitrary `msg.sender` to invoke the function, leading to the unauthorized deployment of `LV2SPStakerStrategy` instances. Such instances are erroneously configured with the `StakerFactory`'s global administrative parameters (e.g., `management`, `keeper`) and subsequently overwrite the `deployments[_asset]` mapping entry for the specified `_asset`.

### Root Cause

1.  **Unauthenticated Invocation:** The absence of an access control modifier (e.g., `onlyOwner` or `onlyManagement`) on `newStrategy` permits any external account or contract to call it.
2.  **Strategy Instantiation:** A new `Strategy` (alias for `LV2SPStakerStrategy`) is deployed: `IStrategyInterface _newStrategy = IStrategyInterface(address(new Strategy(_asset, _name)));`.
3.  **Misattributed Role Configuration:** The newly deployed strategy instance (`_newStrategy`) has its administrative roles set via external calls to the factory's current role parameters:
    *   `_newStrategy.setPerformanceFeeRecipient(performanceFeeRecipient);`
    *   `_newStrategy.setKeeper(keeper);`
    *   `_newStrategy.setPendingManagement(management);`
    *   `_newStrategy.setEmergencyAdmin(emergencyAdmin);`
4.  **Registry Compromise:** The `deployments[_asset]` mapping within `StakerFactory` is updated to associate `_asset` with `address(_newStrategy)`, potentially displacing a previously registered, legitimate strategy for that `_asset`.

### Internal Pre-conditions

None. 

### External Pre-conditions

None. 

### Attack Path

An unprivileged actor calls `newStrategy` with a target `_asset`. A new `LV2SPStakerStrategy` is deployed. This strategy's administrative roles are set to the factory's current, potentially trusted, administrative addresses. The `deployments[_asset]` mapping is overwritten

### Impact

    *   **User Misdirection:** Users querying the factory's `deployments` mapping or `isDeployedStrategy` function may be directed to unauthorized strategy instances. The fact that these unauthorized strategies list the factory's official admin addresses could lend them a false veneer of legitimacy.
    *   **Integrity of `isDeployedStrategy`:** The `isDeployedStrategy` function becomes unreliable as a means of verifying officially deployed strategies, as it will validate attacker-deployed strategies that have overwritten the mapping.
    *   **Potential for Denial of Service:** Legitimate strategies can be effectively de-registered from the factory's viewpoint if their `_asset` mapping is overwritten.
    *   **Resource Consumption:** Unfettered deployment can lead to unnecessary state growth on the blockchain.

### Mitigation

Implement stringent access control on the `StakerFactory.newStrategy` function.
