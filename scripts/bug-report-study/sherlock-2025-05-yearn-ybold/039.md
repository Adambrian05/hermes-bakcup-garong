# `StakerFactory` Will Render `isDeployedStrategy` Unreliable and Overwrite Deployment Records, Affecting Strategy Verification Systems

### Summary

The `StakerFactory` contract is responsible for deploying `LV2SPStakerStrategy` instances and tracking them via a `deployments` [mapping](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/StakerFactory.sol#L18): `mapping(address => address) public deployments;`. The provided code reference points to this mapping and its usage.

The core issues are:

1.  **Key Mismatch in `isDeployedStrategy`:**
    In `StakerFactory.newStrategy(address _asset, string calldata _name)`, the `_asset` parameter (which corresponds to the `_vault` address for the `LV2SPStakerStrategy`) is used as the key to store the newly deployed strategy:
    ```solidity
    deployments[_asset] = address(_newStrategy);
    ```
    However, the `isDeployedStrategy(address _strategy)` function retrieves the strategy's underlying asset via `IStrategyInterface(_strategy).asset()` and uses this address as the key to query the `deployments` mapping:
    ```solidity
    address _asset = IStrategyInterface(_strategy).asset();
    return deployments[_asset] == _strategy;
    ```
    Since a vault's address and its underlying asset's address are generally different, `isDeployedStrategy` queries the mapping with an incorrect key. This results in the function almost always returning `false`, even for currently active and legitimately deployed strategies.

2.  **Overwriting of Entries for the Same Key:**
    The `deployments` mapping can only store one strategy address per key. In `StakerFactory`, this key is the `_asset` parameter of `newStrategy` (the vault address). If `newStrategy` is called multiple times with the same `_asset` (vault address), each subsequent call will overwrite the previous strategy address stored for that key. This means the factory only "remembers" the latest strategy deployed for any given vault address.
    While the key mismatch (Issue 1) already makes `isDeployedStrategy` unreliable, if this were fixed (e.g., by `isDeployedStrategy` using the vault address as the key), the overwriting behavior would then cause it to incorrectly return `false` for any older (but still valid) strategies associated with that vault.

### Root Cause

1.  **Incorrect Key Usage in `isDeployedStrategy`**: The function uses `strategy.asset()` (the strategy's underlying asset address) as the lookup key, while the `deployments` map is populated using the `vault` address (passed as `_asset` to `newStrategy`) as the key.
2.  **Insufficient Granularity of `deployments` Mapping**: The `mapping(address => address)` structure, keyed by the `vault` address, inherently allows only one strategy per vault address. This design leads to previous entries being overwritten when a new strategy is deployed for the same vault address.


### Internal Pre-conditions

*   The `StakerFactory` contract is deployed.
*   The `newStrategy` function in `StakerFactory` uses its `_asset` parameter (vault address) to populate the `deployments` mapping.
*   The `isDeployedStrategy` function in `StakerFactory` uses `IStrategyInterface(_strategy).asset()` to query the `deployments` mapping.


### External Pre-conditions

*   An actor calls `StakerFactory.newStrategy(address _asset, ...)` where `_asset` is a vault address.
    *   To observe the key mismatch: Calling `isDeployedStrategy` for any strategy deployed where its underlying asset address differs from its vault address.
    *   To observe the overwriting issue: Calling `newStrategy` at least twice with the same `_asset` (vault address) parameter. Note that `StakerFactory.newStrategy` is permissionless.


### Attack Path

This vulnerability is more of a design flaw leading to incorrect state representation and function behavior rather than a direct path for an attacker to steal funds. However, it can lead to operational failures:

1.  User/System calls `StakerFactory.newStrategy(VAULT_X, "StrategyAlpha")`, deploying strategy `S_Alpha`.
    *   `deployments[VAULT_X]` is set to `address(S_Alpha)`.
2.  User/System calls `StakerFactory.isDeployedStrategy(address(S_Alpha))`.
    *   The function reads `deployments[S_Alpha.asset()]`. If `VAULT_X != S_Alpha.asset()`, this query will likely access an uninitialized or irrelevant slot, causing `isDeployedStrategy` to return `false` (Key Mismatch Issue).
3.  User/System calls `StakerFactory.newStrategy(VAULT_X, "StrategyBeta")`, deploying strategy `S_Beta` for the same vault.
    *   `deployments[VAULT_X]` is updated to `address(S_Beta)`, overwriting the entry for `S_Alpha` (Overwriting Issue).
4.  If `isDeployedStrategy` were to correctly use `VAULT_X` as a key for `S_Alpha` (hypothetically fixing the key mismatch), it would now find `address(S_Beta)` in `deployments[VAULT_X]`, so `isDeployedStrategy(address(S_Alpha))` would still return `false`.


### Impact

*   **`isDeployedStrategy` Function is Unreliable/Broken:** Due to the key mismatch, the `isDeployedStrategy` function in `StakerFactory` will almost always return `false`, making it ineffective for verifying if a strategy was deployed by this factory.
*   **Loss of Historical Deployment Records:** The factory overwrites previous strategy entries in the `deployments` mapping when a new strategy is deployed for the same vault address. This means the factory effectively "forgets" older strategies associated with that vault.
*   **Operational Issues and System Malfunctions:** Any external contracts, off-chain services, or user interfaces relying on `isDeployedStrategy` for critical checks (e.g., whitelisting, status display, administrative actions) will receive incorrect information. This could lead to:
    *   Valid strategies being misidentified as not deployed by the factory.
    *   Difficulties in auditing or managing the lifecycle of strategies, especially older ones.
*   **Deviation from Intended Design:** The presence of the comment `// Should be asset => pool => strategy` suggests the current implementation in `StakerFactory` is a simplification that misses the robustness of a multi-dimensional mapping (like in `StrategyFactory.sol`), which would be necessary to correctly track multiple strategies per actual asset or vault.
