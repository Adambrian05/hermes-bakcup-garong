# Approval Reset Failures in removeVault

### Summary

The removeVault function in the Accountant contract attempts to remove a vault from the fee system by:

Resetting any existing token approval (safeApprove(vault, 0)).

Marking the vault as removed in the vaults mapping.

However, if the call to safeApprove reverts, the vault removal process fails prematurely, leaving the vault in a partially removed state where it still has system access but without proper token approval. This creates a potential inconsistency and risks incomplete removal.

### Root Cause

In Accountant.sol:removeVault, the approval reset logic (safeApprove(vault, 0)) comes before marking the vault as removed (vaults[vault] = false), causing the function to revert before completing the removal if the token’s safeApprove fails.



https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L221-L237

### Internal Pre-conditions

Vault or fee manager needs to call addVault(vault) to set vaults[vault] to true.

ERC20 token allowance of the accountant to the vault needs to be non-zero.

ERC20 token used in the vault must revert on safeApprove(vault, 0).

### External Pre-conditions



ERC20 token used by the vault reverts when safeApprove(vault, 0) is called.

Gas price may spike, causing out-of-gas reversion on safeApprove.

### Attack Path

The vault is added and vaults[vault] is true.

The vault accumulates non-zero allowances from the accountant.

The vault’s token is modified (or deployed) to revert on approval resets (or misbehaves with non-standard logic).

The fee manager calls removeVault(vault).

The safeApprove(vault, 0) call reverts, preventing vaults[vault] = false from executing.

The vault remains marked as active in the accountant (vaults[vault] == true) but is no longer approved for tokens.



### Impact

The protocol suffers an inconsistent state where vaults that should be removed remain partially active.

Affected vault retains access to fee mechanisms and may exploit this inconsistency.

The attacker gains persistent system access, potentially griefing, exploiting vault access, or causing logic corruption.

In severe cases, an attacker could intentionally deploy a vault with a misbehaving ERC20, which reverts on approval reset, to lock the vault in an active state indefinitely.

### Mitigation

✅ Move vaults[vault] = false; before the external safeApprove call:

vaults[vault] = false;
if (ERC20(asset).allowance(address(this), vault) != 0) {
    try ERC20(asset).safeApprove(vault, 0) {} catch {
        // Log the failure
    }
}
emit VaultChanged(vault, ChangeType.REMOVED);
✅ Alternatively, wrap safeApprove in try/catch to handle external reverts without blocking vault removal.
