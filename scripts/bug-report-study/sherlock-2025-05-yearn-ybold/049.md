# `_tendTrigger` Fails to Signal Tending When New Collateral is Claimable if an Existing Auction is Active

### Summary

The system design includes an invariant stating: "Tending needs to be time-sensitive—once collateral is available for the strategy to claim, a keeper must call tend. The tend trigger must return true to signal that tending is required."
The `LiquityV2SPStrategy._tendTrigger()` [function ](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L253)is responsible for signaling to keepers whether the `_tend()` function should be executed. The `_tend()` function, among other actions, calls `claim()` if `isCollateralGainToClaim()` is true, which withdraws collateral rewards from the Liquity Stability Pool (SP).

The `_tendTrigger()` function includes the following logic:
```solidity
function _tendTrigger() internal view override returns (bool) {
    if (TokenizedStrategy.totalAssets() == 0) return false;

    // If active auction, wait
    if (AUCTION.available(address(COLL)) > 0) return false; // Condition A

    return block.basefee <= maxGasPriceToTend
        && (isCollateralGainToClaim() || COLL.balanceOf(address(this)) > dustThreshold); // Condition B
}
```

According to the invariant, if new collateral is available to be claimed from the Stability Pool (i.e., `isCollateralGainToClaim()` is `true`, satisfying a key part of Condition B), then `_tendTrigger()` should return `true` (assuming other criteria within Condition B, such as gas price, are also met).

**However**, if an existing auction for previously claimed `COLL` tokens still has tokens available (i.e., `AUCTION.available(address(COLL)) > 0`, making Condition A `true`), the `_tendTrigger()` function will **short-circuit and return `false` *before* Condition B is evaluated.**

This means that even if `isCollateralGainToClaim()` is `true` (indicating claimable collateral), `_tendTrigger()` will resolve to `false`. Consequently, this prevents the keeper from calling `_tend()`, thereby delaying the claim of new collateral from the Stability Pool.


### Root Cause

The `_tendTrigger()` function in `LiquityV2SPStrategy` incorrectly prioritizes the status of an ongoing `COLL` token auction over the availability of new collateral gains in the Liquity Stability Pool. If an existing auction still has `COLL` tokens available (i.e., `AUCTION.available(address(COLL)) > 0`), `_tendTrigger()` will return `false`. This occurs even if new collateral is ready to be claimed from the Stability Pool (i.e., `isCollateralGainToClaim()` is `true`). This behavior directly contravenes the specified invariant, which requires the tend trigger to be `true` when collateral is available for claiming to ensure timely action.

### Internal Pre-conditions

For this issue to manifest, the following conditions within the `LiquityV2SPStrategy` and its associated contracts must be met:

1.  **New Collateral Available in Stability Pool:** The strategy must have accumulated claimable collateral gains in the Liquity Stability Pool, meaning `SP.getDepositorCollGain(address(this))` is greater than the `dustThreshold`. This results in `isCollateralGainToClaim()` returning `true`.
2.  **Active Existing Auction:** A previously initiated auction for `COLL` tokens (collateral claimed in an earlier cycle) must still be active and have `COLL` tokens remaining for sale. This means `AUCTION.available(address(COLL))` is greater than `0`.
3.  **Strategy has Assets:** The strategy must have a non-zero total asset value, i.e., `TokenizedStrategy.totalAssets() > 0`.
4.  **Favorable Gas Price (Illustrative):** The current block's base fee should be less than or equal to the strategy's `maxGasPriceToTend`. While not strictly necessary for the bug to exist, if this condition *is* met, it highlights that the auction state is the sole reason `_tendTrigger()` returns `false` despite new claimable collateral.

### External Pre-conditions

The manifestation of this issue also depends on external states and events within the broader Liquity protocol and blockchain environment:

1.  **Liquidations in Liquity Protocol:** Liquidations must have occurred within the Liquity V2 system, leading to the distribution of collateral gains to depositors in the Stability Pool, including the `LiquityV2SPStrategy`.
2.  **Unsold Collateral in Auction:** The `AUCTION` contract, which handles the sale of `COLL` tokens previously claimed by the strategy, must not have sold all its available tokens from a current or previous auction round. This could be due to insufficient demand at the prevailing auction price, auction mechanics, or market conditions.

### Attack Path

This scenario describes a sequence of events leading to the invariant violation, rather than a direct malicious attack. It arises from the interplay of normal protocol operations and the keeper's reliance on the `_tendTrigger()` logic:

1.  **Initial State:** The `LiquityV2SPStrategy` holds deposits in the Liquity Stability Pool and may have previously claimed `COLL` tokens that are currently being auctioned.
2.  **Collateral Becomes Available:** Liquidations occur within the Liquity protocol, resulting in `COLL` token gains being credited to the strategy's Stability Pool deposit. Consequently, `isCollateralGainToClaim()` becomes `true`.
3.  **Concurrent Auction Activity:** Simultaneously, an auction for `COLL` tokens previously claimed by the strategy is still active, and `AUCTION.available(address(COLL))` is greater than zero (i.e., not all `COLL` in that auction has been sold).
4.  **Keeper Check:** A keeper (an automated agent) monitors the strategy and calls `_tendTrigger()` to determine if it should execute the `_tend()` function.
5.  **Trigger Returns False:** Despite `isCollateralGainToClaim()` being `true` (and assuming other conditions like `block.basefee` are favorable), the `_tendTrigger()` function evaluates the condition `if (AUCTION.available(address(COLL)) > 0)` first. Since this condition is `true`, `_tendTrigger()` immediately returns `false`.
6.  **Tending is Skipped:** Because `_tendTrigger()` returned `false`, the keeper does not call the `_tend()` function.
7.  **Delayed Claim:** As a result, the newly available `COLL` gains in the Stability Pool are not claimed by the strategy. This delay in claiming will persist as long as the pre-existing auction continues to have `COLL` tokens available (`AUCTION.available(address(COLL)) > 0`).


### Impact

The failure of `_tendTrigger()` to accurately signal the need for tending when new collateral is claimable (due to an active auction) has several negative consequences:

1.  **Delayed Collateral Claim:**
    *   The primary impact is that new collateral gains from the Stability Pool are not claimed by the strategy in a timely manner. This directly violates the "time-sensitive" requirement of the specified invariant.
2.  **Increased Exposure to Collateral Price Volatility:**
    *   While the `COLL` gains remain unclaimed in the Stability Pool, or while the overall process of claiming and auctioning is delayed, the strategy is exposed to potential adverse price movements of the `COLL` token. If the `COLL` price drops during this delay, the strategy will realize lower returns when the collateral is eventually claimed and sold.
3.  **Deferred Realization of Gains and Reinvestment:**
    *   The process of converting claimed `COLL` back into the strategy's underlying `asset` (e.g., BOLD) through the auction mechanism is postponed. This delays the realization of profits and the availability of these assets for reinvestment into the Stability Pool or for other strategy operations, potentially reducing overall yield.
4.  **Invariant Violation and System Unreliability:**
    *   The system demonstrably fails to adhere to its stated operational invariant. This can lead to keeper systems (which rely on `_tendTrigger()`) behaving suboptimally and the strategy underperforming compared to its design intentions. While a public `claim()` function exists that could potentially be called manually or by a more sophisticated keeper, the standard automated process governed by `_tendTrigger()` is compromised in this scenario.
