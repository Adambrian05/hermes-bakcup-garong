# Rogue Fee Manager will enable excessive fee extraction from strategies, harming vault depositors

### Summary

The lack of an upper bound on customMaxGain in setCustomConfig() will cause excessive fee extraction for vault depositors, as a rogue feeManager will configure customMaxGain to an abnormally high value (e.g., 65,535). This allows the report() function in Accountant.sol to accept extremely large gains without triggering a health check, resulting in the entire gain being taken as fees. Since totalFees = gain and fees are minted to the accountant (and later distributed to stakers), this setup enables the feeManager to indirectly extract large amounts from vault profits at the expense of depositor equity.

### Root Cause

**Root Cause:**
In https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L269-L286, the `setCustomConfig()` function lacks an upper bound check on `customMaxGain`, allowing it to be set to the full `uint16` range (up to 65,535). This bypasses the intended gain sanity checks in the `report()` function and leads to misconfigured vault parameters that can result in excessive fee extraction.

This violates the protocol's stated invariant that:

> “No role should be capable of stealing from depositors or permanently blocking withdrawals.”

By allowing a trusted role (`feeManager`) to set unchecked gain thresholds, the protocol exposes depositor funds to arbitrary fee siphoning, effectively enabling theft via misconfigured performance fees.

### Internal Pre-conditions

1. **FeeManager** needs to call `setCustomConfig()` to set `customMaxGain` to be **at least 65,535**, bypassing meaningful gain limits.
2. **FeeManager** needs to assign this configuration to a **vault with active strategies**.
3. A **strategy** under that vault needs to report a **gain** greater than or equal to its `current_debt`.
4. The **strategy’s `report()` call** must pass the `gain <= current_debt * (customMaxGain / MAX_BPS)` check, which is trivially satisfied due to the unbounded `customMaxGain`.
5. The **vault must not have a corresponding loss** during the same `report()` call, allowing `totalFees = gain` to take full effect.

### External Pre-conditions

1. **None required** — The exploit path is entirely internal and relies on privileged role misuse within the protocol.


### Attack Path

1. **FeeManager** calls `setCustomConfig()` on `Accountant.sol`, setting `customMaxGain = 65535` (max `uint16` value), and enables the `custom` flag.
2. The vault’s strategy later experiences or fabricates a large gain (e.g. 1000x profit vs. its debt).
3. The vault calls `report()` on `Accountant.sol`, passing this gain.
4. The `report()` function skips the `require(gain <= strategyDebt * maxGain / MAX_BPS)` check, since `65535 / 10000 = 6.5535x`, allowing nearly any gain to be considered valid.
5. The function then sets `totalFees = gain`, taking **100% of the gain** as performance fees.
6. These fees are credited to the accountant, not the depositors, effectively **draining strategy profits** away from users.


### Impact

Vault depositors suffer an **approximate loss of up to 100% of legitimate strategy profits**, as the full gain is redirected as fees due to unbounded `customMaxGain`. If the strategy reports a large gain, whether real or fabricated, the `report()` function will accept it and assign the entire gain to `totalFees`. Because `totalFees = gain` is applied unconditionally, **all the profit is taken from depositors and routed to the fee destination** (typically the protocol’s treasury or a fee receiver set by the vault).

Since the fee logic only accounts for avoiding loss-based overcharging, this leaves a blind spot where **malicious or misconfigured fee managers can extract all upside without violating any hardcoded checks**. The attacker (a malicious `FeeManager`) gains control over profit routing and can indirectly or directly claim these excessive fees. This **breaks the protocol invariant** that *“no role should be capable of stealing from depositors”*, as this path allows an authorized actor to steal all yield.

Even without malicious intent, a misconfiguration (e.g. a typo setting `customMaxGain = 65535`) could cause **routine strategy profits to be fully withheld from users**, silently undermining the integrity of the protocol’s fee model.

### Mitigation

The `setCustomConfig()` function should enforce an upper bound on `customMaxGain` using the same `MAX_BPS` (10,000 = 100%) constraint used elsewhere in the codebase. Specifically:

```solidity
require(customMaxGain <= MAX_BPS, "too high");
```

This ensures the maximum allowed gain that can be reported before triggering a revert is capped at 100% of the strategy’s current debt. It prevents a misconfigured or malicious `FeeManager` from setting extreme gain thresholds (e.g., 655.35x), which would allow the `report()` function to extract all or most of the profits as fees.

Additionally:

* Consider adding a sanity check or event alert if `customMaxGain` is set unusually high (e.g., >5000 = 50%), which could be a signal of misconfiguration.
* Optionally, change the `report()` logic to compute `totalFees` based on a percentage of gain, rather than taking the full gain unconditionally.

These mitigations ensure that even trusted roles cannot configure the system in ways that violate depositor safety guarantees.
