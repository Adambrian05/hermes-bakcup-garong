# function calling `Strategy::_freeFunds` can revert if the resulting `SP.withdrawFromSP` leave the SP with under 1e18 BOLD

### Summary

the internal function `_freeFunds` does not check if the resulting total bold deposit in SP is less than 1e18 BOLD after the amount is withdrawed.
because of how SP needs for the `totalBoldDeposits` is greater than 1e18 at all times, this would lead to the `Strategy` contracts to revert when it try to `_freeFunds` without adjusting the amount withdrawed.

### Root Cause

if we check the implementation of SP.withdrawFromSP in the [BOLD repo](https://github.com/liquity/bold/blob/36139d909fcc4d2c2918d7fd2b20b11951138ccb/contracts/src/StabilityPool.sol#L318) : 
```solidity
        require(newTotalBoldDeposits >= MIN_BOLD_IN_SP, "Withdrawal must leave totalBoldDeposits >= MIN_BOLD_IN_SP");
```

it is clear that after the withdraw is concluded, the last line would check if the `newTotalBoldDeposits >= MIN_BOLD_IN_SP`.

now if we check the internal function:
[Strategy.sol#L201-L205](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L201-L205)
```solidity
    function _freeFunds(
        uint256 _amount
    ) internal override {
        SP.withdrawFromSP(_amount, true);
    }
```
there are no check if the resulting withdraw of `_amount` would cause the BOLD in SP to be less than 1e18.
also the true flag is set meaning the SP would then try to also sent the yield/interest of both BOLD and COLL.
so the actual amount withdrawed can be more greater than `_amount`.

also if we check the implementation of `_emergencyWithdraw`:
[Strategy.sol#L218-L222](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L218-L222)
```solidity
    function _emergencyWithdraw(
        uint256 /*_amount*/
    ) internal override {
        _freeFunds(type(uint256).max); // Stability pool scales down to actual balance for us
    }
```
the implementation would try to withdraw the max amount that later would be scaled inside the SP.
while this is true, but the SP contract itself does not handle adjustment of the requirement of leaving 1e18 BOLD amount in SP. if the resulting withdraw would create total bold deposit below 1e18 then it would go revert.

### Attack Path

1. the strategy deposit 1_000e18 BOLD to SP
2. another user outside strategy deposit 1_000e18 BOLD to SP
3. total deposit is 2_000 BOLD
4. liquidation happen and offset 1_500e18
5. the user now can only withdraw 250e18 BOLD, and proceed to withdraw
6. the strategy try to withdraw 250e18 BOLD (either because withdraw/redeem or emergency withdraw)
7. tx revert

### Impact

Liquity SP handles BOLD token as an offset for liquidation in exchange of COLL.
so it is expected for BOLD amount in SP would reduced overtime and they would set the MIN_BOLD_AMOUNT to always exist inside SP as requirement.

if the Strategy does not handle this, the function that use internal function `_freeFunds` (core function and also the emergencyWithdraw for example) would revert if the resulting withdraw would cause the total bold deposit go below the 1e18 minimum bold amount.

so this would clearly broke the core functions of the strategy especially and not limited to `emergencyWithdraw`

### Mitigation

implement for amount of `_freeFunds` to be checked against `SP.getTotalBoldDeposits` so if the resulting withdraw would cause revert, then we can adjust the `_amount` to leave MIN_BOLD_AMOUNT or 1e18 BOLD in SP
