# Potential Price Manipulation in Strategy.sol's Auction Starting Price Calculation

### Summary

The `_tend` function in Strategy.sol contains a vulnerability in the auction starting price calculation that could lead to price manipulation, potentially resulting in collateral being sold at an unfair price.

### Root Cause

In the LiquityV2SPStrategy contract, the `_tend` function is responsible for initiating auctions for collateral tokens. The issue lies in the calculation of the auction starting price, which uses a complex formula that is vulnerable to manipulation:
```solidity
// slither-disable-next-line divide-before-multiply
AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);
```
The calculation performs division before multiplication, which can lead to precision loss. The comment `slither-disable-next-line divide-before-multiply` indicates that the developers were aware of this issue but chose to disable the warning.

The calculation should follow the "multiplication before division" pattern to minimize precision loss. Additionally, the use of multiple divisions by WAD (1e18) can compound precision errors, especially when dealing with tokens that have different decimal places.

This vulnerability is specific to the Yearn yBOLD protocol's auction mechanism, which is critical for converting collateral rewards into BOLD tokens. The issue is particularly concerning because it affects the starting price of auctions, which directly impacts the value extracted from collateral.

The root cause is in:
https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L237

### Internal Pre-conditions

1. The issue is present in the codebase and will be triggered every time an auction is initiated.
2. The presence of the slither-disable-next-line comment suggests the team is aware of potential issues but may not have fully addressed them.

### External Pre-conditions

1. The actual impact depends on specific token decimals and price values, which may not always result in significant precision loss.
2. The issue requires specific market conditions (high price volatility, specific token decimal combinations) to cause material losses.

### Attack Path

PoC provided.

### Impact

The impact is rated as Medium because:

1. The precision loss could lead to auctions starting at a lower price than intended, resulting in potential value loss for the protocol.
2. The issue doesn't directly lead to fund loss but creates conditions where economic value could be extracted unfairly.
3. The impact is limited to the auction starting price and doesn't affect the entire protocol's functionality.
4. Similar precision issues in other DeFi protocols like Compound and Aave have led to economic inefficiencies rather than direct fund theft.

The economic impact depends on the frequency of auctions and the value of collateral being auctioned. For high-value collateral, even small percentage errors can translate to significant absolute losses.

### PoC

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.23;

contract AuctionPriceManipulationPoC {
    uint256 constant WAD = 1e18;
    
    function demonstrateIssue() public pure returns (uint256 correctPrice, uint256 vulnerablePrice) {
        uint256 _available = 100 * 1e18; // 100 tokens
        uint256 _price = 1500 * 1e18; // $1500 per token
        uint256 _bufferPercentage = WAD + 1e17; // 10% buffer
        
        // Correct calculation (multiplication before division)
        correctPrice = (_available * _price * _bufferPercentage) / (WAD * WAD);
        
        // Vulnerable calculation (division before multiplication)
        vulnerablePrice = _available * _price / WAD * _bufferPercentage / WAD / WAD;
        
        // The difference between these values demonstrates the precision loss
    }
    
    function demonstrateWithSmallValues() public pure returns (uint256 correctPrice, uint256 vulnerablePrice) {
        uint256 _available = 1; // Very small amount
        uint256 _price = 1500 * 1e18; // $1500 per token
        uint256 _bufferPercentage = WAD + 1e17; // 10% buffer
        
        // Correct calculation
        correctPrice = (_available * _price * _bufferPercentage) / (WAD * WAD);
        
        // Vulnerable calculation
        vulnerablePrice = _available * _price / WAD * _bufferPercentage / WAD / WAD;
        
        // With small values, the vulnerable calculation can result in zero
    }
}
```

### Mitigation

Modify the auction starting price calculation to perform multiplication before division to minimize precision loss:
```diff
- // slither-disable-next-line divide-before-multiply
- AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);
+ // Perform all multiplications first, then divide
+ AUCTION.setStartingPrice((_available * _price * _bufferPercentage) / (WAD * WAD * WAD));
```
Additionally, consider using a more explicit calculation with intermediate variables to improve code readability and maintainability:
```solidity
// Calculate the total value in USD (with 18 decimals precision)
uint256 totalValueInUsd = (_available * _price);
// Apply buffer percentage
uint256 bufferedValue = (totalValueInUsd * _bufferPercentage);
// Normalize to correct decimals
uint256 startingPrice = bufferedValue / (WAD * WAD * WAD);
AUCTION.setStartingPrice(startingPrice);
```
This approach reduces the risk of precision errors and makes the code more maintainable.
