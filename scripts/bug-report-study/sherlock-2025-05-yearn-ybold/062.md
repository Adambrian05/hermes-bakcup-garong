# Strategy always sets AUCTION starting price to zero or miniscule amounts whenever `_tend()` is invoked leading to reverts or severly underpriced auctions

### Summary

Whenever there's enough `COLL` balance `(i.e _available_COLL_balance > dustThreshold)` and the overriden [LiquityV2SPStrategy::_tend()](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/88a3b89c05fd6e59ec130c79659195cd05d872af/yv3-liquityv2-sp-strategy/src/Strategy.sol#L225-L246) is invoked, the underlying `AUCTION` starting price is set using a price derived from the available `COLL` balance. This price always tends to zero and thus reverts on most invocation as `AUCTION::setStartingPrice()` reverts whenever the passed price is zero.

### Root Cause

The overrriden function - [LiquityV2SPStrategy::_tend()](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/88a3b89c05fd6e59ec130c79659195cd05d872af/yv3-liquityv2-sp-strategy/src/Strategy.sol#L225-L246) attempts to set the `AUCTION` starting price to one derived from available balances whenever the available balance is more than the set threshold and no active auctions exist:

```solidity
    function _tend(
        uint256 /*_totalIdle*/
    ) internal override {
        if (isCollateralGainToClaim()) claim();
        if (AUCTION.isActive(address(COLL)) && AUCTION.available(address(COLL)) == 0) AUCTION.settle(address(COLL));

        uint256 _toAuction = COLL.balanceOf(address(this));
        uint256 _available = COLL.balanceOf(address(AUCTION)) + _toAuction;
        if (_available > dustThreshold) {
            (uint256 _price, bool _isOracleDown) = COLL_PRICE_ORACLE.fetchPrice();
            uint256 _bufferPercentage = bufferPercentage;
            if (_isOracleDown || COLL_PRICE_ORACLE.priceSource() != IPriceFeed.PriceSource.primary) {
                _bufferPercentage *= ORACLE_DOWN_BUFFER_PCT_MULTIPLIER;
            }

            // slither-disable-next-line divide-before-multiply
            AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD); // Reverts if there's an active auction  // @audit: this will revert as the passed price always tends to zero

            COLL.safeTransfer(address(AUCTION), _toAuction);
            AUCTION.kick(address(COLL));
        }
    }
```

The problems lies in the how the price is calculated:

```text
        _available * _price / WAD * _bufferPercentage / WAD / WAD
```

For simplicity sake, lets assume the following:

1. Available balance is `100_000e6 USDT ($100k)`
2. Oracle price is `1e18` (1 USD)
3. Buffer percentage remains the default set `1.1e18` in the constructor
4. Oracle is up and is primary.

Thus the calculation will be evaluated as:

```text
        _available * _price / WAD * _bufferPercentage / WAD / WAD

        = 100_000e6 * 1e18 / 1e18 * 1.1e18 / 1e18 / 1e18
        = 100_000e6 * 1.1e18 / 1e36
        = 0 
```

Thus for legitimate tokens like USDT with 6 decimals, this price always evaluates to zero. This leads to reverts as passing a zero price causes `AUCTION::setStartingPrice()` to revert.

But with tokens  with 18 decimals, this might not revert - but the price will be evaluated to very miniscule prices that are not desireable e.g:

```text
       ASSUMING TOKEN IS DAI (18 decimals) and $100k
        _available * _price / WAD * _bufferPercentage / WAD / WAD

        = 100_000e18 * 1e18 / 1e18 * 1.1e18 / 1e18 / 1e18
        = 100_000e18 * 1.1e18 / 1e36
        = 110_000
```

### Internal Pre-conditions

1. Available balance is more than threshold

### External Pre-conditions

1. Auction has not started yet or it has started but can be settled to begin a new one.

### Attack Path

1. A call to the underlying `BaseStrategy::tendThis()` is made to deploy idle funds.
2. Control flow reaches `AUCTION::setStartingPrice()` as either previous auction is settled or there was no active auction.
3. Price is calculated, if price tends to zero as most tokens with `< 18 decimals` will - the call reverts, if price is not zero as `>= 18 decimal` tokens will evaluate to; the auction is started at very undesireable **miniscule** prices.

### Impact

Idle funds cannot be used to deploy new auctions in contracts with `< 18 decimals` leading to DOS, or auctions are always started with very miniscule prices in tokens with `>= 18 decimals` leading to severe underpricing thus affecting the overall health of the strategy.

### Mitigation

Remove the last WAD division:

```solidity
        // AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD)
        AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD); // @audit-fix
```
