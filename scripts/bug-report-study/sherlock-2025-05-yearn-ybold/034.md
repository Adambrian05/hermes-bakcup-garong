# Incorrect Scaling in Auction Price Calculation Leads to Severe Undervaluation and Loss of Strategy Funds

### Summary

The `_tend` function within the `LiquityV2SPStrategy` contract is responsible for managing accumulated collateral (`COLL`) by auctioning it off for the strategy's main asset (`asset`, which is BOLD). When initiating an auction, it calculates the starting price using the [formula](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L241):
`AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);`
where `WAD` is a constant `1e18`.

This calculation contains an error in scaling that results in the `startingPrice` being set orders of magnitude lower than the intended value (which should be the market price of `_available` COLL, denominated in `asset`, plus the `_bufferPercentage`).


### Root Cause

The fundamental issue is an excessive division by `WAD` (1e18). Let's define the terms and derive the correct vs. actual calculation:

*   `_available`: The amount of `COLL` token to be auctioned, in `COLL`'s base units (e.g., `NominalAmount_COLL * 10^Decimals_COLL`).
*   `_price`: The price of one full `COLL` token in terms of one full `asset` token, scaled by `1e18`. This is fetched from `COLL_PRICE_ORACLE`. (e.g., `TruePrice_AssetPerCOLL * 1e18`). The contract comment "Assumes the price feed is using 18 decimals" supports this interpretation.
*   `_bufferPercentage`: The desired buffer on the price, also scaled by `1e18` (e.g., a 110% buffer means `_bufferPercentage = 1.1 * 1e18`). `MIN_BUFFER_PERCENTAGE = WAD + 1e17` confirms this scaling.
*   `WAD`: A constant equal to `1e18`.
*   `D_coll`: The number of decimals for the `COLL` token.
*   `D_asset`: The number of decimals for the `asset` token (BOLD, which is typically 18 decimals as per Liquity V2 design).

The **intended (ideal) starting price** in base units of `asset` should be:
`Ideal_Starting_Price = (Amount of COLL in full units) * (Price of COLL in full asset units) * (Buffer Ratio) * (10^D_asset)`
`Ideal_Starting_Price = (_available / 10^D_coll) * (_price / WAD) * (_bufferPercentage / WAD) * (10^D_asset)`
Rearranging for safer arithmetic (multiplying before dividing where possible):
`Ideal_Starting_Price = (_available * _price * _bufferPercentage * 10^D_asset) / (10^D_coll * WAD * WAD)`

The **contract's current calculation** is:
`Contract_Starting_Price = (_available * _price * _bufferPercentage) / (WAD * WAD * WAD)`

Comparing the `Contract_Starting_Price` to the `Ideal_Starting_Price`:
The `Contract_Starting_Price` is effectively the `Ideal_Starting_Price` multiplied by a factor of:
`Factor = (10^D_coll) / (WAD * 10^D_asset)`
Since `WAD = 1e18` and `asset` is BOLD (so `D_asset` is likely 18):
`Factor = 10^D_coll / (1e18 * 1e18) = 10^D_coll / 1e36`

*   **Scenario 1: `COLL` has 18 decimals** (e.g., WETH, various LSTs).
    `Factor = 10^18 / 1e36 = 1 / 1e18`.
    The auction starting price will be `10^18` times *lower* than intended.
*   **Scenario 2: `COLL` has 8 decimals** (e.g., WBTC).
    `Factor = 10^8 / 1e36 = 1 / 1e28`.
    The auction starting price will be `10^28` times *lower* than intended.

In both common scenarios, the collateral will be offered at a price that is virtually zero.

### Internal Pre-conditions

*   The `_tend()` function is called by a keeper or other authorized caller.
*   The strategy has accumulated `COLL` tokens such that `_available` (combined balance in strategy and auction contract) is greater than `dustThreshold`.
*   The auction contract (`AUCTION`) is either not active or can have its parameters reset by `setStartingPrice()` before `kick()` is called. The code logic attempts to `settle()` a previous auction if needed.

### External Pre-conditions

*   The `_tendTrigger()` conditions evaluate to true (e.g., `block.basefee` is within `maxGasPriceToTend`).
*   `COLL_PRICE_ORACLE` returns a valid price `_price`.

### Attack Path

1.  An attacker (or any keeper, even a benign one) monitors the strategy for accumulated `COLL` and waits for `_tendTrigger()` conditions to be met.
2.  The `_tend()` function is called.
3.  Inside `_tend()`, the `startingPrice` is calculated using the flawed formula: `_available * _price / WAD * _bufferPercentage / WAD / WAD`. This results in an extremely low `startingPrice`.
4.  `AUCTION.setStartingPrice()` is called with this erroneously low price.
5.  The strategy transfers its `COLL` tokens (`_toAuction`) to the `AUCTION` contract.
6.  `AUCTION.kick(address(COLL))` starts the auction with the collateral available at the near-zero starting price.
7.  The attacker (or any participant) can then purchase all the `_available` `COLL` from the auction for a negligible amount of `asset` token.
8.  The strategy receives a tiny fraction of the actual value of its collateral, leading to a direct and significant loss of funds for the strategy and its depositors.

### Impact

*   **Severe Loss of Funds:** The strategy will sell its collateral (`COLL`) at a price that is drastically lower than its true market value (e.g., `10^18` or `10^28` times too low). This will result in an almost complete loss of the value of the collateral being auctioned.
*   **Strategy Insolvency/Depletion of Assets:** If this occurs repeatedly or with a large amount of collateral, it could rapidly deplete the strategy's assets, potentially leading to insolvency or an inability to honor user withdrawals at their correct value.
*   **Economic Exploitation:** This vulnerability creates a clear arbitrage opportunity for anyone to acquire valuable collateral from the strategy for virtually nothing.
*   **Damage to Protocol Reputation:** Such a critical flaw allowing for easy draining of funds would severely damage the trust and reputation of the protocol.
