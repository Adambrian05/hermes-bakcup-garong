# Open Factory Door - `StakerFactory` Permits Unauthenticated Strategy Creation

### Summary

The `StakerFactory` contract's `newStrategy` endpoint is publicly accessible, lacking any authorization mechanism. This oversight allows arbitrary actors to deploy `LV2SPStakerStrategy` instances. These rogue strategies are incorrectly initialized with the factory's legitimate administrative credentials (management, keeper, etc.), and critically, they can usurp the factory's official record for a given asset in the `deployments` mapping.

### Root Cause

The `StakerFactory.newStrategy(address _asset, string calldata _name)` function is `external` but critically misses an access control modifier, such as `onlyManagement`. As a result:
1.  Any external account can invoke `newStrategy`.
2.  A new `LV2SPStakerStrategy` is created.
3.  This new strategy's `pendingManagement`, `keeper`, `performanceFeeRecipient`, and `emergencyAdmin` are assigned the values currently held by the `StakerFactory` for these roles.
4.  The `StakerFactory.deployments[_asset]` mapping is updated to point to this newly created strategy, potentially overwriting a previously registered legitimate strategy for the same `_asset`.

### Internal Pre-conditions

None. 

### External Pre-conditions

None. 

### Attack Path

An adversary could exploit this by:
1.  Calling `newStrategy` for a widely used `_asset`.
2.  A new strategy instance is deployed, appearing "official" due to its admin roles mirroring the factory's trusted addresses.
3.  The factory's `deployments` mapping now points to the adversary's strategy, potentially causing UIs or dependent contracts relying on `isDeployedStrategy` to misidentify the official strategy.
4.  Users might be lured into interacting with this rogue strategy. While direct fund theft isn't immediate (as admin roles are still the factory's), it creates confusion, enables phishing vectors, and could lead to funds being committed to non-viable or deprecated strategies

### Impact

*   **Registry Poisoning:** The `deployments` mapping, intended as a canonical source of truth, becomes unreliable.
*   **Operational Disruption:** Legitimate strategies can be effectively "de-listed" from the factory's perspective, impacting services that rely on this registry.
*   **Resource Exhaustion:** The ability to deploy strategies without restriction can lead to unnecessary blockchain bloat.

### Mitigation

strict access control on the `StakerFactory.newStrategy` function. It should only be callable by a designated administrative address (e.g., the `management` address). This can be achieved by adding an `onlyManagement` modifier:

```solidity
// StakerFactory.sol
modifier onlyManagement() {
    require(msg.sender == management, "StakerFactory: Caller is not the management");
    _;
}

function newStrategy(address _asset, string calldata _name) 
    external 
    virtual 
    onlyManagement // <<< Apply access control
    returns (address) 
{
    // ... existing logic ...
}
```
