# `report()` Function Can Be DOSed Leading To `yBold` Gains Not Being Distributed Into `st-yBold`

### Summary

The `report()` function in `Accountant.sol` can be DOSed Due to Health check(due to micro gain manipulation)  leading to gains not being minted as yBold to be distributed to `st-yBOLD` 

### Root Cause


When `process_report` is called on yBOLD, any gain must be fully minted as yBOLD to `Accountant.sol`, from which it will be distributed to `st-yBOLD`.

If `process_report` reports a loss, `Accountant.sol` will not take any fees until the yBOLD price per share returns to 1. 
But on calling the `process_report` function in calls the `report()` function in `Accountant.sol` which does a helth check on both profit and Loss and returns the `totalFees/totalRefund`. On first look this is not an issue but the issue arises when the health check  is carried out  too ensure there isn't  " too much gain" using the `fee.maxGain` for gains and `fee.MaxLoss` for losses. As gains can be manipulated to always exceed the max gain Percentage causing the `report()` function to revert inturn causing the `process_report()` function to revert, preventing any gains from being minted to yBolds and being distributed to the `st-yBOLD`: impacting the protocol core functionality and causing loss of (`st-yBOLD`) yield accruing to the vaults indirectly leading to losses.

DETAILS:
this is possible because of the health check in the `report()` in the `Accountant.sol`:
https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L173
```solidity
            } else if (fee.maxGain > 0) {
       
                require(gain <= (strategyParams.current_debt * (fee.maxGain)) / MAX_BPS, "too much gain");
            }
```
As the gains input can be manipulated as it is calculated in the `process_report()` using the balance of the vault contract asset:
https://github.com/yearn/yearn-vaults-v3/blob/104a2b233bc6d43ba40720d68355b04d2dc31795/contracts/VaultV3.vy#L1154
```solidity
        total_assets = ERC20(_asset).balanceOf(self)
        current_debt = self.total_idle
    
    gain: uint256 = 0
    loss: uint256 = 0

    ### Asses Gain or Loss ###

    # Compare reported assets vs. the current debt.
    if total_assets > current_debt:
        # We have a gain.
        gain = unsafe_sub(total_assets, current_debt)
    else:
        # We have a loss.
        loss = unsafe_sub(current_debt, total_assets)

    ### Asses Fees and Refunds ###

    # For Accountant fee assessment.
    total_fees: uint256 = 0
    total_refunds: uint256 = 0
    # If accountant is not set, fees and refunds remain unchanged.
    accountant: address = self.accountant
    if accountant != empty(address):
        total_fees, total_refunds = IAccountant(accountant).report(strategy, gain, loss)
```
As gains can be manipulated by sending an extra amount of asset token(as much as 1 wei or more) to keep the gains above maximum gain percentage in situations where gains are equal to or a little less than the maximum gain percentage. leading to the `report()` function reverting inturn making the `process_report` revert.


### Internal Pre-conditions

1. In situations where the gains is equal to or sligthly less than the maximum gain percentage where the attack in cheap and easy to execute for this exploit to be easily and cheaply executed

### External Pre-conditions

- Strategy gain must approach but not exceed `fee.maxGain`.
- Attacker sends ≥1 wei of the asset token directly to the vault/strategy.
- The vault uses its `balanceOf` to compute `total_assets`, including attacker’s dust.
- `gain` exceeds `maxGain` → `Accountant.report()` reverts → `process_report()` reverts.
- No yield is minted/distributed to `st-yBOLD`, leading to halted rewards and denial of service.


### Attack Path

1. When the `process_report` function in the `Vault` contract is called which inturn calls the `report()` function in the ` Accountant.sol`.
2. An attacker see the transaction in the Memepool and frontruns it with an asset token deposit in to the `vault` contract. To increase the gains just enough to be higher than the maximum gaim percentage to trigger the Report to revert inturn making the `process_report` revert.

Details:
* In the `vault` contract the total asset is the balance of asset tokens held by the vault.
* gains is calculated by subtracting total asset by current debt:
```solidity 
        total_assets = ERC20(_asset).balanceOf(self)
        current_debt = self.total_idle
    
    gain: uint256 = 0
    loss: uint256 = 0

    ### Asses Gain or Loss ###

    # Compare reported assets vs. the current debt.
    if total_assets > current_debt:
        # We have a gain.
        gain = unsafe_sub(total_assets, current_debt)
```
* And in the 'Accountant` contract the health check is performing by comparing the gains is less than or equal  to the the maximum gain percentage:
```solidity 
require(gain <= (strategyParams.current_debt * (fee.maxGain)) / MAX_BPS, "too much gain");
```
So assuming:
* The supposed 
Maximum gain percentage is 250 Bold
And the gain is 250 Bold
Thats:
`245 <= 250`

Gotten from

Total asset being 1250 Bold
Total debt being 1000 Bold

So gains = 1245 - 1000 

* An attacker sees this and frontruns with a deposit of an extra  1 wei worth for even 1 BOLD asset token in to the vault.
Causing:
Total asset to be 1250 Bold + 1wei Bold/1Bold token

So gains now equals to 250Bold + 1wei Bold or even 250 Bold + 1 or more Bold Tokens
Making 
` 250 + 1wei Bold > 250(maximum gains)`

Leading to the `process_Report` to fail on multiple calls.


### Impact

The impact is high as  it tho it does not lead to direct loss of funds,but it leads to `process_report()` function reverting, preventing any gains from being minted to yBolds and being distributed to the `st-yBOLD`: impacting the protocol core functionality and causing loss of (`st-yBOLD`) yield accruing to the vaults indirectly leading to losses.It also leads to loss for a period duration depending on the situations affecting it.
