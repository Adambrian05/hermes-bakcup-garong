# StakerFactory - Unauthorized Strategy Deployment and Configuration

### Summary


The `StakerFactory` contract contains a critical access control vulnerability in its `newStrategy` function. This function, responsible for deploying and initializing new `LV2SPStakerStrategy` instances, lacks any permission checks, allowing any external account to call it. An attacker can exploit this to deploy strategies that appear legitimate due to being configured with the factory's official admin addresses, potentially misleading users or disrupting the factory's tracking of official strategies.



### Root Cause

The `newStrategy(address _asset, string calldata _name)` function in `StakerFactory.sol` is declared `external` but does not have any modifier (like `onlyManagement`) to restrict its invocation. Consequently, any address can trigger the deployment of a new `LV2SPStakerStrategy`. During this process, critical roles for the new strategy (performance fee recipient, keeper, pending management, emergency admin) are set to the current global values stored in the `StakerFactory`. Furthermore, the `deployments[_asset]` mapping in the factory is updated, potentially overwriting an existing legitimate strategy's entry for that asset.

```solidity
// StakerFactory.sol
// ...
    function newStrategy(address _asset, string calldata _name) external virtual returns (address) { // No access control
        // tokenized strategies available setters.
        IStrategyInterface _newStrategy = IStrategyInterface(address(new Strategy(_asset, _name)));

        _newStrategy.setPerformanceFeeRecipient(performanceFeeRecipient);
        _newStrategy.setKeeper(keeper);
        _newStrategy.setPendingManagement(management);
        _newStrategy.setEmergencyAdmin(emergencyAdmin);

        emit NewStrategy(address(_newStrategy), _asset);

        deployments[_asset] = address(_newStrategy); // Overwrites existing entry for _asset
        return address(_newStrategy);
    }
// ...
```

### Internal Pre-conditions

*   The `StakerFactory` contract is deployed.
*   The `StakerFactory` has its `management`, `performanceFeeRecipient`, `keeper`, and `emergencyAdmin` addresses configured.
*   The `LV2SPStakerStrategy` (imported as `Strategy`) contract bytecode is available for deployment.

### External Pre-conditions

*   An attacker (any EOA or malicious contract) can call functions on the deployed `StakerFactory`.
*   The attacker identifies a target `_asset` address (e.g., a popular ERC20).

### Attack Path

1.  The `StakerFactory` is deployed at `factoryAddress`. Its `management` is `admin_A`, `keeper` is `keeper_A`, etc.
2.  A legitimate `LV2SPStakerStrategy` (`LegitStrategy_X`) for `asset_X` may or may not have been deployed by `admin_A` previously.
3.  Attacker calls `StakerFactory(factoryAddress).newStrategy(asset_X, "Attacker's Decoy Strategy")`.
4.  A new `LV2SPStakerStrategy` instance (`AttackerStrategy_X`) is deployed.
5.  `AttackerStrategy_X`'s `pendingManagement` is set to `admin_A`, `keeper` to `keeper_A`, etc., inheriting these from the factory.
6.  `StakerFactory.deployments(asset_X)` is now updated to `address(AttackerStrategy_X)`. If `LegitStrategy_X` existed, it's now de-listed from this mapping.
7.  The `NewStrategy` event is emitted for `AttackerStrategy_X`.
8.  Users inspecting `AttackerStrategy_X` might see the familiar `admin_A`, `keeper_A` roles and mistakenly trust it.
9.  Off-chain systems relying on `StakerFactory.isDeployedStrategy(strategyAddress)` might now validate `AttackerStrategy_X` and invalidate `LegitStrategy_X` for `asset_X`.

### Impact

*   **User Deception & Fund Risk:** Users might deposit into attacker-deployed strategies, believing them official due to the familiar admin roles. While direct theft by the attacker isn't immediate via this vector alone (as admin roles are set to factory's admins), funds could be locked or mismanaged, especially if combined with H-02 (flawed yield).
*   **Disruption of Legitimate Strategy Discovery:** The `deployments` mapping being overwritten means `isDeployedStrategy` will falsely report attacker strategies as official and legitimate ones as unofficial for a given asset, confusing users and dApps.
*   **State Bloat & Griefing:** Malicious actors can deploy numerous strategies, increasing blockchain state and event log noise.

*Note: The PoC for H-01 assumes `LV2SPStakerStrategy` (aliased as `Strategy`) and its base contracts provide getters for roles like `keeper()` and `pendingManagement()`. The `IStrategyInterface` might need to be expanded or the deployed address cast to a more specific type for these checks.*

### Mitigation

access control for the `newStrategy` function in `StakerFactory.sol`. Restrict its invocation to a designated administrative role (e.g., `management`) using a modifier.

```diff
// StakerFactory.sol
// ...
+   modifier onlyManagement() {
+       require(msg.sender == management, "!management");
+       _;
+   }

-   function newStrategy(address _asset, string calldata _name) external virtual returns (address) {
+   function newStrategy(address _asset, string calldata _name) external virtual onlyManagement returns (address) {
// ...
```
