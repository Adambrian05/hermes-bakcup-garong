# External Callers will Cause Denial of Service for `claimNoDeposit` Operation on `LiquityV2SPStrategy` and `LV2SPStakerStrategy` Instances

### Summary

The `IStrategyInterface`, defined in `interfaces/IStrategyInterface.sol`, includes the [function signature](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/interfaces/IStrategyInterface.sol#L49) `claimNoDeposit() external;`.
Both `StrategyFactory.sol` (for `LiquityV2SPStrategy`) and `StakerFactory.sol` (for `LV2SPStakerStrategy`) deploy new strategy instances and cast them to `IStrategyInterface`. This indicates an expectation that these strategy contracts will fully implement the `IStrategyInterface`.

However, neither `LiquityV2SPStrategy.sol` nor `LV2SPStakerStrategy.sol` provide a direct implementation for the `claimNoDeposit()` function. Assuming that their common base contract, `BaseHealthCheck` (and its parent `BaseStrategy`), also does not provide a concrete, operational implementation for this specific interface function (or if it provides a `revert()` stub), any attempt to call `claimNoDeposit()` on instances of these strategies via the `IStrategyInterface` will fail. The EVM will not find the function selector in the contract's bytecode (or will execute a deliberate revert from a base class), causing the transaction to revert.

This effectively means that the `claimNoDeposit()` functionality, whatever its intended purpose (e.g., claiming specific rewards without new deposits, specific state updates), is unavailable for these strategy types, potentially disrupting any system or process that relies on it.

### Root Cause

Omission of the `claimNoDeposit()` function implementation in the `LiquityV2SPStrategy` and `LV2SPStakerStrategy` contracts (and potentially their base contracts), despite `claimNoDeposit()` being part of the `IStrategyInterface` they are expected to conform to, as demonstrated by their casting within their respective factory contracts.

### Internal Pre-conditions

- An instance of `LiquityV2SPStrategy` is deployed by `StrategyFactory`, or an instance of `LV2SPStakerStrategy` is deployed by `StakerFactory`.
- The address of the deployed strategy instance is available and is being interacted with as an `IStrategyInterface` type.
- The `claimNoDeposit()` function is not implemented by the specific strategy contract (`LiquityV2SPStrategy` or `LV2SPStakerStrategy`) nor is a functional version inherited from `BaseHealthCheck` or `BaseStrategy`.

### External Pre-conditions

- An external entity (EOA or contract, such as a keeper, management script, or integrated protocol) attempts to call the `claimNoDeposit()` function on the strategy instance.

### Attack Path

1.  The `StrategyFactory` deploys a new `LiquityV2SPStrategy` (or `StakerFactory` deploys `LV2SPStakerStrategy`).
2.  An authorized EOA, an automated system (e.g., keeper bot), or another smart contract obtains the address of this deployed strategy.
3.  This entity, interacting with the strategy generically through the `IStrategyInterface`, attempts to invoke the `claimNoDeposit()` function:
    ```solidity
    // Example pseudo-code
    IStrategyInterface strategy = IStrategyInterface(deployedStrategyAddress);
    strategy.claimNoDeposit(); // This call will revert
    ```
4.  The transaction attempting to call `claimNoDeposit()` reverts, because the function selector is not found in the target strategy contract's implementation, or a base class implementation explicitly reverts.

### Impact

The primary impact is a **Denial of Service (DoS)** for any operations that rely on the `claimNoDeposit()` function for `LiquityV2SPStrategy` and `LV2SPStakerStrategy` instances.
This can lead to:
-   **Inability to perform specific claim actions:** If `claimNoDeposit()` is intended for claiming certain types of rewards or assets, or for executing a particular state transition without deposits, these actions cannot be performed.
-   **Disruption of automated processes:** Yearn-internal systems (like keepers or management scripts) or external integrator systems that generically manage strategies via `IStrategyInterface` might fail or behave unexpectedly when encountering these strategy types if they try to call `claimNoDeposit()`.
-   **Functional incompleteness:** The strategies do not fully conform to the functional expectations set by `IStrategyInterface`, potentially leading to inconsistencies or requiring special handling for these strategy types.
-   **Potential for locked or delayed value:** If `claimNoDeposit()` is the sole mechanism to access or process certain types of value or information, that value/information might become inaccessible or its processing delayed.
