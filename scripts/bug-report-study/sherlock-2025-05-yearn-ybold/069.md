# Malicious (or not) vault manager will disrupt accounting integrity affecting protocol governance

### Summary

Incomplete vault removal in `Accountant.removeVault()` will cause accounting inconsistencies for the protocol as vault managers can repeatedly add/remove vaults to manipulate fee structures and bypass governance controls.

### Root Cause

In `Accountant.sol`, the `removeVault()` function fails to clear the vault's custom fee configuration when removing it (`customConfig[vault]` remains intact). https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L234 This is a mistake because:
1. The vault can be re-added while retaining its old fee settings
2. Creates inconsistency between `vaults` mapping and `customConfig` states
3. Allows circumvention of governance processes for fee updates

### Internal Pre-conditions

1. **Vault exists**: The vault must have been previously added via `addVault()`
2. **Custom config set**: The vault must have had custom fees configured via `setCustomConfig()`
3. **Manager access**: Caller must be `vaultManager` or `feeManager`

### External Pre-conditions

- None. The vulnerability is entirely internal to the accountant's state management.

### Attack Path

1. Initial setup: 
   - Admin adds VaultA with custom fees (maxGain: 20%, maxLoss: 10%)
   ```solidity
   accountant.setCustomConfig(VaultA, 2000, 1000);
```
2. Malicious removal:
VaultManager calls `removeVault(VaultA)` but custom config remains
3. Re-add exploitation:
VaultManager re-adds VaultA which automatically inherits old fees
```solidity
accountant.addVault(VaultA); // Still has 2000/1000 fees
```
4. Bypass governance: New fees apply without proper `setCustomConfig` approval

### Impact

Governance bypass: Fee changes can occur without proper authorization

Accounting errors: Vaults may operate with outdated/stale fee parameters

Financial risk: Incorrect fee structures may lead to under/over-charging

### PoC

1. Normal flow:
Admin: `addVault(VaultX)`
Admin: `setCustomConfig(VaultX, 3000, 1500)`
Admin: `removeVault(VaultX)` → custom config remains
2. Attack flow:
Attacker (as VaultManager):
```solidity
addVault(VaultX); // Now has previous 3000/1500 config
```
Result: VaultX operates with old fees without new approval

### Mitigation

Clear custom config during removal:
```solidity
function removeVault(address vault) external virtual onlyVaultOrFeeManager {
    require(vaults[vault], "not added");
    
    address asset = IVault(vault).asset();
    if (ERC20(asset).allowance(address(this), vault) != 0) {
        ERC20(asset).safeApprove(vault, 0);
    }
    
    vaults[vault] = false;
    delete customConfig[vault]; // Add this line
    
    emit VaultChanged(vault, ChangeType.REMOVED);
}
```
