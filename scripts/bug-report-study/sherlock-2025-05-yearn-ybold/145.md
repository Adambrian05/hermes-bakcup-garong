# Arithmetic Flaw in `LiquityV2SPStrategy` Leads to Free Collateral in Auctions

### Summary

The `LiquityV2SPStrategy` makes a critical miscalculation when determining the starting price for collateral auctions in its `_tend` function. An extra, erroneous division by the `WAD` constant (`1e18`) is performed on an already correctly scaled price. This results in the auction starting price being set to an infinitesimal fraction (`1/10^18`) of its intended value, allowing offered collateral to be acquired for virtually nothing.

### Root Cause

The problematic line in `LiquityV2SPStrategy._tend()` is:
`AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);`

Let `P_collateral_asset` be the oracle price of collateral in terms of the strategy's asset, scaled by `WAD`.
Let `B_factor` be the buffer percentage (e.g., 1.1 for 10%), scaled by `WAD`.
Let `Q_available` be the quantity of collateral available for auction, scaled by `WAD`.

The intended WAD-scaled starting price for the entire lot is: `(Q_available * P_collateral_asset / WAD) * B_factor / WAD`.

The contract code performs:
1.  `term1 = Q_available * P_collateral_asset / WAD` (Correct: Total value of collateral in asset, WAD-scaled)
2.  `term2 = term1 * B_factor / WAD` (Correct: Buffered total value, WAD-scaled). This `term2` is the *intended* starting price.
3.  `final_price = term2 / WAD` (**Incorrect**: This final division by `WAD` drastically reduces the price).

If `term2` was `X * 1e18` (representing `X` units of asset), the `final_price` becomes `X`. This is `1e18` times too small if the `AUCTION.setStartingPrice` function expects a WAD-scaled value.

**Impact Scenario:**
1.  Strategy has 100 units of `COLL` to auction. Oracle price is 50 `ASSET` per `COLL`. Buffer is 5%.
2.  Intended starting value (WAD-scaled): `(100e18 * 50e18 / 1e18) * 1.05e18 / 1e18 = 5000e18 * 1.05 = 5250e18`.
3.  Actual price set due to bug: `5250e18 / 1e18 = 5250`.
4.  An arbitrageur can acquire 100 `COLL` (worth `5000 * ASSET_PRECISION`) for just `5250` (likely `5250 wei` of `ASSET`), resulting in a near-total loss of the auctioned collateral's value for the strategy.

### Internal Pre-conditions

LiquityV2SPStrategy has accumulated some COLL (collateral token) to auction, exceeding dustThreshold.

COLL_PRICE_ORACLE is functioning and returns a _price.
AUCTION contract (created via AUCTION_FACTORY) is available and its setStartingPrice function is callable.
WAD constant is 1e18.

### External Pre-conditions

The tend() function is triggered (e.g., by a keeper).
Arbitrageurs are monitoring auctions created by this strategy.

### Attack Path

1.  Strategy has 100 units of `COLL` to auction. Oracle price is 50 `ASSET` per `COLL`. Buffer is 5%.
2.  Intended starting value (WAD-scaled): `(100e18 * 50e18 / 1e18) * 1.05e18 / 1e18 = 5000e18 * 1.05 = 5250e18`.
3.  Actual price set due to bug: `5250e18 / 1e18 = 5250`.
4.  An arbitrageur can acquire 100 `COLL` (worth `5000 * ASSET_PRECISION`) for just `5250` (likely `5250 wei` of `ASSET`), resulting in a near-total loss of the auctioned collateral's value for the strategy.

### Impact

*   **Immediate and Irrecoverable Fund Depletion:** Every auction conducted by the strategy will result in the collateral being sold for a negligible amount. This renders the strategy's liquidation mechanism actively harmful.
*   **System Insolvency Risk:** If this strategy is a key component of a larger system relying on its profitability, this flaw could cascade and threaten the stability of the entire protocol.

### Mitigation

The final, erroneous division by `WAD` must be removed from the starting price calculation in `LiquityV2SPStrategy._tend()`.

Corrected line:
```solidity
// Strategy.sol (LiquityV2SPStrategy)
// ...
    function _tend( uint256 /*_totalIdle*/ ) internal override {
        // ...
            // Corrected calculation:
            // uint256 startingPrice = (_available * _price / WAD) * _bufferPercentage / WAD;
            // Alternative with multiplication first for potential precision retention:
            uint256 startingPrice = (_available * _price * _bufferPercentage) / (WAD * WAD);
            AUCTION.setStartingPrice(startingPrice);
        // ...
    }
// ...
```
Both corrected forms achieve the right scaling. The version performing multiplications first is generally preferred to minimize precision loss from intermediate divisions, assuming no overflow in `_available * _price * _bufferPercentage`.
