# Misdirected Yield - `LV2SPStakerStrategy` Harvests for Another's Benefit

### Summary

The `LV2SPStakerStrategy`'s yield harvesting process is fundamentally misconfigured. It attempts to claim rewards from its underlying vault investment by instructing the *underlying vault's accountant* to distribute funds. However, an accountant's `distribute` function sends tokens it holds to *its own designated fee recipient*, not to the entity (the `LV2SPStakerStrategy`) making the harvest call. This results in a complete failure of the strategy to capture any yield for its users.

### Root Cause

Within `LV2SPStakerStrategy._harvestAndReport()`:
1.  `ACCOUNTANT` is defined as `IAccountant(IVault(asset).accountant())`, where `asset` is the underlying vault token (e.g., yvDAI). This `ACCOUNTANT` is therefore the accounting contract associated with the yvDAI vault, not the `LV2SPStakerStrategy` itself.
2.  The line `ACCOUNTANT.distribute(address(asset))` is executed.
3.  This translates to: "Hey yvDAI's Accountant, please distribute your balance of yvDAI tokens."
4.  The `Accountant.distribute` function (from `Accountant.sol`) then transfers any such yvDAI tokens it holds to `this.feeRecipient` (i.e., yvDAI's Accountant's fee recipient).
The `LV2SPStakerStrategy` is merely an initiator of this action and is not a beneficiary.

### Internal Pre-conditions

An LV2SPStakerStrategy instance (stakerStrategy) is deployed, with asset being an IVault implementing accountant() (e.g., mockUnderlyingVault).
mockUnderlyingVault.accountant() returns the address of a deployed Accountant contract (underlyingVaultAccountant).
underlyingVaultAccountant has a feeRecipient configured (underlyingVaultFeeRecipient).

### External Pre-conditions

The harvest() function (which calls _harvestAndReport) on stakerStrategy is invoked.
To demonstrate the flawed logic clearly, underlyingVaultAccountant is pre-funded with some asset tokens (e.g., yvDAI shares). (Normally, an accountant wouldn't hold the vault shares it accounts for, but other fee tokens. This pre-funding is just to show where tokens would go if it had them).

### Attack Path

1.  `LV2SPStakerStrategy` (LSS) holds yvDAI.
2.  yvDAI vault has its own Accountant (yvDAI_Acc) and its own Fee Recipient (yvDAI_FR).
3.  LSS calls `harvest()`.
4.  LSS tells yvDAI_Acc: "Distribute your yvDAI."
5.  If yvDAI_Acc happens to hold any yvDAI (unlikely, as accountants usually hold base assets from fees), it sends them to yvDAI_FR.
6.  LSS receives nothing. Its yvDAI balance is unaffected by this "harvesting" attempt.

### Impact

*   **Zero Yield Accrual:** The strategy is non-functional in its primary goal of generating and distributing yield to its stakers. All yield from the underlying vault is effectively lost from the perspective of `LV2SPStakerStrategy` users.
*   **Misleading Product:** Users depositing into this strategy under the expectation of earning yield will be disappointed, as the mechanism is broken.

### PoC

This PoC shows that when `LV2SPStakerStrategy.harvest()` is called, any `asset` tokens held by the `underlyingVaultAccountant` are transferred to `underlyingVaultFeeRecipient`, while `stakerStrategy` receives nothing.

        assertEq(stakerStrategyFinalBalance, stakerStrategyInitialBalance, "StakerStrategy balance incorrectly changed");

### Mitigation

The `_harvestAndReport` function in `LV2SPStakerStrategy` requires a complete overhaul of its yield realization logic:
1.  The call `ACCOUNTANT.distribute(address(asset));` must be removed.
2.  The correct method depends on how the underlying vault (`asset`) makes yield available to its liquidity providers:
    *   **Appreciation-based:** If yield is realized purely through the increasing value of the `asset` tokens (vault shares), then `_harvestAndReport` might only need to report the current balance: `_totalAssets = asset.balanceOf(address(this));`.
    *   **Explicit Claim:** If the `asset` (underlying vault) provides a function like `claimRewards()`, `harvestLPRewards()`, or similar, the `LV2SPStakerStrategy` must call *that specific function on the `asset` contract itself* to draw the rewards into its own balance.
