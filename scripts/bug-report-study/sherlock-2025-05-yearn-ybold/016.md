# Malicious token will brick strategy via sweep() for management

https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L171

**Summary**
The lack of token type validation in the `sweep()` function will cause a complete denial-of-service for the management address as a malicious token will revert on `safeTransfer()` and make sweeping other assets impossible.

**Root Cause**
In `LiquityV2SPStrategy.sol:171`, there is no validation on the `_token` passed to `sweep()`, and `safeTransfer()` is called directly on it without checking if the token conforms to ERC-20.

**Internal Pre-conditions**

1. Management needs to call `sweep()` with `_token` set to a malicious contract address.
2. A malicious ERC-20-like token with a reverting `transfer()` is transferred into the strategy contract.

**External Pre-conditions**

1. Malicious token is deployed on the same chain.
2. Token is transferred to `LiquityV2SPStrategy` by attacker or accidentally.

**Attack Path**

1. Attacker transfers a malicious token to the `LiquityV2SPStrategy` contract.
2. Management calls `sweep(maliciousToken)`.
3. The malicious token's `transfer()` reverts on call.
4. `safeTransfer()` propagates the revert.
5. Management cannot sweep *any* other tokens due to execution failure.

**Impact**
The management suffers a complete loss of sweep access to affected tokens. The attacker gains a permanent DOS vector against fund recovery for those tokens.

**PoC**

```solidity
contract MaliciousToken {
    function transfer(address, uint256) public pure returns (bool) {
        revert("sweep blocked");
    }
    function balanceOf(address) external pure returns (uint256) {
        return 1e18;
    }
}
```

**Mitigation**
Add a check to ensure the `_token` is in a trusted whitelist or check that `address(_token).code.length > 0` to avoid non-contracts. Consider adding a manual override path that can forcefully drain such tokens through multisig if needed.
