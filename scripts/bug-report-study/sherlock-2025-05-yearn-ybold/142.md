# Auction Pricing Leads to Gross Undervaluation of Collateral

### Summary

The `LiquityV2SPStrategy` contract's `_tend` function, responsible for initiating collateral auctions, contains a severe arithmetic error in the calculation of the auction's starting price. An extraneous division by the `WAD` constant (`1e18`) is performed on an already correctly WAD-scaled and buffered price. This results in the auction starting price being set at `1/WAD` (i.e., `1/1e18`) of its intended value, creating an opportunity for auctioned collateral to be acquired at a negligible fraction of its fair market value.

### Root Cause

The starting price for an auction is determined in `_tend()` by:
`AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);`
Where:
*   `_available`: WAD-scaled quantity of collateral (`COLL`).
*   `_price`: WAD-scaled oracle price of `COLL` in terms of the strategy's `asset`.
*   `_bufferPercentage`: WAD-scaled buffer factor (e.g., `1.1e18` for 10% buffer).
*   `WAD = 1e18`.

The sub-expression `(_available * _price / WAD * _bufferPercentage / WAD)` correctly computes the WAD-scaled total buffered market value of the `_available` collateral. This is the value that `AUCTION.setStartingPrice` presumably expects if it operates on WAD-scaled total lot values.
The *final division by `WAD`* in the contract's formula de-scales this correct value, reducing it by a factor of `1e18`.

### Internal Pre-conditions


*   `LiquityV2SPStrategy` is deployed.
*   It has accumulated some `COLL` (collateral token) to auction, exceeding `dustThreshold`.
*   `COLL_PRICE_ORACLE` is functioning and returns a `_price`.
*   `AUCTION` contract (created via `AUCTION_FACTORY`) is available and its `setStartingPrice` function is callable.
*   `WAD` constant is `1e18`.

### External Pre-conditions


*   The `tend()` function is triggered (e.g., by a keeper).
*   Arbitrageurs are monitoring auctions created by this strategy.

### Attack Path

1.  `LiquityV2SPStrategy` has `_available = 1 * 1e18` (1 unit of `COLL`).
2.  `COLL_PRICE_ORACLE` returns `_price = 2000 * 1e18` (COLL is worth 2000 units of `asset`).
3.  `bufferPercentage` is `1.1 * 1e18` (10% buffer).
4.  Correct WAD-scaled starting price should be: `(1e18 * 2000e18 / 1e18) * 1.1e18 / 1e18 = 2200 * 1e18`.
5.  Strategy's `_tend()` is called.
6.  The calculation becomes:
    *   `_available * _price / WAD = (1e18 * 2000e18) / 1e18 = 2000e18`.
    *   `(...) * _bufferPercentage / WAD = (2000e18 * 1.1e18) / 1e18 = 2200e18`. (This is `Y`, the correct value).
    *   `(...) / WAD = 2200e18 / 1e18 = 2200`.
7.  `AUCTION.setStartingPrice(2200)` is called.
8.  An arbitrageur sees an auction for 1 `COLL` (worth 2000 `asset`) starting at a price of `2200 / 1e18` `asset` per `COLL` (if `AUCTION` interprets the price per unit) or a total price of `2200` (if `AUCTION` interprets it as total lot price, but this usually means scaled by `1eN` where N is asset decimals, not unscaled). Assuming `setStartingPrice` expects a WAD-scaled total value, this is `1/1e18` of the actual value.
9.  Arbitrageur immediately buys the `COLL` for a pittance, e.g., for `2200` wei of `asset` instead of `2200 * 1e18` wei.
10. The strategy loses almost the entire value of the auctioned `COLL`.

### Impact

*   **Catastrophic Loss of Value:** Collateral will be consistently sold via auction at prices drastically below fair market value (effectively for near-zero cost). This will lead to rapid and direct financial losses for the strategy and its depositors.
*   **Compromise of Liquidation Viability:** The strategy's intended function of profitably liquidating collateral is inverted; it becomes a mechanism for extreme value leakage.

### Mitigation

auction starting price in `LiquityV2SPStrategy._tend()` must be rectified by removing the erroneous final division by `WAD`. The calculation should result in a WAD-scaled total value for the auction lot.

```diff
// Strategy.sol (LiquityV2SPStrategy)
// ...
    function _tend( uint256 /*_totalIdle*/ ) internal override {
        // ...
            // Corrected calculation to ensure WAD-scaled output:
-           AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);
+           // Option A (Multiplications first, careful of overflow):
+           // uint256 startingPrice = (_available * _price * _bufferPercentage) / (WAD * WAD);
+           // Option B (Step-wise, maintaining WAD scaling):
+           uint256 totalValueWAD = (_available * _price) / WAD; // Result is WAD-scaled
+           uint256 bufferedTotalValueWAD = (totalValueWAD * _bufferPercentage) / WAD; // Result is WAD-scaled
+           AUCTION.setStartingPrice(bufferedTotalValueWAD);
            
            COLL.safeTransfer(address(AUCTION), _toAuction);
            AUCTION.kick(address(COLL));
    }
// ...
```
It is critical to ensure that `AUCTION.setStartingPrice` indeed expects a WAD-scaled total value for the lot. If it expects a per-unit price or a differently scaled value, the entire formula (even the corrected one) would need re-evaluation based on the `IAuction` interface's precise requirements. Assuming it expects a WAD-scaled lot value, the above correction is appropriate.
