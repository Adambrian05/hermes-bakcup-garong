# Records in the `StakerFactory::deployments` mapping can be distorted by unauthorized users

## Impact
### Summary 
New staker contracts can be deployed using the `StakerFactory::newStrategy` function and this record is stored in the `StakerFactory::deployments` mapping with the `_asset` as key and address of the staker contract as value. However, this record can be distorted by deploying a new staker contract using a previously used asset.

### Vulnerability Details

The vulnerability lies in the fact that any user can call the `StakerFactory::newStrategy` function (see [here](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/StakerFactory.sol#L32-L48)) .

### Impact

Such records will be lost on the contract storage. Additionally, the `StakerFactory::isDeployedStrategy` can return a false value as shown in the poc.

## Proof of Concept
Add the following code in the DualToken.t.sol file

```javascript
function test_Spmaria_PoC_staker_factory_deployment_records_can_be_disrupted() public {

        assertEq(stakerFactory.isDeployedStrategy(address(staker)), true);

        // deploy another staker using same arguments as that of staker
        IStrategyInterface newStaker = IStrategyInterface(stakerFactory.newStrategy(address(vault), "Staked yBOLD Strategy"));

        assertEq(stakerFactory.isDeployedStrategy(address(staker)), false); // the mapping for the first staker contract is disrupted and replaced with the new staker contract

        assertEq(stakerFactory.isDeployedStrategy(address(newStaker)), true);
    }

```

## Recommended Mitigation Steps

Consider adding accesss control to the `StakerFactory::newStrategy` function to prevent unathorized access to avoid loss of storage data.
