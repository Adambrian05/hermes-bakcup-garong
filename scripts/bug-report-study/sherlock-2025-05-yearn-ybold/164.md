# [H-1] Incorrect Starting Price Calculation in Auction Contract Leads to Zero or Near-Zero Prices

### [H-1] Incorrect Starting Price Calculation in `LiquityV2SPStrategy::_tend` Leads to Zero or Near-Zero Prices

**Description:** 
In the auction contract, the starting price calculation is incorrectly implemented with three divisions by WAD (1e18), which results in the starting price being divided by 1e54 (1e18 * 1e18 * 1e18). This makes the starting price effectively zero or near-zero, causing the auction to start at an extremely low price.

LOC: `https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/Strategy.sol#L241`

The problematic code:
```solidity
AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD / WAD);
```

**Impact:** 
- Auctions will start at near-zero prices, allowing buyers to purchase assets at a fraction of their actual value
- Protocol loses significant value as assets are sold at incorrect prices
- Attackers can front-run auctions to purchase assets at minimal cost
- High severity as it directly impacts the economic security of the protocol

**Proof of Concept:**
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.23;

import {Test} from "forge-std/Test.sol";
import {console} from "forge-std/console.sol";

// Mock interface to simplify
interface IAuction {
    function setStartingPrice(uint256) external;
}

// Simplified Strategy contract for testing
contract MockStrategy {
    uint256 public constant WAD = 1e18;
    uint256 public constant DUST_THRESHOLD = 1e15;

    // Original equation from Strategy.sol
    function calculatePriceThreeWADs(
        uint256 _available,
        uint256 _price,
        uint256 _bufferPercentage
    ) public pure returns (uint256) {
        return _available * _price / WAD * _bufferPercentage / WAD / WAD;
    }

    // Corrected equation with two WADs, sequential syntax
    function calculatePriceTwoWADs(
        uint256 _available,
        uint256 _price,
        uint256 _bufferPercentage
    ) public pure returns (uint256) {
        return _available * _price / WAD * _bufferPercentage / WAD;
    }

    // Simplified tend condition check
    function shouldSetPrice(uint256 _available) public pure returns (bool) {
        return _available > DUST_THRESHOLD;
    }
}

contract StrategyPriceTest is Test {
    MockStrategy strategy;

    function setUp() public {
        strategy = new MockStrategy();
    }

    function test_AuctionPrice_ThreeWADs_Vs_TwoWADs() public {
        // Set price to 30 BOLD for 1 wstETH as requested
        uint256 _available = 1e18; // 1 wstETH
        uint256 _price = 30e18; // 30 BOLD per wstETH
        uint256 _bufferPercentage = 1.1e18; // 10% buffer

        // Check tend condition
        bool shouldSet = strategy.shouldSetPrice(_available);
        assertTrue(shouldSet, "Should set price when available > dustThreshold");

        // Three WADs (original, incorrect)
        uint256 priceThreeWADs = strategy.calculatePriceThreeWADs(_available, _price, _bufferPercentage);
        
        // Use emit log for guaranteed output
        emit log_named_uint("Price with three WADs", priceThreeWADs);
        
        // Two WADs (corrected)
        uint256 priceTwoWADs = strategy.calculatePriceTwoWADs(_available, _price, _bufferPercentage);
        emit log_named_uint("Price with two WADs", priceTwoWADs);

        assertEq(priceThreeWADs, 33, "Three WADs should produce incorrect integer price");
        assertEq(priceTwoWADs, 33e18, "Two WADs should produce correct 18-decimal price");
    }
}
```

```solidity
1000e18 * 1e18 / 1e18 * 1.1e18 / 1e18 / 1e18
= 1000e18 * 1.1e18 / 1e54
≈ 0 (effectively zero due to division by 1e54)
```

3. Correct calculation should be:
```solidity
1000e18 * 1e18 / 1e18 * 1.1e18 / 1e18
= 1100e18 (correct price with 10% buffer)
```

**Recommended Mitigation:** 
Remove the extra division by WAD. The correct implementation should be:
```solidity
AUCTION.setStartingPrice(_available * _price / WAD * _bufferPercentage / WAD);
```

This matches the test's calculation pattern and will give the correct price scaling. The fix ensures that:
1. The multiplication of available amount and price is properly normalized
2. The buffer percentage is correctly applied
3. The final price maintains the proper scale for the auction
