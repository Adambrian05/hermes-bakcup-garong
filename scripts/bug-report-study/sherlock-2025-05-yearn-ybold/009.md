# Strategy Actor Can Bypass Loss Limits and Cause Unexpected Vault Losses

### Summary

The root cause is that the report function’s logic only enforces maximum loss limits when no gain is reported, effectively skipping loss checks if a gain is present. This will cause a bypass of loss protections and potential unexpected large losses for the vault and its depositors, as a strategy actor can report a minimal gain alongside a large loss to circumvent the maxLoss enforcement and report excessive losses without restriction.



### Root Cause

Root Cause:
In Accountant.sol in the report function {https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/yv3-liquityv2-sp-strategy/src/periphery/Accountant.sol#L146-L199}, the loss limit check is conditionally performed only if the reported gain is zero or skipped. Specifically, the function branches:

When gain > 0, it performs gain-related checks and fee calculations but does not enforce the maxLoss limit.

When gain == 0, it performs the loss limit check using require(loss <= maxLoss).

This conditional structure creates a conceptual design flaw: the function assumes that gain and loss will never be reported simultaneously, but this is not enforced anywhere in the code or vault logic. As a result, if a strategy reports both a positive gain and a positive loss in the same call, the loss check is skipped.

This means the root cause is a conceptual design oversight in the enforcement of mutually exclusive gain and loss reporting. The protocol implicitly trusts vaults and strategies to uphold this invariant, but it is not enforced programmatically. This leaves the protocol vulnerable to a bypass of loss limits by reporting minimal gain alongside arbitrarily large loss, which could lead to unexpected loss acceptance and improper fee handling.

### Internal Pre-conditions

1. The Strategy must call report() with both gain > 0 and loss > 0 in the same transaction (which is currently allowed by the function’s interface).

2. The Vault (caller of report()) must not enforce any external logic to prevent simultaneous reporting of gain and loss.

3. The customConfig[msg.sender].maxLoss must be set to a value less than the maximum allowed (MAX_BPS), so that the maxLoss check would normally apply if triggered.

4. The Strategy must report a small positive gain (e.g., 1 wei) sufficient to enter the gain-check branch and skip the loss-check branch.

5. The Strategy must simultaneously report a loss larger than the allowed maxLoss, which goes unchecked because the function does not execute loss validation in this scenario.

### External Pre-conditions

1. The Vault contract must allow the Strategy to call report() without enforcing an external check preventing simultaneous gain and loss reporting.

2. The Oracle price feed used by the strategy and vault must not cause immediate liquidation or forced correction that would block or revert the strategy’s report call in the same transaction.

3. The protocol governance or configuration system must permit setting maxLoss to a value less than MAX_BPS without adding additional validation to prevent the inconsistent reporting pattern.

4. No external monitoring or keeper system should intervene to prevent or revert calls to report() when both gain and loss values are non-zero.



### Attack Path

1.A malicious or buggy Strategy prepares to call the report() function on the Vault (via the Accountant contract).

2. The Strategy crafts a report with both gain > 0 (e.g., a small amount like 1 wei) and loss > 0 (a large amount exceeding the configured maxLoss).

3. The Strategy calls report(strategy, gain, loss) on the Accountant contract.

4. Inside report(), the function processes the gain > 0 branch first, skipping the loss check entirely due to the if/else structure.

5. Since the gain branch executes without enforcing the loss limit, the large loss goes unchecked, bypassing the maxLoss validation.

6. The Vault accepts the report, potentially allowing the Strategy to bypass loss restrictions and report artificially reduced asset value, which can disrupt accounting, fee calculations, or liquidations.

### Impact

The Vault and its users suffer a loss of accurate accounting and risk controls because the maxLoss invariant can be bypassed when a strategy reports both a gain and a loss in a single report call. This may lead to underreporting or mismanagement of losses beyond the configured acceptable thresholds.

As a result:

- The Vault may accept excessive losses without triggering expected safeguards or restrictions.

- Performance fee calculations and profit distributions could become inaccurate, causing unfair fee extraction or misaligned rewards.

- The integrity of the Vault’s risk model and collateral accounting breaks, potentially exposing depositors to unexpected losses or degraded value.

While the attacker (strategy) may not gain direct funds, this bypass undermines the protocol’s loss limits invariant and can cause financial harm to the Vault and its users by enabling unbounded loss reporting.

### Mitigation

- Enforce mutually exclusive gain and loss reporting in the report function by adding a require statement that prevents both gain and loss from being non-zero simultaneously.

- Alternatively, handle cases where both gain and loss are reported by applying both maxGain and maxLoss checks in the same call.

- Add thorough unit and integration tests to ensure that reporting with simultaneous gain and loss is either disallowed or properly handled.

- Consider upgrading vaults to enforce strict reporting discipline or rejecting reports that violate this assumption.

- Document this invariant clearly so that strategy developers understand the required behavior.
