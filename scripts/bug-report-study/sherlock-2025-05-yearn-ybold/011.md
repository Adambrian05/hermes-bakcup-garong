# `COLL_PRICE_ORACLE` is incorrectly stored as immutable in the Strategy Contract

### Summary

The `LiquityV2SPStrategy` contract stores LiquityV2's price oracle as an immutable variable during deployment, fetching it from the `AddressesRegistry`. 

The issue is that LiquityV2 may later change the oracle address in `AddressesRegistry` contract. Since the strategy stores the original oracle as immutable, it cannot adapt to any future changes and continues to rely on the outdated oracle.

### Root Cause
The `LiquityV2SPStrategy` contract fetches the oracle from `IAddressesRegistry(_addressesRegistry).priceFeed()` during construction and stores it as an immutable variable. 

the issue is that LiquityV2 has functionality to change the `priceFeed` in their addressesRegistry through [addressesRegistry.setAddresses](https://github.com/liquity/bold/blob/main/contracts/src/AddressesRegistry.sol#L103), the strategy cannot adapt to the new oracle since it is stored in an immutable variable. 

### Internal Pre-conditions

None

### External Pre-conditions

Liquity updates the price feed address in their `AddressesRegistry` contract.

### Attack Path

None

### Impact

The following [invariant from the README](https://github.com/sherlock-audit/2025-05-yearn-ybold/blob/main/README.md#q-what-propertiesinvariants-do-you-want-to-hold-even-if-breaking-them-has-a-lowunknown-impact) is broken since the `LiquityV2SPStrategy` contract cannot update the oracle to what is being used by liquity:
>auctions must start from the collateral price multiplied by a buffer percentage, where the price is fetched from the oracle used by Liquity

If Liquity changes the oracle to fix incorrect price reporting, the strategy is unable to follow this change. It will continue to use the outdated oracle, which may be returning stale or incorrect prices. 

As a result, auctions can start at significantly underpriced values, this leads to a loss for depositors, as the auction may not recoup enough BOLD to match the correct value of the collateral.

### PoC

None

### Mitigation

Avoid storing the oracle as an immutable variable. Instead, fetch it from the `AddressesRegistry` each time it is needed
