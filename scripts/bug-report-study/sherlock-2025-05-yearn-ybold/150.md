# H-1 Fee Calculation Logic Flaw

## Summary

`Accountant::report` contains a flaw in its fee calculation logic where it incorrectly compares vault shares (`totalSupply()`) with underlying assets (`totalAssets()`) as if they represent equivalent units, leading to completely broken fee assessment across different vault types.

## Description

The vulnerability exists in the `report()` function at lines 162-168 where the contract attempts to reduce performance fees when a vault is "underwater":

```solidity
uint256 supply = vault.totalSupply();
uint256 assets = vault.totalAssets();
if (assets < supply) {
    uint256 needed = supply - assets;
    totalFees = gain < needed ? 0 : gain - needed;
}
```

This logic fundamentally misunderstands Yearn vault mechanics. In Yearn vaults:
- `totalSupply()` represents the number of vault shares/tokens in circulation
- `totalAssets()` represents the total underlying assets managed by the vault
- The relationship is: `pricePerShare = totalAssets() / totalSupply()`

The code compares these values directly as if 1 share should equal 1 underlying asset, which breaks the security guarantee that **performance fees should only be charged on actual profits and reduced when vaults are losing value**.

The issue triggers automatically during normal vault operations without requiring malicious input, it depends solely on the numerical relationship between shares and assets, which varies dramatically across different tokens and vault states.

## Impact
Impact is High

- Fee avoidance: vaults with assets numerically less than shares never pay performance fees  
- Excessive fees: vaults with assets numerically greater than shares may charge full fees even during losses  
- Breaks the economic model of vault fee calculation  

## Likelihood
Likelihood is High

- Happens on every gain report automatically  
- Varying token decimals cause inconsistent numerical comparisons  
- Vault price-per-share naturally deviates from 1 across vault types  
- Expected to occur in all vaults under real conditions  


## Proof of Concept

## Example – BOLD Vault with Profit, No Fees Charged

- The vault has **1,000 shares** and **10 BOLD tokens** in assets  
  (10 * 10^18 = 10,000,000,000,000,000,000 wei units)  
- A strategy reports a gain of **1 BOLD**, increasing assets to **11 BOLD**  
  (11 * 10^18 = 11,000,000,000,000,000,000 wei units)  
- `totalSupply()` returns **1,000 * 10^18 = 1e21** shares (in wei)  
- `totalAssets()` returns **11 * 10^18 = 1.1e19** assets (in wei)  
- Flawed check: `assets < supply` → **1.1e19 < 1e21** → **true**  
- Result: `totalFees = gain < (supply - assets) ? 0 : gain - (supply - assets)` → `totalFees = 0`  

Despite generating a real profit of 1 BOLD token, the vault charges **no performance fees** because it compares raw asset units against share units, leading to a meaningless comparison due to the large difference in numeric scale between shares and assets.

## Recommendation

Replace the flawed comparison with proper vault performance tracking:

```diff
- uint256 supply = vault.totalSupply();
- uint256 assets = vault.totalAssets();
- if (assets < supply) {
-     uint256 needed = supply - assets;
-     totalFees = gain < needed ? 0 : gain - needed;
- }
+ // Track high water mark to only charge fees on new profits
+ uint256 currentPPS = vault.pricePerShare();
+ uint256 hwm = highWaterMark[msg.sender];
+ 
+ if (hwm > 0 && currentPPS <= hwm) {
+     // Vault hasn't recovered previous losses, no performance fees
+     totalFees = 0;
+ } else {
+     // Update high water mark for future comparisons
+     highWaterMark[msg.sender] = currentPPS;
+     totalFees = gain; // Charge full performance fee
+ }
```

+ /// @notice Mapping vault => highest price per share achieved
+ mapping(address => uint256) public highWaterMark;
