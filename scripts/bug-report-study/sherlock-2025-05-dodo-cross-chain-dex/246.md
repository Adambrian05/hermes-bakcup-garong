# Flawed Pre-Calculation Check in `swapAndSendERC20Tokens Incorrectly Causes Valid Swaps to Fail

### Summary

In `GatewayCrossChain.sol` (and `GatewayTransferNative.sol`), the `_swapAndSendERC20Tokens` helper function {root cause: performs a balance check using a pre-calculated, worst-case estimate of the swap cost (`amountInMax`) instead of the actual cost (`amounts[0]`) returned after the swap executes}. This will cause an {impact: denial of service for legitimate cross-chain withdrawals} for {affected party: users whose target token is not the same as the destination chain's gas token}. This occurs as {actor: a user performing a normal cross-chain swap} will {vulnerability path: have their transaction reverted if their available `targetAmount` is sufficient to cover the *actual* swap cost for gas but insufficient to cover the *maximum possible* cost (`amountInMax`) including slippage, blocking a transaction that should have succeeded}.


### Root Cause

- In `GatewayCrossChain.sol` and `GatewayTransferNative.sol`, within the `_swapAndSendERC20Tokens` function: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L333 & https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L329
```solidity
  function _swapAndSendERC20Tokens(...) internal returns(uint256 amountsOut) {
      // ...
      uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(...);
      // 'amountInMax' is calculated as a worst-case estimate including slippage tolerance
      uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
      // ...
      // The actual swap is performed
      uint[] memory amounts = IUniswapV2Router01(UniswapRouter).swapTokensForExactTokens(...);

      // ...
      // Flawed check using the worst-case estimate instead of the actual result
@audit>      require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW"); 
      // ...
      // Subsequent logic correctly uses the actual amount spent, amounts[0]
      IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);
      amountsOut = targetAmount - amounts[0];
  }
```

The function calculates `amountInMax` as the maximum amount of `targetZRC20` it is willing to spend to acquire the necessary `gasFee`. After executing the swap, it receives the `amounts` array, where `amounts[0]` is the actual amount of `targetZRC20` spent. The flaw is the `require(targetAmount - amountInMax > 0)` check, which incorrectly validates the user's remaining balance against the pessimistic `amountInMax` estimate, rather than against the actual cost `amounts[0]`.

### Internal Pre-conditions

1.  A user's cross-chain transaction is being processed on ZetaChain by the `_handleEvmOrSolanaWithdraw` function, which then calls `_swapAndSendERC20Tokens`.
2.  The `targetZRC20` (the token the user wants to receive) is different from the required `gasZRC20` for the destination chain, so the swap logic within `_swapAndSendERC20Tokens` is triggered.
3.  The user's total available `targetAmount` is greater than or equal to the *actual* cost of the internal swap required to obtain the `gasFee` (this cost is returned as `amounts[0]` from `swapTokensForExactTokens`).
4.  The user's total available `targetAmount` is less than or equal to the *maximum possible* cost (`amountInMax`) that was calculated based on the initial quote plus slippage tolerance. This situation can occur if the user is swapping an amount very close to the cost of gas conversion, or more commonly, if there is positive slippage (favorable price movement) during the swap execution.


### External Pre-conditions

1.  A user initiates a **cross-chain** swap from a source chain where the desired final output token is not the native gas token of the destination chain.


### Attack Path

*(This describes a failure path for a legitimate operation due to the bug)*
1.  A user performs a cross-chain swap. After the primary on-chain DODO swap on ZetaChain, they are due to receive a `targetAmount` of `98` USDC.ZRC20. Their destination is an EVM chain that requires a `gasFee` paid in `ETH.ZRC20`.
2.  The `_handleEvmOrSolanaWithdraw` function calls `_swapAndSendERC20Tokens` to swap some of the `USDC.ZRC20` for the required `gasFee` amount of `ETH.ZRC20`.
3.  Inside `_swapAndSendERC20Tokens`:
    a.  `UniswapV2Library.getAmountsIn` is called to get a quote. It estimates that `90` USDC (`amountsQuote[0] = 90`) is needed to obtain the required `gasFee` in ETH.
    b.  `amountInMax` is calculated with slippage tolerance (e.g., 10%), resulting in `amountInMax = 99` USDC.
    c.  The contract approves the Uniswap Router for `99` USDC.
    d.  `IUniswapV2Router01(UniswapRouter).swapTokensForExactTokens(...)` is executed. Due to favorable market prices (positive slippage), the swap successfully acquires the `gasFee` by only spending `95` USDC. The returned `amounts` array has `amounts[0] = 95`.
    e.  The flawed check `require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");` is executed.
    f.  This becomes `require(98 - 99 > 0, ...)`.
4.  Because `98` is less than `99`, the subtraction underflows. The `require` statement's condition is false, and the transaction reverts.
5.  A **legitimate** transaction that should have succeeded is blocked. The user should have been able to spend `95` USDC for gas and have the remaining `3` USDC sent to them on the destination chain.


### Impact

* **Legitimate cross-chain swap transactions are incorrectly reverted**, preventing users from completing their intended action. The transaction fails even though the user had sufficient funds (`targetAmount`) to cover the *actual* cost (`amounts[0]`) of swapping for the required gas fee.
* The `require` check is overly pessimistic, using a worst-case cost estimate (`amountInMax`) for a balance check that should be based on the actual, realized cost (`amounts[0]`). This means any time there is favorable price movement (positive slippage), or when a user's available `targetAmount` happens to fall between the actual cost and the maximum estimated cost, the transaction will unfairly fail.
* This leads to a **poor user experience and reduces the reliability and capital efficiency of the protocol**. It does not cause a direct loss of funds but constitutes a Denial of Service for valid user operations.
* Affected Party: Users attempting cross-chain swaps where the destination token is not the native gas token of the destination chain.
