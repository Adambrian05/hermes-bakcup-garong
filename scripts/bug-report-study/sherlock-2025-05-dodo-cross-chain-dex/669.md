# Missing Verification After Swap Allows Attacker to Drain Unclaimed Refunds

### Summary

When the `targetZRC20` is different than the `zrc20` that `GatewayTransferNative:onCall()` receives from the Gateway on Zetachain, it performs a swap on Dodo to get to the `targetZRC20`.
```solidity

>>>     address zrc20,
        uint256 amount,
        bytes calldata message
    ) external override onlyGateway {
...SNIP

        if (decoded.targetZRC20 == zrc20) {
...SNIP...
        } else {
            // Swap on DODO Router
>>>         uint256 outputAmount = _doMixSwap(decoded.swapData, amount, params);

// @audit missing check that outputAmount is in decoded.targetZRC20
>>>         if (decoded.targetZRC20 == WZETA) {
                  IWETH9(WZETA).withdraw(outputAmount);
                  TransferHelper.safeTransferETH(receiver, outputAmount);
            } else {
                TransferHelper.safeTransfer(
>>>                 decoded.targetZRC20,
                    receiver,
                    outputAmount
                );
            }
...SNIP...
        }
    }
```

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L395

The problem is that there's no check to make sure that the `targetZRC20` is the same token that is swapped into on Dodo. This allows an attacker to deposit a low value token (e.g. DAI), set the `targetZRC20` to a high value token (e.g. WBTC), and then set the mixSwapParams to swap to to another low value token (e.g. DAI to USDC) effectively draining the contract of the high value token.

The same exact problem exists on GatewayCrossChain: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L465

The caveat here is that the `GatewayTransferNative` or `GatewayCrossChain` contracts must hold the high value token which is only possible when there are unclaimed refunds.

### Root Cause

Missing validation that the `targetZRC20` (which is user supplied) is the same token as `MixSwapParams.toToken` when there's a swap.

### Internal Pre-conditions

1. There must be unclaimed refunds in either GatewayTransferNative or GatewayCrossChain.

### External Pre-conditions

N/A

### Attack Path

1. Attacker calls `GatewaySend.depositAndCall` using a low-value token (e.g., DAI), setting the `targetZRC20` to a high-value token (e.g., WBTC) that has an unclaimed refund balance in GatewayTransferNative.
2. Attacker crafts the swap data to perform a low-value swap (e.g., DAI to USDC).
3. Upon execution, the contract incorrectly transfers the high-value token (WBTC) amount instead of verifying the swap outcome matches the targetZRC20.
5. Attacker receives high-value tokens, draining the contract's unclaimed refunds in that token.

### Impact

Attacker can drain all unclaimed refunds in GatewayNativeTransfer or GatewayCrossChain.

### PoC

_No response_

### Mitigation

Add a validation in both GatewayNativeTransfer and GatewayCrossChain ensuring the targetZRC20 equals the token that was swapped into.
