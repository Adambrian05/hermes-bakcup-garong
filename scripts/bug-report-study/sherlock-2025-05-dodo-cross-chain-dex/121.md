# Revert Failure with Malicious ERC20 Tokens

__Summary:__ The `onRevert` function's asset refund mechanism, while using `safeTransfer`, remains vulnerable to failure if the asset is a malicious ERC20 token designed to interfere with transfers.

__Vulnerability Detail:__ The `onRevert` function is responsible for returning assets to the user in case of a cross-chain transaction failure. It utilizes `TransferHelper.safeTransfer(context.asset, sender, context.amount);` to perform the refund. `TransferHelper.safeTransfer` is a safer way to interact with ERC20 tokens as it checks the return value of the `transfer` call and reverts if it's `false`. However, it still relies on calling the `transfer` function of the token specified by `context.asset`. A malicious ERC20 token contract could be specifically designed to make its `transfer` function revert or consume excessive gas when called by the `GatewaySend` contract, particularly in the context of an `onRevert` call.

__Impact:__ If a cross-chain transaction involving a malicious ERC20 token needs to be reverted, and that token's `transfer` function is designed to fail when called by `GatewaySend` during the revert process, the `safeTransfer` call will fail. This will prevent the refund from completing, resulting in the user's assets being permanently locked within the `GatewaySend` contract. This is an external dependency risk rather than a direct bug in `GatewaySend`'s logic, but it impacts the reliability of the revert mechanism.

__Recommendation:__ While `TransferHelper.safeTransfer` is the recommended way to interact with ERC20s, it cannot fully protect against deliberately malicious token implementations. Consider implementing a mechanism to only interact with a predefined list of trusted ERC20 tokens for cross-chain transfers, or clearly communicate the risks to users when interacting with untrusted or unknown token addresses.
