# User can permanently lock ETH in GatewaySend by sending it with ERC20 deposit

### Summary

The choice to make `depositAndCall()` payable without rejecting `msg.value` when `asset != ETH` is a mistake as it allows users to accidentally or maliciously send ETH that becomes permanently locked in the GatewaySend contract. This causes trapped ETH and undermines accounting consistency and user trust.

### Root Cause

In [`GatewaySend.sol#237-242`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L237-L242) and [`GatewaySend.sol#315-327`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L315-L327), the `depositAndCall()` function is marked `payable`, but there is no conditional check to ensure `msg.value == 0` when `asset != _ETH_ADDRESS_`. As a result, ETH is accepted and silently stored in the contract when ERC20 tokens are being transferred.

### Internal Pre-conditions

1. User calls `depositAndCall()` with an ERC20 token as `asset`.
2. User includes nonzero `msg.value`, either by mistake or via malicious UI.

### External Pre-conditions

None. 

### Attack Path

1. User constructs a transaction to call `depositAndCall()` with:
   - `asset = ERC20`
   - `msg.value = 1 ether`
2. The function does not reject the ETH.
3. The token transfer and swap proceed as normal.
4. ETH remains locked in `GatewaySend`, with no refund or withdrawal path.

### Impact

Users can permanently lose ETH if they mistakenly send it alongside an ERC20 deposit, as the contract accepts and traps the ETH without processing or refunding it. This leads to silent asset loss, bloated protocol balances, and opens a griefing vector where ETH can be repeatedly locked. If a withdrawal function is ever added, the trapped funds could be arbitrarily extracted, turning a user mistake into a protocol-level trust risk.

### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.20;

import {BaseTest} from "./BaseTest.t.sol";
import "@zetachain/protocol-contracts/contracts/zevm/interfaces/IGatewayZEVM.sol";

contract PoC_LockETH is BaseTest {
    // base in 'test_A2Z2BSwap'.  A - zetachain - B swap: token2A -> token2Z -> token2B -> token1B
    function test_A2Z2BSwap_UnexpectedETH() public {
        address targetContract = address(gatewayCrossChain); 
        uint256 amount = 100 ether;
        uint256 extraETH = 1 ether; // wrong ETH
        address asset = address(token2A); 
        uint32 dstChainId = 2;
        address targetZRC20 = address(token2Z);
        bytes memory sender = abi.encodePacked(user1);
        bytes memory receiver = abi.encodePacked(user2);
        bytes memory swapDataZ = ""; 
        bytes memory contractAddress = abi.encodePacked(address(gatewaySendB));
        bytes memory fromTokenB = abi.encodePacked(address(token2B));
        bytes memory toTokenB = abi.encodePacked(address(token1B));
        bytes memory swapDataB = encodeCompressedMixSwapParams(
            address(token2B),
            address(token1B),
            98995986959878634903,
            0,
            0,
            new address[](1),
            new address[](1),
            new address[](1),
            0,
            new bytes[](1),
            abi.encode(address(0), 0),
            block.timestamp + 600
        );
        bytes memory accounts = "";

        bytes memory payload = encodeMessage(
            dstChainId,
            targetZRC20, 
            sender,
            receiver,
            swapDataZ,
            contractAddress,
            abi.encodePacked(fromTokenB, toTokenB, swapDataB),
            accounts
        );

        vm.deal(user1, extraETH); // 사용자에게 ETH 할당

        // before state: user1 has extra ETH, gatewaySendA has no ETH
        uint256 beforeBalance = token2A.balanceOf(user1);
        assertEq(user1.balance, extraETH, "User1 should have extra ETH before test");
        assertEq(address(gatewaySendA).balance, 0, "GatewaySendA should have no ETH before test");

        vm.startPrank(user1);
        token2A.approve(address(gatewaySendA), amount);
        
        // ERC20 transfer with msg.value → stuck test
        gatewaySendA.depositAndCall{value: extraETH}(
            targetContract,
            amount,
            asset,         
            dstChainId,
            payload
        );

        vm.stopPrank();

        // expected: token2A is swapped normally
        assertEq(token2A.balanceOf(user1), beforeBalance - amount);

        // gatewaySendA have the extra ETH locked
        assertEq(address(gatewaySendA).balance, extraETH, "ETH got stuck in GatewaySendA");
        // user1 should have no ETH left after the test
        assertEq(user1.balance, 0, "User1 should have no ETH left after test");
    }
}
```


### Mitigation

To prevent ETH from being mistakenly sent during ERC20 deposits, add a strict input validation check at the beginning of the `depositAndCall()` function. This ensures that `msg.value` is only accepted when the asset being transferred is ETH, and strictly rejected otherwise:

```solidity
if(fromIsETH) {
   ...
} else { // from Is Not ETH
    // add this
    require(msg.value == 0, "Unexpected ETH");
}
```
