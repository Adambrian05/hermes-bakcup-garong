# The slippage protection inside `_swapAndSendERC20Tokens()` is completely ineffective






## Summary
On the Zeta chain, when withdrawing, you need to pay gasZRC20, which is obtained through `_swapAndSendERC20Tokens()`. However, this exposes the transaction to sandwich attacks.


## Root Cause
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L306

```javascript
function _swapAndSendERC20Tokens(

```
The `_swapAndSendERC20Tokens` function internally uses the real-time price from the UniswapV2 pool for slippage protection calculations, rendering this protection ineffective.  

Specifically, the function employs `UniswapV2Library.getAmountsIn()` to determine the required `amountIn`. However, sandwich attacks manipulate the price of `gasZRC20` by front-running the transaction, forcing the victim to pay an excessively large `targetZRC20` amount for a minimal `gasZRC20` output. Since `amountInMax` is calculated based on the manipulated price (`amountsQuote[0]`), it becomes meaningless as a protection mechanism.  

Additionally, `block.timestamp` represents the block's mining time, and `block.timestamp + MAX_DEADLINE` is effectively equivalent to `block.timestamp`, meaning the transaction remains valid indefinitely. This fails to provide any meaningful expiration protection for the transaction.  

This issue exists in both the `GatewayTransferNative` and `GatewayCrossChain` contracts.  

Even if some blockchains prevent mempool snooping, external transactions altering the pool price can still cause losses in this transaction.

## Attack Path
Assuming the initial pool ratio between `gasZRC20` and `targetZRC20` is 1:1:  

1. When an attacker detects `_swapAndSendERC20Tokens()` in the mempool,  
2. They front-run the transaction by swapping a large amount of `targetZRC20` for `gasZRC20`, skewing the pool ratio to 1:10,000 (e.g., making `gasZRC20` extremely expensive).  
3. The victim’s `_swapAndSendERC20Tokens()` transaction then executes at this manipulated price. Since the function relies on the real-time pool price, the victim must pay an exorbitant amount of `targetZRC20`—e.g., 100,000 `targetZRC20` for just 10 `gasZRC20`.  
4. The attacker then sells their `gasZRC20` back at a favorable rate, profiting from the arbitrage.  

Because the pool price can be freely manipulated, the victim loses nearly all their `targetZRC20`, while the attacker only needs to leave a minimal amount to ensure the cross-chain checks pass. This allows the attack to succeed with minimal cost to the attacker.
## Impact
The user loses the cross-chain tokens.

## Mitigation
The price is determined using an average price or a third-party oracle's price, or the amountInMax is pre-calculated by the user off-chain and passed as a parameter to this function.
