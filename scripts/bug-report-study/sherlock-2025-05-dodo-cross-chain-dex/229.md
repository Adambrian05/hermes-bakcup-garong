# ERC-20 Approve Bug in `_swapAndSendERC20Tokens` function

### Summary

Every time `_swapAndSendERC20Tokens` function tries to do

```Solidity
IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);
```
it does so without first zeroing out any existing allowance. As a result, tokens that enforce “must zero first” (e.g. ZRC-20-USDC, ZRC-20-USDT) will revert immediately.

Non-standard tokens (e.g. USDT, which does not return bool) will cause the Uniswap router call to revert.

Even after the swap, the two subsequent approve(..., address(gateway), …) calls suffer from the same pattern—if there is any non-zero allowance previously set for (targetZRC20, gateway) or (gasZRC20, gateway), those will revert as well.

Because each approve(...) can revert, the entire cross-chain swap fails and the contract ends up in “refund” mode. 

### Root Cause

The issue can be found here: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L302

```Solidity
    function _swapAndSendERC20Tokens(
        address targetZRC20,
        address gasZRC20,
        uint256 gasFee,
        uint256 targetAmount
    ) internal returns(uint256 amountsOut) {
        // Get amountOut for Input gasToken
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );

        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);

        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE
        );

        require(IZRC20(gasZRC20).balanceOf(address(this)) >= gasFee, "INSUFFICIENT_GAS_FOR_WITHDRAW");
        require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");

        IZRC20(gasZRC20).approve(address(gateway), gasFee);
        IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);

        amountsOut = targetAmount - amounts[0];
    }
```

### Attack Path

User bridges for the first time, sending 1000 USDC:

```Solidity
amountInMax = 1000; // based on slippage calc
IZRC20(USDC).approve(UniswapRouter, 1000);
```
This works because the current allowance is zero.
Router does the swap and sends tokens.

Later, same user wants to swap again, this time needing amountInMax = 900.

Here’s what happens:

```Solidity
// THIS LINE REVERTS
IZRC20(USDC).approve(UniswapRouter, 900);
```
But there is still an existing allowance of 1000 from the first time.

ZRC-20-USDC doesn’t allow changing from non-zero → non-zero.

### Impact

Any token enforcing the “must zero first” rule or not returning bool will always cause `_swapAndSendERC20Tokens` to revert, so the Gateway can never complete its intended swap. Users cannot bridge those popular stablecoins (ZRC-20-USDT, ZRC-20-USDC) or any fee-on-transfer token without triggering a refund.

### Mitigation

Always zero out allowance before Setting new one

```Solidity
// Step 1: Reset to 0
IZRC20(targetZRC20).approve(UniswapRouter, 0);
// Step 2: Set exact allowance
bool ok = IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);
```
