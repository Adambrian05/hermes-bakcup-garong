# Direct USDT approval will break ERC-20 deposits

### Summary

Tokens like USDT on Ethereum mainnet enforces a non-standard allowance model: any attempt to change an existing non-zero approval to another non-zero value will revert. Calling `approve(spender, newAmount)` directly without first resetting the allowance to zero will lead to a DoS.

USDT.ETH is listed in the supported assets in the zetachain docs. https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets

### Root Cause

The `GatewaySend` contract attempts to directly change the approval to a non-zero value, which requires the approval to be first set to zero. However, USDT requires you to set the approval to zero before changing it to prevent race conditions.

Happens in `GatewaySend::_handleERC20Deposit` and `GatewaySend::_doMixSwap`

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L184

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L199

### Internal Pre-conditions

1. The contract attempts to approve tokens using `IERC20(_token).approve(...)`.
2. The `_token` address points to USDT that requires zero approval before change in approval.

### External Pre-conditions

- The contract attempts to approve USDT

### Attack Path

1. User interacts with the protocol using USDT.
2. The contract calls IERC20(_token).approve(...) to approve USDT.
3. Since USDT requires zero approval before change in approval, the call reverts.
4. The transaction fails, potentially DoSing or breaking protocol functionality.

### Impact

- All the functions using the `GatewaySend::_handleERC20Deposit` and `GatewaySend::_doMixSwap` functions will lead to a DoS when working with USDT.

_No response_

### Mitigation

Zero out the approval before changing to another amount.
