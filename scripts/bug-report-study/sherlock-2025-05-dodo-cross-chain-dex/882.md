# Static Slippage Parameter in `_swapAndSendERC20Tokens()` Causes Swap Reverts And Economic Losses

### Summary

The `_swapAndSendERC20Tokens()` function uses a statically configured slippage value, set once at deployment with no way to adjust the figure in the contract—to determine the maximum amount of targetZRC20 tokens that can be swapped to obtain a fixed amount of gasZRC20 tokens. This hardcoded slippage fails to reflect real-time on-chain conditions, potentially leading to failed swaps, user fund loss, or exploitation by front-runners and MEV bots.

This becomes even more severe as protocol is supporting tokens like wbtc and these swaps are happening on UniSwapV2. 
These leads to a situation where price can easily be manipulated either to cause the swap to fail or for economic gain. 

### Root Cause

A static slippage value (defined as a percentage in per-mille) is used to compute the `amountInMax` in `_swapAndSendERC20Tokens()` function 
 without accounting for:

1. Real-time liquidity on Uniswap pairs.

2. Market volatility or sudden token price changes.

3. Token-specific liquidity risks like wbtc.

The computation is done as follows:

```solidity
uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
This slippage buffer remains fixed regardless of live market behavior.
```
Normally, this slippage should serve but under certain market conditions, this can lead to serious problems.

Another factor that makes this a critical bug is that there is no function in the contract to set slippage after deployment. So the slippage set at deployment is immutable unlike other variables that can be changed by the owner. There seems to be a missing function to change the slippage. This means the slippage parameter will definitely be outdated in relation to current market conditions leading to unintended revert and economic loss for users.

### Internal Pre-conditions

1. slippage is set in the contract and cannot be dynamically updated.

2. The protocol calls Uniswap V2’s `swapTokensForExactTokens()` with this buffer.



### External Pre-conditions

Swap is routed through UniswapV2 pairs, where liquidity may be low or imbalanced. Also, price can shift due to arbitrage, volatility, or MEV.

### Attack Path


**A. Front-running / Economic Exploitation:**
1. An attacker observes an incoming cross-chain swap with a known, static slippage variable under certain harsh market conditions.

2. The attacker temporarily pushes up the price of the gasZRC20 token pair via small trades. Forces the protocol to use the maximum allowed `amountInMax`.

3. Once swap is complete, attacker reverses price to profit.

4. The protocol overpays in targetZRC20, causing economic inefficiency.

**B. Revert / Denial of Service:**
1. A user attempts a cross-chain transfer using _swapAndSendERC20Tokens().

2. Due to price slippage on Uniswap or gas token volatility, the swap fails:

```solidity
swapTokensForExactTokens(...) reverts because amountIn > amountInMax
```

### Impact

1. Cross-chain transfers may fail completely, especially during high volatility.
2. Overpayment in token swaps causing loss of fund for users.
3. Predictable static slippage opens doors to front-running or sandwich attacks.

### PoC

_No response_

### Mitigation

 Make Slippage Dynamic to correspond to current market conditions.

Either allow users to specify slippage or set a function that can allow owner to modify slippage to reflect current market conditions.
