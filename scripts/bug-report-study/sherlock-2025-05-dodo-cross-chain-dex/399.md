# Attacker will steal funds from the contract by exploiting parameter inconsistency

### Summary

Missing validation between input parameters of [`GatewayTransferNative.withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530-L555) will cause a loss of funds for the contract as an attacker will provide mismatched token addresses and amounts.

### Root Cause

In `GatewayTransferNative.withdrawToNativeChain` the function accepts parameters from two different sources without validating that they are consistent with each other. This allows an attacker to transfer cheap tokens while swapping more expensive tokens already in the contract.

Key issues:

1. No validation between `zrc20` parameter and `params.fromToken` from the decoded message
2. No validation between `amount` parameter and `params.fromTokenAmount` from the decoded `message` param.
3. When ETH is involved, `msg.value` is passed to the swap function while `params.fromTokenAmount` is used for calculations

### Internal Pre-conditions

1. Contract needs to have a balance of valuable tokens that an attacker can target (unclaimed refunds)
2. Contract must be processing user-initiated cross-chain withdrawals

### External Pre-conditions

None specific required.

### Attack Path

1. Attacker calls `withdrawToNativeChain` with a cheap token address as `zrc20` and minimal `amount`
2. In the same call, attacker provides a message with `params.fromToken` set to a more expensive token that the contract holds
3. The contract transfers the cheap token from the attacker but uses the expensive token in the `_doMixSwap` function
4. The swap is executed using the valuable token from the contract's balance instead of the cheap token provided by the attacker
5. The swapped tokens are then withdrawn to the attacker's specified destination

### Impact

The contract suffers an approximate loss equivalent to the difference between the value of the expensive token used in the swap and the cheap token provided by the attacker. The attacker gains this difference.

### PoC

_No response_

### Mitigation

Add validation at the beginning of the `withdrawToNativeChain` function to ensure consistency between directly provided parameters and those decoded from the message:

```solidity
function withdrawToNativeChain(
    address zrc20,
    uint256 amount,
    bytes calldata message
) external payable {
    // Decode message first to validate parameters
    (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message);
    
    // Validate parameter consistency
    require(zrc20 == params.fromToken, "Token address mismatch");
    
    if(zrc20 == _ETH_ADDRESS_) {
        require(amount == msg.value, "ETH amount mismatch");
    } else {
        require(amount == params.fromTokenAmount, "Token amount mismatch");
        require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
    }
    
    // Continue with existing implementation...
}
```

Additionally, other parameter validations should be added to ensure all user inputs are consistent throughout the entire transaction flow.
