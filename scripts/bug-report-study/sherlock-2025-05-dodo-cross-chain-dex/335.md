# Native ETH deposits and call reversion is not handled in `GatewaySend`

## Vulnerability Details

In `GatewaySend`, whenever a user opts to execute the EVM -> Zetachain call flow to interact with a target contract on Zetachain (for instance, GatewaySend -> GatewayTransferNative), the call may revert. In such cases, `GatewaySend` designates itself as the revert address, and the `GatewaySend.onRevert` function is responsible for processing the token refunds to the user.

The problem occurs because native ETH refunds are not addressed in `GatewaySend.onRevert`, leading to a fallback to the `onAbort` function of the Zetachain contract (e.g., `GatewayTransferNative.onAbort`). Consequently, users are unable to retrieve their refunds through `GatewayTransferNative.onAbort`, as the wallet address obtained there corresponds to the user's EVM address. This oversight results in a loss of funds for the user, as `onRevert` fails to manage ETH refunds.

## POC

Consider the following scenario

1. Alice initiates a transfer of 1 ETH using `GatewaySend.depositAndCall`.
2. Prior to reaching `GatewayTransferNative.onCall` through `GatewayEVM`, the transaction fails, and the default revert address is set to `GatewaySend`, invoking `GatewaySend.onRevert`.
3. As a result, she will not receive her ETH refund because `GatewaySend.onRevert` is designed solely for ERC20 token refunds.
4. Her call defaults to `GatewayTransferNative.onAbort` on Zetachain, but her refund information is linked to her EVM address, which she does not own on Zetachain.
5. Ultimately, her funds become stuck as ZRC20 tokens within `GatewayTransferNative`.

## Root Cause

Lack of native ETH refunds handling in `GatewaySend.onRevert`

## Impact

Loss of funds for user

## Mitigation

In `GatewaySend.onRevert`, consider handling ETH refunds by utilizing `TransferHelper.safeTransferETH`
