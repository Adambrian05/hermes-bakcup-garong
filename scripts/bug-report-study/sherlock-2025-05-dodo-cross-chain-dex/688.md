# GatewayTransferNative can be drained via ETH_ADDRESS token collection bypass

### Summary

The `withdrawToNativeChain` function of `GatewayTransferNative` allows attackers to drain any tokens held by the contract by using the `_ETH_ADDRESS_` constant to bypass token collection while specifying different target tokens in the input param `message`. When `_ETH_ADDRESS_` is used as the `zrc20` parameter, the function skips collecting input tokens from the user, but the actual tokens being bridged are determined by the decoded message params. This enables attackers to withdraw assets using the contract's token reserves (collected refunds) without paying anything, effectively draining the contract.

### Root Cause

`GatewayTransferNative` implements [withdrawToNativeChain](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530C14-L530C35) function which can be called by anyone to move funds from ZetaChain to destination chain. The vulnerability stems from a critical disconnect between token collection and token usage, combined with improper handling of the `_ETH_ADDRESS_` constant:
```solidity
function withdrawToNativeChain(address zrc20, uint256 amount, bytes calldata message) external payable {

  // Collection is based on zrc20 parameter
  if (zrc20 != _ETH_ADDRESS_) {
      require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), ...);
  }
  // ...
  // But actual swap uses tokens specified in the provided message
  (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message);
  uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params); 
uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(externalId, decoded, outputAmount, decoded.receiver); // Uses contract's balance of target token
```

Attackers can simply provide  `zrc20 = _ETH_ADDRESS_` to skip collection while targeting any token held by the contract via the message parameters. The actual token being bridged is `decoded.targetZRC20` from the `message` input param. That enables attacker to withdraw funds held by `GatewayTransferNative` and withdraw them to a destination chain to an account controlled by the attacker.

### Internal Pre-conditions

Contract holds token balances from collected refunds



### External Pre-conditions

None

### Attack Path

1. Attacker identifies valuable tokens held by the contract from refunds 
2. Attacker crafts a `swapMessage` specifying the target token they want to drain and desired output
3. Attacker calls `withdrawToNativeChain(_ETH_ADDRESS_, amount, swapMessage)` where:
- `_ETH_ADDRESS_` bypasses input token collection
- swapMessage targets the valuable token held by the contract
4. Function skips token collection: `if (zrc20 != _ETH_ADDRESS_)` condition is false
5. Fee transfer appears successful: low-level call to `_ETH_ADDRESS_` returns `(true, "")`
6. Attacker successfully drains out the asset by bridging it out to the destination chain

Attack can be repeated targeting different tokens until contract is fully drained

### Impact

High severity - attackers can drain any tokens held by the `GatewayTransferNative` contract by exploiting the token collection bypass

### PoC

_No response_

### Mitigation

Remove `zrc20` input param because asset is already encoded in the `message` input param as `targetZRC20`. Also, if asset is native asset, make sure that msg.value is provided that matches the amount to be bridged.
