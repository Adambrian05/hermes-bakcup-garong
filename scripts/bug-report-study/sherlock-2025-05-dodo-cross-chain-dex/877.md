# Improper Check for Refund Ownership in `claimRefund`

The `claimRefund()` function allows users to claim refunds associated with an `externalId`. This function attempts to verify the caller by either ensuring they are part of the predefined `bots` mapping or checking that their address matches the intended address extracted from `walletAddress`. 

However, this method is flawed due to two key issues:
- The `walletAddress` field's validation is incomplete and fails to ensure authenticity.
- Code logic might incorrectly interpret refund ownership when `walletAddress` is either unset or malformed.

This could lead to unauthorized refund claims if a malicious user knows the `externalId` of pending refunds and manipulates the function behavior.

(https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L589)

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}
```
The assumption here is that the refund can be claimed by either `msg.sender` matching the stored wallet address or if `msg.sender` is an authorized bot. 

However if `walletAddress` validation is missing or incorrect, attackers can exploit this logic.

### Recommendation

To mitigate this vulnerability, the developer should add cryptographic validation or verification to ensure `walletAddress` authenticity.
