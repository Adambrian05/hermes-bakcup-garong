# Unauthorized fund claim for Solana cross-chain refunds via flawed recipient Determination

## Summary

When a cross-chain transfer from ZetaChain to Solana fails and triggers a revert, the refund is correctly queued for manual claiming. However, the `claimRefund` function has a flaw where it defaults the refund `recipient` to `msg.sender` (the caller of `claimRefund`) if the stored `walletAddress` is not exactly 20 bytes long. While the protocol intends for a "refund bot" to collect these tokens and manually process refunds for non-EVM addresses (like Solana), the flawed access control logic in `claimRefund` permits any caller to assert themselves as the `recipient`. This creates a race condition susceptible to front-running, directly undermining the intended bot mechanism and leading to the theft of user funds.

## Root Cause

The root cause is a logical flaw within the [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680) function, specifically in how it determines the rightful `recipient` of a refund and enforces access control:

```js
function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```
Incorrect Recipient Determination:

1. The `claimRefund` function initializes `address receiver = msg.sender;`.
2. It then attempts to override this with: `if(refundInfo.walletAddress.length == 20) { receiver = address(uint160(bytes20(refundInfo.walletAddress))); }`.
3. Solana addresses are 32 bytes long. Therefore, for any Solana refund stored in `refundInfos`, the condition `refundInfo.walletAddress.length == 20` will always evaluate to `false`.
4. Consequence: The `receiver` variable will never be set to the actual Solana recipient's EVM-compatible address; it remains `msg.sender` (the caller of `claimRefund`).

## Attack Path

1. A legitimate user attempts a cross-chain transfer to Solana. The transaction fails on the destination chain or via the Gateway, leading to a revert.
2. The `onRevert` function is invoked. It correctly identifies the Solana address (32 bytes) in the `revertMessage` and stores the refund details (including the 32-byte Solana walletAddress) in the `refundInfos` mapping. This action implicitly signals to refund bots that a manual claim is required for this non-EVM refund. An `EddyCrossChainRefund` event is emitted.
3. An attacker or opportunistic user monitors the chain for `EddyCrossChainRefund` events or otherwise obtains a valid `externalId` for a pending Solana refund and calls `claimRefund`.
4. The access control check `require(bots[msg.sender] || msg.sender == receiver)` evaluates to `require(bots[msg.sender] || msg.sender == msg.sender)`, which simplifies to true. This allows the attacker's transaction to proceed.
5. The attacker submits their `claimRefund` transaction with a sufficiently high gas fee to front-run any legitimate refund bot or other users who might also be attempting to claim the funds.
6. The `TransferHelper.safeTransfer` function then transfers the `refundInfo.amount` of `refundInfo.token` to the receiver (which is the attacker's EVM address), instead of the intended Solana recipient. 

## Impact

Users' assets, intended for Solana addresses, are directly transferable to arbitrary EVM addresses controlled by an attacker or unintended claimant. 

## Mitigation

For `refundInfos` entries where `walletAddress` is a non-EVM address (like Solana's 32 bytes), the `claimRefund` function must strictly allow only pre-approved refund bot addresses (`bots[msg.sender]`) to call it. The `msg.sender == receiver` fallback logic should be removed entirely for these cases.
