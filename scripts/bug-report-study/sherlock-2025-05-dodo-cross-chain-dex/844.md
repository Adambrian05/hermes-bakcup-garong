# Inconsistencies in Native vs. ZRC20 Token Handling leading to loss of ether.

### Summary

The protocol mishandles native ETH vs. ZRC20 token differentiation in withdrawToNativeChain. Specifically:
function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 


There is no explicit check that zrc20 == _ETH_ADDRESS_ before using msg.value in _doMixSwap.
Also there's no enforcemnt that ETH can only be sent when zrc20 == _ETH_ADDRESS_.

As a result, a user can:

Pass any non-ETH ZRC20 token address

Still send arbitrary msg.value > 0

Cause ETH to be incorrectly forwarded into DODO’s mixSwap router.

### Root Cause

The root cause is the missing else branch to explicitly handle the case when zrc20 == _ETH_ADDRESS_, which results in undefined behavior or implicit assumptions. Without a separate logic path for ETH transfers, the contract fails to clearly separate the handling of native ETH versus ZRC20 tokens, leading to ambiguous asset processing, potential loss of funds, and inconsistencies in how msg.value and amount are used.

### Internal Pre-conditions

1. zrc20 is not strictly checked against _ETH_ADDRESS_ before using msg.value. This allows ETH to be sent even when a ZRC20 token is expected.
2. The logic assumes msg.value == amount without enforcing that it applies only when zrc20 == _ETH_ADDRESS_

### Impact

The user suffers a loss of the full `msg.value` sent when `zrc20 != _ETH_ADDRESS_` but ETH is still forwarded. The protocol accepts and forwards the ETH even though the swap is meant for a ZRC20 token, effectively causing the ETH to be permanently lost or misrouted. The attacker (user) loses the full ETH amount without receiving any benefit in return (griefing).

### Mitigation

Add an else block to explicitly handle the condition where zrc20 == _ETH_ADDRESS_, ensuring that msg.value == amount is strictly enforced only in this path. For the case where zrc20 != _ETH_ADDRESS_, reject any msg.value > 0 with a clear require(msg.value == 0, "ETH should not be sent when using ZRC20 tokens"). This ensures user inputs are validated based on the asset type and prevents unintentional or malicious ETH loss.
