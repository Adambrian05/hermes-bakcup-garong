# Reentrancy Potential in the `claimRefund` Function

## Vulnerability Details
The `claimRefund` function in both the `GatewayTransferNative` and `GatewayCrossChain` contracts, deletes `refundInfos[externalId]` state after transfering the refund token to the user([+](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L672)) ([+](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L582)). 

```solidity
function claimRefund(bytes32 externalId) external {
    ...
    
@>   TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
@>   delete refundInfos[externalId];
    
    ...
}
```

This creates a potential reentrancy vulnerability where a malicious user can repeatedly call `claimRefund` via reentrancy, potentially draining specific token asset from the contract.

## Proof of Concept
Here's a scenario demonstrating the vulnerability in the `claimRefund` function:

- The attacker attempts to send native tokens from ZetaChain to receive ETH in a smart contract account on the Ethereum mainnet by calling the `withdrawToNativeChain` function in the `GateWayTransferNative` contract.
- The destination smart contract account intentionally lacks a `receive` function, so the attacker expects the transaction to revert.
- When the transaction reverts, the `onRevert` function is called by the gateway, and the transaction data is stored in `refundInfos`. This makes the attacker eligible to call `claimRefund`.
- The origin wallet address on ZetaChain could be a smart contract account with `receive` and `fallback` functions.
- The `fallback` function calls `claimRefund` again before the `refundInfos[externalId]` state variable has been deleted.
- Since the state hasn't been deleted, the checks pass again, and the tokens are transferred once more.
- This process can be looped multiple times, enabling the attacker to drain the entire asset balance of the contract.

## Impact
An attacker could drain the contract's specific token balance, effectively stealing all assets held within the contract.

## Mitigation
Apply the `nonReentrant` modifier to both the `claimRefund` functions to prevent reentrancy attacks. Additionally, follow the [checks-effects-interactions](https://docs.soliditylang.org/en/latest/security-considerations.html#reentrancy) pattern by updating all state variables before making external calls. This approach ensures that the contract’s state is consistent and prevents reentrant exploits.
