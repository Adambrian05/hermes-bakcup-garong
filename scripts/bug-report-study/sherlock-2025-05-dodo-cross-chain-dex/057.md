# No Maximum Array Accounts Limit Validation for Solana Transactions

## Description
The `AccountEncoder` library used in the `GatewayCrossChain` contract does not validate the maximum number of accounts that can be processed for a Solana transaction. The `decompressAccounts()` function can accept up to 65,535 accounts (uint16 maximum), even though Solana has a technical limit of 64 accounts per transaction. This causes cross-chain transactions to be processed successfully on ZetaChain but fail when executed on Solana.

## Code Snippet
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L20-L49

## Root Cause
The root of the problem lies in the `decompressAccounts()` function in the `AccountEncoder` library which does not validate the maximum array length limit before processing.
```solidity
assembly {
    let ptr := add(input, 32)
    
    // PROBLEM: Reading array length without maximum limit validation
    let len := add(shl(8, byte(0, mload(ptr))), byte(1, mload(ptr)))
    // len can be 0 to 65535 (uint16 maximum)
    
    ptr := add(ptr, 2)
    accounts := mload(0x40)
    mstore(accounts, len)  // Save array length without validation
    
    // Loop for each account without Solana limit check
    for { let i := 0 } lt(i, len) { i := add(i, 1) } {
        // ... process each account
    }
}
```
Usage in Cross Chain Gateway:

`_handleEvmOrSolanaWithdraw()` function:
```solidity
// Encode data specifically for Solana if needed
bytes memory encoded = (decoded.dstChainId == SOLANA_EDDY)
    ? AccountEncoder.encodeInput(
        AccountEncoder.decompressAccounts(decoded.accounts), // NO LIMIT VALIDATION
        data
    )
    : data;
```
The problem is that there is no validation that the number of accounts is <= 64 (Solana's limit), blind processing of the claimed array length in the input data, and no early detection of transactions that are bound to fail on Solana.

## Impact
The transaction was successful on ZetaChain but failed on Solana and the 0.5% fee was deducted and not refunded.

## Scenario
1. User Initiation:
- User wants to perform a complex swap from Ethereum to Solana
- Using a DEX aggregator that requires interaction with 80 different pools
- Each pool requires 4 accounts (pool, tokenA, tokenB, authority)
- Total accounts needed: 80 × 4 = 320 accounts
2. Message Encoding on Source Chain:
- Frontend/SDK encodes the message with 320 Solana accounts
- Data is compressed using AccountEncoder format
- Array length = 320 (in uint16 format)
- Message is sent via ZetaChain Gateway
3. Processing on ZetaChain:
```diff
// In GatewayCrossChain.onCall()
(DecodedMessage memory decoded, MixSwapParams memory params) = 
    SwapDataHelperLib.decodeMessage(_message);

// Platform fee cut (success)
uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount);
amount -= platformFeesForTx;

// DODO swap successful
uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
```
4. Account Decompression (Problematic):
```diff
// In _handleEvmOrSolanaWithdraw()
// AccountEncoder.decompressAccounts() successfully decode 320 accounts
// There is NO VALIDATION that 320 > 64 (Solana limit)
Account[] memory accounts = AccountEncoder.decompressAccounts(decoded.accounts);
// accounts.length = 320 ✓ (successful on ZetaChain)
```
5. Withdraw Attempt to Solana:
```diff
bytes memory encoded = AccountEncoder.encodeInput(accounts, data);

withdrawAndCall(
    externalId,
    decoded.contractAddress,
    decoded.targetZRC20,
    amountsOutTarget,
    receiver,
    encoded  // Contains 320 accounts
);
```
6. Failure on Solana:
- ZetaChain Gateway sends transaction to Solana
- Solana runtime rejects transaction: "Too many accounts (320 > 64)"
- Transaction fails on destination chain
7. Revert Handling:
```diff
// onRevert() is called because the Solana transaction failed
// But the platform fee has been deducted and is not returned.
```

## Recommendation
Added validation to `decompressAccounts()` function.
```solidity
function decompressAccounts(bytes memory input) internal pure returns (Account[] memory accounts) {
    require(input.length >= 2, "INSUFFICIENT_DATA");
    
    assembly {
        let ptr := add(input, 32)
        let len := add(shl(8, byte(0, mload(ptr))), byte(1, mload(ptr)))
        
        // ✅ SOLANA LIMIT VALIDATION
        if gt(len, 64) {
            // Revert with clear error message
            mstore(0x00, 0x08c379a0) // Error selector for Error(string)
            mstore(0x20, 0x20)       // Offset to string
            mstore(0x40, 0x1e)       // Length string (30 chars)
            mstore(0x60, "EXCEEDS_SOLANA_ACCOUNT_LIMIT_64")
            revert(0x00, 0x80)
        }
        
        // Data validation is sufficient for all accounts
        if lt(mload(input), add(2, mul(len, 33))) {
            mstore(0x00, 0x08c379a0)
            mstore(0x20, 0x20)
            mstore(0x40, 0x15)
            mstore(0x60, "INSUFFICIENT_ACCOUNT_DATA")
            revert(0x00, 0x80)
        }
        
        ptr := add(ptr, 2)
        accounts := mload(0x40)
        mstore(accounts, len)
        
        // ... rest of decompression logic
    }
}
```
