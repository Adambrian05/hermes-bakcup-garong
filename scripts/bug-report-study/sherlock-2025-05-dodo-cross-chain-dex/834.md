# Any user can claim Refunds for chains with wallets of length != 20

### Summary

The function `GatewayCrossChain.sol::claimRefund()` allows any user to claim refunds for chains with wallets that have address lengths different from 20 bytes, like Bitcoin and Solana.

### Root Cause

This problem comes from the wrong validation of the caller of the function:

```solidity
    function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        //@audit if this length is != 20, any user can claim the refund
        // since msg.send will be the receiver
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        ///@audit second check will always be true for length != 20
   @>   require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }s
```

When `refundInfo.walletAddress.length != 20`, the code skips the receiver assignment, leaving `receiver = msg.sender`. The authorization check `msg.sender == receiver` will always return `true` since both variables point to the same address (`msg.sender`).

The problem comes from the wrong validation one the function caller where it allows any caller different than bots and `refundInfo.walletAddress` to claim other users Refunds.

```solidity
require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```

### Attack Path

1. Attacker monitors refunds created for Solana and Bitcoin chains (addresses ≠ 20 bytes).
2. Attacker calls `claimRefund(externalId)` for any refund with non 20 byte wallet addresses
3. The logic in `claimRefund(externalId)` sets `receiver = msg.sender`, making the check `msg.sender == receiver` always pass
4. Attacker receives the refund tokens for himself.

### Impact

High, since function is completely open for any user to claim refunds for other user’s refunds under any external conditions.

Based on the expected protocol compatibility, refunds for these cases will be affected:

- **Bitcoin**: Address length varies (25-34 bytes for different formats)
- **Solana**: 32-byte addresses

### Mitigation

For mitigate this problem the best thing would be add a proper validation for wallets ≠ 20 to only allow bots and `refundInfo.walletReceiver` to claim refunds.
