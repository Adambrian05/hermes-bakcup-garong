# Denial of Service When `zrc20` is ETH in `_handleFeeTransfer`

### Summary

In the `GatewayTransferNative`, the `_handleFeeTransfer` function assumes that the `zrc20` token is always an ERC-20 token. However, it is called from `withdrawToNativeChain`, which explicitly allows `zrc20` to be the native ETH address. This leads to an unconditional call to` TransferHelper.safeTransfer(zrc20, ...)` even when `zrc20 == _ETH_ADDRESS_`, causing a transaction failure due to an invalid call on ETH. As a result, ETH users are permanently blocked from using the withdrawal function, leading to a denial of service.

### Root Cause

The absence of a conditional branch inside `_handleFeeTransfer` to handle native ETH separately from ERC-20 tokens. The function unconditionally assumes `zrc20` is always an ERC-20 and uses `TransferHelper.safeTransfer`, which fails when used with ETH (0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE).

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L341-L347



### Internal Pre-conditions

The `feePercent` is non-zero.

### External Pre-conditions

A user initiates `withdrawToNativeChain` with `zrc20 == _ETH_ADDRESS_`.
The user provides a valid `amount` and message.

### Attack Path

-

### Impact

- ETH users cannot withdraw funds through `withdrawToNativeChain`.
- Permanent DoS for native token usage.

### PoC

_No response_

### Mitigation

Introduce an explicit check in `_handleFeeTransfer `to handle ETH transfers using native value transfers `TransferHelper.safeTransferETH` instead of `TransferHelper.safeTransfer`.
