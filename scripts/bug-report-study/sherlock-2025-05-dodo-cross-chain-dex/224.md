# Inconsistent Token Validation Between `MixSwapParams` and `DecodeMessage` Structs Enables withdrawing of Arbitrary Tokens

### Summary

The `payload` passed from [`GatewaySend.depositAndCall(...)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L225) to [`GatewayCrossChain.onCall(...)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L446), via `Zetachain Gateway`, contains [two structs](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L453):

- `MixSwapParams`, the struct holding data to swap tokens using `DODORouteProxy` 
- `DecodedMessage`, the struct holding data to bridge ([`withdrawAndCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L404-L405)) 

The contract assumes that the output token from the `MixSwapParams` matches the token specified in the `DecodedMessage` struct. This assumption is not enforced, creating a critical vulnerability.

An attacker can exploit this by performing a swap from `token A` to `token C` (a different token than `token B` in the `DecodeMessage` struct), where `token C` has a higher output quantity but significantly lower monetary value. The function will use the higher [`outputAmount`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L465) of `token C` and [`withdrawAndCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L494) it as if it were `token B`, resulting in:

1. Unexpected tokens being bridged.
2. Over-crediting the recipient.
3. Loss of protocol trust or funds.

### Root Cause


1. The function decouples the token identity from the swap path and bridging path.
2. It uses the output amount from the swap as the input to the bridge, while assuming that the token identity of the `MixSwapParams` output matches the token defined in the `DecodedMessage`.
3. No check is performed to match token addresses between the `MixSwapParams` output and the token address defined in the `DecodedMessage`.

### Internal Pre-conditions

1. `MixSwapParams` and `DecodedMessage` structs are passed in by the user in publicly accessible function  `depositAndCall` on `GatewaySend.sol`.
2. The function `onCall(...)` on `GatewayCrossChain.sol` trusts both structs to be semantically consistent without enforcing it programmatically.

### External Pre-conditions

1. The attacker can construct a swap that yields a high quantity of a low-value token.
2. The attacker can craft the bridge struct to target a high-value token (token B) and specify it for bridging.

### Attack Path

1. Attacker supplies tokenA (input) in the `GatewaySend.depositAndCall(...)`.
2. Constructs a swap path via `DodoRouteProxy`: tokenA -> tokenC, where tokenC is cheap but yields a high output amount.
3. Constructs a `withdrawAndCall` path for tokenB (a high-value token).
4. Encode both the paths in payload of `GatewaySend.depositAndCall(...)`.
5. Token A bridged from Connected Chain to Zetachain.
6. Function performs swap and receives large quantity of tokenC.
7. Function proceeds to bridge the outputAmount as if it's tokenB, not verifying token consistency.
8. On the destination chain, recipient receives outputAmount of token B (or equivalent credit), causing over-crediting or fund misallocation.

### Impact

1. The protocol suffers loss of funds held by the `GatewayCrossChain` contract.
2. Funds held by the contract for user refunds can also be drained.

### Mitigation

Validate `DecodedMessage.targetZRC20 == MixSwapParams.toToken`
