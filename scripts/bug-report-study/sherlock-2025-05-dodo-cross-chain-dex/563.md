# More funds than required are approved to GatewayZEVM which can be leveraged to steal them in the native Gateway and/or erase revertInfos

### Summary

Both the native gateway as well as the cross-chain gateway approve more funds to Zetachain's GatewayZEVM than needed. Although both do, this report will focus on the native gateway for now due the `withdraw` function being public and permissionless, which can be used to exploit this.
Since the visibility of the function is public and contains no checks, malicious users can exploit the un-utilized allowance to bridge the tokens from Zeta to a connected chain and "steal" them from the contract.
The second major impact is that they can use this in order to pass stored externalIds which can be overridden and the funds stored as part of them - lost.

### Root Cause

The root causes of this vulnerability are two:

1. The permissionless nature of the `withdraw` function in the Native Gateway;
2. The `_handleBitcoinWithdraw` and `_handleEvmOrSolanaWithdraw` both approve more tokens to the ZEVMGateway than actually used by it.

During the `withdrawToNativeChain`, if the destination chain is bitcoin, it will check the gas fee (which are gas costs + protocol fees for Zeta) for that particular asset withdrawal, and then it will call `_handleBitcoinWithdraw`, and in case it's else (solana or EVM), `_handleEvmOrSolanaWithdraw` will be invoked. It's important to note that the gas fees for a plain withdraw vs. a withdraw and call are quite different. As one has a fixed cost, the other depends on the amount of gas that we're forwarding.

For the sake of this example, I'm going to show one exploitation path, although more variances might exist. The actual problem is that both `_handleBitcoinWithdraw` and  `_handleEvmOrSolanaWithdraw` approve the outputAmount + gasFee to the gateway, but then passes the outputAmount - gasFee as an argument, leaving one gasFee more as an approval.

The exploitation path shown here is a withdrawAndCall (solana or EVM) gas fee which would be larger than the withdraw-only gas fee.

For the purpose of a hypothetical example, let's say that the output mount is 1000e18 token units, and the gas fee is 50e18 token units (for the withdraw and call). The function logic flow will approve 1050e18 token units to the GatewayZEVM, but will pass 950e18 as a function argument.

```solidity

  if (decoded.targetZRC20 == gasZRC20) {
            if (gasFee >= outputAmount) revert NotEnoughToPayGasFee();
            IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);

            bytes memory data = SwapDataHelperLib.buildOutputMessage(
                externalId, 
                outputAmount - gasFee, 
                decoded.receiver, 
                decoded.swapDataB
            );
            
            bytes memory encoded = (decoded.dstChainId == SOLANA_EDDY)
                ? AccountEncoder.encodeInput(AccountEncoder.decompressAccounts(decoded.accounts), data)
                : data;

            withdrawAndCall(
                externalId, 
                decoded.contractAddress, 
                decoded.targetZRC20, 
                outputAmount - gasFee, 
                receiver, 
                encoded
            );

```

The gatewayZEVM will take the 50e18 fee, and the 950e18, causing an extra 50e18 token units to remain utilized from the allowance. 

From the below functions, part of the GatewayZEVM we can see that the gas fee is taken from the msg.sender (Native Gateway) and burned, and later the amount passed as the argument to ZEVM's withdraw (in our case outputAmount - gasFee) is taken from the user and burned as well.

```solidity

    function _withdrawZRC20WithGasLimit(uint256 amount, address zrc20, uint256 gasLimit) private returns (uint256) {
        uint256 gasFee = _burnProtocolFees(zrc20, gasLimit);

        if (!_safeTransferFrom(zrc20, msg.sender, address(this), amount)) {
            revert ZRC20TransferFailed(zrc20, msg.sender, address(this), amount);
        }

        if (!_safeBurn(zrc20, amount)) {
            revert ZRC20BurnFailed(zrc20, amount);
        }

        return gasFee;
    }

```

```solidity

    function _burnProtocolFees(address zrc20, uint256 gasLimit) private returns (uint256) {
        (address gasZRC20, uint256 gasFee) = IZRC20(zrc20).withdrawGasFeeWithGasLimit(gasLimit);


        if (!_safeTransferFrom(gasZRC20, msg.sender, address(this), gasFee)) {
            revert GasFeeTransferFailed(gasZRC20, address(this), gasFee);
        }


        if (!_safeBurn(gasZRC20, gasFee)) {
            revert ZRC20BurnFailed(gasZRC20, gasFee);
        }


        return gasFee;
    }

```

The extra amount from the non-utilized allowance (in the above example 50e18) can be stolen by malicious users. Since 50e18 was the fee for the call which was based on a custom gas amount (a fee larger than a plain withdraw), the user directly calls the permissionless `withdraw` method on the native gateway. 

Assuming that the fee is 20e18 (as it's just a withdraw, without an arbitrary call to the connected chain), the user will be able to steal the remaining 30e18:

```solidity

 function withdraw(
        bytes32 externalId,
        bytes memory sender,
        address outputToken,
        uint256 amount
    ) public {
        gateway.withdraw(
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
        );
    }

```

They are able set arbitrary values here allowing them to withdraw the difference between the lower gas fee in just the withdraw vs. the higher gas fee which was approved due to the withdraw and call. They are able to do this for any coin corresponding to any chain, as the remainder of the funds would directly be sent to the `sender` address which is set by the user.

The second point is users passing an address that they control as the `sender` with an externalId stored in the native gateway that they want to override. If the onAbort flow is activated after, the externalId utilized will override the already existing one, leading to fund loss.

### Internal Pre-conditions

None

### External Pre-conditions

A withdrawAndCall takes place which approves one gasFee more than it should, since it includes an arbitrary call, the gas fee is larger than with a plain withdraw. 

Considering the difference, a malicious user can then directly call `withdraw` to steal the difference between the two gas fees.

### Attack Path

1. Attacker directly calls `withdraw` on the native gateway in order to "steal" the extra gas fees approved to the Gateway;

### Impact

Contract approves more funds than it should, which could result in a theft of the "extra" approved funds by malicious users.

### Mitigation

1. Approve only the outputAmount instead of the outputAmount + gasFee;
2. Set the `withdraw` function's visibility as internal.
