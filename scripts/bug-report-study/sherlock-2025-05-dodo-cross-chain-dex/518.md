# `GatewayCrossChain`'s fee handling fails for native ZETA transactions


### Summary
`GatewayCrossChain::onCall`'s implementation of `_handleFeeTransfer` is incorrect, as it does not accomodate for the special value of wZETA `` when `GatewayZEVM::depositAndCall` calls `onCall`.


### Root Cause


The `_handleFeeTransfer` function in `GatewayCrossChain` is not equipped to handle native gas tokens. It can only transfer ERC20/ZRC20 tokens.
`GatewayCrossChain::_handleFeeTransfer` is as follows:
```solidity
// file: omni-chain-contracts/contracts/GatewayCrossChain.sol

function _handleFeeTransfer(
    address zrc20,
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000;
       TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
}
```
When `GatewayZEVM` calls `depositAndCall`, for native ZETA, it will set `zrc20` argument to `WZETA`, but sends native ZETA to this `GatewayCrossChain` via `_transferZETA`. Here is the code for `GatewayZEVM::depositAndCall`

```solidity
 function depositAndCall(
        // TODO: What is the context?
        MessageContext calldata context,
        uint256 amount,
        address target,
        bytes calldata message
    )
        external
        nonReentrant
        onlyFungible
        whenNotPaused
    {
        if (target == address(0)) revert ZeroAddress();
        if (amount == 0) revert InsufficientZetaAmount();
        if (target == FUNGIBLE_MODULE_ADDRESS || target == address(this)) revert InvalidTarget();

        _transferZETA(amount, target); 
        UniversalContract(target).onCall(context, zetaToken, amount, message);
    }

     function _transferZETA(uint256 amount, address to) private {
        if (!IWETH9(zetaToken).transferFrom(msg.sender, address(this), amount)) revert FailedZetaSent();
        IWETH9(zetaToken).withdraw(amount);
        (bool sent,) = to.call{ value: amount }("");
        if (!sent) revert FailedZetaSent();
    }
```

The way `_handleFeeTransfer` is used here on `onCall` will cause this function to revert, as the balance of `wZETA` may be insufficient, or that it will transfer out `wZETA` that belongs to someone else. 
Full scope of `GatewayCrossChain::onCall` can be found [here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442-L510).
```solidity
 function onCall(
        MessageContext calldata context,
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external onlyGateway {
  
        (bytes32 externalId) = abi.decode(message[0:32], (bytes32)); 
        bytes calldata _message = message[32:];

        // Decode message and decompress swap params
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(_message);

        // @audit when zrc20 == WZETA,
        // it may have received native ZETA
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // platformFee = 5 <> 0.5%
        amount -= platformFeesForTx;

```

### Internal Pre-conditions

None.

### External Pre-conditions

`GatewaySend::depositAndCall` succeeds.

### Attack Path

1. A user initiates `GatewaySend::depositAndCall` to `GatewayCrossChain`
2. On ZetaChain, `GatewayZEVM` transfers native ZETA to the `GatewayCrossChain` contract and executes its `onCall` function.
3. Inside `onCall`, the `_handleFeeTransfer` function is called, passing the ZRC20 address for ZETA (`WZETA`).
4. The function calculates the fee and attempts to transfer it using `TransferHelper.safeTransfer`.
5. The `safeTransfer` call fails because the contract's ZRC20 balance is zero; it holds the funds as native ZETA. The transaction reverts, or sends someone else's `wZETA`.

### Impact

1.`onCall` will always revert
2. or someone else's wZETA will be used to pay for fees
3. Native ZETA stuck in this contract.
