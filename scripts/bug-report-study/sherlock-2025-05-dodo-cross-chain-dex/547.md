# Bridging native token(zeta token) from zetachain using `withdrawToNativeChain` will always revert

### Summary

For bridging tokens from **Zetachain** to the destination chain, the function [`withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530) is used.

This function will **always revert** when a user attempts to bridge the **ZETA token**, which is the native token on Zetachain. The first parameter passed to `withdrawToNativeChain`, `zrc20` ([source](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L531)), is set to `ETH_ADDRESS` (`0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`).

During token [swaps](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L555), the DODO router attempts to approve the [`DDOApprove`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L434) contract using the `zrc20` interface. However, for the native token address, such a contract does **not** exist, causing the call to revert.


### Root Cause

Native token cases are not handled correctly in [`withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530), leading to failed contract calls when using the native token address.

### Internal Pre-conditions

User tries to bridge zeta token(native token) from Zetachain to any supported chain


### Impact

Users cannot bridge the native ZETA token from Zetachain as the bridging function always reverts, blocking the native token bridging
