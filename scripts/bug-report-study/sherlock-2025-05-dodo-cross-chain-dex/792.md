# Any caller can claim non-EVM refunds, allowing theft of user funds

### Summary

A missing caller check in claimRefund allows anyone to trigger a refund for Bitcoin/Solana (walletAddress.length != 20) and redirect the tokens to themselves.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574C7-L574C39
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661

### Root Cause

In `claimRefund(bytes32)`, when refundInfo.walletAddress.length != 20, the code sets `receiver = msg.sender` and then does:

```solidity
require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```
Since receiver was assigned msg.sender, the check always passes for non-EVM refunds, so no one verifies that the caller is authorized to claim that refund.

### Internal Pre-conditions

A refundInfos[externalId] entry exists with walletAddress.length != 20.
refundInfo.externalId is non-empty.



### External Pre-conditions

None 

### Attack Path

1. (any address) calls claimRefund(externalId) for a refund entry whose walletAddress has length ≠ 20.

2. Inside claimRefund, receiver is set to msg.sender.

3. The require check msg.sender == receiver succeeds trivially.

4. TransferHelper.safeTransfer sends the refund amount to the attacker.

5. The refund record is deleted.

### Impact

All tokens earmarked as Bitcoin/Solana refunds can be stolen by any on-chain user

_No response_

### Mitigation

Add a strict authorization check for non-EVM refunds
