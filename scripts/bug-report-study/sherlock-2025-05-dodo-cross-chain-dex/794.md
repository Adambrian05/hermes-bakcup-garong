# Refund after abort can be stolen due to mismatch in cross-chain account ownership

### Summary

The abort mechanism assumes that an address on the source chain is controlled by the same entity on ZetaChain. When cross-chain TX fail and onRevert also fails, abort mechanism is triggered which makes funds  claimable by whoever controls the original depositor's address, but on ZetaChain. This allows attackers who control the same address on ZetaChain to steal refunds from legitimate users on EVM source chain.

### Root Cause

The [depositAndCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L287) entrypoint function encodes the depositor's address as the refund receiver in the revert message:

```solidity
    function depositAndCall(
        address targetContract,
        uint256 amount,
        address asset,
        uint32 dstChainId,
        bytes calldata payload
    ) public payable {
        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);
        bool isETH = (asset == _ETH_ADDRESS_);
        bytes memory message = concatBytes(externalId, payload);

        RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: targetContract,
            revertMessage: bytes.concat(externalId, bytes20(msg.sender)), // @audit msg.sender is set as refund receiver
            onRevertGasLimit: gasLimit
        });
        // ...
```
If cross-chain TX fails on ZetaChain, protocol will first try to process it by calling `onRevert` on the source chain. However, if `onRevert` fails or is underfunded, protocol will start abort processing mechanism by calling `onAbort` on the `GatewayCrossChain`.

`onAbort` will store `RefundInfo` and set the `walletAddress` as the account who can claim the refund:
```solidity
    function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // ...
        // @audit this account is the address of the depositor on **source chain**
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        // ...
    }
```

The critical thing to notice there is that `walletAddress` is actually the original depositor on the **source chain**. But abort processing happens on the destination chain (ZetaChain). Problem is that there is no guarantee that the same party controls the address on both chains. In case of smart wallets or multisigs, it can easily happen that different party controls address on different chains. That means that other party who controls the address on ZetaChain can steal refund which belongs to the original depositor.

### Internal Pre-conditions

None

### External Pre-conditions

The same address must be controlled by different entities on source chain versus ZetaChain (this commonly occurs with multisig wallets).

### Attack Path

1. Alice controls address `0x123` on Ethereum and deposits funds via `depositAndCall`
2. Cross-chain TX fails and `onRevert` also fails, triggering `onAbort` on ZetaChain
3. `onAbort` creates a refund claimable by address `0x123` on ZetaChain
4. Bob, who controls address `0x123` on ZetaChain (but not on Ethereum), calls `claimRefund` and receives Alice's funds. Alice loses her deposit permanently as the refund has been claimed by Bob.

### Impact

High severity - this vulnerability enables direct theft of user funds through cross-chain address control mismatches. Attackers can systematically target addresses they control on ZetaChain but don't control on source chains, waiting for failed transactions to generate claimable refunds.

### PoC

_No response_

### Mitigation

Let user provide `abortRefundReceiver` address (which they control on the destination chain) as part of the initial `depositAndCall`. Encode that address in the `revertMessage` in addition to the "revertRefundReceiver". That way there will be separate accounts to receive refunds on source chain (onRevert) vs destination chain (onAbort), both provided and controlled by the end user.
