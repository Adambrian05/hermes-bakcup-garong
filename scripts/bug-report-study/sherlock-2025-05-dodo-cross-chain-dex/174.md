# Users may not receive refunds for native tokens if a cross-chain transaction is reverted.

### Summary

The `GatewaySend `contract does not handle refunds for native tokens (ETH) when a cross-chain transaction is reverted. As a result, users who initiate a cross-chain transfer of ETH and experience a revert will not receive their ETH back, leading to a loss of funds for those users.

### Root Cause

In the `GatewaySend` contract, the `onRevert `function is responsible for refunding assets to users when a cross-chain transaction fails. However, it uses `TransferHelper.safeTransfer` to process refunds. The current implementation of `TransferHelper.safeTransfer` only supports ERC20 tokens and does not handle native tokens (ETH, POL, BNB). As a result, when the asset to be refunded is ETH, the refund attempt fails, and the user does not receive their ETH back.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393-L404

### Internal Pre-conditions

The user initiates a cross-chain transfer with native asset. The cross-chain transaction is reverted, triggering the `onRevert `function.

### External Pre-conditions

The protocol is deployed on a chain where ETH (or the native token) is used as an asset.

### Attack Path

1. User bridges ETH using the `GatewaySend `contract.
2. The cross-chain transaction fails and triggers a revert.
3. The contract attempts to refund ETH using `TransferHelper.safeTransfer`, which does not support ETH.
4. The user does not receive their ETH refund.

### Impact

Users may permanently lose their native tokens (ETH) if a cross-chain transaction is reverted, resulting in a loss of funds and trust in the protocol.

_No response_

### Mitigation

Update the `onRevert `function in `GatewaySend `to check if the asset is ETH and use `TransferHelper.safeTransferETH` for native token refunds.
