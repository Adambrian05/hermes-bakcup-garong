# Malicious Revert Can Overwrite Legitimate Refunds via onRevert Function

### Summary

The onRevert function in GatewayCrossChain and GatewayTransferNative contracts allows the attacker to overwrite refund information (refundInfos[externalId]) of an honest user by submitting a revert with a spoofed externalId. This leads to loss of access to legitimate refunds and potential theft.

### Root Cause

The onRevert function unconditionally overwrites the refundInfos mapping using the externalId from the decoded revertContext, without verifying whether an entry for that externalId already exists. Since the externalId is attacker-controlled in their own revert call, this can be exploited to target previously stored user refunds.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L539

### Internal Pre-conditions

NA

### External Pre-conditions

Attacker deploys their own universal contract on ZetaChain.

Attacker crafts a malicious revertContext payload with:

- The same externalId as a legitimate user's transaction.

- Arbitrary token, amount, and walletAddress fields (e.g., attacker-controlled).

### Attack Path

1. Attacker identifies an externalId used by a legitimate user whose refund is pending.

2. Attacker initiates a new cross-chain transaction via their own universal contract.

3. They trigger a revert intentionally in their universal contract, ensuring the ZetaChain infrastructure calls onRevert() on the gateway contract.

4. The revertContext passed to onRevert() contains the spoofed externalId and attacker-controlled refund info.

5. The gateway contract overwrites the existing entry in refundInfos[externalId].

6. The legitimate user can no longer claim their refund, or the attacker may claim it themselves.

### Impact

Loss of Funds: Honest user’s refund can be stolen or permanently lost.
Denial of Service: Refund record can be corrupted, making claim impossible.

_No response_

### Mitigation

Add a cryptographic or signature-based binding between externalId and sender wallet to authenticate the refund origin.
