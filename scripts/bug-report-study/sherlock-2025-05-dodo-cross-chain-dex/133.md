# Silent ERC20 transfer failures may go undetected, causing users to not receive bridged tokens.

### Summary

The use of` IERC20(toToken).transfer(evmWalletAddress, outputAmount);` in the GatewaySend contract does not check for a return value or handle tokens that return false on failure. This can cause silent failures for ERC20 tokens that do not revert but instead return false when a transfer fails, resulting in users not receiving their bridged tokens without any error or revert.

### Root Cause

In the `GatewaySend `contract, the code calls `IERC20(toToken).transfer(evmWalletAddress, outputAmount);` to deliver tokens to the recipient. The ERC20 standard specifies that transfer should return a bool indicating success, but some tokens may return false on failure rather than reverting. Since the code does not check the return value, a failed transfer may go unnoticed, leading to silent loss of funds for the user. For example, USDC returns false on failure.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L371-L373

### Internal Pre-conditions

The user initiates a cross-chain transfer with an ERC20 token that returns false on transfer failure.
The transfer fails (e.g., due to insufficient balance).

### External Pre-conditions

The ERC20 token contract is deployed on the destination chain and implements transfer to return false on failure rather than reverting.

### Attack Path

1. User bridges a token like USDC to a recipient.
2. The transfer fails (e.g., due to insufficient contract balance), and transfer returns false.
3. The contract does not detect the failure and emits a success event, but the user does not receive their tokens.

### Impact

Users may not receive their bridged tokens, and the protocol will emit events indicating a successful transfer, causing confusion and potential loss of trust.

_No response_

### Mitigation

Use a safe transfer helper (such as OpenZeppelin’s SafeERC20.safeTransfer or a low-level call that checks for both revert and false return values) to ensure transfer failures are always detected and handled.
