# Denial of service for Btc and solana addresses leading to permanent loss of funds

### Summary

Hardcoded wallet address length check will cause a denial of service for Solana and some Bitcoin users as non-EVM address holders will be unable to claim refunds when their wallet addresses exceed 20 bytes

### Root Cause

In GatewayTransferNative.sol:onRevert() and GatewayTransferNative.sol:claimRefund() the hardcoded check for 20-byte wallet addresses prevents non-EVM users from claiming refunds
The contract assumes all wallet addresses are 20 bytes (EVM addresses), but Solana addresses are 32 bytes and some Bitcoin addresses can be longer than 20 bytes
the contract checks if context.revertMessage.length == 52 (32 bytes externalId + 20 bytes wallet address) to determine direct refund vs stored refund
 In claimRefund(), the contract only extracts the receiver address when refundInfo.walletAddress.length == 20
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L665

### Internal Pre-conditions

User needs to initiate a cross-chain transaction from zeta to btc or solana

### External Pre-conditions

Cross-chain transaction failure occurs due to external factors

### Attack Path

User initiates a cross-chain swap from Ethereum to Solana with a 32-byte Solana wallet address
Transaction fails on the destination chain due to external factors
Gateway calls onRevert() with revert message containing 32-byte externalId + 32-byte Solana address (total 64 bytes)
Contract skips direct refund because context.revertMessage.length != 52 (it's 64 bytes)
Refund info is stored with the 32-byte Solana wallet address

### Impact

Solana and Bitcoin users cannot claim their refunds when cross-chain transactions fail, resulting in permanent loss of funds. The affected users lose their entire transaction amount with no recovery mechanism available

### Mitigation

Remove hardcoded length assumptions and implement proper address parsing for different chain types
