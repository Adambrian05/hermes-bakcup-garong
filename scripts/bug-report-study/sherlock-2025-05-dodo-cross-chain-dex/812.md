# Missing safe ERC-20 calls can silently break swaps and approvals

### Summary

Using IERC20.transferFrom, transfer, and approve directly—without checking return values—will cause silent failures for non-standard tokens, leading to stuck funds or broken swap logic as the contract will proceed under the false assumption that transfers and approvals succeeded.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L199
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L239

### Root Cause

In some contracts, TransferHelper library is utilized, but it is not employed in CrossChainGateway and GatewayTransferNative.
 The swap and approval logic invokes the following code:
```solidity
IERC20(fromToken).transferFrom(msg.sender, address(this), amount);
IERC20(toToken).transfer(evmWalletAddress, outputAmount);
IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
```
but does not check the boolean return values. Many ERC-20 tokens revert on failure, but some (e.g. USDT‐style) return false without reverting. In those cases, these calls return false, and the contract continues execution as if they succeeded.

beside this if for any reason, the entire allowance is not used after the approval, any further attempt to `safeIncreaseAllowance` with tokens that prohibit any approval change from non-zero to non-zero values, like USDT, will ultimately fail.


### Internal Pre-conditions

user call function that use transfer or approve with a non standard  ERC20 as USDT  or BNB
