# onRevert in gatewaySend will not be able to handle when reverted token is Eth ( native token )

### Summary

The onRevert function in the GatewaySend contract fails to handle refunds when the returned asset is the native token (ETH). Since it tries  a safeTransfer on address(0), the refund fails, causing users to be unable to reclaim their ETH after a failed cross-chain call. This breaks a critical part of the contract’s functionality.

### Root Cause

When depositAndCall inside GatewaySend (on Ethereum) is called with ETH as the asset argument and some msg.value, the flow executes correctly: 
1. the ETH is deposited
2. and the gateways' function (depositAndCall) is invoked successfully.

However, if the call reverts, the ETH is sent back to the GatewaySend contract and the onRevert function is triggered by the gateway. One of the arguments passed in the RevertContext struct is asset, which would be address(0) to indicate the native token (ETH) should be refunded to the user.
```solidity
struct RevertContext {
    address sender;
    address asset;/// @param asset Address of asset. On a connected chain, it contains the fungible
/// token address or is empty if it's a gas token.
    uint256 amount;
    bytes revertMessage;
}
```
The current implementation of the onRevert function does not handle cases where the native token must be refunded. As a result, the safeTransfer call will fail, and the onRevert function will revert. This represents a direct failure of core contract functionality.
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        address sender = address(uint160(bytes20(context.revertMessage[32:])));
        TransferHelper.safeTransfer(context.asset, sender, context.amount):
        
        emit EddyCrossChainRevert(
            externalId,
            context.asset,
            context.amount,
            sender
        );
    }
```
```solidity
function safeTransfer(address token, address to, uint value) internal {
        // bytes4(keccak256(bytes('transfer(address,uint256)')));
        (bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
        require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
    }
```

### Attack Path
1. user calls depostAndCall with some amount of msg.value and asset is ETH(native token)
2. the ETH is deposited and the gateways' function (depositAndCall) is invoked successfully.
3. the cross chain functionality reverts and now the onRevert function is called ( by gatewayEVM also TSS would transfer eth to gatewaySend)
4. since the variable asset inside of RevertContext would be set to address(0) indicating that the native token should be refunded to the user
5. since the onRevert function uses safeTransfer (from transferHelper library) it will try to call the transfer function on address(0) (since the asset passed to the safe transfer is native token ) which will fail
6. the onRevert call will fail
### Impact

Since this vulnerability is present, users will be unable to reclaim their ETH via the onRevert (the function is called by gateway contract and users should receive assets automatically) function when a cross-chain transaction fails and involves ETH as the input asset. Unless a workaround exists, this would result in the user being permanently unable to retrieve their funds.
