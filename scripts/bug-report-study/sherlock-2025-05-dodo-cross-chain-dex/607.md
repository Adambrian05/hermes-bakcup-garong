# Lack of replay protection in onRevert() breaks cross-chain refund guarantees

### Summary

The `onRevert()` function in both `GatewaySend` and `GatewayCrossChain` contracts lacks replay protection, allowing the same `externalId` to be processed more than once. This means that if the ZetaChain gateway retries or accidentally replays a revert message, the associated funds may be refunded multiple times to the same user.

While `onRevert()` is gated by `onlyGateway`, the contracts assume the gateway is always correct and never repeats a message. This breaks the execute-once guarantee critical to cross-chain protocols and exposes the protocol to silent overpayment and irreversible loss of funds.

In `GatewayCrossChain`, the `externalId` is even used as a key in the `refundInfos` mapping, but this offers no idempotency: the value is blindly overwritten with no check for prior existence, allowing multiple refunds to be stored and claimed from the same failure event.

Cross-chain systems must not rely on off-chain behavior to enforce message uniqueness. Without on-chain idempotency enforcement, even minor infrastructure failures can escalate into protocol-wide financial inconsistencies.

### Root Cause

In [`GatewaySend.sol#L393`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393), the `onRevert()` function decodes the externalId and sender from `context.revertMessage`, then refunds assets to the sender:

```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    address sender = address(uint160(bytes20(context.revertMessage[32:])));
    TransferHelper.safeTransfer(context.asset, sender, context.amount);
}
```

However, no state is updated to prevent reprocessing the same `externalId` again. This opens the door for duplicate refunds.

Similarly, in `GatewayCrossChain.sol`[#L517](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517) and [#L550](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L550), both `onRevert()` and `onAbort()` store refund data in the `refundInfos[externalId]` mapping. But this mapping provides no replay protection, as the value is overwritten with no guard against prior execution. The same `externalId` can be used multiple times to insert or update refund records, which can then be repeatedly claimed.

### Internal Pre-conditions

In `GatewaySend.sol`,
1. Gateway (or a test double) must call `onRevert()` with a crafted or repeated revertMessage
2. `context.revertMessage` contains a valid `externalId` and recipient address
3. The contract has sufficient asset balance to issue the refund more than once


### External Pre-conditions

None.

### Attack Path

In `GatewaySend.sol`,

1. Gateway sends a valid `onRevert()` call with an `externalId` and refund data
2. User receives refund
3. Gateway (or attacker in a test/mock environment) calls `onRevert()` again with same message
4. User receives second refund for same failure

### Impact

If a cross-chain transaction fails and the `onRevert()` function is invoked multiple times with the same `externalId`, the recipient can receive multiple refunds for a single failed transaction. This results in the total refund amount exceeding the original input, causing a fundamental imbalance in the protocol's asset accounting.

In real-world cross-chain environments, such duplication can occur accidentally, due to benign issues such as gateway retries, message replays, or chain reorgs. If left unguarded, these non-malicious events can still result in permanent and silent fund leakage.

Furthermore, in the presence of governance or access control failures—where a gateway may be misconfigured or malicious—the lack of replay protection can escalate into a system-wide vulnerability, allowing repeated unauthorized refunds without violating access control constraints.

This issue affects both immediate and deferred refund flows, as seen in `GatewaySend` and `GatewayCrossChain` respectively.

### PoC

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@zetachain/protocol-contracts/contracts/evm/interfaces/IGatewayEVM.sol" ;
import {BaseTest} from "./BaseTest.t.sol";

// Demonstrates double refund in GatewaySend (same logic applies to GatewayCrossChain)
contract PoC_RevertTwice is BaseTest {
    function test_AOnRevertTwice() public {
        bytes32 externalId = bytes32(0);
        uint256 amount = 100 ether;
        token1A.mint(address(gatewaySendA), 2* amount);

        // First refund
        vm.prank(address(gatewayA));
        gatewaySendA.onRevert(
            RevertContext({
                sender: address(this),
                asset: address(token1A),
                amount: amount,
                revertMessage: bytes.concat(externalId, bytes20(user2))
            })
        );

        assertEq(token1A.balanceOf(user2), amount);

        // Second refund with same message
        vm.prank(address(gatewayA));
        gatewaySendA.onRevert(
            RevertContext({
                sender: address(this),
                asset: address(token1A),
                amount: amount,
                revertMessage: bytes.concat(externalId, bytes20(user2))
            })
        );
        
        assertEq(token1A.balanceOf(user2), 2 * amount, "Second refund occurred!");
    }
}
```

### Mitigation

Add an `externalId` guard to track already-processed refunds.

for example, 
```solidity
mapping(bytes32 => bool) public processed;

function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    require(!processed[externalId], "ALREADY_PROCESSED");
    processed[externalId] = true;

    address sender = address(uint160(bytes20(context.revertMessage[32:])));
    TransferHelper.safeTransfer(context.asset, sender, context.amount);
}
```

This ensures that each failed transaction is only processed once.
