# USDT Incompatibility in GatewaySend: Assumes Standard ERC20 Behavior

### Summary

The `GatewaySend` smart contract assumes that all ERC20 tokens conform to the standard by returning a boolean value from `transferFrom`. However, widely-used tokens like **USDT** (Tether) do **not** return a value from `transfer` or `transferFrom`. As a result, interactions with such tokens fail unexpectedly. Specifically, any cross-chain transaction using USDT as the `fromToken` or `asset` in `depositAndCall()` will **hard revert**, rendering the contract **incompatible with USDT** and potentially other non-standard ERC20s.


### Root Cause

The contract uses `IERC20(...).transferFrom(...)` inside a `require(...)` statement, expecting a `bool` return. However, USDT and similar tokens **do not return any value**, which causes the call to revert due to unexpected return data size.

- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L238-L241
- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L359

```solidity
require(
    IERC20(fromToken).transferFrom(msg.sender, address(this), amount), 
    "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
);
```

These will revert for non-standard tokens like USDT.

### Internal Pre-conditions

1. User calls `depositAndCall()` function with a non-standard ERC20 token (e.g., USDT) as `fromToken` or `asset`.
2. User has approved `GatewaySend` to spend their USDT.
3. User has a sufficient USDT balance.

### External Pre-conditions

1. USDT or a similar non-standard ERC20 token is used as the input or output asset.
2. The token contract continues to behave non-standardly (e.g., USDT's `transferFrom()` does not return a value).

### Attack Path

There is no malicious attack per se; rather, the contract **fails silently** for common user scenarios, especially when using USDT.

1. A user initiates a cross-chain transfer or swap using USDT.
2. The transaction reverts unexpectedly due to invalid return data assumptions.
3. No fallback or compatibility handling is present.
4. Funds are not transferred, and the transaction fails.


### Impact

- All `depositAndCall()` flows involving USDT are broken.
- Prevents swaps, bridging, and transfers for one of the most commonly used stablecoins.
- Protocol becomes **incompatible** with USDT, significantly affecting usability and adoption.
- Potential user funds remain untransferred; users experience failed transactions.
- No fallback refund mechanism for failed `transferFrom`.
