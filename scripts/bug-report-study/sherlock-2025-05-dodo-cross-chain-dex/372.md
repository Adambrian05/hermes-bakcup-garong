# GatewayTransferNative.withdrawToNativeChain() allows attacker to steal refunds through dodo swap

### Summary

The distinction between `GatewayTransferNative` and `GatewayCrossChain` is that former does not immediately initiates the withdrawal from ZetaChain to destination chain. Instead, it allows users to call `withdrawToNativeChain()` and transfer funds from ZetaChain themselves.

However, the `withdrawToNativeChain()` can be called with `amount == 0` of `zrc20`. Users can do that and provide a `message` with the `params.fromToken` being the token `GatewayTransferNative` holds as a refund and swap it for the `params.toToken` via dodo swap in internal `_doMixSwap()`. The `outputAmount` will then be the swapped refund tokens, which will be received by the attacker.

All in all, this issue stems from the fact that `withdrawToNativeChain()` does not check if `amount` of tokens provided by the user equal the `params.fromTokenAmount`.

### Root Cause

When users call `GatewayTransferNative.withdrawToNativeChain()`, they provide the `zrc20`, `amount` and `message` parameters to the function call, [here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530-L534). The `message` contains all essential data for CCTX, which includes the dodo swap on ZetaChain:
```solidity
function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
...
```
When users want to swap on dodo, the provide the `swapDataZ`, which includes the `MixSwapParams` values. Typically, users transfer the `amount` of `zrc20` here:
```solidity
if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 
```
and then this amount should be swapped in internal `_doMixSwap()` swap function here:
```solidity
uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
```

However, the issue is that the `withdrawToNativeChain` does not verify that `zrc20` is the same as `params.fromToken`, and that `amount` equals to `params.fromTokenAmount`. This allows anyone to transfer zero tokens (or very small amount of low-value tokens if the erc20 reverts on zero value transfer) but provide the `message` that contains the swap parameters for tokens held by the contract as refunds, and steal these refunds with no cost.

### Internal Pre-conditions

1. Attacker needs to provide the `message` with swap data which includes the `params.fromToken` and `params.fromTokenAmount` of tokens that held by the contract as refund.

### External Pre-conditions

1. `GatewayTransferNative` contract should hold the refund tokens in its balance.

### Attack Path

1. Attacker calls `GatewayTransferNative.withdrawToNativeChain` with spoofed message that includes swap data that will swap tokens held by the `GatewayTransferNative` contract as refund.
2. After the function is called, the tokens that should be refunded will be swapped to `targetZRC20` tokens through dodo
3. Attacker will receive these tokens on the destination chain.

### Impact

Attacker can steal refunds.

### PoC

_No response_
