# `withdraw` in `GatewayTransferNative` can be used to grief and drain unclaimed refund

### Summary

the function `GatewayTransferNative::withdraw` is a public function. at a glance the function would call `gateway.withdraw` where if there are no sufficient allowance and balance this would revert.
but with proper step we can achieve surplus allowance and balance inside the `GatewayTransferNative` contract to make the `withdraw` calls `gateway.withdraw` for it to be succeed, griefing and draining unclaimed refund inside the contract.

### Root Cause

there are 2 component for this exploit can happen: allowance for zeta gateway contract and ZRC-20 equivalent of gas token for target chain inside the contract.

ZRC-20 equivalent of gas inside contract:
this can be achieved if `withdrawToNativeChain` succeed but the corresponding tx in the native chain are reverted.
this would later populating the mapping `refundInfos[externalId]` via `GatewayTransferNative::onRevert` for it to be claimed later by user who initiate the calls.

allowance of said token:
this can be achieved whenever user call `withdrawToNativeChain` and suceed inside the zeta chain. because if we see the implementation of gas token handling:

we can see here that the contract approve the zeta gateway to spend `outputAmount + gasFee` but on `withdrawAndCall` the amount is only `outputAmount - gasFee`.
if we look into zeta gateway contract, the withdraw function would actually try to transferFrom this `GatewayTransferNative` two separate transfer:
1. `gasFee`
2. amount provided in params, in this case `outputAmount - gasFee`
so actually the total allowance spent for this call is `gasFee + outputAmount - gasFee` which is only `outputAmount`

ultimately, the zeta gateway contract only use `outputAmount` but `GatewayTransferNative` contract gave the gateway `outputAmount + gasFee` amount of allowance. so here we can get our surplus allowance that is not used by the zeta gateway, which is `gasFee`.

because of 2 component (allowance for gateway and balance) exist, attacker can just call the public function `GatewayTransferNative::withdraw` using small amount to drain the existing balance to any address.

the constraint is:
1. the current gasFee should be lower than the current allowance from old transaction.
2. only gas token can be used in this because the surplus allowance only happen if the token withdrawed is native gas token in the destination chain (like ETH.ETH or BTC.BTC, [see complete list here](https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets))

### External Pre-conditions

1. there exist unclaimed refund inside the `GatewayTransferNative` from `onRevert`/`onAbort` call
2. let say victim A have 1 ETH unclaimed refund

### Attack Path

1. user (or this can be attacker also) call `withdrawToNativeChain` for ETH.ETH ZRC20 token, the amount is 0.1 ETH
2. gas fee currently is 0.001 ETH (what this means the returned amount of ZRC20.withdrawGasFee is 0.001 ETH, so its already include protocol fee)
3. `GatewayTransferNative` contract now give zeta gateway contract 0.101 ETH allowance
4. call succeed, but zeta gateway only use 0.1 ETH allowance from 0.101 ETH allowance. allowance left is 0.001 ETH
5. attacker then wait until the gas fee is lower, let say the gas fee now 0.0008 ETH
6. attacker calls `GatewayTransferNative::withdraw` using their own externalId, him as the receiver, and appropriate ZRC20 address for ETH.ETH and the amount is 0.0002 ETH. this call is done without attacker sending any ZRC20 ETH token
7. because the amount is 0.0002 ETH and the gas fee is 0.0008, the total amount would transferred from this contract to zeta gateway is 0.001 ETH, the same allowance left in step 4.
8. 0.001 ETH left from this contract to zeta gateway, with the small amount later received by attacker
9. the contract balance now 0.999 ETH, victim A cant withdraw their unclaimed refund because insufficient balance

### Impact

while the amount is negligible, there are two things that would make the impact severe:
1. this exploit can be called everytime an user successfully call `GatewayTransferNative` with gas token as the target, even attacker can attempt this themself. this can be repeated infinitely.
2. `claimRefund` would be DoSed over prolonged repeated exploit, because the amount that can be claimed is mismatched with actual contract balance.
