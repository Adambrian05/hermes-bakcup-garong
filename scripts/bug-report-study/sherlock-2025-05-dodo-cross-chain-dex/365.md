# Using `getAmountsIn()` to calculate `amountInMax` is vulnerable to sandwich attacks

### Summary

Since the result of `getAmountsIn()` is the same as the result of `swapTokensForExactTokens()` in the same transaction, this makes the slippage control in `_swapAndSendERC20Tokens()` not work.

### Root Cause

In [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L313-L330) and [GatewayCrossChain.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L309-L326) ,`_swapAndSendERC20Tokens()` will call `swapTokensForExactTokens()` to swap targetZRC20 for gasZRC20. When calculating `amountInMax`, the protocol uses the result of `getAmountsIn()`. Since the result of `getAmountsIn()` is the same as the result of `swapTokensForExactTokens()` in the same transaction, this makes the slippage control not work.

For example, the current targetZRC20/gasZRC20 = 2500, the attacker manipulates the uniswap price to 1000. Since the prices in `getAmountsIn()` and `swapTokensForExactTokens()` are both 1000, the user will suffer a sandwich attack when performing the swap.

### Internal Pre-conditions

None

### External Pre-conditions

None

### Attack Path

For example, the current targetZRC20/gasZRC20 = 2500, the attacker manipulates the uniswap price to 1000. Since the prices in `getAmountsIn()` and `swapTokensForExactTokens()` are both 1000, the user will suffer a sandwich attack when performing the swap.

### Impact

When the attacker performs a sandwich attack, almost all of the targetAmount will be exchanged for gasZRC20, causing users to suffer losses.

### Mitigation

It is recommended to provide parameters to allow users to control slippage in `_swapAndSendERC20Tokens()`
