# GatewaySend.sol :: onRevert() if a native token is used and the cross-chain transaction reverts, the tokens will be permanently locked in the contract.

### Summary

`onRevert()` is called if the cross-chain transaction fails for any reason. In such cases, the gateway uses it to return the tokens to the user. 

However, if a native token is used as and the transaction reverts, the tokens will be permanently locked in the contract. This happens because the function only implements ERC-20 token transfers and does not handle native token transfers.


### Root Cause

`onRevert()` is implemented as shown below and is triggered by the Gateway when a [depositAndCall()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L287-L339) operation fails. It is used to return the tokens held by the contract back to the user. More information can be found [here](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions).



>Note: The issue arises when the `fromAsset` is the native token and either no swap is performed on DODO or swap is performed and the `toToken` is the native token. This is because `onRevert()` returns the tokens in the form they exist on the connected chain.
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        address sender = address(uint160(bytes20(context.revertMessage[32:])));
        TransferHelper.safeTransfer(context.asset, sender, context.amount);
        
        emit EddyCrossChainRevert(
            externalId,
            context.asset,
            context.amount,
            sender
        );
    }
```
As you can see, only `safeTransfer()` is used to refund the user, which works for ERC-20 tokens but not for native tokens. However, native tokens can be used in [depositAndCall()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L296), as shown in the implementation.

This leads to a critical issue: native tokens can become permanently locked in the contract. The `safeTransfer()` function relies on a low-level `call` to invoke the `transfer` function on the token contract, but native tokens do not support this function. 

As a result, the refund fails, and without any withdrawal mechanism, the native tokens remain irretrievable in the contract.





### Internal Pre-conditions

1. The user calls `depositAndCall()` on the connected chain using a native token as `fromAsset`, with either no swap performed or a swap is performed and `toToken` being a native token.
2. The transaction fails for any reason.
3. The gateway triggers `onRevert()` on connected chain to return the funds to the user using `safeTransfer()`.
4. The funds are not sent to the user and become permanently locked in the contract.


### External Pre-conditions

None.

### Attack Path

None.

### Impact

The tokens will be permanently locked in the contract, causing users to lose their deposits.


### PoC

To better understand the issue, copy the following POC into `GatewaySend.t.sol`.
```solidity
function test_OnRevertFails() public {
        bytes32 externalId = bytes32(0);
        uint256 amount = 100 ether;

        //mint eth to gatewaySendA
        vm.deal(address(gatewaySendA), amount);

        vm.prank(address(gatewayA));
        gatewaySendA.onRevert(
            RevertContext({
                sender: address(this),
                asset: address(_ETH_ADDRESS_),
                amount: amount,
                revertMessage: bytes.concat(externalId, bytes20(user2))
            })
        );

        assertEq(address(user2).balance, 0);
        assertEq(address(gatewaySendA).balance, amount);
    }
```
As you can see, the transaction does not revert, but the funds are not sent to the user. Instead, they remain in `gatewaySendA`, effectively locking the tokens in the contract permanently.

> Note: The transaction does not revert because, in Solidity, a low-level `call` (used by [safeTransfer()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L12-L16)) to an address without code, such as a native token, always returns success and empty data, allowing the `require` statement to be bypassed.


### Mitigation

To resolve the issue, first check if the token is a native token; if so, use `safeTransferETH` to transfer the funds to the user.
```diff
function onRevert(RevertContext calldata context) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        address sender = address(uint160(bytes20(context.revertMessage[32:])));
        
-       TransferHelper.safeTransfer(context.asset, sender, context.amount);
+       if (context.asset == _ETH_ADDRESS_) {
+            TransferHelper.safeTransferETH(sender, context.amount);
+        } else {
+            TransferHelper.safeTransfer(context.asset, sender, context.amount);
+        }
        
        emit EddyCrossChainRevert(
            externalId,
            context.asset,
            context.amount,
            sender
        );
    }
```
