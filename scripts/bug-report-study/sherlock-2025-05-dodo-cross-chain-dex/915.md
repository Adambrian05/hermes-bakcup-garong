# depositAndCall() forwards full msg.value Instead of Specified amount for Native ETH Transactions

### Summary

The no-swap overload of the `depositAndCall` function in `GatewaySend.sol` incorrectly forwards the entire msg.value (ETH sent with the transaction) to the ZetaChain gateway when the specified asset is native ETH. This occurs even if the amount parameter, which dictates the intended quantity for the cross-chain operation, is less than msg.value. This leads to more ETH being committed to the cross-chain process than intended by the user and inconsistencies in event logging.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L287C5-L339C6

### Root Cause

The root cause lies in the handling of native ETH deposits within the depositAndCall(address targetContract, uint256 amount, address asset, uint32 dstChainId, bytes calldata payload) function.

The function accepts an `amount` parameter, representing the intended quantity of asset to be processed.
When asset is _ETH_ADDRESS_ (native ETH), the function correctly checks if `msg.value >= amount` to ensure sufficient funds are provided.

However, it then calls the internal function _handleETHDeposit passing `msg.value` as the amount to be deposited, instead of the ` user-specified amount`.

The `_handleETHDeposit` function subsequently calls `gateway.depositAndCall{value: amount_received}(...)`, thus depositing the entire `msg.value` to the ZetaChain gateway.

Furthermore, the EddyCrossChainSend event emitted at the end of the function logs the user-specified amount for both the input amount and outputAmount fields. This is misleading if msg.value > amount was sent and processed, as the actual amount sent to the gateway was msg.value.

### Internal Pre-conditions

1. User call `function depositAndCall( )` function with msg.value > amount and `asset` == _ETH_ADDRESS_;

### External Pre-conditions

NA

### Attack Path

1.  A user calls the no-swap depositAndCall function for a native ETH transaction, specifying an amount (e.g., 1 ETH) but sends a larger msg.value (e.g., 5 ETH) with the transaction.

2. Flawed Processing: The contract checks if msg.value >= amount (which passes) but then incorrectly uses the entire msg.value (5 ETH) when calling _handleETHDeposit to send funds to the ZetaChain gateway.

3. Outcome: The full msg.value (5 ETH) is committed to the cross-chain operation, exceeding the user's specified amount (1 ETH). The emitted event also misleadingly logs the smaller amount.

### Impact

Users loose extra funds that they have transfered.
Swap gets executed for the whole amount rather than the users expected amount.

### PoC

Consider the following scenario:

targetContract = some_address
amount = 1 ether
asset = _ETH_ADDRESS_ (0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE)
dstChainId = some_chain_id
payload = some_bytes_payload
User calls depositAndCall with msg.value = 5 ether.

Expected Behavior:

1 ether should be processed and sent to the ZetaChain gateway via _handleETHDeposit.
The remaining 4 ether (msg.value - amount) should ideally be refunded to msg.sender or the transaction should revert if exact amounts are required.
The EddyCrossChainSend event should accurately reflect that 1 ether was the intended and processed amount.
Actual Behavior:

The require(msg.value >= amount) (i.e., 5 ether >= 1 ether) passes.
_handleETHDeposit is called with msg.value (i.e., 5 ether).
solidity
_handleETHDeposit(targetContract, 5 ether, message, revertOptions);
Inside _handleETHDeposit, gateway.depositAndCall{value: 5 ether}(...) is executed.
The full 5 ether is sent to the ZetaChain gateway.
The EddyCrossChainSend event is emitted with amount = 1 ether and outputAmount = 1 ether. This is inconsistent with the 5 ether actually sent to the gateway.
This demonstrates that the entire `msg.value` is used for the ETH deposit, not the specified amount.

### Mitigation

```diff

 if (isETH) {
            require(msg.value >= amount, "INSUFFICIENT AMOUNT: ETH NOT ENOUGH");
            _handleETHDeposit(
                targetContract, 
-                msg.value,
+              amount
                message, 
                revertOptions
            );
        } 
```

And then , transfer any extra funds back to the user.
