# Unauthorized withdrawal and fee misaccounting leading to token theft in `GatewayTransferNative::withdraw`

### Summary

Public withdraw function and inconsistent fee handling—approving `amount + fee` but sending `amount - fee` while gateway processes only `amount`—will cause a fund theft vulnerability for contract users, as malicious actors can exploit the approved but unused fee allowance to withdraw excess tokens equal to the fee in `GatewayTransferNative::withdraw`.

### Root Cause

In the gateway contract’s withdraw function, the amount approved for token transfer includes both the `amount` and `fee`, but the actual transfer only sends `amount - fee` [code](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L458). The gateway only accounts for `amount` when withdrawing, leaving the `fee` portion still approved. This inconsistent fee handling is a mistake as it allows malicious users to exploit the leftover approved `fee` allowance to withdraw additional tokens beyond what was intended. This exploit can only occur if the contract currently holds sufficient token assets to cover the unauthorized withdrawals. [code](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286-L304)

### Internal Pre-conditions

1. A user must first call `withdrawToNativeChain`, which triggers `_handleBitcoinWithdraw` where the contract approves `amount + fee`, but the gateway only uses `amount`, leaving the `fee` amount still approved.
2. The contract (`GatewayTransferNative`) must currently hold assets (tokens) that have not been fully withdrawn or “superWithdrawn.”
3. A malicious user calls `withdraw()` and passes the `validateWithdrawalParams` checks in the gateway contract.
4. Upon these conditions, the malicious user can steal the tokens equal to the approved fee amount.

### External Pre-conditions

1. The token contract used for approvals must allow unlimited or sufficient allowance spending by the `GatewayTransferNative` contract.
2. The underlying token’s transfer and approval mechanisms must not revert or restrict partial approvals or transfers during the attack.
3. No external emergency stop or pause mechanism is activated on the `GatewayTransferNative` or token contracts that would prevent withdrawals.

### Attack Path

1. User (malicious actor) calls `withdrawToNativeChain()` which triggers `_handleBitcoinWithdraw()`, approving `amount + fee` tokens to the gateway contract.
2. The gateway contract internally uses only `amount` for withdrawal calculations but the entire `amount + fee` remains approved.
3. Malicious user calls `withdraw()` to transfer tokens, exploiting the approved but unused `fee` portion.
4. The `withdraw()` call passes the `validateWithdrawalParams()` checks inside the gateway contract.
5. If the `GatewayTransferNative` contract currently holds tokens (i.e., tokens have not been fully withdrawn or “superWithdrawn”), the malicious user successfully steals tokens equal to the fee amount.

### Impact

The `GatewayTransferNative` contract suffers an approximate loss of tokens equal to the accumulated fee amount because the `withdraw` function is public. The malicious user gains these tokens by exploiting the approved but unused fee allowance.
