# Malicious Attackers Will Cause Denial of Service for Users Performing Token Withdrawals via GatewayTransferNative Contract

### Summary

Insufficient pool existence validation will cause a denial of service for users performing token withdrawals via GatewayTransferNative as malicious attackers will manipulate pool balance checks to force the use of non-existent Uniswap pools, causing user-initiated withdrawal operations to revert.

### Root Cause

In [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L216-L229), the `_existsPairPool` function only checks if tokens have non-zero balances at a computed pool address without verifying that the pool contract actually exists at that address.

```solidity
function _existsPairPool(
    address uniswapV2Factory,
    address zrc20A,
    address zrc20B
) internal view returns (bool) {
    address uniswapPool = uniswapv2PairFor(
        uniswapV2Factory,
        zrc20A,
        zrc20B
    );
    return
        IZRC20(zrc20A).balanceOf(uniswapPool) > 0 &&
        IZRC20(zrc20B).balanceOf(uniswapPool) > 0;
}
```

The function assumes that if tokens exist at the computed address, then a valid Uniswap pool exists there, but this is not necessarily true.

### Attack Path

1. Attacker identifies target token pairs (targetZRC20, gasZRC20) that would be used in user-initiated withdrawal operations requiring gas fee conversion
2. Attacker computes the deterministic pool address using `uniswapv2PairFor(UniswapFactory, targetZRC20, gasZRC20)`
3. Attacker sends 1 wei of `targetZRC20` and 1 wei of `gasZRC20` directly to the computed address
4. When a legitimate user calls `withdrawToNativeChain()` with a destination where `targetZRC20 != gasZRC20`:
   - `withdrawToNativeChain()` processes the withdrawal and calls `_handleEvmOrSolanaWithdraw()`
   - `_handleEvmOrSolanaWithdraw()` calls `_swapAndSendERC20Tokens()`
   - `_swapAndSendERC20Tokens()` calls `getPathForTokens(targetZRC20, gasZRC20)`
   - `getPathForTokens()` calls `_existsPairPool()` which returns `true` due to non-zero balances
   - Function returns a 2-token path `[targetZRC20, gasZRC20]` instead of 3-token path `[targetZRC20, WZETA, gasZRC20]`
   - `UniswapV2Library.getAmountsIn()` and `swapTokensForExactTokens()` are called with the 2-token path
   - Both calls revert because no actual pool contract exists at the computed address
5. The user's withdrawal operation reverts, causing denial of service

### Impact

Users attempting to withdraw tokens via GatewayTransferNative suffer a complete denial of service when `targetZRC20 != gasZRC20` (requiring gas fee conversion). The attacker loses minimal tokens (2 wei per token pair) to maintain the griefing attack but gains the ability to consistently break user-initiated withdrawals for targeted token pairs.
