# Attacker will steal all stored tokens in `GatewaySend` as asset parameter validation is missing

### Summary

Missing validation between swap output token and `asset` parameter will cause complete loss of all stored tokens for the protocol as an attacker will exploit `asset` parameter mismatch to drain contract balances.

### Root Cause

In `GatewaySend.sol:268-269` there is missing validation that the `asset` parameter matches the output token (`toToken`) from the swap data decoded in `_doMixSwap()`.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218-L245

1. The `MixSwapParams` struct has a `toToken` field that specifies what token the swap should output
2. The `depositAndCall()` function performs a swap via `_doMixSwap()` which returns the output amount 
3. However, the function then uses the `asset` parameter (which is a separate parameter) to deposit through the gateway
4. There's no validation that `asset` matches `params.toToken` from the swap data
5. This allows an attacker to drain any tokens held by the contract

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L266-L272

### Internal Pre-conditions

1. Contract needs to hold any ERC20 tokens from previous failed transactions or leftover balances

### External Pre-conditions

N/A

### Attack Path

1. Attacker calls `GatewaySend::depositAndCall()` with `fromToken=USDC`, `swapData` containing `toToken=USDT`, but `asset=BTC` 
2. Function executes swap from USDC to USDT via `_doMixSwap()`, receiving USDT to the contract
3. Function then deposits BTC (from contract's existing balance) to the gateway using `_handleERC20Deposit()` instead of the USDT from swap
4. Attacker repeats this process for all token types held by the contract to drain them completely

### Impact

The protocol suffers complete loss of all stored token balances. The attacker gains all stolen tokens from the contract.
