# Invalid Check in `GatewayTransferNative.claimRefund` Allows Anyone To Claim Refunds Intended for Non-EVM Addresses

### Summary

Similar to [`GatewayCrossChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-pyk/issues/3), the [`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680) function in `GatewayTransferNative` lacks sufficient authorization for refunds where the original intended recipient was a non-EVM address with a length not equal to 20 bytes (e.g., Solana addresses). This allows any arbitrary caller who discovers the `externalId` for such a refund to claim the ZRC20 tokens, which are then sent to the caller's (`msg.sender`) ZetaChain address. This leads to a misrouting and potential theft of user funds. 

### Root Cause

The bug stems from how refund information for certain non-EVM recipients is stored and the subsequent flawed authorization in `claimRefund`.

1.  **Population of `refundInfo` with Non-EVM Address (e.g., Solana):**
    *   A user calls `GatewayTransferNative.withdrawToNativeChain`. The `message` parameter contains a `DecodedMessage` which includes `decoded.receiver` and `decoded.dstChainId`.
    *   If `decoded.dstChainId` corresponds to a non-Bitcoin, non-EVM chain (e.g., `SOLANA_EDDY`), the function calls `_handleEvmOrSolanaWithdraw`.
    *   `_handleEvmOrSolanaWithdraw` calls the internal `GatewayTransferNative.withdrawAndCall` function.
    *   Within this internal `withdrawAndCall`, `RevertOptions` are set up where `revertMessage` is `bytes.concat(externalId, receiver)`. If `receiver` is a non-EVM address (e.g., a Solana address, not 20 bytes long), its full byte string is used.
    *   If this outgoing cross-chain operation fails, the ZetaChain gateway calls `onRevert` on `GatewayTransferNative`.
        *   Inside `onRevert`, `context.revertMessage` is parsed. `bytes memory walletAddress` is assigned `context.revertMessage[32:]`, capturing the original full non-EVM `receiver` bytes.
        *   The condition `if (context.revertMessage.length == 52)` will be false if the original `receiver` was not 20 bytes (e.g., for a Solana address, `32 + length(solana_addr) != 52`).
        *   Thus, the `else` block is executed, creating a `RefundInfo` struct where `refundInfo.walletAddress` is populated with the full non-EVM `receiver` bytes. This `RefundInfo` is then stored in the `refundInfos` mapping.

2.  **Flawed Authorization in `claimRefund` for these Non-EVM Addresses:**
    *   The `claimRefund` function in `GatewayTransferNative` is identical to the one in `GatewayCrossChain`.
    *   When `refundInfo.walletAddress.length` is not 20 (as would be the case for a Solana address populated above):
        *   The `receiver` variable defaults to and remains `msg.sender`.
        *   The `if (refundInfo.walletAddress.length == 20)` condition evaluates to false.
        *   The authorization check `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");` becomes `require(bots[msg.sender] || msg.sender == msg.sender, "INVALID_CALLER");`, which always passes for any non-bot `msg.sender`.
    *   This allows any address to call `claimRefund` and receive the ZRC20 tokens if the `externalId` corresponds to a refund originally intended for such a non-EVM (e.g., Solana) address. 

### Internal Pre-conditions
1.  A `RefundInfo` entry must exist in `refundInfos` in `GatewayTransferNative`.
2.  `refundInfo.walletAddress` for this entry must have a length not equal to 20 bytes (specifically originating from a non-EVM `receiver` like a Solana address).
3.  `GatewayTransferNative` must hold a balance of `refundInfo.token`.

### External Pre-conditions
1.  A user calls `GatewayTransferNative.withdrawToNativeChain` with a `message` parameter that decodes to a `decoded.receiver` being a non-EVM address (e.g., Solana, with length != 20 bytes) and `decoded.dstChainId` corresponding to such a chain.
2.  The subsequent cross-chain operation fails or is aborted.
3.  The ZetaChain gateway calls `onRevert` on `GatewayTransferNative`, with `revertMessage` containing the full non-EVM `receiver` address.
4.  `GatewayTransferNative` stores a `RefundInfo` with this full non-EVM `walletAddress`.
5.  An attacker discovers the `externalId` for this pending refund.

### Attack Path
1.  A user calls `GatewayTransferNative.withdrawToNativeChain` to send tokens to a Solana address `solana`.
2.  The transaction processing leads to the `_handleEvmOrSolanaWithdraw` path, and the outgoing call fails.
3.  `onRevert` is called on `GatewayTransferNative`, storing `RefundInfo` for `externalId` with `walletAddress = bytes(solanaAddress)`.
4.  An attacker monitors `EddyCrossChainRefund` events, sees `externalId`, and notes `walletAddress` is not 20 bytes.
5.  Attacker calls `GatewayTransferNative.claimRefund(externalId)`.
6.  The flawed authorization check in `claimRefund` passes.
7.  `TransferHelper.safeTransfer` sends `refundInfo.token` to the attacker's ZetaChain address.

### Impact
The attacker steals ZRC20 tokens intended for the user. Loss of user funds.

### Mitigation
Apply the same [mitigation strategy](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-pyk/issues/3) as for `GatewayCrossChain` to the `claimRefund` function in `GatewayTransferNative`. Ensure only registered bots can claim refunds if `refundInfo.walletAddress.length != 20`.

```solidity
function claimRefund(
    bytes32 externalId
) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiverItself = msg.sender; // Default receiver to msg.sender
    bool isBotCaller = bots[msg.sender];

    // Check if the refund entry exists before trying to access its members
    require(refundInfo.externalId != bytes32(0), "REFUND_NOT_EXIST_OR_ALREADY_CLAIMED");

    if (refundInfo.walletAddress.length == 20) {
        address intendedEvmReceiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(isBotCaller || msg.sender == intendedEvmReceiver, "INVALID_CALLER_EVM");
        // If a bot is claiming for an EVM address, send to the intended EVM receiver.
        // If the user themselves is claiming, send to them.
        receiverItself = intendedEvmReceiver;
    } else {
        // For non-EVM addresses, only bots can claim.
        // The tokens will be sent to the bot's address (msg.sender).
        require(isBotCaller, "INVALID_CALLER_NON_EVM_BOT_ONLY");
    }

    // Cache values needed after deletion
    address tokenToRefund = refundInfo.token;
    uint256 amountToRefund = refundInfo.amount;

    // Effect: Delete state BEFORE external call
    delete refundInfos[externalId];

    // Interaction
    TransferHelper.safeTransfer(tokenToRefund, receiverItself, amountToRefund);

    emit EddyCrossChainRefundClaimed(externalId, tokenToRefund, amountToRefund, abi.encodePacked(msg.sender));
}
```
