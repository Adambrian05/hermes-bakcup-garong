Medium

# CEI pattern is not followed which can lead to possible Reentrancy attack

### Summary

The [`GatewayTransferNative::claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661C1-L680C6)  function allows an external call to an untrusted ERC20 token contract (via `TransferHelper.safeTransfer`) before deleting the refund record in storage. This opens the function to a classic **reentrancy attack**, where a malicious token can re-enter[`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661C1-L680C6)  and drain the protocol by claiming the same refund multiple times.

In addition, the same issue exists in the [`GatewayCrossChain::claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571C5-L590C6), the same root cause and potential problem, as well as risk, must be considered there as well.

---

### Root Cause

The function performs an external call to `safeTransfer` **before** updating the internal state ([`delete refundInfos[externalId]`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L672)). If the token being transferred is a malicious contract (e.g. ERC777 or a custom reentrant ERC20), it can exploit this ordering to call [`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661C1-L680C6)   recursively and bypass the `delete` operation, resulting in multiple successful refund claims.

---

### Internal Pre-conditions

- The `refundInfos[externalId]` record exists.
- The caller is either the `receiver` or an authorized bot (`bots[msg.sender] == true`).

---

### External Pre-conditions
N/A

### Attack Path

1. A user or bot calls [`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661C1-L680C6) for a malicious token.
2. `safeTransfer()` triggers an external call to the `receiver`.
3. The `receiver` contract (malicious) calls `claimRefund` again before `delete refundInfos[externalId]` is executed.
4. The refund is processed again and funds are transferred twice (or more).

---

### Impact

The protocol can suffer **funds drain** from its refund pool. Attackers could exploit this to receive multiple refunds using the same `externalId`, leading to significant loss of funds from the treasury or user reserve.

---

### PoC

The vulnerability can be simulated using a custom ERC20 token that overrides `transfer` with a call back into `claimRefund` during the refund process. Example structure of such token:

```solidity
contract MaliciousToken is ERC20 {
    address public gateway;
    bytes32 public savedExternalId;

    constructor(address _gateway, bytes32 _externalId) ERC20("Malicious", "MAL") {
        gateway = _gateway;
        savedExternalId = _externalId;
    }

    function transfer(address to, uint256 amount) public override returns (bool) {
        Gateway(gateway).claimRefund(savedExternalId); // reentrant call
        return true;
    }
}
```

### Mitigation
Reorder the logic in claimRefund so that the state is updated before making external calls:

```solidity
require(refundInfo.externalId != "", "REFUND_NOT_EXIST");

// ✅ Update internal state first
delete refundInfos[externalId];

// ✅ Then call the external token transfer
TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
```
 Or 
Optionally, apply OpenZeppelin's ReentrancyGuard and use the nonReentrant modifier to further mitigate reentrancy risks.
