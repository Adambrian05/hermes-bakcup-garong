# Use of `transferFrom` instead of `safeTransferFrom` fails for some tokens like USDT

### Summary
Some tokens like `USDT` do not return a boolean on successful `transferFrom`, which causes transferring actions in `GatewaySender` to fail when trying to transferFrom those tokens.

### Root Cause
There are multiple places in the `GatewaySender` contract where `transferFrom` is used instead of `safeTransferFrom`:

`GatewaySender::depositAndCall` (with swapData):
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L238-L241
```solidity
           //@audit transferFrom for tokens like USDT don't return a boolean
            require(
                IERC20(fromToken).transferFrom(msg.sender, address(this), amount), 
                "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
            );
```

`GatewaySender::depositAndCall` (without swapData):
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L316-L319
```solidity
           //@audit transferFrom for tokens like USDT don't return a boolean
            require(
                IERC20(asset).transferFrom(msg.sender, address(this), amount),
                "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
            );
```

### Internal Pre-conditions
---

### External Pre-conditions
- `transferFrom` called on a token that does not return a boolean

### Attack Path
- Alice tries to deposit 100 USDT into zetachain
- the `depositAndCall` fails because although the transferFrom is successful there is no boolean returned

### Impact
Some actions in `GatewaySender` (described in root cause) will fail if the deposited asset is a token that does not return a boolean on `transferFrom`.

### PoC
*No response*

### Mitigation
Use `safeTransferFrom`
