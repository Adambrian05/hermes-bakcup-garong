# Every Bitcoin related crosschain sending will be sent to a non desired address due to truncation or leading to tx failures

### Summary

The `GatewayTransferNative.withdraw()` function has a vulnerability where Bitcoin addresses are incorrectly cast to `bytes20`, leading to address truncation. This issue results in corrupted revert messages, which hinder proper refund processing when cross-chain withdrawals to Bitcoin fail. As a consequence, there is a risk of permanently losing funds.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277-L295

### Root Cause

The vulnerability stems from an incorrect assumption that all blockchain addresses follow Ethereum's 20-byte address format. In line 318 of `GatewayTransferNative.sol`, the code performs:

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L291 

Bitcoin addresses have variable lengths and different encoding formats:
- Legacy addresses (P2PKH): ~25-34 characters when base58-encoded
- SegWit addresses (P2WPKH): ~42 characters when bech32-encoded  
- Taproot addresses (P2TR): ~62 characters when bech32m-encoded

Casting these variable-length addresses to `bytes20` (exactly 20 bytes) truncates the address data, corrupting the original Bitcoin address information needed for refunds.

The codebase confirms that `decoded.receiver` is indeed intended to be a Bitcoin address when `decoded.dstChainId == BITCOIN_EDDY` (8332). This is evidenced by several key components:

1. The `DecodedMessage` struct in `SwapDataHelperLib.sol` explicitly states that the receiver field is "compatible for btc/sol/evm":
```solidity
struct DecodedMessage {
    address targetZRC20;
    uint32 dstChainId;
    bytes sender;
    bytes receiver; // compatible for btc/sol/evm
    bytes swapDataZ;
    bytes contractAddress;
    bytes swapDataB;
    bytes accounts;
}
```

2. The `_handleBitcoinWithdraw` function in `GatewayCrossChain.sol` passes `decoded.receiver` directly to the `withdraw` function:
```solidity
function _handleBitcoinWithdraw(
    bytes32 externalId, 
    DecodedMessage memory decoded, 
    uint256 outputAmount,
    uint256 gasFee
) internal {
    if(gasFee >= outputAmount) revert NotEnoughToPayGasFee();
    IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);
    withdraw(
        externalId, 
        decoded.receiver,  // Full Bitcoin address passed here
        decoded.targetZRC20, 
        outputAmount - gasFee
    );
}
```

3. The `withdraw` function in `GatewayZEVM.sol` is designed to handle variable-length addresses through its `bytes memory receiver` parameter:
```solidity
function withdraw(
    bytes memory receiver,
    uint256 amount,
    address zrc20,
    RevertOptions calldata revertOptions
) external whenNotPaused {
    if (receiver.length == 0) revert ZeroAddress();
}
```

This confirms that the system is properly designed to handle different address formats:
- EVM addresses (20 bytes)
- Bitcoin addresses (variable length, 25-62 bytes)
- Solana addresses (variable length)

### Internal Pre-conditions

1. User initiates a cross-chain withdrawal from ZetaChain to Bitcoin using `withdrawToNativeChain()`
2. The withdrawal transaction is processed and calls the internal `withdraw()` function
3. The Bitcoin address (`sender`) gets truncated to 20 bytes in the `revertMessage`
4. The withdrawal fails on the Bitcoin network for any reason (network congestion, insufficient fees, etc.)

### External Pre-conditions

1. Bitcoin network conditions cause the withdrawal to fail or revert
2. The ZetaChain gateway triggers the revert mechanism
3. The `onRevert()` function processes the corrupted revert message containing the truncated Bitcoin address
4. Users cannot claim refunds because the original Bitcoin address is lost

### Attack Path

1. Alice initiates a withdrawal of 10 BTC to Bitcoin address `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4`
2. The withdrawal fails due to Bitcoin network congestion
3. If the withdrawal transaction fails on the Bitcoin network for any reason, the ZetaChain gateway calls the onRevert function in your contract. Due to the address truncation, the refund process fails catastrophically:
4. The revertMessage will have a fixed length of 52 bytes (32 bytes for externalId + 20 bytes for the truncated address).
5. The check if(context.revertMessage.length == 52) on line 571 will incorrectly evaluate to true.
6. The contract then attempts an automatic refund on ZetaChain to an EVM address derived from the truncated, meaningless 20-byte data. These funds are effectively lost.

### Impact

- Permanent loss of user funds when Bitcoin withdrawals fail
