# Non-EVM Refund Claim Without Bot

### Summary

The EVM-centric address validation in `claimRefund()` will cause permanent fund loss for non-EVM users as the protocol requires bot intervention to access refunds for Bitcoin/Solana addresses, creating centralization risk and violating multi-chain design principles.

### Root Cause

In `GatewayCrossChain.sol:575-578` and `GatewayTransferNative.sol:665-668`, the choice to conditionally convert wallet addresses to `address` type only for 20-byte lengths is a mistake as it fails to handle non-EVM addresses (Bitcoin: 25+ bytes, Solana: 32 bytes), forcing exclusive bot dependency for refund access.

### Internal Pre-conditions

- Cross-chain swap to Bitcoin/Solana must fail, triggering `onAbort()`/`onRevert()`
- Refund storage must record a non-EVM address (≠20 bytes) in `refundInfos`
- `bots[msg.sender]` must be false for the original receiver
- Protocol owner must not whitelist user's address as bot


### Attack Path

- User initiates cross-chain transfer to Bitcoin address `bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq `(26 bytes)
- Transaction fails, storing refund with original 26-byte address via `onAbort()`
- User calls `claimRefund()` - reverts at address conversion since 26 ≠ 20
- All authorized bots are temporarily offline/maintenance
- After 90 days, unclaimed refunds are permanently inaccessible

### Impact

Non-EVM users suffer 100% loss of refunded amounts. Protocol permanently locks funds, violating core multi-chain promise.
