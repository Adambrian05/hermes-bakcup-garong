# Missing Input and Target Token Validation Allowing Draining of Unclaimed Refunds

### Summary

In  `GatewayTransferNative::withdrawToNativeChain`, the `_doMixSwap` function performs a swap using Dodo, but if there's no swap data, returns the original input amount:
```solidity
function _doMixSwap(
        bytes memory swapData, 
        uint256 amount, 
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
>>>     if (swapData.length == 0) {
>>>         return amount;
        }
...SNIP...
}
```
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L430-L432

The problem is there's no validation ensuring the `zrc20` input param the user transferred in is the same as the `targetZRC20` when there's no swap being performed. This allows an attacker to deposit a lesser value token and set the targetZRC20 to a high value token. The caveat here is that there must be unclaimed refunds in `GatewayTransferNative::withdrawToNativeChain` of the higher value token for the attack to be possible.

### Root Cause

Note there's another bug I submitted titled, "Missing Verification After Swap Allows Attacker to Drain Unclaimed Refunds", that is similar, but with a different root cause.

The root cause of this issue is missing validation of the `zrc20` input param and `targetZRC20` when there's no swap.

The root cause of the other issue is missing validations of the "swap to" token and the targetZRC20 when there IS a swap.

Both these validations are missing which is why these are two separate issues. 

### Internal Pre-conditions

1. There must be unclaimed refunds in GatewayTransferNative and this tokens must not be the lowest value token of the Zetachain supported assets. 

### External Pre-conditions

N/A

### Attack Path

1. Attacker calls `GatewayTransferNative::withdrawToNativeChain` passing in a low value token (e.g. DAI) as the `zrc20` argument, leaves `DecodedMessage.swapDataZ` empty, but sets `DecodedMessage.tagretZRC20` to the address of the unclaimed refunds (e.g. WBTC).
2. Attacker is able to drain GatewayTransferNative of the WBTC unclaimed refunds.

### Impact

Attacker can drain GatewayTransferNative of unclaimed refunds.

### PoC

_No response_

### Mitigation

Add a check to ensure that if there's no swap, the `zrc20` that the user transferred in when calling `withdrawToNativeChain` is the same as the `targetZRC20`
