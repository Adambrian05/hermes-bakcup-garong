# Non-EVM Refund Receiver Error

### Summary

A critical vulnerability allows any third party to claim refunds intended for users on non-EVM chains (like Bitcoin or Solana) due to a flawed address validation check in the `claimRefund` function.

### Vulnerability Detail

The `claimRefund` function (L286-300) incorrectly determines the refund recipient for non-EVM addresses stored in `refundInfo.walletAddress`. It checks if `walletAddress.length == 20` to cast to an EVM address. For non-EVM addresses (length != 20), this check fails, causing the `receiver` variable to default to `msg.sender`. The subsequent `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");` check is bypassed because `msg.sender == receiver` becomes `msg.sender == msg.sender`, which is always true for any caller not in the `bots` list.

### Impact

Funds intended for users on non-EVM chains that are stored in the `refundInfos` mapping after a transaction revert or abort can be claimed and stolen by any third party who knows the transaction's `externalId`.

### Code Snippet
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661

### Recommendation

Modify `claimRefund` to correctly handle non-EVM addresses. Implement a verification mechanism suitable for non-EVM chains (e.g., authorized claimants/bots for non-EVM refunds) or require a signature verification process that works with the stored `walletAddress` bytes, independent of EVM address casting.
