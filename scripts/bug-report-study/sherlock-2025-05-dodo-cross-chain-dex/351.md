# Any EVM address will steal cross-chain refunds meant for non-EVM users

### Summary

A logic flaw in the `claimRefund()` function allows any Ethereum EOA to steal refunds intended for non-EVM users, such as those on Solana or BTC chains.

This happens because if the `walletAddress` is not 20 bytes, the fallback logic uses `msg.sender` as the refund receiver — even though only whitelisted refund bots are supposed to handle such cases. As non-EVM users cannot call the contract themselves, this design inadvertently grants unauthorized Ethereum addresses the ability to hijack those refunds.

### Root Cause

In [`GatewayCrossChain.sol#L574-L579`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574-L578), the fallback logic does not enforce recipient constraints for non-EVM addresses: 
```solidity
address receiver = msg.sender;
if (refundInfo.walletAddress.length == 20) {
	receiver = address(uint160(bytes20(refundInfo.walletAddress)));
}

require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```

If `walletAddress.length != 20` (e.g., Solana address, 32 bytes), receiver remains as `msg.sender`. The require condition becomes:
```solidity
require(bots[msg.sender] || true) // always passes
```

This effectively allows any Ethereum address to claim the refund, violating the intended invariant that only bots may handle non-EVM refund flows.

### Internal Pre-conditions

1. A refund is triggered (via `onAbort()` or `onRevert()`) with `walletAddress.length != 20`.
2. This refund is stored in `refundInfos[externalId]` on ZetaChain.
3. The intended off-chain refund bot has not yet claimed the refund.

### External Pre-conditions

1. An attacker learns or predicts a valid `externalId` (via logs or coordination).
2. The target `walletAddress` is a 32-byte non-EVM address (e.g., Solana).

### Attack Path

1. A failed cross-chain transaction triggers a refund to a non-EVM address (e.g., solAddress).
2. The attacker observes or guesses the externalId.
3. The attacker (any EVM-based address) calls `claimRefund(externalId)`.
4. Because `walletAddress.length != 20`, the fallback logic sets `receiver = msg.sender`.
5. The `require` statement always passes.
6. The attacker receives the full refund, bypassing the bot-only refund logic.

### Impact

This vulnerability enables unauthorized Ethereum EOAs to unilaterally claim refunds meant for non-EVM recipients. If an attacker discovers a valid externalId, they can receive the full refund amount by exploiting the fallback logic.

Consequences include:
- The intended recipient (e.g., Solana user) loses 100% of the refund.
- The attacker gains the full amount without authorization.
- The cross-chain refund trust model is broken, as only whitelisted bots should process non-EVM refunds.
- This undermines the security boundary between EVM and non-EVM chains, leading to potential loss of user funds and protocol reputation damage.

        assertEq(afterBal - before, initialBalance, "Exploit failed: refund not stolen");
    }

### Mitigation

Strictly separate EVM vs. non-EVM logic:

```solidity
if (refundInfo.walletAddress.length == 20) {
    address receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    require(msg.sender == receiver || bots[msg.sender], "INVALID_CALLER");
} else {
    require(bots[msg.sender], "INVALID_CALLER");
}
```
- Never fallback to `msg.sender` as receiver.
- Enforce bot-only logic for non-EVM addresses.
- Consider emitting events only for off-chain refund handling.
