# _handleEvmOrSolanaWithdraw assumes same entity controls address across chains

### Summary

When  A → ZetaChain → B is performed, through DoDo contracts, any of these operations can fail and this is where Zetachain's onRevert idea comes in to protect the tokens.

But look at this case, you called `GatewaySend.depositAndCall()`, then `GatewayCrossChain.onCall()` will be called and let's say it worked correctly and now it goes to chain B, which is a Polygon or Arbitrum, it doesn't matter. And there `onCall` fails, then `onRevert` on Zetachain will be called. Which `onRevert` exactly to be called and with what is defined when the Outbound tx (Zetachain → chain B) is initiated via `withdrawAndCall`.

`receiver` is passed as `revertMessage` and then this is used inside the `GatewayCrossChain.onRevert` as `receiver`.

This is fine for now, but there is a problem, as the same address is used for the `receiver` in the `onRevert` case and for the recipient on chain B.

The recipient on chain B is inside the message when withdrawAndCall is called, and the same address that was passed to withdrawAndCall is encoded there.

When the `receiver` is a smart wallet or contract, the address will not be the same across all chains. In this case, when `onRevert` is executed, the tokens will be sent to someone else, not the user.

Same issue applies for Zetachain → B inside `GatewayTransferNative.withdrawToNativeChain()`

### Root Cause

Same `receiver` is used for B chain receiver and for receiver inside onRevert on Zetachain.

### Internal Pre-conditions

User to use Smart wallets or contracts for `receiver`.

### External Pre-conditions

None

### Attack Path

None

### Impact

Users will not receive their tokens.

### PoC

N/A

### Mitigation

Await for revertReceiver inside `GatewayCrossChain.onCall` and use it for `onRevert`. This will be passed by the user inside the `payload` when `depositAndCall` is called.
