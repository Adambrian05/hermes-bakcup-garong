# ETH refunds are always lost due to incorrect transfer logic in onRevert

### Summary

GatewaySend [implements](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393) revert handling logic to refund users.  Problem is that function `onRevert` uses ERC20 transfer logic for all asset types, including ETH. When ETH deposits need to be refunded, the function will call the low-level erc20 transfer method on a ETH-placeholder address. That call will succeed, but ETH will actually never leave the `GatewaySend` contract. User effectively loses all initially deposited ETH.

### Root Cause

GaewaySend implements `onRevert` to handle reverts and refund the user.  Problem is that `onRevert` function always uses [TransferHelper.safeTransfer](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L396) regardless of asset type:
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    address sender = address(uint160(bytes20(context.revertMessage[32:])));
    TransferHelper.safeTransfer(context.asset, sender, context.amount); // Always ERC20 logic
    // ...
}
```

For ETH refunds, `context.asset` is address(0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE). The [safeTransfer](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L12) function executes low-level erc20-transfer:
```solidity
function safeTransfer(address token, address to, uint value) internal {
    (bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
    require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
}
```

When low-level call is done on an address with no-code, call will be successful and return nothing. So `safeTransfer` function will report successfully transferring ETH, even though no ETH was moved. Thus ETH will stay stuck in the `GatewaySend` contract, while user will not be refunded, losing their original deposit.


### Internal Pre-conditions

User deposits ETH via `GatewaySend`

### External Pre-conditions

Cross-chain TX needs to fail on Zeta chain. That can happen due to a lot of different reasons. That's why revert mechanism is in place to make sure funds are never lost.

### Attack Path

1. User deposits ETH using `GatewaySend`'s `depositAndCall`
2. Cross-chain TX reverts on ZetaChain (ie. due to slippage while swapping)
3. Protocol triggers refund mechanism by calling `GatewayEVM`'s `executeRevert` on the source chain
4. `GatewayEVM` calls `GatewaySend`'s `onRevert`
5. `onRevert` will try to move token address(0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE), instead of doing proper ETH transfer
6. `onRevert` TX is successful, however user never gets their ETH back

### Impact

High severity - this vulnerability causes direct loss of funds for user

### PoC

_No response_

### Mitigation

Distinguish between ETH and ERC20 refunds, and use appropriate way to transfer ETH back to users
