# withdrawToNativeChain can't be used with NATIVE

### Summary

When a Zetachain → B transfer is initiated, either as part of A → Zetachain → B (`GatewayCrossChain`) or ZetaChain → B (`GatewayTransferNative`), the NATIVE Zeta token can be the input token.

For `GatewayTransferNative.withdrawToNativeChain()` you can pass the placeholder `0xEeEeEe`… if you want to use native zeta.

For `GatewayCrossChain` you will need to transfer ZETA from the connected chain and then `GatewayZEVM` will transfer native via (`depositAndCall` for Native and `_transferZETA`).

But there is a problem, because both `withdrawToNativeChain()` and `GatewayCrossChain.onCall` assume that the input token is WZETA and the functions will fail.

Inside `withdrawToNativeChain`, if pass zrc20 = `0xEeEeEe`…, no erc20 tokens will be transferred, but then `_handleFeeTransfer` only works with erc20 and will fail for NATIVE.

function _handleFeeTransfer(
    address zrc20,
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%

Inside `GatewayCrossChain.onCall` it is the same, the differences are that for `withdrawToNativeChain` the tx will be reverted from the blockchain and nothing will happen, just NATIVE case is not possible. For `GatewayCrossChain` `onCall` will revert, and `onRevert` in `GatewaySend` will always be called.

### Root Cause

`_handleFeeTransfer` assumes that `zrc20` is always erc20.

### Internal Pre-conditions

NATIVE ZETA to be used.

### External Pre-conditions

None

### Attack Path

None

### Impact

NATIVE Zeta cannot be used as input token.

### PoC

N/A

### Mitigation

Either do the fee with native as well, or always wrap Native at the beginning of `withdrawToNativeChain` and `GatewayCrossChain.onCall`.
