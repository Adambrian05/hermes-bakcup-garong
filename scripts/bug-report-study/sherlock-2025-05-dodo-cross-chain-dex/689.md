# Insufficient Input Validation in Message Decoding

### Summary

The message decoding functions in SwapDataHelperLib.sol lack comprehensive input validation, allowing malformed or malicious messages to be processed without proper verification of critical parameters such as addresses, chain IDs, and array bounds.


### Root Cause

The vulnerability exists primarily in the [`decodeMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/SwapDataHelperLib.sol#L56) and [`decodeNativeMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/SwapDataHelperLib.sol#L112) functions within SwapDataHelperLib.sol, which are responsible for parsing complex message structures used in cross-chain operations. These functions perform assembly-level data extraction without implementing adequate validation checks on the decoded parameters, creating potential attack vectors for malicious actors.

The vulnerable code pattern is evident in the `decodeMessage` function:

```solidity
function decodeMessage(
    bytes calldata message
) internal pure returns (DecodedMessage memory, MixSwapParams memory) {
    uint32 dstChainId;
    address targetZRC20;
    uint16 senderLen;
    uint16 receiverLen;
    uint16 swapDataZLen;
    uint16 contractAddressLen;
    uint16 swapDataBLen;
    uint16 accountsLen;

    assembly {
        dstChainId := shr(224, calldataload(message.offset))
        targetZRC20 := shr(96, calldataload(add(message.offset, 4)))
        senderLen := shr(240, calldataload(add(message.offset, 24)))
        receiverLen := shr(240, calldataload(add(message.offset, 26)))
        // ... additional length extractions
    }
    
    // No validation of extracted parameters
    uint offset = 36;
    bytes calldata sender = message[offset : offset + senderLen];
    // ... continued without bounds checking
}
```

The security issues manifest in several ways. First, there is no validation that the `targetZRC20` address is non-zero or corresponds to a supported token. This could lead to operations being attempted on invalid or malicious token contracts. Second, the `dstChainId` parameter is not validated against a whitelist of supported chains, potentially allowing operations targeting unsupported or malicious networks.

Third, the length parameters (`senderLen`, `receiverLen`, etc.) are not bounded, which could lead to out-of-bounds memory access or excessive gas consumption if extremely large values are provided. The function assumes that the provided lengths are reasonable and that sufficient data exists in the message to satisfy the specified lengths.

The vulnerability extends to the array processing in `decodeCompressedMixSwapParams`, where dynamic arrays are constructed based on user-provided length values without validation:

```solidity
uint8 adapterLen = uint8(data[offset]);
offset += 1;
address[] memory mixAdapters = new address[](adapterLen);
for (uint i = 0; i < adapterLen; ++i) {
    address a;
    assembly {
        a := shr(96, calldataload(add(data.offset, offset)))
    }
    mixAdapters[i] = a; // No validation of address
    offset += 20;
}
```

This pattern repeats for multiple array types without validating that the addresses are non-zero or that the array lengths are within reasonable bounds. An attacker could craft messages with extremely large array lengths, causing excessive gas consumption or memory allocation failures.

The root cause of this vulnerability is the assumption that input data is well-formed and trustworthy. In a cross-chain environment where messages can originate from various sources and pass through multiple intermediaries, this assumption is dangerous and violates the principle of defensive programming.

### Internal Pre-conditions

No need for additional internal pre-conditions.

### External Pre-conditions

1. Denial of service attacks could be executed by sending messages with extremely large array lengths or invalid parameters that cause functions to consume excessive gas or fail unexpectedly.

2. Contract state corruption could occur when invalid addresses or chain IDs are processed without validation. For example, if a zero address is used as `targetZRC20`, subsequent operations might fail in unexpected ways, potentially leaving the contract in an inconsistent state. Similarly, invalid chain IDs could cause cross-chain operations to be routed incorrectly or fail silently.


### Attack Path

Test (Attack) scenarios include:

1. **Zero Address Test**: Submit messages with zero addresses for critical parameters
2. **Invalid Chain ID Test**: Use unsupported or zero chain IDs
3. **Oversized Array Test**: Provide extremely large array lengths to cause gas exhaustion
4. **Malformed Length Test**: Provide length values that exceed the actual message size
5. **Edge Case Test**: Test boundary conditions and unusual parameter combinations

### Impact

The medium impact assessment reflects the potential for various forms of protocol disruption and unexpected behavior, though direct fund loss is less likely than in the previous vulnerabilities. The primary impact vectors include denial of service attacks, contract state corruption, and potential bypass of security mechanisms.

Denial of service attacks could be executed by sending messages with extremely large array lengths or invalid parameters that cause functions to consume excessive gas or fail unexpectedly. This could disrupt the cross-chain operation flow and prevent legitimate users from completing their transactions. In a high-volume environment, such attacks could significantly impact protocol availability and user experience.

Contract state corruption could occur when invalid addresses or chain IDs are processed without validation. For example, if a zero address is used as `targetZRC20`, subsequent operations might fail in unexpected ways, potentially leaving the contract in an inconsistent state. Similarly, invalid chain IDs could cause cross-chain operations to be routed incorrectly or fail silently.

The vulnerability could also be exploited to bypass certain security checks or fee calculations. If message parameters are crafted to exploit edge cases in the validation logic, attackers might be able to reduce fees, manipulate swap outcomes, or trigger unintended code paths that were not thoroughly tested.

While direct fund theft is less likely with this vulnerability alone, it could be combined with other vulnerabilities to create more sophisticated attack vectors. The lack of input validation creates a broader attack surface that could be exploited in conjunction with other protocol weaknesses.

### Mitigation

Implement comprehensive input validation throughout the message decoding process:

```diff
function decodeMessage(
    bytes calldata message
) internal pure returns (DecodedMessage memory, MixSwapParams memory) {
+   require(message.length >= 36, "Message too short");
    
    uint32 dstChainId;
    address targetZRC20;
    uint16 senderLen;
    uint16 receiverLen;
    uint16 swapDataZLen;
    uint16 contractAddressLen;
    uint16 swapDataBLen;
    uint16 accountsLen;

    assembly {
        dstChainId := shr(224, calldataload(message.offset))
        targetZRC20 := shr(96, calldataload(add(message.offset, 4)))
        senderLen := shr(240, calldataload(add(message.offset, 24)))
        receiverLen := shr(240, calldataload(add(message.offset, 26)))
        swapDataZLen := shr(240, calldataload(add(message.offset, 28)))
        contractAddressLen := shr(240, calldataload(add(message.offset, 30)))
        swapDataBLen := shr(240, calldataload(add(message.offset, 32)))
        accountsLen := shr(240, calldataload(add(message.offset, 34)))
    }
    
+   // Validate critical parameters
+   require(targetZRC20 != address(0), "Invalid target token");
+   require(isValidChainId(dstChainId), "Unsupported chain ID");
+   require(senderLen > 0 && senderLen <= 100, "Invalid sender length");
+   require(receiverLen > 0 && receiverLen <= 100, "Invalid receiver length");
+   
+   // Validate total message length
+   uint256 expectedLength = 36 + senderLen + receiverLen + swapDataZLen + 
+                           contractAddressLen + swapDataBLen + accountsLen;
+   require(message.length >= expectedLength, "Insufficient message data");
    
    uint offset = 36;
    bytes calldata sender = message[offset : offset + senderLen];
    // ... rest of implementation
}

function isValidChainId(uint32 chainId) internal pure returns (bool) {
    return chainId == 8332 || // BITCOIN_EDDY
           chainId == 1399811149 || // SOLANA_EDDY
           chainId == 7000 || // ZETACHAIN
           chainId == 1 || // Ethereum
           chainId == 137 || // Polygon
           chainId == 42161 || // Arbitrum
           chainId == 8453 || // Base
           chainId == 56; // BNB Chain
}
```
