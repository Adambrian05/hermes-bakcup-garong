# Unauthorized Non-EOA Refund Claims Bypassing Off-Chain Bot Processing

### Summary

###  Are there any off-chain mechanisms involved in the protocol (e.g., keeper bots, arbitrage bots, etc.)? We assume these mechanisms will not misbehave, delay, or go offline unless otherwise specified.
If the receiver of refund info is not an EOA address, refund bots collect the tokens and process the refund manually.

The current implementation of [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661) in both the `GatewayTransferNative.sol` and `GatewayCrossChain.sol` does not specifically enforce non-EOA from not claiming the refunds themselves as if `refundInfo.walletAddress.length !=20` the receiver defaults to `msg.sender` allowing the require statement to pass.

### Root Cause

In the below
```solidity
address receiver = msg.sender;
if(refundInfo.walletAddress.length == 20) {
    receiver = address(uint160(bytes20(refundInfo.walletAddress)));
}
  ```
If `refundInfo.walletAddress` is unset  or invalid (not 20 bytes), receiver defaults to msg.sender, allowing any caller (including non-EOAs) to set themselves as the recipient.

```solidity
  require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```
When `receiver = msg.sender`, the condition msg.sender == receiver is always true, permitting any non-EOA to call without being a bot or the intended recipient.

NIL

### External Pre-conditions

1. A non-EOA account (smart contract) with a refund attempts to `claimRefund`.
2. the check  `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");` passes bypassing protocol assumption

### Attack Path

1. A user/non-EOA account (smart contract) with a refund attempts to `claimRefund`.
2. the check  `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");` passes bypassing protocol assumption of allowing refund bots to claim refund and process them manually

### Impact

1. Tokens may be sent to incompatible non-EOA contract (e.g., one without token withdrawal logic), potentially locking funds and preventing the intended recipient from receiving the refund

2. Undermines the protocol’s design, particularly for non-EOA receivers.
