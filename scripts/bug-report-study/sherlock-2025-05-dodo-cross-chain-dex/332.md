# The `_handleFeeTransfer` function does not account for the assumption that the `zrc20` address could belong to the native token

## Vulnerability Details
The `_handleFeeTransfer` function in both the `GatewayTransferNative` and `GatewayCrossChain` contracts takes a `zrc20` address as input and transfers the fee amount of `zrc20` tokens to the `EddyTreasurySafe` address. The transfer is performed using the `TransferHelper::safeTransfer` function, which is intended for transferring tokens rather than the native blockchain currency. To transfer native tokens, the `TransferHelper::safeTransferETH` function should be used. 
If the `zrc20` input address is `_ETH_ADDRESS_`, the `_handleFeeTransfer` function will revert because it attempts to use `safeTransfer` for a native token transfer, which is incorrect. ([link](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L346))

```solidity
  function _handleFeeTransfer(
      address zrc20,
      uint256 amount
  ) internal returns (uint256 platformFeesForTx) {
      platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
@>    TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
  }
```

One instance where `_handleFeeTransfer` is used is in the `GatewayTransferNative::withdrawToNativeChain` function, which accepts the native token as the `zrc20` input. This indicates that the `zrc20` parameter can sometimes represent the native token itself.

## POC
The `GatewayTransferNative::withdrawToNativeChain` function has some other issues that I reported elsewhere. However, to test the internal `_handleFeeTransfer` function separately, I created a helper function. I tested it once with a ZRC20 token and once with a native token. It pass the first one but failed the second.
Copy the test bellow to the `GatewayTransferNative.t.sol` file.

```solidity
  import {TransferHelper} from "../contracts/libraries/TransferHelper.sol";
  function handleFeeTransfer(
      address zrc20,
      uint256 amount
  ) public returns (uint256 platformFeesForTx) {
      // @auditor: I used an exact same logic of _handleFeeTransfer
      uint256 feePercent = 10; // 1% fee
      platformFeesForTx = (amount * feePercent) / 1000;
      TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
  }

  function testHandleFee() external {
      vm.startPrank(user1);
      uint256 resultToken = handleFeeTransfer(address(token1Z), 100 ether);
      vm.stopPrank();
      assertEq(resultToken, 1 ether);

      vm.startPrank(user1);
      // @auditor: This one fails
      uint256 resultNative = handleFeeTransfer(_ETH_ADDRESS_, 100 ether);
      vm.stopPrank();
  }
```

## Impact
If users invoke the `GatewayTransferNative::withdrawToNativeChain` function and pass the native token as input for `zrc20`, the transaction will revert due to incorrect assumptions in the `_handleFeeTransfer` implementation.

## Mitigation
Consider modifying the `_handleFeeTransfer` function to correctly handle the case when `zrc20` is the native token, such as by checking if `zrc20` equals `_ETH_ADDRESS_` and using `TransferHelper::safeTransferETH` instead of `safeTransfer` in that scenario.

```diff
  function _handleFeeTransfer(
      address zrc20,
      uint256 amount
  ) internal returns (uint256 platformFeesForTx) {
      platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
-     TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+     if(zrc20 == _ETH_ADDRESS_) {
+         TransferHelper.safeTransferETH(EddyTreasurySafe, platformFeesForTx);
+     } else {
+         TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+     }
    }
```
