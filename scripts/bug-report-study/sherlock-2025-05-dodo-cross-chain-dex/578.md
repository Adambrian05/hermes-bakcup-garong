# `GatewayTransferNative.onRevert` Misdirects Refunds for 20-Byte Bitcoin Addresses to Invalid EVM Addresses

### Summary

The [`GatewayTransferNative.withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530) function allows initiating withdrawals to Bitcoin addresses, which can have varying formats and lengths. For example shorter 20-byte hashes like P2PKH, or longer representations for formats like Bech32 which are 32 bytes. When such a withdrawal fails, the `revertMessage` passed to `GatewayTransferNative.onRevert` is constructed using a 20-byte segment derived from the initial Bitcoin address. If this `revertMessage` is 52 bytes long, the `onRevert` function incorrectly interprets this 20-byte segment as an EVM address. It then attempts a direct ZRC20 token transfer to this wrongly derived, invalid EVM address. This results in user funds being permanently lost and bypasses the intended bot-assisted refund mechanism via `refundInfos`.

### Root Cause

The bug originates from how `GatewayTransferNative` constructs the `revertMessage` for Bitcoin withdrawals and how `onRevert` subsequently processes it.

1.  **Initiation via `withdrawToNativeChain` and `_handleBitcoinWithdraw`:** A user calls `withdrawToNativeChain` specifying a Bitcoin destination (`decoded.dstChainId == BITCOIN_EDDY`). This path calls `_handleBitcoinWithdraw`.

    ```solidity
    function _handleBitcoinWithdraw(
        bytes32 externalId,
        DecodedMessage memory decoded, // decoded.receiver is the full Bitcoin address in bytes
        uint256 outputAmount,
        uint256 gasFee
    ) internal {
        if (gasFee >= outputAmount) revert NotEnoughToPayGasFee();
        IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);
        // Calls the internal withdraw function
        withdraw(externalId, decoded.receiver, decoded.targetZRC20, outputAmount - gasFee); 
    }
    ```

    The `decoded.receiver` here is the `bytes` representation of the user's full Bitcoin address.

2.  **`revertMessage` Construction in Internal `withdraw` Function:** The `withdraw` function is called by `_handleBitcoinWithdraw`. It prepares `RevertOptions` for the actual `gateway.withdraw` call:
    ```solidity
    function withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount) public { 
        gateway.withdraw(
            sender, // The full Bitcoin address bytes
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                // This results in a 52-byte revertMessage.
                revertMessage: bytes.concat(externalId, bytes20(sender)), 
                onRevertGasLimit: gasLimit 
            })
        );
    }
    ```
    The `revertMessage` is constructed as `bytes.concat(externalId, bytes20(sender))`. `bytes20(sender)`. This results in a `revertMessage` that `32 + 20 = 52 bytes` long when the withdrawal is for Bitcoin 20 bytes address.

3.  **Flawed Conditional Logic in `onRevert`:**
    When the ZetaChain gateway calls `GatewayTransferNative.onRevert` due to a failed withdrawal:

    ```solidity
    function onRevert(
        RevertContext calldata context
    ) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:]; // This is the 20-byte truncated segment

        if (context.revertMessage.length == 52) { // @audit This condition is ALWAYS met for Bitcoin reverts from internal withdraw
            // @audit walletAddress (truncated Bitcoin segment) is cast to EVM address
            address receiver = address(uint160(bytes20(walletAddress))); 
            // @audit Refund sent to invalid EVM address
            TransferHelper.safeTransfer(context.asset, receiver, context.amount); 

            emit EddyCrossChainRevert(externalId, context.asset, context.amount, walletAddress);
        } else {
            // This block is intended for other non-EVM addresses or complex cases,
            // but Bitcoin refunds are incorrectly caught by the if block.
            RefundInfo memory refundInfo = RefundInfo({ /* ... */ });
            refundInfos[externalId] = refundInfo;
            emit EddyCrossChainRefund(externalId, context.asset, context.amount, walletAddress);
        }
    }
    ```
    *   The condition `if (context.revertMessage.length == 52)` is always met for Bitcoin refunds originating from the internal `withdraw` function.
    *   The code then incorrectly assumes `walletAddress` (the 20-byte truncated segment of the original Bitcoin address) is an EVM address by casting `bytes20(walletAddress)` to `address`.
    *   `TransferHelper.safeTransfer` sends the ZRC20 refund to this derived, invalid EVM address.
    *   The `else` block, intended for bot-assisted manual refunds, is bypassed for all Bitcoin refunds.

### Internal Pre-conditions

1.  `GatewayTransferNative` contract is operational and holds the ZRC20 tokens to be refunded (`context.asset`).

### External Pre-conditions

1.  A user calls `GatewayTransferNative.withdrawToNativeChain` with `decoded.dstChainId = BITCOIN_EDDY` and `decoded.receiver` as their full Bitcoin address.
2.  The cross-chain operation fails for any reason.
3.  The ZetaChain gateway calls `GatewayTransferNative.onRevert` with the `context.revertMessage` constructed as 52 bytes (externalId + 20-byte of Bitcoin address).

### Attack Path

1.  **User Initiates Withdrawal:** User calls `withdrawToNativeChain` to send `1 ZRC20_BTC` to their Bitcoin address `1J8WJh8ygFsA93iayVocwsWjfkLSgyqozS` (P2PKH 20 bytes `bbe5833e357fe53698a1082295d3679598837477`)
2.  **`GatewayTransferNative` Processing:**
    *   `withdrawToNativeChain` calls `_handleBitcoinWithdraw`.
    *   `_handleBitcoinWithdraw` calls the internal `withdraw`.
    *   The internal `withdraw` prepares `RevertOptions`. `revertMessage` becomes `bytes.concat(externalId, bytes20(bytes("bbe5833e357fe53698a1082295d3679598837477")))`. 
3.  **Withdrawal Failure:** The Cross-chain operation fails for any reason.
4.  **`onRevert` Triggered:** ZetaChain's gateway calls `GatewayTransferNative.onRevert`.
    *   `context.revertMessage.length` is 52. The `if` branch is taken.
    *   `walletAddress` becomes the 20-byte truncated segment.
    *   `address receiver = address(uint160(bytes20(walletAddress)));` converts this segment into an EVM address, `evmAddrFromTruncatedBtc`.
    *   `TransferHelper.safeTransfer(context.asset, evmAddrFromTruncatedBtc, context.amount);` sends the `1 ZRC20_BTC` refund to this address.
5.  **Outcome:** The user's `ZRC20_BTC` refund is sent to an EVM address derived from a truncated part of their Bitcoin address. These funds are unrecoverable. The `refundInfos` map is not populated.

### Impact

Direct and permanent loss of user funds for all failed Bitcoin withdrawals processed by `GatewayTransferNative`. Refunded ZRC20 tokens are sent to an inaccessible EVM-style address derived from a (potentially truncated) segment of the Bitcoin address, completely bypassing the intended `refundInfos` mechanism for non-EVM addresses.

### Mitigation

The `onRevert` function in `GatewayTransferNative` must not assume that a 52-byte `revertMessage` implies the last 20 bytes are a standard EVM recipient address, especially when the original transaction involved a non-EVM chain like Bitcoin.
