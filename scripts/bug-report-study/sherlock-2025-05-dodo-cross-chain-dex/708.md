# transfer instead of call can block gnosis wallets and cause loss of funds

### Summary

using transfer instead of call will cause AA wallets, multisigs, and smart contracts to not be able to receive their funds on the EVM chains and will end up losing them. The reason is that Gnosis Safe emits the event `receive` function, which will exceed the 2300 gas forwarded with the transfer :

[[Gnosis](https://github.com/safe-global/safe-smart-account/blob/3f6b83280392ccae0b2b981403322a041faa560a/contracts/common/NativeCurrencyPaymentFallback.sol#L14-L16)](https://github.com/safe-global/safe-smart-account/blob/3f6b83280392ccae0b2b981403322a041faa560a/contracts/common/NativeCurrencyPaymentFallback.sol#L14-L16)

```solidity
abstract contract NativeCurrencyPaymentFallback is INativeCurrencyPaymentFallback {
    /**
     * @inheritdoc INativeCurrencyPaymentFallback
     */
    receive() external payable override {
        emit SafeReceived(msg.sender, msg.value);
    }
}
```

transfer is invoked when Outbound CCTX is processed and finalized by calling the `onCall` function of the [`[GatewaySend](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-blckhv/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L341-L371)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-blckhv/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L341-L371):

```solidity
function onCall(
    MessageContext calldata /*context*/,
    bytes calldata message
) external payable onlyGateway returns (bytes4) {
    (
        bytes32 externalId,
        uint256 amount,
        bytes calldata recipient,
        address fromToken,
        address toToken,
        bytes calldata swapData
    ) = decodePackedMessage(message);

    bool fromIsETH = (fromToken == _ETH_ADDRESS_);
    bool toIsETH = (toToken == _ETH_ADDRESS_);
    address evmWalletAddress = address(bytes20(recipient));

    if(!fromIsETH) {
        IERC20(fromToken).transferFrom(msg.sender, address(this), amount);
    }

    uint256 outputAmount;
    if(fromToken == toToken) {
        outputAmount = amount;
    } else {
        outputAmount = _doMixSwap(swapData);
    }

    if(toIsETH) {
        payable(evmWalletAddress).transfer(outputAmount);//<-----
    } else {
        IERC20(toToken).transfer(evmWalletAddress, outputAmount);
    }

    emit EddyCrossChainReceive(
        externalId,
        fromToken,
        toToken,
        amount,
        outputAmount,
        evmWalletAddress,
        message
    );

    return "";
}
```

### Root Cause

The wrong native transfer function is invoked, limiting the forwarded gas only to 2300, thus resulting in limited subjects being able to receive their bridged funds.

### Internal Pre-conditions

`toIsETH = true`, which is a normal user operation, when it’s required to receive native funds on the EVM chain.

### External Pre-conditions

`evmWalletAddress` to be one of the above-mentioned recipients.

### Attack Path

Normal user operation, which requires native funds to be settled on the destination chain’s receiver.

Let’s say we want to bridge ETH from ZEVM to ETH and supply to AAVE. We initiate `withdrawAndCall` from `GatewayZEVM`, then `GatewayEVM::execute` is invoked which sends the Native tokens to `GatewaySend` passes the data to `GatewaySend::onCall`, where `toIsEth = true`:

```solidity

```

When `evmWalletAddress`'s `receive` is invoked it will be reverting always when there’s a single line of code inside it, making the transaction to be reverted to `ZEVM` and user losing the opportunity.  

### Impact

Inability to send native tokens to AA [wallet](https://etherscan.io/address/0xd1e6626310fd54eceb5b9a51da2ec329d6d4b68a#code)s, multisigs, and contracts that have logic in their `receive` function. Even a single event emitted will exceed the 2300 gas limit. This will prevent integrators from having a nested logic in the recipients.
