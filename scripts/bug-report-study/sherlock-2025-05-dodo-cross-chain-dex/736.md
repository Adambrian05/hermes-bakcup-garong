# Incorrect validation logic in the `claimRefund` function allows unauthorized users to claim refunds when `revertMessage` contains a non-20-byte `walletAddress`

## Summary
The incorrect validation in `claimRefund` for non-20-byte `walletAddress` from non-EVM chains (e.g., Bitcoin, Solana) will cause unauthorized access to refundable funds for any user as an attacker will claim refunds by providing an existing `externalId`.

## Root Cause
In `GatewayCrossChain.sol:claimRefund`, the validation logic for `INVALID_CALLER` (`require(bots[msg.sender] || msg.sender == receiver)`) incorrectly sets `receiver = msg.sender` when `refundInfo.walletAddress.length != 20`, allowing any caller to claim refunds for non-EVM chain addresses (e.g., Bitcoin, Solana) without proper authorization.

[GatewayCrossChain.claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L571)

## Internal Pre-conditions
1. A legitimate user needs to initiate a cross-chain swap from ZetaChain to Chain B (e.g., Bitcoin or Solana) via `depositAndCall`, resulting in a revert on Chain B, triggering `onRevert` on ZetaChain.
2. The `revertMessage` passed to `onRevert` on ZetaChain must include a non-20-byte `walletAddress` (e.g., 34-byte Bitcoin address or 32-byte Solana public key), causing `refundInfos` to store an invalid `walletAddress`.
3. The legitimate user’s `externalId` must be known to the attacker (e.g., through monitoring `EddyCrossChainRefund` events).

## External Pre-conditions
1. The cross-chain swap must target a non-EVM chain (e.g., Bitcoin or Solana) that uses non-20-byte address formats, resulting in a `revertMessage` with a length other than 52 bytes (e.g., 32-byte `externalId` + 34-byte Bitcoin address).

## Attack Path
1. A legitimate user initiates a cross-chain swap from ZetaChain to a non-EVM Chain B (e.g., Bitcoin or Solana) via `depositAndCall`, which reverts on Chain B (e.g., due to a failed swap operation).
2. The revert on Chain B triggers `onRevert` on ZetaChain, receiving a `revertMessage` with a non-20-byte `walletAddress` (e.g., 34-byte Bitcoin address or 32-byte Solana public key), causing `context.revertMessage.length != 52`.
3. In `onRevert`, the condition `context.revertMessage.length == 52` fails, so `refundInfos` stores a `RefundInfo` with a `walletAddress` that is not 20 bytes (e.g., 34 bytes).
4. An attacker monitors `EddyCrossChainRefund` events to identify the `externalId` associated with the legitimate user’s refund.
5. The attacker calls `claimRefund` with the `externalId` on ZetaChain. Since `refundInfo.walletAddress.length != 20`, `receiver` is set to `msg.sender` (the attacker’s address).
6. The `INVALID_CALLER` check passes because `msg.sender == receiver`, allowing the attacker to claim the legitimate user’s refundable funds.

## Impact
The legitimate user cannot claim their refundable funds, as any user can call `claimRefund` with the `externalId` and receive the funds due to incorrect validation of non-20-byte `walletAddress` from non-EVM chains. This renders the refund mechanism useless for cross-chain swaps to non-EVM chains and 100% loss of the refund amount.

## Mitigation
 **Fix Validation Logic in `claimRefund`**: Modify `claimRefund` to enforce stricter validation for EVM and non-EVM addresses. For 20-byte `walletAddress`, require `msg.sender` to match the address; for non-20-byte `walletAddress`, require `msg.sender` to be an authorized bot:
   ```solidity
   function claimRefund(bytes32 externalId) external {
       RefundInfo storage refundInfo = refundInfos[externalId];
       address receiver = msg.sender;
       if (refundInfo.walletAddress.length == 20) {
           receiver = address(uint160(bytes20(refundInfo.walletAddress)));
           require(msg.sender == receiver, "INVALID_CALLER_EVM");
       } else {
           require(bots[msg.sender], "INVALID_CALLER_NON_EVM");
       }
       require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
       TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
       delete refundInfos[externalId];
       emit EddyCrossChainRefundClaimed(externalId, refundInfo.token, refundInfo.amount, abi.encodePacked(msg.sender));
   }
   ```
