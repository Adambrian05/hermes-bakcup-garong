# Integer Overflow Risk in Fee Calculations

### Summary

The fee calculation mechanism in the `_handleFeeTransfer` function is vulnerable to integer overflow when processing large token amounts, potentially resulting in incorrect fee collection or transaction failures.

### Root Cause

The vulnerability exists in the fee calculation logic implemented across multiple contracts, specifically in the `_handleFeeTransfer` function found in both [GatewayCrossChain.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L297) and [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L341). The issue stems from the multiplication of large token amounts with fee percentages without proper overflow protection, which could lead to arithmetic overflow in extreme cases.

The vulnerable code pattern is:

```solidity
function _handleFeeTransfer(address zrc20, uint256 amount) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
    TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
}
```

The security issue manifests when dealing with tokens that have large decimal places or when processing extremely large transaction amounts. For tokens with 18 decimal places, amounts can reach values close to the maximum uint256 value (2^256 - 1). When such large amounts are multiplied by the fee percentage, the result could exceed the maximum representable value in uint256, causing an arithmetic overflow.

In Solidity versions 0.8.0 and above, arithmetic operations automatically check for overflow and revert the transaction if an overflow occurs. While this prevents silent overflow corruption, it creates a denial of service vulnerability where legitimate large transactions would fail due to the overflow in fee calculation, even though the fee amount itself might be reasonable.

The vulnerability is exacerbated by the lack of bounds checking on the `feePercent` parameter. Although the contract documentation suggests a fee of 0.5% (5 basis points), there are no explicit constraints preventing the owner from setting extremely high fee percentages that would increase the likelihood of overflow conditions.

The execution path leading to this vulnerability begins when a user initiates a large cross-chain transaction. The contract calculates platform fees by multiplying the transaction amount by the fee percentage. If this multiplication exceeds uint256 maximum value, the transaction reverts, preventing the user from completing their intended operation despite having sufficient funds and valid parameters.

This vulnerability is particularly concerning for tokens with high decimal precision or for protocols that might handle institutional-level transaction volumes. The cross-chain nature of the protocol means that failed transactions could result in funds being locked on one chain while the corresponding operation on the destination chain fails to complete.

### Internal Pre-conditions

No specific pre-conditions required.

### External Pre-conditions

The overflow condition requires extremely large transaction amounts combined with fee percentages that result in multiplication results exceeding uint256 maximum value. For most practical scenarios with reasonable fee percentages (0.1% to 1%), the transaction amounts would need to be astronomically large to trigger overflow.

However, the likelihood increases with certain factors. Tokens with very high decimal precision (18+ decimals) create larger numerical values that are more susceptible to overflow. Additionally, if the protocol expands to support tokens with unusual decimal configurations or if fee percentages are set higher than anticipated, the risk of overflow increases.

The technical complexity of triggering this vulnerability is low, as it simply requires submitting a transaction with a sufficiently large amount. However, the practical difficulty lies in accumulating such large amounts of tokens, which limits the likelihood of accidental triggering by regular users.

### Impact

The high impact assessment is justified by the potential for significant disruption to protocol operations and user experience, particularly for high-value transactions. While the vulnerability does not directly enable fund theft due to Solidity's automatic overflow protection, it creates a denial of service condition that could affect the protocol's usability and reliability.

The primary impact is the inability to process large legitimate transactions, which could severely limit the protocol's utility for institutional users or high-net-worth individuals. In the competitive DeFi landscape, protocols that cannot handle large transactions reliably may lose significant market share to more robust alternatives.

The impact extends to the protocol's reputation and trustworthiness. Users who experience transaction failures due to overflow issues may lose confidence in the protocol's technical competence, leading to reduced adoption and potential migration to competing platforms. This is particularly damaging in the cross-chain space where technical reliability is paramount.

From an operational perspective, the vulnerability could create customer support burdens as users struggle to understand why their transactions are failing. The technical nature of integer overflow makes it difficult for non-technical users to comprehend the issue, potentially leading to frustration and negative user experiences.

The vulnerability also has implications for the protocol's fee collection mechanism. If large transactions consistently fail due to overflow, the protocol loses potential fee revenue from high-value operations, which could impact the economic sustainability of the platform.

### Mitigation

Implement safe arithmetic operations using OpenZeppelin's SafeMath library or built-in overflow checks:

```diff
+ import "@openzeppelin/contracts/utils/math/SafeMath.sol";

contract GatewayCrossChain {
+   using SafeMath for uint256;
    
    function _handleFeeTransfer(address zrc20, uint256 amount) internal returns (uint256 platformFeesForTx) {
+       // Add bounds checking for fee percentage
+       require(feePercent <= 1000, "Fee percentage too high"); // Max 100%
+       
+       // Use safe multiplication to prevent overflow
+       uint256 feeNumerator = amount.mul(feePercent);
+       platformFeesForTx = feeNumerator.div(1000);
+       
+       // Alternative: Check for overflow before calculation
+       require(amount <= type(uint256).max / feePercent, "Amount too large for fee calculation");
        
-       platformFeesForTx = (amount * feePercent) / 1000;
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
    
+   function setFeePercent(uint256 _feePercent) external onlyOwner {
+       require(_feePercent <= 100, "Fee percentage cannot exceed 10%"); // Reasonable upper bound
+       feePercent = _feePercent;
+       emit FeePercentUpdated(_feePercent);
+   }
}
```

For Solidity 0.8.0+, implement explicit overflow checking:

```solidity
function _handleFeeTransfer(address zrc20, uint256 amount) internal returns (uint256 platformFeesForTx) {
    require(feePercent <= 1000, "Fee percentage too high");
    
    // Check for multiplication overflow
    if (amount > 0 && feePercent > type(uint256).max / amount) {
        revert("Fee calculation would overflow");
    }
    
    platformFeesForTx = (amount * feePercent) / 1000;
    TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
}
```
