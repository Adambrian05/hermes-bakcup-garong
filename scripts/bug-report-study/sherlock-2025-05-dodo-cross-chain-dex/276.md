# Reentrancy in claimRefund

### Summary

In the claimRefund function, TransferHelper.safeTransfer is called before the corresponding entry in the refundInfos mapping is deleted. If the safeTransfer function invokes an external contract, it may allow for a reentrancy attack, enabling the attacker to call claimRefund again before the refundInfos entry is deleted.




### Root Cause

The external call to TransferHelper.safeTransfer occurs before the state variable refundInfos is modified. This violates the reentrancy-safe pattern of state modification preceding external calls.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L581

### Internal Pre-conditions

The claimRefund function is invoked with a valid externalId.

The refundInfos mapping contains a valid refund entry for the externalId.

### External Pre-conditions

A malicious ERC20 token contract is used, which calls back into the claimRefund function during the safeTransfer execution.

The contract lacks reentrancy guards or proper sequencing of state updates.



### Attack Path

Deploy a malicious ERC20 token contract with a transfer function that re-enters claimRefund.

Call claimRefund with a valid externalId tied to the malicious token.

During the execution of safeTransfer, the malicious token triggers another call to claimRefund, which passes the require checks since the refundInfos entry has not yet been deleted.

This allows the attacker to drain multiple refunds tied to the same externalId.

### Impact

Reentrancy allows the attacker to extract more funds than they are entitled to.

The contract's state becomes inconsistent, leading to potential loss of trust and financial damage.



### PoC

```solidity
// Malicious token contract
contract MaliciousToken {
    address public target;

    constructor(address _target) {
        target = _target;
    }

    function transfer(address, uint256) external returns (bool) {
        GatewayCrossChain(target).claimRefund(0x123...); // Reenter claimRefund
        return true;
    }
}

// Deployment
MaliciousToken badToken = new MaliciousToken(address(gatewayCrossChain));
gatewayCrossChain.claimRefund(0x123...);

```

Result: The claimRefund function is called multiple times, allowing the attacker to drain funds.



### Mitigation

To prevent reentrancy attacks, modify the state before making external calls:
 
```solidity
delete refundInfos[externalId];
TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
```
Additionally, implement a reentrancy guard to ensure no function can be re-entered:
 
```solidity
bool private _locked;

modifier nonReentrant() {
    require(!_locked, "Reentrancy");
    _locked = true;
    _;
    _locked = false;
}
```
Apply nonReentrant to the claimRefund function for additional protection.
