# `GatewayCrossChain.withdraw` Truncates 32-Byte Bitcoin Addresses in `revertMessage`

### Summary

The [`GatewayCrossChain.onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277-L295) function, when handling withdrawals to Bitcoin, calls an internal `withdraw` function. This internal `withdraw` function incorrectly truncates 32-byte Bitcoin addresses (P2WSH & P2TR) to their first 20 bytes when constructing the `RevertOptions.revertMessage`. While the primary `sender` argument to the ZetaChain `gateway.withdraw` call correctly receives the full Bitcoin address, the `revertMessage` (critical for refund processing) contains this truncated address. If the cross-chain operation fails and `GatewayCrossChain.onRevert` is called, the refund logic will only have access to this incomplete 20-byte segment, potentially leading to fund loss or inability to process the refund correctly for the original 32-byte recipient.

### Root Cause

The vulnerability exists in the internal `withdraw` function of `GatewayCrossChain` specifically in how it constructs the `revertMessage`.

1.  **Withdrawal Path for Bitcoin:**
    *   A user initiates a cross-chain transaction that results in `GatewayCrossChain.onCall` being triggered.
    *   If the decoded payload indicates a Bitcoin destination (`decoded.dstChainId == BITCOIN_EDDY`), `onCall` calls `_handleBitcoinWithdraw`.
    *   `_handleBitcoinWithdraw` then calls the internal `withdraw` function, passing `decoded.receiver` (the full Bitcoin address as `bytes`) as the `sender` argument to `withdraw`.

    ```solidity
    withdraw(externalId, decoded.receiver, decoded.targetZRC20, outputAmount - gasFee);
    ```

2.  **Truncation in `revertMessage` Construction:** Inside the internal `withdraw` function, `RevertOptions` are prepared for the call to `IGatewayZEVM(gateway).withdraw`.

    ```solidity
    function withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount) internal {
        gateway.withdraw(
            sender, // Full Bitcoin address is correctly passed as the primary 'sender' to the gateway
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                // @audit VULNERABILITY: 'sender' (full Bitcoin address) is truncated to 20 bytes here.
                revertMessage: bytes.concat(externalId, bytes20(sender)), 
                onRevertGasLimit: gasLimit 
            })
        );
    }
    ```

    The line `revertMessage: bytes.concat(externalId, bytes20(sender))` is the issue.
    *   `sender` is the full Bitcoin address (e.g a 32-byte P2WSH script hash).
    *   `bytes20(sender)` explicitly casts/truncates the `sender` to its first 20 bytes.
    *   This truncated 20-byte segment forms the latter part of the 52-byte `revertMessage`.

### Internal Pre-conditions
1.  The `onCall` function is triggered with parameters leading to the `_handleBitcoinWithdraw` path.
2.  The `decoded.receiver` is longer than 20 bytes.

### External Pre-conditions
1.  The cross-chain transaction fails for any reason. 

### Attack Path
1.  **User Initiates Withdrawal:** User initiates a transaction targeting `GatewayCrossChain.onCall`, intending to withdraw assets as BTC to their 32-byte Bitcoin P2WSH address, `btc32b`.
2.  **Internal Processing:**
    *   `onCall` calls `_handleBitcoinWithdraw`.
    *   `_handleBitcoinWithdraw` calls `withdraw(externalId, btc32b, ...)`.
    *   Inside `withdraw`, `revertMessage` is created with `bytes20(btc32b)`, truncating the address.
3.  **Call to Gateway & Cross-Chain Transaction Failure:** `gateway.withdraw` is called. The main `sender` is correct, but `RevertOptions.revertMessage` is truncated. The cross-chain transaction fails.
4.  **`onRevert` Triggered:** ZetaChain Gateway calls `GatewayCrossChain.onRevert` with the 52-byte `revertMessage` containing the truncated address.
5.  **Outcome:** The refund is sent to an EVM address derived from the first 20 bytes of the user's 32-byte Bitcoin address, leading to fund loss.

### Impact

If a withdrawal to a >20-byte Bitcoin address fails, the `revertMessage` used by `onRevert` will contain a truncated version of the recipient's address. This leads to refunds are sent to an incorrect EVM address.


### Mitigation

The internal `withdraw` function in `GatewayCrossChain.sol` must not truncate the `sender` (Bitcoin address) when constructing the `revertMessage` for `RevertOptions`. It should pass the full `sender` bytes.
