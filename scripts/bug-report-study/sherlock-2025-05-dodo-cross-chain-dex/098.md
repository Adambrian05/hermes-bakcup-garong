# Uniswap Gas-Token Swap Logical Bug

### Summary

In the `_swapAndSendERC20Tokens` function, the code checks `require(targetAmount - amountInMax > 0)` instead of comparing against the actual amount consumed (`amounts[0]`). As a result, if `amountInMax ≥ targetAmount`—even when the actual swap uses fewer tokens (`amounts[0] < targetAmount`)—the check fails, causing the entire cross-chain call to revert after deducting platform fees. 

This locks the user’s principal (minus fees) in the contract indefinitely, requiring owner intervention to recover funds.

### Root Cause

The function uses the pessimistic estimate `amountInMax` in the second require, rather than the actual input used (`amounts[0]`). Because `amountInMax` can exceed `targetAmount` (due to high slippage or price movements), valid swaps that would have succeeded with `amounts[0] < targetAmount` end up failing this check.

### Internal Pre-conditions

- `targetAmount` (the token amount arriving after DODO swap) must be greater than zero.
- The Uniswap path computed by `getPathForTokens(targetZRC20, gasZRC20)` must be valid and non‐empty.
- slippage is configured by the owner and influences `amountInMax`.
- The contract holds at least `targetAmount` of targetZRC20.

### External Pre-conditions

None: This issue can be triggered solely by the combination of `targetAmount`, slippage, and on‐chain price movement. A user does not need to satisfy any specific external conditions beyond initiating a swap when prices shift unfavorably.

### Attack Path

1. Owner sets slippage to a non-zero value (e.g., 200 → 20%). 
2. User calls `onCall(...)` to bridge X tokens, which become `targetAmount` after any optional DODO swap.
3. Assume `targetAmount = 100 TKN`.
- Uniswap’s `getAmountsIn` returns `amountsQuote[0] = 50` to obtain `gasFee`.
- With `slippage = 200`, `amountInMax = 50 + (200 × 50/1000) = 60`.
- If prices shift after quotation (or slippage was set too high), the router still only needs `amounts[0] = 52` to complete `swapTokensForExactTokens(gasFee, 60, ...)`
4. The swap succeeds, consuming `amounts[0] = 52` of `targetZRC20`. `gasZRC20` balance is now sufficient (≥ `gasFee`).
5. The code evaluates `require(targetAmount - amountInMax > 0)` → `require(100 - 60 > 0)`, which passes here. But if slippage were set larger (e.g., `slippage = 1000` → `amountInMax = 100`), the check becomes `require(100 - 100 > 0) → false`, even though `amounts[0]` might still be 52. Thus, the function reverts after platform fees were already transferred out.
6. Because the swap reverted, the `onCall` flow aborts. Platform fees are already sent to `EddyTreasurySafe`, and the remaining 100 TKN sits in `GatewayCrossChain` with no refund record. User cannot reattempt the cross‐chain call or trigger `onRevert`. The only escape is for the owner to manually call `superWithdraw(...)` to retrieve stuck tokens.

### Impact

Users lose their platform fee (e.g., 0.5%) immediately and have the rest of their principal permanently locked in the contract until an admin rescues it.
