# Fake UniswapV2 Pool Detection Allows DoS via Crafted Token Transfers

### Summary

The `_existsPairPool` function attempts to detect whether a UniswapV2 pair pool exists by checking if both tokens have a non-zero balance at the computed pair address. However, due to the deterministic nature of UniswapV2 pair addresses (via `CREATE2`), a malicious user can send tokens to the derived address of a **non-deployed** pair, tricking the contract into treating it as a valid pool. This results in selecting an invalid 2-hop swap path and ultimately causes transaction reverts and potential denial-of-service (DoS) for users.

### Root Cause

The `_existsPairPool `function uses token balances to infer the existence of a pool, without verifying whether the actual pair contract is deployed and contains code.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L227-L228
This fails to distinguish between:
- A valid deployed pool contract, and
- A precomputed address that has received token transfers but has no deployed code.

### External Pre-conditions

- An attacker has access to both `zrc20A `and `zrc20B `tokens.
- The attacker can send minimal token balances (e.g., `1 wei`) to the computed pair address.
- The attacker does not need the actual pair contract to be deployed.

### Attack Path

- Attacker computes the deterministic UniswapV2 pair address using `uniswapv2PairFor`.
- Attacker sends `1 wei` of `zrc20A` and `zrc20B `to the computed address.
- `_existsPairPool `reads non-zero balances and returns `true`.
- `getPathForTokens()` selects the direct [zrc20A, targetZRC20] path instead of the `[zrc20, WZETA, targetZRC20]` path.
- Swap attempts to route through a non-existent pair contract.
- The swap fails (e.g., due to call to non-existent contract), resulting in transaction revert.
- This blocks functions like `withdrawToNativeChain` for zrc20 tokens and pairs affected, leading to DoS for affected users who wants to use such tokens.



### Impact

This allows denial-of-service for users who want to use with affected target tokens and it can be caused by attackers or even unintentional DoS by users who mistakenly send tokens to undeployed pair addresses.
