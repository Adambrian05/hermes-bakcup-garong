# An attacker will drain the contract by exploiting reentrancy in `claimRefund()`

### Summary

The missing `nonReentrant` modifier in `claimRefund()` will cause a loss of funds for users as an attacker will reenter the function and claim multiple refunds before state updates occur.

### Root Cause

In [`gatewayCrossChaine.sol:claimRefund(...)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571), there is a missing `nonReentrant` guard. The function performs an external call [(TransferHelper.safeTransfer)](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L14) before deleting the refund record, making it vulnerable to reentrancy.

### Internal Pre-conditions

.

### External Pre-conditions

.

### Attack Path

1. Attacker triggers a cross-chain transaction that will result in a refund being available via refundInfos.
2. Attacker deploys a malicious contract with a `fallback()` or `receive()` function that calls back into `claimRefund()`.
3. The attacker calls `claimRefund()` via their malicious contract.
4. When `TransferHelper.safeTransfer()` is called, control is given to the attacker's contract.
5. The attacker reenters `claimRefund()` again before the `refundInfos[externalId]` is deleted.
6. The attacker drains multiple refunds using a single entry.

### Impact

Draining funds.

### PoC

_No response_

### Mitigation

Add the nonReentrant modifier to claimRefund() using OpenZeppelin’s ReentrancyGuard.
