# Reentrancy Vulnerability in `claimRefund` Function leading to Loss of Funds

### Summary

The `claimRefund` function in the contract is vulnerable to reentrancy attacks despite the `safeTransfer` helper's length check protection.As shown below:
```javascript
    function safeTransfer(address token, address to, uint value) internal {
        // bytes4(keccak256(bytes('transfer(address,uint256)')));
        (bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
@>        require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
    }

```

The helper makes sure that the receivers' address is not a contract by checking whether it has data in it with `data.length == 0`, this check can be bypassed if reentrancy is implemented in the constructor of the attackers' receiver contract. To mitigate this make sure that the function deletes `refundInfos[externalId]` after the token transfer.


### Root Cause

Not following the check effects Interaction pattern

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680

### Internal Pre-conditions

A refund entry for externalId exists in refundInfos with a non-zero amount.

### External Pre-conditions

An attacker has a malicious contract that can call back into the claimRefund function at it's constructor

The attacker's contract is specified as the receiver of the refund

### Attack Path

1. Attacker deploys a malicious receive contract with reentrant logic in its constructor
2. The token's `transfer` function calls back into `claimRefund` before returning control
3. Since `refundInfos[externalId]` hasn't been deleted yet, the attacker can:
   - Re-enter the function multiple times
   - Drain funds beyond the intended amount

### Impact

Loss of funds since an attacker can repeatedly claim the same refund, effectively draining the contract's token reserves
