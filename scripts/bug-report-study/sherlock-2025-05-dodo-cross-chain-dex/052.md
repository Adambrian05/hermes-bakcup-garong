# Admin-controlled slippage allows the protocol to restrict cross-chain swaps during market volatility

### Summary

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L315

The hard-coded slippage mechanism controlled exclusively by admins in GatewayCrossChain.sol will cause failed transactions and potentially stuck funds for users during market volatility, as the slippage parameter may be set too low to accommodate price movements, preventing successful cross-chain swaps.

### Root Cause

In GatewayCrossChain.sol:316, the slippage calculation `uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;` uses an admin-controlled parameter with no user input. This is problematic because:

1. The slippage parameter is set during initialization and can only be modified by the contract owner
2. Users have no control over their acceptable slippage tolerance
3. There is no validation that the slippage parameter is reasonable or appropriate for current market conditions

### Internal Pre-conditions

1. Admin needs to set `slippage` to a value that is too low for current market volatility (e.g., 1 which represents 0.1%)
2. Market price movements need to exceed the allowed slippage tolerance

### External Pre-conditions

1. Market volatility needs to cause price movements greater than the admin-set slippage value
2. Uniswap pool prices need to change more than the allowed slippage percentage between quote and execution

### Attack Path

1. Admin sets `slippage` to a low value (e.g., 1 = 0.1%) or even 0
2. User initiates a cross-chain swap transaction
3. During processing in `_swapAndSendERC20Tokens`, the contract gets a quote for the swap from Uniswap
4. Market conditions change and prices move by more than 0.1%
5. The calculated `amountInMax` is now insufficient for the swap
6. The transaction reverts with `INSUFFICIENT_AMOUNT_FOR_WITHDRAW` or a Uniswap error
7. User funds are now stuck until either market conditions improve or admin increases the slippage tolerance

### Impact

Users suffer from failed transactions and temporarily stuck funds during periods of market volatility. The admin is not aware of the consequences of setting a restrictive slippage value, as they cannot predict future market volatility or individual user preferences for slippage tolerance.

This creates a poor user experience and potential risks when users' funds are locked for extended periods during high volatility. Cross-chain transfers may fail frequently in volatile markets, undermining the reliability of the protocol.

The issue doesn't rely on admin trust assumptions because the admin is unaware of the consequences - [4th point from Sherlock's standards](https://docs.sherlock.xyz/audits/judging/guidelines#iii.-sherlocks-standards).

### Mitigation

There are several approaches to mitigate this issue:

1. Allow users to specify their own slippage tolerance as a parameter in the cross-chain transaction
2. Implement a default slippage tolerance with a reasonable value (e.g., 5%) that accounts for typical market volatility

The most user-friendly solution would be to modify the interface and contract to accept a user-specified slippage parameter during transaction initiation, with a reasonable default value if none is provided.
