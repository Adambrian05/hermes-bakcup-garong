# Malicious actor can `claimRefund` to steal  the other users' refunds.

### Summary

The function [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571) allows anyone to execute it in which it gives an opportunity to attacker to abuse it and claim the refund of other users. Although there are bots assigned to claim the refund, this is not guarantee that they won't be beaten by other faster and well-funded malicious actors to be first in execution. 

Due to the nature of blockchain systems,  which is sequential in nature, only one can win the race in every block, either the bots or malicious actor. If the malicious actor wins the race, he can claim the refunds of other users. So in this method, the faster in execution will be the winner.

Another attack vector we are seeing is that,  the malicious actor can force its transaction to be the first in transaction ordering via frontrunning. It can simply raise its fees slightly higher than the bots' transactions and it will be the first one to be executed, therefore wins the race and steal the users' refunds.

### Root Cause

As you can see in the function below, line 571, with tag of external, anyone can execute this function. This claimRefund process does not check also if the msg.sender is a legitimate owner of the refund records. Look at line 575, if the wallet address is not 20 bytes, the receiver is assigned to msg.sender which can be anyone. 

Please be reminded that not all wallet address is 20 bytes as there are other chains like Bitcoin and Solana is using non-20 bytes. Zetachain is supposed to handle EVM and Non-EVM chains.

Another to look is line 578, the checking here is not enough, it allows msg.sender to be the receiver.

The real root cause here is not enough cross-checking on msg.sender in which it should be linked to the legitimate owner or receiver of refunds.

```Solidity
File: GatewayCrossChain.sol
571:     function claimRefund(bytes32 externalId) external {
572:         RefundInfo storage refundInfo = refundInfos[externalId];
```

### Internal Pre-conditions

1. If refundInfo.walletAddress.length is not 20.

### External Pre-conditions

none

### Attack Path

1. Malicious actor detects refund event from onRevert transaction which is using non-20 byte wallet address and external ID of 0x..01.
2. He calls `claimRefund` immediately using external ID 0x..01.
3. Inside claimRefund, here are the steps
    a. address receiver = msg.sender ⇒ receiver as msg.sender
    b. walletAddress.length ≠ 20 ⇒ wallet is non-20 byte
    c. msg.sender == receiver ⇒ pass the require statement
4. If the malicious actor wins the race against bots, he can claim the other user's refund. 
    

### Impact

Refund of other users can be stolen by malicious actor, therefore loss of funds.

### PoC

see attack path

### Mitigation

Implement robust checking on msg.sender, it should be cross-checked with legitimate owner of refunds.
