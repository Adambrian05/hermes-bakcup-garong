# Uniform Gas Limit Configuration Across Heterogeneous Blockchains Leading to Potential Transaction Failures and Excessive Fees

## Summary
The DODO cross-chain DEX uses a single global `gasLimit` parameter for all supported destination chains in the `GatewayCrossChain` contract. This uniform approach fails to account for the substantial differences in gas economics, execution environments, and transaction requirements across diverse blockchains such as Ethereum, Solana, and various L2 solutions. This can lead to transaction failures on gas-intensive chains or excessive gas fees on more efficient chains, potentially resulting in stuck cross-chain transfers and unnecessary costs for users.

## Root Cause
The root cause is the use of a single `gasLimit` configuration parameter for all destination chains in the `_handleEvmOrSolanaWithdraw` function:

The contract lacks chain-specific gas limit configuration mechanisms, using the same globally set `gasLimit` parameter (initialized in the constructor) for all destination chains.

## Internal Pre-conditions
NA

## External Pre-conditions
**Different blockchains have vastly different gas economics:**
   - Ethereum mainnet typically requires higher gas limits
   - Layer 2 solutions like Arbitrum or Optimism have different gas models
   - Solana uses a completely different computation fee structure


## Attack Path

1. A user initiates a cross-chain swap to a gas-intensive destination (e.g., Ethereum during high congestion)
2. The transaction uses the global `gasLimit` which was configured for average cases
3. If the destination operation requires more gas than allocated:
   - The transaction fails on the destination chain
   - Funds get stuck in the cross-chain bridge
   - Recovery requires manual intervention via `onRevert` or `onAbort`

Alternatively, if the `gasLimit` is set high enough for the most gas-intensive chains:
1. Users sending to efficient chains (e.g., Polygon, Optimism) pay unnecessarily high gas fees
2. This makes small transactions economically unviable on certain chains

## Impact
This vulnerability leads to Cross-chain transactions can fail if the gas limit is insufficient for the specific destination chain, resulting in stuck funds requiring manual intervention

## Mitigation
Implement chain-specific gas limits by modifying the contract to store different gas limits for each supported chain:

```solidity
// Add a mapping to store gas limits per chain
mapping(uint32 => uint256) public chainGasLimits;

// Update the initialize function
function initialize(
    address payable _gateway,
    address _EddyTreasurySafe,
    address _dodoRouteProxy,
    address _dodoApprove,
    uint256 _feePercent,
    uint256 _slippage,
    uint256 _defaultGasLimit
) public initializer {
    // ... existing code ...
    gasLimit = _defaultGasLimit; // Keep for backward compatibility
}

// Add a function to set chain-specific gas limits
function setChainGasLimit(uint32 chainId, uint256 gasLimit) external onlyOwner {
    chainGasLimits[chainId] = gasLimit;
    emit ChainGasLimitUpdated(chainId, gasLimit);
}

// Modify the withdraw function to use chain-specific gas limits
function _handleEvmOrSolanaWithdraw(
    bytes32 externalId,
    DecodedMessage memory decoded,
    uint256 outputAmount,
    bytes memory receiver
) internal returns (uint256 amountsOutTarget) {
    // Use chain-specific gas limit if set, otherwise fall back to default
    uint256 chainSpecificGasLimit = chainGasLimits[decoded.dstChainId];
    if (chainSpecificGasLimit == 0) {
        chainSpecificGasLimit = gasLimit;
    }
    
    (address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(chainSpecificGasLimit);
    
    // ... rest of the function using chainSpecificGasLimit ...
}
```
