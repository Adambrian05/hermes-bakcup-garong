# Invalid Check in `GatewayCrossChain.claimRefund` Allows Anyone To Claim Refunds Intended for Non-EVM Addresses

### Summary

The [`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590) function in `GatewayCrossChain` lacks sufficient authorization for refunds where the original intended recipient was a non-EVM address. This allows any arbitrary caller who discovers the `externalId` for such a refund to claim the ZRC20 tokens, which are then sent to the caller's (`msg.sender`) ZetaChain address. This leads to a misrouting and potential theft of user funds, as the tokens are not directed to the original intended recipient or a designated trusted bot as implied by documentation.

### Root Cause

The bug stems from a combination of how refund information for non-EVM recipients is stored and how the authorization in `claimRefund` is subsequently handled.

1.  **Population of `refundInfo` with Non-EVM Address:**
    *   The `GatewayCrossChain.onCall` function is called by the ZetaChain `gateway`. This function processes an incoming cross-chain message.
    *   Within `onCall`, if the logic determines an outgoing cross-chain operation is needed, it calls the internal function `GatewayCrossChain.withdrawAndCall`. The `receiver` parameter passed to this internal `withdrawAndCall` is of type `bytes memory`, intended to accommodate various address formats, including non-EVM ones.
    *   During the setup of `RevertOptions` within the internal `withdrawAndCall`, the `revertMessage` is constructed as `bytes.concat(externalId, receiver)`. If `receiver` is a non-EVM address, this full byte string is used.
    *   If this outgoing cross-chain operation fails, the ZetaChain gateway calls `onRevert` back on `GatewayCrossChain`.
        *   Inside `onRevert`, `context.revertMessage` is parsed. `bytes memory walletAddress` is assigned `context.revertMessage[32:]`, capturing the original `receiver` bytes.
        *   The condition `if (context.revertMessage.length == 52)` checks if the message implies a 20-byte EVM address for direct refund. If the original `receiver` was a non-EVM address, `context.revertMessage.length` would be 32 (for `externalId`) + 34 (for `receiver`) = 66 bytes, which is not 52.
        *   Thus, the `else` block is executed, creating a `RefundInfo` struct where `refundInfo.walletAddress` is populated with the full non-EVM `receiver` bytes. This `RefundInfo` is then stored in the `refundInfos` mapping.

2.  **Flawed Authorization in `claimRefund` for Non-EVM Addresses:**
    *   In `GatewayCrossChain`, within the `claimRefund` function, the authorization check is `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER")`.
    *   When `refundInfo.walletAddress.length` is not 20:
        *   The `receiver` variable, which will receive the refunded tokens, defaults to and remains `msg.sender`.
        *   The `if (refundInfo.walletAddress.length == 20)` condition evaluates to false.
        *   Consequently, the authorization check becomes `require(bots[msg.sender] || msg.sender == msg.sender, "INVALID_CALLER")`.
        *   This simplifies to `require(bots[msg.sender] || true, "INVALID_CALLER")`, which always passes for any `msg.sender`, regardless of whether they are a registered bot.
    *   This allows any address to successfully call `claimRefund` and receive the ZRC20 tokens if the `externalId` corresponds to a refund originally intended for a non-EVM address.

### Internal Pre-conditions
1.  A `RefundInfo` entry must exist in the `refundInfos` mapping within `GatewayCrossChain` for a specific `externalId`.
2.  The `refundInfo.walletAddress` field for this `externalId` must have a byte length not equal to 20 (e.g., a Bitcoin or Solana address representation).
3.  The `GatewayCrossChain` contract must hold a sufficient balance of the `refundInfo.token` to cover the `refundInfo.amount`.

### External Pre-conditions
1.  A user on a source chain initiates a cross-chain transaction through that chain's ZetaChain gateway contract. This transaction is intended to ultimately interact with `GatewayCrossChain.onCall` on ZetaChain.
2.  The payload from the source chain is structured such that when `GatewayCrossChain.onCall` processes it:
    *   It decodes a `DecodedMessage.receiver` that is a non-EVM address (e.g., `bytes(receiver)`).
    *   It subsequently calls the internal `GatewayCrossChain.withdrawAndCall` function, with this non-EVM `DecodedMessage.receiver` address being used as the `receiver` parameter for the outgoing call.
3.  The cross-chain operation initiated by `GatewayCrossChain.withdrawAndCall` then reverted.
4.  The ZetaChain gateway calls `onRevert` back on `GatewayCrossChain`. The `revertMessage` contains `externalId` and the original non-EVM `bytes(receiver)`.
5.  Consequently, `GatewayCrossChain` stores a `RefundInfo` entry where `walletAddress` is `bytes(receiver)`.
6.  An attacker discovers `externalId` by monitoring `EddyCrossChainRefund` events.

### Attack Path
1.  A legitimate user's transaction, originating from a connected chain, results in `GatewayCrossChain.onCall` being invoked by the ZetaChain gateway. The decoded parameters from the incoming message lead to `GatewayCrossChain.withdrawAndCall` being called internally with a non-EVM `receiver` address.
2.  The outgoing ZetaChain transaction fails, leading the ZetaChain gateway to call `onRevert` on `GatewayCrossChain`. The `revertMessage` includes `externalId` and `receiver`.
3.  `GatewayCrossChain` stores a `RefundInfo` where `walletAddress` is `bytes(receiver)`. An `EddyCrossChainRefund` event is emitted with `externalId` and `bytes(receiver)`.
4.  An attacker monitors these events, sees `externalId`, and notes that `walletAddress` is not 20 bytes long.
5.  The attacker calls `GatewayCrossChain.claimRefund(externalId)` from their own ZetaChain address (`msg.sender`).
6.  Inside `claimRefund`:
    *   `receiver` (local variable in `claimRefund`) is initialized to `msg.sender`.
    *   The condition `refundInfo.walletAddress.length == 20` is false.
    *   The check `require(bots[attacker_Zeta_address] || attacker_Zeta_address == attacker_Zeta_address, "INVALID_CALLER")` passes.
    *   The check `require(refundInfo.externalId != bytes32(0), "REFUND_NOT_EXIST_OR_ALREADY_CLAIMED")` passes.
7.  The `TransferHelper.safeTransfer` function sends `refundInfo.token` to `msg.sender`.
8.  The `refundInfo` for `externalId` is deleted.
9. **Result**: `msg.sender` receives the the `refundInfo.token`.

### Impact

The attacker successfully steals the ZRC20 tokens from the `GatewayCrossChain` contract. These tokens were intended as a refund for the original user. The original user does not receive their refund on ZetaChain. This is a direct loss of user funds.

### Mitigation

Strengthen the authorization logic in `claimRefund` in `GatewayCrossChain` for non-EVM addresses. One robust approach is to ensure only registered bots can claim refunds when `refundInfo.walletAddress.length != 20`.

```solidity
function claimRefund(
    bytes32 externalId
) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiverItself = msg.sender; // Default receiver to msg.sender
    bool isBotCaller = bots[msg.sender];

    // Check if the refund entry exists before trying to access its members
    require(refundInfo.externalId != bytes32(0), "REFUND_NOT_EXIST_OR_ALREADY_CLAIMED");

    if (refundInfo.walletAddress.length == 20) {
        address intendedEvmReceiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(isBotCaller || msg.sender == intendedEvmReceiver, "INVALID_CALLER_EVM");
        // If a bot is claiming for an EVM address, send to the intended EVM receiver.
        // If the user themselves is claiming, send to them.
        receiverItself = intendedEvmReceiver;
    } else {
        // For non-EVM addresses, only bots can claim.
        // The tokens will be sent to the bot's address (msg.sender).
        require(isBotCaller, "INVALID_CALLER_NON_EVM_BOT_ONLY");
    }

    // Cache values needed after deletion
    address tokenToRefund = refundInfo.token;
    uint256 amountToRefund = refundInfo.amount;

    // Effect: Delete state BEFORE external call
    delete refundInfos[externalId];

    // Interaction
    TransferHelper.safeTransfer(tokenToRefund, receiverItself, amountToRefund);

    emit EddyCrossChainRefundClaimed(externalId, tokenToRefund, amountToRefund, abi.encodePacked(msg.sender));
}

```

The mitigation also incorporates the CEI pattern and ensures the check for `refundInfo.externalId != bytes32(0)` happens before accessing other members of the struct to prevent reverts on an empty storage slot. The logic for `receiverItself` ensures correct recipient for EVM addresses whether claimed by user or bot.
