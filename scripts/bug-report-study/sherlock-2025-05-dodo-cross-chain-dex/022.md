# The logic flaw in the `_existsPairPool()` function could lead to a griefing attack.




## Summary
By donating 1 wei of zrc20A and zrc20B to the calculated PairPool address, the `_existsPairPool()` function incorrectly returns `true`, causing `getPathForTokens()` to construct an invalid path and resulting in a DoS.


## Root Cause
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L216
```javascript
function _existsPairPool(
        address uniswapV2Factory,
        address zrc20A,
        address zrc20B
    ) internal view returns (bool) {
@>        address uniswapPool = uniswapv2PairFor(
            uniswapV2Factory,
            zrc20A,
            zrc20B
        );
        return
@>            IZRC20(zrc20A).balanceOf(uniswapPool) > 0 &&
@>            IZRC20(zrc20B).balanceOf(uniswapPool) > 0;
    }

    function getPathForTokens(
        address zrc20,
        address targetZRC20
    ) internal view returns(address[] memory path) {
        bool existsPairPool = _existsPairPool(
            UniswapFactory,
            zrc20,
            targetZRC20
        );

@>        if (existsPairPool) {
            path = new address[](2);
            path[0] = zrc20;
            path[1] = targetZRC20;
        } else {
            path = new address[](3);
            path[0] = zrc20;
            path[1] = WZETA;
            path[2] = targetZRC20;
        }
    }
```
The `uniswapv2PairFor()` function only calculates the address of the pool composed of `zrc20A` and `zrc20B` but does not actually verify the existence of the pool in the UniswapFactory contract.  

An attacker can exploit this by donating 1 wei of `zrc20A` and `zrc20B` to the calculated `PairPool` address, causing `_existsPairPool()` to incorrectly return `true`. As a result, `getPathForTokens()` constructs an invalid path because the pool has not actually been created, leading to a revert in `_swapAndSendERC20Tokens()`.  

If the transaction had taken the `zrc20 → WZETA → targetZRC20` path instead, it would have succeeded.  

This issue exists in both the `GatewayTransferNative` and `GatewayCrossChain` contracts.

## Attack Path
1. The attacker calculates the address of the pool composed of `zrc20A` and `zrc20B`.  
2. The attacker donates 1 wei of `zrc20A` and `zrc20B` to this pool address.  
3. When a user attempts to swap `zrc20A` and `zrc20B` via `_swapAndSendERC20Tokens()`, the transaction will revert due to the non-existent pool.


## Impact

This leads to a Denial-of-Service (DoS) for certain tokens during cross-chain operations.

## Mitigation
