# Reentrancy in claimRefund allows attacker to drain the contract

### Summary

When cross-chain TX is aborted, `GatewayCrossChain` (or `GatewayTransferNative`) will store the refund info so that user can claim it. Problem is that `claimRefund` function makes an external call to transfer refund before deleting the refund state. Malicious refund receiver can reenter the  `claimRefund` function and claim the same refund multiple times, draining the contract. That's means all the not-yet-claimed refunds of all the users can be stolen. 

### Root Cause

The [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571) function in `GatewayCrossChain` (and `GatewayTransfernative`) does the external call before clearing the state:
```solidity
    function claimRefund(bytes32 externalId) external {
        // ...

        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount); // @audit external call is done first
        delete refundInfos[externalId]; // @audit only then state is cleared
        //....
    }
```

If asset being refunded is native asset, or if it is a token with transfer hooks, the malicious refund receiver can re-enter the `claimRefund` multiple times until it completely drains out the asset from the contract.

### Internal Pre-conditions

Abort mechanism creates `refundInfo` input for the user's failed cross-chain TX

### External Pre-conditions

None

### Attack Path

1. Attacker crafts a cross-chain TX which will end-up triggering abort mechanism. `onAbort` in `GatewayCrossChain` creates `refundInfo` that can be claimed by attacker.
2. Attacker calls `claimRefund` from a malicious contract which is used as refund receiver
3. Upon receiving the refund, malicious contract re-enters the `claimRefund`. That's possible because refund info is not yet cleared
4. Attacker can repeat the re-entrancy as long as there is more asset to be drained

### Impact

High severity - this vulnerability allows attackers to drain the contract by claiming the same refund multiple times. So all the not-yet-refunded assets can be stolen by the attacker

### PoC

_No response_

### Mitigation

Clear the state first, only then do the external call:
```solidity
        delete refundInfos[externalId];
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
```
