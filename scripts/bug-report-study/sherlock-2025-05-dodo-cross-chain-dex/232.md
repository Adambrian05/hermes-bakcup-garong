# Zeta Chain contracts doesn't check source sender, which results in compromised instructions

### Summary


ZetaChain transaction flow from connected chain to hub is as follows:
- Source app calls `GatewayEVM` bridging function (deposit, depositAndCall, call) and gateway emit important event with important params such as:
```solidity
    event DepositedAndCalled(
        address indexed sender,
        address indexed receiver,
        uint256 amount,
        address asset,
        bytes payload,
        RevertOptions revertOptions
    );
```

- Those events are used to verify the transaction on ZataChain side and construct `MessageContext` on the Hub:
```solidity
struct MessageContext {
    bytes origin;
    address sender;
    uint256 chainID;
}
```
In the current prject context, `sender` will be source `GatewaySend` contract.
- After the ZetaChain network validates the transaction, validator calls `GatewayZEVM::execute` on the hub chain with the constructed context and user provided `address zrc20, uint256 amount, address target,  bytes calldata message`
- Then we call `GatewayCrossChain/GatewayTransferNative::onCall`  with user encoded data 

However, `GatewayTransferNative` and `GatewayCrossChain` - `onCall` function doesn't verify if `MessageContext.sender` is a trusted contract (from the connected chain). 

This means that anyone can deploy a malicious contract on source, construct malicious `message` and provide Dodo's `GatewayCrossChain`, or `GatewayTransferNative` contract as `target`.  This means that the exploiter can manipulate all values including `externalId`, `DecodedMessage` and  `MixSwapParams`. 

### Root Cause

[GatewayCrossChain](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442-L454)::onCall and `GatewayTransferNative::onCall` don't verify sender of the message from the connected chain.

### Internal Pre-conditions

None

### External Pre-conditions

Exploiter invoking calling message from connected chain and providing `GatewayCrossChain` or `GatewayTransferNative`  as target.

### Attack Path

If a malicious user execute the following path, providing existing `externalId` for a user, whose transaction is waiting to be refunded on ZetaChain, he can force the transaction to revert on destination, enter the `onAbort` and [override refundInfos](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L550-L562) with a dust amount of the cheapest token, which will result in locking the tokens in the contracts.

1. On ZetaChain we have a entry in `refundInfos`, which is for victim address - 1 eth zrc20
2. Exploiter create `Expoit` contract on Arb and will to bridge to Mainet 1 wei eth
3. He send a message encoding the same `externalId` as the one waiting for refund
4. Inside `GatewayCrossChain::onCall` we enter the [withdrawAndCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L244-L270) where we encode a revert message pointing to this contract with provided `receiver` 
5. The transaction reverts on `Eth mainnet`, so `onRevert` on `GatewayCrossChain` is executed. If `onRevert` reverts, `onAbort` is called, which will override the valid `externalId` entry, resulting in 1 etc being stucked in the contract.

### Impact

Victim's loose tokens that are allocated for refunds

### Mitigation

Inside `GatewayCrossChain::onCall` and `GatewayTransferNative::onCall`  check that `MessageContext.sender` is a trusted address from a valid connected chain.
