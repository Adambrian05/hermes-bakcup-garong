# Undefined Token Handling in GatewaySend Leads to Draining of Contract-Held Tokens

### Summary

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218C5-L245C53

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L195C5-L216C6

`GatewaySend`'s handling of input tokens for `depositAndCall` > `_doMixSwap` will cause **fund draining** for the **protocol** as an **attacker** will pass a low-value token as `fromToken` while crafting `swapData` to point to a valuable token held by the contract, leading to its swap.


### Root Cause

In `GatewaySend.sol`, within `depositAndCall`, the contract takes `fromToken` as a direct parameter but uses `params.fromToken` (decoded from `swapData`) for the DODO `mixSwap`, without verifying they are identical.


### Internal Pre-conditions

* The `GatewaySend` contract needs to hold a balance of a valuable ERC20 token (e.g., from previous operations or unintended deposits/refunds).


### External Pre-conditions

N/A

### Attack Path

1.  **Attacker** identifies a valuable ERC20 token held by the `GatewaySend` contract.
2.  **Attacker** crafts a `swapData` payload. This payload is constructed such that when `SwapDataHelperLib.decodeCompressedMixSwapParams(swapData)` is called, the resulting `params.fromToken` is the address of the valuable ERC20 held by `GatewaySend`, and `params.fromTokenAmount` is the amount of this valuable token the **attacker** wishes to drain. `params.toToken` is set to a token the **attacker** wishes to receive.
3.  **Attacker** calls the external `GatewaySend::depositAndCall` function (`L173`):
    ```solidity
    function depositAndCall(
        address fromToken, // Attacker's arbitrary/low-value token
        uint256 amount, // Some arbitrary amount of attacker's token
        bytes calldata swapData, // Crafted payload for params.fromToken = victim token
        address targetContract, // Attacker's controlled address for receiving swapped tokens
        address asset,
        uint32 dstChainId,
        bytes calldata payload
    ) public payable {
        // ...
        // Handle input token
        // ...
        require(
            IERC20(fromToken).transferFrom(msg.sender, address(this), amount), // L188-L191
            "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
        );
        // ...
    }
    ```
    The **attacker** provides their own arbitrary, low-value token as `fromToken` and a nominal `amount`. This `fromToken` is transferred from `msg.sender` (the **attacker**) to `address(this)` (`GatewaySend`).
4.  Inside `GatewaySend::depositAndCall`, the function then calls the internal `_doMixSwap` (`L194`):
    ```solidity
    // Swap on DODO Router
    uint256 outputAmount = _doMixSwap(swapData);
    ```
5.  Inside `GatewaySend::_doMixSwap` (`L142`):
    ```solidity
    function _doMixSwap(bytes calldata swapData) internal returns (uint256) {
        MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData); // L143

        if(params.fromToken != _ETH_ADDRESS_) {
            IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount); // L146
        }
        // ...
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}( // L150
            params.fromToken,
            // ... (rest of swap params)
        );
    }
    ```
    `_doMixSwap` decodes the **attacker**'s crafted `swapData`. It then proceeds to `approve` `DODOApprove` for `params.fromTokenAmount` of `params.fromToken` (the valuable token held by `GatewaySend`), and executes `IDODORouteProxy(DODORouteProxy).mixSwap` to swap these valuable tokens from `GatewaySend`'s balance.
6.  The `mixSwap` operation completes, converting the valuable `params.fromToken` into `params.toToken`. The resulting `outputAmount` of `params.toToken` is returned.
7.  Back in `GatewaySend::depositAndCall`, this `outputAmount` of `params.toToken` is passed to either `_handleETHDeposit` or `_handleERC20Deposit` (depending on `asset`). For the ERC20 case (`L237`):
    ```solidity
    _handleERC20Deposit(
        targetContract, // L238: Attacker's controlled address
        outputAmount,
        asset, // L240: The params.toToken from the swap
        message,
        revertOptions
    );
    ```
    This leads to a call to `gateway.depositAndCall` (`L129`), which ultimately transfers the `outputAmount` of `asset` (the swapped valuable token) to the `targetContract` (the **attacker**'s controlled address) on the destination chain.


### Impact

The **protocol** suffers an approximate loss of **potentially all valuable ERC20 tokens held by `GatewaySend`** that an **attacker** can identify and target. The **attacker** gains the corresponding swapped tokens on the destination chain.
