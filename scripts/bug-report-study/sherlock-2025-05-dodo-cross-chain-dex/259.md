# Unchecked ERC20 transfer return value

### Summary

In `GatewaySend::onCall` there a ERC20 [transfer](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L371-L375) call, where we don't check the transfer type:
```solidity
        if(toIsETH) {
            payable(evmWalletAddress).transfer(outputAmount);
        } else {
            IERC20(toToken).transfer(evmWalletAddress, outputAmount);
        }
```

From ERC20 specification:
`Callers MUST handle false from returns (bool success). Callers MUST NOT assume that false is never returned!`

In the contest README it is stated that supported ERC20 are tokens supported by ZetaChain. Those are currently less than 10, but new assets can be whitelisted if they [satisfy whitelisting requirements](https://www.zetachain.com/docs/developers/architecture/whitelisting/).

### Root Cause

Not checking return value of `ERC20::transfer` and `ERC20::transferFrom` (assuming it will revert, or the call is successful)

### Internal Pre-conditions

None

### External Pre-conditions

An ERC20 which return false if something's wrong (paused token, or blocklisted user) on `transfer/transferFrom` is whitelisted on Zetachain.

### Attack Path

-

### Impact

Broken ERC20 integration may result in user loosing tokens -> bridge message is marked as finished, but ERC20 tokens transfer was not successful.

### PoC

_No response_

### Mitigation

Require `transfer/transferFrom` calls to return true
