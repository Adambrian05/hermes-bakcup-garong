# `_existsPairPool` has flawed design, which allows for an attacker to control

### Summary

[ _existsPairPool](https://github.com/Skyewwww/omni-chain-contracts/blob/e71f74a8e8a8716c5eeebb92a492d46ef88af61c/contracts/EddyCrossChain.sol#L174-L188) has a flawed design, which allows for an attacker to manipulate the outcome of the check.

The balance check is flawed, because an attacker can derive the `uniswapPool` address and then send tokens to it, which will result in assuming that we have a pool for the token pairs while that's not true:

```js
function _existsPairPool(
        address uniswapV2Factory,
        address zrc20A,
        address zrc20B
    ) internal view returns (bool) {
        address uniswapPool = uniswapv2PairFor(
            uniswapV2Factory,
            zrc20A,
            zrc20B
        );
        return
            IZRC20(zrc20A).balanceOf(uniswapPool) > 0 &&
            IZRC20(zrc20B).balanceOf(uniswapPool) > 0;
    }
```

This will result in a revert when trying to execute `swapTokensForExactTokens` for the given path because such pool doesn't exist. 

### Root Cause

Flawed check for existing uniswap pool in `_existsPairPool` both in `GatewayTransferNative` and `GatewayCrossChain`

### Internal Pre-conditions

None

### External Pre-conditions

Someone sends 1 Wei from both zrc20 tokens to the derived uniswap pool address

### Attack Path

1. Bob initiates a tx from Arb -> Mainnet for USDC, which should be swapped for PEPE on ZetaChain
- Bob sends 1000 USDC
2. On ZetaChain there is no pool `USDC:Arb/PEPE:Arb`, so the swap should be multihop
3. However, malicious actor deposit 1 Wei to uniswap pool address derived for `USDC:Arb/PEPE:Arb` and `GatewayCrossChain::onCall` tries to execute the swap on this pool
- The transaction revert and proceeds with calling `onRevert` on source (Arb)
4. The victim looses gas funds and is victim to a griefing attack

### Impact

Griefing

### PoC

_No response_

### Mitigation

Check if the pool exists by checking for code on the derived pool address.
