# Unsafe Native ETH and ERC20 Transfer Patterns in onCall Function Can Cause Transaction Failures and Fund Loss

### Summary

The `onCall` function in `GatewaySend.sol` {root cause: uses unsafe token transfer patterns for delivering the final assets to the recipient. Specifically, it uses `payable.transfer()` for native ETH, which has a hardcoded gas stipend of 2300, and raw `IERC20.transfer()` for ERC20 tokens, which does not validate the return value}. This will cause {impact: (1) failed cross-chain transactions if the ETH recipient is a contract requiring more than 2300 gas, leading to funds needing manual refund, or (2) silent transfer failures for non-compliant ERC20s, resulting in a loss of funds for the user} for {affected party: users receiving assets from a cross-chain swap}. This occurs as {actor: a user whose transaction completes on ZetaChain} will {vulnerability path: trigger the `onCall` handler. If the final asset is ETH and the recipient is a contract like a multisig wallet, `transfer()` will revert due to gas limits. If the final asset is a non-standard ERC20, `transfer()` might fail silently, but the function will continue as if successful, leading to an inconsistent state and user fund loss}.


### Root Cause

 In `contracts/GatewaySend.sol`, within the `onCall` function, the final asset transfer logic contains two issues:  https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L369-L373
```solidity
  function onCall(...) external payable onlyGateway returns (bytes4) {
      // ...
      if(toIsETH) {
          // Flaw 1: Uses .transfer() with a fixed 2300 gas stipend, which can easily fail for contract recipients.
          payable(evmWalletAddress).transfer(outputAmount); 
      } else {
          // Flaw 2: Uses raw .transfer() without checking the boolean return value,
          // which is unsafe for non-compliant or malicious ERC20 tokens.
          IERC20(toToken).transfer(evmWalletAddress, outputAmount);
      }
      // ...
  }
```

1. **Unsafe Native ETH Transfer**: payable(evmWalletAddress).transfer(outputAmount) forwards a fixed, non-adjustable gas stipend of 2300. This is insufficient for any recipient smart contract whose receive() or fallback() function performs any state-changing operation (like an SSTORE) or has slightly complex logic. This is a well-known deprecated practice.
2. **Unsafe ERC20 Transfer**: IERC20(toToken).transfer(...) does not check the boolean success value that the transfer function should return according to the EIP-20 standard. Some ERC20 tokens, upon failure, do not revert but instead return false. The current implementation would not detect such a failure and would proceed as if the transfer were successful.

**The issues with `transfer()` are outlined here: https://consensys.net/diligence/blog/2019/09/stop-using-soliditys-transfer-now/**


### Internal Pre-conditions

1.  A cross-chain message is routed to the `onCall` function of `GatewaySend.sol`.
2.  The logic within `onCall` successfully decodes the message and reaches the final transfer stage after performing any necessary swaps.
3.  For the native ETH issue: The decoded `toToken` is the native ETH address (`_ETH_ADDRESS_`), and the `evmWalletAddress` (the final recipient) is a smart contract whose `receive()` or `fallback()` function consumes more than 2300 gas (e.g., it performs a storage write or emits an event).
4.  For the ERC20 issue: The decoded `toToken` is the address of a non-compliant ERC20 token that returns `false` on transfer failure instead of reverting.


### External Pre-conditions

1.  A user initiates a cross-chain transaction where the final intended recipient is a smart contract address (e.g., a multisig wallet, a custom vault, or another DeFi protocol).


### Attack Path

**Path A: Native ETH Transfer Failure (DoS)**
1.  A user initiates a cross-chain transaction. The final desired output is native ETH (`toToken` is `_ETH_ADDRESS_`), and the destination recipient (`evmWalletAddress`) is their multisig wallet contract address.
2.  The transaction is successfully processed on ZetaChain, and the `onCall` function in `GatewaySend.sol` is triggered by the gateway.
3.  The `if(toIsETH)` block is executed.
4.  The call `payable(multisig_wallet_address).transfer(outputAmount)` is made.
5.  The multisig wallet's `receive()` function begins to execute. However, its internal logic (e.g., logging the deposit, checking signatures, etc.) requires more gas than the 2300 gas stipend forwarded by `.transfer()`.
6.  The `.transfer()` call runs out of gas and reverts. This causes the entire `onCall` transaction to fail.
7.  The user's cross-chain transaction fails at the very last step of delivery. The funds, which are now on ZetaChain, must be refunded via the more complex `onRevert` process, making the primary success path unusable for this common use case.

**Path B: ERC20 Silent Failure (Fund Loss)**
1.  A user initiates a cross-chain transaction where the `toToken` is a (potentially whitelisted but non-compliant) ERC20 token (`BadToken`) which returns `false` on certain transfer failures (e.g., if the recipient is on a token-level blacklist) instead of reverting.
2.  The `onCall` function is triggered.
3.  The `else` block is executed: `IERC20(BadToken).transfer(recipient, amount)`.
4.  Assume the transfer fails inside the `BadToken` contract for some reason, and the function returns `false`.
5.  The `GatewaySend.sol` contract does not check this boolean return value and continues its execution as if the transfer was successful.
6.  The `EddyCrossChainReceive` event is emitted, signaling a successful operation to off-chain listeners and the user interface.
7.  The user never receives their tokens because the transfer silently failed. The funds remain in the `GatewaySend.sol` contract, but the protocol's state (via the event) indicates the process was completed. This creates an unresolvable state for the user, resulting in a loss of their funds from their perspective.


### Impact

* For native ETH transfers to contracts, the use of `payable.transfer()` **will cause legitimate transactions to fail**, preventing users from sending funds to common smart contract wallets or other protocols. This forces funds into a more cumbersome refund process and makes the protocol unreliable and unusable for a significant portion of DeFi interactions.
* For ERC20 transfers, the lack of a return value check can lead to **silent failures where the user loses their funds**. The protocol will incorrectly record the transaction as successful, leaving the user with no assets and no clear path to recovery, as the system believes the delivery was completed.
* The affected party is any user of the protocol, especially those interacting with smart contracts as final recipients or when swapping to a variety of ERC20 tokens which may not all be perfectly compliant.
