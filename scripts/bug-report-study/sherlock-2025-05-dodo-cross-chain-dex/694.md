# Hardcoded zero `abortAddress` in `GatewayCrossChain.withdraw/withdrawAndCall` will cause funds to be stuck

# [H-1] Hardcoded zero `abortAddress` in `GatewayCrossChain.withdraw` will cause funds to be stuck

## Vulnerability Details

In the normal Zetachain [flow](https://www.zetachain.com/blog/zetachains-new-revert-handling-for-cross-chain),

> If the onCall function on the connected chain reverts, a cross-chain transaction automatically calls back into the universal contract on ZetaChain. Because ZetaChain features free cross-chain calls from connected chains, the revert mechanism doesn’t depend on having deposited tokens; the system will still call onRevert on ZetaChain, allowing the contract to handle cleanup or error logic.

> In this scenario, the flow is: ZetaChain → Connected chain onCall reverts → ZetaChain onRevert

> However, if onRevert itself fails on ZetaChain, the onAbort function is triggered to provide a final fallback: ZetaChain → Connected chain onCall reverts → ZetaChain onRevert reverts → ZetaChain onAbort

In both the `GatewayCrossChain.withdraw` and `GatewayCrossChain.withdrawAndCall` functions, the `abortAddress` in the `RevertOptions` struct is hardcoded to the zero address. Meanwhile, the `revertAddress` is designated as the `GatewayCrossChain` contract itself. Consequently, if `GatewayCrossChain.onRevert` fails, the funds will not be returned to the originally specified `receiver`.

Transactions can be aborted directly by `ZetaChain` or, in cases where `onRevert` fails, it will subsequently invoke `onAbort`. However, since no `abortAddress` is provided, the funds will be sent to the zero address. This results in the relevant `refundInfos` mapping remaining unchanged, leading to potential loss of funds for the user as they cannot claim their refund.

In `GatewayZEVM.executeAbort`

```solidity
/// @notice Call onAbort on a user-specified contract on ZEVM.
/// this function doesn't deposit the asset to the target contract. This operation is done directly by the protocol.
@> /// the assets are deposited to the target contract even if onAbort reverts. // @audit assets cannot be given to target contract since it is specified as zero address 
/// @param target The target contract to call.
/// @param abortContext Abort context to pass to onAbort.
function executeAbort(
    address target,
    AbortContext calldata abortContext
)
    external
    nonReentrant
    onlyProtocol
    whenNotPaused
{
    if (target == address(0)) revert ZeroAddress();
    Abortable(target).onAbort(abortContext);
}
```

## POC

Consider the following scenario

1. Alice's call from EVM chain `GatewaySend.depositAndCall` -> `GatewayEVM` invokes a transaction using `GatewayCrossChain.onCall`.
2. Her transaction fails because `GatewayCrossChain.onRevert` causes a revert, leading to an abort.
3. The Zetachain protocol (assuming it is trusted) is unable to execute the abort since the address is hardcoded to the zero address in both `GatewayCrossChain.withdraw` and `GatewayCrossChain.withdrawAndCall`.
4. Consequently, Alice's funds remain trapped in the protocol's custody, leaving her with no means to recover them.

## Root Cause

Hardcoded zero abort address

## Impact

Loss of funds for users because the funds become inaccessible, as the user's refund information state cannot be modified through `onAbort`.

## Mitigation

Set the `abortAddress` to the address of `GatewayCrossChain` (i.e., `address(this)`).
