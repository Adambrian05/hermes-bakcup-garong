# Incompatible Encoding and Decoding Functions in AccountEncoder Library Lead to Malformed Cross-Chain Messages for Solana

### Summary

The `_handleEvmOrSolanaWithdraw` function {root cause: calls `AccountEncoder.encodeInput` on the result of `AccountEncoder.decompressAccounts` when the destination is Solana. However, `decompressAccounts` parses a custom compact byte format, while `encodeInput` produces a standard ABI-encoded byte string. These two functions are not functional inverses}. This will cause {impact: a malformed message payload to be sent to the Solana destination} for {affected party: users attempting a cross-chain swap to Solana}. This occurs as {actor: the system during normal operation} will {vulnerability path: take the user-provided compact `accounts` data, decode it into a struct array, and then immediately re-encode it using a different, incompatible standard (`abi.encode`), which guarantees the final payload format will not match what the Solana-side receiver likely expects, causing the transaction to fail on the destination chain}.


### Root Cause

- The primary issue stems from the design flaw within the `AccountEncoder.sol` library, where the encoding and decoding functions are mismatched: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L15 & https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L19
  - The `decompressAccounts` function uses low-level assembly to parse a highly specific, custom-packed byte array format (`[2-byte length][32-byte pk][1-byte bool]...`).
    ```solidity
    // In libraries/AccountEncoder.sol
    function decompressAccounts(bytes memory input) internal pure returns (Account[] memory accounts) {
        assembly {
            // ... custom assembly logic for a compact format ...
        }
    }
    ```
  - The `encodeInput` function uses the standard `abi.encode` mechanism, which produces a completely different format with 32-byte slots, offsets for dynamic types, and padding.
    ```solidity
    // In libraries/AccountEncoder.sol
    function encodeInput(Account[] memory accounts, bytes memory data) internal pure returns (bytes memory) {
        return abi.encode(Input(accounts, data));
    }
    ```
- This flawed library is then used incorrectly in `GatewayCrossChain.sol` (and `GatewayTransferNative.sol`) within the `_handleEvmOrSolanaWithdraw` function: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L399
  ```solidity
  // In contracts/GatewayCrossChain.sol (or GatewayTransferNative.sol)
  bytes memory encoded = (decoded.dstChainId == SOLANA_EDDY)
      ? AccountEncoder.encodeInput(AccountEncoder.decompressAccounts(decoded.accounts), data)
      : data;
    ```

This line of code attempts to decode a byte string (`decoded.accounts`) using the custom `decompressAccounts` logic and then immediately re-encodes the result using the incompatible `encodeInput` function, creating a malformed payload for the Solana destination.

### Internal Pre-conditions

1. A user initiates a cross-chain swap from any source chain to a Solana destination (`dstChainId == SOLANA_EDDY`).
2. The cross-chain message payload from the source chain includes a `bytes` field for accounts, which is assumed to be in the custom compact format expected by `AccountEncoder.decompressAccounts`.
3. The transaction is successfully processed on ZetaChain up to the point where `_handleEvmOrSolanaWithdraw` is called.

### External Pre-conditions

1. A LayerZero message destined for the `onCall` function of GatewayCrossChain.sol (or GatewayTransferNative.sol) on ZetaChain is successfully relayed from a source chain.

### Attack Path

*(This describes a failure path for a legitimate operation due to the bug)*
1.  A user initiates a cross-chain swap from a source chain (e.g., Ethereum) to Solana, providing a recipient address and any other necessary data. The `accounts` data required for the Solana transaction is encoded into a custom, gas-efficient compact byte format and included in the cross-chain message.
2.  The ZetaChain `Gateway` receives the assets and message and calls the `onCall` function of the DODO DEX's ZetaChain contract (e.g., `GatewayCrossChain.sol`).
3.  After the on-chain DODO swap (if any) is performed, `onCall` calls `_handleEvmOrSolanaWithdraw` to prepare the final withdrawal message for Solana.
4.  Inside `_handleEvmOrSolanaWithdraw`, the condition `decoded.dstChainId == SOLANA_EDDY` evaluates to true.
5.  The code executes the sequence `AccountEncoder.encodeInput(AccountEncoder.decompressAccounts(decoded.accounts), data)`.
    a.  `AccountEncoder.decompressAccounts(decoded.accounts)` is called. Assuming `decoded.accounts` is in the correct custom compact format, this successfully decodes the data into a standard `Account[] memory` array.
    b.  This `Account[] memory` array is then immediately passed to `AccountEncoder.encodeInput`. This function uses standard `abi.encode` to create a new `encoded` byte string. This new string has a completely different structure (with ABI-standard offsets, padding, and length specifiers) than the original compact format.
6.  This malformed `encoded` message is sent via `gateway.withdrawAndCall` to the Solana chain.
7.  The receiving program on the Solana chain, which almost certainly expects the original custom compact format to save on costs and complexity, receives the standard ABI-encoded message instead.
8.  The Solana program's decoder fails to parse the unexpected format, causing the transaction on Solana to fail.
9.  The failure triggers ZetaChain's `onRevert` or `onAbort` mechanism, and the user's funds must be manually recovered through the refund process.


### Impact

* **All cross-chain swaps destined for Solana will fail.** The core functionality for this specific cross-chain path is broken due to the malformed message payload sent to the destination.
* This results in a poor user experience, as transactions consistently fail for a supported destination chain, and funds must be manually recovered via the more complex refund process (`claimRefund`).
* It wastes gas on ZetaChain for executing the flawed logic and sending a LayerZero message that is guaranteed to fail on the receiving end.
* The affected party is any user attempting to perform a cross-chain swap to Solana through the protocol. They cannot successfully complete their intended action.
