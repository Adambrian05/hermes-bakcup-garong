# Refund Can Be Claimed by Unauthorized User if Wallet Address Is Not Exactly 20 Bytes

### Summary

The claimRefund function falls back to msg.sender as the refund recipient when walletAddress.length != 20. This bypasses proper ownership checks and allows an attacker to claim someone else's refund by supplying a valid externalId with a malformed or incorrectly stored walletAddress.

### Root Cause

In claimRefund, the receiver is set to msg.sender by default. Only when walletAddress.length == 20 is the receiver properly decoded. If the length is incorrect (e.g., due to data corruption or implementation error), the contract assumes the caller (msg.sender) is the intended refund recipient. This fallback mechanism creates a security flaw.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571C4-L590C6

### Internal Pre-conditions

refundInfos[externalId] must exist and contain a non-empty walletAddress value that is not exactly 20 bytes in length.

### External Pre-conditions

NA

### Attack Path

1. Attacker finds a valid externalId whose walletAddress.length != 20.

2. Calls claimRefund(externalId).

3. Contract sets receiver = msg.sender.

4. The check msg.sender == receiver passes trivially.

5. Contract transfers funds to attacker.

6. Refund is permanently lost to the rightful owner.

### Impact

Unauthorized users can steal refund funds from honest users. A single incorrect walletAddress entry could allow loss of user funds, undermining the integrity of cross-chain refund logic.

### Mitigation

if fallback to msg.sender is necessary, enforce that msg.sender was explicitly set as the intended recipient in a secure and verifiable manner.
