# Gateway will send reverted funds to wrong address due to insufficient revert message validation

### Summary

Insufficient validation of revert message length will cause fund loss for users as the gateway will send reverted cross-chain transaction funds to an incorrect address when processing malformed revert messages.

### Root Cause

In `GatewaySend.sol:onRevert()` function, there is missing validation on the `context.revertMessage` length before extracting the sender address, allowing bytes slice operations on insufficient data.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L395-L395



### Internal Pre-conditions

1. Gateway needs to call `onRevert()` with a `RevertContext` containing `revertMessage` that is less than 52 bytes
2. The `revertMessage` needs to be structured differently than expected (32 bytes externalId + 20 bytes address)

### External Pre-conditions

1. ZetaChain gateway needs to send malformed revert messages during cross-chain transaction failures

### Attack Path

Not an attack per say, but this is how the issue can manifest:

1. **User calls `depositAndCall()` to initiate a cross-chain swap with legitimate parameters**
2. **Cross-chain transaction fails on destination chain, triggering revert mechanism**
3. **Gateway calls `onRevert()` with malformed `RevertContext` where `revertMessage` is less than 52 bytes**
4. **Code executes `address sender = address(uint160(bytes20(context.revertMessage[32:])))` without validating message length**
5. **Address extraction fails or produces incorrect address due to insufficient bytes**
6. **`TransferHelper.safeTransfer()` sends reverted funds to wrong/invalid address instead of original sender**

### Impact

The user suffers complete loss of their deposited tokens (amount varies per transaction). The funds are either sent to an uncontrolled address or the transaction reverts, leaving funds locked in the contract.

### PoC

## POC Walkthrough

### Scenario Setup
- User deposits 1000 USDC for a cross-chain swap
- Expected `revertMessage` should be 52 bytes: 32 bytes (externalId) + 20 bytes (user address)
- Gateway sends malformed `revertMessage` of only 40 bytes 

### Step-by-Step Execution

#### Step 1: Normal Transaction Initiation
```solidity
// User calls depositAndCall with 1000 USDC
// externalId = 0x1234...abcd (32 bytes)
// user address = 0x742d35Cc6634C0532925a3b8D9B57C0e8D8E2c0F (20 bytes)
// Expected revertMessage = externalId + userAddress = 52 bytes total
```

#### Step 2: Cross-Chain Transaction Fails
```solidity
// Destination chain swap fails
// Gateway prepares revert with RevertContext
// BUG: Gateway only includes 40 bytes instead of 52 bytes
// Malformed revertMessage = externalId (32 bytes) + partial_data (8 bytes)
```

#### Step 3: onRevert() Execution with Malformed Data
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    // context.revertMessage.length = 40 bytes (instead of expected 52)
    
    // This works fine - extracts full 32 bytes
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    
    // BUG: This extracts bytes from position 32 onwards
    // context.revertMessage[32:] = only 8 bytes available (instead of 20)
    // bytes20() cast on 8 bytes creates: 0x742d35Cc6634C053 + 12 zero bytes
    // Result: 0x742d35Cc6634C0530000000000000000000000000000
    address sender = address(uint160(bytes20(context.revertMessage[32:])));
}
```

#### Step 4: Fund Transfer to Wrong Address
```solidity
// TransferHelper.safeTransfer() sends 1000 USDC to wrong address:
// Intended: 0x742d35Cc6634C0532925a3b8D9B57C0e8D8E2c0F
// Actually sent to: 0x742d35Cc6634C0530000000000000000000000000000

TransferHelper.safeTransfer(
    context.asset,    // USDC
    sender,          // Wrong address due to malformed extraction
    context.amount   // 1000 USDC
);
```

### Vulnerability Demonstration

#### Input Data Visualization:
```solidity
Expected revertMessage (52 bytes):
[externalId - 32 bytes][user_address - 20 bytes]
0x1234...abcd742d35Cc6634C0532925a3b8D9B57C0e8D8E2c0F

Malformed revertMessage (40 bytes):
[externalId - 32 bytes][partial_data - 8 bytes]
0x1234...abcd742d35Cc6634C053

Extraction Result:
context.revertMessage[32:] = 742d35Cc6634C053 (8 bytes)
bytes20() padding = 742d35Cc6634C0530000000000000000 (20 bytes)
Final address = 0x742d35Cc6634C0530000000000000000000000000000
```

#### Code Execution Flow:
```solidity
// No validation - vulnerability entry point
// Missing: require(context.revertMessage.length == 52, "Invalid length");

// Silent failure - extracts insufficient bytes
bytes20 addressBytes = bytes20(context.revertMessage[32:]); // 8 bytes + 12 zero padding

// Funds sent to wrong address
address wrongAddress = address(uint160(addressBytes));
// wrongAddress = 0x742d35Cc6634C0530000000000000000000000000000

// User's 1000 USDC lost forever
TransferHelper.safeTransfer(USDC, wrongAddress, 1000e6);
```

### Impact Summary
- **User funds**: 1000 USDC sent to uncontrolled address `0x742d35Cc...0000`
- **Recovery**: Impossible - address has no known private key
- **Root cause**: Zero validation on critical external data structure
- **Frequency**: Every revert with malformed message length

This demonstrates how a simple missing validation check can result in complete fund loss during the revert mechanism.

### Mitigation

Add strict validation to ensure revertMessage has the exact expected length before processing
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    // MITIGATION: Validate revert message structure
    require(context.revertMessage.length == 52, "Invalid revert message length");
    
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    address sender = address(uint160(bytes20(context.revertMessage[32:52])));
    
    TransferHelper.safeTransfer(context.asset, sender, context.amount);
    
    emit EddyCrossChainRevert(externalId, context.asset, context.amount, sender);
}
```
