# `GatewaySend::onCall` uses `transfer` instead of `safeTransfer`, risking fund loss

### Summary

USDT.ETH (USDT on Eth mainnet) is listed as one of the [supported assets](https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets) on ZetaChain.

The `GatewaySend.onCall` function uses the standard `IERC20.transfer` function to send tokens to the recipient. However, some ERC20 tokens, notably USDT, do not revert on failure but instead return `false`.

The current implementation does not check the return value of the `transfer` call. If a transfer fails for any reason, the transaction will continue as if it succeeded, but the user will not receive their funds.

### Root Cause
The `onCall` function in `GatewaySend.sol` directly calls `IERC20.transfer` without validating its success as seen [here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L372)

```solidity
// file: omni-chain-contracts/contracts/GatewaySend.sol

function onCall(
    //...
) external payable onlyGateway returns (bytes4) {
    //...
    if(toIsETH) {
        //...
    } else {
        IERC20(toToken).transfer(evmWalletAddress, outputAmount);
    }
    //...
}
```
The project's own `TransferHelper.sol` library contains a `safeTransfer` function that properly checks the return value and would prevent this issue, but it is not used here.

### Internal Pre-conditions

`GatewaySend::onCall` is triggered and `toToken` is USDT.

### External Pre-conditions

ZetaChain Universal Contract initiates a transaction to GatewaySend and it succeeds.

### Attack Path

This is not an attack, but a functional bug leading to loss of funds.
1. A user initiates a cross-chain swap from ZETACHAIN , for example using `GatewayTransferNative::withdrawToNativeChain` to receive USDT on the destination connected chain.
2. The transaction is processed and succeeds, and `GatewaySend.onCall` is executed on the destination connected chain.
3. The `onCall` function attempts to transfer USDT to the user. Assume the USDT contract's `transfer` function returns `false`.
4. Because the return value is not checked, the transaction does not revert. It proceeds to emit an `EddyCrossChainReceive` event, signaling a successful transaction.
5. The user never receives their USDT, but the system has recorded the transaction as complete. The funds are not returned to the user and remain in the `GatewaySend` contract.


### Impact

User funds are stuck in GatewaySend contract.

### PoC

Please refer to attack path.

### Mitigation

```diff
// ...
+ import {TransferHelper} from "./libraries/TransferHelper.sol";
// ...

function onCall(
    //...
) external payable onlyGateway returns (bytes4) {
    //...
    if(toIsETH) {
        payable(evmWalletAddress).transfer(outputAmount);
    } else {
+        TransferHelper.safeTransfer(toToken, evmWalletAddress, outputAmount);
-        IERC20(toToken).transfer(evmWalletAddress, outputAmount);
    }
    //...
}
```
