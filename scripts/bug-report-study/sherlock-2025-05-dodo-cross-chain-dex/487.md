# Refunds sent to integrator contracts can become permanently locked

### Summary

The protocol sends refunds directly to msg.sender from the original `depositAndCall` transaction. When users interact through integrator contracts that call `depositAndCall` on their behalf, refunds are sent to these integrator contracts which may not be designed to handle token transfers, causing funds to become permanently locked.

### Root Cause

The [depositAndCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218) function encodes msg.sender as the refund recipient:
```solidity
RevertOptions memory revertOptions = RevertOptions({
    revertAddress: address(this),
    callOnRevert: true,
    abortAddress: targetContract,
    revertMessage: bytes.concat(externalId, bytes20(msg.sender)), // @audit msg.sender encoded
    onRevertGasLimit: gasLimit
});
```

The `onRevert` function blindly sends refunds to this encoded address:
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    address sender = address(uint160(bytes20(context.revertMessage[32:])));
    TransferHelper.safeTransfer(context.asset, sender, context.amount); // @audit Direct transfer to original msg.sender
   // ...
    }
```

The protocol assumes msg.sender can always receive and handle token refunds, but integrator contracts are often not designed to handle unexpected token transfers. Many contracts lack proper token handling mechanisms or may only be designed for specific operations.

### Internal Pre-conditions

None

### External Pre-conditions

User interacts through an integrator contract that calls `depositAndCall` on behalf of users. The integrator contract lacks proper token handling mechanisms such as missing receive() function for ETH, no token forwarding logic, or no admin functions to recover stuck tokens. 

### Attack Path

1. User deposits funds through an integrator contract
2.  Cross-chain transaction fails and protocol initiates refund via `onRevert`
3.  Protocol sends refund directly to the integrator contract address. Integrator contract receives tokens but has no mechanism to handle them (no receive function for ETH, no forwarding logic, no admin recovery). Funds become permanently locked in the integrator contract with no way for the original user to recover them.

### Impact

Medium severity - this vulnerability can cause direct loss of user funds through architectural design flaw rather than malicious exploit

### PoC

_No response_

### Mitigation

Modify the refund mechanism to allow specifying a separate refund recipient address in the `depositAndCall`
