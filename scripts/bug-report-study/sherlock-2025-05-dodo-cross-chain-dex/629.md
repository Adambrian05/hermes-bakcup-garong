# Insufficient slippage protection in `GatewayTransferNative::_swapAndSendERC20Tokens`

### Summary

In [`GatewayTransferNative::_swapAndSendERC20Tokens`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L306C14-L306C37), UniswapV2Library.getAmountsIn is used to calculate the value of [`amountInMax`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L319) which is used for slippage protection when calling `IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens` but the issue here is getAmountsIn can be manipulated by an attacker thereby making the slippage paramater ineffective.

### Root Cause

In [`GatewayTransferNative.sol::319`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L319) we can see the slippage parameter `amountInMax` that prevents swap from spending more tokens than desired being calculated but the issue here is `amountInMax` uses `getAmountsIn` in calculation to determine how much the swap will cost in real time and this is a problem because the outcome of `getAmountsIn` can be mannipualted by an attacker which makes the whole check ineffective.

### Internal Pre-conditions

Attacker needs to manipulate the return value of `getAmountsIn` either by flash loan attacks or something else

### External Pre-conditions

no external pre-con

### Attack Path

1. when _swapAndSendERC20Tokens is called 
2. Attackers frontruns the swap to manipulate the reserves to make getAmountsIn return amountsQuote in his favour

### Impact

There is no real slippage protection as slippage can be manipulated by an attacker
