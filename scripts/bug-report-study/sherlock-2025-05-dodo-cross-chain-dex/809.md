# Uninitialized Gateway Vulnerability

### Summary

The `withdraw` function in both [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286) and [GatewayCrossChain.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277) can be called before the contract is properly initialized, leading to calls on an uninitialized `gateway` variable (address(0)), causing transaction failures and potential denial of service.

### Root Cause

The vulnerability exists in the contract initialization pattern where the `gateway` variable is declared but not immediately initialized, creating a window where public functions can be called on an uninitialized state. The `withdraw` function directly calls `gateway.withdraw()` without verifying that the gateway has been properly initialized.

The vulnerable code pattern in GatewayTransferNative.sol:

```solidity
contract GatewayTransferNative is UniversalContract, Initializable, OwnableUpgradeable, UUPSUpgradeable {
    // ...
    GatewayZEVM public gateway; // Initially address(0)
    
    // Constructor disables initializers but doesn't set gateway
    constructor() {
        _disableInitializers();
    }
    
    // Gateway is set during initialize() call
    function initialize(
        address payable _gateway,
        // ... other parameters
    ) public initializer {
        // ...
        gateway = GatewayZEVM(_gateway); // Gateway set here
        // ...
    }
    
    // withdraw() can be called before initialize()
    function withdraw(
        bytes32 externalId,
        bytes memory sender,
        address outputToken,
        uint256 amount
    ) public {
        gateway.withdraw( // ← Calls on address(0) if not initialized
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
        );
    }
}
```

The security issue manifests in the deployment and initialization sequence. When the contract is deployed using a proxy pattern, there's a period between deployment and initialization where the contract exists but the `gateway` variable remains at its default value of `address(0)`. During this window, any caller can invoke the public `withdraw` function, which will attempt to call methods on `address(0)`.

The vulnerability follows this execution path:
1. Contract is deployed via proxy but not yet initialized
2. `gateway` variable remains at default value `address(0)`
3. Attacker calls `withdraw()` function
4. Function attempts to call `gateway.withdraw()` on `address(0)`
5. Transaction fails with low-level call error or unexpected behavior

The root cause is the lack of initialization checks in functions that depend on initialized state variables. The contract uses OpenZeppelin's `Initializable` pattern but doesn't protect individual functions from being called before initialization is complete.

This vulnerability is particularly dangerous in upgradeable contracts where the initialization process might be delayed or where multiple initialization steps are required. The public visibility of the `withdraw` function combined with the lack of initialization guards creates an attack vector for denial of service and potential state corruption.

### Impact

The high impact assessment is justified by several factors that could significantly affect the protocol's security and reliability. The primary impact is the potential for denial of service attacks during the critical initialization period, which could prevent proper contract setup and deployment.

During the initialization window, malicious actors could repeatedly call the `withdraw` function, causing transaction failures that might interfere with the proper initialization process. This could delay or prevent the contract from becoming operational, affecting the entire cross-chain operation flow.

The vulnerability also creates unpredictable behavior during contract deployment. Failed calls to `address(0)` might consume gas, generate confusing error messages, or trigger unexpected state changes that could complicate the initialization process. This unpredictability makes it difficult to ensure reliable contract deployment in production environments.

From a security perspective, the vulnerability demonstrates a broader pattern of insufficient initialization guards that could affect other functions as well. If the `withdraw` function lacks proper initialization checks, other critical functions might have similar vulnerabilities, creating multiple attack vectors during the initialization period.

The impact extends to the protocol's operational security, as failed initialization attempts could leave the contract in an undefined state. This could require redeployment or complex recovery procedures, potentially affecting user funds or cross-chain operations that depend on the contract's availability.

Exploitation scenarios:

1. **Immediate Exploitation**: Call `withdraw()` immediately after contract deployment

3. **Race Condition**: Exploit timing between deployment and initialization
4. **State Corruption**: Cause unexpected state changes during initialization window

### Mitigation

Implement comprehensive initialization checks and proper access controls:

```diff
contract GatewayTransferNative is UniversalContract, Initializable, OwnableUpgradeable, UUPSUpgradeable {
    
+   modifier onlyInitialized() {
+       require(address(gateway) != address(0), "Contract not initialized");
+       _;
+   }
    
    function withdraw(
        bytes32 externalId,
        bytes memory sender,
        address outputToken,
        uint256 amount
-   ) public {
+   ) public onlyInitialized {
+       require(address(gateway) != address(0), "Gateway not initialized");
        gateway.withdraw(
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
        );
    }
    
+   function isInitialized() external view returns (bool) {
+       return address(gateway) != address(0);
+   }
}
```

Additional recommendations:

1. **Atomic Deployment**: Ensure initialization occurs in the same transaction as deployment
2. **Initialization Guards**: Add initialization checks to all public functions that depend on initialized state
3. **State Validation**: Implement comprehensive state validation before critical operations
4. **Access Controls**: Consider restricting access during initialization period

```solidity
modifier onlyAfterInitialization() {
    require(
        address(gateway) != address(0) && 
        EddyTreasurySafe != address(0) && 
        DODORouteProxy != address(0),
        "Contract not fully initialized"
    );
    _;
}
```

This approach ensures that all critical state variables are properly initialized before allowing function execution, preventing the vulnerability while maintaining the intended functionality.
