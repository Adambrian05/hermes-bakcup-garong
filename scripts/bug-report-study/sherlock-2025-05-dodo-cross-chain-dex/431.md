# Anyone can claim refunds for Solana/Btc addresses through `claimRefunds` function.

### Summary

Anyone can claim refunds through `claimRefunds` method from `GatewayCrossChain` or `GatewayTransferNative` contract for wallet addresses with Solana and Bitcoin networks (Non-EVM networks).


### Root Cause

[GatewayCrossChain.sol:574-579](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574C9-L579C66)

```solidity
address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
```

`claimRefund` method from `GatewayCrossChain` contract deal with claiming refund which is created by `onAbort` or `onRevert` methods.
It checks `msg.sender` is allowed bot or valid `receiver` for authorization for claiming, but it only set receiver as `walletAddress` from `refundInfo` when this address is EVM-compatible address (160bit).
But in case of `walletAddress` is from Solana or Bitcon network, `receiver` is initiallly set as `msg.sender` and no else statement, so `msg.sender` can always pass the `require` statement.
This lead to any attacker can claim refund which is generated from Solana and Bitcoin networks by getting only externalId with analyzing log.

Same issue is found in `GatewayTransferNative` contract because of same code base and logic.

### Internal Pre-conditions

1. The loss of funds could occur in case of refund is created with Solana/Bitcoin wallet address through `onRevert` and `onAbort` methods.

### External Pre-conditions

No external condition is needed.

### Attack Path

1. Attacker consistently watches logs to find the refund which is generated from Solana and Bitcoin networks. (It is only generated when `onRevert` and `onAbort` is called.)
2. Attacker calls `claimRefund` method with `externalId` which is id for refund with Solana/Bitcoin networks.
3. `claimRefund` function always works in case of Solana/Bitcoin refund regardless the value of `msg.sender` and this lead to loss of user's funds.

### Impact

Impact: High
Anyone could claim refunds for Solana and Bitcoin wallet addresses.
Likelihood: Low
Refund is created only in failed transactions through `onRevert` and `onAbort` method and only vulnerable for Solana/Bitcoin network wallet addresses.
Impact: Medium

### PoC

```solidity
function test_Z_ClaimRefund() public {
        bytes32 externalId = keccak256(abi.encodePacked(block.timestamp));
        uint256 amount = 100 ether;
        token1Z.mint(address(gatewayTransferNative), amount);

        vm.prank(address(gatewayZEVM));
        gatewayTransferNative.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset: address(token1Z),
                amount: amount,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(externalId, solAddress)
            })
        );

        vm.prank(user2);
        gatewayTransferNative.claimRefund(externalId);

        assertEq(token1Z.balanceOf(user2), amount);
    }
```

Add this test code into `GatewayTransferNative.t.sol` file.
It generate refund by calling `onAbort` method externally, and `user2` claim refund successfully regardless of controlling walletAddress.

### Mitigation

Don't initialize `receiver` value with `msg.sender` or just add the logic for handling Bitcoin/Solana network wallet addresses.
