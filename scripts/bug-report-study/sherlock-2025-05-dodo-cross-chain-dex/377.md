# An attacker will steal/deny refunds from legitimate users

### Summary

The lack of `context.sender` validation in the `onRevert`, `onAbort` and `onCall` functions is catastrophic in all cases.

### Root Cause

In both `GatewayCrossChain.sol` and `GatewayTransferNative.sol`, the `onRevert`, `onAbort` and `onCall` functions only validate that the call is coming from the gateway contract but don't validate the original `context.sender`.

This is fundamentally flawed because ZetaChain operates with a single gateway per chain for all universal applications ([reference to ZetaChain docs](https://www.zetachain.com/docs/developers/evm/gateway/)).

Since this single gateway can be used by anyone to deliver messages, simply validating that a message came from the gateway provides no security. An attacker can craft malicious messages through the same legitimate gateway.

### Internal Pre-conditions

The contract has at least one unclaimed refund.

### External Pre-conditions

None specific - the attack can be executed in normal operating conditions

### Attack Path

Using `onCall` for stealing funds:

1. Attacker sends a crafted `depositAndCall` message from a contract deployed on an external chain to `GatewayTransferNative` where:
   a. It includes a small amount of an inexpensive token
   b. Sets `targetZRC20` to a more valuable token
   c. Leaves `swapData` empty
   d. Sets `receiver` to an address controlled by the attacker

2. Due to the empty `swapData`, the `_doMixSwap` function returns the exact amount without performing any swap. As a result, the more valuable `targetZRC20` token is transferred to the attacker's address.

Using `onRevert` for DoS:

1. Attacker identifies a victim's unclaimed refund with a known `externalId`
2. Attacker sends a message from a Contract deployed on ZetaChain to any address that will revert or fail.
3. Attacker sets the `revertAddress` to the vulnerable contract address (either `GatewayCrossChain` or `GatewayTransferNative`)
4. Attacker constructs a `revertMessage` that begins with the victim's `externalId` (32 bytes) followed by arbitrary data
5. The message reverts or aborts, causing the gateway to call `onRevert` on the vulnerable contract
6. The contract creates a new RefundInfo entry with the same `externalId` as the victim's, overwriting the legitimate refund data
7. The victim attempts to claim their refund but finds it has been modified or replaced with invalid data

Using `onAbort` for DoS:

Similar to `onRevert`, but in this scenario, the initial contract is deployed on an external blockchain, using the vulnerable contract's address as the `abortAddress` parameter.

### Impact

The legitimate user suffers loss of access to their funds that are rightfully owed as a refund.

### PoC

_No response_

### Mitigation

Add proper validation in `onRevert`, `onAbort` and `onCall` functions to ensure the original sender is a trusted contract.

Example fix:

```solidity
mapping(address => bool) public trustedContracts;

function setTrustedContract(address adr, bool isTrusted) external onlyOwner {
  trustedContracts[adr] = isTrusted;
}

modifier onlyTrustedContract(address sender) {
  require(sender == address(this) || trustedContracts[sender], "Unauthorized sender");
}

function onCall(AbortContext calldata context) external onlyGateway onlyTrustedContract(context.sender) {
    // function remains the same
}

function onRevert(RevertContext calldata context) external onlyGateway onlyTrustedContract(context.sender) {
    // function remains the same
}

function onAbort(AbortContext calldata context) external onlyGateway onlyTrustedContract(context.sender) {
    // function remains the same
}
```
