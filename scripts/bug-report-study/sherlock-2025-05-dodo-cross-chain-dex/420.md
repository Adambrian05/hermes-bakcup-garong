# Anyone can steal pending refunds due to flawed recipient validation

### Summary

The `claimRefund` function, which is identical in both ZetaChain contracts (`GatewayCrossChain.sol` and `GatewayTransferNative.sol`), is vulnerable to theft. When a legitimate user's transaction fails due to a common, non-malicious error in an integrated adapter (e.g., `UniAdapter.sol`), it creates a vulnerable refund state. A malicious attacker can then exploit this state via the `claimRefund` logic to steal the legitimate user's entire pending refund.

### Root Cause

The root cause is the insecure processing of arbitrary revert messages from external dependencies. The [`onRevert`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517) function blindly slices the incoming `context.revertMessage` at the 32-byte mark to derive a `walletAddress`. If the original revert message from any integrated adapter is not exactly 52 bytes long, the resulting `walletAddress` slice will have a length other than 20.

### Internal Pre-conditions

- A `RefundInfo` entry exists in either `GatewayCrossChain` or `GatewayTransferNative` where the `walletAddress` field has a length other than 20 bytes.

### External Pre-conditions

- A legitimate user's [`mixSwap`](https://github.com/DODOEX/contractV2/blob/82733a61f329c22e5e31b755c8a30c51884a5afd/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1392) transaction results in a revert from any of its downstream dependencies (e.g., an adapter or a liquidity pool). The revert message from this failure must not be exactly 52 bytes long.

### Attack Path

This attack path describes how a malicious actor steals funds from a legitimate user. We suppose that DODO uses `UniAdapter` as its implementation for `IDODOAdapter`.

1. A normal user initiates a cross-chain swap via `GatewayCrossChain` contract for 10 WETH. This transaction will invoke `mixSwap`->`_deposit`->[`sellBase`](https://github.com/DODOEX/contractV2/blob/82733a61f329c22e5e31b755c8a30c51884a5afd/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1443) function. Their transaction is then routed through [`UniAdapter.sol`](https://github.com/DODOEX/contractV2/blob/82733a61f329c22e5e31b755c8a30c51884a5afd/contracts/SmartRoute/adapter/UniAdapter.sol#L15C24-L15C36) to a pool that momentarily has insufficient liquidity.
2. The user's transaction fails inside the [`UniAdapter`](https://github.com/DODOEX/contractV2/blob/82733a61f329c22e5e31b755c8a30c51884a5afd/contracts/SmartRoute/adapter/UniAdapter.sol#L25) with the `'UniAdapter: INSUFFICIENT_LIQUIDITY'` error due to the requirement `require(reserveIn > 0 && reserveOut > 0, 'UniAdapter: INSUFFICIENT_LIQUIDITY');`. This is a standard, non-malicious failure.
3. The [`onRevert`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517) callback is triggered. It receives a `context.amount` of ~10 WETH (minus platform fee) but a `revertMessage` that is 132 bytes long. This creates a `RefundInfo` struct for the user's 10 WETH, but with a flawed 100-byte `walletAddress`. The user's funds are now pending refund in a vulnerable state.
4.  A malicious attacker, monitoring the blockchain for [`EddyCrossChainRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L541) events, spots this vulnerable refund.
5.  The attacker immediately calls `claimRefund` with the `externalId` from the user's failed transaction, front-running the user or any recovery bot.
6.  The flawed logic authorizes the attacker, who successfully calls [`TransferHelper.safeTransfer`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L581) to steal the legitimate user's 10 WETH.

Note that this is just a viable example, any non-standard revertMessage returned by DODO can lead to the same issue.

### Impact

This vulnerability allows a malicious actor to directly steal the full principal from any legitimate user whose transaction fails with a non-standard revert message. It completely undermines the safety of the protocol's refund mechanism.

### Mitigation

The `claimRefund` function in **both contracts** (`GatewayCrossChain.sol` and `GatewayTransferNative.sol`) must be restructured to explicitly handle claims for EOA-refunds and non-EOA-refunds separately. This ensures that only a whitelisted bot can claim a refund originating from a non-standard revert.

```solidity
// This updated logic must be applied to both GatewayCrossChain.sol and GatewayTransferNative.sol
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    require(refundInfo.externalId != 0, "REFUND_NOT_EXIST");

    bool isBot = bots[msg.sender];
    bool isEoaRefund = refundInfo.walletAddress.length == 20;
    address receiver;

    if (isEoaRefund) {
        // A standard refund to an EOA can be claimed by the owner OR a bot.
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(isBot || msg.sender == receiver, "INVALID_CALLER");
    } else {
        // A non-standard refund can ONLY be claimed by a bot for manual processing.
        require(isBot, "ONLY_BOT_CAN_CLAIM");
        receiver = msg.sender;
    }
    
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}
```
