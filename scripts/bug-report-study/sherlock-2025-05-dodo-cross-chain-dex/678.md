# Swap Slippage Not Enforced — Front-Running Enables Excessive Token Consumption

### Summary

The `_swapAndSendERC20Tokens()` function attempts to account for slippage when swapping `targetZRC20 `for `gasZRC20 `using `swapTokensForExactTokens`. However, it calculates the maximum input (`amountInMax`) based on a pre-swap reserve quote from `getAmountsIn`, which can be manipulated. A front-runner can alter pool reserves just before the swap, causing significantly more `targetZRC20 `to be consumed than anticipated, violating slippage expectations.

### Root Cause

Slippage is applied to a static quote (`getAmountsIn`) which is not resistant to manipulation. 
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L313-L319

The actual swap relies on `swapTokensForExactTokens`, but the slippage protection is not enforced dynamically — there's no validation of the actual price execution vs. acceptable bounds.

### Attack Path

- The attacker monitors mempool for a call to `_swapAndSendERC20Tokens()`.
- The attacker performs a swap (`swapExactTokensForTokens`) using `targetZRC20 `→ `gasZRC20`, distorting the pool reserves.
- The victim’s transaction uses outdated reserve data from `getAmountsIn`, resulting in underestimating the real `amountIn `needed.
- The swap still succeeds, but at a significantly worse rate, consuming far more `targetZRC20` than anticipated.
- The attacker profits by arbitraging the reserve delta or simply causes a DoS-like condition by draining excessive funds.

### Impact

**Slippage violation:** Users lose more `targetZRC20` than expected.
