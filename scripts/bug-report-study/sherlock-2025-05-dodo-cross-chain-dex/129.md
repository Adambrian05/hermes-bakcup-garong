# Buffer Over-read in AccountEncoder.decompressAccounts

__Summary:__ The `decompressAccounts` function in `AccountEncoder.sol` contains a buffer over-read vulnerability in its assembly code. It reads account data based on an internal length field without validating the read offset against the actual input buffer size, allowing attackers to cause out-of-bounds reads.

__Vulnerability Detail:__ The assembly block in `decompressAccounts` reads a `uint16` length (`len`) from offset 32 of the input byte array. It then iterates `len` times, using `calldataload` (or `mload`) to read 33 bytes for each account. The code lacks checks to ensure that the current read offset (`ptr`) remains within the bounds of the input byte array (`input.length`). This can be triggered by crafting a cross-chain message with a large declared account count but insufficient actual data when processed by `GatewayCrossChain` or `GatewayTransferNative`.

__Impact:__ An attacker can provide a malicious input that causes the function to read beyond the allocated buffer. This will likely lead to transaction reversion, causing a Denial of Service (DoS) for legitimate cross-chain operations that use this decoding path. In some environments, it could potentially lead to reading unintended memory contents.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L19

__Recommendation:__ Implement explicit bounds checks within the assembly loop before each `calldataload` (or `mload`) operation to ensure that the current read offset (`ptr`) does not exceed the actual length of the input byte array (`mload(input)` for memory, or check against calldata length if input is calldata).
