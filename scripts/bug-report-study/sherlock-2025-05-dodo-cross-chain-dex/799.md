# Insufficient `msg.value` Check in `withdrawToNativeChain` Leads to Low-Cost ERC20 Refund Draining

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530C5-L556C9

#### Summary
The `withdrawToNativeChain` function in `GatewayTransferNative` is `payable` but critically lacks validation for the **`msg.value`** (native ETH sent) against the **`amount`** parameter when `zrc20` is `_ETH_ADDRESS_`. This oversight enables an **attacker** to pay a minimal amount of native ETH while initiating a transaction that drains valuable ERC20 tokens (e.g., unclaimed refunds) from the contract.

---
#### Root Cause
In `GatewayTransferNative::withdrawToNativeChain`, the contract's logic for handling input tokens differentiates based on the `zrc20` parameter.

```solidity
function withdrawToNativeChain(
    address zrc20,
    uint256 amount,
    bytes calldata message
) external payable {
    if(zrc20 != _ETH_ADDRESS_) { // L365
        require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED"); // L366
    }
    // ...
    // amount -= platformFeesForTx; // L381
    // ...
    // uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params); // L384
    // ...
}
```

If `zrc20` is `_ETH_ADDRESS_` (indicating a native ETH transfer), the `if` condition at `L365` evaluates to `false`, bypassing the `require(IZRC20(zrc20).transferFrom(...))` call at `L366`. Crucially, no equivalent `require(msg.value >= amount)` check is implemented to ensure that the actual native ETH sent via **`msg.value`** corresponds to the **`amount`** parameter. Consequently, the **`amount`** parameter, as provided by the caller, proceeds to subsequent operations like fee calculation (`_handleFeeTransfer` at `L380`) and `_doMixSwap` (`L384`), irrespective of the actual (potentially negligible) **`msg.value`** received.

---
#### Internal Pre-conditions
* The `GatewayTransferNative` contract holds a balance of one or more valuable ERC20 tokens, such as those accumulated from unclaimed refunds stored in the **`refundInfos`** mapping.

```solidity
mapping(bytes32 => RefundInfo) public refundInfos; // externalId => RefundInfo
```

* An attacker can craft a malicious **`message`** payload where `params.fromToken` points to a desired valuable ERC20 token held by the contract, and `params.fromTokenAmount` specifies the amount of this ERC20 to be drained.

---
#### External Pre-conditions
None.

---
#### Attack Path
1.  An **attacker** identifies valuable ERC20 tokens (e.g., Token X) held within the `GatewayTransferNative` contract, typically from unclaimed refunds.
2.  The **attacker** calls the **`GatewayTransferNative::withdrawToNativeChain`** function (`L364`) with the following inputs:
    * **`zrc20`**: Set to `_ETH_ADDRESS_`. This allows the call to bypass the `transferFrom` check for an ERC20 input.
    * **`amount`**: An arbitrary value (e.g., the amount of Token X they wish to drain). This `amount` parameter is **not validated against `msg.value`**.
    * **`msg.value`**: A minimal amount of native ETH (e.g., 0.0001 ETH). The attacker exploits the missing check to minimize their transaction cost.
    * **`message`**: A specially crafted payload. When `SwapDataHelperLib.decodeMessage(message)` (`L376`) is processed, it will yield `params.fromToken` as the address of Token X (the victim ERC20 refund token), and `params.fromTokenAmount` as the exact amount of Token X to be swapped.

3.  Because `zrc20` is `_ETH_ADDRESS_`, the `if` condition at `L365` evaluates to `false`, and the `require` statement at `L366` is skipped.

4.  The `amount` parameter (the value specified by the attacker, not `msg.value`) is then used for calculating platform fees in `_handleFeeTransfer` and subsequently passed to `_doMixSwap` (`L384`).

    ```solidity
    // Transfer platform fees
    uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // L380
    amount -= platformFeesForTx; // L381

    // Swap on DODO Router
    uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params); // L384
    ```

5.  Inside `_doMixSwap` (`L325`):

    ```solidity
    function _doMixSwap(
        bytes memory swapData,
        uint256 amount, // This 'amount' is the attacker-provided parameter from withdrawToNativeChain
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }

        IZRC20(params.fromToken).approve(DODOApprove, amount); // L331
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}( // L332
            params.fromToken, // This is Token X (the victim ERC20 refund token)
            params.toToken,
            params.fromTokenAmount, // This is the amount of Token X to swap, from crafted message
            params.expReturnAmount,
            params.minReturnAmount,
            params.mixAdapters,
            params.mixPairs,
            params.assetTo,
            params.directions,
            params.moreInfo,
            params.feeData,
            params.deadline
        );
    }
    ```
    `IZRC20(params.fromToken).approve(DODOApprove, amount)` (`L331`) is called. Here, `params.fromToken` is Token X (the valuable ERC20 refund token), and `amount` is the attacker's chosen value. The contract successfully approves its own Token X balance for the swap. The subsequent `IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(...)` (`L332`) is then executed. The key here is that `params.fromToken` for the swap is Token X, and `params.fromTokenAmount` (from the crafted **`message`**) dictates the amount of Token X to be swapped. The **`value: msg.value`** component represents the *negligible* ETH amount sent by the attacker. Since Token X is an ERC20, the actual **`msg.value`** provided by the attacker does not need to correspond to the value of Token X being swapped.

6.  The `mixSwap` operation then converts the contract's valuable Token X (refunds) into `params.toToken` (controlled by the attacker).
7.  Finally, the swapped `params.toToken` is transferred to the **attacker**'s controlled `receiver` address on the destination chain via `_handleBitcoinWithdraw` or `_handleEvmOrSolanaWithdraw`.

---
#### Impact
This vulnerability allows an **attacker** to drain **valuable ERC20 tokens (including unclaimed refunds)** from the `GatewayTransferNative` contract at a significantly reduced cost. By setting `zrc20 = _ETH_ADDRESS_` and sending only a minimal **`msg.value`**, the attacker bypasses the necessity of transferring a substantial amount of an arbitrary ERC20 token or a large sum of ETH to initiate the draining process. This leads to **direct financial losses for the protocol** due to the theft of user funds held in custody for refunds, all while minimizing the attacker's transaction expenses.
