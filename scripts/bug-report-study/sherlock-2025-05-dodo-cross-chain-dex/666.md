# Insufficient slippage protection in `GatewayCrossChain::_swapAndSendERC20Tokens`

### Summary

The [`amountInMax`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L315) being used as a slippage protection parameter in `_swapAndSendERC20Tokens` is manipulatable by an attacker because of the use of `getAmountsIn` in calculating `amountsQuote` this makes the protection offered insufficient

### Root Cause

The use of `getAmountsIn` in calculating `amountsQuote` which is further used in calculating `amountInMax`

```solidity
>        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20));

>        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
```

The problem is attacker can manipulate the return value of `getAmountsIn` by manipulating the reserves of these tokens directly.

### Internal Pre-conditions

Attacker has to manipulate the results of `getAmountsIn` to desired value

### External Pre-conditions

n/a

### Attack Path

1. `onCall` must be called by gateway
2. then require DecodedMessage.dstChainId != BITCOIN_EDDY so the else block can run
3. Then `amountsOutTarget` is returned by calling `_handleEvmOrSolanaWithdraw` which further calls -> 4. _swapAndSendERC20Tokens when `DecodedMessage.targetZRC20 != gasZRC20` 
5. But before `_swapAndSendERC20Tokens` is executed attacker frontruns this with a flash-loan attack or something to manipulate reserves of tokens to return desired outcome to make swap in his favour

### Impact

Insufficient slippage protection allows attackers to manipulate swap

### PoC

_No response_

### Mitigation

Introduce amountInMax function param
