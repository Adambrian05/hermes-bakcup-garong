# The GatewaySend contract will not properly handle ETH refunds in onRevert function

### Summary

Missing logic to handle ETH refunds in the `onRevert` function of `GatewaySend` will cause a loss of funds for users as they won't receive their ETH back when a cross-chain transaction reverts. Moreover since there's no check on `context.sender` for `onCall` of the same contract, such ETH is extractable by an attacker.

### Root Cause

In `GatewaySend.sol` the `onRevert` function only handles ERC20 tokens and does not properly handle the case when the original deposit was ETH

The current implementation assumes that `context.asset` will always be a valid ERC20 token address and uses `TransferHelper.safeTransfer()` to return funds. However, when the original deposit was ETH, `context.asset` will be empty (0x0000...) which always immediately succeeds with a `.call` (and `safeTransfer()`), leaving ETH tokens in the contract itself.

### Internal Pre-conditions

1. A user needs to make a cross-chain transaction with ETH as the input asset by calling `depositAndCall` with ETH
2. The cross-chain transaction needs to fail and trigger the `onRevert` callback

### External Pre-conditions

None Specific

### Attack Path

1. User sends a cross-chain transaction with ETH using one of the `depositAndCall` functions with ETH as the source token
2. The transaction fails on the destination chain for any reason
3. The gateway contract calls `onRevert` on the `GatewaySend` contract
4. The `onRevert` function attempts to transfer the ETH back to the user using `TransferHelper.safeTransfer(context.asset, sender, context.amount)`
5. Nothing is transferred since the token address is empty (`safeTransfer` succeeds with no funds being transferred).
6. The ETH remains trapped in the contract.
7. Attacker can use another vulnerability of `onCall` that doesn't check for `context.sender` to extract trapped ETH (sending a carefully crafted transaction to this contract from another contract deployed on ZetaChain, which is delivered via gateway).

### Impact

Users who experience reverted cross-chain transactions with ETH as the source token will permanently lose their ETH deposits.

The ETH will remain locked in the contract, extractable by attackers. This is particularly severe as ETH is the native token of many chains and likely to be a common choice for cross-chain transactions.

### Mitigation

Modify the `onRevert` function to handle both ETH and ERC20 token refunds:

```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    address sender = address(uint160(bytes20(context.revertMessage[32:])));
    
    if (context.asset == 0) {
        // Handle ETH refund
        payable(sender).transfer(outputAmount);
    } else {
        // Handle ERC20 refund
        TransferHelper.safeTransfer(context.asset, sender, context.amount);
    }

    emit EddyCrossChainRevert(
        externalId,
        context.asset,
        context.amount,
        sender
    );
}
```
