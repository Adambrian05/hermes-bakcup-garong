# Missing Input Validation: Zero Address Checks

### Summary

The fromToken and toToken addresses for swaps are derived directly from cross-chain messages. A malicious actor could set fromToken or toToken to address(0) in a crafted message. The contract doesn't explicitly check for these zero addresses; it only uses _ETH_ADDRESS_ as a specific constant for native Ether. If address(0) is used as a token, it will lead to an unpredictable revert when attempting to interact with the non-existent ERC20 contract at that address (e.g., during approve or mixSwap calls).

### Root Cause

In https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357
In https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L425
In https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530
There is no explicit zero-address checks for fromToken or toToken in critical paths.

1. fromToken and toToken derivation:
-The onCall function receives a message as bytes calldata. This message is then decoded into DecodedNativeMessage and MixSwapParams.
-Within _doMixSwap, the params.fromToken and params.toToken are used directly in the DODO mix swap. These params originate from the message decoded in onCall or withdrawToNativeChain. This means fromToken and toToken values indeed derive from cross-chain messages, making them susceptible to manipulation by a malicious sender.

2. No explicit zero-address checks for fromToken or toToken in critical paths:
-In the _doMixSwap() function params.fromToken and params.toToken are directly used in the IZRC20(params.fromToken).approve call and subsequently passed to the IDODORouteProxy(DODORouteProxy).mixSwap function. There are no require(params.fromToken != address(0), "..."); or require(params.toToken != address(0), "..."); checks before these interactions.
-Next, consider where these params (and thus fromToken and toToken) originate. They are decoded from the message parameter in onCall and withdrawToNativeChain:
-In both onCall  and withdrawToNativeChain, the message is decoded into MixSwapParams params using SwapDataHelperLib.decodeNativeMessage or SwapDataHelperLib.decodeMessage. There are no explicit checks on the params.fromToken or params.toToken values after decoding and before _doMixSwap is called. This confirms that a malicious sender could potentially pass address(0) through the message payload.

3. Treatment of _ETH_ADDRESS_ as a sentinel:
-The contract defines address constant _ETH_ADDRESS_ = 0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE;.
-The superWithdraw function explicitly checks if (token == _ETH_ADDRESS_) to differentiate between native ETH and ZRC20 tokens for withdrawal.
-Similarly, withdrawToNativeChain checks if(zrc20 != _ETH_ADDRESS_) to decide whether to perform a transferFrom.
-This confirms that _ETH_ADDRESS_ acts as a sentinel for native ETH.





### Internal Pre-conditions

1. No Zero-Address Guard: onCall takes fromToken/toToken directly from the message
2.  ETH Sentinel ≠ Zero: The contract uses an _ETH_ADDRESS_ constant (e.g. 0xEeee…), so a true address(0) slips through as a “valid” token.
3. Unconditional ERC-20 Call: onCall always executes "IERC20(fromToken).transferFrom(user, address(this), amount);" even if fromToken == address(0). 


### External Pre-conditions

1. Source-Chain Contract Permits 0x0 as Token
2. Cross-Chain Message Schema Carries Raw Token Address
3. Off-Chain Relayer Doesn’t Sanitize Inputs
4. Gateway Access Control Allows Malformed Messages

### Attack Path

1. Craft Malicious Deposit on Source Chain
      Attacker calls the source-chain bridge entry point, supplying:
          -fromToken = address(0)
          -toToken = <any valid ERC-20 or _ETH_ADDRESS_>
          -A positive amount and valid _receiver address.

2. Message Packaging by Gateway
      The gateway protocol bundles the raw parameters—including the true zero address—into its cross-chain message payload without filtering.

3. Relayer Broadcasts to Destination
    A relayer/oracle node observes the new message on Chain A and invokes the on-chain gateway on Chain B, passing along fromToken = address(0) exactly as received.

4. Destination Contract’s onCall Execution
   - GatewayTransferNative.onCall(...) begins processing and reads fromToken from the message.
   - It does not check require(fromToken != address(0)).

5. Unconditional ERC-20 Call
   - The contract executes:
    IERC20(fromToken).transferFrom(user, address(this), amount);
   - Since fromToken == address(0), this translates to IERC20(address(0)).transferFrom(...).

6. Low-Level Revert / DoS Triggered
    -Calling a function on the zero address is invalid and causes an out-of-gas or low-level revert.
    -onCall (and thus the entire cross-chain invocation) aborts.

7. Denial-of-Service Outcome
    No further messages in the gateway’s queue can be processed until this malformed one is cleared or circumvented, effectively halting the bridge.

### Impact

Denial of service (DoS) for legitimate transactions.

### PoC

_No response_

### Mitigation

Zero‐Address Guard: Immediately after decoding fromToken and toToken, add:

    if (fromToken == address(0) || toToken == address(0)) revert ZeroAddress();
or require them to be either _ETH_ADDRESS_ or legitimate ERC‐20 addresses.
