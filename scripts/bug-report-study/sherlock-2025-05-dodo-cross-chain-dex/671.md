# DODO-CROSSCHAIN-DEX Zero Abort Address DOS the Zetachain Gateway OnAbort Mechanism

### Summary

In `GatewayTransferNative.sol` and `GatewayCrosschain.sol`, the `Withdraw` & `WithdrawAndCall` functions, when making calls to the `gateway.Withdraw`, incorrectly sets the `AbortAdress` to `address(0)` which when the call is made to the ZetaChain's gaateway contract, the call would always revert. 

### Root Cause

The bug exists in the DODO Protocol's cross-chain withdrawal implementation where the abort address is set to `address(0)` (the zero address).
`GatewayTransferNative.withdraw`
```Solidity
 /**
     * @notice - Function to withdraw using gateway
     * @param sender Sender address
     * @param outputToken output token address
     * @param amount amount to withdraw
     */
    function withdraw(
        bytes32 externalId,
        bytes memory sender,
        address outputToken,
        uint256 amount
    ) public {
        gateway.withdraw(   // @> calls th gateway here
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),   // @>
                revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
        );
    }
```
`GatewayTransferNative.WithdrawAndCall`
```solidity
 function withdrawAndCall(
        bytes32 externalId,
        bytes memory contractAddress,
        address targetZRC20,
        uint256 outputAmount,
        bytes memory receiver,
        bytes memory message
    ) internal {
        gateway.withdrawAndCall(   // @> calls the gateway here
            contractAddress,
            outputAmount,
            targetZRC20,
            message,
            CallOptions({
                isArbitraryCall: false,

            }),
            RevertOptions({

```
Same process for `GatewayCrossChain.Withdraw` and `GatewayCrossChain.WithdrawAndCall`

When a cross-chain transaction fails and its subsequent revert handling also fails, ZetaChain attempts to execute the abort path. However, ZetaChain's [`executeAbort`](https://github.com/zeta-chain/protocol-contracts/blob/2e61e029e89792c1b10ed15d2aa19818a77dd4d8/contracts/zevm/GatewayZEVM.sol#L497-L513) function explicitly validates against zero addresses with `validateNonZeroAddress()` and reverts with an `EmptyAddress()` error when provided with [`address(0)`](https://github.com/zeta-chain/protocol-contracts/blob/2e61e029e89792c1b10ed15d2aa19818a77dd4d8/contracts/zevm/libraries/GatewayZEVMValidations.sol#L22-L24).

>>Refer to this from Zetachain's gateway contract
```solidity
    /// @notice Call onAbort on a user-specified contract on ZEVM.
    /// this function doesn't deposit the asset to the target contract. This operation is done directly by the protocol.
    /// the assets are deposited to the target contract even if onAbort reverts.
    /// @param target The target contract to call.
    /// @param abortContext Abort context to pass to onAbort.
    function executeAbort(
        address target,
        AbortContext calldata abortContext
    )
        external
        nonReentrant
        onlyProtocol
        whenNotPaused
    {
        GatewayZEVMValidations.validateNonZeroAddress(target);
        Abortable(target).onAbort(abortContext);
    }
```
Proceeds to call --> `validateNonZeroAddress`
```solidity
    function validateNonZeroAddress(address addr) internal pure {
        if (addr == address(0)) revert EmptyAddress();
    }
```
This means that the `ExecuteAbort` function will fail if the address is address 0.

This breaks the final fallback mechanism for failed transactions, potentially leading to permanent loss of user funds with no recovery path. The protocol's implementation of ``withdrawAndCall` and `Withdraw` lacks proper error handling for this worst-case scenario.

### Internal Pre-conditions

1. `withdrawToNativeChain` needs to be called which proceeds to call `_handleEvmOrSolanaWithdraw` which then calls the `withdrawAndCall`, then finally `gateway.withdrawAndCall` is triggered.
2. The public `withdraw` function in the GatewayTransferNative contract needs to be triggered.

### External Pre-conditions

1. A cross-chain withdrawal transaction fails.
2. The subsequent `onRevert` function call also fails.
3. When this double-failure scenario occurs, ZetaChain attempts to execute the abort path with the configured abort address (address(0)), which will always revert at the validation step, leaving user funds with no recovery mechanism.

### Attack Path

The abort address has been set to address(0) already from the code.
1. User calls `withdrawToNativeChain` to move assets from ZetaChain to a connected chain.
2. `withdrawToNativeChain` calls `_handleEvmOrSolanaWithdraw`. `_handleEvmOrSolanaWithdraw` calls internal `withdrawAndCall` , `withdrawAndCall` calls ZetaChain's gateway with `abortAddress: address(0)`
3.  The transaction on the connected chain fails (which zetachain designed the abort mechanism for)
4. ZetaChain attempts to call onRevert on the protocol contract.  The `onRevert` function also fails
5. ZetaChain tries to execute the abort flow: Calls `executeAbort(address(0)`,  `executeAbort` immediately runs `validateNonZeroAddress(address(0))`
This validation fails with `EmptyAddress()` error
6. The entire abort mechanism fails to execute.  

### Impact

1. User funds can become permanently trapped with no recovery path.
2. DOS to the onAbort mechanism
