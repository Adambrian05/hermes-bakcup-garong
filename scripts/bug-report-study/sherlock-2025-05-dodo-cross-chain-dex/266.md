# Users can steal funds meant for refunds through `_doMixSwap`

### Summary

When user bridge from chain A to chain B, it always go trough zeta chain `GatewayTransferNative`, or `GatewayCrossChain` contract. 
User provides `payload` data, which holds `(DecodedMessage memory decoded, MixSwapParams memory params)` for ZetaChain, or destination chain.
`MixSwapParams` are used if user wants to swap bridged assets on `GatewayTransferNative/GatewayCrossChain`. However, there is a significant problem:
The `onCall` function doesn't verify that the token that we want to swap matches the bridged asset (token that the user has sent from source):
```solidity
    function _doMixSwap(
        bytes memory swapData, 
        uint256 amount, 
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }

        IZRC20(params.fromToken).approve(DODOApprove, amount);
        return IDODORouteProxy(DODORouteProxy).mixSwap(
            params.fromToken,
            params.toToken,
            params.fromTokenAmount,
            params.expReturnAmount,
            params.minReturnAmount,
            params.mixAdapters,
            params.mixPairs,
            params.assetTo,
            params.directions,
            params.moreInfo,
            params.feeData,
            params.deadline
        );
    }
```
[_doMixSwap](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L337-L362) function is approving and swapping `params.fromToken`, which may be different than the zrc20 provided. This can be exploited by user by bridging a cheap token (Pepe) and using an expensive one (Eth) as `params.fromToken` . The following way the user will steal eth allocated for refunds.

### Root Cause

It is not validated if `MixSwapParams.fromToken`  matches the bridged ZRC20

### Internal Pre-conditions

- Funds allocated for refunds in `GatewayTransferNative/GatewayCrossChain`
- Cheaper token with same decimals used for the deposit in `GatewaySend` 

### External Pre-conditions

None

### Attack Path

1. Victim's transaction reverted and 1 eth is waiting in `GatewayCrossChain` to be claimed as a refund.
2. Exploiter calls `GatewaySend::depositAndCall` providing 1e18 DAI, but encoded swap data for where `fromToken == ethZRC20`
3. Transaction is bridged, 1e18 zrc20 eth is bridged for `USDC : eth` on ZetaChain 
4. The USDC representation of 1 eth is send to the exploiter on Mainnet 
5. Victim can claim his funds only if another user funds enter the contract for refunds

### Impact

Theft of funds allocated for refunds

### PoC

_No response_

### Mitigation

Validate that `MixSwapParams.fromToken == zrc20`
