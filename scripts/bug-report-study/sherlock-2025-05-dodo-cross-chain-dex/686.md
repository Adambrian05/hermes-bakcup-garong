# Missing `MixSwapParams.fromTokenAmount` Check Allows Anyone to Use GatewaySend's ERC20 Balance for Swap

### Summary

A lack of validation on the source of funds for the swap operation within the [`depositAndCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218-L285) function in `GatewaySend` allows an attacker to utilize the contract's own token balances for a swap. An attacker can call `depositAndCall` with a deposit `amount` of 0 for a specific `fromToken`. Simultaneously, they provide `swapData` where `params.fromToken` is the same `fromToken`, but `params.fromTokenAmount` is set to the contract's balance of that token. This results in the `GatewaySend` contract's funds being used for the swap initiated by `_doMixSwap`, and the output of this swap is then sent cross-chain.

### Root Cause

In `GatewaySend`, the `depositAndCall` function takes a user-specified `amount` of `fromToken` to be deposited. However, when `_doMixSwap(swapData)` is called, it decodes `MixSwapParams memory params` from the `swapData`.

Inside `_doMixSwap`:
1.  `MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData)` decodes the user controlled `swapData`. The crucial fields here are `params.fromToken` and `params.fromTokenAmount`.
2.  If `params.fromToken` is not ETH, the contract executes `IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);`. This makes the `GatewaySend` contract approve `DODOApprove` to spend `params.fromTokenAmount` of its own (`address(this)`) balance of `params.fromToken`.
3.  The subsequent call `IDODORouteProxy(DODORouteProxy).mixSwap(...)` uses `params.fromTokenAmount` as the amount to be swapped.

The bug lies in the fact that the `amount` deposited by the user (which can be 0) is not directly used or validated against `params.fromTokenAmount` which is taken from `swapData` and used in the `_doMixSwap` function. If the contract holds `params.fromToken` (e.g., USDC), it will approve and allow `DODORouteProxy` to use its own balance for the swap.

### Internal Pre-conditions

1.  The `GatewaySend` contract must have a non-zero balance of an ERC20 token that the attacker intends to drain.
2.  `DODORouteProxy` and `DODOApprove` addresses must be correctly set in `GatewaySend`.
3.  The attacker must know an ERC20 token that `GatewaySend` holds.

### External Pre-conditions

1.  The DODO protocol must have a liquidity pool for the swap pair defined in `swapData` (e.g., USDC/USDT).
2.  The `gateway` must be operational for the cross-chain message to be processed.

### Attack Path

1.  **Pre-condition:** `GatewaySend` contract holds 1000 USDC.
2.  **Attacker's Action:** The attacker calls `GatewaySend.depositAndCall` with the following parameters:
    *   `fromToken`: `address(USDC)`
    *   `amount`: `0`
    *   `swapData`: Crafted by the attacker. When decoded by `SwapDataHelperLib.decodeCompressedMixSwapParams`, this `swapData` yields:
        *   `params.fromToken`: `address(USDC)`
        *   `params.toToken`: `address(USDT)` or any other token
        *   `params.fromTokenAmount`: `1000 * 10**6`. The amount to drain.
        *   `params.minReturnAmount`: `0` to ensure the swap is executed.
        *   Other `MixSwapParams` fields are valid.
    *   `asset`: `address(USDT)` the token the attacker wants to receive cross-chain.
    *   `dstChainId`: A valid destination chain ID.
3.  **Execution within `depositAndCall`:**
    *  `IERC20(fromToken).transferFrom(msg.sender, address(this), amount)` is called. Since `amount` is `0`, this transfers 0 USDC from the attacker to `GatewaySend` and succeeds.
    *   `uint256 outputAmount = _doMixSwap(swapData);` is called.
        *   Inside `_doMixSwap`: `IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);` executes as `IERC20(USDC).approve(DODOApprove, 1000 * 10**6);`. The `GatewaySend` contract approves `DODOApprove` to spend 1000 of its *own* USDC.
        *   `IDODORouteProxy(DODORouteProxy).mixSwap(...)` is called with `params.fromTokenAmount`. The `DODORouteProxy` will pull 1000 USDC from `GatewaySend`'s balance for the swap to USDT via `DODOApprove.claimTokens`.
    *   The `outputAmount` is returned.
    *   This `outputAmount` of USDT is then prepared and sent via `gateway.depositAndCall` to the `targetContract` on `dstChainId`, as specified by the attacker.
4.  **Result**: The `GatewaySend` contract's 1000 USDC balance is used in the swap. The attacker receives the swapped USDT on the destination chain.

### Impact

The `GatewaySend` contract suffers a direct loss of its ERC20 token holdings (up to the amount specified in `swapData.fromTokenAmount` if the contract has sufficient balance). The attacker does not need to supply these tokens; they exploit the contract to use its own funds for a swap and subsequent cross-chain transfer that benefits the attacker. The severity is **Critical** as it leads to direct theft of funds from the contract.

### PoC

_No response_

### Mitigation

In `_doMixSwap`, `params.fromTokenAmount` should be validated against the `amount` that was actually transferred from the user in the `depositAndCall` function.
