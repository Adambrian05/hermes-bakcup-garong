# Swap deadline calculated from execution time allows stale price execution

### Summary

The [_swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L302) function calculates swap deadlines from execution time rather than user submission time, allowing swaps to execute under market conditions vastly different from when users initiated transactions. Combined with cross-chain processing delays and low priority fees, users can be forced into unfavorable swaps that should have expired.

### Root Cause

The [function](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L325) sets swap deadline using current execution timestamp:
```solidity
IUniswapV2Router01(UniswapRouter).swapTokensForExactTokens(
    gasFee,
    amountInMax, 
    getPathForTokens(targetZRC20, gasZRC20),
    address(this),
    block.timestamp + MAX_DEADLINE  // @audit -> deadline from execution time, not submission time
);
```
Deadline protection is designed to prevent swaps from executing after market conditions have changed significantly from when users made their trading decisions. However, this implementation completely misses that protection by effectively resetting the deadline clock at execution time. Current implementation using `block.timestamp` to calculate deadline is equivalent to saying "execute this swap anytime, regardless of how long it's been delayed" rather than "execute only if we're still within the user's time tolerance." 

### Internal Pre-conditions

None

### External Pre-conditions

TX sitting in a mempool for a prolonged time will mean that gas-token swap can easily get executed at prices which would otherwise be unacceptable for user.

### Attack Path

1. GatewayCrossChain's `onCall` is called with a certain gas price bid and priority fee. TX involves doing a Uniswap swap on ZetaChain to buy gas-token, in order to pay for final leg of withdrawing funds to destination chain. Slippage protection is set according to current market prices
2. Market price spike, causing TX to sit in mempool due to too low priority fee or gas price bid
3. After ie. 10 min, TX gets included and executed. If deadline was properly implemented (based on submission time and not execution time), TX would revert due to swap executing after the deadline. However, since dealine protection is totally ineffective, swap gets executed at a price much more unfavorable for the user, effectively causing the loss of funds

### Impact

Medium severity - this vulnerability breaks core contract functionality by executing swaps under market conditions users never consented to. Users become locked into transactions at prices significantly worse than submission time, with no staleness protection. 

### PoC

_No response_

### Mitigation

Do not use `block.timestamp` for deadline calculation. That way deadline will be properly set based in submission time and not execution time.
