# Unsafe ERC20 transfer in `GatewaySend::onCall` may lead to stuck funds

### Summary

Improper use of raw `ERC20.transfer` without return value verification will cause a silent token transfer failure for users as some ERC20 tokens return `false` on failure instead of reverting, allowing the transfer to fail silently and funds to remain stuck in the contract.

### Root Cause

In [`GatewaySend::onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L372) the `ERC20.transfer` function is called without checking its return value, which is unsafe as some tokens return `false` on failure instead of reverting, leading to silent transfer failures. The transferred tokens remain stuck in the contract, as there is no `superWithdraw` or owner withdrawal mechanism implemented to recover them. The code must be updated to use the `TransferHelper` library.

### Internal Pre-conditions

1. The gateway needs to invoke `onCall()` to initiate a token transfer via `IERC20(toToken).transfer(...)`.
2. The `toToken` must be an ERC20 token that returns `false` on `transfer()` failure instead of reverting.
3. The contract must not revert on a failed `transfer()`, allowing the transaction to succeed even if the token is not transferred.
4. There must be no recovery mechanism (e.g., `superWithdraw`) for the stuck tokens in the contract.

### External Pre-conditions

1. The ERC20 token standard implementation used by `toToken` must be returns `false` on `transfer` failure instead of reverting.
2. The external token contract must be deployed and accessible by the `GatewaySend` contract during the transfer operation.
3. No external protocol or user intervention occurs to recover or refund the stuck tokens after the silent transfer failure.

### Attack Path

1. The gateway triggers `onCall()`, with `toToken` which returns `false` on failed transfers instead of reverting.
2. The contract calls `IERC20(toToken).transfer(evmWalletAddress, outputAmount)` without checking the return value.
3. The token’s `transfer` call returns `false` due to failure, but the contract does not detect it and does not revert.
4. The tokens are not transferred but remain stuck inside the contract.
5. Because there is no recovery or withdrawal mechanism for stuck tokens, the user’s funds become inaccessible.

### Impact

The users suffer an approximate loss of funds stuck in the contract due to silent transfer failures. The users cannot retrieve their tokens because the contract does not revert or provide a mechanism to recover failed transfers.

### PoC

_No response_

### Mitigation

Replace all raw `ERC20.transfer` calls with `TransferHelper.safeTransfer` to ensure the transfer succeeds or reverts on failure. This enforces checking the return value and prevents silent transfer failures that can cause funds to get stuck in the contract.
