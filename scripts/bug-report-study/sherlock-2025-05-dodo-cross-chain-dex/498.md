# Anyone can steal refunds intended for Solana receivers

### Summary

The `claimRefund` function in the `GatewayCrossChain` has flawed authorization logic that allows anyone to steal refunds intended for non-EVM addresses (like Solana). When the refund recipient is not a 20-byte EVM address, the function allows any caller to claim the funds, effectively stealing them from rightful owners.

### Root Cause

When `GatewayCrossChain` calls the protocol gateway to move the funds, it [encodes](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L265) the receiver address to be refund recipient as well (will be used later in `onRevert` and `claimRefund`):
```solidity
    function withdrawAndCall(
        bytes32 externalId,
        bytes memory contractAddress,
        address targetZRC20,
        uint256 outputAmount,
        bytes memory receiver,
        bytes memory message
    ) internal {
        gateway.withdrawAndCall(
            contractAddress,
            outputAmount,
            targetZRC20,
            message,
            CallOptions({
                isArbitraryCall: false,
                gasLimit: gasLimit
            }),
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, receiver), // @audit receiver is encoded here to be refund recipeint
                onRevertGasLimit: gasLimit
            })
        );
    }
```

In case that destination is Solana, the encoded receiver will be 32 bytes length (vs. 20 bytes if destination chain is EVM). If cross-chain TX fails on the destination chain, protocol will call [onRevert](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517) function of the `GatewayCrossChain`. 
```solidity
    function onRevert(RevertContext calldata context) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:];

        if(context.revertMessage.length == 52) {
            address receiver = address(uint160(bytes20(walletAddress)));
            TransferHelper.safeTransfer(context.asset, receiver, context.amount);

            emit EddyCrossChainRevert(
                externalId,
                context.asset,
                context.amount,
                walletAddress
            );
        } else {
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress // @audit refundInfo is created with Solana receiver stored here
            });
            refundInfos[externalId] = refundInfo;
            
            emit EddyCrossChainRefund(
                externalId,
                context.asset,
                context.amount,
                walletAddress
            );
        }
    }
```

In the case of Solana receiver, `revertMessage` will be longer than 52 bytes (32 bytes ID + 32 bytes walletAddress). So `RefundInfo` get created in the storage. 

Next, there is [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571) function which shall be used by rightful users or bots to get their refunds:
```solidity
    function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if (refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); // @audit faulty check
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");

        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        // ...
    }
```

That's were the core of the issue is - due to the broken implementation, **anyone** can call this function and claim the refund:

1. Solana address is 32 bytes, so `refundInfo.walletAddress.length == 20` is false
2. `receiver` remains as msg.sender (the caller)
3. Authorization check becomes: `require(bots[msg.sender] || msg.sender == msg.sender)`
4. Since `msg.sender == msg.sender` is always true (no matter who is the caller), check passes and refund is claimed/stolen


### Internal Pre-conditions

None

### External Pre-conditions

Cross-chain TX to Solana fails, so revert mechanism is triggered

### Attack Path

1. Attacker monitors `EddyCrossChainRefund` events for refunds with non-20-byte addresses
2. Attacker calls `claimRefund(externalId)` for any such refund
3. Attacker receives refund tokens intended for non-EVM address holders

### Impact

High severity - this vulnerability enables systematic theft of all refunds intended for non-EVM addresses

### PoC

_No response_

### Mitigation

For non-EVM addresses, allow only trusted bots to claim the refunds
