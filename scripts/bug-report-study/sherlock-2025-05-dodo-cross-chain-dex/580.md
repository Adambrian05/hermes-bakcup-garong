# withdrawToNativeChain doesn't properly handle the case in which ZRC20 == nativeToken

### Summary

As it can be seen from the `withdrawToNativeChain` the function intends to handle the case in which the native token is the ZRC20 (i.e. Zeta), but there are multiple mishaps within the handling of this case within the function which make it exploitable in multiple ways explained in this report.

### Root Cause

The problems with the handling of the native token within `withdrawToNativeChain` are multiple, including but not limited to:

1. The function never checks if the msg.value >= amount, when the zrc20 == ETH_ADDRESS;
2. `_doMixSwap` never checks if the native token is in-question or a ZRC20 one (it always performs a ZRC20 approval);
3. The Zeta token isn't exchanged to WZETA prior to it;

Although the `withdrawToNativeChain` function is payable and expects to handle the native token, as it checks for said case, the function isn't equipped in multiple ways to handle it:

```solidity

 function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 

        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);

        // Decode message and decompress swap params
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message);
        
        // Check if the message is from Bitcoin to Solana
        // address evmWalletAddress = (decoded.dstChainId == BITCOIN_EDDY || decoded.dstChainId == SOLANA_EDDY)
        //     ? msg.sender
        //     : address(uint160(bytes20(decoded.receiver)));

        // Transfer platform fees
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // platformFee = 5 <> 0.5%
        amount -= platformFeesForTx;

        // Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);

```

First, function logic checks if ZRC20 == ETH_ADDRESS, if it does, it won't perform a transfer. The first problem is that the function never checks if the msg.value provided is equal to or higher than the amount.

Second, when `_handleFeeTransfer` is invoked, it always treats the token as a ZRC20 token, instead of a native one:

```solidity

    function _handleFeeTransfer(
        address zrc20,
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }

```
This wouldn't work as the native token isn't a ZRC20 token, there's no condition which handles the case in which the token is the native one, and Zeta isn't wrapped prior to the fee transfer.

A similar case is also present in the `_doMixSwap` as it always treats it as a ZRC20 token (with the approve method):

```solidity

 function _doMixSwap(
        bytes memory swapData, 
        uint256 amount, 
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }

        IZRC20(params.fromToken).approve(DODOApprove, amount);
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(

```

Due to a multitude of reasons mentioned above, the function logic isn't equipped to handle the native token, and these calls would always revert.
