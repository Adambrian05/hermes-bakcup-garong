# _calcExternalId doesn’t utilize block.chainid in the creation of the hash leading to collisions and loss of funds

### Summary

`_calcExternalId` generates a hash which is used as a key in order to store the revert information so that later it can be claimed by the user. The problem is if a transaction originating from a connected chain (non-zeta) to Zeta fails both the onCall and doesn't have enough funds to cover the revert gas fee OR if the revert call itself reverts, the abort flow is initiated.

The problem is that the onAbort might store calls from different chains (e.g. Arbitrum, Optimism), and by not including a block.chainid when producing the hash, two identical external ids can be created for two different transactions, on two different chains.

### Root Cause

Creation/calculation of the externalId so that it can be included as part of the message/revert options in the cross-chain transaction:

```solidity

function _calcExternalId(address sender) internal view returns (bytes32 externalId) {
        externalId = keccak256(abi.encodePacked(address(this), sender, globalNonce, block.timestamp));
    }

```

If a transaction from a Connected chain -> ZetaChain fails during the onCall, the revert flow is initiated to send the funds back to the originating chain. If the funds aren't enough to cover the gas/protocol fee or the onRevert call reverts, the onAbort flow is initiated on Zetachain:

```solidity

function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }

``` 

It should also be noted that refund infos are also stored during the onRevert call in both the cross-chain and native Gateway when the revert message is longer than 52 bytes:

```solidity

 } else {
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress
            });
            refundInfos[externalId] = refundInfo;
            
            emit EddyCrossChainRefund(

                context.asset,
                context.amount,
                walletAddress
            );

```

Since the onAbort call will store hashes from different chains, it means that two transactions originating from two different chains can have the same hash due to the lack of inclusion of the block.chainId in it. 

Since function flow doesn't check if the revert info already exists, this would overwrite a previous revertInfo with the same externalId causing the previous one to be lost.

Considering that the amount being sent or another differentiating factor isn't included in the hash as well, it means that a "newer" revert could replace an already existing one with the same id, and the new one can have less funds, causing fund loss.

### Internal Pre-conditions

1. The address of the send gateway is the same on two different chains.
2. The nonce is the same on said chains.

### External Pre-conditions

1. The same address initiates a cross-chain transaction at the same time on different chains (for e.g. Arbitrum and Base).

### Impact

If two transactions are initiated by the same address on two different chains at the same time (assuming an identical nonce) and both fail, the revert information for only one will be stored due to the lack of inclusion of the block.chainId in the hash generation.

### Mitigation

Include block.chainid in the generation of the hash, ideally also include other differentiating factors like the amount being sent, the target token, and/or also include a check if the same externalId already exists in the `onAbort`, `onRevert` flow, and if it does, create a mechanism to handle that scenario.
