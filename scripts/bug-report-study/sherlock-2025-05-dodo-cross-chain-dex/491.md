# Bitcoin Address Truncation in Revert Message Causes Failed Refunds

## Summary

Bitcoin address truncation to 20 bytes will cause permanent fund loss for Bitcoin users as the protocol will lose critical address information when processing reverted cross-chain transactions.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277-L295

## Root Cause

In `GatewayCrossChain.sol:291` the `bytes20(sender)` truncation loses Bitcoin address data as Bitcoin addresses require more than 20 bytes when encoded from their string representation.

## Internal Pre-conditions

1. User needs to initiate a cross-chain swap from any chain to Bitcoin
2. The transaction needs to fail or revert on the destination chain  
3. The revert mechanism needs to trigger to process the refund

## External Pre-conditions

1. Bitcoin transaction needs to fail on the destination chain due to network issues, insufficient gas, or other factors

## Attack Path

1. User initiates cross-chain swap to Bitcoin with a valid Bitcoin address (e.g., `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4` - 42 bytes)
2. Transaction fails on destination chain, triggering revert mechanism
3. Protocol truncates Bitcoin address from 42 bytes to exactly 20 bytes using `bytes20(sender)`, losing 22 bytes of critical address data (`r3zarvary0c5xw7kv8f3t4`)
4. `onRevert()` function receives corrupted address data that represents an invalid Bitcoin address (`bc1qw508d6qejxtdg4y5`)
5. Refund process attempts to use truncated address, making it impossible to identify the correct recipient
6. User's funds become permanently locked in the refund system

## Impact

Bitcoin users suffer a 100% loss of their swapped funds when transactions revert. The protocol permanently locks user funds as the truncated Bitcoin addresses become invalid and unusable for refund processing.

## Technical Deep Dive

### How Address Truncation Destroys Bitcoin Addresses

**Original Bitcoin Address**: `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4` (42 bytes)

**Step 1 - Address as bytes**:
```js
[0x62, 0x63, 0x31, 0x71, 0x77, 0x35, 0x30, 0x38, 0x64, 0x36, 0x71, 0x65, 0x6a, 0x78, 0x74, 0x64, 0x67, 0x34, 0x79, 0x35, 0x72, 0x33, 0x7a, 0x61, 0x72, 0x76, 0x61, 0x72, 0x79, 0x30, 0x63, 0x35, 0x78, 0x77, 0x37, 0x6b, 0x76, 0x38, 0x66, 0x33, 0x74, 0x34]
```

**Step 2 - Destructive Truncation**: `bytes20(sender)` takes only the first 20 bytes:
```js
[0x62, 0x63, 0x31, 0x71, 0x77, 0x35, 0x30, 0x38, 0x64, 0x36, 0x71, 0x65, 0x6a, 0x78, 0x74, 0x64, 0x67, 0x34, 0x79, 0x35]
```
Representing: `bc1qw508d6qejxtdg4y5` (INVALID - too short, fails checksum)

**Step 3 - Data Loss**: 22 bytes permanently destroyed:
```js
// LOST: [0x72, 0x33, 0x7a, 0x61, 0x72, 0x76, 0x61, 0x72, 0x79, 0x30, 0x63, 0x35, 0x78, 0x77, 0x37, 0x6b, 0x76, 0x38, 0x66, 0x33, 0x74, 0x34]
// Represents: "r3zarvary0c5xw7kv8f3t4"
```

### Problematic Code Flow

```solidity
// In onCall() - where truncation occurs
RevertOptions({
    revertAddress: address(this),
    callOnRevert: true,
    abortAddress: address(0),
    revertMessage: bytes.concat(externalId, bytes20(sender)), // @error this destroys bitcoin addresses
    onRevertGasLimit: gasLimit

```

```solidity
// In onRevert() - processing corrupted data
function onRevert(RevertContext calldata context) external onlyGateway {
    bytes32 externalId = bytes32(context.revertMessage[0:32]);
    bytes memory walletAddress = context.revertMessage[32:]; // Only 20 bytes available
    
    if(context.revertMessage.length == 52) { // 32 + 20 = 52
        address receiver = address(uint160(bytes20(walletAddress))); // @error Invalid Bitcoin address
        TransferHelper.safeTransfer(context.asset, receiver, context.amount); // @error this fails
    }
}
```

### Bitcoin Address Requirements

| Bitcoin Address Type | Example | Byte Length |
|---------------------|---------|-------------|
| Legacy (P2PKH) | `1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa` | ~34 bytes |
| Script Hash (P2SH) | `3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy` | ~34 bytes |
| Bech32 (P2WPKH) | `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4` | ~42 bytes |
| Bech32m (P2TR) | `bc1p5d7rjq7g6rdk2yhzks9smlaqtedr4dekq08ge8ztwac72sfr9rusxg3297` | ~62 bytes |

**All Bitcoin addresses require more than 20 bytes - the truncation makes ALL invalid.**

## Mitigation

Remove `bytes20()` truncation and preserve full address length in revert messages while adding 1024-byte length validation.
