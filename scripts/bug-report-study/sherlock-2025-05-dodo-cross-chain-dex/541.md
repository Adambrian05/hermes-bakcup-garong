# Mismatch between ETH placeholder causes denial of service for ETH bridging via ZetaChain

### Summary

The `GatewaySend `contract uses `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE `as the ETH placeholder address, while ZetaChain uses the zero address `(address(0))` as the ETH placeholder. This mismatch causes ETH transfers to fail when `onCall` is invoked, resulting in a denial of service for users attempting to bridge ETH.



### Root Cause

In the `GatewaySend `contract, the constant `_ETH_ADDRESS_ `is set to `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE `and is used to identify ETH throughout the contract. However, ZetaChain’s protocol uses `address(0)` to represent ETH. When `onCall `is called by the gateway, it passes `address(0) `for ETH, but the contract checks for `_ETH_ADDRESS_`, causing ETH logic to be skipped and resulting in failed  ETH transfers.

### Internal Pre-conditions

1. The user initiates a cross-chain transfer of ETH using the ZetaChain gateway.
2. The gateway calls `onCall `on the `GatewaySend `contract, passing `address(0)` as the ETH asset.

### External Pre-conditions

ZetaChain protocol is used, which specifies `address(0)` as the ETH placeholder.


### Attack Path

1. User bridges ETH via ZetaChain.
2. The gateway calls `onCall `with `fromToken `or `toToken `set to `address(0)`.
3. The contract checks against `_ETH_ADDRESS_ (0xEeee...)`, so ETH logic is not executed.
4. The transfer fails, resulting in a denial of service for ETH bridging.

### Impact

Users will be unable to bridge ETH using the protocol, resulting in a denial of service for all ETH cross-chain transfers.

### PoC

_No response_

### Mitigation

Update the contract to use `address(0)` as the ETH placeholder to match ZetaChain’s standard, or add logic to treat both `address(0)` and `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE` as ETH.
