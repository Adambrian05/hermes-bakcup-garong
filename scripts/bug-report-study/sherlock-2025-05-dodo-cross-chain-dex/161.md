# Unauthorized Claiming of User Refunds

## Summary

The claimRefund function in the GatewayTransferNative and GatewayCrossChain contracts contains an access control flaw. This flaw occurs due to the incorrect validation of the caller's identity when processing refunds for non-EVM chains (e.g., Bitcoin, Solana). This vulnerability enables any unauthorized user to steal the refunded assets of other users whose transactions to non-EVM chains have failed, resulting in a direct and permanent loss of funds.

## Vulnerability Details

The claimRefund function is designed to allow users or authorized bots to reclaim funds from a failed cross-chain transaction. The logic attempts to differentiate between refunds for EVM-compatible addresses (which are 20 bytes long) and non-EVM addresses.

The faulty logic is in the access control check:

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender; // The receiver defaults to the caller
    if(refundInfo.walletAddress.length == 20) {
        // This path is for EVM addresses.
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    // The check is: caller must be a bot OR the caller must be the receiver.
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    // Tokens are transferred to the 'receiver'.
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];
    // ...
}
```

When a transaction to a non-EVM chain fails, the refundInfo.walletAddress will be a string representing, for example, a Bitcoin address. Its length will not be 20 bytes.

Consequently, the if(refundInfo.walletAddress.length == 20) condition evaluates to false.

The receiver variable retains its default value, which is msg.sender.

The access control check require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER") becomes require(bots[msg.sender] || msg.sender == msg.sender, ...).

Since msg.sender == msg.sender is always true, the entire condition evaluates to true, completely bypassing the access control.

The function then proceeds to transfer the refunded tokens to the receiver, which is the attacker's address (msg.sender).

## Exploitation Scenario:

Alice initiates a transaction to send 10,000 USDC from an EVM chain to her Bitcoin address.

The transaction fails on the destination side, and the onRevert or onAbort function in GatewayTransferNative is triggered.

An EddyCrossChainRefund event is emitted, containing an externalId and Alice's Bitcoin address in the walletAddress field.

An attacker, Bob, is monitoring the chain for these events. He sees Alice's refund event.

Bob calls claimRefund(alice_externalId) from his address.

Inside the function, since Alice's Bitcoin address is not 20 bytes long, the receiver is set to Bob's address (msg.sender).

The require check passes because Bob's address == Bob's address is true.

The contract transfers the 10,000 USDC to Bob. Alice has lost her funds permanently.

## Impact

The impact of this vulnerability is High.

Direct Theft of User Funds: Any attacker can systematically monitor the protocol for failed non-EVM transactions and steal 100% of the refunded amounts.

Permanent Loss of Funds: For affected users, the loss is permanent and irrecoverable. The core safety mechanism of the bridge (refunding failed transactions) is fundamentally broken.

Loss of Trust: This vulnerability completely undermines user trust in the protocol. A bridge that cannot securely handle refunds is not viable. This will lead to catastrophic financial and reputational damage to Eddy Finance.

## Recommendations


The following change is recommended for the claimRefund function:
```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");

    address receiver;
    if(refundInfo.walletAddress.length == 20) {
        // EVM Address Refund Path
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        // Only the intended recipient or a whitelisted bot can claim.
-       require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
+       require(bots[msg.sender] || msg.sender == receiver, "CLAIM_NOT_AUTHORIZED");
+       // The tokens are sent to the rightful owner.
+       TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    } else {
        // Non-EVM Address Refund Path
-       receiver = msg.sender;
-       require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
+       // For non-EVM refunds, ONLY a whitelisted bot can claim the funds.
+       // The bot is then responsible for handling the off-chain refund process.
+       require(bots[msg.sender], "ONLY_BOTS_CAN_CLAIM_NON_EVM_REFUNDS");
+       // The bot receives the tokens to process the refund.
+       receiver = msg.sender;
+       TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    }
    
-   TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender) // Log the address that initiated the claim
    );
}
```
