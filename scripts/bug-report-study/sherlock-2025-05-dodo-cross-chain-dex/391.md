# externalIds can be overridden by anyone with malicious revertOptions initiated from an arbitrary address

### Summary

Currently Native and Cross-chain adapters save the revert information in both onAbort and onRevert for failed transactions based on an externalId. The problem is that a malicious actor can "override" a legitimate saved revert with a 0 or near 0 amount causing the original sender's tokens to be lost.

### Root Cause

In both onAbort and onRevert there's a mechanism which stores the reverts based on the externalId, so that the original sender (or a bot) can later claim them:

```solidity

    function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }

```

The saved refund info can later be claimed by the transaction initiator or a bot via `claimRefund`:

```solidity

function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }

```

The problem is that any arbitrary user can initiate a transaction on ZetaChain which can intentionally be made to fail (target contract that reverts, not enough gas, etc. ) with custom revert options which can set the revert and abort address as the Gateway contract, callOnRevert set as true, with the externalId the malicious actor wants to override, and the revertMessage can be made bigger than 52 bytes so that it's overridden immediately in the revert flow.

```solidity

 RevertOptions memory revertOptions = RevertOptions({
            revertAddress: GatewayContract,
            callOnRevert: true,
            abortAddress: GatewayContract,
            revertMessage: bytes.concat(maliciousExternalId, bytes20(msg.sender)),
            onRevertGasLimit: gasLimit
        });

```

This will override the already existing revertInfo with a new one with the same externalId but in this case a new wallet address and a new amount. The original sender's revert info stored, together with the funds will be "lost" and won't be able to be claimed.

### Internal Pre-conditions

1. There's a stored revertInfo which hasn't been claimed.

### External Pre-conditions

1. A malicious actor sends a transaction with the revert and abort address set as the gateway which is intentionally made to revert. This will trigger the onRevert (or onAbort) flow, and since they've included a malicious externalId, this will override the stored one causing fund loss.

### Attack Path

1. Malicious actor initiates a ZetaChain -> Connected Chain transaction which is intentionally made to revert, with the revert/abort address set as the Gateway contract with the revertMessage containing the externalId they want to override.
2. Transaction fails on Connected chain and a revert flow is triggered on ZetaChain by calling the onRevert function on the Gateway contract.
3. They made the revert message greater than 52 bytes so that the `else` clause in `onRevert` is triggered and the revert info is stored instead of it being immediately sent to the wallet.
4. Since they included whatever externalId they want in the revertMessage, this overrides an existing legitimate revert info with a new malicious one with a 0 amount (or a low one for that matter) with a random address.
5. The malicious actor successfully overrode a legitimate revert info causing the funds stored as part of it to be forever lost.

### Impact

Legitimate stored revert info information containing fund info that should be later claimed by the bot or original sender can be overridden by malicious users causing the funds to be lost.

_No response_

### Mitigation

Check who the original sender of the transaction is to ZetaChain and make sure that it's a trusted Gateway, or create a mechanism which will check if a revertInfo is stored under a certain externalId (i.e. isn't empty) and if it is, handle it in a different way.
