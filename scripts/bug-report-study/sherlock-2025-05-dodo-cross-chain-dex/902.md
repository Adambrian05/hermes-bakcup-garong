# Incorrect Access Control in `claimRefund`: Anyone Can Claim Refunds

### Summary

The `claimRefund()` function in both `GatewayCrossChain` and `GatewayTransferNative` contracts allows **unauthorized users** to claim refunds that belong to other users. This is due to a flawed access control check that assumes all `walletAddress` values are exactly 20 bytes long. When this assumption fails (e.g. non-EVM addresses like Solana or Bitcoin), the contract defaults to comparing `msg.sender` with itself, letting **anyone** claim the funds.

### Root Cause

`claimRefund()` function:

- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680
- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    
    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }

    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    ...
}
```

If `walletAddress.length != 20`, the `receiver` is left as `msg.sender`, and **any** caller becomes authorized. So, refunds with non-20-byte wallet addresses (common in cross-chain flows) are left unprotected.


### Internal Pre-conditions

1. A refund entry exists in `refundInfos` (from failed cross-chain swap).
2. Refund entry has a `walletAddress` that is not exactly 20 bytes.
3. Tokens are stored and available for refund in the contract.


### External Pre-conditions

1. Any user on ZetaChain can call `claimRefund()`.
2. Refunds use wallet addresses longer or shorter than 20 bytes (e.g., Bitcoin/Solana).
3. No `bots[msg.sender] == true`.

### Attack Path

1. A legitimate user triggers a refund from a Bitcoin or Solana destination.
2. `walletAddress` is set to something non-EVM (e.g., 32 bytes Solana address).
3. A malicious user monitors the blockchain for refund entries with non-20-byte `walletAddress`.
4. Attacker calls `claimRefund(externalId)` and:

   - Bypasses the `require` check
   - Becomes authorized by default
   - Steals the funds intended for the original cross-chain user.

### Impact

- Loss of user funds: Any refund with non-standard `walletAddress` can be stolen.
- Loss of trust: Refunds meant for cross-chain users are vulnerable to front-running and theft.
- No recovery: Stolen funds are transferred out without recourse.
