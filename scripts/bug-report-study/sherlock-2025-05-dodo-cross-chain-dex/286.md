# Attacker can steal refunds on GatewayCrossChain by depositing higher decimals token amount and providing malicious payload with targetZRC20 with low decimals on the source chain

### Summary

`GatewayCrossChain` contract has ZRC20 tokens in its balance that were refunded by ZetaChain in case when cross-chain transaction (CCTX) reverted. These refunds are supposed to be claimed by receivers in `claimRefund()` function.

When users want to make CCTX from connected chain to ZetaChain, they call `GatewaySend.depositAndCall()` on the source chain and transfer ERC20 and amount to the contract, which then transfer them to `Gateway`. Alongside with `ERC20`, users provide custom payload that include the `targetZRC20` token they want to get on ZetaChain.

The issue is that since `GatewayCrossChain` on ZetaChain might have different tokens in its balance as refunds, malicious user can provide high decimal token on the connected chain but craft payload with `targetZRC20` of low decimal token to steal refunds.

Suppose that `ERC20` user provides is `SHIB` with 18 decimals on ethereum, and user crafts the payload so that `targetZRC20 == USDC.ETH` on Zetachain with 6 decimals. The `ZRC20` user should receive is `ZRC20.SHIB`, but since `targetZRC20` is not validated and `GatewayCrossChain` holds refunds in its balance, user would receive `USDC.ETH` tokens. 

Also suppose that `GatewayCrossChain` contract holds `1000e6` `USDC.ETH` in balance that are due to be claimed.

Malicious user then needs to provide `SHIB` `amount == 1000e6`, which would equal to `0.000000001 shib` if we divide `1000e6 / 1e18`, a very low amount of usd (1 shib equals to 0.000013 usd). On the ZetaChain they would receive `1000e6` usdc from refund amounts, stealing from users.

### Root Cause

When users want to make CCTX, they [call](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L287-L292) `GatewaySend.depositAndCall()` function on connected chain:
```solidity
function depositAndCall(
        address targetContract,
        uint256 amount,
        address asset,
        uint32 dstChainId,
        bytes calldata payload
    ) public payable {
...
```
They [provide an address of the asset and amount](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L316-L318), which are transferred from them to `GatewaySend`:
```solidity
require(
                IERC20(asset).transferFrom(msg.sender, address(this), amount),
                "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
            );
            _handleERC20Deposit(
                targetContract, 
                amount,
                asset, 
                message, 
                revertOptions
            );
```
And in `_handleERC20Deposit()` the `GatewaySend` [approves the `Gateway` to transfer amount of asset](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L184-L193) and calls `gateway.depositAndCall`, which transfers tokens from `GatewaySend` and emits an event, which includes the `message` for call on ZetaChain:
```solidity
function _handleERC20Deposit(
        address targetContract,
        uint256 amount,
        address asset,
        bytes memory message,
        RevertOptions memory revertOptions
    ) internal {
        IERC20(asset).approve(address(gateway), amount);

        gateway.depositAndCall(
            targetContract,
            amount,
            asset,
            message,
            revertOptions
        );
    }
```
The `message` is the `payload` user provide to `GatewaySend.depositAndCall()`. This `payload` contains the `targetZRC20` token user wants to receive on `ZetaChain`.

When CCTX gets validated, the `GatewayZEVM` on ZetaChain transfers the equivalent of zrc20 `asset` on connected chain to `GatewayCrossChain` contract and calls the `onCall()` function:
```solidity
function depositAndCall(
        MessageContext calldata context,
        address zrc20,
        uint256 amount,
        address target,
        bytes calldata message
    )
        external
        nonReentrant
        onlyProtocol
        whenNotPaused
    {
        if (zrc20 == address(0) || target == address(0)) revert ZeroAddress();
        if (amount == 0) revert InsufficientZRC20Amount();
        if (target == PROTOCOL_ADDRESS || target == address(this)) revert InvalidTarget();

        if (!IZRC20(zrc20).deposit(target, amount)) revert ZRC20DepositFailed();
        UniversalContract(target).onCall(context, zrc20, amount, message);
    }
```
The `zrc20` and `amount` here are ZRC20 equivalent of `asset`, and `amount` transferred from user on `GatewaySend.depositAndCall()`.

The `onCall()` function decodes the `message`, do the swap in dodo if any swap data was provided and [initiates withdrawal](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442-L510) via `_handleEvmOrSolanaWithdraw()`, which approves the `decoded.targetZRC20` tokens to ZetaChain `Gateway` along with the gas tokens:
```solidity
IZRC20(gasZRC20).approve(address(gateway), gasFee);
        IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);
```
At the end of the flow [`withdrawAndCall()` is called](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L244-L269) on gateway with `targetZRC20`:
```solidity
function withdrawAndCall(
        bytes32 externalId,
        bytes memory contractAddress,
        address targetZRC20,
        uint256 outputAmount,
        bytes memory receiver,
        bytes memory message
    ) internal {
        gateway.withdrawAndCall(
            contractAddress,
            outputAmount,
            targetZRC20,
            message,
            CallOptions({
                isArbitraryCall: false,
                gasLimit: gasLimit
            }),
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, receiver),
                onRevertGasLimit: gasLimit
            })
        );
    }
```
The `Gateway` then transfers `targetZRC20` amounts from `GatewayCrossChain` contract, and receiver encoded in the message receives them on destination chain.
 
`zrc20` equivalent of the `erc20` token on source chain may not match the `targetZRC20` token encoded in the payload. This is done because `GatewayCrossChain` allows users to swap the `zrc20` via dodo so that output token would match the `targetZRC20`. 

However, the issue is that `GatewayCrossChain` may hold refund tokens that are due to be claimed. Malicious user can then provide high-decimal low-value `ERC20` token on the source chain and encode in the message `targetZRC20` token with low-decimals. The `amount` transferred from the `GatewayCrossChain` will match the `amount` of the `ERC20` tokens, but will be in `targetZRC20` token. The exact example described in the summary.

### Internal Pre-conditions

None.

### External Pre-conditions

1. `GatewayCrossChain` must have tokens that were refunded by ZetaChain that are due to be claimed

### Attack Path

1. User creates a `payload` with `targetZRC20` being the tokens `GatewayCrossChain` holds as refund tokens;
2. Uses call the `GatewaySend.depositAndCall()` function on source chain with low-value high-decimal ERC20 token and malicious payload;
3. When CCTX goes through `GatewayCrossChain` contract, the same `amount` that was provided on the source chain will be transferred to receiver on destination chain, but in the `targetZRC20` tokens.

### Impact

Users' refund being stolen by attacker at practically no cost.

### PoC

_No response_

### Mitigation

I think the best way to mitigate is to create a separate smart-contract with only the refund logic so that `GatewayCrossChain` never had any tokens in its balance. And when `GatewayCrossChain.withdrawAndCall` is called, the `revertAddress` would point to that contract:
```diff
function withdrawAndCall(
        bytes32 externalId,
        bytes memory contractAddress,
        address targetZRC20,
        uint256 outputAmount,
        bytes memory receiver,
        bytes memory message
    ) internal {
        gateway.withdrawAndCall(
            contractAddress,
            outputAmount,
            targetZRC20,
            message,
            CallOptions({
                isArbitraryCall: false,
                gasLimit: gasLimit
            }),
            RevertOptions({
-                revertAddress: address(this),
+                revertAddress: refundContract,
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, receiver),
                onRevertGasLimit: gasLimit
            })
        );
    }
```
The same fix should be applied to `GatewayTransferNative` contract.
