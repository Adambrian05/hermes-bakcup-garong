# Zero platformFeesForTx Value Will Cause Transaction Reverts for Users

### Summary

The _handleFeeTransfer functions in GatewayCrossChain.sol and GatewayTransferNative.sol calculate the platformFeesForTx value as:
```solidity
platformFeesForTx = (amount * feePercent) / 1000;
```
These functions are located at:
[GatewayCrossChain.sol:298](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L298)
[GatewayTransferNative.sol:345](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L345)
When the calculated platformFeesForTx is zero, the subsequent call to TransferHelper.safeTransfer fails with a TRANSFER_FAILED error, causing the entire transaction to revert. This results in legitimate transactions being unexpectedly blocked—even though the small amounts involved are not the primary concern.

### Root Cause

The fee calculation logic itself is correct:
```solidity
platformFeesForTx = (amount * feePercent) / 1000;
```
However, in some edge cases, the resulting platformFeesForTx can be zero even for non-zero amount values (e.g., when amount * feePercent < 1000). This zero value is then passed to TransferHelper.safeTransfer (or safeTransferFrom) as the value parameter:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
```
(See full code at [TransferHelper.sol:18-22](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L18-L22)).
Since some tokens do not accept zero-value transfers, this triggers a revert with "TransferHelper: TRANSFER_FAILED". Similarly, in safeTransferFrom (lines 10–14 of the same file), it can trigger a "TransferHelper: TRANSFER_FROM_FAILED" revert.
The functions affected by this logic are:
[GatewayCrossChain.sol:298](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L298)
[GatewayTransferNative.sol:345](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L345)
Thus, while the core fee calculation logic is sound, it does not protect against zero-value transfers for these edge-case scenarios—leading to transaction failures.

### Internal Pre-conditions

- amount is small enough that (amount * feePercent) / 1000 evaluates to zero.

### External Pre-conditions

- The ERC20 (or ZRC20) token used in the transfer must not accept zero-value transfers.

### Attack Path

1. User initiates a swap or cross-chain transfer with a small amount value.
2. The platformFeesForTx calculation results in zero.
3. The transaction attempts to transfer zero tokens to EddyTreasurySafe using TransferHelper.safeTransfer.
4. The zero-value transfer fails due to the ERC20 token implementation.
5. The require in TransferHelper.safeTransfer reverts the transaction, causing the entire swap or cross-chain transfer to fail.

### Impact

- Users: Legitimate transactions revert unexpectedly, preventing transfers.
- Protocol: Degrades user experience and reliability of the platform’s transfers.


### PoC

Example scenario where the transaction fails:
```solidity
// feePercent = 5
// amount = 199  
// (199 * 5) / 1000 = 0  
_gatewayCrossChain._handleFeeTransfer(zrc20, 199);
```
This triggers TransferHelper.safeTransfer with zero as the amount, causing the transaction to revert with:
TransferHelper: TRANSFER_FAILED


### Mitigation

Add a validation check to ensure that platformFeesForTx is greater than zero before performing the transfer:
```solidity
require(platformFeesForTx > 0, "platformFeesForTx must be > 0");
```
Alternatively, consider enforcing a minimum fee or adjusting the fee calculation logic to avoid zero-value transfers.
