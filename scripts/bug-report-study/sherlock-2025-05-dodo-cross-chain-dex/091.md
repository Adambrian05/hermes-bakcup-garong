# Hardcoded Init Code Hash Causes Systemic Failure in Uniswap V2 Pair Address Calculation

## Description
The `GatewayCrossChain` contract uses a hardcoded init code hash in the `uniswapv2PairFor()` function to deterministically calculate the Uniswap V2 pair address. The init code hash used (`0x96e8ac4277198ff8b6f785478aa9a39f403cb768dd02cbee326c3e7da348845f`) is likely inconsistent with the actual Uniswap V2 deployment on ZetaChain, which will cause systemic failures in all operations that rely on pair address calculation.

Note: this issue also occurs with the `GatewayTransferNative` contract.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L208

## Code Snippet
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L191-L204

## Root Cause
The problem is in the `uniswapv2PairFor()` function.
```solidity
pair = address(
    uint160(
        uint256(
            keccak256(
                abi.encodePacked(
                    hex"ff",
                    factory,
                    keccak256(abi.encodePacked(token0, token1)),
                    hex"96e8ac4277198ff8b6f785478aa9a39f403cb768dd02cbee326c3e7da348845f" // ❌ HARDCODED INIT CODE HASH
                )
            )
        )
    )
);
```
The root of the problem is that the init code hash is hardcoded without verification against the actual Uniswap V2 deployment on ZetaChain. There is no mechanism to update the init code hash if something changes. It is a false assumption that all Uniswap V2 deployments have the same init code hash.

Each blockchain has an independent Uniswap V2 deployment. The compiler bytecode, Solidity version, and optimization settings may be different. The constants and libraries used in the deployment may be different. This init code hash is for Uniswap V2 on Ethereum mainnet `hex"96e8ac4277198ff8b6f785478aa9a39f403cb768dd02cbee326c3e7da348845f"`, but this contract will be deployed on ZetaChain, Ethereum, Polygon, Arbitrum, Base, BNB Chain.

## Impact
Any swap operation that relies on pair detection will fail or be suboptimal.

## Scenario Step by Step
1. User makes a large swap
2. Contract calculates path based on incorrect pool detection
3. Uniswap router tries to access pair at wrong address
4. Transaction reverts with error "INSUFFICIENT_LIQUIDITY" or "PAIR_NOT_EXISTS"
5. User experiences failed transaction
6. User funds are reverted to the original chain

## Recommendation
Add a state variable to store the init code hash and modify the `uniswapv2PairFor()` function to use the variable.
```solidity
// Add a state variable to store the init code hash
bytes32 public uniswapV2InitCodeHash;

// Updated the uniswapv2PairFor function
function uniswapv2PairFor(
    address factory,
    address tokenA,
    address tokenB
) public view returns (address pair) {
    (address token0, address token1) = sortTokens(tokenA, tokenB);
    
    pair = address(
        uint160(
            uint256(
                keccak256(
                    abi.encodePacked(
                        hex"ff",
                        factory,
                        keccak256(abi.encodePacked(token0, token1)),
                        uniswapV2InitCodeHash // ✅ USING VARIABLES
                    )
                )
            )
        )
    );
}
```
