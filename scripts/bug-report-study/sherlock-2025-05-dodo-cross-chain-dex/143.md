# USDT Approval Logic Causes Reversion


## Summary

The DODO gateway contracts have an issue where they do not handle USDT's non-standard approval behavior, leading to transaction failures with USDT tokens on chains where USDT still implements the non-standard approval pattern. This issue arises due to the fact that the contracts directly set new approvals without resetting to zero first, and if USDT is used on affected chains, modifying an allowance from a non-zero value to another non-zero value will revert if the allowance from previous transactions is not fully consumed, which will result in reverting subsequent USDT transactions across the main gateway contracts.

## Root Cause

In [[[GatewaySend.sol:164](https://github.com/code4rena-c4/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L164)](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L164)](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L199) the contract directly approves tokens without resetting to zero first, assuming all tokens follow standard ERC20 approval behavior. USDT requires resetting approval to zero before setting a new non-zero allowance.

**GatewaySend.sol:**

@>      IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);

## Internal Pre-conditions

1. User needs to have previously approved tokens to DODOApprove contract to set existing allowance to be greater than 0
2. User needs to initiate a new swap to trigger approval process with different amount

## External Pre-conditions

1. User needs to swap using USDT token which has non-standard approval behavior
2. USDT contract needs to have existing non-zero allowance for the caller to DODOApprove

## Attack Path

1. User calls `GatewaySend.depositAndCall()` with USDT, contract approves 100 USDT to DODOApprove
2. Swap executes successfully, but 50 USDT allowance remains unused
3. User initiates second swap calling `GatewaySend.depositAndCall()` with 200 USDT  
4. Function calls `IERC20(USDT).approve(DODOApprove, 200e6)` while existing allowance is 50 USDT
5. USDT contract reverts with `NonZeroToNonZeroApproval()` error
6. Transaction fails and user cannot perform USDT swaps until manually resetting approval
7. All subsequent USDT transactions fail until allowance is reset to zero

## Impact

The protocol suffers transaction failures for all USDT swaps and transfers when users have existing non-zero allowances. Since USDT is a major stablecoin, this breaks core functionality for the gateway contract for a significant portion of users. The issue affects cross-chain swaps, compounding as more users encounter failed transactions requiring manual intervention to reset approvals.

**Severity Justification**: Medium severity due to:
- Breaks functionality for major stablecoin (USDT) on Ethereum mainnet
- Affects cross-chain swap operations
- High likelihood occurrence in normal usage patterns
- Requires manual user intervention to resolve
- No fund loss but significant protocol usability impact

## PoC
The test file `GatewaySend.t.sol` was modified to demonstrate the issue by adding a USDT mock and test:

```solidity
// Added to GatewaySend.t.sol
contract USDTMock is ERC20Mock {
    error NonZeroToNonZeroApproval();

    constructor() ERC20Mock("USDT", "USDT", 6) {}

    function approve(address spender, uint256 amount) public override returns (bool) {
        // USDT requires resetting to zero before setting a new non-zero allowance
        if (amount != 0 && allowance(msg.sender, spender) != 0) {
            revert NonZeroToNonZeroApproval();
        }
        return super.approve(spender, amount);
    }
}

// Added to GatewaySend.t.sol
function test_USDTApprovalIssue() public {
    // Create a mock token that behaves like USDT (non-standard approval)
    USDTMock usdtMock = new USDTMock();
    usdtMock.mint(user1, 1000e6);

    // Setup DODO mock price for USDT
    dodoRouteProxyA.setPrice(address(usdtMock), address(token2A), 1e18); // 1:1 price

    vm.startPrank(user1);
    
    // First approval works
    usdtMock.approve(address(gatewaySendA), 100e6);
    
    // Try to change approval without resetting to zero - should fail
    vm.expectRevert(abi.encodeWithSelector(USDTMock.NonZeroToNonZeroApproval.selector));
    usdtMock.approve(address(gatewaySendA), 200e6);
    
    // Reset to zero first - should work
    usdtMock.approve(address(gatewaySendA), 0);
    
    // Now set new approval - should work
    usdtMock.approve(address(gatewaySendA), 200e6);
    
    vm.stopPrank();
}
```

The test demonstrates that:
1. The `USDTMock` contract implements USDT's non-standard approval behavior on Ethereum mainnet
2. Initial approval of 100 USDT works
3. Attempting to change approval to 200 USDT without resetting fails with `NonZeroToNonZeroApproval` error
4. Resetting to zero first allows setting the new approval
5. This matches USDT's behavior on Ethereum mainnet where changing from non-zero to non-zero allowance requires resetting to zero first

This test was added to verify that the contract's direct approval calls in `_doMixSwap` will fail when interacting with USDT on chains where it implements this non-standard behavior.

## Mitigation

Implement a safe approval pattern that resets allowance to zero before setting new value in the affected contract:

```solidity
// In GatewaySend.sol
if(params.fromToken != _ETH_ADDRESS_) {
    // Reset to zero first to handle non-standard tokens like USDT
    IERC20(params.fromToken).approve(DODOApprove, 0);
    IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
}
```

## Notes

This issue specifically affects the `GatewaySend.sol` contract which operates on Ethereum mainnet and other EVM chains where USDT implementations may retain the non-standard approval behavior. The issue is most relevant for Ethereum mainnet where the original USDT contract (0xdAC17F958D2ee523a2206206994597C13D831ec7) still requires the reset-to-zero approval pattern.
