# Mismatched token assumption in `withdrawToNativeChain`: `gasFee.token` may differ from `targetToken`

### Summary

Assuming `gasFee.token` is always equal to `targetToken` will cause incorrect token transfers or accounting errors for users as the contract will process withdrawals using mismatched tokens, leading to unintended token deductions or failed bridging operations.

```solidity
            (, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFee(); //@audit the gasToken may differ from `decoded.targetZRC20`
            _handleBitcoinWithdraw(externalId, decoded, outputAmount, gasFee);
```

### Root Cause

In `GatewayTransferNative.sol:withdrawToNativeChain`, the function assumes that `gasFee.token` is equal to `targetToken` without validating this assumption, which can lead to incorrect token transfers if the two differ.
[code](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L559)

### Internal Pre-conditions

1. Admin or configuration manager needs to set `gasFee.token` to be different from `targetToken`
2. User needs to call `withdrawToNativeChain()` expecting the target asset to match `targetToken`
3. The `GatewayTransferNative` contract must not validate that `gasFee.token == targetToken`

### External Pre-conditions

1. The `gasFee.token` price needs to deviate significantly from the `targetToken` price, causing a mismatch in value coverage.
2. The cross-chain bridge mechanism must allow withdrawal calls where `gasFee.token` differs from `targetToken` without rejecting or adjusting.
3. The system must process `withdrawToNativeChain` transactions assuming `gasFee.token` equals `targetToken` without explicit verification.

### Attack Path

1. User calls `GatewayTransferNative::withdrawToNativeChain` with parameters where `gasFee.token` is different from `targetToken`, and `decoded.dstChainId == BITCOIN_EDDY`.
2. The contract processes the withdrawal assuming `gasFee.token` and `targetToken` are the same, applying gas fee calculations incorrectly.
3. This causes the gas fee to be paid or deducted in an unintended token, which will lead to a revert because there is no approval for this token during the fee deduction process on the Bitcoin Eddy chain.

### Impact

The users cannot complete their withdrawal on the Bitcoin Eddy chain, leading to a denial of service (DoS) for withdrawals when the gas fee token differs from the target token, because the transaction reverts due to missing token approval for the unintended gas fee token.

### PoC

_No response_

### Mitigation

Add an explicit check to ensure the `gasFee` token is the same as the `targetToken` before proceeding with the withdrawal, or if they are different, perform a swap from the  target token  to the gas token to properly handle the withdrawal.
