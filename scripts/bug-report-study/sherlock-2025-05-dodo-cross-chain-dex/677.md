# Lack of validation for CrossChainMessages to the `GatewayCrossChain` would lead to loss of  user funds

### Summary

Incoming Crosschain messages to the [GatewayCrossChain::onCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442-L444)  lacks necessary validation checks, which would allow anyone to craft malicious payloads and since the adapter doesn't validate the payload or the caller the call would result in loss of users funds.
### Root Cause

The GatewayCrossChain adapter  (a Universal Contract) which serves as one of the vital components of the dodo protocol to facilitate CrossChain Swaps from and to ZetaChain. The issue with this module is that it lacks proper validation for CrossChain messages which is commonly prioritized in CrossChain Messaging, it could also be put as the adapter doesn't verify where cross-chain  messages Originates from and who sent the message.


Since the current implementation blindly trusts cross-chain messages malicious users could use its flaws to their advantage to steal funds .
The `MessageContext` Struct parameter stores all information required to verify the crosschain call.

### Internal Pre-conditions

The dodo protocol has been deployed to any of the connected chain and Zetachain

### External Pre-conditions

None

### Attack Path


1. There must be active refunds in the adapter on zetachain.

2. Bob sees these active refunds craft a crosschain message to send a token of lower value i.e if the active refunds are `Ether` he sends `DAI` or `RAI`.A crosschain payload is a stream of bytes made up of an abi encoded tuple consisting of the fields abi.encodePacked(bytes32 externalId,DecodedMessage decodedMsg,MixSwapParams),you should already know the MixSwapParams is used to hold details for our swap on the ZetaChain and then the DecodedMessage represents where our tokens received from the swap should be deposited to.

```solidity

struct DecodedMessage {
    address targetZRC20;
    uint32 dstChainId;
    bytes sender;
    bytes receiver;
    bytes swapDataZ;
    bytes contractAddress;
    bytes swapDataB;
    bytes accounts;
}


//AND

struct MixSwapParams {
    address fromToken;//Received Zeta token
    address toToken;// Target ZRC20 token to Swap `fromTokenAmount` of`fromToken` to `toToken`
    uint256 fromTokenAmount;
    uint256 expReturnAmount;
    uint256 minReturnAmount;
    address[] mixAdapters;
    address[] mixPairs;
    address[] assetTo;
    uint256 directions;
    bytes[] moreInfo;
    bytes feeData;
    uint256 deadline;
}
```
4. Since there are no validation checks the expression isn't guaranteed to be true `MixSwapParams::toToken==DecodedMessage.targetZRC20`  which means Bob could swap usdt for usdc and set targetZRC20 to bitcoin or Ethereum or any other token which results in Bob being profitable.
5. The targetZRC20 tokens are dispatched  on the `DecodedMessage::dstChainId` to `DecodedMessage::receiver`

### Impact

All refunds stored in the adapter would be drained 

### PoC

A quick fix would be to first address the elephant in the room which is CrossChain messages are invalidated.

```solidity
mapping(uint256 dstChainId=>address adapter)private allowedAdapters

function addAdapter(address _adapter,uint256 _chainId) onlyOwner external{
    allowedAdapters[_chainId]=_adapter;
}

function removeAdapter(uint256 _chainId) onlyOwner external{
   delete  allowedAdapters[_chainId];
}

  function onCall(
        MessageContext calldata context,
        address zrc20,//Zrc20 token sent crosschain
        uint256 amount,
        bytes calldata message
    ) external onlyGateway {
        require(allowedAdapters[context.chainId]==context.sender."Unknown Adapter");
        //Also ensure
      require(DecodedMessage.targetZRC20==MixSwapParams.toToken,"Mismatched token address");

    }

```
