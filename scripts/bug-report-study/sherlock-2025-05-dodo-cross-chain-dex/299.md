# Unintended ETH Retention in depositAndCall Function

## Summary  
In the `GatewaySend` contract, the [depositAndCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L234) function allows users to send ETH when selecting ETH as the token. However, if the user sends more ETH than the `amount` parameter specified in the function call (i.e., `msg.value > amount`), the contract retains the entire amount of ETH sent without refunding the excess (`msg.value - amount`). This behavior can result in users unintentionally losing funds, as there is no mechanism to return the remaining ETH or enforce that only the exact amount is sent.  

## Root Cause (In Detailed)  
The issue originates from the logic in the `depositAndCall` function when ETH is selected as the token (e.g., `fromToken == _ETH_ADDRESS_`). The contract includes a check to ensure that the amount of ETH sent by the user (`msg.value`) is at least equal to the specified `amount` parameter (`msg.value >= amount`). While this ensures the transaction can proceed with the required funds, it does not handle cases where `msg.value` exceeds `amount`.  

For instance:  
- If a user specifies `amount = 1 ETH` but sends `msg.value = 2 ETH`, the contract processes the transaction using only the 1 ETH specified in `amount`.  
- The remaining 1 ETH (i.e., `msg.value - amount`) is not utilized, refunded, or accounted for—it simply remains trapped in the contract's balance.  

This problem arises because:  
1. The condition `msg.value >= amount` allows excess ETH to be accepted without restriction, rather than requiring an exact match (`msg.value == amount`).  
2. The function lacks any logic to calculate and refund the excess ETH back to the user after processing the required `amount`.  
3. There is no additional mechanism in the contract to allow users to recover the excess ETH once it is retained.  

This design flaw can lead to accidental fund loss, especially if users are not aware of the need to send precisely the `amount` specified or if the user interface does not enforce this constraint.  

## Recommendation  
To resolve this issue and prevent unintended ETH retention, the following solutions are recommended:  

1. **Enforce Exact ETH Amount**:  
   Update the function to require that the ETH sent (`msg.value`) exactly matches the specified `amount`. This prevents the contract from accepting excess ETH and eliminates the need for a refund mechanism.  
   ```solidity
   if (fromToken == _ETH_ADDRESS_) {
       require(msg.value == amount, "EXACT_AMOUNT_REQUIRED: ETH AMOUNT MISMATCH");
   }
   ```

2. **Refund Excess ETH**:  
   If flexibility is desired (e.g., allowing `msg.value > amount`), implement a refund mechanism to return any excess ETH to the user after processing the required `amount`. This approach ensures users do not lose funds unintentionally.  
   ```solidity
   if (fromToken == _ETH_ADDRESS_) {
       require(msg.value >= amount, "INSUFFICIENT_AMOUNT: ETH NOT ENOUGH");
       uint256 excess = msg.value - amount;
       if (excess > 0) {
           payable(msg.sender).transfer(excess);
       }
   }
   ```

3. **Improve User Experience**:  
   In addition to code changes, enhance the user interface and documentation to:  
   - Clearly instruct users to send the exact `amount` of ETH required.  
   - Provide warnings or validation checks to prevent sending excess ETH.  

Implementing one of these code changes—preferably the refund mechanism for greater flexibility—combined with better user guidance, will ensure that excess ETH is not retained by the contract and that the process is transparent and safe for users.
