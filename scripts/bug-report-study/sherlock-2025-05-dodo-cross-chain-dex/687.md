# `GatewayTransferNative.withdraw` Truncates 32-Byte Bitcoin Addresses in `revertMessage`

### Summary

The [`GatewayTransferNative.withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530) function, when processing withdrawals to Bitcoin, calls`withdraw` function. This `withdraw` function incorrectly truncates 32-byte Bitcoin addresses (P2WSH, P2TR) to their first 20 bytes when constructing the `RevertOptions.revertMessage`. While the primary `sender` params to the ZetaChain `gateway.withdraw` call correctly receives the full Bitcoin address, the `revertMessage` (critical for refund processing) contains this truncated address. If a transaction subsequently fails and `onRevert` is called, the refund logic in `onRevert` will only have access to this incomplete 20-byte segment, potentially leading to fund loss or inability to process the refund correctly for the original 32-byte recipient.

### Root Cause

The bug exists in the `withdraw` function of `GatewayTransferNative` specifically in how it constructs the `revertMessage`.

1.  **Withdrawal Path for Bitcoin:**
    *   A user calls `withdrawToNativeChain` targeting a Bitcoin destination (`decoded.dstChainId == BITCOIN_EDDY`).
    *   This calls `_handleBitcoinWithdraw`.
    *   `_handleBitcoinWithdraw` then calls the `withdraw` function, passing `decoded.receiver` (the full Bitcoin address as `bytes`) as the `sender` argument to `withdraw`.

    ```solidity
    withdraw(externalId, decoded.receiver, decoded.targetZRC20, outputAmount - gasFee);
    ```

2.  **Truncation in `revertMessage` Construction:** Inside the `withdraw` function, `RevertOptions` are prepared for the call to `IGatewayZEVM(gateway).withdraw`.
    ```solidity
    function withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount) public { // Visibility is public but usage is internal
        gateway.withdraw(
            sender, // Full Bitcoin address is correctly passed as the primary 'sender' to the gateway
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                // @audit BUG: 'sender' (full Bitcoin address) is truncated to 20 bytes here.
                revertMessage: bytes.concat(externalId, bytes20(sender)), 
                onRevertGasLimit: gasLimit 
            })
        );
    }
    ```
    The line `revertMessage: bytes.concat(externalId, bytes20(sender))` is the issue.
    *   `sender` is the full Bitcoin address (e.g., a 32-byte P2WSH script hash, or a Bech32 address string converted to bytes which would also be >20 bytes).
    *   `bytes20(sender)` explicitly casts/truncates the `sender` to its first 20 bytes. The remaining bytes are lost.
    *   This truncated 20-byte segment, along with `externalId`, forms the 52-byte `revertMessage`.

### Internal Pre-conditions
1.  The `withdrawToNativeChain` function is called with `decoded.dstChainId == BITCOIN_EDDY`.
2.  The `decoded.receiver` (Bitcoin address) is longer than 20 bytes.

### External Pre-conditions

None directly for the truncation itself, but for the impact to manifest:

1.  The `gateway.withdraw` call must fail for any reason, triggering `onRevert`.

### Attack Path 

1.  **User Initiates Withdrawal:** User calls `withdrawToNativeChain` to send `ZRC20_BTC` to their 32-byte Bitcoin P2WSH address, `btc32b` (which is 32 bytes long).
2.  **Internal Processing:**
    *   `_handleBitcoinWithdraw` calls `withdraw(externalId, btc32b, ZRC20_BTC, amount)`.
    *   Inside `withdraw`, `revertMessage` is created as `bytes.concat(externalId, bytes20(btc32b))`. The `btc32b` is truncated to its first 20 bytes.
3.  **Call to Gateway:** `gateway.withdraw` is called. The `sender` parameter is the full `btc32b`, but `RevertOptions.revertMessage` contains the truncated 20-byte version.
4.  **Withdrawal Failure & `onRevert`:** The cross-chain withdrawal to Bitcoin fails. ZetaChain Gateway calls `GatewayTransferNative.onRevert`.
    *   `context.revertMessage` is 52 bytes long (externalId + truncated 20-byte address).
    *   The `if (context.revertMessage.length == 52)` branch in `onRevert` is taken.
    *   `walletAddress` becomes the truncated 20-byte segment of `btc32b`.
    *   `address receiver = address(uint160(bytes20(walletAddress)));` creates an EVM address from this truncated segment.
    *   `TransferHelper.safeTransfer` sends the `ZRC20_BTC` refund to this incorrect EVM address.
5.  **Outcome:** The user's refund is sent to an EVM address derived from the first 20 bytes of their 32-byte Bitcoin address. These funds are lost as the user does not control this derived EVM address, and it doesn't represent their full Bitcoin address for any off-chain recovery.

### Impact
If a withdrawal to a >20-byte Bitcoin address fails, the `revertMessage` stored and used by `onRevert` will contain a truncated version of the recipient's address. This leads to:

1.  **Fund Loss:** Refunds are sent to an incorrect EVM address derived from the truncated Bitcoin address if the `onRevert` 52-byte path is taken.
2.  **Incorrect Refund Processing:** Even if the `else` path in `onRevert` were taken, `refundInfos` would store a truncated address, making correct bot-assisted manual refunds for the original 32-byte address impossible.

The primary issue is the data corruption in `revertMessage` which makes subsequent refund logic faulty.


### Mitigation

The `withdraw` function in `GatewayTransferNative` must not truncate the `sender` (Bitcoin address) when constructing the `revertMessage`. It should use the full `sender` bytes.
