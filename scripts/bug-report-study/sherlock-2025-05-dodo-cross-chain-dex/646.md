# Insufficient liquidity check in `_existsPairPool()` enables incorrect routing and potential DoS

### Summary

The `_existsPairPool()` function in the GatewayCrossChain contract incorrectly determines the presence of a usable Uniswap V2 liquidity pool solely based on non-zero token balances ([here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L218-219)). This flaw allows an attacker to "poison" the routing logic by sending minimal "dust" amounts of tokens to a predetermined pair address. Consequently, `getPathForTokens()` selects an inefficient direct swap path lacking real liquidity, causing legitimate `_swapAndSendERC20Tokens()` operations to revert due to insufficient liquidity or extreme slippage. This leads to a Denial of Service (DoS) for users attempting cross-chain swaps for affected token pairs.

### Root Cause

The `_existsPairPool()` function's strictly relies on `IZRC20(zrc20A).balanceOf(uniswapPool) > 0 && IZRC20(zrc20B).balanceOf(uniswapPool) > 0` as the only condition for determining if a pool exists or not, which is insufficient. A Uniswap V2 pair contract, identified by its deterministic address, can hold positive token balances even if those balances represent negligible or no actual liquidity. The function fails to check for a sufficient amount of liquidity, allowing an effectively empty pool to be considered viable for routing.

### Internal Pre-conditions

- The `uniswapv2PairFor()` function is used to derive the pair address for zrc20A and zrc20B.
- The `IZRC20(zrc20A).balanceOf(uniswapPool)` and `IZRC20(zrc20B).balanceOf(uniswapPool)` need to be greater than 0.
- The actual token reserves in uniswapPool for zrc20A and zrc20B needs to be significantly less than required for a meaningful swap.

### External Pre-conditions

An external actor needs to send a minimal amount (e.g., 1 wei worth) of both zrc20A and zrc20B to the deterministically calculated Uniswap V2 pair address for (zrc20A, zrc20B) via a standard token transfer. This is a low-cost operation.

### Attack Path

1. An attacker (or anyone) calculates the deterministic Uniswap V2 pair address for any two ZRC20 tokens, let's call them TokenX and TokenY, using the `uniswapv2PairFor()` function.
2. The attacker then performs two direct transfer() operations, sending a very small, non-zero amount of TokenX and TokenY to the calculated pair address
3. A legitimate user initiates a cross-chain swap through the GatewayCrossChain contract, intending to swap TokenX for TokenY and viceversa or a swap where these two tokens form a segment of the swap path.
4. During the execution of `_swapAndSendERC20Tokens()`, the `_existsPairPool()` incorrectly returns true, indicating that a direct pool tokenX/tokenY exists.
5. `getPathForTokens()` then returns a 2-hop path ([TokenX, TokenY]) instead of the correct 3-hop path ([TokenX, WZETA, TokenY]) which would route through a liquid WZETA pool.
6. Since the liquidity in the "poisoned" TokenX-TokenY pool is negligible , the swap transaction will almost certainly revert with errors like INSUFFICIENT_LIQUIDITY or due to slippage limits being hit.



### Impact

- DoS is possibile since legitimate cross-chain swap transactions for any token pair targeted by this attack will consistently revert, preventing users from completing their desired operations.  
- Users incur gas costs for failed transactions due to reverts.
- In cases where a swap might not immediately revert the trade would execute with huge slippage, leading to significant financial loss for the user.

_No response_

### Mitigation

Improve the _existsPairPool() function to verify the depth of liquidity, not just its presence introducing a minimum liquidity threshold or consider evaluating multiple swap paths (e.g., direct vs. through WZETA) and choose the best by comparing output estimations.
