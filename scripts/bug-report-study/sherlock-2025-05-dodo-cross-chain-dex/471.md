# Unintended withdrawal behavior to Bitcoin due to misleading `dstChainId` check breaks non-core functionality

### Summary

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L558
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L468

The misleading conditional check on `dstChainId` in `GatewayTransferNative::withdrawToNativeChain` will cause unexpected behavior for non-core protocols as an attacker or misconfigured integrator can bypass intended withdrawal handling logic by setting `dstChainId` to `BITCOIN_EDDY` even when `targetZRC20` is not the Bitcoin ZRC20. since  connected chains are identified by the zrc20 address readmore [here](https://www.zetachain.com/docs/developers/chains/zetachain/#withdraw-zrc-20-tokens-and-call-a-contract-on-a-connected-chain)

 This bypasses expected validation and causes the wrong logic branch to execute, which breaks compatibility and causes misrouted or failed withdrawals. 



### Root Cause

In `GatewayTransferNative::withdrawToNativeChain`, the logic to determine if a withdrawal is to Bitcoin incorrectly uses:

```solidity
if (decoded.dstChainId == BITCOIN_EDDY)
```

instead of validating based on the actual token to be withdrawn, which should be:

```solidity
if (decoded.targetZRC20 == BTC_ZRC20)
```

This mistake means that withdrawal behavior is incorrectly governed by `dstChainId`, which may not accurately reflect the actual asset being withdrawn

### Internal Pre-conditions

1. A user or attacker must craft a withdrawal request where `decoded.dstChainId == BITCOIN_EDDY`
2. The `targetZRC20` must be a valid non-BTC ZRC20 token.

### External Pre-conditions

n/q

### Attack Path

1. An attacker or misconfigured integration sets `decoded.dstChainId = BITCOIN_EDDY` while using a non-Bitcoin `targetZRC20`.
2. The `withdrawToNativeChain` function incorrectly calls `_handleBitcoinWithdraw` instead of a general handler.
3. The withdrawal logic proceeds incorrectly, failing to execute properly or routing assets incorrectly.
4. Legitimate non-core protocol transactions are broken or funds may be lost due to failed operations.

### Impact

The protocol suffers functional breakage for non-core assets and withdrawals, as incorrect routing logic causes failed or misprocessed transactions. This can lead to denial-of-service (DoS) for affected protocols, misrouted funds, or unusable integrations.
#### Note 
a variant  of this  issue exist in `GatewayCrossChain`.
### PoC

n/q

### Mitigation

Replace the condition:

```solidity
if (decoded.dstChainId == BITCOIN_EDDY)
```

with a safer and more accurate token-based check:

```solidity
address BTC_ZRC20 = 0x13A0c5930C028511Dc02665E7285134B6d11A5f4;
if (decoded.targetZRC20 == BTC_ZRC20)
```
