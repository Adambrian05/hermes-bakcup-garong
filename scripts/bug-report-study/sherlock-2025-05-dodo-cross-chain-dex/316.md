# Malicious tokens can reenter onCall, claimRefund, superWithdraw and mess with state

### Summary

Missing `nonReentrant` guards will cause reentrancy vulnerabilities for the protocol as malicious ERC20 tokens can hijack control flow via callbacks during state updates.

### Root Cause

In [`GatewayCrossChain.sol:claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571), `onCall`, and `superWithdraw`, the contract makes external calls (e.g., ERC20 transfers) before updating state.
No `nonReentrant` modifier is present to prevent nested execution.

### Internal Pre-conditions

1. An attacker deploys a malicious ERC20 token contract.
1. Admin or user sets a refund/swap path involving this token.
1. Refunds or transfers are initiated with this malicious token.

### External Pre-conditions

Malicious ERC20 implements fallback logic to reenter the vulnerable function.
Reentrancy alters internal state mid-transaction.

### Attack Path

Attacker uses a crafted token that reenters `claimRefund()` during `safeTransfer`.

State isn't updated yet, so they call `claimRefund()` again.

They claim multiple times before the state is finalized.

### Impact

The attacker may double-claim tokens or manipulate protocol logic.
Protocol suffers from potential loss of funds or corrupted state.

### PoC

```solidity
function transfer(address to, uint amount) public override returns (bool) {
    if (!entered) {
        entered = true;
        // Reenter vulnerable function
        target.claimRefund(refundId);
    }
    return true;
}
```

### Mitigation

Add `nonReentrant` modifier to all state-changing functions that perform external calls.

Use `OpenZeppelin’s ReentrancyGuardUpgradeable`
