# Unprotected claimRefund Lets Attackers Steal Other Users’ Refunds

### Summary

[claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571) is declared external, so any user can call it. Because the function never verifies that msg.sender is the rightful owner of the refund entry, a front-runner can intercept the call and withdraw funds that belong to someone else. Bots are supposed to claim refunds, but on a public mempool a better-funded or faster actor can simply outbid them on gas and win the race.

### Root Cause

Let's review this 'claimRefund` function. As you can see below are the reasons of root causes.

```Solidity
File: GatewayCrossChain.sol
571:     function claimRefund(bytes32 externalId) external {
572:         RefundInfo storage refundInfo = refundInfos[externalId];
573: 
574:         address receiver = msg.sender;
575:         if(refundInfo.walletAddress.length == 20) {
576:             receiver = address(uint160(bytes20(refundInfo.walletAddress)));
577:         }
578:         require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
579:         require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
580:         
581:         TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
582:         delete refundInfos[externalId];
583: 
584:         emit EddyCrossChainRefundClaimed(
585:             externalId,
586:             refundInfo.token,
587:             refundInfo.amount,
588:             abi.encodePacked(msg.sender)
589:         );
590:     }
```
1. No ownership check: msg.sender is never correlated with the refund’s recorded owner.

2. Fallback to caller: For non-20-byte addresses such as Bitcoin and Solana accounts, receiver remains msg.sender, so any msg.sender passes the require (line 578).

3. Role bypass via frontrun: Even if a bot address is whitelisted, the contract does not prevent someone else from beating the bot in transaction ordering.

### Internal Pre-conditions

1. refundInfo.walletAddress.length == 20 should be false.

### External Pre-conditions

none

### Attack Path

Exploit Walk-Through by attacker: 
1. Watch onRevert events for a refund whose walletAddress.length != 20; assume externalId = 0x…abc.

2. Submit claimRefund(0x…abc) with a slightly higher gas price than the bots use.

3. Inside claimRefund:

     a. receiver stays equal to msg.sender.

     b. Line 578 passes (msg.sender == receiver).

      c. safeTransfer moves the refund to the attacker.

4. The legitimate user never sees their funds.



### Impact

Full value of any refund tied to a non-20-byte address can be irreversibly stolen. The attacker pays only gas.



### PoC

see attack path

### Mitigation

Restrict claimRefund to approved bots, and have bots forward funds to the recorded recipient.
