# Insufficient native ETH validation in `GatewaySend.onCall()`

### Summary

The `onCall()` function ([here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L341-387)) within the GatewaySend contract, which is responsible for processing incoming cross-chain transfers from GatewayEVM, fails to validate the msg.value (actual native ETH received) against the amount (expected amount from the decoded message) when handling native ETH transfers. This oversight can lead to the GatewaySend contract transferring out more native ETH than it received for a particular transaction, potentially draining the contract's ETH balance.

### Root Cause

The root cause is a missing require statement to assert that msg.value is exactly equal to the amount parsed from the incoming message when fromToken is identified as native ETH (_ETH_ADDRESS_). The current logic only checks for ERC20 transfers using transferFrom() and implicitly relies on the msg.value being correct for native ETH, without explicit verification.

### Internal Pre-conditions

- `GatewaySend.onCall()` function is called.
- `fromToken (decoded from message) needs to be exactly `_ETH_ADDRESS_`
- `amount` (decoded from message) needs to be greater than msg.value (the actual ETH sent with the transaction).
- the GatewaySend contract's own native ETH balance needs to be at least `amount - msg.value` to facilitate the overpayment in the `if(toIsETH)` branch.

### External Pre-conditions

The entity calling `onCall()` must send an amount in the packed message that does not match the `msg.value` sent with the transaction. This could occur due to:
- A malicious call `onCall()` if the address calling it (checked through `onlyGateway` modifier) is compromised
- A legitimate but flawed cross-chain message from ZetaChain that causes GatewayEVM to send an incorrect msg.value relative to the amount in the message.

### Attack Path

1. A legitimate but flawed message from the gateway to GatewaySend makes the function `decodePackedMessage()` in `onCall()` to parse an `amount` of a value X. 
2. The `msg.value` (actual native ETH sent with the onCall transaction) is set to a value Y, where Y < X. (i.e., less ETH is sent than declared in the message).
3. Inside GatewaySend.onCall(), `fromIsETH` is evaluated as true and `if(!fromIsETH)` block is skipped
4. The `outputAmount` variable is set to amount (which is X) if fromToken == toToken (e.g., direct ETH transfer without swap).
5. The contract then attempts to do `payable(evmWalletAddress).transfer(outputAmount)`, transferring X ETH to the recipient.
6. If GatewaySend had a pre-existing native ETH balance of at least X - Y, it will successfully transfer X ETH to the recipient, effectively losing X - Y ETH from its own balance.

### Impact

Direct loss of funds since the GatewaySend contract can be drained of its native ETH balance. Also if the contract's ETH reserves are emptied, it may be unable to process legitimate cross-chain transfers or other functions that require native ETH.

### PoC

_No response_

### Mitigation

Introduce a require statement to explicitly verify that msg.value matches the amount decoded from the message when fromToken is native ETH.
