# Reentrancy vulnerability in claimRefund

### Summary

### Q: Are there any off-chain mechanisms involved in the protocol (e.g., keeper bots, arbitrage bots, etc.)? We assume these mechanisms will not misbehave, delay, or go offline unless otherwise specified.
If the receiver of refund info is not an EOA address, refund bots collect the tokens and process the refund manually.

In the [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661) in both the `GatewayTransferNative.sol` and `GatewayCrossChain.sol` are both vulnerable to reentrancy attack. ). The reentrancy occurs
because the functions perform external calls via safeTransfer before clearing the state by deleting the `refundInfos` this allows an attacker to reenter the function and drain funds


### Root Cause

In the [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661) in both the `GatewayTransferNative.sol` and `GatewayCrossChain.sol` does not follow the standard method of check effects and interactions (CEI) and perform external calls before deleting the state.

```solidity
           TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];
```

### Internal Pre-conditions

1. Both the `GatewayTransferNative.sol` and `GatewayCrossChain.sol` have tokens which should be refunded to user (ETH or ERC20 tokens)

### External Pre-conditions

1. User have funds which should be refunded back.

### Attack Path

1. An attacker has token say ETH which should be refunded back.
2. Another User alice with same token which should be refunded is in the contract since both contract has a receive and fallback function.
3. An attacker claims refund and then frontruns alice or another user till depletion of tokens in the contract
4. Other users would not be able to claim refunds.

### Impact

A repeated calls via reentrancy can drain contracts on tokens which should be able to be refunded to other users since an attacker can repeatedly perform this.

### PoC

NIL

### Mitigation

Consider following the checks effects interactions and update the state before any external call is made.

```solidity
     function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
         delete refundInfos[externalId];
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
       

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```
