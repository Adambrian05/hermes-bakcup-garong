# Denial of Service in `GatewayCrossChain::onCall` Due to Incorrect Handling of `getPathForTokens`

### Summary

When `onCall` triggers `_handleEvmOrSolanaWithdraw`, and `decoded.targetZRC20 != gasZRC20`, the function `_swapAndSendERC20Tokens` is invoked to swap the target token into the gas token using a Uniswap pool. This relies on `getPathForTokens` to return a valid swap path.

`getPathForTokens` checks if a path between the two tokens exists by verifying the token balances in the Uniswap pair. This approach is flawed:

* An **attacker can send a small amount of a token** to a pool that doesn’t actually facilitate proper swaps. This causes the contract to **falsely assume the pool is valid**.
* When the actual swap is attempted, it **fails** due to insufficient liquidity, causing a **revert** and breaking the flow.
* Even without malicious intent, any token pair with **low liquidity** will cause the function to revert, making the contract **fragile** and easily DOSed until liquidity is added — which is not guaranteed by the protocol.

This behaviour allows attackers (or benign network conditions) to **completely block Onchain call** for affected ZRC20 pairs.

### Root Cause

Insufficient logic for finding valid path

### External Pre-conditions

Liquidity pool doesn't have enough funds

### Attack Path

this issue could happen with attack or by normal:
- attacker send to some token to liquidity pool
- liquidity pool doesn't have enough funds

### Impact

DOS in `onchain` call

### PoC

Not needed

### Mitigation

Use Solidity's `try/catch` construct to **safely attempt the swap**, and handle failures gracefully without reverting the entire transaction. Specifically:

* Wrap the swap operation inside a `try/catch` block.
* In case of failure: Fallback to a default safe path or **reject unsupported pairs explicitly** with a better validation strategy (e.g., whitelisting known token paths).
