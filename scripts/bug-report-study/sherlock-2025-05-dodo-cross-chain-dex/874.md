# Users' assets sent to Bitcoin will be permanently lost if the cross-chain transfer reverts.

## Summary

When a user attempts to send funds from ZetaChain to the Bitcoin network via the `withdrawToNativeChain` function. If this cross-chain transaction fails for any reason (e.g., due to an issue on the destination chain or the Gateway), the `onRevert` function on the `GatewayTransferNative.sol` contract is designed to handle the refund.

The relevant flow is:
1. `withdrawToNativeChain` (initiates the cross-chain transfer)
2. Calls `_handleBitcoinWithdraw`
3. Calls `gateway.withdraw` (this is where the `RevertOptions`  are constructed for a Bitcoin transfer)
4. If the `gateway.withdraw` call fails, the `onRevert` function is triggered on `GatewayTransferNative.sol`.

## Root Cause

The fundamental problem lies in how the Bitcoin `recipient` address is embedded within the `revertMessage` for the `RevertOptions` struct, specifically in the `withdraw` function call within [_handleBitcoinWithdraw](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L451-L465).

[GatewayTransferNative.sol#L286-L303](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286-L303)

```js
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
@>              revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
```
Here, sender is `decoded.receiver` (a `bytes memory` type that holds the Bitcoin address).

The expression `bytes20(sender)` attempts to forcefully cast the bytes representation of the Bitcoin address into a bytes20 type.

Bitcoin addresses are not 20 bytes long (they are variable, typically 26-42 characters, but fundamentally different from EVM addresses). This cast truncates or pads the Bitcoin address, storing a malformed 20-byte value in the revertMessage.

When the `onRevert` function is triggeredby the gateway contract:
[GatewayTransferNative.sol#L607-L638](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607-L638)
```js
    function onRevert(RevertContext calldata context) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:];

        if(context.revertMessage.length == 52) {
            // Direct Refund
            address receiver = address(uint160(bytes20(walletAddress)));
            TransferHelper.safeTransfer(context.asset, receiver, context.amount);
            emit EddyCrossChainRevert(...);
        } else {
            // Store Refund Info for later claim
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress
            });
            refundInfos[externalId] = refundInfo;
            emit EddyCrossChainRefund(...);
        }
    }
```
It checks `context.revertMessage.length == 52`. Since `bytes.concat(externalId, bytes20(sender))` always results in a 52-byte message, this condition is always met for Bitcoin transactions.

It then attempts a "direct refund" by casting the malformed `20-byte walletAddress` (derived from `revertMessage`) to an `address` (EVM address).
The `TransferHelper.safeTransfer` then attempts to send the context.asset (the ZRC20 token) to this incorrect EVM address.

## Attack Path

1. User sends funds from `ZetaChain`, targeting a Bitcoin address.
2. The `withdrawToNativeChain -> _handleBitcoinWithdraw` path is executed.
3. The Bitcoin address is incorrectly cast to `bytes20` and included in the `revertMessage` for `RevertOptions`.
4. The cross-chain transfer fails.
5. The ZetaChain gateway calls `onRevert` on `GatewayTransferNative`.
6. onRevert interprets the malformed 20-byte Bitcoin address as an EVM address.
7. The contract attempts to transfer the ZRC20 tokens to this invalid EVM address.
8. The tokens are irretrievably lost, as the EVM address is not controlled by the user and is likely non-existent or inaccessible.

## Impact

Users' assets sent to Bitcoin will be permanently lost if the cross-chain transfer reverts.

## Mitigation

The `if(context.revertMessage.length == 52)` block in onRevert should be re-evaluated. Direct transfers should only occur if the `walletAddress` is guaranteed to be a valid EVM address; otherwise, the refund should always go to a claimable queue.
