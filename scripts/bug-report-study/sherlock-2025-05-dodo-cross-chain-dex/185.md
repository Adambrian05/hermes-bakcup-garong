# Incorrect Use of transferFrom(msg.sender) in onCall() Causes Cross-Chain Token Transfer Failure

### Summary

The incorrect assumption that Gateway will approve tokens to the destination contract will cause a consistent ERC20 transfer failure for users as the destination chain contract will attempt to transferFrom(msg.sender) (the Gateway) without approval in onCall(), breaking the cross-chain transfer and triggering fallback mechanisms or fund loss.



### Root Cause

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L341-L344
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L358-L360
under the assumption that the Gateway contract will approve token allowances to the receiver contract. However, ZetaChain's Gateway transfers tokens directly before calling onCall() and does not set allowances, making this transferFrom() always fail.


### Internal Pre-conditions

no

### External Pre-conditions

The onCall() function of the destination chain contract attempts to transfer tokens via transferFrom, but the Gateway has not granted authorization.

### Attack Path

* A user initiates a cross-chain ERC20 transfer via depositAndCall() with fromToken = USDC, amount = 100.

* On the destination chain, Gateway receives the cross-chain message and transfers the 100 USDC to the receiver contract DestinationContract.

* The Gateway calls onCall() with the packed message payload.

* Inside onCall(), the receiver contract runs:
```solidity
IERC20(fromToken).transferFrom(msg.sender, address(this), amount);
```
* But msg.sender == Gateway and Gateway has not approved the destination contract to spend any USDC.

* The transferFrom() call fails, reverting the transaction.

* The cross-chain transfer is marked as failed, possibly triggering a refund or leading to funds being locked.




### Impact

1. Although the funds are successfully sent from the source chain, the business logic on the destination chain will not execute.
2. Gateway may invoke `onRevert()` to trigger the fallback logic, which in severe cases can result in user assets being stuck or critical functionality being disrupted.


### PoC

no

### Mitigation

* According to ZetaChain's cross-chain design, the Gateway will first transfer the tokens to the target contract before calling `onCall()`.

* However, `transferFrom` requires the Gateway to have approved the target contract beforehand, which does not happen.

* Therefore, using `transferFrom` in this context is redundant and incorrect.
```solidity
if (!fromIsETH) {
-    IERC20(fromToken).transferFrom(msg.sender, address(this), amount);
+    uint256 balance = IERC20(fromToken).balanceOf(address(this));
+    require(balance >= amount, "Token not received from Gateway");
}

```
