# Potential Token Loss via Swap Slippage

### Summary

Potential Token Loss via Swap Slippage + Incorrect Amount Handling



In _doMixSwap() and _swapAndSendERC20Tokens():

we are assuming:

The swap returns the exact required amount of targetZRC20 and/or gas token.

Sufficient tokens are present to proceed with withdrawAndCall().

However,  not verifying that:

 The swap output meets or exceeds the required targetAmount.

 The actual tokens received exist in the contract before approval or transfer.


 There’s no hard revert or fallback if swap returns less than expected.




 Example Scenario

Let’s say the swap quotes:

amountsQuote[0] = 1,000, and slippage is set to 1% → amountInMax = 1,010.

But due to price movement or poor liquidity:

Swap only returns 950 gas tokens.


Now:

You proceed with withdrawAndCall() assuming you have 1000, but only have 950.

This fails silently, or reverts in ZetaChain.



 Risks

Under-withdrawal or failed cross-chain call.

Stuck or lost tokens if ZetaChain rejects the call and onRevert() is misconfigured.

Inconsistent gas payment, especially if the swap returns less than required.

Loss of user funds or incorrect refund logic if you don’t track what was actually spent.

### Mitigation

1. Check Swap Output Amount
Ensure swap result meets or exceeds expectation:


require(amountsOut[1] >= targetAmount, "Insufficient swap output");

2. Confirm Token Balances Before Approving
Check balance before calling approve() or withdrawAndCall():


require(IERC20(targetZRC20).balanceOf(address(this)) >= targetAmount, "Insufficient token received");


3. Cap Slippage Using Basis Points
Standardize slippage as basis points (e.g., 100 = 1%) and validate:


uint256 maxSlippage = (quote * (10_000 + slippageBps)) / 10_000;
require(amountUsed <= maxSlippage, "Exceeded max slippage");


4. Graceful Refund Handling
Make onRevert() fallback deterministic and robust:


// Track swap outcome and emit event
emit SwapFailure(...);
_safeRefundUser(...);
