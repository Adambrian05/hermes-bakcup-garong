# GatewaySend.onRevert() can not handle native refunds

### Summary

The revert mechanism of incoming transactions is explained [here](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions). 

For dodo cross-chain, the revert for incoming transaction might happen when the `GatewayTransferNative.onCall()` reverts. Then, ZetaChain protocol initiates revert by calling the `revertAddress` on the source chain. For dodo, the revert address would be the `GatewaySend` contract, and the call would be to `GatewaySend.onRevert()`. If `GatewaySend.onRevert()` fails, then the the refund will be directly sent to `GatewayTransferNative` contract and `GatewayTransferNative.onAbort()` will be called. You can check the summary of revert handling [here](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions:~:text=Connected%20%E2%86%92%20ZetaChain,onAbort()%20on%20ZetaChain).

The issue is that `GatewaySend.onRevert()` does not handle native token refunds and will revert. Then, ZetaChain protocol will transfer the refund directly to `GatewayTransferNative` contract address and will call `executeAbort()` on `GatewayZEVM` which will trigger the `GatewayTransferNative.onAbort()` function. The `onAbort()` will save the `walletAddress` to `refundInfos` storage from the `revertMessage`. 

However, in the case explained above **the `walletAddress` would be the address from the source chain** because the `revertMessage` is created with address of the msg.sender on the source chain. But on ZetaChain this address will either be non-existent, or belong to someone else. So no one except `bots` would be able to claim this refund. But even when bots do so, the funds will be transferred to the wrong `receiver` address from the `revertMessage`

### Root Cause

Users can initiate cross-chain interaction on the `GatewaySend.depositAndCall()` [with asset being native token](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L307-L314):
```solidity
bool toIsETH = (asset == _ETH_ADDRESS_);
        if (toIsETH) {
            _handleETHDeposit(
                targetContract,
                outputAmount,
                message,
                revertOptions
            );
```
Also, the `depositAndCall()` function [creates `revertOptions` with `revertMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L299-L305) to handle refunds in case of revert:
```solidity
RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: targetContract,
            revertMessage: bytes.concat(externalId, bytes20(msg.sender)),
            onRevertGasLimit: gasLimit
        });
```
Particularly, the `revertMessage` will be used to extract the address where refund should happen - the msg.sender address on the source chain.

`depositAndCall()` will initiate cross-chain transaction to `GatewayTransferNative.onCall` function. If it reverts for any reason, ZetaChain protocol will try to call the `GatewaySend.onRevert()` function:
```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        address sender = address(uint160(bytes20(context.revertMessage[32:])));
        TransferHelper.safeTransfer(context.asset, sender, context.amount);
        
        emit EddyCrossChainRevert(
            externalId,
            context.asset,
            context.amount,
            sender
        );
    }
```
However, this will revert for `context.asset == _ETH_ADDRESS_` since `TransferHelper.safeTransfer` function tries to transfer erc20 tokens. 

When the `GatewaySend.onRevert()` reverts itself, ZetaChain protocol will try to handle the refund on the ZetaChain. It will transfer the funds to `GatewayTransferNative` contract and [will call the](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L640-L651)  `GatewayTransferNative.onAbort()` function:
```solidity
function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:]; //@audit this will be the address of the src chain

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress //@audit src chain address
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }
```
The issue is that `onAbort` treats the `revertMessage` as if it was created on ZetaChain. However, for this particular instance, the `revertMessage[32:]` will contain the address that belong to the source chain, and it will be entirely wrong for the ZetaChain.

The `claimRefund()` function allows for refund claiming, but it will transfer the funds exactly to the `abortContext.revertMessage[32:]` address from the src chain:
```solidity
if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress))); //@audit 
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount); //@audit 
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
```

### Internal Pre-conditions

1. User needs to initiate cross-chain transaction with `asset == _ETH_ADDRESS_`;
2. The `GatewayTransferNative.onCall()` should fail and refund mechanism should be executed, but it won't be handled correctly for this case.

### External Pre-conditions

None.

### Attack Path

Check internal pre-conditions.

### Impact

Funds stuck at the `GatewayTransferNative` permanently or transferred to the wrong address and lost.

### PoC

_No response_

### Mitigation

In `GatewaySend.onRevert()` function check if the `asset == _ETH_ADDRESS_` and use `TransferHelper.safeTransferETH()` function in such case:
```diff
function onRevert(RevertContext calldata context) external onlyGateway {
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        address sender = address(uint160(bytes20(context.revertMessage[32:])));
+      if (context.asset == _ETH_ADDRESS_) {
+          TransferHelper.safeTransferETH(sender, context.amount);
+      } else {
+          TransferHelper.safeTransfer(context.asset, sender, context.amount);
}
```
