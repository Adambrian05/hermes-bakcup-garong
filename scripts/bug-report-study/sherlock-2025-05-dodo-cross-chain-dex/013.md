# Insecure Handling of Non-EVM Addresses in `onRevert`

__Summary:__ Funds sent from non-EVM chains might be lost or become permanently stuck if the cross-chain transaction reverts. This is due to the contract incorrectly handling non-EVM recipient addresses during the revert process.

__Vulnerability Detail:__ The `onRevert` function is called when a cross-chain transaction fails during the withdrawal phase on the target chain. It attempts to extract the original recipient address from the revert message. The logic assumes that if the address data is 20 bytes long, it's an EVM address and tries to send funds directly. However, non-EVM addresses (like Bitcoin or Solana) have different formats and lengths. If a non-EVM address's byte representation is misinterpreted or its length doesn't match the expected 20 bytes for direct transfer, the funds won't be sent to the correct recipient. In some cases, funds might be sent to an incorrect, unrecoverable address.

__Impact:__ Users initiating cross-chain transfers from non-EVM chains (like Bitcoin or Solana) risk losing their funds if the transaction fails after the swap on ZetaChain and triggers the `onRevert` callback.

__Code Snippet:__

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517-L548

__Recommendation:__ Modify the `onRevert` function to correctly identify and handle different non-EVM address formats included in the revert message. Avoid making assumptions based solely on byte length. Ensure that refunds for non-EVM recipients are consistently stored in `refundInfos` using a reliable identifier linked to the original non-EVM address.
