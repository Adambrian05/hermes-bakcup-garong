# Anyone can claim refund for non-EVM wallets

### Summary

The gateway offers refund options in case of revert and abort. Upon revert and abort, the external ID, wallet address, token address and amount will be stored and can be claimed later by user. However, due to a critical flaw in `claimRefund`, anyone can claim an non-EVM wallet refund if they know external ID.

### Root Cause

In [`onRevert`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517):
```solidity
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:];

        if(context.revertMessage.length == 52) {
            address receiver = address(uint160(bytes20(walletAddress)));
            TransferHelper.safeTransfer(context.asset, receiver, context.amount);

            emit EddyCrossChainRevert(
                externalId,
                context.asset,
                context.amount,
                walletAddress
            );
        } else {
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress
            });
            refundInfos[externalId] = refundInfo;
            
            emit EddyCrossChainRefund(
                externalId,
                context.asset,
                context.amount,
                walletAddress
            );
        }
```

Revert message is decoded, for EVM wallet addresses, the format will be 32 bytes of `externalId` and 20 bytes of address. But on other chains, address may be longer, and as a fallback mechanism, those will not immediately be transferred back to user. Instead, they will be stored in `RefundInfo`. Later, in `claimRefund`:
```solidity
    function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```

We see by default, `receiver` is set to `msg.sender`, but if the wallet address is 20 bytes, meaning it's an EVM address, it will update `receiver` to wallet's address. The next `require` clause does some access control, by making sure either `msg.sender` is one of the bots, which are trusted, or `msg.sender == receiver`. This issue lies here, if the wallet address is not an EVM address, the if branch will not be reached at all, so `receiver` will not be reassigned and keep its value as `msg.sender`. This means anyone can claim refund, as long as they know the external ID.

### Internal Pre-conditions

none

### External Pre-conditions

1. An non-EVM address is used to for cross chain transferring.
2. For any reasons, revert happened

### Attack Path

1. Attacker captured the revert event, and stole the refund.

### Impact

An non-EVM wallet refund will be stolen by anyone knows the `externalId`, which is quite simple, due to storage data is public on chain.

### PoC

_No response_

### Mitigation

Remove the `receiver = msg.sender` line at the start of function.
