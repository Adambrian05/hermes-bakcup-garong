# Cross-chain/Native Gateway never validate if the targetZRC is bitcoin, as well if the gasZRC matches the target one

### Summary

GatewayCrossChain's `onCall`, as well as GatewayNative's `withdrawToNativeChain` only validate the `decoded.dstChainId` which is a user input, they never check if the actual token is equal to Bitcoin (BTC.BTC).
Users are able to set the destination chain to bitcoin, but have a completely different ZRC20 being bridged, and this results in two things:

- Users being able to withdraw any gas token to any chain, not just bitcoin;
- The transaction failing because there isn't enough approval for the gasToken, since the zrc20 isn't a gas token.

### Root Cause

This report will focus on GatewayCrossChain's `onCall` flow.

When the ZetaChain Gateway invokes the `onCall` flow, after performing swaps, validations, fee reductions, etc. the flow will check the destination chain id, and if it's bitcoin, it will invoke the withdraw flow:

```solidity

 if (decoded.dstChainId == BITCOIN_EDDY) {
            (, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFee();
            _handleBitcoinWithdraw(
                externalId, 
                decoded, 
                outputAmount,
                gasFee
            );

            emit EddyCrossChainSwap(
                externalId, 
                uint32(context.chainID),
                decoded.dstChainId, 
                zrc20, 
                decoded.targetZRC20, 
                amount, 
                outputAmount - gasFee, 
                decoded.sender,
                decoded.receiver, 
                platformFeesForTx
            );
        } else {
            uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, 
                outputAmount, 
                decoded.receiver
            );


```

The problem is that it only checks the `dstChainId` which is a user-input and can be arbitrary. It never actually validates if the targetZRC20 is BTC.BTC (ZetaChain has a different ZRC20 for each connected chain that they support):

https://www.zetachain.com/docs/developers/tokens/zrc20/

Considering this, users are able to input an arbitrary targetZRC20, but with the dstChainId set as bitcoin which would allow them to withdraw the coin without going through the withdrawAndCall flow, i.e. `_handleEvmOrSolanaWithdraw` flow. The only requirement is that the token in-question is a gas token, for e.g. ETH.ETH.

### Internal Pre-conditions

None

### External Pre-conditions

User sets the dstChainId as Bitcoin, but the targetZRC20 as any gas token supported by ZetaChain;

### Attack Path

1. User sets the dstChainId as Bitcoin, but the targetZRC20 as any gas token supported by ZetaChain, allowing them to perform a withdrawal without going through the withdrawAndCall / _handleEvmOrSolanaWithdraw solana flow.

### Impact

Due to insufficient validation on the targetZRC20 whether it equals BTC.BTC, users are able to withdraw any gas token or cause the function to revert for any non-gas token while the dstChainId remains BTC.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L468

_No response_

### Mitigation

Check if the targetZRC20 is BTC.BTC, rather than checking a user-input which can be arbitrary.
