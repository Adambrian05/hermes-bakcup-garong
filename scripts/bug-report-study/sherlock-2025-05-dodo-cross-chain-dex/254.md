# Bypass of asset verification in `GatewayTransferNative::withdrawToNativeChain` enables theft of contract-held tokens via malicious ZRC20 message payload

### Summary

Improper separation of fee payment and message payload token validation in `GatewayTransferNative::withdrawToNativeChain` will cause unauthorized withdrawal of real assets from the contract, as an attacker can pay fees with a malicious ZRC20 token but specify real token addresses and amounts in the message payload to drain assets not yet superWithdrawn by the owner.

### Root Cause

In [`GatewayTransferNative::withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L531), the function uses the provided ZRC20 token only for fee payment and initial transfer validation but does not validate that the tokens and amounts specified in the `message` payload correspond to the same token used for fees. This design flaw allows an attacker to pass a malicious ZRC20 token to cover fees while specifying real token addresses and amounts in the `message`, enabling unauthorized withdrawal of real assets still held by the contract.

### Internal Pre-conditions

1. Attacker needs to call `withdrawToNativeChain` passing a malicious ZRC20 token address that covers the required fee and passes all initial token checks.
2. The contract must hold real tokens (the “real assets”) that have not been superWithdrawn by the owner yet.
3. The attacker needs to craft the message data in `withdrawToNativeChain` to specify real token addresses and amounts that exist in the contract’s balance.
4. The system does not perform cross-validation between the ZRC20 token used for fees and the token addresses/amounts specified in the `message`.
5. Even if(not necessary to happen) the withdrawal transaction reverts, the code enters `onRevert`, which will transfer the specified tokens (real assets) to the attacker.

### External Pre-conditions

1. The contract must currently hold the real tokens referenced in the malicious `message` payload.
2. The cross-chain message relay system must accept and forward the crafted `message` data without validating token consistency.

### Attack Path

1. Attacker deploys or uses a malicious ZRC20 token contract that passes fee checks but is under their control.
2. Attacker calls `GatewayTransferNative::withdrawToNativeChain` using the malicious ZRC20 token to pay fees and initiate the transfer.
3. In the `message` data, attacker specifies real token addresses and amounts currently held in the contract (assuming owner hasn’t superWithdrawn).
4. The contract verifies and deducts fees based on the malicious token but does not validate that the `message` corresponds to the token used for fees.
5. When the withdrawal triggers, the cross-chain message processing executes with the `message` data referencing real tokens, effectively withdrawing them to attacker’s destination.
6. If the withdrawal or transfer fails and reverts, the contract enters the `onRevert` handler, which then transfers the referenced tokens to the attacker anyway.


### Impact

The protocol suffers a full loss of all un-withdrawn legitimate ZRC20 tokens held in the contract. The attacker gains this entire amount by crafting malicious `withdrawToNativeChain` calls that misuse real token addresses embedded in the message payload.
