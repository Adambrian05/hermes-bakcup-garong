# Callable Refund Manipulation in GatewayCrossChain.sol

The `claimRefund` function can potentially be called by anyone if the `bots` mapping for their address is set to `true`. 

This opens up a possibility for refunds to be claimed by addresses that are not authorized recipients. 

While the verification ensures that either the message sender is a bot (`bots[msg.sender] == true`) or the sender is the rightful `receiver` of the refund, it fails to validate the legitimacy of the caller's role as a bot, leaving room for unchecked access if an address has mistakenly or maliciously been added to the `bots` mapping by an owner.

An attacker could manipulate or impersonate "bot" roles for refund claims, illegally redirecting funds, especially if bot provisioning is incorrectly handled in the `setBot` function or externally subverted.

(https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L589)

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); // Problematic access check
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");             

    // Transfers funds to potentially unauthorized "bot" role
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];  
    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}
```

### Recommendation

For any refund or bot-related interaction, cryptographic validation signatures can add an additional layer of security for ensuring legitimacy of the caller.
