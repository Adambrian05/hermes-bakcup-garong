# Overpaid ETH and unsolicited transfers remain locked due to missing refund and withdrawal logic

### Summary

Allowing msg.value to exceed the declared amount without refunding the surplus—and providing only receive()/fallback() to accept ETH with no way to withdraw it—locks both user overpayments and any accidental or malicious ETH transfers permanently in the contract

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L406

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L234

### Root Cause

In `depositAndCall`, the code only enforces msg.value ≥ amount and never refunds any msg.value – amount

The contract implements:

```solidity
receive() external payable {}
fallback() external payable {}
```
so it will accept any ETH sent, but there is no function to withdraw or recover that ETH.

### Internal Pre-conditions

1. User calls depositAndCall with fromToken == _ETH_ADDRESS_ and msg.value > amount.

2. Or any party sends ETH directly to the contract (triggering receive or fallback).



### External Pre-conditions

None 

### Attack Path

None

### Impact

User overpayments (the msg.value – amount portion) become irretrievably locked.

Accidental or malicious transfers to the contract (via receive/fallback) also become permanently trapped.

Over time, significant ETH can accumulate in the contract with no withdrawal mechanism.

Add an ETH withdrawal function restricted to authorized roles
