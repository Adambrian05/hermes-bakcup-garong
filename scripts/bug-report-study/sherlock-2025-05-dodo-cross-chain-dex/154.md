# Attacker will drain all ETH / ERC-20 held by GatewaySend contracts and their users

### Summary

A message-format mismatch between the *sender* (`depositAndCall`) and *receiver* (`onCall`) functions causes **arbitrary-value decoding** and will enable **unauthorised token transfers** for every GatewaySend instance, as an attacker can craft a cross-chain payload that `onCall` mis-interprets as the withdrawal parameters.


### Root Cause

In **`GatewaySend.sol`** the outbound message is built as

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218

```solidity
// depositAndCall(...)
bytes memory message = concatBytes(externalId, payload);  // <— only 32-byte ID + user payload
```

but the inbound parser expects

```solidity
// decodePackedMessage(...)
externalId  | uint256 outputAmount | uint16 receiverLen | uint16 dataLen | receiver | data
```

and `onCall` trusts the decoded values directly:

```solidity
(address fromToken, address toToken, ...) = decodePackedMessage(message);
...
IERC20(toToken).transfer(evmWalletAddress, outputAmount);  // <— attacker-controlled
```

Because **no length or field-order checks** are made, any payload of sufficient length is accepted, letting the attacker set `outputAmount`, `toToken` and `evmWalletAddress` at will.

### Internal Pre-conditions

1. **GatewaySend** must **hold** a positive balance of the target token or ETH.
2. The contract has an **allowance** from the Gateway equal to, or greater than, the attacker-chosen `outputAmount`.

### Path

1. Attacker learns GatewaySend’s address on **Chain B** and its token balances.
2. On **Chain A** attacker calls `depositAndCall`, sending a trivial amount (or even 0 if permitted).
3. `payload` is hand-crafted so that, when prefixed by a dummy `externalId`, its first 32 bytes after the ID equal the entire balance the attacker wants (`outputAmount`), the next 2 bytes give a small `receiverLen`, and the following bytes encode the attacker’s address and repeat the same token address for `fromToken` = `toToken`.
4. Gateway delivers `externalId || payload` to GatewaySend.onCall on Chain B.
5. `onCall` decodes the attacker’s values and, since `fromToken == toToken`, skips any swap.
6. `transfer` (or ETH send) moves `outputAmount` from the contract to the attacker.
7. Event logs show a legitimate `EddyCrossChainReceive`, masking the theft.

---

### Impact

The **GatewaySend contract (and, transitively, its users)** can lose **up to its entire ETH and ERC-20 balances** on each destination chain. The attacker gains the same amount; there is no cost beyond the minimal relay fee on the source chain.

---

### Mitigation

* **Encode–decode symmetry**: construct the outbound message with the full field layout that `decodePackedMessage` expects, or redesign the parser to read only the bytes appended by the sender.
* **Strict length & sanity checks** before acting on decoded parameters (e.g., require `message.length ≥ 68 + receiverLen + dataLen`).
