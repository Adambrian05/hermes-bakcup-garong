# Loss of ETH because onAbort() + claimRefund() Don’t Handle ETH Refunds

### Summary

When a cross-chain transaction sends ETH and the recipient is a **smart contract**, `onCall()` fails due to using Solidity’s `transfer()` (which doesn’t work on smart contracts). This triggers a revert path (`onRevert()` or `onAbort()`) to handle the ETH refunds but the problem here is `claimRefund()` handles only ERC20 logic and cannot actually refund ETH

Here the ETH will not be sent to the smart contracts because of using `transfer` function instead of `call()` function

```solidity
  if(toIsETH) {
      payable(evmWalletAddress).transfer(outputAmount);
  }
```

As a result, **users permanently lose ETH** because `claimRefund()` handles only Token refunds not Native ETH refunds. Here is the code snippet, please refer `@audit` comment

```solidity
    function claimRefund(bytes32 externalId) external {
       ...
       //@audit - Doesn't handle ETH transfers
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);\
       ...
    }
```

### Root Cause

1. **ETH transfer in `onCall()` fails**:

   ```solidity
   if (toIsETH) {
       payable(evmWalletAddress).transfer(outputAmount); // fails for contract receivers
   }
   ```

   * Transfer to Smart Contracts revert.
   * Triggers `GatewayCrosschain.onAbort()` finally by TSS

2. **Refund are not processed correctly in `GatewayCrosschain.claimRefund()`

   ```solidity
   TransferHelper.safeTransfer(refund.token, msg.sender, refund.amount);
   ```

   * This works for ERC20, but **fails silently for ETH (`address(_ETH_ADDRESS)`)**. //0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE
   * `claimRefund()` does not check if refund is ETH and does not use `.call{value: ...}("")`.

### Attack Path

1. Deploy a smart contract
2. Use its address as receiver in a cross-chain ETH swap.
3. `onCall()` fails due to `.transfer()`
4. TSS calls `onAbort()` when revert fails, refund is stored with:
   ```solidity
   refund.token == address(_ETH_ADDRESS) // 0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE
   refund.amount == ETH sent
   ```
5. User calls `claimRefund()` but the transaction `fails` because it considers ETH address as ERC20 token but they should transfer native ETH  -  **ETH is not received**.
7. ETH remains stuck inside `gatewaySend`. User loses the fund because claimRefund() doesnt handle it properly


### Impact

* **Permanent ETH loss** for any user sending ETH to contracts
* **Permanent ETH loss** for any user sending ETH but reverts due during cross chain transactions

### Mitigation

Update `claimRefund()` to make sure we are handling ETH transfers as well

   ```diff
 +  if (refund.token == _ETH_ADDRESS) {
 +      TransferHelper.safeTransferETH(msg.sender, refund.amount);
   } else {
       TransferHelper.safeTransfer(refund.token, msg.sender, refund.amount);
   }
   ```

 Alternatively consider updating `GatewaySend.onCall()` to use `call()` in place of `transfer()` because transfer is not to be used if we see from good security practices unless there is any strong reason not to support smart contract ETH transfers by the protocol but make sure `claimRefund` is fixed as shown above

   ```diff
   - payable(evmWalletAddress).transfer(outputAmount);
    // use  receiver instead of evmWalletAddress
   + (bool success, ) = receiver.call{value: outputAmount}("");
   + require(success, "ETH transfer failed");
   ```
