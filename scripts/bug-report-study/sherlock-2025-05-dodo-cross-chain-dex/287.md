# ETH Revert Handling Failure in Cross-Chain Operations

### Summary

Incorrect ETH handling in the revert function will cause a complete failure of ETH refunds for users as the gateway will attempt to call an invalid ERC20 transfer on the ETH placeholder address.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393-L404

### Root Cause

In `GatewaySend.sol:394-404` the `onRevert` function uses `TransferHelper.safeTransfer()` for all assets including ETH, but ETH uses a placeholder address `address(0)` which is not a valid ERC20 contract as explained below

```js
/// @notice Struct containing revert context passed to onRevert.
/// @param sender Address of account that initiated smart contract call.
/// @param asset Address of asset. On a connected chain, it contains the fungible
>> @/// token address or is empty if it's a gas token. On ZetaChain, it contains the 
/// address of the ZRC20.
/// @param amount Amount specified with the transaction.
/// @param revertMessage Arbitrary data sent back in onRevert.
struct RevertContext {
    address sender;
    address asset;
    uint256 amount;
    bytes revertMessage;
}
``` 


### Internal Pre-conditions

1. User needs to initiate a cross-chain ETH transfer that fails on the destination chain
2. Gateway needs to call `onRevert` with `context.asset` set to `address(0)` 

### External Pre-conditions

None

### Attack Path

1. User calls `depositAndCall` with ETH as the asset
2. Cross-chain transaction fails on destination chain
3. Gateway calls onRevert with ETH context
4. `TransferHelper.safeTransfer()` attempts to call transfer on 0x00000000000000000000
5. Transaction reverts as this address has no ERC20 contract

### Impact

Users cannot receive ETH refunds when cross-chain ETH transactions fail, resulting in permanent loss of their ETH deposits.
