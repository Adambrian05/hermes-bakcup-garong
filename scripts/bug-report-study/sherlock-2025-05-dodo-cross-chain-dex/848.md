# Incorrect Pool Validation Allows Griefing via Dummy Contracts in Cross-Chain Swap Routing

### Summary

The _existsPairPool() function incorrectly assumes that checking token balances is sufficient to validate the usability of a UniswapV2-style pair. This allows an attacker to send minimal token amounts to a predicted pool address, tricking the system into routing swaps through non-functional addresses. causing a dos when a swap between two tokens that do not have a uniswap pool with sufficient liquidity occurs rather than routing the swap through other paths 



### Root Cause


```solidity
function _existsPairPool(...) internal view returns (bool) {
    address uniswapPool = uniswapv2PairFor(...);
    return IZRC20(zrc20A).balanceOf(uniswapPool) > 0 &&
           IZRC20(zrc20B).balanceOf(uniswapPool) > 0;
}
```
This is a conceptual mistake :
The choice to rely solely on balance checks is a mistake as it does not confirm that the computed pool address contains a valid UniswapV2-compliant contract or has sufficient liquidity for meaningful trades.

### Attack Path

1. Attacker computes a predicted pool address using CREATE2 logic.
2. Sends 1 wei of each token to that address to mimic liquidity.
3. User initiates a cross-chain swap; the system routes through the fake pool due to positive balance checks.
4. Swap reverts during execution .



### Impact

users will be griefed from performing swaps that do not have a already deployed uniswap pair or that has a pair but with insufficient liquidity
