# onRevert

### Summary

A strict equality check on the `revertMessage` length in `onRevert` forces transactions into the manual refund claim process unnecessarily, impacting usability and potentially exposing non-EVM refunds to theft.

### Vulnerability Detail

The `onRevert` function (L268-284) uses `if(context.revertMessage.length == 52)` to decide whether to directly transfer funds or store refund information. If the gateway sends a message with a length other than exactly 52 bytes (even if it contains the necessary prefix), the check fails, and the refund is stored in `refundInfos`.

### Impact

Users whose transactions revert may be forced to manually call `claimRefund` to retrieve their funds, even if a direct transfer was possible. For non-EVM chain refunds, this forces the funds into the `refundInfos` mapping, making them vulnerable to the High severity non-EVM refund theft vulnerability (Issue 1).

### Code Snippet
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L612

### Recommendation

Change the strict equality check (`== 52`) to a prefix check (`>= 52`) if the gateway is expected to send messages that might be longer than 52 bytes but still contain the necessary prefix for direct transfer. Ensure the logic for handling messages with length != 52 is robust and secure, especially considering the non-EVM refund vulnerability.
