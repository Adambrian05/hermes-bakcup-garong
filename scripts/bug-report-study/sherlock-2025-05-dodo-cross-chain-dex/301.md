# Amount Mismatch in depositAndCall Function

## Summary  
In the `GatewaySend` contract, the `depositAndCall` function facilitates token deposits and cross-chain calls, with an optional token swap via the DODO router. A critical issue arises when the `amount` of tokens sent by the user does not equal the `swapData.fromTokenAmount` specified for the swap. There is no validation to enforce this equality, leading to two scenarios:  
- If `amount > swapData.fromTokenAmount`, the excess tokens are retained by the contract without being utilized or refunded to the user.  
- If `amount < swapData.fromTokenAmount`, the swap fails due to insufficient tokens, causing the entire transaction to revert.  
This lack of validation can result in users losing funds or experiencing failed transactions, negatively impacting usability and trust in the contract.
- Issue at [line](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L205)

## Root Cause (In Detailed)  
The issue stems from the absence of a validation check in the `depositAndCall` function to ensure that the `amount` parameter matches the `fromTokenAmount` field in the `swapData` structure when a swap is involved. Here’s how the function operates:  
- The user transfers `amount` of `fromToken` to the contract, either as ETH (via `msg.value`) or an ERC20 token (via a prior transfer).  
- If `swapData` is provided, it is decoded into a `MixSwapParams` struct, which contains `fromTokenAmount`—the expected input amount for the swap.  
- The swap is executed by calling `_doMixSwap`, which uses `fromTokenAmount` as the input amount, regardless of the actual `amount` received.  

Since no check enforces `amount == swapData.fromTokenAmount`, the following problems occur:  

1. **Excess Tokens (`amount > swapData.fromTokenAmount`)**:  
   - The swap consumes only `swapData.fromTokenAmount` of the `fromToken`.  
   - The remaining tokens (`amount - swapData.fromTokenAmount`) stay in the contract after the swap completes.  
   - No mechanism exists to refund or otherwise handle these excess tokens, effectively locking them in the contract.  

2. **Insufficient Tokens (`amount < swapData.fromTokenAmount`)**:  
   - The contract receives only `amount` of `fromToken`.  
   - During the swap, `_doMixSwap` attempts to approve and transfer `swapData.fromTokenAmount` to the DODO router.  
   - Since the contract’s balance of `fromToken` is less than `swapData.fromTokenAmount`, the transfer fails, causing the transaction to revert.  

This vulnerability arises from the assumption that users will always provide consistent values for `amount` and `swapData.fromTokenAmount`. Without proper validation, user errors lead to either lost funds or wasted gas from reverted transactions.

## Example  
Below are two examples illustrating the consequences of the mismatch:  

**Example 1: Excess Tokens Sent**  
- A user wants to swap 100 USDC and calls `depositAndCall` with `amount = 150 USDC` and `swapData.fromTokenAmount = 100 USDC`.  
- The swap executes successfully, using 100 USDC as specified in `swapData`.  
- The remaining 50 USDC stays in the contract, inaccessible to the user, resulting in an unintentional loss of 50 USDC.  

**Example 2: Insufficient Tokens Sent**  
- A user intends to swap 100 USDC but mistakenly sets `amount = 80 USDC` while `swapData.fromTokenAmount = 100 USDC`.  
- The swap attempts to transfer 100 USDC to the DODO router, but only 80 USDC is available in the contract.  
- The transaction reverts due to the insufficient balance, and the user incurs gas costs for a failed attempt.

2. **Test Case 1: Excess Tokens**

3. **Test Case 2: Insufficient Tokens**  
   - User calls `depositAndCall` with `amount = 80e6` (80 USDC).  
   - The transaction reverts when `_doMixSwap` attempts to transfer 100 USDC.  
   - Confirm that no tokens are swapped, and the user’s funds remain unchanged (minus gas costs).

## Recommendation  
To mitigate this issue and enhance the contract’s reliability, consider the following solutions:  

1. **Enforce Exact Match (Preferred)**:  
   Add a validation check to ensure `amount` equals `swapData.fromTokenAmount` when a swap is specified. This prevents both excess and insufficient token scenarios.  
   ```solidity
   function depositAndCall(address fromToken, uint256 amount, bytes calldata swapData, address targetContract, address asset, uint32 dstChainId, bytes calldata payload) public payable {
       if (swapData.length > 0) {
           MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
           require(amount == params.fromTokenAmount, "AMOUNT_MISMATCH: amount must equal fromTokenAmount");
       }
       // Proceed with deposit and swap logic
   }
   ```

2. **Refund Excess Tokens**:  
   Allow flexibility by accepting `amount >= swapData.fromTokenAmount` and refunding any excess to the user.  
   ```solidity
   if (swapData.length > 0) {
       MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
       require(amount >= params.fromTokenAmount, "INSUFFICIENT_AMOUNT: amount less than fromTokenAmount");
       uint256 excess = amount - params.fromTokenAmount;
       if (excess > 0) {
           if (fromToken == _ETH_ADDRESS_) {
               payable(msg.sender).transfer(excess);
           } else {
               IERC20(fromToken).transfer(msg.sender, excess);
           }
       }
   }
   ```

The exact match enforcement (Option 1) is recommended as the simplest, most secure fix, ensuring users cannot accidentally lose funds or waste gas on failed transactions due to input errors.
