# Fee deduction logic mismatch causes incorrect amount processing in `GatewayTransferNative::onCall`

### Summary

The fee is not subtracted from the amount in `GatewayTransferNative::onCall`, so when swapping tokens, the swap is called with the full amount instead of `amount - platformFeesForTx`, causing incorrect token processing.

### Root Cause

In [`GatewayTransferNative::onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L395), the fee is not subtracted from the input amount before swapping tokens, causing the contract to attempt swapping the full amount. This may lead to swapping tokens that are not actually held by the contract and effectively bypasses fee deductions if the contract holds tokens, resulting in an incorrect balance and unintended token transfers.

### Internal Pre-conditions

1. The contract must hold a non-zero balance of the token being swapped.
2. The fee amount is deducted elsewhere but not subtracted from the swap amount in `GatewayTransferNative::onCall`.
3. The function triggering the swap is called with an amount equal to the full input (including fee).
4. The swap logic relies on the full input amount without verifying available token balance in the contract.

This allows the user to bypass the fees, as they effectively get the fee amount back, or the entire transaction unintentionally reverts.

### External Pre-conditions

1. The token contract must allow transfers or swaps without additional restrictions.
2. The external swap protocol (DEX or router) used must accept the amount parameter as-is without verifying fees deducted elsewhere.
3. No external mechanism enforces fee deduction before the swap call.
4. External conditions (e.g., token balance on the contract) remain unchanged during the swap execution.

### Attack Path

1. The gateway calls `GatewayTransferNative::onCall` with an amount including fee.
2. The contract initiates a token swap using the full amount (without subtracting the fee).
3. If the contract holds tokens, the swap attempts to use tokens which are not intended for swaps (since fees weren’t subtracted).
4. This causes the user to effectively bypass the fee, as the fee amount is never deducted or enforced.
5. Alternatively, the transaction may revert unexpectedly because the contract does not contain the tokens

### Impact

The fee is not subtract from the inputed `amount` which allows the receiver to bypass the fees, as they effectively get the fee amount back, or the entire transaction unintentionally reverts.

### Mitigation

Ensure the fee is consistently subtracted from the input amount before any swap or transfer operations across all relevant contract functions.
