# Setting non-zero `feePercent` turns every swap-path call into a revert and may lead to funds being siphoned

### Summary

In `GatewayTransferNative`, a non-zero `feePercent` introduces a platform fee that is deducted from the swap amount and is transferred to the treasury. When a swap involves a cross-chain transfer of two different tokens (e.g. Chain A -> ZetaChain, swapping token1A -> token1Z -> token2Z), the platform fee is not deducted from the amount encoded in the message that gets sent to the DODORouter. The router contract tries to pull the full amount but the `GatewayTransferNative` contract will have insufficient balance of the token (token1Z) since a platform fee has already been deducted from the full amount, and thus reverts. Users who need to swap can no longer complete a transfer since the fee logic creates a DOS. In the worst case scenario, any surplus of token1Z in the contract can gradually get siphoned away by the faulty fee logic.

This affects the following cross-chain swap paths:
- token1A -> token1Z -> token2Z
- ETH -> token3Z -> token2Z
- token1A -> ETH -> token3Z -> token2Z
- token1A -> token2A -> token2Z -> token1Z
 
(Not sure if Solana or BTC related swaps are affected because they were not tested)

### Root Cause

In [`GatewayTransferNative::onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L367-L396), the function decodes `_message` which contains the swap parameters (`params`) needed for the DODO Router - including the swap amount. Then it calls `_handleFeeTransfer` which calculates the platform fee and also sends that fee amount to the treasury. The `else` block gets executed when a swap on the DODO Router is required, however the function does not handle the fee deduction and passes the parameters directly to the router.

### Internal Pre-conditions

Owner sets a fee percent by calling `GatewayTransferNative::setFeePercent` with an argument that is any amount more than `0`, not exceeding `1000`.

N/A

### Attack Path

Normal workflow from `GatewaySend::depositAndCall` which subsequently calls `GatewayTransferNative::onCall`.
I.e. Assuming that fees have been set in `GatewayTransferNative`:
1. User -> `GatewaySend` (`depositAndCall`)
2. `GatewaySend` -> `GatewayEVM` (`depositAndCall`)
3. `GatewayEVM` -> `GatewayZEVM` (`depositAndCall`)
4. `GatewayZEVM` -> `GatewayTransferNative` (`onCall`)
```scss
User1
  └─(ERC-20 & payload)─► GatewaySend
        └─► GatewayEVM
              └─(cross-chain)─► GatewayZEVM
                    └─► GatewayTransferNative.onCall
```

### Impact

Without the deduction from the swap amount specified in the parameters passed to the DODO Router, the router will try to pull the full amount from the contract. Two outcomes can arise from this problem:

- Scenario A: Contract Balance < amount for swap
All cross-chain swap calls goes through `GatewayTransferNative` will fail, resulting in permanent DOS until the contract has sufficient balance.

- Scenario B: Contract Balance >= amount for swap (because contract has surplus)
The DODO Router succeeds but pulls extra tokens (token1Z) from the contract's reserves. The extra tokens that were pulled from the reserves would be equivalent to the user's platform fee. Gradually, the reserves of the token in `GatewayTransferNative` will be silently drained over time. Note that it is possible to build up a reserve in the `GatewayTransferNative` contract (as demonstrated in [`test_ANativeSwap2ZSwap()`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/test/GatewayTransferNative.t.sol#L141-L204) when the second swap amount leaves a surplus in the contract).
