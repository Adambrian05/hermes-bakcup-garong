# Missing Collateral Locking During Cross-Chain Transfers Allows Protocol Draining

### Summary

The absence of an explicit collateral lock during cross-chain transfer operations will cause a protocol-draining risk for all users as a malicious actor can initiate a cross-chain transfer via depositAndCall and reuse or withdraw their collateral on the source chain before the cross-chain state is synchronized. This allows them to escape with swapped or released funds on the destination chain, leaving the protocol under-collateralized.

### Root Cause

In GatewaySend.depositAndCall, the contract performs a transferFrom of tokens or receives native ETH from the user and then immediately sends a cross-chain message via ZetaChain. However, there is no collateral locking, internal balance tracking, or in-flight accounting to prevent the user from reclaiming or double-using the same tokens while the cross-chain message is pending.

On the destination chain, the onCall function assumes the cross-chain payload is valid and proceeds to execute a token transfer or swap unconditionally. This finalizes a release of assets based on the belief that tokens are fully committed on the source chain — a trust assumption that is exploitable without enforced locking.

### Internal Pre-conditions

	
1. A user must have a valid token allowance or sufficient ETH to execute depositAndCall().
2 The token must support transferFrom() without enforcing non-reentrancy or locking internally.
3. There is no collateral accounting in GatewaySend to track in-flight cross-chain messages.

### External Pre-conditions

1. ZetaChain must allow onCall() on the destination chain to execute asynchronously after the source call.
2. The destination chain relies solely on the input payload for swap execution and has no on-chain collateral verification.
3. Network delay or transaction timing must allow the attacker to act before destination finalization.


### Attack Path

1. The attacker calls GatewaySend.depositAndCall(), transferring 1000 tokens to initiate a cross-chain swap.
2. The function performs transferFrom() and immediately forwards a cross-chain message via ZetaChain.
3. Before the destination onCall() executes, the attacker manipulates allowances, triggers a withdrawal, or reuses the token balance elsewhere (e.g., flashloan or faulty accounting).
4. GatewayCrossChain.onCall() executes on the destination chain, assuming that the 1000 tokens are locked on the source.
5. The swap executes and sends value to the attacker’s wallet on the destination chain.
6. The attacker walks away with output assets while leaving the protocol short of the required input on the source chain.

### Impact

The protocol becomes under-collateralized. A malicious user drains assets from the destination chain without leaving valid locked collateral on the source. In the worst case, this can lead to insolvency and loss of user funds across chains.

### Mitigation

- Lock tokens on the source chain using internal accounting (e.g., pendingTransfers[user][token] = amount) during depositAndCall.
- Prevent reuse or withdrawal of tokens with active in-flight operations.
- Clear pending transfers only after a verified onCall() receipt or onRevert() cleanup.
- Alternatively, enforce collateral reserve logic via an intermediate vault or custody contract.
