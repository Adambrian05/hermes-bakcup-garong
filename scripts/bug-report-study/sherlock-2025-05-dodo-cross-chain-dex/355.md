# The `amount` input in the `withdrawToNativeChain` function can be more than `msg.value` if user tries to withdraw by native token

## Vulnerability Details
In a situation where a user wants to call the `withdrawToNativeChain` function to withdraw native tokens, the `amount` input should not exceed `msg.value`. If this condition is violated, the following malicious scenario could occur:

A malicious user calls the `withdrawToNativeChain` function, providing `_ETH_ADDRESS_` as `zrc20` input address and specifying an `amount` of 5 ether. However, he intentionally sets `msg.value` to only 1 ether. 

As a result:
- The user pays only 1 ether (`msg.value`).
- The specified withdrawal `amount` in destination chain is 5 ether of value.

The `withdrawToNativeChain` function proceeds to call `_handleEvmOrSolanaWithdraw`, which in turn calls `withdrawAndCall`. This function interacts with the gateway, using `outputAmount - gasFee` as the transfer amount, which is essentially 5 ether minus some fees.

This means an attacker could receive more funds at the destination chain than they originally paid, potentially leading to fund discrepancies and exploitation.


## POC
In the test below, `amount` is 100 ETH, while `msg.value` is only 1 ETH. The `withdrawToNativeChain` function works without any restrictions until it reaches the `_handleEvmOrSolanaWithdraw` function at line [580](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L580), which is the subject of another issue I reported separately. The point of this report is that the code continues executing there without any restrictions, unlike the logic in `GatewaySend::depositAndCall` at line [232](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L232C9-L233C12), where we needed similar restrictions in `withdrawToNativeChain` as well.
Copy the test bellow to the `GatewayTransferNative.t.sol` file. 

```solidity
  function testWithdrawWithNativeToken() public {
      uint256 amount = 100 ether;
      uint32 dstChainId = 2;
      address targetZRC20 = address(token1Z);
      bytes memory sender = abi.encodePacked(user1);
      bytes memory receiver = abi.encodePacked(user2);
      bytes memory swapDataZ = "";
      bytes memory contractAddress = abi.encodePacked(address(gatewaySendB));
      bytes memory fromTokenB = abi.encodePacked(address(token1B));
      bytes memory toTokenB = abi.encodePacked(address(token1B));
      bytes memory swapDataB = "";
      bytes memory accounts = "";
      bytes memory message = encodeMessage(
          dstChainId,
          targetZRC20,
          sender,
          receiver,
          swapDataZ,
          contractAddress,
          abi.encodePacked(fromTokenB, toTokenB, swapDataB),
          accounts
      );

      vm.startPrank(user1);
      token1Z.approve(address(gatewayTransferNative), amount);
      gatewayTransferNative.withdrawToNativeChain{value: 1 ether}(
          _ETH_ADDRESS_,
          amount,
          message
      );
      vm.stopPrank();
  }
```
## Impact
An attacker could receive more funds at the destination chain than they originally paid in the zetachain. 

## Mitigation
Consider modifying the `withdrawToNativeChain` function as shown below:

```diff
    function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
+      if(zrc20 == _ETH_ADDRESS_) {
+        require(
+          msg.value >= amount, 
+          "INSUFFICIENT AMOUNT: ETH NOT ENOUGH"
+        );
+      }

      ...
    }
```
