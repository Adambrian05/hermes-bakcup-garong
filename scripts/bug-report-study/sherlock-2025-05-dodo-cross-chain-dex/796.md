# Cross Chain Transaction Fails During Fee Transfer When Deposited Token is Native

### Summary

When a cross-chain transaction occurs where GatewayCrossChain is the targetContract and Zeta is deposited, GatewayZEVM has a special depositAndCall function that handles native Zeta. First it performs some validations, then it transfers Zeta to the targetContract, and then finally calls GatewayTransferNative.onCall(), passing in zetaToken (i.e. wZETA) as the asset.

When GatewayCrossChain:onCall receives the call, the call will always fail at `_handleFeeTransfer` because the contract holds native Zeta, but attempts to transfer wZETA as the protocol fee. 

### Root Cause

Protocol attempts to transfer wZeta when it only has Zeta:
```solidity
function _handleFeeTransfer(address zrc20, uint256 amount) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; 
>>>     TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
```
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L297-L300

### Internal Pre-conditions

1. User initiates a cross-chain transaction where GatewayCrossChain is the targetContract and Zeta is deposited

### External Pre-conditions

n/a

### Attack Path

1. User initiates a cross-chain transaction depositing native Zeta
2. Native Zeta is transferred to GatewayCrossChain
3. GatewayCrossChain:onCall attempts to charge protocol fees in wZETA, but the contract only holds native Zeta, causing _handleFeeTransfer to revert.

### Impact

GatewayCrossChain is incompatible when the native token is Zeta.

### PoC

_No response_

### Mitigation

Immediately convert the Zeta to wZETA when the contract receives Zeta.
