# User-Controlled Swap Params Allow Draining of Contract-Owned Tokens

### Summary

The onCall() function in the ZEVM contract receives a token and amount from the Gateway but does not validate that the decoded MixSwapParams match these values.

Specifically:

params.fromToken is taken directly from user-provided message
params.fromTokenAmount is also user-controlled
As a result, an attacker can:

Bridge a negligible amount of any token (e.g., 1 DAI)
Encode a swap from a high-value token (e.g., WZETA) that the contract already owns
Receive the output token (e.g., USDC), while the contract uses its own funds to fulfill the swap
This opens up a attack vector and allows attackers to completely drain contract-held tokens .



### Root Cause

In onCall():

```solidity
uint256 outputAmount = _doMixSwap(decoded.swapData, amount, params);
```
Where:
amount and zrc20 are provided by the Gateway (safe)
But params.fromToken and params.fromTokenAmount come from the user-encoded message
No validation ensures:

```solidity
params.fromToken == zrc20
params.fromTokenAmount == amount
```
So the contract assumes the user deposited params.fromTokenAmount of params.fromToken — even if they didn’t.

### Attack Path

assuming price of wzeta = 4000 usd 
Step 1: Attacker calls depositAndCall() with minimal deposit
Sends 1 DAI to bridge to ZEVM
Encodes message claiming:
fromToken = WZETA
fromTokenAmount = 100
targetZRC20 = DAI
Step 2: On ZEVM, onCall() decodes message
Receives 1 DAI → stores it in contract
Decodes message as request to swap 100 WZETA → DAI
Calls DODO router with those parameters
Step 3: DODO performs swap using contract-owned WZETA
Since contract holds 100 WZETA, swap succeeds
Step 4: Contract sends DAI to attacker
Even though attacker only sent 1 DAI
Result:
Contract loses 100 WZETA (~$40,000)
Attacker receives DAI worth ~$40,000
For only $1 cost

### Impact

zevm contracts can be fully drained of any token
