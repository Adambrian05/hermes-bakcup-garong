# Incorrect Address Decoding Leading to Fund Loss

__Summary:__ A logical error in `BytesHelperLib.bytesToAddress` causes it to incorrectly decode address values from byte arrays. When this flawed function is used in `GatewayTransferNative.sol` to decode the target ZRC20 token address from a cross-chain message, it creates a critical vulnerability allowing attackers to redirect token transfers and steal funds.

__Vulnerability Detail:__ The `BytesHelperLib.bytesToAddress` function slices 20 bytes from the input (`data[offset:offset + 20]`) into a temporary `bytes memory` variable `b`. Its assembly code then attempts to load the address using `mload(add(b, 20))`. This assembly logic is incorrect for extracting the 20-byte address from the memory representation of `b`. This function is called by `SwapDataHelperLib.decodeNativeMessage` to decode the `targetZRC20` address from the beginning of the incoming cross-chain message. The resulting, incorrectly decoded `targetZRC20` address is subsequently used as the recipient token address in `TransferHelper.safeTransfer` calls within `GatewayTransferNative.onCall`.

__Impact:__ An attacker can craft a cross-chain message such that the initial bytes, when processed by the flawed `BytesHelperLib.bytesToAddress` function, result in an address controlled by the attacker. `GatewayTransferNative.onCall` will then proceed to transfer the user's tokens to this attacker-controlled address instead of the intended recipient, leading to direct theft of user funds.

__Recommendation:__ Correct the `BytesHelperLib.bytesToAddress` function to accurately decode a 20-byte address. Replace the assembly block with standard Solidity conversion: `return address(bytes20(data[offset:offset+20]));`. Ensure this fix is applied and tested thoroughly, and review all other usages of `BytesHelperLib` functions for similar issues.
