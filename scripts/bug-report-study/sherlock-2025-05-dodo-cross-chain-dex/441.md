# Misaligned Calldata Access in decodePackedData Leads to Incorrect Address Decoding

## Description
 The function decodePackedData, there is a misalignment risk in calldata decoding using low-level calldataload, which can lead to incorrect address extraction, especially for tokenB.

It uses calldataload with hardcoded offsets and assumes tight packing of 20-byte addresses in calldata. However, calldataload always reads 32 bytes, so extracting a 20-byte address from a non-32-byte-aligned offset (like byte 20 for tokenB) risks misalignment and incorrect data interpretation.

Impact:
Incorrect extraction of tokenB from calldata can:

Lead to reading and using an incorrect address.

Cause token transfer or swap logic to malfunction.

Introduce fund loss or unexpected behavior in downstream logic relying on tokenB.

## Recommendation
Replace the low-level assembly decoding with safe, high-level Solidity slicing.
```solidity
function decodePackedData(bytes calldata data) internal pure returns (
    address tokenA,
    address tokenB,
    bytes calldata swapDataB
) {
    require(data.length >= 40, "Invalid calldata: too short");

    tokenA = address(bytes20(data[0:20]));
    tokenB = address(bytes20(data[20:40]));
    swapDataB = data.length > 40 ? data[40:] : data[0:0]; // safely slice any remaining bytes
}
```
Why This Is the Best Solution:
Safe alignment: Slicing bytes calldata respects alignment and avoids manual offset errors.

No assembly: Easier to read, audit, and maintain. Avoids the risks of incorrect bit shifting and alignment.

Gas-efficient: On the EVM level, slicing from calldata is relatively efficient and comparable to assembly in many cases.

Fails early: The require ensures that the calldata contains enough bytes, preventing out-of-bounds access.
