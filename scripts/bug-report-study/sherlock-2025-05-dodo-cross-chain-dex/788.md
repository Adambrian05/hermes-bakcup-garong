# `GatewayCrossChain::claimRefund` allows anyone to steal Solana refunds

### Summary

The `claimRefund` function in `GatewayCrossChain` has a critical authorization bypass vulnerability. When a refund is queued for a non-evm `walletAddress`, anybody can call the function to claim the `refund`

### Root Cause

The flawed logic is in how the `receiver` address is determined and used in the authorization check. If the stored `refundInfo.walletAddress` is not 20 bytes long (the length of an EVM address), the `receiver` variable defaults to `msg.sender`.

```solidity
// file: omni-chain-contracts/contracts/GatewayCrossChain.sol

function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    
    // For non-EVM addresses, receiver == msg.sender, so this check is always true.
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    // ...
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    // ...
}
```
When `receiver` is equal to `msg.sender`, the `require` statement becomes `bots[msg.sender] || true`, which is always true. This completely bypasses the intended check, which was likely meant to restrict the caller to either the legitimate recipient or a trusted bot.

### Attack Path

1. Wait for someone to initiate `GatewaySend::depositAndCall`, which then calls `GatewayCrossChain::onCall`. For this scenario, let's say that `_handleEVMorSolanaWithdraw` is executed.

2. This person would then specify his preferred 32-byte Solana address in decoded.receiver seen [here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L490-L495):

```solidity
  uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, 
                outputAmount, 
                decoded.receiver
            );
```

3. Should for any reason `onCall` fails on the Solana Program, `GatewayCrossChain::onRevert` will be triggered. Do note that the devs plan to make this compatible with Solana programs by specifying `bytes memory contractAddress` in `GatewayCrossChain::withdrawAndCall`to accomodate for 32-byte Solana addresses.

4. In `GatewayCrossChain::onRevert`, since `context.revertMessage.length != 52`, the else statement is executed:
```solidity

function onRevert(RevertContext calldata context) external onlyGateway {
    //...
 bytes memory walletAddress = context.revertMessage[32:];
//...
 if(context.revertMessage.length == 52) {
    //...
 }
    else {
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress // 32 bytes here
            });
            refundInfos[externalId] = refundInfo;
            
            //...
        }
```
5. Attacker monitors this and calls claimRefund with the user's `externalId`. Since `refundInfo.walletAddress.length != 20`, the `receiver` will be set to the attacker as `msg.sender`, and the funds will be transferred to the attacker as seen [here](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574-L581)
### Impact

Should `withdrawAndCall` fail on Solana network, anyone can steal `SOL.SOL` via `claimRefund`.
