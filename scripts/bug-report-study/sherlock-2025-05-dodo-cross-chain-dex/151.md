# Fee calculation bug enables protocol fund drainage or transaction failures

### Summary

A fee calculation logic error will cause either transaction failures or protocol fund drainage as the contract attempts to swap the full original amount instead of the amount after fees are deducted. When the contract has accumulated token balances, users will effectively get free swaps using protocol funds, and when insufficient balances exist, transactions will fail completely.

### Root Cause

In [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L395C12-L395C81) the `_handleFeeTransfer()` function deducts platform fees from the contract's token balance and sent to `EddyTreasurySafe`, but in the `_doMixSwap()` function still attempts to swap the original full amount rather than the amount after fees are deducted.

```solidity
//  Fees are sent to EddyTreasurySafe
function _handleFeeTransfer(
    address zrc20,
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
    TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
}
```

```solidity
// Swap attempts to use full original amount instead of (amount - platformFeesForTx)
uint256 outputAmount = _doMixSwap(decoded.swapData, amount, params);
```

### Internal Pre-conditions

1. `feePercent` > 0

### External Pre-conditions

None

### Attack Path

1. User calls any function that triggers `onCall()` with a cross-chain swap (e.g., via `gatewaySend.depositAndCall()`)
2. Gateway transfers tokens to `GatewayTransferNative` contract and calls `onCall()`
3. `onCall()` calls `_handleFeeTransfer(zrc20, amount)` which transfers `(amount * feePercent) / 1000` tokens to treasury
4. Contract now has `amount - platformFeesForTx` tokens remaining
5. `onCall()` calls `_doMixSwap(decoded.swapData, amount, params)` attempting to swap the full original `amount`
6. **Two possible outcomes:**
   - **If contract has insufficient balance:** Transaction fails with `ERC20InsufficientBalance` error
   - **If contract has accumulated balances:** Transaction succeeds, but uses protocol's accumulated funds to subsidize the user's swap

### Impact

The protocol suffers from two critical issues:

1. When the contract has accumulated token balances, users receive more swap value than they should. While users do pay fees (sent to treasury), they get swap outputs based on the full pre-fee amount instead of the post-fee amount. The protocol's accumulated funds make up the difference, effectively subsidizing users' swaps.

2. When the contract has insufficient accumulated balances, all cross-chain swap transactions fail completely, causing a denial of service for the protocol's core functionality.

The `superWithdraw()` function indicates the contract is designed to hold multiple token types, making subsidization the more likely scenario in production. Users would effectively receive enhanced swap value at the protocol's expense, leading to gradual depletion of accumulated funds.

_No response_

### Mitigation

Fix the swap amount calculation to use the amount after fees are deducted
