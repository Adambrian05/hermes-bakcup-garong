# Out-of-Bounds read in refund handlers can cause temporary or permanent fund loss

### Summary

**Affected Contracts:**
- [`GatewaySend.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393)
- [`GatewayCrossChain.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517)
- [`GatewayTransferNative.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607)

The `onRevert` and `onAbort` callback functions are critical for refunding users if a cross-chain operation fails. These functions parse a [`revertMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L394) from ZetaChain using a fixed-offset slice. However, if a failure in a downstream dependency (such as an external DEX accessed via an adapter) causes a short revert message, the ZetaChain protocol will forward this raw message. The Gateway's refund handler will then crash due to an out-of-bounds read when parsing this short message, trapping the user's funds. Whether this loss is temporary or permanent depends on which Gateway contract the error occurs in.

### Root Cause

When a normal user initiates a cross-chain swap via Gateway contracts, this transaction will invoke `mixSwap`, then `_deposit`, and finally `sellBase` on the used adapter by the DODO-DEX protocol. For instance, two adapters that are probably used by DODO are [`UniV3Adapter`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/adapter/UniV3Adapter.sol) and [`CurveAdapter`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/adapter/CurveAdapter.sol#L38).

The vulnerability exists because the refund handlers do not validate the length of `context.revertMessage` before processing it. The DODO-DEX protocol's architecture relies on adapters to call external liquidity sources, and these external sources are known to produce short revert messages that are not handled safely.

As an example, this can occur in several ways:

- **Modern Protocols (like Uniswap V3):** Revert with gas-efficient custom errors. For example, the official Uniswap V3 pools revert with errors like **`LOK()`** (for locked liquidity). These are encoded as short, **4-byte** messages. When an adapter calls a V3 pool and it reverts, this 4-byte message is passed all the way back to the `onRevert` handler.
    * *Reference: The `LOK()` error is defined in the Uniswap/v3-core [source code](https://github.com/Uniswap/v3-core/blob/main/contracts/UniswapV3Pool.sol#L607).*

- **Older Gas-Optimized Protocols (like classic Curve pools):** Often revert with no data at all to save gas, resulting in a message of **0 bytes**.

In both cases, the DODO Gateway contract attempts to execute `bytes32(context.revertMessage[0:32])` on a message that is shorter than 32 bytes, causing a fatal out-of-bounds error.

### Internal Pre-conditions

- A cross-chain operation fails, triggering an `onRevert` or `onAbort` callback to one of the Gateway contracts.


### External Pre-conditions

- A [`mixSwap`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1392) transaction is routed through a DODO adapter to an external liquidity pool (e.g. a Uniswap V3 or Curve pool).
- That external pool reverts with a message shorter than 32 bytes.
- The ZetaChain Gateway correctly forwards this raw, short revert reason back to the source contract's `onRevert`/`onAbort` handler.

### Attack Path

1.  A user's transaction is routed via a DODO adapter to an external protocol like Uniswap V3.
2.  The Uniswap V3 pool fails due to a temporary liquidity lock and reverts with the 4-byte `LOK()` custom error.
3.  The DODO adapter and DODO proxy bubble this 4-byte error up.
4.  The ZetaChain protocol catches the 4-byte error and calls `onRevert` back on the originating DODO Gateway contract. The `context.revertMessage` is now this 4-byte error.
5.  The `onRevert` handler crashes while trying to read 32 bytes from the 4-byte message. The user's funds, which were sent to the Gateway contract for the refund, are now trapped.

### Impact

The impact and severity depend on where the failure occurs, creating two distinct scenarios:

**High severity impact (in [`GatewaySend.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol))**
If this crash happens in the `onRevert` handler of the `GatewaySend.sol` contract, the user's funds are **permanently frozen**. This contract lacks a `superWithdraw` function or any other rescue mechanism for ERC20 tokens. The funds are irrecoverable without a full contract upgrade.

**Medium severity impact (in [`GatewayCrossChain.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517) & [`GatewayTransferNative.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607))**
If this crash happens in the `onRevert` or `onAbort` handlers of the contracts on ZetaChain, the user's funds are **temporarily frozen**. The automated refund mechanism is broken, but the owner can eventually recover the funds using the `superWithdraw` function. This constitutes a "temporary freezing of funds" and a "break of a core protocol mechanism."

### Mitigation

The mitigation should be a focused, two-part strategy implemented in all `onRevert` and `onAbort` functions in the Gateway contracts:

1.  Before any processing, validate the length of `context.revertMessage`. If it's too short to be safely parsed, emit a dedicated event and halt execution to prevent a crash.
2.  The event emitted for a malformed message should include all available context (`asset`, `amount`, the full `revertMessage`, etc.). This provides an on-chain record that is crucial for identifying the trapped funds and facilitating their manual recovery by the owner where possible.

```solidity
// Suggested implementation for the top of each onRevert/onAbort function

if (context.revertMessage.length < 32) {
    // Message is too short to parse externalId. The refund cannot be processed.
    emit MalformedRevertMessage(
        context.chainID,
        context.sender,
        context.asset,
        context.amount,
        context.revertMessage
    );
    // Halt execution to prevent a crash. Funds are now trapped in this contract,
    // requiring manual owner intervention via superWithdraw where available.
    return;
}

// Proceed with the original parsing logic, now that it's safe.
bytes32 externalId = bytes32(context.revertMessage[0:32]);
```
