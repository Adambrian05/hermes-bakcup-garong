# Missing User-Defined Deadline in `swapTokensForExactTokens` Timestamp Manipulation Exploits

### Summary

The GatewayCrossChain.sol contract calls which means the user cannot specify the maximum allowed time for execution. Due to this there will be a risk of delayed execution and Validator nodes timestamp manipulation. 

`block.timestamp` is not the time when the user sends the transaction - it's the time when the block is created by the Validator nodes or validator.

If the Validator nodes decides not to include the transaction immediately and delays it by hours or even days, the block.timestamp will still look valid at that delayed time.

So, if there’s no proper `deadline` check, the transaction can be executed much later than the user expects and timing should be respected especially in cross chain bridging transactions.

`amountInMax` ensures acceptable slippage—but cannot prevent delayed execution. Without a user-defined deadline, the deadline time check becomes useless and unsafe


```solidity
.swapTokensForExactTokens(
    gasFee,
    amountInMax,
    getPathForTokens(targetZRC20, gasZRC20),
    address(this),
    block.timestamp + MAX_DEADLINE
);
```


### Root Cause

The user cannot specify the maximum allowed time for execution

### Impact

The current `deadline` parameter is ineffective as it can be easily manipulated by Validator nodes when necessary
Validator nodes can delay or withhold high-value transactions indefinitely, making transactions never expire



### PoC

1. Attacker bots watch for a bridge transaction submitting a swap with no real deadline.
2. Validator nodes holds it in a private block and tweaks `timestamp` to keep it valid.
3. Market moves unfavorably for user (e.g. token price drops).
4. Validator nodes executes the user’s swap at a much worse rate for the user

### Mitigation

Let the user to specify a deadline, but fall back to the existing block.timestamp + MAX_DEADLINE if the value is 0

This approach protects against:

* **Delayed execution**, which `amountInMax` alone cannot prevent.
* **MEV attacks and stale pricing**, by bounding the time window for swap validity.
* **Validator manipulation**, by limiting reliance on `block.timestamp`.
