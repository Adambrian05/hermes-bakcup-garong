# Using ERC20 Transfer Function Without Checking for Success in the `GatewaySend` Contract

## Vulnerability Details
In the `GatewaySend` Contract, token transfers are performed via the ERC20 `transfer` and `transferFrom` functions. This functions return a boolean indicating whether the transfer was successful. It is essential to capture and verify this return value to ensure that the transfer has succeeded. However, in the mentioned functions, these return values are neither checked nor handled.

For example, in the `onCall` function, there is a line of code like the following:

```solidity
    IERC20(toToken).transfer(evmWalletAddress, outputAmount);
```

Additionally, the USDT token contract does not return a boolean value on the Ethereum mainnet. Since USDT is considered a supported token on ZetaChain ([see documentation](https://www.zetachain.com/docs/developers/tokens/zrc20/#:~:text=0x95aD61b0a150d79219dCF64E1E6Cc01f0B64C4cE-,ETH%20Mainnet,0xdAC17F958D2ee523a2206206994597C13D831ec7,-ETH%20Mainnet)), and since Ethereum mainnet is one of the chains where the `GatewaySend` will be deployed, implementing `transferFrom` as shown below will cause a revert when interacting with USDT:
```solidity
require(
    IERC20(asset).transferFrom(msg.sender, address(this), amount),
    "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
);
```

## POC
The issue of unchecked return values from `ERC20::transfer` has been previously reported in the Sherlock contest: ([issue #169](https://github.com/sherlock-audit/2023-05-Index-judging/issues/169))

## Impact
- If the token transfer fails and the return value is not checked, the transaction will not revert, potentially leading to loss of funds for users.
- Trying to use USDT token in this contract leads to revert in some functions. 

## Mitigation
Either of these two methods can be used:
- Replace the use of `ERC20::transfer` with `SafeERC20::safeTransfer`, which handles the success check internally and reverts the transaction if the transfer fails.
- To ensure code consistency, use the `TransferHelper` library throughout the code.
(Note: the `TransferHelper` library has a inaccuracy, which I reported as a separate issue.)
