# Missing Validation on params.fromToken Enables Arbitrary Token Drains via Forged SwapData

### Summary

The `GatewaySend.depositAndCall()` function does not validate whether the `fromToken` argument matches the `params.fromToken` embedded within the `swapData`. An attacker can:

* Pass a cheap token address as `fromToken` (e.g., a low-value ERC-20).
* Craft `swapData` whose `params.fromToken` is a high-value token address.
* Cause `_doMixSwap()` to approve and swap the expensive token from the contract’s own balance, draining those assets. 

This vulnerability is marked as medium severity because it only becomes exploitable when the contract holds token balances. Under normal operation, the contract may not hold tokens for long. However, if any tokens are accidentally or temporarily left in the contract, an attacker can exploit the missing validation between the `fromToken` argument and `params.fromToken` in `swapData` to drain those tokens. This can be fixed by adding the following minimal validation inside the `_doMixSwap()` function:

```solidity
function _doMixSwap(bytes calldata swapData) internal returns (uint256) {
    MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
    //@audit - should validate that `params.fromToken == fromToken` passed into depositAndCall()
    if (params.fromToken != _ETH_ADDRESS_) {
        IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
    }
    ...
}
```

### Root Cause

No check is performed to ensure that the token the user intended to swap (`fromToken` argument to `depositAndCall`) matches the token extracted from the calldata (`params.fromToken`). This discrepancy allows malicious swap payloads to target arbitrary tokens held by the contract.

### Impact

### PoC

1. **Setup**

   * Contract holds `100` units of **TokenB** (high-value). 
   * Attacker has `100` units of **TokenA** (low-value).
   * User wants TokenCZ in zeta chain
   * Here are the prices
   * TokenB = 2 * TokenA
   * TokenC = 4 * TokenA 

2. **Craft Swap Data**

   * Call `depositAndCall(TokenA, 100, swapData, …)`
   * In `swapData`, set:
     ```js
     params.fromToken = address(TokenB);
     params.fromTokenAmount = 100;  
     // other swap parameters as needed
     ```

3. **Exploit Execution**

   * Contract approves 100 TokenB to the DodoRouter and gets 50 TokenC from `_doMixSwap()`
   * Transfers 50 TokenC over the chain and received TokenCZ in the destination
   * 50 TokenCZ will be sent to the user which is rougly 400 TokenA (50 * 4) but user paid only 100 TokenA

### Mitigation

Add a requirement to ensure on‐chain consistency between the function argument and calldata:

```diff
function _doMixSwap(
    bytes calldata swapData,
    address fromToken
) internal returns (uint256) {
    MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
+   require(params.fromToken == fromToken, "fromToken mismatch");
    if (params.fromToken != _ETH_ADDRESS_) {
        IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
    }
    // ...swap execution...
}
```

Ensure that `depositAndCall()` forwards its `fromToken` argument into `_doMixSwap()` so this check can be enforced.
