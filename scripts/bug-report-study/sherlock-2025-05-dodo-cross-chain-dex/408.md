# ETH can be permanently locked in `GatewaySend` during ERC20 transactions and unrecoverable by protocol owner without a full contract upgrade

### Summary

Both `depositAndCall` functions in [`GatewaySend.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol) are `payable`, allowing them to receive ETH. However, if a user sends ETH (`msg.value > 0`) while executing a transaction for an **ERC20 token** (not native ETH), the contract logic does not account for this ETH. It is never used, nor is it refunded, causing it to be permanently locked in the contract.

### Root Cause

The `depositAndCall` functions have logic paths for handling native ETH transactions and separate paths for ERC20 token transactions. The ERC20 paths correctly transfer the specified `amount` of the token, but they do not check for, handle, or refund any `msg.value` that was also sent.

This issue is exacerbated by the fact that, unlike [`GatewayCrossChain.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L161) and [`GatewayTransferNative.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L166) (which have a `superWithdraw` function), the `GatewaySend.sol` contract has **no function for an owner or anyone else to rescue accidentally locked funds.** This makes any such error permanent and requires a full contract upgrade to recover assets.


### Internal Pre-conditions

- The contract receives a call to either `depositAndCall` function.
- The token being sent (`fromToken` or `asset`) is an ERC20 address (not `_ETH_ADDRESS_`).
- The transaction is sent with `msg.value > 0`.

### External Pre-conditions

- A user, due to a misconfigured wallet, UI error, or simple mistake, sends ETH along with a transaction that is intended to move an ERC20 token.

### Attack Path

This is a design flaw leading to unintentional fund loss.

1.  A user wants to bridge 1,000 USDC using the `depositAndCall(address targetContract, uint256 amount, ...)` function.
2.  They correctly set the `asset` parameter to the USDC token address and `amount` to `1000e6`.
3.  However, their wallet or application mistakenly includes `msg.value: 0.1 ether` in the transaction.
4.  The function executes the `else` block for non-ETH assets. It correctly pulls 1,000 USDC from the user and sends it to the ZetaChain gateway.
5.  The 0.1 ETH sent as `msg.value` is ignored by this logic path.
6.  The transaction completes, but the 0.1 ETH is now permanently locked in the `GatewaySend.sol` contract's balance.

### Impact

This flaw causes a direct, permanent loss of user funds. While unintentional, it represents a leak of value from users due to a lack of necessary safety checks in `payable` functions. The absence of an owner-controlled rescue function makes the loss irreversible without a contract upgrade.

### PoC

- The following test demonstrates the vulnerability and can be appended to the file `GatewayTransferNative.t.sol`. It shows that when a user calls `depositAndCall` for an ERC20 token but accidentally includes `msg.value`, the intended cross-chain action succeeds, but the accidentally sent ETH becomes locked in the `GatewaySend` contract.

```solidity
// This test demonstrates that ETH sent with an ERC20 transaction becomes locked.
function test_A2ZSwap_StuckETH_During_ERC20_Swap() public {
    address targetContract = address(gatewayTransferNative);
    uint256 amount = 100 ether;
    uint256 stuckEthAmount = 0.5 ether;
    uint32 dstChainId = 7000;
    address asset = address(token1A);
    address targetZRC20 = address(token2Z);

    // Check pre-conditions: GatewaySend should have no ETH.
    assertEq(address(gatewaySendA).balance, 0, "Initial ETH balance of GatewaySend should be 0");

    bytes memory sender = abi.encodePacked(user1);
    bytes memory receiver = abi.encodePacked(user2);
    bytes memory swapDataZ = encodeCompressedMixSwapParams(
        address(token1Z),
        address(token2Z),
        amount,
        0,
        0,
        new address[](1),
        new address[](1),
        new address[](1),
        0,
        new bytes[](1),
        abi.encode(address(0), 0),
        block.timestamp + 600
    );
    bytes memory payload = encodeNativeMessage(
        targetZRC20,
        sender,
        receiver,
        swapDataZ
    );

    vm.startPrank(user1);
    token1A.approve(
        address(gatewaySendA),
        amount
    );

    // User calls depositAndCall for the ERC20 token (`asset`),
    // but accidentally includes `msg.value` (`stuckEthAmount`).
    gatewaySendA.depositAndCall{value: stuckEthAmount}(
        targetContract,
        amount,
        asset,
        dstChainId,
        payload
    );
    vm.stopPrank();

    // Assert that the intended swap was successful
    assertEq(token1A.balanceOf(user1), initialBalance - amount);
    assertEq(token2Z.balanceOf(user2), 200000000000000000000);  

    // CRITICAL: Assert that the ETH sent by the user is now permanently locked in the GatewaySend contract.
    assertEq(
        address(gatewaySendA).balance,
        stuckEthAmount,
        "ETH sent with the transaction should be locked in the contract"
    );
}

```

### Mitigation

Add a check to the logic paths that handle ERC20 tokens to ensure that `msg.value` is zero. Alternatively, a more user-friendly approach would be to refund any ETH that is unintentionally sent.

```solidity

// In GatewaySend.sol -> depositAndCall(address fromToken, ...)

// ...
if(fromIsETH) {
    // ... ETH logic
} else {
    require(msg.value == 0, "ETH_NOT_ALLOWED_IN_ERC20_TX"); // Add this check
    require(
        IERC20(fromToken).transferFrom(msg.sender, address(this), amount), 
        "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
    );
}
// Apply similar logic to the other depositAndCall function.

```
