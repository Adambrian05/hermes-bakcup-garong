# depositAndCall function forwards msg.value instead of amount to _handleEthDeposit in GatewaySend.sol contract

### Summary

The `depositAndCall` function in `GatewaySend.sol` contract uses `msg.value` instead of using the user-declared `amount`. Consequently, any ETH sent in excess of amount is forwarded to the gateway and wrapped into ZRC-20 or otherwise locked. This causes users to lose unintended ETH without a refund mechanism.

### Root Cause

Issue can be found here : https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L287 


```Solidity
    function depositAndCall(
        address targetContract,
        uint256 amount,
        address asset,
        uint32 dstChainId,
        bytes calldata payload
    ) public payable {
        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);
        bool isETH = (asset == _ETH_ADDRESS_);
        bytes memory message = concatBytes(externalId, payload);

        RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: targetContract,
            revertMessage: bytes.concat(externalId, bytes20(msg.sender)),
            onRevertGasLimit: gasLimit
        });

        if (isETH) {
            require(msg.value >= amount, "INSUFFICIENT AMOUNT: ETH NOT ENOUGH");
            _handleETHDeposit(
                targetContract, 
                msg.value, //@audit should be amount instead of msg.value
                message, 
                revertOptions
            );
        } else {
            require(
                IERC20(asset).transferFrom(msg.sender, address(this), amount),
                "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
            );
            _handleERC20Deposit(
                targetContract, 
                amount,
                asset, 
                message, 
                revertOptions
            );
        }

        emit EddyCrossChainSend(
            externalId,
            dstChainId,
            asset,
            asset,
            amount,
            amount,
            msg.sender,
            message
        );
    }
```

The `GatewaySend.sol` contract exposes two overloaded functions named `depositAndCall` that allow users to deposit either an ERC-20 or native ETH, optionally swap tokens, and then relay a cross-chain message via ZetaChain’s gateway (gateway.depositAndCall{value: amount}(…)).

Both ETH-payable overloads check `require(msg.value >= amount, …)`, ensuring the user sent at least amount.

Then it calls:  
`_handleETHDeposit(targetContract, msg.value, message, revertOptions);`
Here, instead of using `amount` value set by the user, `msg.value` is forwarded.


https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L164


```Solidity
    function _handleETHDeposit(
        address targetContract,
        uint256 amount,
        bytes memory message,
        RevertOptions memory revertOptions
    ) internal {
        gateway.depositAndCall{value: amount}(
            targetContract,
            message,
            revertOptions
        );
    }
```

Because amount in `_handleETHDeposit` is set to the entire `msg.value` (not the user’s declared amount), any ETH above the stated amount will be sent on-chain through the gateway. There is no code path that refunds “msg.value − amount” back to msg.sender.

### Attack Path

Suppose Alice wants to send exactly 1 ETH cross-chain . She calls:

```Solidity
contract.depositAndCall(
    targetContract,
    1 ether,
    payload,
    { value: 1.1 ether } // sends 1.1 ETH
);
```
`require(msg.value >= amount)` passes because 1.1 ETH >= 1 ETH.

`_handleETHDeposit` is invoked with `amount = msg.value = 1.1 ETH`.

The gateway wraps 1.1 ETH into ZRC-20 tokens or locks them and pushes 1.1 ETH worth of ZRC-20 to the destination, instead of 1 ETH.

Result: Alice has lost 0.1 ETH with no refund.

### Impact

The code does not revert when msg.value > amount; it only reverts if msg.value < amount. Sending extra ETH is silently accepted and forwarded. So, this causes:

* Users lose ETH they did not intend to bridge.
* Could be used to grief users.
* Funds go to the ZetaChain gateway, and there’s no refund path.

### Mitigation

Use this require instead:

`require(msg.value == amount, "AMOUNT MISMATCH");`
