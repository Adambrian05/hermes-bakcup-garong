# Refunds will be transferred to incorrect address on ZetaChain since revertMessage encodes address for the receiver on the destination chain

### Summary

When users initiate CCTX (e.g. source -> ZetaChain -> destination) they provide a payload on the source chain that includes the `receiver` address on the destination chain.

There is also a refund mechanism on ZetaChain in case if transaction reverts on path `ZetaChain -> destination chain`. Whenever this happens, the ZetaChain protocol calls the `revertAddress.onRevert()`  function and transfers the fund to the `revertAddress`.

For Dodo in particular, the `revertAddress` is the `GatewayCrossChain`. When `onRevert()` is called, the function immediately transfers the refund to recipient address from the `revertMessage`.

The issue is that this address is the address of the recipient on the destination chain, which is wrong since the refund happens on the ZetaChain. Thus, tokens will be refunded to the wrong address and lost.

### Root Cause

When `GatewayCrossChain.onCall()` is called by `Gateway`, the withdrawal happens from `ZetaChain` to destination chain. The `message` provided includes the `receiver` address that should receive tokens from the CCTX.

The `message` contains the `receiver`, we can see that when the destination `data` [is being encoded](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L420-L424):
```solidity

                externalId, 
                outputAmount - gasFee, 
                decoded.receiver, //@audit
                decoded.swapDataB
            );
```

On destination chain, [the `Gateway.onCall()` function is called](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L346-L356):
```solidity

        MessageContext calldata /*context*/,
        bytes calldata message
    ) external payable onlyGateway returns (bytes4) {

            bytes32 externalId, 
            uint256 amount, 
            bytes calldata recipient, 
            address fromToken, 
            address toToken, 
            bytes calldata swapData

        bool fromIsETH = (fromToken == _ETH_ADDRESS_);
        bool toIsETH = (toToken == _ETH_ADDRESS_);

        } else {

        } else {
```

The `recipient` here is the `receiver` encoded in the `data` previously.

The issue is that `GatewayCrossChain` [makes the `revertMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L261-L267) with the same `receiver` destination chain address:

The `walletAddress` here is the address from the `revertMessage`, which is the `receiver` on the destination chain. 

Thus, if `ZetaChain -> destination chain` transaction reverts, the refund will be sent to the wrong address.

### Internal Pre-conditions

None.

### External Pre-conditions

1. `ZetaChain -> destination chain` transaction reverts.

### Attack Path

`GatewayCrossChain.withdrawAndCall()` function incorrecly encodes the `revertMessage` with the wrong address of the `receiver` in the destination chain. If CCTX `ZetaChain -> destination chain` reverts, the refund logic will transfer refunded tokens to the wrong address on ZetaChain.

### Impact

Loss of refund.

### PoC

_No response_

### Mitigation

In `GatewayCrossChain.withdrawAndCall()` function the `revertMessage` should be encoded with ZetaChain address:
```diff
RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
-                revertMessage: bytes.concat(externalId, receiver),
+                revertMessage: bytes.concat(externalId, zetaChainRefundAddress),
                onRevertGasLimit: gasLimit
            })
```

You should also change the decoding mechanism in `SwapDataHelpberLib` that would consider the new address `zetaChainRefundAddress`.
