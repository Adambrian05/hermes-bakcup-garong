# Missing withdrawal capacity checks on ZRC20 tokens in GatewayCrossChain can cause cross-chain transaction reverts

### Summary

The missing allowance and success check in GatewayCrossChain.sol::_swapAndSendERC20Tokens and _handleEvmOrSolanaWithdraw will cause a denial-of-service for users as a non-compliant or malicious ZRC20 token silently fails the approve() call, preventing subsequent withdraw or withdrawAndCall from functioning.

### Root Cause

In GatewayCrossChain.sol, functions such as _swapAndSendERC20Tokens and _handleEvmOrSolanaWithdraw directly calls:
IZRC20(targetZRC20).approve(address(gateway), amount);
with no verification that the allowance was successfully set.
Furthermore, the contract makes no fallback if the allowance was not increased, nor does it read allowance() before/after to confirm the gateway can actually spend tokens.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277-L296



### Internal Pre-conditions

1. A ZRC20 token implements approve() but returns false (or always fails silently).

2. outputAmount and gasFee are computed and user funds are processed.

3. The contract calls approve() assuming it will succeed.

### External Pre-conditions

1. The ZRC20 token is listed in ZetaChain’s supported assets but implements a non-standard or mutable approval mechanism (e.g., requiring 0 reset or rejecting identical allowance updates).

2. ZetaChain's GatewayZEVM expects transferFrom to succeed based on assumed allowances.



### Attack Path

1. User initiates a cross-chain withdrawal using a non-standard ZRC20.

2. Contract calls approve() which silently fails.

3. gateway.withdraw(...) or withdrawAndCall(...) is invoked.

3. The ZetaChain gateway fails the withdrawal due to insufficient allowance.

4. Funds are not moved, onRevert/onAbort is triggered, and refund requires manual bot intervention.



### Impact

1. Users experience failed withdrawals and delayed refunds.

2. Refund bots must manually intervene, increasing centralized reliance and support load.

3.  Inconsistent state between ZetaChain and the source chain.

4. If tokens are not recoverable, funds may become permanently stuck.

_No response_

### Mitigation

- Check return values of approve() calls and revert if false.

- For safety, use safeApprove() or perform an allowance() readback to ensure expected allowance is set.

- Consider implementing logic to handle tokens that require setting allowance to 0 before increasing it.
