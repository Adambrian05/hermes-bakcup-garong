# Some uniswap pools have low liquidity and getAmountsIn will revert with underflow, dosing the bridge execution

### Summary

In case of outgoing transactions (from ZetaChain to destination chain) users have to pay the fees in `gasZRC20` tokens. `GatewayCrossChain` contract allows to obtain it by swapping the `targetZERC20` token for the necessary `gasFees` amount.

Contest page also mentions that protocol supports tokens within [this](https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets) list. 

The issue is that not all pair of tokens have sufficient liquidity in the uniswap pool to allow swap, and the execution will revert with underflow when `_swapAndSendERC20Tokens()` function would try to calculate `amountsQuote` in `UniswapV2Library.getAmountsIn()`, the necessary `amountIn` of target token required to swap for `gasFees` of the gas token.

### Root Cause

Zetachain's gateway contract calls the `GatewayCrossChain.onCall()` function when there is a request for outgoing transaction. During the call, it transfers the `zrc20` tokens along with the message to `GatewayCrossChain`. The latter contract decodes the `targetZRC20` token address from the message, which is the token user want to bridge to destination chain. Also, the `GatewayCrossChain` contract swaps the `zrc20` tokens through DODO to `targetZRC20` if any swap data was provided in the message.

Ultimately, the `GatewayCrossChain.onCall()` swaps the portion of `targetZRC20` tokens for gas token required for execution in case when `decoded.targetZRC20 != gasZRC20`. In internal `_handleEvmOrSolanaWithdraw()` the gas token address is being retrieved along with the `gasFees`. Later, the `_swapAndSendERC20Tokens()` is called for `outputAmount` (the amount of target tokens received from DODO swap):
```solidity
// Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params); //@audit-info target tokens amount
...
uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, 
                outputAmount, 
                decoded.receiver
            );
...
(address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);
...
amountsOutTarget = _swapAndSendERC20Tokens(
                decoded.targetZRC20, 
                gasZRC20, 
                gasFee, 
                outputAmount //@audit this output is actually input for target
            );
```

The `_swapAndSendERC20Tokens()` function [calculates](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L309-L312) the required amount of target tokens for the `gasFees` amounts of gas token using the `UniswapV2Library.getAmountsIn()` function:
```solidity
// Get amountOut for Input gasToken
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );
```
The library just calculates the required amount of tokens based on the pool reserves.

The issue is that not all pool pairs have sufficient reserves. 

Consider the case when `targetZRC20` is the `WBTC.ETH` token (which is in the list of supported tokens). The `getPathForTokens()` function would calculate the path being `path = [WBTC.ETH, WZETA, gasZRC20]` since there is no pool for `[WBTC.ETH, gasZRC20]` pair. 

However, when `UniswapV2Library.getAmountsIn()` function would calculate the `amountIn` for `[WBTC.ETH, WZETA]` pool, it will revert with underflow here:
```solidity
function getAmountIn(uint amountOut, uint reserveIn, uint reserveOut) internal pure returns (uint amountIn) {
        require(amountOut > 0, 'UniswapV2Library: INSUFFICIENT_OUTPUT_AMOUNT');
        require(reserveIn > 0 && reserveOut > 0, 'UniswapV2Library: INSUFFICIENT_LIQUIDITY');
        uint numerator = reserveIn.mul(amountOut).mul(1000);
        uint denominator = reserveOut.sub(amountOut).mul(997); //@audit underflow
        amountIn = (numerator / denominator).add(1);
    }
```

This is due to the fact that this pool has very little liquidity in it with only 222 WBTC.ETH tokens, which is if divide it by the decimal value equals to `222 / 1e8 = 0.00000222 btc, or 0.23 usd`, check it [here](https://zetachain.blockscout.com/address/0xFc80D320e17635B4143C57c789309e6339d1445b?tab=index). And `WZETA` only has reserves of 2.37 tokens, which is 0.52 usd roughly.

All in all, any meaningful cross-chain bridge of `WBTC.ETH` is not supported by the protocol due to low liquidity uniswap pool, which would result in dos and refund mechanism back to the connected source chain.

### Internal Pre-conditions

No pre-conditions

### External Pre-conditions

Low liquidity pool

### Attack Path

1. User wants to bridge `WBTC.ETH` to ethereum using the `GatewayCrossChain`;
2. `GatewayCrossChain` tries to swap `WBTC.ETH` for gas token using uniswap pool;
3. The transaction fails with underflow because of low reserves;

### Impact

DoS of bridging functionality for supported tokens if uniswap pool of `[token; gas token] or [token; wzeta]` does not have enough liquidity.

### Mitigation
Consider fetching the reserves of the pool first. If target token reserve is very low, consider swapping the target token to some other token (maybe through dodo) and then swap the newly acquired tokens for gas token.
