# Reentrancy Attacker will drain funds from the protocol

### Summary

The absence of reentrancy protection in GatewayTransferNative.sol will cause a complete loss of WZETA or ETH funds for the protocol, as an attacker will deploy a malicious receiver contract that reenters the onCall() function during an external call to TransferHelper.safeTransferETH(). This design violates the Checks-Effects-Interactions pattern, enabling recursive drain attacks due to unguarded state updates that occur after untrusted external calls.

### Root Cause

In GatewayTransferNative.sol, https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357-L423 the onCall() function calls IWETH9(WZETA).withdraw() and TransferHelper.safeTransferETH() without any reentrancy guard. It sends native ETH to the receiver, which could be a malicious contract implementing a receive() or fallback() function that recursively invokes onCall() again before the function completes, draining protocol assets repeatedly.


```solidity
// GatewayTransferNative.sol
function onCall(MessageContext memory, address zrc20, uint256 amount, bytes calldata message) external override onlyGateway {
    ...
    if (decoded.targetZRC20 == WZETA) {
        IWETH9(WZETA).withdraw(outputAmount); // Vulnerable: External call to WZETA
        TransferHelper.safeTransferETH(receiver, outputAmount); // Vulnerable: Sends ETH to receiver, which can reenter
    } else if (swapData.length != 0) {
        outputAmount = _doMixSwap(swapData, amount, params); // Vulnerable: External call to DODORouteProxy
        ...
        TransferHelper.safeTransfer(params.toToken, receiver, outputAmount);
    }
    emit EddyCrossChainSwap(...); // State update after external calls
}
```


This structure places untrusted external interactions *before* internal state changes or protections, violating a key invariant in smart contract security.

### Internal Pre-conditions


**Internal Pre-conditions:**

1. Attacker needs to deploy a malicious contract to set receiver to their contract address in the cross-chain message.
2. Protocol needs to hold at least 1 ETH or equivalent WZETA in its balance to be drained during onCall.


### External Pre-conditions


External Pre-conditions:

1. ZetaChain’s GatewayZEVM must process the cross-chain message to trigger onCall.

### Attack Path


**Attack Path:**


1. Attacker deploys a malicious receiver contract with a `receive()` or `fallback()` function.
2. Attacker sends a cross-chain message via ZetaChain that:
    - Targets `GatewayTransferNative.onCall()`
    - Sets `targetZRC20 = WZETA`
    - Sets `receiver = attack contract`
3. During `onCall()`:
    - `IWETH9.withdraw()` unwraps WZETA to ETH.
    - `TransferHelper.safeTransferETH()` sends ETH to attacker.
4. Attacker’s fallback function is triggered and **recursively invokes `onCall()` again** before state or balances are updated.
5. This process **repeats in a loop**, draining the protocol’s entire ETH/WZETA balance.

### Impact

##  Impact

- Complete loss of WZETA or native ETH held in `GatewayTransferNative.sol`.
- Attacker walks away with all protocol funds without restriction.
- Cross-chain message flow can be exploited repeatedly.
- This bypasses accounting, slippage protection, and any fee logic.

### Mitigation

- **Implement a reentrancy guard (`nonReentrant`)** on the `onCall()` function.
- **Move state updates (e.g., accounting, token burns, internal locks)** before making any external call.
- **Apply Checks-Effects-Interactions** pattern rigorously.
- **Consider using `ReentrancyGuard` from OpenZeppelin** or custom state-locking logic to prevent recursive entry.
