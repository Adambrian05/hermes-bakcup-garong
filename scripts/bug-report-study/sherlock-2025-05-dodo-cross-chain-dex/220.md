# Using `transfer` to send native token is preventing gateway from transfering ETH to smart contract users via `GatewaySend::onCall` function

## Vulnerability Detail
> Note: This vulnerability report is separate from the ERC20 `transfer` function and focuses solely on the native token `transfer`.

Using `transfer` to send native token in the `GatewaySend::onCall` function can lead to issues, as `transfer` can only send ETH to individuals, not contracts. This may cause the `onCall` function to always revert when a gateway tries to transfer ETH to smart contract accounts.

links to vulnerability:  
([GatewaySend.sol, Line 370](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L370))

```solidity
    if(toIsETH) {
        payable(evmWalletAddress).transfer(outputAmount);
    } 
```

Additionally the `transfer` returns a boolean indicating whether the transfer was successful. It is essential to capture and verify this return value to ensure that the transfer has succeeded. However, in the mentioned vulnerability, these return values are neither checked nor handled.

## POC
The similar issue has been previously reported ([here](https://solodit.cyfrin.io/issues/deprecated-eth-transfer-method-may-prevent-validators-from-being-registered-zokyo-none-yieldnest-markdown))

## Impact
Smart contact users are limited to fully use the protocol. 


## Mitigation
Instead of using the `transfer` function, protocol can simply use `call` .

```diff
  if(toIsETH) {
-    payable(evmWalletAddress).transfer(outputAmount);
+    (bool sent, ) = payable(evmWalletAddress).call{value: outputAmount}("");
+    require(sent, "Failed");
  }
```
