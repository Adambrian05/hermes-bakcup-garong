# Inconsistent `outputAmount` handling when `tokenIn == tokenOut` in `withdrawToNativeChain` and `GatewayCrossChain::onCall` functions

### Summary

A missing equality check for `tokenIn == tokenOut` will cause an incorrect `outputAmount` assignment for cross-chain users as the gateway logic will unnecessarily attempt a swap or miscalculate the transferred amount, leading to potential loss of funds or unintended token behavior.

### Root Cause

In [`GatewayTransferNative::withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L555) and [`GatewayCrossChain::onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L465), there is a missing check for whether `tokenIn == tokenOut`. Without this check, the code may attempt an unnecessary swap or miscalculate outputAmount, even when no swap is needed. [Correct implementation](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L363-L367)

### Internal Pre-conditions

1. The caller (bridge or external actor) needs to invoke `withdrawToNativeChain` or `onCall` with `tokenIn` equal to `tokenOut`
2. The swap path must be empty or result in a no-op due to identical tokens
3. The functions must proceed without checking for `tokenIn == tokenOut`, leading to incorrect `outputAmount` assumptions

### External Pre-conditions

1. The token bridge or cross-chain messaging protocol must forward a transfer request with identical source and destination tokens.
2. No external contract or relayer intervenes to correct or reject a zero-swap operation involving identical tokens.

### Attack Path

1. User calls `GatewayTransferNative::withdrawToNativeChain` with parameters where the source and destination tokens are the same.
2. Because the code does not bypass the swap logic for identical tokens, it incorrectly calculates `outputAmount` different from the original `amount`.
3. This causes a mismatch in token amounts sent or expected on the native chain, potentially resulting in loss of funds or failed transfers.
4. Alternatively, gateway calls `GatewayCrossChain::onCall` with a cross-chain message involving the same token on both sides.
5. The function incorrectly processes the transfer amount due to missing equality checks, causing an inconsistent token amount to be handled.

### Impact

The users suffer an approximate loss of their transferred tokens’ value due to incorrect amount handling when tokens are the same. The attacker can cause fund loss or transfer failure by exploiting the inconsistent `outputAmount` calculation.

### PoC

_No response_

### Mitigation

Add a conditional check in both `GatewayTransferNative::withdrawToNativeChain` and `GatewayCrossChain::onCall` functions to detect when the token being transferred is the same as the output token. In this case, bypass any swapping logic and set `outputAmount` to be exactly equal to `amount`.
