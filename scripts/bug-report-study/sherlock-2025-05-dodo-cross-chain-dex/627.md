# Malicious Actor Claims Other User's Refund

### Summary

The `claimRefund` function in both [GatewayCrossChain.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol) and [GatewayTransferNative.sol](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol)  contains a critical access control vulnerability that allows any user to claim refunds intended for non-EVM wallet addresses (Bitcoin, Solana). The vulnerability stems from a tautological condition `msg.sender == receiver` that always evaluates to `true` when the refund is for non-EVM addresses, effectively bypassing the intended access control mechanism.

### Root Cause

The vulnerability exists in the access control logic of the `claimRefund` function.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590

Incorrect line : 
```solidity
 address receiver = msg.sender;  
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); 
```
1. The `receiver` variable is initialized to `msg.sender`
2. It only gets reassigned if `walletAddress.length == 20` (EVM addresses)
3. For non-EVM addresses nonEVM `receiver` remains `msg.sender`
4. The condition `msg.sender == receiver` becomes `msg.sender == msg.sender`, which is always `true`
5. This creates a logical bypass where anyone can claim non-EVM refunds regardless of bot status

### Internal Pre-conditions

A `RefundInfo` entry must be present in the `refundInfos` mapping
The refund must be associated with a non-EVM wallet address (length ≠ 20)
Attacker must know or guess the `externalId`

### External Pre-conditions

During periods of high cross-chain activity, more refunds are generated


### Attack Path

1. Alice initiates a cross-chain swap. For some reason, the transaction fails, but the system correctly creates a RefundInfo struct associated with her externalId and her full Solana wallet address. Her funds are now waiting in the contract to be claimed.
2.  Bob calls the claimRefund(alicesExternalId) function from his own wallet.
3. Inside the Vulnerable claimRefund function:
- RefundInfo storage refundInfo = refundInfos[alicesExternalId]; -> The contract loads Alice's refund data.
- address receiver = msg.sender; -> receiver is set to Bob's address.
- if(refundInfo.walletAddress.length == 20) -> This check fails because Alice's Solana address is not 20 bytes long. The receiver variable remains set to Bob's address.
- require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); -> This is the critical flaw. The check becomes require(bots[Bob's address] || Bob's address == Bob's address). Since Bob == Bob is always true, the check passes.

### Impact

- All refunds for Bitcoin/Solana users can be stolen
- Severe damage to cross-chain bridge reputation
- Loss of funds
