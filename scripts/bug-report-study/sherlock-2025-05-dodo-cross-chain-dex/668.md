# Slippage is not effective

### Summary

Both `GatewayCrossChain` and `GatewaySend` have public slippage parameter, which can be set arbitrary by owner upon initialization of contracts, or when the contracts are upgraded as there are no setter functions in both contracts and is a fixed percentage, which is then being used for internal UniswapV2 gas swaps, when the `GatewayCrossChain` or `GatewayTransferNative` contract needs to swap targetZRC20 for gasZRC20 it calls the Uniswaps V2's `swapTokensForExactTokens`. The `amountInMax` for this swap is being calculated as **amountInMax = (amountsQuote[0])  + (slippage * amountsQuote[0]) / 1000**. These swaps can be sandwiched or fail

1. if `slippage` is too high, constant value leakage to MEV bots
2. if `slippage` is too low, the internal gas swaps might fail due to normal market volatility

### Root Cause

Slippage parameter being set as a fixed percentage

### Attack Path

1. Observes the gateway contract's pending swap, the malicious user buys the gasZRC20 or sells in the same pool pushing the price up.
2. The gateway contract's `swapTokensForExactTokens` now executes. To get the required gasFee, it has to pay more `targetZRC20` but still within its `amountInMax`, the malicious user effectively extracts this slippage.
3. Immediately after the gateway's transaction, the malicious user sells the gasZRC20 it bought, realizing the a profit from the price difference.

### Impact

More `targetZRC20` is consumed to acquire the necessary `gasZRC20` or the transaction fails.
