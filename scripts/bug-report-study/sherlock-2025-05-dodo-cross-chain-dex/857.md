# Unhandled Excess Native Value Leads to Trapped Funds in `GatewaySend`

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L232

#### Summary
The `depositAndCall` function in `GatewaySend` permits users to send more native coin (`msg.value`) than the specified `amount` when initiating native transfers. This oversight leads to the **permanent trapping of excess native coin** within the contract, as it lacks any mechanism to recover or manage these surplus funds.

---

#### Root Cause
In `GatewaySend::depositAndCall` (`L173-L253`), specifically when handling native coin deposits (`fromToken == _ETH_ADDRESS_`), the contract only verifies that the sent `msg.value` is *greater than or equal to* the `amount` parameter (`L185`). It does not implement a mechanism to return any surplus `msg.value` back to the user or to otherwise account for the difference if `msg.value > amount`.

```solidity
// File: GatewaySend.sol
function depositAndCall(
    address fromToken, // This will be _ETH_ADDRESS_ for native coin transfers
    uint256 amount,    // The amount the user intends for the transaction
    bytes calldata swapData,
    address targetContract,
    address asset,
    uint32 dstChainId,
    bytes calldata payload
) public payable { // Function is payable to receive native coin
    // ...
    bool fromIsETH = (fromToken == _ETH_ADDRESS_); // L181

    // Handle input token
    if(fromIsETH) { // L184
        require(
            msg.value >= amount, // L185: Checks if msg.value is sufficient, but doesn't handle excess
            "INSUFFICIENT AMOUNT: ETH NOT ENOUGH"
        );
    } else {
        // ... (ERC20 transfer logic)
    }
    // ... (rest of the function proceeds with 'amount' for calculations)
}
```

---

#### Internal Pre-conditions
None.

---

#### External Pre-conditions
A user accidentally or deliberately sends `msg.value` that is strictly greater than the `amount` parameter when calling `GatewaySend::depositAndCall` with `fromToken` set to `_ETH_ADDRESS_` (native coin).

---

#### Attack Path / Scenario
1.  A **user** calls the external **`GatewaySend::depositAndCall`** function (`L173`) intending to send a specific `amount` of native coin.
    * The **user** sets `fromToken` to `_ETH_ADDRESS_`.
    * The **user** sets the `amount` parameter to their desired value (e.g., 1 ETH).
    * The **user** (accidentally or deliberately) sends `msg.value` that is *more* than the `amount` parameter (e.g., sends 1.5 ETH as `msg.value` when `amount` is 1 ETH).

    ```solidity
    // File: GatewaySend.sol
    function depositAndCall(
        address fromToken,
        uint256 amount,
        // ...
    ) public payable {
        // ...
        bool fromIsETH = (fromToken == _ETH_ADDRESS_); // L181
        if(fromIsETH) { // L184
            require(
                msg.value >= amount, // L185: This condition passes, but 0.5 ETH excess is ignored
                "INSUFFICIENT AMOUNT: ETH NOT ENOUGH"
            );
        }
        // ...
    }
    ```

2.  The `require(msg.value >= amount)` check at `L185` successfully passes, as `1.5 ETH >= 1 ETH`.

3.  The `GatewaySend::depositAndCall` function then proceeds with all subsequent calculations and operations (like calling `_doMixSwap` and `_handleETHDeposit` or `_handleERC20Deposit`) using the **`amount`** parameter (1 ETH) and *not* the actual `msg.value` (1.5 ETH).

4.  The excess `msg.value` (0.5 ETH in this example) remains in the `GatewaySend` contract's balance. There are no further checks or mechanisms within the contract's code that would refund this surplus to the original sender, nor are there any functions to withdraw or manage these accumulated funds.

---

#### Impact
Excess native coin sent to the `depositAndCall` function that exceeds the `amount` parameter becomes **permanently trapped** within the `GatewaySend` contract. The contract lacks any functionality to **recover or manage these accumulated surplus funds**.
