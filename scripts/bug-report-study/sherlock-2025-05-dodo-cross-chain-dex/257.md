# Incorrect Handling of Native Tokens in `onRevert` Function Causes Transfer Reverts

### Summary

The `onRevert` function is designed to handle failed cross-chain swaps by returning funds to the sender. However, it uses `TransferHelper.safeTransfer` indiscriminately on all assets, including native tokens (e.g., ETH, BNB) which are represented by the placeholder address `0x0000000000000000000000000000000000000000`.

The `TransferHelper.safeTransfer` utility is designed for ERC20 tokens, not native tokens. When it is used with the native token placeholder address, it incorrectly attempts to call `transfer(...)` on an invalid contract address, causing a revert. ### Root Cause

`onRevert` attempts to transfer the `context.asset` back to the sender using:
>```TransferHelper.safeTransfer(context.asset, sender, context.amount);```

The [`TransferHelper.safeTransfer`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L12-L16) function tries to call `transfer(...)` on `address(0)`, which is not a deployed contract, resulting in low-level call failures and revert of the entire function execution.


### Internal Pre-conditions

1. A failed cross-chain swap leads to a call to `onRevert(...)` from the gateway.
2. The asset in the context is a native token, represented as `0x0000000000000000000000000000000000000000`.
3. `TransferHelper.safeTransfer` is called with this `address(0)`.

### External Pre-conditions

1. A user initiates a swap using a native token (e.g., ETH on Ethereum).
2. The swap fails.
3. The `onRevert(...)` handler is invoked by the gateway to refund the user.

### Attack Path

> This is not a financial exploit, but a user experience degradation vector:

1. User swaps native token (e.g., ETH).
2. Swap fails — `onRevert(...)` is triggered on the source chain.
3. Native token transfer is attempted using `TransferHelper.safeTransfer`.
4. Call reverts due to `0x0000000000000000000000000000000000000000` not being a contract.
5. Refund fails on source chain.
6. Zetachain executes `onAbort(...)` and stores refund data on Zetachain.
7. User is forced to claim the refund manually on Zetachain, or wait for protocol bots.

### Impact

- Medium severity (UX reliability / logic correctness).
- Refund path becomes manual or delayed for native token users.
- Creates support burden and refund inconsistencies.
- Could be used in griefing patterns (e.g., forcing many reverts to flood `onAbort` queue).
- Increases trust assumptions: user must trust bot or UI to assist in claiming from Zetachain.
