# On-Chain Slippage and Deadline Calculation Enables Front-Running and Value Extraction

### Summary

Currently, the slippage and deadline protections are calculated on-chain rather than off-chain by the user. This undermines the intent of slippage controls and leaves transactions vulnerable to front-running and price manipulation.

- General Risk Illustration

Assume a user wants to swap 1 ETH for 2500 USDC with a 1% slippage:

* Off-chain logic calculates the minimum output (e.g., `minReceived = 2500 * 0.99 = 2475`).
* If an attacker dumps ETH before the swap, causing ETH price to crash to \$2000, the on-chain `minReceived` now becomes `2000 * 0.99 = 1980`, and the swap still proceeds — despite being far worse for the user.

- Specific Vulnerability in Context

In the contest code, within `GatewayTransferNative`, when a user calls `withdrawToNativeChain`, the internal `_handleEvmOrSolanaWithdraw` function is executed. If `decoded.targetZRC20 != gasZRC20`, it routes to `_swapAndSendERC20Tokens`, where:

```solidity
amountInMax = amountsQuote[0] * (1 + slippage);
deadline = block.timestamp + MAX_DEADLINE;
```

This logic:

* Computes the `amountInMax` based on a **mutable on-chain quote**, and
* Sets a deadline from the current block timestamp.

Both values are therefore **modifiable by the network environment**, giving attackers a window to manipulate prices and force poor execution outcomes.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L319-L330

The same issue exist in `GatewayCrossChain` as well.

### Root Cause

Calculation of `amountInMax` and `deadline on-chain.

### Mitigation

Perform slippage tolerance and deadline computation **off-chain** and pass those values into the contract as parameters, so they are **user-defined and fixed** at transaction creation. Specifically:

Accept `amountInMax` and `deadline` as user-specified inputs in `_swapAndSendERC20Tokens`.
