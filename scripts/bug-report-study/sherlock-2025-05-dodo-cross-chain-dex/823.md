# GatewayTransferNative's _handleFeeTransfer will cause transaction reverts for users as native ZETA transfers cannot be processed

### Summary

The use of TransferHelper.safeTransfer() in _handleFeeTransfer() will cause transaction reverts for users as the function cannot handle native ZETA transfers when zrc20 is set to _ETH_ADDRESS_.

### Root Cause

In GatewayTransferNative.sol, the [_handleFeeTransfer()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L341) function uses TransferHelper.safeTransfer() for all assets, which cannot handle native ZETA transfers. The function needs to use TransferHelper.safeTransferETH() when zrc20 is ETH_ADDRESS.

### Internal Pre-conditions

1. User needs to call withdrawToNativeChain() with zrc20 set to *ETH_ADDRESS*
2. The function needs to attempt to transfer platform fees via _handleFeeTransfer()

### External Pre-conditions

None

### Attack Path

1. User calls withdrawToNativeChain() with zrc20 = *ETH_ADDRESS*
2. Function skips transferFrom check (correctly)
3. _handleFeeTransfer() is called to process platform fees
4. TransferHelper.safeTransfer() attempts to call transfer() on *ETH_ADDRESS*
5. Transaction reverts as *ETH_ADDRESS* is not a contract

### Impact

Users cannot execute withdrawToNativeChain() with native ZETA as the transaction will revert when attempting to transfer platform fees. This prevents users from performing cross-chain operations with native ZETA.

### PoC

_No response_

### Mitigation

Modify _handleFeeTransfer() to handle native ZETA differently:

```solidity
function _handleFeeTransfer(
    address zrc20,
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000;

    if (zrc20 == _ETH_ADDRESS_) {
        TransferHelper.safeTransferETH(EddyTreasurySafe, platformFeesForTx);
    } else {
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
}

```
