# GatewayTransferNative.sol :: withdrawToNativeChain() if the input token is the native token (ZETA), users will avoid paying fees.

### Summary

The `withdrawToNativeChain()` facilitates cross-chain withdrawals from ZetaChain to other networks, supporting both ZRC-20 tokens and the native token (ZETA).

However, when ZETA is used, the fee mechanism is not correctly implemented, allowing users to bypass the fee logic and effectively pay no fees.






### Root Cause

[withdrawToNativeChain()](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530-L600) is implemented as follows.

As shown, ZETA can be used, and the function invokes `_handleFeeTransfer()` to calculate the fees.
```solidity
unction _handleFeeTransfer(
        address zrc20,
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
```
`safeTransfer` is invoked from the `TransferHelper` library. In this context, `zrc20` refers to ZETA.
```solidity
function safeTransfer(address token, address to, uint value) internal {
        // bytes4(keccak256(bytes('transfer(address,uint256)')));
        (bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
        require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
    }
```
`safeTransfer()` uses a low-level `CALL` to invoke the `transfer` function on the token contract and checks both the returned boolean and data. The issue is that ZETA is a native token, not a ZERC20, and therefore does not implement the `transfer()` function. 

This is a problem because in Solidity, a low-level `CALL` to an address with no code (such as a native token) always returns success with empty data. This causes the `require` check to pass even though no actual native tokens are sent. As a result, if users withdraw using the native token, they effectively bypass the fee payment.


### Internal Pre-conditions

The problem is intrinsic to the code itself.


### External Pre-conditions

Users must use the native token `zrc20 = ZETA` when calling `withdrawToNativeChain()`.


### Attack Path

None.

### Impact

Users can bypass fee payments, resulting in a loss of funds for the protocol.


### PoC

As you can see, the transaction completes successfully without reverting, but user1 still retains the full balance, indicating that no actual transfer occurred.

### Mitigation

To resolve the issue, `_handleFeeTransfer()` must verify whether the `zrc20` is the native token and, if so, use `safeTransferETH`.
```diff
function _handleFeeTransfer(
        address zrc20,
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%

-       TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+       if (zrc20 == _ETH_ADDRESS_) {
+           TransferHelper.safeTransferETH(EddyTreasurySafe, platformFeesForTx);
+       } else {
+           TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+       }
    }
```
