# Using global slippage tolerance for all pairs is inefficient

### Summary

The `GatewayCrossChain` contract uses a single fixed slippage parameter for all token pairs, which fails to account for the varying volatility and liquidity characteristics of different tokens. This can lead to failed transactions for volatile token pairs (slippage too low) or excessive slippage for stable pairs (slippage too high), resulting potential value loss.

### Root Cause

In `GatewayCrossChain`, the slippage is defined as a fixed single state variable that applies to all token swaps:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L124
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L315
```solidity
uint256 public slippage; // Set during initialization, same for all tokens

uint amountInMax = (amountsQuote[0]) + 
    (slippage * amountsQuote[0]) / 1000;
```
There are no admin functions to update `slippage` in volatile or unpredictable market situation.

### Internal Pre-conditions

- Contract is initialized with a fixed slippage value (e.g., 5 = 0.5%).

### External Pre-conditions

- Different `zrc20/gasZrc20` pairs have different volatility / slippage
- Users attempt swaps during periods of high market volatility.

### Attack Path

**Slippage too low:**
- Protocol sets conservative slippage (e.g., 1% for stability).
- Price moves more than 1% for `USDT_zrc20`/`ETH_zrc20`
- Transaction reverts due to insufficient slippage allowance.
- `CCTX` operation fails.

**Slippage Too High for Stable Pairs**
- Protocol sets high slippage (e.g., 5%) to accommodate volatile pairs.
- `_swapAndSendERC20Tokens` swaps  `SHIB_zrc20`/`ETH_zrc20` to provide for gas token
- Swap executes with unnecessarily high slippage tolerance.
- More `targetZRC20` is swapped for `ETH_zrc20` and user receives less amount on destination chain

### Impact

The protocol's implementation of a uniform slippage parameter across all `gasZRC20/targetZRC20` trading pairs is inadequate for handling diverse token characteristics. For example, tokens with fee-on-transfer (FOT) mechanisms require elevated slippage thresholds to compensate for their inherent transfer fees. Given ZetaChain's future to integrate increasingly more assets, a static global slippage configuration becomes insufficient. This design flaw creates a binary failure mode: restrictive slippage settings cause legitimate `zrc20=>gasZRC20` exchanges to revert, while permissive settings expose users to value extraction through MEV exploitation and sandwich attacks due to unnecessarily wide price tolerance bands.
