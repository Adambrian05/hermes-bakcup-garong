# Untrusted `onAbort`/`onRevert` call will allow overwriting of legitimate external ID for cross-chain refund logic

### Summary
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L640

When sending a  cross chain transaction using zetachain maybe via the `GatewayZEVM` using `withdrawAndCall` 
```solidity
  function withdrawAndCall(
        bytes memory receiver,
        uint256 amount,
        address zrc20,
        bytes calldata message,
        CallOptions calldata callOptions,
        RevertOptions calldata revertOptions
    )
        external;
```
 or the `GatewayEVM` using `depositAndCall` 
```solidity 
 function depositAndCall(address receiver, bytes calldata payload, RevertOptions calldata revertOptions)
        external
        payable ;
```
as seen for the function signature above there is a `RevertOptions` struct that defines how do handle the transaction when the cctx fails here is the definition 
```solidity
struct RevertOptions {
    address revertAddress;
    bool callOnRevert;
    address abortAddress;
    bytes revertMessage;
    uint256 onRevertGasLimit;
}
```
below is a flow of a cctx from zetachain to a conntected  as explained in the zetachain docs  read more [here](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions)

**Flow:**

1. A universal contract on ZetaChain initiates a call to a connected chain via `withdrawAndCall` or `call`.
2. The Gateway forwards the message and/or tokens to the target contract on the connected chain.
3. If the target contract reverts, ZetaChain initiates the revert process.

**Revert Behavior:**

* If `callOnRevert` is `true`:

  * The Gateway invokes the `onRevert` function on the `revertAddress` on ZetaChain.
  * The remaining ZRC-20 tokens are passed along with the revert context.
  * If the `onRevert` call **itself reverts**, the Gateway transfers ZRC-20 tokens to and calls `onAbort` on the `abortAddress` on ZetaChain.

* If `callOnRevert` is `false`:

  * The Gateway transfers tokens to the `revertAddress` without invoking any function.

from this flow we can see that `revertAddress` or the `abortAddress` can be any contract set by the transaction initiator.  armed with this knowledge an attacker can craft a transaction so that it fails and the gateway will  trigger the `onAbort` or `onRevert` on `GatewayTransferNative`   
remember whenever  `onAbort` or `onRevert` is called on `GatewayTransferNative`   
```solidity 
function onAbort(AbortContext calldata abortContext) external onlyGateway {
        
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;

        emit EddyCrossChainRefund(externalId, abortContext.asset, abortContext.amount, walletAddress);
    }
```
a new refundInfo is created so the attack can just craft the revertMessage to overwrite an existing `externalId` successfully locking the users funds in the contract this can be repeated for all the refundInfo on the contract 



### Root Cause

In `GatewayTransferNative.sol`, the `onAbort` and `onRevert` functions parse the `revertMessage` to extract and store `RefundInfo` using an `externalId` key. These functions lack checks to verify whether the `externalId` is new or already used, and also fail to validate the origin of the call, allowing any body  to invoke them.


### Internal Pre-conditions

1. `GatewayTransferNative` store refunds  keyed by a 32-byte `externalId` in the `refundInfos` mapping.


### External Pre-conditions

1. The attacker submits a cross-chain transaction via ZetaChain’s `GatewayZEVM.withdrawAndCall()` or `GatewayEVM.depositAndCall()` with a deliberately crafted `RevertOptions` pointing to `GatewayTransferNative` as the `abortAddress` or `revertAddress`.
2. The attacker intentionally causes the cross-chain transaction to fail (e.g., by calling an invalid function on the destination chain) so that ZetaChain initiates the revert flow.
3. ZetaChain Gateway calls `onAbort()` or `onRevert()` on `GatewayTransferNative` with attacker-supplied `revertMessage`.


### Attack Path

1. Attacker observes a legitimate `externalId` stored in `refundInfos` from a prior user's transaction.
2. Attacker submits a new cross-chain transaction via ZetaChain with:
   - `revertAddress` or `abortAddress` set to `GatewayTransferNative`
   - `callOnRevert = true`
   - `revertMessage` = `externalId || attackerWallet`
3. Attacker causes the transaction to fail, triggering the Gateway to call `onAbort()` or `onRevert()` on `GatewayTransferNative`.
4. Because the contract does not check the `sender`, the existing refund record is overwritten with attacker-controlled values.
5. The legitimate user can no longer retrieve their original funds, effectively locking or stealing them.


### Impact

The affected users suffer a permanent loss or denial-of-access to their legitimate cross-chain refunds. The attacker does not gain the funds directly, but can grief the protocol by corrupting or hijacking all refund records via `externalId` spoofing.


#### Note 
a variant  of this  issue exist in `GatewayCrossChain` and `GatewaySend`

`N/Q`

### Mitigation

Implement a check for `sender`  whenever `onRevert` or `onAbort` is triggered maybe have a whitelist for allowed sender.
