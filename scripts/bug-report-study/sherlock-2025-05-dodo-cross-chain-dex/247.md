# Improper address validation allows unauthorized refund claims via `claimRefund` bypassing `bots` mapping

### Summary

The `receiver` variable is defaulted to `msg.sender`, so if `refundInfo.walletAddress.length != 20`, any user can pass the check `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");`, causing unauthorized refund claims as callers bypass the `bots` mapping and steal funds via the `claimRefund` function.

### Root Cause

In `GatewayCrossChain.sol` (around the [`onRevert` function](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590)), the receiver variable is set by default to `msg.sender`. However, when `refundInfo.walletAddress.length != 20`, the contract does not properly validate the refund recipient’s address. This allows any caller to satisfy the check `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");`, effectively bypassing the `bots` restriction and enabling unauthorized users to claim refunds.

### Internal Pre-conditions

1. The contract needs to store a `refundInfo.walletAddress` whose length is not equal to 20 bytes (i.e., an invalid or malformed address).
2. A user (attacker) needs to call the `onRevert` function or trigger the refund mechanism while `refundInfo.walletAddress.length != 20`.
3. The `receiver` variable is automatically set to `msg.sender` during the refund claim process.
4. The attacker needs to call `claimRefund` passing as `msg.sender` an address that satisfies `msg.sender == receiver`, bypassing the `bots` mapping check.
5. The refund amount must be different from the specific sum (e.g., 52), which triggers automatic transfer bypassing safe storage.

### External Pre-conditions

1. The off-chain system or cross-chain protocol must provide a `refundInfo.walletAddress` with an invalid length (not 20 bytes) when submitting refund data to the contract.
2. The refund event or revert must be triggered externally through a cross-chain message or transaction that causes the contract to store malformed refund data.
3. The attacker can monitor and detect refund records with malformed addresses to exploit the `claimRefund` function.

### Attack Path

1. An attacker observes or triggers a cross-chain refund event where the stored `refundInfo.walletAddress` length is not 20 bytes (malformed address).
2. Because `receiver` defaults to `msg.sender` and the refundInfo address length check is bypassed, the attacker calls `claimRefund`.
3. Inside `claimRefund`, the check `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");` passes because `msg.sender == receiver` by default.
4. The attacker successfully claims the refund intended for another user, stealing their funds.
5. The `bots` mapping intended to restrict access is effectively bypassed due to the malformed address and the default `receiver` assignment.

### Impact

The legitimate users suffer an approximate loss of their refunded funds, as attackers can steal these refunds. The attacker gains the stolen funds by bypassing the `bots` restriction and impersonating the receiver due to the malformed `refundInfo.walletAddress`.

### Mitigation

Avoid defaulting the `receiver` variable to `msg.sender`. Update the code to:
```solidity
        address receiver;
        if (refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```
