# Unpredictable Transaction Reverts Due to Incorrect Gas Fee Validation in `_swapAndSendERC20Tokens`

## Summary
The incorrect use of `amountInMax` instead of `amounts[0]` in the `INSUFFICIENT_AMOUNT_FOR_WITHDRAW` check will cause unpredictable transaction reverts for users as the validation fails when the actual swapped amount is less than the overestimated `amountInMax` including slippage.

## Root Cause
In `_swapAndSendERC20Tokens`, the check `require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW")` incorrectly uses `amountInMax` (which includes slippage) instead of `amounts[0]` (the actual amount swapped), leading to transaction reverts when the gas fee swap consumes a smaller amount than the overestimated maximum.

[GatewayTransferNative._swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L306-L306)

Also in `GatewayCrossChain`.

## Internal Pre-conditions
1. A user needs to initiate a cross-chain swap from ZetaChain to Chain B (e.g., Ethereum) via `depositAndCall`, triggering `onCall` and `_handleEvmOrSolanaWithdraw`, which calls `_swapAndSendERC20Tokens` to exchange `targetZRC20` for `gasZRC20`.
2. The `targetZRC20` must not be the gas token for Chain B, requiring a swap to obtain gas tokens (e.g., ZRC20 ETH for Ethereum).
3. The `targetAmount` must be small enough that the estimated `amountInMax` (including slippage) is close to or exceeds `targetAmount`, but the actual swapped amount (`amounts[0]`) is less than `amountInMax`.

## External Pre-conditions
1. Gas prices on Chain B (e.g., Ethereum) must be high (e.g., during a market bull run), requiring a significant `gasFee` that consumes a large portion of `targetAmount` when swapped.

## Attack Path
This is a vulnerability path, not an attack path, as the issue causes transaction failures rather than exploitable loss:

1. A user initiates a cross-chain swap from ZetaChain to Chain B (e.g., Ethereum) with a small targetAmount (e.g., 1000 wei of targetZRC20) via depositAndCall.
2. The onCall function triggers _handleEvmOrSolanaWithdraw, which calls _swapAndSendERC20Tokens to swap targetZRC20 for gasZRC20 to cover the gasFee (e.g., 0.01 ETH equivalent).
3. _swapAndSendERC20Tokens calculates amountInMax as amountsQuote[0] + (slippage * amountsQuote[0]) / 1000 (e.g., 1000 wei with slippage), but the actual swap consumes only amounts[0] (e.g., 900 wei).
4. The require(targetAmount - amountInMax > 0) check fails because targetAmount (1000 wei) minus amountInMax (1000 wei) equals 0, even though targetAmount - amounts[0] (1000 - 900 = 100 wei) would pass.
5. The transaction reverts with INSUFFICIENT_AMOUNT_FOR_WITHDRAW, preventing the user from completing the swap despite sufficient funds for the actual gas fee.

## Impact
The user cannot complete cross-chain swaps to Chain B (e.g., Ethereum) when the `amountInMax` with slippage is close to or exceeds `targetAmount`, rendering the swap mechanism useless for small transactions or high gas fee scenarios.

## PoC
See Attack Path

## Mitigation
Modify the `INSUFFICIENT_AMOUNT_FOR_WITHDRAW` check to use `amounts[0]` (the actual amount swapped) instead of `amountInMax`.
