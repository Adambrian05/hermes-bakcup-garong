# _handleERC20Deposit is incompatible with tokens who have missing return values on approvals

### Summary

GatewaySend utilizes .approve in _handleERC20Deposit in order to approve the token-in-question before the depositAndCall so that the Zeta Gateway can utilize it and transfer it to their gateway. The problem is that instead of utilizing the SafeERC20 library (for e.g. the one from OZ) in order to handle edge case scenarios originating from weird ERC20 tokens, like missing return values, they're directly using .approve.

Considering that DODO will utilize all assets supported by Zetachain, part of them is USDT.ETH which is USDT on mainnet where this problem exists: https://etherscan.io/token/0xdac17f958d2ee523a2206206994597c13d831ec7#code

### Root Cause

During the `_handleERC20Deposit` call which handles the transfer from the DODO Gateway to the ZetaChain one, the contract logic will try to approve the amount to the Zeta Gateway:

```solidity

    function _handleERC20Deposit(
        address targetContract,
        uint256 amount,
        address asset,
        bytes memory message,
        RevertOptions memory revertOptions
    ) internal {
        IERC20(asset).approve(address(gateway), amount);

        gateway.depositAndCall(
            targetContract,
            amount,
            asset,
            message,
            revertOptions
        );
    }

```

The problem is that they're using OZ's IERC20 interface which expects a boolean return value to indicate that the approval is successful, considering that the USDT contract will never return one, this call will always fail and the GatewaySend will be incompatible with USDT as an asset.
