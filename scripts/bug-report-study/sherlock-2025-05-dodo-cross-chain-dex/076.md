# Missing amount == 0 Check Leads to Unbounded Gas Consumption / RPC Griefing

### Summary

Multiple functions across the codebase allow amount == 0 to pass unchecked, resulting in unnecessary execution of expensive logic before eventually reverting. Although no direct fund loss occurs, this behavior leads to gas griefing and potential denial-of-service vectors, especially when chained with high-frequency RPC interactions.

for example, there is no amount check like:
`require(amount > 0, "zero amount);` or `require(amount != 0 , "zero amount);`

### Root Cause

we will take the case of the code `withdrawToNativeChain:530` where there is no check for amount = 0 either

### Internal Pre-conditions

create a function or contract that makes withdrawals and calls onCall with amount 0 repeatedly or with several calls, or one is enough.

### External Pre-conditions

1. Gas consumption tinggi karena banyak storage/read/write dilakukan sebelum akhirnya revert.
2. Can cause HTTP 429 (rate-limited) if run repeatedly.

### Attack Path

no theft of funds, but can cause gas and RPC limits to be limited.

### Impact

Allowing amount == 0 skips a trivial check but still initiates costly internal logic (e.g., minting, approvals, payload decoding, message forwarding).

Even though the calls eventually revert, gas is still burned up to that point, making the tx very expensive.

In testing, the revert-path with amount = 0 consumed over 1 billion gas units in cumulative test runs.

Attackers can flood chains/RPC providers with amount = 0 transactions to congest queues or force rate limits (see: 429 errors from BlockPI RPC).

This makes it a valid denial-of-service vector — especially in environments with shared queue-based infrastructure.

### Mitigation

in all the code I included in the summary section, add the mitigation :
`require(amount > 0, "zero amount);` or `require(amount != 0 , "zero amount);`

even for addresses, always tighten it so that it reverts immediately if the amount or address is 0.
