# Due to Missing Validation of fromTokenAmount, User Can Inflate Target Token Output in GatewaySend.depositAndCall()

### Summary


The `GatewaySend.depositAndCall()` function does not validate whether amount parameter is matching with the fromTokenAmount present in swapData due to which they can craft attacker can craft swapData to request more tokens than they paid for, causing the contract to transfer inflated output amounts across chains and mint or credit extra tokens on the destination. 


 
Here is the code snippet where we have an issue

```solidity
  function _doMixSwap(bytes calldata swapData) internal returns (uint256) {
        MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
       //@audit  - missing validtion on fromTokenAmount, we should check amount == fromTokenAmount
        if(params.fromToken != _ETH_ADDRESS_) {
            IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
        }
```

This vulnerability is marked as medium severity because it only becomes exploitable when the contract holds token balances. Under normal operation, it may not hold tokens for long. However, if any tokens are accidentally or temporarily left in the contract, an attacker can exploit the lack of validation to drain them. This can be fixed by keeping the minimum validation of swap input parameters within the `_doMixSwap()` function

```solidity
require(amount == params.fromTokenAmount, "Amounts are not matching");
```


### Root Cause

The contract does not validate that the user-supplied `amount` passed in depositAndCall() function matches the `params.fromTokenAmount` decoded from `swapData`. As a result, attackers can forge `swapData` to inflate the input amount used in swaps, even though they deposited less—causing excess tokens to be minted or credited on the destination chain.

### Internal Pre-conditions

Contract holds a balance of the high-value tokens.
Attacker knows the contract’s token holdings

### External Pre-conditions

NA

### Attack Path

1. User holds TokenA with an actual amount of 100 ETH.  
2. The call sets params.fromTokenAmount to 200 ETH (mismatched amount).  
3. The user sends 100 ETH when calling depositAndCall().  
4. Internally, the swap function _doMixSwap() uses 200 ETH as the input amount instead of the actual 100 ETH sent.  
5. Suppose the TokenA-to-TokenB price ratio is 1:3  
6. Based on the inflated amount, the swap outputs 600 ETH worth of TokenB instead of the correct 300 ETH.  
7. The system cross-chains and sends 600 ETH TokenB to the destination.  
8. The user ultimately receives 600 ETH TokenB on the destination chain—double what they should get.  

This highlights how missing validation on fromTokenAmount allows output inflation.  


### Impact

Attackers can obtain additional output tokens, effectively minting extra assets without depositing corresponding value
