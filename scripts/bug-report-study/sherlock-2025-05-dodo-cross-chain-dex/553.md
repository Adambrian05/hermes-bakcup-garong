# Non-standard token incompatibility in `GatewaySend::depositAndCall`

### Summary

In `GatewaySend::depositAndCall`, when users deposit assets to external chains, the contract uses `IERC20.transferFrom` to transfer tokens. However, if a non-standard ERC20 token (like `USDT`) is used, the call to `transferFrom` will revert because these tokens don’t return a boolean value as expected. As a result, the cross-chain deposit fails, and the feature becomes unusable for tokens like `USDT`.

### Root Cause

The protocol supports tokens listed here: https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets, which include nonstandard ERC20 tokens like `USDT`.

In [GatewaySend.sol#L239](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L239) and [GatewaySend.sol#L317](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L317), the contract assumes that the token’s `transferFrom` follows the ERC20 standard. However, some tokens such as USDT do not return a boolean value on `transferFrom`, which breaks compatibility with the standard interface.  As a result, calling `transferFrom` through the standard interface causes a low-level revert due to ABI mismatch.

### Internal Pre-conditions

None

### External Pre-conditions

The user passes a non-compliant ERC20 token, such as `USDT`, as the asset when calling `depositAndCall`.

### Attack Path

A user tries to transfer `USDT` across chains using `depositAndCall`:

1. The user approves `GatewaySend` to spend their `USDT`.
2. The user calls `depositAndCall`, attempting to deposit `USDT` and trigger a cross-chain message.
3. When `transferFrom` is called, the low-level call fails because `USDT` does not return a boolean as expected by the IERC20 interface. This causes the transaction to revert immediately.

As a result, the cross chain transfer never proceeds, and using `USDT` with `depositAndCall` always fails.

### Impact

Users may be unable to use `USDT` on external chains through the protocol. This makes the protocol unusable for `USDT` and similar tokens, effectively causing a denial of service for those assets.


### PoC

In `depositAndCall`, if the fromToken is `USDT`, calling `IERC20.transferFrom` will revert:

```solidity
IERC20(fromToken).transferFrom(msg.sender, address(this), amount)
```

To demonstrate this, we simulate the scenario using a forked Ethereum mainnet:

1. The `USDT` holder has enough balance
2. The holder successfully approves the `recipient` (e.g., the GatewaySend contract)
3. When `transferFrom` is called, the transaction reverts due to the missing boolean return value, which breaks the expected ERC20 interface behavior。

Below is the runnable test case:

Add a file named `PoC.t.sol` to the `test` folder.

```solidity
// SPDX-License-Identifier: MIT

pragma solidity ^0.8.20;

import {Test} from "forge-std/Test.sol";
import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";

interface IUSDC {
    function approve(address spender, uint value) external;
}

contract PoC is Test {

    function test_usdt_transfer_revert() public {
        // Ethereum mainnet USDT Contract (non-standard ERC20)
        address USDT = 0xdAC17F958D2ee523a2206206994597C13D831ec7;
        // USDT holder with a sufficient balance
        address holder = 0x30Ba21597F22aAfa4B0E86C250c8a6EEbAf0da54;
        // Mock receiver
        address receiver = makeAddr("receiver");
        // Ensure sufficient gas
        vm.deal(holder, 1 ether);
        // Amount to be approved and transferred
        uint256 amount = 1e6;
        // Ensure holder has sufficient balance
        assertGt(IERC20(USDT).balanceOf(holder), amount);

        // Step 1: Holder successfully approves the recipient
        vm.prank(holder);
        IUSDC(USDT).approve(receiver, amount);

        // Step 2: transferFrom is expected to revert
        vm.prank(receiver);
        IERC20(USDT).transferFrom(receiver, address(this), amount);
    }
}
```

Then run the test using the following command with your Ethereum mainnet RPC as `--fork-url`:

```shell
forge test --mt test_usdt_transfer_revert -vvv --fork-url https://mainnet.infura.io/v3/${API_KEY_INFURA}
```

As expected, the transaction reverts immediately when the `GatewaySend` calls USDT’s `transferFrom`. The output confirms the failure due to an `EvmError`:

### Mitigation

Consider using OpenZeppelin’s `SafeERC20` library. Replace all direct calls to `IERC20.transferFrom` with `SafeERC20.safeTransferFrom`. Ensure all token transfers use the `SafeERC20` library to maximize compatibility and safety.
