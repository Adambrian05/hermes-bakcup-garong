# `GatewayTransferNative::withdraw` having the wrong visibility can permit frontRunning

### Summary

`GatewayTransferNative::withdraw`  uses public visibility instead of internal and can be called by anyone, in `GatewayCrossChain::withdraw` the visibility is kept as internal  preventing wrong access to it.

### Root Cause

`GatewayTransferNative::withdraw::L291`  uses a public visibility instead of a `internal`
[https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L291](url)

### Attack Path

1. an attacker monitors the mempool for pending transactions
2. Calculates the expected externalId
3. Front-run with their  withdraw call using the same externalId and their address

### Impact

1. The legitimate user's `withdrawToNativeChain` call would likely fail when it tries to execute the same withdrawal operation that the attacker already processed.
2. The user's tokens would already be transferred to the contract but the withdrawal would have been processed by the attacker's transaction.
3.  The user's funds could become trapped in the contract since the externalId would already be used, and there's no mechanism to handle duplicate external IDs.

Make `GatewayTransferNative::withdraw` internal.
