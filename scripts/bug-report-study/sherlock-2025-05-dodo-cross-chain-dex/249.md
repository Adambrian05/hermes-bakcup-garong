# Authorization Bypass in claimRefund Allows Theft of All Pending Refunds for Non-EVM Addresses

### Summary

The `claimRefund` function in both `GatewayCrossChain.sol` and `GatewayTransferNative.sol` {root cause: contains flawed authorization logic that defaults the refund `receiver` to `msg.sender` for any refund destined for a non-EVM address (e.g., Bitcoin, Solana). This incorrectly makes the subsequent permission check `require(bots[msg.sender] || msg.sender == receiver)` always pass for any caller}. This will cause a {impact: direct theft of user funds} for {affected party: any user whose failed cross-chain transaction was destined for a non-EVM address}. This occurs as {actor: any malicious actor on ZetaChain} will {vulnerability path: monitor for `EddyCrossChainRefund` events for non-EVM destinations, call `claimRefund` with the corresponding `externalId`, and successfully pass the authorization check, causing the refunded assets to be transferred to the attacker's address instead of the rightful owner}.


### Root Cause

- In `contracts/GatewayCrossChain.sol` and the identical function in `contracts/GatewayTransferNative.sol`, within the `claimRefund` function: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574C1-L578C79 & https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L664-L669
```solidity
  function claimRefund(bytes32 externalId) external {
      RefundInfo storage refundInfo = refundInfos[externalId];

      address receiver = msg.sender; // Step 1: Receiver defaults to the caller
      if(refundInfo.walletAddress.length == 20) { // Step 2: This check is only true for EVM-style addresses
          receiver = address(uint160(bytes20(refundInfo.walletAddress)));
      }
      // If walletAddress.length is NOT 20 (e.g., for BTC/SOL), 'receiver' remains msg.sender.

      // Step 3: Authorization check is bypassed
      require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); 

      // ... transfer to 'receiver' (the attacker) ...
  }
```
The core vulnerability lies in the combination of the `receiver` determination logic and the authorization check. When a refund is for a non-EVM destination, the `refundInfo.walletAddress.length` **will not be 20**. As a result, the `if` block is skipped, and the `receiver` variable retains its default value of `msg.sender`. The subsequent `require` statement then effectively checks `require(bots[msg.sender] || msg.sender == msg.sender)`, which simplifies to `require(bots[msg.sender] || true)`. This condition is always true for any caller, completely bypassing the intended access control for non-EVM refunds.

### Internal Pre-conditions

1.  A user's cross-chain transaction, initiated via `GatewaySend.sol` (or a similar entry point), fails in a way that triggers the `onRevert` or `onAbort` function on `GatewayCrossChain.sol` or `GatewayTransferNative.sol`.
2.  The intended recipient address for this failed transaction is a non-EVM address (e.g., a Bitcoin, Solana address), and thus its byte representation (`walletAddress`) does not have a length of 20.
3.  The contract's `onRevert` or `onAbort` handler correctly stores the refund details (including the `externalId`, token, amount, and the non-EVM `walletAddress`) in the `refundInfos` mapping. An `EddyCrossChainRefund` event is emitted.


### External Pre-conditions

1.  An attacker is monitoring `EddyCrossChainRefund` events on the ZetaChain network.
2.  The attacker observes an event corresponding to a pending refund where the `walletAddress` field has a length different from 20 bytes, and notes down the associated `externalId`.


### Attack Path

1.  A legitimate user, Alice, initiates a cross-chain swap from Ethereum to her personal Bitcoin address. The transaction fails after reaching ZetaChain (e.g., due to an issue on the Bitcoin side of the process).
2.  The `onRevert` or `onAbort` function on the DODO DEX contract on ZetaChain is triggered. Because Alice's Bitcoin address length is not 20, the refund details are stored in the `refundInfos` mapping. An `EddyCrossChainRefund` event is emitted containing the `externalId` for Alice's refund.
3.  An attacker, Bob, sees this event and extracts the `externalId`.
4.  Bob calls `claimRefund(externalId)` from his own EOA, `0xBob`.
5.  Inside the `claimRefund` function:
    a.  The `RefundInfo` for Alice's refund is loaded from storage. The stored `refundInfo.walletAddress.length` is not 20.
    b.  The `receiver` variable is initialized to `msg.sender`, which is Bob's address (`0xBob`). The `if(refundInfo.walletAddress.length == 20)` condition is false, so `receiver` remains `0xBob`.
    c.  The authorization check is performed: `require(bots[0xBob] || 0xBob == 0xBob, "INVALID_CALLER");`.
    d.  The `0xBob == 0xBob` part of the OR condition evaluates to `true`, so the entire `require` statement passes. The authorization is completely bypassed.
6.  The function proceeds to `TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount)`.
7.  The refunded tokens are transferred to `receiver`, which is Bob's address. Bob has **successfully stolen** Alice's refund.


### Impact

* **Direct theft of user funds.** Any pending refund destined for a non-EVM address (such as Bitcoin or Solana) can be stolen by any party on ZetaChain by calling `claimRefund` with the correct `externalId`.
* This represents a critical failure of the protocol's refund mechanism, which is a crucial safety net for users of a cross-chain system.
* The affected party is any user of the DODO Cross-Chain DEX performing a cross-chain transaction to a non-EVM chain whose transaction fails and requires a refund. Their funds are at high risk of being stolen by front-running bots or malicious observers.
