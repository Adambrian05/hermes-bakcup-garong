# User can underpay the fee

### Summary

The withdrawToNativeChain function allows users to manipulate the fee payment mechanism by supplying mismatched fromToken and zrc20 values(fromTroken == Native token, and zrc20 token to be token that has smaller value then native but same amount of decimals), enabling them to pay significantly less in fees than intended. This results in fee evasion and financial loss to the protocol.



### Root Cause

Since the withdrawToNativeChain function does not validate whether the params.fromToken and the zrc20 argument are to the same token. It is possible forusers to deposit ZETA (1 ZETA is around 0.21usd) as the native token through msg.value and specify it as params.fromToken, while setting the zrc20 parameter to a much cheaper token (e.g., ZPepe: 1 Pepe is around 0.000011usd).

As a result, the protocol calculates the fee using the zrc20 token, even though the actual token being swapped is ZETA. This allows users to significantly underpay the fee while still receiving the correct swapped output on the destination chain.
```solidity
function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 

        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);

        // Decode message and decompress swap params
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message);
        
        // Check if the message is from Bitcoin to Solana
        // address evmWalletAddress = (decoded.dstChainId == BITCOIN_EDDY || decoded.dstChainId == SOLANA_EDDY)
        //     ? msg.sender
        //     : address(uint160(bytes20(decoded.receiver)));

        // Transfer platform fees
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // platformFee = 5 <> 0.5%
        amount -= platformFeesForTx;

        // Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
        
        // Withdraw
        if (decoded.dstChainId == BITCOIN_EDDY) {
            (, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFee();
            _handleBitcoinWithdraw(
                externalId, 
                decoded, 
                outputAmount,
                gasFee
            );

            emit EddyCrossChainSwap(
                externalId, 
                ZETACHAIN,
                decoded.dstChainId, 
                zrc20, 
                decoded.targetZRC20, 
                amount, 
                outputAmount - gasFee, 
                decoded.sender,
                decoded.receiver, 
                platformFeesForTx
            );
        } else {
            uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, 
                outputAmount, 
                decoded.receiver
            );

            emit EddyCrossChainSwap(
                externalId, 
                ZETACHAIN,
                decoded.dstChainId, 
                zrc20, 
                decoded.targetZRC20, 
                amount, 
                amountsOutTarget, 
                decoded.sender,
                decoded.receiver, 
                platformFeesForTx
            );
        }
    }
```

```solidity
function _doMixSwap(
        bytes memory swapData, 
        uint256 amount, 
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }

        IZRC20(params.fromToken).approve(DODOApprove, amount);
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(
            params.fromToken,
            params.toToken,
            params.fromTokenAmount,
            params.expReturnAmount,
            params.minReturnAmount,
            params.mixAdapters,
            params.mixPairs,
            params.assetTo,
            params.directions,
            params.moreInfo,
            params.feeData,
            params.deadline
        );
    }
```

### Attack Path

1. User holds the same amount of Zeta token and some zrc20 that is a lot cheaper then Zeta(in Poc ZPepe is used)
2. user calls withdrawToNativeChain, where he transfers amount of Zeta token and specifies the zrc20 token as token that is cheaper then native token and provides the same amount of that token(so that zrc20 token has to be cheaper and have same amount of decimals), also in swapParams from token has to be set as Zeta(Native token)
3. User pays less fee( the whole amount of zrc20 token that was provided) since the zrc20 token is a lot cheaper then Zeta
4. swap executes
5. _handleEvmOrSolanaWithdraw executes, calls WithdrawAndCall function and then gateway.withdrawAndCall is called
6. after that the amount of target token is bridged to the user on Ethereum (via onCall which is called by gatewayEVM) and user receives target tokens.

### Impact

Users can underpay for protocol fee, causing the protocol to lose significant fee revenue

### PoC

Lets say that user holds:
- 1000 ZETA (worth around 0.21 usd per token → 210 usdtotal)
- 1000 ZPepe (worth around 0.000011 usd per token → ~0.011 usd total)
- *Note: Zeta and ZPepe have same amount of decimals

Now user wants to withdraw his ZETA (Native token) tokens to some dstChain, which is completely expected behaviour if we spot that withdrawToNativeChain function is payable and it handles native tokens deposits.
So the user calls the withdrawToNativeChain function with:
- msg.value: 1000 ZETA (sent as native token)
- zrc20: ZPepe
- amount: 1000 (ZPepe)
- message that contains:
a) Decoded Message (only populating some fields, although allFields would be populated in real scenario)
    address targetZRC20; -> ZUSDC
    uint32 dstChainId; -> Ethereum
    bytes sender;
    bytes receiver; address(user)
    bytes swapDataZ;(swapDataZ will not be 0 as we are executing the trade)
    bytes contractAddress; // empty for withdraw, non-empty for withdrawAndCall
    bytes swapDataB; 
    bytes accounts;

b) MixSwapParams  (only populating some fields for simplicity, although allFields would be populated in real scenario) 
    address fromToken; -> ETH_ADDRESS indicting that its the native token (ZETA)
    address toToken; -> ZUSDC
    uint256 fromTokenAmount; -> 1000ZETA
    uint256 expReturnAmount; 210 Zusdc
    uint256 minReturnAmount; 208.95 (included the slippage of 0.5%)
    address[] mixAdapters;
    address[] mixPairs;
    address[] assetTo;
    uint256 directions;
    bytes[] moreInfo;
    bytes feeData;
    uint256 deadline;

So with these configuration of the call it is possible for user to underpay the fee (pay fee with very low amount).
Since the msg.value would be 1000Zeta and Zeta would also be fromToken in swapParams
but since user have specified zrc20 argument as ZPepe the fee will be payed with ZPepe tokens (and also the whole ZPepe token amount specified in function call will be lost for user)

So the amount of 1000Zpepe is worth around of 0.011usd and the amount of 1000ZETA is worth around of 210 usd

Lets say that the fee is set to 5%

The amount that user should have payed for 1000Zeta is around 10.5usd
but the actual amount that user have payed is 0.011usd (using the full worth of ZPepe amount since user will loose whole amount)
So the user have saved around 10.489 usd and protocol have lost that same amount in fees

The ZETA swap executes successfully, and _handleEvmOrSolanaWithdraw is called, inside of _handleEvmOrSolanaWithdraw  the WithdrawAndCall is called which then calls gateway.withdrawAndCall .
The USDC amount is bridged to the user on Ethereum via onCall ( called by gatewayEVM).

### Mitigation

Consider checking whether the fromToken and zrc20 provided in function call are the same.
