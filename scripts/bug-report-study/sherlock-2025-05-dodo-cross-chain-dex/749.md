# `onCall` function will always revert during zeta token `depositAndCall` operation.

### Summary

During `GatewayZEVM` zeta token`depositAndCall` operation, [onCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357) function in contract `GatewayTransferNative` is being executed in which platform fees is being deducted through `_handleFeeTransfer` however this part will always revert because the wzeta token `safeTransfer` is being used for transferring tokens  instead of calling native zeta transfer `safeTransferETH`.

 Remember that the `GatewayTransferNative` is receiving native zeta tokens and not wrapped zeta token. Therefore, the call will just revert because the wrapped token is not available. What available inside the contract is native zeta.

### Root Cause

The root cause is the wrong call operation being used in `_handleFeeTransfer`. This will simply revert because it is transferring wrapped zeta tokens instead of native zeta tokens. Native zeta token transfer is using `safeTransferETH`.

```Solidity
File: GatewayTransferNative.sol
341:     function _handleFeeTransfer(
342:         address zrc20,
343:         uint256 amount
344:     ) internal returns (uint256 platformFeesForTx) {
345:         platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
346:         TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx); //@audit transferring zrc-20 token instead of native token transfer.
347:     }
```

To further explain the flow, let's discuss on how the native token transfer ended up in `GatewayTransferNative`. We need to study first `depositAndCall` function under `GatewayZEVM`. In the function below, line 398, it calls `_transferZETA` to transfer native zeta from `GatewayZEVM` to `GatewayTransferNative`.

Details of `_transferZETA`
Line 127 pertains to the actual transfer of native zeta token from `GatewayZEVM` to `GatewayTransferNative`. This is a proof that `GatewayTransferNative` receives native zeta token instead of wrapped zeta token, that's why it makes sense that `safeTransferETH` should be use in onCall's `_handleFeeTransfer`.
```Solidity
File: GatewayZEVM.sol
124:     function _transferZETA(uint256 amount, address to) private {

127:         (bool sent,) = to.call{ value: amount }(""); // @note transfer native zeta to the to address which is GTN
128:         if (!sent) revert FailedZetaSent();
```

### Internal Pre-conditions

1. Happens only during GatewayZEVM zeta token depositAndCall operation.

### External Pre-conditions

none

### Attack Path

1. The user want to transfer zeta tokens from Ethereum to Zetachain via `depositAndCall` operation
2. User deposited zeta tokens in Ethereum chain custody contract.
3. This will emit event and  `depositAndCall` will be executed in `GatewayZEVM` contract.
4. Target contract `GatewayTransferNative` will receive native zeta token.
5. `onCall` function inside `GatewayTransferNative` will be executed.
6.  `_handleFeeTransfer` will revert because the wzeta token `safeTransfer` is being used for transferring tokens instead of calling native zeta transfer `safeTransferETH`.

### Impact

Denial of service for core operation of transferring zeta tokens from external chain to destination chain Zetachain.
This cross-chain operation simply don't work.

### PoC

See attack path

### Mitigation

Need to create another `_handleFeeTransfer` with `safeTransferETH` feature to be used during GatewayZEVM zeta token depositAndCall operation.
