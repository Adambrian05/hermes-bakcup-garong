# Unchecked Return Values from Non-Standard Tokens Can Cause Silent Failures

### Summary

The unsafe assumption that all tokens return true on transfer() and transferFrom() will cause silent failures for token transfers for cross-chain users as the GatewaySend contract will fail to detect failed transactions when interacting with non-standard tokens like BTC.BTC and SOL.SOL.



### Root Cause

In GatewaySend.sol, the function uses IERC20.transferFrom() and IERC20.transfer() without validating whether the returned value is true. Non-standard tokens like ZRC20 representations of BTC or SOL may not return any value, leading the EVM to assume a success.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L238-L241

### Internal Pre-conditions

A user must use a token like BTC.BTC or SOL.SOL that does not return a boolean value on transfer.

The GatewaySend contract uses the transferFrom() or transfer() functions without safe wrappers.

The token silently fails (does not revert but also doesn’t return true).

### External Pre-conditions

The token is listed on ZetaChain as a supported asset. BTC.BTC (native Bitcoin)
SOL.SOL (native Solana)

The token behaves in a non-standard way—e.g., no return value or conditional success logic.



### Attack Path

User approves GatewaySend for transfer of a ZRC20 token (e.g., BTC.BTC).

User calls depositAndCall() or a cross-chain transaction is routed to onCall().

The token’s transferFrom() fails silently (returns no value).

The GatewaySend contract interprets the transfer as successful.

Output token transfer is attempted, potentially transferring incorrect or zero amount.

User believes transaction succeeded but funds are lost, stuck, or misrouted.

### Impact

Users suffer a loss of tokens or receive zero output on cross-chain swaps. The contract behaves as if the operation was successful due to false positives from non-standard token responses. This could lock funds, break workflows, or falsely emit events (like EddyCrossChainSend) that indicate success.

### Mitigation

Use OpenZeppelin's SafeERC20.safeTransfer and safeTransferFrom which handle missing return values properly.

Whitelist only ERC20-compliant ZRC20 tokens or implement interface checking logic before interactions.

Add a validation layer per token to ensure behavioral conformity.
