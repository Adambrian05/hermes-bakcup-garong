# ExternalId collosion can lead to refundinfo sturct overwrittting

### Summary

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewaySend.sol#L160

The reused external ID generation logic will cause a refund overwrite for cross-chain users as `GatewaySend` deployed with the same address on different chains may collide when calling `GatewayTransferNative`.

```solidity

    function _calcExternalId(address sender) internal view returns (bytes32 externalId) {
        externalId = keccak256(abi.encodePacked(address(this), sender, globalNonce, block.timestamp));
    }
```
If two   `GatewaySend`  contracts  deployed using `create2` on different chains share the same address and emit transactions with matching `msg.sender`, `globalNonce`, and `block.timestamp`, they will generate the same `externalID`. 

### Root Cause


In `GatewaySend`, the `externalID` is built using `abi.encodePacked(address(this), sender, globalNonce, block.timestamp)`. If the contract is deployed using `create2` on multiple EVM chains with the same init code and salt, its address will be the same, increasing the chance of collision.


### Internal Pre-conditions

1. Devs deploy `GatewaySend` on multiple chains using `create2` with the same salt and init code
2. The user sends a cross-chain transaction at a shared block timestamp
3. `globalNonce` and `sender` are reused across chains

### **note**

**`block.timestamp` on L2 is slower than on L1 because L2 batches many transactions and settles them periodically on L1.**

L2 timestamps usually reflect the time when these batches are finalized on L1, not when each L2 block or transaction happens. This batching and dependency on L1 finality cause L2 timestamps to update less frequently and appear slower than L1’s. so transaction executed on at different on eth and base may have the same `block.timestamp`


### External Pre-conditions

1. Two transaction(this can be more than 2 but have more than 2 is very unlikely) land at the same `block.timestamp` on separate EVM chains and produce same `externalId`
2. Both are routed to `GatewayTransferNative` or `GatewayCrossChain`on ZetaChain
3. and they both revert or abort maybe due to `GatewayZevm` been paused or something else.


### Attack Path

1. Two cross-chain transactions are sent at the same time from different chains
2. Both generate the same `externalID`
3. and they both revert or abort maybe due to `GatewayZevm` been paused or something else.
4. `GatewayTransferNative` stores a refund struct using this ID
5. One refund entry overwrites the other, causing data loss

### Impact

Users suffer refund failure or incorrect refund due to overwritten struct. Funds may be stuck or lost.

n/q

### Mitigation

Include `block.chainid` in the `externalID` construction to ensure uniqueness across chains and prevent collision.
