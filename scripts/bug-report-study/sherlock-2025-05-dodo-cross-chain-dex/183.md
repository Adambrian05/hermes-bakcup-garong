# ETH Native Value Validation Leading to Fund Loss and Fee Calculation Errors

## Description
The `GatewayTransferNative` contract has a serious issue in handling native ETH in the `withdrawToNativeChain()` function. This function is declared as `payable` to receive native ETH, but does not validate the `msg.value` (the actual ETH received) with the `amount` parameter (which is used for fee and swap calculations). This causes problems in calculating platform fees and potential loss of user funds.

## Code Snippet
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530

## Root Cause
`withdrawToNativeChain()` function:  
```solidity
function withdrawToNativeChain(
    address zrc20,              // Source token to be withdrawn
    uint256 amount,             // The number of tokens to be withdrawn
    bytes calldata message      // The encoded data contains swap instructions and destinations.
) external payable {            // ⚠️ PROBLEM: Payable but no validation msg.value
    
    // Check if the token is not native ETH
    if(zrc20 != _ETH_ADDRESS_) {
        // ✅ TRUE: For ERC20/ZRC20 tokens, there is a transferFrom validation
        require(
            IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), 
            "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED"
        );
    } 
    // ❌ MAIN PROBLEM: For native ETH, there is no validation of msg.value vs amount!
    // User can send different ETH with amount parameter

    // ... the rest of the functions use the amount parameter, not msg.value for calculations
    uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // ⚠️ Use amount instead of msg.value
}
```
The root of the problem is that when `zrc20 == _ETH_ADDRESS_`, there is no check whether `msg.value == amount`. The `amount` parameter is used for fee and swap calculations, `msg.value` is the ETH that the contract actually receives, but there is no synchronization between the two. If the user sends `msg.value > amount`, the excess ETH is not returned.

## Impact
Users can lose ETH if they send an amount that does not match the parameters.

## Scenario
1. Setup: User wants to swap 5 ETH to another token
2. Execution: User calls `withdrawToNativeChain(_ETH_ADDRESS_, 5 ether, message)` but sends `msg.value = 10 ether`
3. Process:
- Contract receives 10 ETH (`msg.value`)
- Fee calculation based on 5 ETH only (`amount`)
- `platformFeesForTx = (5 ether * feePercent) / 1000` = fee based on 5 ETH only
4. Result:
- User pays lower fee than expected
- 5 excess ETH stuck in contract without being returned

## Recommendation
Add `msg.value` vs `amount` validation for ETH Native.
```solidity
function withdrawToNativeChain(
    address zrc20,              
    uint256 amount,             
    bytes calldata message      
) external payable {
    
    if(zrc20 != _ETH_ADDRESS_) {
        // For ERC20/ZRC20 tokens
        require(
            IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), 
            "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED"
        );
        
        // ✅ ADDITION: Make sure no ETH is sent for non-ETH tokens
        require(msg.value == 0, "ETH_NOT_EXPECTED_FOR_TOKEN_TRANSFER");
    } else {
        // ✅ ADDED: For native ETH, validate msg.value must be equal to amount
        require(msg.value == amount, "ETH_AMOUNT_MISMATCH");
        require(msg.value > 0, "ETH_AMOUNT_ZERO");
    }
    
    // ... remaining functions remain the same
}
```
