# Missing Validation for Native Token Amount in `withdrawToNativeChain`

### Summary

The `GatewayTransferNative.withdrawToNativeChain()` function does not validate how much native ZETA is sent when users withdraw native tokens (`zrc20 == _ETH_ADDRESS_`). This lets an attacker claim large withdrawals while sending very little value, breaking cross-chain logic and allowing them to drain protocol funds and bypass fees.

### Root Cause

For ERC20 tokens, the function uses `transferFrom()` which checks the amount automatically. But for native ZETA, there's no check like:

```solidity
require(msg.value == amount, "Amount mismatch");
```

So when a user sends a small amount (like 0.1 ZETA) but claims a large one (like 1000 ZETA), the contract accepts it and processes based on the **fake, inflated** amount.

- `withdrawToNativeChain()` function- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530-L600
```solidity
    function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 

        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);

        // Decode message and decompress swap params
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message);
        
        // Check if the message is from Bitcoin to Solana
        // address evmWalletAddress = (decoded.dstChainId == BITCOIN_EDDY || decoded.dstChainId == SOLANA_EDDY)
        //     ? msg.sender
        //     : address(uint160(bytes20(decoded.receiver)));

        // Transfer platform fees
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // platformFee = 5 <> 0.5%
        amount -= platformFeesForTx;

        // Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
        
        // Withdraw
        if (decoded.dstChainId == BITCOIN_EDDY) {
            (, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFee();
            _handleBitcoinWithdraw(
                externalId, 
                decoded, 
                outputAmount,
                gasFee
            );

            emit EddyCrossChainSwap(
                externalId, 
                ZETACHAIN,
                decoded.dstChainId, 
                zrc20, 
                decoded.targetZRC20, 
                amount, 
                outputAmount - gasFee, 
                decoded.sender,
                decoded.receiver, 
                platformFeesForTx
            );
        } else {
            uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, 
                outputAmount, 
                decoded.receiver
            );

            emit EddyCrossChainSwap(
                externalId, 
                ZETACHAIN,
                decoded.dstChainId, 
                zrc20, 
                decoded.targetZRC20, 
                amount, 
                amountsOutTarget, 
                decoded.sender,
                decoded.receiver, 
                platformFeesForTx
            );
        }
    }
```

### Internal Pre-conditions

* Contract is deployed on ZetaChain
* It holds ZRC20 tokens from normal operations (e.g., user refunds)
* Fee percentage is set (affects fee logic)


### External Pre-conditions

* Attacker has small amount of native ZETA (e.g., 0.1)
* Gateway system is working
* Valid target chain and receiver exist

### Attack Path

1. Attacker calls `withdrawToNativeChain` with:

   - `zrc20`: `_ETH_ADDRESS_`
   - `amount`: 1000 ZETA
   - `msg.value`: 0.1 ZETA
   - `message`: a valid withdrawal message

2. Because there's **no check**, the contract:

   - Accepts the small payment
   - Calculates and processes based on the large fake amount
   - Sends large amounts across chains or consumes protocol funds

3. Result:

   - Attacker pays: 0.1 ZETA
   - Attacker receives: \~995 ZETA in value (after fake fee)
   - Fee goes uncollected (because `_ETH_ADDRESS_` can't be transferred)

### Impact

- Contract loses funds (used in processing fake large amounts)
- Platform fee logic breaks (fees based on fake amount, and ETH transfers fail)
- Real users waiting for withdrawals may lose their tokens
- Large profit from tiny input

### PoC

_No response_

### Mitigation

Add native token validation like this:

```solidity
if(zrc20 == _ETH_ADDRESS_) {
    require(msg.value >= amount, "Native token amount mismatch");
}
```
