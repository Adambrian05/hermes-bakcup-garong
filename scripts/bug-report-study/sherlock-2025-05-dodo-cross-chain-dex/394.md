# Lack of Nonce-Replay Protection on Cross-Chain Messages

### Summary

In the GatewayTransferNative.sol . The externalId (a unique nonce), lacks a check to prevent replay of the same externalId.
If the same externalId is used twice (maliciously or due to delays), a user could receive twice the tokens, or an attacker could reuse a previous “successful” message.

### Root Cause

In https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357
The onCall function processes messages and performs swaps or transfers based on the externalId but there's no check to see if an externalId has been processed before.

In https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607
The onRevert function uses externalId to create or update refund information but there's no replay protection.

The globalNonce declared is used in  _calcExternalId to generate externalId. The externalId, which incorporates globalNonce , is passed into cross-chain functions like withdraw and withdrawAndCall. However, the onCall function, responsible for executing cross-chain swaps, lacks an explicit mechanism to validate or prevent the reuse of an externalId. Similarly, the onRevert function, which handles cross-chain swap reverts, also doesn't have replay protection for externalId.

### Internal Pre-conditions

1. A successful cross-chain onCall or onRevert transaction must have occurred previously, generating an externalId.
2. The externalId from the previous transaction must be known to the attacker.
3. The contract must not have a mechanism to mark externalId as already processed or consumed for onCall and onRevert functions. While claimRefund does delete the refundInfos entry associated with an externalId, this is for refunds specifically and doesn't prevent replay of the initial onCall or onRevert messages.




### External Pre-conditions

Attacker Control or Observation of External Messages: An attacker must either have the ability to:
1. Intercept and re-send previously broadcast cross-chain messages.
2. Trigger the external Gateway to re-deliver a previously processed message.
3. Know the externalId and relevant transaction details to construct a replay attack.





### Attack Path

Scenario 1: Accidental or malicious resubmission

How it works:

-Sometimes, due to network latency or a consumer application’s retry logic, the same cross‐chain request might be broadcast twice (e.g., the user clicked “Send” again because they didn’t see confirmation).
-The user can also maliciously make a resubmission.
-Because the contract doesn’t check the nonce, both submissions process, and the recipient gets funds twice.


Scenario 2: Passive Mempool “Sniffing”

How it works:

-Suppose the destination chain mempool is public. As soon as the first valid onCall() transaction is broadcast, a watcher bot notices it, extracts the calldata (including externalId), and immediately resubmits the identical calldata to the same gateway.
-Since the contract doesn’t block a second use of that nonce, the “bot” pays gas and gets tokens twice.



### Impact

1.Double‐Spend of Funds: Attacker or recipient could drain contract’s token balances by replaying messages.

2.Cross‐Chain Inconsistency: Upstream ZetaChain gateway thinks it delivered once; contract processes twice, causing accounting mismatch.

### PoC

_No response_

### Mitigation

Introduce a mapping(bytes32 => bool) public processedMessages;

At top of onCall, check require(!processedMessages[externalId], "Replay detected");, then mark processedMessages[externalId] = true.

Similarly, for onRevert, track which revert messages have been processed to avoid double‐refund.
