# Token Mismatch Vulnerability in `GatewayTransferNative` Functions

### Summary

The `GatewayTransferNative` contract fails to validate that the token being swapped (`params.toToken`) matches the token being withdrawn (`decoded.targetZRC20`) in both `onCall()` and `withdrawToNativeChain()`. This allows users to swap one token (e.g., TokenA), then instruct the contract to withdraw a different token (e.g., TokenB) to a target address. If TokenB is held by the contract (from other operations), the attacker can effectively **drain arbitrary tokens**.

### Root Cause

In `onCall()` and `withdrawToNativeChain()`, the `params.toToken` field is used as the **swap output token**, while `decoded.targetZRC20` or input `targetZRC20` is used for **withdrawal**. But there is **no check** ensuring both tokens are the same.


### Affected Code (onCall):
- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L395
```solidity
// Swap output:
uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);

// Withdraws *targetZRC20* regardless of what the swap actually output:
_handleEvmOrSolanaWithdraw(
    externalId,
    decoded,
    outputAmount,
    decoded.receiver
);
```

### Affected Code (withdrawToNativeChain):
- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L555
```solidity
uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);

// No check if output token matches native token for withdrawal
require(msg.value >= amount, "Native token mismatch");
```


### Internal Pre-conditions

1. `GatewayTransferNative` has multiple token balances (from onRevert, leftover swaps, etc.)
2. Cross-chain withdrawal logic is operational
3. User supplies arbitrary `params.toToken` and different `decoded.targetZRC20`

### External Pre-conditions

1. Attacker knows the contract holds tokens like TokenB
2. Attacker can craft valid `MixSwapParams` and `DecodedMessage` structures

### Attack Path

1. Attacker crafts a cross-chain swap with:

   - `params.toToken`: token they can manipulate (e.g., TokenA with low liquidity)
   - `decoded.targetZRC20`: valuable token held by contract (e.g., TokenB)

2. Performs a cheap or low-value swap (or no swap at all)

3. Contract performs the swap for TokenA but withdraws TokenB

4. Attacker receives TokenB even though TokenA was the output of the swap

### Impact

- Arbitrary token withdrawal: If TokenB is in the contract, it can be drained
- Loss of protocol funds: Legitimate user funds may be stolen by misaligned withdrawal
- Incorrect accounting: Cross-chain accounting and swap integrity breaks
- Bypass fee logic: Platform fees and gas cost logic is calculated based on mismatched tokens
