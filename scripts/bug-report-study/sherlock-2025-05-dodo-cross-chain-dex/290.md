# Use of block.timestamp as Swap Deadline Enables Validator Exploitation

### Summary

In the [GatewayCrossChain.sol._swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L325) and the [GatewayTransferNative,sol._swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L329) function the call to the `IUniswapV2Router.swapTokensForExactTokens` passes `block.timestamp + MAX_DEADLINE` as the deadline for the swap to execute. Using this and not the actual deadline passed by a user is prone to manipulation by validators as validators can deliberately delay including the transaction in a block this can be particularly detrimental for a user who wants to make a time sensitive transaction or may introduce the user to dangerous sandwich attacks. Using `block.timestamp + MAX_DEADLINE` is equivalent to having no deadline at all. Since block.timestamp is only evaluated at the time of block inclusion (which validators control), it offers no protection against delays or MEV strategies

### Root Cause

In both  [GatewayCrossChain.sol._swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L325) and the [GatewayTransferNative,sol._swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L329) when calling `swapTokensForExactTokens` it passes `block.timestamp + MAX_DEADLINE` as the deadline

### External Pre-conditions

Always happens consider critical function called by the gateway in the [GatewayCrossChain.sol.onCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442) or the [GatewayTransferNative.withdrawToNativeChain](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530) which internally calls function like `_handleEvmOrSolanaWithdraw` which calls `swapTokensForExactTokens`

### Attack Path

1. Suppose a user Alice transacting in the EVM and uses the `GatewaySend` to deposit ERC20 tokens or normal ETH via external call to the `GatewaySend.sol.depositAndCall`
2. Alice decides to withdraw tokens and Alice chose a transaction fee that is too low for miners to be interested in including her transaction in a block
3. The transaction stays pending in the mempool for extended periods, which could be hours, days, weeks, or even longer.


### Impact

Validators can intentionally delay including the transaction in a block until a more favorable time for them (or less favorable for the user), yet still satisfy the deadline check. Without a user-specified deadline, the transaction remains vulnerable to sandwich attacks or unfavorable execution at a future time.
