# Missing Recipient Length Validation resulting in a permanent loss of funds

### Summary

The onCall function in GatewaySend.sol decodes a recipient address from an incoming cross-chain message. It then converts this recipient (which is bytes) to an address using address(bytes20(recipient)) without first validating if recipient.length is exactly 20 bytes. If the length is incorrect, this conversion will lead to either truncation (if > 20 bytes) or zero-padding (if < 20 bytes) of the recipient address. Consequently, funds intended for the user will be sent to an incorrect address, resulting in a permanent loss of funds

### Root Cause

The [onCall](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L356) function implicitly assumes that the recipient byte array, decoded from the message payload (originating from the ZetaChain gateway), will always be exactly 20 bytes long when representing an EVM address. There is no explicit require(recipient.length == 20) check before the address(bytes20(recipient)) typecast

```solidity
function onCall(
        MessageContext calldata /*context*/,
        bytes calldata message
    ) external payable onlyGateway returns (bytes4) {
        (
            bytes32 externalId, 
            uint256 amount, 
            bytes calldata recipient, 
            address fromToken, 
            address toToken, 
            bytes calldata swapData
        ) = decodePackedMessage(message);

        bool fromIsETH = (fromToken == _ETH_ADDRESS_);
        bool toIsETH = (toToken == _ETH_ADDRESS_);
        address evmWalletAddress = address(bytes20(recipient));  ///@audit-issue There is no check for this 

        if(!fromIsETH) {
            IERC20(fromToken).transferFrom(msg.sender, address(this), amount);
        }

        uint256 outputAmount;
        if(fromToken == toToken) {
            outputAmount = amount;
        } else {
            outputAmount = _doMixSwap(swapData);
        }

        if(toIsETH) {
            payable(evmWalletAddress).transfer(outputAmount);
        } else {
            IERC20(toToken).transfer(evmWalletAddress, outputAmount);
        }
        
        emit EddyCrossChainReceive(
            externalId,
            fromToken,
            toToken,
            amount,
            outputAmount,
            evmWalletAddress,
            message
        );

        return "";
    }
```

### Internal Pre-conditions

1- GatewaySend.sol is deployed on an EVM-compatible chain.

2- The onCall function is invoked by the trusted ZetaChain gateway (onlyGateway modifier).

3- The message payload received by onCall contains a recipient field whose byte length is not 20 (e.g., 19 bytes or 21 bytes)

### External Pre-conditions

None

### Attack Path

1- Upstream Error: A bug in an upstream contract (e.g., GatewayCrossChain.sol on ZetaChain) or the ZetaChain gateway itself causes a cross-chain message to be generated where the recipient byte array is, for example, 21 bytes long instead of the correct 20 bytes for an EVM address. (e.g., 0x11223344556677889900aabbccddeeff1122334455 instead of 0x11223344556677889900aabbccddeeff11223344).

2- Gateway Relays Message: The ZetaChain gateway, unaware of the malformed recipient length, calls GatewaySend.sol#onCall with this message.

3- Decoding in onCall:
decodePackedMessage(message) extracts the recipient as a 21-byte array.

4- Incorrect Address Conversion:
address evmWalletAddress = address(bytes20(recipient)); is executed. The 21-byte recipient is truncated to its first 20 bytes. The evmWalletAddress now holds an address different from the intended one (e.g., 0x11223344556677889900aabbccddeeff11223344 instead of the one ending in ...334455).

5- Fund Transfer: The contract proceeds to transfer tokens (either ETH via payable(evmWalletAddress).transfer() or ERC20 via IERC20(toToken).transfer()) to this truncated, incorrect evmWalletAddress

### Impact

The user (the intended final recipient of the cross-chain transaction) suffers a permanent loss of the transferred funds. The funds are sent to an incorrect address due to the silent truncation or padding of the recipient bytes. The system does not gain anything; the funds are simply misdirected and lost

### PoC

_No response_

### Mitigation

Add an explicit length check for the recipient byte array in the onCall function before converting it to an address

```solidity
// Inside onCall function, after decodePackedMessage:
(
    bytes32 externalId, 
    uint256 amount, 
    bytes calldata recipient, 
    address fromToken, 
    address toToken, 
    bytes calldata swapData
) = decodePackedMessage(message);

// MITIGATION: Add this check
require(recipient.length == 20, "GatewaySend: Invalid recipient length");

bool fromIsETH = (fromToken == _ETH_ADDRESS_);
// ... rest of the function
address evmWalletAddress = address(bytes20(recipient));
// ...
```
