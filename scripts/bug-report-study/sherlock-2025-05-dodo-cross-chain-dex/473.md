# `withdrawToNativeChain` will break ETH cross-chain swaps for all users via `_doMixSwap's` invalid approve call

### Summary

The `GatewayTransferNative.sol` contract contains a critical bug that prevents all ETH-based cross-chain swaps from executing successfully. When users attempt to swap ETH (represented by a special address like `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`), the `_doMixSwap` function incorrectly attempts to call the `approve()` function on the ETH address, causing the transaction to revert since ETH is not an ERC20 token and doesn't implement the `approve()` function. As a result, ETH swaps, despite being one of the most common transaction types, consistently fail during cross-chain execution.

### Root Cause

**Core Issue:** The root cause lies in the `_doMixSwap()` function within `GatewayCrossChain.sol`. The function unconditionally calls `approve()` on all `fromToken` addresses without checking whether the token is ETH:

[contracts/GatewayTransferNative.sol:_doMixSwap#L434-L435](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L434-L435)
```solidity
function _doMixSwap(bytes memory swapData,  uint256 amount, MixSwapParams memory params ) internal returns (uint256 outputAmount) {
    // @audit This line fails when `params.fromToken` is ETH address
    IZRC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
    
    return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(
        // ... parameters
    );
}
```

[contracts/GatewayTransferNative.sol:withdrawToNativeChain#L555](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L555)

In DODO protocol, ETH is represented by a special address (commonly `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`) which is not a deployable contract address and therefore doesn't implement ERC20 functions like `approve()`.

### ETH Swap Failure - Simplified Call Flow

This issue prevents users from successfully executing ETH swaps through direct cross-chain entry points results in a transaction failure. The following sections break down the simplified call flow for both `withdrawToNativeChain()` and `_doMixSwap`, illustrating where and why the failure occurs. 

```solidity
1. User calls withdrawToNativeChain(receiver, amount, nativeMessage)
   ↓
2. Function decodes message to get messageParams
   ↓    ↓
3. Calls _doMixSwap(params.swapParams)
   ↓
4. _doMixSwap attempts: IZRC20(params.fromToken).approve(DODOApprove, amount)
   ↓
5. REVERT: If params.fromToken == ETH_ADDRESS (no approve function exists)
   ↓
6.TRANSACTION FAILS: User's withdrawal fails completely
```

### Internal Pre-conditions

1. The contract must receive a cross-chain message with swap parameters
2. The `fromToken` parameter must be set to the ETH address (`_ETH_ADDRESS_`)
3. The swap operation must be routed through the `_doMixSwap()` function

### External Pre-conditions

1. User initiates a cross-chain swap with ETH as the source token
2. The cross-chain message is properly formatted and routed to the contract
3. DODO protocol is configured to use the special ETH address for native ETH swaps

### Attack Path

1. User initiates a cross-chain swap sending ETH from another chain (e.g., Ethereum mainnet)
2. The cross-chain message arrives at `GatewayTransferNative.withdrawToNativeChain()`
3. The function decodes the message and identifies it as a swap operation
4. `_doMixSwap()` is called with `params.fromToken = _ETH_ADDRESS_`
5. The function attempts to execute `IZRC20(_ETH_ADDRESS_).approve(DODOApprove, amount)`
6. Since `_ETH_ADDRESS_` is not a contract with an `approve()` function, the call reverts
7. The entire transaction fails, and the user's cross-chain swap is not completed

### Impact

**High Severity** - Complete denial of service for all ETH cross-chain swaps

This high-severity vulnerability causes a complete denial of service for `all ETH cross-chain swaps`, resulting in persistent transaction failures. Since ETH swaps are among the most common operations, the issue significantly disrupts protocol functionality and reliability.

As a result, ETH swaps, despite being one of the most common transaction types, consistently fail during cross-chain execution.

The test works in conjunction with existing successful ERC20 tests (e.g., `test_ZSwap2B`) to demonstrate that:

- **ERC20 tokens work fine** - They have real `approve()` functions

### Mitigation

Implement conditional logic to handle ETH separately from ERC20 tokens:

```solidity
function _doMixSwap(bytes memory swapData,  uint256 amount, MixSwapParams memory params ) internal returns (uint256 outputAmount) {
    if (swapData.length == 0) {
        return amount;
    }
    // @audit Only approve for ERC20 tokens, not ETH
+   if (params.fromToken != _ETH_ADDRESS_) {
        IZRC20(params.fromToken).approve(DODOApprove, amount );
    }
        
    return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(
        params.fromToken,
        params.toToken,
        params.fromTokenAmount,
        params.expReturnAmount,
        params.minReturnAmount,
        params.mixAdapters,
        params.mixPairs,
        params.assetTo,
        params.directions,
        params.moreInfo,
        params.feeData,
        params.deadline
    );
}
```
