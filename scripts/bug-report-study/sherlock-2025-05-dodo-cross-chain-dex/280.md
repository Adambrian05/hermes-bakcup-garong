# Fixed Slippage Setting Leads to User Losses

### Summary

Global slippage configuration will cause economic losses for users as MEV bots will exploit predictable slippage tolerance during cross-chain swaps.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L306-L320

### Root Cause

In `GatewayTransferNative.sol:306-320` the `_swapAndSendERC20Tokens` function uses a global `slippage` variable instead of user-specified slippage, forcing all users to accept the same slippage tolerance regardless of market conditions.

You can find a similar report on [solodit](https://solodit.cyfrin.io/issues/user-may-not-be-able-to-override-slippage-on-destination-spearbit-connext-pdf)


### Internal Pre-conditions

1. Owner needs to call `initialize()` to set global `slippage` value
2. Users need to initiate cross-chain swaps that require token swapping on destination chain

### External Pre-conditions

1. Market volatility needs to create arbitrage opportunities
2. MEV bots need to monitor the contract for predictable slippage patterns

### Attack Path

1. User initiates cross-chain swap via `withdrawToNativeChain()`
2. Contract calls `_handleEvmOrSolanaWithdraw()` which triggers `_swapAndSendERC20Tokens()`
3. Function uses global slippage: `uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000`
4. MEV bot frontruns the swap knowing exact slippage tolerance
5. Bot sandwiches the transaction, extracting value from predictable slippage bounds

### Impact

Users suffer approximate losses of 0.5-5% (depending on global slippage setting) per swap due to MEV extraction and inability to set appropriate slippage for market conditions.

_No response_

### Mitigation

Allow users to specify their own slippage tolerance in the message data instead of using a global slippage variable.
