# Attacker will steal funds from users with non-EVM refunds

### Summary

Flawed access control logic in claimRefund will cause a loss of funds for users awaiting non-EVM refunds as an attacker will call claimRefund for a non-EVM refund, bypass the authorization check due to receiver being incorrectly set to msg.sender, and receive the funds

### Root Cause

In [claimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574-L578) function the receiver address is not correctly determined for non-EVM refunds if refundInfo.walletAddress.length is not 20. This causes the access control condition msg.sender == receiver within the require statement at L578 to become msg.sender == msg.sender when bots[msg.sender] is false, which is always true, thus bypassing the intended access control for non-EVM refunds

```solidity
 function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");      ///@audit-issue this check is always true 
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];        

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }

    receive() external payable {}

    fallback() external payable {}
}
```

### Internal Pre-conditions

1- A RefundInfo entry exists in the refundInfos mapping for a specific externalId, where refundInfos[externalId].walletAddress.length is not equal to 20 (indicating the refund is intended for a non-EVM address)

2- The externalId for this specific non-EVM refund is known to the attacker

3- The attacker's address (msg.sender) is not registered as a bot (i.e., bots[msg.sender] evaluates to false)

### External Pre-conditions

None

### Attack Path

1- A legitimate cross-chain operation fails, or another condition triggers a refund. A refund entry is created and stored in refundInfos with a unique externalId. This entry specifies refundInfo.token (the token to be refunded), refundInfo.amount (the amount to be refunded), and refundInfo.walletAddress (the intended recipient's address, which in this case is a non-EVM address, so refundInfo.walletAddress.length != 20).

2- An attacker, who is not a whitelisted bot, learns or guesses the externalId corresponding to this pending non-EVM refund.

3- The attacker calls the claimRefund(externalId) function.

4- Inside the claimRefund function: a. RefundInfo storage refundInfo = refundInfos[externalId]; loads the refund details. b. address receiver = msg.sender; initializes receiver to the attacker's address. c. The condition if(refundInfo.walletAddress.length == 20) evaluates to false because the refund is for a non-EVM address. d. Consequently, receiver remains set to msg.sender (the attacker's address). e. The access control check require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER"); is evaluated. Since bots[msg.sender] is false (attacker is not a bot) and receiver is equal to msg.sender, the condition becomes require(false || true, "INVALID_CALLER"), which passes.

5- TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount); is executed, transferring the refundInfo.amount of refundInfo.token to the receiver (which is the attacker's address).

6- The attacker successfully steals the funds that were intended for the user with the non-EVM address.

7- delete refundInfos[externalId]; removes the refund entry, preventing the legitimate user or a bot from claiming it later.

### Impact

The users whose refunds were intended for non-EVM addresses will suffer a complete loss of their refundable amount. The attacker gains these funds directly

### Mitigation

This proposed fix correctly addresses the vulnerability by ensuring that for non-EVM addresses, only whitelisted bots can claim the refund. The bot would then be responsible for handling the refund process on the respective non-EVM chain 

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST"); 

    address receiver; // Changed from 'address payable' as token transfers don't require payable
    bool isEVM = refundInfo.walletAddress.length == 20;

    if (isEVM) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    } else {
        // For non-EVM refunds, only whitelisted bots can claim.
        // The bot is responsible for handling the refund on the other chain.
        require(bots[msg.sender], "ONLY_BOT_CAN_CLAIM_NON_EVM");
        receiver = msg.sender; // Bot receives funds (on this EVM chain) to handle off-chain
    }

    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];
    
    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender) // Logs who initiated the claim on-chain
    );
}
```
