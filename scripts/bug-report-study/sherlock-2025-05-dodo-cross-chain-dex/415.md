# Fee Deduction Does Not Reflect in `msg.value`, Causes Overdraw or Incorrect Swap for ETH

### Summary

In `withdrawToNativeChain`, the amount passed to `_doMixSwap `is reduced by the platform fee. However, `msg.value` is not updated accordingly. For ETH swaps, this results in the DODO Router receiving the original `msg.value`, not accounting for fee deductions.

### Root Cause

The root issue lies in the mismatch between how fee deductions are handled for ERC-20 tokens versus ETH (native token). In `withdrawToNativeChain`, after calculating and deducting `platformFeesForTx `from `amount`, the contract updates the `amount `variable used for swaps. However, this deduction is not reflected in `msg.value`, which remains equal to the original `amount` provided by the user.

This becomes problematic in `_doMixSwap`, where the DODO router's `mixSwap` function is invoked using the unadjusted `msg.value`. When `fromToken `is ETH (i.e., `_ETH_ADDRESS_`), the router expects `msg.value` to match the intended swap input, but the contract has already reduced the swap amount internally. ### Attack Path

- User sends ETH with `msg.value == amount`.
- Fee is deducted internally, reducing `amount`.
- `msg.value` is passed unchanged to `mixSwap`, which uses it as the full input.
- Swap is attempted with a higher-than-available value or without intended fee deduction.

### Impact

Transaction will revert due to insufficient ETH balance (if `msg.value == amount` and fee is deducted).

### Mitigation

Update `msg.value` passed to `mixSwap `by subtracting the deducted fee amount if ETH is the `fromToken`.
```solidity
uint256 adjustedMsgValue = msg.value;
if (zrc20 == _ETH_ADDRESS_) {
    adjustedMsgValue -= platformFeesForTx;
}

outputAmount = IDODORouteProxy(DODORouteProxy).mixSwap{value: adjustedMsgValue}(...);

```
