# Incorrect Gas Fee Handling for Bitcoin Withdrawals

## Summary
The [_handleBitcoinWithdraw](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L363-L377) function in the `GatewayCrossChain` contract mishandles gas fees for Bitcoin withdrawals. It approves the gateway to spend `outputAmount + gasFee` but passes `outputAmount - gasFee` to the `withdraw` function, leading to the receiver getting less than intended and potentially insufficient gas fees for the Bitcoin transaction.

## Finding Description
The `_handleBitcoinWithdraw` function is responsible for processing Bitcoin withdrawals in the `GatewayCrossChain` contract. It interacts with a ZRC20 token contract and a gateway (assumed to be `GatewayZEVM`) to facilitate the withdrawal process. The function takes several parameters, including `outputAmount` (the amount to be withdrawn to the Bitcoin network) and `gasFee` (the fee to cover the Bitcoin transaction costs).

The issue arises in how the function handles these two values:
1. **Approval Step**: The function calls `IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee)`, approving the gateway to spend a total amount that includes both the withdrawal amount (`outputAmount`) and the gas fee (`gasFee`). This suggests that the contract intends for the gateway to manage both the amount sent to the receiver and the transaction fee on the Bitcoin network.
2. **Withdrawal Step**: However, when invoking the `withdraw` function, it passes `outputAmount - gasFee` as the withdrawal amount: `withdraw(externalId, decoded.receiver, decoded.targetZRC20, outputAmount - gasFee)`. This means the gateway is instructed to withdraw an amount that has already had the gas fee subtracted.

This behavior is inconsistent with standard cross-chain bridge operations, such as those seen in systems like ZetaChain. Typically, a bridge contract approves a total amount (`outputAmount + gasFee`) to the gateway, and the gateway then deducts the gas fee internally, ensuring the receiver gets the full `outputAmount` while the fee covers the destination chain's transaction costs. By subtracting the `gasFee` before calling `withdraw`, the contract:
- Reduces the amount received by the end user on the Bitcoin network below the intended `outputAmount`.
- Risks providing insufficient funds to cover the Bitcoin transaction fee, as the gateway receives less than the approved total.

This discrepancy between the approval and withdrawal amounts indicates a logical error in the gas fee handling, undermining the reliability of the withdrawal process.

## Example
Consider a scenario where a user initiates a Bitcoin withdrawal through the gateway:
- **Input**: The user specifies `outputAmount = 1 BTC` (intended amount for the receiver) and `gasFee = 0.001 BTC` (estimated Bitcoin network fee).
- **Approval**: The function approves the gateway to spend `1 + 0.001 = 1.001 BTC` of the ZRC20 token.
- **Withdrawal**: The function calls `withdraw` with `1 - 0.001 = 0.999 BTC`.
- **Outcome**:
  - The receiver on the Bitcoin network receives only `0.999 BTC`, short of the intended `1 BTC`.
  - The gateway, having been approved for `1.001 BTC` but instructed to withdraw `0.999 BTC`, may lack the additional `0.001 BTC` needed to pay the Bitcoin network fee, depending on its internal logic.

This mismatch results in a financial loss for the user and potential transaction failure on the Bitcoin network.

## Impact
This issue has significant consequences:
- **Financial Loss**: Users receive less than the intended withdrawal amount (e.g., `0.999 BTC` instead of `1 BTC`), leading to unexpected shortfalls.
- **Transaction Failures**: If the gateway relies on the withdrawn amount to cover both the receiver’s funds and the gas fee, passing `outputAmount - gasFee` may leave insufficient funds for the Bitcoin transaction fee, causing the transaction to fail or funds to become stuck.
- **User Trust**: Inconsistent and unreliable withdrawal amounts erode confidence in the cross-chain bridge, potentially driving users away.

## Proof of Concept
To demonstrate this issue:
1. Deploy mock contracts for `GatewayZEVM` and `IZRC20` in a test environment.
2. Configure `_handleBitcoinWithdraw` with:
   - `outputAmount = 1e8` satoshis (1 BTC).
   - `gasFee = 1e5` satoshis (0.001 BTC).
3. Execute the function and observe:
   - Approval: `IZRC20.approve` is called with `1e8 + 1e5 = 100100000` satoshis.
   - Withdrawal: `withdraw` is called with `1e8 - 1e5 = 99900000` satoshis.
4. Result: The receiver gets `0.999 BTC` instead of `1 BTC`, and the gateway may lack funds to cover the `0.001 BTC` fee.

## Recommendation
Modify the `_handleBitcoinWithdraw` function to pass the full `outputAmount` to the `withdraw` function, allowing the gateway to handle gas fee deduction internally, consistent with standard bridge practices. Here’s the corrected implementation:

```solidity
function _handleBitcoinWithdraw(bytes32 externalId, DecodedMessage memory decoded, uint256 outputAmount, uint256 gasFee) internal {
    if (gasFee >= outputAmount) revert NotEnoughToPayGasFee();
    IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);
    withdraw(externalId, decoded.receiver, decoded.targetZRC20, outputAmount);
}
```

Additionally, verify the `GatewayZEVM` contract’s behavior to ensure it deducts the `gasFee` from the approved total and sends the full `outputAmount` to the receiver on the Bitcoin network.
