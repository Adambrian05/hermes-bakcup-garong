# Unauthorized Refund Claims for Non-EVM Addresses

### Summary

Missing access control validation will cause a complete loss of refund funds for users with non-EVM addresses as any attacker will monitor refund events and immediately claim the funds intended for Bitcoin/Solana users.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680

### Root Cause

In `GatewayTransferNative.sol:claimRefund` the access control logic incorrectly allows `msg.sender` to remain as the receiver when `walletAddress.length != 20`, making the require statement `require(bots[msg.sender] || msg.sender == msg.sender)` always pass since `msg.sender == msg.sender` is always true.


### Internal Pre-conditions

1. A refund needs to be created for a non-EVM address (walletAddress.length != 20)
2. The refund must be stored in the `refundInfos` mapping via `onRevert()` or `onAbort()`

### External Pre-conditions

None

### Attack Path

1. Attacker monitors `EddyCrossChainRefund` events for refunds with non-20-byte wallet addresses
2. Attacker calls `claimRefund(externalId)` with the observed external ID
3. The function sets `receiver = msg.sender` since `walletAddress.length != 20`
4. The require check passes because `msg.sender == msg.sender` is always true
5. Attacker receives the refund tokens intended for the legitimate user


### Impact

The legitimate users with non-EVM addresses (Bitcoin/Solana) suffer a complete loss of their refund amounts. The attacker gains the full refund value with no cost except gas fees.

### PoC

_No response_

### Mitigation

Implement proper access control separation for EVM vs non-EVM addresses
