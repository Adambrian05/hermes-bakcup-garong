# A reverted bridge transaction will cause a denial of service for future USDT deposits as the contract does not reset allowance to zero.

### Summary

The lack of allowance reset in `_handleERC20Deposit `will cause a denial of service for users bridging USDT as USDT requires allowance to be set to zero before updating, and a reverted bridge transaction will leave a nonzero allowance, blocking subsequent deposits.

### Root Cause

In `GatewaySend.sol`, the `_handleERC20Deposit `function calls `IERC20(asset).approve(address(gateway), amount) `directly before initiating the cross-chain deposit. If the bridge transaction reverts after this approval but before the allowance is spent, the contract is left with a nonzero allowance for the gateway. For tokens like USDT on Ethereum mainnet, which require the allowance to be set to zero before updating it to a new value, this leftover approval will cause all subsequent calls to approve with a nonzero value to revert. As a result, users will be unable to bridge USDT (or similar tokens) until the allowance is manually reset to zero, leading to a denial of service for those assets.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L177-L193

The same issue exists in the `TransferHelper.sol`, where `safeApprove `also directly sets the approval to a nonzero value without first resetting it to zero. As a result, both patterns are incompatible with non-standard ERC20 tokens like USDT and will cause a denial of service for those assets

### Internal Pre-conditions

1. User calls `depositAndCall `with USDT as the asset.
2. The bridge transaction reverts after approval but before allowance is spent.
3. The contract now has a nonzero allowance for the gateway.

### External Pre-conditions

USDT (or any ERC20 with non-standard approval mechanics) is used as the asset.

### Attack Path

1. User calls `depositAndCall `with USDT, approval is set, but the bridge transaction reverts.
2. User (or another user) tries to call `depositAndCall `again with USDT.
3. The approval call reverts, causing a denial of service for USDT deposits.

### Impact

Users cannot bridge USDT (or similar tokens) after a reverted transaction, resulting in a denial of service for those tokens.

### PoC

_No response_

### Mitigation

Before setting a new approval, always reset allowance to zero if it is nonzero:

```solidity
if (IERC20(asset).allowance(address(this), address(gateway)) > 0) {
    IERC20(asset).approve(address(gateway), 0);
}
IERC20(asset).approve(address(gateway), amount);
```

Alternatively, use OpenZeppelin’s SafeERC20.safeApprove with the same zero-reset logic.
