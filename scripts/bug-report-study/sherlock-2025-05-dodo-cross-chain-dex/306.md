# Funds can be stolen by any attacker when user uses a cross-chain payload with a non-20-byte “receiver.”

### Summary

Both `GatewayCrossChain.sol` and `GatewayTransferNative.sol` assume that the `revertMessage` they receive is exactly 52 bytes `(32 bytes externalId + 20 bytes user address)`. However, there is no check enforcing this length. If any user supplies a “receiver” field of length ≠ 20 bytes (for instance, 21 bytes). When a cross-chain withdraw fails, the contract stores that malformed 21-byte payload as `walletAddress`, then `claimRefund(...)` will let any caller receive the funds because `walletAddress.length != 20` causes `receiver` to default to `msg.sender`. In other words, a single off-by-one in the ABI-encoded “receiver” allows anyone to drain the refund.

### Root Cause

In `GatewayCrossChain.onAbort`(AbortContext calldata abortContext):  

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L550


```Solidity
    function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }
```
There is no “require(revertMessage.length == 52)” here

So, it always goes to “store for manual claim” if length != 52
Later, in `claimRefund(bytes32 externalId)`:  

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571

```Solidity
    function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```
Because there is no check that `walletAddress.length == 20`,  any time `onAbort` stored a non-20-byte `walletAddress`, `claimRefund` function will allow any `msg.sender` to claim the funds.

In practice this means any caller can invoke `claimRefund(externalId)` and receive the tokens for themselves whenever the stored `walletAddress` is not exactly 20 bytes.



### Internal Pre-conditions

User sends a `payload` whose encoded “receiver” section isn’t exactly 20 bytes in `depositAndCall`

### External Pre-conditions

NA

### Attack Path

1. User sends a wrong receiver address in the payload of `depositAndCall` ex, 21 bytes instead of 20. They pack the rest of the swap instructions normally, but put receiverLen = 21 and append 21 bytes of data. So, `decodeMessage` on Zeta reads `receiverLen` = 21, it stores a 21-byte `decoded.receiver`.

2.  ZetaChain executes `GatewayCrossChain.onCall`
`decodeMessage(...)` returns `decoded.receiver = 21 bytes`.
The DODO swap succeeds and the contract calls `withdrawAndCall`

3. “Withdraw to Ethereum” fails. For whatever reason, the cross-chain withdraw reverts.
Zeta automatically invokes ex: 
```Solidity
GatewayCrossChain.onAbort(
  revertMessage = externalId (32 bytes) ‖ decoded.receiver (21 bytes),
  asset         = WETH-ZRC20,
  amount        = 0.05 WETH
);
```
In `onAbort`, no length check → walletAddress = revertMessage[32:] (21 bytes).

The contract does ex:
```Solidity
refundInfos[externalId] = {
  externalId:    externalId,
  token:         WETH-ZRC20,
  amount:        0.05 WETH,
  walletAddress: <21 bytes>
}
```

4. Attacker (or anyone) calls
```Solidity
GatewayCrossChain.claimRefund(externalId);
```
Inside `claimRefund`, because `walletAddress.length == 21 ≠ 20`, the code sets `receiver = msg.sender`.

The require `bots[msg.sender] || msg.sender == receiver` passes (since `receiver == msg.sender`).

The contract transfers the 0.05 WETH to the caller, draining the refund.


5. The attacker (or any front-runner) walks away with the entire 0.05 WETH because supplying a 21‐byte “receiver” bypassed the intended 20-byte check.

### Impact

Any user whose “receiver” field is mis-encoded will expose their refund to immediate theft. 
Instead of safely refunding only to the original user, the contract opens a public bounty of refund tokens.

### Mitigation

In `claimRefund(...)` :
When reading `refundInfo.walletAddress`, enforce:

```Solidity
require(refundInfo.walletAddress.length == 20, "MALFORMED_WALLET_ADDRESS"); //add this
address receiver = address(uint160(bytes20(refundInfo.walletAddress)));
require(
  msg.sender == receiver || bots[msg.sender],
  "NOT_AUTHORIZED"
);
```
