# Multi-account will lead to Incorrect isWritable bool parsing in AccountEncoder Library

### Summary

Incorrect byte reading in `AccountEncoder.decompressAccounts()` will cause incorrect account permission parsing for Solana integrations as users submitting multi-account transactions will have their read-only accounts incorrectly flagged as writable due to the function reading 32 bytes instead of 1 byte for boolean fields.

### Root Cause

In [`contracts/libraries/AccountEncoder.sol:44-45`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L44-L45) the `mload(ptr)` instruction reads 32 bytes for a boolean field that should only be 1 byte, causing it to read into subsequent account data and return incorrect permission flags.

### Internal Pre-conditions

1. User needs to submit a Solana transaction with at least 2 accounts in the compressed account data
2. First account needs to have `isWritable = false` (read-only permission)
3. Second account needs to have a non-zero public key (typical scenario)
4. The transaction needs to go through the cross-chain pipeline that uses `AccountEncoder.decompressAccounts()`

### External Pre-conditions

1. No external pre-conditions required - this is an internal parsing bug

### Attack Path

1. **User calls a cross-chain function** that involves Solana with multiple accounts, where the first account should be read-only
2. **The system calls `AccountEncoder.decompressAccounts()`** to parse the compressed account data
3. **The function incorrectly reads 32 bytes** starting from the first account's `isWritable` field, which includes the first 31 bytes of the second account's public key
4. **Since the second account's public key is non-zero**, the entire 32-byte value becomes non-zero
5. **The `iszero(iszero(non_zero_value))` returns `true`** instead of the correct `false` value
6. **The first account is incorrectly flagged as writable** when it should be read-only

### Impact

The protocol suffers from incorrect Solana account permission interpretation, which can cause Solana program calls to fail or behave unexpectedly. This affects the reliability of cross-chain operations involving Solana and may lead to failed transactions or incorrect program execution.

### PoC

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.7;

import "forge-std/Test.sol";
import {Account as SolanaAccount, AccountEncoder} from "../contracts/libraries/AccountEncoder.sol";

contract AccountEncoderBugPoC is Test {
    function testMultiAccountPermissionBug() public {
        // Create test data with 2 accounts
        bytes32 pubkey1 = keccak256("readonly_account");
        uint8 isWritable1 = 0; // Should be FALSE (read-only)
        
        bytes32 pubkey2 = keccak256("writable_account"); 
        uint8 isWritable2 = 1; // Should be TRUE (writable)
        
        bytes memory testData = abi.encodePacked(
            uint16(2),      // Account count
            pubkey1,        // First account pubkey
            isWritable1,    // First account: isWritable = FALSE
            pubkey2,        // Second account pubkey (non-zero!)
            isWritable2     // Second account: isWritable = TRUE
        );
        
        // Parse using vulnerable function
        SolanaAccount[] memory accounts = AccountEncoder.decompressAccounts(testData);
        
        // Demonstrate the bug
        console.log("Expected - Account 1 isWritable: false");
        console.log("Actual   - Account 1 isWritable:", accounts[0].isWritable);
        
        // Bug: First account should be false but returns true
        assertEq(accounts[0].isWritable, true, "BUG: readonly account parsed as writable");
        assertEq(accounts[1].isWritable, true, "Second account correctly parsed as writable");
    }
    
    function testSingleAccountWorksCorrectly() public {
        // Single account should work correctly (no bug)
        bytes32 pubkey = keccak256("single_readonly");
        uint8 isWritable = 0; // FALSE
        
        bytes memory testData = abi.encodePacked(
            uint16(1),
            pubkey,
            isWritable
        );
        
        SolanaAccount[] memory accounts = AccountEncoder.decompressAccounts(testData);
        
        // Single account parses correctly
        assertEq(accounts[0].isWritable, false, "Single account should parse correctly");
    }
}
```

### Mitigation

Fix the boolean parsing by masking to only read the first byte:

```solidity
// Current vulnerable code:
mstore(add(acc, 32), iszero(iszero(mload(ptr))))

// Recommended fix:
mstore(add(acc, 32), iszero(iszero(and(mload(ptr), 0xff))))
```

Both solutions ensure only the actual boolean value (first byte) is considered, preventing contamination from subsequent account data.
