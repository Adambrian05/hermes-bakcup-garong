# Approve() Usage Without Resetting to Zero Can Cause Transaction Failures with USDT-like Tokens

### Summary

The contract calls approve() on ERC20 tokens before performing swaps, without resetting the approval allowance to zero first. This usage pattern is incompatible with some widely-used tokens, such as USDT (Tether), which revert the transaction if approve() is called when the current allowance is non-zero and different from the new value.

Because the project targets multiple EVM-compatible chains including Ethereum, Polygon, Arbitrum, Base, BNB Chain, and ZetaChain, this bug can cause critical transaction failures across all supported chains for tokens that follow this non-standard approve behavior.



### Root Cause

In the internal function _doMixSwap the call IZRC20(params.fromToken).approve(DODOApprove, amount); directly sets approval without resetting the allowance to zero, which fails on tokens like USDT that require allowance to be zero before changing it.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L346

### Internal Pre-conditions

The contract must hold an existing non-zero allowance for DODOApprove spender on the fromToken.

The token must implement the “non-standard” approve logic (e.g., USDT) that reverts if allowance is not zero before setting a new value.



### External Pre-conditions

The user must attempt to perform a swap involving a USDT-like token or any token with similar approve logic.

The contract is deployed on chains where such tokens exist (Ethereum, Polygon, Arbitrum, Base, BNB Chain, ZetaChain).

### Attack Path

Contract calls approve(DODOApprove, amount) on a token with a non-zero current allowance.

Token’s approve() function reverts because allowance is non-zero and differs from the new amount.

The swap transaction reverts, causing failed token transfers and failed user operations.



### Impact

Users attempting swaps with USDT-like tokens will experience failed transactions, leading to poor user experience and lost gas fees. This affects all users interacting with the contract on supported chains and can block critical cross-chain token swaps.

### Mitigation

Modify the approval logic to reset allowance to zero before setting a new amount, for example:

uint256 currentAllowance = token.allowance(address(this), spender);
if (currentAllowance != 0) {
    token.approve(spender, 0);
}
token.approve(spender, newAmount);
