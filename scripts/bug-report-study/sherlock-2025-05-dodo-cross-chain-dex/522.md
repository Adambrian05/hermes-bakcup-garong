# A malicious user can steal funds of other users in the contract GatewayTransferNative.sol

### Summary

A malicious user can easily observe the zetachain mempool wait for a fail transaction to occur that will hit the function onRevert now when the context.revertMessage.length is not == 52 the failed transaction info + amount will be added to refundInfos mapping - refundInfos[externalId] = refundInfo;, - context on when this happens - ( if a solana cross chain transaction is failed this will occur as they are 32-byte addresses so 32bytes + 32bytes(externalid) length = 64, there can be more reasons for this too but this is a context that funds will be present in this contract) now when the malicious user sees funds present in the contract they can call the public function withdraw put parameter values to pass checks put there own address to transfer whatever amount + token the failed transaction had and steal the funds of the innocent users

### Root Cause

the root cause of this is - 
the lack of checks present in the function withdraw- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286-L304


### Internal Pre-conditions

none 

### External Pre-conditions

a transaction should fail and context.revertMessage.length is not == 52 (explained above when this will happen)
and gateway as designed will call the function onRevert

### Attack Path

for this attack lets assume a malicious user named alice and a innocent user named bob - 
1) Bob transferred any solana supported asset to his solana chain address using the function withdrawToNativeChain -
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530 
 - list of assets supported https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets 
(note length of revert msg will be greater then 52 as explained above)
2) bob transaction failed for some reason - (could be any reason for this -  Invalid or Incomplete Message Data Chain Congestion or Timeouts or anything at all)
3) alice- malicious user monitoring the mempool sees a onrevert transaction hitting the onrevert with msg.length > 52 
4) alice waits for the transaction to finish frontruns everyone(even bob) call the function withdraw - https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286
5) alice put passing parameters that pass all the checks + her own address to steal lets assume bob failed transaction was worth 10k usd
  example of passing parameters - 

```solidity
function withdraw(
        bytes32 externalId, 
        bytes memory sender,
        address outputToken,
        uint256 amount
    ) public {
        gateway.withdraw(
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                revertMessage: bytes.concat(externalId, bytes20(sender)),
                onRevertGasLimit: gasLimit
            })
        );
    }
```
for example in this
externalid == it can be any value lets take 5 for eg(take 5 has not been used too) the logic behind this arbitary is that this doesnt matter as its check are already passed before and this is a late entry in this public function
sender == alice address where they want there funds
output token == token which bob deposited
amount == the amount of transaction that failed( actually a little less as in gateway.withdraw it takes gas fee then amount so leave space for gas)
now when this calls the function gateway.withdraw
every check will pass and the transaction will go through without any problem  
```solidity
/// @notice Withdraw ZRC20 tokens to an external chain.
    /// @param receiver The receiver address on the external chain.
    /// @param amount The amount of tokens to withdraw.
    /// @param zrc20 The address of the ZRC20 token.
    /// @param revertOptions Revert options.
    function withdraw(
        bytes memory receiver,
        uint256 amount,
        address zrc20,
        RevertOptions calldata revertOptions
    )
        external
        whenNotPaused
    {
        if (receiver.length == 0) revert ZeroAddress();
        if (amount == 0) revert InsufficientZRC20Amount();
        if (revertOptions.revertMessage.length > MAX_MESSAGE_SIZE) revert MessageSizeExceeded();

        uint256 gasFee = _withdrawZRC20(amount, zrc20);
        emit Withdrawn(
            msg.sender,
            0,
            receiver,
            zrc20,
            amount,
            gasFee,
            IZRC20(zrc20).PROTOCOL_FLAT_FEE(),
            "",
            CallOptions({ gasLimit: IZRC20(zrc20).GAS_LIMIT(), isArbitraryCall: true }),
            revertOptions
        );
    }

```
this will pass and transfer the funds to allice address(note even if for some reason alice cross chain transaction fails after this above transaction which is highly unlikely but now the externalid params will be of alice and the funds can be claimed by alice now)



### Impact

Big loss of funds for users whose transactions have failed
a malicious user can keep repeating this attack over and over again and steal all the claim funds of other users
