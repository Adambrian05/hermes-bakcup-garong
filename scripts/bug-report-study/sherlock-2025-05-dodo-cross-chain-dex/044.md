# The fromTokenAmount assembled for cross-chain _doMixSwap()  does not match the actual fund amount.


## Summary
In _doMixSwap(), the fromTokenAmount parameter is preset by the user, while the actual funds used for the swap are dynamically changing. The issue lies in not resetting params.fromTokenAmount to align it with the actual funds.


## Root Cause
The root issue is that when preparing data for mixSwap after cross-chain operations, params.fromTokenAmount was not reset to match the actual funds.  

Here’s a detailed scenario analysis using GatewayTransferNative::withdrawToNativeChain(), followed by the execution of GatewaySend::onCall() on the Ethereum chain, which internally includes _doMixSwap().

Let's continue the explanation using the simpler scenario in `_handleEvmOrSolanaWithdraw()` where `decoded.targetZRC20 == gasZRC20`, assuming `targetZRC20` is `ETH.ETH`.  

In this case, the actual amount of ETH transferred to the Ethereum chain is `outputAmount - gasFee`, where `gasFee` also fluctuates in real time.  

However, when performing `mixSwap` on the Ethereum chain, all required parameters come from `decoded.swapDataB`, which was cross-chain forwarded via `_handleEvmOrSolanaWithdraw()`. The issue arises because `_handleEvmOrSolanaWithdraw()` does not update `decoded.swapDataB.fromTokenAmount`, causing `fromTokenAmount` to no longer match `outputAmount - gasFee`.

Assuming the final desired token is TokenX (not ETH), the system will use the parameter `swapDataB` to execute `_doMixSwap()` and obtain TokenX.  

Here, three possible outcomes may occur:  

1. **If `fromTokenAmount > outputAmount - gasFee`**:  
   - The `_doMixSwap()` call in the cross-chain `onCall()` will **revert** due to insufficient funds.  

2. **If `fromTokenAmount == outputAmount - gasFee`**:  
   - The `_doMixSwap()` executes normally, but since both `outputAmount` and `gasFee` fluctuate in real time, this scenario is **almost impossible** to achieve predictably.  

3. **If `fromTokenAmount < outputAmount - gasFee`**:  
   - Excess funds remain stuck in the contract, resulting in **permanent loss for the user**.  

The same issue occurs in the `else` branch of `_handleEvmOrSolanaWithdraw()`, because `_swapAndSendERC20Tokens()` does not guarantee a deterministic amount of `targetZRC20` to be swapped—it depends on real-time market conditions.  


The issue is not due to user input parameter errors, but rather the system's use of incorrect data, which prevents users from entering appropriate parameters.

## Impact
This could lead to user fund losses or cause `_doMixSwap()` to revert, resulting in system functionality becoming unavailable.

## PoC
Taking USDC.ETH withdrawal to Ethereum chain to obtain Token X as an example for PoC explanation.  

Assume withdrawing 1000e6 USDC.ETH, user estimates ETH gas will consume 10e6 USDC.ETH:  

1. USDC.ETH amount is 1000e6, fromTokenAmount is set to 990e6  
2. ETH price fluctuates, Ethereum chain gas fees also fluctuate. Assume _swapAndSendERC20Tokens() actually consumes 5e6 USDC.ETH:  
   2.1 _doMixSwap() executes swap with 990e6, resulting in 5e6 USDC remaining in the contract on Ethereum chain  
3. Assume _swapAndSendERC20Tokens() actually consumes 11e6 USDC.ETH:  
   3.1 _doMixSwap() executes swap with 990e6, but contract only has 989e6 USDC, causing _doMixSwap() execution failure

## Mitigation
When rebuilding the output message, update `fromTokenAmount` to make it equal to `outputAmount - gasFee`.
