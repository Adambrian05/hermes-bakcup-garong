Handsome Emerald Tapir

Medium

# attacker might create a dummy `targetZRC20/gasZRC20` pair without enough liquidity, causing `targetZRC20 => gasZRC20` swaps to fail

### Summary
`_existsPairPool` function only checks if a pool exists by verifying that both tokens have a balance greater than 0 in the pair, but doesn't validate sufficient liquidity. This allows attackers to create malicious pairs with minimal liquidity (1 wei), causing legitimate swaps to fail when the contract attempts to swap `targetZRC20` to `gasZRC20` for gas fees.

### Root Cause
`_existsPairPool` checks whether a pool exists for `targetZrc20` and `gasZrc20`, it does so by checking if balance of pair is more than 0:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L216-L229
```solidity
    function _existsPairPool(
        address uniswapV2Factory,
        address zrc20A,
        address zrc20B
    ) internal view returns (bool) {
        address uniswapPool = uniswapv2PairFor(
            uniswapV2Factory,
            zrc20A,
            zrc20B
        );
        return
            //@audit if either has a balance > 0, return true
            IZRC20(zrc20A).balanceOf(uniswapPool) > 0 &&
            IZRC20(zrc20B).balanceOf(uniswapPool) > 0;
  }
```
If the pool exists (i.e., both tokens have > 0 balance), it returns `true` and the swap path will be a direct path of `[targetZrc20, gasZrc20]`:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L231-L251
```solidity
     if (existsPairPool) {
            path = new address[](2);
            path[0] = zrc20;
            path[1] = targetZRC20;
```
Later, this path will be used to swap the `targetZrc20` to `gasZrc20`:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L313-L330
```solidity
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            //@audit this returns the malicious path
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );
        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);
        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE
        );
```
The problem is that anyone can create a `targetZrc20/gasZrc20` pair and fund it with as little as 1 wei of either token, and this swap will fail because there are not enough assets to satisfy the `gasFee` requirement.

### Internal Pre-conditions
- `targetZRC20 != gasZrc20`

### External Pre-conditions
- `targetZRC20/gasZRC20` pair does not exist
- `targetZRC20/gasZRC20` exists but does not have enough liquidity
- Attacker creates a malicious `targetZRC20/gasZRC20` pair and funds it with a very small amount of both tokens

### Attack Path
1. Alice tries to deposit 100 USDT from ethereum into zetachain and then arbitrum
2. Since USDT is not the gasZRC20, a swap is initiated to swap a portion of USDT into gasZRC20
3. USDT/gasZRC20 doesn't exist, so an attacker creates a malicious pair with 1 unit of USDT and 1 wei of gasZRC20
4. Alice's CCTX fails because `swapTokensForExactTokens` attempts to swap through a pair that doesn't have enough liquidity

### Impact
- User CCTX failure
- User loss of funds because they pay for gas

### PoC
*No response*

### Mitigation
Add more checks to ensure that the pair has enough liquidity of both tokens (or the gasZRC20 token).
