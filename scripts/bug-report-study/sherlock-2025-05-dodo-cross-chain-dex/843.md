# Inability to Collect Fees for Native Coin Transfers Leading to DoS and Revenue Loss

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L341


https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L551


#### Summary
The `_handleFeeTransfer` function attempts to collect platform fees using `TransferHelper.safeTransfer`. However, if the `zrc20` parameter represents the native coin (indicated by `_ETH_ADDRESS_`), `safeTransfer` will attempt to call a non-existent `transfer` function on the native coin's address, leading to a transaction revert. This prevents the protocol from collecting fees on native coin transfers and causes a denial of service for such transactions.

---

#### Root Cause
The `_handleFeeTransfer` function (`L354-L357`) is designed to transfer fees using `TransferHelper.safeTransfer`.

```solidity
// File: GatewayTransferNative.sol
function _handleFeeTransfer(
    address zrc20, // Can be _ETH_ADDRESS_
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
    TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx); // L357
}
```
In `GatewayTransferNative::withdrawToNativeChain`, the `zrc20` parameter can be `_ETH_ADDRESS_` (`L364`), which typically represents the native coin where the contract is deployed (handled via `msg.value` as a native transfer).

```solidity
// File: GatewayTransferNative.sol
function withdrawToNativeChain(
    address zrc20, // Can be _ETH_ADDRESS_ (native coin address)
    uint256 amount,
    bytes calldata message
) external payable {
    if(zrc20 != _ETH_ADDRESS_) { // L365
        require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
    }
    // ...
    uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // L380
    // ...
}
```
When `_handleFeeTransfer` is invoked with `zrc20 = _ETH_ADDRESS_`, `TransferHelper.safeTransfer` is called with `_ETH_ADDRESS_` as the token. Standard `TransferHelper` implementations for ERC20 tokens internally attempt to call `IERC20(token).transfer(recipient, amount)`. Since `_ETH_ADDRESS_` (representing the native coin) is not a smart contract and does not implement the `transfer` ERC20 interface, this call will inevitably revert, causing the entire `withdrawToNativeChain` transaction to fail.

---

#### Internal Pre-conditions
None.

---

#### External Pre-conditions
A **user** attempts to initiate a cross-chain transfer or swap where the input token is the native coin, through the `withdrawToNativeChain` function.

---

#### Attack Path / Scenario
1.  A **user** calls the **`GatewayTransferNative::withdrawToNativeChain`** function (`L364`) with the intent to transfer the native coin:
    * **`zrc20`**: Set to `_ETH_ADDRESS_`.
    * **`amount`**: The amount of the native coin the user wants to transfer.
    * **`msg.value`**: Equal to `amount` (the native coin being sent, which is implicitly deposited into the contract).
    * **`message`**: A valid message for the intended cross-chain operation.

    ```solidity
    // File: GatewayTransferNative.sol
    function withdrawToNativeChain(
        address zrc20, // Can be _ETH_ADDRESS_ (native coin address)
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) { // L365
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        }
        // ...
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // L380
        // ...
    }
    ```

2.  The `if` condition `if(zrc20 != _ETH_ADDRESS_)` (`L365`) in `withdrawToNativeChain` evaluates to `false`, thus bypassing the `transferFrom` check at `L366`. The native coin is already received by the contract via `msg.value`.

3.  The contract then proceeds to call the internal **`_handleFeeTransfer`** function (`L380`), passing `_ETH_ADDRESS_` as the `zrc20` argument.

    ```solidity
    // File: GatewayTransferNative.sol
    function _handleFeeTransfer(
        address zrc20, // This is _ETH_ADDRESS_ from withdrawToNativeChain
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000;
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx); // L357
    }
    ```

4.  Inside `_handleFeeTransfer`, `platformFeesForTx` is calculated. Subsequently, the function attempts to execute `TransferHelper.safeTransfer(_ETH_ADDRESS_, EddyTreasurySafe, platformFeesForTx)` (`L357`).

5.  This call to `safeTransfer` with `_ETH_ADDRESS_` as the token address will fail because `_ETH_ADDRESS_` (representing the native coin) is not an ERC20 token contract and does not expose a `transfer` function. This failure causes the entire `withdrawToNativeChain` transaction to revert.

---

#### Impact
* **Loss of Protocol Revenue:** The protocol is inherently unable to collect the intended `feePercent` from any cross-chain transactions initiated with the native coin via the `withdrawToNativeChain` function. This results in a direct and continuous loss of revenue for the protocol for a common transaction type.
* **Denial of Service (DoS):** All legitimate cross-chain transactions initiated with the native coin through the `withdrawToNativeChain` function will consistently revert. This prevents **users** from utilizing the protocol for such transfers, severely impacting user experience and disrupting the overall service for a fundamental functionality.
