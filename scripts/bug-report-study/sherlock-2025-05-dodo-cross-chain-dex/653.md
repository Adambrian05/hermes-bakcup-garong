# Unauthorized fund drainage through public withdraw function

### Summary

The `withdraw` function in GatewayTransferNative is publicly accessible without authorization checks, allowing anyone to drain tokens held by the contract. The attack is highly practical because the contract accumulates refund tokens from failed transactions and maintains leftover ERC20 approvals from a bug in the withdrawal flow. Attackers can exploit these leftover approvals to drain accumulated refunds.

### Root Cause

The `withdraw` function in [GatewayTransferNative](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286C14-L286C22) lacks access controls. Anyone can call it to  bridge tokens from the `GatewayTransferNative` contract's own balance rather than the caller's balance:
```solidity
function withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount) public {
    gateway.withdraw(sender, amount, outputToken, RevertOptions({...}));
}
```
When called, ZetaChain's `GatewayZEVM` executes `transferFrom(msg.sender, address(this), amount)` where msg.sender is the `GatewayTransferNative` contract, effectively draining the contract's token balance.

In order for attack to be profitable for the attacker, `GatewayTransferNative` should hold funds and there should be approval from the `GatewayTransferNative` to the `GatewayZEVM`. Both of those pre-requisites will be satisfied in practice:
1) `GatewayTransferNative` [collects](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L271) and holds refund tokens from failed cross-chain transactions
2) In [_handleEvmOrSolanaWithdraw](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L477), the contract approves more tokens than it actually uses:
```solidity
// @audit Approves: outputAmount + gasFee
IZRC20(decoded.targetZRC20).approve(address(gateway), outputAmount + gasFee);
...
// @audit Only uses: 'outputAmount - gasFee' to bridge in addition to 'gasFee' for fees -> in total 'outputAmount', but 'outputAmount + gasFee' is approved
withdrawAndCall(externalId, contractAddress, targetZRC20, outputAmount - gasFee, receiver, encoded);
```

So each legitimate transaction leaves `gasFee` worth of leftover approval, which attackers can exploit through the public withdraw function.

### Internal Pre-conditions

1. GatewayTransferNative holds token balances from unclaimed refunds (stored via onRevert() and onAbort() functions)
2. Contract has leftover ERC20 approvals to GatewayZEVM from the approval bug in `_handleEvmOrSolanaWithdraw()` where `outputAmount + gasFee` is approved but only `outputAmount` is consumed, leaving `gasFee` worth of approval

### External Pre-conditions

None

### Attack Path

1. Attacker observes contract holds refund tokens from failed bridge transactions
2. Attacker checks that contract has leftover approvals to GatewayZEVM (from normal operations creating `gasFee` worth of excess approvals)
3. Attacker calls `withdraw(arbitraryId, arbitraryReceiver, tokenAddress, amount)` where `amount = remaining approval`
4. GatewayZEVM receives the call and executes `transferFrom(GatewayTransferNative, GatewayZEVM, amount)`
5. Tokens are transferred from contract's balance to GatewayZEVM and burned
6. Tokens are unlocked on destination chain to the attacker
7. Result: contract's token balance drained, refunds stolen from legitimate users

### Impact

High severity - attackers can drain accumulated refund tokens held by the `GatewayTransferNative` contract. The attack is immediately profitable since every legitimate transaction creates leftover approvals worth `gasFee` amounts. Users lose their rightful refunds. The vulnerability affects all tokens with existing approvals and enables systematic drainage of contract holdings.

_No response_

### Mitigation

1. Add access controls - restrict withdraw function to authorized callers only
2. Fix approval bug: in `_handleEvmOrSolanaWithdraw()`, approve only the exact amount needed
