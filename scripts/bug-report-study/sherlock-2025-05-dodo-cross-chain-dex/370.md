# The `_handleEvmOrSolanaWithdraw` function revert when the `decoded.targetZRC20` address belongs to the native token

## Vulnerability Details
The `_handleEvmOrSolanaWithdraw` function in both the `GatewayTransferNative` and `GatewayCrossChain` contracts takes a `decoded` DecodedMessage as input and calculates the fee token address and fee amount (e.g. at line [473](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L473) of `GatewayTransferNative` contract)

```solidity
function _handleEvmOrSolanaWithdraw(
        bytes32 externalId,
        DecodedMessage memory decoded,
        uint256 outputAmount,
        bytes memory receiver
    ) internal returns (uint256 amountsOutTarget) {
@>      (address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);
```
The function incorrectly assumes that `decoded.targetZRC20` is always zrc20 address. However it could be native token too. In that case the mentioned line will revert. 

The only instance where `_handleEvmOrSolanaWithdraw` is used is in the `GatewayTransferNative::withdrawToNativeChain` function, which accepts the native token as the `zrc20` input. So the mentioned scenario is possible.

## POC
The following test fails because of Incorect logic of `_handleEvmOrSolanaWithdraw` function. Copy the test to the `GatewayTransferNative.t.sol` file. 

```solidity
    function testWithdrawWithNativeToken() public {
        uint256 amount = 100 ether;
        uint32 dstChainId = 2;
        address targetZRC20 = address(token1Z);
        bytes memory sender = abi.encodePacked(user1);
        bytes memory receiver = abi.encodePacked(user2);
        bytes memory swapDataZ = "";
        bytes memory contractAddress = abi.encodePacked(address(gatewaySendB));
        bytes memory fromTokenB = abi.encodePacked(address(token1B));
        bytes memory toTokenB = abi.encodePacked(address(token1B));
        bytes memory swapDataB = "";
        bytes memory accounts = "";
        bytes memory message = encodeMessage(
            dstChainId,
            targetZRC20,
            sender,
            receiver,
            swapDataZ,
            contractAddress,
            abi.encodePacked(fromTokenB, toTokenB, swapDataB),
            accounts
        );

        vm.startPrank(user1);
        token1Z.approve(address(gatewayTransferNative), amount);
        gatewayTransferNative.withdrawToNativeChain{value: amount}(
            _ETH_ADDRESS_,
            amount,
            message
        );
        vm.stopPrank();
    }
```

## Impact
If users invoke the `GatewayTransferNative::withdrawToNativeChain` function and pass the native token as input for `zrc20`, the transaction will revert due to incorrect assumptions in the `_handleEvmOrSolanaWithdraw` implementation.

## Mitigation
Consider modifying the `_handleEvmOrSolanaWithdraw` function to correctly handle the case when `decoded.targetZRC20` is the native token, such as by checking if `decoded.targetZRC20` equals `_ETH_ADDRESS_` and using seperate logic for that case.

```diff
function _handleEvmOrSolanaWithdraw(
        bytes32 externalId,
        DecodedMessage memory decoded,
        uint256 outputAmount,
        bytes memory receiver
    ) internal returns (uint256 amountsOutTarget) {
-     (address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);

+     if(decoded.targetZRC20 == _ETH_ADDRESS_) {
+         // DO the callculation of gassFee and gasZRC20 seperately. they can even hardcoded.
+     } else {
+     (address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);
+     }
    }
```
