# `GatewayTransferNative::withdrawToNativeChain` can't work with native ZETA

### Summary

[withdrawToNativeChain](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530-L538) function is used to swap and bridge zrc20, or ZETA to the native asset on target chain. 
The function should support depositing native ZETA and then use it for swap as we can see on the first lines:
```solidity
    function withdrawToNativeChain(
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
        } 
```
=> If `zrc20 == _ETH_ADDRESS_` (in this context it is ZETA native token), we don't user ERC20 transfer mechanism.

However, `_handleFeeTransfer` is designed to only handle ERC20 tokens and the transaction will revert when we try to invoke `safeTransfer` on the key address that marks native funds:
```solidity
    function _handleFeeTransfer(
        address zrc20,
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
``` 

`_doMixSwap` is also flawed and cannot be used with native tokens.

### Root Cause

`_handleFeeTransfer` assuming `zrc20` is always a ERC20 token

### Internal Pre-conditions

None

### External Pre-conditions

User wanting to call `GatewayTransferNative::withdrawToNativeChain` with native assets

### Attack Path

Described above

### Impact

Broken protocol functionality.

### PoC

_No response_

### Mitigation

Edit `_handleFeeTransfer` and `_doMixSwap` to handle native funds flow.
