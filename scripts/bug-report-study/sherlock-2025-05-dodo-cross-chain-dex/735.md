# Unchecked `payload` sent to `GatewayCrossChain` or `GatewayTransferNative` can lead to a loss of valuable tokens.

### Summary

There is no check for the user input `payload` sent from `GatewaySend::depositAndCall()` to `GatewayCrossChain::onCall()`, but the included data `targetZRC20` ``and the `swapDataZ` are crucial parameters in `onCall()`. This will lead to potential token loss and other users cannot claim from the `GatewayCrossChain` when the underlying token is stolen out.
And `GatewayTransferNative` shares the similar problem.

### Root Cause


https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L442-L510

In `GatewayCrossChain::onCall()`, there are two actions involve in this function, first the function will swap from the zrc20 token minted by zeta protocal to another zrc20 token for the next cross chain withdraw (For example, from `USDC.ARB` to `USDC.AVAX`). Then it will handle the withdraw action to withdraw these tokens to its corresponding chain.

However, in `onCall()`, there is no checks for decoded data `params` and `decoded.targetZRC20`, the data `param` and `decoded.targetZRC20` are both from the user input `payload` in `GatewaySend::depositAndCall()` .The payload is formed by the following method according to the test files.
```solidity
        abi.encodePacked(
            bytes4(dstChainId),
@>            bytes20(targetZRC20),
            uint16(sender.length),
            uint16(receiver.length),
            uint16(swapDataZ.length),
            uint16(contractAddress.length),
            uint16(swapDataB.length),
            uint16(accounts.length),
            sender,
            receiver,
@>           swapDataZ,
            contractAddress,
            swapDataB,
            accounts
        );
```
When the payload is send to `GatewayCrossChain::onCall()` in zeta chain, `onCall()` will decode the message into `decoded` and `params`. 
```solidity
        (
            DecodedMessage memory decoded,
            MixSwapParams memory params
        ) = SwapDataHelperLib.decodeMessage(_message);

```
But the data `params` is a data from `swapDataZ`, and `decoded.targetZRC20` is from the original bytes20 data `targetZRC20`

This means that an attacker can swap in `_doMixSwap()` from `tokenA` to `tokenB`, but in the handle withdraw functions uses another `tokenC` as the targetZRC20.

Since the contract `GatewayCrossChain` can hoard some tokens due to `onRevert` or `onAbort` process, any melicious user can exploit this vulnerability to swap from lower value token to a higher value token. 

For instance, the easiest attack is to skip the swap by inputing `swapDataZ.length ==0`, and simply set target.zrc20 token as `WBTC`, but the original token send by user is `USDC`. As a result, only 1e8 `USDC`(10 dollars) can withdraw 1e8 `WBTC`.

### Internal Pre-conditions

No checks and calibration for the swapped out token and targetZRC20 token. The `onCall` function allows them to be different tokens.



### External Pre-conditions

A melicious attacker set targetZRC20 token as a higher value token then the swapped out token. 

And enought target token is left in the contract due to `onRevert` and `onAboard`

### Attack Path

For instance, the easiest attack is to skip the swap by inputing `swapDataZ.length ==0`, and simply set target.zrc20 token as `WBTC`, but the original token send by user is `USDC`. As a result, only 1e8 `USDC`(100 dollars) can withdraw 1e8 `WBTC`(1 BTC).


### Impact

Valuable tokens will get sacked, and some users could not withdraw their tokens if no token is left.

### PoC

_No response_

### Mitigation

Add a check for the targetZRC20 token and swapped out token address, make sure they are the same token.
