# `RefundInfo` on ZetaChain Can Be Overwritten via Malicious `onRevert` Call Due to Missing Caller Context from Gateway

### Summary

The `GatewayCrossChain` on Zetachain maintains refund metadata (`refundInfo`) to allow users to reclaim funds in cases where cross-chain swaps fail. This metadata is written during the `onRevert` call on Zetachain when a transaction fails on the destination chain.

However, the protocol fails to associate or verify the original caller or initiator address from the source chain (in this case Zetachain) when executing [`GatewayCrossChain.onRevert(...)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517). As a result, an attacker can craft a malicious transaction that calls `onRevert` with exisiting `externalId` and overwrite existing `refundInfo` for a legitimate user.

This leads to legitimate user `refundInfo` being lost.

### Root Cause

- The [`refundInfo`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L533-L538) mapping is written on Zetachain during GatewayCrossChain.onRevert` (after destination chain failure).
- The `Gateway` does not include the source-chain initiator address or any trusted metadata to validate the refund’s origin as seen in [Zetachain documentation](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions).
```solidity
struct RevertContext {
    address asset;
    uint64 amount;
    bytes revertMessage;
}
 
interface Revertable {
    function onRevert(RevertContext calldata revertContext) external;
}
```
- The `externalId` is derived from `RevertContext.revertmessage` which can be created by anyone during a cross-chain call via Zetachain defined in `RevertOptions`.
```solidity
struct RevertOptions {
    address revertAddress;
    bool callOnRevert;
    address abortAddress;
    bytes revertMessage;
    uint256 onRevertGasLimit;
}
```
- The protocol does not verify if the overwrite attempt comes from a trusted flow or is targeted at a legitimate user.

### Internal Pre-conditions

1. **Any arbitrary cross-chain transfer** from chain A → Zetachain → chain B fails on the destination chain (B) with `RevertOptions.revertAddress` set to `GatewayCrossChain`.
2. `GatewayCrossChain` receives a `onRevert` call with `refundInfo` to write.
3. `RefundInfo` is already written or exists for that `externalId`.

### External Pre-conditions

1. An attacker prepares `RevertOptions.revertMessage` using an already exisiting `externalId` on `GatewayCrossChain`.
2. The attacker's cross-chain call fails and calls `onRevert` on GatewayCrossChain using their own calldata overwriting:
```solidity
refundInfo.token
refundInfo.amount
refundInfo.walletAddress
```

### Attack Path

1. A attacker initiates a valid cross-chain `withdrawAndCall` from **their version** of `Universal Contract` on Zetachain → destination.
2. Attacker provides malicious `RevertOptions.revertMessage` and `RevertOptions.revertAddress` as `GatewayCrossChain`.
3. The cross-chain transaction fails on the destination chain.
4. `GatewayCrossChain` expects to handle the failure by writing refundInfo in `onRevert`.
5. The malicious `revertMessage` contains and exisitng `externalId`. 
6. Because the `GateCrossChain` contract doesn't validate which source call initiated this fallback:
7. The attacker’s version of `refundInfo` overwrites the legitimate one.
8. The legitimate user cannot claim their refund.

### Impact

Users with pending refunds loose access to their funds.
