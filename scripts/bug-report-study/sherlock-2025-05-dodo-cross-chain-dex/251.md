# Logical Flaw in GatewaySend.onCall Renders It Non-Functional for ERC20 Tokens Due to Impossible transferFrom Call on Gateway

### Summary

The `onCall` function in `GatewaySend.sol` {root cause: incorrectly attempts to execute `IERC20(fromToken).transferFrom(msg.sender, ...)` where `msg.sender` is the trusted ZetaChain `gateway` contract}. This will cause {impact: all cross-chain transactions that trigger this `onCall` handler with an ERC20 `fromToken` to revert}, creating a {impact: denial of service for a core part of the protocol's functionality} for {affected party: the protocol itself and any user attempting a cross-chain flow that relies on this handler}. This occurs as {actor: any system or user triggering a valid cross-chain message} will {vulnerability path: cause the `onCall` function to be invoked by the trusted `gateway`. The function then attempts to pull ERC20 tokens from the `gateway`'s address, which is an impossible operation as the gateway does not hold funds in this manner and would never grant such an approval. The `transferFrom` call will always fail, causing the entire cross-chain workflow to revert}.


### Root Cause

- In `contracts/GatewaySend.sol`, within the `onCall` function, the logic for handling non-native (`fromToken != _ETH_ADDRESS_`) assets is fundamentally flawed: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L358-L360
```solidity
  function onCall(
      MessageContext calldata /*context*/,
      bytes calldata message
  ) external payable onlyGateway returns (bytes4) {
      // ... message decoding logic ...
      bool fromIsETH = (fromToken == _ETH_ADDRESS_);
      // ...
      if(!fromIsETH) {
          // 'msg.sender' is the trusted 'gateway' contract address due to the 'onlyGateway' modifier.
          // This call attempts to pull 'fromToken' from the 'gateway' address to this contract.
          // This will always fail.
          IERC20(fromToken).transferFrom(msg.sender, address(this), amount); 
      }
      // ...
  }
```

The function is protected by `onlyGateway`, meaning `msg.sender` is guaranteed to be the ZetaChain `gateway` contract address. The line `IERC20(fromToken).transferFrom(msg.sender, address(this), amount)` attempts to make the `GatewaySend` contract `(address(this)`) pull `amount` of `fromToken` from the `gateway` contract (`msg.sender`). This operation will always fail because the ZetaChain gateway **is a piece of infrastructure that relays assets; it does not hold token balances** in a way that would allow a third-party contract to call `transferFrom` on it. Furthermore, the gateway would never have called `approve()` to grant `GatewaySend.sol` an allowance to spend its tokens. This reflects a misunderstanding of the ZetaChain asset and message passing model (e.g., `depositAndCall`), where assets are deposited into the target contract's balance before `onCall` is executed.

### Internal Pre-conditions

1.  A cross-chain message is constructed where the `fromToken` field, when decoded by `decodePackedMessage`, corresponds to an ERC20 token address (not `_ETH_ADDRESS_`, i.e., `fromToken` is an ERC20 address).
2.  The `GatewaySend.sol` contract's `onCall` function is triggered by the trusted `gateway` contract with this message.


### External Pre-conditions

1.  A user or system on another chain initiates a cross-chain transaction involving an ERC20 token that is routed to the `GatewaySend.sol` contract on the current chain for execution.


### Attack Path

*(This describes a failure path for any legitimate transaction that meets the criteria)*
1.  A user on a source chain (e.g., Ethereum) initiates a cross-chain transaction. The payload for this transaction is a `message` string where the decoded `fromToken` is an ERC20 token (e.g., USDC).
2.  The ZetaChain Gateway processes this cross-chain call and invokes the `onCall(context, message)` function on the deployed `GatewaySend.sol` contract on the target chain.
3.  Inside the `onCall` function, the `onlyGateway` modifier passes, correctly identifying `msg.sender` as the `gateway` contract's address.
4.  The `message` is decoded, and `fromToken` is identified as the USDC address. The condition `if(!fromIsETH)` evaluates to `true`.
5.  The code attempts to execute `IERC20(USDC_ADDRESS).transferFrom(gateway_address, address(this), amount)`.
6.  This `transferFrom` call will **always revert**. The `gateway` contract does not hold token balances in a way that allows a third party to pull from it, and crucially, the `gateway` would never have executed an `approve()` call to grant an allowance to the `GatewaySend.sol` contract.
7.  The entire `onCall` transaction reverts, causing the cross-chain workflow to fail. The user's intended action is blocked, and the transaction will likely need to be refunded via the `onRevert` mechanism.


### Impact

* The `onCall` function is **completely non-functional and will always revert for all ERC20 token interactions** (where the decoded `fromToken` is not the native ETH address).
* Any cross-chain workflow designed to trigger this function with an ERC20 token as the primary asset will be broken and will always fail.
* This is a **critical functional bug** that renders a significant part of the contract's intended capabilities useless. While it does not directly lead to a loss of funds through theft within this specific function (as the transaction simply fails), **it breaks the protocol's core logic** and can lead to user funds being sent into the ZetaChain cross-chain flow only to be reverted later, requiring a separate and potentially complex refund process.
* The affected party is the DODO DEX protocol itself, as a core piece of its cross-chain logic is broken, and any user attempting to utilize this functionality for ERC20 tokens.
