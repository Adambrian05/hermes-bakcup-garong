# User loses his funds if he uses safe wallet or account abstraction wallet, when his cross-chain transaction reverts

### Summary

If user cross-chain transaction reverts, `onRevert` being called, if it reverts then `onAbort` being called. so after cross-chain transaction fails, user can call `claimRefund` function in both `GatewayTransferNative` or `GatewayCrossChain` (depends on the pointing `targetContract` while initiating transaction) contracts to claim the funds from these contracts. But they will fail if user wallet address in chain A and Zetachain are different, this is possible when using the safe wallet or account abstraction. So even bot calls the `claimRefund` function the funds get transferred to address same as user in source chain, but not representing the user in destination chain. Or may the transaction itself get reverted due to the address generation is different for 2 different chains

### Root Cause

When user calls the function [`GatewaySend::depositAndCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218-L285), inside the function itself there is a part of code where it sets the message for counter react the scenario for cross-chain transaction revert. In the below code, you can see how the [`revertMessage`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L253) being set, i.e., with `externalId` and `msg.sender` converted into bytes20. This message is same for both the functions `onRevert` (in source gateway contract) and `onAbort` (in receiving contract, i.e., in Zetachain)

```solidity
        RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: targetContract,
>@            revertMessage: bytes.concat(externalId, bytes20(msg.sender)),
            onRevertGasLimit: gasLimit
        });
```

The problem here is that the function `onAbort` in both `GatewayTransferNative` and `GatewayCrossChain`, the wallet address that extracted from the `revertMessage` is been taken, which further be called by the function `claimRefund`, where user get back his funds for the failing on cross-chain transaction. 

```solidity
    function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
>@        bytes memory walletAddress = abortContext.revertMessage[32:];


        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
>@            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }
```

```solidity
    function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;
        if(refundInfo.walletAddress.length == 20) {
>@            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
>@        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];


        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```

The issue here is that the wallet address isn't always same across the chains, so when user tries to claim the funds it get reverted as the check `msg.sender == receiver` fails user cannot get his funds back. But allowed bot can pass this check, and send the funds to the anonymous address, which is same as users in the source chain or may get reverted is the address generation is different for source chain and zetachain.

**> if user uses safe wallet or account abstraction then the wallet address of user is different in different chain, even when they are sidechains**

### Attack Path

- user uses a wallet in which the address of each chain is different (safe wallet or account abstraction)
- when user cross-chain transaction reverts, `onRevert` being called, if it fails `onAbort` being called
- because of wrongly assigned address of the user in destination chain, the funds of user get lost

### Impact

The impact is High, but likelihood is medium-low. When the cross-chain transaction reverts and `onAbort` being called upon reverting `onRevert`, user funds get locked in the contract and when tries to call `claimRefund`, the function reverts as the wallet address is different from the stored address in the `revertMessage` of abort context. Which ultimately loses user funds, which need to be cleared by the protocol as their contract is being at fault.

### Mitigation

Add the receiver address also in the `revertMessage` and extract that receiver address and store it in the wallet address in `onAbort` function
