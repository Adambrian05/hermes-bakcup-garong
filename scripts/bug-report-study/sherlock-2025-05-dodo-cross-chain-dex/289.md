# `platformFeesForTx` is not appropriately accounted for in `GateWayTransferNative`

### Summary

In  GrateWayTransferNative contract, the `_handleFeeTransfer()` function calculates the `platformFeesForTx` and transfers it to  `EddyTreasurySafe` address. `_handleFeeTransfer()` is called before swapping on DODO router.  The problem here is that if `decoded.targetZRC20 != zrc20`, and the gateway triggers a crosschain swap, `platformFeesForTx` is not accounted for during the swap, this means the user's initial amount is still swapped and sent as `outputAmount to the receiver after the swap.

### Root Cause

`platformFeesForTx` is not adequately deducted from the user's intial amount before they are sent to the receiver. This issue occurs in the  `GrateWayTransferNative` contract.

Link to affected code:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357-L423

### Internal Pre-conditions

No attack path, the protocol does not earn protocol fees in some instances.

### External Pre-conditions

In `GrateWayTransferNative` this will happen when `decoded.targetZRC20 != zrc20`. The only time platform fee is deducted  is when `decoded.targetZRC20 == zrc20`, in any other case platform fees are not deducted.

In the `GatewayCrossChain` contract, this will happen anytime there is call to withdraw an asset.

### Attack Path

no response

### Impact

The protocol loses fees when a cross-chain swap is triggered.

### PoC

no response 

### Mitigation

consider subtracting the `platformFeesForTx` apropriately from the intial amount before executing the swap.
