# `GatewayCrossChain.onRevert` Misdirects Refunds for 20-Byte Bitcoin Addresses to Invalid EVM Addresses

### Summary

The [`GatewayCrossChain.onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L468-L489) function can initiate withdrawals to Bitcoin addresses. Bitcoin addresses can be represented in various formats, including shorter 20-byte hashes (P2PKH, P2SH) and longer 32-byte hashes (P2WPKH, P2WSH). When a cross-chain withdrawal to a Bitcoin address fails and the ZetaChain gateway calls `GatewayCrossChain.onRevert`, the refund logic mishandles cases where the `revertMessage` is 52 bytes long. This length typically occurs if the original Bitcoin address hash was 20 bytes. The `onRevert` function incorrectly interprets this 20-byte Bitcoin hash as an EVM address, attempting a direct ZRC20 token transfer to this derived, invalid EVM address. This results in user funds being lost to an unrecoverable address, bypassing the intended bot-assisted refund mechanism via `refundInfos`.

### Root Cause

The bug lies in the `onRevert` function within `GatewayCrossChain and how it processes the `context.revertMessage` for refund distribution, particularly when the message length suggests a 20-byte recipient identifier.

1.  **Withdrawal Initiation and Revert Message Construction:** When a user initiates a cross-chain transaction via `GatewaySend` that targets a Bitcoin address for withdrawal, the `GatewayCrossChain.onCall` function eventually calls internal withdrawal helper functions `_handleBitcoinWithdraw` which in turn call the lower-level `withdraw` or `withdrawAndCall`.

    These functions prepare `RevertOptions` for the call to `GatewayZEVM`:

    ```solidity
    gateway.withdrawAndCall(
        // ...
        RevertOptions({
            revertAddress: address(this), // GatewayCrossChain itself
            callOnRevert: true,
            abortAddress: address(0),
            // 'receiver' here is the original Bitcoin address bytes from the payload
            revertMessage: bytes.concat(externalId, receiver), 
            onRevertGasLimit: gasLimit
        })
    );
    ```
    If the `receiver` (the Bitcoin address) is a 20-byte hash, `bytes.concat(externalId, receiver)` will result in a `revertMessage` of `32 (externalId) + 20 (receiver) = 52 bytes`.

2.  **Flawed Conditional Logic in `onRevert`:** When the ZetaChain gateway calls `GatewayCrossChain.onRevert` due to a failed withdrawal:

    ```solidity
    function onRevert(
        RevertContext calldata context
    ) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:];

        if (context.revertMessage.length == 52) { // @audit This condition is met for 20-byte Bitcoin address hashes
            address receiver = address(uint160(bytes20(walletAddress))); // @audit walletAddress (Bitcoin hash) is cast to EVM address
            TransferHelper.safeTransfer(context.asset, receiver, context.amount); // @audit Refund sent to invalid EVM address

            emit EddyCrossChainRevert(externalId, context.asset, context.amount, walletAddress);
        } else {
            // This block is intended for longer non-EVM addresses (like 32-byte Bitcoin hashes)
            // or when the refund needs bot intervention.
            RefundInfo memory refundInfo = RefundInfo({
                externalId: externalId,
                token: context.asset,
                amount: context.amount,
                walletAddress: walletAddress
            });
            refundInfos[externalId] = refundInfo;

            emit EddyCrossChainRefund(externalId, context.asset, context.amount, walletAddress);
        }
    }
    ```
    *   The condition `if (context.revertMessage.length == 52)` is met if the original Bitcoin address hash was 20 bytes long.
    *   The code then incorrectly assumes `walletAddress` the 20-byte Bitcoin hash is an EVM address by casting `bytes20(walletAddress)` to `address`.
    *   `TransferHelper.safeTransfer` sends the ZRC20 refund to this derived, invalid EVM address. The funds are lost because this address is not the user's actual Bitcoin address.
    *   The `else` block, which correctly stores `RefundInfo` for bot-assisted manual refunds (presumably intended for all non-standard EVM address refunds or complex cases), is bypassed for these 20-byte Bitcoin address scenarios.

### Internal Pre-conditions

1. GatewayCrossChain is operational.

### External Pre-conditions

1.  A user initiates a cross-chain transaction targeting a Bitcoin address represented by a 20-byte hash (e.g., P2PKH, P2SH).
2.  This transaction is processed by `GatewayCrossChain.onCall`, leading to a withdrawal attempt to this Bitcoin address.
3.  The withdrawal operation initiated by `GatewayCrossChain` fails.
4.  ZetaChain's gateway calls `GatewayCrossChain.onRevert` with a `context.revertMessage` that is exactly 52 bytes long, containing the 32-byte `externalId` and the 20-byte Bitcoin address hash.

### Attack Path

1.  **User Initiates Withdrawal:** User initiates a transaction from a source chain (e.g Ethereum) via `GatewaySend`, intending to swap and withdraw assets as BTC to their 20-byte Bitcoin hash address `btcHash20`.
2.  **`GatewayCrossChain` Processing:** `GatewayCrossChain.onCall` receives the instruction. It performs any internal swaps and then calls `gateway.withdraw` targeting `btcHash20`. The `RevertOptions.revertMessage` is set to `bytes.concat(externalId, bytes20(btcHash20))`, which is 52 bytes.
3.  **Withdrawal Failure:** The withdrawal to Bitcoin fails for some reason (e.g, network issue, invalid parameters for Bitcoin side not caught earlier).
4.  **`onRevert` Triggered:** ZetaChain's gateway calls `GatewayCrossChain.onRevert`.
    *   `context.revertMessage.length` is 52.
    *   `walletAddress` becomes `bytes(btcHash20)`.
    *   `address receiver = address(uint160(bytes20(walletAddress)));` converts `btcHash20` into an EVM address, `evmAddrFromBtcHash`.
    *   `TransferHelper.safeTransfer(context.asset, evmAddrFromBtcHash, context.amount);` sends the ZRC20 refund to `evmAddrFromBtcHash`.
5.  **Outcome:** The user's ZRC20 refund is sent to an EVM address derived from their Bitcoin hash. These funds are irrecoverable by the user as they do not control the private key for this specific EVM address. The intended `refundInfos` entry for bot processing is not created.

### Impact

Direct and permanent loss of user funds for failed withdrawals intended for 20-byte Bitcoin hash addresses. The refund mechanism sends tokens to an inaccessible EVM address instead of making them available for the documented bot-assisted refund process.

}

### Mitigation

The `onRevert` function in `GatewayCrossChain` needs to differentiate between 20-byte EVM addresses and 20-byte non-EVM address identifiers (like Bitcoin hashes). A robust solution would involve knowing the `dstChainId` for which the original withdrawal failed.
