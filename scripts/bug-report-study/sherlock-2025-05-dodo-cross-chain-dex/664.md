# During onAbort calls on Zeta, contract logic assumes that the user owns the same EVM address on Zeta

### Summary

In the GatewaySend when the revert data is constructed, the onAbort address is the target address, the native/cross-chain gateway deployed on Zeta. 

The problem is if the onAbort flow is activated (if the onRevert call on the connected chain fails), the logic assumes that the owner of the EVM address which initiated a call on the connected chain owns the same address on Zeta, which may not be the case. 

### Root Cause

When a depositAndCall is initiated from a connected chain (for example: Arbitrum), the RevertOptions are constructed in case the onCall reverts on Zeta:

```solidity

 RevertOptions memory revertOptions = RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: targetContract,
            revertMessage: bytes.concat(externalId, bytes20(msg.sender)),
            onRevertGasLimit: gasLimit
        });

```

As it can be seen from the options above, the `revertAddress` set is address(this) which is the GatewaySend (the gateway on the connected chain), while the abortAddress is the target contract on Zeta (GatewayNative or GatewayCrossChain). As if the revert flow on the connected chain (onRevert) fails, the onAbort flow will be activated on Zeta.

The problem with this approach is that the revertMessage will be utilized on Zeta in order to store the refundInfo:

```solidity

 function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }

```

Now the owner of the address (msg.sender on Arbitrum) might not be the owner of the same address on ZetaChain. This is due to a multitude of reasons such as that being an Account Abstraction / Smart wallet which initiated the call, or a contract.

This will result in someone else being able to claim the funds on Zeta.

### Internal Pre-conditions

None

### External Pre-conditions

Users which initiate the call on a connected chain with a smart wallet / smart contract, may lose all of their funds if the onAbort flow gets activated.

### Attack Path

N/A

### Impact

Users with account abstraction wallets / smart contracts may lose all of their funds if the onAbort flow gets activated.
