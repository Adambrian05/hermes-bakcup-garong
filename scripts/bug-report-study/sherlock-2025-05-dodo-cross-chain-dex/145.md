# ETH Refund Handling Vulnerability in GatewayCrossChain Contract.

## Summary
The `claimRefund` function in the GatewayCrossChain contract has a vulnerability in how it handles ETH refunds. The function uses `TransferHelper.safeTransfer()` for all token types, but this method only works for ERC20 tokens and will revert when trying to transfer ETH. As a result, any ETH refunds stored in the contract become permanently locked, with no way for users to recover their funds.

## Root Cause
The function uses a single transfer method for all token types:

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L581

```solidity
TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
```

However, looking at the contract implementation:
1. ETH is represented using a special address: `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`
2. The `safeTransfer` function attempts to call the ERC20 `transfer()` method on this address
3. Since there is no contract at this address, the call fails and reverts

This is in contrast to the `superWithdraw` function, which correctly handles both ERC20 tokens and ETH:
```solidity
if (token == _ETH_ADDRESS_) {
    TransferHelper.safeTransferETH(EddyTreasurySafe, amount);
} else {
    TransferHelper.safeTransfer(token, EddyTreasurySafe, amount);
}
```

## Internal Pre-conditions
1. A cross-chain transaction involving ETH must have failed
2. The transaction failure must have triggered `onRevert` or `onAbort`
3. The refund be stored in the `refundInfos` mapping with `token` set to `_ETH_ADDRESS_`

## External Pre-conditions
1. A user attempt to claim their ETH refund by calling `claimRefund`

## Attack Path
This is denial of service for legitimate refunds:

1. User initiates a cross-chain transaction involving ETH
2. The transaction fails on the destination chain or ZetaChain
3. The contract stores refund information with `token` set to `_ETH_ADDRESS_`
4. User calls `claimRefund` to retrieve their ETH
5. The function attempts to use `safeTransfer` on the ETH address
6. The transaction reverts, making it impossible to claim the refund

## Impact
- ETH refunds become permanently locked in the contract
- Users are unable to recover their funds after failed cross-chain transactions


## Mitigation
Update the `claimRefund` function to handle ETH correctly, similar to the `superWithdraw` function:

```diff
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    
    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    // Store values before deleting the refund
    address token = refundInfo.token;
    uint256 amount = refundInfo.amount;

-    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    
+    if (token == _ETH_ADDRESS_) {
+        TransferHelper.safeTransferETH(receiver, amount);
+   } else {
+        TransferHelper.safeTransfer(token, receiver, amount);
+   }

    delete refundInfos[externalId];
    
    emit EddyCrossChainRefundClaimed(
        externalId,
        token,
        amount,
        abi.encodePacked(msg.sender)
    );
}
```
