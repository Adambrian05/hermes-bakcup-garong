# Incorrect Validation Using Maximum Swap Estimate Instead of Actual Spent Amount Leads to DoS


## Summary
In `GatewayTransferNative.sol`, the `_swapAndSendERC20Tokens` function performs validation using `amountInMax` (maximum estimate with slippage) but then executes the remainder of its operations using `amounts[0]` (actual amount spent). This inconsistency creates a DoS vulnerability where legitimate transactions can fail unnecessarily when DEX prices are manipulated.

## Vulnerability Detail


The function `_swapAndSendERC20Tokens`  in the following contract gets quotes for token swaps, adds slippage tolerance, performs the swap, and then conducts validation:

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L425
 The key issue is that `amountInMax` is an estimated maximum with slippage, while `amounts[0]` is the actual amount spent. Since `amounts[0]` is always less than or equal to `amountInMax` (due to how `swapTokensForExactTokens` works), using `amountInMax` in the validation creates a stricter check than necessary.

## Root Cause
The validation check uses the maximum possible amount with slippage (`amountInMax`) rather than the actual amount spent (`amounts[0]`), creating an inconsistency with the rest of the function that reduces protocol availability.

## Attack Path
1. An attacker manipulates the DEX price for the `targetZRC20/gasZRC20` pair temporarily.
2. This causes `getAmountsIn` to return an inflated quote value.
3. `amountInMax` becomes artificially high due to the manipulation.
4. The validation check `targetAmount - amountInMax > 0` fails even though the actual swap executed successfully.
5. The transaction reverts unnecessarily, creating a DoS condition.

## Impact
This vulnerability creates a Denial of Service condition that:
- Causes legitimate user transactions to fail unnecessarily.
- Is especially impactful during market volatility.
- Makes the protocol susceptible to price manipulation attacks.
- Creates poor UX as users don't understand why transactions fail.

This issue does not directly risk funds but significantly impacts protocol availability, especially during market stress when the protocol should be most reliable.

## Mitigation
Replace the validation check with the actual amount spent:

```diff 


 function _swapAndSendERC20Tokens(
        address targetZRC20,
        address gasZRC20,
        uint256 gasFee,
        uint256 targetAmount
    ) internal returns(uint256 amountsOut) {
        // Get amountOut for Input gasToken
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );

        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);

        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE
        );

        require(IZRC20(gasZRC20).balanceOf(address(this)) >= gasFee, "INSUFFICIENT_GAS_FOR_WITHDRAW");
-       require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");
+      require(targetAmount - amounts[0] > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");
        IZRC20(gasZRC20).approve(address(gateway), gasFee);
        IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);

        amountsOut = targetAmount - amounts[0];
    }

```

This change ensures consistency between validation and operational logic, significantly reducing the DoS attack surface and improving user experience.
