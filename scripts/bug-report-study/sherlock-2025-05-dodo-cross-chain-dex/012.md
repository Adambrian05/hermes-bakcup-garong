# EXTERNAL ID COLLISION (Transaction Replay/Manipulation)

### Summary

Predictable external ID generation will cause transaction integrity compromise for legitimate users as attackers will predict future external IDs using known parameters (contract address, sender, globalNonce, block.timestamp) and front-run transactions to claim intended IDs, manipulate transaction ordering, and redirect funds across ZetaChain gateway contracts.

### Root Cause

In GatewaySend.sol:_calcExternalId() and GatewayTransferNative.sol:_calcExternalId() the external ID generation uses only predictable parameters (contract address, sender, globalNonce, block.timestamp) without any cryptographic randomness, allowing attackers to calculate future external IDs before transactions are executed.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L160

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L176

### Internal Pre-conditions

1. Gateway contracts need to be deployed and initialized with globalNonce starting at 0
2. At least one legitimate user needs to initiate a transaction (calling depositAndCall() or withdrawToNativeChain()) to increment the globalNonce
3. The attacker needs to observe pending transactions in the mempool to identify target transactions with known parameters
4. The attacker needs to have sufficient token balance and ETH for gas to execute front-running transactions
5. Multiple transactions need to occur within the same block timestamp to enable nonce race conditions

### External Pre-conditions

1. Block timestamp needs to remain predictable and within attacker's calculation window (typically 12-15 seconds for Ethereum blocks)
2. Network congestion needs to allow transaction ordering manipulation through gas price bidding
3. Mempool visibility needs to be available for attackers to observe pending transactions before execution
4. Block miners/validators need to process transactions in gas-price order within the same block
5. Cross-chain bridge infrastructure needs to be active to enable external ID conflicts across different gateway contracts

### Attack Path

1. Legitimate user calls depositAndCall() or withdrawToNativeChain() with their transaction parameters, broadcasting to mempool
2. Attacker observes the pending transaction in mempool and extracts key parameters (sender address, current globalNonce, expected block timestamp)
3. Attacker calculates the victim's future external ID using keccak256(abi.encodePacked(contractAddress, victimAddress, globalNonce + 1, block.timestamp))
4. Attacker submits identical or conflicting transaction with higher gas price to execute first in the same block
5. Attacker's transaction gets processed first, consuming the predicted external ID and incrementing globalNonce
6. Victim's transaction either fails, gets processed with unexpected external ID, or experiences state corruption due to ID collision
7. Attacker repeats process across multiple gateway contracts (GatewaySend and GatewayTransferNative) to create cross-contract ID conflicts
8. Attacker can manipulate transaction ordering and outcomes by controlling external ID generation through timing attacks

### Impact

The legitimate users suffer transaction integrity compromise and potential fund redirection with no upper bound on loss value. The attacker gains the ability to manipulate cross-chain transactions, claim intended external IDs, and extract MEV through front-running without direct token gains but with significant control over transaction outcomes.

### Mitigation

Replace the predictable external ID generation with cryptographically secure randomness by modifying the _calcExternalId() function to include unpredictable elements:
```solidity
function _calcExternalId(address sender, uint256 userNonce) internal view returns (bytes32) {
    return keccak256(abi.encodePacked(
        address(this),
        sender,
        globalNonce,
        userNonce,  // User-provided entropy
        blockhash(block.number - 1),  // Recent unpredictable hash
        block.prevrandao  // Post-merge randomness (or block.difficulty pre-merge)
    ));
}
```
