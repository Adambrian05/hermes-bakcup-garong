# Tokens can be stolen from GatewaySend and GatewayCrossChain

### Summary

An attacker can deposit worthless tokens but trigger massive approvals of valuable tokens held by the contract. For example, deposit 1e18 of an 18-decimal token, but approve 1e18 amount of a different 6-decimal token because validation is missing.

### Root Cause

There is no validation that the deposited token (`zrc20`) matches the swap token (`params.fromToken`). Anyone can pass swap data with `fromToken` different from the `zrc20` token and use the contract’s balance to execute the swap in [_doMixSwap](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L465) with the amount of the deposited `zrc20`:

```solidity
function onCall(
    MessageContext calldata context,
>   address zrc20,
>   uint256 amount,
    bytes calldata message
) external onlyGateway {
    // ...
>   uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
    // ...
}
```

```solidity
function _doMixSwap(
    bytes memory swapData, 
>   uint256 amount, 
    MixSwapParams memory params
) internal returns (uint256 outputAmount) {
    if (swapData.length == 0) {
        return amount;
    }

>   IZRC20(params.fromToken).approve(DODOApprove, amount);
    return IDODORouteProxy(DODORouteProxy).mixSwap(
>       params.fromToken,
        params.toToken,
>       params.fromTokenAmount,
        params.expReturnAmount,
        params.minReturnAmount,
        params.mixAdapters,
        params.mixPairs,
        params.assetTo,
        params.directions,
        params.moreInfo,
        params.feeData,
        params.deadline
    );
}
```

The amount is calculated from the deposited token but can be applied to a different token with less decimals, based on the provided params.

The same attack can be executed even easier in `GatewaySend` since it directly approves whatever is passed in `params.fromTokenAmount`.

### Attack Path

All values are rounded for simplicity.

The attacker will deposit a small amount of PEPE in order to steal USDC sitting in the `GatewayCrossChain`. A simpler scenario can be executed to steal any tokens in the `GatewaySend` contract as well.
 
1. `GatewayCrossChain` contract holds USDC
2. Attacker deposits 1 PEPE (~$0.00001, 18 decimals) using `depositAndCall` in `GatewaySend` with malicious `payload` that is never validated
3. The `onCall` in `GatewayCrossChain` function will be called by the gateway with `zrc20 = PEPE`, `amount = 1e18` and the maliciously crafted `message` (payload)
4. The malicious `message` contains `params.fromToken = USDC` (6 decimals), and `params.fromTokenAmount = 1e18` (a little bit less if fees are applied)
5. `GatewayCrossChain` executes `USDC.approve(DODOApprove, 1e18)`
6. 1e18 USDC (1,000,000,000,000 USDC) approval from $0.00001 deposit
7. DODO swaps USDC for USDT and drains the USDC balance of the contract
8. The malicious message sets USDT as `targetZRC20`, enabling the function to use the swapped amount for gas and successfully execute `withdrawAndCall`

The project only integrates tokens from the ZetaChain's supported assets.

PEPE, USDC and USDT are all supported in ZetaChain. [Source](https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets)

### Impact

Anyone can steal tokens held in `GatewaySend` and `GatewayCrossChain`.
