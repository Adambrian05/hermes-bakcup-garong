# Unreliable Address Type Check in onRevert Can Lead to Permanent Loss of User Funds

### Summary

The `onRevert` function in `GatewayCrossChain.sol` and `GatewayTransferNative.sol` {root cause: incorrectly assumes that a 20-byte `walletAddress` (derived from the `revertMessage`) is an Externally Owned Account (EOA) based solely on `context.revertMessage.length == 52`}. This will cause a {impact: direct transfer of refunded assets to a smart contract address, potentially resulting in permanent loss of funds if the contract cannot handle the incoming transfer} for {affected party: users whose cross-chain transaction to a smart contract receiver fails}. This occurs as {actor: the protocol's `onRevert` handler} will {vulnerability path: mistakenly identify a 20-byte smart contract address as an EOA and attempt a `safeTransfer`. If the recipient contract is not designed to receive these tokens (e.g., lacks a proper `receive`/`fallback` function or has a bug), the assets can become permanently locked}. This behavior also contradicts the Q&A which states that **refunds to non-EOA addresses should be handled manually by bots**.


### Root Cause

- In `GatewayCrossChain.sol` and `GatewayTransferNative.sol`, within the `onRevert` function: https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L522-L539 & https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L612-L629
```solidity
  function onRevert(RevertContext calldata context) external onlyGateway {
      // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
      bytes32 externalId = bytes32(context.revertMessage[0:32]);
      bytes memory walletAddress = context.revertMessage[32:];

      // Flawed check: Assumes a 20-byte address is an EOA
      if(context.revertMessage.length == 52) {
          address receiver = address(uint160(bytes20(walletAddress)));
          // This direct transfer is unsafe if 'receiver' is a contract that cannot handle the funds
          TransferHelper.safeTransfer(context.asset, receiver, context.amount);
          // ...
      } else {
          // This is the intended safe path for non-EOAs
          // ... store refund info for manual claim ...
      }
  }
```

The core issue is the condition `if(context.revertMessage.length == 52)`. In EVM-compatible chains, **both EOA addresses and smart contract addresses are 20 bytes long**. This check cannot distinguish between them. It incorrectly assumes that any 20-byte address is an EOA that can safely receive a direct token transfer, bypassing the intended safe mechanism (storing refund info for manual claim) for smart contract recipients mentioned in the **Q&A**.

### Internal Pre-conditions

1.  A user initiates a cross-chain transaction using `GatewaySend.sol`, targeting a smart contract address (`receiverContract`) on a destination chain. The address of `receiverContract` is 20 bytes long.
2.  The `revertMessage` for the transaction is constructed on the source chain to contain the transaction's `externalId` and the `receiverContract`'s 20-byte address, resulting in a `revertMessage` total length of 52 bytes.
3.  The `receiverContract` on the destination chain is not designed to receive direct `safeTransfer` calls of the specific `context.asset` token. For example, it might lack a `receive()` or `fallback()` function, or its internal logic might cause incoming transfers of that token to revert or lock the funds.
4.  The cross-chain transaction fails on the destination chain for any reason (e.g., destination contract logic reverts, out of gas, etc.), triggering the `onRevert` callback on the source ZetaChain contract (`GatewayCrossChain.sol` or `GatewayTransferNative.sol`).


### External Pre-conditions

1.  A user sends a cross-chain transaction with the ultimate intended recipient being a smart contract address on another chain.
2.  The transaction execution on the destination chain reverts. This causes ZetaChain's `GatewayZEVM` to call the `onRevert` function on the source contract.


### Attack Path

*(This describes a scenario leading to user fund loss)*
1.  A user (`Alice`) uses the DODO DEX UI on Chain A (e.g., Ethereum) to perform a cross-chain swap. She intends to send the swapped tokens to a smart contract on Chain B (e.g., a Gnosis Safe, a DeFi protocol's vault, or any other contract). The address of this smart contract is `0xContractAddress`.
2.  The `GatewaySend` contract on Chain A initiates the cross-chain transaction. During this process, a `revertMessage` is prepared for potential failures. This message is constructed to contain the transaction's `externalId` and the 20-byte address of the recipient, `0xContractAddress`. The total length of this `revertMessage` is therefore 52 bytes.
3.  The transaction is processed on ZetaChain, but fails when trying to deliver the funds on the destination Chain B (e.g., the `onCall` on the `0xContractAddress` on Chain B reverts, or the execution runs out of gas).
4.  ZetaChain's `GatewayZEVM` detects the failure and calls the `onRevert` function on the DODO DEX contract on ZetaChain (the one that initiated the final `withdrawAndCall`).
5.  Inside the `onRevert` function:
    a.  `context.revertMessage.length` is checked. It is `52`.
    b.  The `if` block is executed. `receiver` is decoded as `0xContractAddress`.
    c.  `TransferHelper.safeTransfer(context.asset, 0xContractAddress, context.amount)` is called, attempting to directly send the refunded tokens to the smart contract address on ZetaChain.
6.  **Failure Scenario**: The `0xContractAddress` on ZetaChain (or its equivalent if addresses differ) is not designed to handle a direct incoming `safeTransfer` of `context.asset`. The transfer either reverts (causing the `onRevert` transaction itself to fail and leaving the funds in a state requiring admin intervention) or, in a worse case, succeeds but the funds become inaccessible and permanently locked within `0xContractAddress` due to its internal logic.
7.  Alice's refunded assets are now permanently lost. This contradicts the Q&A, which states refunds to non-EOA addresses should be handled by a manual bot/claim process.


### Impact

* **Users can suffer a permanent loss of funds.** If a cross-chain transaction destined for a smart contract fails, the `onRevert` logic incorrectly attempts a direct transfer of the refund to that contract address. If the recipient contract cannot properly handle the incoming tokens, the refunded assets can become permanently locked and irrecoverable.
* This behavior **directly contradicts the protocol's stated design in the Q&A**, where refunds to non-EOA addresses are meant to be handled by bots, implying a safer, non-direct transfer mechanism (like the one implemented in the `else` block).
* This flaw creates a significant risk for any user interacting with the cross-chain functionality to send assets to any smart contract, which is a common use case in DeFi.
* Affected Party: Users of the DODO Cross-Chain DEX whose transactions to smart contract addresses fail and require a refund.
