# Malicious Users Can Redirect Cross-Chain Transfers to Arbitrary Addresses

### Summary

The GatewaySend.onCall function blindly casts a user-supplied recipient field to an address and sends funds to it without verification. This allows an attacker to craft a malicious cross-chain message that redirects funds to an arbitrary wallet. Without cryptographic checks or binding the message to a legitimate sender, the contract trusts unverified data — enabling unauthorized withdrawals and making this a critical cross-chain security flaw.

### Root Cause

In [GatewayTransferNative.onCall()], the recipient field is extracted from untrusted cross-chain message data and used as the withdrawal target without any validation or binding to the source sender.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L356

### Internal Pre-conditions

1. The GatewaySend contract is live and registered to receive onCall() messages on the destination chain (ZetaChain).
2. The contract directly uses address(bytes20(recipient)) from the cross-chain message without verifying that it matches the original depositor or intended recipient.
3. There is no commitment, hash binding, or signature check linking the payload to a trusted sender.
4. The contract holds enough tokens or ETH to fulfill the swap and transfer to the recipient.

### External Pre-conditions

1. The attacker is a regular user with access to the front-end or smart contract interface that lets them call depositAndCall() — as any end user is supposed to.
2. The attacker submits a legitimate depositAndCall() with a valid ZRC20 deposit and crafts the payload to include a recipient address they control.
3. The ZetaChain gateway forwards this user-crafted message to the destination chain without verifying the integrity of the recipient field.
4. The onCall() function on the destination chain processes the payload and sends funds to the attacker-controlled address

### Attack Path

1. Attacker calls depositAndCall() on the source chain, sending tokens along with a custom message payload.
2. The payload includes:
•	A valid fromToken and toToken for the swap (can even be the same),
•	A recipient field that is a wallet they control, not the intended user,
•	Any swap data (could be a no-op or valid route).
3. The ZetaChain gateway forwards the payload to the destination chain and calls GatewaySend.onCall().
4. GatewaySend.onCall() decodes the message and extracts the recipient, then casts it directly as address(bytes20(recipient)).
5. The contract sends the swapped tokens or ETH to the attacker’s wallet — with no checks, no authentication, and no binding to the original sender.
6. The attacker receives funds on ZetaChain that were meant for another user or workflow, with no way to revert the transfer.

### Impact

The protocol allows any user to submit a depositAndCall() with a crafted payload that diverts funds to an arbitrary address. As a result, users can redirect cross-chain assets to themselves or others without permission or verification.
	•	Affected party: Any legitimate cross-chain user using depositAndCall().
	•	Loss: Full loss of bridged or swapped tokens intended for a recipient.
	•	Attacker gain: 100% of the swapped output or bridged assets on the destination chain.
	•	Systemic risk: This breaks the trust model of cross-chain messaging, allowing fund theft with no contract compromise.

### Mitigation

Use signature-based validation:
	•	Require the message to be signed by the legitimate sender.
	•	Recover the signer in onCall() and validate it matches the original user.
