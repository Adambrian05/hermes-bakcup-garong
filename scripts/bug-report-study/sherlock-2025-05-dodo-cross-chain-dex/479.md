# Malicious actors can steal refunds meant for Bitcoin/Solana users in Gateway contracts


## Summary
Both `GatewayCrossChain` and `GatewayTransferNative` contracts have a critical vulnerability that allows any user to claim refunds that belong to Bitcoin or Solana users. This occurs because the `claimRefund` function has flawed validation logic that fails to properly authenticate non-EVM address formats, allowing attackers to steal funds from failed cross-chain transactions.

## Details

### Code Locations
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680

```solidity
// In both GatewayCrossChain.sol and GatewayTransferNative.sol
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    delete refundInfos[externalId];

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}
```

### Root Cause
The vulnerability stems from insufficient validation in the `claimRefund` function. For EVM addresses (exactly 20 bytes), it correctly converts the stored address and compares it with the caller. However, for non-EVM addresses (Bitcoin/Solana), which have different formats and lengths, the function simply defaults to using `msg.sender` as the receiver, making the condition `msg.sender == receiver` always true, effectively bypassing authentication.

### Exploit Path
1. A Bitcoin or Solana user initiates a cross-chain transaction that fails on ZetaChain.
2. The ZetaChain Gateway calls either `onRevert` or `onAbort` on the GatewayCrossChain contract:
   ```solidity
   // Example from onRevert
   if(context.revertMessage.length == 52) {
       // EVM address handling (direct transfer)
   } else {
       // Non-EVM address like Bitcoin/Solana (stored for later claim)
       RefundInfo memory refundInfo = RefundInfo({
           externalId: externalId,
           token: context.asset,
           amount: context.amount,
           walletAddress: walletAddress  // Non-EVM format (not 20 bytes)
       });
       refundInfos[externalId] = refundInfo;
       
       emit EddyCrossChainRefund(externalId, context.asset, context.amount, walletAddress);
   }
   ```
3. An attacker monitors the blockchain for `EddyCrossChainRefund` events, which contain the necessary `externalId`.
4. The attacker front-runs any legitimate refund claim by calling `claimRefund(externalId)`.
5. Inside `claimRefund`, since the stored `walletAddress` is not 20 bytes (Bitcoin/Solana format):
   - The condition `refundInfo.walletAddress.length == 20` evaluates to false.
   - `receiver` remains set to `msg.sender` (the attacker).
   - The check `msg.sender == receiver` always passes.
   - The tokens are transferred to the attacker.
6. The refund record is deleted, preventing the legitimate user from claiming.
7. The legitimate Bitcoin/Solana user is permanently unable to claim their refund.

## Impact
**High severity.** Any failed cross-chain transaction from Bitcoin or Solana can have its refund stolen by attackers who monitor the blockchain. Since the `refundInfos` entry is deleted after the first claim, legitimate users have no recourse to recover their funds once stolen. This vulnerability affects all Bitcoin and Solana users of the cross-chain DEX.

## Mitigation
Implement a secure claiming mechanism for non-EVM addresses:
```solidity
function claimRefund(bytes32 externalId, bytes calldata proof) external {
    RefundInfo storage refundInfo = refundInfos[externalId];
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    // For EVM addresses (20 bytes)
    if(refundInfo.walletAddress.length == 20) {
        address receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        require(msg.sender == receiver || bots[msg.sender], "INVALID_CALLER");
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
    } 
    // For non-EVM addresses (Bitcoin/Solana)
    else {
        // Only authorized bots can process non-EVM refunds
        require(bots[msg.sender], "ONLY_AUTHORIZED_BOTS");
        // Verify the proof matches the intended recipient (implementation depends on chain)
        require(verifyProof(refundInfo.walletAddress, proof), "INVALID_PROOF");
        // Send funds to a protocol-controlled escrow or integration endpoint
        processNonEvmRefund(externalId, refundInfo.token, refundInfo.amount, refundInfo.walletAddress);
    }
    
    delete refundInfos[externalId];
    emit EddyCrossChainRefundClaimed(externalId, refundInfo.token, refundInfo.amount, refundInfo.walletAddress);
}
```
