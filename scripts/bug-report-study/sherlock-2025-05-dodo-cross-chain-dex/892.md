# ETH Refund Failure in `GatewaySend::onRevert()` Causes Permanent Loss

### Summary

The `GatewaySend` contract, part of the DODO Cross-Chain DEX protocol, incorrectly handles ETH refunds in its `onRevert()` function. Specifically, it attempts to refund ETH using ERC20 logic through `TransferHelper.safeTransfer()`, which fails when the asset is ETH (represented by the constant `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`). This leads to failed refunds and permanent loss of ETH for users in case of cross-chain call reverts.

### Root Cause

The refund logic in `onRevert()` assumes all tokens, including ETH, are ERC20-compliant and invokes:

- https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L393-L404
```solidity
TransferHelper.safeTransfer(context.asset, sender, context.amount);
```

However, if `context.asset == _ETH_ADDRESS_` (i.e., ETH), `safeTransfer()` tries to perform an ERC20 `transfer()` call on a non-contract address, which always fails and reverts.

### Internal Pre-conditions

- The contract must receive a call to `onRevert()` from the `gateway`.
- The `context.asset` must be `_ETH_ADDRESS_` (0xEeee…).
- The refund is expected to transfer native ETH back to the user.

### External Pre-conditions

- A cross-chain transaction initiated via `GatewaySend.depositAndCall()` using ETH as the source asset.
- The destination execution fails or is aborted, triggering a call to `onRevert()`.

### Attack Path

This is not an attack vector but a **functional correctness failure** that leads to **user fund loss** under expected failure conditions. Any cross-chain ETH transaction that needs to be reverted will result in stuck funds.


### Impact

- User ETH will be permanently locked in the `GatewaySend` contract upon revert conditions.
- No way for the user to reclaim funds without external rescue or contract patching.
- Affects all users interacting with ETH cross-chain through this contract.
