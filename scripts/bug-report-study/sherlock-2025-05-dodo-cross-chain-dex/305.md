# Fee Transfer Failure

### Summary

Missing Zeta handling in `_handleFeeTransfer` will cause transaction reversion for users as any user calling `withdrawToNativeChain` with Zeta will trigger a failed token transfer on a placeholder address.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L341-L347

### Root Cause

In `GatewayTransferNative.sol:_handleFeeTransfer()` the function attempts to call `TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx)` where `zrc20` is `_ETH_ADDRESS_` (0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE), which is a placeholder address and not a valid ERC20 contract.


### Internal Pre-conditions

1. User needs to call `withdrawToNativeChain()` with `zrc20` parameter set to `_ETH_ADDRESS_`
2. Contract needs to have `feePercent` set to any value greater than 0


### External Pre-conditions

None

### Attack Path

1. User calls `withdrawToNativeChain()` with `zrc20 = _ETH_ADDRESS_` and sends Zeta via `msg.value`
2. Function proceeds to `_handleFeeTransfer(zrc20, amount)`
3. `_handleFeeTransfer` attempts to call `TransferHelper.safeTransfer(_ETH_ADDRESS_, EddyTreasurySafe, platformFeesForTx)`
4. Transaction reverts because `_ETH_ADDRESS_` is not a valid contract

### Impact

User cannot swap zeta to desired zrc20 token to be sent crosschain . All zeta swap to  zrc20 withdrawal attempts will revert, making the zeta functionality completely unusable.

### Mitigation

```diff
function _handleFeeTransfer(
    address zrc20,
    uint256 amount
) internal returns (uint256 platformFeesForTx) {
    platformFeesForTx = (amount * feePercent) / 1000;
-   TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+   if (zrc20 == _ETH_ADDRESS_) {
+       TransferHelper.safeTransferETH(EddyTreasurySafe, platformFeesForTx);
+   } else {
+       TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
+   }
}
```
