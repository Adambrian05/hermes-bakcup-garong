# Inconsistent DODO Address Configurability in `GatewaySend`: `DODOApprove` is Immutable

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L19

#### Summary
The `GatewaySend` contract exhibits an inconsistency in how it manages its DODO protocol dependencies. While it provides a mechanism for post-deployment updates of the `DODORouteProxy` address, it critically lacks a similar function to update the `DODOApprove` address. This renders `DODOApprove` immutable after the contract's deployment, hindering `GatewaySend`'s ability to fully adapt to future changes or security incidents within the DODO ecosystem without a full redeployment.

---

#### Root Cause
The inconsistency stems from the differing update capabilities for DODO-related addresses within the `GatewaySend.sol` contract:

1.  **`DODORouteProxy` is updateable:**
    The contract includes an `onlyOwner` function `setDODORouteProxy` to modify the `DODORouteProxy` address after deployment.
    ```solidity
    // File: GatewaySend.sol
    function setDODORouteProxy(address _dodoRouteProxy) external onlyOwner { // L85
        DODORouteProxy = IDODORouteProxy(_dodoRouteProxy); // L86
        emit DODORouteProxyUpdated(_dodoRouteProxy); // L87
    }
    ```

2.  **`DODOApprove` is immutable post-deployment:**
    Conversely, the `DODOApprove` address, which is also a critical external dependency used for ERC20 approvals in DODO swaps, is only set during the contract's construction. There is no `onlyOwner` (or similar privileged access control) function provided to update this address after the initial deployment.
    ```solidity
    // File: GatewaySend.sol
    address public DODOApprove; // L45 (No setter function found for this)
    // ...
    constructor(
        address zetaToken_,
        address dodoRouteProxy_,
        address dodoApprove_
    ) {
        // ...
        DODOApprove = dodoApprove_; // L69
        // ...
    }
    ```
This creates an internal inconsistency in the management of external DODO dependencies within the `GatewaySend` contract.

---

#### Internal Pre-conditions
None.

---

#### External Pre-conditions
* The DODO protocol upgrades its `DODOApprove` contract, invalidating the currently configured address in `GatewaySend`.
* A critical vulnerability is discovered in the specific `DODOApprove` contract currently integrated with `GatewaySend`, necessitating a switch to a patched version.
* The `DODOApprove` contract becomes deprecated, requiring `GatewaySend` to integrate with a new approval mechanism.

---

#### Attack Path / Scenario
This issue represents a **governance and operational rigidity** for the `GatewaySend` contract rather than a direct exploit path for a malicious actor.

1.  The `GatewaySend` contract is deployed, with its `DODORouteProxy` and `DODOApprove` addresses initially set.
2.  At some point in the future, the `DODOApprove` contract integrated with `GatewaySend` requires an update (e.g., due to an upgrade, deprecation, or discovery of a security vulnerability).
3.  The owner of `GatewaySend` is able to update `DODORouteProxy` if needed, but is **unable to update the `DODOApprove` address** due to the lack of a setter function.
4.  Consequently, `GatewaySend` continues to reference the **outdated or insecure `DODOApprove` contract**.
5.  Any attempts by users to perform swaps via DODO using `GatewaySend` that rely on the `DODOApprove` contract will:
    * Fail (if the old `DODOApprove` contract is deprecated or non-functional).
    * Expose users to vulnerabilities present in the old `DODOApprove` contract.
    * Encounter issues with token approvals required for DODO swaps.

---

#### Impact
* **Partial Operational Rigidity:** `GatewaySend` cannot fully adapt to necessary changes within the DODO ecosystem. While its router address can be updated, its `DODOApprove` address cannot, leading to potential incompatibility or exposure to risks if that specific contract needs to change.
* **Service Disruption and High Costs:** If the `DODOApprove` address needs an update, the only recourse is a full redeployment of the `GatewaySend` contract. 
* **Inability to Respond to Security Incidents:** In the event of a critical vulnerability being discovered in the `DODOApprove` contract, `GatewaySend` cannot quickly mitigate the risk by updating the address, leaving users exposed to potential issues related to approvals.
