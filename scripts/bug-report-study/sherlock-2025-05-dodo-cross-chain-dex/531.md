# Fixed gas limit configuration causes operational failures and user overpayment

### Summary

Dodo gateway contracts use a single, fixed `gasLimit` for all cross-chain operations and both main calls and revert callbacks. This creates operational risks where transactions fail due to insufficient gas, and on other hand, users constantly waste funds by overpaying for operations requiring less gas.

### Root Cause

`GatewaySend`, `GatewayCrossChain` and `GatewayTransferNative` all store the storage variable `gasLimit`. That fixed value is used for all [cross-chain calls](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L268) and for [onRevert recoveries](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L275). 

Different operations require different amount of gas. For example, a simple ETH cross-chain transfer is much more cheaper compared to cross-chain TX which requires Dodo swap from one asset to another and then additional Uniswap swap to get the gas-tokens to pay for fees. Also, the same `gasLimit` should cover the `onRevert` execution which writes at least 4 storage slots for `RefundInfo`. 

Problem is following - `gasLimit` should be set high enough to cover for the most expensive possible operation. And all users need to pay for that `gasLimit` every time they use the protocol, even though most times much lower `gasLimit` will be needed. And ZetaChain protocol does not give gas refunds.

### Attack Path

Scenario 1: Insufficient gas leading to failed operations

- Gas requirements increase on destination chains
- Fixed gasLimit becomes insufficient for complex operations
- Transactions fail, triggering revert mechanism
- Revert mechanism possibly fails as well due to not enough gas

Scenario 2: Overpayment due to uniform gas pricing

- User initiates simple operation (e.g., basic token transfer)
- Contract charges gas for complex operations (same gasLimit for all)
- User overpays significantly for simple operations
- Revert operations use same gas limit as main calls, causing further overpayment

### Impact

Medium severity - if `gasLimit` is not set high enough, complex user operations will fail since cross-chain TXs or revert recoveries will run out of gas. On the other hand, if `gasLimit` is set high enough to cover the most complex operations, that means users will routinely waste funds by overpaying the gas that is not used at all.

### Mitigation

Let user provide `gasLimit` as an input paramer, so that `gasLimit` can match the actual operation complexity
