# Lack of Post-Deployment gasLimit Mutability Can Lead to Cross-Chain Message Failures

### Summary

The gasLimit parameter is initialized once during the initialize() function call but cannot be updated thereafter. This design restricts the contract from adapting to evolving gas requirements on the destination chain, potentially resulting in message failures, fund lockups, or wasted gas. 

### Root Cause

The contract sets the gasLimit during initialize() and lacks any setter function or governance hook to update it later. Gas demand on destination chains may change, but the contract cannot accommodate such fluctuations, leading to potential execution failures.

### Attack Path

1. A user triggers a cross-chain transaction via send(...).

2. The destination contract requires more gas than the hardcoded gasLimit.

3. The transaction is sent but fails execution on the destination chain.

4. This can lead to:

- Message being marked failed and funds being locked.

- Users having to retry or request a manual refund.

- Repeated attempts consuming user funds or relayer gas.

### Impact

Messages may fail due to insufficient gas leads to DoS of the functionality.

### Mitigation

Introduce a setter function like other contracts to allow controlled updates to the gasLimit:

```solidity
function setGasLimit(uint256 newGasLimit) external onlyOwner {
    gasLimit = newGasLimit;
    emit GasLimitUpdated(newGasLimit);
}
```
