# Native ETH Refund Fails in GatewaySend::onRevert, Leading to Stuck Funds

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L396

https://github.com/zeta-chain/protocol-contracts/blob/2e61e029e89792c1b10ed15d2aa19818a77dd4d8/contracts/Revert.sol#L28



#### Summary
When a user initiates a cross-chain transfer involving a native asset (like ETH) via `GatewaySend.depositAndCall`, and the subsequent cross-chain execution fails, the protocol attempts to refund the user through `GatewaySend.onRevert`. However, for any native asset, the `RevertContext.asset` is `address(0)`, causing the `TransferHelper.safeTransfer` call within `onRevert` to revert. As `onRevert` is called in a separate transaction by the ZetaChain protocol, this failure prevents the refund, leading to the user's native asset becoming permanently stuck in the **protocol's TSS (Threshold Signature Scheme) address**.

---

#### Root Cause
The core of this vulnerability lies in the `GatewaySend.onRevert` function's inability to correctly handle native asset refunds due to an incompatible transfer mechanism.

The `onRevert` function is designed to process refund requests and is called by the ZetaChain protocol (e.g., via `GatewayEVM.executeRevert`) in a separate transaction from the initial `depositAndCall`. It receives a `RevertContext` struct containing details of the original transaction:

```solidity
/// @notice Struct containing revert context passed to onRevert.
/// @param sender Address of account that initiated smart contract call.
/// @param asset Address of asset. On a connected chain, it contains the fungible
/// token address or is empty if it's a gas token. On ZetaChain, it contains the
/// address of the ZRC20.
/// @param amount Amount specified with the transaction.
/// @param revertMessage Arbitrary data sent back in onRevert.
struct RevertContext {
    address sender;
    address asset;
    uint256 amount;
    bytes revertMessage;
}
```

As per the `RevertContext` definition, when the original transaction involved a native asset (e.g., the "gas token" on a connected chain), the `context.asset` field will be `address(0)`.

Within `GatewaySend.onRevert`, the refund attempt for the original asset occurs:

```solidity
// File: GatewaySend.sol
function onRevert(
    RevertContext calldata context
) external override onlyGateway {
    // ...
    TransferHelper.safeTransfer(context.asset, context.sender, context.amount); // L387
    // ...
}
```
At `L387`, `TransferHelper.safeTransfer(address(0), context.sender, context.amount)` is executed. The `TransferHelper.safeTransfer` function is typically implemented to handle ERC20 transfers (by calling `transfer` on the token contract) or perform a low-level `call` for native value. However, `address(0)` is not a contract address, and attempting to call an ERC20 `transfer` function on it, or a raw `call` without explicit value, will revert. This causes the entire `onRevert` transaction initiated by the protocol to fail.

---

#### Internal Pre-conditions
* The protocol's TSS address holds native assets that need to be refunded.
* The ZetaChain protocol attempts to execute `GatewaySend.onRevert` due to a prior cross-chain transaction failure involving a native asset.

---

#### External Pre-conditions
A user initiates a cross-chain transfer of a native asset (e.g., ETH) via `GatewaySend.depositAndCall`, and the subsequent cross-chain execution fails, triggering the `onRevert` flow.

---

#### Attack Path / Scenario
This is a **functional bug leading to fund loss** rather than a direct attack path.

1.  A **user** calls `GatewaySend.depositAndCall` with native assets (`msg.value`).
    * This `depositAndCall` transaction successfully transfers the user's native assets into the **protocol's custody (TSS address)**. This is a completed Ethereum transaction.
2.  The cross-chain operation, which began with this `depositAndCall`, encounters a failure on the destination chain or during an intermediate step.
3.  The ZetaChain protocol's internal system (e.g., via `GatewayEVM.executeRevert`) initiates a **new, separate Ethereum transaction** on the source chain to call `GatewaySend.onRevert(context)`.
4.  Within this `onRevert` call, `context.asset` is `address(0)` because the original asset was a native asset.
5.  At `L387`, `TransferHelper.safeTransfer(address(0), context.sender, context.amount)` is executed.
6.  This `safeTransfer` call on `address(0)` (which is not a contract and doesn't implement ERC20 `transfer` or a suitable fallback for direct native value transfer) **reverts**.
7.  Because the `safeTransfer` call reverts, the entire `onRevert` transaction itself reverts. This means the intended refund of the native asset fails to execute.

---

#### Impact
* **Permanent Loss of User Funds:** The user's native assets, which were originally successfully transferred into the **protocol's TSS address**, become permanently stuck and irrecoverable there. Since the `onRevert` transaction fails, there is no mechanism to return these funds to the user.
* **Critical Operational Failure:** The core refund mechanism for native assets is broken, leading to a critical functional defect for the protocol.
* **Negative User Experience and Trust Erosion:** Users who attempt to perform cross-chain transactions with native assets that later fail will experience unrecoverable loss of their funds, leading to severe distrust and dissatisfaction with the protocol.
