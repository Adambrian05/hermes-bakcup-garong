# Untrusted caller will spoof cross-chain messages

### Summary

The use of abi.decode() before verifying the caller will cause forged swap execution for the protocol as any malicious actor can call onCall() and simulate a legitimate cross-chain message from ZetaChain Gateway.

### Root Cause

In GatewayTransferNative.sol:449, the onCall() function decodes the message payload using abi.decode() prior to enforcing that msg.sender == address(gateway). If onlyGateway is ever removed, bypassed, or misconfigured, the function will process any arbitrary input as a valid cross-chain request.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L357-L424

### Internal Pre-conditions

1. [onlyGateway modifier is absent, removed, or incorrectly applied] on onCall()
2. [Caller sends] forged calldata mimicking a legitimate ZetaChain cross-chain payload

### External Pre-conditions

1. [ZetaChain infrastructure is used for cross-chain message passing]
2. [No cryptographic signature or payload validation is performed beyond msg.sender]

### Attack Path

1. Attacker constructs a fake message payload with a plausible DecodedNativeMessage
2. Attacker calls onCall() directly from an EOA or malicious contract
3. Function decodes and accepts forged data
4. Attacker receives funds, triggers swaps, or causes misaccounting

### Impact

The protocol suffers unauthorized swap execution or fund emission. The attacker gains unearned tokens, can execute mixSwap, drain liquidity routes, or abuse fee logic.

_No response_

### Mitigation

• Enforce onlyGateway modifier strictly and early in the function
• Move all abi.decode() calls after msg.sender validation
• Optionally bind message hashes to a signed digest (cryptographic origin validation)
