# Pending users refunds could be overridden by malicious actors due to absence of validation check

### Summary

Malicious actors could override pending refunds leading to permanent loss of funds without recovery due to lack of input validation.

### Root Cause

The [ GatewayCrossChain::onRevert/onAbort](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L550) is used to store failed crosschain actions so as to allow the initiator to claim the tokens involved.A refundInfo is modeled as a struct

```solidity
    struct RefundInfo {
        bytes32 externalId;
        address token;
        uint256 amount;
        bytes walletAddress;
    }

```
and stored as a mapping <bytes32 externalId,RefundInfo info> in the adapter.
Failed actions are entered into the mapping.So assuming there are pending refunds,A malicious user could craft a crosschain payload meant to fail and set the RevertOptions.revertAddress to the GatewayCrossChain address and the payload could be crafted as abi.encodePacked(externalId,walletAddress) the malicious actor could pick a valid refund externalId and craft the payload thereby overwriting the previous refundInfo for the externalId with a new amount and refundAddress.The actor could later claim their tokens losing only the percentage spent on calling the `onRevert` method but the previous RefundInfo which was overwritten would forever be lost in the adapter with no means to reclaim those tokens.

### Internal Pre-conditions

Pending Refunds exist in the GatewayCrossChain adapter

### External Pre-conditions

The actor crafts a crosschain payload that always revert sending any tokens of their choice

### Attack Path

1. Pending refunds exist in the GatewayCrossChain adapter.
2. Alice crafts a crosschain payload sending some tokens to a connected chain the transaction must revert to trigger the callback. revertOptions.revertAddress  is set to the adapter's address and the revertOptions.revertMessage  is set to the externalId of a valid refunds encoded with a wallet address
3. The Payload is submitted to the gateway on the hub chain and since it's crafted to revert the `onRevert()` method is called which overwrites all info of the specified `externalId`
4. The Attacker ends up losing only the amount used for the Crosschain call and onRevert while the target loses all their tokens.

### Impact

1. Permanent loss of user's refunds.

### Mitigation

//  Validate `RevertContext` to ensure only the adapter failed transactions could be processed into the refund queue
i.e

```solidity
  function onRevert(Revert calldata context)external{
    require(context.sender==address(this));
  }
```
