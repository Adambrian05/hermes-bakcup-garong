# Uniswap deadline is not working

### Summary

The deadline used for the UniV2 swaps is not sufficient and will allow swaps to be sandwiched. The reason is that `block.timestamp + MAX_DEADLINE` is used, which effectively means there’s no deadline, as the time of transaction finalization will be used.

[[GatewayCrossChain](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-blckhv/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L302C5-L335C6)](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex-blckhv/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L302C5-L335C6)

```solidity
function _swapAndSendERC20Tokens(
        address targetZRC20,
        address gasZRC20,
        uint256 gasFee,
        uint256 targetAmount
    ) internal returns(uint256 amountsOut) {
        // Get amountOut for Input gasToken
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );

        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);

        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE //<-----
        );

        require(IZRC20(gasZRC20).balanceOf(address(this)) >= gasFee, "INSUFFICIENT_GAS_FOR_WITHDRAW");
        require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");

        IZRC20(gasZRC20).approve(address(gateway), gasFee);
        IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);

        amountsOut = targetAmount - amounts[0];
    }
```

Note that the issue persists in both ZEVM contracts.

### Root Cause

Usage of `block.timestamp`  as deadline

### Internal Pre-conditions

NONE

### External Pre-conditions

NONE

### Attack Path

User submits swap with valid slippage at time `T1`, but for one reason or another, the transaction isn’t finalized. At time `T2`, the price has moved with > 10%, making his slippage stale, and due to the ineffective deadline, his swap will be able to be sandwiched by manipulating the token price in the pool to the old conditions, which were valid at the time of creating the transaction.

### Impact

Loss of funds, since the deadline is not effective and allows an arbitrary wait time until transaction finalization.

### PoC

N/A

### Mitigation

Allow the users to set their deadlines.
