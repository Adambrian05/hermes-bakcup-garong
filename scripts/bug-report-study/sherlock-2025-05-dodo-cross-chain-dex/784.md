# Token Mismatch in `withdrawToNativeChain` Leading to Refund Drain

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L530C5-L556C9


#### Summary
The `withdrawToNativeChain` function in `GatewayTransferNative` allows an attacker to manipulate the `zrc20` input parameter, leading to a token mismatch when combined with the `decoded.targetZRC20` from the `message` parameter. This flaw enables the attacker to force the contract to swap an arbitrary token (specifically, **valuable tokens held by the contract, including unclaimed refunds**) instead of the user's intended token, thereby draining the contract's balances.

#### Root Cause
The `withdrawToNativeChain` function (`L364-L440`) performs an initial `transferFrom` using the `zrc20` parameter supplied by the caller (`L365-L367`). However, later in the function, specifically within the `_doMixSwap` call (`L384`), the token used for the actual swap is `params.fromToken`, which is derived from `SwapDataHelperLib.decodeMessage(message)` (`L376`) and then `MixSwapParams memory params`. There is no check to ensure that the `zrc20` provided by the user in `withdrawToNativeChain` matches `params.fromToken` from the decoded `message`.

#### Internal Pre-conditions
* The `GatewayTransferNative` contract must hold a balance of a valuable ERC20 token that an attacker wants to drain. These tokens often accumulate from **unclaimed refunds** stored in the `refundInfos` mapping (`L56`).
* An attacker must be able to craft a malicious `message` parameter that includes `swapData` where `params.fromToken` points to the valuable token held by the contract, and `params.toToken` is a token they wish to receive.

#### External Pre-conditions
None.

#### Attack Path
1.  **Attacker** identifies a valuable ERC20 token (e.g., Token X) held by the `GatewayTransferNative` contract. This could be an unclaimed refund from a previous cross-chain transaction.
2.  **Attacker** crafts a malicious `message` payload. This `message` is constructed such that when `SwapDataHelperLib.decodeMessage(message)` is called, the resulting `params.fromToken` (`L376`) is the address of Token X (the valuable token held by `GatewayTransferNative`). `params.fromTokenAmount` is set to the amount of Token X to be drained, and `params.toToken` is set to a token the **attacker** wants to receive (e.g., WETH).
3.  **Attacker** calls the external `GatewayTransferNative::withdrawToNativeChain` function (`L364`):
    ```solidity
    function withdrawToNativeChain(
        address zrc20, // Attacker's arbitrary/low-value token (e.g., Token Y)
        uint256 amount, // Arbitrary amount of attacker's token
        bytes calldata message // Crafted payload for params.fromToken = victim token (Token X)
    ) external payable {
        if(zrc20 != _ETH_ADDRESS_) {
            // REQUIRES THE ATTACKER TO TRANSFER THE TOKEN HE IS TRYING TO SWAP (Token Y)
            require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED"); // L365-L367
        }
        // ...
        // Decodes message, params.fromToken will be Token X (the victim token)
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(message); // L376
        // ...
    }
    ```
    The **attacker** supplies a low-value or worthless token as the `zrc20` parameter (e.g., Token Y) along with a nominal `amount`. This `zrc20` (Token Y) is transferred from `msg.sender` (the **attacker**) to `GatewayTransferNative`. **Crucially, while the attacker transfers Token Y, the crafted `message` directs the contract to *swap Token X* from its internal balance.**
4.  Further down in `GatewayTransferNative::withdrawToNativeChain`, the function calls the internal `_doMixSwap` function (`L384`):
    ```solidity
    // Swap on DODO Router
    uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
    ```
5.  Inside `GatewayTransferNative::_doMixSwap` (`L325`):
    ```solidity
    function _doMixSwap(
        bytes memory swapData,
        uint256 amount,
        MixSwapParams memory params // params where params.fromToken is Token X
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }
        // Approves DODOApprove for Token X from GatewayTransferNative's balance
        IZRC20(params.fromToken).approve(DODOApprove, amount); // L331
        // Swaps Token X from GatewayTransferNative's balance
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}( // L332
            params.fromToken, // This is Token X
            params.toToken,
            params.fromTokenAmount,
            // ... (rest of swap params)
        );
    }
    ```
    The `_doMixSwap` function uses `params.fromToken` (which is Token X, the valuable token held by the contract from the **attacker**'s crafted `message`) for the `approve` and `mixSwap` calls. Since the contract holds a balance of Token X (e.g., from an unclaimed refund), it successfully approves and then swaps Token X from its own reserves.
6.  The `mixSwap` operation completes, converting Token X into `params.toToken` (e.g., WETH). The resulting `outputAmount` is returned.
7.  The `outputAmount` of `params.toToken` is then used in subsequent withdrawal logic (`_handleBitcoinWithdraw` or `_handleEvmOrSolanaWithdraw`, `L388` and `L400`) to send the swapped tokens to the **attacker**'s controlled `receiver` address on the destination chain.
#### Impact
The **protocol** suffers an approximate loss of **potentially all valuable ERC20 tokens held by `GatewayTransferNative` (including unclaimed refunds)** that an **attacker** can identify and target by manipulating the `message` parameter. The **attacker** gains the corresponding swapped tokens on the destination chain.
