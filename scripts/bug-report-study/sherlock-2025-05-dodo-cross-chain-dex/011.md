# Revert Message Manipulation - Cross-chain fund redirection

### Summary

Insufficient revert message validation will cause complete fund theft for legitimate cross-chain transaction users as malicious actors will craft 52-byte revert messages containing attacker-controlled addresses to redirect reverted funds during failed cross-chain transactions.

### Root Cause

In GatewayCrossChain.sol:517 and GatewayTransferNative.sol:607 the onRevert function lacks validation that the address extracted from the revert message matches the original transaction sender, allowing arbitrary address injection via crafted 52-byte messages

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607

### Internal Pre-conditions

1. Gateway contracts need to be initialized and funded with tokens to have sufficient balance for revert transfers
2. Cross-chain transaction needs to be initiated by a legitimate user to create a valid transaction context
3. Revert scenario needs to be triggered to activate the onRevert() function execution path
4. Attacker needs to craft revert message to be exactly 52 bytes in length to bypass length validation checks
5. Gateway ZEVM needs to call onRevert() to execute the vulnerable revert message processing logic

### External Pre-conditions

1. Cross-chain transaction needs to fail on the destination chain to trigger the revert mechanism back to the source chain
2. ZetaChain ZEVM gateway needs to receive and process the revert notification from the external chain infrastructure
3. Network conditions need to allow the revert message to be transmitted back through the cross-chain messaging protocol
4. External chain gas limits or execution failures need to cause transaction reversion to initiate the onRevert flow

### Attack Path

1. Attacker initiates a cross-chain transaction calling call() or deposit() with legitimate parameters but crafted revert options
2. Attacker ensures the destination chain transaction fails by providing insufficient gas, invalid parameters, or other failure conditions
3. External chain infrastructure detects the transaction failure and triggers the cross-chain revert mechanism
4. ZetaChain ZEVM gateway receives the revert notification and prepares to call onRevert()
5. Attacker's pre-crafted revert message (exactly 52 bytes: 32-byte externalId + 20-byte attacker address) gets processed by the gateway
6. Gateway calls onRevert() with RevertContext containing the malicious revert message
7. onRevert() function extracts the attacker's address from bytes 32-52 of the revert message without validation
8. Contract executes TransferHelper.safeTransfer() sending the reverted funds directly to attacker's address instead of legitimate user
9. Attacker receives the stolen funds while legitimate user gets nothing

### Impact

The legitimate cross-chain transaction users suffer a complete loss of their reverted funds (100% of transaction amount). The attacker gains the full amount of the stolen reverted funds from multiple victims.

### Mitigation

Add recipient address validation in the onRevert() function to ensure the address extracted from the revert message matches the original transaction sender:
```solidity
if(context.revertMessage.length == 52) {
    address receiver = address(uint160(bytes20(walletAddress)));
    require(receiver == context.sender, "REVERT_RECIPIENT_MISMATCH");
    TransferHelper.safeTransfer(context.asset, receiver, context.amount);
}
```
