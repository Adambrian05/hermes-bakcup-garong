# Hub chain contracts `onAbort` and `onRevert` functions doesn't verify sender resulting in manipulated message values

### Summary

[onRevert](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L607-L608) and [onAbort](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L640-L641) functions are used to handle failed on destination message. In the context that `GatewayCrossChain/GatewayTransferNative` are the contracts on source (Zeta Chain), those functions should be invoked if a message from `ZetaChain -> Any other chain`  fails on destination. (or `onAbort` if destination `onRevert` fails) 
First we try to execute `onRevert`, but if it's not possible, we execute `onAbort`.
In our context we will update storage var to account for the funds that are waiting to be claimed:
```solidity
    function onAbort(AbortContext calldata abortContext) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(abortContext.revertMessage[0:32]);
        bytes memory walletAddress = abortContext.revertMessage[32:];

        RefundInfo memory refundInfo = RefundInfo({
            externalId: externalId,
            token: abortContext.asset,
            amount: abortContext.amount,
            walletAddress: walletAddress
        });
        refundInfos[externalId] = refundInfo;
        
        emit EddyCrossChainRefund(
            externalId,
            abortContext.asset,
            abortContext.amount,
            walletAddress
        );
    }
```
The problem is that both functions (onAbort and onRevert) in both contracts (GatewayTransferNative, GatewayCrossChain) don't check `AbortContext/RevertContext.sender` of the message, which is the address that initialized the cross-chain transaction. This means that malicious user can send a transaction that he knows will revert directly to `GatewayZEVM` and provide `GatewayTransferNative/GatewayCrossChain` address as `revertAddress` for `RevertOptions` and arbitrary data for `bytes revertMessage`. 
This means that the exploiter can provide existing `externalId`, which is waiting to be claimed and override the original asset and amount in `refundInfos` array.

### Root Cause

`onRevert` and `onAbort` fails to validate `sender` both in `GatewayTransferNative.sol` and `GatewayCrossChain.sol` contracts

### Internal Pre-conditions

Having a refund transaction on ZetaChain contract

### External Pre-conditions

Exploiter sets `GatewayTransferNative.sol` as a `revertAddress` if initiated executed from hub

### Attack Path

1. In `GatewayTransferNative.sol` there is a 1 ETH waiting to be refunded for `externalId = x`
2. Malicious actor initiates a bridge message from ZetaChain to any other chain with a dust amount of zrc20 directly calling `GatewayZEVM`. He sets `GatewayTransferNative.sol` as a `revertAddress` and makes so the destination receiver reverts
3. The transaction reverts and calls Dodo's `GatewayTransferNative.sol::onRevert` func. 
4. Because user has control over the whole message and format, he can make `(context.revertMessage.length != 52)`  and force the func into the `else` block, which will result in overriding the valid `refundInfos[externalId]` value

### Impact

Loss of funds for victims.
The funds are locked in the Zetachain contract/s


### PoC

_No response_

### Mitigation

- Introduce a check in onRevert and onAbort to ensure that the corresponding context `.sender` is a trusted contract address.
