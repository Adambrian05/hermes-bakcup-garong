# Assumes existence of WZETA pool for all tokens in `GatewayCrossChain::getPathForTokens`, causing swap failures

### Summary

Hardcoded assumption of WZETA pool existence will cause swap path resolution failures for users/traders as the router will attempt to build invalid paths through non-existent WZETA liquidity, leading to failed swaps or degraded UX.

### Root Cause

In `GatewayCrossChain.sol:getPathForTokens`, there is a flawed assumption in the implementation that every supported token has an available liquidity pool with `WZETA`. The function constructs a swap path by defaulting through `WZETA` without verifying if such a pair actually exists via the connected DEX router. This results in swap paths being generated that are invalid or non-functional in cases where no liquidity pool exists between the source or destination token and `WZETA`. As a consequence, token swaps that rely on this logic will revert or fail silently depending on downstream handling, leading to broken cross-chain swaps or bridging operations. The lack of validation introduces a systemic fragility in the swapping mechanism and can cause user funds to become stuck or unusable until manually recovered. This issue stems from a design oversight where flexibility was sacrificed for simplicity, without accounting for real-world liquidity availability.

### Internal Pre-conditions

1. `_swapAndSendERC20Tokens`  calls `getPathForTokens()` expecting a valid WZETA pool path.
2. No pool exists between zrc20 and targetZRC20 
3. Enter the else in `getPathForTokens` and make a path but some tokens does not have pools with WZETA.
4. Router accepts invalid swap paths without checks leading to DoS because we use invalid path for the tokens

### External Pre-conditions

1. The external pool between the token and WZETA must be absent or illiquid.

### Attack Path

1. User calls `GatewayCrossChain::getPathForTokens` requesting a swap path involving a token without a WZETA pool.
2. The function attempts to construct a route using WZETA as an intermediary but fails due to the missing pool.
3. The swap transaction either reverts or executes with an invalid path, causing failed swaps or stuck funds.
4. User experiences failed transactions or unexpected behavior due to the faulty routing logic.

### Impact

The users suffer a Denial of Service (DoS) and cannot execute token swaps involving certain supported tokens because the routing logic assumes all tokens have a WZETA pool, which is not true. This results in failed transactions and loss of usability, but no direct financial loss or gain.

### Mitigation

Update the `GatewayCrossChain::getPathForTokens` function to dynamically verify the existence of a liquidity pool between the given token and WZETA before constructing the swap path. If no direct pool exists, implement fallback logic to find alternative routes.
