# Unauthorized Non-EVM Refund Claim

### Summary

The bug allow attackers to steal non-EVM (Bitcoin/Solana) refunds due to improper validation in the `claimRefund` function. Malicious actors can bypass authorization checks and drain funds intended for cross-chain users for any valid ID passed in the params.

### Root Cause

In [GateWayTransferNative.ClaimRefund](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571-L589)
```solidity
 function claimRefund(bytes32 externalId) external {
        RefundInfo storage refundInfo = refundInfos[externalId];

        address receiver = msg.sender;   // @>
        if(refundInfo.walletAddress.length == 20) {
            receiver = address(uint160(bytes20(refundInfo.walletAddress)));
        }
        require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");   // @> always true for non evm
        require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
        
        TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
        delete refundInfos[externalId];

        emit EddyCrossChainRefundClaimed(
            externalId,
            refundInfo.token,
            refundInfo.amount,
            abi.encodePacked(msg.sender)
        );
    }
```
For non-EVM refunds (`walletAddress.length != 20`), `receiver` defaults to `msg.sender`
=> `msg.sender == receiver` becomes true
So Authorization check passes for any caller.

### Internal Pre-conditions

1. Refund stored with `walletAddress.length` > 20 (non-EVM)
2. `refundInfos[externalId].amount` > 0

### External Pre-conditions

1. Failed cross-chain transaction to Bitcoin/Solana

### Attack Path

1. User's Bitcoin withdrawal fails → onRevert() stores:
```solidity
refundInfos[id] = RefundInfo({
  walletAddress: "bc1qxy2kgdygjrsqtzq2n0yrf2493p83kkfjhx0wlh" // 42 bytes
});
```
2. Attacker calls claimRefund(id)
`walletAddress.length` != 20 → receiver = msg.sender (attacker)
`msg.sender == receiver` → check passes
3. Funds transferred to attacker instead of Bitcoin address

### Impact

1. Theft of all non-EVM refunds
2. Fund loss for cross-chain users

### Mitigation

Explicit require(bots[msg.sender]) for non-20-byte addresses, then No fallback to msg.sender for non-EVM cases
Something like this 
```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refund = refundInfos[externalId];
    require(refund.externalId != "", "REFUND_NOT_EXIST");
    
    if (refund.walletAddress.length == 20) {
        address evmReceiver = address(uint160(bytes20(refund.walletAddress)));
        require(bots[msg.sender] || msg.sender == evmReceiver, "UNAUTHORIZED");
        TransferHelper.safeTransfer(refund.token, evmReceiver, refund.amount);
    } else {
        require(bots[msg.sender], "ONLY_BOT_CAN_CLAIM_NON_EVM");
        TransferHelper.safeTransfer(refund.token, msg.sender, refund.amount);
    }
    
    delete refundInfos[externalId];
    emit EddyCrossChainRefundClaimed(...);
}
```
