# A lack of swap data validation on the fromToken/targetToken/ZRC20 allows malicious users to exploit cross-chain/native gateways in multiple ways

### Summary

All gateways lack logic for swap data validation, but this report will focus on the exploitation of it in the cross-chain and native gateway.
Due to how the methods are structured with the actual zrc20 token, the fromToken, targetToken and the fact that the gateways are supposed to hold token balances (due to onRevert / onAbort), users can utilize this in multiple ways in order to "steal" the underlying balances.

### Root Cause

There are multiple ways to exploit the protocol logic due to lack of strict checks on swap data in both the native and cross-chain gateway, but this report will focus on two. Cross-chain gateway will be taken as an example although the native one is able to be exploited as well.

**Case no. 1 (GatewayCrossChain) -> param.fromToken is never checked against the ZRC20 in onCall:**

When onCall is invoked on the cross-chain gateway by the ZetaChain Gateway in this case:

```solidity

 function onCall(
        MessageContext calldata context,
        address zrc20,
        uint256 amount,
        bytes calldata message
    ) external onlyGateway {
        // Decode the message: 32 bytes(externalId) + bytes message
        (bytes32 externalId) = abi.decode(message[0:32], (bytes32)); 
        bytes calldata _message = message[32:];

        // Decode message and decompress swap params
        (DecodedMessage memory decoded, MixSwapParams memory params) = SwapDataHelperLib.decodeMessage(_message);

        // Transfer platform fees
        uint256 platformFeesForTx = _handleFeeTransfer(zrc20, amount); // platformFee = 5 <> 0.5%
        amount -= platformFeesForTx;

        // Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);

```
The ZRC20 which was bridged from the connected chain is passed to DODO's gateway. After performing the swap decodings as well as the fee transfer, if the user passed swap data in the message, `_doMixSwap` will use the DODO swap router to swap it to the target token.

```solidity

 function _doMixSwap(
        bytes memory swapData, 
        uint256 amount, 
        MixSwapParams memory params
    ) internal returns (uint256 outputAmount) {
        if (swapData.length == 0) {
            return amount;
        }

        IZRC20(params.fromToken).approve(DODOApprove, amount);
        return IDODORouteProxy(DODORouteProxy).mixSwap(
            params.fromToken,
            params.toToken,
            params.fromTokenAmount,
            params.expReturnAmount,
            params.minReturnAmount,
            params.mixAdapters,
            params.mixPairs,
            params.assetTo,
            params.directions,
            params.moreInfo,
            params.feeData,
            params.deadline
        );

```

Imagine the following scenario, the contract holds 10 BNB due to a failed call (revert). The user bridged 10 PEPE which has a significantly lower price than the BNB (this is the ZRC20 token which was actually bridged and sent to this gateway).

Since the logic never validated if the ZRC20 == the params.fromToken, this param is used to approve the amount (10e18). So now we're using the underlying balance of 10 BNB which belongs to someone else in order to perform the swap.

BNB price: 650 USD per token unit;
PEPE price: 0.000011 USD per token unit;

So for the price of 0.00011 USD we're swapping 6500 USD worth of BNB to ETH for example (which is the target token). Let's say that this equals 3 ETH. 

After the DODO router performs the swap, the outputAmount (3 ETH) can be used to send it to a user on another connected chain -> mainnet for example:
