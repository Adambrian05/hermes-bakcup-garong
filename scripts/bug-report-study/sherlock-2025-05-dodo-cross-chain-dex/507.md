# Bitcoin refunds in onRevert are sent to uncontrolled EVM Addresses and permanently lost

### Summary

When `GatewayCrossChain` processes failed cross-chain TXs in `onRevert`, Bitcoin refunds are automatically sent to EVM addresses derived from truncated Bitcoin addresses, causing permanent loss of funds. The `withdraw` function truncates Bitcoin addresses to 20 bytes and treats them as EVM addresses, but these derived addresses are not controlled by the original Bitcoin users.

### Root Cause

When the destination of the cross-chain TX is Bitcoin, function [withdraw](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277) is called in the `GatewayCrossChain`. Function will truncate the Bitcoin address to 20 bytes and encode it in the `revertMessage`:
```solidity
    function withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount) internal {
        gateway.withdraw(
            sender,
            amount,
            outputToken,
            RevertOptions({
                revertAddress: address(this),
                callOnRevert: true,
                abortAddress: address(0),
                // @audit 'sender' (in reality bitcoin receiver address) is encoded and later used as refund receiver
                revertMessage: bytes.concat(externalId, bytes20(sender)), 
                onRevertGasLimit: gasLimit
            })
        );
    }
```
If cross-chain TX fails on Bitcoin side, protocol will trigger [onRevert](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517C1-L548C6) function of the `GatewayCrossChain`. The 'sender' (bitcoin receiver address) that was encoded in `revertMessage` is used as refund receiver:
```solidity
    function onRevert(RevertContext calldata context) external onlyGateway {
        // 52 bytes = 32 bytes externalId + 20 bytes evmWalletAddress
        bytes32 externalId = bytes32(context.revertMessage[0:32]);
        bytes memory walletAddress = context.revertMessage[32:];

        if (context.revertMessage.length == 52) {
             // @audit previously truncated bitcoin address is used here as EVM refund receiver
            address receiver = address(uint160(bytes20(walletAddress))); 
            TransferHelper.safeTransfer(context.asset, receiver, context.amount);
            // ....
```
Since `context.revertMessage.length == 52` is true (32 bytes id + 20 bytes bitcoin address), function  immediately transfers funds to the truncated address interpreted as an EVM address. But that EVM address is uncontrolled (ie. no known private key), since that's actually a Bitcoin address. Thus funds are permanently lost.

### Internal Pre-conditions

None

### External Pre-conditions

Cross-chain transaction to Bitcoin fails. Refund mechanism activates via onRevert.

### Attack Path

This is not an attack but a systematic loss of funds:

1. User initiates cross-chain transaction to Bitcoin
2. Transaction fails on Bitcoin side
3. Protocol truncates Bitcoin address to 20 bytes and stores it for refund processing
4. Refund is automatically sent to the truncated address interpreted as an EVM address
5. Funds are permanently lost since this EVM address is not controlled by the original user

### Impact

High severity - this vulnerability causes 100% loss of all Bitcoin refunds

### PoC

_No response_

### Mitigation

Bitcoin refunds can be handled similar to Solana refunds - stored in `RefundInfo` for manual claiming by trusted bots, rather than attempting automatic transfer to truncated addresses.
