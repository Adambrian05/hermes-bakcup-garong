`GatewayTransferNative` has a payable receive function to receive these funds. This means users won't be able to deposit Zeta on an EVM chain and swap to a ZRC20 on Zetachain, wasting their gas and breaking a portion of the protocol's functionality. 

### Root Cause

GatewayZEVM unwraps and transfers native Zeta tokens directly to GatewayTransferNative before calling onCall, resulting in a zero msg.value when swapping via the non-payable onCall, causing the Dodo Router to revert.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L435

### Internal Pre-conditions

1. A user must deposit Zeta and then swap Zeta to another ZRC20 on Zetachain

### External Pre-conditions

N/A

### Attack Path

1. User calls `GatewaySend::depositAndCall`, specifying Zeta as the asset and `GatewayTransferNative` as the `targetContract`.
2. GatewayZEVM sends native Zeta to the payable receive function of GatewayTransferNative.
3. GatewayZEVM subsequently calls the non-payable GatewayTransferNative::onCall (so msg.value is 0)
4. GatewayTransferNative::onCall triggers _doMixSwap, requiring a non-zero msg.value for Zeta swaps via the Dodo Router.
5. Dodo Router reverts the transaction due to mismatch between msg.value (zero) and the expected amount, preventing successful swaps and causing user gas loss.

### Impact

Users attempting to deposit Zeta and swap to ZRC20 via GatewayTransferNative experience transaction reverts, resulting in lost gas and broken swap functionality.

### Mitigation

It'd probably be best to keep track of native tokens balances before and after each onCall. Then you can subtract the after amount minus before amount and pass that into the value field for the DodoRouter instead of msg.value.
