# Users cant claim their refund if their refunded token is native token

## Vulnerability Details
The `GatewayTransferNative::claimRefund` function incorrectly assumes the refunded token is always zec20 token, So it uses `TransferHelper::safeTransfer` function to transfer token back to the user ([link to code](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L671)). 

```solidity
    function claimRefund(bytes32 externalId) external {
      ...
        
@>    TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
      delete refundInfos[externalId];
      
      ...
    }
```
However the refunded token could be zetachain native token. in this scenario the `claimRefund` function will revert causing loss of funds for users.

## POC
In a test bellow `user1` cant claim refund of aborted transaction when the token is native token.the test fails because of that.
Copy the test bellow to the `GatewayTransferNative.t.sol` file. 
```solidity
  function testClaimRefundETH() public {
      bytes32 externalId = keccak256(abi.encodePacked(block.timestamp));
      uint256 amount = 100 ether;
      vm.deal(address(gatewayTransferNative), amount);
      vm.prank(address(gatewayZEVM));
      gatewayTransferNative.onAbort(
          AbortContext({
              sender: abi.encode(address(this)),
              asset: _ETH_ADDRESS_, // @auditor asset is native token
              amount: amount,
              outgoing: false,
              chainID: 7000,
              revertMessage: bytes.concat(externalId, bytes20(user1))
          })
      );

      uint256 beforeBalance = user1.balance;
      vm.prank(user1);
      gatewayTransferNative.claimRefund(externalId);
      uint256 afterBalance = user1.balance;
      assertEq(beforeBalance + amount, afterBalance);
  }
```
## Impact
Users whose transactions are reverted cannot claim their refunds by the `GatewayTransferNative::claimRefund` function if their original token is the native token, which result in a loss of funds for them.

## Mitigation
Consider modifying the `claimRefund` function to correctly handle the case when `refundInfo.token` is the native token, such as by checking if `refundInfo.token` equals `_ETH_ADDRESS_` and using `TransferHelper::safeTransferETH` instead of `safeTransfer` in that scenario.

```diff
  function claimRefund(bytes32 externalId) external {
      ...

-   TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
+   if(refundInfo.token == _ETH_ADDRESS_) {
+       TransferHelper.safeTransferETH(receiver, refundInfo.amount);
+   } else {
+       TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
+   }
      ...      
  }
```
