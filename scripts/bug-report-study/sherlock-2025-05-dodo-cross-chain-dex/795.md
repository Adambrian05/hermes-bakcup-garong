# Unsafe Truncation of Dynamic sender Bytes in withdraw function

## Description
The root cause is in the function withdraw, the sender parameter is a dynamic bytes array, and the code assumes it can be cast to bytes20 in bytes.concat(externalId,bytes20(sender)). If sender is shorter than 20 bytes, the cast will pad it with zeros, which is intentional. However, if sender is longer than 20 bytest, the cast truncates it, potentially lossing critical data.
Issue breakdown

```solidity
bytes.concat(externalId, bytes20(sender))
```
This line attempts to cast sender (of type bytes, which is dynamically sized) to bytes20 before concatenating it with externalId. This operation has unsafe and potentially unintended side effects depending on the length of sender.

If sender.length > 20:
Solidity truncates the value to the first 20 bytes (left-aligned).

 This is unsafe, as it loses the trailing data, which might be essential, especially if sender encodes complex or sensitive information (e.g., a serialized structure, BTC address, etc.).

Why This Matters
The resulting revertMessage built with bytes.concat(externalId, bytes20(sender)) may not accurately represent the sender.

 Impact
Truncating sender to bytes20 can:

Cause incorrect sender identification, especially when sender encodes non-EVM data like a BTC address.

Lead to fund misrouting or revert misattribution, particularly in cross-chain bridges or token gateways.

## Recommendation
Ensure that the full sender data is preserved when creating the revertMessage. For example:
```solidity
revertMessage: bytes.concat(externalId, sender)
```
If exactly 20 bytes are needed, validate and enforce it beforehand, with clear error messages to avoid silent truncation:
```solidity
require(sender.length == 20, "Sender must be exactly 20 bytes");
revertMessage: bytes.concat(externalId, sender)
```
Alternatively, if truncation is truly desired (e.g., for backward compatibility), document it explicitly and make sure upstream code complies.
