# ClaimRefund funds can be stolen by anybody

### Summary

Hardcoded wallet address length check will cause fund theft when cross chain transaction is sent to solana chain when a transaction is failed for any reason an attacker can steal non-EVM address users refunds by exploiting the authorization logic when wallet addresses exceed 20 bytes (as solana addresses are 32 bytes)

### Root Cause

In GatewayTransferNative.sol:claimRefund() the hardcoded 20-byte address check causes the receiver to default to msg.sender(whenever a solana wallet is used as its 32 bytes), allowing anyone to pass the authorization check and steal refunds intended for Solana users https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L661-L671
When a Solana address (32 bytes) is stored, the if condition fails, receiver remains as msg.sender, and the authorization check msg.sender == receiver always passes for any caller.

### Internal Pre-conditions

The cross-chain transaction needs to fail and trigger a revert that stores refund info
The stored wallet address needs to be longer than 20 bytes which it is due to = (Solana addresses  = 32 bytes)


### External Pre-conditions

Cross-chain transaction failure occurs due to external factors (network congestion, insufficient gas, slippage, etc.)
Gateway contract triggers onRevert() which stores the refund info instead of direct transfer when the if condition fails(which it does)

### Attack Path

to understand this issue better here is a scenario 
-Victim initiates cross-chain swap from zetachain to Solana with 32-byte Solana wallet address as the receiving address (they use the function withdrawToNativeChain)
-Transaction fails on destination chain and Gateway calls onRevert() can fail due to various reasons 
-Contract stores refund info because context.revertMessage.length == 52 (it's 64 bytes: 32 externalId + 32 Solana address)
-A malicious users observes the mempool and sees the transaction fail on the other network and wait for the gateway to call onrevert( with the revert message) 
-now after the transaction onrevert is completed the malicious user can front run everyone and call claimRefund(externalId) with the victim's external ID
-Contract sets receiver = msg.sender (attacker's address) because refundInfo.walletAddress.length != 20
-Authorization check passes because msg.sender == receiver (attacker's address)
-Refund tokens are transferred to attacker instead of the original victim
-Attacker successfully steals the victim's refund
so basically whenever a zeta to solana transaction is failed funds that are coming back to onRevert can be stolen by an attacker
### Impact

Users suffer complete loss of their refund amounts to attackers when cross-chain transactions fail. Attackers gain the entire refund value by simply calling claimRefund() with publicly visible external IDs, 
This is a huge profit attack and requires no funds to do just gas fee and huge profits 
for example if a cross chain transaction failed was worth 10k usd ( which is common) attacker can steal it without any work
