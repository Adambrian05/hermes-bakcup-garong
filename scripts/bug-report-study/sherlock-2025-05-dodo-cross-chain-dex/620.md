# Unauthorized Access to Withdrawal Function

### Summary

The `withdraw` function in GatewayTransferNative.sol is declared as public, allowing any external caller to invoke withdrawal operations that should only be accessible internally within the contract's cross-chain operation flow.

### Root Cause

The vulnerability exists in the https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286, where the `withdraw` function is declared with public visibility instead of internal visibility. This function is designed to facilitate withdrawals through the ZetaChain gateway as part of the cross-chain operation workflow, but its public accessibility creates a significant security risk.

The function signature reveals the problematic access control:

```solidity
function withdraw(
    bytes32 externalId,
    bytes memory sender,
    address outputToken,
    uint256 amount
) public {
    gateway.withdraw(
        sender,
        amount,
        outputToken,
        RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: address(0),
            revertMessage: bytes.concat(externalId, bytes20(sender)),
            onRevertGasLimit: gasLimit
        })
    );
}
```

This vulnerability breaks the security guarantee that withdrawal operations should only occur as part of legitimate cross-chain transactions initiated through the proper channels (onCall or withdrawToNativeChain functions). A malicious actor could potentially exploit this by calling the withdraw function directly with crafted parameters, bypassing the intended transaction flow and fee collection mechanisms.

The vulnerability manifests when the contract holds token approvals to the gateway contract. In such scenarios, an attacker could invoke the public withdraw function with arbitrary parameters, potentially draining approved tokens from the contract. The execution path that leads to this vulnerability begins with any external caller having the ability to invoke the withdraw function directly, which then calls the gateway's withdraw method without proper authorization checks.

The root cause stems from incorrect access control implementation, where the function visibility was set to public instead of internal. This violates the principle of least privilege and creates an unintended attack surface. The function should only be callable from within the contract itself as part of the legitimate cross-chain operation flow, specifically from the `_handleBitcoinWithdraw` function and similar internal operations.

### Internal Pre-conditions

The vulnerability requires specific preconditions to be exploitable, primarily that the contract must hold token approvals to the gateway contract. However, this is a common operational state for the contract during normal cross-chain operations, making exploitation feasible.

### External Pre-conditions

The discoverability of this vulnerability is relatively high, as the public function visibility is easily identifiable through contract interface analysis or blockchain explorers. The technical complexity of exploitation is low, requiring only basic knowledge of contract interaction and the ability to craft appropriate function parameters.

The likelihood is somewhat mitigated by the fact that the contract's token holdings and approvals are typically transient, existing only during active cross-chain transactions. However, the high frequency of cross-chain operations in a production environment increases the window of opportunity for potential attackers.

### Attack Path

To execute this exploit:

1. Identify when the GatewayTransferNative contract has token approvals to the gateway
2. Call the `exploitPublicWithdraw` function with the target contract address
3. Specify the token address and amount to withdraw
4. The function will bypass all intended security checks and fee collection

### Impact

The high impact assessment is justified by the potential for unauthorized fund drainage from the contract. If the GatewayTransferNative contract holds any token approvals to the gateway contract, an attacker could exploit this vulnerability to withdraw tokens without going through the proper cross-chain transaction flow. This could result in direct financial loss to users who have initiated legitimate cross-chain transactions.

The vulnerability also undermines the integrity of the fee collection mechanism, as attackers could bypass platform fees by calling the withdraw function directly. This could lead to significant revenue loss for the protocol operators. Furthermore, the unauthorized withdrawals could disrupt the cross-chain transaction flow, potentially causing legitimate transactions to fail due to insufficient token balances.

### Mitigation

The immediate fix requires changing the function visibility from public to internal:

```diff
- function withdraw(
+ function _withdraw(
    bytes32 externalId,
    bytes memory sender,
    address outputToken,
    uint256 amount
- ) public {
+ ) internal {
    gateway.withdraw(
        sender,
        amount,
        outputToken,
        RevertOptions({
            revertAddress: address(this),
            callOnRevert: true,
            abortAddress: address(0),
            revertMessage: bytes.concat(externalId, bytes20(sender)),
            onRevertGasLimit: gasLimit
        })
    );
}
```

Additionally, update all internal calls to use the new function name `_withdraw` instead of `withdraw`. This change ensures that the withdrawal functionality remains accessible only to the contract's internal operations while preventing unauthorized external access.
