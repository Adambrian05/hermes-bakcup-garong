# Users can bypass protocol fees by performing same-token transfers

### Summary

The [`onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L363) function, which handles the final leg of a cross-chain transaction, contains a special logic path for when the input token and output token are the same (`fromToken == toToken`). This path bypasses the call to [`_doMixSwap`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L195), which is the required entry point to the [`DODOFeeRouteProxy`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1392) where protocol fees are collected. This allows a user to leverage the protocol's cross-chain infrastructure to perform simple token transfers without paying the intended service fees.

### Root Cause

The root cause is a conditional check in the [`onCall`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L363) function that creates a fee-less execution path, bypassing the entire fee collection mechanism.

The intended fee-taking process is as follows:
1.  [`_doMixSwap`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L195) in `GatewaySend.sol` is called.
2.  This calls the [`mixSwap`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1392) function on the `DODOFeeRouteProxy`.
3.  After any swap logic, `mixSwap` calls the internal `_routeWithdraw` function to handle payouts and fees.
4.  The fee logic resides entirely inside [`_routeWithdraw`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1471), where it calculates and deducts the `routeFee` and `brokerFee`:
    ```solidity
    // In DODOFeeRouteProxy.sol -> _routeWithdraw()
    uint256 routeFee = DecimalMath.mulFloor(receiveAmount, routeFeeRate);
    uint256 brokerFee = DecimalMath.mulFloor(receiveAmount, brokerFeeRate);
    // ...
    receiveAmount = receiveAmount - routeFee - brokerFee;
    ```

The vulnerability is in the `onCall` function, which contains this logic:
```solidity
// In GatewaySend.sol -> onCall()
if(fromToken == toToken) {
    outputAmount = amount; // @audit Fee-taking logic in _doMixSwap is skipped
} else {
    outputAmount = _doMixSwap(swapData);
}
```

By creating a special case for same-token transfers, this if block completely circumvents the call to `_doMixSwap` and, by extension, the `_routeWithdraw` function. This provides a loophole for fee-less cross-chain transfers.


### Internal Pre-conditions


- The `onCall` function is triggered by the gateway.
- The message payload is crafted such that the `fromToken` and `toToken` are identical.

### External Pre-conditions

A user wishes to perform a cross-chain transfer of a token without paying the protocol's swap fee.


### Attack Path

- A user on Chain A wants to transfer 1,000 USDC to their own wallet on Chain B, but wants to avoid the protocol's swap fees.
- They initiate a cross-chain transaction via `depositAndCall`. In the payload for the destination chain, they craft the message such that both `fromToken` and `toToken` are set to the USDC address on Chain B.
- The transaction is processed on ZetaChain and relayed to the `GatewaySend` contract on Chain B.
- The `onCall` function is triggered. It decodes the message and sees that `fromToken` is equal to `toToken`.
- The `if(fromToken == toToken)` condition evaluates to true. The logic bypasses `_doMixSwap` and sets `outputAmount` directly to the input amount.
- The full `outputAmount` is transferred to the user's wallet.

**Result:** The user has successfully used the cross-chain infrastructure for free, denying the protocol its intended revenue from the operation.

### Impact

This vulnerability leads to a direct loss of protocol revenue. This flaw undermines the economic model of the protocol, as a core fee-generating mechanism can be bypassed by any user.

### Mitigation

The fee bypass for same-token transfers must be closed. However, a simple fix is insufficient because both `routeFee` and `brokerFee` must be handled. We propose two possible solutions:

**Primary recommendation (Architectural Fix)**

The cleanest and most robust solution is to modify the **`DODOFeeRouteProxy.mixSwap`** function. We recommend removing the [`require(mixPairs.length > 0, ...)`](https://github.com/DODOEX/contractV2/blob/main/contracts/SmartRoute/proxies/DODOFeeRouteProxy.sol#L1406) check and allowing the function to handle an empty `mixPairs` array.

This would allow `GatewaySend.onCall` to unconditionally call `_doMixSwap` for all transactions. The `DODOFeeRouteProxy` would then become the single source of truth for all fee logic, correctly handling both same-token transfers (by skipping its swap loop) and complex swaps, while applying the appropriate `routeFee` and `brokerFee` in all cases. This eliminates logic duplication and centralizes responsibility. We strongly recommend this path if modification of the proxy contract is possible.

**Secondary Recommendation**

If the `DODOFeeRouteProxy` contract cannot be modified, then the [`if (fromToken == toToken)`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L363) block in `GatewaySend.onCall` must be enhanced to fully replicate the DODO proxy's fee logic. This is less ideal as it introduces logic duplication but is necessary to patch the vulnerability within this contract's scope.

The updated logic must perform these steps:

1. Use the `SwapDataHelperLib` to decode the `swapData` payload and extract the `feeData`.
2. Decode the `feeData` to get the `broker` address and `brokerFeeRate`.
3. Calculate the `brokerFee` and transfer it to the `broker`.
4. Read `routeFeeRate` and `routeFeeReceiver` from the proxy, calculate the `routeFee`, and transfer it.
5. The final `outputAmount` for the user is the original `amount` minus both fees.

```solidity
// Conceptual implementation for the secondary recommendation

uint256 outputAmount;
if (fromToken == toToken) {
    // This path must fully replicate the fee logic from DODOFeeRouteProxy.
    
    // 1. Decode swapData to get feeData
    MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);
    (address broker, uint256 brokerFeeRate) = abi.decode(params.feeData, (address, uint256));

    // 2. Handle global route fee
    uint256 routeFeeRate = IDODORouteProxy(DODORouteProxy).routeFeeRate();
    address routeFeeReceiver = IDODORouteProxy(DODORouteProxy).routeFeeReceiver();
    uint256 routeFee = (amount * routeFeeRate) / 1e18; // Note: please use safe math here

    // 3. Handle per-tx broker fee
    uint256 brokerFee = (amount * brokerFeeRate) / 1e18; // Note: please use safe math here

    uint256 totalFee = routeFee + brokerFee;
    require(totalFee < amount, "Fee exceeds amount");

    // 4. Transfer fees
    if (routeFee > 0) {
        IERC20(fromToken).transfer(routeFeeReceiver, routeFee);
    }
    if (brokerFee > 0) {
        IERC20(fromToken).transfer(broker, brokerFee);
    }

    // 5. Set final output amount for the user
    outputAmount = amount - totalFee;

} else {
    outputAmount = _doMixSwap(swapData);
}
// The rest of the function
```
