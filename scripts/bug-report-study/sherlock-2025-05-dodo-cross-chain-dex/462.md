# `GatewaySend::onRevert` fails to handle refunds for native gas tokens

### Summary

`GatewaySend::onRevert` does not correctly handle refunds for transactions involving native gas tokens (e.g., ETH). 

According to ZetaChain's [documentation](https://www.zetachain.com/docs/developers/chains/zetachain/#revert-transactions:~:text=On%20a%20connected%20chain%2C%20asset%20is%20the%20ERC%2D20%20originally%20deposited%20(or%20zero%20address%20for%20gas%20assets).), native assets that are refunded on the connected chain is represented by `address(0)` in the `RevertContext`.

Further proof can be found in this transaction on [etherscan](https://etherscan.io/tx/0xb77e4b64dbeb0ef519cfe96ab4d0515b7fd6ffc7e2052505ad6e736c961c389e).

 When the `onRevert` function calls `TransferHelper.safeTransfer` to refund assets, but this function is designed exclusively for ERC20 tokens, resulting in stuck funds when `onCall` reverts on Zetachain.

### Root Cause

The `onRevert` function in `GatewaySend.sol` uses `TransferHelper.safeTransfer` to handle all token refunds seen [as follows](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L396):

```solidity
function onRevert(RevertContext calldata context) external onlyGateway {
    // ...
    TransferHelper.safeTransfer(context.asset, sender, context.amount);
    // ...
}
```
However, `TransferHelper::safeTransfer` is only implemented for ERC20 tokens [as follows](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/TransferHelper.sol#L12-L16):
```solidity
function safeTransfer(address token, address to, uint value) internal {
    (bool success, bytes memory data) = token.call(abi.encodeWithSelector(0xa9059cbb, to, value));
    require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED');
}
```

### Internal Pre-conditions

`GatewaySend::depositAndCall` succeeds.

### External Pre-conditions

`onCall` on ZetaChain Universal contract reverts, triggering `onRevert` to be called on `GatewaySend`.

### Attack Path

This is not an attack path but a functional bug that leads to loss of funds.
1. A user initiates a cross-chain transaction involving ETH via`GatewaySend::depositAndCall` contract. Transaction on this chain succeeds.
2. `onCall` reverts on the destination chain, and the `GatewayEVM` initiates a revert on `GatewaySend::onRevert`.
3. The gateway calls `GatewaySend.onRevert`, providing a `RevertContext` where `context.asset` is `address(0)` and `context.amount` is the ETH amount to be refunded.
4. `onRevert` calls `TransferHelper.safeTransfer(address(0), sender, amount)`.
5. The `safeTransfer` call fails because it executes a call on `address(0)`.
6. The `onRevert` transaction itself reverts. Because the top-level revert failed, the user's ETH is now permanently locked in the `GatewaySend` contract, as there is no other mechanism to withdraw it.

### Impact

Stuck funds.

### PoC

See attack path.
