# GatewayTransferNative::onCall doesn't handle native Zeta to wZeta deposits

### Summary

When a cross-chain transaction occurs where GatewayTransferNative is the `targetContract` and Zeta is deposited, GatewayZEVM has a special `depositAndCall` function that handles native Zeta. First it performs some validations, then it transfers Zeta to the `targetContract`, and then finally calls `GatewayTransferNative.onCall()`, passing in  `zetaToken` (i.e. wZETA) as the asset:

Currently, the protocol doesn't handle native Zeta deposits correctly when the targetZRC20 is wZeta. 

If the `targetZRC20` is wZeta, then onCall will try to transfer wZETA, but the contract only holds Zeta, so this call will revert.

### Root Cause

GatewayZEVM sends native Zeta tokens to the GatewayTransferNative contract but subsequently calls onCall specifying wZeta (wrapped Zeta) as the asset, causing a mismatch that leads to a failed transfer.
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L373-L379

### Internal Pre-conditions

1. A user calls `GatewaySend::depositAndCall()` where the targetZRC20 is wZeta, Zeta is the deposit token, and GatewayTransferNative is the `targetContract`

### External Pre-conditions

n/a

### Attack Path

1. A user calls `GatewaySend::depositAndCall()` where the targetZRC20 is wZeta, Zeta is the deposit token, and GatewayTransferNative is the `targetContract`
2. GatewayZEVM sends native Zeta (unwrapped) to GatewayTransferNative and calls GatewayTransferNative.onCall specifying the asset as wrapped Zeta (wZeta).
3. GatewayTransferNative attempts to transfer wZeta, but holds only native Zeta.
4. The transfer fails, causing the entire transaction to revert.

### Impact

Breaks core protocol functionality. Users waste gas.
