# Attacker will drain protocol funds from unclaimed refunds

### Summary

Incorrect approval calculations combined with exposed internal methods will cause a loss of protocol funds as an attacker will exploit the unprotected `withdraw` function in `GatewayTransferNative`.

### Root Cause

Although each issue individually poses only a low risk, their combination creates a high-impact vulnerability due to their interconnected nature:

1. In `GatewayTransferNative.sol`, the `withdraw` function is declared as `public` rather than `internal` as it is in the `GatewayCrossChain.sol` contract.

2. In both contracts, there are multiple instances of incorrect approval calculations across various functions:
   - In [`GatewayTransferNative.sol:458-463`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L458-L463) inside the `_handleBitcoinWithdraw` function
   - In [`GatewayTransferNative.sol:477-497`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L477-L497) inside the `_handleEvmOrSolanaWithdraw` function
   - Similar issues exist in the `GatewayCrossChain` contract too, though not exploitable.

The key insight is that in normal execution flow, like in `_handleBitcoinWithdraw`, the contract does:

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L370-L376

The approval is for `outputAmount + gasFee`, but the withdrawal is only for `outputAmount - gasFee`.

Inside the ZetaChain gateway, the `gasFee` is charged separately from the amount passed for withdrawal, resulting in a total transfer of:
`(outputAmount - gasFee) + gasFee = outputAmount`

This means the contract is approving `outputAmount + gasFee` when it only needs to approve `outputAmount`, creating an over-approval of `gasFee`.

An attacker can exploit this discrepancy by directly calling the public `withdraw` function in `GatewayTransferNative`, stealing tokens from the contract's balance (including unclaimed refunds).

### Internal Pre-conditions

1. The contract must have unclaimed refunds stored (refund tokens belonging to users that haven't been claimed yet).
2. The `GatewayTransferNative` contract must be deployed and accessible

### External Pre-conditions

None specific required.

### Attack Path

Using a MEV-bot:

1. Attacker listens on transactions involving a call to `withdrawToNativeChain` (that approves more than necessary)
2. Attacker calls the public `withdraw` function with crafted parameters
3. The function attempts to withdraw tokens through gateway and due to the over-approval, tokens that belong to unclaimed refunds will be used
4. The gateway transfers these tokens out, effectively draining them from the contract

### Impact

The protocol suffers a loss of unclaimed refund tokens stored in the `GatewayTransferNative` contract. Users with pending refunds will be unable to claim their tokens.

The severity is high as it involves a direct theft of funds from the contract, affecting user refunds that are supposed to be safely held until claimed (at least last refund always fails).

### PoC

_No response_

### Mitigation

Two changes are needed to fix this vulnerability:

1. Change the `withdraw` function in `GatewayTransferNative.sol` to be `internal` instead of `public`, matching the access level in `GatewayCrossChain.sol`.

2. Fix the approval calculations in both contracts to approve only the necessary amount (`outputAmount`).

These changes would prevent both the immediate security issue and any potential future exploits based on the same pattern.
