# Flawed authorization logic in `claimRefund` allows theft of non-EVM refunds

### Summary

A flawed authorization check in the `claimRefund` function will cause a loss of funds for the user as an attacker will call `claimRefund` for any pending non-EVM refund and receive the tokens themselves.

### Root Cause

In [GatewayCrossChain.sol:574-578](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L574-L578) and [GatewayTransferNative.sol:664-668](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayTransferNative.sol#L664-L668), the authorization logic incorrectly defaults the `receiver` to `msg.sender`. When a refund address is for a non-EVM chain (and thus not 20 bytes long), the logic fails to assign the correct recipient, allowing the access control check to be trivially bypassed by the caller.

#### Code
```solidity
address receiver = msg.sender; // Defaults to msg.sender
if(refundInfo.walletAddress.length == 20) {
    // This block is skipped for non-EVM refunds
    receiver = address(uint160(bytes20(refundInfo.walletAddress)));
}
// The check becomes require(bots[attacker] || attacker == attacker), which is true
require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
```

### Internal Pre-conditions

- A refund must exist where `refundInfo.walletAddress.length` is not equal to 20. This happens when a user's cross-chain transaction to a non-EVM chain fails and is reverted by the gateway.

### External Pre-conditions

None

### Attack Path

1. A user's cross-chain transaction to a non-EVM address fails, creating a `RefundInfo` struct in the contract. An event is emitted with the `externalId`.
2. An attacker monitors the contract for these events and finds a valid `externalId` for a non-EVM refund.
3. The attacker calls `claimRefund(externalId)`.
4. Inside the function, the check `refundInfo.walletAddress.length == 20` is false.
5. `receiver` remains set to its default value, which is `msg.sender` (the attacker's address).
6. The authorization check, `require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER")`, passes because the attacker's address is equal to the `receiver` address.
7. The refund is successfully transferred to the attacker.

### Impact

- The original user suffers a 100% loss of their refunded amount. 
- The attacker gains this amount.

### PoC

_No response_

### Mitigation

The original transaction sender's address should be stored alongside the refund information. The `claimRefund` function should then verify that `msg.sender` is either a trusted bot or the original sender.
