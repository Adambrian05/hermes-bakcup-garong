# slippage property must be per token

### Summary

Each token has a different volatility profile, and using a single `slippage` parameter will expose the users to griefing and sandwich attacks or will block swaps.

Furthermore, since `UniswapV2` is used, there’s no effective TWAP protection, but a CPAMM mechanism is used, which makes the manipulation extremely feasible.

### Root Cause

A single `slippage` parameter for all the tokens in Zeta will make the swaps insufficient and won’t give the option to the admin to fine-tune it per token to minimize honest users being sandwiched.

### Internal Pre-conditions

Tokens with different volatility profiles are to be used.

### External Pre-conditions

None

### Attack Path

Let’s compare the [`PEPE.ETH` with `CBBTC.SOL`](https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets), where:

1. `[PEPE,WZETA]: $6,540.41` and `[WZETA:BridgedETH]: $185,026.84`
2. `[CBBTC,WZETA]: $2,023.30` and `[WZETA,SOL]: $5,259.11`

Significant difference in the liquidity and ratios.

As the `PEPE` price is 28x less than `BridgedETH`, vs. `2.6x` for `CBBTC` to `SOL`.

From here, if the global slippage is 0.5-1%, there’s a high chance the `CBBTC.SOL` withdrawals to fail, since the `amountInMax` won’t be enough, **due to the price impact caused.**

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L315

```solidity
uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);

        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE
        );
```

On the contrary, if the `slippage` has been modified to a greater value - 10%+, this will allow anyone to sandwich the swaps and abuse the inflated `amountInMax`, which serves no protection. The attack will involve increasing the ratio of the input token, so the entire `amountInMax` is being used, the swap going through at an inflated rate, and then finalizing with the attacker inverting his initial swap to materialize the profit.

### Impact

Loss of funds if the slippage is set too high or failing withdrawals for more volatile assets if the slippage is too low.

N/A

### Mitigation

Introduce per-asset slippage mapping, so they can be fine-tuned.
