# USDT cannot be sent from a connected chain to ZetaChain

### Summary

According to audit docs, this is the list of assets supported as ZRC20 token in ZetaChain: https://www.zetachain.com/docs/developers/tokens/zrc20/#supported-assets, however GatewaySend.depositAndCall() will revert when trying to send USDT token (included in the mentioned list) to ZetaChain.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L237-L242

### Root Cause

This happens because GatewaySend.depositAndCall() checks whether `transferFrom()` function from ERC20 standard returns true to confirm that tokens were correctly transferred to the contract, however some implementation of ERC20 tokens (weird tokens) do not return a boolean when being transferred, and USDT is one example of these.

As a result, when trying to deposit USDT or any other ERC20 token that does not return true when transferred will result in a revert: the contract expects a true expression to be evaluated in that `require` but there is no expression to evaluate.

SafeERC20 library from OpenZeppelin usually handles this cases in which transferFrom() does not return a boolean.

### Attack Path

1. Alice wants to deposit USDT tokens from Ethereum mainnet to ZetaChain and calls `GatewaySend.depositAndCall()` for so, however the function reverts as it expects that transferFrom() function in USDT token to return true when successful transfer but it returns nothing.

### Impact

USDT token (or any other token that do not return true when succesful transfer) cannot be deposited into ZetaChain or swapped through DODO. This is not the expected behaviour of the contract as previously explained, all the supported tokens in ZetaChain should be supported as well by the protocol.

USDT is one of these supported assets, but it is not possible to deposit it into ZetaChain, clearly breaking one of the main funcitonalities of the protocol.

### Mitigation

Import and use SafeERC20 library from OpenZeppelin, which automatically handles these weird tokens that do not return true in succesful transfers. This way the function will check that the transfer was correctly done itself, so that `require` is not needed:

```solidity
function depositAndCall(
        address fromToken,
        uint256 amount,
        bytes calldata swapData,
        address targetContract,
        address asset,
        uint32 dstChainId,
        bytes calldata payload
    ) public payable {
        globalNonce++;
        bytes32 externalId = _calcExternalId(msg.sender);
        bool fromIsETH = (fromToken == _ETH_ADDRESS_);

        // Handle input token
        if(fromIsETH) {
            require(
                msg.value >= amount, 
                "INSUFFICIENT AMOUNT: ETH NOT ENOUGH"
            );
        } else {
-            require(
-               IERC20(fromToken).transferFrom(msg.sender, address(this), amount), 
-               "INSUFFICIENT AMOUNT: ERC20 TRANSFER FROM FAILED"
-           );
+          IERC20(fromToken).safeTransferFrom(msg.sender, address(this), amount);
        }
```
