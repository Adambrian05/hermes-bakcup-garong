# Attacker will spoof receiver to farm rewards or DoS campaign via cross-chain spoofing

### Summary

The ability for users to set arbitrary receiver in GatewayCrossChain.sol will cause unauthorized reward farming or denial-of-service for destination-chain campaigns as an attacker will encode contract addresses or token-rich pools to spoof legitimate user participation.

### Root Cause

In GatewayCrossChain.sol:onCall, the decoded.receiver field from the cross-chain message is used directly in withdraw() or withdrawAndCall() with no validation that it is an EOA or matches a user-provided address. This allows attackers to redirect participation to contract addresses and manipulate downstream campaign logic.

### Internal Pre-conditions

1. User (attacker) sets decoded.receiver to an arbitrary address (e.g., Uniswap V2 pool or self-deployed smart contract).

2. Tokens are sent to that spoofed address by GatewayCrossChain.

3. Downstream campaign logic attributes participation or rewards to decoded.receiver.

### External Pre-conditions

1.Destination chain includes a campaign (e.g., NudgeCampaign) that uses receiver as a participation identity.

2. No verification (e.g., sig binding or msg.sender check) is done on userAddress in handleReallocation.



### Attack Path

1. Attacker initiates cross-chain swap and encodes payload with decoded.receiver = poolAddress.

2. Tokens are sent to pool by GatewayCrossChain using withdrawAndCall().

3. Campaign calls handleReallocation() and registers poolAddress as a participant.

4. Reward system sees poolAddress has the balance, accepts it.

5. If campaign locks up, it DoSes real users. If not, attacker or accomplice withdraws rewards from spoofed pool or contract.



### Impact

- The campaign on the destination chain registers fake participants, possibly locking up large amounts of rewards.

- Campaign fails to serve real users (DoS).

- Protocol burns rewards for spoofed recipients.

- Risk is magnified by 6.4M+ users and $100B+ assets, especially due to Safe (account abstraction) users having non-uniform addresses across chains.

### PoC

_No response_

### Mitigation

- Enforce receiver.code.length == 0 to disallow contract addresses.

- Introduce origin-binding: require a signature or Merkle proof that binds destination receiver to origin msg.sender.

- Update downstream campaign logic (like NudgeCampaign) to:

- Require msg.sender == userAddress or

- Allow users to explicitly configure userAddress cross-chain.
