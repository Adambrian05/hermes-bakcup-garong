# On-chain slippage calculation can cause user to lose all funds

### Summary

The [_swapAndSendERC20Tokens](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L302) function calculates slippage protection on-chain using current pool state, making it vulnerable to sandwich attacks. Attackers can manipulate pool prices and force users to pay significantly more tokens than expected, while the "slippage protection" uses the manipulated price as baseline, providing no actual protection.

### Root Cause

When user is doing cross-chain swap of non-gas token, one portion of the funds needs to be swapped for the gas token in order to pay for gas fees. Function `_swapAndSendERC20Tokens` is using Uniswap pool to do that.  Variable `amountInMax` is used for slippage protection. It is calculated **on-chain**, at execution time:
```solidity
uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
    UniswapFactory,
    gasFee,
    getPathForTokens(targetZRC20, gasZRC20)
);

uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
```
This approach uses the current pool state as the reference price for slippage calculation. But current price (amountsQuote) can be manipulated by attackers. Attacker can manipulate it to perform the classic sandwhich attack to effectively steal user's funds. True slippage protection should use the price the user saw when submitting the transaction, calculated off-chain.

### Internal Pre-conditions

None

### External Pre-conditions

Attacker can monitor the mempool and perform the front-run and back-run of the ZetaChain's leg of the cross-chain swap. 

### Attack Path

1. User calls `GatewaySend`'s `depositAndCall` to move funds from chain A to chain B via ZetaChain
2. ZetaChain's leg is about to be triggered. Leg consists of `GatewayZEVM` calling `GatewayCrossChain`'s `onCall`. Funds being moved are not gas-tokens, so `GatewayCrossChain` will swap part of the funds for the gas-tokens, in order to pay for the final leg that moves funds from ZetaChain to chain B
3. Attacker monitors CCTXs/mempool for `GatewayCrossChain` TXs requiring gas-token swaps
4. Front-run Manipulation: Attacker notices TX from step 2 and front-runs it by doing a large swap to manipulate pool price, making it much more expensive for user to get gas-tokens. So user effectively spends a much bigger cut of funds being moved to pay for the gas. Ie. instead of paying 2% of funds to swap for gas-tokens and pay for gas, due to attack user spends 20% of funds. In theory, in low liquid pool which can be easily manipulated, user could lose up to 100% of funds
5. Attacker back-runs the user's ZetaChain leg TX, and makes a profit from a successful sandwhich attack

### Impact

HIGH severity - this vulnerability causes direct loss of funds for user. Attacker doing the sandwhich attack effectively steals user's funds due to ineffective slippage protection. User can lose up to 100% of funds. Exact amount of loss depends on attacker's capability to distort the price.

### PoC

_No response_

### Mitigation

Variable `amountInMax` which is used for slippage protection must not be calculated on-chain based on current price. Instead, it should be calculated up-front and provided by user as one of the input parameters.
