# A user can permanently lose funds if cross-chain execution fails and refund bots are offline or misconfigured

### Summary

The absence of an on-chain lock-and-unlock escrow mechanism in depositAndCall() will cause permanent loss of funds for users if cross-chain message delivery fails or onCall() reverts, as the system relies solely on off-chain refund bots for unlocking tokens — creating a critical single point of failure with no fallback for self-service recovery.

### Root Cause


In [GatewaySend.sol:depositAndCall], the contract accepts user tokens and generates an externalId, but does not:
	•	Record the locked funds in a mapping (e.g., lockedTransfers[externalId])
	•	Emit an explicit failure-handling flag
	•	Provide a public function like claimRefund() for users to unlock their assets

Instead, the protocol documentation specifies that if a refund is needed and the recipient is not an EOA, it is the responsibility of refund bots to collect and redistribute the locked tokens.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L218-L286

### Internal Pre-conditions

1. A user or dApp sends tokens using depositAndCall(), triggering a cross-chain operation.
2. The externalId is generated but not recorded for future state tracking.

### External Pre-conditions

1. onCall() fails on the destination chain due to:
	•	Invalid swapData
	•	Insufficient liquidity
	•	Transfer revert or adapter issue
2. The refund bot is offline, misconfigured, or unaware of the failure.

### Attack Path

1. User sends 1000 USDT using depositAndCall() for a cross-chain swap.
2. onCall() fails on destination due to bad adapter or liquidity issue.
3. GatewaySend holds the tokens, but:
 •	There is no on-chain unlock path
 •	No flag marks this externalId for manual refund
4. The refund bot fails to act or is not running.
5. User has no way to recover funds.


### Impact

The user suffers a complete loss of deposited assets.
Even well-behaving users can lose funds during network failures.
This becomes a critical issue under high volume, gas spikes, or bot downtime.

### Mitigation

Implement escrow logic on depositAndCall():
lockedTransfers[externalId] = LockedTransfer({
    user: msg.sender,
    token: fromToken,
    amount: amount,
    refunded: false
});

Add claimRefund() function:
function claimRefund(bytes32 externalId) external {
    LockedTransfer storage lock = lockedTransfers[externalId];
    require(lock.user == msg.sender, "Not authorized");
    require(!lock.refunded, "Already refunded");
    lock.refunded = true;
    IERC20(lock.token).transfer(msg.sender, lock.amount);
}
Use refund bots only as automation, not as the sole path to recovery.
