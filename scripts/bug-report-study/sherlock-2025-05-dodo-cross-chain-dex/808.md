# Token transfer will not happen if refundInfo.token is ETH.

### Summary

In `onRevert()` & `claimRefund()` function if a cross-chain transaction is initiated with native ETH receiver will not receive tokens if `refundInfo.token` / context.asset is `_ETH_ADDRESS_`.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L571C5-L590C6

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517C5-L532C17

### Root Cause

The key line is `TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);`.

If refundInfo.token is _ETH_ADDRESS_ (i.e., 0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE):

>The call becomes: _ETH_ADDRESS_.call(abi.encodeWithSelector(0xa9059cbb, receiver, refundInfo.amount)).
>
>This attempts to execute the ERC20 transfer(address,uint256) function (selector 0xa9059cbb) on the _ETH_ADDRESS_.
>
>The _ETH_ADDRESS_ is a special address representing native Ether; it is not a contract and does not have an ERC20 >transfer function.
>
>The success variable will be true.
>
>The data returned will be empty (data.length == 0).
>
>The require condition `require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: 
>
>TRANSFER_FAILED')` will evaluate to require(true && (true || ...)) which is `true`.
>
>Therefore, the TransferHelper.safeTransfer call will not revert.
>
>The `refundInfos[externalId]` entry will be deleted and no funds will be received by the receiver.

### Internal Pre-conditions

1. `onAbort` or `orRevert` is called for a failed transaction.
2. Token to transfer is native ETH i.e `0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE`

### External Pre-conditions

NA

### Attack Path

1. A user initiates a cross-chain transaction sending native ETH (e.g., via GatewaySend.depositAndCall(...)). The transaction subsequently fails, triggering a refund process on ZetaChain (e.g., onRevert or claimRefund in GatewayCrossChain.sol).

2. During the refund process, the token to be refunded (refundInfo.token or context.asset) is identified as _ETH_ADDRESS_.

3. The refund logic calls `TransferHelper.safeTransfer(_ETH_ADDRESS_, receiver, amount)`. This function attempts an ERC20 transfer call on _ETH_ADDRESS_. Since _ETH_ADDRESS_ is not a contract, the call returns `success = true` and empty data, but no actual native currency (e.g., ZETA on ZetaChain) is transferred.

4. The `TransferHelper.safeTransfer` call completes without reverting. The system then incorrectly assumes the refund was successful, deletes the `refundInfos` entry , and the user permanently loses their funds.

### Impact

Users who send native ETH in a cross-chain transaction that subsequently fails and triggers a refund will not receive their funds back. The system will incorrectly indicate that the refund was successful, leading to a direct and permanent loss of the user's assets corresponding to the refund amount.

### PoC

1. The line (bool success, bytes memory data) = _ETH_ADDRESS_.call(abi.encodeWithSelector(0xa9059cbb, receiver, amount)); is executed.
2. success will be true.
3. Data will be empty (data.length == 0).
4. The condition require(success && (data.length == 0 || abi.decode(data, (bool))), 'TransferHelper: TRANSFER_FAILED') becomes require(true && (true || ...)) which is true.
5. The function completes without error, but no native currency is transferred to receiver.
