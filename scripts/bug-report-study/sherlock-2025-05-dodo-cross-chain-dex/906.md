# Stale `swapDataB.fromTokenAmount` after execution of `swapDataZ` and `gasFee` deduction

### Summary

`GatewaySender::onCall` swaps `swapDataB.fromTokenAmount` of `swapDataB.fromToken` to `swapDataB.toToken`. However, if the CCTX contains a `swapDataZ` which is executed on the zeta-chain, then the output of `swapDataZ` is expected to equal `swapDataB.fromTokenAmount`. The issue arises when the `outputAmount` of `swapDataZ` might be less than `swapDataB.fromTokenAmount`, resulting in asset shortage when `GatewaySend::onCall` tries to execute the swap, or when it's more than `swapDataB.fromTokenAmount`, causing a portion of assets to be locked in the `GatewaySend` contract.

### Root Cause

In `CrossChainRouter`, the `outputAmount` is set to the result of `_doMixSwap`:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L464-L465
```solidity
        // Swap on DODO Router
        uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);
```
The `outputAmount` is then sent to the destination native chain:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L580-L585
```solidity
        // Withdraw
        if (decoded.dstChainId == BITCOIN_EDDY) {
            // SKIP - this part doesn't contain any swap data
        } else {
            uint256 amountsOutTarget = _handleEvmOrSolanaWithdraw(
                externalId, 
                decoded, // ----> swapDataB is still unmodified with stale parameters
                outputAmount, // ----> withdraw outputAmount to destination
                decoded.receiver
            );
        }
```
On the native chain side (**EVM** in this scope), we perform a swap using `swapData`:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L341-L367
```solidity
    function onCall(
        MessageContext calldata /*context*/,
        bytes calldata message
    ) external payable onlyGateway returns (bytes4) {
        (
            bytes32 externalId, 
            uint256 amount, //-----> the amount we just withdrew from zeta-chain (i.e the outputAmount of swapDataZ)
            bytes calldata recipient, 
            address fromToken, 
            address toToken, 
            bytes calldata swapData
        ) = decodePackedMessage(message);

        // Rest of code...

        uint256 outputAmount;
        if(fromToken == toToken) {
            outputAmount = amount;
        } else {
            outputAmount = _doMixSwap(swapData); //-----> swap tokenFromAmount of tokenFrom => tokenTo 
        }
```
In `_doMixSwap`, we assume that `params.fromTokenAmount` exists fully in the contract:
https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewaySend.sol#L196-L215
```solidity

    function _doMixSwap(bytes calldata swapData) internal returns (uint256) {
        MixSwapParams memory params = SwapDataHelperLib.decodeCompressedMixSwapParams(swapData);

        if(params.fromToken != _ETH_ADDRESS_) {
            IERC20(params.fromToken).approve(DODOApprove, params.fromTokenAmount);
        }

        return IDODORouteProxy(DODORouteProxy).mixSwap{value: msg.value}(
            params.fromToken,
            params.toToken,
            params.fromTokenAmount, // ----> DODORouter will try to transfer this amount from this contract
            params.expReturnAmount,
            params.minReturnAmount,
            params.mixAdapters,
            params.mixPairs,
            params.assetTo,
            params.directions,
            params.moreInfo,
            params.feeData,
            params.deadline
        );
    }
```
Even when constructing the `swapDataB`, if we take into account the platform fees, we still cannot account for:
- Gas fees which will be deducted from the `outputAmount` of `swapDataZ`
- How many tokens will be withdrawn from the zeta chain and deposited into chain B, because the result of swapDataZ is subject to market volatility

Hence, we cannot always be sure that `swapDataB.fromTokenAmount` is received on chain B.

### Internal Pre-conditions

- `SwapDataZ.length > 0` and `swapDataB.length > 0`
- `SwapDataZ.toToken == swapDataB.fromToken`
- `uint256 outputAmount = _doMixSwap(decoded.swapDataZ, amount, params);` is expected to cover `swapDataB.fromTokenAmount`

### External Pre-conditions

- Market volatility and price slippage + gas fee deduction results in `outputAmount` on zeta-chain being less than `swapDataB.fromTokenAmount`, which causes reverts due to asset shortage
- Market volatility and price slippage results in `outputAmount` on zeta-chain being more than `swapDataB.fromTokenAmount`, which results in loss of funds

### Attack Path

1. Alice decides to deposit 100 USDT into zetachain, swap them to 100 USDC arbitrum, then withdraw the 100 USDC tokens to arbitrum network and swap 100 USDC on arbitrum to ETH
2. 100 USDT is deposited on zetachain, `GatewayCrossChain::onCall` is executed and 100 USDT is swapped to 99.8 USDC
3. A portion of 99.8 USDC is swapped to native ETH (gasZRC20) and deposited to gateway
4. `GatewaySender::onCall` on arbitrum receives 98 USDC
5. `_doMixSwap` fails trying to swap `100` USDC (`fromTokenAmount`) to ETH due to insufficient funds supplied

### Impact

CCTX containing two swaps might fail due to the described issues, resulting in:
- User CCTX failure => user loss of funds because they pay for gas
- Some assets locked in `GatewaySender` because the deposited amount is more than `swapDataB.fromTokenAmount`

### PoC

_No response_

### Mitigation

Re-encode the outputAmount of swapDataZ in swapDataB (after applying gas fees)
