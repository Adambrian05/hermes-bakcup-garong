# Incorrect check for `targetAmount` means small transfers of tokens from zetachain to EVM/Solana chain will be DOS-ed

## Vulnerability Details

In `GatewayTransferNative`, the user will call `GatewayTransferNative.withdrawToNativeChain -> GatewayTransferNative._handleEvmOrSolanaWithdraw -> GatewayTransferNative._swapAndSendERC20Tokens` to execute a swap via a Uniswap pool, using the `targetZRC20` token to obtain the `gasZRC20` token when the two tokens differ.

The issue occurs due to an excessively strict check that may permanently hinder users from conducting small token transfers if they wish to do so. Furthermore, the slippage applied for the swap from `targetZRC20` to `gasZRC20` is hardcoded by the protocol, which means users have no control over the slippage.

Consequently, any small token amounts cannot be transferred to the destination EVM/Solana chain if a user attempts to do so, resulting in a failure of core functionality.

In `GatewayTransferNative._swapAndSendERC20Tokens`

```solidity
    function _swapAndSendERC20Tokens(
        address targetZRC20,
        address gasZRC20,
        uint256 gasFee,
        uint256 targetAmount
    ) internal returns(uint256 amountsOut) {
        // Get amountOut for Input gasToken
        uint[] memory amountsQuote = UniswapV2Library.getAmountsIn(
            UniswapFactory,
            gasFee,
            getPathForTokens(targetZRC20, gasZRC20) // [targetZRC, gasZRC] or [targetZRC, WZETA, gasZRC]
        );

        uint amountInMax = (amountsQuote[0]) + (slippage * amountsQuote[0]) / 1000;
        IZRC20(targetZRC20).approve(UniswapRouter, amountInMax);

        // Swap TargetZRC20 to gasZRC20
        uint[] memory amounts = IUniswapV2Router01(UniswapRouter)
            .swapTokensForExactTokens(
                gasFee, // Amount of gas token required
                amountInMax,
                getPathForTokens(targetZRC20, gasZRC20), // path[0] = targetZRC20, path[1] = gasZRC20
                address(this),
                block.timestamp + MAX_DEADLINE
        );

        require(IZRC20(gasZRC20).balanceOf(address(this)) >= gasFee, "INSUFFICIENT_GAS_FOR_WITHDRAW");
@>        require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW"); //@audit should be targetAmount - amounts[0] instead

        IZRC20(gasZRC20).approve(address(gateway), gasFee);
        IZRC20(targetZRC20).approve(address(gateway), targetAmount - amounts[0]);

        amountsOut = targetAmount - amounts[0];
    }
```

## POC

Consider the following scenario

1. The protocol establishes a `slippage` rate of 1% within `GatewayTransferNative`.
2. Alice plans to transfer 1 USDC to her Ethereum receiver address.
3. Following the path of `GatewayTransferNative.withdrawToNativeChain -> GatewayTransferNative._handleEvmOrSolanaWithdraw -> GatewayTransferNative._swapAndSendERC20Tokens`
    - The `gasFees` will amount to 1 USDC which is used to swap for `gasUSDC`.
    - The `amountInMax` will be calculated as 1 + 1 * 0.01 = 1.01 USDC.
4. Rather than receiving the leftover 0.01 USDC (which is 1% of her initial amount), her transaction fails due to the `require(targetAmount - amountInMax > 0, "INSUFFICIENT_AMOUNT_FOR_WITHDRAW");` condition, which incorrectly indicates that Alice lacks sufficient funds to withdraw, despite her having a remaining of 0.01 USDC to transfer.
5. Consequently, her attempt to withdraw to her EVM/Solana address is unsuccessful, resulting in a breakdown of the protocol's core functionality.

## Root Cause

Wrong check enforced to check whether amount to be transferred is enough in `GatewayTransferNative._swapAndSendERC20Tokens

## Impact

Broken protocol core functionality

## Mitigation

Reduce the `targetAmount` by the actual utilized amount `amounts[0]` rather than the slippage variable `amountInMax`
