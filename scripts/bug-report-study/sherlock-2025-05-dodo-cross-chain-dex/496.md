# Potential indefinite delay of cross-chain swap transactions due to reliance on block.timestamp-based deadline

### Summary

The _swapAndSendERC20Tokens function uses a swap deadline set as block.timestamp + MAX_DEADLINE (where MAX_DEADLINE is 200 seconds). While this limits how long the swap is valid after inclusion in a block, it does not prevent malicious validators from indefinitely delaying the transaction from being included on-chain. This can cause cross-chain transactions to be stalled indefinitely, harming user experience and potentially causing loss of funds or system inconsistencies.

### Root Cause

The swap deadline is based on block.timestamp + MAX_DEADLINE and only starts counting down when the transaction is included in a block. However, validators or miners can withhold the transaction from inclusion indefinitely in the mempool, causing the swap to never execute. This behavior is possible because Ethereum and EVM-compatible chains do not enforce transaction inclusion timing constraints.

### Attack Path

1. A user initiates a cross-chain swap transaction invoking _swapAndSendERC20Tokens.

2. The transaction is broadcast to the network but not immediately included in a block.

3. A malicious validator detects the transaction and intentionally delays including it.

4. Since the swap deadline is calculated using block.timestamp (which only advances once included in a block), the validator can delay execution indefinitely.

5. The cross-chain transaction remains pending, potentially causing funds to be locked or inconsistent system state.

### Impact

Cross-chain swaps can be delayed indefinitely, degrading system reliability.

Users may experience locked funds or failed cross-chain operations.

Malicious validators can exploit this to censor or stall specific transactions, creating denial-of-service scenarios.
