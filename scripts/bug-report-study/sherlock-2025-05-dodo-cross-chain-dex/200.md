# Attacker will Deny Legitimate Withdrawals via Zero-Amount Flooding

### Summary

The missing check on withdrawal amount in `GatewayCrossChain.sol` will cause a denial of service for users, as an attacker will spam zero-amount withdrawals and clog the system.

### Root Cause

In `GatewayCrossChain.sol`, the [`withdraw()`](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L277) function does not validate that the amount parameter is greater than zero.
This allows an attacker to queue unlimited 0-value withdrawals, forcing governance to match gas costs to process them.

### Internal Pre-conditions

- `msg.sender` can call a function (like `_handleBitcoinWithdraw`) that leads to a `withdraw()` call
- The output amount after subtracting gas fees becomes 0 or a dust value
- No check exists to revert if amount == 0 in withdraw()

### External Pre-conditions

-  `Gateway` contract must not have internal checks for minimum withdrawal amount
- The relayers/gateway infra must process all withdraw() requests regardless of amount

### Attack Path

- Attacker triggers `_handleBitcoinWithdraw()` 
- `outputAmount` - `gasFee` equals 0
- Function calls `withdraw()` with 0 amount
- Attacker loops this action, creating 1000s of `withdraw` messages
- Gateway queues are filled governance relayers must process all or risk locking real user funds

### Impact

The protocol suffers from a Denial of Service on its withdrawal mechanism.

### PoC

Attacker initiates a cross-chain swap to Bitcoin with:
`outputAmount` = known Bitcoin withdrawal `gasFee`
`targetZRC20` = token to drain
receiver = attacker's Bitcoin address
```solidity
// In _handleBitcoinWithdraw:
if (gasFee >= outputAmount) revert ... // gasFee == outputAmount passes!
IZRC20(targetZRC20).approve(gateway, outputAmount + gasFee); // Approves 2 * outputAmount
withdraw(externalId, receiver, targetZRC20, 0); // Withdraw 0 tokens
```
Gateway Revert
Gateway processes 0 withdrawal, then triggers `onRevert`
```solidity
// In onRevert:
if (revertMessage.length == 52) { // Always true
    address receiver = address(uint160(bytes20(walletAddress)));
    TransferHelper.safeTransfer(context.asset, receiver, context.amount); 
    // Transfers original amount (outputAmount) to attacker
}
```
Attacker receives the full `outputAmount` in their wallet despite the withdrawal failing.
Repeated attacks can drain the contract's token balance.

### Mitigation

- Add a minimum withdrawal threshold in `withdraw()`
- Add a strict inequality check to prevent zero withdrawals
