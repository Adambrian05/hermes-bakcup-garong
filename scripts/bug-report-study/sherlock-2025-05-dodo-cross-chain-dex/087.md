# Unbounded memory allocation in AccountEncoder.sol in function decompressAccounts

### Summary

The function `decompressAccounts(bytes memory input)` decodes a compressed array of Account structs from raw bytes using inline assembly. However, it does not validate the decoded length of the array (len), allowing a malicious input to trigger unbounded memory allocation and potential gas denial-of-service, especially if called in an unbounded loop or from another contract.

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/libraries/AccountEncoder.sol#L19

### Root Cause

in AccountEncoder:19 :

```solidity
function decompressAccounts(bytes memory input) internal pure returns (Account[] memory accounts) {
        assembly {
            let ptr := add(input, 32) // without checking input.length >= 2

            // Read accounts length (uint16)
            let len := add(shl(8, byte(0, mload(ptr))), byte(1, mload(ptr))) 
            ptr := add(ptr, 2)
...
```

the function reads the len field using byte(0, mload(ptr)) without checking input.length >= 2.
The value of len is trusted directly and used to:
Allocate dynamic memory via mstore, Copy data with mload(ptr) without bounds checks, Loop up to len times and increment ptr by 33 * len bytes.

### Internal Pre-conditions

1. function decompressAccounts(bytes memory input) is called with user-controlled or externally-crafted input.
2. The first two bytes of input encode a large number for len (e.g., 0xffff).
3. The contract does not enforce any limits or validate input.length.

### External Pre-conditions

None required. This is a self-contained decoding bug within the contract library.
If this function is ever reachable via user input or cross-chain messages, it becomes exploitable.

### Attack Path

1. Attacker crafts a bytes input with the first two bytes set to 0xffff, representing len = 65535.
2. Remaining bytes can be zeros (or even missing).
3. Attacker submits the input to a contract that calls decompressAccounts(input).
4. Memory allocation and pointer incrementation proceed for 65,535 iterations, leading to excessive memory 5. usage and likely out-of-gas.

### Impact

1. Memory growth scales with len * 64, leading to gas exhaustion.
2.  mload(ptr) in the loop can read out of bounds from input, causing undefined behavior.
3.  Can be used to grief transactions that decode inputs from trusted but unchecked sources (e.g., cross-chain message).

### Mitigation

```solidity
function decompressAccounts(bytes memory input) internal pure returns (Account[] memory accounts) {
    require(input.length >= 2, "Input too short to contain length");

    assembly {
        let ptr := add(input, 32)
        let len := add(shl(8, byte(0, mload(ptr))), byte(1, mload(ptr)))

        // Additional protection: input length must be sufficient for len * 33
        if lt(sub(mload(input), 2), mul(len, 33)) {
            revert(0, 0)
        }

        ...
    }
}
```
