# Decimal Mismatch in Cross-Chain Token Handling

### Summary

The protocol does not account for differences in token decimals between chains, such as USDT’s 6 decimals on some chains and 18 decimals on others. This can lead to miscalculations in token amounts during cross-chain transfers, swaps, and gas fee computations, potentially causing financial losses or transaction failures.

### Root Cause

Many tokens, including stablecoins like USDT, have varying decimal precisions across different blockchain networks. For instance, a token may use 6 decimals on one chain (e.g., 1 token = 1,000,000 units) and 18 decimals on another (e.g., 1 token = 10^18 units). The codebase does not query or normalize token decimals, assuming uniform precision across all chains, which can lead to significant errors in amount calculations.

### Security Guarantees Broken
- Token amounts are miscalculated due to decimal mismatches, breaking the protocol’s intended functionality.
- Users receive incorrect token amounts, leading to substantial losses or unintended gains.

### Propagation of Malicious Input
- User Deposits Tokens on Source Chain:
 In `GatewaySend.sol`, the `depositAndCall `function accepts a user-specified amount via `IERC20.transferFrom`:

```solidity
require(IERC20(fromToken).transferFrom(msg.sender, address(this), amount), ...);
```

The amount is used without adjusting for the token’s decimals on the source chain.

Swap Execution:

In `_doMixSwap`, the amount is approved and passed to DODO’s `mixSwap`:

```solidity
IZRC20(params.fromToken).approve(DODOApprove, amount);
IDODORouteProxy(DODORouteProxy).mixSwap(...);
```

If the target chain or DODO expects a different decimal precision, the amount is misinterpreted, resulting in incorrect swap outputs.

Cross-Chain Withdrawal to Destination Chain:
In `GatewayCrossChain.sol` or `GatewayTransferNative.sol`, `_handleEvmOrSolanaWithdraw `processes withdrawals:

```solidity
(address gasZRC20, uint256 gasFee) = IZRC20(decoded.targetZRC20).withdrawGasFeeWithGasLimit(gasLimit);
```
If the token’s decimals on the destination chain differ from the source chain, the gasFee or withdrawal amount may be miscalculated, leading to transaction failures or incorrect transfers.

Refund Handling:
In `onRevert` or `claimRefund`, refunded amounts are transferred using `TransferHelper.safeTransfer`. Decimal mismatches result in incorrect refund amounts.

Example: USDT on Ethereum vs. BSC
- Ethereum USDT: The USDT contract (0xdAC17F958D2ee523a2206206994597C13D831ec7) uses 6 decimals (1 USDT = 1,000,000 units).
- BSC USDT: The USDT contract (0x55d398326f99059fF775485246999027B3197955) uses 18 decimals (1 USDT = 10^18 units).
A user depositing 1 USDT (1,000,000 units) on Ethereum via `depositAndCall` expects 1 USDT on BSC. If the protocol does not adjust for decimals, 1,000,000 units may be interpreted as 0.000001 USDT on BSC, causing a 1,000,000,000,000-fold error.


### Attack Path

An attacker could deposit tokens on a chain with fewer decimals (e.g., Ethereum USDT) and withdraw on a chain with more decimals (e.g., BSC USDT), exploiting the mismatch to receive inflated amounts. For example, depositing 1,000,000 units on Ethereum could yield 10^12 USDT on BSC if amounts are not normalized.

### Impact

- Financial Loss: Users could lose significant funds (e.g., 1 USDT on one chain becomes 0.000001 USDT on another) or attackers could drain funds by exploiting mismatches.
- Operational Disruption: Gas fee miscalculations lead to failed transactions, requiring manual refunds and eroding trust.
- Scalability: The issue affects any token with varying decimals across supported chains, including popular stablecoins like USDT.

The bug compromises core cross-chain functionality, with severe financial consequences and exploitable outcomes across multiple chains.
