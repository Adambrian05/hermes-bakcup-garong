# Reentrancy Vulnerability in GatewayCrossChain's claimRefund Function

## Summary
The `claimRefund` function in the GatewayCrossChain contract contains a reentrancy vulnerability due to its failure to follow the Checks-Effects-Interactions pattern. The function performs token transfers before updating critical state, allowing a malicious contract to potentially call back into the function and claim the same refund multiple times.

## Root Cause
The vulnerability exists because the `claimRefund` function updates state after making an external call:

https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/d4834a468f7dad56b007b4450397289d4f767757/omni-chain-contracts/contracts/GatewayCrossChain.sol#L582

```solidity
// External call occurs first
TransferHelper.safeTransfer(refundInfo.token, receiver, refundInfo.amount);
// State is updated after the external call
delete refundInfos[externalId];
```

This violates the Checks-Effects-Interactions pattern, creating a window where reentrancy is possible.

## Internal Pre-conditions
1. A refund has been stored in the `refundInfos` mapping
2. The refund token is either:
   - A ZRC20 token that implements callback functionality
   - A special ETH address (if the contract is modified to handle ETH correctly)

## External Pre-conditions
1. The attacker controls a malicious contract that can receive tokens
2. The attacker's contract implements either:
   - A token receive hook (for tokens with callbacks)
   - A `receive()` function (for ETH refunds)

## Attack Path
1. Attacker identifies a refund with a significant amount
2. Attacker deploys a malicious contract with reentrancy capabilities
3. Malicious contract calls `claimRefund(externalId)`
4. The function performs validation checks and proceeds to transfer tokens
5. During token transfer, control is passed to the attacker's contract via callback
6. Attacker's contract calls `claimRefund(externalId)` again
7. Since `refundInfos[externalId]` hasn't been deleted yet, the second claim passes validation
8. This process can repeat until gas limits are reached
9. Eventually, the attacker extracts multiple times the intended refund amount

## Impact
- Potential theft of multiple refunds using a single claim


## Mitigation
Implement the Checks-Effects-Interactions pattern by moving state updates before external calls:

```solidity
function claimRefund(bytes32 externalId) external {
    RefundInfo storage refundInfo = refundInfos[externalId];

    address receiver = msg.sender;
    if(refundInfo.walletAddress.length == 20) {
        receiver = address(uint160(bytes20(refundInfo.walletAddress)));
    }
    require(bots[msg.sender] || msg.sender == receiver, "INVALID_CALLER");
    require(refundInfo.externalId != "", "REFUND_NOT_EXIST");
    
    // Store values temporarily before deleting state
    address token = refundInfo.token;
    uint256 amount = refundInfo.amount;
    bytes memory walletAddress = abi.encodePacked(msg.sender);
    
    // Update state BEFORE external call
    delete refundInfos[externalId];
    
    // Make external call AFTER state is updated
    if (token == _ETH_ADDRESS_) {
        TransferHelper.safeTransferETH(receiver, amount);
    } else {
        TransferHelper.safeTransfer(token, receiver, amount);
    }
    
    emit EddyCrossChainRefundClaimed(
        externalId,
        token,
        amount,
        walletAddress
    );
}
```
