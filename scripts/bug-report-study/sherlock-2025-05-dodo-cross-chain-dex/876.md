# GatewayTransferNatives _handleFeeTransfer will not work with native token

### Summary

A core function intended to support withdrawals to native chains fails when handling the native token (Zeta token), due to incorrect fee transfer logic. This leads to reverted transactions and breaking a key part of the protocol's functionality.

### Root Cause

The withdrawToNativeChain function does not properly handle the case when the token being withdrawn is the native token (_ETH_ADDRESS_) and msg.value is sent. Specifically, the internal _handleFeeTransfer function attempts to treat the native token as a ZRC20 token by calling zrc20.transfer(...), which fails since the native token is not a contract (native token is not really the contract, but rather the convention that developers use to signal that the native token is used) and does not support the ERC-20 interface.

As the protocol is designed to allow withdrawals of Zeta (native) tokens to external chains (before what Zeta would be swapped to a supported asset), this bug results in a failure of one of the protocol’s core flows.

### Attack Path
1. Lets say that user initiated the call to withdrawToNativeChain function where zrc20 asset is set to native token (on ZetaChain its Zeta) and the msg.value and amount are equal and set to the 1000Zeta tokens
2. the _handleFeeTransferFunction will be called with arguments amount and zrc20(which is native token "address")
3. since the _handleFeeTransferFunction uses safeTransfer from transferHelper it doesnt handle the situation when zrc20 is Native token, which mean that the transfer attempt will fail.
4. function withdrawToNative chain will be unusable with native tokens because of inability to transfer the fee to EddyTreasurySafe

### Impact

If the withdrawToNativeChain function is called with a native token (msg.value is sent and zrc20 == _ETH_ADDRESS_), the call will revert because the _handleFeeTransfer function incorrectly treats the native token as a ZRC20 token and attempts to call transfer on it (even thought the native token is not really the contract, but rather the convention that developers use to signal that the native token is used). This makes it impossible for users to withdraw to a native chain using this function when dealing with the native token. As a result, protocol could loose fees (as its not possible to handle Zeta token), and users will be forced to search for alternative methods to complete their intended actions. This breaks core functionality of the contract.
