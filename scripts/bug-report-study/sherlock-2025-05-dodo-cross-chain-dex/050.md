# The `onCall` functions in `GatewayCrossChain` and `GatewayTransferNative` incorrectly handle the native ZETA token.




## Summary

The `onCall()` functions in `GatewayCrossChain` and `GatewayTransferNative` mistakenly assume they are receiving WZETA (wrapped ZETA), when in fact they are processing the native ZETA token, resulting in incorrect handling logic throughout.

The `onCall()` function assumes that all tokens sent by the Gateway caller are ZRC20 tokens, leading it to use `_handleFeeTransfer` for token transfers. However, this logic fails when the incoming token is native ZETA (not a ZRC20).
```javascript
function _handleFeeTransfer(
        address zrc20,
        uint256 amount
    ) internal returns (uint256 platformFeesForTx) {
        platformFeesForTx = (amount * feePercent) / 1000; // platformFee = 5 <> 0.5%
        TransferHelper.safeTransfer(zrc20, EddyTreasurySafe, platformFeesForTx);
    }
```
In reality, when the parameter zrc20 in onCall is WZETA, the gateway transfers the native token ZETA instead. As a result, _handleFeeTransfer will fail.  
The subsequent processing logic in onCall is also incorrect.

## Attack Path


## Impact
1. When depositing and calling ERC20 (ZETA) on the Ethereum chain, all calls will fail on the Zeta chain, rendering the functionality unusable. Additionally, users' gas fees on the Ethereum chain will be wasted.  

2. This will trigger the **onRevert()** process, and the Zeta protocol will internally consume user funds as execution fees for **onRevert()**.  

In summary, the functionality fails to work properly while also consuming user funds.

## Mitigation
The onCall function must first verify whether zrc20 is WZETA. If it is WZETA, an additional logic branch needs to be implemented for proper handling.
