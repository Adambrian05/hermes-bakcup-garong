# Revert transaction from BTC will refund funds to a random address

### Summary

__NOTE__ that the same issues exists in both contracts `GatewayTransferNative` and `GatewayCrossChain`.

When a message is created to be send to Bitcoin - `decoded.receiver` is a BTC address, which has `Bech32` format (32 bytes). This is the receiver on the BTC chain. However, when we encode the revert message on the ZetaChain, we [truncate](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L291) the value to 20 bytes and set it as  `revertMessage`. 
This is a problem because in case of revert, we will enter the first `if` branch from [onRevert](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayCrossChain.sol#L517-L532) function and sent the refunded funds to bytes(20) address representation of the receiver address from BTC, which is some unknown address.

### Root Cause

In `_handleBitcoinWithdraw` path in both ZetaChain contracts, BTC receiver address is used as a `sender`. The bytes value is truncated to 20 bytes and is written to the `RevertOptions::revertMessage`

### Internal Pre-conditions

None

### External Pre-conditions

Someone bridges to BTC and tx reverts.

### Attack Path

Described above

### Impact

Lost funds

### PoC

_No response_

### Mitigation

Don't truncate the bytes in `_handleBitcoinWithdraw` path
