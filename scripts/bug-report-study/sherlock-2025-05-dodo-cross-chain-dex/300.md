# Any External Actor will Steal Approved ZRC20 Tokens from `GatewayTransferNative` Contract

### Summary

The `withdraw` [function](https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L286) within the `GatewayTransferNative.sol` contract is declared with `public` visibility and lacks any access control modifiers, such as `onlyOwner` or a modifier restricting calls to an authorized entity like the ZetaChain Gateway itself or an internal contract function. This `public` function allows any external user account (EOA) or contract to call it.

### Root Cause

The root cause of the vulnerability is the `public` visibility of the `withdraw(bytes32 externalId, bytes memory sender, address outputToken, uint256 amount)` function in `GatewayTransferNative.sol` without any form of access control. This allows any arbitrary caller to invoke the function, which then unconditionally instructs the `GatewayZEVM` to perform a withdrawal operation using the `GatewayTransferNative` contract's funds and approvals.

### Internal Pre-conditions

1.  The `GatewayTransferNative` contract must have a non-zero balance of the specific ZRC20 token (`outputToken`) that the attacker intends to withdraw.
2.  The `GatewayTransferNative` contract must have an active allowance (set via `approve`) permitting `address(gateway)` (the ZetaChain `GatewayZEVM` contract) to spend an amount of `outputToken` greater than or equal to the `amount` specified by the attacker. This approval could be a remnant from a previous, legitimate, but incompletely processed transaction or a transaction that set an approval and then reverted.

### External Pre-conditions

1.  The attacker must identify a ZRC20 token (`outputToken`) for which the `GatewayTransferNative` contract meets the internal preconditions (balance and gateway approval).
2.  The attacker needs to know the address of this `outputToken`.

### Attack Path

1.  **Setup State:** A situation occurs where the `GatewayTransferNative` contract accumulates a balance of a ZRC20 token, say `TokenX` (e.g., 100 units). Simultaneously, due to a prior operation (e.g., a user calling `withdrawToNativeChain` which internally calls `_handleEvmOrSolanaWithdraw` or `_handleBitcoinWithdraw`), an approval is set for `address(gateway)` to spend `TokenX` from `GatewayTransferNative`'s holdings. This approval might be for the exact amount of a transaction that later failed partially, or for an amount larger than what was consumed, leaving a residual approval (e.g., an approval for 100 units of `TokenX`).
2.  **Attacker's Call:** The attacker discovers this state (e.g., by monitoring contract storage or transaction history). They then call the `public` `withdraw` function on `GatewayTransferNative.sol` with the following parameters:
    *   `externalId`: Any `bytes32` value (e.g., `0xATTACKER...`).
    *   `sender`: A `bytes` representation of an address controlled by the attacker on the target chain where they wish to receive the funds.
    *   `outputToken`: The address of `TokenX`.
    *   `amount`: The amount of `TokenX` to steal, up to the available balance and approved amount (e.g., 100 units).
3.  **Execution within `GatewayTransferNative`:** The `withdraw` function executes. Since it's `public` and has no access control, the call proceeds.
4.  **Call to ZetaChain Gateway:** The function calls `gateway.withdraw(attacker_controlled_sender_bytes, 100, TokenX_address, revertOptions)`.
5.  **Withdrawal by Gateway:** The ZetaChain `GatewayZEVM` (`gateway`) receives this call. It verifies that:
    *   `GatewayTransferNative` (the caller of `gateway.withdraw` in this context, from the perspective of token movement) has at least 100 units of `TokenX`.
    *   `GatewayTransferNative` has approved `address(gateway)` to spend at least 100 units of `TokenX`.
    Since both internal preconditions are met, the `GatewayZEVM` proceeds.
6.  **Funds Siphoned:** The `GatewayZEVM` debits 100 units of `TokenX` from `GatewayTransferNative`'s ZRC20 balance on ZetaChain and initiates the process to credit these tokens to the attacker's specified `sender` address on the designated target chain.
7.  **Impact Realized:** The attacker successfully steals 100 units of `TokenX` from the `GatewayTransferNative` contract.


### Impact

*   **Direct Loss of Funds:** Any ZRC20 tokens held by the `GatewayTransferNative` contract that have an active approval for the `gateway` can be stolen by an attacker. This leads to direct financial loss for the protocol, potentially including user funds that were in transit or fees collected.
*   **Operational Disruption:** If significant funds are drained, the contract may be unable to fulfill its intended cross-chain operations, process refunds, or pay necessary fees, leading to failed transactions for legitimate users.
