# Inconsistent Native ETH Handling in Cross-Chain Transfers

### Summary

The `withdrawToNativeChain` function allows users to transfer ETH but fails to properly validate that `msg.value` matches the specified amount parameter when ETH is being used, creating inconsistencies in the transaction flow.

### Root Cause

The `GatewayTransferNative` contract supports cross-chain transfers of tokens, including native ETH (represented as `_ETH_ADDRESS_`). When a user initiates a withdrawal of a standard token, the contract correctly verifies the transfer of tokens from the user to the contract. However, when handling native ETH, the contract does not verify that the actual ETH sent in the transaction (`msg.value`) matches the amount parameter specified by the user.

This inconsistency can create several issues:

1. If a user provides `amount > msg.value`, the contract would try to process more ETH than was actually received, likely causing transaction failure at later stages.
2. If a user provides `amount < msg.value`, the excess ETH would remain in the contract without proper accounting.

The contract also forwards `msg.value` directly to the DODO router in the `_doMixSwap` function, regardless of whether native ETH is involved in the swap, which could cause unexpected behavior or transaction failures.

### Attack Path

1. The `withdrawToNativeChain` function accepts a parameter `zrc20` which can be the special address `_ETH_ADDRESS_` to indicate native ETH.
2. When zrc20 is not `_ETH_ADDRESS_`, the function correctly verifies token transfers with `transferFrom`.
3. When `zrc20` is `_ETH_ADDRESS_`, no verification is performed to ensure that `msg.value` matches amount.
4. The amount parameter is then used for fee calculations and swap operations, not the actual received ETH (`msg.value`).
5. When `_doMixSwap` is called, it always forwards `msg.value` to the DODO router, which is incorrect if the swap doesn't involve native ETH.

### Impact

Impact: High - Inconsistent ETH handling can lead to transaction failures, loss of user funds, or locked ETH in the contract.

Likelihood: Medium - The issue requires specific circumstances but could be triggered by user error or intentionally.

### Mitigation

Add proper validation when handling native ETH to ensure consistency between msg.value and amount. Also, only forward ETH to the router when it's actually needed for the swap.
```solidity
function withdrawToNativeChain(
    address zrc20,
    uint256 amount,
    bytes calldata message
) external payable {
    if(zrc20 == _ETH_ADDRESS_) {
        require(msg.value == amount, "SENT ETH MUST MATCH AMOUNT");
    } else {
        require(IZRC20(zrc20).transferFrom(msg.sender, address(this), amount), "INSUFFICIENT ALLOWANCE: TRANSFER FROM FAILED");
    } 

    // ... rest of function
}

function _doMixSwap(
    bytes memory swapData, 
    uint256 amount, 
    MixSwapParams memory params
) internal returns (uint256 outputAmount) {
    if (swapData.length == 0) {
        return amount;
    }

    if (params.fromToken != _ETH_ADDRESS_) {
        IZRC20(params.fromToken).approve(DODOApprove, amount);
        return IDODORouteProxy(DODORouteProxy).mixSwap(
            // ... parameters
        );
    } else {
        // Native ETH case
        return IDODORouteProxy(DODORouteProxy).mixSwap{value: amount}(
            // ... parameters
        );
    }
}
```
