# An incorrect fee­-aware amount mismatch in GatewayTransferNative.onCall


### Summary

An **incorrect fee­-aware amount mismatch** in `GatewayTransferNative.onCall` will cause **a token-swap revert and permanent lock of assets** for **end-users** as a relayer (the **actor**) submits a swap message whose `fromTokenAmount` equals the pre-fee deposit, triggering a failure path that strands the tokens inside the contract.

### Root Cause

* In **`GatewayTransferNative.sol:onCall`** the platform fee is transferred out **before** calling `_doMixSwap`, yet the **full gross `amount`** is still passed both to `approve()` and (via `params.fromTokenAmount`) to `IDODORouteProxy.mixSwap`.

* https://github.com/sherlock-audit/2025-05-dodo-cross-chain-dex/blob/main/omni-chain-contracts/contracts/GatewayTransferNative.sol#L370-L396
* After the fee transfer the contract balance is `amount – fee`, so `mixSwap` reverts when it tries to pull the full `amount`.

---

### Internal Pre-conditions

1. **Owner** sets `feePercent > 0`, so a non-zero fee is always skimmed.
2. **GatewayZEVM** delivers exactly `amount` ZRC20 tokens to `GatewayTransferNative` and then calls `onCall`.
3. **Relayer** encodes `params.fromTokenAmount = amount` in `swapData` (default behaviour in current off-chain builder).

---

### External Pre-conditions

1. **DODO RouteProxy** is live and its `mixSwap` implementation uses `transferFrom` for the input token.
2. Target ZRC20 token obeys the ERC-20 standard (`transferFrom` reverts on insufficient allowance/balance).

---

### Attack Path

1. Relayer builds a cross-chain swap message, leaving `fromTokenAmount` equal to the gross deposit.
2. Gateway delivers the tokens and executes `onCall`.
3. `onCall` skims the fee, lowering the contract’s balance to `amount – fee`.
4. `onCall` calls `_doMixSwap` with `amount` (gross), which approves that same amount to the DODO proxy.
5. DODO proxy’s `mixSwap` tries `transferFrom(contract, amount)`.
6. Call reverts for insufficient balance; `_doMixSwap` bubbles the revert; `onCall` reverts.
7. If subsequent `onRevert` / `onAbort` handling also fails (e.g., malformed revert message) the tokens remain stuck in the contract indefinitely.


### Impact

* **Users** lose immediate access to their tokens; they may be forced to file a manual refund or depend on an admin “superWithdraw”.
* Potential loss equals **100 % of every affected swap’s gross amount**. Attack scale is limited only by liquidity routed through the contract.
* **Attacker/relayer** gains no direct funds but can create widespread denial of service and tie up user capital.


### Mitigation

**Use net amount**:

   ```solidity
   uint256 net = amount - platformFeesForTx;
   require(params.fromTokenAmount <= net, "FROM_AMOUNT_GT_NET");
   uint256 out = _doMixSwap(decoded.swapData, net, params);
   ```
